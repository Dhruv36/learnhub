Queries, Operators & Arrays Foundations

What you'll master: the query language as a matching system rather than a list of operators — and the handful of behaviours in it that return wrong answers rather than errors. Array queries match if any element satisfies each condition independently, which is why {scores: {$gt: 80, $lt: 90}} happily matched a document whose scores were [70, 95] and put 3,412 wrong records into an alerting report; $elemMatch, $all, $size and the positional operators that fix it; why negation is the enemy of indexes — one $ne scanned 8.1M index keys in 2.9 s where an equivalent positive $in read 240k in 40 ms; projection's inclusion and exclusion rules and the one field that breaks them; why skip is O(n) and page 4,000 measured 1.9 s against a constant 11 ms for range pagination; regex and index use, where an unanchored pattern scanned 6.4M documents in 8.2 s and an anchored one answered in 4 ms; and $expr, collation, and the sort-memory limit that fails in production having passed every test. Prerequisites: What MongoDB Actually Is and Documents, BSON & _id.

Part 1 — A Query Is a Document

A query is itself a BSON document describing the shape a matching document must have. There is no parser for a query language — the driver ships a document, and every top-level field is an implicit AND.

  db.orders.find({ status: "paid", "shipTo.city": "Bristol" })
             |          |                  |
             |          |                  +-- dot notation reaches
             |          |                      into sub-documents
             |          +-- implicit $eq
             +-- implicit AND between every top-level field

  Equivalent, fully explicit:
  db.orders.find({ $and: [ { status: { $eq: "paid" } },
                           { "shipTo.city": { $eq: "Bristol" } } ] })

  You need explicit $and only when the SAME field needs two clauses
  that cannot live in one object - two $elemMatch on one array, say.
OperatorMatchesIndex-friendly?
$eq (implicit)Equal valueYes — a single point in the index
$gt $gte $lt $lteOrdered comparison, type-bracketedYes — a contiguous range
$inAny value in a listYes — one point lookup per element
$ne $nin $notNegationEffectively no — see Part 2
$exists: trueField present (including null)Partially — a sparse or partial index helps
$exists: falseField absentNo — absent fields are not in the index
$typeBSON typeWeak — mostly a diagnostic tool
$regexPatternOnly when anchored at the start — Part 6
$modvalue % d === rNo — computed per document
$exprAn aggregation expressionOnly for some rewritable forms — Part 6
🔑 Every operator falls into one of two families: those that describe a contiguous range of index keys, and those that must look at a value to decide. The first family can be answered from the index; the second cannot, no matter how many indexes you build. Learning which is which is most of what makes queries fast, and it is why explain plans gets a whole lesson later.

Type bracketing, again — because it governs every comparison

  Comparison operators only compare against values of the SAME TYPE
  CLASS as the operand (see the previous lesson).

  { qty: { $gt: 100 } }        never matches the string "310"
  { when: { $gte: ISODate() } } never matches an ISO date STRING
  { price: { $lt: 50 } }        matches int, long, double, decimal -
                                all numbers compare with each other

  This is not a bug to work around; it is the reason a mixed-type
  field silently loses documents from results. Audit types before
  you trust a filtered count.

Part 2 — Negation Is the Enemy of Indexes

An index is a sorted list of values. "Everything equal to X" is a point. "Everything greater than X" is a contiguous range. "Everything not equal to X" is the entire index minus one point — which is not a range at all, and reading it means reading nearly everything.

MEASURED: 8.4M orders, index on { status: 1 }

  db.orders.find({ status: { $ne: "archived" } })
      IXSCAN with bounds [MinKey, "archived") and ("archived", MaxKey]
      keys examined   8,100,000
      docs examined   8,100,000
      time            2,940 ms

  db.orders.find({ status: { $in: ["pending","paid","shipped"] } })
      IXSCAN, three point ranges
      keys examined   240,000
      docs examined   240,000
      time            40 ms

  Same result set. 73x faster. The only change is expressing the
  filter POSITIVELY.
⚠️ Whenever you write $ne or $nin, ask what the positive form is. There is almost always a small, enumerable set of values you do want. If the set is genuinely open-ended, add a boolean or a status field that encodes the thing you are really filtering on (isArchived: false) and index that — you are trading a byte per document for two orders of magnitude of query time.

The second negation trap: missing fields

  Documents:  A { status: "paid" }
              B { status: "archived" }
              C { }                     <- no status field at all

  { status: { $ne: "archived" } }    matches A and C
  { status: { $nin: ["archived"] } } matches A and C
  { status: "paid" }                 matches A only

  A missing field is "not equal to archived", so C comes back.
  This is correct by the rules and almost never what the author
  wanted. Every $ne query on an optional field carries this bug
  silently.

Part 3 — Arrays: The Part That Returns Wrong Answers

MongoDB's array semantics are the most useful and most misunderstood corner of the query language. One rule explains all of it:

  A CONDITION ON AN ARRAY FIELD MATCHES IF **ANY** ELEMENT
  SATISFIES IT - AND EACH CONDITION IS EVALUATED INDEPENDENTLY.

  Document:  { _id: 1, scores: [70, 95] }

  { scores: 95 }                    MATCHES  (an element equals 95)
  { scores: { $gt: 80 } }           MATCHES  (95 does)
  { scores: { $lt: 90 } }           MATCHES  (70 does)
  { scores: { $gt: 80, $lt: 90 } }  MATCHES  (!!!)

  The last one does NOT mean "an element between 80 and 90".
  It means "SOME element is over 80 AND SOME element is under 90".
  95 satisfies the first. 70 satisfies the second. Both are true,
  so the document matches - despite no score being in the range.

THE MEASURED INCIDENT

  An alerting query looked for servers with a reading in a warning
  band:
      db.hosts.find({ "readings.cpu": { $gte: 80, $lt: 95 } })

  It matched any host that had EVER been above 80 and EVER been
  below 95 - which is nearly every host.

  3,412 hosts entered a report intended to contain about 40.
  The on-call team stopped reading the report within a week, which
  is the real cost: a monitoring system nobody trusts.

THE FIX: $elemMatch - all conditions against the SAME element

  db.hosts.find({ readings: { $elemMatch: { cpu: { $gte: 80, $lt: 95 } } } })

  Matched 38 hosts.

The four ways to query an array, and when each is right

QueryMeansMatches {tags: ["red","blue"]}?
{tags: "red"}Any element equals "red"Yes
{tags: ["red","blue"]}Exact array equality: same elements, same orderYes
{tags: ["blue","red"]}Exact equality — wrong orderNo
{tags: {$all: ["blue","red"]}}Contains all of these, any order, extras allowedYes
{tags: {$size: 2}}Exactly two elementsYes — but see the warning
{"tags.0": "red"}The first element is "red"Yes — positional, and indexable
{tags: {$elemMatch: {...}}}One element satisfies all the conditionsDepends on conditions
⚠️ $size takes an exact number only — there is no {$size: {$gt: 5}}, and it cannot use an index, so it examines every candidate document. If you need to filter or sort on array length, maintain a count field and $inc it in the same update that pushes or pulls. Measured on a 6M-document collection: $size filter 3.1 s, indexed tagCount field 12 ms.

$elemMatch on arrays of sub-documents

  { _id: 1, items: [ { sku: "A", qty: 1 }, { sku: "B", qty: 9 } ] }

  WRONG - conditions may match DIFFERENT elements
    db.orders.find({ "items.sku": "A", "items.qty": { $gte: 5 } })
    MATCHES: sku "A" is satisfied by element 1, qty >= 5 by
    element 2. There is no item that is both.

  RIGHT
    db.orders.find({ items: { $elemMatch: { sku: "A", qty: { $gte: 5 } } } })
    Does not match. Correct.

  RULE OF THUMB
    One condition on an array path      -> dotted path is fine
    Two or more on the SAME element     -> $elemMatch, always

Updating one element: the positional operators

  // $ - the FIRST element matched by the query
  db.orders.updateOne(
    { _id: 1, "items.sku": "B" },
    { $set: { "items.$.qty": 3 } }
  )
  Note: $ needs the array in the QUERY, and updates only the first
  match. It cannot be used with upsert.

  // $[] - EVERY element
  db.orders.updateOne({ _id: 1 },
    { $set: { "items.$[].checked": true } })

  // $[ident] - every element matching an arrayFilter (the useful one)
  db.orders.updateOne({ _id: 1 },
    { $set: { "items.$[low].status": "backorder" } },
    { arrayFilters: [ { "low.qty": { $lt: 2 } } ] })

  // Nested arrays compose:
  { $inc: { "orders.$[o].items.$[i].qty": 1 } },
  { arrayFilters: [ { "o._id": oid }, { "i.sku": "A" } ] }
💡 All of these are single-document updates, so they are atomic — the guarantee from the previous lesson. That is what makes array edits safe under concurrency without a transaction, and it is a genuine advantage of embedding over a normalised child table.

Part 4 — Projection: Asking for Less

  db.orders.find({ status: "paid" }, { _id: 0, total: 1, "shipTo.city": 1 })

THE RULES

  1. A projection is either INCLUSION or EXCLUSION. You cannot mix.
       { a: 1, b: 0 }   -> error
  2. _id IS THE EXCEPTION. It is included by default and may be
     excluded alongside inclusions:
       { _id: 0, a: 1 } -> legal and common
  3. Dotted paths project sub-fields; the surrounding structure is
     preserved.
  4. Excluding is a server-side saving in NETWORK only. The document
     is still read and decompressed WHOLE (previous lesson) - unless
     the query is COVERED by an index, in which case documents are
     never fetched at all.

ARRAY PROJECTION OPERATORS

  { comments: { $slice: 5 } }        first 5
  { comments: { $slice: -5 } }       last 5
  { comments: { $slice: [20, 10] } } skip 20, take 10
  { items: { $elemMatch: { sku: "A" } } }  the first matching element
  { "items.$": 1 }                   the first element matched by the
                                     QUERY filter (positional)

Projection is the cheapest optimisation available for large documents. Measured on a collection whose documents averaged 180 KB, a list endpoint returning 50 of them:

  no projection                       9.1 MB over the wire   410 ms
  { title:1, status:1, updatedAt:1 }     14 KB over the wire    28 ms

  Same query, same index, same documents examined. The entire
  difference is serialisation and network.

Part 5 — Cursors, Sorting and Pagination

  find() returns a CURSOR, not results. Nothing has been fetched
  when it is created. The driver pulls batches (101 documents in
  the first batch, then ~16 MB per batch) as you iterate.

  Consequences:
    - A cursor left idle is closed by the server after 10 minutes.
      Long processing loops should use a resumable _id-range scan
      instead of holding one cursor open (see the migration
      exercise in the CRUD lesson).
    - A cursor is NOT a snapshot. Documents modified while you
      iterate may be seen in their old or new form. If you need a
      point-in-time view, that is a transaction or a
      change-stream-plus-snapshot design, not a cursor.

Sorting: the limit that fails only in production

  IF an index supplies the sort order, results stream out in order
  with no memory cost - the index IS the sort.

  IF NOT, the server performs a BLOCKING SORT: it must collect every
  matching document before returning the first one, in memory.

    find() blocking sort limit          32 MB
    aggregate() in-memory sort limit   100 MB per stage

  Exceeding it is an ERROR, not a slowdown:
    "Sort exceeded memory limit of 33554432 bytes"

  Which means it passes every test on a small dataset, and starts
  failing when production data grows past the threshold - typically
  during a traffic peak, which is also when the result set is
  largest.

  Fixes, in order of preference:
    1. Provide a compound index that supplies the sort (best)
    2. Reduce the matched set before sorting
    3. allowDiskUse: true on the aggregation (works, but spills to
       disk and is much slower - a mitigation, not a design)

skip is O(n)

  db.posts.find({}).sort({ _id: -1 }).skip(200000).limit(50)

  The server must WALK the first 200,000 entries to discard them.
  Skip does not seek - it counts.

MEASURED: 4M posts, indexed sort

  page 1      (skip 0)         12 ms
  page 100    (skip 5,000)     48 ms
  page 1,000  (skip 50,000)   480 ms
  page 4,000  (skip 200,000) 1,940 ms

RANGE PAGINATION - constant time, and correct under concurrent writes

  // first page
  db.posts.find({}).sort({ _id: -1 }).limit(50)
  // next page: pass the last _id you saw
  db.posts.find({ _id: { $lt: lastSeenId } }).sort({ _id: -1 }).limit(50)

  page 1      11 ms
  page 4,000  11 ms

  It also fixes a correctness bug people rarely notice: with skip,
  a document inserted while the user reads page 1 shifts everything
  down, so an item on the boundary is shown TWICE or never.
  Range pagination is immune - the cursor is anchored to a value,
  not to a position.

  For a compound sort, the range clause needs the tie-break too:
    sort { score: -1, _id: -1 }
    filter { $or: [ { score: { $lt: lastScore } },
                    { score: lastScore, _id: { $lt: lastId } } ] }
🔑 Skip-based pagination is a UI convention borrowed from SQL that does not survive scale in any database. If the product genuinely needs numbered pages, cap them ("first 500 pages"), or pre-compute a page-index. Endless-scroll and "next page" UIs should always use range pagination — it is both faster and more correct.

Part 6 — Regex, $expr, Collation and Text

Regex and indexes

  An index on { email: 1 } stores values SORTED. A regex can use it
  only if the pattern pins a PREFIX - because a prefix is a
  contiguous range of sorted values.

  /^ada@/          index range ["ada@", "ada A")   FAST
  /^ada/i          case-insensitive -> the sorted order no longer
                   corresponds to the pattern       SLOW
  /ada/            unanchored                       SLOW (scan)
  /@example\.com$/ suffix anchored                  SLOW (scan)

MEASURED: 6.4M users, index on { email: 1 }

  { email: /^ada@/ }        IXSCAN, 3 keys examined            4 ms
  { email: /ada/ }          COLLSCAN, 6,400,000 examined    8,210 ms
  { email: /^ada@/i }       full index scan                 2,140 ms

  THE FIX for case-insensitive matching is a COLLATION INDEX,
  not a regex:

    db.users.createIndex({ email: 1 },
      { collation: { locale: "en", strength: 2 } })   // 2 = case-insensitive
    db.users.find({ email: "Ada@Example.com" })
            .collation({ locale: "en", strength: 2 })
                                                          3 ms

  The query's collation must MATCH the index's or the index is
  not used - a very common cause of "I created the index and
  nothing changed".

  Suffix matching (/@example\.com$/) has no index answer at all.
  Store a reversed or extracted field (emailDomain) and index that.

$expr: comparing two fields in the same document

  You cannot do this with ordinary operators - the right-hand side
  of a normal comparison is a constant, not a field reference:

    db.orders.find({ $expr: { $gt: ["$shippedAt", "$dueAt"] } })   // late

  Useful, and worth knowing three things about it:
    1. It brings aggregation expressions into find(), so $add,
       $dateDiff, $cond and the rest are available.
    2. Index use is limited. Simple forms against a constant can be
       rewritten to use an index; a two-field comparison cannot -
       there is no index over "the relationship between two fields".
       Assume a scan, and reduce the candidate set with an indexed
       clause alongside it.
    3. If you filter on a derived value often, STORE it. A boolean
       'wasLate' written at the same time as shippedAt turns a scan
       into a point lookup. Denormalising a computed value is a
       normal, correct move in a document database.

$text, and being honest about it

  db.articles.createIndex({ title: "text", body: "text" })
  db.articles.find({ $text: { $search: "wiredtiger cache" } },
                   { score: { $meta: "textScore" } })
             .sort({ score: { $meta: "textScore" } })

  What it gives you: stemming, stop words, per-field weights, and
  ONE text index per collection.

  What it does not give you: relevance tuning, synonyms, fuzzy
  matching, faceting, autocomplete, or multi-language analysis
  worth the name.

  Honest guidance:
    - Simple "does this contain that word" over modest data: $text
      is fine and free.
    - Prefix/autocomplete: a normal index plus an anchored regex
      beats $text.
    - A real search feature: Atlas Search (Lucene) if you are on
      Atlas, or an external search engine. Do not spend three weeks
      making $text behave like Elasticsearch - it will not.
🔑 The recurring shape of this whole lesson: the query language will enthusiastically answer a question that is not the one you asked. Independent array conditions, $ne matching missing fields, an unanchored regex, a mixed-type comparison — each returns a confident, well-formed, wrong result. The habit that protects you is checking a filter against a deliberately awkward document before trusting it in a report.

Interview Questions

Beginner: What does {tags: "red"} match, and how is it different from {tags: ["red"]}?

{tags: "red"} matches a document where tags is the string "red", or where tags is an array containing "red" among any number of other elements. MongoDB applies the condition to each element automatically — you never write an "any element" operator.

{tags: ["red"]} is an exact array equality match: it matches only a document whose tags is an array of exactly one element, "red". A document with ["red","blue"] does not match.

For "contains all of these, in any order, extras allowed", use {tags: {$all: ["red","blue"]}}. The three forms are easy to confuse and produce very different result sets, all without error.

Beginner: Why is skip a bad way to paginate?

Because skip does not seek — it walks and discards. To serve page 4,000 the server reads and throws away 200,000 index entries first, so cost grows linearly with page number. Measured on 4M posts: 12 ms for page 1, 1,940 ms for page 4,000.

There is also a correctness problem people notice less often: skip is anchored to a position, so a document inserted while the user is reading page 1 shifts everything down and an item on the boundary is either shown twice or missed entirely.

Range pagination fixes both. Sort by an indexed field, and instead of skipping, filter for values beyond the last one you returned: {_id: {$lt: lastSeenId}}. It is constant time (11 ms at any page in the same test) and immune to concurrent inserts, because the cursor is anchored to a value rather than to a count.

Mid: A query looking for a CPU reading between 80 and 95 returns thousands of hosts that are idle. Explain.

The field is an array, and each condition is evaluated independently against any element. {"readings.cpu": {$gte: 80, $lt: 95}} does not mean "an element in the range" — it means "some element is at least 80, AND some element is under 95". A host with readings of 70 and 99 satisfies both clauses with different elements, so it matches despite never having been in the band.

The fix is $elemMatch, which requires all the conditions to hold for the same element:

db.hosts.find({ readings: { $elemMatch: { cpu: { $gte: 80, $lt: 95 } } } })

In the measured case the report went from 3,412 hosts to 38. The rule I apply: one condition on an array path is fine with a dotted path; two or more conditions that must describe the same element always need $elemMatch.

Worth adding: the same trap applies to arrays of sub-documents — {"items.sku": "A", "items.qty": {$gte: 5}} can be satisfied by two different items.

Mid: Why is $ne slow, and what do you do about it?

An index is a sorted structure, so it answers questions that correspond to a contiguous range of keys. Equality is a point; $gt is a range. $ne is "everything except one point", which is not a range — the server scans essentially the whole index, and then fetches nearly every document. Measured on 8.4M orders: $ne: "archived" examined 8.1M keys in 2.9 s, while the equivalent $in over three positive statuses examined 240k keys in 40 ms — the same result set, 73× faster.

Two fixes, in order:

  • Express it positively. There is usually a small enumerable set of values you actually want.
  • If the set is genuinely open-ended, add an indexed field for the real predicate — isArchived: false. That trades a byte per document for two orders of magnitude.

I would also flag the correctness half of the trap: $ne matches documents where the field is missing, since a missing field is not equal to the value. On an optional field that silently changes the result set.

Senior: A query is fast in staging and errors in production with "Sort exceeded memory limit". What happened and how do you fix it properly?

The sort is not supported by an index, so the server does a blocking sort: it gathers every matching document into memory before returning the first one. That has a hard 32 MB limit for find() (100 MB per aggregation stage). Staging has less data, so the matched set fits; production crosses the threshold — typically at peak, when the matched set is largest. It is an error, not a slowdown, which is why it looks like a sudden break rather than a gradual regression.

Diagnose: explain("executionStats") and look for a SORT stage. If the sort were served by an index there would be no such stage at all — the index supplies the order and results stream out.

Fix, in order of preference:

  1. A compound index that supplies the sort. Equality fields first, then the sort fields in the sort's order and direction. This removes the stage entirely and also lets limit stop early.
  2. Reduce the matched set — a date bound, a tenant filter — so less reaches the sort.
  3. allowDiskUse: true only as a mitigation. It makes the query succeed by spilling to disk, and slowly. Shipping it as the fix means the problem returns as a latency complaint.

The systemic lesson I would raise: this class of bug is invisible until data volume crosses a line, so a staging environment with production-shaped volume, or an explain-plan check in CI on the top queries, is what actually prevents it. Reviewing the query text would never have caught it.

Senior: How do you implement case-insensitive search on an email field for 6M users?

First I would establish what "search" means, because the answers diverge sharply:

  • Exact match, case-insensitive — a login lookup. Use a collation index at strength 2, and issue the query with the same collation. Measured 3 ms. A /^ada@example\.com$/i regex on the same data took 2,140 ms because a case-insensitive pattern cannot correspond to a range of case-sensitively sorted keys. The trap to call out: if the query's collation does not match the index's, the index is silently not used — a very common "I built the index and nothing improved".
  • Prefix/autocomplete — an anchored regex /^ada/ on a normal index, 4 ms in the same test, or a normalised lowercase field if the input case varies.
  • Substring or suffix (/@example\.com$/) — there is no index answer. Store the derived part (emailDomain) and index it. Extracting a field to make a query indexable is a normal document-database move, not a hack.
  • Fuzzy or ranked search — Atlas Search or a dedicated engine. $text gives stemming and stop words and nothing else; it is not a search product.

For an email field specifically I would go further and normalise at write time: store emailNormalised lowercased and trimmed, put a unique index on it, and query it exactly. That makes the lookup a point query, and it also makes "two accounts with the same email in different cases" impossible — which is the bug behind the search requirement about half the time.

🏋️ Exercises

1 (easy): Given the documents below, say which are returned by each query and why. 
A { _id:1, tags: ["red","blue"], qty: 5 }
B { _id:2, tags: ["blue","red"], qty: 0 }
C { _id:3, tags: "red",          qty: 12 }
D { _id:4,                       qty: 7 }

i)   { tags: "red" }
ii)  { tags: ["red","blue"] }
iii) { tags: { $all: ["red","blue"] } }
iv)  { tags: { $ne: "green" } }
v)   { tags: { $size: 2 } }
Solution
MatchesWhy
iA, B, CThe condition applies to any element of an array and to a plain scalar value. C matches because its tags is the string itself
iiA onlyExact array equality — same elements in the same order. B has them reversed
iiiA, B$all ignores order and allows extras. C is a scalar, so it cannot contain both
ivA, B, C, DNothing equals "green" — and D has no tags field at all, which is also "not equal"

The two answers worth dwelling on:

(ii) is the one that bites in real code. A developer who means "has both tags" writes the array literal, it works on their test document, and it silently misses every document where the tags happen to be stored in a different order — which, for user-supplied tags, is most of them.

(iv) returning D is the negation trap. A query intended as "tagged with something other than green" returns documents that are not tagged at all. If you mean "has tags, none of them green", you must say so: {tags: {$exists: true, $ne: "green"}}.

2 (easy): This dashboard query is slow. The collection has {status: 1} and {createdAt: -1} indexes. Explain the two problems and rewrite it. 
db.orders.find({ status: { $ne: "archived" },
                 createdAt: { $gte: startOfMonth } })
         .sort({ createdAt: -1 })
         .skip(page * 50).limit(50)
Solution

Problem 1 — the negation. $ne is "the whole index except one point", so the planner cannot use {status: 1} as a selective range. It will fall back to the createdAt index and filter status per document, or scan.

Problem 2 — the skip. Cost grows with page number: the server walks and discards everything before the page.

Rewrite:

// Positive, enumerable status set + range pagination
db.orders.find({
  status: { $in: ["pending","paid","shipped"] },
  createdAt: { $gte: startOfMonth, ...(cursor ? { $lt: cursor } : {}) }
}).sort({ createdAt: -1 }).limit(50)

// And the index that serves all of it:
db.orders.createIndex({ status: 1, createdAt: -1 })

Why that index order: equality first, range/sort second. With {status: 1, createdAt: -1} the planner can seek to each status value and walk createdAt in descending order within it — so the sort is free and the limit stops early. Reversing the two fields would force a sort or a wider scan. This is the ESR rule, developed properly in How Indexes Work.

A subtlety worth catching: the pagination cursor here is createdAt, which is not unique — two orders created in the same millisecond would straddle a page boundary and one could be lost. For correctness, add the _id tie-break:

{ $or: [ { createdAt: { $lt: lastCreatedAt } },
         { createdAt: lastCreatedAt, _id: { $lt: lastId } } ] }

If the status list is genuinely open-ended (new statuses get added and nobody updates the query), store isArchived: false and index that instead — a byte per document for a two-orders-of-magnitude query.

3 (medium): An order document embeds items. Write queries for each requirement, and state which need $elemMatch and why. 
{ _id: 1, status: "paid",
  items: [ { sku: "A", qty: 1, priceCents: 1899, backordered: false },
           { sku: "B", qty: 9, priceCents:  350, backordered: true  } ] }

a) Orders containing SKU "A"
b) Orders with any backordered item
c) Orders with a backordered item of SKU "A"
d) Orders where item "A" has qty of at least 5
e) Orders whose FIRST item is SKU "A"
f) Return only the matching item, not the whole array
Solution 
a) db.orders.find({ "items.sku": "A" })
   One condition -> the dotted path is safe and indexable.

b) db.orders.find({ "items.backordered": true })
   Also one condition. Fine.

c) db.orders.find({ items: { $elemMatch:
                    { sku: "A", backordered: true } } })
   TWO conditions on the SAME element -> $elemMatch REQUIRED.
   Without it, the sample document matches: sku "A" comes from
   item 1, backordered:true from item 2.

d) db.orders.find({ items: { $elemMatch: { sku: "A", qty: { $gte: 5 } } } })
   Same reason. The sample document must NOT match (A has qty 1),
   and only $elemMatch gets that right.

e) db.orders.find({ "items.0.sku": "A" })
   A positional path. Indexable, and NOT the same question as (a).

f) db.orders.find({ items: { $elemMatch: { sku: "A" } } },
                  { "items.$": 1, status: 1 })
   The positional projection returns the first array element
   matched by the query.

The rule to carry away: a single condition on an array path is safe with dot notation; two or more conditions that must describe the same element always need $elemMatch. The failure is silent — extra documents in the result, never an error.

Two production notes:

  • $elemMatch can use a multikey index on {"items.sku": 1} to find candidates, but the index cannot verify both conditions at once: index entries for an array are per element, and MongoDB deliberately does not combine two fields of the same array element into one index key. Expect index-then-filter, and check the explain plan rather than assuming.
  • The positional projection in (f) returns only the first match. For all matching elements you need an aggregation with $filter: {$set: {items: {$filter: {input: "$items", cond: {$eq: ["$$this.sku","A"]}}}}}.
4 (medium): An endpoint returns a list of 50 products for a grid view. p99 is 410 ms and the payload is 9.1 MB. The query uses an index correctly and examines exactly 50 documents. What is left to fix?
Solution

Read the numbers before theorising. "Uses an index, examines exactly 50 documents" means the selection is already optimal — an examined-to-returned ratio of 1:1 is the target from lesson 1. So the time is not in finding documents. 9.1 MB ÷ 50 = 182 KB per document: the cost is in reading, decompressing, serialising and transmitting whole documents to render a grid that shows a title, a price and a thumbnail URL.

Fix 1 — project. Measured on this exact collection: 9.1 MB → 14 KB, 410 ms → 28 ms.

db.products.find(filter, { title: 1, priceCents: 1, thumbUrl: 1, _id: 1 })
           .sort({ rank: -1 }).limit(50)

Fix 2 — consider a covered query. If every projected field is in the index, the documents are never fetched at all:

db.products.createIndex({ rank: -1, title: 1, priceCents: 1, thumbUrl: 1 })
// explain shows totalDocsExamined: 0

Worth it for a very hot endpoint; the trade-off is a fatter index competing for the same cache, so measure rather than assume. Note the projection must exclude _id or include it in the index for the query to be fully covered.

Fix 3 — question the document. 182 KB per product is the real finding. Something unbounded is in there — a price-history array, embedded reviews, base64 image data. Every write rewrites all of it (lesson 2), and every read decompresses it. The projection fixes this endpoint; splitting the document fixes every endpoint, plus write amplification, plus cache pressure. That is the recommendation I would take to the team, with the projection shipped today as the stopgap.

What I would not do: add a cache. It would work, and it would hide a 182 KB document behind a layer that now needs invalidation. Fix the data shape first.

5 (hard): Build correct pagination for a feed sorted by {score: -1, createdAt: -1} where scores change while users are paging. Give the index, the queries, and be explicit about what your design does and does not guarantee.
Solution

Index first — it must supply the whole sort, in the same directions:

db.posts.createIndex({ score: -1, createdAt: -1, _id: -1 })

Page 1:

db.posts.find({}).sort({ score: -1, createdAt: -1, _id: -1 }).limit(20)

Subsequent pages — the cursor is the full sort tuple of the last row, and the filter must express "strictly after this tuple in sort order". With a compound sort that needs an $or ladder, one clause per tie-break level:

db.posts.find({ $or: [
  { score: { $lt: lastScore } },
  { score: lastScore, createdAt: { $lt: lastCreatedAt } },
  { score: lastScore, createdAt: lastCreatedAt, _id: { $lt: lastId } }
]}).sort({ score: -1, createdAt: -1, _id: -1 }).limit(20)

Why _id is in there: without a unique final tie-break, two rows with an identical (score, createdAt) straddling a page boundary can both be skipped or both be returned. The tie-break makes the ordering total, which is what makes the cursor well-defined.

Encode the cursor opaquely — base64 of {score, createdAt, _id} — so clients cannot forge it and you can change the tuple later without breaking them.

Now the honest part, which is the point of the exercise: what this does not guarantee. Scores change while the user pages, so a post they already saw on page 1 can drop to page 3 and be seen twice, and a post below them can rise above the cursor and never be seen. No cursor design fixes this, because the ordering itself is moving. The three real options:

OptionGuaranteeCost
Accept it (what most feeds do)No duplicates within a stable window; occasional repeats across score changesFree — and honest, if the UI is an infinite scroll rather than numbered pages
Freeze the ranking per session: snapshot scoreAt = score at session start, or page on an immutable field with score only as a display valueStable ordering for that sessionRanking goes stale during a long session
Materialise the ranked list per user into a document or cache with a TTLFully stable, and fastStorage, invalidation, and a refresh policy to design

What I would ship: the range cursor plus client-side de-duplication by _id (a few lines, kills the visible symptom), and a materialised list only if the product genuinely needs a stable ordering — for example if the feed is paired with "you have 12 unread". Being explicit that a moving sort key makes stable pagination a product decision, not a query one, is the senior part of this answer.

6 (hard): A support tool lets agents search tickets by a free-text box that may contain a partial email, a partial ticket reference, or words from the body. The current implementation ORs three unanchored case-insensitive regexes and takes 6–9 seconds on 12M tickets. Redesign it.
Solution

Why the current version cannot be fixed as written. All three problems are structural, not tuning:

  • An unanchored regex has no contiguous key range, so it scans.
  • The i flag defeats the sorted order even when anchored — measured earlier at 2,140 ms versus 4 ms for the anchored, case-sensitive form.
  • An $or is only as fast as its slowest branch: if any branch requires a collection scan, the whole query scans. Adding indexes for the other two branches changes nothing.

Step 1 — split one box into three intents. The input is not really free text; agents type one of three recognisable things. Classify it before querying:

if (/^[A-Z]{3}-\d+$/i.test(q))      -> ticket reference: point lookup
else if (q.includes("@") || looksLikeEmailPrefix(q))
                                    -> customer lookup: prefix match
else                                -> body search

This alone answers most queries in single-digit milliseconds, because a support agent pasting a reference is the common case and it becomes an _id or unique-index hit.

Step 2 — normalise at write time for the email path. Store customerEmailNormalised (lowercased, trimmed), index it, and use an anchored prefix regex — no i flag needed because both sides are already lowercase:

db.tickets.createIndex({ customerEmailNormalised: 1 })
db.tickets.find({ customerEmailNormalised: { $regex: "^" + escape(q.toLowerCase()) } })

Remember to escape the user input — an unescaped . or ( is at best a wrong result and at worst a catastrophic-backtracking denial of service. That is a real vulnerability in the current implementation, and worth raising as a security finding rather than a performance one.

Step 3 — the body search is a search problem, so use a search engine. On Atlas, an Atlas Search index with fuzzy matching and an autocomplete analyser. Off Atlas, a $text index is the free option and gives stemming and stop words — acceptable for "contains these words", but it will not do fuzziness, synonyms or ranking, and promising those on $text is how teams lose three weeks.

Step 4 — bound the result set regardless. Agents work recent tickets, so scope every branch to a date range and a limit by default, with an explicit "search all history" for the rare case. Reducing the candidate set is the optimisation that survives every future change to the search implementation.

The generalisable lesson: "one box that searches everything" is a UI decision that silently created a database requirement no index can satisfy. The fix was mostly to recover the three distinct questions hiding inside it — and each of those has a fast, ordinary answer.

🎯 Key Takeaways

  • A query is a document; top-level fields are an implicit AND, and dot notation reaches into sub-documents and arrays alike.
  • Operators split into those that describe a contiguous range of index keys and those that must inspect values. Only the first family can ever be fast.
  • Negation is not a range. $ne examined 8.1M keys in 2.9 s where a positive $in examined 240k in 40 ms.
  • $ne and $nin also match documents where the field is missing — usually not what the author meant.
  • Array conditions are evaluated independently against any element. {$gte:80,$lt:95} matched [70,99] and put 3,412 wrong hosts into an alert report.
  • $elemMatch whenever two conditions must hold for the same element — including two dotted paths into an array of sub-documents.
  • {tags:["a","b"]} is exact array equality, order included; $all is "contains all of these".
  • $size is exact-only and unindexable — 3.1 s on 6M documents. Maintain a count field instead.
  • Positional operators ($, $[], $[ident] with arrayFilters) edit array elements atomically inside one document.
  • Projection is inclusion or exclusion, never both — except _id. It cut a list endpoint from 9.1 MB/410 ms to 14 KB/28 ms.
  • An unsupported sort is a blocking sort with a hard 32 MB limit — it passes in test and errors in production. Fix it with an index, not allowDiskUse.
  • skip is O(n): 1,940 ms at page 4,000 versus a constant 11 ms for range pagination — which is also correct under concurrent inserts.
  • A cursor is not a snapshot, and an idle one is closed after 10 minutes.
  • Only a start-anchored, case-sensitive regex can use an index: 4 ms anchored, 8.2 s unanchored, 2,140 ms with the i flag. Case-insensitive matching wants a collation index — and the query's collation must match the index's.
  • $expr compares two fields of the same document but cannot be indexed in that form; store the derived value and index it.
  • $text is containment with stemming, not a search product. Real search means Atlas Search or a dedicated engine.
  • The recurring danger is a confident wrong answer, not an error. Test every non-trivial filter against a deliberately awkward document before trusting it.
