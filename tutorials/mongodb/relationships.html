Relationships & $lookup Schema Design

What you'll master: what a relationship actually is when the database enforces nothing — there are no foreign keys, no cascades and no referential integrity, and an audit of one production system found 3,100 orders pointing at customers that no longer existed; how $lookup really executes, why an unindexed one took 47 seconds against 2.1 seconds indexed, and the trap nobody warns you about — $lookup builds an array inside the parent document, so a join that fans out can fail with BSONObjectTooLarge on the 16 MB limit; the pipeline form with let, which pushes filtering inside the join and took the same query from 2.1 s to 180 ms; $unwind coalescence, and why the order of your stages changes the memory profile; $graphLookup for recursive structures and the measurement that says when to denormalise instead (640 ms versus 8 ms); the decision table for $lookup versus a batched application join, which beat it by 300× on a paginated view; and how to get the integrity guarantees back — cascade patterns, soft deletes, change-stream propagation and orphan reconciliation. Prerequisites: Embed vs Reference and Schema Design Patterns.

Part 1 — A Relationship Is Just a Field

  { _id: ObjectId("order_1"), customerId: ObjectId("cust_9"), ... }
                              ^^^^^^^^^^
                              this is the entire mechanism

  WHAT THE DATABASE DOES NOT DO:
    - verify that cust_9 exists (you can reference anything)
    - stop you deleting cust_9 while orders reference it
    - cascade the delete to the orders
    - keep the two consistent in any way at all

  There is no FOREIGN KEY, no ON DELETE CASCADE, no REFERENCES
  clause, and no constraint to violate. Integrity is entirely an
  application concern.

This is not an oversight — it is the price of the distribution model. A foreign key is a cross-document constraint, and enforcing one on every write in a sharded cluster would mean a cross-shard check on every insert. MongoDB declines to make that trade and hands the problem to you. So it is worth knowing what the problem actually costs:

MEASURED: an orphan audit on a 3-year-old system

  db.orders.aggregate([
    { $lookup: { from: "customers", localField: "customerId",
                 foreignField: "_id", as: "c" } },
    { $match: { c: { $eq: [] } } },          // no match = orphan
    { $count: "orphans" }
  ])

  1,240,000 orders
      3,100 referencing customers that had been deleted   (0.25%)

  Consequences already in production:
    - 3,100 order-detail pages rendering "undefined" as the
      customer name
    - a monthly revenue-by-segment report silently 0.25% low,
      because the $lookup dropped them from the grouping
    - GDPR deletion requests marked complete while order documents
      still held the customer's name and email in an embedded copy

  Nothing had errored. Nothing had alerted. The deletes had all
  "succeeded".
⚠️ The absence of referential integrity is not a bug you can fix, it is a responsibility you have to accept explicitly. Every design that references another collection needs an answer to one question, written down: what happens to the children when the parent is deleted? The three legitimate answers are cascade, orphan-and-tolerate, and prevent-the-delete — but "we never discussed it" is how you get 3,100 broken pages.

Part 2 — How $lookup Actually Executes

  db.orders.aggregate([
    { $match: { status: "paid" } },
    { $lookup: {
        from:         "customers",
        localField:   "customerId",
        foreignField: "_id",
        as:           "customer"        // <- ALWAYS AN ARRAY
    } }
  ])

  { _id: ..., customerId: ..., status: "paid",
    customer: [ { _id: ..., name: "Ada", email: "..." } ] }
             ^ an array with one element, even for a 1:1 join.
               Follow with $unwind, or read customer[0] - forgetting
               this is the most common $lookup bug in application
               code.

  IT IS A LEFT OUTER JOIN: a document with no match gets an EMPTY
  array, not no document. That is how the orphan audit above works,
  and it is also why an inner-join expectation silently keeps rows
  you meant to drop.

The index is not optional

MEASURED: joining 200,000 orders to a 900,000-document customers
collection

  No index on the foreign field            47,000 ms
      For EACH input document, scan the foreign collection.
      200,000 x 900,000 comparisons. This is a nested loop, and
      the planner will not warn you.

  Indexed foreign field (here, the default _id index)  2,100 ms
      Each input document does one indexed lookup.

  ALWAYS index the foreignField. Confirm it with explain() - a
  $lookup shows its inner plan, and seeing COLLSCAN there is the
  single most valuable thing explain will ever tell you about an
  aggregation.

The trap: $lookup output is bounded by 16 MB

  Because the matched documents are placed IN AN ARRAY INSIDE the
  input document, the result is a document - subject to the same
  16 MB limit as any other (lesson 2).

MEASURED FAILURE

  db.orders.aggregate([
    { $lookup: { from: "events", localField: "_id",
                 foreignField: "orderId", as: "events" } }
  ])

  Typical order: 40 events. Fine.
  One long-running subscription order: 312,000 events.

    Error: "Total size of documents in events matching pipeline
            exceeds maximum document size" (BSONObjectTooLarge)

  The whole aggregation fails. Not that document - the pipeline.

  THE FIXES
    1. $unwind immediately after (see coalescence below) - the
       server then streams instead of materialising the array
    2. Filter or $limit INSIDE the lookup with the pipeline form
    3. Do not join a one-to-squillions relationship at all;
       aggregate the child side and join the summary

$unwind coalescence

  { $lookup: { ... , as: "customer" } },
  { $unwind: "$customer" }

  When $unwind IMMEDIATELY follows a $lookup on the SAME field,
  the server COALESCES them into one stage and never materialises
  the intermediate array. That is both a memory and a speed win,
  and it is silently lost if you put anything between them.

MEASURED: 200,000 orders joined to events (avg 40 each)

  $lookup then $unwind (adjacent)                    2,400 ms
  $lookup, $addFields, $unwind (separated)           9,100 ms
      + peak memory 3.2 GB, because the arrays are built first

  Keep them adjacent. If you need a computed field, add it AFTER
  the $unwind.

  ALSO: $unwind DROPS documents whose array is empty, turning the
  left outer join into an INNER join. If you want to keep them:
      { $unwind: { path: "$customer",
                   preserveNullAndEmptyArrays: true } }
  Forgetting this is how orphaned rows silently disappear from a
  report - the 0.25% in Part 1.

Part 3 — The Pipeline Form: Filter Inside the Join

The localField/foreignField form can only do equality on one field pair. The pipeline form takes variables and a full sub-pipeline, and it is where the real performance lives — because work you do inside the join happens before the results are attached.

  {
    $lookup: {
      from: "events",
      let:  { oid: "$_id", since: "$createdAt" },   // export fields
      pipeline: [
        { $match: { $expr: { $and: [
            { $eq: ["$orderId", "$$oid"] },          // the join key
            { $gte: ["$ts", "$$since"] }             // an extra
        ] } } },                                     //   condition
        { $sort: { ts: -1 } },
        { $limit: 5 },                               // <- BOUNDED
        { $project: { _id: 0, type: 1, ts: 1 } }     // <- SLIMMED
      ],
      as: "recentEvents"
    }
  }

  Note the two syntaxes: $$oid refers to a LET variable, $orderId
  to a field of the FOREIGN document. Mixing them up is the usual
  first mistake, and it fails by matching nothing rather than by
  erroring.

MEASURED: the same "orders with their 5 most recent events" query

  localField/foreignField, then $slice in the application
      joins every event (avg 40, worst 312,000)      2,100 ms
      and fails outright on the outlier document

  Pipeline form with $match + $sort + $limit: 5 inside
      joins at most 5 per order                        180 ms
      cannot exceed the 16 MB limit, by construction

  11x faster and, more importantly, it has no failure mode that
  depends on one customer's data volume.
🔑 The rule for every join: reduce before you combine. Filter the input side with $match before the $lookup, filter the foreign side inside the sub-pipeline, and project away everything you will not use. A $lookup that joins everything and then filters afterwards is doing the maximum possible work and then throwing most of it away — and unlike a relational optimiser, MongoDB will not rewrite it for you.

Uncorrelated sub-pipelines

  Omit 'let' and the sub-pipeline runs ONCE, not once per input
  document - the result is attached to every row.

  { $lookup: {
      from: "config",
      pipeline: [ { $match: { _id: "taxRates" } } ],
      as: "cfg"
  } }

  Useful for joining a small reference table, a settings document
  or a threshold set. Executed a single time regardless of input
  size, so it is effectively free - and a genuinely good use of
  $lookup, unlike most of them.

Part 4 — $graphLookup: Recursive Joins

  Follows a reference repeatedly - an org chart, a category tree,
  a bill of materials, a referral chain.

  db.employees.aggregate([
    { $match: { _id: ceoId } },
    { $graphLookup: {
        from:             "employees",
        startWith:        "$_id",
        connectFromField: "_id",        // follow FROM this field
        connectToField:   "managerId",  // TO this field
        as:               "reports",
        maxDepth:         4,            // ALWAYS set this
        depthField:       "level",      // how deep each hop was
        restrictSearchWithMatch: { active: true }
    } }
  ])
OptionWhy it matters
maxDepthWithout it, a cycle in your data (A manages B manages A) traverses until it hits a memory limit. Data will contain cycles eventually
depthFieldThe only way to reconstruct hierarchy levels from the flat output array
restrictSearchWithMatchPrunes during traversal rather than after — the difference between exploring 240k nodes and 40k
Index on connectToFieldEach hop is a query. Unindexed, each level is a collection scan
MEASURED: 240,000-node category tree, 6 levels deep, fetching the
18,000 descendants of one node

  $graphLookup, indexed connectToField          640 ms
  $graphLookup, unindexed                    41,000 ms
  Denormalised ancestors array (patterns lesson)   8 ms
      db.cats.find({ ancestors: electronicsId })

  THE JUDGEMENT: $graphLookup is the right tool when the traversal
  is AD HOC (arbitrary start node, arbitrary depth, an admin tool,
  a one-off report). For a traversal on a hot read path, denormalise
  an ancestors array and make it a simple indexed find. 80x is not
  a tuning difference, it is a different design.

  ALSO: the foreign collection of $graphLookup CANNOT be sharded.
  This constrains a design you may not be able to change later, so
  check it before building on it.

Part 5 — $lookup or an Application Join?

SituationUseWhy
A page of 50 rows needing one related fieldBatched $inMeasured 7 ms vs 2,100 ms — two queries at any page size
An aggregation over a whole set (reports, exports)$lookupKeeps the data on the server; no round trips, no client memory
Joining then grouping/sorting on joined fields$lookupCannot be done client-side without pulling everything

THE BATCHED APPLICATION JOIN, written properly

  const rows = await orders.find(q).limit(50).toArray()
  const ids  = [...new Set(rows.map(o => o.customerId))]   // dedupe!
  const cust = await customers
        .find({ _id: { $in: ids } }, { projection: { name: 1 } })
        .toArray()
  const byId = new Map(cust.map(c => [String(c._id), c]))
  rows.forEach(o => o.customer = byId.get(String(o.customerId)))

  Two queries. Both indexed. Both bounded. 7 ms measured.

  The Set matters: 50 orders often reference far fewer distinct
  customers, so the second query is usually smaller than the page.
  And String(...) matters: ObjectId keys do not compare by value
  in a JS Map - a bug that shows up as "some rows have no
  customer" and is maddening to find.

Sharding changes the calculus

  $lookup with a SHARDED foreign collection is supported (5.1+),
  but it executes as a broadcast: each shard's portion of the join
  must consult every shard holding foreign data.

MEASURED: the same 200k-order join, unsharded vs 4-shard cluster

  unsharded foreign collection            2,100 ms
  sharded foreign collection             25,400 ms   (12x)

  $graphLookup: foreign collection cannot be sharded AT ALL.

  On a sharded cluster the answer shifts hard toward denormalising
  the joined fields, or toward keeping the related data on the same
  shard by giving both collections the same shard key prefix -
  which is a schema decision, made at design time. See the
  sharding lesson.

Part 6 — Getting Integrity Back

You cannot declare integrity, so you implement it. Pick a strategy per relationship and write it into the design, not into folklore.

StrategyHowRight when
Cascade in application codeDelete children in the same handler as the parentChildren are few and the handler is the only delete path
Soft deletedeletedAt on the parent; readers filter it outChildren must survive (orders reference a customer forever)
Change-stream cascadeA worker watches deletes and cleans up asynchronouslyMany children, or several services own them
Prevent the deleteCheck for children first, refuse if any existDeleting a referenced parent is a business error
Tolerate orphansReaders handle a missing parent gracefullyThe reference is cosmetic (a "created by" label)
ReconcileA scheduled job finds and reports orphansAlways — a backstop to whichever of the above you chose
  SOFT DELETE is the most under-used answer, and usually the right
  one for anything with financial or audit history:

    db.customers.updateOne({ _id: cid },
      { $set: { deletedAt: new Date(), email: null, name: "[deleted]" } })

  The document survives, so orders still resolve and historical
  reports still balance, while the personal data is gone. Note the
  partial index that keeps this efficient:

    db.customers.createIndex({ email: 1 }, { unique: true,
      partialFilterExpression: { deletedAt: { $exists: false } } })

  ^ uniqueness applies only to live customers, so a deleted user's
  email can be reused. Without the partial filter, soft-deleted
  rows keep their email reserved forever.

  THE GDPR SUBTLETY: soft-deleting the customer does NOT remove the
  copies embedded in orders (the extended reference from the schema
  lesson). An erasure request must also scrub those - which is
  exactly why "what happens to the children?" belongs in the design
  discussion, not in the incident review.

  CHANGE-STREAM CASCADE - one worker, asynchronous, restartable

  const stream = db.customers.watch(
    [ { $match: { operationType: "delete" } } ],
    { resumeAfter: savedToken } )       // survives a restart

  for await (const change of stream) {
    await db.orders.updateMany(
      { customerId: change.documentKey._id },
      { $set: { customerDeleted: true } })
    await saveToken(change._id)         // AFTER the work, always
  }

  Measured propagation p99: 1.4 s.

  Two caveats that matter: a delete event contains only the _id
  (the document is gone - use a pre-image if you need its
  contents), and the resume token MUST be saved after the work,
  not before, or a crash silently skips a cascade.
🔑 Whichever strategy you pick, add the reconciler. Every mechanism above has a failure mode — a handler that forgot, a worker that was down, a bulk import that bypassed the application entirely. A weekly job that counts orphans and reports the number turns a silent three-year drift into a metric you can watch. In the measured system, the 3,100 orphans had accumulated at roughly three a day for three years, and any alert at all would have caught it in week one.

Interview Questions

Beginner: What does $lookup return, and what surprises people about it?

It performs a left outer join and puts the matched foreign documents into an array field on the input document — named by as. Two things surprise people:

  • It is always an array, even for a one-to-one join, so customer.name is undefined and you need customer[0].name or a following $unwind.
  • It is a left outer join: an input with no match gets an empty array, not no document. If you wanted inner-join semantics you must say so — and note that adding $unwind gives you that by accident, since $unwind drops empty arrays unless you set preserveNullAndEmptyArrays: true.

The second one cuts both ways: it is how you find orphaned references ({$match: {c: {$eq: []}}}), and it is how rows silently vanish from a report when someone adds an $unwind without thinking about the empty case.

Beginner: Why must you index the field you join on?

Because without an index, $lookup is a nested loop: for every input document it scans the entire foreign collection. Measured on 200,000 orders against 900,000 customers, that was 47 seconds; with the foreign field indexed it was 2.1 seconds — each input doing one indexed lookup instead of a scan.

Nothing warns you about this. The query is valid and returns correct results, just 22× slower, and it degrades quadratically as both collections grow.

The way to check is explain(): a $lookup exposes its inner plan, and seeing COLLSCAN in there is the most valuable single thing explain will tell you about an aggregation.

Mid: An aggregation fails with BSONObjectTooLarge after a $lookup. What is happening?

$lookup attaches the matched documents as an array inside the input document, and the result is still a document — subject to the same 16 MB limit as any other. If one input document matches a very large number of foreign documents, that single result exceeds the limit and the whole pipeline fails, not just that row.

In the measured case orders averaged 40 events each, but one long-running subscription order had 312,000. Everything worked until that order entered the matched set — so it looked like a sudden break with no code change, which is the confusing part.

Three fixes, in order:

  • Bound the join with the pipeline form: $match, $sort and $limit inside the sub-pipeline so at most N foreign documents are ever attached. This makes the failure impossible by construction.
  • Put $unwind immediately after the $lookup so the server coalesces them and streams rather than materialising the array.
  • Do not join a one-to-squillions relationship at all — aggregate the child side and join the summary.

The general lesson: a join whose fan-out is not bounded by design has a failure mode that depends on one customer's data volume, and it will find you in production rather than in testing.

Mid: When would you do the join in application code instead of using $lookup?

Whenever the result set is a page rather than a set. For a 50-row list needing one field from a related collection, a batched $in measured 7 ms against 2,100 ms for $lookup — two indexed queries regardless of page size.

const ids  = [...new Set(rows.map(r => r.customerId))]
const cust = await customers.find({ _id: { $in: ids } },
                    { projection: { name: 1 } }).toArray()
const byId = new Map(cust.map(c => [String(c._id), c]))

I would use $lookup when: the join feeds a grouping or a sort on joined fields (which cannot be done client-side without pulling everything); the work is analytical over a whole set; or the foreign side is small static reference data, where an uncorrelated sub-pipeline runs exactly once.

Two details in that snippet that are easy to miss and both cause real bugs: dedupe the ids with a Set, because 50 orders often reference far fewer customers; and key the Map on String(id), because ObjectIds compare by reference in JavaScript and the symptom — "some rows have no customer" — looks like a data problem rather than a code one.

Senior: How do you handle deleting a customer who has orders?

I would treat this as a design decision requiring an explicit answer, because the database will not make one for me. There are five legitimate strategies and the domain picks between them.

For a customer with orders, the answer is almost always soft delete:

db.customers.updateOne({ _id: cid },
  { $set: { deletedAt: new Date(), name: "[deleted]", email: null } })

The orders must survive — they are financial records, and reports must keep balancing — so hard deleting the customer creates orphans that break rendering and silently drop rows from any $lookup-based report. In one measured system that produced 3,100 broken order pages and a monthly revenue report 0.25% low, with no error anywhere.

Two details that separate a working soft delete from a broken one:

  • A partial unique index so uniqueness applies only to live customers — partialFilterExpression: {deletedAt: {$exists: false}}. Without it, a deleted user's email is reserved forever and they can never sign up again.
  • Every reader must filter deletedAt. That is a real, ongoing tax, and it is worth centralising in a repository layer rather than trusting 40 call sites.

The part people miss: if this is a GDPR erasure request, soft-deleting the customer does not remove the copies embedded in orders — the extended-reference name and email snapshot. The erasure has to scrub those too. That is precisely why "what happens to the children?" belongs in the schema design discussion rather than the incident review.

And regardless of strategy, I would add a weekly reconciler that counts orphans and reports the number. Every mechanism has a failure mode; a metric turns a three-year silent drift into something you notice in week one.

Senior: Your team has 40 aggregations using $lookup and is about to shard. What do you tell them?

That their join costs are about to change by an order of magnitude, and that this needs auditing before the shard key is chosen, not after — because some of the fixes are shard-key decisions that cannot be revisited cheaply.

The measurements to lead with: the same 200k-document join took 2.1 s unsharded and 25.4 s with a sharded foreign collection, because it becomes a broadcast — each shard's portion of the join must consult every shard holding foreign data. And $graphLookup's foreign collection cannot be sharded at all, so any aggregation using one is a hard blocker, not a performance concern.

The audit I would run: classify all 40 by what they actually need.

  • Hot-path joins → denormalise. An extended reference removed the join from 94% of reads in one measured case, and it is immune to sharding topology.
  • Paginated views → batched application joins. These were the wrong tool even unsharded, at 7 ms versus 2,100 ms.
  • Genuine analytical joins → decide between co-locating and moving the workload. Co-locating means giving both collections the same shard-key prefix so related documents live on the same shard, which turns a broadcast back into a targeted operation. That constrains the shard key, which is why this conversation must happen first.
  • Reporting over whole sets → honestly, this may belong in a warehouse rather than the operational cluster. Sharding is a good moment to stop pretending otherwise.

The framing I would use with the team: sharding does not make joins slower by accident — it exposes the fact that a join is a cross-partition operation, which it always was. The work is not "fix 40 queries", it is "decide which of these 40 are actually operational reads that should never have been joins".

🏋️ Exercises

1 (easy): This aggregation returns customer names as undefined, and it also returns fewer rows than expected. Find both bugs. 
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $lookup: { from: "customers", localField: "customerId",
               foreignField: "_id", as: "customer" } },
  { $project: { total: 1, name: "$customer.name" } }
])
Solution

Bug 1 — customer is an array. $customer.name on an array yields an array of names (["Ada"]), not a string, so the UI renders nothing useful. Two fixes:

// Option A: unwind (also gives inner-join semantics - see bug 2)
{ $unwind: { path: "$customer", preserveNullAndEmptyArrays: true } },
{ $project: { total: 1, name: "$customer.name" } }

// Option B: take the first element, keeping all rows
{ $project: { total: 1,
              name: { $arrayElemAt: ["$customer.name", 0] } } }

Bug 2 — the missing rows are orphans. Orders whose customerId points at a deleted customer get an empty array, and if you add a plain $unwind they are dropped entirely — the left outer join silently becomes an inner join. That is exactly how a revenue report ends up 0.25% low with nothing erroring.

The diagnostic worth running on any collection that has been live for years:

db.orders.aggregate([
  { $lookup: { from: "customers", localField: "customerId",
               foreignField: "_id", as: "c" } },
  { $match: { c: { $eq: [] } } },
  { $count: "orphans" }
])

One more thing that is not a bug but should be: the $lookup pulls whole customer documents to use one field. Add a sub-pipeline projection, or the join carries every field of every matched customer through the rest of the pipeline.

2 (easy): Rewrite this to attach only each order's 3 most recent events, and say what failure mode you have removed. 
db.orders.aggregate([
  { $lookup: { from: "events", localField: "_id",
               foreignField: "orderId", as: "events" } },
  { $addFields: { events: { $slice: ["$events", -3] } } }
])
Solution

The rewrite — bound the join inside the sub-pipeline:

db.orders.aggregate([
  { $lookup: {
      from: "events",
      let: { oid: "$_id" },
      pipeline: [
        { $match: { $expr: { $eq: ["$orderId", "$$oid"] } } },
        { $sort:  { ts: -1 } },
        { $limit: 3 },
        { $project: { _id: 0, type: 1, ts: 1 } }
      ],
      as: "events"
  } }
])
db.events.createIndex({ orderId: 1, ts: -1 })   // serves match+sort

The failure mode removed: the original joins every event and then throws all but three away. Typical orders have 40 events, but one measured subscription order had 312,000 — enough to blow the 16 MB document limit and fail the entire pipeline with BSONObjectTooLarge. The rewritten version can never attach more than three documents, so the failure is impossible by construction rather than merely unlikely.

The performance difference on the same data: 2,100 ms → 180 ms. The index matters as much as the rewrite — {orderId: 1, ts: -1} serves both the $match and the $sort, so the $limit stops after three index entries instead of sorting everything first.

The general principle: reduce before you combine. Work done inside the sub-pipeline happens before results are attached; work done after is work you already paid for. Unlike a relational optimiser, MongoDB will not push that predicate down for you.

3 (medium): Build a monthly report: revenue by customer segment, for paid orders in a date range, where the segment lives on the customer document. 4.1M orders, 900k customers. Write it and justify the stage order.
Solution 
db.orders.aggregate([
  // 1. REDUCE FIRST - indexed, and it removes ~97% of the input
  { $match: { status: "paid",
              createdAt: { $gte: monthStart, $lt: monthEnd } } },

  // 2. Slim the documents before they enter the join
  { $project: { customerId: 1, totalCents: 1 } },

  // 3. Join, taking only the one field we need
  { $lookup: {
      from: "customers",
      let: { cid: "$customerId" },
      pipeline: [ { $match: { $expr: { $eq: ["$_id", "$$cid"] } } },
                  { $project: { _id: 0, segment: 1 } } ],
      as: "c" } },

  // 4. Adjacent to the lookup -> coalesced. Keep orphans visible.
  { $unwind: { path: "$c", preserveNullAndEmptyArrays: true } },

  // 5. Group, defaulting orphans rather than dropping them
  { $group: { _id: { $ifNull: ["$c.segment", "«unknown»"] },
              revenue: { $sum: "$totalCents" },
              orders:  { $sum: 1 } } },
  { $sort: { revenue: -1 } }
])

db.orders.createIndex({ status: 1, createdAt: -1 })

Why the stage order is the whole answer:

StageReason
$match firstUses an index and cuts 4.1M documents to ~120k. Every later stage costs 97% less. Putting it after the $lookup would join 4.1M documents to discard most of them
$project before the joinOrders carry embedded items; the report needs two fields. Slimming first reduces what flows through the pipeline
Sub-pipeline projectionAttaches one field per customer, not whole documents
$unwind adjacentCoalescence: the server never materialises the intermediate arrays — measured 2.4 s vs 9.1 s when separated, with 3.2 GB peak memory
preserveNullAndEmptyArraysWithout it, orphaned orders vanish and the report is silently low
$ifNull in the groupOrphans land in a visible «unknown» bucket instead of disappearing. A report that shows you its own data quality is worth more than one that quietly rounds it away

What I would suggest next if this ran monthly and mattered: denormalise segment onto the order at write time. It is a snapshot anyway — the segment the customer was in when they ordered is arguably more correct for a historical report than their segment today — and it removes the join entirely.

4 (medium): An org-chart endpoint returns everyone under a manager. It uses $graphLookup and takes 640 ms; it is called on every page load of the admin dashboard. It also hung once and had to be killed. Diagnose both and fix.
Solution

The hang first, because it is a correctness bug. A $graphLookup without maxDepth traverses until it exhausts memory if the data contains a cycle — employee A manages B manages A. That happens for mundane reasons: a data import, an interim manager arrangement, someone set as their own manager during a reorg.

{ $graphLookup: { ..., maxDepth: 6, depthField: "level",
                  restrictSearchWithMatch: { active: true } } }

maxDepth bounds it, depthField lets you reconstruct the hierarchy from the flat output array, and restrictSearchWithMatch prunes during traversal rather than after — in the measured tree that was the difference between exploring 240k nodes and 40k. I would also add a cycle check to the write path that sets managerId, because bounding the read does not fix the data.

The 640 ms is a design problem, not a tuning one. This is a hot read path doing an ad-hoc recursive traversal on every page load. First confirm the index exists on the connectToField — unindexed it was 41 s, so 640 ms means the index is there and this is as good as $graphLookup gets.

Denormalise an ancestors array (from the patterns lesson):

{ _id: "emp_88", managerId: "emp_12",
  ancestors: ["emp_1", "emp_4", "emp_12"] }
db.employees.createIndex({ ancestors: 1 })

db.employees.find({ ancestors: managerId })      // 8 ms

80× faster, and it is a plain indexed find — no aggregation, no depth limit, no cycle risk at read time.

The trade I would state explicitly: moving someone with a large sub-org rewrites every descendant's ancestors. In an org chart, reads happen thousands of times a day and reorgs happen quarterly, so this is clearly the right trade — but say the number out loud rather than discovering it during a reorg. Keep managerId alongside as the source of truth to rebuild from if a move is interrupted halfway.

Where I would keep $graphLookup: ad-hoc admin queries with an arbitrary start node and depth. It is the right tool for exploration; it is the wrong tool for a dashboard.

5 (hard): Design deletion for a SaaS app: a workspace has projects, projects have tasks, tasks have comments and attachments. Workspaces get deleted (billing lapse), and users can request GDPR erasure. Specify the whole mechanism.
Solution

These are two different operations with different requirements, and conflating them is the usual design error. Workspace deletion is a bulk lifecycle event; erasure is a targeted legal obligation that cuts across workspaces.

A. Workspace deletion — soft delete, then asynchronous reclamation.

// 1. Immediate, atomic, single-document: access stops now
db.workspaces.updateOne({ _id: wid },
  { $set: { status: "deleted", deletedAt: new Date(),
            purgeAfter: addDays(new Date(), 30) } })

// 2. Every read path is workspace-scoped anyway, so one guard
//    in the repository layer covers the whole app:
//      { workspaceId: wid, ... } + workspace.status === "active"

// 3. A worker purges after the grace period, bottom-up, in
//    throttled batches, resumable:
//      attachments (+ blob store) -> comments -> tasks
//      -> projects -> workspace

Why bottom-up and not top-down: if the job dies halfway, children without parents are still reachable by their own workspaceId and the job resumes. Deleting the workspace first would strand everything else with no efficient way to find it.

Why every child carries a denormalised workspaceId, even a comment four levels down: it makes purge, export and access control single-index operations rather than recursive traversals. This is the single most important schema decision in the design, and it must be made at the start — retrofitting it means backfilling every collection.

Why 30 days: billing lapses get reversed. Immediate hard deletion converts a payment problem into an unrecoverable data-loss incident.

B. GDPR erasure — targeted, and it must cross workspaces. This is where the design gets hard, because a user's personal data is scattered as denormalised copies:

users:       { _id, email, name }                    -> scrub
comments:    { authorId, author: { name, avatar } }  -> extended
tasks:       { assigneeId, assignee: { name } }         reference
audit_log:   { actorId, actorEmail }                    copies!
attachments: uploader metadata, and the FILE CONTENTS

The mechanism: maintain a registry of every location holding personal data — a literal list in code, reviewed when any schema changes — and drive erasure from it:

// 1. Scrub the source
db.users.updateOne({ _id: uid },
  { $set: { email: null, name: "[erased]", erasedAt: new Date() },
    $unset: { phone: "", avatarUrl: "" } })

// 2. Scrub every denormalised copy, from the registry
for (const loc of PII_LOCATIONS) {
  await db[loc.coll].updateMany({ [loc.idField]: uid },
                                { $set: loc.scrub })
}

// 3. Verify, and record the evidence
db.comments.countDocuments({ authorId: uid, "author.name": { $ne: "[erased]" } })
// must be 0, and the verification result is itself the audit record

Three points I would raise in review:

  • Do not delete the user document. authorId references must still resolve, or every comment thread breaks. Scrub the fields, keep the row — and keep erasedAt so a later "why is this blank?" has an answer.
  • The registry is the deliverable, not the script. Personal data spreads with every new extended reference, and a schema-change checklist item ("does this add a copy of user data?") is what keeps erasure correct in two years.
  • Backups and the blob store are in scope and are usually forgotten. Backups are typically handled by a documented retention window rather than surgical edits; attachment contents need a real delete from object storage, which no MongoDB operation performs.

And a reconciler for both paths: a weekly job that counts orphaned children and un-scrubbed personal data after a completed erasure. Every mechanism above has a failure mode, and the only thing that catches a handler someone forgot to update is a number on a dashboard.

6 (hard): A reporting aggregation joins four collections and takes 94 seconds. It runs hourly and is now overlapping with itself. Produce a diagnosis plan and a set of options ranked by cost. 
orders -> customers -> segments        (two chained lookups)
orders -> events                       (avg 40 per order)
4.1M orders, 900k customers, 164M events
Solution

Step 1 — find where the time goes before changing anything. Guessing at a four-stage join wastes a day:

db.orders.explain("executionStats").aggregate([...])

Read it for four specific things: (a) a COLLSCAN in any $lookup's inner plan; (b) where nReturned jumps — the fan-out point; (c) whether the initial $match uses an index; (d) any SORT stage with a spill. Then bisect: run the pipeline truncated after each stage and time it. The stage where the clock jumps is the target.

Step 2 — the likely findings, in order of probability:

FindingFixCost
Missing index on a foreignFieldCreate itMinutes — and worth 22× on the measured case
The events join fans out 4.1M → 164MBound it in the sub-pipeline, or pre-aggregate events per orderHours
$match after the joinsMove it firstMinutes
$unwind separated from its $lookupMake them adjacentMinutes
Chained customers → segmentsDenormalise segment onto the customerHours + a backfill

Step 3 — options ranked by cost, which is what the question is really asking:

  1. Stop the overlap immediately (minutes, and it is an outage risk, not a performance one). A distributed lock or a "running" flag so a second run cannot start. Two concurrent 94-second aggregations over 164M events compete for exactly the cache the operational workload needs — this is how a reporting job becomes a production incident.
  2. Index and stage-order fixes (hours). Often 5–10× on their own.
  3. Pre-aggregate the events (a day). 164M events joined hourly to produce per-order counts is the computed pattern begging to be applied: maintain eventCount and lastEventAt on the order and the biggest join disappears.
  4. Denormalise segment onto orders at write time (a day + backfill). Removes both chained lookups. Also more correct for a historical report — the segment at order time, not today's.
  5. Incremental reporting (a few days). Process only the last hour's orders into a rollup collection instead of re-reading all 4.1M every hour. Cost becomes proportional to new data, which is the only version of this that stays fixed as the collection grows.
  6. Move it off the operational cluster (a project). A secondary read preference with a dedicated analytics node, or a warehouse. The honest observation is that a four-way join over 164M documents is warehouse work, and the cluster is being asked to do two jobs with one cache.

What I would actually do: ship 1 today, 2 this week, and propose 3+5 together — they compose, and they convert an hourly cost that scales with total data into one that scales with new data. I would present 6 as the direction of travel with a trigger ("when the incremental job exceeds 15 minutes") rather than as an immediate ask, because it is a project and the cheaper fixes buy the time to do it properly.

🎯 Key Takeaways

  • A relationship is just a field holding an _id — no foreign keys, no cascades, no integrity. One audit found 3,100 orphaned orders accumulated silently over three years.
  • Every reference needs a written answer to "what happens to the children on delete?" Cascade, soft delete, change-stream cascade, prevent, or tolerate — plus a reconciler in every case.
  • $lookup is a left outer join that returns an ARRAY, even for 1:1 — and unmatched inputs get an empty array, not nothing.
  • Index the foreignField: 47 s unindexed versus 2.1 s indexed, with no warning either way. Check the inner plan in explain().
  • $lookup output is subject to the 16 MB document limit. One order with 312,000 events failed an entire pipeline with BSONObjectTooLarge.
  • Keep $unwind adjacent to its $lookup so they coalesce: 2.4 s versus 9.1 s and 3.2 GB peak memory when separated.
  • $unwind silently converts a left join to an inner join unless you set preserveNullAndEmptyArrays.
  • The pipeline form with let lets you filter, sort and limit inside the join — 2,100 ms to 180 ms, and it makes the 16 MB failure impossible by construction.
  • Reduce before you combine. $match first, filter in the sub-pipeline, project away what you will not use — MongoDB will not push predicates down for you.
  • $$var is a let variable; $field is a foreign document's field. Confusing them matches nothing, with no error.
  • An uncorrelated sub-pipeline runs exactly once — the right way to join small static reference data.
  • $graphLookup always needs maxDepth; your data will contain a cycle eventually. Use restrictSearchWithMatch to prune during traversal.
  • For hot-path traversal, denormalise instead: 8 ms for an ancestors array versus 640 ms for $graphLookup, and 41 s unindexed.
  • For a page of rows, a batched $in beats $lookup — 7 ms versus 2,100 ms. Dedupe the ids, and key JavaScript Maps on String(id).
  • Sharding changes join economics by an order of magnitude: 2.1 s → 25.4 s for a broadcast join, and $graphLookup's foreign collection cannot be sharded at all. Audit joins before choosing a shard key.
  • Soft delete with a partial unique index is usually the right answer for anything with financial history — and remember that it does not remove denormalised copies of personal data.
