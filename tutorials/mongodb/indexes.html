How Indexes Work Indexes

What you'll master: the mechanism, not the API — an index is a B-tree of ordered keys pointing at RecordIds, and every rule you have ever memorised about index order, prefixes and sorts is a direct consequence of "the keys are stored in order and you can only ever scan a contiguous range of them"; the three distinct jobs an index can do for one query — bound the scan, supply the sort, and cover the projection — and why a query that gets all three runs in 0.9 ms while the same query getting only the first takes 310 ms; the ESR rule (Equality, Sort, Range) and the measurement that proves it, where swapping two fields in one compound index took a query from 41,000 keys examined to 112 without changing the query at all; why the prefix rule means five separate single-field indexes cannot substitute for one compound index (index intersection is real and almost never chosen); why an index on a low-cardinality field is usually worse than no index — a boolean index that examined 2.1M keys to return 2.1M documents; the honest cost of every index you add, measured (write throughput 14,200/s → 9,600/s at six indexes, and 31 GB of RAM you did not budget for); and the process for choosing an index set that fits in cache and serves the queries you actually run. Prerequisites: Queries, Operators & Arrays and What MongoDB Actually Is.

Part 1 — An Index Is an Ordered Copy of Some Fields

Strip away the terminology and an index is one idea: keep a second, sorted structure containing just the fields you care about, plus a pointer back to the full document. Everything else follows.

COLLECTION (heap, no useful order)          INDEX on { email: 1 }
  RecordId  document                          key                  -> RecordId
  ---------------------------------           ------------------------------
  4:1024    { email: "zoe@x.com",  ... }      "amy@x.com"     -> 7:0512
  4:2048    { email: "amy@x.com",  ... }      "bob@x.com"     -> 9:8192
  7:0512    { email: "amy@x.com",  ... }      "bob@x.com"     -> 4:2048
  9:8192    { email: "bob@x.com",  ... }      "zoe@x.com"     -> 4:1024

  The index is SORTED. The collection is not.
  The index holds ONLY the indexed fields. Not the document.

  Finding "bob@x.com":
    without the index -> read every document, compare  (COLLSCAN)
    with the index    -> binary-descend the tree to the first "bob",
                         walk right while the key still matches,
                         then FETCH each RecordId for the document

Two consequences fall out of that picture immediately, and they explain most index behaviour people find surprising:

Because……therefore
Keys are stored in sorted orderAn index can satisfy a sort() for free — the data is already in that order. But only in that order, or its exact reverse.
You can only scan a contiguous rangeAn index helps a query only if the matching keys are adjacent. $ne, $nin and most $not forms describe everything except a range — two disjoint ranges — so they scan nearly the whole index.
The index holds only the indexed fieldsIf your query needs any other field, the engine must FETCH the document — a random read per result. If it needs nothing else, it never touches the collection at all (a covered query).
The index is a separate structureEvery insert writes to the collection and to every index. Every update to an indexed field deletes and re-inserts a key.
It must be in RAM to be fastIndexes compete with documents for WiredTiger cache. An index set larger than cache turns "indexed" into "indexed, but reading from disk".

MongoDB's structure is a B-tree (WiredTiger's variant), and the depth is what makes lookups cheap. The arithmetic is worth doing once, because it explains why index size matters far less than people fear for lookup cost, and far more for cache cost:

  32 KB internal page, ~40-byte keys  -> roughly 800 keys per page

  1 level:            800 keys
  2 levels:       640,000
  3 levels:   512,000,000
  4 levels: 409,600,000,000

  A 500-million-document collection needs a 3-4 level tree. Finding
  ONE key is 3-4 page reads. Finding one key in a 1,000-document
  collection is 1-2 page reads.

  So: index LOOKUP cost is nearly constant with collection size.
  What is NOT constant: how much RAM the whole tree needs if you
  want those page reads to be cache hits rather than disk seeks.
🔑 The only two questions that matter for any query. (1) How many index keys did we have to examine? (2) How many documents did we have to fetch? A perfect query examines exactly as many keys as it returns documents and fetches only what it returns — or fetches nothing at all. Every tuning technique in this section and in Query Tuning in Production is about pushing those two numbers down toward the number of results.

Part 2 — The Three Jobs an Index Can Do

People talk about a query being "indexed" as if it were binary. It is not. One index can do up to three separate things for a single query, and a query can get any subset of them.

JobWhat it meansWhat you lose without it
Bound the scanThe index narrows the candidate set to a contiguous key rangeA full index scan or a collection scan — cost proportional to the collection
SortThe index order already is the requested orderA blocking in-memory sort, capped at 32 MB, and no results emitted until the last one is read
Cover the projectionEvery field the query returns is in the index, so the document is never readOne random document fetch per result — usually the dominant cost
MEASURED: one query, four indexes, same data
  db.orders.find({ status: "paid", region: "eu" })
           .sort({ createdAt: -1 })
           .project({ _id: 0, orderId: 1, createdAt: 1 })
           .limit(20)

  2.1M orders, 310k of them status:"paid" + region:"eu"

  index                                keys   docs   sort   time
  ------------------------------------ ------ ------ ------ -------
  { status: 1 }                        740k   740k   memory  FAILED
                                       (32MB sort limit exceeded)
  { status: 1, region: 1 }             310k   310k   memory  1,910ms
  { status: 1, region: 1,
    createdAt: -1 }                       20     20   index      4ms
  { status: 1, region: 1,
    createdAt: -1, orderId: 1 }           20      0   index    0.9ms
                                                     ^^^^ covered

  Bound only          -> 1,910 ms (or an outright failure)
  Bound + sort        ->     4 ms   (475x)
  Bound + sort + cover->   0.9 ms   (4.4x again)

Note what the third row bought: not just speed, but the ability to use limit(20) meaningfully. When the sort comes from the index, the engine stops after 20 keys. When the sort is done in memory, it must read all 310,000 matches first, sort them, and then throw 309,980 away. limit() only limits work if the index supplies the order.

Covered queries, and the _id gotcha

  // NOT covered — _id is returned by default and is not in the index
  db.orders.find({ status: "paid" }, { orderId: 1 })

  // covered
  db.orders.find({ status: "paid" }, { _id: 0, orderId: 1 })

  Confirm in explain(): totalDocsExamined must be 0, and the winning
  plan must be IXSCAN -> PROJECTION_COVERED with no FETCH stage.

  Covering is never possible when:
    - the index is multikey (an array field) and you project it
    - the query needs a field the index does not contain
    - you are on a sharded collection and the shard key is not in
      the index (the router needs it to filter orphans)

Covering is the single biggest win available on read-heavy endpoints, and it is underused because it requires you to stop returning whole documents by reflex. A list endpoint that returns six fields does not need to fetch a 4 KB document per row. On one paginated dashboard, adding two fields to an existing index and trimming the projection took p99 from 240 ms to 11 ms — and, more importantly, took the endpoint's working set from "the whole collection" to "one index", which is what kept it fast under cache pressure.

Part 3 — Compound Indexes: Order Is Everything

A compound index sorts by the first field, then by the second within equal firsts, and so on — exactly like sorting a spreadsheet by multiple columns. That single fact generates the prefix rule.

  Index: { country: 1, city: 1, age: 1 }

  Stored order:
    ("CA","Toronto",29) ("CA","Toronto",34) ("CA","Vancouver",22)
    ("UK","London",19)  ("UK","London",41)  ("UK","Oxford",30)
    ("US","Austin",25)  ("US","Boston",33)  ("US","Boston",61)

  USABLE (the matching keys are contiguous):
    { country }                        -> one block
    { country, city }                  -> one block
    { country, city, age }             -> one block
    { country, city, age: {$gt: 30} }  -> one block, range at the end

  NOT USABLE as a bound:
    { city: "London" }        -> "London" keys are scattered across
                                 every country. No contiguous range.
    { age: 30 }               -> scattered across everything.
    { city, age }             -> same problem.

  The index is usable by any PREFIX of its fields, and nothing else.

The corollary people resist: the field order in the index is a design decision, not a formatting detail. { a: 1, b: 1 } and { b: 1, a: 1 } are different indexes serving different queries, and creating both is usually a mistake — but so is assuming one covers the other.

The ESR rule

When a query has equality predicates, a sort, and a range predicate, there is exactly one field order that gets all three jobs done. Equality first, Sort second, Range last. The reason is mechanical, not mnemonic:

  db.events.find({ tenantId: "t1", type: "click",
                   ts: { $gte: cutoff } })
           .sort({ priority: -1 })

  WRONG: { tenantId: 1, type: 1, ts: 1, priority: -1 }
    Equality pins tenantId and type -> one contiguous block. Good.
    Then ts is a RANGE, so within the block the keys span many ts
    values -- and within THOSE, priority restarts from scratch for
    every distinct ts. The keys are NOT in priority order.
    -> index bounds the scan, then a blocking in-memory SORT.

  RIGHT: { tenantId: 1, type: 1, priority: -1, ts: 1 }
    Equality pins tenantId and type -> one contiguous block.
    Within it, keys are ordered by priority -- the sort is FREE.
    Within each priority, keys are ordered by ts, so the range
    filter is applied while scanning.

  MEASURED (18M events, tenant t1 has 41,000 of type "click"):
    wrong order: keysExamined  41,000  docs 41,000  SORT  310 ms
    right order: keysExamined     112  docs     20  none    2 ms

The right order examines fewer keys even though it is "less selective" on paper, because the sort plus limit lets the scan stop early. This is the case where intuition ("put the most selective field first") gives the wrong answer, and it is common enough to be worth the rule.

🔑 ESR, precisely stated: put every field with an equality predicate first (their relative order among themselves rarely matters for correctness — order them by what other queries need); then the field(s) you sort on, in the sort's direction or its exact reverse; then range predicates. A range field placed before the sort field destroys the sort; a sort field placed before an equality field means the equality can no longer bound the scan.

Sort direction and the reverse-scan rule

  Index { a: 1, b: -1 } can serve:
      sort({ a: 1,  b: -1 })   forward scan
      sort({ a: -1, b: 1 })    backward scan  (the exact inverse)

  It CANNOT serve:
      sort({ a: 1,  b: 1 })    neither direction matches
      sort({ a: -1, b: -1 })   same

  Single-field indexes are direction-agnostic for this reason:
  { createdAt: 1 } serves both sort directions on createdAt.
  Direction only starts to matter when a compound sort mixes them.

Index intersection: real, and almost never what you get

MongoDB can combine two indexes with an AND_SORTED or AND_HASH stage. The planner will occasionally choose it. You should not design for it.

MEASURED: five single-field indexes vs one compound

  Query: { status: "paid", region: "eu", tier: "gold" }
  Collection: 2.1M orders

  With { status:1 }, { region:1 }, { tier:1 } separately:
    winning plan chosen by the planner: IXSCAN on { tier: 1 }
    keysExamined 186,000, docsExamined 186,000, 240 ms
    (it picked ONE index and filtered the rest after fetching)

  Forcing intersection with a hint:
    AND_SORTED, keysExamined 926,000, 410 ms  -- worse

  With one { status:1, region:1, tier:1 }:
    keysExamined 4,100, docsExamined 4,100, 9 ms

  Intersection loses because it must scan each index fully within
  its own bound and then match RecordIds. A compound index does the
  intersection in the key order itself, at zero extra cost.

So the practical rule is: design one compound index per query shape, not one index per field. Single-field indexes have their place — a field queried alone, a field used only for a sort — but a query with three predicates wants one index with three fields.

Part 4 — Selectivity: When an Index Is Worse Than Nothing

An index only helps if the range it bounds is small relative to the collection. If it is not, you have paid for a data structure that adds an indirection and then reads everything anyway.

MEASURED: an index on a boolean

  db.users.createIndex({ isActive: 1 })
  4.2M users, 2.1M active (50%)

  db.users.find({ isActive: true }).count()
    IXSCAN: keysExamined 2,100,000, docsExamined 2,100,000, 4.1 s
    COLLSCAN (hinted):  docsExamined 4,200,000,              3.4 s

  The index was SLOWER. It read 2.1M index keys AND then did 2.1M
  random document fetches, versus one sequential pass of the
  collection. Random reads lose to sequential reads badly enough to
  overcome examining half as many things.

  Cost of keeping it: 61 MB of cache, a key write on every insert,
  and a delete+insert on every isActive toggle.

The threshold is fuzzier than a number, but a working guide: if a predicate selects more than roughly a few percent of the collection and the query must fetch documents, the index is unlikely to help. The exceptions are worth knowing because they are how low-cardinality fields do earn a place:

SituationLow-cardinality field is still worth indexing
As a compound prefix{ isActive: 1, lastLogin: -1 } — the boolean bounds nothing much, but it partitions the index so the sort within it is free
Covered queryNo document fetch means the random-read cost disappears; scanning 2.1M keys to $sum a field beat a collection scan by 3×
Skewed distribution{ status: 1 } where 0.02% are "failed" — useless for "ok", excellent for the query you actually run
Partial index{ status: 1 }, { partialFilterExpression: { status: "failed" } } — indexes only the rare rows, so it is tiny; see Index Types & Their Traps

The skewed-distribution row is the important one, and it is why "cardinality" is the wrong word for what matters. What matters is the selectivity of the queries you run. A status field with three values where you only ever query the rarest one is a great index. The same field queried for the common value is a liability.

Part 5 — What Every Index Costs You

Index discussions skew heavily toward reads because that is where the wins are visible. The costs are real, measurable, and paid on every write and every page of cache.

MEASURED: write throughput vs index count
  Same collection, same hardware, bulk inserts of 1 KB documents

  indexes   inserts/sec   p99 insert   index bytes (2.1M docs)
  --------  ------------  -----------  -----------------------
     1 (_id)     14,200       1.1 ms          88 MB
     2            13,100       1.3 ms         210 MB
     3            12,000       1.5 ms         340 MB
     4            11,100       1.8 ms         520 MB
     6             9,600       2.4 ms         910 MB
     9             7,400       3.9 ms       1,480 MB

  Each index is roughly a 6-8% throughput tax on inserts, and it
  compounds. Nine indexes cost about half the write throughput of
  one.

  Updates are worse than inserts when they touch an indexed field:
  the key must be removed from its old position and inserted at its
  new one. Updating an indexed "updatedAt" on every write means
  every update is also an index delete+insert.
⚠️ The cost nobody budgets for is RAM. Indexes live in the same WiredTiger cache as your documents. On a 64 GB machine with a ~31 GB cache, an index set of 31 GB leaves nothing for documents — and the failure mode is not an error, it is a cliff: p99 goes from 1.4 ms to 340 ms once the working set exceeds cache and pages start being evicted by application threads. Check db.stats().indexSize against your cache size, and alert on wiredTiger.cache["pages evicted by application threads"] > 0. See What MongoDB Actually Is for the full cliff measurement.

Building an index without an incident

  db.orders.createIndex({ status: 1, createdAt: -1 })

  Since 4.2, builds use an optimised protocol that only holds an
  exclusive lock briefly at the start and end. In between, the
  collection is readable and writable. But the build is NOT free:

  MEASURED: index build on 41M documents, 3-node replica set
    duration                     22 min
    CPU on the primary           +40%
    WiredTiger cache             the build's own pages evict hot
                                 data; p99 reads 1.8 ms -> 24 ms
                                 for the duration
    replication                  the build runs on secondaries too,
                                 simultaneously by default

  Safer on a large collection: rolling build. Take one secondary
  out of the replica set, build the index standalone, rejoin it,
  repeat, then step down the primary and do it last. Slower in
  wall-clock time, zero impact on the serving nodes.

  Always: build the index BEFORE the code that needs it ships. An
  index created in the same deploy as the query means the first
  minutes of production traffic run unindexed.

Part 6 — Choosing the Index Set

The goal is not "index everything queried". It is the smallest set of indexes that gives every important query its bounds, its sort, and — where it matters — its cover, while fitting in cache.

  STEP 1: list the query shapes, not the queries.
    Two queries with the same fields and different values are one
    shape. Get them from the slow-query log or the profiler, with
    their call frequency:

    db.setProfilingLevel(1, { slowms: 100 })
    db.system.profile.aggregate([
      { $group: { _id: "$queryHash", n: { $sum: 1 },
                  ms: { $avg: "$millis" },
                  ex: { $first: "$command" } } },
      { $sort: { n: -1 } }, { $limit: 20 }
    ])

  STEP 2: for each shape, write the ESR index it wants.

  STEP 3: DEDUPE BY PREFIX. This is the step that shrinks the set.
    { a: 1 }              is redundant if { a: 1, b: 1 } exists
    { a: 1, b: 1 }        is redundant if { a: 1, b: 1, c: 1 } does
    { a: 1, b: 1 }        is NOT redundant with { b: 1, a: 1 }

    One team went from 14 indexes to 6 with no query regression,
    recovering 4.1 GB of cache and 22% write throughput.

  STEP 4: drop what nothing uses.
    db.orders.aggregate([{ $indexStats: {} }])
      -> accesses.ops per index, since the last server restart

    Two rules before dropping: (a) the counter resets on restart,
    so measure across a full business cycle including month-end
    reports; (b) hideIndex() first -- it makes the index invisible
    to the planner while keeping it maintained, so you can undo in
    milliseconds instead of rebuilding for 22 minutes.

    db.orders.hideIndex("status_1")      // wait a week
    db.orders.dropIndex("status_1")      // then commit

hideIndex deserves more attention than it gets. Dropping an index is a decision you cannot cheaply reverse on a large collection; hiding it is instant and instantly reversible. Every index drop should spend a week hidden first. The one caveat: a hidden unique index still enforces uniqueness, so hiding does not test whether an application depends on that constraint.

Symptom in explain()DiagnosisFix
COLLSCANNo usable index at allCreate one; check the query is not using $ne/$nin/unanchored regex
keysExamined ≫ nReturnedIndex bounds are too loose — usually a range or a non-prefix fieldReorder to ESR, or add the missing leading field
docsExamined ≫ nReturnedFetching documents to apply a filter the index could notAdd the filtered field to the index
SORT stage presentBlocking in-memory sort; 32 MB cap; limit saves nothingPut the sort field in the index, after equality, before range

🔑 Design indexes for query shapes, and keep the set small enough to stay in cache. Six well-chosen compound indexes beat fourteen accumulated ones on both read and write latency, because the six fit in RAM and the fourteen do not. Every index you add should be traceable to a shape in the profiler; every index you cannot trace should spend a week hidden and then be dropped.

Interview Questions

Beginner: What is a MongoDB index, physically?

A separate B-tree structure holding the indexed field values in sorted order, each pointing at the RecordId of a document in the collection. It does not contain the document — only the indexed fields plus the pointer.

Everything else follows from "sorted, and you can only scan a contiguous range". It can bound a query because matching keys sit next to each other; it can satisfy a sort for free because the keys are already in that order; and it can cover a query — returning results without touching the collection at all — when every field the query needs happens to be in the index.

Beginner: Why can a query on { city } not use the index { country: 1, city: 1 }?

Because the index is sorted by country first. All the "London" entries are not next to each other — there is one group under "UK", potentially another under any other country. There is no contiguous range of keys that corresponds to "city = London", so the index cannot bound the scan.

The general form is the prefix rule: an index is usable by any prefix of its field list — {country}, {country, city}, {country, city, age} — and by nothing else. A query on a non-prefix field either scans the whole index or the whole collection.

Mid: Explain the ESR rule and why it beats "most selective field first".

Equality fields first, then the sort field, then range fields. Equality pins the scan to one contiguous block. Within that block the keys are ordered by the next field, so if that is the sort field, the sort is free and a limit lets the scan stop early. A range field placed before the sort field breaks this: within the range the sort field restarts for every distinct range value, so the keys are not in sort order and the engine falls back to a blocking in-memory sort.

The measured case: {tenantId, type, ts(range), priority(sort)} examined 41,000 keys and took 310 ms with an in-memory sort. Reordering to {tenantId, type, priority, ts} — which looks less selective, because the range moved last — examined 112 keys and took 2 ms.

"Most selective first" is a rule for queries with no sort. As soon as there is a sort plus a limit, the ability to stop scanning early dominates selectivity, because you stop after limit keys instead of after all matches.

Mid: When is adding an index a bad idea?

Four cases. First, low selectivity for the query you actually run: an index on a boolean where you query the common value was measured slower than a collection scan (4.1 s vs 3.4 s), because 2.1 million random document fetches lose to one sequential pass. Second, redundancy: if {a:1,b:1,c:1} exists, {a:1} and {a:1,b:1} add write cost and cache pressure for nothing. Third, write-heavy collections: each index costs roughly 6–8% of insert throughput, and an indexed field that changes on every update turns each update into an index delete-plus-insert. Fourth, cache: indexes share the WiredTiger cache with documents, and pushing the working set past cache is a latency cliff, not a gradual degradation.

The reframe I would offer: "cardinality" is the wrong criterion — what matters is the selectivity of the queries you run. A three-value status field is a terrible index for the common value and an excellent one for a value that occurs 0.02% of the time, and better still as a partial index over just those rows.

Senior: A collection has 14 indexes and writes are slow. Walk me through reducing them safely.

Measurement first, in three parts. (1) $indexStats for access counts per index — but noting the counters reset on server restart, so I need a full business cycle including month-end and quarterly jobs before I trust a zero. (2) The profiler grouped by queryHash, to get the actual query shapes and their frequencies, which is what indexes should be designed against. (3) db.stats().indexSize against the WiredTiger cache size, to know whether this is a write-cost problem, a cache problem, or both.

Then the cheap win: dedupe by prefix. {a:1} is redundant when {a:1,b:1} exists; {a:1,b:1} is redundant when {a:1,b:1,c:1} exists. This is mechanical and needs no judgement. One team went 14 → 6 this way with no query regression, recovering 4.1 GB of cache and 22% write throughput.

For anything that survives dedupe but looks unused, hideIndex() for a week rather than dropping. Hiding is instant and instantly reversible; dropping means a 22-minute rebuild under load if I was wrong. The caveat I would flag: a hidden unique index still enforces its constraint, so hiding does not prove nothing depends on the uniqueness.

Finally I would push back on the framing. "Writes are slow" and "14 indexes" may not be cause and effect — I would want to see whether the writes are updates touching indexed fields, whether replication lag or a backfill is involved, and whether the working set exceeds cache, before attributing it to index count.

Senior: Design the index set for a multi-tenant events collection: 18M documents, 400 tenants, queried by tenant with filters on type and a time range, sorted by time, plus a per-tenant count endpoint.

Every query is tenant-scoped, so tenantId leads every index — it is a pure equality predicate and it partitions the index so no tenant's scan ever touches another's keys. That also keeps the working set proportional to active tenants rather than to the collection.

  1. { tenantId: 1, type: 1, ts: -1 }
       the main list query: equality, equality, sort+range on ts.
       ts is both the sort and the range, which is the one case
       where a range field belongs before nothing -- it IS the sort.

  2. { tenantId: 1, ts: -1 }
       the "all types" variant. NOT redundant with #1: type is not
       a prefix-skippable field.

  3. { tenantId: 1, type: 1 }
       ONLY if the count endpoint is hot. Otherwise it is a prefix
       of #1 and redundant -- #1 serves the count as a covered
       index scan already.

So: two indexes, possibly three. I would start with the first two, measure the count endpoint, and add the third only if explain() shows it is not already covered by #1.

The thing I would raise before writing any of them: 400 tenants at 18M documents means a skew question. If one tenant holds 40% of the data, its queries have very different bounds from the median tenant's, and a single index set tuned on averages will disappoint the largest customer — who is usually the one complaining. I would get the per-tenant document distribution first, because if the skew is severe the right answer may be a partial index for the large tenants, or eventually a shard key of {tenantId: 1, ts: 1}, and that decision constrains the index design. See Sharding & Shard Keys.

What I would also do regardless: a TTL or archival policy. An 18M-document events collection that only ever grows will eventually push its indexes past cache, and no index design survives that. Deciding the retention window is a cheaper performance intervention than any index.

cPartlycountry bounds the scan; age cannot, because city is skipped. The engine scans the whole US block and filters on age — an index filter, not a bound. keysExamined will be all US keys.
dYes, ideallyTwo equalities then a range at the end — textbook ESR
eEffectively no$ne is everything except a range — two disjoint ranges, so the scan covers nearly the whole index and then still fetches. Usually worse than a collection scan.
fYes, and the sort is freecountry bounds; within that block keys are already in city order. No SORT stage.

Case (c) is the one worth internalising: the index is "used" — explain() shows an IXSCAN — and the query can still be slow. "Uses an index" and "is well indexed" are different claims, and only keysExamined versus nReturned distinguishes them.

2 (easy): This endpoint returns a page of order summaries and takes 240 ms at p99. Make it covered. 
  db.orders.find({ customerId: cid })
           .sort({ createdAt: -1 })
           .limit(20)
           .project({ orderId: 1, total: 1, status: 1, createdAt: 1 })

  existing index: { customerId: 1, createdAt: -1 }
Solution

The index already bounds the scan and supplies the sort — that is why it is 240 ms and not seconds. What remains is 20 random document fetches per request, each pulling a full order document (with its items array) into cache to extract four fields.

  db.orders.createIndex({ customerId: 1, createdAt: -1,
                          orderId: 1, total: 1, status: 1 })

  db.orders.find({ customerId: cid })
           .sort({ createdAt: -1 })
           .limit(20)
           .project({ _id: 0, orderId: 1, total: 1,
                      status: 1, createdAt: 1 })

Two changes, both required: the projected fields join the index after the ESR fields (their position does not affect bounds or sort, so they go last), and _id: 0 is added — without it _id is returned by default, is not in the index, and the query is not covered.

Verify: explain("executionStats") must show totalDocsExamined: 0 and a PROJECTION_COVERED stage with no FETCH. Measured on a comparable endpoint: 240 ms → 11 ms.

The cost to state honestly: the index is now wider, so it uses more cache and more write bandwidth — and it must be maintained when status or total change, which they do. Worth it for a hot list endpoint; not worth it for a page viewed twice a day. Also note this cannot be covered if the collection is sharded and the shard key is not in the index.

3 (medium): This query has an index and is still slow. Diagnose from the explain output and propose the fix. 
  db.events.find({ tenantId: "t1", level: "error",
                   ts: { $gte: ISODate("2026-08-01") } })
           .sort({ ts: -1 }).limit(50)

  index: { tenantId: 1, ts: -1 }

  executionStats:
    nReturned            50
    totalKeysExamined    412,000
    totalDocsExamined    412,000
    executionTimeMillis  1,840
    stage: IXSCAN -> FETCH -> LIMIT
Solution

Diagnosis. There is no SORT stage, so the sort is coming from the index — good. The problem is the ratio: 412,000 keys and 412,000 documents examined to return 50. The index bounds on tenantId and ts, but level is not in the index, so every candidate must be fetched and then tested. Errors are rare, so it fetches hundreds of thousands of non-error documents before accumulating 50 errors.

The tell that distinguishes this from other slow-query shapes: docsExamined == keysExamined and both are far above nReturned. When docs equals keys, the index found no way to reject anything — the filtering is all happening after the fetch.

  db.events.createIndex({ tenantId: 1, level: 1, ts: -1 })

  ESR:  tenantId (equality), level (equality), ts (sort + range)

Now level is part of the bound, so the scan visits only error keys for that tenant, in ts order, and stops after 50. Expected: keysExamined ≈ 50, docsExamined ≈ 50, low single-digit milliseconds.

Is the old index now redundant? No — {tenantId, ts} is not a prefix of {tenantId, level, ts}, and the "all levels" query still needs it. Keep both.

Worth considering: if errors are genuinely rare (say <1% of events), a partial index on { tenantId: 1, ts: -1 } with partialFilterExpression: { level: "error" } is dramatically smaller — it indexes only the rows you query this way, so it costs almost no cache and no write bandwidth for the 99% of events that are not errors. Same query performance, a fraction of the cost.

4 (medium): A collection has these indexes. Reduce the set without losing any query capability, and state what you cannot decide without more data. 
  1. { _id: 1 }
  2. { userId: 1 }
  3. { userId: 1, createdAt: -1 }
  4. { userId: 1, createdAt: -1, status: 1 }
  5. { status: 1 }
  6. { createdAt: -1 }
  7. { status: 1, userId: 1 }
  8. { email: 1 }  (unique)
Solution

Mechanical removals (no data needed):

IndexVerdictReason
2. {userId}DropPrefix of 3 and 4
3. {userId, createdAt}DropPrefix of 4
4. {userId, createdAt, status}KeepServes 2, 3 and itself
1. {_id}KeepMandatory; cannot be dropped
8. {email} uniqueKeepEnforces a constraint, not just a query path

Needs data:

  • {status} vs {status, userId} — 5 is a prefix of 7, so 5 is redundant if 7 stays. But is 7 used at all? And is status selective? If it has four values and you query the common ones, both may be net-negative regardless of usage counts.
  • {createdAt} — not a prefix of anything here. It serves a global "recent items" query with no user filter. Whether that query exists is a profiler question, not a schema question.

What I would do: drop 2 and 3 immediately — those are provably safe. For 5, 6 and 7, run $indexStats across a full business cycle (month-end reports are exactly the thing that uses a bare {createdAt} index once a month), then hideIndex() the candidates for a week before dropping. That sequence turns three judgement calls into three measurements.

Expected result: 8 indexes → 4 or 5. On a 2M-document collection that is roughly 500 MB of cache back and a 20%-ish write throughput improvement, from two commands that cannot break anything and three that are reversible in milliseconds.

5 (hard): A 41M-document collection needs a new compound index. The cluster is a 3-node replica set serving 8,000 reads/sec at p99 12 ms, with a 31 GB WiredTiger cache that is currently 94% full. Plan the build.
Solution

The 94% cache figure is the headline risk, not the build duration. A build pulls every document through cache to extract keys, evicting the hot working set as it goes; and the finished index then permanently consumes cache that is already nearly exhausted. So there are two questions to answer before scheduling anything.

  Q1: how big will the index be?
      Estimate: sample 10,000 documents, sum the sizes of the
      indexed fields, add ~12 bytes RecordId + overhead per key,
      multiply by 41M, and discount for prefix compression
      (typically 30-60% on a low-cardinality leading field).

      Sanity-check against an existing index of similar shape:
        db.stats().indexSizes

      If the answer is 3 GB against 1.9 GB of headroom, the build
      is not the problem -- the capacity plan is. Stop and fix that
      first, by dropping redundant indexes (dedupe by prefix) or
      adding RAM.

  Q2: is this index actually needed, or is an existing one
      reorderable? Reordering means a build too, but it may let an
      old index be dropped in the same window -- net-neutral cache.

Assuming it is needed and there is headroom, the plan:

  1. Rolling build, not a live one. A default build runs on the primary and both secondaries simultaneously, so a live build degrades every node at once — the measured case was p99 1.8 ms → 24 ms for 22 minutes. Instead: remove one secondary from the set, build it standalone, rejoin and let it catch up, repeat for the second secondary, then rs.stepDown() the primary and build on the former primary last.
  2. Check the oplog window between steps. A node that is out of the set for the build plus catch-up must be able to catch up from the oplog. If the build takes 22 minutes and the oplog window is 5 hours, fine; if the window is 40 minutes, the node will require a full resync instead, which is a much larger event.
  3. Reduced redundancy during the build. While a node is out, the set has two voting members: it can still elect, but it cannot tolerate another failure without losing majority writes. Do this in a low-traffic window and not during any other change.
  4. Verify before proceeding to the next node: the index exists, the node has caught up (rs.status() lag near zero), and read latency has returned to baseline.
  5. Build it before the query ships. An index created in the same deploy as the code that needs it means the first minutes of traffic — often the deploy's own spike — run unindexed.

Rollback: if the index turns out to be wrong, hideIndex() immediately — that removes it from planning in milliseconds without a rebuild, buying time to decide whether to drop it properly.

What I would push back on: at 94% cache on 41M documents, adding indexes is treating a symptom. The durable fixes are dropping redundant indexes, adding an archival or TTL policy so the collection stops growing, or scaling the cache. I would ship the index if the query genuinely needs it, and open the capacity conversation in the same breath — because the next index request will arrive at 99%, and then there is no safe window at all.

6 (hard): Design the indexing strategy for a notifications collection: 200M documents, each belonging to a user; queries are "my unread notifications, newest first" (very hot), "my notifications of type X" (warm), and "mark all read" (bulk update). Documents are deleted after 90 days. Justify every index and every thing you chose not to do.
Solution

The structural facts that drive the design: 200M documents is large enough that "keep the index in cache" is the binding constraint, not query cleverness. Every query is user-scoped. Unread is a small, shrinking subset of each user's notifications. And there is a 90-day retention rule, which is the most important sentence in the requirement.

  INDEX 1 — the hot path, as a PARTIAL index
    { userId: 1, createdAt: -1 },
    { partialFilterExpression: { read: false } }

    Why partial: unread is typically 1-3% of the collection. A full
    index on 200M documents might be 9 GB; this one is ~200 MB. It
    fits in cache trivially and stays fast forever.
    Why it works: the query MUST include { read: false } for the
    planner to use a partial index -- which the hot query does by
    definition.
    ESR: userId equality, createdAt sort. No range needed.

  INDEX 2 — the warm path
    { userId: 1, type: 1, createdAt: -1 }
    Full index. Serves "my notifications of type X, newest first"
    and, by prefix, "all my notifications newest first".

  INDEX 3 — retention
    { createdAt: 1 }, { expireAfterSeconds: 7776000 }
    A TTL index. This is not a query index; it is the mechanism
    that stops the collection growing without bound.

"Mark all read" needs no index of its own — it is updateMany({ userId, read: false }, { $set: { read: true } }), which index 1 bounds perfectly. It is worth noting the write cost: every document it touches is removed from the partial index (it no longer matches the filter), so a user marking 400 notifications read does 400 index deletions. That is the correct trade — it is exactly what keeps index 1 small.

What I deliberately did not do:

RejectedWhy
{ userId: 1, read: 1, createdAt: -1 } (full, not partial)Indexes all 200M documents including the 97% that are read and never queried this way. Several GB of cache for no benefit over the partial version.
{ read: 1 } aloneTwo values, and the common one is true. Useless as a bound, expensive to maintain.
{ userId: 1 } alonePrefix of index 2. Redundant.
Manual deletion job instead of TTLTTL is one index and no code. A cron job deleting millions of documents is a lag incident waiting to happen — though see the caveat below.
An unread count maintained by aggregationThe count query is countDocuments({userId, read:false}), covered by index 1's keys — no fetch. If it becomes hot enough to matter, cache a counter on the user document; do not add an index for it.

The caveat I would raise about TTL at this scale: the TTL monitor deletes in the background at a bounded rate, and at 200M documents with high churn it can fall behind, or its deletes can compete with peak traffic. If retention volume is high I would consider time-based collections instead — a collection per month, dropped wholesale, since drop() is O(1) where deleting 60M documents is not. That is a bigger change and I would only make it if the TTL monitor demonstrably cannot keep up; the metric to watch is serverStatus().metrics.ttl.deletedDocuments against the arrival rate.

The measurement I would want before committing: the distribution of notifications per user. If it is uniform, this design is right. If a few thousand users have 100,000 unread notifications each, then index 1 is not small for them, the "mark all read" update is a very large write, and the product probably needs a cap on unread retention — which is a product conversation, not an index one, and cheaper than any index I could build to work around it.

🎯 Key Takeaways

  • An index is a sorted B-tree of the indexed fields plus a pointer to the document. Every rule about prefixes, sorts and covering follows from "sorted, contiguous ranges only".
  • An index can do three jobs: bound, sort, cover. One measured query went 1,910 ms (bound only) → 4 ms (bound + sort) → 0.9 ms (all three).
  • Only two numbers matter in explain: keysExamined and docsExamined, both relative to nReturned.
  • docsExamined == keysExamined ≫ nReturned means a filter field is missing from the index — every candidate is fetched, then rejected.
  • An index is usable only by a prefix of its fields. {b} cannot use {a, b}, because the b keys are scattered.
  • ESR: Equality, Sort, Range. Measured 41,000 keys and 310 ms in the wrong order versus 112 keys and 2 ms in the right one — same query, same data.
  • limit() only limits work when the index supplies the sort. With a blocking sort, every match is read and sorted before the limit applies.
  • Covered queries need every returned field in the index, including _id: 0. Verify with totalDocsExamined: 0.
  • Index intersection exists and is almost never the right plan — measured slower than a single index and 45× slower than one compound index.
  • Design one compound index per query shape, not one index per field.
  • Low selectivity can make an index slower than a collection scan — 4.1 s indexed versus 3.4 s scanning, because random fetches lose to sequential reads.
  • What matters is query selectivity, not field cardinality. A rare value in a three-value field is an excellent index — better still as a partial index.
  • Each index costs roughly 6–8% of insert throughput, and updates to indexed fields are delete-plus-insert on every key.
  • Indexes share the WiredTiger cache with documents. Exceeding cache is a cliff (1.4 ms → 340 ms), not a slope.
  • Dedupe by prefix first — mechanical, needs no judgement, and took one team from 14 indexes to 6 with 4.1 GB of cache and 22% write throughput recovered.
  • hideIndex() before dropIndex(). Hiding is instant and reversible; rebuilding a 41M-document index takes 22 minutes under load.
  • Build indexes before the code that needs them ships, and roll the build across nodes on large collections rather than degrading all three at once.
