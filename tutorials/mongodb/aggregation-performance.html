Aggregation Performance Aggregation

What you'll master: where the time in a pipeline actually goes, which is almost never where people look — the first stage decides the cost of everything after it, and a pipeline whose opening $match cannot use an index has already lost before the interesting stages run; the ordering discipline stated as a measurable rule, with the numbers (the same six stages reordered went from 9.1 s to 240 ms, and the single stage inserted between $sort and $limit that cost 3.2 GB of peak memory); $lookup economics — why an unindexed join was 47 s against 2.1 s indexed, why the sub-pipeline form took the same query to 180 ms, and the case where a batched application join beat $lookup by 300×; how memory is really budgeted (per blocking stage, per $facet branch, per $setWindowFields partition) and why $group cardinality, not document count, predicts a spill; what a sharded aggregation does — which stages run on the shards, which force a merge, and the pipeline whose $group ran 12 times in parallel and then once more on the merging node; and the decision that matters more than any of it: whether the pipeline should run on the request path at all. Prerequisites: The Aggregation Pipeline, Advanced Stages and Reading Explain Plans.

Part 1 — The First Stage Decides Everything

A pipeline's cost is dominated by how many documents enter it. Only the first stage can use an index to reduce that number, so the first stage is not one optimisation among several — it is the one that determines whether the others matter.

  db.orders.explain("executionStats").aggregate([...])

  The first thing to read is $cursor in the explain output:

    "$cursor": {
      "queryPlanner": { "winningPlan": { "stage": "IXSCAN", ... } },
      "executionStats": { "nReturned": 4100,
                          "totalDocsExamined": 4100 }
    }

  IXSCAN with a small nReturned  -> the pipeline starts small
  COLLSCAN                       -> the pipeline reads everything,
                                    and no later stage can undo that

MEASURED: the same aggregation, four opening stages

  Collection: 41M orders. Target: August revenue by region.

  A. { $group: ... } first, $match on the group after
       reads 41,000,000 documents                        118 s

  B. { $match: { createdAt: { $gte: aug } } } first,
     no index on createdAt
       COLLSCAN 41,000,000, then groups 1,240,000          31 s

  C. same $match, index { createdAt: -1 }
       IXSCAN, 1,240,000 documents                        3.4 s

  D. same, index { status: 1, createdAt: -1 } and the
     status predicate moved into the leading $match
       IXSCAN, 310,000 documents                          0.9 s

  A to D is 131x, and three of the four changes are one line.
🔑 Read $cursor before anything else in an aggregation explain. If it shows a COLLSCAN or a large nReturned, stop optimising later stages — nothing downstream can recover the cost of reading the collection. Get an indexed, selective first $match, then look at the rest.

What the first stage can and cannot use

Opening stageIndex-capable?
$match with normal query operatorsYes — it becomes an ordinary indexed query
$match with $exprWeakly. Some forms are optimised; many are not. Prefer the query form
$sortYes — an index in that order makes it non-blocking
$geoNearYes, and it requires a geo index. Must be first
$match + $sort togetherYes, if one compound index serves both (ESR order — see How Indexes Work)
Anything after a reshaping stageNo. Once a document has been transformed, indexes are irrelevant

Part 2 — Reduce Before You Compute

The rule is one sentence: every stage that removes data should come before every stage that adds or computes it. Here is what following it is worth.

MEASURED: six stages, two orders

  BEFORE                                  AFTER
    $set    (compute a label)               $match  (indexed)
    $lookup (join users)                    $sort
    $unwind                                 $limit 100
    $sort                                   $lookup
    $set    (compute another field)         $unwind
    $limit 100                              $set, $set
    $match  (filter!)
                    9.1 s                            240 ms
       peak memory 3.2 GB                     peak memory 41 MB
       spilled to disk                        no spill

  Nothing was added or removed. The stages were reordered.
MoveWhy it paysTypical effect
$match to the frontBecomes an indexed query; every later stage sees fewer documentsThe largest single win, usually 10–100×
Split a mixed $matchThe optimiser cannot push a $match forward if any clause depends on an earlier stage — but you can split itRemoves the join cost for the filtered-out majority
$project/$unset before $unwind$unwind multiplies the stream; unused fields are multiplied too2–5× on memory
$sort adjacent to $limitCoalesces into a bounded top-k holding k documents instead of all of them3.2 GB → 40 MB in the measured case
$limit before $lookup100 joins instead of millionsOften the difference between seconds and milliseconds
Computation last$set/$project expressions run per document; run them on the survivorsProportional to how much you filtered
  THE SPLIT THAT THE OPTIMISER CANNOT DO FOR YOU

  { $lookup: { from: "customers", ... , as: "c" } },
  { $unwind: "$c" },
  { $match: { "c.region": "eu",                    // needs the join
              createdAt: { $gte: cutoff } } }      // does NOT

  Both clauses sit in one $match, so nothing moves. Split it:

  { $match: { createdAt: { $gte: cutoff } } },     // indexed, first
  { $lookup: { ... } },
  { $unwind: "$c" },
  { $match: { "c.region": "eu" } }

  If the date filter keeps 3% of orders, you just removed 97% of
  the join work with a two-line edit.

Part 3 — $lookup Economics

  $lookup executes, conceptually, one query against the foreign
  collection PER INPUT DOCUMENT. It is an N+1 inside the database.

  Which means everything depends on two numbers:
    N = how many documents reach the $lookup
    cost of one foreign lookup (indexed or not)

MEASURED: the same join, four ways

  1.24M orders joined to customers

  A. foreignField not indexed
       COLLSCAN of customers per input document        47 s
  B. foreignField indexed (_id)                        2.1 s
  C. reduced N first ($match before the $lookup,
     3% of orders survive)                             94 ms
  D. sub-pipeline form: filter and project INSIDE
     the join, so less crosses the boundary          180 ms
     (on the full 1.24M input -- compare with B)

  THE SUB-PIPELINE FORM

  { $lookup: {
      from: "orders",
      let: { cid: "$_id" },
      pipeline: [
        { $match: { $expr: { $eq: ["$customerId", "$$cid"] } } },
        { $match: { status: "paid" } },        // filter INSIDE
        { $sort:  { createdAt: -1 } },
        { $limit: 3 },                         // bound INSIDE
        { $project: { total: 1, createdAt: 1 } }
      ],
      as: "recentOrders" } }

  Three things this buys:
    - the joined array is bounded by construction, so the 16 MB
      document limit can never be hit
    - only the fields you need cross the boundary
    - $$cid is a let variable; $customerId is a field of the
      FOREIGN document. Confusing the two matches nothing, silently
SituationUseWhy
Small N, indexed foreign key, need the whole document$lookup localField/foreignFieldSimplest, and fast enough
Need only some joined rows, or only some fieldsSub-pipeline with letFilters and bounds inside the join
A page of ~20 rows in an applicationBatched $in in the applicationMeasured 7 ms versus 2,100 ms — one extra round trip beats 20 server-side joins
Small, static reference dataUncorrelated sub-pipeline (no let)Runs exactly once for the whole aggregation
Sharded foreign collectionReconsider the schemaCross-shard joins broadcast; 2.1 s became 25.4 s in the measured case
⚠️ An unindexed $lookup gives no warning. It does not fail, it does not log, and the top-level explain shows a normal stage. The only place it is visible is the nested inner plan inside the $lookup stage of an executionStats explain. A COLLSCAN there against a foreign _id field is also diagnostic of something worse: it usually means a type mismatch (a string customerId against an ObjectId _id), which means some joins are already silently returning empty arrays.

Part 4 — Memory, Honestly

  Budget: 100 MB PER BLOCKING STAGE.
  Not per pipeline. Not per document. Per stage.

  Which stages hold memory, and proportional to what:

    $sort      the whole input, unless coalesced with $limit
               (then k documents) or served by an index (then none)
    $group     ONE ENTRY PER DISTINCT KEY, plus each accumulator's
               state. Document count is almost irrelevant
    $facet     each branch's blocking stages, all live at once
    $setWindowFields   one partition at a time
    $bucket    one entry per bucket -- naturally small
    $graphLookup   the visited set; capped at 100 MB and
               allowDiskUse does NOT lift it

MEASURED: cardinality predicts a spill, volume does not

  $group over 41M orders

  _id: "$status"          4 distinct keys        1.2 MB   1.9 s
  _id: "$customerId"      2.1M distinct keys      410 MB  SPILLED
  _id: "$orderId"         41M distinct keys       8.2 GB  SPILLED
                                                          hard
  Same input size every time. The only variable is how many
  groups exist.

  Two ways out, in order of preference:
    1. reduce the input first (a $match, or a coarser key --
       group by month instead of by day, by customer instead of
       by order)
    2. accept the spill, but only in a batch job, on a secondary,
       with allowDiskUse and maxTimeMS
SymptomCauseFix
Exceeded memory limit for $sortSorting the whole streamIndex the sort order, or coalesce with an adjacent $limit
Exceeded memory limit for $groupToo many distinct keysFilter first, or use a coarser grouping key
BSONObjectTooLarge after $groupAn unbounded $push/$addToSet$topN, bounded by construction

The last row is the one that reaches production. A $group by customer over a 5,000-document staging set has 40 groups and 200 KB of state. The same pipeline in production has 2.1 million groups and 410 MB. Nothing about the code changed; the shape of the data did, and no amount of code review catches it.

Part 5 — Aggregations on a Sharded Cluster

  A sharded aggregation is split in two:

    SHARD PART   runs on every targeted shard, in parallel
    MERGE PART   runs on ONE node -- a random shard, or the
                 PRIMARY SHARD for some stages

  mongos splits the pipeline at the first stage that cannot be
  parallelised, and everything from there runs on the merger.
StageWhere it runs
$match, $project, $unwind, $limitOn every shard, in parallel
$sortPartially on shards, then a merge-sort on the merger
$groupBoth — a partial group per shard, then a final group on the merger
$facet, $graphLookup, $out, $lookup (in most forms)Merging node only, and often forced onto the primary shard
$mergeWrites distributed, coordinated by the merger
MEASURED: what the summary hides

  12 shards, orders sharded on { customerId: "hashed" }

  db.orders.aggregate([
    { $match: { createdAt: { $gte: cutoff } } },   // no shard key!
    { $group: { _id: "$region", revenue: { $sum: "$amount" } } }
  ])

  shardsTargeted: 12         <- a broadcast
  Each shard: IXSCAN on createdAt, partial $group, ~40 rows out
  Merger: final $group over 480 partial rows

  Total 380 ms and it looks fine. It is not fine at scale:
  every one of these queries occupies all 12 shards. At 200
  queries/sec that is 2,400 shard operations/sec of pure
  coordination, and ADDING A SHARD MAKES IT WORSE.

  With the shard key in the $match:
    { $match: { customerId: cid, createdAt: { $gte: cutoff } } }
    shardsTargeted: 1     -- 12x less cluster work
RuleReason
Include the shard key in the leading $match whenever possibleTurns a broadcast into a targeted query
Do the heavy reduction in shard-parallel stages$match, $project and the partial $group all scale with shard count; merge stages do not
Avoid $facet, $graphLookup and unindexed $lookup on sharded collectionsThey collapse the work onto one node, which then becomes the bottleneck for the whole cluster
Check shardsTargeted and mergeType in explainmergeType: "primaryShard" means one node is doing work that could not be distributed

Part 6 — The Decision Before the Optimisation

Everything above assumes the pipeline should run when it runs. Often the largest available win is deciding that it should not.

QuestionIf the answer is…Then
How fresh must the result be?"Within an hour is fine"Pre-compute with $merge; the request reads a document
How many distinct results exist?"A few hundred rows"Materialise all of them; do not compute per request
Who runs it?"Every page load"Cache it, even for 60 seconds — that is a 99% reduction at 100 rps
Where does it run?"The primary"Move it to secondaryPreferred or an analytics node at minimum
Can the first stage use an index?"No"It does not belong on a request path at all

🔑 Monitor aggregations as a distinct class of work. They show up in the profiler with command.aggregate, and the fields worth alerting on are usedDisk: true (a spill that will get worse), millis above a threshold, and a rising count of a shape you thought was scheduled — the classic regression is a nightly rollup that someone quietly wired into a request handler. Group by queryHash and rank by total time, exactly as in Query Tuning in Production; an aggregation run 10,000 times an hour at 40 ms outranks the report everyone complains about.

Interview Questions

Beginner: What is the single most important stage for aggregation performance?

The first one, because only the first stage can use an index to reduce how many documents enter the pipeline, and everything after it is proportional to that number.

In one measured case the same result took 118 seconds with $group first and 0.9 seconds with a selective indexed $match first. No later stage can undo the cost of having read 41 million documents, so if the $cursor section of the explain shows a COLLSCAN, that is where the work is — not in the stages that look complicated.

Beginner: Why is $lookup sometimes very slow?

Because it performs a lookup against the foreign collection for each input document — an N+1 inside the database. Two things determine the cost: how many documents reach the $lookup, and whether the foreignField is indexed.

Unindexed, each input document causes a scan of the foreign collection: 47 seconds versus 2.1 indexed, in the case I have measured. And the unindexed version gives no warning — the top-level explain shows a normal stage, and only the nested inner plan reveals the COLLSCAN.

The other half is reducing N. Moving a $match before the $lookup so only 3% of documents are joined took the same query from 2.1 seconds to 94 milliseconds.

Mid: A $group works in staging and exceeds the memory limit in production. Why?

Because $group memory is proportional to the number of distinct group keys, not to the number of input documents, and staging has different cardinality. The same 41M-document input grouped by status (four keys) used 1.2 MB; grouped by customerId (2.1 million keys) it used 410 MB and spilled.

Staging with 5,000 documents and 40 customers has 40 groups. The code is identical, the data shape is not, and no code review catches it.

The fixes in order: reduce the input with a leading indexed $match; use a coarser grouping key if the fine one is not needed (month rather than day, customer rather than order); and only then consider allowDiskUse, which is legitimate for a batch job on a secondary and is a 19× slowdown rather than a fix.

The durable fix is a seeded test dataset with production-like cardinality, because this class of bug is only ever found in production otherwise.

Mid: How does an aggregation execute on a sharded cluster?

mongos splits the pipeline into a shard part and a merge part. The shard part runs in parallel on every targeted shard; the merge part runs on a single node — sometimes an arbitrary shard, sometimes the primary shard specifically. The split happens at the first stage that cannot be parallelised.

$match, $project, $unwind and $limit run on the shards. $group is interesting: it runs in both halves — a partial group per shard, then a final group on the merger, which is why it parallelises well. $facet, $graphLookup and most $lookup forms run only on the merging node, which makes them the stages to avoid on sharded collections.

The number I would check first is shardsTargeted. A pipeline whose leading $match omits the shard key broadcasts to every shard — which can look fine at 380 ms and low volume, and does not scale: adding a shard makes each such query more expensive, not less.

Senior: Walk me through optimising a 22-second aggregation.

Explain first, and read it in a specific order. The $cursor section: is the opening stage an IXSCAN and how many documents does it produce? Then usedDisk, to see whether anything spilled. Then, on a sharded collection, shardsTargeted and mergeType. Then the nested plan inside any $lookup.

Then the ordering pass, which is mechanical and usually where the win is: can the opening $match use an index; is there a $match later that could be split so its join-independent half leads; are $sort and $limit adjacent; is there a projection before any $unwind or $lookup; is every accumulator bounded. In a measured case those changes alone took 9.1 seconds to 240 milliseconds with no stage added or removed.

Then verify by re-running the explain and comparing the same numbers — not by impression.

But the question I would ask before any of it is why it runs at all. If it is on a request path, the largest available win is usually not making it faster — it is pre-computing it with $merge so the request reads a document. On the dashboard I have measured, careful tuning gave 4.6× and pre-computation gave another 55×, and the pre-computed version's cost is independent of traffic.

And one thing that is easy to miss: moving the aggregation off the primary changed no latency at all for the aggregation itself, but took unrelated p99 from 34 ms to 4 ms, because the primary's cache had been getting churned. Large scans and low-latency point reads want opposite things from a cache, and that cost lands on queries nobody has connected to the dashboard.

Senior: When should an aggregation not run on the operational database at all?

My test is whether the first stage can use an index to reduce the input to something small. If it cannot — if the pipeline's job is inherently to read a large fraction of a large collection — then it is a batch workload, and running it on the operational cluster means it competes for the same cache and CPU as the writes and point reads the product depends on.

The ladder I would walk, cheapest first: run it on a secondary or hidden analytics member; pre-compute it with $merge so requests read documents; and only then move the workload out entirely, to a warehouse or an analytical store.

Most "we need a data warehouse" conversations, at the scale most products actually operate at, are satisfied by the middle rung — a handful of scheduled pipelines writing summary collections. That costs staleness, which is a product decision I would put in front of whoever owns the dashboard with the actual numbers attached rather than deciding on their behalf.

The genuine signals to move out: ad-hoc exploration over full history (no fixed set of materialised views satisfies it), joins across many collections that keep growing, retention requirements measured in years, and analysts who need to write their own queries. Those are not tuning problems, and treating them as tuning problems is how an operational cluster ends up sized for reporting.

What I would resist: moving out prematurely. A warehouse is a pipeline to build, a freshness contract to maintain, and a second copy of the truth to reconcile. If three scheduled $merge jobs solve it, that is a week of work rather than a quarter, and it can be reversed.

🏋️ Exercises

1 (easy): Reorder this pipeline and state the expected effect of each move. 
  db.orders.aggregate([
    { $set:   { year: { $year: "$createdAt" } } },
    { $sort:  { total: -1 } },
    { $limit: 50 },
    { $match: { status: "paid" } }
  ])
Solution

First, note that this is also wrong, not just slow: the $match applies to the 50 highest-value orders of any status, so it returns however many of those happen to be paid — not the 50 highest-value paid orders. A pipeline that filters last usually has this bug.

  db.orders.aggregate([
    { $match: { status: "paid" } },      // 1. indexed, and correct
    { $sort:  { total: -1 } },           // 2. adjacent to...
    { $limit: 50 },                      //    ...the limit
    { $set:   { year: { $year: "$createdAt" } } }   // 3. on 50 docs
  ])

  index: { status: 1, total: -1 }
MoveEffect
$match to the frontBecomes an IXSCAN; fixes the correctness bug
$sort+$limit kept adjacentCoalesces into a top-50 sort holding 50 documents rather than all matches
$set moved lastThe $year expression runs 50 times instead of once per order in the collection
The indexWith { status: 1, total: -1 } the sort comes from the index too, so there is no SORT stage at all and the scan stops after 50 keys

With that index the pipeline examines roughly 50 index keys and fetches 50 documents, regardless of collection size.

2 (easy): This explain fragment is from a slow aggregation. What is wrong, and what would you check next? 
  "$cursor": {
     "queryPlanner": { "winningPlan": { "stage": "COLLSCAN" } },
     "executionStats": { "nReturned": 4100000,
                         "totalDocsExamined": 4100000,
                         "executionTimeMillis": 8200 }
  },
  ... later stages ...
  "usedDisk": true
Solution

What is wrong: the pipeline reads all 4.1 million documents before doing anything. Everything else — including the spill — is a consequence. The usedDisk: true is not an independent problem; a blocking stage exceeded 100 MB precisely because 4.1 million documents reached it.

The order to investigate:

  1. Is there a $match at all? If not, does the report genuinely need every document, or has a date/status filter been left out?
  2. If there is one, why is it a COLLSCAN? Likely causes: no index on the predicate field; the $match is not first; it uses $expr or a computed expression ({ $year: "$createdAt" }) that cannot be indexed; or it uses $ne/$nin/an unanchored regex.
  3. Can a $match that appears later be split so a join-independent, indexable half moves to the front?

What I would not do: add allowDiskUse: true. It would stop the error and make it slower — the measured penalty is around 19×. The spill is a symptom telling you the pipeline is carrying data it should have filtered out.

What I would check next in the explain: which stage spilled (it names the stage in the error or the stage-level stats), because that tells you whether the fix is a filter, a coarser $group key, or an index for a $sort.

3 (medium): This runs in 240 ms for most customers and 40 seconds for the biggest one. Diagnose and fix. 
  db.customers.aggregate([
    { $match: { _id: cid } },
    { $lookup: { from: "orders", localField: "_id",
                 foreignField: "customerId", as: "orders" } },
    { $set: { recent: { $slice: [ { $sortArray: {
                 input: "$orders", sortBy: { createdAt: -1 } } }, 10 ] },
              ltv: { $sum: "$orders.total" } } },
    { $unset: "orders" }
  ])
Solution

Diagnosis: the $lookup pulls every order for the customer into an array inside a single document, then sorts that array in memory and discards all but 10. For a customer with 50 orders that is trivial. For one with 400,000 it is a 400,000-element array in one document — which is both enormous to build and at risk of the 16 MB document limit, at which point the pipeline does not get slower, it fails.

The cost is proportional to the customer's order count, which is exactly the "works for most, fails for the biggest" signature.

  db.customers.aggregate([
    { $match: { _id: cid } },
    { $lookup: {
        from: "orders",
        let: { cid: "$_id" },
        pipeline: [
          { $match: { $expr: { $eq: ["$customerId", "$$cid"] } } },
          { $sort:  { createdAt: -1 } },
          { $limit: 10 },
          { $project: { total: 1, createdAt: 1, status: 1 } }
        ],
        as: "recent" } }
  ])

  index: { customerId: 1, createdAt: -1 }

Now the join returns at most 10 small documents regardless of the customer, the sort is served by the index inside the sub-pipeline, and the 16 MB limit is unreachable by construction.

The ltv field needs a different answer, because it genuinely depends on every order and no bounded join can produce it. Three options:

OptionTrade-off
A second uncorrelated $lookup doing a $group sum inside the sub-pipelineReturns one number instead of 400,000 documents — far better than the original, but still scans all the customer's orders on every request
Maintain ltv on the customer document, $inced at order timeExact and instant; needs a reconciler because counters drift through failed writes and refunds
Nightly rollup into a customer_stats collectionCheapest to operate; stale by the job interval

I would take the second: users notice immediately if their own lifetime total is wrong, so exactness matters here in a way it does not for, say, a percentile rank. The reconciler is a weekly job that recomputes a sample and alerts on mismatches.

4 (medium): A pipeline is fine on 11 shards and slow on the 12th. What could cause that, and how would you investigate?
Solution

The most likely causes, in order of probability:

CauseHow to confirm
Data skew — the shard key concentrates a disproportionate share of matching documents on that shardPer-shard nReturned and docsExamined in the explain's shards section; sh.status() chunk distribution
It is the primary shard and the pipeline has a merge-only stage ($facet, $graphLookup, $lookup)mergeType in the explain; that shard is doing the merge plus its own share
A missing or different index on that shardCompare getIndexes() across shards — a rolling index build that failed partway leaves exactly this state
Hardware or cache differenceserverStatus().wiredTiger.cache on that member; a smaller instance or a colder cache after a restart
Another workload on that shardcurrentOp; a backup, a resync, or an index build

The investigation order: read the per-shard stats in the explain first, because they separate "this shard has more work" (skew) from "this shard is slower at the same work" (index, hardware, contention). That one distinction eliminates half the list immediately.

If it is skew, the fix is not a pipeline change — it is the shard key, and that is a significant piece of work. The interim mitigations are including the shard key in the leading $match where possible so most queries do not touch that shard at all, and checking whether a jumbo chunk is blocking the balancer.

If it is the merge concentrating on the primary shard, the fix is restructuring the pipeline to avoid merge-only stages, or pre-computing the result so the pipeline runs on a schedule rather than on requests.

What I would check before all of this: whether the pipeline includes the shard key at all. If it broadcasts to 12 shards, the "slow shard" may simply be the one whose latency dominates a scatter-gather — and the real finding is that the query should not be broadcasting.

What I would ship and when: 1, 2 and 4 immediately — they are low-risk, mechanical, and likely to take 8 minutes to well under one. 5 in the same change, because it costs nothing and fixes a problem nobody has attributed to this report. 3 as a follow-up with careful before/after row comparison. 6 only if the report is run often enough to justify a scheduled job — for something run twice a month, an 8-minute pipeline that becomes a 40-second one on a secondary is finished work, and building a materialised view for it is over-engineering.

The structural question I would raise alongside the plan: four joins in an operational database is a signal. It may mean the schema is modelled relationally and the read pattern is fighting it — see Embed vs Reference — or it may mean reporting has grown into the operational cluster without anyone deciding it should. Neither is fixed by optimisation, and both get more expensive to address later. I would put the numbers in front of whoever owns the roadmap rather than absorbing it quietly as a tuning task.

6 (hard): Design the monitoring that would have caught every problem in this lesson before a user did.
Solution

The design principle: alert on properties that predict future failure, not just on current latency. Every problem in this lesson had a leading indicator that was visible before it became an incident.

Plus a CI gate, because the cheapest incident is the one that never ships: run each registered pipeline against a seeded dataset with production-like cardinality and fail the build on a COLLSCAN opening stage, a spill, or an unindexed inner $lookup plan. Cardinality is the part that matters and the part everyone omits — a fixture with 40 customers cannot reproduce a 2.1-million-group spill.

What I would deliberately not alert on: raw aggregation latency thresholds. A batch rollup legitimately takes minutes, and an alert that fires on it every night gets muted, taking the useful alerts with it. Alert on the properties (COLLSCAN, spill, staleness, drift) and let duration be a dashboard.

Ordering, if I could only build some of it: the profiler ranking and the usedDisk alert first — a day's work, and between them they surface most of what this lesson describes. Then view staleness, because a silently dead rollup is the failure that damages trust the most. The cardinality scan and the CI gate last; they are the most work and they prevent rather than detect.

🎯 Key Takeaways

  • The first stage decides everything. Read $cursor in the explain before optimising anything else — 118 s versus 0.9 s for the same result.
  • Only the opening stage can use an index. After any reshaping, indexes are irrelevant.
  • Reduce before you compute — reordering six stages went from 9.1 s and a 3.2 GB spill to 240 ms and 41 MB, with nothing added or removed.
  • Split a mixed $match yourself. The optimiser cannot push it forward if any clause depends on an earlier stage.
  • Keep $sort and $limit adjacent, and put $limit before $lookup.
  • $lookup is an N+1 inside the database. Cost is (documents reaching it) × (cost of one foreign lookup).
  • An unindexed $lookup is silent — 47 s versus 2.1 s, visible only in the nested inner plan.
  • A COLLSCAN on a foreign _id means a type mismatch, which is a correctness bug before it is a performance one.
  • The sub-pipeline form filters, sorts and bounds inside the join, which also makes the 16 MB limit unreachable by construction.
  • For a page of rows, a batched $in in the application beats $lookup — 7 ms versus 2,100 ms.
  • Memory is 100 MB per blocking stage, and $group memory tracks distinct keys: 4 keys = 1.2 MB, 2.1M keys = 410 MB, on identical input.
  • Cardinality, not volume, predicts a spill — which is why staging never reproduces it.
  • On a sharded cluster, $group runs twice (partial per shard, final on the merger), while $facet and $graphLookup run only on the merging node.
  • Check shardsTargeted. A broadcast can look fine at 380 ms and gets worse with every shard you add.
  • Moving a rollup off the primary changed its own latency by nothing and took unrelated p99 from 34 ms to 4 ms.
  • Pre-computation beats tuning. On one dashboard, tuning gave 4.6× and $merge gave another 55× — with cost independent of traffic.
  • If the first stage cannot use an index to shrink the input, the pipeline is batch work, whatever the code that calls it looks like.
