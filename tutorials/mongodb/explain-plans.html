Reading Explain Plans Indexes

What you'll master: how to read explain() the way an engineer reads a stack trace — bottom-up, because the stage tree executes from the leaves inward, and the top-level summary is the last thing that happens, not the first; the three verbosity levels and why queryPlanner alone has misled more people than any other MongoDB output (it reports a plan chosen against a trial sample, with no execution numbers at all); the four numbers that diagnose every slow query and the three ratios between them that name the defect precisely — docsExamined ≫ nReturned means a missing filter field, keysExamined ≫ nReturned means loose bounds, and a SORT stage means you lost the ordering; how to actually read indexBounds, including the [MinKey, MaxKey] entry that means "this field contributed nothing" and is the single fastest way to spot a wasted compound field; the plan cache — why a query that was fast for six months went to 4.2 seconds after a deploy that changed nothing, how the trial period picks a winner from a 101-document sample that is not representative, and what planCacheKey, works and cache eviction actually mean; and the parts that behave differently — aggregation pipelines, sharded clusters where the summed docsExamined hid a broadcast to all 12 shards, and the operations explain silently refuses to model. Prerequisites: How Indexes Work and Index Types & Their Traps.

Part 1 — Three Verbosity Levels, Three Different Questions

ModeRuns the query?AnswersUse when
"queryPlanner" (default)NoWhich plan would be chosen, and what bounds it would useYou are designing an index and want to know if it is eligible
"executionStats"Yes, the winning planWhat it actually cost: keys, docs, time, stage-by-stageAlmost always. This is the default you should have
"allPlansExecution"Yes, all candidates through the trial periodWhy the planner chose this plan over the othersThe planner picked something you disagree with
  db.orders.find({ status: "paid" }).explain("executionStats")

  db.orders.explain("executionStats")
           .find({ status: "paid" })     // same thing, chainable form

  db.orders.explain("executionStats")
           .aggregate([ ... ])           // aggregation form

  // and for an update/delete, which you cannot easily test otherwise:
  db.orders.explain("executionStats")
           .update({ status: "paid" }, { $set: { x: 1 } })
  // explain does NOT apply the update. Safe to run in production.
⚠️ Default explain() with no argument runs queryPlanner, which executes nothing. It tells you which index the planner believes is best, based on a trial over a small sample — and it reports no keys examined, no documents examined and no time. Every "the explain looked fine but the query is slow" conversation starts here. Get in the habit of typing explain("executionStats") every time; the extra 17 characters are the difference between a plan and a measurement.

Part 2 — The Stage Tree, Read Bottom-Up

The winningPlan is a tree. Each stage has an inputStage (or inputStages) beneath it. Data flows upward from the leaves, so the deepest stage runs first and the outermost stage runs last — the opposite of the reading order.

  "winningPlan": {
    "stage": "LIMIT",              <- 4th: stop after 20
      "inputStage": {
        "stage": "SORT",           <- 3rd: sort them in memory  (BAD)
          "sortPattern": { createdAt: -1 },
          "memLimit": 33554432,
          "inputStage": {
            "stage": "FETCH",      <- 2nd: read each document
              "filter": { region: { "$eq": "eu" } },
              "inputStage": {
                "stage": "IXSCAN", <- 1st: scan the index
                  "indexName": "status_1",
                  "indexBounds": { status: [ "[\"paid\", \"paid\"]" ] }
              }}}}

  Reading it bottom-up as a sentence:
    "Scan the status_1 index for status = paid, fetch every matching
     document, throw away the ones where region is not eu, sort what
     is left in memory by createdAt, then keep 20."

  Three defects are visible in that sentence:
    - region is filtered AFTER the fetch  -> not in the index
    - SORT is a stage             -> the index did not supply order
    - LIMIT is above SORT         -> the limit saves NOTHING; every
                                     matching document was read and
                                     sorted before 20 were kept

The stage catalogue

StageMeaningGood sign?
COLLSCANReading every document in the collectionOnly on tiny collections or deliberate full scans
IXSCANScanning a contiguous range of index keysYes — but check keysExamined, an IXSCAN can scan the whole index
FETCHReading the full document for a RecordId from the indexNormal, unless docsExamined ≫ nReturned, or it carries a filter
FETCH with a filterDocuments are being read and then rejectedNo. That field belongs in the index
PROJECTION_COVEREDAnswered from index keys alone, no document readThe best possible outcome
PROJECTION_SIMPLE / _DEFAULTFields trimmed after fetchingNeutral — it is not a covered query
SORT + SORT_KEY_GENERATORBlocking in-memory sort, 32 MB cap (unless allowDiskUse)No. Order should come from the index
LIMIT / SKIPRow cutoffOnly helps if it is below any SORT in the tree
COUNT_SCANCounting from index keys with no fetchExcellent — a covered count
DISTINCT_SCANIndex seek that skips duplicate keysExcellent, and a reason to prefer distinct() over $group where it applies
AND_SORTED / AND_HASHIndex intersection of two indexesUsually means a compound index is missing
OR / SUBPLANA $or planned as separate branches, results deduplicatedFine — if every branch is indexed. One unindexed branch scans the collection
SHARD_MERGE / SHARDING_FILTERMerging shard results / discarding orphaned documentsExpected on sharded collections; see Part 6
EOFThe planner proved the query matches nothingFree — e.g. a contradictory predicate

Part 3 — Four Numbers and Three Ratios

  "executionStats": {
    "nReturned":            20,
    "totalKeysExamined": 412000,
    "totalDocsExamined": 412000,
    "executionTimeMillis": 1840
  }

The absolute values matter less than the relationships between them. Three comparisons diagnose almost every slow query, and each names a different defect with a different fix.

ObservationDiagnosisFix
keysExamined ≈ docsExamined ≈ nReturnedIdeal. The index found exactly the right rowsNothing
docsExamined == 0 with an IXSCANCovered query — the best caseNothing
docsExamined ≫ nReturned, and docsExamined ≈ keysExaminedA filter field is not in the index; every candidate is fetched then rejectedAdd that field to the index (in ESR position)
keysExamined ≫ docsExaminedThe index bounds are loose but the index can reject rows without fetching — usually a non-prefix field, or a multikey rangeReorder the index so the selective field leads; or $elemMatch for arrays
keysExamined ≫ nReturned with a SORT stageEvery match is being read to sort it; limit is saving nothingMove the sort field into the index, after equality, before range
COLLSCAN with a large docsExaminedNo usable index — or a predicate that cannot use one ($ne, $nin, unanchored $regex, $where)Create an index; or rewrite the predicate as a positive range
Low examined counts, high executionTimeMillisNot a query-shape problem. Disk reads (cold cache), lock contention, or a saturated serverCheck cache hit rate and currentOp, not the index

That last row is the one people miss, and it changes the whole investigation. A query examining 50 keys and taking 900 ms is not badly indexed — it is waiting for something. The distinguishing check:

  // is the query itself slow, or is the SERVER slow?
  db.orders.find({ ... }).explain("executionStats")
    .executionStats.executionTimeMillis      -> 900

  Run it twice. If the second run is 3 ms, the first was reading
  from disk: the working set is not in cache. That is a capacity
  problem, not an index problem, and adding an index makes it
  slightly worse.

  Confirm with:
    db.serverStatus().wiredTiger.cache
      ["pages read into cache"]                  rising fast
      ["pages evicted by application threads"]   > 0 = the cliff

executionTimeMillis is not what you think

It measures the query's execution, including the planner's trial period on the first run. It excludes network transfer to the client and it excludes time spent waiting for the client to request more batches. So a query reported at 4 ms can take 900 ms end-to-end if the driver iterates a cursor of 200,000 documents in 101-document batches over a slow link. When the explain looks fast and the application does not, measure at the driver, and check nReturned — the fix is usually a limit, a projection, or a larger batchSize, not an index.

Part 4 — Reading indexBounds

This is the most information-dense part of the output and the most skipped. It shows, per indexed field, the exact key range the scan will cover.

  index: { status: 1, region: 1, createdAt: -1 }

  QUERY: { status: "paid", region: "eu",
           createdAt: { $gte: ISODate("2026-08-01") } }

  "indexBounds": {
    "status":    [ "[\"paid\", \"paid\"]" ],
    "region":    [ "[\"eu\", \"eu\"]" ],
    "createdAt": [ "[new Date(9999999999999), new Date(1754006400000)]" ]
  }

  Read it as:
    status    exact point   (equality  -- tightest possible)
    region    exact point   (equality)
    createdAt bounded range (descending index, so hi..lo)

  All three fields contribute. This is a fully-bounded scan.

  THE BOUND THAT MEANS "THIS FIELD DID NOTHING"

  QUERY: { status: "paid", createdAt: { $gte: ... } }
         (region omitted)

  "indexBounds": {
    "status":    [ "[\"paid\", \"paid\"]" ],
    "region":    [ "[MinKey, MaxKey]" ],           <<<<<
    "createdAt": [ "[MinKey, MaxKey]" ]            <<<<<
  }

  [MinKey, MaxKey] = the entire range of that field. The scan
  covers EVERY region and EVERY createdAt within status: "paid".
  The createdAt predicate is applied as a filter DURING the scan,
  not as a bound -- because region sits between them and was
  skipped, so matching keys are not contiguous.

  This is the prefix rule, visible in the output. One glance at the
  bounds tells you which compound fields are earning their place
  and which are dead weight.
Bound you seeWhat it means
["x", "x"]Equality — the tightest possible bound
["x", "z")Range, inclusive lower / exclusive upper (bracket vs parenthesis)
[MinKey, MaxKey]No bound at all — this field contributed nothing
Multiple intervals, e.g. ["a","a"], ["c","c"]An $in — each value gets its own seek, which is efficient
[MinKey, "x"), ("x", MaxKey]A $ne — two disjoint ranges covering nearly the whole index. Effectively unbounded
["", {}) on a string fieldA prefix regex like /^abc/ — anchored, so it is bounded. Unanchored regexes give [MinKey, MaxKey]
🔑 The 10-second index review: read indexBounds top to bottom and stop at the first [MinKey, MaxKey]. Every field below it is contributing nothing to the bound — it is being applied as a filter during the scan at best. If that happens on field two of a five-field index, you are paying to maintain three fields that no query bound ever uses, and the index probably wants reordering or splitting.

Part 5 — The Plan Cache: Why Fast Queries Become Slow

MongoDB does not evaluate plans on every execution. It runs a trial, caches the winner, and reuses it. Understanding that loop explains a whole class of "nothing changed but it got slow" incidents.

  1. First execution of a query SHAPE (fields + operators, not
     values). The planner enumerates candidate plans.

  2. TRIAL PERIOD: each candidate runs interleaved until one of
     them either returns 101 results or examines a fixed number
     of "works" (units of work). The one that gets furthest with
     the least work wins.

  3. The winner is cached against the planCacheKey.

  4. Every later query of that shape reuses the cached plan --
     with no trial, and regardless of its VALUES.

  5. The plan is evicted and re-planned when:
       - performance degrades badly vs the cached expectation
         (the "replan" trigger)
       - an index on the collection is created or dropped
       - the collection is modified (collMod) or dropped
       - the server restarts
       - you call db.coll.getPlanCache().clear()

Step 4 is where the incidents come from. The plan was chosen using one set of values, and is then applied to every other set.

MEASURED: the tenant that broke the plan cache

  Query shape: { tenantId: ?, status: ?, createdAt: { $gte: ? } }
  Indexes:     { tenantId: 1, createdAt: -1 }
               { status: 1, createdAt: -1 }

  The first execution after each restart happened to be from a
  SMALL tenant. For a small tenant, both plans return 101 rows
  almost immediately, and the status_1 plan won by a hair.

  Cached: status_1.

  For the LARGEST tenant, status: "active" matches 4.1M documents
  and tenantId matches 90,000. The cached plan scans 4.1M keys.

    small tenant, cached plan:      6 ms
    large tenant, cached plan:  4,200 ms
    large tenant, correct plan:    31 ms

  Nothing "changed". The plan was always wrong for that tenant; it
  only became visible when that tenant grew. And it was
  intermittent: after a restart, whichever tenant queried first
  decided the plan for everyone.

  INVESTIGATING IT

  // what shapes are cached, and what won
  db.orders.aggregate([ { $planCacheStats: {} } ])
    -> planCacheKey, createdFromQuery, works, isActive,
       cachedPlan, timeOfCreation

  // the key for THIS query -- shows in explain output too
  db.orders.find({...}).explain().queryPlanner.planCacheKey

  // force a re-plan for one collection
  db.orders.getPlanCache().clear()

  // see what the planner rejected and why
  db.orders.find({...}).explain("allPlansExecution")
    -> allPlansExecution[].executionStages, each with its own
       nReturned / works / executionTimeMillisEstimate

works is the planner's own cost unit — roughly "one unit of progress", such as advancing an index cursor or fetching a document. In allPlansExecution it is the number that actually decided the contest, and comparing works across candidate plans tells you what the planner saw that you did not.

The three durable fixes

FixHowTrade-off
Make one plan obviously bestBuild the compound index that serves the whole shape — { tenantId: 1, status: 1, createdAt: -1 } — so there is no close contest to get wrongNone. This is the real fix; the plan cache is not the bug, the ambiguity is
hint()Pin the index for a specific queryBypasses the planner permanently. If the data shifts, nothing adapts, and the hint outlives the person who added it. Use for a genuine emergency, then remove it
Differentiate the shapesSplit into distinct queries so small and large tenants do not share a cache entryApplication complexity, and it treats a symptom
🔑 A plan-cache incident is almost always an index-design signal. The cache only makes the wrong choice when two plans are close enough that a 101-document sample cannot separate them. If one index served the whole query shape — equality fields, then sort, then range — there would be no contest to lose. Reach for hint() to stop the bleeding, then fix the index and remove the hint; a permanent hint is a permanent commitment to today's data distribution.

Part 6 — Aggregations, Sharding, and What Explain Refuses to Do

  db.orders.explain("executionStats").aggregate([
    { $match:  { status: "paid" } },
    { $group:  { _id: "$customerId", total: { $sum: "$amount" } } },
    { $sort:   { total: -1 } },
    { $limit:  10 }
  ])

Aggregation explain output is a list of stages, not a single tree, and the first thing to look for is which stages the optimiser rewrote:

What to checkWhy
Did $match move to the front?The optimiser pushes filters toward the source. If a $match stayed after a $group, it could not be pushed — usually because it references a computed field
Was the first stage absorbed into a query?A leading $match becomes a normal indexed query with its own IXSCAN. If you see a COLLSCAN here, the whole pipeline reads the collection
Did $sort + $limit coalesce?Adjacent, they become a bounded top-k sort that uses far less memory. Separated by another stage, they do not
Did $lookup get an indexed inner plan?The sub-plan appears nested. An unindexed foreignField is invisible in timings until you look here
usedDisk: trueA stage exceeded its 100 MB memory limit and spilled. Correct, but orders of magnitude slower

Sharded clusters: the summary hides the important thing

MEASURED: the query that looked fine and was broadcasting

  Sharded on { customerId: "hashed" }, 12 shards.

  db.orders.find({ createdAt: { $gte: cutoff } })
           .explain("executionStats")

  Top-level summary:
    nReturned            412
    totalDocsExamined    412
    executionTimeMillis  380

  Those numbers look excellent. 412 examined for 412 returned.

  But shards[] had TWELVE entries, each with its own IXSCAN, and
  the top level SUMS them. The query did not target one shard --
  it went to all twelve, each did a scan, and the merger combined
  the results.

  The tells, all of which are above the summary:
    "shardsTargeted": 12          (vs 1 for a targeted query)
    winningPlan.stage: "SHARD_MERGE"
    twelve separate executionStages entries

  At 380 ms and low volume it is invisible. At 8,000 queries/sec
  it is 96,000 shard operations per second, and the cluster cannot
  grow its way out -- adding a shard makes every such query
  MORE expensive, not less.

So on a sharded collection the first number to read is not docsExamined, it is shardsTargeted. A query that does not include the shard key is a broadcast, and broadcasts are the reason sharded clusters stop scaling. See Sharding & Shard Keys.

What explain will not tell you

LimitationDetail
It does not model $out or $mergeThose stages are skipped; the pipeline is explained up to that point
It does not perform writesexplain().update() plans the operation without applying it — which makes it safe, and means it cannot report write conflicts or retries
It does not include time waiting on locks or the clientA query slow because of contention looks fast here; check currentOp and the slow-query log instead
queryPlanner results depend on the current dataAn explain from staging with 5,000 documents predicts nothing about production with 40 million
It reflects the plan cacheRunning explain can return the cached plan rather than a fresh contest. Clear the cache if you want a true re-plan

The complement to explain is the profiler, which reports what actually happened rather than what would happen — including lock waits, response length and the real end-to-end duration:

  db.setProfilingLevel(1, { slowms: 100 })

  db.system.profile.find({ ns: "shop.orders" })
    .sort({ ts: -1 }).limit(5)
    -> millis, planSummary, keysExamined, docsExamined,
       nreturned, responseLength, locks, queryHash, planCacheKey

  planSummary is the fast triage field: "COLLSCAN" or
  "IXSCAN { status: 1 }" tells you the shape without an explain.

  Group by queryHash to find the shapes worth fixing, ranked by
  total time rather than by worst single execution -- a 40 ms
  query run 100,000 times costs more than a 4 s query run twice.

Interview Questions

Beginner: What are the four numbers you look at first in an explain?

nReturned, totalKeysExamined, totalDocsExamined and executionTimeMillis — and the first three matter mostly as ratios against each other.

The ideal is all three roughly equal: the index found exactly the documents you wanted. Even better is docsExamined: 0, which means the query was covered by the index and never touched the collection. Anything where examined counts are orders of magnitude above nReturned is work being thrown away, and which of the two counts is inflated tells you whether the problem is loose bounds or a missing filter field.

Beginner: Why is a SORT stage in the plan a warning sign?

Because it means the index did not supply the ordering, so MongoDB is doing a blocking in-memory sort. Three consequences: it has a 32 MB limit and fails outright above it (unless allowDiskUse, which is slow); nothing is returned until the last input document has been read; and any limit above it saves no work at all, because every match must be read and sorted before the top N can be identified.

The fix is to place the sort field in the index — after the equality fields, before any range field. In one measured case that took a query from 310 ms with 41,000 keys examined to 2 ms with 112.

Mid: An explain shows keysExamined: 412000, docsExamined: 412000, nReturned: 20. Diagnose it.

The equality of keys and docs is the key signal: every index key scanned resulted in a document fetch, and then 411,980 of those documents were discarded. That means the index bounded the scan on something, but a predicate the index does not contain is being applied after the fetch — you would see it as a filter on the FETCH stage.

The fix is to add that field to the index so the filtering happens on keys rather than documents. If there is also a SORT stage, the field ordering matters: equality fields, then the sort field, then ranges.

Contrast with keysExamined ≫ docsExamined, which is a different defect — there the index is rejecting rows without fetching, so the bounds are loose (often a skipped compound field or a multikey range) and the fix is reordering rather than adding.

Mid: What is [MinKey, MaxKey] in indexBounds and why does it matter?

It means the scan spans that field's entire range — the field contributed nothing to bounding the scan. It appears when a compound field is skipped by the query, because the prefix rule means every field after the gap is unbounded too.

It matters because it is invisible in the summary numbers and it is the fastest way to audit a compound index. Read the bounds top to bottom and stop at the first [MinKey, MaxKey]: every field below it is dead weight for this query. If that happens on field two of a five-field index, you are paying write cost and cache for three fields no query bound uses, and the index wants reordering or splitting.

Senior: A query was fast for six months and is now 4 seconds, with no deploy and no schema change. Walk me through it.

My first hypothesis is the plan cache, because "nothing changed" plus a step change in latency is its signature.

MongoDB caches one plan per query shape, chosen by a trial period that stops at roughly 101 results. If two plans are close on a small sample, the winner is effectively arbitrary — and it is then applied to every set of values, including ones for which it is catastrophically wrong. The case I have seen: a multi-tenant query where the first execution after a restart came from a small tenant, so a status index won; for the largest tenant that index matched 4.1M documents where the tenantId index matched 90,000. Same shape, 6 ms versus 4,200 ms, and intermittent — whichever tenant queried first after a restart decided the plan for everyone.

How I would confirm it: $planCacheStats to see what is cached and when it was created; explain("allPlansExecution") to see the rejected plans and their works counts; and the profiler grouped by planCacheKey to see whether latency correlates with a plan change rather than with traffic.

What else I would rule out in parallel: data growth crossing the cache boundary (examined counts unchanged but time up, with rising application-thread evictions), an index dropped by a migration, and a distribution shift that made a previously-selective predicate unselective.

The fix is not hint(), except as a stopgap. A plan-cache incident means two plans were close enough that a small sample could not separate them, which means no single index serves the whole query shape. I would build the compound index that does — equality, sort, range — so there is no contest to lose, and then remove any hint I added. A permanent hint freezes today's data distribution and outlives the person who wrote it.

Senior: How would you build a systematic process for finding and fixing slow queries, rather than reacting to complaints?

Explain is a debugging tool for one query; the process has to start somewhere else, because you cannot explain a query you do not know is slow.

1. Collect. Profiler at level 1 with a threshold matched to the workload — 100 ms is a reasonable start, but for a 5 ms API the threshold should be far lower. Cap the profile collection size so it cannot fill a disk.

2. Rank by total time, not worst case. Group by queryHash and sort by count × mean. A 40 ms query run 100,000 times an hour costs far more than a 4-second report run twice a day, and the 4-second one is what gets reported by humans. This inversion is the main value of the process.

3. Triage with planSummary. It is in the profiler output already, so COLLSCAN entries can be found and fixed without opening an explain at all.

4. Explain the survivors with executionStats, apply the ratio diagnosis, and check indexBounds for dead compound fields.

5. Close the loop. An index change that is not verified is a guess: re-run the same profiler aggregation after deploying and compare the same queryHash. And check $indexStats afterwards for indexes the change made redundant — an optimisation that only ever adds indexes eventually becomes a cache problem.

The organisational half, which matters more than the technical half: this needs to be a scheduled review with an owner, not a heroic effort during an incident. I would also put the profiler aggregation in CI against a production-shaped dataset so a new COLLSCAN fails the build rather than being discovered three months later. The cheapest slow query to fix is the one that never ships.

What I would be careful about: profiling at level 2 (all operations) on a busy primary has real overhead and generates a lot of writes. Level 1 with a sensible threshold, or sampling, is almost always the right setting — and I would run the analysis against a secondary where possible.

🏋️ Exercises

1 (easy): Read this plan bottom-up and describe in one sentence what the database did. Then name the two defects. 
  { stage: "LIMIT", limitAmount: 10,
    inputStage: { stage: "SORT", sortPattern: { price: 1 },
      inputStage: { stage: "FETCH", filter: { inStock: { $eq: true } },
        inputStage: { stage: "IXSCAN", indexName: "category_1",
          indexBounds: { category: [ "[\"shoes\", \"shoes\"]" ] } }}}}
Solution

The sentence: "Scan the category_1 index for category = shoes, fetch every one of those documents, discard the ones that are out of stock, sort what remains by price in memory, then return the first 10."

Defect 1 — inStock is filtered after the FETCH. Every shoe document is read from disk or cache just to check a boolean. If shoes are 40,000 documents and 30,000 are in stock, that is 40,000 document reads to eventually return 10.

Defect 2 — the SORT is blocking, and the LIMIT is above it. All 30,000 in-stock shoes must be sorted before the top 10 can be identified. The limitAmount: 10 looks like it bounds the work and bounds nothing. It is also at risk of the 32 MB sort limit as the catalogue grows.

The fix, applying ESR:

  db.products.createIndex({ category: 1, inStock: 1, price: 1 })

  category  equality -> bounds the scan
  inStock   equality -> bounds it further, on KEYS not documents
  price     sort     -> keys already in price order, no SORT stage

Now the scan walks in-stock shoes in price order and stops after 10 keys. Expected: keysExamined: 10, docsExamined: 10, no SORT stage, and the LIMIT stage sitting directly above the IXSCAN where it actually saves work.

2 (easy): Two queries against the same index. Which is better indexed, and what would you do about the other? 
  A: nReturned 1,200  keysExamined 1,200  docsExamined     0  time  8ms
  B: nReturned 1,200  keysExamined 1,200  docsExamined 1,200  time 94ms
Solution

A is better and is in fact optimal. docsExamined: 0 means the query was covered — every field it returns was available in the index keys, so the collection was never touched. That is the best outcome available.

B is not broken. Its ratios are healthy: it examined exactly as many keys and documents as it returned, so the index bounds are perfect and nothing is being discarded. The 86 ms difference is 1,200 document fetches — each one a random read into cache.

Whether to "fix" B is a judgement call, and the honest answer is usually no:

Consider covering B if…Leave B alone if…
It runs thousands of times a second — 86 ms × high QPS is real capacityIt runs occasionally; 94 ms is fine
It projects a handful of small fieldsIt returns whole documents — you cannot cover that
The extra index fields are rarely updatedThe fields change on every write, so covering them adds constant index churn
Cache headroom existsThe cluster is already cache-constrained; a wider index makes everything else slower

The point worth taking away: docsExamined == nReturned is already a well-indexed query. Covering is an optimisation on top of correctness, not a correction of a defect, and it is not free — it widens the index, which costs cache and write bandwidth on every insert.

3 (medium): Interpret these bounds against the index { a: 1, b: 1, c: 1, d: 1 }, and say what the query must have been. 
  "indexBounds": {
    "a": [ "[1, 1]" ],
    "b": [ "[5, inf.0]" ],
    "c": [ "[MinKey, MaxKey]" ],
    "d": [ "[MinKey, MaxKey]" ]
  }
Solution

Reading the bounds:

  • a: [1, 1] — an equality predicate, a: 1. Tightest possible.
  • b: [5, inf.0] — a range, b: { $gte: 5 }. Inclusive lower bound (square bracket), unbounded above.
  • c and d — [MinKey, MaxKey], no bound at all.

The query was something like { a: 1, b: { $gte: 5 } }, possibly with predicates on c or d as well — but if there were, they are being applied as filters, not bounds.

Why c and d are unbounded even if the query mentions them: once a range appears in a compound index, every field after it is unbounded. Within a=1, b≥5 the keys span many b values, and c restarts its ordering for each distinct b. So matching c values are not contiguous and cannot be bounded. This is the same mechanism as a skipped field, and it is exactly why ESR puts ranges last.

What to do about it depends on what the query needs:

If the query is…Then…
{ a: 1, b: { $gte: 5 } } onlyNothing is wrong, but c and d are dead weight in this index. Check whether another query needs them; if not, drop them from the key pattern.
{ a: 1, b: { $gte: 5 }, c: "x" }Reorder to { a: 1, c: 1, b: 1 } — equality fields before the range. Then both a and c bound the scan.
{ a: 1, b: { $gte: 5 } } sorted by cReorder to { a: 1, c: 1, b: 1 } as well — the sort field must precede the range or you get a blocking SORT.

In all three cases the diagnosis came from four lines of indexBounds, before looking at a single execution statistic. That is why it is worth reading.

4 (medium): A query intermittently takes 4 seconds; the same query with different values takes 6 ms. The index set has not changed. Design the investigation.
Solution

Hypothesis, from the shape of the symptom: the plan cache has a single entry for this query shape, and the cached plan is right for some values and wrong for others. "Intermittent, same shape, value-dependent" is close to a signature.

Step 1 — confirm the plan is shared.

  db.coll.find(FAST_VALUES).explain().queryPlanner.planCacheKey
  db.coll.find(SLOW_VALUES).explain().queryPlanner.planCacheKey
  // same key = one cached plan serving both = hypothesis alive

Step 2 — see what is cached and when it was decided.

  db.coll.aggregate([{ $planCacheStats: {} }])
    -> cachedPlan, works, timeOfCreation, isActive
  // timeOfCreation near a server restart or index change is a
  // strong tell: the plan was decided by whichever query ran first.

Step 3 — see what the planner rejected, for the slow values.

  db.coll.find(SLOW_VALUES).explain("allPlansExecution")
    -> compare works / nReturned / executionTimeMillisEstimate
       across candidates

If a rejected plan is dramatically better for the slow values, that is the confirmation.

Step 4 — prove it. db.coll.getPlanCache().clear(), then run the slow query first so it decides the plan, and re-measure both. If slow becomes fast and fast becomes slow, the diagnosis is certain — and it also demonstrates that no single cached plan can serve both, which is the actual finding.

The fix. Not a hint. The cache only mis-chooses when two plans are close on a 101-document sample, which means no index serves the whole shape. Build the compound index that does — equality fields, then sort, then range — and the contest disappears. A hint() is acceptable as a stopgap during an incident, but it bypasses the planner permanently and freezes today's data distribution; remove it once the index is in place.

What I would rule out in parallel, because they present similarly: a value that is genuinely far less selective (a skew problem, not a plan problem — check the match counts directly), and cold-cache disk reads (run the slow case twice; if the second is fast, it was I/O).

5 (hard): This aggregation takes 22 seconds. Diagnose from the explain and propose fixes in priority order. 
  db.orders.aggregate([
    { $lookup: { from: "customers", localField: "customerId",
                 foreignField: "_id", as: "cust" } },
    { $unwind: "$cust" },
    { $match: { "cust.region": "eu",
                createdAt: { $gte: ISODate("2026-08-01") } } },
    { $group: { _id: "$cust.segment", revenue: { $sum: "$total" } } },
    { $sort: { revenue: -1 } }
  ])

  explain shows: first stage COLLSCAN on orders (4.1M docs),
  $lookup inner plan COLLSCAN on customers, usedDisk: true
Solution

Three separate defects, each multiplying the others.

#DefectCost
1$match is after $lookup, so it cannot be pushed to the front. All 4.1M orders are joined before anything is filteredThe dominant cost by far
2foreignField: "_id" shows a COLLSCAN on customers — which should be impossible, since _id is always indexed. This means the join is on mismatched types (string customerId vs ObjectId _id), so the index cannot be usedA full customer scan per input document
3usedDisk: true — a stage exceeded 100 MB and spilledOrders of magnitude on the affected stage

Fix 1 (largest win): split the $match and put what you can first.

  { $match: { createdAt: { $gte: ISODate("2026-08-01") } } },  // FIRST
  { $lookup: { ... } },
  { $unwind: "$cust" },
  { $match: { "cust.region": "eu" } },   // must stay after the join
  ...

The createdAt predicate does not depend on the join, so it can run against an index before the join. If August is 3% of orders, this alone removes 97% of the join work. The optimiser could not do this itself because the two predicates were in one $match and one of them referenced a joined field.

Fix 2: resolve the type mismatch. A COLLSCAN on _id is diagnostic — the only way to miss that index is to compare incompatible types. Confirm with db.orders.findOne().customerId versus db.customers.findOne()._id. This is a data-correctness bug as much as a performance one: type bracketing means some joins may already be silently returning empty arrays. Fix it with a migration to a consistent type, not with $toObjectId in the pipeline, which would fix the symptom and leave every other query broken.

Fix 3: index for the new shape. { createdAt: -1 } at minimum, so the leading $match is an IXSCAN.

Fix 4: reduce what crosses the join. Only region and segment are used from the customer, so a sub-pipeline projection stops whole customer documents being materialised:

  { $lookup: { from: "customers",
      let: { cid: "$customerId" },
      pipeline: [
        { $match: { $expr: { $eq: ["$_id", "$$cid"] } } },
        { $match: { region: "eu" } },        // filter INSIDE the join
        { $project: { segment: 1, region: 1 } }
      ],
      as: "cust" } },
  { $unwind: "$cust" },

This also fixes the usedDisk spill, because far less data reaches $group.

Priority order: Fix 1 first — it is a two-line change with the largest effect and no risk. Then Fix 3, then Fix 4. Fix 2 last as a scheduled migration, because it touches data and needs its own plan — but I would open the bug immediately, since a type mismatch on a join key means some results may already be wrong, and a fast wrong answer is worse than a slow one.

What I would also question: this is a monthly revenue rollup. If it runs on a dashboard load, the real fix is a pre-computed rollup collection updated incrementally, not a 22-second (or even 2-second) aggregation on the hot path. See Aggregation Performance.

6 (hard): You are given production access to a cluster with no monitoring and a report that "the app is slow". Produce a prioritised list of query problems within two hours, without risking the cluster.
Solution

Constraint that shapes everything: no monitoring means no history, so I have to generate observations rather than query them, and I must do it without adding load to a cluster that is already struggling.

0–10 min: is this even a query problem?

  db.serverStatus().wiredTiger.cache
    ["bytes currently in the cache"] vs ["maximum bytes configured"]
    ["pages evicted by application threads"]   > 0 = the cliff
  db.serverStatus().connections      // saturated pool?
  db.serverStatus().opcounters       // what kind of load?
  rs.printSecondaryReplicationInfo() // lag?
  db.currentOp({ secs_running: { $gt: 3 } })  // what is stuck NOW

If application-thread evictions are non-zero, the working set exceeds cache and every query is slow for a reason no index will fix. That reframes the whole investigation, and it is a 30-second check.

10–30 min: collect, cheaply. Enable the profiler at level 1 with a threshold — but set it on a secondary if reads go there, and cap the profile collection size first. Level 2 on a struggling primary is how a diagnosis becomes an outage.

  db.setProfilingLevel(1, { slowms: 200 })   // start conservative
  // and set a calendar reminder to turn it off

30–60 min: rank by total cost, not worst case.

  db.system.profile.aggregate([
    { $match: { millis: { $gte: 200 } } },
    { $group: { _id: { hash: "$queryHash", plan: "$planSummary",
                       ns: "$ns" },
                n: { $sum: 1 }, total: { $sum: "$millis" },
                avg: { $avg: "$millis" }, max: { $max: "$millis" },
                keys: { $avg: "$keysExamined" },
                docs: { $avg: "$docsExamined" },
                ret:  { $avg: "$nreturned" },
                sample: { $first: "$command" } } },
    { $sort: { total: -1 } }, { $limit: 20 }
  ])

Sorting by total rather than max is the single most important decision here. The queries humans complain about are the slowest ones; the queries destroying the cluster are the moderately slow ones run constantly.

60–90 min: triage without explaining anything. planSummary is already in the output. Every COLLSCAN on a large namespace goes straight onto the list. So does every entry where average docsExamined is more than ~100× average nreturned. That is usually most of the list, identified with zero additional load.

90–120 min: explain the top 5 with executionStats, read indexBounds for dead fields, and write the proposed index for each.

The deliverable is a table: namespace, query shape, calls/hour, total ms/hour, current plan, proposed index, expected effect, and risk. Ranked by total ms. That is a document someone can act on and argue with, which "the app is slow" is not.

What I would refuse to do in the first two hours: create or drop any index. Index builds consume CPU and evict cache on a cluster that may already be at its limit, and a drop is not cheaply reversible. The output of two hours should be a plan, not a change — and if something is urgent enough to change immediately, hint() or a query-side fix in the application is reversible in a way an index build is not.

The one exception: if currentOp shows a runaway operation actively degrading the cluster, kill it. That is triage, not optimisation, and it comes before everything above.

🎯 Key Takeaways

  • Always explain("executionStats"). Bare explain() runs nothing and reports no keys, documents or time.
  • Read the stage tree bottom-up. The deepest inputStage executes first; the outermost stage executes last.
  • Four numbers, three ratios. docsExamined ≫ nReturned = a missing filter field; keysExamined ≫ docsExamined = loose bounds; SORT present = the index lost the ordering.
  • A filter on a FETCH stage names the field to add to the index.
  • LIMIT above SORT saves nothing — everything was read and sorted before the cutoff applied.
  • docsExamined: 0 with an IXSCAN is a covered query, the best possible outcome.
  • [MinKey, MaxKey] in indexBounds means that field contributed nothing. Everything below the first one is dead weight.
  • Low examined counts with high time is not an index problem — it is disk, locks or a saturated server. Run it twice.
  • executionTimeMillis excludes network and cursor iteration. 4 ms on the server can be 900 ms in the application.
  • The plan cache stores one plan per query shape, chosen from a ~101-result trial, then applied to all values.
  • "Fast for months, now 4 seconds, nothing changed" is the plan cache's signature — 6 ms for a small tenant, 4,200 ms for a large one, same shape.
  • A plan-cache incident means no index serves the whole shape. Build the compound index; use hint() only as a stopgap and remove it.
  • In aggregations, check whether $match was pushed to the front and whether $sort+$limit coalesced; usedDisk: true means a stage spilled past 100 MB.
  • On sharded collections read shardsTargeted first — the summary sums all shards and can hide a 12-shard broadcast behind excellent-looking ratios.
  • Explain does not model $out/$merge, does not perform writes, and excludes lock waits. The profiler covers what it cannot.
  • Rank slow queries by total time, not worst case. A 40 ms query run 100,000 times costs more than a 4-second report run twice.
  • A staging explain predicts nothing. Plan choice depends on data volume and distribution.
