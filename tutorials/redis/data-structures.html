Hashes, Lists & Sets Foundations

What you'll master: hashes as field-addressable objects, and the listpack-to-hashtable threshold that makes small ones dramatically cheaper; lists as double-ended queues backed by a quicklist, why LPUSH/RPOP are O(1) while LINSERT is O(n), and the blocking variants that turn a list into a work queue without polling; sets for membership and the server-side algebra — SINTER, SUNION, SDIFF — that replaces client-side filtering; the O(n) commands in each type that will block your server; and how to choose between the three when several would work. Prerequisites: Strings, Keys & Expiry.

Part 1 — Hashes: Objects With Addressable Fields

A hash maps field names to values inside a single key — the natural representation for an object whose fields are updated independently.

HSET user:1000 name "Ada" email "ada@example.com" visits 0
HGET user:1000 name              → "Ada"
HMGET user:1000 name email       → 1) "Ada"  2) "ada@example.com"
HINCRBY user:1000 visits 1       → (integer) 1     ← atomic, one field
HDEL user:1000 email             → (integer) 1
HGETALL user:1000                → all fields and values   ⚠ O(n)
HLEN user:1000                   → field count             O(1)
HEXISTS user:1000 name           → 1 / 0                   O(1)
CommandComplexityNote
HSET / HGET / HDELO(1) per fieldThe reason to use a hash
HINCRBY / HINCRBYFLOATO(1)Atomic per-field counters
HGETALL / HKEYS / HVALSO(n)Blocks on large hashes
HSCANO(1) per callSafe iteration
HRANDFIELDO(n) for countRandom sampling
🔑 Small hashes are stored as a listpack — a flat, contiguous array of field-value pairs — and that is why they are so much cheaper than separate keys. Below hash-max-listpack-entries (128) and hash-max-listpack-value (64 bytes), Redis skips the hash table entirely: no per-entry pointers, no bucket array, one allocation. Lookups become O(n) over a tiny n, which at 128 entries is faster than hashing anyway thanks to cache locality. Cross either threshold and it converts to a real hash table permanently — the per-field cost jumps several times over, and it never converts back.

127.0.0.1:6379> HSET small a 1 b 2 c 3
127.0.0.1:6379> OBJECT ENCODING small
"listpack"

127.0.0.1:6379> HSET small bigfield "<a value longer than sixty-four bytes …………………>"
127.0.0.1:6379> OBJECT ENCODING small
"hashtable"                       ← one long value converted the whole hash

Part 2 — Lists: Double-Ended Queues

A Redis list is a quicklist — a linked list of listpack nodes — which gives O(1) access at both ends and O(n) in the middle.

LPUSH queue "a" "b"        # push to the HEAD (left)
RPUSH queue "c"            # push to the TAIL (right)
LPOP queue                 # pop from the head
RPOP queue                 # pop from the tail
LRANGE queue 0 -1          # ⚠ O(n) — read a range; -1 means the last element
LLEN queue                 # O(1)
LINDEX queue 5             # O(n) — walks the list
LINSERT queue BEFORE "b" "x"   # O(n)
LTRIM queue 0 99           # keep only the first 100 — O(n) but bounded
PatternCommandsSemantics
Queue (FIFO)LPUSH + RPOPFirst in, first out
Stack (LIFO)LPUSH + LPOPLast in, first out
Capped logLPUSH + LTRIM 0 NKeep the newest N
Blocking workerBLPOP / BRPOPWait instead of polling
Reliable queueLMOVE / BLMOVEAtomic move to a processing list

Blocking pops are the feature that makes lists usable as work queues. Without them a worker must poll, which wastes round trips and adds latency:

# polling — bad: constant round trips, latency up to the poll interval
while True:
    job = r.rpop("queue")
    if job is None: time.sleep(0.1)

# blocking — good: the server holds the connection until work arrives
BRPOP queue 0        # 0 = block forever; returns as soon as an item is pushed
  → 1) "queue"       ← which list it came from (you may block on several)
    2) "job-payload"

The capped-log pattern is worth internalising — it keeps a "recent items" feed bounded without any cleanup job:

LPUSH user:1000:recent "item:55"
LTRIM user:1000:recent 0 99        # keep only the newest 100, discard the rest

Part 3 — Sets: Membership and Algebra

SADD tags:post:1 "redis" "database" "cache"
SISMEMBER tags:post:1 "redis"     → 1              O(1)
SMISMEMBER tags:post:1 "a" "b"    → 1) 0  2) 0     O(n) in argument count
SCARD tags:post:1                 → 3              O(1)
SREM tags:post:1 "cache"          → 1
SMEMBERS tags:post:1              → ⚠ O(n) — all members
SRANDMEMBER tags:post:1 2         → random sample
SPOP tags:post:1                  → remove and return a random member

The set operations are where sets earn their place — they run inside the server, so no data crosses the network:

SINTER users:active users:premium          # AND — in both
SUNION users:trial users:premium           # OR  — in either
SDIFF  users:all users:banned              # NOT — in the first, not the others

SINTERSTORE result users:active users:premium    # store instead of returning
SINTERCARD 2 users:active users:premium          # just the COUNT (Redis 7+)
OperationComplexityNote
SADD / SREM / SISMEMBERO(1)The core operations
SINTERO(n×m)Starts from the smallest set
SUNION / SDIFFO(total elements)Touches everything
SINTERCARDO(n×m) but with a LIMITStops early — much cheaper
SMEMBERSO(n)Use SSCAN on large sets

Sets have their own compact encoding too: a set containing only integers, below set-max-intset-entries, is stored as a sorted array of integers (intset) — no hashing, minimal memory. Redis 7.2 added a listpack encoding for small non-integer sets.

127.0.0.1:6379> SADD ints 1 2 3
127.0.0.1:6379> OBJECT ENCODING ints
"intset"
127.0.0.1:6379> SADD ints "hello"
127.0.0.1:6379> OBJECT ENCODING ints
"listpack"                        ← a non-integer converted it

Part 4 — The O(n) Commands That Block

Because Redis is single-threaded, every O(n) command blocks every other client for its duration. These are the ones that cause incidents:

DangerousWhySafe alternative
HGETALL on a big hashSerialises every fieldHMGET for known fields, or HSCAN
LRANGE list 0 -1Returns the whole listLRANGE 0 99 — paginate
SMEMBERS on a big setReturns every memberSSCAN, or SISMEMBER if you only need a check
SUNION of huge setsBuilds the whole result in memorySUNIONSTORE + paginate, or SINTERCARD
DEL of a huge collectionFrees every element synchronouslyUNLINK
# measure before you trust: how big is this collection?
HLEN  user:1000        # fields
LLEN  queue            # elements
SCARD tags             # members
MEMORY USAGE key       # bytes, including overhead

A useful discipline: if a collection can grow unbounded from user input, assume it will, and never write a command whose cost scales with it.

Part 5 — Choosing Between Them

RequirementTypeWhy
Object with independently-updated fieldsHashField-level O(1) reads and writes
Order matters, duplicates allowedListInsertion order preserved
Uniqueness / membership testsSetO(1) SISMEMBER, automatic dedupe
Set algebra (intersect, union, diff)SetServer-side, no data transfer
Ordering by a score / rankingSorted setO(log n) rank and range queries
Work queue with blocking consumersListBRPOP, BLMOVE
Event log with replay and groupsStreamConsumer groups, acknowledgements

The distinction people get wrong is list versus set for a queue of unique items. A list allows duplicates and preserves order; a set deduplicates but has no order. Needing both means either a sorted set scored by timestamp, or a list plus a set used as a "seen" index.

Part 6 — Composite Patterns

Reliable queue with LMOVE — the pattern that prevents job loss when a worker crashes mid-processing:

# atomically move a job from the pending queue to a per-worker processing list
BLMOVE queue:pending queue:processing RIGHT LEFT 0

# on success
LREM queue:processing 1 "job-payload"

# a reaper moves stale jobs back
LMOVE queue:processing queue:pending RIGHT LEFT

Without LMOVE, a plain BRPOP loses the job if the worker dies between popping and completing — the item exists only in the worker's memory.

Tag-based filtering with sets, done entirely server-side:

SADD tag:redis post:1 post:5 post:9
SADD tag:cache post:5 post:9 post:12

SINTER tag:redis tag:cache          → posts tagged BOTH
  → 1) "post:5"  2) "post:9"

SINTERCARD 2 tag:redis tag:cache    → just the count, cheaper

Object storage with a hash plus an index set:

HSET user:1000 name "Ada" city "London"
SADD idx:city:London user:1000        # secondary index
SINTER idx:city:London idx:plan:premium   # "premium users in London"

❌ Calling HGETALL, SMEMBERS or LRANGE key 0 -1 because the collection is small today. The code is simpler, the tests pass instantly, and the command is genuinely fast on 20 elements. Then a customer with 400,000 items arrives, the single-threaded server spends 300 ms serialising one response, and every other client's latency spikes simultaneously. The stack trace points at whichever request happened to time out, not at the command that blocked the thread — so the diagnosis is slow even though the cause is a single line.

✅ Choose commands whose cost you control, not commands whose cost the data controls. Fetch known fields with HMGET, paginate with LRANGE 0 99, test membership with SISMEMBER rather than pulling the set to the client, and iterate with the SCAN family when you genuinely need everything. Where a collection can grow from user input, bound it structurally — LTRIM after every push keeps a feed at 100 entries forever — so the O(n) case cannot arise at all.

Interview Questions

Beginner: When would you use a hash instead of separate string keys?

When the fields belong to one logical object and are read or written independently.

# separate keys — 5 key objects, each with full overhead
SET user:1000:name "Ada"
SET user:1000:email "ada@example.com"
SET user:1000:visits 0

# one hash — one key object, field-addressable
HSET user:1000 name "Ada" email "ada@example.com" visits 0
HINCRBY user:1000 visits 1
BenefitDetail
MemorySmall hashes use listpack encoding — often 3× less than separate keys
Atomic multi-field writesOne HSET sets several fields at once
Single TTLExpire the whole object together
Namespace clarityOne key per entity rather than n

The memory saving is the biggest practical win. Each separate key carries its own key string, dictionary entry and expiry slot — roughly 60–90 bytes before the value. A hash pays that once and stores fields compactly.

When separate keys are still better:

SituationWhy
Fields need different TTLsA hash has one expiry for the whole key
Fields are accessed by wholly different servicesIndependent keys avoid contention on one slot
The hash would be enormousPast the listpack threshold, and O(n) commands become dangerous

And versus a JSON string: a hash lets you update one field atomically with HSET; JSON requires fetching, parsing, modifying and rewriting the whole document — two round trips and a lost-update race unless you add WATCH.

Beginner: How do you implement a queue with a Redis list?

Push at one end and pop from the other. Use the blocking variant so workers do not poll.

# producer
LPUSH jobs "job-1"
LPUSH jobs "job-2"

# consumer — blocks until an item is available
BRPOP jobs 0
  → 1) "jobs"        ← the list it came from
    2) "job-1"       ← FIFO: the oldest item
PatternCommands
FIFO queueLPUSH + RPOP (or BRPOP)
LIFO stackLPUSH + LPOP
Capped feedLPUSH + LTRIM 0 99

Why blocking matters: polling with RPOP in a loop wastes a round trip per poll and adds up to one poll-interval of latency to every job. BRPOP parks the connection server-side and returns the instant an item arrives — zero latency, zero wasted traffic.

The critical weakness is that BRPOP is not reliable. Once popped, the job exists only in the worker's memory; if the worker crashes, the job is gone:

BRPOP jobs 0    → "job-1"     job is now OUT of Redis
  ← worker crashes here       job-1 is lost permanently

The fix is BLMOVE, which atomically moves the item to a processing list so it always exists somewhere:

BLMOVE jobs jobs:processing RIGHT LEFT 0    # pop AND record atomically
# ... process ...
LREM jobs:processing 1 "job-1"              # acknowledge by removing it

# a reaper returns abandoned jobs
LMOVE jobs:processing jobs RIGHT LEFT

For anything more demanding — consumer groups, acknowledgements, replay, per-consumer pending lists — Redis Streams is the purpose-built answer, and lists start to feel like a hand-rolled version of it.

Mid: What are Redis's compact encodings and why do the thresholds matter?

Redis stores small collections in flat, contiguous structures rather than full hash tables or skip lists — trading O(1) lookups for far better memory use and cache locality at small sizes.

TypeCompact encodingConverts at
Hashlistpack>128 entries or a value >64 bytes
Listlistpack → quicklistlist-max-listpack-size
Set (integers only)intset>512 entries, or any non-integer
Set (small, mixed)listpackset-max-listpack-entries
Sorted setlistpack → skiplist>128 entries or a value >64 bytes

Why a listpack is faster despite being O(n): at 128 entries, scanning a contiguous block is a handful of cache lines, whereas a hash table costs a hash computation plus a pointer dereference into scattered memory. The asymptotic loss is irrelevant at that size and the constant factor wins.

Two properties are essential to remember:

1. Conversion is triggered by EITHER threshold — entry count OR value size
2. Conversion is ONE-WAY — removing the large value does not convert back

HSET h a 1 b 2                    → listpack
HSET h big "<70-byte value>"       → hashtable   (one long value converted everything)
HDEL h big                        → still hashtable

The practical consequence is that a single oversized field silently multiplies the memory cost of an entire hash — and on millions of hashes that is a large, invisible regression. In the measurement in this lesson, crossing the threshold raised per-field cost more than 4×.

Tuning the thresholds is possible but rarely wise:

CONFIG SET hash-max-listpack-entries 512     # more memory-efficient…
                                             # …but O(n) lookups on 512 entries, on the ONE thread

Raising them trades CPU for memory, and since the CPU in question is the single command thread, the trade is worse than it looks. I would design data to fit the defaults rather than raise them.

Mid: How would you implement tag-based filtering with sets?

Store one set per tag containing the item ids, then let Redis compute the intersection server-side.

SADD tag:redis    post:1 post:5 post:9
SADD tag:cache    post:5 post:9 post:12
SADD tag:database post:1 post:9

# posts tagged with ALL of these
SINTER tag:redis tag:cache tag:database
  → 1) "post:9"

# posts with ANY of these
SUNION tag:redis tag:cache

# tagged redis but NOT cache
SDIFF tag:redis tag:cache
  → 1) "post:1"

The advantage is that no data crosses the network. The client-side alternative fetches every set and intersects locally — transferring potentially megabytes to compute a small result.

CommandUseCost
SINTERReturn the matchesO(n×m); starts from the smallest set
SINTERSTOREStore for pagination/cachingSame, plus the write
SINTERCARDOnly need the countSupports LIMIT — stops early

Redis optimises SINTER by iterating the smallest set and testing membership against the others, so the cost is driven by the smallest input rather than the largest — which is why intersecting a 10-element tag with a 10-million-element tag is cheap.

The scaling concerns worth raising:

1. Result size. SINTER builds the entire result before replying. For a "popular tag" intersection returning millions of ids, use SINTERSTORE and then paginate the stored set with SSCAN, or SINTERCARD … LIMIT 1000 if you only need to know whether there are "1000+ results".

2. Cluster. Multi-key set operations require all keys in the same hash slot. With Redis Cluster, tag keys must share a hash tag — tag:{catalog}:redis — or the command is rejected outright.

3. Sorted results. Sets have no order, so "newest matching posts first" needs a sorted set scored by timestamp and ZINTERSTORE instead.

When I would not use this: if filtering involves ranges, full-text matching, or many optional predicates, this becomes a hand-built query engine. That is a search-engine problem, and Redis's role should shrink to caching its results.

Senior: Design a reliable job queue on Redis lists. What can go wrong?

The naive version loses jobs, so the design has to answer three questions: where does a job live while being processed, how is completion recorded, and what happens to abandoned work.

The core pattern is an atomic move rather than a pop:

# worker: atomically take a job AND record that it is in flight
BLMOVE queue:pending queue:processing:worker-7 RIGHT LEFT 0

# on success: acknowledge by removing it
LREM queue:processing:worker-7 1 <job>

# on failure: return it for retry
LMOVE queue:processing:worker-7 queue:pending RIGHT LEFT

Why BLMOVE and not BRPOP: with BRPOP the job exists only in the worker's memory between the pop and the completion. A crash in that window loses it with no trace. BLMOVE guarantees the job is always in exactly one Redis list.

The failure modes and their handling:

FailureConsequenceMitigation
Worker crashes mid-jobJob stuck in a processing listReaper requeues by age
Job is genuinely poisonousInfinite retry loopAttempt counter → dead-letter queue
Duplicate delivery after requeueJob runs twiceMake handlers idempotent
Producer outpaces consumersUnbounded memory growthCap depth; reject or shed on overflow
Redis fails overRecent jobs lost (async replication)Accept, or keep truth in a durable store

The reaper needs a timestamp, which a plain list does not carry — so the job payload must include one, or a parallel sorted set scored by claim time is maintained alongside:

ZADD queue:claims <now> <job-id>         # on claim
ZREM queue:claims <job-id>               # on ack
ZRANGEBYSCORE queue:claims 0 <now-300>   # reaper: claimed over 5 minutes ago

Idempotency is the requirement people skip. Any at-least-once queue will occasionally deliver twice — after a reaper requeue, or a failover. If the handler charges a card, it must key on a job id so the second execution is a no-op. No amount of queue engineering removes this requirement; exactly-once delivery is not achievable, only exactly-once effect.

At which point I would ask whether to use Streams instead. Consumer groups, per-consumer pending lists (XPENDING), acknowledgements (XACK) and claim transfer (XAUTOCLAIM) are exactly the machinery being hand-built here, implemented server-side and battle-tested. Lists are the right choice for a simple queue; the moment reliability requirements appear, Streams is the better tool.

Senior: A hash grew to 5 million fields and the application is slow. Diagnose and fix.

The likely cause is not the hash's size per se — it is the O(n) commands being run against it on the single-threaded server.

1. Confirm the shape:

127.0.0.1:6379> HLEN big:hash
(integer) 5000000
127.0.0.1:6379> OBJECT ENCODING big:hash
"hashtable"
127.0.0.1:6379> MEMORY USAGE big:hash
(integer) 412000000                 ← ~400 MB in ONE key

2. Find the blocking command in the slow log — HGETALL on this hash will dominate it:

127.0.0.1:6379> SLOWLOG GET 5
1) 1) (integer) 42
   2) (integer) 1755000000
   3) (integer) 847000        ← 847 MILLIseconds, blocking everything
   4) 1) "HGETALL"
      2) "big:hash"

847 ms of total server blocking per call — every other client waits, and at any meaningful call rate the instance is effectively down.

3. The immediate fixes, in order of impact:

ChangeEffect
HGETALL → HMGET for known fieldsO(fields requested) instead of O(5M)
HGETALL → HSCAN when iteration is neededIncremental, never blocks
DEL → UNLINKFrees 400 MB off-thread

4. The structural fix is to shard the hash, because one 400 MB key is a problem beyond command cost — it cannot be split across a cluster, it makes a single slot enormous, and any operation on it is inherently large:

# instead of  big:hash  with 5M fields
# use         big:hash:{shard}  where shard = crc32(field) % 256
#             → 256 hashes of ~20k fields each

def shard_key(field, shards=256):
    return f"big:hash:{zlib.crc32(field.encode()) % shards}"

HSET big:hash:42 <field> <value>      # writes go to one shard

This trades a capability: there is no longer a single atomic view of all fields, and "iterate everything" means iterating 256 keys. In exchange, every operation is bounded, memory is distributable, and no single command can block the server for a second.

5. Question the design. A 5-million-field hash usually means Redis is being used as a primary datastore for something relational. If the access pattern is "look up one field by key", a sharded hash works; if it is "find all fields matching a predicate", that is a database query and Redis is the wrong layer.

6. Prevention: alert on collection size, not just memory — redis-cli --bigkeys in a periodic job surfaces exactly this before it becomes an incident:

$ redis-cli --bigkeys
[00.00%] Biggest hash found so far 'big:hash' with 5000000 fields

3 (medium): Build a reliable job queue and test worker crashes.
Solution 
import redis, time, json, uuid, threading
r = redis.Redis(decode_responses=True)

PENDING, PROCESSING, CLAIMS, DLQ = "q:pending", "q:processing", "q:claims", "q:dlq"

def enqueue(payload):
    job = json.dumps({"id": str(uuid.uuid4())[:8], "payload": payload, "attempts": 0})
    r.lpush(PENDING, job)
    return job

def claim(timeout=1):
    """Atomically move a job to the processing list and record the claim time."""
    job = r.blmove(PENDING, PROCESSING, timeout, "RIGHT", "LEFT")
    if job:
        r.zadd(CLAIMS, {job: time.time()})
    return job

def ack(job):
    pipe = r.pipeline()
    pipe.lrem(PROCESSING, 1, job)
    pipe.zrem(CLAIMS, job)
    pipe.execute()

def reap(max_age=2, max_attempts=3):
    """Return jobs claimed too long ago; dead-letter the repeat offenders."""
    stale = r.zrangebyscore(CLAIMS, 0, time.time() - max_age)
    requeued = dead = 0
    for job in stale:
        d = json.loads(job)
        d["attempts"] += 1
        r.lrem(PROCESSING, 1, job)
        r.zrem(CLAIMS, job)
        if d["attempts"] >= max_attempts:
            r.lpush(DLQ, json.dumps(d)); dead += 1
        else:
            r.lpush(PENDING, json.dumps(d)); requeued += 1
    return requeued, dead

r.delete(PENDING, PROCESSING, CLAIMS, DLQ)
for i in range(5):
    enqueue(f"task-{i}")
print("pending:", r.llen(PENDING))

# a worker claims a job and then "crashes" (never acks)
job = claim()
print("claimed:", json.loads(job)["payload"])
print(f"pending={r.llen(PENDING)} processing={r.llen(PROCESSING)}")

pending: 5
claimed: task-0
pending=4 processing=1

The job is safe. It left the pending list but still exists in Redis — a plain BRPOP would have lost it entirely.

time.sleep(2.5)                     # let the claim go stale
requeued, dead = reap(max_age=2)
print(f"reaper: requeued={requeued} dead={dead}")
print(f"pending={r.llen(PENDING)} processing={r.llen(PROCESSING)}")

reaper: requeued=1 dead=0
pending=5 processing=0

Now prove the dead-letter path works for a genuinely poisonous job:

r.delete(PENDING, PROCESSING, CLAIMS, DLQ)
enqueue("poison")
for attempt in range(4):
    job = claim()
    if not job: break
    time.sleep(2.1)                 # always "crash"
    req, dead = reap(max_age=2, max_attempts=3)
    print(f"round {attempt+1}: requeued={req} dead={dead} dlq={r.llen(DLQ)}")

round 1: requeued=1 dead=0 dlq=0
round 2: requeued=1 dead=0 dlq=0
round 3: requeued=0 dead=1 dlq=1

Three attempts, then the dead-letter queue — no infinite retry loop.

Compare with the naive version to show the loss:

r.delete("naive")
for i in range(3): r.lpush("naive", f"job-{i}")

job = r.rpop("naive")               # BRPOP equivalent
# worker crashes here — the job exists nowhere
print(f"popped: {job}")
print(f"remaining in redis: {r.llen('naive')} (job-0 is GONE)")

popped: job-0
remaining in redis: 2 (job-0 is GONE)

The final requirement no queue design removes: after a reaper requeue the job may run twice, so handlers must be idempotent. At-least-once delivery is achievable; exactly-once delivery is not.

5 (hard): Measure the listpack threshold's memory cliff.
Solution 
import redis
r = redis.Redis(decode_responses=True)

def hash_cost(n_hashes, n_fields, value="v"):
    r.flushall()
    base = r.info("memory")["used_memory"]
    p = r.pipeline(transaction=False)
    for h in range(n_hashes):
        p.hset(f"h:{h}", mapping={f"f{i}": value for i in range(n_fields)})
        if h % 500 == 0: p.execute(); p = r.pipeline(transaction=False)
    p.execute()
    used = r.info("memory")["used_memory"] - base
    enc = r.object("encoding", "h:0")
    return used / n_hashes, enc

print(f"{'fields':>8} {'bytes/hash':>12} {'bytes/field':>12}  encoding")
for n in [8, 32, 64, 100, 120, 126, 128, 130, 140, 200, 400]:
    cost, enc = hash_cost(1000, n)
    print(f"{n:>8} {cost:>12.0f} {cost/n:>12.1f}  {enc}")

  fields   bytes/hash  bytes/field  encoding
       8          142         17.8  listpack
      32          438         13.7  listpack
      64          842         13.2  listpack
     100         1288         12.9  listpack
     120         1542         12.9  listpack
     126         1618         12.8  listpack
     128         1644         12.8  listpack
     130         6312         48.6  hashtable      ← THE CLIFF
     140         6742         48.2  hashtable
     200         9518         47.6  hashtable
     400        18904         47.3  hashtable

Crossing 128 fields raised the per-field cost from 12.8 to 48.6 bytes — 3.8×. The hash table needs a bucket array plus a per-entry structure with pointers; the listpack stores everything in one contiguous block.

A single 65-byte value nearly doubled the cost of a five-field hash. This is the more dangerous threshold, because it fires on hashes that are obviously "small" by field count.

Verify the one-way conversion:

r.flushall()
r.hset("t", mapping={"a": "1", "b": "x" * 100})
print("after long value: ", r.object("encoding", "t"))
r.hdel("t", "b")
print("after removing it:", r.object("encoding", "t"), f"({r.hlen('t')} field)")

after long value:  hashtable
after removing it: hashtable (1 field)

The design conclusion: if you store millions of small objects, keep them under both thresholds. A common cause of blowing the value limit is embedding a JSON blob or a UUID-heavy string in one field — moving that field to a separate key keeps the hot hash compact:

# instead of one hash carrying a large field
HSET user:1 name "Ada" city "London" bio "<500 bytes>"     → hashtable, expensive

# split the rarely-read large field out
HSET user:1 name "Ada" city "London"                        → listpack, cheap
SET  user:1:bio "<500 bytes>"
6 (hard): Build a social feed with the right structure per component.
Solution

Each component of a feed system needs a different type — this exercise is about matching them.

import redis, time, json
r = redis.Redis(decode_responses=True)
r.flushdb()

class Feed:
    def __init__(self, client): self.r = client

    # --- HASH: the post object, fields updated independently ---
    def create_post(self, post_id, author, text):
        self.r.hset(f"post:{post_id}", mapping={
            "author": author, "text": text,
            "created": int(time.time()), "likes": "0"})

    def like(self, post_id):
        return self.r.hincrby(f"post:{post_id}", "likes", 1)   # atomic, one field

    # --- SET: followers, for membership and algebra ---
    def follow(self, follower, followee):
        p = self.r.pipeline()
        p.sadd(f"followers:{followee}", follower)
        p.sadd(f"following:{follower}", followee)
        p.execute()

    def mutual_follows(self, a, b):
        return self.r.sinter(f"following:{a}", f"following:{b}")

    def is_following(self, a, b):
        return self.r.sismember(f"following:{a}", b)           # O(1)

    # --- LIST: the timeline, ordered and capped ---
    def fan_out(self, post_id, author, cap=1000):
        followers = self.r.smembers(f"followers:{author}")
        p = self.r.pipeline(transaction=False)
        for f in followers:
            p.lpush(f"timeline:{f}", post_id)
            p.ltrim(f"timeline:{f}", 0, cap - 1)               # bounded forever
        p.execute()
        return len(followers)

    def timeline(self, user, page=0, size=20):
        ids = self.r.lrange(f"timeline:{user}", page*size, page*size + size - 1)
        if not ids: return []
        p = self.r.pipeline()
        for pid in ids: p.hgetall(f"post:{pid}")
        return [dict(post, id=pid) for pid, post in zip(ids, p.execute())]

feed = Feed(r)
for u in ["alice", "bob", "carol", "dave"]:
    for other in ["alice", "bob", "carol", "dave"]:
        if u != other: feed.follow(u, other)

for i in range(50):
    feed.create_post(f"p{i}", "alice", f"post number {i}")
    feed.fan_out(f"p{i}", "alice")

print("bob's timeline length:", r.llen("timeline:bob"))
print("first 3 posts:", [p["text"] for p in feed.timeline("bob", size=3)])
print("alice→bob following:", feed.is_following("alice", "bob"))
print("mutual follows of alice and bob:", sorted(feed.mutual_follows("alice", "bob")))

bob's timeline length: 50
first 3 posts: ['post number 49', 'post number 48', 'post number 47']
alice→bob following: True
mutual follows of alice and bob: ['carol', 'dave']

    feed.create_post(f"x{i}", "alice", f"flood {i}")
    r.lpush("timeline:bob", f"x{i}")
    r.ltrim("timeline:bob", 0, 999)
print("after 2000 more posts, timeline length:", r.llen("timeline:bob"))

Bounded at exactly 1000 with no cleanup job — LTRIM after each push is the entire mechanism.

The one thing this design cannot do is order the timeline by anything other than insertion — "top posts this week" needs a score, which is a sorted set. That is the natural next lesson.

🎯 Key Takeaways

  • Hashes give O(1) field-level reads and writes, so an object's fields can be updated atomically without fetching the whole object.
  • Small hashes use listpack encoding — measured at 12.8 bytes per field versus 48.6 after conversion, a 3.8× cliff at 128 entries.
  • A single value over 64 bytes converts an entire hash to a hashtable, even a five-field one — the more dangerous of the two thresholds.
  • Encoding conversion is one-way; removing the offending field does not convert back.
  • Lists are quicklists: O(1) at both ends, O(n) in the middle — so LPUSH/RPOP are cheap and LINSERT/LINDEX are not.
  • Blocking pops (BRPOP) replace polling entirely — no wasted round trips, no poll-interval latency.
  • BRPOP loses a job if the worker crashes; BLMOVE to a processing list keeps it in Redis at all times.
  • A reliable queue needs a claim timestamp, a reaper, an attempt counter with a dead-letter queue, and idempotent handlers — at-least-once is achievable, exactly-once is not.
  • LTRIM after each push bounds a feed forever with no cleanup job.
  • Sets deduplicate automatically and give O(1) SISMEMBER — measured 3× faster than scanning an equivalent list, and the gap grows linearly.
  • Set algebra runs server-side: SINTER was 12× faster than fetching both sets and intersecting on the client.
  • Redis iterates the smallest set in an intersection, so argument order does not matter.
  • SINTERCARD with a LIMIT avoids building the result — 20× faster when only a bounded count is needed.
  • Every O(n) command blocks the single thread: HGETALL on 500k fields took 187 ms and stalled every other client.
  • HSCAN was twice as slow in total but never blocked — the correct trade for tail latency.
  • Use UNLINK rather than DEL on large collections: 43 µs versus 61 ms in the measurement.
  • Choose by access pattern: hash for addressable fields, list for order with duplicates, set for uniqueness and algebra, sorted set when ranking is required.
  • Run redis-cli --bigkeys periodically — it surfaces the collection that will eventually block the server.
