Replication & Failover Durability & Distribution

What you'll master: why Redis replication is asynchronous and exactly which acknowledged writes that loses at failover; full sync versus partial resync, and the one buffer setting that decides whether a brief network blip costs a 20 GB retransfer; replica read staleness and the read-your-own-writes bug it produces; Sentinel's quorum — and the distinction between the quorum that detects failure and the majority that authorises promotion, which is where most people's answer falls apart; split-brain, the two settings that bound it, and why they cannot eliminate it; replica-read-only and how a "harmless" write to a replica silently disappears; and what failover actually looks like from a client. Prerequisites: Persistence: RDB & AOF, The Single-Threaded Model.

Part 1 — Asynchronous by Design, and What It Costs

A replica issues REPLICAOF host port and receives a copy of the primary's dataset, then a continuous stream of every write. The critical property is in the ordering:

Client → primary:  SET k v
primary → client:  +OK                    ← acknowledged HERE
primary → replica: SET k v                ← sent AFTER the ack, asynchronously

The client is told the write succeeded before any replica has seen it.
🔑 Redis never waits for a replica before acknowledging a write, so a failover can lose any write the primary had not yet propagated. That is a deliberate latency trade, not a defect — waiting for replicas would put a network round trip inside every write. The consequence is concrete: if the primary dies with 40 ms of un-replicated writes in flight, and a replica is promoted, those acknowledged writes simply do not exist afterwards. No error is raised to anyone, because the client that received +OK has long since moved on.

PropertyRedis replication
AcknowledgementPrimary only — replicas are not waited on
Replica lagTypically sub-millisecond on a LAN; unbounded under load
Consistency modelEventual
Reads from replicasAllowed, and may be stale
Writes to replicasRejected by default (replica-read-only yes)
Data loss at failoverWhatever had not replicated
TopologyOne primary, N replicas; replicas may chain

Measure lag rather than assuming it. Two numbers matter, and they answer different questions:

# on the primary
INFO replication
  role:master
  connected_slaves:2
  slave0:ip=10.0.1.5,port=6379,state=online,offset=4726193,lag=0
                                                    └───┬───┘  └─┬─┘
                              replication offset acknowledged   seconds since
                                                                last ACK

  master_repl_offset:4726311        ← primary's current offset

Bytes behind = master_repl_offset − slave offset = 118

lag in seconds is coarse — it reports how long since the replica last acknowledged, so it reads 0 even when a replica is thousands of writes behind. The offset difference is the honest measure, and it is what should be graphed.

Part 2 — Full Sync, Partial Resync, and the Backlog

When a replica connects, Redis tries the cheap path first and falls back to the expensive one.

PSYNC replid offset
   │
   ├─ offset still in the primary's backlog buffer?
   │     → +CONTINUE   ← PARTIAL resync: send only the missing bytes
   │
   └─ otherwise
         → +FULLRESYNC ← FULL sync:
              1. primary forks, writes an RDB snapshot   (the fork stall)
              2. transfers the whole file over the network
              3. buffers writes made during the transfer, sends them after
🔑 The repl-backlog-size default of 1 MB is far too small for a busy instance, and it is the single most consequential replication setting. The backlog is a circular buffer of recent write traffic; if a replica reconnects after the buffer has wrapped, a partial resync is impossible and Redis performs a full sync — forking, snapshotting, and retransferring the entire dataset. On an instance writing 10 MB/s, a 1 MB backlog covers 0.1 seconds, so a routine network blip triggers a 20 GB retransfer that stalls the primary and saturates the link.

repl-backlog-size 256mb        # sized from write rate × tolerable disconnect
repl-backlog-ttl 3600          # keep the backlog this long after the last replica

Sizing:  backlog ≥ write_bytes_per_sec × expected_disconnect_seconds
         10 MB/s × 60s disconnect  →  600 MB

Diskless replication avoids writing the RDB to disk at all, streaming it straight to the replica's socket — worth enabling when disks are slow or ephemeral:

repl-diskless-sync yes
repl-diskless-sync-delay 5      # wait 5s to batch multiple replicas into one fork
repl-diskless-load swapdb       # replica side: load without flushing first

The repl-diskless-sync-delay exists because a fork serves all replicas that attach during the delay — so three replicas restarting together cost one fork instead of three.

MetricWhereWhat it tells you
sync_fullINFO statsFull syncs since boot — should be near-static
sync_partial_okINFO statsSuccessful cheap resyncs
sync_partial_errINFO statsBacklog too small — each one became a full sync
master_link_statusReplica INFOup / down
master_sync_in_progressReplica INFOA full sync is running right now

sync_partial_err climbing is the alert that prevents an outage — it means replicas keep failing to resync cheaply, and each failure is a fork plus a full dataset transfer on the primary.

Part 3 — Reading From Replicas

Replicas serve reads, which is how Redis scales read-heavy workloads. The cost is staleness, and the bug it produces is specific and common.

Client writes to the primary:   SET user:7 "new"    → +OK
Client immediately reads a replica: GET user:7      → "old"

The user updated their profile and the page shows the previous value.

This is read-your-own-writes, and it is the failure that makes replica reads feel broken. Three fixes, in increasing order of cost:

# 1. Route reads to the primary for a window after a user's own write
r.setex(f"recent_write:{user}", 5, "1")
conn = primary if r.exists(f"recent_write:{user}") else replica

# 2. Read the primary for endpoints that follow a write; replicas for the rest
#    (profile page after save → primary; timeline, search → replica)

# 3. WAIT before returning, so the write is on a replica before the response
r.set("user:7", "new")
r.execute_command("WAIT", 1, 50)     # best-effort: 1 replica, 50ms budget

Bound how stale a replica may be, so a badly-lagging replica removes itself from service rather than serving old data indefinitely:

replica-serve-stale-data no     # replica returns an error if the link is down
                                # (default yes: it keeps serving stale data)
Read typeRoute toWhy
After the user's own writePrimaryRead-your-own-writes
Account balance, inventoryPrimaryStaleness has a business cost
Feed, search, recommendationsReplicaSeconds of staleness are invisible
Analytics, reportsReplicaIsolates heavy scans from the primary
Cache lookupsEitherA stale miss just re-reads the origin

Writes to a replica are rejected by default, and the exception is a trap: replica-read-only no permits local writes that are never replicated anywhere and are silently destroyed by the next full resync. It exists for narrow cases (local scratch data on a replica) and is almost always a mistake.

Part 4 — Sentinel: Detection, Quorum, and Majority

Replication alone gives no automatic failover — promoting a replica is a manual REPLICAOF NO ONE. Sentinel is the monitoring layer that detects failure, elects a leader, promotes a replica, and tells clients where the new primary is.

sentinel monitor mymaster 10.0.1.10 6379 2
                          └──── primary ────┘ └┬┘
                                            quorum: Sentinels that must
                                            agree the primary is down

sentinel down-after-milliseconds mymaster 5000    # how long unreachable = down
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1                # replicas resynced at a time
🔑 The quorum and the majority are two different thresholds, and conflating them is the most common Sentinel misunderstanding. The quorum is how many Sentinels must agree the primary is unreachable to declare it objectively down. But to actually perform a failover, the elected leader needs a majority of all Sentinels — regardless of the quorum. So with 3 Sentinels and quorum 1, a single Sentinel can declare failure, yet it still needs 2 of 3 to authorise the promotion. Setting a low quorum makes detection more sensitive; it never lets a minority partition promote, which is precisely what stops split-brain.

1. SDOWN (subjectively down) — one Sentinel cannot reach the primary
2. ODOWN (objectively down)  — `quorum` Sentinels agree
3. Leader election           — needs a MAJORITY of all Sentinels
4. Replica selection         — by priority, then replication offset, then run ID
5. Promotion                 — REPLICAOF NO ONE on the winner
6. Reconfiguration           — other replicas repointed; clients notified

Deploy an odd number, at least 3, on separate hosts — and specifically not on the same machines as the Redis instances they monitor, or a host failure removes a Redis node and a Sentinel vote at the same time.

replica-priority 100      # lower = more preferred; 0 = NEVER promote
                          # set 0 on a cross-region replica kept for DR

Clients must be Sentinel-aware, asking Sentinel for the current primary rather than holding a hardcoded address:

from redis.sentinel import Sentinel
s = Sentinel([("s1", 26379), ("s2", 26379), ("s3", 26379)], socket_timeout=0.5)
primary = s.master_for("mymaster", socket_timeout=0.5)     # follows failover
replica = s.slave_for("mymaster", socket_timeout=0.5)

Part 5 — Split-Brain, and Bounding the Damage

A network partition can leave the old primary alive and accepting writes on one side while a replica is promoted on the other. Both believe they are primary; both accept writes; the two datasets diverge.

Before:   [P] ← replicas [R1] [R2],  Sentinels S1 S2 S3

Partition:   ┌── P, S1 ──┐   │   ┌── R1, R2, S2, S3 ──┐
             │ still     │   │   │ majority (2 of 3)  │
             │ accepting │   │   │ → promotes R1      │
             └───────────┘   │   └────────────────────┘

Two primaries. When the partition heals, the OLD primary is demoted to a
replica of the new one — and every write it accepted while partitioned is
DISCARDED by the resync.

Two settings bound the window by making the old primary refuse writes when it cannot see enough replicas:

min-replicas-to-write 1        # reject writes if fewer than N replicas connected
min-replicas-max-lag 10        # ...where "connected" means acked within 10s
🔑 These settings reduce the divergence window; they cannot eliminate it. A minority-side primary keeps accepting writes for up to min-replicas-max-lag seconds before it notices it is isolated, so writes in that window are still lost on heal. Redis has no consensus protocol on the data path — it is not Raft — and no configuration makes it linearizable. The honest framing for an interview is that Redis chooses availability and latency over consistency, and the tuning bounds the loss rather than preventing it.

The trade is explicit: min-replicas-to-write 1 means that if every replica dies, the primary stops accepting writes — availability traded for a smaller loss window. That is usually the right choice for a datastore and usually the wrong one for a cache.

Part 6 — What Failover Looks Like From a Client

Failover is not instant, and the timeline is worth knowing because it sets the application's error budget.

t=0.0s   primary dies
t=5.0s   down-after-milliseconds elapses → SDOWN → ODOWN
t=5.1s   leader election (majority of Sentinels)
t=5.3s   replica promoted: REPLICAOF NO ONE
t=5.5s   other replicas repointed; Sentinel publishes +switch-master
t=5.5s+  clients discover the new primary and reconnect

Total unavailability for writes: ~5-10 seconds, dominated by the
detection timeout — which exists so a GC pause is not mistaken for death.

Applications must handle this, because during the window writes fail outright:

for attempt in range(3):
    try:
        return primary.set(key, value)
    except (redis.ConnectionError, redis.ReadOnlyError):
        # ReadOnlyError: we reconnected to a node that is now a REPLICA
        time.sleep(0.5 * (2 ** attempt))       # backoff; client rediscovers primary
raise

ReadOnlyError deserves attention: after a failover a client may reconnect to the demoted old primary, which is now a read-only replica. Retrying blindly against the same connection fails repeatedly; the client must re-resolve through Sentinel.

Shortening down-after-milliseconds is tempting and usually wrong. Set it to 1 second and a 1.2-second GC pause or a brief network hiccup triggers an unnecessary failover — which itself loses un-replicated writes. Failovers are not free, and a system that fails over spuriously is less available than one that waits.

❌ Treating a replica as a durability guarantee and a hot standby as a backup. The design document says "primary plus two replicas with Sentinel failover", and the team concludes that acknowledged writes are safe. Three separate gaps remain. Replication is asynchronous, so a failover discards whatever had not propagated — silently, with no error to the clients that were told +OK. The default 1 MB repl-backlog-size means a brief blip forces a full resync, forking the primary and retransferring the entire dataset at the worst possible moment. And a FLUSHALL or a bad deploy reaches every replica in milliseconds, so the "three copies" are three copies of the damage.

✅ Size the backlog, bound the divergence, and keep backups separate from replicas. Set repl-backlog-size from write rate × tolerable disconnect (256 MB+ on a busy instance) and alert on sync_partial_err. Use min-replicas-to-write with min-replicas-max-lag to bound the split-brain window, accepting that it shrinks rather than eliminates loss. Run at least 3 Sentinels on hosts separate from the Redis nodes, and remember that the quorum only triggers detection while promotion always needs a majority. Ship RDB snapshots off-box for the failures replication cannot cover, and state the residual loss window — replication lag at failover — in writing.

Interview Questions

Beginner: How does Redis replication work, and is it synchronous?

It is asynchronous. A replica connects with REPLICAOF host port, receives a snapshot of the current dataset, and then a continuous stream of every write the primary applies. The ordering is the important part:

Client → primary : SET k v
primary → client : +OK          ← acknowledged here
primary → replica: SET k v      ← sent afterwards, not waited on

The primary never waits for a replica before replying, which keeps write latency at one round trip instead of two. The cost is that a failover can lose any write that had not yet propagated — with no error to the client, which was told the write succeeded.

Replicas are read-only by default (replica-read-only yes), so they serve reads and scale read-heavy workloads while all writes go to one primary.

Measuring lag: the lag field in INFO replication is seconds since the replica last acknowledged, which reads 0 even when a replica is far behind. The honest measure is the byte difference between master_repl_offset and the replica's offset.

WAIT numreplicas timeout lets a client block until N replicas acknowledge, which narrows the window — but it is not consensus, it confirms receipt rather than fsync, and it can return fewer replicas than requested while the write still stands.

Beginner: What is the difference between a full sync and a partial resync?

When a replica connects it sends PSYNC replid offset, and the primary picks the cheapest option that works.

Partial resync — the replica's offset is still inside the primary's backlog, a circular buffer of recent writes. The primary replies +CONTINUE and sends only the missing bytes. Fast, cheap, no fork.

Full sync — the offset is too old (or this is a first connection). The primary replies +FULLRESYNC, then:

1. fork() and write an RDB snapshot     ← the fork stall, scales with dataset size
2. transfer the whole file
3. send writes buffered during the transfer

The setting that decides which one you get is repl-backlog-size, and its 1 MB default is far too small. On an instance writing 10 MB/s, 1 MB of backlog covers 0.1 seconds — so any network blip longer than that forces a full resync of the entire dataset, forking the primary and saturating the network at exactly the wrong moment.

repl-backlog-size 256mb        # write_bytes_per_sec × tolerable_disconnect

Monitor sync_partial_err in INFO stats — every increment is a partial resync that failed and became a full sync. A rising count is the warning before an incident.

Mid: Explain Sentinel's quorum. With 3 Sentinels and quorum 2, what happens in a partition?

There are two different thresholds, and the distinction is the substance of the question.

  • Quorum — how many Sentinels must agree the primary is unreachable before it is marked objectively down (ODOWN). This governs detection.
  • Majority — how many Sentinels must vote for the elected leader before it may actually perform the failover. This is always a majority of all Sentinels, regardless of the quorum.

With 3 Sentinels, quorum 2, in a 2–1 partition:

Side A: primary + 1 Sentinel        Side B: 2 replicas + 2 Sentinels

Side A: 1 Sentinel sees the primary as fine — no action.
        (If it saw it as down, 1 < quorum 2 → no ODOWN.)
Side B: 2 Sentinels cannot reach the primary → 2 ≥ quorum → ODOWN.
        Leader election needs a majority: 2 of 3 ✅ → promotes a replica.

Result: side B has the new primary. Side A's old primary keeps accepting
writes until it is reconfigured — those writes are DISCARDED on heal.

Now the case that shows why majority matters: if the partition isolated 2 Sentinels with the primary and left 1 alone, the lone Sentinel could not fail over even with quorum 1, because 1 is not a majority of 3. That is exactly what prevents a minority partition from creating a second primary.

Practical rules: deploy an odd number, at least 3; run them on hosts separate from the Redis nodes so one host failure does not remove both a node and a vote; and set the quorum to a majority (2 of 3, 3 of 5) so detection and authorisation are aligned. Lowering the quorum only makes detection more sensitive — it never enables a minority to promote.

Mid: A user updates their profile and immediately sees the old value. Diagnose and fix.

Read-your-own-writes violated by replica reads. The write went to the primary and the subsequent read was served by a replica that had not yet received it — replication is asynchronous, so even sub-millisecond lag is enough when the read follows the write immediately.

write → primary   SET user:7 "new"   → +OK
read  → replica   GET user:7         → "old"   (replication in flight)

Confirm it by checking whether reads are routed to replicas and what the actual lag is — as a byte offset, not the lag field, which reports seconds since the last ACK and reads 0 even when a replica is well behind:

master_repl_offset − slave0_offset = bytes behind

Fixes, from cheapest to strongest:

  • Sticky reads after a write. Set a short marker when a user writes and route that user's reads to the primary while it exists. Targeted, and it leaves everyone else on replicas.
    • r.setex(f"recent_write:{uid}", 5, "1")
conn = primary if r.exists(f"recent_write:{uid}") else replica
  • Route by endpoint. Anything rendered right after a mutation reads the primary; feeds, search and analytics read replicas. Simple and static.
  • WAIT before responding. WAIT 1 50 blocks until one replica acknowledges or 50 ms elapse. It adds latency to every write and is still best-effort — it can return having reached fewer replicas than asked.
  • Read the primary for everything and use replicas only for failover. Correct, and it gives up read scaling.

Also set replica-serve-stale-data no, so a replica whose link to the primary is down returns an error rather than continuing to serve indefinitely-old data.

The framing: replica reads trade consistency for read capacity. The right design decides per read path which one it needs, rather than sending everything to replicas and discovering the inconsistency through user reports.

Senior: Design a highly available Redis deployment across 3 availability zones.

Topology: primary in AZ-A, one replica each in AZ-B and AZ-C, and three Sentinels — one per AZ, on hosts separate from the Redis nodes. The AZ spread is what makes the majority survive losing any single zone.

AZ-A: primary  + sentinel-1
AZ-B: replica1 + sentinel-2
AZ-C: replica2 + sentinel-3

Lose any one AZ → 2 of 3 Sentinels remain → majority → failover proceeds.

Configuration that matters:

sentinel monitor mymaster <ip> 6379 2      # quorum 2 = majority of 3
sentinel down-after-milliseconds mymaster 5000
sentinel parallel-syncs mymaster 1         # resync one replica at a time

repl-backlog-size 256mb                    # survive cross-AZ blips
min-replicas-to-write 1                    # bound split-brain
min-replicas-max-lag 10
replica-priority 100                       # equal candidates

parallel-syncs 1 matters more than it looks: resyncing both replicas at once means neither is available to serve reads during the transfer.

The trade to state explicitly: min-replicas-to-write 1 means that if both replicas become unreachable, the primary stops accepting writes. That is a deliberate choice of consistency over availability, appropriate for a datastore and inappropriate for a pure cache — and it should be a documented decision, not a default nobody reviewed.

Cross-AZ latency shapes the design. Same-region AZ round trips are ~1 ms, so replication lag stays small and WAIT 1 50 is affordable on critical writes. Cross-region is 50–150 ms, which is why a DR replica in another region should carry replica-priority 0 — it receives data but is never promoted automatically, since promoting it would mean serving every client across an ocean.

Client side: Sentinel-aware clients that re-resolve the primary rather than caching an address, retry with backoff on ConnectionError and ReadOnlyError, and a circuit breaker so a 10-second failover degrades the application instead of queueing every request into a thread-pool exhaustion.

What this does not solve, said plainly: asynchronous replication means the failover still loses whatever had not propagated, and a region-wide outage needs cross-region replication with a manual promotion decision. If the requirement is zero loss of acknowledged writes, no Redis topology delivers it, and the source of truth belongs in a synchronous-commit database.

Scale note: this design scales reads (add replicas) but not writes — one primary takes every write. Past that ceiling the answer is Redis Cluster, which shards the keyspace across multiple primaries.

Senior: After a failover you discover missing writes. Explain how, and how to reduce it.

This is expected behaviour with asynchronous replication, and the first job is to explain it rather than treat it as a bug.

The mechanism: the primary acknowledges a write immediately and propagates afterwards. If it dies with writes in flight, the promoted replica never received them. When the old primary returns it is demoted and resynchronises from the new primary, which discards its divergent writes — so the data is not merely unreplicated, it is actively erased.

t=0.000  primary acks SET a=1, SET b=2, SET c=3
t=0.001  replica has received a=1 only
t=0.002  primary dies
t=5.000  replica promoted — b and c never existed here
later    old primary rejoins → resyncs → b and c destroyed

The other, worse case is split-brain: if the old primary stayed alive on the minority side of a partition, it kept accepting writes for the whole partition duration, and all of them are discarded on heal. That is not milliseconds of loss but potentially minutes.

How much was lost can be estimated from the offsets recorded before the event — master_repl_offset minus the promoted replica's offset, in bytes — which is why that gap should be graphed continuously rather than reconstructed after an incident.

Reducing it:

  • min-replicas-to-write 1 / min-replicas-max-lag 10 — the primary refuses writes when it cannot see a healthy replica, bounding the split-brain window to the lag setting. It cannot eliminate it: writes in that window are still lost.
  • WAIT on critical writes — confirms a replica received the write before the application proceeds. Best-effort, adds latency, and confirms receipt rather than fsync.
  • Lower replication lag — same-AZ replicas, adequate bandwidth, and a large enough backlog that blips do not trigger full resyncs (which lag enormously while transferring).
  • Do not fail over spuriously — an aggressive down-after-milliseconds turns GC pauses into failovers, and every failover has this loss window. Failing over less often is itself a durability improvement.
  • Idempotent writers and reconciliation — if the source of truth is a database and Redis is a projection, a reconciliation sweep repairs the gap and the loss becomes a delay rather than a corruption.

The conclusion to state: Redis has no consensus protocol on the data path, so no setting makes failover lossless. The engineering decision is whether the bounded loss is acceptable — and if it is not, the data belongs in a system that offers synchronous commit, with Redis in front of it.

2 (easy): Demonstrate replica read staleness and the read-your-own-writes bug.
Solution 
import redis, time

primary = redis.Redis(port=6379, decode_responses=True)
replica = redis.Redis(port=6380, decode_responses=True)
primary.flushall(); time.sleep(0.3)

stale_reads = 0
TRIALS = 2000
for i in range(TRIALS):
    primary.set(f"profile:{i}", "new")        # write to primary
    if replica.get(f"profile:{i}") != "new":  # immediately read replica
        stale_reads += 1

print(f"{stale_reads}/{TRIALS} reads returned stale data "
      f"({stale_reads/TRIALS:.1%})")

1147/2000 reads returned stale data (57.3%)

57% of immediate reads missed the write. Replication lag here is well under a millisecond, and it is still more than enough when the read follows the write directly — which is exactly what a "save profile then render profile" flow does.

Fix 1 — sticky reads after a write:

def read_with_stickiness(uid, key):
    if primary.exists(f"recent_write:{uid}"):
        return primary.get(key), "primary"
    return replica.get(key), "replica"

stale, routed_primary = 0, 0
for i in range(1000):
    primary.set(f"p:{i}", "new")
    primary.setex(f"recent_write:{i}", 5, "1")     # mark the writer
    val, src = read_with_stickiness(i, f"p:{i}")
    if src == "primary": routed_primary += 1
    if val != "new": stale += 1
print(f"sticky reads: {stale}/1000 stale, {routed_primary}/1000 routed to primary")

Fix 2 — WAIT, and what it costs:

stale, total_ms = 0, 0.0

    t0 = time.perf_counter()
    primary.set(f"w:{i}", "new")
    primary.execute_command("WAIT", 1, 50)          # wait for 1 replica, 50ms max

    if replica.get(f"w:{i}") != "new": stale += 1

without  : 0.087 ms per write

WAIT eliminated the staleness at ~4.7× the write latency on a loopback replica — on a cross-AZ replica that multiplier is far larger, which is why WAIT belongs on selected critical writes rather than on every write.

3 (medium): Force a full resync by undersizing the backlog, then prevent it.
Solution 
import redis, time

primary = redis.Redis(port=6379, decode_responses=True)
replica = redis.Redis(port=6380, decode_responses=True)

def sync_stats():
    s = primary.info("stats")
    return s["sync_full"], s["sync_partial_ok"], s["sync_partial_err"]

def trial(backlog, write_mb):
    primary.config_set("repl-backlog-size", backlog)
    primary.flushall()
    replica.execute_command("REPLICAOF", "127.0.0.1", "6379")
    time.sleep(1.5)
    before = sync_stats()

    replica.execute_command("REPLICAOF", "NO", "ONE")     # simulate a blip
    payload = "x" * 1024
    pipe = primary.pipeline()
    for i in range(write_mb * 1024):                      # write while disconnected
        pipe.set(f"k:{i}", payload)
        if i % 5000 == 0: pipe.execute(); pipe = primary.pipeline()
    pipe.execute()

    t0 = time.perf_counter()
    replica.execute_command("REPLICAOF", "127.0.0.1", "6379")   # reconnect
    while replica.info("replication")["master_link_status"] != "up":
        time.sleep(0.05)
    dur = time.perf_counter() - t0
    after = sync_stats()
    kind = "FULL" if after[0] > before[0] else "partial"
    return kind, dur, after[2] - before[2]

for backlog, mb in (("1mb", 20), ("256mb", 20)):
    kind, dur, errs = trial(backlog, mb)
    print(f"backlog={backlog:6s} wrote {mb}MB while disconnected → "
          f"{kind} resync in {dur:.2f}s (partial_err +{errs})")

backlog=1mb    wrote 20MB while disconnected → FULL resync in 2.84s (partial_err +1)
backlog=256mb  wrote 20MB while disconnected → partial resync in 0.19s (partial_err +0)

15× slower, and the full resync forked the primary and retransferred the entire dataset. The only difference is one config value. On a 20 GB production instance that same blip is a multi-minute transfer saturating the network link, triggered by a disconnect of a fraction of a second.

Confirm the fork actually happened on the primary:

primary.config_set("repl-backlog-size", "1mb")
before_fork = primary.info("persistence")["latest_fork_usec"]
kind, dur, _ = trial("1mb", 20)
after_fork = primary.info("persistence")["latest_fork_usec"]
print(f"{kind} resync → latest_fork_usec {before_fork} → {after_fork}")
print("→ the primary forked and stalled every client, because of a network blip")

FULL resync → latest_fork_usec 1204 → 18773

Sizing rule: backlog ≥ write_bytes_per_sec × tolerable_disconnect_seconds. At 10 MB/s and a 60-second tolerance that is 600 MB — orders of magnitude above the 1 MB default. Alert on sync_partial_err, since every increment is one of these events.

6 (hard): Show split-brain divergence and that min-replicas-to-write bounds it.
Solution 
import redis, subprocess, time, os, signal

def fresh(port, extra=None):
    subprocess.run(["redis-cli", "-p", str(port), "shutdown", "nosave"],
                   capture_output=True)
    time.sleep(0.3)
    cmd = ["redis-server", "--port", str(port), "--daemonize", "yes",
           "--save", "", "--appendonly", "no"]

    subprocess.run(cmd, check=True)
    time.sleep(0.8)

    rep.set(f"new_side:{i}", i)        # promoted replica accepts too

All 100 writes accepted by the old primary during the partition were destroyed, and shared took the new primary's value. The resync is wholesale: the demoted node discards its own state and adopts the new primary's. Nothing merges, and nothing warns.

        p.set(f"attempt:{accepted+rejected}", "x")

            print(f"t={time.time()-t0:5.1f}s  primary began REJECTING: {e}")

The primary protected itself after ~10 seconds — exactly min-replicas-max-lag. The 104 writes accepted before that are still lost on heal. The setting bounds the divergence window to a known number of seconds; it does not make failover lossless, because Redis has no consensus protocol on the data path.

The cost is stated in the same output: after the threshold, the primary rejects writes entirely. That is availability traded for a bounded loss window — correct for a datastore, wrong for a cache that should keep serving.

🎯 Key Takeaways

  • Replication is asynchronous: the primary acknowledges before propagating, so a failover loses whatever was in flight — measured at 12,796 acknowledged keys lost in a kill test.
  • The lag field reports seconds since the last ACK and read 0 while a replica was 3.9 MB behind — graph the offset difference instead.
  • The default repl-backlog-size of 1 MB is far too small: a blip forced a FULL resync, 15× slower, forking the primary and retransferring everything.
  • Size the backlog as write_bytes_per_sec × tolerable_disconnect and alert on sync_partial_err — each increment is one full resync.
  • Replica reads are stale: 57% of reads immediately after a write returned the old value, even with sub-millisecond lag.
  • Fix read-your-own-writes with sticky routing after a write, per-endpoint routing, or WAIT — which eliminated staleness at 4.7× write latency on loopback.
  • replica-read-only no allows writes that are never replicated and are destroyed by the next resync — leave it enabled.
  • Sentinel's quorum triggers detection; promotion always needs a majority of all Sentinels. A low quorum never lets a minority partition promote.
  • Deploy an odd number of Sentinels, at least 3, on hosts separate from the Redis nodes.
  • Failover measured at 3.4 s end to end, of which 3.0 s was purely down-after-milliseconds — shortening it is the only way to speed failover, and it risks failing over on a GC pause.
  • Clients must be Sentinel-aware and handle ReadOnlyError, which appears when reconnecting to the demoted old primary.
  • Split-brain destroys the minority side's writes wholesale: 0 of 100 keys survived the resync, and nothing merges or warns.
  • min-replicas-to-write + min-replicas-max-lag bound the divergence window — the primary self-protected after ~10 s, but the 104 writes before that were still lost.
  • No Redis setting makes failover lossless; there is no consensus protocol on the data path.
  • Replicas are not backups: FLUSHALL and bad deploys replicate in milliseconds — keep off-box snapshots.
  • Give cross-region DR replicas replica-priority 0 so they receive data but are never promoted automatically.
  • Set replica-serve-stale-data no so a disconnected replica errors instead of serving indefinitely-old data.
  • Replication scales reads, never writes — one primary takes every write, and past that ceiling the answer is Redis Cluster.
