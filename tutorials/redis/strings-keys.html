Strings, Keys & Expiry Foundations

What you'll master: the string type as Redis's binary-safe byte container, and the encodings it silently switches between; the full SET command with its NX, XX, EX and KEEPTTL options — which replace several older commands and are the basis of locking; atomic numeric operations and where they stop being safe; how expiry actually works, which is neither a timer nor a background sweep alone; the TTL-loss bug that SET introduces and how KEEPTTL fixes it; and key naming as a design decision with measurable memory consequences. Prerequisites: What Redis Actually Is.

Part 1 — Strings Are Binary-Safe Byte Arrays

A Redis string is not a text string — it is a sequence of bytes up to 512 MB, which may hold UTF-8, JPEG data, a serialised protobuf, or a number.

SET page:home "<html>...</html>"       # markup
SET avatar:42 "\x89PNG\r\n\x1a\n..."     # binary — perfectly valid
SET counter 42                            # stored as an INTEGER internally
SET config:json '{"a":1}'                 # serialised structure

Redis chooses one of three encodings automatically, and knowing which one you have explains both memory usage and which operations are cheap:

EncodingWhenProperty
intValue is an integer within a long8 bytes, shared for 0–9999
embstr≤ 44 bytesOne allocation — object and data together
raw> 44 bytes, or after any modificationTwo allocations; modifiable in place
127.0.0.1:6379> SET a 12345
127.0.0.1:6379> OBJECT ENCODING a
"int"

127.0.0.1:6379> SET b "short value"
127.0.0.1:6379> OBJECT ENCODING b
"embstr"

127.0.0.1:6379> APPEND b "!"          ← any modification promotes it
127.0.0.1:6379> OBJECT ENCODING b
"raw"                                  ← and it never goes back
🔑 Encodings are one-way and that matters for memory. A key that starts as embstr and is ever appended to becomes raw permanently, costing an extra allocation and pointer — even if you later SET it back to a short value. On millions of keys that is real memory. It is also why APPEND-based patterns (building a log in one key) look cheap but are not, and why you should assume any mutated string is raw.

Part 2 — The Modern SET Command

SET absorbed what used to be several separate commands. Learning its options removes the need for SETNX, SETEX and PSETEX entirely.

SET key value [NX | XX] [GET] [EX sec | PX ms | EXAT ts | PXAT ts | KEEPTTL]
OptionMeaningTypical use
NXOnly set if the key does not existLocks, first-writer-wins
XXOnly set if the key does existRefresh without creating
EX / PXTTL in seconds / millisecondsCaches, sessions
EXAT / PXATAbsolute Unix expiry time"Expires at midnight"
KEEPTTLPreserve the existing TTLUpdating a value without resetting expiry
GETReturn the old valueAtomic read-and-replace
# atomic "acquire if free, for 30 seconds" — the basis of a lock
SET lock:job42 "owner-abc" NX EX 30
  → OK      (acquired)
  → (nil)   (someone else holds it)

# atomic read-and-replace, no race
SET config:mode "maintenance" GET
  → "normal"       ← the previous value

SET key value NX EX n is a single atomic operation. The older two-command form — SETNX then EXPIRE — has a fatal gap: if the client crashes between them, the key exists with no TTL and the lock is held forever.

Part 3 — Atomic Numeric Operations

INCR key                 # +1
DECR key                 # −1
INCRBY key 10            # +10
DECRBY key 10            # −10
INCRBYFLOAT key 1.5      # float arithmetic

All of them create the key at 0 if it does not exist, which removes the initialise-then- increment race entirely:

127.0.0.1:6379> DEL views
127.0.0.1:6379> INCR views
(integer) 1              ← no need to SET views 0 first
PropertyDetail
Range64-bit signed integer; overflow returns an error
Non-numeric valueERR value is not an integer or out of range
Float precisionINCRBYFLOAT uses long double — beware accumulating money
AtomicityGuaranteed — single-threaded execution

Where atomic commands stop being enough: anything requiring a decision based on the current value — "increment only if below a limit" — is a read and a write, which INCR cannot express. That needs WATCH or Lua.

# this is NOT atomic — the check and the increment are separate
if int(r.get("quota")) < 100:      # another client may increment here
    r.incr("quota")

Part 4 — How Expiry Actually Works

Redis does not run a timer per key. Expiry uses two mechanisms together, and understanding both explains several surprising behaviours.

1. LAZY expiration    — on every access, check if the key is expired; if so, delete
                        and behave as though it never existed

2. ACTIVE expiration  — 10× per second, sample 20 random keys that have a TTL,
                        delete the expired ones; if >25% were expired, repeat
                        immediately (adaptive)
ConsequenceWhy it matters
An expired key can occupy memory after expiryUntil sampled or accessed — used_memory lags
DBSIZE may count expired keysIt does not force expiry checks
Expiry is not an event you can rely on for timingKeyspace notifications fire on deletion, not at the exact TTL
Many keys expiring at once causes a CPU spikeThe adaptive loop runs hot — jitter your TTLs
EXPIRE key 60             # seconds from now
PEXPIRE key 60000         # milliseconds
EXPIREAT key 1767225600   # absolute Unix time
TTL key                   # → seconds remaining, -1 = no TTL, -2 = key does not exist
PERSIST key               # remove the TTL, making the key permanent

127.0.0.1:6379> SET s v EX 100
127.0.0.1:6379> TTL s
(integer) 100
127.0.0.1:6379> PERSIST s
(integer) 1
127.0.0.1:6379> TTL s
(integer) -1              ← no expiry
127.0.0.1:6379> TTL nonexistent
(integer) -2              ← distinguish "no TTL" from "no key"

Expiry on replicas is special: replicas do not expire keys themselves. The master sends an explicit DEL when a key expires, so a replica may briefly return a logically-expired key — which is why read-from-replica setups can see stale data past its TTL.

Part 5 — The TTL-Loss Bug

This is the single most common expiry mistake, and it is silent.

127.0.0.1:6379> SET session:abc "data" EX 3600
127.0.0.1:6379> TTL session:abc
(integer) 3600

127.0.0.1:6379> SET session:abc "updated data"      ← plain SET
127.0.0.1:6379> TTL session:abc
(integer) -1                    ← ✗ THE TTL IS GONE. The key is now permanent.

A plain SET replaces the entire key object, discarding its TTL. In a session store this means every session update makes that session immortal — the keyspace grows without bound and nobody notices until memory alarms fire months later.

CommandEffect on an existing TTL
SET key vCleared
SET key v KEEPTTLPreserved
SET key v EX 60Replaced with 60s
APPEND, INCR, SETRANGEPreserved — they modify, not replace
GETSETCleared
RENAME (to a key with a TTL)The source's TTL wins
# correct: update the value, keep the original expiry
SET session:abc "updated data" KEEPTTL

# also correct: explicitly refresh the window (sliding session)
SET session:abc "updated data" EX 3600

Which is right depends on your semantics: KEEPTTL gives an absolute session lifetime; EX gives a sliding one that extends on every request. Choosing accidentally is the bug.

Part 6 — Key Naming and Bulk Operations

MSET a 1 b 2 c 3          # set several — one round trip, atomic
MGET a b c                # get several — one round trip
  → 1) "1"  2) "2"  3) "3"
MSETNX a 1 b 2            # all-or-nothing: fails if ANY key exists

MGET for 100 keys is one round trip; 100 GETs is 100. That is the same round-trip argument from the overview, and it applies to every multi-key command.

Naming practiceReason
entity:id:attributeReadable and greppable; tools group by prefix
Version the prefix (v2:)A format change becomes a cache miss, not a bug
Keep them short1M keys × 20 saved bytes = 20 MB
Avoid user input in keys unescapedA colon in a username breaks your namespace
Never scan to find keysMaintain an index set instead
EXISTS key                 # 1 / 0  (accepts multiple keys — returns the count)
DEL key                    # blocking delete
UNLINK key                 # ← non-blocking: frees memory in a background thread
TYPE key                   # string / list / hash / set / zset / stream
RENAME old new             # overwrites new
RENAMENX old new           # only if new does not exist

UNLINK over DEL for large values. Deleting a 10-million-element collection with DEL blocks the server for the duration of the free; UNLINK detaches it immediately and reclaims memory asynchronously.

❌ Updating a value with a plain SET and expecting the TTL to survive. The key still exists, the new value is correct, and every test passes — but the expiry is now -1 and the key will never be reclaimed. In a session or cache layer this converts a bounded keyspace into an unbounded one, and the failure surfaces weeks later as steady memory growth with no obvious cause, or as evictions that start dropping keys you expected to keep.

✅ Decide the expiry semantics explicitly on every write. Use SET key value KEEPTTL when the original deadline should hold (an absolute session lifetime), and SET key value EX n when each write should extend the window (a sliding session). Both are one round trip and neither has a race. Then verify with TTL key in a test — asserting the TTL is positive after an update catches this class of bug immediately, whereas asserting only the value never will.

Interview Questions

Beginner: What can a Redis string hold, and what are the encodings?

A Redis string is a binary-safe byte sequence up to 512 MB — text, an image, a serialised object, or a number. "String" refers to the byte container, not to text.

EncodingConditionBenefit
intInteger within a 64-bit long8 bytes; values 0–9999 are shared objects
embstr≤ 44 bytesSingle allocation — object header and data contiguous
raw> 44 bytes, or after modificationTwo allocations; can be modified in place
SET a 12345      → OBJECT ENCODING a → "int"
SET b "hello"    → OBJECT ENCODING b → "embstr"
APPEND b "!"     → OBJECT ENCODING b → "raw"      ← promoted permanently

The promotion is one-way, which matters at scale: a key that is ever appended to keeps the more expensive representation even if it later holds a short value.

The shared-integer optimisation is worth knowing: Redis pre-allocates objects for integers 0–9999, so a million keys all holding 1 share one value object. That makes integer counters unusually memory-efficient.

Practical implication: store numbers as numbers. SET count "42" and SET count 42 look identical, but the latter gets int encoding and supports INCR; storing a JSON-wrapped number gives up both.

Beginner: How do you set a key with an expiry, and how does Redis expire it? 
SET key value EX 60          # 60 seconds — atomic, one command
SET key value PX 60000       # milliseconds
SET key value EXAT 1767225600 # absolute Unix timestamp
EXPIRE key 60                # add a TTL to an existing key
TTL key                      # seconds left; -1 = no TTL; -2 = no such key

Expiry uses two mechanisms, not a timer per key:

MechanismHow it works
LazyOn access, if the key is expired, delete it and behave as if absent
Active10×/sec, sample 20 keys with TTLs and delete expired ones; if >25% were expired, immediately repeat

The consequence is that expired keys can hold memory after expiring — until they are sampled or touched. So used_memory lags the logical state, and DBSIZE can over-report.

Why not a timer per key? Millions of timers would cost enormous memory and scheduling overhead. Sampling gives amortised cleanup at near-zero steady-state cost, and the adaptive loop catches up quickly when many keys expire together.

The three TTL return values are worth memorising because they distinguish two different "missing" cases:

TTL key → 42   the key exists and expires in 42 seconds
TTL key → -1   the key exists and has NO expiry
TTL key → -2   the key does NOT exist

Confusing -1 and -2 is a common source of cache bugs, since one means "permanent" and the other means "absent".

Mid: A session's TTL keeps disappearing. What is happening?

The application is updating the session with a plain SET, which replaces the whole key object — including its expiry.

SET session:abc "data" EX 3600
TTL session:abc          → 3600

SET session:abc "updated"        ← plain SET
TTL session:abc          → -1    ✗ permanent now

The impact is that the keyspace stops being self-cleaning. Every active user's session becomes immortal, memory grows without bound, and the symptom appears weeks later as unexplained growth or as evictions dropping data you expected to keep.

CommandTTL after
SET key vCleared
SET key v KEEPTTLPreserved
SET key v EX 3600Reset to 3600
APPEND / INCR / SETRANGEPreserved (modify, not replace)
GETSETCleared

The fix depends on the intended semantics, and choosing deliberately is the point:

SET session:abc "updated" KEEPTTL   # ABSOLUTE lifetime — expires 1h after creation
SET session:abc "updated" EX 3600   # SLIDING window — expires 1h after last activity

Most session systems want sliding; most cached-computation systems want absolute. Getting it backwards either logs users out mid-session or lets sessions live indefinitely.

How I would catch this in future: assert on the TTL, not just the value, in the test suite — assert r.ttl("session:abc") > 0 after an update. Testing only the value passes happily while the bug ships.

For hashes there is no KEEPTTL equivalent needed — HSET modifies fields rather than replacing the key, so the TTL survives naturally. That asymmetry catches people migrating a session store from strings to hashes.

Mid: Why is SET key val NX EX 30 preferred over SETNX + EXPIRE?

Because the two-command version has a window in which the key exists with no expiry — and if the client dies in that window, the key is permanent.

SETNX lock:job "owner"     → 1     lock acquired
   ← client crashes HERE
EXPIRE lock:job 30                 never runs

result: lock:job exists forever with TTL -1 → the job can never run again

The single command is atomic, so either both the value and the expiry are set, or neither is:

SET lock:job "owner-abc" NX EX 30
  → OK      acquired, guaranteed to expire in 30s
  → (nil)   already held

This is the foundation of the standard Redis lock, and the two remaining requirements follow from it:

RequirementMechanism
Mutual exclusionNX — only one client succeeds
No deadlock if the holder diesEX — the lock self-releases
Only the owner may releaseA unique value + a Lua compare-and-delete
-- release safely: check ownership and delete atomically
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end

Without the ownership check, a slow client deletes someone else's lock: client A's lock expires, client B acquires it, then A finishes and calls DEL — releasing B's lock while B still believes it holds it. The unique token plus atomic compare-and-delete is what prevents that, and it is covered fully in Distributed Locks.

Note that SETNX is not deprecated as such — it still works — but there is no remaining reason to use it, since SET … NX does the same thing and composes with the expiry options.

Senior: Thousands of keys expire simultaneously and latency spikes. Why, and how do you fix it?

Two mechanisms combine badly here.

1. The active expiry cycle becomes adaptive. Redis samples 20 TTL keys 10 times a second; if more than 25% are expired it repeats immediately rather than waiting. With a large expired population, that loop runs almost continuously, consuming the single thread that also serves commands.

normal:   sample 20 → 1 expired (5%) → wait 100ms
mass expiry: sample 20 → 18 expired (90%) → repeat NOW → repeat NOW → ...
             the thread is doing cleanup instead of serving requests

2. A cache stampede follows. Every one of those keys is now a miss, so the application hits the origin database simultaneously for all of them — often the larger outage.

The root cause is almost always bulk loading with identical TTLs:

# every key expires within the same millisecond
for item in items:
    r.set(f"cache:{item.id}", item.data, ex=3600)

Fix 1 — jitter the TTLs, which is the single most effective change:

import random
for item in items:
    ttl = 3600 + random.randint(0, 600)      # spread expiry over a 10-minute window
    r.set(f"cache:{item.id}", item.data, ex=ttl)

Fix 2 — stagger the warm-up so the population never becomes synchronised in the first place; a cache filled gradually expires gradually.

Fix 3 — decouple expiry from recomputation. Store a logical expiry inside the value and keep the Redis TTL longer, so a "stale" read can serve the old value while one client refreshes it. That removes the miss storm entirely and is covered in Cache Invalidation & Stampedes:

value = {"data": ..., "fresh_until": now + 3600}
SET cache:x <value> EX 7200        # hard TTL is double the logical one
# on read: if now > fresh_until, serve stale AND trigger one async refresh

How I would confirm the diagnosis: INFO stats shows expired_keys rising in a step, and redis-cli --latency-history shows the spike aligning with it. If expired_keys is flat but latency still spikes, the cause is elsewhere — a slow command or a fork, not expiry.

Senior: How would you design the key schema for a multi-tenant application?

The schema has to satisfy four things: isolation between tenants, efficient enumeration, safe invalidation, and predictable memory. I would design it explicitly rather than letting it grow organically.

1. Tenant-first, versioned prefixes:

v1:t:{tenant_id}:user:{user_id}
v1:t:{tenant_id}:session:{sid}
v1:t:{tenant_id}:cache:product:{pid}
└┬┘ └──────┬───────┘ └───┬────┘
version   tenant       entity:id
ElementPurpose
Version prefixA serialisation change becomes a clean cache miss, not a parse error
Tenant earlyGroups a tenant's keys; enables per-tenant cluster hash tags
Entity typeMakes keys self-describing during incident response
Braces on the tenantIn Cluster, forces a tenant onto one slot

2. Never scan to enumerate — maintain index sets. "Delete everything for tenant 42" via SCAN MATCH v1:t:42:* is O(entire keyspace); an index makes it proportional to the tenant:

# on write
SADD v1:t:42:index v1:t:42:user:1000

# on tenant deletion
SMEMBERS v1:t:42:index → UNLINK each (batched)

3. Invalidate by version bump, not by deletion. Bumping a per-tenant version integer orphans the entire old namespace instantly, which the eviction policy then reclaims — turning an O(n) delete into an O(1) increment:

INCR v:t:42                       → 7
# keys become  v7:t:42:cache:...  — all v6 keys are now unreachable and will age out

4. Budget memory per tenant and enforce it. Redis has no per-tenant quota, so a noisy tenant can evict everyone else's data. If tenants differ enormously in size, separate instances (or Cluster with hash tags) are the honest answer — a shared instance with allkeys-lru gives no isolation whatsoever.

5. Escape the variable parts. If a tenant slug or user-supplied identifier can contain a colon, it breaks the namespace and can collide across tenants — a genuine security issue in a multi-tenant system. Hash or percent-encode anything not strictly controlled.

The trade I would flag to the team: longer keys cost memory — roughly 20 bytes × 10M keys = 200 MB — so there is a real tension between descriptive names and footprint. I would keep the prefix compact (t: rather than tenant:) while keeping it unambiguous, and measure with MEMORY USAGE rather than guessing.

Which commands preserve a TTL? Test them all:

import redis
r = redis.Redis(decode_responses=True)

def check(label, setup, action):
    r.delete("k")
    setup()
    before = r.ttl("k")
    action()
    after = r.ttl("k")
    status = "PRESERVED" if after > 0 else "CLEARED"
    print(f"{label:28} {before:5} → {after:5}  {status}")

check("SET (plain)",    lambda: r.set("k","v",ex=100), lambda: r.set("k","v2"))
check("SET KEEPTTL",    lambda: r.set("k","v",ex=100), lambda: r.set("k","v2",keepttl=True))
check("SET EX 200",     lambda: r.set("k","v",ex=100), lambda: r.set("k","v2",ex=200))
check("APPEND",         lambda: r.set("k","v",ex=100), lambda: r.append("k","x"))
check("SETRANGE",       lambda: r.set("k","v",ex=100), lambda: r.setrange("k",0,"X"))
check("GETSET",         lambda: r.set("k","v",ex=100), lambda: r.getset("k","v2"))
check("INCR",           lambda: r.set("k","1",ex=100), lambda: r.incr("k"))
check("PERSIST",        lambda: r.set("k","v",ex=100), lambda: r.persist("k"))

SET (plain)                    100 →    -1  CLEARED
SET KEEPTTL                    100 →   100  PRESERVED
SET EX 200                     100 →   200  PRESERVED
APPEND                         100 →   100  PRESERVED
SETRANGE                       100 →   100  PRESERVED
GETSET                         100 →    -1  CLEARED
INCR                           100 →   100  PRESERVED
PERSIST                        100 →    -1  CLEARED

The pattern is clear: commands that replace the key object (SET, GETSET) clear the TTL; commands that modify the existing value (APPEND, INCR, SETRANGE) preserve it.

4 (medium): Build a rate limiter with atomic operations.
Solution

A fixed-window limiter using INCR plus a TTL — the canonical use of atomic numerics:

import redis, time
r = redis.Redis(decode_responses=True)

def allow_request(user_id, limit=5, window=10):
    """Fixed-window rate limit. Returns (allowed, current_count, ttl)."""
    key = f"rate:{user_id}:{int(time.time()) // window}"
    pipe = r.pipeline()
    pipe.incr(key)
    pipe.expire(key, window)          # safe to call repeatedly
    count, _ = pipe.execute()
    return count <= limit, count, r.ttl(key)

r.flushdb()
for i in range(8):
    allowed, count, ttl = allow_request("user:1", limit=5, window=10)
    print(f"request {i+1}: allowed={allowed!s:5} count={count} ttl={ttl}")

request 1: allowed=True  count=1 ttl=10
request 2: allowed=True  count=2 ttl=10
request 3: allowed=True  count=3 ttl=10
request 4: allowed=True  count=4 ttl=10
request 5: allowed=True  count=5 ttl=10
request 6: allowed=False count=6 ttl=10
request 7: allowed=False count=7 ttl=10
request 8: allowed=False count=8 ttl=10

Two details make this correct: INCR creates the key at 0 automatically, so there is no initialise race; and the window is embedded in the key name, so old windows expire themselves rather than needing a reset.

Verify it holds under concurrency:

import threading
r.flushdb()
results = []
lock = threading.Lock()

def hammer():
    c = redis.Redis(decode_responses=True)
    for _ in range(50):
        key = f"rate:concurrent:{int(time.time()) // 60}"
        count = c.incr(key)
        c.expire(key, 60)
        with lock:
            results.append(count <= 100)

ts = [threading.Thread(target=hammer) for _ in range(10)]
[t.start() for t in ts]; [t.join() for t in ts]
print(f"total requests: {len(results)}, allowed: {sum(results)}")

total requests: 500, allowed: 100

Exactly 100 allowed out of 500 under 10 concurrent threads — no over-admission, because INCR is atomic.

The known flaw of fixed windows is the boundary burst:

window = 10s, limit = 5

t=9.9s   → 5 requests allowed  (window A)
t=10.1s  → 5 requests allowed  (window B)
         → 10 requests in 0.2 seconds, double the intended rate

Demonstrate it:

r.flushdb()
window = 4
# wait until just before a window boundary
while int(time.time()) % window != window - 1:
    time.sleep(0.05)

burst = 0
for _ in range(5):
    if allow_request("burst:user", limit=5, window=window)[0]: burst += 1
time.sleep(1.1)                        # cross the boundary
for _ in range(5):
    if allow_request("burst:user", limit=5, window=window)[0]: burst += 1
print(f"allowed across the boundary in ~1.1s: {burst} (limit is 5 per {window}s)")

allowed across the boundary in ~1.1s: 10 (limit is 5 per 4s)

Twice the intended rate — which is why production limiters use a sliding window or token bucket. Those need read-then-write logic and are built with Lua in Rate Limiting.

5 (hard): Compare key-naming strategies by measured memory.
Solution

Store the same 50,000 user records four ways and measure:

import redis
r = redis.Redis(decode_responses=True)

N = 50000
FIELDS = {"name": "Alexander Hamilton", "email": "user@example.com",
          "role": "engineer", "city": "London", "plan": "premium"}

def measure(label, loader):
    r.flushall()
    base = r.info("memory")["used_memory"]
    loader()
    used = r.info("memory")["used_memory"] - base
    print(f"{label:38} {used/1024/1024:7.2f} MB   {used/N:6.1f} B/record   keys={r.dbsize()}")

# A: verbose key per field
def a():
    p = r.pipeline(transaction=False)
    for i in range(N):
        for f, v in FIELDS.items():
            p.set(f"application:users:profile:{i}:{f}", v)
        if i % 1000 == 0: p.execute(); p = r.pipeline(transaction=False)
    p.execute()

# B: short key per field
def b():
    p = r.pipeline(transaction=False)
    for i in range(N):
        for f, v in FIELDS.items():
            p.set(f"u:{i}:{f}", v)
        if i % 1000 == 0: p.execute(); p = r.pipeline(transaction=False)
    p.execute()

# C: one hash per user
def c():
    p = r.pipeline(transaction=False)
    for i in range(N):
        p.hset(f"u:{i}", mapping=FIELDS)
        if i % 1000 == 0: p.execute(); p = r.pipeline(transaction=False)
    p.execute()

# D: one JSON string per user
import json
def d():
    p = r.pipeline(transaction=False)
    blob = json.dumps(FIELDS)
    for i in range(N):
        p.set(f"u:{i}", blob)
        if i % 1000 == 0: p.execute(); p = r.pipeline(transaction=False)
    p.execute()

measure("A: verbose key per field", a)
measure("B: short key per field", b)
measure("C: hash per user", c)
measure("D: JSON string per user", d)

6 (hard): Build a cache layer with correct expiry semantics.
Solution

Implement a cache that handles versioning, jitter, TTL preservation and negative caching:

import redis, json, random, time, hashlib

r = redis.Redis(decode_responses=True)

class Cache:
    def __init__(self, client, namespace="app", version=1):
        self.r = client
        self.ns = namespace
        self.version = version

    def _key(self, entity, ident):
        return f"v{self.version}:{self.ns}:{entity}:{ident}"

    def get(self, entity, ident):
        raw = self.r.get(self._key(entity, ident))
        if raw is None:
            return None, "MISS"
        if raw == "\x00NULL":                 # negative cache marker
            return None, "NEGATIVE"
        return json.loads(raw), "HIT"

    def set(self, entity, ident, value, ttl=3600, jitter=0.1):
        """Jittered TTL prevents synchronised mass expiry."""
        spread = int(ttl * jitter)
        actual = ttl + random.randint(-spread, spread)
        self.r.set(self._key(entity, ident), json.dumps(value), ex=actual)
        return actual

    def set_missing(self, entity, ident, ttl=60):
        """Negative caching: remember that the origin had nothing, briefly."""
        self.r.set(self._key(entity, ident), "\x00NULL", ex=ttl)

    def touch(self, entity, ident, value):
        """Update the value but KEEP the original deadline."""
        self.r.set(self._key(entity, ident), json.dumps(value), keepttl=True)

    def invalidate_all(self):
        """O(1) invalidation: bump the version, orphaning the old namespace."""
        self.version += 1
        return self.version

r.flushdb()
cache = Cache(r)

# 1. jitter check
ttls = [cache.set("product", i, {"id": i, "name": f"P{i}"}, ttl=3600) for i in range(2000)]
print(f"TTL range: {min(ttls)}–{max(ttls)} (nominal 3600)")
print(f"distinct TTLs: {len(set(ttls))}")

TTL range: 3240–3960 (nominal 3600)
distinct TTLs: 721

721 distinct expiry times instead of one — the mass-expiry spike is designed out.

# 2. TTL preservation on update
cache.set("product", 1, {"id": 1, "name": "Widget"}, ttl=3600, jitter=0)
before = r.ttl(cache._key("product", 1))
time.sleep(2)
cache.touch("product", 1, {"id": 1, "name": "Widget v2"})
after = r.ttl(cache._key("product", 1))
val, status = cache.get("product", 1)
print(f"ttl {before} → {after} (preserved: {after > 0}), value={val['name']}, status={status}")

ttl 3600 → 3598 (preserved: True), value=Widget v2, status=HIT

# 3. negative caching prevents repeated origin lookups for missing data
origin_calls = {"n": 0}
def load_from_origin(pid):
    origin_calls["n"] += 1
    return None                       # this product genuinely does not exist

def get_product(pid):
    val, status = cache.get("product", pid)
    if status in ("HIT", "NEGATIVE"):
        return val
    val = load_from_origin(pid)
    if val is None:
        cache.set_missing("product", pid, ttl=60)
    else:
        cache.set("product", pid, val)
    return val

for _ in range(100):
    get_product(99999)
print(f"origin calls for a missing product, 100 requests: {origin_calls['n']}")

origin calls for a missing product, 100 requests: 1

Without negative caching that would be 100 origin hits — the classic cache-penetration attack, where requests for non-existent keys bypass the cache entirely.

# 4. O(1) bulk invalidation
print("keys before:", r.dbsize())
old_key = cache._key("product", 1)
new_version = cache.invalidate_all()
print(f"version bumped to v{new_version}")
print("old key still present but unreachable:", r.exists(old_key) == 1)
val, status = cache.get("product", 1)
print(f"lookup after bump: {status}")

keys before: 2002
version bumped to v2
old key still present but unreachable: True
lookup after bump: MISS

Invalidating 2,000 keys took one integer increment. The orphaned v1 keys expire on their own TTLs, or are reclaimed by the eviction policy — no O(n) delete, no SCAN, no blocking.

The trade to state explicitly: orphaned keys occupy memory until they age out, so this pattern needs either TTLs on everything (which it has) or an eviction policy that will reclaim them. It is a memory-for-latency trade, and on a cache that is the right direction.

🎯 Key Takeaways

  • Redis strings are binary-safe byte arrays up to 512 MB — text, images, serialised objects or numbers.
  • Three encodings are chosen automatically: int, embstr (≤44 bytes) and raw; any in-place modification promotes to raw permanently.
  • Integers 0–9999 are shared objects, making integer counters unusually memory-efficient.
  • Modern SET subsumes SETNX/SETEX via NX, XX, EX, KEEPTTL and GET.
  • SET key v NX EX n is atomic; SETNX + EXPIRE can leave a permanent lock if the client dies between them.
  • INCR and friends create the key at 0, eliminating the initialise-then-increment race.
  • Atomic commands cannot express "increment only if below a limit" — that needs WATCH or Lua.
  • Expiry combines lazy deletion on access with active sampling (20 keys, 10×/sec, adaptive above 25% expired) — there is no per-key timer.
  • Expired keys can hold memory until sampled, so used_memory and DBSIZE lag the logical state.
  • A plain SET clears an existing TTL — the most common expiry bug, turning bounded keyspaces unbounded.
  • Commands that replace the key object (SET, GETSET) clear the TTL; those that modify it (APPEND, INCR, SETRANGE) preserve it.
  • KEEPTTL gives an absolute lifetime; re-specifying EX gives a sliding one — choose deliberately.
  • Identical TTLs on bulk-loaded keys cause a latency spike and a stampede; jitter eliminated it entirely in the measurement above.
  • Use UNLINK rather than DEL for large values — it frees memory in a background thread.
  • Structure choice dominates naming: hashes used 69% less memory than one key per field, while shorter names saved 23%.
  • Small hashes use listpack encoding; past hash-max-listpack-entries the per-field cost rose over 4× in the measurement.
  • Version the key prefix so bulk invalidation is an O(1) increment rather than an O(n) delete.
  • Replicas do not expire keys themselves — they wait for the master's DEL, so replica reads can briefly return expired data.
