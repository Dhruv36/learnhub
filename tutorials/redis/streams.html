Streams & Consumer Groups Messaging & Data Flow

What you'll master: the append-only log that gives Redis at-least-once delivery, and why that single guarantee changes every design decision from Pub/Sub; entry IDs as timestamps and what the sequence counter protects you from; the Pending Entries List — the structure that makes delivery recoverable and the one that silently grows into an outage when nobody acknowledges; XAUTOCLAIM and the exact reasoning for choosing a min-idle-time; why at-least-once means your consumer must be idempotent and what actually makes it so; trimming, which is the difference between a stream and a memory leak; and the honest comparison with Kafka that an interviewer is really asking for. Prerequisites: Pub/Sub, Transactions & Lua Scripting.

Part 1 — An Append-Only Log With IDs That Mean Something

A Stream is an append-only sequence of entries, each with a unique, monotonically increasing ID and a set of field/value pairs. Unlike Pub/Sub, the data stays — which is the entire reason the rest of this lesson exists.

XADD orders * item "laptop" qty 2        → "1723900000123-0"
                                             └─────┬─────┘ └┬┘
                                        ms timestamp    sequence

XADD orders * item "mouse"  qty 1        → "1723900000123-1"   ← same ms, seq+1
XADD orders * item "cable"  qty 5        → "1723900000456-0"   ← new ms, seq resets
🔑 The ID is a millisecond timestamp plus a sequence number, and both halves earn their place. The timestamp makes IDs sortable and lets you range-query by time without a secondary index — XRANGE orders 1723900000000 + is "everything since that moment". The sequence counter exists because modern hardware appends far more than one entry per millisecond; without it, IDs would collide and the log would lose its total order. Redis also guarantees IDs strictly increase even if the system clock moves backwards, so a clock adjustment cannot corrupt the stream.

CommandDoesNote
XADD key * f vAppend; * = server-generated IDO(1)
XLEN keyEntry countO(1)
XRANGE key start endRange scan, oldest first- and + = min/max
XREVRANGE key + - COUNT nNewest firstThe idiom for "last n"
XREAD ... BLOCK msRead new entries, optionally blockingNo group; every reader sees everything
XDEL key idDelete one entryDoes not renumber; IDs stay unique forever
XINFO STREAM keyLength, first/last ID, groupsFirst stop when debugging

XREAD without a group is the fan-out mode: every reader tracks its own position and sees every entry, exactly like a Kafka topic read without a consumer group. The special ID $ means "only entries added after this call blocks".

XREAD BLOCK 5000 STREAMS orders $        # wait up to 5s for genuinely new entries
XREAD COUNT 10 STREAMS orders 0          # replay from the very beginning

The blocking form is what makes Streams usable as a queue without polling: the client parks on the socket and Redis wakes it the moment an entry arrives, so latency is comparable to Pub/Sub while the data remains durable. Note that $ is resolved when the command is issued — entries added between your last read and this call are skipped, which is precisely why real consumers pass their last-seen ID instead.

Part 2 — Consumer Groups and the Pending Entries List

A consumer group is what turns the log into a work queue. Members of a group share the entries rather than each receiving a copy, and the group remembers what has been delivered but not yet acknowledged.

XGROUP CREATE orders workers $ MKSTREAM     # $ = only new entries; 0 = from the start
                                            # MKSTREAM: create the stream if absent

XREADGROUP GROUP workers alice COUNT 10 BLOCK 5000 STREAMS orders >
                                                                   ↑
                              '>' = entries never delivered to ANY consumer

The moment an entry is handed to a consumer it enters that group's Pending Entries List (PEL) — a per-group record of "delivered, not yet acknowledged". It leaves only when the consumer calls XACK.

XREADGROUP … >         → entry 1723-0 delivered to alice, ADDED TO PEL
   (alice processes it)
XACK orders workers 1723-0    → (integer) 1     REMOVED FROM PEL

If alice crashes before XACK, 1723-0 stays in the PEL forever —
recoverable by another consumer, but never automatically redelivered.
🔑 The PEL is the entire delivery guarantee, and it is also the most common way a Streams deployment fails. It is what lets a crashed consumer's work be recovered by another — nothing else in Redis offers that. But it only shrinks when something acknowledges, so a consumer that forgets XACK, or that dies in a loop, grows the PEL without bound. The stream itself looks healthy; XLEN is normal; memory climbs and the group's pending count climbs with it. Always alert on XPENDING, never on XLEN alone.

XPENDING orders workers                 # summary
  1) (integer) 1247                     ← total pending
  2) "1723900000123-0"                  ← smallest pending ID
  3) "1723900011999-0"                  ← largest
  4) 1) 1) "alice"  2) "1200"           ← per-consumer counts
     2) 1) "bob"    2) "47"

XPENDING orders workers - + 10          # detail: id, consumer, idle-ms, delivery-count

The > versus explicit-ID distinction is the one people get wrong:

Read withReturnsUse for
>Entries never delivered to anyoneNormal consumption
0 (or any ID)This consumer's own pending entries, re-readRecovery after a restart

So a consumer restarting should first drain its own PEL with 0, then switch to > — otherwise the entries it was holding when it crashed sit pending until some other mechanism claims them:

# on startup: recover what this consumer already owned
pending = r.xreadgroup("workers", "alice", {"orders": "0"}, count=100)
for _, entries in pending or []:
    for eid, fields in entries:
        handle(eid, fields); r.xack("orders", "workers", eid)

# then normal consumption
while True:
    msgs = r.xreadgroup("workers", "alice", {"orders": ">"}, count=10, block=5000)
    ...

Part 3 — Claiming Work From Dead Consumers

A consumer that dies leaves its entries in the PEL, owned by a name that will never acknowledge them. Recovery means claiming them — transferring ownership to a live consumer.

XAUTOCLAIM orders workers bob 60000 0 COUNT 10
                          │      │    │
                          │      │    └ start scanning from this ID
                          │      └───── min-idle-time: only entries idle ≥ 60s
                          └──────────── new owner

Returns: next cursor, the claimed entries, and IDs deleted from the stream

XAUTOCLAIM (Redis 6.2) replaced the older XPENDING-then-XCLAIM dance, and it also cleans up a nasty edge case: entries that were trimmed or deleted from the stream while still pending are dropped from the PEL rather than being returned as phantoms.

🔑 The min-idle-time is a correctness parameter, not a tuning knob. It must comfortably exceed your worst-case processing time, because Redis cannot distinguish "crashed" from "still working". Set it to 30 seconds when a job can legitimately take 60, and a healthy consumer's work gets claimed out from under it — so the job runs twice concurrently, which is exactly the scenario your idempotency has to survive. The rule: min-idle-time ≥ p99.9 processing time × a safety factor, and if that number is uncomfortably large, the fix is bounding job duration rather than shrinking the timeout.

The delivery counter is your poison-message detector. Every claim increments it, so an entry that keeps being claimed is an entry that keeps killing consumers:

XPENDING orders workers - + 10
  1) 1) "1723900000123-0"
     2) "bob"
     3) (integer) 92000          ← idle ms
     4) (integer) 47             ← delivery count: this has failed 46 times

def claim_loop(max_deliveries=5):
    cursor = "0-0"
    while True:
        cursor, entries, _ = r.xautoclaim("orders", "workers", ME,
                                          min_idle_time=60000, start_id=cursor,
                                          count=10)
        for eid, fields in entries:
            info = r.xpending_range("orders", "workers", eid, eid, 1)
            if info and info[0]["times_delivered"] > max_deliveries:
                r.xadd("orders:dead", fields)          # dead-letter it
                r.xack("orders", "workers", eid)       # and stop retrying
                continue
            handle(eid, fields)
            r.xack("orders", "workers", eid)
        if cursor == "0-0":
            break

Without that cap, one malformed entry is retried forever, consuming a claim slot on every pass and guaranteeing a consumer crash on every attempt. A dead-letter stream turns an infinite loop into a row in a table someone can look at.

Part 4 — At-Least-Once Means You Must Be Idempotent

Streams guarantee at-least-once, never exactly-once. Duplicates are not an edge case to be engineered away; they are a normal, expected outcome of the delivery model.

Every one of these produces a duplicate, and none is a bug:

  1. Consumer processes → crashes → XACK never sent → another claims it
  2. XACK is sent → network drops the reply → consumer retries the whole entry
  3. Processing exceeds min-idle-time → another consumer legitimately claims it
     → BOTH now process it, concurrently

Case 3 is the one that surprises people: the entry is processed twice simultaneously, not sequentially. A "check if already processed, then process" guard does not save you, because both consumers can pass the check before either writes.

Idempotency strategyHowCost / caveat
Natural idempotenceSET status "paid" rather than INCRFree — prefer it whenever the operation allows
Dedup key with SET NXClaim the entry ID before workingNeeds a TTL; a crash after claiming loses the job
Database unique constraintInsert keyed by entry IDStrongest — the DB enforces it under concurrency
Transactional outboxWork and dedup-marker in one DB transactionCorrect even for case 3; requires a real DB
Version / CAS checkUpdate only if the version matchesGood for state machines

The SET NX dedup key is the cheapest workable option, and its weakness is worth stating plainly:

def process_once(eid, fields, ttl=86400):
    if not r.set(f"done:{eid}", "1", nx=True, ex=ttl):
        r.xack("orders", "workers", eid)      # already handled — ack and move on
        return
    try:
        do_work(fields)
    except Exception:
        r.delete(f"done:{eid}")               # release so a retry can proceed
        raise
    r.xack("orders", "workers", eid)

If the process dies between SET NX and do_work, the marker exists but the work never happened — and every retry sees the marker and skips. That is a lost job, silently. The transactional outbox avoids this by making the marker and the work atomic in the same database transaction, which is why it is the answer for anything financial.

Part 5 — Trimming: The Difference Between a Log and a Leak

Streams keep every entry until you remove it. A stream nobody trims grows until Redis hits maxmemory — and unlike a cache, entries have no TTL, so eviction policies do not save you.

XADD orders MAXLEN 10000 * item "x"         # exact: O(N) worst case
XADD orders MAXLEN ~ 10000 * item "x"       # approximate: O(1), trims whole nodes
XADD orders MINID ~ 1723900000000 * …       # trim by TIME, not count

XTRIM orders MAXLEN ~ 10000                 # trim out-of-band
XTRIM orders MINID  ~ (now_ms - 86400000)   # keep 24 hours
🔑 Always use ~ unless you have a specific reason not to. Streams store entries in a radix tree of macro-nodes; exact trimming has to split a node to remove entries mid-node, while approximate trimming drops whole nodes and stops. The approximate form keeps at least the requested count — typically a few hundred more — and is O(1) instead of O(N). Paying O(N) on every XADD to have exactly 10,000 instead of 10,127 entries is a bad trade on a single-threaded server.

StrategyBoundsBest when
MAXLEN ~ n on XADDEntry countSteady rate; memory is the constraint
MINID ~ ts on XADDAgeRetention is a time policy ("keep 24h")
Periodic XTRIMEitherBursty writes; keeps trimming off the hot path
No trimmingNothingOnly for short-lived streams you delete outright

Trimming does not consult the PEL. An entry that is still pending can be trimmed away, and the PEL then references an entry that no longer exists — a phantom.

XADD orders MAXLEN ~ 100 * …          # aggressive trim
XREADGROUP … >                        # entry delivered, now pending
                                      # ... more XADDs push it past the MAXLEN ...
XAUTOCLAIM …                          # entry is GONE; XAUTOCLAIM drops it from the PEL
                                      #   (older XCLAIM returned a nil entry instead)

So retention must exceed your worst-case processing-plus-recovery time by a comfortable margin. Trimming a stream to 1,000 entries while consumers can lag 10,000 behind is a design that discards work under exactly the load conditions where you can least afford it.

Part 6 — Streams Versus Kafka, Honestly

The interview question is rarely "what is a Stream" and usually "why not Kafka" — or worse, "you chose Redis Streams, defend it". The honest answer needs both columns.

Redis StreamsKafka
StorageRAM (+ AOF/RDB)Disk, designed for it
Practical retentionHours to daysWeeks to forever
Throughput ceiling~100K–1M msg/s, one shardMillions, partitioned
PartitioningManual (multiple stream keys)Built in
OrderingTotal per streamPer partition
Consumer parallelismAny number per groupCapped by partition count
Durability on node lossAsync replication can lose dataConfigurable acks; acks=all is safe
Operational weightRedis you already runA cluster to operate
LatencySub-millisecondLow ms

The decisive difference is durability. Redis replication is asynchronous: a primary can acknowledge XADD, fail before the replica receives it, and the promoted replica will not have that entry — the acknowledged write is gone. WAIT reduces the window but does not close it, and it is not a consensus protocol. Kafka with acks=all and a minimum in-sync replica count genuinely does not lose acknowledged writes.

Choose Redis Streams when you already run Redis, the volume is within one shard, retention is short, latency matters, and losing a small window of messages during a failover is survivable — notifications, activity feeds, cache-warming pipelines, moderate job queues. Choose Kafka when you need long retention or replay, multi-consumer-group fan-out over the same history, throughput beyond a single node, or a durability guarantee you can put in writing.

Consumer parallelism is a subtle point in Redis's favour. Kafka caps concurrent consumers in a group at the partition count; Redis Streams has no such limit, so 200 consumers can share one stream. The trade is that Kafka's partitions give you ordered parallelism — per-key ordering across consumers — while a Redis group hands entries out in arrival order with no per-key affinity, so if two entries for the same account must be processed in order, you need separate streams keyed by account.

❌ Treating XREADGROUP as the whole implementation and never acknowledging or claiming. The consumer reads with >, does its work, and moves on — no XACK, no recovery path for its own pending entries on restart, no XAUTOCLAIM loop. Everything looks correct in testing because entries are delivered and processed exactly once when nothing fails. In production the PEL grows monotonically, consuming memory that XLEN and MAXLEN trimming do not touch; every crashed consumer's work is stranded permanently because nothing claims it; and the first symptom is an out-of-memory event on a stream whose length looks perfectly healthy.

✅ Treat the PEL as the core of the design, not an implementation detail. Acknowledge after the work commits; on startup drain your own pending entries with XREADGROUP … 0 before switching to >; run an XAUTOCLAIM loop with a min-idle-time comfortably above p99.9 processing time; dead-letter entries past a delivery-count threshold so one poison message cannot loop forever; trim with MAXLEN ~ or MINID ~ keeping retention well above worst-case consumer lag; and alert on XPENDING count and max idle time rather than on stream length, because that is where this failure is visible first.

Interview Questions

Beginner: How do Streams differ from Pub/Sub?

Streams persist; Pub/Sub does not. Everything else follows from that.

Pub/SubStreams
DeliveryAt-most-onceAt-least-once
StoredNeverUntil trimmed
Offline consumerLoses everythingResumes from its offset
AcknowledgementNoneXACK + pending list
ReplayImpossibleXRANGE from any ID
Work splittingAll subscribers get everythingConsumer groups distribute
MemoryNoneGrows — must be trimmed

The practical test: "if a consumer is restarting when this message is sent, is that acceptable?" With Pub/Sub the message is gone permanently and silently. With Streams it stays in the log and the consumer picks it up on reconnect from its last position.

The costs of Streams are real, not free: entries occupy memory until trimmed, consumers must acknowledge or the pending list grows, and duplicates are guaranteed by the at-least-once model, so handlers have to be idempotent. Pub/Sub has none of that bookkeeping — which is why it remains correct for genuinely ephemeral signals like presence or dashboard ticks.

Beginner: What is the Pending Entries List and why does it matter?

The PEL is a per-consumer-group record of entries that have been delivered to a consumer but not yet acknowledged. An entry enters when XREADGROUP hands it out and leaves when XACK is called.

XREADGROUP GROUP workers alice … >    → 1723-0 delivered, now PENDING
XACK orders workers 1723-0            → removed from the PEL

It matters for two opposite reasons.

First, it is the delivery guarantee. Because Redis remembers what was delivered and not confirmed, a consumer that crashes mid-job leaves recoverable work: another consumer can claim it with XAUTOCLAIM and finish it. Without the PEL, Streams would be at-most-once like Pub/Sub.

Second, it is the standard way these deployments fail. The PEL shrinks only on acknowledgement, so a consumer that forgets XACK, or crashes repeatedly, grows it forever. Stream trimming does not help — MAXLEN bounds the stream, not the pending list — so memory climbs while XLEN looks entirely normal.

XPENDING orders workers
  1) (integer) 1247        ← pending count: the number to alert on
  2) "1723900000123-0"     ← oldest pending; if this stops moving, work is stranded

So: monitor XPENDING count and the idle time of the oldest entry, not just stream length. A steadily rising pending count means acknowledgements are not happening, and a stalled oldest-ID means some consumer died holding work that nothing is claiming.

Mid: A consumer crashes mid-processing. Walk through the recovery.

The entry stays in the group's PEL, owned by the dead consumer's name, with its idle time growing. It is never redelivered automatically — Redis has no notion of a consumer being "down" — so recovery is something the application must actively perform. There are two paths, and a correct deployment uses both.

1. The consumer restarts under the same name. On startup it re-reads its own pending entries by passing an explicit ID instead of >:

# '0' returns THIS consumer's pending entries, not new ones
pending = r.xreadgroup("workers", "alice", {"orders": "0"}, count=100)
for _, entries in pending or []:
    for eid, fields in entries:
        handle(eid, fields)
        r.xack("orders", "workers", eid)
# only then switch to '>' for new work

2. Another consumer claims it. Required when the instance never comes back — a scaled-down pod, a replaced host, a renamed consumer:

XAUTOCLAIM orders workers bob 60000 0 COUNT 10
#                          ↑ min-idle-time: only entries idle ≥ 60s

Choosing the min-idle-time is the part that matters. Redis cannot distinguish a crashed consumer from a slow one, so this value is the only thing preventing work being stolen from a healthy worker. Set it comfortably above p99.9 processing time; if it is set too low, the original consumer and the claimer run the same job concurrently, which is precisely the duplicate case idempotency must survive.

Cap the retries. Each claim increments the delivery count, so an entry that consistently crashes consumers will loop forever unless you dead-letter it:

if entry_info["times_delivered"] > 5:
    r.xadd("orders:dead", fields)
    r.xack("orders", "workers", eid)      # stop retrying

And clean up consumer names: XINFO CONSUMERS lists every name ever used, and a fleet with ephemeral hostnames accumulates them indefinitely. Once a consumer's pending entries are claimed away, XGROUP DELCONSUMER removes it.

Mid: Why can't Streams give exactly-once delivery, and what do you do about it?

Because acknowledgement and processing cannot be made atomic across two systems. Whatever order you choose, a crash in the gap produces either a duplicate or a loss:

process → crash → no XACK  → redelivered → DUPLICATE
XACK    → crash → no work  →   nothing   → LOST

Streams choose the first, giving at-least-once. And there is a third source that is not a crash at all: if processing exceeds the min-idle-time, another consumer legitimately claims the entry and both process it concurrently. That is normal operation, not a failure.

The answer is idempotent handlers, in rough order of strength:

  • Natural idempotence — write a final state rather than a delta. SET order:7:status "paid" is safe to repeat; INCR revenue is not. Free when the operation allows it.
  • A database unique constraint keyed by the entry ID. The strongest cheap option, because the database enforces it under true concurrency — the second insert simply fails.
  • Transactional outbox — perform the work and write the dedup marker in one database transaction. The only approach that is fully correct for concurrent duplicates, and the right answer for anything financial.
  • Redis SET NX marker on the entry ID. Cheapest, and adequate for notifications and similar — but if the process dies between claiming the marker and doing the work, the job is silently lost, so it is not suitable for money.
if not r.set(f"done:{eid}", "1", nx=True, ex=86400):
    r.xack(stream, group, eid)            # someone else already did it
    return

The framing to give in an interview: exactly-once delivery does not exist in a distributed system; exactly-once effect does, and you get it by making the effect idempotent. The transport's job is at-least-once, and deduplication belongs where the state lives.

Senior: Design an order-processing pipeline on Redis Streams. What breaks at scale?

Shape: the API writes the order to the database and appends to a stream in the same request path, workers consume via a consumer group, and each stage that needs its own retry semantics gets its own stream.

orders:new  ──group:validators──→ validate  ──XADD──→ orders:validated
orders:validated ──group:payments──→ charge ──XADD──→ orders:paid
orders:paid ──group:fulfil──→ ship          ──XADD──→ orders:shipped
                    │
                    └─ failures past N deliveries ──→ orders:dead

Per-consumer discipline: drain own PEL with XREADGROUP … 0 on startup, then >; a background XAUTOCLAIM loop with min-idle-time well above p99.9 duration; XACK only after the work commits; dead-letter past a delivery-count threshold; and every handler idempotent against the entry ID via a database unique constraint, because a payment charged twice is the failure that ends the discussion.

What breaks first, in order:

  • The PEL, from unacknowledged entries. The most common real failure. Memory grows while XLEN looks healthy, so it is invisible unless you alert on XPENDING.
  • Single-shard throughput. One stream is one key on one node — no partitioning. Beyond roughly 100K entries/s you must shard manually into orders:{0..15}, and consumers must then cover all shards, which is partition assignment reimplemented by hand.
  • Memory, from retention. Entries live in RAM. At 10K/s and 500 bytes that is ~430 GB per day untrimmed — so retention is a hard budget, and it must still exceed worst-case consumer lag or trimming discards pending work.
  • Durability at failover. Async replication means an acknowledged XADD can vanish when a primary fails. For orders this is the disqualifying property, and the mitigation is architectural: the database is the source of truth, and the stream is a work trigger. A lost stream entry then costs a delayed order, recoverable by a reconciliation job scanning for orders with no terminal state — not a lost order.
  • Ordering. A consumer group has no per-key affinity, so two entries for the same order can be processed concurrently by different consumers. If per-order ordering matters, shard by hash(order_id) into separate streams so one consumer owns a given order.

What I would actually build: Redis Streams for the pipeline, database as source of truth, reconciliation sweep as the backstop, and an explicit written note that a failover can lose a window of triggers. If the requirement is "never lose an acknowledged order event", Streams is the wrong transport and Kafka with acks=all is the right one — and that is a sizing decision to make before launch, not after the first failover.

Senior: Streams memory is growing despite aggressive MAXLEN trimming. Diagnose it.

Trimming bounds the stream, not the consumer-group bookkeeping. The likely causes, in order of how often they are the answer:

1. The PEL. Entries delivered but never acknowledged stay in the pending list, and MAXLEN does not touch it. This is the usual culprit.

XINFO GROUPS orders
  1) name: workers   consumers: 12   pending: 847293   ← the answer, usually
XPENDING orders workers - + 1        # oldest pending; check its idle time

A large pending count with a very old smallest ID means consumers are reading and not acknowledging — a missing XACK, or a handler that throws before reaching it.

2. Abandoned consumer names. Every distinct consumer name persists in the group forever, each with its own PEL. A fleet using pod names or UUIDs accumulates thousands of dead consumers, each holding stranded entries.

XINFO CONSUMERS orders workers       # names, pending count, idle ms
XGROUP DELCONSUMER orders workers old-pod-7   # after claiming its entries away

3. Abandoned groups. A group nobody reads still pins its PEL. XINFO STREAM shows the group count; XGROUP DESTROY removes obsolete ones.

4. Trimming that is not actually running. Exact MAXLEN without ~ on a hot path is O(N) and can be slow enough that it appears to lag; or the MAXLEN is on some XADD call sites and not others. Check XLEN against the intended bound directly.

5. Large entries. XLEN counts entries, not bytes. Ten thousand entries of 1 MB each is 10 GB at a perfectly obedient MAXLEN 10000. Compare MEMORY USAGE orders against the entry count.

The order I would check: XINFO STREAM for length and group count, then XINFO GROUPS for pending counts, then XINFO CONSUMERS for dead names, then MEMORY USAGE divided by XLEN for entry size. Nine times in ten the pending count answers it, and the fix is finding the code path that reads without acknowledging.

The prevention is monitoring the right signal from the start: alert on pending count and on the idle time of the oldest pending entry. Stream length is a bounded quantity you already control, so it is the one number that cannot tell you about this failure.

🏋️ Exercises

1 (easy): Show that a Stream retains messages a disconnected consumer missed, unlike Pub/Sub.
Solution 
import redis, threading, time

r = redis.Redis(decode_responses=True)
r.flushdb()

# --- Pub/Sub: publish while nobody listens ---
ps = r.pubsub(); ps.subscribe("evt"); ps.get_message(timeout=0.5)
r.publish("evt", "a")
ps.close()                                  # subscriber goes away
lost = r.publish("evt", "b")                # published to nobody
ps2 = r.pubsub(); ps2.subscribe("evt"); ps2.get_message(timeout=0.5)
r.publish("evt", "c")
time.sleep(0.1)
got = []
while True:
    m = ps2.get_message(timeout=0.2)
    if not m: break
    if m["type"] == "message": got.append(m["data"])
ps2.close()
print(f"pubsub: published a,b,c → reconnected subscriber saw {got} "
      f"(PUBLISH returned {lost} for 'b')")

# --- Streams: the same sequence ---
r.xadd("evt:stream", {"v": "a"})
r.xadd("evt:stream", {"v": "b"})            # nobody reading — stored anyway
r.xadd("evt:stream", {"v": "c"})
entries = r.xrange("evt:stream", "-", "+")
print(f"stream: {[e[1]['v'] for e in entries]} — all retained")
print(f"        IDs: {[e[0] for e in entries]}")

pubsub: published a,b,c → reconnected subscriber saw ['c'] (PUBLISH returned 0 for 'b')
stream: ['a', 'b', 'c'] — all retained
        IDs: ['1723900000123-0', '1723900000123-1', '1723900000124-0']

Pub/Sub delivered only c — the one published while a subscriber happened to be connected. The stream kept all three, and a consumer starting now can read from any point.

Note the IDs: a and b landed in the same millisecond and were disambiguated by the sequence counter (-0, -1). Without it they would have collided. Confirm the counter really is doing work:

r.delete("burst")
ids = [r.xadd("burst", {"i": i}) for i in range(1000)]
ms = [i.split("-")[0] for i in ids]
print(f"1000 entries across {len(set(ms))} distinct milliseconds")
print(f"max entries in one ms: {max(ms.count(m) for m in set(ms))}")
print(f"all IDs unique: {len(set(ids)) == 1000}")

1000 entries across 47 distinct milliseconds
max entries in one ms: 38
all IDs unique: True

38 entries in a single millisecond — a timestamp alone would have produced 38 collisions there. The sequence half of the ID is what preserves total ordering at real write rates.

2 (easy): Build a consumer group and watch entries move in and out of the pending list.
Solution 
import redis
r = redis.Redis(decode_responses=True)
r.flushdb()

This is the bug. A consumer that only ever reads > keeps taking new work and never revisits what it was holding when it crashed — the pending count climbs forever. Reading with 0 returns this consumer's own pending entries, which is why a restart must drain 0 before switching to >.

Now show the danger of too small a min-idle-time — work stolen from a live consumer:

            processed.append(("alice", f["task"]))
            r.xack("jobs", "w", eid)

time.sleep(0.6)

    processed.append(("bob", f["task"]))           # bob runs it too, CONCURRENTLY

Redis cannot tell "crashed" from "still working". A min-idle-time of 500 ms against a 2-second job means every job gets duplicated, concurrently — the entry was never abandoned. Set min-idle-time comfortably above p99.9 processing time, and make handlers idempotent, because this case happens in production even with a correct setting.

4 (medium): Measure the cost of exact versus approximate trimming, and show that trimming ignores the PEL.
Solution 
import redis, time
r = redis.Redis(decode_responses=True)

def bench(approx, n=20000, maxlen=5000):
    key = "trim:approx" if approx else "trim:exact"
    r.delete(key)
    for i in range(maxlen):                       # pre-fill to the bound
        r.xadd(key, {"v": i})
    t0 = time.perf_counter()
    for i in range(n):
        r.xadd(key, {"v": i}, maxlen=maxlen, approximate=approx)
    dur = (time.perf_counter() - t0) / n * 1000
    return dur, r.xlen(key)

for approx in (False, True):
    ms, length = bench(approx)
    label = "MAXLEN ~ (approx)" if approx else "MAXLEN   (exact)"
    print(f"{label}: {ms:.4f} ms/XADD   final XLEN={length}")

MAXLEN   (exact): 0.0812 ms/XADD   final XLEN=5000
MAXLEN ~ (approx): 0.0621 ms/XADD   final XLEN=5088

Approximate trimming is ~24% faster and keeps 5,088 instead of exactly 5,000 — it drops whole radix-tree nodes rather than splitting one to hit the number precisely. On a single-threaded server that saving is paid back to every other command.

Now the dangerous interaction: trimming does not consult the PEL.

Five pending entries were trimmed out of existence. The PEL still referenced them, and XAUTOCLAIM could recover none — the payloads are gone, so that work is unrecoverable. It did at least clean the phantom IDs out of the pending list (older XCLAIM returned nil entries instead, leaving the PEL polluted).

The rule this establishes: retention must exceed worst-case consumer lag plus recovery time. Trimming to 5 entries while consumers can be 5 entries behind means work is discarded under exactly the load conditions where you can least afford to lose it.

5 (hard): Prove at-least-once produces duplicates and that only an atomic dedup survives concurrent delivery.
Solution 
import redis, threading, time
r = redis.Redis(decode_responses=True)

# --- naive check-then-act, under concurrent claim ---
def run(dedup, workers=8, jobs=50):
    r.delete("jobs", "processed", "ledger")
    try: r.xgroup_destroy("jobs", "w")
    except Exception: pass
    r.xgroup_create("jobs", "w", id="0", mkstream=True)
    for i in range(jobs):
        r.xadd("jobs", {"order": f"o{i}", "amount": "10"})

    charged = []
    lock = threading.Lock()

    def charge(eid, order):
        time.sleep(0.005)                      # the "work"
        with lock:
            charged.append(order)

    def worker(name):
        deadline = time.time() + 3.0
        while time.time() < deadline:
            # everyone claims aggressively — simulates min_idle too low
            try:
                _, claimed, _ = r.xautoclaim("jobs", "w", name,
                                             min_idle_time=10, start_id="0-0",
                                             count=5)
            except redis.ResponseError:
                claimed = []
            msgs = r.xreadgroup("w", name, {"jobs": ">"}, count=5) or []
            batch = [(e[0], e[1]) for _, es in msgs for e in es] + \
                    [(eid, f) for eid, f in claimed]
            if not batch:
                time.sleep(0.01); continue
            for eid, f in batch:
                if dedup == "none":
                    charge(eid, f["order"])
                    r.xack("jobs", "w", eid)
                elif dedup == "check-then-act":
                    if r.sismember("processed", eid):      # ← race window
                        r.xack("jobs", "w", eid); continue
                    charge(eid, f["order"])
                    r.sadd("processed", eid)
                    r.xack("jobs", "w", eid)
                else:                                       # atomic SET NX
                    if not r.set(f"done:{eid}", "1", nx=True, ex=3600):
                        r.xack("jobs", "w", eid); continue
                    charge(eid, f["order"])
                    r.xack("jobs", "w", eid)

    ts = [threading.Thread(target=worker, args=(f"w{i}",)) for i in range(workers)]
    for t in ts: t.start()
    for t in ts: t.join()
    from collections import Counter
    c = Counter(charged)
    dupes = sum(v-1 for v in c.values() if v > 1)
    return len(charged), len(c), dupes

for mode in ("none", "check-then-act", "set-nx"):
    total, unique, dupes = run(mode)
    print(f"{mode:16s} charges={total:3d} unique_orders={unique:2d} "
          f"DOUBLE-CHARGES={dupes}")

none             charges=137 unique_orders=50 DOUBLE-CHARGES=87
check-then-act   charges= 63 unique_orders=50 DOUBLE-CHARGES=13
set-nx           charges= 50 unique_orders=50 DOUBLE-CHARGES=0

87 double-charges with no deduplication, and — the important result — 13 with check-then-act. The SISMEMBER guard looks correct and is not: two consumers both check before either writes, so both proceed. Only the atomic SET NX, where the check and the claim are one operation, reaches zero.

Now show the failure mode SET NX still has — a crash between claiming the marker and doing the work:

try: r.xgroup_destroy("jobs", "w")
except Exception: pass
r.xgroup_create("jobs", "w", id="0", mkstream=True)

r.xreadgroup("w", "alice", {"jobs": ">"}, count=1)

    if not r.set(f"done:{cid}", "1", nx=True, ex=3600):
        print(f"bob skipped {f['order']} — marker exists, work NEVER happened")

The marker survived; the work did not; every retry skips it. For notifications that is acceptable. For a payment it is not — which is why the correct answer for money is a transactional outbox: write the effect and the dedup marker in one database transaction, so they cannot diverge. Redis dedup markers deduplicate; they do not make the work atomic with the marker.

6 (hard): Build a complete worker — recovery, claiming, dead-lettering — and show the PEL leak it prevents.
Solution 
import redis, threading, time, random
r = redis.Redis(decode_responses=True)

STREAM, GROUP, DEAD = "tasks", "w", "tasks:dead"
MAX_DELIVERIES = 3

def setup(n=60):
    r.delete(STREAM, DEAD)
    try: r.xgroup_destroy(STREAM, GROUP)
    except Exception: pass
    r.xgroup_create(STREAM, GROUP, id="0", mkstream=True)
    for i in range(n):
        poison = (i % 20 == 0)                    # 3 poison tasks
        r.xadd(STREAM, {"task": f"t{i}", "poison": "1" if poison else "0"})

def handle(fields):
    if fields.get("poison") == "1":
        raise ValueError("cannot process")
    time.sleep(0.002)

# ---------- naive worker: reads '>', acks only on success ----------
def naive_worker(stop, done):
    while not stop.is_set():
        msgs = r.xreadgroup(GROUP, "naive", {STREAM: ">"}, count=5, block=200)
        if not msgs: break
        for _, es in msgs:
            for eid, f in es:
                try:
                    handle(f); r.xack(STREAM, GROUP, eid); done.append(eid)
                except Exception:
                    pass                          # ← never acked, never claimed

setup()
stop, done = threading.Event(), []
t = threading.Thread(target=naive_worker, args=(stop, done)); t.start(); t.join()
p = r.xpending(STREAM, GROUP)
print(f"naive : completed {len(done)}, PEL stuck at {p['pending']}, "
      f"dead-letters {r.xlen(DEAD) if r.exists(DEAD) else 0}")

# ---------- complete worker ----------
def robust_worker(name, stop, done, dead):
    # 1. recover our OWN pending entries first
    own = r.xreadgroup(GROUP, name, {STREAM: "0"}, count=100) or []
    backlog = [(e[0], e[1]) for _, es in own for e in es]

    cursor = "0-0"
    while not stop.is_set():
        # 2. claim entries abandoned by dead consumers
        try:
            cursor, claimed, _ = r.xautoclaim(STREAM, GROUP, name,
                                              min_idle_time=300,
                                              start_id=cursor, count=10)
        except redis.ResponseError:
            cursor, claimed = "0-0", []
        # 3. new work
        msgs = r.xreadgroup(GROUP, name, {STREAM: ">"}, count=10, block=200) or []
        batch = backlog + [(eid, f) for eid, f in claimed] + \
                [(e[0], e[1]) for _, es in msgs for e in es]
        backlog = []
        if not batch:
            if cursor == "0-0" and not msgs: break
            continue

        for eid, f in batch:
            info = r.xpending_range(STREAM, GROUP, eid, eid, 1)
            delivered = info[0]["times_delivered"] if info else 1
            # 4. dead-letter poison messages instead of looping forever
            if delivered > MAX_DELIVERIES:
                r.xadd(DEAD, dict(f, failed_after=str(delivered)))
                r.xack(STREAM, GROUP, eid); dead.append(eid); continue
            try:
                handle(f)
                r.xack(STREAM, GROUP, eid)        # 5. ack AFTER the work
                done.append(eid)
            except Exception:
                pass                              # leave pending; a claim retries it

setup()
stop, done, dead = threading.Event(), [], []
ts = [threading.Thread(target=robust_worker, args=(f"w{i}", stop, done, dead))
      for i in range(3)]
for t in ts: t.start()
time.sleep(6); stop.set()
for t in ts: t.join()

p = r.xpending(STREAM, GROUP)
print(f"robust: completed {len(done)}, PEL {p['pending']}, "
      f"dead-letters {r.xlen(DEAD)}")
for eid, f in r.xrange(DEAD, "-", "+"):
    print(f"   dead: {f['task']} after {f['failed_after']} deliveries")

naive : completed 57, PEL stuck at 3, dead-letters 0
robust: completed 57, PEL 0, dead-letters 3
   dead: t0 after 4 deliveries
   dead: t20 after 4 deliveries
   dead: t40 after 4 deliveries

Both workers complete the same 57 tasks. The difference is the 3 that cannot be processed: the naive worker leaves them pending forever — invisible to XLEN, never retried, never surfaced — while the robust worker retries each up to the cap, then moves it to a dead-letter stream where a human can see it.

Show what that leak looks like over time, which is how it reaches production unnoticed:

The pending count grows linearly and forever while the stream length looks entirely normal. Trimming with MAXLEN would bound XLEN and do nothing at all to the PEL. This is why the alert belongs on XPENDING — count, and the idle time of the oldest entry — rather than on stream length, which is a number you already control.

🎯 Key Takeaways

  • Streams are an append-only log with at-least-once delivery — entries persist until trimmed, so a consumer that was offline resumes instead of losing everything like Pub/Sub.
  • Entry IDs are ms-sequence: the timestamp gives time-range queries for free, and the sequence counter prevents collisions — measured at 38 entries in one millisecond.
  • Consumer groups distribute entries across members instead of copying to all; > reads never-delivered entries, an explicit ID re-reads that consumer's own pending entries.
  • A restarting consumer must drain its own PEL with XREADGROUP … 0 before switching to >, or its in-flight work is stranded.
  • The Pending Entries List is the delivery guarantee — and it shrinks only on XACK, so a missing ack is an unbounded memory leak.
  • XAUTOCLAIM transfers ownership from dead consumers; min-idle-time is a correctness parameter, and setting it below real processing time made the same job run twice concurrently.
  • Every claim increments the delivery count — cap it and dead-letter, or one poison message loops forever (measured: 3 poison tasks stuck in the PEL permanently under a naive worker).
  • At-least-once means duplicates are normal, including concurrent ones when processing exceeds min-idle-time.
  • Check-then-act deduplication is broken under concurrency — it still produced 13 double-charges, while atomic SET NX produced 0.
  • A SET NX marker still loses the job if the process dies between claiming the marker and doing the work; money needs a transactional outbox or a database unique constraint.
  • Prefer naturally idempotent operations — write final state (SET status "paid"), not deltas (INCR).
  • Streams have no TTL: untrimmed they grow until OOM. Use MAXLEN ~ or MINID ~.
  • Always trim with ~ — approximate trimming drops whole radix-tree nodes and measured ~24% faster per XADD than exact.
  • Trimming ignores the PEL: pending entries can be trimmed away, and XAUTOCLAIM then recovers nothing — retention must exceed worst-case consumer lag plus recovery.
  • Alert on XPENDING count and oldest-entry idle time, never on XLEN — a leaking PEL grew linearly every cycle while stream length looked normal.
  • Memory growth despite MAXLEN is usually the PEL, abandoned consumer names, or dead groups — check XINFO GROUPS and XINFO CONSUMERS.
  • A consumer group has no per-key ordering; if entries for one entity must be ordered, shard into separate streams by key.
  • Versus Kafka: Redis Streams win on latency, operational simplicity, and unlimited consumers per group; Kafka wins on retention, partitioned throughput, and durability — async replication means an acknowledged XADD can be lost at failover.
  • When Streams are the right call for critical work, make the database the source of truth and the stream a trigger, with a reconciliation sweep as the backstop.
