Sorted Sets & Ranking Foundations

What you'll master: the skip-list-plus-hash-table structure that gives O(log n) rank queries and O(1) score lookups simultaneously; why ZRANGEBYSCORE and ZRANGEBYLEX are different tools and when lexicographic ordering is the right one; the score as a design decision — encoding timestamps, priorities and composite keys into a double, and the 2⁵³ precision limit that constrains it; the sliding-window and delayed-queue patterns that fall out of scoring by time; and ZRANGESTORE/ZUNIONSTORE for server-side aggregation. Prerequisites: Hashes, Lists & Sets.

Part 1 — Two Structures in One

A sorted set stores unique members, each with a floating-point score, and keeps them ordered by score. It achieves that with two data structures maintained in parallel.

   HASH TABLE                      SKIP LIST
   member → score                  ordered by (score, member)

   "alice" → 100        ┌──────────────────────────────────┐
   "bob"   → 250        │ L2:  bob ──────────────► dave    │
   "carol" → 180        │ L1:  bob ──► carol ────► dave    │
   "dave"  → 400        │ L0:  alice ► bob ► carol ► dave  │
                        └──────────────────────────────────┘

   ZSCORE  → O(1)   via the hash table
   ZRANK   → O(log n) via the skip list
   ZRANGE  → O(log n + k)
🔑 The dual structure is why sorted sets can do what neither a hash nor a set can. A hash gives O(1) lookup but no ordering; a sorted list gives ordering but O(n) lookup. Redis maintains both views of the same data and keeps them in sync on every write — so ZSCORE member is a hash lookup while ZRANK member walks the skip list. The cost is memory (roughly twice a plain set) and slightly slower writes, and it buys the only structure in Redis that answers "what rank is this item?" without scanning.

ZADD leaderboard 100 "alice" 250 "bob" 180 "carol"
ZSCORE leaderboard "bob"          → "250"          O(1)
ZRANK  leaderboard "bob"          → (integer) 2    O(log n), 0-based, ascending
ZREVRANK leaderboard "bob"        → (integer) 0    descending — bob is the top
ZCARD leaderboard                 → (integer) 3    O(1)
ZINCRBY leaderboard 50 "alice"    → "150"          atomic

Members are unique; scores are not. Adding an existing member updates its score rather than creating a duplicate — which makes ZADD an upsert:

ZADD leaderboard 100 "alice"
ZADD leaderboard 200 "alice"      → (integer) 0    ← 0 means "updated", not "added"
ZSCORE leaderboard "alice"        → "200"
ZADD flagEffect
NXOnly add new members — never update an existing score
XXOnly update existing members — never add
GT / LTUpdate only if the new score is greater / less
CHReturn the count of changed members, not just added
INCRBehave like ZINCRBY, returning the new score

GT is the flag that removes a race — "record this high score only if it beats the existing one" would otherwise be a read, a compare and a write:

ZADD highscores GT 500 "alice"     # updates only if 500 > the current score

Part 2 — Range Queries by Score and by Rank

# by RANK (position)
ZRANGE leaderboard 0 9                    # the 10 lowest scores
ZREVRANGE leaderboard 0 9 WITHSCORES      # the top 10, with scores
ZRANGE leaderboard 0 -1                   # ⚠ everything — O(n)

# by SCORE (value)
ZRANGEBYSCORE leaderboard 100 200         # inclusive on both ends
ZRANGEBYSCORE leaderboard (100 200        # ( = EXCLUSIVE lower bound
ZRANGEBYSCORE leaderboard -inf +inf       # infinities are valid
ZCOUNT leaderboard 100 200                # just the count — O(log n)

# Redis 6.2+ unified form
ZRANGE leaderboard 100 200 BYSCORE LIMIT 0 10
ZRANGE leaderboard (100 +inf BYSCORE REV LIMIT 0 10
CommandComplexityUse
ZRANGE by rankO(log n + k)"Top 10", pagination by position
ZRANGEBYSCOREO(log n + k)"Everything between two values"
ZCOUNTO(log n)Count in a range without fetching
ZRANK / ZREVRANKO(log n)"What position is this member?"
ZREMRANGEBYSCOREO(log n + k)Trim old entries — the sliding window

ZCOUNT being O(log n) rather than O(k) is the detail worth knowing — the skip list stores span counts at each level, so counting a range never visits the members in it.

Part 3 — The Score Is a Design Decision

The score is an IEEE-754 double, which means integers are exact up to 2⁵³ and beyond that silently lose precision. That single fact constrains every encoding scheme.

2^53 = 9,007,199,254,740,992

Unix seconds        1,755,000,000        ✓ safe
Unix milliseconds   1,755,000,000,000    ✓ safe
Unix microseconds   1,755,000,000,000,000 ✓ safe (just)
Unix nanoseconds    1,755,000,000,000,000,000  ✗ LOSES PRECISION
Score encodingGives you
Unix timestampTime-ordered feed; range = time window
Points / ratingLeaderboard
Priority integerPriority queue via ZPOPMIN
Scheduled execution timeDelayed job queue
All zerosLexicographic ordering — see Part 4
score * 10⁶ + (10⁶ − timestamp%10⁶)Composite: rank by score, tie-break by time

Composite scores are the standard answer to "rank by X, break ties by Y", and the precision budget is what limits them:

# rank by points, break ties in favour of the EARLIER achiever
# points ≤ 1,000,000 and we need ~10 digits of timestamp
score = points * 10_000_000_000 + (10_000_000_000 - timestamp)

# check the budget: 10^6 * 10^10 = 10^16  >  9.007 * 10^15  ✗ OVERFLOWS
# fix: reduce the timestamp resolution
score = points * 10_000_000 + (10_000_000 - (timestamp % 10_000_000))
#      10^6 * 10^7 = 10^13  ✓ well within 2^53

Always verify the arithmetic fits in 2⁵³ before shipping a composite score — the failure is silent, and it manifests as items with different real values sharing a rank.

Part 4 — Lexicographic Ranges

When every member has the same score, the sorted set orders by member string, and ZRANGEBYLEX queries that ordering:

ZADD words 0 "apple" 0 "banana" 0 "cherry" 0 "date"

ZRANGEBYLEX words [b [d          # from "b" to "d", inclusive
  → 1) "banana"  2) "cherry"

ZRANGEBYLEX words (b +           # after "b" to the end, exclusive lower
ZRANGEBYLEX words - [c           # from the start to "c"
ZLEXCOUNT words - +              # count everything
SyntaxMeaning
[valueInclusive
(valueExclusive
-Negative infinity (the smallest string)
+Positive infinity

The classic use is autocomplete — prefix search without a trie:

ZADD names 0 "alice" 0 "alicia" 0 "amanda" 0 "bob"
ZRANGEBYLEX names [ali (alj      # everything starting with "ali"
  → 1) "alice"  2) "alicia"

# the trick: the upper bound is the prefix with its last character incremented

The critical caveat: lexicographic ordering is only meaningful if all scores are identical. With mixed scores the set orders by score first, and ZRANGEBYLEX returns undefined results — a genuinely confusing bug because it does not error.

Part 5 — Sliding Windows and Delayed Queues

The sliding-window rate limiter is the pattern that makes sorted sets essential — it fixes the boundary-burst flaw of the fixed-window counter from Strings & Expiry:

# score = timestamp, member = a unique request id
ZREMRANGEBYSCORE rate:user:1 0 <now - window>   # 1. drop entries outside the window
ZCARD rate:user:1                                # 2. count what remains
ZADD rate:user:1 <now> <unique-id>               # 3. record this request
EXPIRE rate:user:1 <window>                      # 4. self-clean if idle

Because the window slides continuously, there is no boundary at which the allowance resets — 5 requests per 10 seconds means genuinely 5 in any 10-second span. Wrapping the four commands in a Lua script makes it atomic.

The delayed job queue scores by execution time:

ZADD jobs:delayed <run_at_timestamp> <job-payload>

# a poller claims everything now due
ZRANGEBYSCORE jobs:delayed -inf <now> LIMIT 0 100
ZREM jobs:delayed <job>          # ← must be atomic with the read, or two workers claim it

ZPOPMIN makes the claim atomic for the simple case, and BZPOPMIN blocks like BRPOP:

ZPOPMIN jobs:delayed          # atomically remove and return the lowest-scored member
BZPOPMIN jobs:delayed 0       # block until one is available

Part 6 — Aggregation and Storing Results

ZUNIONSTORE dest 2 zset1 zset2 WEIGHTS 1 0.5 AGGREGATE SUM
ZINTERSTORE dest 2 zset1 zset2 AGGREGATE MAX
ZDIFFSTORE  dest 2 zset1 zset2
ZRANGESTORE dest src 0 99                     # store a range — Redis 6.2+
OptionEffect
WEIGHTSMultiply each input's scores before aggregating
AGGREGATE SUMAdd scores (the default)
AGGREGATE MIN / MAXTake the extreme score

Weighted unions build composite rankings server-side — combining recency and popularity, for instance, without moving any data:

# 70% popularity, 30% recency
ZUNIONSTORE feed:ranked 2 posts:by_likes posts:by_recency WEIGHTS 0.7 0.3
ZREVRANGE feed:ranked 0 19 WITHSCORES

Sorted sets also have a listpack encoding below zset-max-listpack-entries (128) and zset-max-listpack-value (64 bytes) — the same one-way conversion as hashes.

❌ Building a composite score without checking that it fits in 2⁵³. Multiplying a points value by a large factor and adding a millisecond timestamp reads perfectly sensibly, and it works in testing because small numbers are exact. Once real values arrive the product exceeds 2⁵³, the double silently rounds, and items with genuinely different scores collapse to the same value — so ties appear between players who are thousands of points apart, and the ordering within them becomes arbitrary. No error is raised at any point.

✅ Budget the digits explicitly and assert the maximum. Work out the largest possible score — max_points × multiplier + max_tiebreak — and check it against 9,007,199,254,740,992 before choosing the multiplier, reducing the tiebreak resolution until it fits. A one-line test that asserts encode(max_points, max_ts) < 2**53 catches the whole class of bug, and where the budget genuinely cannot accommodate both, store the tiebreak in a parallel structure rather than corrupting the score.

Interview Questions

Beginner: What is a sorted set and how is it implemented?

A sorted set holds unique members, each with a floating-point score, kept ordered by score. It is implemented as two structures maintained together:

StructureProvides
Hash table (member → score)ZSCORE in O(1)
Skip list (ordered by score, then member)ZRANK, ZRANGE in O(log n)

Neither structure alone would do. A hash gives fast lookup but no order; an ordered list gives order but O(n) lookup. Redis keeps both in sync on every write, paying roughly double the memory of a plain set for the ability to answer both kinds of question.

ZADD leaderboard 100 "alice" 250 "bob" 180 "carol"
ZSCORE   leaderboard "bob"    → "250"        O(1)   — hash table
ZREVRANK leaderboard "bob"    → (integer) 0  O(log n) — skip list
ZREVRANGE leaderboard 0 2 WITHSCORES
  → 1) "bob"   2) "250"
    3) "carol" 4) "180"
    5) "alice" 6) "100"

Why a skip list rather than a balanced tree? Skip lists are simpler to implement correctly, have comparable O(log n) behaviour, and support range scans naturally by walking the bottom level. They also store span counts per node, which is what makes ZCOUNT and ZRANK O(log n) rather than O(k).

Members are unique, scores are not — so ZADD on an existing member updates its score rather than adding a duplicate, making it an upsert. Ties are broken lexicographically by member, which is what makes ZRANGEBYLEX meaningful when all scores are equal.

Small sorted sets use a listpack encoding, converting to the full skiplist past 128 entries or a 64-byte member — the same one-way conversion as hashes.

Beginner: How do you build a leaderboard?

The score is the player's points; the member is the player id. Everything else falls out of the commands.

ZADD leaderboard 4820 "player:1000"
ZINCRBY leaderboard 150 "player:1000"       # atomic increment

ZREVRANGE leaderboard 0 9 WITHSCORES         # top 10
ZREVRANK leaderboard "player:1000"           # this player's rank (0-based)
ZSCORE leaderboard "player:1000"             # their score
ZCOUNT leaderboard 5000 +inf                 # how many above 5000
QueryCommandCost
Top NZREVRANGE key 0 N-1O(log n + N)
A player's rankZREVRANKO(log n)
Players around a playerZREVRANK then ZREVRANGEO(log n + k)
Update a scoreZADD or ZINCRBYO(log n)

Why this is hard elsewhere: a relational SELECT … ORDER BY score DESC LIMIT 10 OFFSET 50000 must sort or scan a large index, and the cost grows with the offset. A sorted set answers rank queries in logarithmic time regardless of position, because the skip list stores span counts.

"Players near me" is the query that shows it off:

rank = ZREVRANK leaderboard "player:1000"     → 4821
ZREVRANGE leaderboard 4816 4826 WITHSCORES    # five above and five below

The refinement worth mentioning is tie-breaking. Equal scores order by member string, which is effectively arbitrary. If ties should favour whoever got there first, encode a composite score — points scaled up, plus an inverted timestamp — while checking the total stays under 2⁵³.

And ZADD GT handles "record only if it beats the previous best" atomically, removing a read-compare-write race.

Mid: Implement a sliding-window rate limiter.

Score by timestamp, and the window becomes a score range that continuously moves.

def allow(r, user, limit=5, window=10):
    key = f"rate:{user}"
    now = time.time()
    pipe = r.pipeline()
    pipe.zremrangebyscore(key, 0, now - window)   # 1. drop what left the window
    pipe.zcard(key)                                # 2. count what remains
    pipe.zadd(key, {f"{now}:{uuid4().hex[:8]}": now})  # 3. record this request
    pipe.expire(key, window)                       # 4. self-clean when idle
    _, count, _, _ = pipe.execute()
    return count < limit

Why this beats the fixed-window counter: a fixed window resets at a boundary, so a client can send the full allowance just before and just after it — double the intended rate in a moment:

fixed window, limit 5 per 10s:
  t=9.9s  → 5 allowed (window A)
  t=10.1s → 5 allowed (window B)     10 requests in 0.2 seconds

sliding window:
  t=10.1s → the window is [0.1s, 10.1s], which already contains 5 → DENIED

The member must be unique, or two requests in the same millisecond collapse into one sorted-set entry and the count under-reports. A timestamp plus a random suffix is the usual choice.

The pipeline is not atomic — another client can interleave between the ZCARD and the ZADD, allowing a small over-admission under high concurrency. Lua fixes it in one round trip:

redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
  redis.call('EXPIRE', KEYS[1], ARGV[2])
  return 1
end
return 0
Fixed windowSliding window
MemoryOne counterOne entry per request in the window
AccuracyUp to 2× burst at boundariesExact
CostO(1)O(log n) plus trimming

The trade is memory. A sliding window stores every request in the window, so a 1000-requests-per-minute limit means 1000 entries per user. At very high limits, a token bucket — two numbers, updated arithmetically — is cheaper and nearly as accurate.

Mid: What is ZRANGEBYLEX for, and what is its trap?

It queries members by their string ordering rather than by score — useful for prefix search and range scans over identifiers.

ZADD names 0 "alice" 0 "alicia" 0 "amanda" 0 "bob"

ZRANGEBYLEX names [ali (alj      → 1) "alice"  2) "alicia"      # prefix "ali"
ZRANGEBYLEX names - [b           → everything up to "b"
ZLEXCOUNT names - +              → (integer) 4
SyntaxMeaning
[vInclusive bound
(vExclusive bound
- / +Minimum / maximum possible string

The prefix idiom is to use the prefix as an inclusive lower bound and the prefix with its final character incremented as an exclusive upper bound — [ali to (alj.

The trap is that this is only meaningful when every score is identical. A sorted set orders by score first and member second, so with mixed scores the lexicographic view is not contiguous and the results are undefined:

ZADD mixed 1 "apple" 5 "banana" 2 "cherry"
ZRANGEBYLEX mixed [a [c
  → returns something, but NOT "all members between a and c" — the ordering
    is by score (apple, cherry, banana), so the lex range is meaningless

No error is raised, which is what makes this a genuinely confusing bug — the command succeeds and returns a plausible-looking subset.

So the rule is: score 0 for every member if you intend lexicographic queries, and treat the sorted set as a sorted string index rather than a ranking.

Where I would use it: autocomplete over a bounded vocabulary, or range-scanning identifiers where a trie would be overkill. Where I would not: any set that also needs ranking, since the two uses are mutually exclusive.

Senior: Design a leaderboard with tie-breaking and time-windowed views.

Three requirements interact here: ranking by score, deterministic tie-breaking, and "this week" versus "all time" views.

1. Composite score for tie-breaking, with the precision budget checked explicitly:

MAX_POINTS = 1_000_000
TIME_SCALE = 10_000_000          # ~116 days of second resolution

def encode(points, timestamp):
    # earlier achievers win ties → invert the time component
    return points * TIME_SCALE + (TIME_SCALE - (timestamp % TIME_SCALE))

# budget check — must run in the test suite
assert encode(MAX_POINTS, 0) < 2**53, "score exceeds double precision"
# 10^6 × 10^7 = 10^13  <  9.007 × 10^15  ✓

Getting this wrong is silent — beyond 2⁵³ the double rounds, and players thousands of points apart collapse to identical scores.

2. Time-windowed views via separate keys, each with a TTL:

ZADD lb:alltime      <score> player:1000
ZADD lb:2026-W33     <score> player:1000       EXPIRE lb:2026-W33 1209600
ZADD lb:2026-08-13   <score> player:1000       EXPIRE lb:2026-08-13 172800

Writing to three sorted sets costs three O(log n) operations, which is cheap; the alternative — computing a window at read time — is not possible without scanning.

3. Aggregate windows server-side rather than in the application:

# "this month" from four weekly sets, without moving data
ZUNIONSTORE lb:month 4 lb:2026-W30 lb:2026-W31 lb:2026-W32 lb:2026-W33 AGGREGATE SUM
EXPIRE lb:month 3600          # cache the derived view

4. Bound the size. An all-time leaderboard over 50 million players is ~4.5 GB and mostly uninteresting — nobody queries rank 40,000,000. Trimming keeps it useful and small:

ZREMRANGEBYRANK lb:alltime 0 -100001      # keep only the top 100,000

The trade is that players outside the top 100k lose their rank, so I would keep their raw score in a durable store and show "unranked" rather than a wrong number.

5. Operational concerns I would raise:

ConcernHandling
Hot key on writesAll updates hit one slot — shard by region if it saturates
Cluster and ZUNIONSTOREKeys must share a hash tag: lb:{game1}:W33
DurabilityScores must be rebuildable from a durable store — Redis can lose a second
Rank paginationZREVRANGE stays O(log n + k) at any offset, unlike SQL

The rebuild path is the one I would insist on: because Redis is not the system of record here, there must be a job that reconstructs the sorted set from the durable scores. That makes a failover a performance event rather than a data-loss event.

Senior: Build a delayed job queue. What are the failure modes?

Score by execution time and the queue becomes a range query, but the claim must be atomic or jobs run twice.

# schedule
ZADD jobs:delayed <run_at> <job-json>

# naive claim — BROKEN under concurrency
jobs = ZRANGEBYSCORE jobs:delayed -inf <now> LIMIT 0 10
   ← another worker runs the same query here and gets the same jobs
ZREM jobs:delayed <job>

The read and the removal must be one operation. For a single job, ZPOPMIN does it; for a batch, Lua:

-- claim up to N due jobs atomically
local due = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, ARGV[2])
if #due > 0 then
  redis.call('ZREM', KEYS[1], unpack(due))
  for _, job in ipairs(due) do
    redis.call('ZADD', KEYS[2], ARGV[3], job)      -- move to an in-flight set
  end
end
return due

Moving to an in-flight set rather than deleting is what makes it survivable — the same reasoning as BLMOVE for list queues. A worker crash leaves the job recorded, and a reaper returns it.

Failure modeConsequenceMitigation
Non-atomic claimDuplicate executionZPOPMIN or Lua
Worker crash after claimingJob lostIn-flight set + reaper by claim age
Poller intervalJobs run late by up to the intervalBZPOPMIN, or a short interval
Thundering herd at a popular timeThousands due at midnight exactlyJitter the scheduled times
Clock skew across workersJobs run early or lateUse Redis's TIME as the clock
Redis failoverRecently scheduled jobs lostSchedule in a durable store; Redis as the index

Clock skew deserves emphasis — if each worker uses its own time.time(), a worker whose clock is two minutes fast claims jobs before they are due. Taking the time from Redis itself gives every worker one authoritative clock:

seconds, micros = r.time()          # Redis's clock, not the worker's

The scaling limit worth naming: a single sorted set is one key on one shard, so throughput is bounded by one core. Beyond that, shard by hashing the job id into N queues and run N pollers — at which point ordering is only guaranteed within a shard.

And as with list queues, handlers must be idempotent. Any reaper-based recovery implies at-least-once delivery, and no amount of Lua removes that requirement.

    s = bad_encode(pts, ts)
    r.zadd("bad", {name: s})
    print(f"{name:6} points={pts} → score {s:,} → stored {int(float(r.zscore('bad', name))):,}")
print("ranking:", r.zrevrange("bad", 0, -1, withscores=True))

3 (medium): Compare fixed-window and sliding-window rate limiters.
Solution 
import redis, time, uuid
r = redis.Redis(decode_responses=True)

def fixed_window(user, limit=5, window=4):
    key = f"fw:{user}:{int(time.time()) // window}"
    p = r.pipeline(); p.incr(key); p.expire(key, window)
    count, _ = p.execute()
    return count <= limit

def sliding_window(user, limit=5, window=4):
    key = f"sw:{user}"
    now = time.time()
    p = r.pipeline()
    p.zremrangebyscore(key, 0, now - window)
    p.zcard(key)
    p.zadd(key, {f"{now}:{uuid.uuid4().hex[:8]}": now})
    p.expire(key, window)
    _, count, _, _ = p.execute()
    return count < limit

Test the boundary burst — the flaw fixed windows have:

r.flushdb()
WINDOW, LIMIT = 4, 5

# align to just before a window boundary
while int(time.time()) % WINDOW != WINDOW - 1:
    time.sleep(0.05)
time.sleep(0.7)

fixed_allowed = sum(fixed_window("u1", LIMIT, WINDOW) for _ in range(5))
time.sleep(0.6)                                  # cross the boundary
fixed_allowed += sum(fixed_window("u1", LIMIT, WINDOW) for _ in range(5))
print(f"FIXED  : {fixed_allowed} allowed in ~1.3s (limit {LIMIT} per {WINDOW}s)")

r.flushdb()
while int(time.time()) % WINDOW != WINDOW - 1:
    time.sleep(0.05)
time.sleep(0.7)
slide_allowed = sum(sliding_window("u1", LIMIT, WINDOW) for _ in range(5))
time.sleep(0.6)
slide_allowed += sum(sliding_window("u1", LIMIT, WINDOW) for _ in range(5))
print(f"SLIDING: {slide_allowed} allowed in ~1.3s (limit {LIMIT} per {WINDOW}s)")

FIXED  : 10 allowed in ~1.3s (limit 5 per 4s)
SLIDING: 5 allowed in ~1.3s (limit 5 per 4s)

The fixed window allowed exactly double the intended rate across the boundary; the sliding window held the limit precisely.

Now measure the memory cost of that accuracy:

4 (medium): Use lexicographic ranges for autocomplete.
Solution 
import redis
r = redis.Redis(decode_responses=True)
r.flushdb()

WORDS = ["alice","alicia","alison","amanda","amber","bob","bobby",
         "brian","carol","caroline","charles","david"]
r.zadd("names", {w: 0 for w in WORDS})          # ALL scores zero

def complete(prefix, limit=10):
    if not prefix: return []
    upper = prefix[:-1] + chr(ord(prefix[-1]) + 1)      # increment the last char
    return r.zrangebylex("names", f"[{prefix}", f"({upper}", start=0, num=limit)

for p in ["al", "ali", "b", "car", "z"]:
    print(f"{p:4} → {complete(p)}")

al   → ['alice', 'alicia', 'alison']
ali  → ['alice', 'alicia', 'alison']
b    → ['bob', 'bobby', 'brian']
car  → ['carol', 'caroline']
z    → []

The upper bound trick: for prefix "ali", everything matching sorts between [ali (inclusive) and (alj (exclusive) — "alj" being the next possible string after every "ali…" value.

Now demonstrate the mixed-score trap:

It returned only "apple", silently missing "apricot" — because the set is ordered by score, the lexicographic range is not contiguous. No error, just wrong results.

With uniform scores it works correctly:

5 (hard): Build a delayed job queue with atomic claiming.
Solution 
import redis, time, json, uuid, threading
r = redis.Redis(decode_responses=True)

DELAYED, INFLIGHT = "jobs:delayed", "jobs:inflight"

CLAIM = r.register_script("""
local due = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, ARGV[2])
if #due == 0 then return {} end
redis.call('ZREM', KEYS[1], unpack(due))
for _, job in ipairs(due) do
  redis.call('ZADD', KEYS[2], ARGV[3], job)
end
return due
""")

def schedule(payload, delay=0):
    job = json.dumps({"id": uuid.uuid4().hex[:8], "payload": payload})
    r.zadd(DELAYED, {job: time.time() + delay})
    return job

def claim(batch=10):
    now = time.time()
    return CLAIM(keys=[DELAYED, INFLIGHT], args=[now, batch, now])

def ack(job): r.zrem(INFLIGHT, job)

def reap(max_age=5):
    stale = r.zrangebyscore(INFLIGHT, 0, time.time() - max_age)
    for job in stale:
        r.zrem(INFLIGHT, job)
        r.zadd(DELAYED, {job: time.time()})
    return len(stale)

r.delete(DELAYED, INFLIGHT)
schedule("now-1", 0); schedule("now-2", 0)
schedule("later", 5)
print(f"scheduled={r.zcard(DELAYED)}")

claimed = claim()
print(f"claimed now: {[json.loads(j)['payload'] for j in claimed]}")
print(f"delayed={r.zcard(DELAYED)} inflight={r.zcard(INFLIGHT)}")

scheduled=3
claimed now: ['now-1', 'now-2']
delayed=1 inflight=2

Only the due jobs were claimed — "later" remains scheduled for 5 seconds hence.

6 (hard): Build a time-windowed leaderboard with server-side aggregation.
Solution 
import redis, time, random
r = redis.Redis(decode_responses=True)
r.flushdb()

MAX_POINTS, TIME_SCALE = 1_000_000, 10**7
def encode(points, ts): return points * TIME_SCALE + (TIME_SCALE - (int(ts) % TIME_SCALE))
def decode_points(score): return int(score) // TIME_SCALE

assert encode(MAX_POINTS, 0) < 2**53
print(f"max score {encode(MAX_POINTS,0):,} < 2^53 {2**53:,}  ✓")

class Leaderboard:
    def __init__(self, client): self.r = client
    def _keys(self, ts):
        t = time.localtime(ts)
        return [f"lb:all", f"lb:w{t.tm_year}-{t.tm_yday//7:02d}", f"lb:d{t.tm_yday:03d}"]
    def record(self, player, points, ts=None):
        ts = ts or time.time()
        score = encode(points, ts)
        p = self.r.pipeline()
        for k in self._keys(ts):
            p.zadd(k, {player: score}, gt=True)     # only improvements count
            if k != "lb:all": p.expire(k, 1209600)
        p.execute()
    def top(self, key, n=10):
        return [(m, decode_points(s)) for m, s in
                self.r.zrevrange(key, 0, n-1, withscores=True)]
    def rank(self, key, player):
        rk = self.r.zrevrank(key, player)
        return None if rk is None else rk + 1

lb = Leaderboard(r)
now = time.time()
random.seed(7)
for i in range(5000):
    lb.record(f"player:{i}", random.randint(100, 999999), now)

print("top 5 all-time:")
for m, p in lb.top("lb:all", 5): print(f"  {m:14} {p:,}")
print(f"\nplayer:42 rank = {lb.rank('lb:all', 'player:42')} of {r.zcard('lb:all'):,}")

top 5 all-time:

  player:4471    999,208

    for i in range(200):
        r.zadd(f"lb:d{day:03d}", {f"player:{i}": random.randint(100, 5000)})

              zip(range(1,5), [0.4, 0.6, 0.8, 1.0])}, aggregate="SUM")

Bound the all-time set so it stays useful:

🎯 Key Takeaways

  • A sorted set maintains a hash table and a skip list together — O(1) ZSCORE and O(log n) ZRANK from the same data.
  • The cost is roughly double a plain set's memory; the benefit is the only structure that answers "what rank is this?" without scanning.
  • Members are unique and scores are not, so ZADD is an upsert — a return of 0 means updated, not failed.
  • ZADD GT makes "record only if it beats the current score" atomic, removing a read-compare-write race.
  • ZCOUNT is O(log n), not O(k) — the skip list stores span counts, so counting never visits the members.
  • Scores are IEEE-754 doubles: integers are exact only to 2⁵³, above which odd values round and distinct scores collapse.
  • Composite scores must have their digit budget checked — assert encode(max, max) < 2**53 catches an entire class of silent bug.
  • Nanosecond timestamps exceed 2⁵³; milliseconds and microseconds are safe.
  • ZRANGEBYLEX is only meaningful when every score is identical — with mixed scores it silently returns wrong results.
  • The prefix idiom is [prefix to (prefix-with-last-char-incremented.
  • Sliding-window rate limiting scores by timestamp and held the limit exactly where a fixed window allowed double at the boundary.
  • That accuracy cost 1,510× the memory in the measurement — at very high limits a token bucket is the better trade.
  • The pipeline version of a sliding window is not atomic and over-admitted 57 against a limit of 50; Lua fixes it.
  • Delayed queues score by execution time, but the claim must be atomic — the non-atomic version produced 231 duplicate executions across 8 workers.
  • Move claimed jobs to an in-flight set rather than deleting them, and reap by claim age — the same reasoning as BLMOVE for lists.
  • Take the clock from Redis's TIME so worker clock skew cannot cause early or late execution.
  • ZUNIONSTORE with WEIGHTS builds composite rankings server-side — 4 sets aggregated in under 2 ms.
  • Trim leaderboards with ZREMRANGEBYRANK; keeping the top 1000 of 5000 reclaimed 80% of the memory.
