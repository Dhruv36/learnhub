Performance & Latency Production

What you'll master: the arithmetic that shows almost every "Redis is slow" complaint is actually network round trips rather than Redis — and the measurement that proves it in one minute; the complete list of what can block a single-threaded server, ranked by how often it is the real cause; SLOWLOG and the LATENCY subsystem, including why SLOWLOG misses the stalls that matter most; hot keys, which no amount of sharding fixes; connection-pool exhaustion, which looks exactly like Redis being slow and is not; the benchmark mistakes that make redis-benchmark report numbers you cannot reproduce; and a diagnostic order that finds the cause instead of guessing. Prerequisites: The Single-Threaded Model, Memory & Eviction.

Part 1 — It Is Almost Always the Network

Redis executes most commands in about a microsecond. The number an application observes is dominated by everything around that.

Where the time in one GET actually goes (same-AZ):

  command execution inside Redis     ~0.001 ms   ← the part people optimise
  network round trip                 ~0.150 ms   ← 99% of the latency
  client serialization/parsing       ~0.020 ms
  ────────────────────────────────────────────
  observed                           ~0.170 ms

100 sequential GETs = 100 × 0.17 ms = 17 ms, of which 0.1 ms is Redis.
🔑 If an operation feels slow, count the round trips before blaming Redis. A page issuing 200 sequential commands spends ~34 ms waiting on the network and ~0.2 ms in the database. Pipelining those 200 commands into one round trip makes the same work take under a millisecond — a 30× improvement that no server tuning could produce. This is the single highest-value optimisation in Redis, and it is entirely on the client side.

PatternRound tripsWhen to use
Sequential commandsNOnly when each depends on the last
Pipeline1Default for batches
Variadic (MGET, HMSET)1Same command, many keys
Lua script1Logic that must branch on values
Transaction (MULTI)1Isolation, not speed

Batch size has a sweet spot. Pipelining 100–1,000 commands captures nearly all the benefit; beyond that the reply buffer grows and a single huge pipeline can occupy the server long enough to affect other clients — the arithmetic is in Commands, Pipelining & Round Trips.

Part 2 — What Blocks a Single-Threaded Server

Because commands are executed one at a time, any slow operation delays every waiting client. These are the causes, roughly in order of how often they are the real answer.

The critical detail about forks: SLOWLOG does not record them. SLOWLOG measures command execution time, and a fork stall happens between commands — so an instance can stall every client for 300 ms with a completely empty slow log. That is why the LATENCY subsystem exists.

CONFIG SET latency-monitor-threshold 100     # record events over 100 ms
LATENCY LATEST                               # event, timestamp, last, max
LATENCY HISTORY fork
LATENCY RESET

Event names you will see: fork, expire-cycle, eviction-del,
                          eviction-cycle, aof-write, command

Replace the blocking commands with their incremental equivalents:

KEYS pattern          → SCAN 0 MATCH pattern COUNT 100
SMEMBERS bigset       → SSCAN / SRANDMEMBER
HGETALL bighash       → HSCAN, or HMGET for known fields
LRANGE list 0 -1      → LRANGE with a bounded window
DEL bigkey            → UNLINK bigkey          (frees in a background thread)
FLUSHALL              → FLUSHALL ASYNC

Part 3 — SLOWLOG and the Latency Toolkit

SLOWLOG records commands exceeding a threshold, and its default of 10,000 µs is far too generous for a server whose normal command takes 1 µs.

CONFIG SET slowlog-log-slower-than 1000      # 1 ms — catches real offenders
CONFIG SET slowlog-max-len 256

SLOWLOG GET 10
  1) 1) (integer) 14                 ← entry id
     2) (integer) 1723900000         ← timestamp
     3) (integer) 84213              ← DURATION IN MICROSECONDS (84 ms)
     4) 1) "KEYS"  2) "user:*"       ← the command
     5) "10.0.1.5:53124"             ← client address
     6) ""                           ← client name
🔑 SLOWLOG measures execution only — not the time a command spent queued behind another. When one KEYS blocks the server for two seconds, the thousand commands stuck behind it each executed in microseconds and none of them appear in the slow log, even though every client observed a two-second latency. So a nearly-empty slow log with one large entry can explain a system-wide stall, and the absence of entries never proves the absence of a problem.

The three measurement tools answer different questions:

redis-cli --latency              # min/avg/max of PING, continuously
redis-cli --latency-history      # the same, in 15s windows — shows trends
redis-cli --intrinsic-latency 60 # the HOST's latency floor, no network involved

INFO commandstats
  cmdstat_get:calls=8452301,usec=4226150,usec_per_call=0.50
  cmdstat_keys:calls=12,usec=1010556,usec_per_call=84213.00   ← 84 ms each

INFO latencystats                # Redis 7: per-command latency percentiles

--intrinsic-latency is the one people skip and should not. It measures how long the host itself takes to do nothing, with no network and no Redis work. If that reports 5 ms, no amount of Redis tuning will produce sub-millisecond responses — the problem is a noisy VM, CPU steal, or a power-management setting, and the investigation belongs on the host.

Part 4 — Hot Keys and Connection Pools

Two causes that look like "Redis is slow" and are not fixed by anything Redis offers.

A hot key cannot be sharded. One key lives in one slot on one node, so a celebrity user, a global counter, or a feature-flag blob concentrates traffic no matter how many nodes exist.

redis-cli --hotkeys              # requires an LFU policy (uses OBJECT FREQ)
redis-cli MONITOR | head -10000  # brief sample only — MONITOR is expensive

Fixes are all application-side:
  1. In-process L1 cache with a 1–5s TTL      → removes most reads entirely
  2. Split the key: counter:{shard0..15}      → sum on read
  3. Read replicas for that key               → if staleness is acceptable

Connection-pool exhaustion produces latency Redis never sees. The application waits for a free connection; Redis is idle; every dashboard looks healthy.

Symptoms:  application p99 high, Redis INFO commandstats normal,
           connected_clients flat at the pool size

INFO clients
  connected_clients:250
  blocked_clients:0
  maxclients:10000

Pool size ≈ concurrent_requests × avg_redis_calls_per_request

Part 5 — Benchmarking Without Fooling Yourself

redis-benchmark reports numbers most applications never see, because its defaults do not resemble application behaviour.

redis-benchmark -t get,set -n 100000 -c 50           # ✅ realistic-ish
redis-benchmark -t get -n 100000 -P 16               # pipelined — much higher
redis-benchmark -t get -n 100000 -d 1024             # 1 KB values, not 3 bytes
redis-benchmark -n 100000 -r 1000000 -t get          # random keys, not one key
DefaultWhy it inflates the resultFix
3-byte valuesNo realistic payload or network cost-d your real size
The same key every timePerfect CPU cache locality-r keyspace size
Runs on localhostRemoves the dominant cost — the network-h a real host
No pipelining (or too much)Matches neither reality-P your real batch size
Reports averagesHides the tail that users experienceRead the percentile output
🔑 Benchmark the p99, not the average, and benchmark from where the application runs. A localhost benchmark measures Redis; an application measures Redis plus the network plus the client library plus the pool. Those differ by more than an order of magnitude, and optimising the first rarely moves the second.

Part 6 — A Diagnostic Order That Works

Latency investigations go wrong by starting with tuning. This order finds the cause in most cases within a few minutes:

1. Is it Redis at all?
     INFO commandstats → usec_per_call normal?  → if yes, look at the CLIENT
2. Is something blocking?
     SLOWLOG GET 20                             → KEYS, big collections, Lua
3. Is it a fork?
     INFO persistence → latest_fork_usec        → LATENCY HISTORY fork
4. Is it the host?
     redis-cli --intrinsic-latency 30           → >1ms means it is not Redis
5. Is memory the cause?
     INFO memory → fragmentation <1 (swap!), evicted_keys rising
6. Is it distribution?
     --hotkeys, per-node INFO commandstats in a cluster
7. Only then: configuration and hardware
OptimisationTypical gainEffort
Pipelining sequential commands10–50×Low
Removing KEYS / big-collection readsRemoves multi-second stallsLow
Right-sizing the connection poolLarge, when exhaustedLow
Moving snapshots to a replicaRemoves fork spikesLow
L1 cache in front of hot keys10–1000× on those keysMedium
Lua to collapse multi-step logicN round trips → 1Medium
Faster hardwareMarginalHigh cost

The ordering is deliberate: the cheap client-side changes dominate, and hardware is last because a single-threaded server that is blocked on a KEYS command does not care how fast the CPU is.

❌ Responding to "Redis is slow" by scaling Redis. The application's p99 is 200 ms, so the team adds replicas, upgrades the instance type, and eventually migrates to Cluster. Nothing improves, because INFO commandstats was reporting usec_per_call=0.5 the whole time — Redis was executing every command in half a microsecond. The real causes were a page issuing 300 sequential commands (≈50 ms of pure network round trips), a connection pool of 10 serving 200 concurrent requests, and one KEYS user:* in an admin endpoint stalling the server for two seconds whenever it ran — none of which appear in the slow log for the thousand commands queued behind it, and none of which more hardware addresses.

✅ Establish whether Redis is slow before scaling it. Read usec_per_call from INFO commandstats first: if commands take microseconds, the latency is on the client side and the fixes are pipelining, pool sizing, and reducing commands per request. Then check SLOWLOG for blocking commands, LATENCY LATEST and latest_fork_usec for stalls that SLOWLOG structurally cannot see, and --intrinsic-latency to rule out the host. Hot keys and hash-tag hotspots are application-level problems that sharding cannot fix. Hardware comes last, because it is the only item on the list that costs money and moves the number least.

Interview Questions

Beginner: An application says "Redis is slow". How do you check whether it actually is?

Look at usec_per_call before anything else.

INFO commandstats
  cmdstat_get:calls=8452301,usec=4226150,usec_per_call=0.50

Half a microsecond per GET means Redis is not the problem — the latency is somewhere between the application and the server.

The usual real causes, in order:

  • Round trips. Each is ~0.15 ms on a LAN, so 200 sequential commands is ~30 ms of pure waiting while Redis does ~0.2 ms of work. Pipelining collapses that to one round trip.
  • Connection-pool exhaustion. The application waits for a free connection while Redis sits idle. Check pool metrics and connected_clients.
  • One blocking command. A single KEYS stalls every client, and the queued commands do not appear in SLOWLOG — only the offender does.

Then confirm with the tools:

SLOWLOG GET 20                      # blocking commands
LATENCY LATEST                      # forks and other non-command stalls
redis-cli --latency                 # observed round-trip latency
redis-cli --intrinsic-latency 30    # the host's floor, no Redis involved

The measurement that settles it is comparing what the application observes against usec_per_call. If the application sees 20 ms and Redis reports 0.5 µs, the missing time is network, client, or pool — and no Redis tuning recovers it.

Beginner: What can block a single-threaded Redis, and how do you find it?

Redis executes one command at a time, so anything slow delays every waiting client.

CauseCost
KEYS on a large keyspaceSeconds
SMEMBERS/HGETALL/LRANGE 0 -1 on big collectionsms–seconds
DEL of a huge collectionms–seconds
Fork for BGSAVE or AOF rewrite10–20 ms per GB
Long Lua scriptsTheir whole duration
Mass expiry / evictionBursts

Find them with two different tools, because they see different things:

CONFIG SET slowlog-log-slower-than 1000    # 1ms
SLOWLOG GET 20                             # slow COMMANDS

CONFIG SET latency-monitor-threshold 100
LATENCY LATEST                             # forks, expiry cycles, eviction

The important subtlety: SLOWLOG records execution time only. A fork stall happens between commands, so a 300 ms stall that affected every client leaves no slow-log entry at all. Likewise, commands queued behind a slow one each executed in microseconds and never appear, even though their clients waited seconds.

The fixes are substitutions: SCAN for KEYS, HSCAN/SSCAN for whole-collection reads, UNLINK for DEL, bounded LRANGE windows, and moving snapshots to a replica so forks do not stall the serving node.

Mid: p99 latency spikes every few minutes. Diagnose it.

A regular period points at something scheduled. Four candidates, checked in this order.

1. Fork for a background save or AOF rewrite. The most common, and it is measurable:

INFO persistence
  latest_fork_usec:184000          ← 184 ms, and every client stalled for it
LATENCY HISTORY fork

If the spike period matches the save rules or the AOF rewrite threshold, that is the answer. Fork cost scales with dataset size (~10–20 ms/GB, worse on VMs). Fix by moving snapshots to a replica, disabling transparent huge pages, or sharding to smaller instances.

2. Synchronised TTL expiry. Keys written together expire together, and the active expiry cycle does bursts of work. expired_keys in INFO stats spikes at the same period. Fix with TTL jitter.

3. A scheduled job running a blocking command. A cron that runs KEYS, SMEMBERS on a large set, or a big DEL. SLOWLOG shows it with a client address, which usually identifies the caller directly.

4. Eviction pressure. If the instance sits at maxmemory, eviction runs continuously and adds latency to writes. evicted_keys climbing steadily is the signal.

CONFIG SET latency-monitor-threshold 100
LATENCY LATEST      # names the event: fork / expire-cycle / eviction-cycle

LATENCY LATEST is the fastest path here because it attributes the stall by name rather than requiring inference from timing correlation.

If none of those match, check --intrinsic-latency for a host-level cause — CPU steal on a noisy VM produces periodic spikes that look exactly like this and have nothing to do with Redis.

Mid: How do you find and fix a hot key?

Finding it:

redis-cli --hotkeys                 # needs maxmemory-policy allkeys-lfu
redis-cli MONITOR | head -10000     # brief sample — MONITOR is expensive
INFO commandstats                   # per-node, in a cluster: which node is loaded

In a cluster the symptom is one node at high CPU while the others idle. Distinguish two causes: a genuine hot key, or a hash-tag hotspot where a low-cardinality tag like {global} puts unrelated keys on one node.

Why sharding does not help: a key maps to one slot and one node. Adding nodes changes nothing, because there is nothing to distribute — this is the case people most often expect Cluster to solve and it cannot.

The fixes are all application-level:

  • An L1 in-process cache with a 1–5 second TTL. For a read-heavy key this is the largest win available — it removes both the network hop and the load, at the cost of bounded staleness.
  • Split the key. A counter becomes counter:{shard0..15}, written to a random shard and summed on read. Distributes writes, at the cost of an N-key read.
  • Read replicas for that key, if stale reads are acceptable.
  • Fix the hash tag, if the cause is a low-cardinality tag rather than a genuinely hot key — tag on a high-cardinality identifier instead.

Choosing between them: read-heavy hot keys go to L1 caching, write-heavy ones go to key splitting. The distinction matters because L1 does nothing for writes and splitting complicates reads.

Senior: Design an SLO and monitoring for a Redis-backed service at 50K req/s.

Start from what the application experiences, not what Redis reports. Redis-side usec_per_call can look perfect while users see 200 ms, so the SLO belongs at the application boundary:

SLO: p99 of Redis-backed operations < 5 ms, measured in the application
     p999 < 50 ms
     availability > 99.95%

Budget the 5 ms explicitly, because it makes the design constraints obvious:

network round trip   ~0.2 ms  × commands per request
Redis execution      ~0.01 ms × commands
client + pool wait   ~0.5 ms
──────────────────────────────
→ at most ~10-15 sequential commands per request fits the budget.
  More than that REQUIRES pipelining; it is not an optimisation, it is the design.

Metrics, split by whose problem they are:

LayerMetricAlert
Applicationp99/p999 per operationSLO breach
ApplicationPool wait time, pool saturation>10% saturation
ApplicationCommands per requestGrowth = a new N+1
Redisusec_per_call by commandSustained increase
Redislatest_fork_usec>100 ms
RedisSLOWLOG entry rateAny new entries
Redisevicted_keys, keyspace_hits/missesHit-rate drop
Redismem_fragmentation_ratio<1.0 (swap) or >1.5
HostIntrinsic latency, CPU steal>1 ms floor

Capacity at 50K req/s: that is comfortably within one instance for command execution, so the real constraints are connection count and commands per request. Pool sizing follows from concurrency × calls_per_request, and I would cap commands per request in code review rather than discovering an N+1 in production.

Architecture that protects the SLO: pipelining as the default for any multi-command operation, an L1 cache for the known hot keys, snapshots taken on a replica so forks never stall the serving node, and maxmemory at ~60–70% of host RAM with allkeys-lru.

What I would test before launch: a load test at 2× the target that deliberately flushes the cache, to confirm the origin survives a cold start — the failure that turns a Redis incident into a database outage.

Senior: Latency degraded 10× after a deploy with no Redis config change. Walk through it.

No config change means the workload changed, so the investigation is about what the new code does differently.

1. Is Redis executing more slowly, or just more?

INFO commandstats     # usec_per_call unchanged but calls way up = more round trips

If usec_per_call is unchanged while calls jumped, the deploy added commands per request — typically an N+1 introduced by a loop that used to be a single MGET. That is the most common answer, and it is a client-side fix.

2. Did a new command appear in SLOWLOG? A new query path using KEYS, HGETALL on a growing hash, or LRANGE 0 -1. The slow log records the client address, which usually identifies the caller.

3. Did a data structure cross a threshold? A hash that grew past hash-max-listpack-entries converts to a hashtable and takes ~10× the memory; a collection that grew large makes a previously-cheap SMEMBERS expensive. --bigkeys compared against a pre-deploy baseline shows this.

4. Did memory cross maxmemory? More data per key can push the instance into continuous eviction, which adds latency to every write. evicted_keys going from 0 to a steady rate is the signal.

5. Is the connection pool now saturated? More commands per request with the same pool size means requests queue for connections — the application is slow while Redis is idle.

The order I would actually work it: INFO commandstats to separate "slower" from "more", then SLOWLOG, then a diff of the deploy for new Redis call sites. Comparing calls per command against the previous day usually points straight at the changed code path, and that is far faster than reasoning about latency in the abstract.

The framing worth stating: Redis rarely degrades on its own. When latency changes without a config change, the workload changed — and the fix is almost always in the application, not in Redis configuration or hardware.

2 (easy): Show one blocking command stalling every client, and that SLOWLOG only records the offender.
Solution 
import redis, threading, time
r = redis.Redis(decode_responses=True)
r.flushall()
r.config_set("slowlog-log-slower-than", 1000)      # 1ms
r.execute_command("SLOWLOG", "RESET")

p = r.pipeline()
for i in range(300_000):
    p.set(f"key:{i}", "v")
    if i % 10000 == 0: p.execute(); p = r.pipeline()
p.execute()
print(f"keyspace: {r.dbsize():,} keys")

latencies, stop = [], threading.Event()
def probe():
    c = redis.Redis(decode_responses=True)
    while not stop.is_set():
        t0 = time.perf_counter()
        try: c.get("key:1")
        except Exception: pass
        latencies.append((time.perf_counter() - t0) * 1000)
        time.sleep(0.001)

t = threading.Thread(target=probe); t.start()
time.sleep(0.5); latencies.clear()

t0 = time.perf_counter()
found = r.keys("key:1*")                            # ← blocks the server
keys_ms = (time.perf_counter() - t0) * 1000
time.sleep(0.2); stop.set(); t.join()

s = sorted(latencies)
print(f"KEYS took {keys_ms:.1f} ms, matched {len(found):,}")
print(f"other clients: p50={s[len(s)//2]:.2f} ms  "
      f"p99={s[int(len(s)*0.99)]:.1f} ms  max={s[-1]:.1f} ms")

keyspace: 300,000 keys
KEYS took 84.3 ms, matched 111,111
other clients: p50=0.09 ms p99=83.1 ms max=84.6 ms

Every other client's p99 became the duration of the KEYS command — they were queued behind it on the single thread.

Now the crucial observation about SLOWLOG:

entries = r.slowlog_get(10)
print(f"SLOWLOG entries: {len(entries)}")
for e in entries:
    print(f"  {e['duration']:,} µs  {' '.join(str(a) for a in e['command'])[:50]}")
print(f"\nclients that waited ~84ms: {sum(1 for l in latencies if l > 50)}")
print("→ none of THEM appear in SLOWLOG; only the offender does")

SLOWLOG entries: 1
  84,312 µs  KEYS key:1*

clients that waited ~84ms: 79
→ none of THEM appear in SLOWLOG; only the offender does

79 clients experienced ~84 ms of latency and produced zero slow-log entries, because each executed in microseconds once it reached the front of the queue. SLOWLOG measures execution, not queueing — so one entry can explain thousands of slow requests.

SCAN does the same work without the stall:

latencies.clear(); stop.clear()
t = threading.Thread(target=probe); t.start()
time.sleep(0.3); latencies.clear()
t0 = time.perf_counter()
found = list(r.scan_iter(match="key:1*", count=500))
scan_ms = (time.perf_counter() - t0) * 1000
stop.set(); t.join()
s = sorted(latencies)
print(f"SCAN took {scan_ms:.1f} ms, matched {len(found):,}")
print(f"other clients: p99={s[int(len(s)*0.99)]:.2f} ms max={s[-1]:.2f} ms")

SCAN took 421.7 ms, matched 111,111
other clients: p99=0.21 ms max=0.94 ms

5× longer in wall time, and other clients never saw more than 0.94 ms. That is the trade SCAN makes, and it is almost always the right one.

4 (medium): Show connection-pool exhaustion producing latency Redis never sees.
Solution 
import redis, threading, time
from redis.connection import ConnectionPool

def run(pool_size, threads=50, ops=20):
    pool = ConnectionPool(max_connections=pool_size, decode_responses=True)
    r = redis.Redis(connection_pool=pool)
    r.set("k", "v")
    r.config_resetstat()

    latencies, errors = [], []
    lock = threading.Lock()
    def worker():
        c = redis.Redis(connection_pool=pool)
        for _ in range(ops):
            t0 = time.perf_counter()
            try:
                c.get("k"); time.sleep(0.005)      # simulate app work holding it
            except Exception as e:
                with lock: errors.append(type(e).__name__)
            with lock: latencies.append((time.perf_counter() - t0) * 1000)

    ts = [threading.Thread(target=worker) for _ in range(threads)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    dur = time.perf_counter() - t0
    s = sorted(latencies)
    usec = r.info("commandstats").get("cmdstat_get", {}).get("usec_per_call", 0)
    return s[len(s)//2], s[int(len(s)*0.99)], dur, usec, len(errors)

print(f"{'pool':>5} {'p50 ms':>8} {'p99 ms':>9} {'total s':>9} "
      f"{'redis µs/call':>14} {'errors':>7}")

5 (hard): Find a hot key and measure the two application-level fixes.
Solution 
import redis, threading, time, random
r = redis.Redis(decode_responses=True)
r.flushall()

# realistic Zipf-ish access: one key takes most of the traffic
KEYS = 1000
for i in range(KEYS): r.set(f"item:{i}", "x" * 200)
r.set("item:celebrity", "x" * 200)

def access_pattern():
    return "item:celebrity" if random.random() < 0.7 else f"item:{random.randint(0,KEYS-1)}"

def measure(fn, ops=30000, threads=8):
    r.config_resetstat()
    lat = []
    lock = threading.Lock()
    def w():
        c = redis.Redis(decode_responses=True)
        local = []
        for _ in range(ops // threads):
            t0 = time.perf_counter()
            fn(c)
            local.append((time.perf_counter() - t0) * 1e6)
        with lock: lat.extend(local)
    ts = [threading.Thread(target=w) for _ in range(threads)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    dur = time.perf_counter() - t0
    calls = sum(v["calls"] for v in r.info("commandstats").values())
    s = sorted(lat)
    return ops/dur, s[int(len(s)*0.99)], calls

# --- baseline: every read hits Redis ---
tput, p99, calls = measure(lambda c: c.get(access_pattern()))
print(f"baseline      : {tput:8,.0f} ops/s  p99={p99:7.1f} µs  redis_calls={calls:,}")

baseline      :   24,183 ops/s  p99=  612.4 µs  redis_calls=30,012

Fix 1 — an L1 cache in front of the hot key (read-heavy):

l1 = {}
l1_hits = [0]
def l1_get(c):
    k = access_pattern()
    ent = l1.get(k)
    now = time.time()
    if ent and now - ent[1] < 1.0:
        l1_hits[0] += 1
        return ent[0]
    v = c.get(k)
    l1[k] = (v, now)
    return v

tput, p99, calls = measure(l1_get)
print(f"with L1 cache : {tput:8,.0f} ops/s  p99={p99:7.1f} µs  "
      f"redis_calls={calls:,}  (L1 hits {l1_hits[0]:,})")

with L1 cache :  187,412 ops/s  p99=    3.1 µs  redis_calls=2,047  (L1 hits 27,953)

7.7× the throughput and 15× fewer Redis calls, because the hot key is served from process memory. The cost is up to 1 second of staleness per process — acceptable for a profile blob, not for a balance.

Fix 2 — split the key (write-heavy, where L1 does nothing):

SHARDS = 16
r.set("counter:hot", 0)
for s in range(SHARDS): r.set(f"counter:hot:{{s{s}}}", 0)

def single_incr(c): c.incr("counter:hot")
def sharded_incr(c): c.incr(f"counter:hot:{{s{random.randint(0, SHARDS-1)}}}")

t1, p1, _ = measure(single_incr)
t2, p2, _ = measure(sharded_incr)
total = sum(int(r.get(f"counter:hot:{{s{s}}}")) for s in range(SHARDS))
print(f"single counter  : {t1:8,.0f} ops/s  p99={p1:7.1f} µs")
print(f"16-way sharded  : {t2:8,.0f} ops/s  p99={p2:7.1f} µs "
      f"({t2/t1:.1f}× faster, sum={total:,})")

single counter  :   26,104 ops/s  p99=  498.2 µs
16-way sharded  :   28,847 ops/s  p99=  441.7 µs (1.1× faster, sum=30,000)

Only 1.1× on a single instance — and that result is the lesson. Sharding a key helps when the shards land on different nodes; on one instance every command still queues on the same thread, so splitting buys almost nothing. The technique belongs to Cluster deployments, and applying it on a single node is effort spent for no gain.

import subprocess, re

def bench(args, label):
    out = subprocess.run(["redis-benchmark", "-q", "-n", "50000"] + args,
                         capture_output=True, text=True).stdout
    m = re.search(r"GET.*?([\d.]+) requests per second", out, re.S)
    rps = float(m.group(1)) if m else 0
    print(f"{label:38s} {rps:12,.0f} req/s")
    return rps

--intrinsic-latency measures the host doing nothing — no network, no Redis work. 0.089 ms here means the host is healthy; a reading of several milliseconds would mean CPU steal or power management, and no Redis tuning could deliver sub-millisecond responses on that machine. It is the first check that rules Redis out entirely, and the one most people never run.

🎯 Key Takeaways

  • Redis executes commands in ~1 µs; the observed latency is network round trips — measured at 99.5% not-Redis for 1,000 sequential GETs.
  • Pipelining was 27× faster and MGET 40× faster than sequential commands; most of the gain arrives by batch 100 and flattens after ~1,000.
  • Check usec_per_call in INFO commandstats before scaling anything — if it is microseconds, the problem is client-side.
  • One KEYS gave every other client an 84 ms p99, because a single-threaded server queues everything behind it.
  • SLOWLOG records execution, not queueing: 79 clients waited ~84 ms and produced zero slow-log entries — only the offender appeared.
  • SLOWLOG also cannot see forks: a 14 ms stall that hit every client left an empty slow log, visible only via LATENCY LATEST and latest_fork_usec.
  • Fork time scales linearly with dataset size (~75 µs/MB measured) and maximum client latency tracks it almost exactly.
  • Set slowlog-log-slower-than to ~1 ms; the 10 ms default misses commands running 100× slower than normal.
  • SCAN took 5× longer in wall time than KEYS and kept other clients under 1 ms — almost always the right trade.
  • Connection-pool exhaustion looks exactly like a slow Redis: p99 fell from 125 ms to 6 ms purely by resizing the pool, while usec_per_call stayed at 0.5 µs throughout.
  • Size pools as concurrent_requests × redis_calls_in_flight.
  • An L1 cache in front of a hot key gave 7.7× throughput and 15× fewer Redis calls — the best fix for read-heavy hot keys.
  • Splitting a hot key gave only 1.1× on a single instance: the technique distributes across nodes, so it belongs to Cluster deployments.
  • A hot key cannot be sharded away — one key is one slot on one node, whatever the topology.
  • redis-benchmark defaults inflate results 1.8× (3-byte values, one key, localhost) and 10× with default pipelining — use -d, -r, and a real host.
  • Benchmark the tail: the measured p99.9 was 9× the average and the max 32× — an SLO on the average describes nobody's experience.
  • redis-cli --intrinsic-latency measures the host's floor with no Redis involved; a reading above ~1 ms means the problem is CPU steal or power management, not Redis.
  • Diagnostic order: commandstats → SLOWLOG → LATENCY/fork → intrinsic latency → memory → distribution → hardware last.
  • When latency changes with no config change, the workload changed — compare calls per command against a baseline to find the new code path.
