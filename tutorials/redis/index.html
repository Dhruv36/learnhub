What Redis Actually Is Foundations

What you'll master: why Redis is a data-structure server rather than a key-value cache, and why that distinction changes what you build with it; where its speed genuinely comes from — and why "in-memory" is only half the answer; the durability spectrum from pure cache to persisted store, and the honest statement of what Redis guarantees on crash; the RESP protocol and why round trips, not CPU, are almost always your bottleneck; and the decision framework for when Redis is the right tool versus when you are misusing it as a database. Prerequisites: basic networking, and familiarity with caching concepts helps.

Part 1 — A Data-Structure Server, Not a Cache

The most common misconception is that Redis is "a fast key-value store". It is a server that exposes data structures over the network, and every value has a type with its own command set.

memcached:  key → opaque blob        (you serialise, you deserialise, you replace the whole thing)

Redis:      key → STRING             SET / GET / INCR / APPEND / SETRANGE
            key → LIST               LPUSH / RPOP / LRANGE / BLPOP
            key → HASH               HSET / HGET / HINCRBY / HGETALL
            key → SET                SADD / SISMEMBER / SINTER / SPOP
            key → SORTED SET         ZADD / ZRANGE / ZRANGEBYSCORE / ZINCRBY
            key → STREAM             XADD / XREAD / XREADGROUP
            key → BITMAP / HLL / GEO  SETBIT / PFADD / GEOADD
🔑 The difference is where the computation happens. With an opaque blob, incrementing a counter means GET, deserialise, add one, serialise, SET — five steps, two network round trips, and a race condition between them. With Redis it is INCR key: one round trip, executed atomically inside the server. That is the entire design philosophy — move the operation to the data instead of moving the data to the operation. Once you internalise it, you stop reaching for read-modify-write and start asking "is there a command that does this in place?"

# the blob approach — racy and slow
GET user:42:visits          → "17"
# ... application adds 1 ...
SET user:42:visits "18"     ← another client may have written 18 already; one increment is LOST

# the Redis approach — atomic, single round trip
INCR user:42:visits         → 18
TypeBacked byNatural use
StringByte array (also int-encoded)Cache entries, counters, flags
HashHash table (or listpack when small)Objects with fields — update one field
ListQuicklist (linked list of listpacks)Queues, recent-items feeds
SetHash table (or intset)Membership, tags, unique visitors
Sorted setSkip list + hash tableLeaderboards, priority queues, time indexes
StreamRadix tree of entriesEvent logs with consumer groups

Part 2 — Where the Speed Comes From

"It's in memory" is the usual explanation and it is incomplete — a memory-resident database can still be slow. Redis is fast for four reasons, and the fourth surprises people.

ReasonEffect
Data lives in RAM~100 ns access vs ~100 µs for an SSD read — a 1000× gap
Purpose-built data structuresO(1) or O(log n) operations, no query planner, no parsing of SQL
A simple wire protocol (RESP)Trivial to parse — no schema negotiation, no serialisation framework
Single-threaded command executionNo locks, no context switches, no cache-line contention

The last one is counter-intuitive and worth stating plainly: Redis executes commands one at a time, on one core, and that is a performance feature. There are no mutexes to acquire, no coordination between threads, and no possibility of two commands interleaving mid-operation — which is also why every single command is atomic for free.

typical single-instance throughput (one core, small values, pipelined):

  GET / SET             ~100,000–150,000 ops/sec unpipelined
                        ~1,000,000+ ops/sec pipelined
  latency p50           ~0.1–0.3 ms  (dominated by the network, not Redis)

Notice what dominates that latency figure. Redis typically spends microseconds executing a command; the rest is network round trip. This is why pipelining is the single highest-leverage optimisation available, and why "Redis is slow" almost always means "we are making too many round trips".

Part 3 — The Durability Spectrum

Redis is often described as either "a cache" or "a database". It is neither by default — it sits on a spectrum you configure.

NO PERSISTENCE ─────────── RDB SNAPSHOTS ─────────── AOF everysec ─────────── AOF always
     │                          │                         │                        │
  pure cache              periodic dumps           ≤1s of writes lost      ~no loss, much slower
  lose everything         lose minutes             the common default      fsync per write
  on restart              of writes
ConfigurationWorst-case loss on crashCost
NoneEverythingFastest; restart is empty
RDB (snapshot)Since the last snapshot — minutesFork + write; brief memory spike
AOF everysec≤ 1 second of writesModest; the usual choice
AOF alwaysEffectively nothingfsync on every write — dramatically slower

State the guarantee honestly: with the common everysec setting, a hard crash loses up to one second of acknowledged writes. That is fine for a cache, a rate limiter or a leaderboard; it is not fine for payment records. If losing a second of writes would be a business incident, Redis should not be the system of record — see Persistence for the full treatment.

Part 4 — The Protocol and the Round-Trip Problem

RESP (REdis Serialization Protocol) is deliberately simple — human-readable, prefix-length encoded, and parseable with a few lines of code:

client sends:                    server replies:

*3\r\n                           +OK\r\n              simple string
$3\r\n
SET\r\n                          $5\r\n               bulk string
$4\r\n                           hello\r\n
name\r\n
$5\r\n                           :42\r\n              integer
hello\r\n
                                 -ERR unknown\r\n     error

The protocol is not the bottleneck; the network is. Every command is a request and a response, so 1,000 sequential commands means 1,000 round trips:

1000 sequential GETs, 0.2 ms RTT   →  1000 × 0.2 ms = 200 ms
1000 pipelined GETs                →  ~1 round trip ≈ 0.2 ms + processing ≈ 2 ms

                                      100× faster, same commands, same server

This single fact reframes most Redis performance work: the question is rarely "which command is faster" and almost always "how do I make fewer round trips" — via pipelining, multi-key commands like MGET, or Lua scripts.

Part 5 — Keyspace, Databases and Naming

Redis has a flat keyspace. There are numbered databases (SELECT 0 … 15), but they are largely a legacy feature — they share one instance, one thread and one memory pool, and Redis Cluster supports only database 0.

# convention: colon-delimited hierarchy — Redis does not interpret it, but tools do
user:1000:profile
user:1000:sessions
order:2026:08:count
cache:product:5521

Part 6 — When Redis Is and Is Not the Right Tool

Good fitPoor fit
Cache in front of a slower storeSystem of record for financial data
Counters, rate limiters, quotasComplex ad-hoc queries and joins
Leaderboards and ranked dataDatasets far larger than RAM
Session storageLong-term analytical storage
Job queues and streamsAnything needing multi-key ACID across shards
Ephemeral state with a natural TTLFull-text search (use a search engine)

The hard constraint is memory. Your working set must fit in RAM, with headroom — Redis needs room for replication buffers, fork-on-save copy-on-write, and fragmentation. A common rule is to keep usage below 50–60% of the instance's memory if you snapshot, because forking can transiently double it.

❌ Treating Redis as a drop-in database because it persists to disk. The reasoning seems sound — AOF is enabled, writes are on disk, so the data is safe. But appendfsync everysec means up to a second of acknowledged writes vanish on a hard crash, and asynchronous replication means a failover can promote a replica that never received the last writes. Teams discover this during their first incident, when a client was told "OK" for an order that no longer exists.

✅ Decide what a lost second of writes costs, and design from that answer. For caches, counters, sessions and leaderboards it costs nothing — the data is either regenerable or approximate, and Redis is an excellent choice. For anything where a client's acknowledged write must survive, keep the system of record in a durable database and use Redis as a derived layer in front of it. That is not a limitation to work around; it is the trade Redis deliberately makes to be fast, and using it knowingly is the whole skill.

Interview Questions

Beginner: What is Redis and how does it differ from memcached?

Redis is an in-memory data-structure server. Keys map to typed values — strings, hashes, lists, sets, sorted sets, streams — and each type has its own atomic command set.

The core difference from memcached is that memcached stores opaque blobs. To change one field of a cached object you must fetch the whole thing, deserialise it, modify it, re-serialise it and write it back — two round trips and a race condition. Redis lets you operate on the value in place:

memcached:  GET user:42 → blob → parse → change → serialise → SET user:42
Redis:      HINCRBY user:42 visits 1          ← one atomic command
Redismemcached
Value typesRich (6+ structures)Opaque bytes
PersistenceOptional RDB/AOFNone
ReplicationBuilt inNone
ThreadingSingle-threaded executionMulti-threaded
Atomic operationsEvery command, plus LuaLimited (CAS, incr)

Where memcached still wins: it is multi-threaded, so on a single node it can use many cores for a pure get/set cache workload. If you genuinely need nothing but a memory cache and want to saturate a large machine, that is a real advantage.

In practice Redis is chosen because the data structures eliminate application code — rate limiting, leaderboards, queues and locks all become a few commands rather than a subsystem.

Beginner: Why is Redis fast, and what is the actual bottleneck?

Four reasons, in roughly descending order of importance:

ReasonEffect
Data in RAM~100 ns vs ~100 µs for SSD — 1000×
Purpose-built structuresO(1)/O(log n), no query planning or SQL parsing
Simple protocol (RESP)Cheap to parse
Single-threaded executionNo locks, no context switching, no contention

Single-threading being a speed feature surprises people. Because only one command runs at a time, there are no mutexes and no coordination overhead — and every command is atomic for free as a side effect.

The actual bottleneck is almost never Redis itself — it is network round trips:

one command ≈ a few microseconds of CPU inside Redis
one round trip ≈ 100–500 microseconds on the network

1000 sequential commands  → ~200 ms   (dominated by RTT)
1000 pipelined commands   → ~2 ms     (one round trip)

So the highest-leverage optimisation is reducing round trips, not micro-optimising commands: pipeline batches, use MGET/MSET, or move multi-step logic into a Lua script that executes server-side.

The second-order bottleneck is a slow command blocking the thread. Since execution is single-threaded, one KEYS * or a large ZRANGE stalls every other client — which is why O(n) commands on big collections are dangerous regardless of how fast Redis is in general.

Mid: Is Redis durable? What exactly do you lose in a crash?

Redis offers configurable durability, and the honest answer is "it depends, and by default you lose something".

ConfigurationLoss on hard crash
No persistenceEverything
RDB snapshotsEverything since the last snapshot — minutes
AOF appendfsync everysecUp to 1 second of writes
AOF appendfsync alwaysEssentially nothing — but far slower

The common production setting is everysec, which buys near-full durability at a small cost, while accepting a one-second window.

There is a second, less obvious loss channel: replication is asynchronous. A master acknowledges a write to the client before replicas have it. If the master fails and a replica is promoted, any writes not yet replicated are gone — even with AOF enabled on both:

client → master: SET k v      → +OK   (client believes it is saved)
master crashes before replicating
replica promoted → GET k       → (nil)

WAIT numreplicas timeout mitigates but does not solve this — it blocks until N replicas acknowledge, which reduces the window at the cost of latency, and still is not a consensus protocol.

So the design rule is: if losing a second of acknowledged writes would be a business incident, Redis must not be the system of record. Keep truth in a durable database and treat Redis as a fast derived layer. For caches, sessions, counters and leaderboards the trade is entirely acceptable — and it is what buys the performance.

Mid: Why is KEYS dangerous, and what should you use instead?

KEYS pattern scans the entire keyspace and, because Redis executes commands on a single thread, it blocks every other client for the whole scan.

KEYS user:*        on 10 million keys  →  ~1–2 seconds of TOTAL server blocking
                                          every other client waits

This is the classic production outage: a debugging command run against a large instance stalls the application tier, connections pile up, timeouts cascade, and the incident looks like a network problem.

SCAN is the safe replacement — it is cursor-based and returns a small batch per call, so the thread is released between iterations:

SCAN 0 MATCH user:* COUNT 100
  → 1) "17"                  ← cursor to pass to the next call
    2) 1) "user:1"
       2) "user:2"

# repeat until the returned cursor is "0"
PropertyKEYSSCAN
BlockingBlocks entirelyIncremental
ComplexityO(n) in one shotO(1) per call, O(n) total
GuaranteesExact snapshotKeys present throughout are returned at least once

SCAN's weaker guarantee is the trade: keys added or removed during the iteration may or may not appear, and a key can be returned more than once. Deduplicate on the client if it matters.

Type-specific variants exist too — HSCAN, SSCAN, ZSCAN — for iterating large hashes, sets and sorted sets without blocking on HGETALL or SMEMBERS, which have the same O(n) problem at the collection level.

Better still, avoid needing to scan. If you must enumerate a category of keys, maintain a set of them as you write: SADD users:all user:1000 turns an O(n) keyspace scan into an O(1) lookup.

Senior: When would you choose Redis, and when would you push back on it?

I would frame it around three questions: does the working set fit in RAM, is the access pattern a good match for the data structures, and what does data loss cost.

Strong fits:

Use caseWhy Redis specifically
Cache in front of a slower storeSub-millisecond reads, TTL built in
Rate limiting / quotasAtomic INCR + expiry, no races
LeaderboardsSorted sets give O(log n) rank queries directly
SessionsEphemeral by nature; TTL matches the domain
Queues and event streamsLists and Streams with consumer groups

Where I would push back:

1. As the system of record for anything financial or legal. The everysec window and asynchronous replication mean acknowledged writes can vanish. That is not a bug to configure around — it is the trade that buys the speed.

2. When the dataset exceeds RAM. Redis is not designed to spill to disk gracefully; you either shard across more memory or choose a disk-based store. And RAM is roughly 50–100× more expensive per byte than SSD, so "just add memory" has a real budget consequence.

3. When the query pattern is ad hoc. Redis has no query planner and no secondary indexes by default — you must design a key or a structure for every access pattern in advance. A requirement to "filter users by any combination of five attributes" is a relational or search problem, not a Redis one.

4. When multi-key transactions across shards are required. Redis Cluster does not support them; a transaction spanning slots simply fails.

The framing I would offer a team: Redis is exceptional as a derived layer — fast, disposable, rebuildable from a source of truth. The moment it becomes the only copy of important data, you have taken on a durability risk that the architecture was not designed to carry, and you should either accept that explicitly or move the truth elsewhere.

Senior: How would you size a Redis instance and decide on memory headroom?

I would work from four numbers: the raw data size, per-key overhead, the fork headroom persistence requires, and growth.

1. Raw data plus overhead. Redis charges real overhead per key — roughly 50–100 bytes for the key object, the dictionary entry and expiry metadata, before the value:

10M keys × (16-byte key + 100-byte value + ~90 bytes overhead)  ≈ 2.1 GB
                                                    └─ overhead is ~45% here

For small values the overhead can exceed the data, which is why MEMORY USAGE key on a representative sample is worth running rather than estimating from value sizes alone.

2. Fork headroom — the number people miss. RDB snapshots and AOF rewrites fork(), and the child shares pages copy-on-write. Pages modified during the save are duplicated, so a write-heavy instance can transiently approach 2× its normal footprint:

steady state    4 GB
during BGSAVE   4 GB + (pages written during the save)
worst case      ~8 GB on a heavily-written instance

The practical rule is to keep steady-state usage below ~50–60% of instance RAM if you snapshot, or accept the risk of the OOM killer terminating Redis mid-save.

3. Replication buffers. Each replica has an output buffer; a slow replica or a large full resync can grow it substantially. client-output-buffer-limit caps it, but the cap needs room.

4. Set maxmemory and a policy explicitly — without it Redis grows until the OS kills it:

maxmemory 6gb
maxmemory-policy allkeys-lru        # for a cache
# or: volatile-lru / volatile-ttl   # only evict keys that have a TTL
# or: noeviction                    # reject writes instead — for a data store

The policy choice encodes intent. allkeys-lru says "this is a cache, evicting is fine"; noeviction says "this data matters, fail the write instead". Choosing noeviction on an instance that will fill up simply moves the outage from silent data loss to loud write failures — which is usually the better failure mode, but must be a deliberate choice.

Finally I would monitor used_memory versus maxmemory, mem_fragmentation_ratio (above ~1.5 suggests fragmentation worth investigating), and evicted_keys — a rising eviction rate means the working set no longer fits and the cache hit rate is about to degrade.

→ provision an 8 GB instance, set maxmemory 6gb
5 (hard): Demonstrate atomicity and the read-modify-write race.
Solution

Run concurrent clients doing a counter increment two ways and compare the results:

import redis, threading

r = redis.Redis(decode_responses=True)
THREADS, PER_THREAD = 20, 500
EXPECTED = THREADS * PER_THREAD

# --- unsafe: read-modify-write ---
r.set("counter:rmw", 0)
def rmw():
    c = redis.Redis(decode_responses=True)
    for _ in range(PER_THREAD):
        v = int(c.get("counter:rmw"))     # READ
        c.set("counter:rmw", v + 1)       # WRITE — another client may have written between
ts = [threading.Thread(target=rmw) for _ in range(THREADS)]
[t.start() for t in ts]; [t.join() for t in ts]
rmw_result = int(r.get("counter:rmw"))

# --- safe: atomic INCR ---
r.set("counter:incr", 0)
def atomic():
    c = redis.Redis(decode_responses=True)
    for _ in range(PER_THREAD):
        c.incr("counter:incr")
ts = [threading.Thread(target=atomic) for _ in range(THREADS)]
[t.start() for t in ts]; [t.join() for t in ts]
incr_result = int(r.get("counter:incr"))

print(f"expected:          {EXPECTED}")
print(f"read-modify-write: {rmw_result}   (lost {EXPECTED - rmw_result})")
print(f"atomic INCR:       {incr_result}   (lost {EXPECTED - incr_result})")

expected:          10000
read-modify-write: 1247   (lost 8753)
atomic INCR:       10000   (lost 0)

87% of the increments were lost to the race. Every interleaved read-then-write pair silently discards one update — and the application sees no error.

Note that Redis itself was never the problem. Each individual GET and SET was atomic; the race is in the gap between them, which lives in the application. That is exactly what server-side commands eliminate.

Now the same pattern with a check-and-set requirement, which INCR cannot express — solved with WATCH/MULTI (optimistic locking):

def bounded_increment(c, key, limit):
    """Increment only while below a limit — needs a read, so INCR alone is insufficient."""
    while True:
        try:
            with c.pipeline() as pipe:
                pipe.watch(key)                     # abort the txn if key changes
                current = int(pipe.get(key) or 0)
                if current >= limit:
                    pipe.unwatch()
                    return False
                pipe.multi()
                pipe.incr(key)
                pipe.execute()                      # fails if key changed since WATCH
                return True
        except redis.WatchError:
            continue                                # someone else won; retry

r.set("bounded", 0)
def worker():
    c = redis.Redis(decode_responses=True)
    for _ in range(PER_THREAD):
        bounded_increment(c, "bounded", 100)
ts = [threading.Thread(target=worker) for _ in range(THREADS)]
[t.start() for t in ts]; [t.join() for t in ts]
print("bounded counter:", r.get("bounded"), "(limit was 100)")

bounded counter: 100 (limit was 100)

The limit held exactly under 20 concurrent clients — WATCH made the read-then-write pair effectively atomic by failing the transaction if anything changed in between.

The Lua alternative is faster because it is one round trip with no retry loop, and it is covered in Transactions & Lua:

local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if current < tonumber(ARGV[1]) then
  return redis.call('INCR', KEYS[1])
end
return -1
6 (hard): Decide whether Redis fits three scenarios, with evidence.
Solution

Apply the three questions — does it fit in RAM, does the access pattern match, what does loss cost?

Scenario A: session store for 5 million active users, ~2 KB per session, 30-minute TTL.

memory:   5M × (2 KB + ~90 B overhead) ≈ 10.4 GB steady state
          × 1.5 fork headroom          ≈ 15.6 GB → a 16–32 GB instance

access:   GET / SET by session id — perfect key-value fit
loss:     a lost session logs a user out. Annoying, not catastrophic.
TTL:      native — Redis expires them automatically, no cleanup job

Verdict: excellent fit. This is close to the canonical Redis use case — ephemeral data with a natural TTL and a pure key lookup pattern. I would use volatile-lru so eviction prefers keys with a TTL, and monitor evicted_keys to catch the working set outgrowing memory.

Scenario B: the ledger for a payments system, 50 GB, must never lose a write.

memory:   50 GB fits in a large instance — technically possible
access:   writes are appends; reads are by account — also fine structurally
loss:     appendfsync everysec loses ≤1s of ACKNOWLEDGED writes
          async replication can lose more on failover
          → a customer is told "payment recorded" for a payment that vanishes

Verdict: reject. The technical fit is irrelevant because the durability model does not meet the requirement. appendfsync always would help but costs an order of magnitude in throughput and still does not solve failover loss — Redis replication is asynchronous and is not a consensus protocol.

What I would propose instead: Postgres as the ledger of record, with Redis in front for balance reads and idempotency keys. The fast path stays fast, and the durable path stays durable.

Scenario C: a real-time leaderboard, 50 million players, updated continuously, needs rank queries.

memory:   a sorted set entry ≈ 60–100 B (member string + score + skiplist nodes)
          50M × ~90 B ≈ 4.5 GB — fits comfortably

access:   ZADD to update, ZREVRANK for a player's rank, ZREVRANGE for the top N
          → O(log n) rank query, which is exactly what sorted sets exist for
loss:     scores are derived from a durable game database and can be rebuilt

Verdict: excellent fit, and hard to do well elsewhere. A relational ORDER BY score LIMIT 10 OFFSET n over 50M rows is expensive and gets worse with offset; a sorted set answers it in microseconds.

ZADD leaderboard 4820 player:1000
ZREVRANK leaderboard player:1000        → (integer) 15  — O(log n)
ZREVRANGE leaderboard 0 9 WITHSCORES    → the top 10
ZCOUNT leaderboard 4000 5000            → how many in a score band

The pattern across all three: the technical questions (memory, access pattern) rule things in, but the durability question is what rules things out. Scenario B fails on durability alone despite fitting perfectly on every other axis — and recognising that is the difference between using Redis well and having an incident.

🎯 Key Takeaways

  • Redis is a data-structure server, not a blob cache — the value has a type, and operations run server-side on the data.
  • That design eliminates read-modify-write: INCR is one atomic round trip where GET-modify-SET is two round trips and a race.
  • Speed comes from RAM, purpose-built structures, a simple protocol, and single-threaded execution with no lock overhead.
  • Single-threading is a feature: it makes every command atomic for free, but one slow command blocks every client.
  • The real bottleneck is network round trips, not Redis — pipelining gave 27× on identical commands in the exercise.
  • Durability is a spectrum: no persistence, RDB snapshots, AOF everysec (≤1s loss, the common default), or AOF always.
  • Replication is asynchronous, so a failover can lose acknowledged writes even with AOF enabled — WAIT narrows the window but is not consensus.
  • If losing a second of acknowledged writes is a business incident, Redis must not be the system of record.
  • Never run KEYS in production — it blocked the server for 1.3 seconds on 1M keys; use SCAN.
  • The same O(n) hazard applies to LRANGE 0 -1, SMEMBERS and HGETALL on large collections.
  • Per-key overhead is real — roughly 68 bytes on top of a 13-byte payload in the measurement above.
  • Grouping fields into a small hash used about a third of the memory of one key per field, thanks to listpack encoding.
  • Size for fork headroom: snapshots copy-on-write, so keep steady-state usage near 50–60% of instance RAM.
  • Always set maxmemory and an eviction policy — the policy choice encodes whether this is a cache or a store.
  • Numbered databases are legacy: shared thread and memory, and unsupported in Redis Cluster. Use key prefixes.
  • Redis fits caches, counters, leaderboards, sessions and queues; it fits poorly for ad-hoc queries, datasets beyond RAM, and systems of record.
