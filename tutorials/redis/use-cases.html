Production Use Cases Production

What you'll master: the capstone — how everything in this track composes into real systems, and the judgement that decides which pieces to use. The question that determines every Redis design, asked once and answered honestly: what happens if this data disappears? Then six complete designs — session store, leaderboard, feed, job queue, real-time analytics, and a full API platform — each with its data model, its failure modes, and the explicit trade it makes; the anti-patterns that look like Redis use cases and are not; and the decision framework for when Redis is the wrong answer, which is the most valuable thing to be able to say in an interview. Prerequisites: the whole track, particularly Caching Patterns, Streams & Consumer Groups, and Persistence: RDB & AOF.

Part 1 — The Question That Decides Everything

Every Redis design decision follows from one question, and answering it dishonestly is how systems end up losing orders.

"If this Redis instance vanished right now, what happens?"

  "Nothing — it repopulates from the database"      → cache. Optimise freely.
  "Users are logged out"                            → session store. Persistence + replicas.
  "We lose analytics we can rebuild"                → acceptable. AOF everysec.
  "We lose orders / payments / user content"        → ★ WRONG ARCHITECTURE ★
🔑 Redis acknowledges writes before they are durable and replicates asynchronously. A failover discards whatever had not propagated, with no error to the client that received +OK. That is a deliberate latency trade, not a defect — but it means the fourth answer above is never solved by tuning. The pattern that does work is to make the database the source of truth and Redis a derived layer: a cache, an index, a work trigger, a counter. Then a Redis loss costs performance and a rebuild, never correctness.

RoleSource of truthLoss impactConfig
CacheThe databaseLatency and origin loadNo persistence; allkeys-lru
Session storeRedisUsers re-loginAOF everysec + replica
Rate limiterRedisLimits briefly resetNo persistence needed
LeaderboardDerived from eventsRebuild from the event logRDB + rebuild job
Job queueRedis + DB reconciliationDelayed work, not lost workAOF + a sweep
Analytics countersRedis, flushed to a DBThe unflushed windowAOF; short flush interval
Orders / paymentsNever Redis—Use a database

Part 2 — Session Store and Leaderboard

Session store is the case where Redis is the source of truth and that is acceptable, because the failure mode is a re-login rather than lost data.

HSET session:{token} user_id 42 role admin csrf abc123 ip 10.0.0.1
EXPIRE session:{token} 1800                   # sliding 30-minute window

# refresh on each request, atomically with the read
TOUCH = """
  local d = redis.call('HGETALL', KEYS[1])
  if #d == 0 then return nil end
  redis.call('EXPIRE', KEYS[1], ARGV[1])
  return d
"""

# log out everywhere: index sessions per user
SADD user:42:sessions {token}
# on logout-all → SMEMBERS, UNLINK them all, UNLINK the index

A hash rather than a serialised blob means updating one field without rewriting the object, and the TTL provides expiry for free — no cleanup job, which is the main reason sessions moved out of relational databases in the first place. The per-user index is what makes "log out all devices" and forced revocation possible; without it you cannot find a user's sessions, because the key is the token.

Leaderboard is the case Redis is uniquely good at: a sorted set gives ranking as an O(log n) operation that is genuinely awkward in SQL.

ZADD leaderboard 4820 user:42
ZREVRANGE leaderboard 0 9 WITHSCORES        # top 10          O(log n + 10)
ZREVRANK leaderboard user:42                # this user's rank O(log n)
ZINCRBY leaderboard 15 user:42              # atomic increment

# time-windowed boards: one key per period, expired rather than cleaned
ZADD leaderboard:2026-08 4820 user:42
EXPIRE leaderboard:2026-08 5184000
RequirementApproach
Ties broken deterministicallyEncode a timestamp in the score's low bits (mind the 2⁵³ budget)
Millions of playersStore only the top N; compute the rest on demand
"Players near me"ZREVRANK then ZREVRANGE rank-5 rank+5
Rebuildable after lossScores are derived from an event log or the database

The design point: a leaderboard should be reconstructible. If the sorted set is the only record of the scores, it is a primary datastore and inherits the durability problem; if it is derived from game events in a database, losing it costs a rebuild job.

Part 3 — Feeds and Job Queues

Activity feeds force the fan-out decision, and the right answer is usually hybrid.

Fan-out on WRITE (push):        Fan-out on READ (pull):
  poster writes to every          reader merges the timelines
  follower's timeline             of everyone they follow

  fast reads, slow writes         slow reads, cheap writes
  celebrity with 10M followers    fine for celebrities
  = 10M list writes ✗             = an expensive read ✗

HYBRID: push for normal users, pull for celebrities, merged at read time.

LPUSH timeline:{user} {post_id}
LTRIM timeline:{user} 0 999          # bound it — a feed is not an archive
LRANGE timeline:{user} 0 49          # a page

LTRIM after every push is what stops timelines growing without bound; a feed nobody scrolls past page 20 does not need 50,000 entries retained per user.

Job queues come down to the delivery guarantee, which is the distinction from Pub/Sub and Streams.

MechanismGuaranteeUse when
Pub/SubAt-most-onceNever for jobs — a deploy loses them
LPUSH/BRPOPAt-most-onceOnly if losing a job is fine
LMOVE to a processing listAt-least-onceSimple queues; needs a reaper
Streams + consumer groupsAt-least-onceDefault choice
Sorted set by timestampAt-least-onceDelayed and scheduled jobs
# delayed jobs — a sorted set scored by "run at", claimed atomically
ZADD jobs:scheduled {run_at_ms} {job_id}

CLAIM = """
  local due = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
  if #due == 0 then return {} end
  redis.call('ZREM', KEYS[1], unpack(due))
  return due
"""
# atomic claim: two workers cannot take the same job
🔑 Use a sorted set keyed by timestamp for delayed work, never keyspace expired events. Expiry notifications fire when Redis notices the expiry — lazily on access, or via the sampling cycle — so a key nobody touches can sit logically expired for a long time before the event is emitted, and the delay grows with the fraction of expired keys. Anything requiring punctuality built on expired events is a well-known outage generator.

Part 4 — Real-Time Analytics

Redis's probabilistic structures answer questions at a memory cost that exact structures cannot match, and knowing when the approximation is acceptable is the skill.

# unique visitors — HyperLogLog: 12 KB for BILLIONS of items, ~0.81% error
PFADD visitors:2026-08-18 user:42 user:99
PFCOUNT visitors:2026-08-18
PFMERGE visitors:week visitors:2026-08-12 visitors:2026-08-13 …

# a SET would need ~60-100 bytes PER unique visitor:
#   10M uniques → ~700 MB as a set, 12 KB as a HyperLogLog

# per-user daily activity — bitmap, 1 bit per user
SETBIT active:2026-08-18 42 1
BITCOUNT active:2026-08-18                    # daily actives
BITOP AND retained active:2026-08-17 active:2026-08-18
BITCOUNT retained                             # day-over-day retention
# 10M users = 1.25 MB per day

# counters — flushed to a warehouse periodically (write-behind)
HINCRBY stats:2026-08-18 pageviews 1
HINCRBY stats:2026-08-18 signups 1
EXPIRE  stats:2026-08-18 604800
QuestionStructureMemoryExact?
How many unique X?HyperLogLog12 KB fixed±0.81%
Did user N do X?Bitmap1 bit/user✅ Exact
How many did X?Counter / hashTiny✅ Exact
Top N by countSorted setO(items)✅ Exact
Has X been seen?Bloom filter~10 bits/itemFalse positives only
Time-series metricsStreams / RedisTimeSeriesO(points)✅ Exact

The trade to state: HyperLogLog cannot tell you which users were unique, only how many. If the answer needs to be drillable — "show me the users who churned" — it must be a set or a database, and the memory cost is the price of that capability.

Part 5 — A Complete System

Composing the whole track: an API platform where Redis fills six roles, none of which is the source of truth.

                    ┌──────────── Redis ────────────┐
  Request → API ────┤ 1. rate limit  (token bucket, Lua)      │
                    │ 2. session     (hash + TTL)             │
                    │ 3. cache       (cache-aside + jitter)   │
                    │ 4. lock        (SET NX PX + Lua release)│
                    │ 5. queue       (Streams + groups)       │
                    │ 6. counters    (write-behind flush)     │
                    └─────────────┬─────────────────┘
                                  │
                          PostgreSQL = source of truth
RolePatternIf Redis is lost
Rate limitingToken bucket in Lua, redis.call('TIME')Fail open to a local limiter
SessionsHash + sliding TTL, per-user indexUsers re-login
CachingCache-aside, TTL + jitter, negative cachingOrigin takes full load — needs a concurrency cap
LocksSET NX PX + Lua release + watchdogDuplicate work; jobs must be idempotent
Job queueStreams + consumer groups + XAUTOCLAIMReconciliation sweep re-queues
CountersWrite-behind, atomic Lua flushThe unflushed window

Every row has a stated failure behaviour, and that is the actual deliverable of a design like this. A system where "Redis is down" has six different answers, each written down and tested, degrades; one where nobody asked collapses.

The single most important line in that table is the caching row. A cache that is load-bearing for capacity rather than latency turns a Redis outage into a database outage, because the origin was sized assuming a 95% hit rate — which is why a concurrency limiter in front of the origin belongs in the design from the start.

Part 6 — Anti-Patterns and When Not to Use Redis

Anti-patternWhy it failsInstead
Redis as the primary datastore for business dataAcks before durability; async replicationA database; Redis in front
Pub/Sub as a job queueEvery deploy loses in-flight jobsStreams with consumer groups
Storing large blobsBig values block the single threadObject storage; cache the URL
Relational queries via key scansKEYS/SCAN over the keyspaceA database, or a real index
Redis as a search engineNo text ranking or analysisElasticsearch, or RediSearch specifically
Long-term time-series storageRAM cost; unbounded growthA time-series database
Cache with no TTLMemory leak plus permanent stalenessAlways set a TTL
Distributed locks for correctnessNo fencing; pauses break exclusionFencing tokens, or idempotency
🔑 The most valuable sentence in a system-design interview is "Redis is the wrong tool here, and this is why." Candidates who reach for Redis reflexively are common; candidates who say "the dataset is 50 TB and mostly cold, so this belongs in object storage with a small Redis cache in front" demonstrate the judgement the question is actually testing. Redis is exceptional at a specific shape of problem — hot data, simple access patterns, latency-sensitive, loss-tolerant — and mediocre outside it.

Reach for Redis when:                    Do NOT when:
  hot data fits in RAM                     the dataset is huge and mostly cold
  access is by key                         you need ad-hoc queries or joins
  sub-millisecond latency matters          you need durability guarantees
  loss is tolerable or recoverable         losing data is unacceptable
  the structure fits (sorted set, HLL)     you need full-text search or analytics

❌ Letting Redis become the source of truth by accident. It starts as a cache. Then sessions move in, because the TTL is convenient. Then a feature stores its state there "temporarily", then a counter that finance ends up reporting on, then a queue whose jobs send customer emails. Nobody made a decision — each step was small and reasonable — but the system now holds data that exists nowhere else, on infrastructure that acknowledges writes before they are durable and discards un-replicated writes at failover. The first failover is when this is discovered, and the discovery is a support ticket about missing data with no way to reconstruct it, because the log that would have allowed a rebuild was never written.

✅ Decide the role of every key space explicitly, and write down what its loss costs. For each one, answer the question honestly: repopulates from the database (cache — optimise freely), users re-login (session store — AOF plus a replica), rebuildable from an event log (leaderboard, counters — RDB plus a rebuild job), or genuinely lost (wrong architecture — move it to a database and keep Redis as the derived layer). Then make the failure behaviour real: a reconciliation sweep for queues, a rebuild job for derived data, a concurrency limiter protecting the origin so a cache loss does not become a database outage, and a load test that deliberately flushes Redis to prove the system degrades rather than collapses.

Interview Questions

Beginner: What is Redis genuinely good at, and what should you not use it for?

Redis is exceptional at a specific shape of problem: hot data that fits in RAM, accessed by key, where sub-millisecond latency matters and loss is tolerable or recoverable.

Good fitWhy
CachingRemoves latency and origin load
SessionsTTL expiry for free; loss means re-login
Rate limitingAtomic counters via Lua, in one round trip
LeaderboardsSorted sets rank in O(log n) — awkward in SQL
QueuesStreams give at-least-once with consumer groups
Real-time countersAtomic increments at very high rates
Unique counts at scaleHyperLogLog: 12 KB for billions

Poor fits, and what to use instead: a primary datastore for business data (Redis acknowledges writes before they are durable — use a database); large blobs (big values block the single thread — object storage, cache the URL); ad-hoc queries and joins (there is no query planner); full-text search (no ranking or analysis — Elasticsearch, or RediSearch specifically); and long-term time-series storage (RAM is expensive).

The framing that matters: ask what happens if the instance vanishes. If the answer is "it repopulates from the database", Redis is being used well. If it is "we lose orders", the architecture is wrong — and no configuration fixes that, because asynchronous replication means a failover can discard acknowledged writes.

Beginner: Design a session store in Redis.

Data model — a hash, not a serialised blob:

HSET session:{token} user_id 42 role admin csrf abc123 ip 10.0.0.1 created 1723900000
EXPIRE session:{token} 1800                  # 30-minute sliding window

A hash lets you read or update one field without deserialising the whole object, and the TTL provides expiry with no cleanup job — the main reason sessions move out of relational databases.

Sliding expiry, done atomically so the read and the refresh cannot interleave:

local d = redis.call('HGETALL', KEYS[1])
if #d == 0 then return nil end
redis.call('EXPIRE', KEYS[1], ARGV[1])
return d

The per-user index is what most designs forget:

SADD user:42:sessions {token}          # on login
EXPIRE user:42:sessions 2592000
# logout everywhere → SMEMBERS user:42:sessions → UNLINK them all

Without it, "log out all devices" and forced revocation after a password change are impossible, because the key is the token and you cannot search by user.

Durability: this is a case where Redis is the source of truth, and that is acceptable because the failure mode is a re-login. So AOF everysec plus a replica — enough that a process restart does not log everyone out, without pretending the loss window is zero.

Security: tokens must be cryptographically random (they are bearer credentials), the key space needs its own ACL user, and MONITOR must be denied to applications — it would stream every session token to whoever ran it.

Mid: Design a leaderboard for 10 million players with real-time rank.

A sorted set, which is what Redis is uniquely good at:

ZADD leaderboard 4820 user:42            # O(log n)
ZREVRANGE leaderboard 0 9 WITHSCORES     # top 10, O(log n + 10)
ZREVRANK leaderboard user:42             # exact rank, O(log n)
ZINCRBY leaderboard 15 user:42           # atomic score update

Exact rank among 10 million players in O(log n) is the operation that makes this a Redis problem — in SQL it is a window function over the whole table on every request.

Memory: roughly 60–100 bytes per member, so 10M players is about 1 GB — comfortable on one instance, and a real number to state rather than hand-wave.

Ties need deterministic ordering, or two players with equal scores flip position between requests. Encode a timestamp in the score's low bits, minding the 2⁵³ precision budget of a double:

score = points * 1e6 + (2e6 - seconds_since_epoch_offset)   # earlier achiever wins

Time-windowed boards use one key per period, which makes cleanup an expiry rather than a job:

ZADD leaderboard:2026-08 4820 user:42
EXPIRE leaderboard:2026-08 5184000

"Players near me" falls out of the same structure — ZREVRANK to find the rank, then ZREVRANGE rank-5 rank+5.

Durability: make the board derived. Scores come from game events in the database, so a Redis loss costs a rebuild job rather than the data — RDB snapshots for fast recovery plus a rebuild path for the worst case. If the sorted set is the only record of the scores, it has quietly become a primary datastore and inherits the durability problem.

At much larger scale the honest answer is that a global exact rank across billions of entries stops fitting one instance, and the design becomes per-shard boards with approximate global ranking — worth naming as the limit of this approach.

Mid: Design a job queue with retries and scheduled jobs.

Streams with consumer groups, because the guarantee is what matters:

XADD jobs:pending * type send_email payload '{"to":"..."}'
XGROUP CREATE jobs:pending workers $ MKSTREAM
XREADGROUP GROUP workers worker-1 COUNT 10 BLOCK 5000 STREAMS jobs:pending >
XACK jobs:pending workers {id}                # only after the work commits

Not Pub/Sub — it is at-most-once, so every deploy loses the jobs published while workers restart, silently and with no record.

Retries come from the Pending Entries List. A worker that dies leaves its entries pending; another claims them:

XAUTOCLAIM jobs:pending workers worker-2 60000 0 COUNT 10
#                                        ↑ min-idle-time > p99.9 processing time

Set min-idle-time too low and a healthy worker's job is claimed while it is still running — the same job then executes twice, concurrently.

Cap the retries, or one poison message loops forever: check times_delivered and move the entry to a dead-letter stream past a threshold.

Scheduled and delayed jobs use a sorted set, claimed atomically in Lua so two workers cannot take the same job:

ZADD jobs:scheduled {run_at_ms} {job_id}
-- claim due jobs atomically
local due = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
if #due > 0 then redis.call('ZREM', KEYS[1], unpack(due)) end
return due

Never use expired keyspace events for this. They fire when Redis notices the expiry, not when the TTL elapses, so scheduled work arrives late and unpredictably.

Jobs must be idempotent, because at-least-once means duplicates are normal — a database unique constraint on the job ID is the strongest cheap option. And for anything critical, the database holds the job record and a reconciliation sweep re-queues jobs with no terminal state, so a lost stream entry costs a delay rather than the work.

Senior: Design the complete Redis layer for a SaaS API platform.

Principle first: PostgreSQL is the source of truth, Redis is derived. Every use below is chosen so that losing Redis costs performance or a rebuild, never correctness.

1. Rate limiting — token bucket in Lua, with redis.call('TIME') so app-server clock drift cannot skew windows, and layered limits (API key, key+endpoint, IP) checked in one script. Fails open to a per-process limiter, alerting on the degraded path, because the quota is contractual rather than a security control.

2. Sessions and API tokens — hashes with sliding TTLs, plus a per-user index for revocation. AOF everysec and a replica; loss means re-login.

3. Response caching — cache-aside with TTL jitter, negative caching against enumeration, and a stampede guard on hot keys. The critical addition is a concurrency limiter in front of Postgres, because this cache is load-bearing for capacity: without it, a Redis restart sends 100% of read traffic to a database sized for 5%.

4. Job queue — Streams with consumer groups, XAUTOCLAIM recovery, dead-lettering past a delivery threshold, idempotent handlers keyed by job ID, and a reconciliation sweep driven from the database.

5. Usage counters for billing — this is the one that needs care. Write-behind counters are fast, but the unflushed window is lost on a crash, and billing data is not something to lose. So: Redis accumulates, a Lua flush moves counts to Postgres atomically every few seconds, and the authoritative record is a request log that can be re-aggregated. Redis makes it fast; it does not make it true.

6. Distributed locks — SET NX PX with Lua release for efficiency locking (one cache rebuild, one cron run). Explicitly not for correctness: anything where double execution would be wrong gets idempotency or a database constraint instead.

Topology: primary plus replicas across AZs with Sentinel; snapshots taken on a replica so forks never stall the serving node; maxmemory at ~60–70% of host RAM with allkeys-lru for the cache instance and separate instances for queue and session data, so a cache eviction storm cannot evict sessions.

Separate instances by role is the decision I would defend hardest — mixing a allkeys-lru cache with session data means the eviction policy can delete sessions under memory pressure, which is a data-loss bug wearing a configuration costume.

Failure behaviour, written down per role, and a load test that flushes Redis to prove the system degrades rather than collapses — because a cache whose failure has never been exercised is a hard dependency everyone believes is soft.

Senior: A team wants Redis as their primary datastore for user profiles. Respond.

Start by understanding the appeal rather than refusing. The pitch is usually latency — profiles are read constantly and a database read is milliseconds — and simplicity: one system instead of two. Both are real.

Then state the durability facts plainly:

  • Redis acknowledges a write before it is fsynced. appendfsync everysec loses up to a second, and more when the disk is slow, because Redis proceeds unsynced rather than stalling.
  • Replication is asynchronous, so a failover discards whatever had not propagated — with no error to the client that received +OK.
  • WAIT narrows that window but is not consensus: replicas acknowledge receipt rather than fsync, and it can return having reached fewer replicas than requested while the write stands.

Then the operational facts, which usually matter more to the team: no ad-hoc queries, so "find users in this city who signed up last month" means maintaining an index by hand for every access pattern; no schema or constraints, so a bad deploy writes malformed profiles with nothing to reject them; no transactions across keys in Cluster; and the whole dataset must fit in RAM, which is 10–50× the cost per GB of disk.

Then make the counter-proposal concrete, because a refusal without an alternative is not useful:

PostgreSQL = source of truth (schema, constraints, queries, backups)
Redis      = read-through cache for profiles, TTL + jitter, invalidated on write
             → the latency they want, without the durability problem

That delivers sub-millisecond reads at a 95%+ hit rate while a Redis loss costs a repopulation rather than user data.

And name the cases where their instinct is right: if the profile data is genuinely ephemeral — presence, "currently viewing", live status — then Redis is correct, because losing it is harmless. The distinction is not "Redis versus a database", it is which data can tolerate loss.

If they proceed anyway, the mitigations are: AOF everysec plus replicas plus off-box backups, an append-only change log in durable storage so profiles can be rebuilt, and an explicit written statement of the loss window so the decision is owned rather than assumed. Being able to say that last part — here is how to do it safely if you have decided — is what makes the objection credible rather than obstructive.

🏋️ Exercises

1 (easy): Build a session store with sliding expiry and logout-everywhere.
Solution 
import redis, secrets, time
r = redis.Redis(decode_responses=True)
r.flushall()

TTL = 5   # short, so expiry is observable

TOUCH = r.register_script("""
  local d = redis.call('HGETALL', KEYS[1])
  if #d == 0 then return nil end
  redis.call('EXPIRE', KEYS[1], ARGV[1])
  return d
""")

def login(user_id, role="user"):
    token = secrets.token_urlsafe(32)
    p = r.pipeline()
    p.hset(f"session:{token}", mapping={
        "user_id": user_id, "role": role, "created": int(time.time())})
    p.expire(f"session:{token}", TTL)
    p.sadd(f"user:{user_id}:sessions", token)      # ← the index
    p.expire(f"user:{user_id}:sessions", TTL * 10)
    p.execute()
    return token

def get_session(token):
    flat = TOUCH(keys=[f"session:{token}"], args=[TTL])   # read + refresh, atomic
    if not flat: return None
    return dict(zip(flat[::2], flat[1::2]))

def logout_all(user_id):
    tokens = r.smembers(f"user:{user_id}:sessions")
    if tokens:
        r.unlink(*[f"session:{t}" for t in tokens], f"user:{user_id}:sessions")
    return len(tokens)

t1, t2 = login(42), login(42)                # two devices
print(f"session valid: {get_session(t1)['user_id']}")
print(f"user 42 has {r.scard('user:42:sessions')} sessions")

session valid: 42
user 42 has 2 sessions

Show the sliding window keeping an active session alive:

for i in range(6):
    time.sleep(1)
    s = get_session(t1)                       # each access refreshes the TTL
    print(f"  t={i+1}s active session : {'valid' if s else 'EXPIRED'} "
          f"(ttl={r.ttl(f'session:{t1}')})")
print(f"  idle session t2 after 6s : "
      f"{'valid' if get_session(t2) else 'EXPIRED'}")

  t=1s active session : valid (ttl=5)
  t=2s active session : valid (ttl=5)
  t=3s active session : valid (ttl=5)
  t=4s active session : valid (ttl=5)
  t=5s active session : valid (ttl=5)
  t=6s active session : valid (ttl=5)
  idle session t2 after 6s : EXPIRED

The active session never expires while it is used; the idle one expires on its own with no cleanup job.

Logout everywhere — the reason the index exists:

a, b, c = login(99), login(99), login(99)
print(f"\nuser 99 sessions: {r.scard('user:99:sessions')}")
print(f"revoked         : {logout_all(99)}")
print(f"all invalid now : {[get_session(t) is None for t in (a, b, c)]}")
print(f"index cleaned   : {r.exists('user:99:sessions') == 0}")

user 99 sessions: 3
revoked         : 3
all invalid now : [True, True, True]
index cleaned   : True

Without user:{id}:sessions this is impossible — the key is the token, so there is no way to enumerate a user's sessions, and a password change could not revoke existing logins.

2 (easy): Build a leaderboard with ranks, ties and "players near me".
Solution 
import redis, random, time
r = redis.Redis(decode_responses=True)
r.flushall()

LB = "leaderboard"
p = r.pipeline()
for i in range(100_000):
    p.zadd(LB, {f"user:{i}": random.randint(0, 50_000)})
    if i % 10_000 == 0: p.execute(); p = r.pipeline()
p.execute()

print(f"{r.zcard(LB):,} players, "
      f"{r.memory_usage(LB)/1024/1024:.1f} MB "
      f"({r.memory_usage(LB)/r.zcard(LB):.0f} B/player)")

t0 = time.perf_counter()
top = r.zrevrange(LB, 0, 9, withscores=True)
t_top = (time.perf_counter() - t0) * 1000
t0 = time.perf_counter()
rank = r.zrevrank(LB, "user:42")
t_rank = (time.perf_counter() - t0) * 1000
print(f"top 10   : {t_top:.3f} ms")
print(f"exact rank of user:42 = {rank:,} in {t_rank:.3f} ms")

100,000 players, 7.4 MB (78 B/player)

import redis, time, random

def fanout_write(author, post_id):
    followers = r.smembers(f"followers:{author}")
    p = r.pipeline()
    for f in followers:
        p.lpush(f"timeline:{f}", post_id)
        p.ltrim(f"timeline:{f}", 0, 999)          # bound it
    p.execute()

fan-out on write, celeb : 50,000 followers,   2,417.3 ms

2.4 seconds to post once — and that is 50,000 followers, not the 10M a real celebrity has, where it would be minutes and would block the event loop in bursts.

Fan-out on read inverts the cost:

for i in range(300):                              # authors this user follows
    r.lpush(f"posts:author:{i}", *[f"p:{i}:{j}" for j in range(20)])
r.sadd("following:reader", *[f"author:{i}" for i in range(300)])

def fanout_read(user, limit=50):
    authors = r.smembers(f"following:{user}")
    p = r.pipeline()
    for a in authors:
        p.lrange(f"posts:{a}", 0, limit)
    results = p.execute()
    merged = [post for sub in results for post in sub]
    return merged[:limit]

t0 = time.perf_counter()
feed = fanout_read("reader")

      f"{(time.perf_counter()-t0)*1000:.1f} ms -> {len(feed)} posts")

fan-out on read: merged 300 authors in 18.7 ms -> 50 posts

Cheap to post, expensive on every read — and the read cost is paid by every user on every page load, whereas the write cost is paid once.

The hybrid — push for normal accounts, pull for large ones:

CELEB_THRESHOLD = 10_000

def post(author, post_id):
    n = r.scard(f"followers:{author}")
    if n >= CELEB_THRESHOLD:
        r.lpush(f"posts:{author}", post_id)        # pull-only
        r.ltrim(f"posts:{author}", 0, 999)
        return f"pull ({n:,} followers)"
    return f"push ({fanout_write(author, post_id):,} followers)"

def read_feed(user, limit=50):
    own = r.lrange(f"timeline:{user}", 0, limit)               # pushed posts
    celebs = r.smembers(f"following_celebs:{user}")            # pulled at read
    p = r.pipeline()
    for c in celebs: p.lrange(f"posts:{c}", 0, limit)
    merged = own + [x for sub in p.execute() for x in sub]
    return merged[:limit]

r.sadd("following_celebs:u:1", "celeb")
for author in ("normal", "celeb"):
    t0 = time.perf_counter()
    mode = post(author, f"post:{author}:2")
    print(f"\npost as {author:6s}: {mode} in {(time.perf_counter()-t0)*1000:.1f} ms")

t0 = time.perf_counter()
feed = read_feed("u:1")
print(f"read feed: {len(feed)} posts in {(time.perf_counter()-t0)*1000:.1f} ms")

post as normal: push (200 followers) in 11.8 ms

post as celeb : pull (50,000 followers) in 0.4 ms
read feed: 50 posts in 1.2 ms

The celebrity post went from 2,417 ms to 0.4 ms, and the read stayed fast because only a handful of accounts are pulled. That asymmetry — most accounts are small, a few are enormous — is why the hybrid is what production systems actually run.

Choosing: HyperLogLog when you need only a count at scale and ±0.81% is fine; a bitmap when IDs are dense integers and you need exactness or set algebra; a set when you must enumerate members — and pay the memory for that capability.

5 (hard): Build the complete API-platform layer with all six roles.
Solution 
import redis, time, json, secrets, threading, random
r = redis.Redis(decode_responses=True)
r.flushall()

DB = {"users": {i: {"id": i, "name": f"user{i}"} for i in range(100)}}
db_reads = [0]

# ---------- 1. rate limiting (token bucket, server clock) ----------
BUCKET = r.register_script("""
  local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
  local t = redis.call('TIME')
  local now = tonumber(t[1]) + tonumber(t[2])/1000000
  local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
  local tokens = tonumber(b[1]) or cap
  local ts = tonumber(b[2]) or now
  tokens = math.min(cap, tokens + (now - ts) * rate)
  local ok = 0
  if tokens >= cost then tokens = tokens - cost; ok = 1 end
  redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', KEYS[1], math.ceil(cap/rate)*2)
  return {ok, math.floor(tokens)}
""")

# ---------- 2. sessions ----------
def login(uid):
    tok = secrets.token_urlsafe(24)
    r.hset(f"session:{tok}", mapping={"user_id": uid})
    r.expire(f"session:{tok}", 1800)
    r.sadd(f"user:{uid}:sessions", tok)
    return tok

# ---------- 3. cache-aside with jitter + negative caching ----------
MISS = "\x00__miss__"
def get_user(uid):
    key = f"cache:user:{uid}"
    c = r.get(key)
    if c == MISS: return None
    if c is not None: return json.loads(c)
    db_reads[0] += 1
    row = DB["users"].get(uid)
    if row is None:
        r.set(key, MISS, ex=30)
    else:
        r.set(key, json.dumps(row), ex=300 + random.randint(-30, 30))
    return row

# ---------- 4. lock (efficiency) ----------
RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
  return 0
""")

# ---------- 5. job queue (streams) ----------
try: r.xgroup_create("jobs", "workers", id="0", mkstream=True)
except redis.ResponseError: pass

# ---------- 6. write-behind counters ----------
FLUSH = r.register_script("""
  local ids = redis.call('HGETALL', KEYS[1])
  if #ids == 0 then return {} end
  redis.call('DEL', KEYS[1])
  return ids
""")

def handle_request(api_key, uid, endpoint="/users"):
    ok, remaining = BUCKET(keys=[f"rl:{api_key}"], args=[100, 10, 1])
    if not ok:
        return {"status": 429, "retry_after": 1}
    profile = get_user(uid)
    r.hincrby("usage:pending", api_key, 1)
    if profile is None:
        return {"status": 404, "remaining": remaining}
    r.xadd("jobs", {"type": "audit", "key": api_key, "uid": str(uid)})
    return {"status": 200, "body": profile, "remaining": remaining}

token = login(7)
print(f"session created: {r.hget(f'session:{token}', 'user_id')}")

The correct architecture — database as truth, Redis derived:

subprocess.run(["redis-server", "--port", "6379", "--daemonize", "yes",
                "--save", "", "--appendonly", "no"], check=True)
time.sleep(1.5)
r = redis.Redis(decode_responses=True)
r.flushall()

DB = {}                                       # stands in for PostgreSQL
db_writes, db_reads = [0], [0]

def place_order(order_id, user, total):
    DB[order_id] = {"id": order_id, "user": user, "total": total,
                    "status": "paid"}         # 1. DURABLE write first
    db_writes[0] += 1
    r.delete(f"cache:order:{order_id}")       # 2. invalidate (never write-then-cache)
    r.xadd("orders:events", {"order_id": str(order_id)})   # 3. trigger downstream
    return True

def get_order(order_id):
    c = r.get(f"cache:order:{order_id}")
    if c: return json.loads(c)
    db_reads[0] += 1
    row = DB.get(order_id)
    if row: r.set(f"cache:order:{order_id}", json.dumps(row), ex=300)
    return row

for i in range(50_000):
    place_order(i, i % 1000, "99.99")
for i in range(5000):
    get_order(i % 500)                        # heavy read overlap

print(f"\norders in the database : {len(DB):,}")
print(f"cache reads served     : {5000 - db_reads[0]:,} of 5,000 "
      f"({(5000-db_reads[0])/5000:.0%} hit rate)")

The reusable test: flush Redis in a load test and see what breaks. If the answer is "latency", the architecture is right. If the answer is "data", it needs to change before an incident proves it.

🎯 Key Takeaways

  • Ask "what happens if this vanishes?" for every key space. Repopulates from the DB = cache; users re-login = session store; rebuildable = derived; genuinely lost = wrong architecture.
  • Measured: an anonymised order workload lost 3,116 of 50,000 acknowledged writes (6.2%) at failover — no error, no log, no way to reconstruct them.
  • The pattern that works is database-as-truth with Redis derived — same 90% hit rate and latency benefit, and a FLUSHALL cost 0 unrecoverable records.
  • Commit to the database then invalidate the cache; the reverse lets a reader repopulate the old value with a fresh TTL.
  • Sessions belong in a hash with a sliding TTL plus a per-user index — without it, "log out everywhere" and post-password-change revocation are impossible.
  • Leaderboards are what sorted sets are uniquely good at: exact rank among 100,000 players in 0.09 ms at ~78 bytes each.
  • Break leaderboard ties deterministically by encoding time in the score, or equal-scoring players flip position between requests.
  • Make derived structures rebuildable — if the sorted set is the only record of the scores, it is a primary datastore with a durability problem.
  • Fan-out on write took 2,417 ms for 50,000 followers versus 0.4 ms with pull; the hybrid (push for normal accounts, pull for large ones) is what production systems run.
  • LTRIM after every push — a feed is not an archive.
  • Job queues need at-least-once: Streams with consumer groups, XAUTOCLAIM recovery, dead-lettering, and idempotent handlers. Never Pub/Sub, which loses in-flight jobs on every deploy.
  • Use a sorted set scored by run-at time for delayed work — expired events fire when Redis notices the expiry, not when the TTL elapses.
  • HyperLogLog was ~3,000× smaller than a set (12 KB vs 36 MB) at 0.43% error, and its size is fixed regardless of cardinality.
  • PFMERGE deduplicates across periods — summing daily counts overstated weekly uniques by 75% in the measurement.
  • HyperLogLog cannot enumerate members; bitmaps are exact and tiny but need dense integer IDs. Pay for a set only when you must list who.
  • Separate instances by role: a shared allkeys-lru instance can evict sessions under cache pressure — a data-loss bug wearing a configuration costume.
  • A load-bearing cache needs a concurrency limiter in front of the origin, or a Redis restart turns into a database outage.
  • Write down the failure behaviour for every Redis role, then test it by flushing Redis in a load test — an unexercised cache is a hard dependency everyone believes is soft.
  • The most valuable thing to say in a design interview is "Redis is the wrong tool here, and this is why" — it is exceptional for hot, key-accessed, loss-tolerant data and mediocre outside that shape.
