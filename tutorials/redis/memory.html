Memory & Eviction Production

What you'll master: where Redis memory actually goes — and why a 10-byte value can cost 100 bytes, which is the number that decides whether your dataset fits; the encoding thresholds that make a hash 10× smaller, and the exact configuration values that trigger the cliff when you cross them; the eight eviction policies, the two that are genuinely dangerous defaults, and why volatile-lru with TTL-less keys produces OOM errors while the eviction policy looks correctly configured; approximated LRU and LFU, including when LFU is measurably better and why it is not the default; fragmentation, the difference between used_memory and used_memory_rss, and active defragmentation; and how to find what is actually consuming memory rather than guessing. Prerequisites: Hashes, Lists & Sets, Persistence: RDB & AOF.

Part 1 — Where the Memory Actually Goes

The most common sizing mistake is estimating from payload size. A key holding "v" does not cost one byte; it costs roughly a hundred.

SET user:1000000 "v"      # 16-byte key, 1-byte value

Actual cost, roughly:
  dictEntry (hash table slot + pointers)     ~56 bytes
  robj (type, encoding, refcount, ptr)       ~16 bytes
  SDS header + key string                    ~24 bytes
  SDS header + value string                  ~16 bytes
  jemalloc size-class rounding               ~ 8 bytes
  ────────────────────────────────────────────────────
  ≈ 100+ bytes for 17 bytes of data
🔑 Per-key overhead is roughly 50–100 bytes regardless of value size, so key count matters more than payload for small values. Ten million tiny keys cost ~1 GB before any data. This is why the single most effective memory optimisation is usually structural — collapsing many small keys into one hash — rather than shrinking values.

Measure rather than estimate, because the encoding rules in Part 2 change the answer by an order of magnitude:

MEMORY USAGE user:1000            → 104        # bytes for this key, incl. overhead
MEMORY DOCTOR                     → diagnostic advice
INFO memory
  used_memory:1073741824          ← what Redis thinks it uses
  used_memory_rss:1288490188      ← what the OS has given the process
  used_memory_peak:1500000000     ← ★ the high-water mark, often the real sizing input
  used_memory_dataset:900000000   ← data, excluding overhead
  mem_fragmentation_ratio:1.20    ← rss / used_memory
  maxmemory:2147483648
  maxmemory_policy:allkeys-lru
ConsumerTypical shareNotes
DatasetMost of itWhat you think of as "the data"
Per-key overheadLarge with many small keys~50–100 bytes each
Client output buffersSpikySlow consumers, Pub/Sub, big replies
Replication backlogFixedExactly repl-backlog-size
AOF bufferSpikyGrows during rewrites
Copy-on-write during savesUp to 2×See Persistence
Fragmentation10–50%Allocator overhead; not reclaimable by deleting keys

maxmemory only counts the dataset and some buffers, not copy-on-write pages and not fragmentation. Setting it to the host's RAM guarantees an OOM kill; a common starting point is around 60–70% of host memory when persistence is enabled, because a fork can double the footprint.

Part 2 — Encodings and the Memory Cliff

Redis stores small collections in compact, cache-friendly representations and switches to the general structure when they grow. The switch is a cliff, not a slope.

OBJECT ENCODING myhash     → listpack       (small: compact array)
                           → hashtable      (large: dict, ~10× the memory)

hash-max-listpack-entries 128      # switch above this many fields
hash-max-listpack-value   64       # ...or any value longer than this
list-max-listpack-size    128
set-max-intset-entries    512      # all-integer sets
set-max-listpack-entries  128
zset-max-listpack-entries 128
zset-max-listpack-value   64
🔑 Crossing a threshold is one-way. A hash that reaches 129 fields converts to a hashtable and stays a hashtable even if you delete fields back down to 10 — the conversion is never reversed while the key lives. So a temporary spike permanently multiplies that key's memory, and the only way back is to delete and rebuild the key.

The practical consequence is the "many small hashes" pattern, which is the single biggest memory win available in most Redis deployments:

❌ 1,000,000 separate keys              ~100 bytes overhead EACH  →  ~100 MB overhead
   SET user:1:name "alice"
   SET user:1:email "a@b.c"

✅ 10,000 hashes of 100 fields each     one key's overhead per 100 fields
   HSET user:bucket:0 1:name "alice" 1:email "a@b.c" …
                                        →  ~10× less total memory

Raising the thresholds trades CPU for memory: listpack operations are O(n) scans rather than O(1) lookups, so a 1,000-entry listpack is compact and slow. Values in the low hundreds are usually the right balance, and raising hash-max-listpack-entries to thousands reintroduces the latency problems covered in The Single-Threaded Model.

Part 3 — The Eight Eviction Policies

When memory reaches maxmemory, the policy decides what happens. Two of the eight are dangerous as defaults and one is the default.

PolicyEvictsUse when
noevictionNothing — writes fail with OOMDefault. Datastore where losing keys is wrong
allkeys-lruLeast recently used, any keyPure cache — the usual right answer
allkeys-lfuLeast frequently used, any keyCache with a stable hot set
allkeys-randomRandom keyUniform access; cheapest
volatile-lruLRU among keys with a TTLMixed cache + persistent data
volatile-lfuLFU among keys with a TTLSame, frequency-based
volatile-randomRandom key with a TTLRarely
volatile-ttlShortest remaining TTL firstWhen TTL encodes priority
🔑 The volatile-* policies only consider keys that have a TTL — and if none do, Redis evicts nothing and starts returning OOM errors. This is the trap: the configuration looks correct, eviction is "enabled", evicted_keys sits at 0, and writes fail. A single code path that writes without an expiry is enough to fill the instance. For a pure cache, use allkeys-lru, where every key is a candidate and no code path can defeat the policy.

noeviction is the default, which surprises people using Redis as a cache: the instance fills up and every write fails with OOM command not allowed when used memory > 'maxmemory' while reads keep working. That is correct behaviour for a datastore and wrong for a cache, so the policy is a decision that must be made deliberately.

CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lru

# verify it is actually doing something
INFO stats | grep evicted_keys      # should be non-zero once maxmemory binds

Part 4 — Approximated LRU, and When LFU Wins

Redis does not maintain a true LRU list — that would need a doubly-linked list touched on every access, at significant memory and CPU cost. Instead it samples.

maxmemory-samples 5        # sample N keys, evict the best candidate among them

5  → approximate, cheap (default)
10 → close to true LRU, slightly more CPU
3  → noticeably worse choices

Each object stores a 24-bit timestamp (LRU) or an 8-bit counter (LFU). With sampling at 5, Redis picks the best of five random candidates, which is close enough to true LRU in practice and vastly cheaper.

LFU is the better choice when access frequency is stable, because LRU has a specific weakness: one large scan touches every key, making genuinely cold keys look recently used and evicting the real hot set.

lfu-log-factor 10          # how fast the counter saturates (higher = slower growth)
lfu-decay-time 1           # minutes before an unused counter halves

The decay is what stops yesterday's hot key staying "frequent" forever.
WorkloadBetter policyWhy
Stable hot set, occasional scansLFUA scan does not displace the hot set
Recency-driven (sessions, feeds)LRURecent access genuinely predicts reuse
Uniform random accessrandomNothing to learn; cheapest
Mixed cache + permanent keysvolatile-*Only TTL'd keys are candidates

LFU is not the default because it needs tuning — lfu-log-factor and lfu-decay-time depend on the workload's access distribution, whereas LRU works acceptably with no tuning at all.

Part 5 — Fragmentation

used_memory_rss exceeding used_memory is normal; a large gap is not.

mem_fragmentation_ratio = used_memory_rss / used_memory

  1.0 – 1.5   normal
  > 1.5       significant fragmentation — investigate
  < 1.0       ★ the process is SWAPPING — far worse than fragmentation
🔑 A ratio below 1.0 means part of the dataset has been swapped to disk, and it is the most urgent thing this metric can tell you. Redis is designed on the assumption that memory access is nanoseconds; when a page comes from disk instead, latency rises by orders of magnitude while the server keeps reporting healthy. Disable swap on Redis hosts, or set vm.swappiness=0, and treat any ratio under 1.0 as an incident.

Fragmentation comes from the allocator: jemalloc rounds allocations to size classes, so freeing a 100-byte value and allocating a 130-byte one cannot reuse the space. Workloads that repeatedly write different-sized values fragment the most.

activedefrag yes                      # jemalloc-only; costs CPU
active-defrag-ignore-bytes 100mb      # do not bother below this
active-defrag-threshold-lower 10      # start at 10% fragmentation
active-defrag-threshold-upper 100     # maximum effort at 100%
active-defrag-cycle-min 5             # % CPU floor
active-defrag-cycle-max 75            # % CPU ceiling

Active defragmentation moves objects to compact the heap while Redis runs. It costs CPU on a single-threaded server, so enable it when the ratio is genuinely high and watch latency afterwards — a restart also clears fragmentation entirely, and on a replica that is often the cheaper fix.

Part 6 — Finding What Is Actually Using Memory

Guessing is the slowest way to reduce memory. Three tools answer it directly:

# 1. Offline analysis of an RDB file — no load on the server
redis-cli --bigkeys                   # largest key per type, sampled, safe
redis-cli --memkeys                   # by MEMORY USAGE (Redis 6+)
rdb --command memory dump.rdb         # rdbtools: full per-key report

# 2. Per-key, live
MEMORY USAGE key SAMPLES 0            # exact for collections (0 = sample all)

# 3. Server-wide breakdown
MEMORY STATS                          # overhead by category
INFO keyspace                         # keys and TTL coverage per db

--bigkeys is safe to run in production — it uses SCAN rather than KEYS, so it never blocks the server. It reports the largest key of each type, which finds the single 5-million-member set that quietly became half the instance.

Reduction techniqueTypical savingCost
Group small keys into hashesUp to 10×Restructuring; loses per-field TTL
Shorter key names5–20% with many keysReadability
Compress large values (lz4/gzip)50–80% on textCPU per read/write
msgpack instead of JSON~30%Not human-readable
Shorter TTLsProportionalLower hit rate
Stay under listpack thresholds~10× per keyO(n) operations on those keys
Integer values where possibleShared objects for 0–9999Only for small integers

Redis shares immutable objects for small integers (0–9999), so storing counters and flags as integers rather than strings is free memory — one of the few optimisations with no downside.

❌ Setting maxmemory to the host's RAM with volatile-lru, and sizing from payload arithmetic. The estimate said 10 million keys × 100-byte values ≈ 1 GB, so the host got 2 GB and maxmemory 2gb. In production the instance uses closer to 2 GB before the data is complete, because per-key overhead is ~100 bytes on top of every value. Then the eviction policy turns out to be inert: one code path writes keys without a TTL, and volatile-lru cannot evict those, so evicted_keys stays at 0 while every write fails with OOM. And because maxmemory equals host RAM, the first background save forks, copy-on-write doubles the footprint, and the kernel OOM-killer takes the process.

✅ Measure with MEMORY USAGE, use allkeys-lru for caches, and leave headroom for the fork. Size from a real measurement of representative keys, not payload arithmetic — per-key overhead frequently dominates. Set maxmemory to roughly 60–70% of host RAM when persistence is on, because a save can approach 2× the dataset. Choose allkeys-lru for a pure cache so no TTL-less code path can defeat eviction, and verify with evicted_keys that eviction actually happens. Then find the real consumers with --bigkeys and --memkeys, and collapse many small keys into hashes under the listpack thresholds — that structural change routinely saves 10× where value-shrinking saves percent.

Interview Questions

Beginner: Why does a small value cost far more than its size in Redis?

Because every key carries fixed overhead independent of its value.

SET user:1000000 "v"       # 16-byte key, 1-byte value

  dictEntry (hash slot + pointers)   ~56 bytes
  robj (type/encoding/refcount)      ~16 bytes
  SDS header + key                   ~24 bytes
  SDS header + value                 ~16 bytes
  jemalloc rounding                  ~ 8 bytes
  ────────────────────────────────────────────
  ≈ 100+ bytes for 17 bytes of data

So key count matters more than payload size for small values: ten million tiny keys cost about 1 GB before any data. Sizing from "10M × 100 bytes = 1 GB" underestimates by roughly 2×.

The fix is structural. Grouping many small keys into hashes pays the per-key overhead once per hash rather than once per field, and if the hash stays under hash-max-listpack-entries it also uses the compact listpack encoding — together often a 10× reduction.

MEMORY USAGE user:1000        # measure, do not estimate
redis-cli --bigkeys           # find the actual consumers (SCAN-based, safe)

Also note what maxmemory does not include: copy-on-write pages during a background save, and fragmentation. Both are real memory on the host.

Beginner: What are the eviction policies, and which do you pick for a cache?

Eight policies, in two families. allkeys-* consider every key; volatile-* consider only keys that have a TTL.

PolicyBehaviour
noevictionDefault — writes fail with OOM
allkeys-lru / -lfu / -randomEvict any key
volatile-lru / -lfu / -random / -ttlEvict only TTL'd keys

For a pure cache, use allkeys-lru. The reason is not that LRU is superior in the abstract — it is that allkeys makes every key a candidate, so no code path can defeat eviction.

The trap with volatile-*: if keys are written without a TTL, they are not eviction candidates at all. Redis then evicts nothing, evicted_keys stays at 0, and writes start failing with OOM command not allowed — while the configuration looks correct. One forgotten EX in one code path is enough.

Consider allkeys-lfu when the hot set is stable and periodic scans would otherwise pollute LRU by making cold keys look recently used.

And note that noeviction is the default, which is correct for a datastore — losing keys silently would be worse than refusing writes — and wrong for a cache.

Mid: Explain listpack encodings and the memory cliff.

Redis stores small collections in a listpack — a compact, contiguous array with no per-element pointers — and converts to the general structure (hashtable, skiplist) once a threshold is crossed.

hash-max-listpack-entries 128       # >128 fields    → hashtable
hash-max-listpack-value   64        # any value >64B → hashtable
zset-max-listpack-entries 128
set-max-intset-entries    512
OBJECT ENCODING myhash              # check which one a key is using

The listpack is roughly 10× smaller, because it stores elements inline instead of allocating a dict entry and object header per field. Its cost is O(n) scans instead of O(1) lookups, which is fine at 128 entries and not at 10,000.

The cliff is one-way. A hash that reaches 129 fields converts to a hashtable and stays one even after fields are deleted back to 10 — Redis never converts back for a live key. So a temporary spike permanently multiplies that key's memory, and the only remedy is deleting and rebuilding it.

Why this matters practically: the "group small keys into one hash" optimisation only pays off if the hash stays under the threshold. Bucketing a million keys into 10,000 hashes of 100 fields each keeps every hash in listpack encoding; bucketing into 1,000 hashes of 1,000 fields converts them all and gives up most of the saving.

Raising the thresholds trades CPU for memory. Values in the low hundreds are the usual balance; raising them to thousands makes every access an O(n) scan on a single-threaded server.

Mid: Redis memory keeps growing despite TTLs and a maxmemory limit. Diagnose it.

Check the policy first, because the most common cause is an inert eviction configuration:

CONFIG GET maxmemory-policy
INFO stats | grep evicted_keys        # 0 while at maxmemory = eviction is not working

If the policy is volatile-* and some keys have no TTL, those keys are not candidates — Redis evicts nothing and returns OOM on writes. Confirm with INFO keyspace, which reports how many keys have expiries:

db0:keys=4821003,expires=1200,avg_ttl=0     ← 4.8M keys, only 1,200 with a TTL

Then look at what is outside the dataset. maxmemory does not bound everything:

  • Client output buffers — a slow consumer or a large reply. CLIENT LIST shows omem per connection.
  • Replication backlog — exactly repl-backlog-size, which is often set to hundreds of MB.
  • Copy-on-write during saves — up to 2× the dataset, invisible in used_memory but very visible in RSS.
  • Fragmentation — compare used_memory_rss with used_memory.

Then find the consumers rather than guessing:

redis-cli --bigkeys        # largest key per type (SCAN-based, safe in production)
redis-cli --memkeys        # ranked by MEMORY USAGE
MEMORY STATS               # overhead by category

Other real causes I would check: a Streams consumer group whose pending list is growing because nothing acknowledges (invisible to XLEN and to MAXLEN trimming), and keys written by a path that forgets the TTL — the audit for which is expires versus keys in INFO keyspace.

The order I would work it: policy and evicted_keys, then TTL coverage, then --bigkeys, then the non-dataset consumers. The first two explain most cases in a minute.

Senior: Design memory management for a 500 GB cache workload on Redis.

Start with what 500 GB actually means, because the number people quote is usually the payload sum and the real figure includes overhead. Measure representative keys with MEMORY USAGE first; if the workload is many small values, the real requirement can be double the estimate.

Then challenge the working-set assumption. Cache access is Zipf-distributed, so caching 10% of the keyspace typically delivers ~80% of the hit rate. If 500 GB is the whole data set, the right cache may be 50 GB — an order of magnitude cheaper for a few points of hit rate. That question comes before any topology decision.

Topology: assuming 500 GB is genuinely needed, shard it — not primarily for capacity but for fork cost. A single 500 GB instance forks for seconds (roughly 10–20 ms per GB), stalling every client. Sixteen shards of ~32 GB keep fork stalls under half a second and let recovery run in parallel. Hosts sized so maxmemory is ~60–70% of RAM, leaving room for copy-on-write.

Per-shard configuration:

maxmemory 32gb
maxmemory-policy allkeys-lru        # every key evictable — no code path defeats it
maxmemory-samples 5                 # 10 if eviction quality matters more than CPU
save ""                             # snapshots on a replica, not here
activedefrag yes                    # with conservative thresholds

allkeys-lru rather than volatile-lru specifically because at this scale you cannot guarantee every write path sets a TTL, and the failure mode of volatile-* is OOM errors rather than eviction.

Key schema is where the real savings are. Group related fields into hashes kept under hash-max-listpack-entries, use short prefixes, store small integers as integers to hit shared objects, and compress values above ~10 KB. Structural changes routinely save 10×; value tuning saves percent.

Monitoring that matters: used_memory against maxmemory, evicted_keys rate (zero at the limit means eviction is broken), mem_fragmentation_ratio — with an alert below 1.0 for swapping, not just above 1.5 — keyspace_hits/misses, and latest_fork_usec.

The trade to state explicitly: more memory buys hit rate with diminishing returns. I would size from a measured hit-rate curve rather than from the data set, and revisit it as the access distribution changes.

Senior: mem_fragmentation_ratio is 2.5. Walk through it.

2.5 means RSS is 2.5× what Redis believes it is using — a 10 GB dataset occupying 25 GB of host memory. Before treating it as fragmentation, rule out the things that produce the same ratio for different reasons.

1. Is a background save running? Copy-on-write pages inflate RSS during BGSAVE or an AOF rewrite, and this is not fragmentation at all:

INFO persistence | grep -E "rdb_bgsave_in_progress|aof_rewrite_in_progress"

2. Did the dataset recently shrink? A large deletion or mass expiry frees memory inside the allocator's arenas without returning pages to the OS, so the ratio spikes. It usually recovers as new data reuses the space; used_memory_peak versus used_memory shows this.

3. Client output buffers. These count toward RSS and can be substantial with slow consumers or Pub/Sub — CLIENT LIST shows omem.

4. Genuine fragmentation. jemalloc rounds allocations to size classes, so a workload that repeatedly replaces values with different-sized ones cannot reuse freed space. This is the real cause when the ratio is persistently high with no save running and no recent shrink.

Remedies, in order of cost:

MEMORY PURGE                       # ask jemalloc to release free pages — try first
CONFIG SET activedefrag yes        # active defrag; costs CPU on a single thread

Active defragmentation moves objects to compact the heap while running. Enable it with conservative thresholds (active-defrag-threshold-lower 10, active-defrag-cycle-max 25 to start) and watch latency, because the work happens on the same thread that serves commands. A restart clears fragmentation completely, and doing it on a replica then failing over is often the cheapest fix of all.

Prevention: uniform value sizes fragment far less, so padding values to size classes can help pathological workloads. And the more important check is the opposite direction — a ratio below 1.0 means the process is swapping, which is far more urgent than any fragmentation and should be alerted on separately.

1 (easy): Measure real per-key overhead and show that key count dominates for small values.
Solution 
import redis
r = redis.Redis(decode_responses=True)
r.flushall()

for size in (1, 10, 100, 1000):
    r.set(f"k:{size}", "x" * size)
    usage = r.memory_usage(f"k:{size}")
    print(f"value {size:5d}B → MEMORY USAGE {usage:5d}B "
          f"(overhead {usage - size:4d}B, {usage/size:6.1f}× the payload)")

value     1B → MEMORY USAGE    56B (overhead   55B,   56.0× the payload)
value    10B → MEMORY USAGE    64B (overhead   54B,    6.4× the payload)

value  1000B → MEMORY USAGE  1072B (overhead   72B,    1.1× the payload)

Overhead is roughly constant at 55–70 bytes, so it dominates completely for small values and is negligible for large ones. That constant is why key count, not payload, drives memory in most caches.

for prefix, label in (("user:session:data:", "long prefix"), ("u:", "short prefix")):

long prefix   :  11.2 MB
short prefix  :   9.8 MB

12% saved from key names alone — worth doing at scale, and an order of magnitude less than the structural change in Exercise 2.

2 (easy): Demonstrate the listpack cliff and the one-way conversion.
Solution 
import redis
r = redis.Redis(decode_responses=True)
r.flushall()

print(f"threshold: {r.config_get('hash-max-listpack-entries')}")

r.delete("h")
prev_enc = None
for i in range(1, 200):
    r.hset("h", f"field{i}", "value")
    enc = r.object("encoding", "h")
    if enc != prev_enc:
        print(f"  {i:3d} fields → encoding={enc:10s} "
              f"memory={r.memory_usage('h'):6d}B")
        prev_enc = enc

threshold: {'hash-max-listpack-entries': '128'}
    1 fields → encoding=listpack   memory=    72B
  129 fields → encoding=hashtable  memory=  8760B

At 128 fields the hash is a listpack; at 129 it converts. Compare like for like:

r.delete("small", "big")
for i in range(128): r.hset("small", f"f{i}", "value")
for i in range(129): r.hset("big",   f"f{i}", "value")
s, b = r.memory_usage("small"), r.memory_usage("big")
print(f"128 fields (listpack) : {s:6,d} B  ({s/128:.1f} B/field)")
print(f"129 fields (hashtable): {b:6,d} B  ({b/129:.1f} B/field)")
print(f"→ one extra field cost {b - s:,} bytes ({b/s:.1f}× total)")

128 fields (listpack) :  2,120 B  (16.6 B/field)
129 fields (hashtable):  8,760 B  (67.9 B/field)
→ one extra field cost 6,640 bytes (4.1× total)

Now prove the conversion is one-way:

for i in range(129, 10, -1):
    r.hdel("big", f"f{i}")
print(f"after deleting down to {r.hlen('big')} fields:")
print(f"  encoding = {r.object('encoding', 'big')}  ← still hashtable")
print(f"  memory   = {r.memory_usage('big')}B")

r.delete("rebuilt")
for i in range(r.hlen("big")): r.hset("rebuilt", f"f{i}", "value")
print(f"rebuilt with the same {r.hlen('rebuilt')} fields:")
print(f"  encoding = {r.object('encoding', 'rebuilt')}")
print(f"  memory   = {r.memory_usage('rebuilt')}B "
      f"({r.memory_usage('big')/r.memory_usage('rebuilt'):.1f}× smaller)")

after deleting down to 11 fields:
  encoding = hashtable  ← still hashtable
  memory   = 4216B
rebuilt with the same 11 fields:
  encoding = listpack
  memory   = 232B (18.2× smaller)

18× more memory for identical data, purely because that key once exceeded the threshold. A temporary spike permanently inflates the key, and only deleting and rebuilding recovers it.

The structural win — bucketing keys into hashes:

N = 100_000
r.flushall(); base = r.info("memory")["used_memory"]
p = r.pipeline()
for i in range(N):
    p.set(f"user:{i}", "value")
    if i % 5000 == 0: p.execute(); p = r.pipeline()
p.execute()
flat = r.info("memory")["used_memory"] - base

r.flushall(); base = r.info("memory")["used_memory"]
p = r.pipeline()
for i in range(N):
    p.hset(f"bucket:{i // 100}", str(i), "value")     # 100 fields per hash
    if i % 5000 == 0: p.execute(); p = r.pipeline()
p.execute()
bucketed = r.info("memory")["used_memory"] - base

print(f"{N:,} separate keys : {flat/1024/1024:6.2f} MB")
print(f"{N//100:,} hashes × 100 : {bucketed/1024/1024:6.2f} MB "
      f"({flat/bucketed:.1f}× smaller)")

100,000 separate keys :   8.34 MB
1,000 hashes × 100 :   1.12 MB (7.4× smaller)

7.4× less memory for the same data — the single largest memory optimisation available, and it works only because 100 fields stays under the 128-entry listpack threshold.

It worked until the TTL-less keys filled the instance by themselves, then failed permanently — evicting 196,203 cache keys first, so the hit rate collapsed before the errors began. That staged failure is why the bug is hard to diagnose from the outside.

4 (medium): Compare LRU and LFU under a scan that pollutes the cache.
Solution 
import redis, random
r = redis.Redis(decode_responses=True)

HOT, COLD, VALUE = 200, 20_000, "v" * 512

def run(policy, samples=5):
    r.flushall()
    r.config_set("maxmemory", "6mb")
    r.config_set("maxmemory-policy", policy)
    r.config_set("maxmemory-samples", samples)
    r.config_resetstat()

    # establish a hot set with heavy repeated access
    for i in range(HOT): r.set(f"hot:{i}", VALUE)
    for _ in range(20):
        for i in range(HOT): r.get(f"hot:{i}")

    # a batch job scans a large cold keyspace once
    for i in range(COLD):
        r.set(f"cold:{i}", VALUE)
        r.get(f"cold:{i}")

    survived = sum(1 for i in range(HOT) if r.exists(f"hot:{i}"))
    return survived, r.info("stats")["evicted_keys"]

print(f"{'policy':>16} {'hot keys survived':>19} {'evicted':>9}")
for policy in ("allkeys-lru", "allkeys-lfu", "allkeys-random"):
    survived, evicted = run(policy)
    print(f"{policy:>16} {survived:>13d}/{HOT:<5d} {evicted:9,d}")

          policy   hot keys survived   evicted
     allkeys-lru            18/200      19,412
     allkeys-lfu           171/200      19,388
  allkeys-random            21/200      19,433

LRU kept 18 of 200 hot keys; LFU kept 171. The scan touched every cold key exactly once, which under LRU makes them all look recently used and pushes out the genuinely hot set. LFU counts frequency, so keys accessed 20 times outrank keys accessed once — exactly the property that survives a scan.

Now the opposite workload, where recency genuinely predicts reuse:

def run_recency(policy):
    r.flushall()
    r.config_set("maxmemory", "6mb")
    r.config_set("maxmemory-policy", policy)
    r.config_resetstat()
    # sliding window: recent keys are the ones that will be requested again
    hits = 0
    for step in range(20_000):
        k = f"s:{step}"
        r.set(k, VALUE)
        recent = f"s:{max(0, step - random.randint(1, 300))}"
        if r.get(recent) is not None: hits += 1
    return hits

for policy in ("allkeys-lru", "allkeys-lfu"):
    print(f"{policy:>16}: {run_recency(policy):,} hits on recent keys")

     allkeys-lru: 18,204 hits on recent keys
     allkeys-lfu: 14,881 hits on recent keys

LRU wins on the recency-driven workload — sessions, feeds, sliding windows — because a recently written key has never accumulated frequency. Neither policy is universally better; the choice follows the access pattern.

And maxmemory-samples trades CPU for eviction quality:

for samples in (3, 5, 10):
    survived, _ = run("allkeys-lru", samples=samples)
    print(f"maxmemory-samples {samples:2d}: {survived:3d}/{HOT} hot keys survived")

maxmemory-samples  3:  11/200 hot keys survived
maxmemory-samples  5:  18/200 hot keys survived
maxmemory-samples 10:  27/200 hot keys survived

Higher sampling approximates true LRU more closely at more CPU per eviction — but note it never rescues LRU from the scan-pollution problem, which is a property of the algorithm rather than the sampling.

Three structural changes, three very different returns. Bucketing sessions saved 3.8× by paying per-key overhead once per 100 fields. Splitting the 300-field profiles into 100-field hashes would cut them 3× per field by staying in listpack encoding. And compressing a repetitive text blob saved 188× — compression ratios on real data are far lower, but large text values are usually worth compressing.

The ordering lesson: the audit came first. Optimising the 50,000 session keys felt obvious, but the five index:* sets were a larger share of memory — and no amount of intuition would have surfaced that without MEMORY USAGE per key.

🎯 Key Takeaways

  • Per-key overhead is ~50–100 bytes regardless of value size — a 1-byte value measured 56 bytes, and 200,000 small keys used 2.9× the payload estimate.
  • Key count, not payload, drives memory for small values; size from MEMORY USAGE on real keys, never from arithmetic.
  • Small collections use compact listpack encoding; crossing a threshold converts them — one extra field took a hash from 2,120 to 8,760 bytes.
  • The conversion is one-way: deleting fields back down left the hash at 18× the memory of an identical rebuilt key.
  • Bucketing many small keys into hashes under the listpack threshold saved 7.4× — the single largest memory optimisation available.
  • noeviction is the default: correct for a datastore, wrong for a cache, where writes fail with OOM while reads keep working.
  • volatile-* policies only evict keys with a TTL — with none set, it behaved identically to noeviction: 0 evictions and hard OOM.
  • A mixed workload where 10% of writes lacked a TTL evicted 196,203 cache keys first, then failed permanently — the hit rate collapsed before the errors appeared.
  • Audit TTL coverage by comparing expires with keys in INFO keyspace; anything below ~100% under volatile-* is a latent OOM.
  • Use allkeys-lru for pure caches so no code path can defeat eviction.
  • LRU is approximated by sampling, not tracked exactly — maxmemory-samples 3/5/10 kept 11/18/27 hot keys, trading CPU for eviction quality.
  • LFU survives scan pollution and LRU does not: after a cold scan, LFU kept 171 of 200 hot keys against LRU's 18 — but LRU won the recency-driven workload.
  • Fragmentation is used_memory_rss / used_memory: deleting half the keys pushed it to 2.09 because jemalloc kept the pages.
  • MEMORY PURGE then activedefrag brought 1.93 down to 1.13 in ~15 s — on the same thread that serves commands, so watch latency.
  • A ratio below 1.0 means the process is swapping — more urgent than any fragmentation. Alert on both directions.
  • maxmemory excludes copy-on-write pages and fragmentation; set it to ~60–70% of host RAM when persistence is enabled.
  • Find consumers with --bigkeys and per-key MEMORY USAGE, not intuition — 5 sets were 31% of memory against 50,000 session keys' 24%.
  • Small integers 0–9999 use shared objects, so storing counters and flags as integers is free memory.
