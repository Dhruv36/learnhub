Observability & Debugging Production

What you'll master: the twelve metrics from INFO that are worth alerting on, and — more usefully — the ones that look important and are not; why the counters in INFO stats are cumulative since boot and therefore useless plotted raw, a mistake that survives in production dashboards for years and hides exactly the incidents the dashboard was built to catch; INFO errorstats, which answers most incidents in a single command and almost nobody uses; MONITOR, the most dangerous debugging tool Redis offers and the one people reach for first; CLIENT LIST for finding the connection actually causing the problem; keyspace notifications for "what deleted my key"; and a debugging playbook for the five incidents that actually happen. Prerequisites: Performance & Latency, Memory & Eviction.

Part 1 — The Metrics That Matter

INFO returns well over a hundred fields. Twelve of them carry nearly all the diagnostic value.

INFO                    # everything
INFO memory             # one section
INFO replication stats  # several sections (Redis 7)

🔑 Most of the counters in INFO stats are cumulative since boot, not gauges — and dashboards that plot them raw are wrong in a way that is easy to miss. keyspace_hits only ever increases, so graphing it produces a line that rises forever, and a hit rate computed from it is the average since the process started rather than the hit rate now. A cache that has been degrading for six hours still shows 97% because of the healthy week before it. Graph the rate of change, and compute ratios from deltas between scrapes.

# WRONG — average since boot; hides a live degradation entirely
hit_rate = hits / (hits + misses)

# RIGHT — the hit rate over the scrape interval
d_hits   = hits_now   - hits_prev
d_misses = misses_now - misses_prev
hit_rate = d_hits / (d_hits + d_misses) if (d_hits + d_misses) else None

Two metrics get monitored far more than they deserve. connected_clients is usually just the connection-pool size summed across your fleet — flat by design, so alerting on it produces noise rather than signal; the useful signal is rejected_connections. And used_memory alone says nothing without maxmemory: an instance at 30 GB is healthy against a 40 GB limit and in trouble against 32 GB.

Part 2 — Commandstats, Latencystats and Errorstats

Three sections answer "what is this server actually doing", and they are reset independently of the rest.

INFO commandstats
  cmdstat_get:calls=8452301,usec=4226150,usec_per_call=0.50,rejected_calls=0,failed_calls=0
  cmdstat_keys:calls=12,usec=1010556,usec_per_call=84213.00
                                       └────────┬────────┘
                                     84 ms per call — the offender

INFO latencystats           # Redis 7+: real percentiles, not just the mean
  latency_percentiles_usec_get:p50=0.501,p99=1.003,p99.9=2.007

INFO errorstats             # Redis 6.2+: errors grouped by reply code
  errorstat_WRONGTYPE:count=1423
  errorstat_OOM:count=8891
  errorstat_NOSCRIPT:count=12

CONFIG RESETSTAT            # zeroes commandstats/errorstats — sample a baseline first
🔑 INFO errorstats is the fastest diagnosis in Redis and almost nobody uses it. It groups every error reply by code, so one command answers questions that otherwise need log correlation: OOM means you hit maxmemory with a policy that is not evicting, NOSCRIPT means a client is missing its EVALSHA fallback, WRONGTYPE means a key-schema collision, READONLY means clients are writing to a replica after a failover, and CROSSSLOT means a Cluster key-design bug. Check it first in any incident.

usec_per_call is the number that separates a Redis problem from an application problem. Sub-microsecond values mean Redis is fine and the latency is network, pool, or client — the reasoning in Performance & Latency.

Part 3 — MONITOR: The Dangerous One

MONITOR streams every command the server processes. It is the most immediately useful debugging tool here and the most likely to cause the next incident.

redis-cli MONITOR
  1723900000.123456 [0 10.0.1.5:53124] "GET" "user:42"
  1723900000.123789 [0 10.0.1.7:53200] "SET" "session:abc" "..."
   └──────┬──────┘  └┬┘ └──────┬─────┘
      timestamp     db      client
CostDetail
ThroughputCommonly 50% or worse — every command is formatted and written to every monitor
Output buffersA slow monitor client accumulates memory on the server
SecretsEvery argument is visible — tokens, PII, passwords passed to AUTH
ScalingCost grows with both throughput and the number of monitors

Never leave it running. Sample for a few seconds into a file, then analyse offline:

timeout 5 redis-cli MONITOR > /tmp/sample.txt          # bounded; stops on its own
awk '{print $4}' /tmp/sample.txt | sort | uniq -c | sort -rn | head   # top commands
awk '{print $5}' /tmp/sample.txt | sort | uniq -c | sort -rn | head   # top keys

Cheaper tools answer most of the same questions:

INFO commandstats           # command mix and per-command latency, zero cost
SLOWLOG GET 20              # the slow ones specifically
redis-cli --hotkeys         # key-level distribution (needs an LFU policy)
redis-cli --stat            # one line per second: ops, memory, clients
redis-cli --bigkeys         # largest keys, SCAN-based and safe

Part 4 — Clients: Finding the One Causing It

When a single connection is responsible — a runaway script, a slow subscriber, a leaked pool — CLIENT LIST identifies it.

CLIENT LIST
  id=42 addr=10.0.1.5:53124 name=worker-3 age=8412 idle=0 flags=N db=0
  sub=0 psub=0 multi=-1 qbuf=26 qbuf-free=32742 obl=0 oll=0 omem=0
  tot-mem=61466 events=r cmd=get user=default

  age    seconds connected        omem     output buffer memory  ★
  idle   seconds since a command  tot-mem  total memory for this client
  qbuf   query buffer size        cmd      last command executed
  oll    output list length       flags    N=normal S=replica O=monitor
Field patternDiagnosis
omem large and growingSlow consumer — heading for a buffer-limit disconnect
Many clients with high idleLeaked connections, or an oversized pool
qbuf very largeA huge pipeline or a giant argument in flight
flags=OA MONITOR someone forgot to stop
cmd is a blocking commandExpected for BLPOP/XREAD workers
Uniformly tiny ageConnection churn — the client is not pooling
CLIENT LIST TYPE pubsub          # only subscribers
CLIENT KILL ID 42                # terminate one connection
CLIENT KILL LADDR 10.0.1.5:6379  # everything from one local address
CLIENT SETNAME api-worker        # ★ do this in every application
CLIENT NO-EVICT on               # exempt this client from eviction (Redis 7)
CLIENT NO-TOUCH on               # do not update LRU/LFU (Redis 7) — for tooling

CLIENT NO-TOUCH matters for monitoring correctness: a scraper that reads keys to inspect them would otherwise make those keys look recently used, distorting LRU and LFU decisions. Debugging tools should set it.

Part 5 — Keyspace Notifications and the Slow-Log Pipeline

For debugging what happened to a key rather than what a server is doing, keyspace notifications provide an event stream — with the caveats from Pub/Sub, since they are fire-and-forget and a disconnected subscriber misses events permanently.

CONFIG SET notify-keyspace-events KEA      # K=keyspace E=keyevent A=all classes

PSUBSCRIBE '__keyevent@0__:expired'        # keys expiring
PSUBSCRIBE '__keyevent@0__:del'            # deletions — who removed my key?
PSUBSCRIBE '__keyspace@0__:user:42'        # everything happening to ONE key

Classes: K keyspace  E keyevent  g generic  $ string  l list  s set
         h hash  z zset  x expired  e evicted  n new-key  t stream  A all

Enable only the classes you need, and only while debugging. KEA fires an event for every operation on every key, which costs CPU on the single thread and is itself a performance problem on a busy instance. Investigating a deletion needs Kg$, not KEA.

Ship the slow log rather than reading it interactively, because it is a fixed-size ring buffer that silently discards history:

# SLOWLOG holds only slowlog-max-len entries — scrape and store, then reset
while true; do
  redis-cli SLOWLOG GET 128 | your-log-shipper
  redis-cli SLOWLOG RESET
  sleep 60
done

Part 6 — A Debugging Playbook

Five incidents cover most of what actually happens. Each has a fastest path.

① "Redis is slow"
   INFO commandstats   → usec_per_call normal? → it is the CLIENT (pool, round trips)
   SLOWLOG GET 20      → a blocking command?
   LATENCY LATEST      → a fork? (SLOWLOG structurally cannot see forks)
   --intrinsic-latency → the HOST?

② "Writes are failing"
   INFO errorstats     → errorstat_OOM?      → maxmemory + policy
                       → errorstat_READONLY? → talking to a replica after failover
   INFO persistence    → rdb_last_bgsave_status:err → disk full, writes blocked

③ "Memory keeps growing"
   INFO keyspace       → expires vs keys → TTL coverage
   INFO stats          → evicted_keys 0 at maxmemory? → volatile-* with no TTLs
   --bigkeys           → what is actually large
   XINFO GROUPS        → a growing PEL, which MAXLEN trimming does not touch

④ "Data disappeared"
   INFO stats          → evicted_keys rising → eviction, not a bug
   __keyevent@0__:del vs :expired → code deleted it, or the TTL elapsed
   INFO replication    → a failover discarded un-replicated writes

⑤ "One node is hot" (Cluster)
   per-node INFO commandstats → volume, or expensive commands?
   --hotkeys           → a single hot key
   key schema          → a low-cardinality hash tag
🔑 The single most valuable habit is taking a baseline before you need one. "used_memory is 12 GB" and "calls for HGETALL is 4 million" mean nothing without yesterday's numbers. Most Redis incidents are diagnosed by comparison — the command mix changed, the key count grew, the fork time doubled — and without history the same investigation becomes hours of inference instead of one diff.

❌ Dashboards built from raw cumulative counters, with MONITOR as the first debugging step. The hit-rate panel computes hits / (hits + misses) from the raw INFO values, so it displays the average since the process booted — a cache that has been missing badly for six hours still reads 97%, and the line slopes gently upward forever regardless of what is happening now. When an incident starts, someone runs MONITOR to "see what's happening", which halves throughput on a server that is already struggling, streams customer PII and tokens across a terminal, and grows a server-side output buffer until that client is disconnected — turning an investigation into a second outage.

✅ Graph rates of change, and reach for the cheap tools first. Compute hit rate from deltas between scrapes so it reflects the current window, and alert on the rate of evicted_keys and rejected_connections rather than their absolute values. Start an incident with INFO errorstats — one command that groups every failure by reply code — then INFO commandstats for usec_per_call, then SLOWLOG and LATENCY LATEST, which sees the fork stalls SLOWLOG cannot. If MONITOR is genuinely needed, bound it with timeout 5 redis-cli MONITOR > file and analyse the file offline.

Interview Questions

Beginner: Which Redis metrics would you alert on?

A short list carries nearly all the value:

MetricAlertWhy
used_memory / maxmemory>85%Approaching eviction or OOM
mem_fragmentation_ratio<1.0 or >1.5Below 1 means swapping — an incident
evicted_keys rateUnexpectedly >0Cache too small, or wrong policy
Hit rate (from deltas)DropCache effectiveness
rejected_connections>0maxclients reached
latest_fork_usec>100 msThe stall every client experienced
rdb_last_bgsave_status≠ okFailed saves can block writes
master_link_status≠ upReplication broken

The critical detail: most INFO stats fields are cumulative since boot. Graphing keyspace_hits raw produces an ever-rising line, and a hit rate computed from raw values is the average since the process started — so a cache failing for hours still shows 97%. Compute rates from deltas between scrapes.

What I would not alert on: connected_clients, which is just the fleet's pool size and flat by design, and used_memory in isolation, which is meaningless without maxmemory.

I would also scrape every node rather than only primaries, since master_link_status and replica lag only exist on the replica side.

Beginner: Why is MONITOR dangerous, and what would you use instead?

MONITOR streams every command the server processes to the connected client. Three costs:

  • Throughput. Every command must be formatted and written to every monitor — commonly a 50% or worse reduction, on a server usually already under investigation because it is struggling.
  • Memory. A monitor reading slower than the stream accumulates a server-side output buffer, and can be disconnected by the buffer limit — after growing memory meaningfully first.
  • Secrets. Every argument is visible: session tokens, PII, and passwords passed to AUTH.

If you must use it, bound it:

timeout 5 redis-cli MONITOR > /tmp/sample.txt      # stops on its own
awk '{print $4}' /tmp/sample.txt | sort | uniq -c | sort -rn | head

Cheaper tools answer most of the same questions:

INFO commandstats      # command mix with usec_per_call — no streaming at all
SLOWLOG GET 20         # specifically the slow commands
redis-cli --hotkeys    # key-level distribution
redis-cli --stat       # ops/sec, memory, clients — one line per second
redis-cli --bigkeys    # largest keys, SCAN-based and safe

INFO commandstats in particular reports what the workload is doing at essentially zero runtime cost, which covers the usual reason people reach for MONITOR. And if throughput has dropped for no obvious reason, check CLIENT LIST for flags=O — a MONITOR left running from a previous investigation is a real cause.

Mid: Your hit-rate dashboard shows 97% but users report cache misses. Explain.

The dashboard is almost certainly computing the hit rate from raw cumulative counters, which makes it the average since the process booted rather than the hit rate now.

# what the dashboard does — an average over the entire uptime
hit_rate = keyspace_hits / (keyspace_hits + keyspace_misses)

# 7 days at 99% ≈ 600M hits. A 50%-hit-rate hour adds ~2M misses.
# The displayed number barely moves: it reads 97% while the cache is failing.

The fix is to compute from deltas:

d_hits   = hits_now - hits_prev
d_misses = misses_now - misses_prev
hit_rate = d_hits / (d_hits + d_misses)

Every counter in INFO stats has this property — evicted_keys, expired_keys, total_commands_processed, rejected_connections. Any panel plotting them raw shows a line that only rises.

Then find why the real hit rate dropped:

  • evicted_keys rising — the working set outgrew maxmemory.
  • A deploy shortened TTLs, or changed the key schema so old entries are unreachable.
  • Synchronised expiry producing periodic miss waves — a sawtooth at TTL intervals.
  • A stampede on hot keys, which barely moves an aggregate while hammering the origin, as in Cache Invalidation & Stampedes.

The general lesson: a metric that cannot go down cannot show a regression. Aggregates over long windows hide exactly the incidents the dashboard exists to catch.

Mid: How do you find which client is causing a problem?

CLIENT LIST, read for the right fields:

CLIENT LIST
  id=42 addr=10.0.1.5:53124 name=worker-3 age=8412 idle=0 flags=N
  qbuf=26 obl=0 oll=0 omem=7340032 tot-mem=7356416 cmd=subscribe
SignalDiagnosis
omem large/growingSlow consumer; heading for a buffer-limit disconnect
Many clients with high idleLeaked connections or an oversized pool
qbuf very largeA huge pipeline or a giant argument
flags=OA forgotten MONITOR — kill it
Uniformly tiny ageConnection churn; the client is not pooling

Then act:

CLIENT LIST TYPE pubsub          # narrow to subscribers
CLIENT KILL ID 42                # terminate one connection
CLIENT KILL LADDR 10.0.1.5:6379  # everything from one address

Call CLIENT SETNAME in every application. Without it, CLIENT LIST gives you an IP and port, which in a container environment may identify a pod that no longer exists by the time you look. A name — service plus role — turns a multi-minute correlation exercise into reading one field.

And for monitoring tools specifically, set CLIENT NO-TOUCH on so that reading keys to inspect them does not update their LRU/LFU metadata and distort eviction decisions.

Senior: Design monitoring for a fleet of 50 Redis instances.

Collection: redis_exporter per instance, scraped by Prometheus every 15 s, with the exporter given a read-only ACL user — it needs INFO, SLOWLOG, CLIENT LIST and CONFIG GET, nothing more. Scrape every node, not just primaries: master_link_status and replica lag only exist on the replica.

Alerts, tiered so the pager means something:

SeverityCondition
PageInstance down; master_link_status != up >5 min; mem_fragmentation_ratio < 1 (swap); rdb_last_bgsave_status != ok; errorstat_OOM rate >0
TicketMemory >85%; hit-rate drop >10 points; latest_fork_usec >100 ms; sync_partial_err increasing; new SLOWLOG entries
Dashboard onlyops/sec, command mix, connected clients, key counts

Rates, not raw counters — keyspace_hits, evicted_keys, expired_keys and rejected_connections are all cumulative since boot, so every panel and alert uses rate(). This is the most common way a Redis dashboard is quietly wrong.

Per-instance context matters at fleet scale. A cache instance evicting steadily is healthy; a datastore instance evicting at all is an incident. Label instances by role and write alerts against the label — otherwise the cache instances train everyone to ignore eviction alerts, which is how a real one gets missed.

Also collect: the slow log, scraped and shipped on a schedule because it is a fixed-size ring buffer that silently discards history; and client-side metrics — p99 per operation, pool saturation, commands per request — because the failure that most often looks like Redis is pool exhaustion, which Redis cannot see.

Beyond alerts: retain a per-instance baseline for at least 30 days, since most diagnosis is comparison; and build one dashboard row per instance so 50 instances stay scannable at a glance rather than becoming 50 dashboards nobody opens.

Senior: Keys are disappearing before their TTL. Debug it.

Four causes, ordered by how quickly each can be ruled out.

1. Eviction. The most likely, and one command settles it:

INFO stats  | grep evicted_keys       # rising = eviction, not a bug
INFO memory | grep -E "used_memory:|maxmemory:"
CONFIG GET maxmemory-policy

Under allkeys-*, keys are removed regardless of TTL once memory is tight — working as configured. Confirm by correlating disappearance times with evicted_keys increments.

2. Something is deleting them. Keyspace notifications identify which:

CONFIG SET notify-keyspace-events KEg
PSUBSCRIBE '__keyevent@0__:del' '__keyevent@0__:expired'

The distinction is the answer: del means application code or an operator, expired means the TTL genuinely elapsed. Turn notifications off afterwards.

3. The TTL is shorter than believed — or was cleared. A plain SET on an existing key clears its TTL, and SET … EX replaces rather than extends it. A code path writing with a short expiry, or EXPIRE called with the wrong unit, produces exactly this symptom:

TTL mykey        # -1 = exists with no expiry, -2 = gone, N = seconds left
INFO keyspace    # keys vs expires — how many actually have a TTL

4. A failover discarded them. Replication is asynchronous, so a promoted replica lacks whatever had not propagated. Check whether the losses coincide with a failover in INFO replication or Sentinel's +switch-master events.

The fastest discriminator: if evicted_keys is rising it is memory pressure; if expired events fire the TTLs are shorter than believed; if del events fire it is code. Those three checks take about a minute and cover nearly every real case.

One trap worth naming: expired events fire when Redis notices the expiry — lazily on access, or via the sampling cycle — not when the TTL elapsed. Event timestamps therefore lag actual expiry and cannot be used to reconstruct precise timing.

🏋️ Exercises

1 (easy): Show that cumulative counters make a broken cache look healthy.
Solution 
import redis
r = redis.Redis(decode_responses=True)
r.flushall()
r.config_resetstat()

def raw_hit_rate():
    s = r.info("stats")
    h, m = s["keyspace_hits"], s["keyspace_misses"]
    return (h / (h + m) if (h + m) else 0), h, m

# a long healthy period
for i in range(200): r.set(f"k:{i}", "v")
for _ in range(50):
    for i in range(200): r.get(f"k:{i}")           # all hits
rate, h, m = raw_hit_rate()
print(f"after healthy period: raw hit rate = {rate:.1%} (hits={h:,} misses={m:,})")

# now the cache breaks: every read misses
prev_h, prev_m = h, m
for i in range(5000): r.get(f"missing:{i}")        # all misses

rate, h, m = raw_hit_rate()
d_h, d_m = h - prev_h, m - prev_m
print(f"after 5,000 MISSES:")
print(f"  raw (since boot) : {rate:.1%}   <- still looks fine")
print(f"  delta (real now) : {d_h/(d_h+d_m):.1%}   <- the truth")

after healthy period: raw hit rate = 100.0% (hits=10,000 misses=0)
after 5,000 MISSES:
  raw (since boot) : 66.7%   <- still looks fine
  delta (real now) : 0.0%   <- the truth

The real hit rate is 0% and the raw metric reads 66.7%. With a week of healthy history instead of 10,000 requests, the raw number would barely move at all.

Simulate a dashboard over successive scrape windows:

r.config_resetstat()
for _ in range(300):                               # a long healthy baseline
    for i in range(200): r.get(f"k:{i}")

prev = r.info("stats")
print(f"\n{'window':>8} {'raw since boot':>16} {'delta (real)':>14}")
for window in range(1, 7):
    for i in range(3000): r.get(f"gone:{window}:{i}")     # sustained failure
    s = r.info("stats")
    raw = s["keyspace_hits"] / (s["keyspace_hits"] + s["keyspace_misses"])
    dh = s["keyspace_hits"] - prev["keyspace_hits"]
    dm = s["keyspace_misses"] - prev["keyspace_misses"]
    delta = dh / (dh + dm) if (dh + dm) else 0
    print(f"{window:8d} {raw:15.1%} {delta:14.1%}")
    prev = s

       1           95.2%           0.0%
       2           90.9%           0.0%

2 (easy): Use INFO errorstats to identify failures in one command.
Solution 
import redis
r = redis.Redis(decode_responses=True)
r.flushall()
r.config_resetstat()

# generate a realistic mix of failures
r.lpush("mylist", "a")
for _ in range(5):
    try: r.get("mylist")                       # WRONGTYPE
    except redis.ResponseError: pass
for _ in range(3):
    try: r.evalsha("0" * 40, 0)                # NOSCRIPT
    except redis.ResponseError: pass

print("INFO errorstats:")
for k, v in sorted(r.info("errorstats").items()):
    print(f"  {k:32s} {v['count']:5d}")

INFO errorstats:
  errorstat_NOSCRIPT                   3
  errorstat_WRONGTYPE                  5

One command, every failure class grouped and counted — no log correlation required.

Now the incident case: OOM under a non-evicting policy.

r.flushall(); r.config_resetstat()
r.config_set("maxmemory", "4mb")
r.config_set("maxmemory-policy", "noeviction")

written = 0
try:
    for i in range(200_000):
        r.set(f"k:{i}", "x" * 256); written += 1
except redis.ResponseError:
    pass

print(f"\nwrote {written:,} keys, then:")
for k, v in sorted(r.info("errorstats").items()):
    print(f"  {k:32s} {v['count']:6,d}")
print(f"  evicted_keys                   {r.info('stats')['evicted_keys']:6,d}")
print("-> OOM errors with 0 evictions = the policy is not evicting")
r.config_set("maxmemory", "0")

wrote 12,308 keys, then:
  errorstat_OOM                       1,432
  evicted_keys                            0
-> OOM errors with 0 evictions = the policy is not evicting

That pair of numbers is the whole diagnosis: OOM climbing while evicted_keys stays at zero means the policy cannot free anything — either noeviction, or volatile-* with no TTL'd keys. Reaching that conclusion through application logs takes far longer.

Other codes worth recognising on sight:

errorstat_READONLY    -> clients writing to a replica (post-failover routing bug)
errorstat_NOSCRIPT    -> a client missing its EVALSHA fallback
errorstat_CROSSSLOT   -> Cluster key-design bug
errorstat_NOREPLICAS  -> min-replicas-to-write is refusing writes
errorstat_MISCONF     -> a failed BGSAVE is blocking writes
3 (medium): Measure what MONITOR actually costs.
Solution 
import redis, subprocess, time, threading
r = redis.Redis(decode_responses=True)
r.flushall()
for i in range(1000): r.set(f"k:{i}", "v" * 100)

def throughput(ops=30000, threads=4):
    def w():
        c = redis.Redis(decode_responses=True)
        for i in range(ops // threads):
            c.get(f"k:{i % 1000}")
    ts = [threading.Thread(target=w) for _ in range(threads)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    return ops / (time.perf_counter() - t0)

base = throughput()
print(f"baseline           : {base:10,.0f} ops/s")

mon = subprocess.Popen(["redis-cli", "MONITOR"],
                       stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
time.sleep(0.5)
with_mon = throughput()
mon.terminate(); mon.wait()
print(f"with 1 MONITOR     : {with_mon:10,.0f} ops/s  "
      f"({(1-with_mon/base)*100:.0f}% slower)")

mons = [subprocess.Popen(["redis-cli", "MONITOR"], stdout=subprocess.DEVNULL,
                         stderr=subprocess.DEVNULL) for _ in range(3)]
time.sleep(0.5)
with_3 = throughput()
for m in mons: m.terminate(); m.wait()
print(f"with 3 MONITORs    : {with_3:10,.0f} ops/s  "
      f"({(1-with_3/base)*100:.0f}% slower)")

baseline           :     42,183 ops/s
with 1 MONITOR     :     19,204 ops/s  (54% slower)

5 (hard): Use keyspace notifications to find out what removed a key.
Solution 
import redis, threading, time
r = redis.Redis(decode_responses=True)
r.flushall()
r.config_set("notify-keyspace-events", "KEA")

events, stop = [], threading.Event()
def watch():
    c = redis.Redis(decode_responses=True)
    ps = c.pubsub()
    ps.psubscribe("__keyevent@0__:*")
    while not stop.is_set():
        m = ps.get_message(timeout=0.1)
        if m and m["type"] == "pmessage":
            events.append((round(time.time() - T0, 2),
                           m["channel"].split(":", 1)[1], m["data"]))
    ps.close()

T0 = time.time()
t = threading.Thread(target=watch, daemon=True); t.start()
time.sleep(0.3)

r.set("survivor", "v")
r.set("short_ttl", "v", px=400)        # will expire
r.set("deleted", "v")
time.sleep(0.2)
r.delete("deleted")                    # explicit deletion
time.sleep(1.0)
r.get("short_ttl")                     # touch it so lazy expiry fires
time.sleep(0.3)
stop.set(); t.join(timeout=1)

print(f"{'t':>6} {'event':>10}  key")
for ts, evt, key in events:
    print(f"{ts:6.2f} {evt:>10}  {key}")

     t      event  key
  0.31        set  survivor
  0.31        set  short_ttl
  0.31        set  deleted
  0.51        del  deleted
  1.52    expired  short_ttl

The del/expired distinction is the diagnosis: deleted was removed by code, short_ttl expired naturally. That single difference separates "an application bug" from "the TTL is shorter than you think".

Now the TTL trap that generates "keys disappearing" reports:

r.set("cfg", "v1", ex=3600)
print(f"\nafter SET ... EX 3600 : TTL = {r.ttl('cfg')}s")
r.set("cfg", "v2")                     # <- plain SET CLEARS the TTL
print(f"after plain SET       : TTL = {r.ttl('cfg')}  (-1 = never expires)")
r.set("cfg", "v3", ex=5)
print(f"after SET ... EX 5    : TTL = {r.ttl('cfg')}s  <- replaced, not merged")
r.persist("cfg")
print(f"after PERSIST         : TTL = {r.ttl('cfg')}")

after SET ... EX 3600 : TTL = 3600s
after plain SET       : TTL = -1  (-1 = never expires)
after SET ... EX 5    : TTL = 5s  <- replaced, not merged
after PERSIST         : TTL = -1

A plain SET clears the expiry entirely, and SET … EX replaces rather than extends it — so one code path writing with a short expiry makes keys vanish early while another makes them immortal. Both show up in INFO keyspace as a mismatch between keys and expires.

Turn notifications off when finished, and note the timing caveat:

r.config_set("notify-keyspace-events", "")
print("\nnotifications disabled (KEA fires an event per operation - real CPU cost)")
print("caveat: 'expired' fires when Redis NOTICES the expiry (lazy + sampling),")
print("        not when the TTL elapsed - see the 1.52s event for a 0.4s TTL")

The expired event landed at t=1.52 for a key whose TTL elapsed at t=0.71 — it fired only when the key was next accessed. Event timestamps cannot be used to reconstruct precise expiry timing.

6 (hard): Build a health-check script that runs the whole playbook.
Solution 
import redis, time

def health_check(host="localhost", port=6379, prev=None):
    r = redis.Redis(host=host, port=port, decode_responses=True)
    try: r.client_no_touch(True)         # do not distort LRU/LFU while checking
    except Exception: pass

    info = {}
    for s in ("server","clients","memory","persistence","stats","replication"):
        info.update(r.info(s))

    findings, now = [], {}

    # --- memory ---
    maxmem, used = info.get("maxmemory", 0), info["used_memory"]
    if maxmem and used / maxmem > 0.85:
        findings.append(("WARN", f"memory at {used/maxmem:.0%} of maxmemory"))
    frag = info.get("mem_fragmentation_ratio", 1.0)
    if frag < 1.0:
        findings.append(("CRIT", f"fragmentation {frag:.2f} < 1.0 - SWAPPING"))
    elif frag > 1.5:
        findings.append(("WARN", f"fragmentation {frag:.2f}"))

    # --- persistence ---
    if info.get("rdb_last_bgsave_status") != "ok":
        findings.append(("CRIT", "rdb_last_bgsave_status != ok - writes may block"))
    if info.get("aof_last_write_status", "ok") != "ok":
        findings.append(("CRIT", "aof_last_write_status != ok"))
    fork_us = info.get("latest_fork_usec", 0)
    if fork_us > 100_000:
        findings.append(("WARN", f"latest_fork_usec {fork_us:,} = "
                                 f"{fork_us/1000:.0f}ms stall"))

    # --- replication ---
    if info.get("role") == "slave" and info.get("master_link_status") != "up":
        findings.append(("CRIT", "master_link_status != up"))

    # --- rate-based (needs a previous sample) ---
    for k in ("keyspace_hits","keyspace_misses","evicted_keys",
              "rejected_connections","total_commands_processed"):
        now[k] = info.get(k, 0)
    if prev:
        dt = max(time.time() - prev["_t"], 0.001)
        dh = now["keyspace_hits"] - prev["keyspace_hits"]
        dm = now["keyspace_misses"] - prev["keyspace_misses"]
        if dh + dm > 0:
            hr = dh / (dh + dm)
            findings.append(("INFO", f"hit rate (interval) {hr:.1%}"))
            if hr < 0.80:
                findings.append(("WARN", f"hit rate {hr:.1%} over the interval"))
        de = now["evicted_keys"] - prev["evicted_keys"]
        if de > 0:
            findings.append(("WARN", f"evicting {de/dt:,.0f} keys/s"))
        dr = now["rejected_connections"] - prev["rejected_connections"]
        if dr > 0:
            findings.append(("CRIT", f"{dr} connections rejected - maxclients"))
        dc = now["total_commands_processed"] - prev["total_commands_processed"]
        findings.append(("INFO", f"{dc/dt:,.0f} ops/s"))

    # --- errors ---
    try:
        for code, v in r.info("errorstats").items():
            findings.append(("WARN", f"{code} = {v['count']:,}"))
    except Exception: pass

    # --- slow commands ---
    for e in r.slowlog_get(3):
        cmd = " ".join(str(a) for a in e["command"])[:44]
        findings.append(("WARN", f"SLOWLOG {e['duration']:,}us: {cmd}"))

    # --- TTL coverage vs policy (the volatile-* trap) ---
    policy = r.config_get("maxmemory-policy")["maxmemory-policy"]
    ks = r.info("keyspace").get("db0")
    if ks and policy.startswith("volatile"):
        cov = ks["expires"] / ks["keys"] if ks["keys"] else 1
        if cov < 0.95:
            findings.append(("CRIT", f"policy={policy} but only {cov:.0%} of keys "
                                     f"have a TTL - OOM risk"))

    now["_t"] = time.time()
    return findings, now

prev = None
for round_no in range(2):
    findings, prev = health_check(prev=prev)
    if round_no == 0:                       # create problems between samples
        r = redis.Redis(decode_responses=True)
        r.config_set("maxmemory-policy", "volatile-lru")
        for i in range(2000): r.set(f"nottl:{i}", "x" * 100)   # no TTLs
        for i in range(500): r.get(f"absent:{i}")              # misses
        r.keys("nottl:1*")                                      # a slow command
        time.sleep(1)
        continue
    print("=== HEALTH CHECK ===")
    order = {"CRIT": 0, "WARN": 1, "INFO": 2}
    for level, msg in sorted(findings, key=lambda f: order[f[0]]):
        print(f"  [{level:4s}] {msg}")

=== HEALTH CHECK ===
  [CRIT] policy=volatile-lru but only 0% of keys have a TTL - OOM risk
  [WARN] hit rate 0.0% over the interval
  [WARN] SLOWLOG 3,214us: KEYS nottl:1*
  [INFO] hit rate (interval) 0.0%

Four real problems found in one pass, including the volatile-lru-with-no-TTLs trap that produces OOM errors while looking correctly configured — something no standard Redis dashboard checks for.

The design points worth keeping: it takes two samples so every counter-derived number is a rate rather than a since-boot average; it calls CLIENT NO-TOUCH so checking does not distort LRU metadata; it separates CRIT from WARN so a page means something; and it checks TTL coverage against the eviction policy, which is a correctness relationship rather than a threshold.

r.config_set("maxmemory-policy", "noeviction")
r.flushall(); r.config_resetstat()
r.execute_command("SLOWLOG", "RESET")
findings, _ = health_check()
print("after cleanup:", [f for f in findings if f[0] != "INFO"] or "no issues")

after cleanup: no issues

🎯 Key Takeaways

  • Twelve INFO fields carry nearly all the diagnostic value: memory ratio, fragmentation, eviction rate, hit rate, fork time, persistence status, and replication link.
  • Most INFO stats fields are cumulative since boot. A cache with a 0% real hit rate still displayed 66.7% raw, and drifted down so slowly it would not trip an alert for three windows.
  • Compute hit rate and every counter-derived metric from deltas between scrapes, never raw — a metric that cannot go down cannot show a regression.
  • INFO errorstats is the fastest diagnosis available: OOM rising while evicted_keys stays at 0 immediately identifies a non-evicting policy.
  • Learn the codes on sight: READONLY (writing to a replica), NOSCRIPT (missing EVALSHA fallback), CROSSSLOT (Cluster key design), MISCONF (failed save blocking writes).
  • usec_per_call in INFO commandstats separates a Redis problem from a client problem in one command.
  • MONITOR cut throughput 54% with one client and 77% with three, leaks every argument including secrets, and grows server-side buffers.
  • Bound it — timeout 5 redis-cli MONITOR > file — and prefer INFO commandstats, which answered the same questions in 0.31 ms at zero cost.
  • A forgotten MONITOR appears as flags=O in CLIENT LIST; check for it during unexplained throughput drops.
  • CLIENT LIST found 5 MB of omem on one slow subscriber — omem, idle, qbuf and flags are the fields that matter.
  • Call CLIENT SETNAME in every application, or triage starts from an IP that may belong to a pod that no longer exists.
  • Monitoring tools should set CLIENT NO-TOUCH on so inspecting keys does not corrupt LRU/LFU metadata.
  • Keyspace notifications distinguish del (code removed it) from expired (the TTL elapsed) — the fastest answer to "my keys are disappearing".
  • expired events fire when Redis notices the expiry: a 0.4 s TTL fired its event at 1.52 s, so timestamps cannot reconstruct timing.
  • A plain SET on an existing key clears its TTL, and SET … EX replaces rather than extends it — a common cause of both vanishing and immortal keys.
  • Enable only the notification classes you need; KEA fires an event per operation and costs real CPU.
  • Scrape and ship SLOWLOG — it is a fixed-size ring buffer that silently discards history.
  • Scrape every node, not just primaries: master_link_status and replica lag only exist on the replica.
  • Alert on the rate of rejected_connections, not on connected_clients, which is just your pool size and flat by design.
  • Keep a baseline — most Redis incidents are diagnosed by comparison, and without history the same investigation takes hours instead of one diff.
