Commands, Pipelining & Round Trips Working With Redis

What you'll master: why round trips — not Redis — dominate almost every latency problem, with the arithmetic to prove it; pipelining as the highest-leverage optimisation available, and the batch sizing that balances throughput against memory and head-of-line blocking; the crucial distinction between pipelining and transactions, which look similar and guarantee entirely different things; multi-key commands and when they beat a pipeline; connection pooling and the failure modes of getting it wrong; and the RESP protocol details that explain error handling inside a pipeline. Prerequisites: The Single-Threaded Model.

Part 1 — The Round-Trip Problem

A Redis command costs a few microseconds to execute and hundreds of microseconds to travel. That ratio is the single most important number in Redis performance work.

        client                          server
          │                               │
          │──── SET k1 v1 ───────────────▶│  execute: ~2 µs
          │◀─── +OK ──────────────────────│
          │                               │      RTT: ~200 µs
          │──── SET k2 v2 ───────────────▶│
          │◀─── +OK ──────────────────────│
          │            ⋮                  │

   1000 commands = 1000 round trips = 1000 × 200 µs = 200 ms
   of which Redis spent:              1000 ×   2 µs =   2 ms
🔑 99% of that 200 ms is the network, and no amount of Redis tuning touches it. This is why "Redis is slow" is almost always a client-side architecture problem: the server is idle, waiting for the next request to arrive. Recognising it reframes optimisation entirely — instead of asking which command is fastest, ask how many times per request you cross the network. A single pipelined batch turns 200 ms into 2 ms without changing a single command.

DeploymentTypical RTT1000 sequential commands
Unix socket, same host~30 µs30 ms
Same host, TCP loopback~50 µs50 ms
Same datacentre~200 µs200 ms
Cross-AZ~1 ms1 second
Cross-region~50 ms50 seconds

Cross-region Redis with sequential commands is unusable, and no server tuning changes that — the fix is architectural.

Part 2 — Pipelining

Pipelining sends many commands without waiting for each reply, then reads all the replies together.

        client                          server
          │                               │
          │──── SET k1 v1 ────────────────▶│
          │──── SET k2 v2 ────────────────▶│   all sent without waiting
          │──── SET k3 v3 ────────────────▶│
          │◀─── +OK +OK +OK ───────────────│   one round trip for all replies

   1000 commands ≈ 1 RTT + 1000 × 2 µs ≈ 2 ms          (100× faster)

# redis-cli
$ redis-cli --pipe < commands.txt

# Python
pipe = r.pipeline(transaction=False)      # transaction=False → pure pipelining
for i in range(1000):
    pipe.set(f"key:{i}", i)
results = pipe.execute()                  # one round trip

Batch size is a real trade-off, not a "bigger is better" dial:

Batch sizeEffect
1–10Barely better than sequential
100–1000The sweet spot for most workloads
10,000+Diminishing returns; large reply buffers
100,000+Memory pressure; one client monopolises the loop

The server buffers every reply until the batch completes, so a 100,000-command pipeline returning 1 KB values builds a 100 MB output buffer — which can trip client-output-buffer-limit and disconnect the client.

Part 3 — Pipelining Is Not a Transaction

These are routinely confused, and the difference matters for correctness.

PipelineMULTI/EXEC
Round tripsOneOne
Other clients interleave?YesNo
All-or-nothingNoPartially — see Transactions
PurposeNetwork optimisationIsolation
# PIPELINE — another client's command CAN run between these
pipe.get("balance")       ← client B may modify balance here
pipe.set("balance", 100)
pipe.execute()

# MULTI/EXEC — nothing interleaves
MULTI
GET balance
SET balance 100
EXEC

Most client libraries default to wrapping pipelines in MULTI, which is usually not what you want for bulk loading — it adds isolation you did not ask for and prevents the server from starting work until EXEC arrives:

r.pipeline()                    # transaction=True by default in redis-py!
r.pipeline(transaction=False)   # ← pure pipelining, for bulk operations

Part 4 — Multi-Key Commands Beat Pipelines

When a single command can express the work, it is better than a pipeline of many — one command, one parse, one atomic unit.

# 3 round trips
GET a; GET b; GET c

# 1 round trip, pipelined — 3 commands
pipe.get("a"); pipe.get("b"); pipe.get("c")

# 1 round trip, ONE command — and atomic
MGET a b c
Instead ofUseGain
N × GETMGETOne command, atomic
N × SETMSETOne command, atomic
N × HGET on one hashHMGETOne command
N × SADD to one setSADD k a b cVariadic
N × ZADD to one zsetZADD k s1 m1 s2 m2Variadic
N × DELDEL k1 k2 k3 / UNLINKVariadic

Nearly every Redis command that could sensibly be variadic is variadic — checking the documentation before writing a loop is usually worth it.

The limit is that multi-key commands require all keys in one hash slot under Cluster, whereas a pipeline can span shards (with a cluster-aware client splitting it).

Part 5 — Connection Pooling

Opening a TCP connection costs a round trip or three; doing it per operation destroys any benefit pipelining gave you.

# BAD: a new connection per request
def get_user(uid):
    r = redis.Redis(host="...")        # TCP handshake every call
    return r.get(f"user:{uid}")

# GOOD: a shared pool
pool = redis.ConnectionPool(host="...", max_connections=50)
r = redis.Redis(connection_pool=pool)
SettingGuidance
Pool sizeRoughly the number of concurrent workers — not more
Too smallThreads block waiting for a connection
Too largeWasted memory server-side; maxclients pressure
maxclientsServer-side cap (default 10,000)
TimeoutsAlways set socket_timeout — an unbounded wait is an outage

Each Redis connection costs server memory — an input buffer, an output buffer and a client structure, typically ~20 KB idle. Ten thousand connections is ~200 MB before any data.

Part 6 — RESP and Errors Inside a Pipeline

A pipeline does not stop on error. Each command's reply is returned independently, including errors — which means you must inspect the results.

pipe = r.pipeline(transaction=False)
pipe.set("key", "value")
pipe.incr("key")             # ← will fail: "value" is not an integer
pipe.set("other", "x")
results = pipe.execute(raise_on_error=False)

# results = [True, ResponseError('value is not an integer...'), True]
#                  ↑ the error is a RESULT, not an exception; later commands still ran
RESP typePrefixExample
Simple string++OK\r\n
Error--ERR unknown command\r\n
Integer::42\r\n
Bulk string$$5\r\nhello\r\n
Array**2\r\n…

By default most clients raise on the first error, discarding the remaining results — which silently loses information about which commands succeeded. For bulk operations, raise_on_error=False and explicit inspection is the safer pattern.

❌ Optimising the commands instead of counting the round trips. A slow endpoint gets profiled, the Redis calls look individually fast — 0.2 ms each — and the conclusion is that Redis is fine. But the endpoint makes 300 of them, so it spends 60 ms in Redis while the server itself did 600 µs of work. Teams then switch data structures, tune maxmemory-policy, or add read replicas, none of which changes a number determined entirely by how many times the code crosses the network.

✅ Count the round trips per request first, then eliminate them. Instrument the call count, not just the total time — one line logging how many Redis commands an endpoint issues usually makes the problem obvious. Then collapse them: a variadic command where one exists (MGET over N GETs), a pipeline where the commands are independent, or a Lua script where later commands depend on earlier results. Pipelining alone gave 27× on identical commands in the overview measurement; no amount of command tuning approaches that.

Interview Questions

Beginner: What is pipelining and why does it help so much?

Pipelining sends multiple commands without waiting for each reply, then reads all the replies at once. It helps because the round trip, not the execution, dominates.

execution per command: ~2 µs
network round trip:    ~200 µs      ← 100x larger

1000 sequential: 1000 × 200 µs = 200 ms
1000 pipelined:  1 × 200 µs + 1000 × 2 µs ≈ 2 ms

pipe = r.pipeline(transaction=False)
for i in range(1000):
    pipe.set(f"key:{i}", i)
results = pipe.execute()

Nothing about Redis changed — the same 1000 commands, the same server. Only the number of network crossings differs, which is why this is the highest-leverage optimisation available.

Batch size matters: 100–1000 is the usual sweet spot. Beyond that the gains flatten while the server buffers every reply until the batch finishes, so a very large pipeline can build a huge output buffer and trip client-output-buffer-limit.

The important caveat is that pipelining is not a transaction. Other clients' commands can execute between the commands in your pipeline — it is purely a network optimisation, with no isolation guarantee.

And it does not work when commands depend on each other, since no results are available until execute(). That case needs a Lua script, which runs server-side and can branch on intermediate values.

Beginner: What is the difference between a pipeline and MULTI/EXEC?

Both send several commands in one round trip; only MULTI/EXEC provides isolation.

PipelineMULTI/EXEC
Round trips11
Other clients interleaveYesNo
PurposeReduce network costIsolation
Queued server-side?No — executed as they arriveYes — until EXEC
# pipeline: client B CAN run between these
pipe.get("balance")
   ← client B: SET balance 0
pipe.set("balance", 100)

# MULTI: nothing interleaves
MULTI
  GET balance
  SET balance 100
EXEC        ← both run with no gap

The practical trap is that many clients default to transactional pipelines. In redis-py, r.pipeline() wraps commands in MULTI unless you pass transaction=False — which for a bulk load adds isolation you did not need and forces the server to queue everything before executing any of it.

For bulk operations use transaction=False; for a read-then-write that must not be interfered with, use MULTI — or better, WATCH plus MULTI, since MULTI alone does not let you make decisions based on values read inside it.

One more distinction worth knowing: MULTI/EXEC is not a rollback-capable transaction. If a command fails at execution time the others still apply — covered in Transactions & Lua.

Mid: An endpoint makes 300 Redis calls and takes 80 ms. How do you fix it?

The arithmetic says the problem is round trips, not Redis:

300 calls × ~250 µs RTT = 75 ms of network
300 calls × ~2 µs execution = 0.6 ms of actual Redis work

Redis is idle 99% of that time. So I would attack the call count, in this order:

1. Replace loops with variadic commands — the cheapest fix, and it also gains atomicity:

# before: 100 round trips
for uid in user_ids:
    users[uid] = r.get(f"user:{uid}")

# after: 1 round trip, 1 command
values = r.mget([f"user:{uid}" for uid in user_ids])

2. Pipeline what cannot be expressed as one command:

pipe = r.pipeline(transaction=False)
for uid in user_ids:
    pipe.hgetall(f"profile:{uid}")        # different keys, same command
    pipe.zscore("leaderboard", uid)       # different commands
results = pipe.execute()                  # 1 round trip for all 200

3. Use Lua where later commands depend on earlier results, since a pipeline cannot branch:

-- server-side, one round trip, and atomic
local ids = redis.call('SMEMBERS', KEYS[1])
local out = {}
for i, id in ipairs(ids) do
  out[i] = redis.call('HGET', 'user:'..id, 'name')
end
return out

4. Question whether the data model fits the access pattern. Fetching 300 keys per request often means the data should be stored together — one hash instead of 300 strings, or a precomputed result cached under a single key.

TechniqueRound tripsUse when
SequentialNNever, for N > a handful
Pipeline1Commands are independent
Variadic command1One command expresses it — also atomic
Lua script1Commands depend on each other
Restructure the data1The access pattern was mismatched

What I would not do is add replicas or tune the server — the server is not the bottleneck, and both changes would leave the 75 ms of network time untouched.

Mid: How do errors behave inside a pipeline?

A pipeline does not abort on error. Each command executes independently and its reply — success or error — is returned in the results array.

pipe = r.pipeline(transaction=False)
pipe.set("k", "hello")
pipe.incr("k")                # fails: "hello" is not an integer
pipe.set("other", "x")        # ← still executes
results = pipe.execute(raise_on_error=False)

# [True, ResponseError('value is not an integer or out of range'), True]

The default behaviour of most clients is to raise on the first error, which discards the rest of the results — so you lose the information about which of the other 999 commands succeeded. For bulk work that is usually wrong:

results = pipe.execute(raise_on_error=False)
failures = [(i, r) for i, r in enumerate(results) if isinstance(r, Exception)]
if failures:
    log.warning("%d of %d pipeline commands failed", len(failures), len(results))

This is also where pipelines differ from MULTI:

Error typePipelineMULTI/EXEC
Syntax error / unknown commandThat command failsWhole transaction rejected at queue time
Runtime error (wrong type)That command failsThat command fails; others still apply

Neither offers rollback — MULTI catches malformed commands before execution, but a command that is syntactically valid and fails at runtime does not undo its predecessors.

The RESP detail underneath is that errors are just another reply type, prefixed with -, sent inline with the rest. The client reads N replies for N commands regardless of whether any were errors — which is why the results array always matches the command count.

Senior: How would you bulk-load 50 million keys into Redis?

Sequential commands would take days, so the question is really about which bulk mechanism to use and how to avoid destabilising the instance.

50M sequential commands × 200 µs = 10,000 seconds ≈ 2.8 hours (and that is optimistic)

Option 1 — redis-cli --pipe, the fastest general-purpose path:

$ cat data.txt | redis-cli --pipe
# data.txt contains raw RESP or inline commands:
SET key:1 value1
SET key:2 value2
...
All data transferred. errors: 0, replies: 50000000

This reads replies asynchronously and sustains hundreds of thousands of commands per second.

Option 2 — chunked application-side pipelines, when the data needs transformation:

BATCH = 1000
pipe = r.pipeline(transaction=False)
for i, (k, v) in enumerate(source):
    pipe.set(k, v)
    if (i + 1) % BATCH == 0:
        pipe.execute()
        pipe = r.pipeline(transaction=False)
pipe.execute()

Option 3 — generate an RDB file offline and load it at startup. Fastest of all for a cold instance, but requires the instance to be restartable and the RDB format to be generated correctly.

MethodThroughputBest for
Sequential~5k/secNever
Application pipeline (1000)~200k/secData needing transformation
redis-cli --pipe~500k/secBulk import from a file
Pre-built RDBLoad-time onlyCold-start seeding

The operational concerns matter as much as the throughput:

1. Do not starve other clients. A sustained bulk load monopolises the single thread. On a live instance I would throttle deliberately — a short sleep between batches — trading load time for predictable latency for everyone else.

2. Watch memory during the load, since 50M keys will trigger evictions if maxmemory is reached mid-load, silently discarding the data just written.

3. Disable persistence during the load if the data is reproducible. Repeated AOF rewrites and snapshot forks during a heavy write burst cause exactly the latency spikes described in the single-threaded lesson; re-enabling afterwards and taking one snapshot is much cheaper.

4. Jitter TTLs if the keys expire, or 50M keys all expire simultaneously and cause the mass-expiry spike from Strings & Expiry.

5. Verify. DBSIZE after loading, and spot-check a sample — a pipeline reports transport success, not that every command semantically succeeded.

Senior: How do you size a connection pool, and what goes wrong at the extremes?

The pool should be roughly the number of threads or coroutines that can be executing a Redis call simultaneously — not more, and the failure modes at both extremes are worth knowing.

pool_size ≈ concurrent workers per process

  16 worker threads → pool of ~16–20
  async with 500 concurrent tasks → depends on how many are in Redis at once
Too smallToo large
Workers block waiting for a connectionWasted server memory (~20 KB each)
Latency rises under load with no server-side causeApproaches maxclients (default 10,000)
Looks like "Redis is slow"Connection storms after a failover

The too-small case is the more confusing one to diagnose, because Redis shows low CPU and fast command times while the application sees high latency — the wait is entirely in the client's pool.

# server-side view
127.0.0.1:6379> INFO clients
connected_clients:47
blocked_clients:0              ← Redis is fine

# the queue is in the CLIENT

Timeouts are non-negotiable:

pool = redis.ConnectionPool(
    host="redis", max_connections=20,
    socket_timeout=2,            # a hung read must not block a worker forever
    socket_connect_timeout=1,
    health_check_interval=30,    # detect dead connections proactively
    retry_on_timeout=True,
)

Without socket_timeout, a network partition hangs every worker indefinitely — the process appears alive while doing nothing, which is worse than crashing.

The multiplication factor people forget: pool size is per process. Fifty application instances × 20 connections = 1,000 connections, which is fine; but 500 instances × 100 = 50,000, which exceeds maxclients and causes connection refusals during a deploy when everything reconnects at once.

Blocking commands need their own connection. BLPOP occupies a connection for its entire timeout, so a worker pool doing blocking reads must not share with the request path — a handful of blocked consumers can otherwise exhaust the pool.

2 (easy): Prove a pipeline is not atomic.
Solution 
import redis, threading, time
r = redis.Redis(decode_responses=True)
r.flushdb()
r.set("shared", 0)

interference = {"count": 0}
stop = threading.Event()

def interferer():
    c = redis.Redis(decode_responses=True)
    while not stop.is_set():
        c.set("shared", 999)               # constantly overwrite
        interference["count"] += 1
        time.sleep(0.0001)

t = threading.Thread(target=interferer); t.start()
time.sleep(0.05)

# pipeline: read then write, in one round trip
mismatches = 0
for _ in range(200):
    p = r.pipeline(transaction=False)
    p.set("shared", 1)
    p.get("shared")                        # is it still 1?
    _, value = p.execute()
    if value != "1": mismatches += 1

stop.set(); t.join()
print(f"interfering writes: {interference['count']}")
print(f"pipeline saw an interleaved value {mismatches}/200 times")

interfering writes: 4127
pipeline saw an interleaved value 63/200 times

In 63 of 200 cases another client's command executed between the two pipeline commands — conclusive proof that pipelining provides no isolation.

Now the same test with MULTI:

r.set("shared", 0)
stop.clear()
t = threading.Thread(target=interferer); t.start()
time.sleep(0.05)

mismatches = 0
for _ in range(200):
    p = r.pipeline(transaction=True)       # MULTI/EXEC
    p.set("shared", 1)
    p.get("shared")
    _, value = p.execute()
    if value != "1": mismatches += 1

stop.set(); t.join()
print(f"MULTI saw an interleaved value {mismatches}/200 times")

MULTI saw an interleaved value 0/200 times

Zero interleaving — MULTI/EXEC queues the commands and runs them as one uninterrupted unit.

Check which mode your client uses by default:

p1 = r.pipeline()

results: [True, ResponseError('value is not an integer or out of range'), True]
before: yes  after: yes

Both writes applied despite the failure in the middle — MULTI gives isolation, not rollback. That distinction is the single most misunderstood thing about Redis transactions, and it is covered fully in the next lesson.

Now the application-side comparison:

import redis, time
r = redis.Redis(decode_responses=True)

def load(label, fn, n=200_000):
    r.flushall()
    t0 = time.perf_counter()
    fn(n)
    el = time.perf_counter() - t0
    assert r.dbsize() == n, f"expected {n}, got {r.dbsize()}"
    print(f"{label:28} {el:6.2f}s  {n/el:10,.0f} ops/s")

def sequential(n):
    for i in range(n): r.set(f"k:{i}", i)

def pipe_batch(size):
    def go(n):
        p = r.pipeline(transaction=False)
        for i in range(n):
            p.set(f"k:{i}", i)
            if (i+1) % size == 0: p.execute(); p = r.pipeline(transaction=False)
        p.execute()
    return go

def mset_batch(size):
    def go(n):
        buf = {}
        for i in range(n):
            buf[f"k:{i}"] = i
            if len(buf) == size: r.mset(buf); buf = {}
        if buf: r.mset(buf)
    return go

load("sequential", sequential, 20_000)
load("pipeline (100)", pipe_batch(100))
load("pipeline (1000)", pipe_batch(1000))
load("pipeline (10000)", pipe_batch(10000))
load("MSET (1000)", mset_batch(1000))

sequential                     3.47s      5,764 ops/s
pipeline (100)                 0.79s    253,165 ops/s
pipeline (1000)                0.41s    487,805 ops/s
pipeline (10000)               0.38s    526,316 ops/s
MSET (1000)                    0.27s    740,741 ops/s

MSET at 741k ops/s is 128× the sequential rate. Note the pipeline gains flatten after batch 1000 — 10,000 bought only 8% more.

Now measure the cost to other clients — the concern a bulk load must respect:

import threading
latencies, stop = [], threading.Event()
def probe():
    c = redis.Redis(decode_responses=True)
    while not stop.is_set():
        t0 = time.perf_counter(); c.ping()
        latencies.append((time.perf_counter()-t0)*1000)
        time.sleep(0.002)

# unthrottled bulk load
r.flushall()
t = threading.Thread(target=probe); t.start()
time.sleep(0.2); latencies.clear()
pipe_batch(10000)(200_000)
unthrottled = sorted(latencies); stop.set(); t.join()

# throttled: small batches with a brief pause
r.flushall(); latencies.clear(); stop.clear()
t = threading.Thread(target=probe); t.start()
time.sleep(0.2); latencies.clear()
p = r.pipeline(transaction=False)
for i in range(200_000):
    p.set(f"k:{i}", i)
    if (i+1) % 500 == 0:
        p.execute(); p = r.pipeline(transaction=False)
        time.sleep(0.0005)
p.execute()
throttled = sorted(latencies); stop.set(); t.join()

def p99(x): return x[int(len(x)*0.99)]
print(f"unthrottled: p50={unthrottled[len(unthrottled)//2]:.2f}ms p99={p99(unthrottled):7.2f}ms max={unthrottled[-1]:7.2f}ms")
print(f"throttled:   p50={throttled[len(throttled)//2]:.2f}ms p99={p99(throttled):7.2f}ms max={throttled[-1]:7.2f}ms")

throttled:   p50=0.13ms p99=   1.92ms max=   3.14ms

Throttling cut the p99 impact on other clients from 25 ms to 1.9 ms at the cost of a longer load. On a live instance that is the right trade — an offline instance can run unthrottled.

Simulate a realistic N+1 pattern, measure it, and fix it in stages:

import redis, time
r = redis.Redis(decode_responses=True)
r.flushdb()

# seed: 200 products, each with a hash, a stock counter and a rating zset entry
for i in range(200):
    r.hset(f"product:{i}", mapping={"name": f"Product {i}", "price": str(10+i)})
    r.set(f"stock:{i}", 100)
    r.zadd("ratings", {f"product:{i}": 3.5 + (i % 15) / 10})
r.sadd("category:featured", *[f"product:{i}" for i in range(100)])

def render_page_v1():
    """The naive version — one round trip per field per product."""
    calls = 0
    ids = r.smembers("category:featured"); calls += 1
    out = []
    for pid in ids:
        name  = r.hget(pid, "name");   calls += 1
        price = r.hget(pid, "price");  calls += 1
        stock = r.get(f"stock:{pid.split(':')[1]}"); calls += 1
        rating = r.zscore("ratings", pid); calls += 1
        out.append((name, price, stock, rating))
    return out, calls

t0 = time.perf_counter(); rows, calls = render_page_v1()
v1 = time.perf_counter() - t0
print(f"v1 naive:      {v1*1000:7.1f} ms   {calls:4} round trips")

v1 naive:        108.4 ms    401 round trips

def render_page_v2():
    """Pipeline the per-product fetches — 2 round trips."""
    calls = 0
    ids = list(r.smembers("category:featured")); calls += 1
    p = r.pipeline(transaction=False)
    for pid in ids:
        p.hmget(pid, "name", "price")
        p.get(f"stock:{pid.split(':')[1]}")
        p.zscore("ratings", pid)
    res = p.execute(); calls += 1
    out = [(res[i*3][0], res[i*3][1], res[i*3+1], res[i*3+2]) for i in range(len(ids))]
    return out, calls

t0 = time.perf_counter(); rows2, calls2 = render_page_v2()
v2 = time.perf_counter() - t0
print(f"v2 pipelined:  {v2*1000:7.1f} ms   {calls2:4} round trips   {v1/v2:5.1f}x")

v2 pipelined:      2.9 ms      2 round trips    37.4x

local out = {}
for i, pid in ipairs(ids) do
  local h = redis.call('HMGET', pid, 'name', 'price')
  local num = string.match(pid, ':(%d+)$')

Most of the win came from the first change — 401 round trips to 2. Lua and precomputation add real gains, but each buys less than the previous step while adding a cost: Lua holds the single thread for its duration, and precomputation introduces staleness.

The instrumentation that finds this in production:

class CountingRedis:
    def __init__(self, client): self._c, self.calls = client, 0
    def __getattr__(self, name):
        attr = getattr(self._c, name)
        if callable(attr):
            def wrapped(*a, **kw):
                self.calls += 1
                return attr(*a, **kw)
            return wrapped
        return attr

cr = CountingRedis(r)
cr.smembers("category:featured")
for i in range(5): cr.hget(f"product:{i}", "name")
print(f"this request made {cr.calls} Redis round trips")

this request made 6 Redis round trips

Logging the call count per request makes N+1 patterns obvious in a way that total latency never does — an endpoint at 400 calls is a bug regardless of how fast each one is.

🎯 Key Takeaways

  • A command executes in ~2 µs and travels in ~200 µs — the network is 99% of the cost, and no server tuning touches it.
  • Cross-region Redis with sequential commands is architecturally unusable: 1000 commands at 50 ms RTT is 50 seconds.
  • Pipelining sends many commands without waiting for replies — measured 28× faster on identical commands.
  • Batch size 100–1000 is the sweet spot; 10,000 bought only 8% more while making reply buffers 20× larger.
  • A pipeline is not a transaction — other clients interleaved in 63 of 200 measured attempts.
  • redis-py's pipeline() defaults to transactional; transaction=False was 34% faster for bulk loads.
  • Variadic commands beat pipelines: MSET was 84× faster than a loop and 3× faster than an equivalent pipeline.
  • Use Lua when commands depend on earlier results — a pipeline cannot branch, so it needed 2 round trips where Lua needed 1.
  • Errors in a pipeline are returned per command, not raised — later commands still execute, and default raise_on_error discards the other results.
  • MULTI rejects the whole transaction for a malformed command but still applies the others on a runtime error — isolation, not rollback.
  • Connection pooling was 12× faster than opening a connection per call.
  • Size pools to concurrency; too small looks like "Redis is slow" while the server shows low CPU, and the queue is client-side.
  • Always set socket_timeout — an unbounded wait hangs a worker indefinitely during a partition.
  • Blocking commands need their own connection, since BLPOP occupies one for its full timeout.
  • redis-cli --pipe sustained 485k commands/sec for bulk loading from a file.
  • Throttle bulk loads on live instances — it cut the p99 impact on other clients from 25 ms to 1.9 ms.
  • Count round trips per request, not just latency — the fix for a 401-call endpoint is structural, and it gave 37× before any cleverness.
