The Single-Threaded Model Foundations

What you'll master: the event loop that processes every command on one thread, and why that is a deliberate design choice rather than a limitation; the two guarantees it buys for free — atomicity without locks, and predictable ordering — and the one liability it creates, head-of-line blocking; what Redis does use extra threads for, which is not command execution; how to find and eliminate the slow commands that stall every client; the fork-based operations that pause the loop for reasons unrelated to commands; and how to scale past one core when you genuinely need to. Prerequisites: What Redis Actually Is, Hashes, Lists & Sets.

Part 1 — One Loop, One Command at a Time

Redis runs a single event loop. It multiplexes thousands of connections with epoll, but executes exactly one command at a time.

          ┌──────────────── event loop (ONE thread) ────────────────┐
          │                                                          │
 sockets  │  epoll_wait  →  read request  →  parse  →  EXECUTE  →   │  → write reply
 (10,000) │       ▲                                        │         │
          │       └────────────────────────────────────────┘         │
          └──────────────────────────────────────────────────────────┘

 10,000 concurrent CONNECTIONS, 1 command executing at any instant
🔑 Concurrency and parallelism are different things, and Redis chose one deliberately. It is highly concurrent — tens of thousands of connections make progress — but not parallel: no two commands ever run simultaneously. That choice eliminates mutexes, condition variables, cache-line contention between cores and every class of data race, which is why a single Redis core outperforms many multi-threaded stores on small operations. The price is that the loop is a shared resource: one expensive command stalls everyone, and no amount of hardware fixes it.

ConsequenceEffect
Every command is atomicNo locks needed — nothing can interleave
Deterministic orderingCommands execute in arrival order per connection
No lock overhead~100k+ ops/sec on one core
Head-of-line blockingOne slow command stalls every client
One core per instanceScale by sharding, not by bigger machines

Part 2 — Atomicity for Free

Because no two commands interleave, every single command is atomic without any coordination:

# 1000 clients all running this simultaneously
INCR counter

# result: EXACTLY 1000. No lost updates, no locks, no CAS retry loop.

The atomicity boundary is one command, which is precisely why read-modify-write across two commands is not safe:

GET counter      → "5"        ← another client can execute between these two
SET counter 6                    lines; that update is lost
ScopeAtomic?Mechanism
A single command✅ AlwaysSingle-threaded execution
Multi-key command (MSET, SINTERSTORE)✅ YesStill one command
MULTI/EXEC✅ YesQueued, then run without interruption
A Lua script✅ YesRuns to completion as one unit
Two separate commands❌ NoOthers interleave between them
A pipeline❌ NoBatching is not atomicity

Pipelining and atomicity are commonly confused. A pipeline sends many commands in one round trip, but other clients' commands can still be interleaved between them — it is a network optimisation, not a transaction.

Part 3 — Head-of-Line Blocking

The liability is that every client shares one execution resource. A command taking 200 ms adds 200 ms to every other client's latency, regardless of how trivial their request is.

time →

client A:  KEYS *  ────────────────────────────────  (1200 ms)
client B:      GET foo ......................waiting......  then 0.1 ms
client C:        SET bar ....................waiting......  then 0.1 ms
client D:          INCR n ...................waiting......  then 0.1 ms

           every client's p99 becomes 1200 ms
Dangerous commandCostSafe alternative
KEYS patternO(n) over the whole keyspaceSCAN
HGETALL / SMEMBERS on large collectionsO(n)HSCAN / SSCAN, or targeted reads
LRANGE key 0 -1O(n)Paginate
DEL on a huge valueO(n) to freeUNLINK
FLUSHALL / FLUSHDBO(n)FLUSHALL ASYNC
SORT on a big collectionO(n log n)Pre-sort with a sorted set
A long Lua scriptBlocks until it returnsKeep scripts short; chunk the work
ZUNIONSTORE over huge setsO(n)Precompute; bound the inputs

The slow log is the diagnostic tool, and it records execution time excluding network — so anything appearing there genuinely held the loop:

CONFIG SET slowlog-log-slower-than 10000    # microseconds — 10ms
SLOWLOG GET 10
SLOWLOG RESET
SLOWLOG LEN

Part 4 — What Redis Actually Threads

"Single-threaded" describes command execution. Redis has used background threads for years, and Redis 6 added threaded I/O — neither makes command execution parallel.

WorkThreadSince
Command executionMain loop onlyAlways
Reading/writing socketsI/O threads (optional)Redis 6
UNLINK — freeing memoryBackgroundRedis 4
FLUSHALL ASYNCBackgroundRedis 4
AOF fsyncBackgroundLong-standing
RDB/AOF rewriteForked processAlways
Closing large client buffersBackgroundRedis 4
# threaded I/O — parses/writes sockets in parallel, execution stays serial
io-threads 4
io-threads-do-reads yes

Threaded I/O helps only when the bottleneck is socket work — large values, very high connection counts, or TLS. It does nothing for a workload bottlenecked on command execution, and enabling it on a small instance can be a net loss.

Part 5 — Fork: The Other Source of Pauses

Snapshots and AOF rewrites call fork(). The child does the writing, but the fork itself pauses the parent while the kernel copies the page tables.

fork() pause ≈ proportional to the number of memory PAGES, not the data size

  1 GB dataset   →  ~10–20 ms pause
 10 GB dataset   →  ~100–200 ms pause
 50 GB dataset   →  ~500 ms–1 s pause     ← every client stalls for this long
FactorEffect on fork time
Dataset sizeLinear — more pages to copy
Transparent Huge Pages (THP)Dramatically worse — disable it
Virtualised environmentsSlower page-table operations than bare metal
Write rate during the saveMore copy-on-write faults afterwards
# THP makes both fork latency and copy-on-write far worse
$ echo never > /sys/kernel/mm/transparent_hugepage/enabled

# check the last fork's cost
127.0.0.1:6379> INFO stats | grep latest_fork_usec
latest_fork_usec:184213          ← 184 ms of blocking

latest_fork_usec is a metric worth alerting on — a growing value predicts the latency spikes users will eventually notice.

Part 6 — Scaling Past One Core

ApproachHowTrade-off
Reduce round tripsPipelining, MGET, LuaDo this first — usually the real problem
Read replicasRoute reads to replicasEventual consistency on reads
Multiple instances on one hostOne per core, shard client-sideManual sharding; no cross-instance ops
Redis ClusterAutomatic sharding across nodesNo multi-key ops across slots
Threaded I/Oio-threads 4Only helps if I/O-bound

The order matters. Teams reach for Cluster when their actual problem is 10,000 sequential round trips per request — sharding a workload that is not CPU-bound adds operational complexity and changes nothing.

# is Redis actually CPU-bound? check before sharding
127.0.0.1:6379> INFO cpu
used_cpu_sys:412.83
used_cpu_user:1847.22          ← compare against wall-clock time

$ redis-cli --stat
------- data ------ --------------------- load -------------------- - child -
keys       mem      clients blocked requests            connections
1000000    1.02G    52      0       1847221 (+1204)     238

❌ Adding CPU cores or enabling io-threads to fix Redis latency. The instance shows high latency, the host has 16 idle cores, and giving Redis more of them looks obviously correct. But command execution is serial by design — extra cores cannot execute commands in parallel, and io-threads only accelerates socket reads and writes. If the cause is one HGETALL over a large hash, the machine could have a thousand cores and every client would still wait behind it.

✅ Find what is holding the loop before changing hardware. The slow log names the exact command and its microsecond cost, --latency-history shows when the spikes occur, and --bigkeys finds the collections that make O(n) commands expensive. In practice the fix is almost always one of: replace an O(n) command with a bounded one, batch round trips into a pipeline, or split a giant key. Only once the loop is genuinely saturated by legitimate work does sharding across instances become the right answer — and then it is Cluster or client-side sharding, not more cores.

Interview Questions

Beginner: Why is Redis single-threaded, and is that not a limitation?

It is a deliberate trade. Redis executes every command on one event loop, which removes an entire category of cost that multi-threaded stores must pay.

What single-threading removesEffect
Mutexes and condition variablesNo lock acquisition on the hot path
Context switching between threadsNo scheduler overhead
Cache-line contention between coresData stays in one core's cache
Data racesAtomicity for free on every command

The design bet is that Redis is rarely CPU-bound. Operations are O(1) or O(log n) on in-memory structures, taking microseconds; the dominant cost is the network round trip. Adding threads would introduce coordination overhead to speed up something that was never the bottleneck.

one command executing:  ~1–10 microseconds
one network round trip: ~100–500 microseconds     ← 50x larger

It is concurrent but not parallel — epoll multiplexes tens of thousands of connections, all making progress, while exactly one command executes at any instant.

The genuine limitation is head-of-line blocking. A single O(n) command stalls every client, and no hardware fixes it — which is why avoiding KEYS, HGETALL on large hashes and similar commands is not a style preference but a correctness requirement for latency.

And Redis is not entirely single-threaded — background threads handle UNLINK, AOF fsync and lazy frees, and Redis 6 added optional I/O threads for socket work. Command execution remains serial in all cases.

Beginner: What does single-threading guarantee about atomicity?

Every individual command is atomic, with no locking required — because nothing can interleave with it.

# 1000 concurrent clients
INCR counter
→ counter is EXACTLY 1000. No lost updates.

The boundary is one command, and that is the critical detail. Two commands are not atomic together:

GET counter   → "5"
   ← ANOTHER CLIENT'S COMMAND CAN RUN HERE
SET counter 6                    that client's increment is lost
UnitAtomic?
Single command✅ Always
Multi-key command (MSET, SINTERSTORE)✅ Still one command
MULTI/EXEC✅ Executed without interruption
Lua script✅ Runs to completion as one unit
Two separate commands❌ No
Pipeline❌ No — batching, not atomicity

The pipeline confusion is worth stating explicitly: a pipeline sends N commands in one round trip, but Redis may execute another client's command between any two of them. It is purely a network optimisation.

So the practical rule is: if a decision depends on a value you just read, you need MULTI/WATCH or a Lua script. If the operation can be expressed as a single command — INCR, SETNX, ZADD GT, LMOVE — it is already atomic and nothing further is needed.

Mid: Redis latency spiked to 500 ms. How do you diagnose it?

I would work through the causes in order of likelihood, because the single-threaded model narrows the possibilities considerably.

1. The slow log — a blocking command is the most common cause:

127.0.0.1:6379> SLOWLOG GET 10
1) 1) (integer) 14
   2) (integer) 1755000000
   3) (integer) 487221          ← 487 ms of execution
   4) 1) "HGETALL"
      2) "sessions:all"

Anything here held the loop for that entire duration, blocking every other client.

2. Fork pauses — check whether a save was running:

127.0.0.1:6379> INFO stats | grep latest_fork_usec
latest_fork_usec:512847         ← 512 ms, matches the spike
127.0.0.1:6379> INFO persistence | grep -E "rdb_bgsave_in_progress|aof_rewrite_in_progress"

3. Big keys — the cause behind most slow commands:

$ redis-cli --bigkeys
[00.00%] Biggest hash found so far 'sessions:all' with 2000000 fields

4. Memory pressure — swapping or eviction storms:

127.0.0.1:6379> INFO memory | grep -E "used_memory_human|maxmemory_human|mem_fragmentation_ratio"
127.0.0.1:6379> INFO stats | grep evicted_keys

A fragmentation ratio well above 1.5, or a rising eviction count, both point at memory as the cause.

5. Distinguish server latency from network latency, which changes the entire investigation:

$ redis-cli --latency          # includes network
$ redis-cli --intrinsic-latency 100   # the server's own scheduling latency, no network

If intrinsic latency is high, the problem is the host — CPU steal on a noisy hypervisor, THP, or swap — not Redis.

EvidenceCauseFix
Slow log entryO(n) commandReplace with a bounded command
High latest_fork_usecSnapshot forkDisable THP; save on a replica
--bigkeys finds a huge keyStructuralShard the key
Rising evicted_keysMemory pressureMore memory, or reduce the working set
High intrinsic latencyHost problemTHP, swap, CPU steal

What I would not do first is add cores — none of these causes is addressed by more CPU.

Mid: What does Redis use threads for, and should you enable io-threads?

Redis has had background threads since version 4, and Redis 6 added optional I/O threading. Neither makes command execution parallel.

WorkWhere it runs
Command executionMain loop — always serial
Socket read/parse and reply writeI/O threads, if enabled
UNLINK, lazy freeBackground thread
AOF fsyncBackground thread
RDB save / AOF rewriteForked child process
io-threads 4                 # 1 = disabled (default)
io-threads-do-reads yes      # also thread the read/parse side

Whether to enable it depends entirely on where the time goes. I/O threads help when the loop spends its time on socket work rather than execution:

Enable whenDo not bother when
Large values (KBs) being transferredSmall values, simple commands
Very high connection countsFew connections
TLS enabled (encryption is I/O-side work)Plaintext, low throughput
The instance is network-saturatedThe instance is command-saturated

The guidance is to set it to fewer than the number of cores — typically 2–4 — and to measure before and after. On a small instance the coordination overhead can make it slower.

The important framing: io-threads raises the ceiling on throughput for I/O-heavy workloads, but does nothing for latency caused by a slow command. If the slow log shows a 200 ms HGETALL, threading the sockets changes nothing at all — the loop is still busy for 200 ms.

Senior: How do fork-based operations affect latency, and how do you mitigate them?

RDB snapshots and AOF rewrites call fork(). The child does the work, but the fork itself blocks the parent while the kernel duplicates page tables — and that pause scales with the memory footprint.

fork pause ∝ number of memory PAGES

  1 GB   →  ~10–20 ms
 10 GB   →  ~100–200 ms
 50 GB   →  ~500 ms – 1 s      every client stalls

There is a second cost after the fork: copy-on-write. Parent and child share pages until one writes; each write during the save duplicates a page. A write-heavy instance can therefore approach 2× its memory footprint mid-save, which is why sizing must leave headroom.

MitigationEffect
Disable Transparent Huge PagesLargest single win — THP makes both fork and CoW dramatically worse
Snapshot on a replica, not the masterMoves the pause off the serving path entirely
Schedule saves off-peakReduces user impact
Smaller instances (shard)Fork time is proportional to size
AOF everysec without frequent rewritesFewer forks overall
Bare metal over virtualisedPage-table operations are faster
$ echo never > /sys/kernel/mm/transparent_hugepage/enabled
$ echo never > /sys/kernel/mm/transparent_hugepage/defrag

127.0.0.1:6379> INFO stats | grep latest_fork_usec
latest_fork_usec:18432          ← 18 ms on a 1 GB instance, THP off

THP deserves the emphasis because it is enabled by default on many distributions and Redis logs a warning about it at startup that is routinely ignored. With 2 MB huge pages, a single byte written copies 2 MB instead of 4 KB — a 512× amplification of copy-on-write cost.

The architectural mitigation is to snapshot on a replica. The master serves traffic with persistence disabled; a replica takes the snapshots and absorbs the fork pauses. The trade is that a master crash falls back to the replica's slightly older data, which for a cache is entirely acceptable.

What I would monitor: latest_fork_usec over time, since it grows with the dataset and predicts the pause users will eventually notice. An alert at, say, 100 ms gives warning before it becomes visible.

Senior: An instance is saturating one core. Walk through how you would scale it.

I would confirm it is genuinely CPU-bound first, because it usually is not, and then choose the cheapest option that addresses the real constraint.

Step 0 — verify the diagnosis:

$ redis-cli --stat                     # ops/sec and connection count
127.0.0.1:6379> INFO commandstats      # which commands dominate CPU time
127.0.0.1:6379> SLOWLOG GET 10         # anything blocking?
$ top -p $(pgrep redis-server)         # is the process actually at 100% of one core?

If CPU is at 40% and latency is high, the problem is a slow command or the network, and sharding would change nothing.

Step 1 — eliminate round trips, which is usually the actual issue:

1000 sequential GETs → 1000 round trips → ~200 ms
1000 pipelined GETs  → 1 round trip     → ~2 ms

This costs nothing operationally and frequently removes the apparent capacity problem entirely. Multi-key commands (MGET, HMGET) and Lua scripts do the same for multi-step logic.

Step 2 — check for one expensive command dominating:

127.0.0.1:6379> INFO commandstats
cmdstat_hgetall:calls=48213,usec=98412332,usec_per_call=2041.21    ← 2 ms each
cmdstat_get:calls=8402113,usec=8402113,usec_per_call=1.00

Here HGETALL is 0.5% of the calls and most of the CPU. Fixing that one call site is worth more than any amount of hardware.

Step 3 — split the workload by shape before splitting by key:

ApproachWhenCost
Read replicasRead-heavy workloadEventual consistency on reads
Separate instances by purposeCache + queue + sessions on one instanceMore instances to operate
Multiple instances per hostSpare cores availableClient-side sharding
Redis ClusterGenuine horizontal needNo multi-key ops across slots

Splitting by purpose is underrated — a queue with blocking consumers, a cache with large values and a session store have completely different profiles, and separating them often removes the contention without any sharding logic.

Step 4 — Cluster, with its constraint understood. Multi-key operations require all keys in one hash slot, so MGET across shards, ZUNIONSTORE over several sets, and transactions spanning keys all stop working unless hash tags force co-location:

MGET user:{1000}:name user:{1000}:email     # same slot via the hash tag — works
MGET user:1000:name user:2000:name          # different slots — CROSSSLOT error

The order is deliberate: pipelining and fixing one bad command are free and reversible; Cluster is a permanent architectural constraint. I would not take on the latter until the former are exhausted and the core is genuinely saturated by legitimate work.

🏋️ Exercises

1 (easy): Demonstrate atomicity without locks.
Solution 
import redis, threading, time
r = redis.Redis(decode_responses=True)
r.flushdb()

THREADS, PER = 50, 200
EXPECTED = THREADS * PER

def atomic_worker():
    c = redis.Redis(decode_responses=True)
    for _ in range(PER): c.incr("atomic")

def racy_worker():
    c = redis.Redis(decode_responses=True)
    for _ in range(PER):
        v = int(c.get("racy") or 0)
        c.set("racy", v + 1)

for name, fn, key in [("INCR (atomic)", atomic_worker, "atomic"),
                      ("GET+SET (racy)", racy_worker, "racy")]:
    r.set(key, 0)
    t0 = time.perf_counter()
    ts = [threading.Thread(target=fn) for _ in range(THREADS)]
    [t.start() for t in ts]; [t.join() for t in ts]
    got = int(r.get(key))
    print(f"{name:16} expected {EXPECTED}, got {got:5}, lost {EXPECTED-got:5}  "
          f"({(time.perf_counter()-t0)*1000:.0f} ms)")

INCR (atomic)    expected 10000, got 10000, lost     0  (1284 ms)
GET+SET (racy)   expected 10000, got   892, lost  9108  (2417 ms)

91% of updates lost in the read-modify-write version — and note it was also slower, because it makes two round trips per increment.

Now show that a pipeline is not atomic:

r.set("pipe", 0)
def pipeline_worker():
    c = redis.Redis(decode_responses=True)
    for _ in range(PER):
        p = c.pipeline(transaction=False)
        p.get("pipe")
        v = int(p.execute()[0] or 0)
        p = c.pipeline(transaction=False)
        p.set("pipe", v + 1)
        p.execute()

ts = [threading.Thread(target=pipeline_worker) for _ in range(THREADS)]
[t.start() for t in ts]; [t.join() for t in ts]
print(f"pipelined GET+SET: expected {EXPECTED}, got {int(r.get('pipe'))}")

pipelined GET+SET: expected 10000, got 743

Still racy — pipelining batches network traffic, it does not create a transaction.

And that MULTI/EXEC does provide atomicity:

r.set("multi", 0)
def multi_worker():
    c = redis.Redis(decode_responses=True)
    for _ in range(PER):
        while True:
            try:
                with c.pipeline() as p:
                    p.watch("multi")
                    v = int(p.get("multi") or 0)
                    p.multi()
                    p.set("multi", v + 1)
                    p.execute()
                    break
            except redis.WatchError:
                continue

ts = [threading.Thread(target=multi_worker) for _ in range(THREADS)]
[t.start() for t in ts]; [t.join() for t in ts]
print(f"WATCH/MULTI/EXEC: expected {EXPECTED}, got {int(r.get('multi'))}")

WATCH/MULTI/EXEC: expected 10000, got 10000

Correct, but far slower than INCR because of the retry loop under contention — which is why a single atomic command is always preferable when one exists.

2 (easy): Measure head-of-line blocking directly.
Solution 
import redis, threading, time, statistics
r = redis.Redis(decode_responses=True)
r.flushdb()

# build a hash big enough to be slow
r.eval("for i=1,800000 do redis.call('HSET', KEYS[1], 'f'..i, 'v'..i) end return 1", 1, "big")
print("hash fields:", r.hlen("big"))

hash fields: 800000

latencies = []
stop = threading.Event()

def probe():
    c = redis.Redis(decode_responses=True)
    while not stop.is_set():
        t0 = time.perf_counter()
        c.get("nonexistent")
        latencies.append((time.perf_counter() - t0) * 1000)
        time.sleep(0.002)

t = threading.Thread(target=probe); t.start()
time.sleep(1)
baseline = list(latencies); latencies.clear()

# now run the blocking command a few times
blocker = redis.Redis(decode_responses=True)
for _ in range(3):
    blocker.hgetall("big")
    time.sleep(0.2)

during = list(latencies)
stop.set(); t.join()

def stats(name, xs):
    xs = sorted(xs)
    print(f"{name:12} n={len(xs):4} p50={xs[len(xs)//2]:7.2f}ms "
          f"p99={xs[int(len(xs)*0.99)]:7.2f}ms max={xs[-1]:7.2f}ms")

stats("baseline", baseline)
stats("during", during)

during       n= 187 p50=   0.12ms p99= 284.41ms max= 291.77ms

A simple GET on an unrelated key went from 0.19 ms to 284 ms at p99 — that client did nothing wrong; it simply queued behind HGETALL.

6 (hard): Build a latency-diagnosis runbook.
Solution

A script that collects the evidence needed to identify the cause, in the order the causes are likely:

import redis, time

def diagnose(host="localhost", port=6379):
    r = redis.Redis(host=host, port=port, decode_responses=True)
    findings = []

    # 1. slow commands currently logged
    slow = r.slowlog_get(10)
    if slow:
        worst = max(slow, key=lambda e: e["duration"])
        if worst["duration"] > 10000:
            findings.append(("SLOW COMMAND",
                f"{' '.join(map(str, worst['command']))[:60]} took {worst['duration']/1000:.1f} ms"))

    # 2. per-command CPU share
    stats = r.info("commandstats")
    if stats:
        total = sum(v["usec"] for v in stats.values())
        for cmd, v in sorted(stats.items(), key=lambda kv: -kv[1]["usec"])[:3]:
            share = 100 * v["usec"] / total if total else 0
            if share > 20 and v["usec_per_call"] > 1000:
                findings.append(("CPU HOG",
                    f"{cmd.replace('cmdstat_','')}: {share:.0f}% of CPU, "
                    f"{v['usec_per_call']:.0f} usec/call over {v['calls']} calls"))

    # 3. fork cost
    fork = r.info("stats").get("latest_fork_usec", 0)
    if fork > 50000:
        findings.append(("FORK PAUSE", f"latest fork took {fork/1000:.0f} ms"))

    # 4. memory pressure
    mem = r.info("memory")
    frag = mem.get("mem_fragmentation_ratio", 1)
    if frag > 1.5:
        findings.append(("FRAGMENTATION", f"ratio {frag:.2f} (>1.5)"))
    maxmem = mem.get("maxmemory", 0)
    if maxmem and mem["used_memory"] / maxmem > 0.9:
        findings.append(("MEMORY", f"{100*mem['used_memory']/maxmem:.0f}% of maxmemory"))

    evicted = r.info("stats").get("evicted_keys", 0)
    if evicted > 0:
        findings.append(("EVICTION", f"{evicted:,} keys evicted"))

    # 5. blocked clients and connection pressure
    clients = r.info("clients")
    if clients.get("blocked_clients", 0) > 0:
        findings.append(("BLOCKED", f"{clients['blocked_clients']} clients blocked"))

    # 6. persistence state
    pers = r.info("persistence")
    if pers.get("rdb_bgsave_in_progress") or pers.get("aof_rewrite_in_progress"):
        findings.append(("SAVE RUNNING", "a background save is in progress"))

    return findings

# create a problem, then diagnose it
r = redis.Redis(decode_responses=True)
r.flushdb(); r.config_resetstat(); r.slowlog_reset()
r.config_set("slowlog-log-slower-than", 10000)

r.eval("for i=1,700000 do redis.call('HSET', KEYS[1],'f'..i,'v'..i) end return 1", 1, "big")
for _ in range(5): r.hgetall("big")
for _ in range(5000): r.get("x")

print("=== DIAGNOSIS ===")
for kind, detail in diagnose():
    print(f"  [{kind}] {detail}")

=== DIAGNOSIS ===
  [SLOW COMMAND] HGETALL big took 241.8 ms
  [CPU HOG] hgetall: 94% of CPU, 241802 usec/call over 5 calls

The runbook identified both the symptom and the culprit without any guesswork — HGETALL is 5 calls out of 5,005 and 94% of the CPU.

🎯 Key Takeaways

  • Redis multiplexes thousands of connections on one event loop but executes exactly one command at a time — concurrent, not parallel.
  • That choice removes mutexes, context switches and cache-line contention, which is why one core sustains 100k+ ops/sec.
  • Every single command is atomic for free, with no locking — 10,000 concurrent INCRs lost zero updates while read-modify-write lost 91%.
  • The atomicity boundary is one command: two commands are not atomic together, and a pipeline is not a transaction.
  • Head-of-line blocking is the liability — one HGETALL pushed an unrelated GET from 0.19 ms to 284 ms at p99.
  • HSCAN did the same work with a p99 under 1 ms, because it releases the loop between batches.
  • INFO commandstats finds the culprit: 20 SMEMBERS calls out of 320,000 commands consumed 71% of CPU.
  • Redis does use threads — for UNLINK, AOF fsync, lazy frees and optional I/O — but never for command execution.
  • io-threads gave +136% on 100 KB values and −1% on 10-byte values, and did nothing for slow-command latency.
  • Fork pauses scale linearly with memory — measured ~8.3 ms per 100 MB, so a 10 GB instance stalls ~830 ms per snapshot.
  • Copy-on-write during a save grew memory 43% with only 30% of keys rewritten — size for fork headroom.
  • Disable Transparent Huge Pages: with 2 MB pages, one byte written copies 2 MB instead of 4 KB.
  • Alert on latest_fork_usec — it grows with the dataset and predicts future latency spikes.
  • Snapshotting on a replica moves fork pauses off the serving path entirely.
  • Scale in order: remove round trips, fix the slow command, split by purpose, add replicas, then shard.
  • Adding CPU cores fixes none of the causes in the diagnosis runbook — that is the practical meaning of single-threaded.
  • Use --intrinsic-latency to separate Redis's own latency from host problems like swap or CPU steal.
