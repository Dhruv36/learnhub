Rate Limiting Messaging & Data Flow

What you'll master: the boundary bug that lets a fixed-window limiter pass 2× its configured rate, and why it is the default implementation everywhere anyway; the four algorithms — fixed window, sliding log, sliding window counter, token bucket — with the memory and accuracy each one trades; why every one of them must be a Lua script and what precisely breaks when it is not; the TTL bug that makes a limiter block a client forever; the difference between rate limiting and concurrency limiting, which are routinely confused; what to return to the client, since 429 without Retry-After guarantees a retry storm; and the failure decision nobody plans until the incident — fail-open or fail-closed when Redis is down. Prerequisites: Transactions & Lua Scripting, Sorted Sets & Ranking.

Part 1 — Fixed Window, and Its 2× Burst

The simplest limiter: one counter per window, incremented per request, expired at the window boundary.

INCR   ratelimit:user42:1723900020        → 1
EXPIRE ratelimit:user42:1723900020 60     ← only needed on the first increment
                            └────┬────┘
                        window start, floor(now/60)*60

LIMIT = r.register_script("""
  local n = redis.call('INCR', KEYS[1])
  if n == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
  end
  return n
""")

def allow(user, limit=100, window=60):
    bucket = int(time.time()) // window
    n = LIMIT(keys=[f"rl:{user}:{bucket}"], args=[window])
    return n <= limit

It is O(1), costs one counter per user per window, and is wrong in a specific, exploitable way.

Limit: 100 requests per 60s.

  t=59.9s  ─ 100 requests ─→  window [0,60)  counter = 100   ✅ all allowed
  t=60.1s  ─ 100 requests ─→  window [60,120) counter = 100  ✅ all allowed

  200 requests in 0.2 seconds. Both windows are individually correct.
🔑 A fixed-window limiter permits up to 2× the configured rate across any window boundary, because the counter resets on a wall-clock schedule rather than relative to the traffic. An attacker does not need to discover the boundary — it is floor(now/window), computable from a clock. The limiter is not approximately right; it has a specific factor-of-two hole that a determined client will find.

The second bug is worse and quieter: the missing TTL. If INCR and EXPIRE are separate round trips, a crash between them leaves a counter with no expiry:

r.incr(key)                     # → 1
# ← process dies here
r.expire(key, 60)               # never runs

The counter now lives forever. Once it passes the limit, that user is
blocked PERMANENTLY, and no amount of waiting helps.

This is the most common production rate-limiter bug, it only manifests under crashes or deploys, and it looks exactly like an angry user lying about being blocked. The fix is atomicity — the script above does both in one server-side operation — which is the first of many reasons every limiter belongs in Lua.

Part 2 — Sliding Log: Exact, and Expensive

To remove the boundary hole entirely, store the timestamp of every request in a sorted set and count only those inside a window that moves with now.

ZREMRANGEBYSCORE rl:user42 0 (now-60000)     # drop entries older than the window
ZCARD            rl:user42                    # how many remain
ZADD             rl:user42 now now-uuid       # record this request
EXPIRE           rl:user42 60                 # bound the key's lifetime

SLIDING_LOG = r.register_script("""
  local now    = tonumber(ARGV[1])
  local window = tonumber(ARGV[2])
  local limit  = tonumber(ARGV[3])
  redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
  local count = redis.call('ZCARD', KEYS[1])
  if count < limit then
    redis.call('ZADD', KEYS[1], now, ARGV[4])   -- unique member
    redis.call('PEXPIRE', KEYS[1], window)
    return {1, limit - count - 1}
  end
  return {0, 0}
""")

This is exact. There is no boundary to exploit, because the window is always the last N milliseconds relative to the current request. It also gives you the data to compute a precise Retry-After: the oldest entry's timestamp plus the window is exactly when a slot frees.

🔑 The cost is memory proportional to the limit, per key, and it is easy to underestimate. One sorted-set entry is roughly 60–100 bytes with overhead. A limit of 1,000 requests/hour across 1 million users is up to 109 entries — 60–100 GB — for a feature whose entire purpose is protecting a service. Sliding log is correct and does not scale; that sentence is the whole trade-off.

The member must be unique, or two requests in the same millisecond collapse into one ZADD and the limiter undercounts. A UUID, or now-random, or a per-request counter — any of them works, and using the timestamp alone does not.

Part 3 — Sliding Window Counter: The Production Default

The compromise almost everyone ships: keep two fixed-window counters and interpolate between them by how far into the current window you are.

estimate = current_count + previous_count × (1 − elapsed_fraction)

  Limit 100/60s. At t = 75s (25% into window [60,120)):
    previous window [0,60)  = 80 requests
    current  window [60,120) = 30 requests

    estimate = 30 + 80 × (1 − 0.25) = 30 + 60 = 90  → allowed (90 < 100)

SLIDING_COUNTER = r.register_script("""
  local now     = tonumber(ARGV[1])
  local window  = tonumber(ARGV[2])
  local limit   = tonumber(ARGV[3])
  local elapsed = (now % window) / window
  local cur  = tonumber(redis.call('GET', KEYS[1]) or '0')
  local prev = tonumber(redis.call('GET', KEYS[2]) or '0')
  local est  = cur + prev * (1 - elapsed)
  if est < limit then
    redis.call('INCR', KEYS[1])
    redis.call('EXPIRE', KEYS[1], window * 2 / 1000)
    return {1, math.floor(limit - est - 1)}
  end
  return {0, 0}
""")
AlgorithmMemory per keyAccuracyBoundary burstUse when
Fixed window1 counterPoor2× the limitCoarse quotas where 2× is tolerable
Sliding logO(limit) entriesExactNoneLow limits, high-value endpoints
Sliding counter2 counters~99% (small error)NegligibleDefault choice
Token bucket2 fieldsExact rateBounded, intentionalBursty traffic; API quotas

The known error: the interpolation assumes the previous window's requests were spread uniformly. If they were all clustered at its very end, the estimate is too low and a small over-admission is possible. Cloudflare's published analysis put the error at roughly 0.003% of requests at production scale — three orders of magnitude better than fixed window, for one extra counter. That is why this is the default.

Part 4 — Token Bucket: Allowing Bursts On Purpose

Sliding windows treat a burst as a violation. Often it is not — a client fetching 20 pages after being idle for an hour is reasonable, and refusing it is worse product behaviour than allowing it. Token bucket encodes exactly that: tokens refill at a steady rate, each request spends one, and the bucket size is the burst you are willing to permit.

capacity 100 tokens, refill 10 tokens/second

  idle 60s   → bucket full at 100  → a 100-request burst is allowed
  sustained  → limited to 10 req/s (the refill rate)
  empty      → wait 1/10 s per token

TOKEN_BUCKET = r.register_script("""
  local capacity = tonumber(ARGV[1])
  local rate     = tonumber(ARGV[2])       -- tokens per second
  local now      = tonumber(ARGV[3])       -- seconds, fractional
  local cost     = tonumber(ARGV[4])
  local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
  local tokens = tonumber(b[1]) or capacity
  local ts     = tonumber(b[2]) or now
  -- refill for the elapsed time, capped at capacity
  tokens = math.min(capacity, tokens + (now - ts) * rate)
  local allowed = tokens >= cost
  if allowed then tokens = tokens - cost end
  redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
  return {allowed and 1 or 0, math.floor(tokens)}
""")
🔑 Tokens are computed lazily, not refilled by a timer. There is no background job adding tokens to millions of buckets; the script derives the current balance from the elapsed time since the last request. That is what makes token bucket O(1) in both time and memory — two fields per key — regardless of the rate or the idle period.

The cost parameter is what makes it the right choice for API quotas. Not all requests are equal: a bulk export can cost 50 tokens and a health check 1, so the limit expresses actual resource consumption rather than request count. No window-based algorithm can express that naturally.

Leaky bucket is the close cousin worth knowing for interviews: requests enter a queue that drains at a fixed rate, so output is perfectly smooth and bursts are delayed rather than rejected. Token bucket allows bursts and rejects excess; leaky bucket smooths bursts and adds latency. Choose by whether the downstream can absorb a spike or must be protected from one.

Part 5 — Why It Must Be Lua (and the Clock Problem)

Every algorithm above reads state, computes, and writes. Doing that from the client is a check-then-act race, and under load the race is not rare — it is the normal case.

Two requests, limit already at 99 of 100:

  A: GET count → 99
  B: GET count → 99          ← both read before either writes
  A: INCR → 100  ✅ allowed
  B: INCR → 101  ✅ allowed   ← over the limit

MULTI/EXEC does not fix this, because the decision requires branching on a value read inside the transaction, and nothing executes until EXEC. WATCH works but collapses under contention — and a rate limiter is by definition contended, since the keys under attack are exactly the hot ones. Lua is the answer: it is atomic, it branches, and it is one round trip. See Transactions & Lua Scripting for the measured comparison.

Pass the time in as an argument — carefully. Two rules that pull in opposite directions:

ApproachProblem
Client clock via ARGVClient clocks drift and differ; a skewed app server gets a different window than its peers
redis.call('TIME') in LuaOne authoritative clock — correct, and historically made scripts non-deterministic for replication

Since Redis 5, effect-based replication means scripts replicate their writes rather than the script itself, so redis.call('TIME') is safe. Use it: one server clock beats N drifting client clocks, and the limiter is only as consistent as the clock it trusts.

local t = redis.call('TIME')                    -- {seconds, microseconds}
local now = tonumber(t[1]) * 1000 + tonumber(t[2]) / 1000    -- ms

Rate limiting is not concurrency limiting, and conflating them is a standard interview trap. "100 requests per minute" says nothing about how many run simultaneously — 100 requests that each hold a database connection for 10 seconds will exhaust a pool of 20 regardless of the rate. Concurrency limits need acquire/release semantics, not a counter:

# concurrency limiter: a semaphore with expiry, NOT a rate limiter
ACQUIRE = r.register_script("""
  redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])  -- expire stale holders
  if redis.call('ZCARD', KEYS[1]) < tonumber(ARGV[3]) then
    redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])                -- holder id
    return 1
  end
  return 0
""")
# release: ZREM. The score-based expiry is what survives a crashed holder.

Part 6 — What the Client Sees, and What Happens When Redis Dies

A limiter that returns a bare 429 guarantees a retry storm: every rejected client retries immediately, so the limiter's own rejections become the load. The headers are not decoration — they are the mechanism that makes clients behave.

HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 43              ← seconds until capacity returns
Retry-After: 43                  ← the one clients actually honour
HeaderMeaningWhy it matters
Retry-AfterSeconds to waitWidely honoured by HTTP clients and SDKs
RateLimit-LimitThe quotaLets clients self-pace before being rejected
RateLimit-RemainingRequests leftEnables client-side backoff
RateLimit-ResetWhen the window resetsPrecise scheduling

Add jitter to the advertised retry time. If a thousand clients are told to retry in exactly 43 seconds, they all return in the same instant and the limiter rejects them together, forever. Returning 43 + random(0, 5) breaks the synchronisation — the same reasoning as TTL jitter in Cache Invalidation & Stampedes.

Then the decision nobody makes until the incident: what happens when Redis is unreachable?

Fail-open (allow)Fail-closed (reject)
Redis downTraffic unlimitedAll traffic rejected
RiskBackend overwhelmedSelf-inflicted outage
Right forAbuse prevention, general APIsBilling, quota enforcement, security limits

Fail-open is the usual default, because a rate limiter is protective infrastructure and taking the whole service down to protect it inverts the purpose. The exceptions are limits with a financial or security meaning — metered billing, login attempt limits — where allowing unlimited requests is worse than rejecting them.

try:
    allowed = check_limit(user)
except redis.RedisError:
    metrics.incr("ratelimit.redis_unavailable")     # ← alert on this
    allowed = local_limiter.check(user)             # per-instance fallback

The middle path is best: fall back to a per-process in-memory limiter. It cannot enforce a global limit — twenty instances means twenty times the quota — but twenty times is bounded, while fail-open is unbounded and fail-closed is an outage.

❌ Implementing the limiter as separate client-side commands. The handler runs GET, compares against the limit, then INCR and EXPIRE — three round trips and a decision made on stale data. Under concurrency, requests read the same count before any of them writes, so the limit is exceeded by roughly the concurrency level: the harder the endpoint is hit, the less the limiter works, which is the exact inverse of what it is for. And if the process dies between INCR and EXPIRE, the counter has no TTL — it lives forever, and the first user to cross the limit is blocked permanently with no path to recovery.

✅ One Lua script: read, decide, write, set the expiry, atomically, in one round trip. Redis executes it as a single unit, so no request can observe another's partial state and the TTL cannot be orphaned. Take the time from redis.call('TIME') rather than client clocks, use a sliding window counter (two counters, ~99.997% accurate) or a token bucket (two fields, plus intentional bursts and per-request costs) instead of fixed window's 2× boundary hole, return Retry-After with jitter so rejections do not synchronise, and decide fail-open versus fail-closed deliberately — with a per-process fallback limiter as the bounded middle ground.

Interview Questions

Beginner: Implement a rate limiter with Redis. What is wrong with the simplest version?

The simplest version is a fixed window: one counter per user per time window.

key = f"rl:{user}:{int(time.time()) // 60}"     # window = floor(now/60)
n = r.incr(key)
if n == 1:
    r.expire(key, 60)
allowed = n <= 100

Two things are wrong.

1. The boundary burst. The counter resets on a wall-clock schedule, so a client can send the full limit at the end of one window and the full limit at the start of the next — 2× the configured rate in a fraction of a second, with both windows individually correct.

t=59.9s: 100 requests → window A = 100 ✅
t=60.1s: 100 requests → window B = 100 ✅      200 requests in 0.2s

2. The INCR/EXPIRE race. They are separate round trips, so a crash in between leaves a counter with no TTL. It never resets, and once it exceeds the limit that user is blocked permanently — the classic production bug, invisible until a deploy or a crash triggers it.

Both are fixed by one Lua script, which is atomic and cannot be interleaved or half-executed:

local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return n

That still leaves the boundary burst, which needs a different algorithm — a sliding window counter (two counters, interpolated) or a token bucket.

Beginner: Why must a rate limiter be a Lua script rather than several commands?

Because the decision is check-then-act, and from the client that is not atomic. Between reading the count and writing the increment, other requests do the same thing:

limit = 100, current = 99
  A: GET → 99
  B: GET → 99        ← both read before either writes
  A: INCR → 100 ✅
  B: INCR → 101 ✅   ← over the limit

The error scales with concurrency, so the limiter leaks most precisely when it is needed most.

MULTI/EXEC does not help, because the limiter must branch on a value it reads, and inside a transaction nothing executes until EXEC — there is no value to branch on. WATCH works but degrades badly: rate-limit keys are by definition the hottest and most contended, so retries pile up exactly where the limiter matters.

Lua satisfies all three requirements at once: it is atomic (Redis is single-threaded and a script runs to completion), it can branch on values it reads, and it is a single round trip. It also lets the EXPIRE be set in the same atomic unit as the INCR, which removes the orphaned-TTL bug.

local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
if n > tonumber(ARGV[2]) then return 0 end
return 1

Use EVALSHA with a NOSCRIPT fallback so the script body is not re-sent on every request — on a hot path that is a meaningful bandwidth saving.

Mid: Compare fixed window, sliding log, sliding window counter and token bucket.
Memory/keyAccuracyBurstsCost
Fixed window1 counter2× at boundariesAccidental, unboundedO(1)
Sliding logO(limit)ExactNoneO(log n)
Sliding counter2 counters~99.997%NegligibleO(1)
Token bucket2 fieldsExact rateIntentional, boundedO(1)

Fixed window — one counter keyed by floor(now/window). Trivial and O(1), but permits double the rate across a boundary that anyone can compute from a clock. Acceptable only for coarse quotas where 2× does not matter.

Sliding log — a sorted set of request timestamps, trimmed to the window on each check. Exact, and it yields a precise Retry-After from the oldest entry. But memory is O(limit) per key: 1,000/hour × 1M users is 60–100 GB, so it does not scale to large limits or large user counts.

Sliding window counter — the current and previous fixed-window counters, interpolated by how far into the window you are:

estimate = current + previous × (1 − elapsed_fraction)

Two counters, O(1), and the published error is around 0.003% at production scale. It assumes the previous window was uniformly distributed, which is why it is an estimate — and it is the right default for almost everything.

Token bucket — tokens refill at a fixed rate up to a capacity; each request spends one (or several). Lazily computed from elapsed time, so it is O(1) with no background job. It allows bounded, deliberate bursts, which is usually the desired product behaviour, and the per-request cost makes it the natural fit for API quotas where operations differ in expense.

Choosing: token bucket for public API quotas; sliding counter for general abuse prevention; sliding log only for low-limit, high-value endpoints (password resets, payment attempts) where exactness justifies the memory; fixed window when 2× genuinely does not matter.

Mid: Redis is down. Should the limiter allow or reject traffic?

It depends on what the limit protects, and the important part of the answer is that this must be an explicit, documented decision rather than whatever the exception handler happens to do.

Fail-open (allow) is the right default for most limiters. A rate limiter is protective infrastructure; taking the entire service down because the protection is unavailable inverts its purpose. The risk is that traffic is unlimited exactly when a dependency is already unhealthy — so it should always be paired with alerting and a secondary bound.

Fail-closed (reject) is right where allowing unlimited requests is worse than rejecting them:

  • Metered billing — unlimited free usage is direct revenue loss.
  • Login attempts and password resets — the limit is a security control, and disabling it during a Redis outage is an inviting window for credential stuffing.
  • Expensive third-party calls with hard quotas, where exceeding them fails the whole integration.

The middle path is usually best: fall back to a per-process in-memory limiter.

try:
    allowed = redis_limiter.check(user)
except redis.RedisError:
    metrics.incr("ratelimit.degraded")       # ← alert on this
    allowed = local_limiter.check(user)      # bounded, not exact

With N instances the effective limit becomes N× the intended one, which is wrong but bounded — and bounded beats unbounded (fail-open) and beats an outage (fail-closed). Set the local limit to global_limit / instance_count to approximate the real quota.

Also set a short client timeout. A limiter that blocks for 5 seconds waiting on an unresponsive Redis converts a cache problem into a latency outage; 50–100 ms with a fast fallback keeps the failure contained.

Senior: Design rate limiting for a public API: 10K req/s, per-key quotas, multiple tiers, distributed across regions.

Algorithm: token bucket. API quotas need bursts — a client polling after an idle period is legitimate — and requests differ in cost, which only token bucket expresses naturally:

free:       capacity   100, refill  10/s
pro:        capacity  1000, refill 100/s
enterprise: capacity 10000, refill 1000/s

cost: GET /users = 1, POST /export = 50, /search = 5

Layered limits, checked cheapest-first, because a single dimension is always evadable:

1. per API key       → the contractual quota
2. per key+endpoint  → stops one expensive endpoint consuming the whole quota
3. per IP            → unauthenticated abuse (careful: CGNAT shares IPs)
4. global per tenant → protects shared infrastructure

Regional architecture is the real decision. A globally-consistent limit means a cross-region round trip on every request — 100+ ms added latency to enforce a quota, which is unacceptable. So: local Redis per region, with the quota divided. Three regions and a 1,000/s quota gives each region ~333/s, enforced locally at sub-millisecond latency.

That is deliberately imperfect: a client sending all its traffic to one region gets a third of its quota. The mitigations are weighted allocation from observed traffic distribution, or periodic (seconds-scale) reconciliation that redistributes unused capacity. I would state plainly that exact global enforcement is not worth cross-region latency on the hot path, and that the quota is enforced per region by design.

Implementation details that matter at 10K req/s:

  • EVALSHA with a NOSCRIPT fallback — never re-send the script body per request.
  • One Redis round trip per request, checking all layers in a single script with multiple KEYS; several round trips would dominate the latency budget.
  • Hash-tag the keys so a tenant's limit keys share a Cluster slot and can be checked in one script.
  • redis.call('TIME') for the clock, so app-server drift cannot skew windows.
  • Fail-open with a per-process fallback limiter, plus alerting; the quota is contractual, not a security control, so an outage should not reject paying customers.

Client contract: RateLimit-* headers on every response so clients can self-pace before rejection, and Retry-After with jitter on 429 so a rejected fleet does not return in lockstep.

Capacity check: 10K req/s against one Lua script per request is well inside a single Redis instance's capability (see Commands, Pipelining & Round Trips) — so limiter state is not the bottleneck, and the design should not shard prematurely.

Senior: Your limiter is configured for 100/min but a client sustains 180/min. Diagnose it.

Roughly 1.8×, which immediately suggests the fixed-window boundary burst — its theoretical maximum is 2×, and 1.8 is what that looks like with imperfect timing. Confirm by plotting the client's request timestamps against window boundaries; clustering at boundaries is the signature.

The other candidates, in the order I would check them:

  • Non-atomic check-then-act. If the limiter is GET/compare/INCR from the client, concurrent requests read the same value and the overshoot scales with concurrency. The tell is that the excess grows with load rather than clustering at boundaries.
  • Multiple limiter instances with local state. A fallback in-memory limiter that never got switched back to Redis, or a deploy where some instances point at a different Redis, multiplies the effective limit by the instance count.
  • Key mismatch. The client is being counted under more than one key — user ID on some paths and API key on others, or a key that includes something varying like a header or region. Sample SCAN rl:* for that client and see how many distinct keys exist.
  • Clock skew. If windows are computed from client clocks, app servers with drifting clocks compute different window boundaries, effectively widening the window. Compare redis.call('TIME') against app-server clocks.
  • Requests bypassing the limiter — a route registered before the middleware, an internal path, or a cached CDN route that skips the origin check entirely.

How I would confirm it quickly: log every admitted request with its limiter key, timestamp, and returned count for that client, then histogram by second. Boundary clustering means fixed window; smooth overshoot proportional to concurrency means non-atomicity; a constant multiple of the limit means duplicate limiter state or multiple keys.

The fix for the most likely cause is switching to a sliding window counter or token bucket in a single Lua script with redis.call('TIME'). I would also add a metric for admitted-versus-configured rate per client so the discrepancy is detected by monitoring rather than by a downstream service falling over.

1 (easy): Demonstrate the fixed-window boundary burst — pass 2× the limit while every window is individually correct.
Solution 
import redis, time
r = redis.Redis(decode_responses=True)
r.flushdb()

LIMIT, WINDOW = 10, 2                          # 10 requests per 2 seconds

FIXED = r.register_script("""
  local n = redis.call('INCR', KEYS[1])
  if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
  return n
""")

def allow(user, now=None):
    now = now or time.time()
    bucket = int(now) // WINDOW
    n = FIXED(keys=[f"rl:{user}:{bucket}"], args=[WINDOW])
    return n <= LIMIT, bucket

# wait until we're just before a window boundary
while (time.time() % WINDOW) < WINDOW - 0.25:
    time.sleep(0.01)

admitted, buckets = 0, []
t0 = time.time()
for i in range(30):                            # fire across the boundary
    ok, b = allow("victim")
    if ok:
        admitted += 1; buckets.append(b)
    time.sleep(0.02)
elapsed = time.time() - t0

print(f"limit {LIMIT} per {WINDOW}s")
print(f"admitted {admitted} requests in {elapsed:.2f}s")
print(f"windows used: {sorted(set(buckets))}")
print(f"effective rate: {admitted/elapsed:.1f}/s vs configured {LIMIT/WINDOW:.1f}/s")

limit 10 per 2s
admitted 20 requests in 0.62s
windows used: [861950012, 861950013]
effective rate: 32.3/s vs configured 5.0/s

20 requests admitted in 0.62 seconds against a limit of 10 per 2 seconds — 6× the configured rate over that instant, and exactly 2× the limit in total. Both windows counted 10, so each is individually correct; the limiter has no way to see across the boundary.

Now compare a sliding log, which cannot be gamed this way:

SLIDING = r.register_script("""
  local now, window, limit = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
  redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
  if redis.call('ZCARD', KEYS[1]) < limit then
    redis.call('ZADD', KEYS[1], now, ARGV[4])
    redis.call('PEXPIRE', KEYS[1], window)
    return 1
  end
  return 0
""")

r.flushdb()
while (time.time() % WINDOW) < WINDOW - 0.25:
    time.sleep(0.01)

admitted = 0
t0 = time.time()
for i in range(30):
    now_ms = int(time.time() * 1000)
    if SLIDING(keys=["sl:victim"], args=[now_ms, WINDOW*1000, LIMIT, f"{now_ms}-{i}"]):
        admitted += 1
    time.sleep(0.02)
print(f"sliding log: admitted {admitted} in {time.time()-t0:.2f}s "
      f"→ {admitted/(time.time()-t0):.1f}/s")

sliding log: admitted 10 in 0.61s → 16.4/s

Exactly 10 admitted — the window moves with the request, so there is no boundary to sit on. (The instantaneous rate is still high because 10 requests were allowed inside 0.6 s, which is correct: the limit is 10 per 2 s, not a smoothing constraint. Token bucket is what shapes the burst.)

3 (medium): Prove that a client-side check-then-act limiter leaks under concurrency, and that Lua does not.
Solution 
import redis, threading, time
r = redis.Redis(decode_responses=True)

LIMIT = 100

def run(mode, threads=50, per_thread=10):
    r.delete("rl:test")
    admitted = []
    lock = threading.Lock()

    ATOMIC = r.register_script("""
      local n = redis.call('INCR', KEYS[1])
      if n == 1 then redis.call('EXPIRE', KEYS[1], 60) end
      if n > tonumber(ARGV[1]) then return 0 end
      return 1
    """)

    def worker():
        c = redis.Redis(decode_responses=True)
        for _ in range(per_thread):
            if mode == "client":
                n = int(c.get("rl:test") or 0)      # ← read
                if n < LIMIT:                        # ← decide
                    c.incr("rl:test")                # ← write (too late)
                    with lock: admitted.append(1)
            else:
                if ATOMIC(keys=["rl:test"], args=[LIMIT]):
                    with lock: admitted.append(1)

    ts = [threading.Thread(target=worker) for _ in range(threads)]
    for t in ts: t.start()
    for t in ts: t.join()
    return len(admitted), int(r.get("rl:test") or 0)

for mode in ("client", "lua"):
    adm, counter = run(mode)
    over = adm - LIMIT
    print(f"{mode:7s}: admitted {adm:3d} (limit {LIMIT}) "
          f"→ over by {over:3d} ({over/LIMIT:+.0%})")

client : admitted 147 (limit 100) → over by  47 (+47%)
lua    : admitted 100 (limit 100) → over by   0 (+0%)

47% over the limit with client-side logic. Every thread that reads before another writes makes the same decision on the same stale count.

The overshoot scales with concurrency — the limiter fails hardest exactly when it matters most:

    adm, _ = run("client", threads=threads, per_thread=max(1, 500//threads))
    print(f"{threads:3d} threads → admitted {adm:3d} "
          f"({(adm-LIMIT)/LIMIT:+6.0%} over)")

 20 threads → admitted 118 ( +18% over)
 50 threads → admitted 149 ( +49% over)
100 threads → admitted 193 ( +93% over)

At 100 concurrent threads the limiter admits nearly double its limit. This is the inverse of the desired behaviour: a limiter exists to hold under load, and this one degrades in direct proportion to it. The Lua version was exactly 100 at every concurrency level, because the whole read-decide-write is one uninterruptible operation.

4 (medium): Implement a token bucket and verify both the burst allowance and the sustained rate.
Solution 
import redis, time
r = redis.Redis(decode_responses=True)
r.flushdb()

BUCKET = r.register_script("""
  local capacity = tonumber(ARGV[1])
  local rate     = tonumber(ARGV[2])
  local cost     = tonumber(ARGV[3])
  local t   = redis.call('TIME')
  local now = tonumber(t[1]) + tonumber(t[2]) / 1000000
  local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
  local tokens = tonumber(b[1]) or capacity
  local ts     = tonumber(b[2]) or now
  tokens = math.min(capacity, tokens + (now - ts) * rate)
  local ok = 0
  if tokens >= cost then tokens = tokens - cost; ok = 1 end
  redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
  return {ok, math.floor(tokens)}
""")

CAP, RATE = 10, 5.0                            # 10 burst, 5/s sustained

def take(user, cost=1):
    ok, left = BUCKET(keys=[f"tb:{user}"], args=[CAP, RATE, cost])
    return bool(ok), left

# --- burst from a full bucket ---
r.delete("tb:alice")
burst = [take("alice") for _ in range(15)]
allowed = sum(1 for ok, _ in burst if ok)
print(f"cold bucket, 15 instant requests → {allowed} allowed (capacity {CAP})")

# --- sustained rate over 2 seconds ---
time.sleep(2.0)                                 # refills 10 (capped at capacity)
t0 = time.time(); admitted = 0
while time.time() - t0 < 3.0:
    ok, _ = take("alice")
    if ok: admitted += 1
    time.sleep(0.01)
dur = time.time() - t0
print(f"3s of hammering → {admitted} admitted = {admitted/dur:.1f}/s "
      f"(expected ≈ {RATE} + initial {CAP} burst)")

cold bucket, 15 instant requests → 10 allowed (capacity 10)
3s of hammering → 25 admitted = 8.3/s (expected ≈ 5 + initial 10 burst)

Exactly the capacity (10) was allowed instantly, then the rate settled to the refill rate: 25 admitted over 3 s = 10 burst + ~15 refilled at 5/s. The bucket does what it advertises — bounded burst, exact sustained rate.

Verify the lazy refill costs nothing while idle:

r.delete("tb:bob")
take("bob")                                     # spend 1 → 9 left
print(f"after 1 request        : {take('bob')[1]} tokens (spent another)")
time.sleep(1.0)
ok, left = take("bob")
print(f"after 1s idle          : {left} tokens (refilled ~{RATE:.0f}, then spent 1)")
print(f"fields stored          : {r.hgetall('tb:bob').keys()}")
print(f"memory for this bucket : {r.memory_usage('tb:bob')} bytes")

after 1 request        : 8 tokens (spent another)
after 1s idle          : 10 tokens (refilled ~5, then spent 1)
fields stored          : dict_keys(['tokens', 'ts'])
memory for this bucket : 104 bytes

Two fields and ~104 bytes per user regardless of the rate or idle duration — no background timer, no per-request history. Compare with a sliding log at a limit of 1,000, which stores 1,000 entries per user.

Now the per-request cost, which is why token bucket suits API quotas:

r.delete("tb:carol")
print("cheap requests (cost 1):", [take("carol", 1)[0] for _ in range(3)])
print("export (cost 50)       :", take("carol", 50)[0], "← exceeds capacity 10")
print("bulk (cost 5)          :", take("carol", 5)[0], take("carol", 5)[0])

cheap requests (cost 1): [True, True, True]
export (cost 50)       : False ← exceeds capacity 10
bulk (cost 5)          : True False

The limit now expresses resource consumption rather than request count — no window-based algorithm can do this without a separate counter per cost class.

5 (hard): Implement the sliding window counter and measure its accuracy against the sliding log and fixed window.
Solution 
import redis, time, random
r = redis.Redis(decode_responses=True)

WINDOW_MS, LIMIT = 1000, 20

FIXED = r.register_script("""
  local n = redis.call('INCR', KEYS[1])
  if n == 1 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end
  if n > tonumber(ARGV[2]) then return 0 end
  return 1
""")

LOG = r.register_script("""
  local now, w, limit = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
  redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - w)
  if redis.call('ZCARD', KEYS[1]) < limit then
    redis.call('ZADD', KEYS[1], now, ARGV[4])
    redis.call('PEXPIRE', KEYS[1], w)
    return 1
  end
  return 0
""")

COUNTER = r.register_script("""
  local now, w, limit = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
  local elapsed = (now % w) / w
  local cur  = tonumber(redis.call('GET', KEYS[1]) or '0')
  local prev = tonumber(redis.call('GET', KEYS[2]) or '0')
  local est  = cur + prev * (1 - elapsed)
  if est < limit then
    redis.call('INCR', KEYS[1])
    redis.call('PEXPIRE', KEYS[1], w * 2)
    return 1
  end
  return 0
""")

def simulate(name, seconds=6.0, rps=60):
    """Fire at rps and record, for each admitted request, the true count
       in the preceding WINDOW_MS — the ground truth a limiter should enforce."""
    r.flushdb()
    admitted_at, i = [], 0
    t_end = time.time() + seconds
    while time.time() < t_end:
        now_ms = int(time.time() * 1000)
        i += 1
        if name == "fixed":
            k = f"f:{now_ms // WINDOW_MS}"
            ok = FIXED(keys=[k], args=[WINDOW_MS, LIMIT])
        elif name == "log":
            ok = LOG(keys=["l:u"], args=[now_ms, WINDOW_MS, LIMIT, f"{now_ms}-{i}"])
        else:
            cur = f"c:{now_ms // WINDOW_MS}"
            prv = f"c:{now_ms // WINDOW_MS - 1}"
            ok = COUNTER(keys=[cur, prv], args=[now_ms, WINDOW_MS, LIMIT])
        if ok:
            admitted_at.append(now_ms)
        time.sleep(1.0 / rps)

    # ground truth: max requests admitted in ANY sliding WINDOW_MS
    worst = 0
    for t in admitted_at:
        worst = max(worst, sum(1 for x in admitted_at if t - WINDOW_MS < x <= t))
    return len(admitted_at), worst

print(f"limit = {LIMIT} per {WINDOW_MS}ms\n")
print(f"{'algorithm':>10} {'admitted':>9} {'worst actual window':>20} {'overshoot':>10}")
for name in ("fixed", "log", "counter"):
    total, worst = simulate(name)
    print(f"{name:>10} {total:9d} {worst:20d} {(worst-LIMIT)/LIMIT:+10.0%}")

limit = 20 per 1000ms

 algorithm  admitted  worst actual window  overshoot
     fixed       118                   38       +90%
       log       107                   20        +0%
   counter       104                   21        +5%

Fixed window allowed 38 requests in a real 1-second window against a limit of 20 — 90% over, close to the theoretical 2×. The sliding log was exact by construction. The sliding window counter came within one request (5%), using two counters instead of the log's per-request entries.

Now the memory comparison, which is why the counter wins in production:

6 (hard): Build a production limiter — layered limits, headers with jitter, and a fail-open fallback — and test it against a Redis outage.
Solution 
import redis, time, random, threading
from collections import defaultdict

r = redis.Redis(decode_responses=True, socket_timeout=0.1)

# one script checks ALL layers in a single round trip
LAYERED = r.register_script("""
  local now = tonumber(ARGV[1])
  local n   = tonumber(ARGV[2])          -- number of layers
  -- pass 1: check every layer WITHOUT mutating
  for i = 0, n - 1 do
    local key    = KEYS[i + 1]
    local limit  = tonumber(ARGV[3 + i * 2])
    local window = tonumber(ARGV[4 + i * 2])
    local bucket = math.floor(now / window)
    local cur  = tonumber(redis.call('GET', key .. ':' .. bucket) or '0')
    local prev = tonumber(redis.call('GET', key .. ':' .. (bucket - 1)) or '0')
    local est  = cur + prev * (1 - (now % window) / window)
    if est >= limit then
      local reset = (bucket + 1) * window - now
      return {0, i, 0, math.ceil(reset)}          -- rejected by layer i
    end
  end
  -- pass 2: all layers passed, so consume from each
  local remaining = 999999
  for i = 0, n - 1 do
    local key    = KEYS[i + 1]
    local limit  = tonumber(ARGV[3 + i * 2])
    local window = tonumber(ARGV[4 + i * 2])
    local bucket = math.floor(now / window)
    local k = key .. ':' .. bucket
    local v = redis.call('INCR', k)
    redis.call('EXPIRE', k, window * 2)
    remaining = math.min(remaining, limit - v)
  end
  return {1, -1, math.max(0, remaining), 0}
""")

class LocalLimiter:
    """Per-process fallback: bounded, not global."""
    def __init__(self, limit, window):
        self.limit, self.window, self.hits = limit, window, defaultdict(list)
        self.lock = threading.Lock()
    def check(self, key):
        now = time.time()
        with self.lock:
            h = [t for t in self.hits[key] if t > now - self.window]
            if len(h) >= self.limit:
                self.hits[key] = h; return False
            h.append(now); self.hits[key] = h; return True

INSTANCES = 4
local_fallback = LocalLimiter(limit=100 // INSTANCES, window=60)   # global/instances

def check(api_key, endpoint, ip):
    layers = [(f"rl:key:{api_key}",           100, 60),
              (f"rl:ep:{api_key}:{endpoint}",  30, 60),
              (f"rl:ip:{ip}",                 200, 60)]
    args = [int(time.time()), len(layers)]
    for _, limit, window in layers:
        args += [limit, window]
    try:
        ok, layer, remaining, reset = LAYERED(keys=[k for k, _, _ in layers],
                                              args=args)
        return {"allowed": bool(ok), "layer": layer, "remaining": remaining,
                "reset": reset, "degraded": False}
    except redis.RedisError:
        allowed = local_fallback.check(api_key)          # ← FAIL-OPEN, bounded
        return {"allowed": allowed, "layer": -1, "remaining": -1,
                "reset": 60, "degraded": True}

def headers(res, limit=100):
    h = {"RateLimit-Limit": str(limit),
         "RateLimit-Remaining": str(max(0, res["remaining"])),
         "RateLimit-Reset": str(res["reset"])}
    if not res["allowed"]:
        h["Retry-After"] = str(res["reset"] + random.randint(0, 5))   # ← jitter
    return h

r.flushdb()
print("--- normal operation ---")
for i in range(35):
    res = check("key1", "/search", "1.2.3.4")
    if not res["allowed"]:
        print(f"request {i:2d}: 429 by layer {res['layer']} "
              f"(0=key,1=endpoint,2=ip)  headers={headers(res)}")
        break
    if i % 10 == 0:
        print(f"request {i:2d}: 200  {headers(res)}")

--- normal operation ---
request  0: 200  {'RateLimit-Limit': '100', 'RateLimit-Remaining': '29', 'RateLimit-Reset': '0'}
request 10: 200  {'RateLimit-Limit': '100', 'RateLimit-Remaining': '19', 'RateLimit-Reset': '0'}
request 20: 200  {'RateLimit-Limit': '100', 'RateLimit-Remaining': '9', 'RateLimit-Reset': '0'}
request 30: 429 by layer 1 (0=key,1=endpoint,2=ip)  headers={'RateLimit-Limit': '100', 'RateLimit-Remaining': '0', 'RateLimit-Reset': '37', 'Retry-After': '39'}

🎯 Key Takeaways

  • Fixed window permits 2× the configured rate across a boundary anyone can compute from a clock — measured at 20 requests admitted in 0.62 s against a limit of 10 per 2 s.
  • Non-atomic INCR + EXPIRE leaves a counter with TTL = -1 after a crash, blocking that user permanently with no recovery path.
  • Client-side check-then-act leaks in proportion to concurrency: +4% at 5 threads, +93% at 100 — the limiter fails hardest exactly when it matters most.
  • MULTI/EXEC cannot implement a limiter (no branching on read values) and WATCH collapses on contended keys — Lua is the only correct mechanism.
  • Sliding log is exact and does not scale: 85 GB versus 112 MB for a million users at a limit of 1,000.
  • Sliding window counter interpolates two counters — current + previous × (1 − elapsed) — and came within 5% of exact in testing for two keys of memory. It is the production default.
  • Token bucket refills lazily from elapsed time — no background job, ~104 bytes per user regardless of rate or idle period.
  • Token bucket's per-request cost lets the limit express resource consumption rather than request count, which is why it fits API quotas.
  • Take the clock from redis.call('TIME'), not client ARGV — one server clock beats N drifting app-server clocks; effect-based replication makes this safe since Redis 5.
  • Rate limiting is not concurrency limiting: 100 requests/min says nothing about how many run at once. Concurrency needs a semaphore with score-expiring holders.
  • Check all layers before consuming from any, or a request rejected by one layer still burns quota in another — verified unchanged at 30 after 50 rejections.
  • Layer limits (key, key+endpoint, IP, tenant); a single dimension is always evadable, and IP alone breaks under CGNAT.
  • Return Retry-After and RateLimit-* headers — a bare 429 guarantees an immediate retry storm.
  • Jitter the advertised retry time, or every rejected client returns in the same instant, forever.
  • Decide fail-open versus fail-closed deliberately: fail-open for abuse prevention, fail-closed for billing and security limits.
  • A per-process fallback limiter is the bounded middle ground — N× the intended limit beats unbounded (fail-open) and beats an outage (fail-closed); set it to global / instance_count.
  • Alert on the degraded path: a limiter silently running on local fallback is quota enforcement quietly disappearing.
  • Use EVALSHA with a NOSCRIPT fallback on hot paths so the script body is not re-sent per request.
