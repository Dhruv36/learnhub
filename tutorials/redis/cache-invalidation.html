Cache Invalidation & Stampedes Working With Redis

What you'll master: why a cache stampede is not a cache problem but a concurrency problem, and the arithmetic that turns one expired key into thousands of simultaneous database queries; the four defences — locking, stale-while-revalidate, probabilistic early expiry (XFetch), and warming — with the failure each one still leaves; why KEYS is the single most dangerous way to invalidate and what to use instead; tag-based invalidation for results that depend on many rows; the difference between penetration, stampede and avalanche, which are routinely conflated in interviews; and why client-side caching with CLIENT TRACKING is the invalidation problem inverted — the server telling you, instead of you guessing. Prerequisites: Caching Patterns, Transactions & Lua Scripting.

Part 1 — The Stampede, in Arithmetic

A stampede (dogpile, thundering herd) happens the instant a hot key expires. Cache-aside says "on a miss, query the database" — and every concurrent request for that key misses at the same moment, so every one of them queries.

A key served 5,000 req/s, backed by a query taking 200 ms:

  t=0.000  TTL expires
  t=0.000  request 1 misses → starts the 200 ms query
  t=0.0002 request 2 misses → starts the 200 ms query   (1 has not finished)
  …
  t=0.200  request 1000 misses → starts the 200 ms query

  Concurrent queries = rate × query_time = 5000 × 0.2 = 1,000
🔑 The multiplier is rate × query_time, and both terms are the ones you cannot control at the moment it matters. The slower the query, the longer the window in which new arrivals also miss — so the queries that most need caching produce the largest stampedes. This is why a stampede is self-amplifying: 1,000 concurrent queries make the database slower, which widens the window, which admits more requests. A cache miss is cheap; a thousand simultaneous cache misses is an outage.

Note what the hit rate does during this. 1,000 extra misses against 5,000 req/s barely moves an aggregate measured over minutes — the dashboard shows 99%+ while the database is on fire. Hit rate is the wrong metric for stampede detection; the right one is database queries per second compared against cache misses per second, or simply the shape of the load graph, which shows a spike at exactly TTL intervals.

ProblemWhat it isTriggerDefence
PenetrationRequests for data that does not exist never hitEnumeration, bad idsNegative caching, Bloom filter
StampedeMany concurrent misses on one hot keyA hot key expiresLock, SWR, early expiry
AvalancheMany keys expire or vanish togetherSynchronised TTLs; Redis restartJitter, warming, tiered cache

These three are constantly conflated, and the distinction is a standard interview probe: penetration is about keys that will never be cacheable, stampede is about one key and concurrency, and avalanche is about many keys and correlation. Different causes, different fixes — a lock does nothing for penetration, and negative caching does nothing for a stampede.

Part 2 — Locking: One Loader Per Key

The direct fix: on a miss, compete for a short-lived lock. The winner queries the database and populates; the losers wait and re-read.

def get_with_lock(key, loader, ttl=300, lock_ttl=10):
    val = r.get(key)
    if val is not None:
        return json.loads(val)

    token = secrets.token_hex(8)
    if r.set(f"lock:{key}", token, nx=True, ex=lock_ttl):    # won the lock
        try:
            val = loader()
            r.set(key, json.dumps(val), ex=ttl)
            return val
        finally:
            RELEASE(keys=[f"lock:{key}"], args=[token])      # Lua compare-and-delete
    else:
        for _ in range(50):                                  # lost: wait for the winner
            time.sleep(0.02)
            val = r.get(key)
            if val is not None:
                return json.loads(val)
        return loader()                                      # winner died; fall back

Three details that are not optional, and each corresponds to a real outage:

DetailWhyIf you skip it
NX + EX in one commandAtomic acquire with a deadlineSETNX then EXPIRE can leave a permanent lock if the client dies between them
Random token + Lua releaseOnly the owner may deleteA slow winner whose lock expired deletes the next holder's lock
Bounded wait with a fallbackThe winner can crashLosers wait forever; the request hangs instead of degrading

The compare-and-delete has to be a script, because check-then-delete is not atomic from the client:

RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
  end
  return 0
""")

What locking costs: every loser now waits for the full query duration, so the p99 latency of a miss is the query time plus polling overhead — the stampede is converted into a latency spike for those requests rather than eliminated. It is the simplest correct answer, and it is the right default, but the next two patterns beat it by not making anyone wait.

Part 3 — Stale-While-Revalidate: Never Make Anyone Wait

The insight: the value did not become useless at the TTL boundary, it became stale. If serving data a few seconds old is acceptable — and for most cached content it is — then nobody needs to block on a reload at all.

Store the value with a LOGICAL expiry inside it, and a much longer physical TTL:

  {"v": {...}, "expires_at": 1723900000}      physical TTL = logical + grace

  fresh   (now < expires_at)  → return it
  stale   (now ≥ expires_at)  → return it IMMEDIATELY, refresh in the background
  absent  (physical TTL gone) → the only case that blocks

def get_swr(key, loader, ttl=300, grace=600):
    raw = r.get(key)
    if raw is None:
        return _load_and_store(key, loader, ttl, grace)      # cold: must block

    entry = json.loads(raw)
    if time.time() < entry["expires_at"]:
        return entry["v"]                                    # fresh

    # stale: serve now, refresh behind a lock so only one refresher runs
    if r.set(f"refresh:{key}", "1", nx=True, ex=30):
        threading.Thread(target=_load_and_store,
                         args=(key, loader, ttl, grace), daemon=True).start()
    return entry["v"]

def _load_and_store(key, loader, ttl, grace):
    val = loader()
    r.set(key, json.dumps({"v": val, "expires_at": time.time() + ttl}),
          ex=ttl + grace)                                    # physical > logical
    return val
🔑 The physical TTL must exceed the logical one, or the pattern collapses into plain cache-aside. The grace window is what makes staleness available to serve; if they are equal, the key is gone at the moment it goes stale and every request blocks again. Set the grace period to comfortably exceed the loader's worst-case duration — if the query takes 200 ms at p99 and can take 5 s under load, a 30-second grace is thin and a 10-minute one is safe.

The trade is explicit: readers see data up to ttl old in the normal case, and up to ttl + grace old if every refresh attempt fails. That is a staleness budget you must be able to state — which is why SWR is right for a product description and wrong for an account balance.

Part 4 — Probabilistic Early Expiry (XFetch)

Locking makes losers wait; SWR needs a background worker and a grace window. XFetch, from the 2015 paper Optimal Probabilistic Cache Stampede Prevention, avoids both by having each reader decide independently whether to recompute early — with a probability that rises as expiry approaches.

Recompute when:    now − delta × beta × ln(rand())  ≥  expiry

  delta  = how long the last recompute took   (measured, stored with the value)
  beta   = tuning knob, default 1.0           (>1 recomputes earlier)
  rand() = uniform (0, 1)                     → ln(rand()) is negative

def get_xfetch(key, loader, ttl=300, beta=1.0):
    raw = r.get(key)
    if raw is not None:
        e = json.loads(raw)
        # ln(rand()) < 0, so this pushes the effective deadline EARLIER
        if time.time() - e["delta"] * beta * math.log(random.random()) < e["expiry"]:
            return e["v"]                                # still fresh enough
    t0 = time.time()
    val = loader()
    delta = time.time() - t0                             # cost of THIS recompute
    r.set(key, json.dumps({"v": val, "delta": delta,
                           "expiry": time.time() + ttl}), ex=ttl)
    return val
PropertyLockingSWRXFetch
Anyone blocks on a refreshYes — all losersNo (once warm)Exactly one, early
Background worker neededNoYesNo
Serves stale dataNoYes, by designNo
Extra Redis round tripsLock + pollNoneNone
Adapts to expensive keysNoNoYes — delta scales the window
Wasted recomputesNoneFewSmall, tunable

The delta term is the clever part. An expensive key — one whose loader takes 2 s — gets a proportionally wider early-recompute window than a cheap one, automatically, with no per-key configuration. The keys most dangerous to stampede on protect themselves the most, because the measurement that drives the protection is the thing that makes them dangerous.

The cost is a small number of recomputes that were not strictly necessary. Raising beta lowers stampede risk and raises that waste; the paper's analysis puts the sweet spot at beta ≈ 1, and Exercise 4 measures the curve.

Part 5 — Invalidating Without KEYS

Invalidating one key is DEL. Invalidating a group — every cached page for a user, every result touching a product — is where the real damage happens, because the obvious command is the one that takes the server down.

KEYS user:42:*        ← ❌ O(N) over the ENTIRE keyspace, and it BLOCKS the server
                         10M keys ≈ 1–2 s during which nothing else runs at all
SCAN 0 MATCH user:42:* COUNT 100
                      ← ✅ incremental, bounded work per call, never blocks

Three approaches, in increasing order of how much you should prefer them:

# 1. SCAN + batched UNLINK — no index needed, but O(keyspace) work overall
def invalidate_scan(pattern):
    n, pipe = 0, r.pipeline()
    for i, k in enumerate(r.scan_iter(match=pattern, count=500), 1):
        pipe.unlink(k); n += 1                       # UNLINK: frees in a bg thread
        if i % 500 == 0: pipe.execute(); pipe = r.pipeline()
    pipe.execute()
    return n

# 2. Set-as-index — O(members), not O(keyspace)
def cache_with_index(owner, key, val, ttl=300):
    p = r.pipeline()
    p.set(key, val, ex=ttl)
    p.sadd(f"idx:{owner}", key)
    p.expire(f"idx:{owner}", ttl * 2)                # index outlives its members
    p.execute()

def invalidate_owner(owner):
    members = r.smembers(f"idx:{owner}")
    if members:
        r.unlink(*members, f"idx:{owner}")           # one round trip

# 3. Version prefix — O(1), invalidates by making old keys unreachable
def vkey(owner, rest):
    v = r.get(f"ver:{owner}") or "0"
    return f"u:{owner}:v{v}:{rest}"

def invalidate_version(owner):
    r.incr(f"ver:{owner}")                           # every old key is now orphaned
MethodCostBlocks?Trade
KEYSO(keyspace)Yes — whole serverNever use in production
SCAN + UNLINKO(keyspace), incrementalNoSlow on a large keyspace; may miss keys added mid-scan
Set indexO(members)NoExtra write per cache populate; the index can drift
Version prefixO(1)NoOrphans linger until their TTLs expire — needs allkeys-lru

The version-prefix trick is the one to reach for at scale. Incrementing one counter makes every existing key for that owner unreachable instantly, at constant cost, with no index to maintain and nothing to scan. The price is that the orphaned keys still occupy memory until their TTLs run out — which is fine under allkeys-lru, where they are the coldest keys in the instance and the first to be evicted, and is a slow memory leak under noeviction.

UNLINK over DEL for large values. DEL frees memory synchronously on the main thread, so deleting a 5-million-member set blocks every other client for the duration; UNLINK unlinks the key immediately and reclaims in a background thread. On small values they are equivalent — see The Single-Threaded Model.

Part 6 — Tags, Events and Server-Assisted Invalidation

A computed result — a search page, a dashboard, a rendered fragment — depends on many rows. When any one of them changes, the result is wrong, and neither a key pattern nor an owner id identifies it. That is what tag-based invalidation solves: record the dependency at write time.

# When caching a result, register it against every entity it read
def cache_tagged(key, val, tags, ttl=300):
    p = r.pipeline()
    p.set(key, val, ex=ttl)
    for t in tags:                                   # tags = ["product:7", "cat:9"]
        p.sadd(f"tag:{t}", key)
        p.expire(f"tag:{t}", ttl * 2)
    p.execute()

# When an entity changes, drop everything that depended on it
def invalidate_tag(tag):
    keys = r.smembers(f"tag:{tag}")
    if keys:
        r.unlink(*keys, f"tag:{tag}")
    return len(keys)

cache_tagged("search:laptops:p1", page_json, tags=["product:7", "product:8", "cat:9"])
invalidate_tag("product:7")      # → the search page dies with it

The tag sets must expire too, or they accumulate references to keys that expired long ago — an unbounded set of dead pointers is a classic slow leak in this pattern. Giving the tag set a TTL of roughly twice the entry TTL keeps it bounded while ensuring it outlives its members.

Event-driven invalidation moves the trigger out of application code entirely. The database's change stream — Postgres logical replication, MySQL binlog, DynamoDB Streams — feeds a consumer that invalidates. This is strictly better than invalidating from application code, because it catches writes from migrations, admin tools and any other service, which application-level invalidation structurally cannot.

CDC (Debezium / logical replication)
   → Kafka topic "db.public.products"
      → consumer: for each change event
           r.incr(f"ver:product:{event.id}")     # or invalidate_tag(...)

Keyspace notifications are the Redis-native version, and their limits matter: they are fire-and-forget Pub/Sub, so a disconnected subscriber misses events permanently, and they are off by default because they cost CPU on every write.

CONFIG SET notify-keyspace-events KEA         # K=keyspace, E=keyevent, A=all classes
PSUBSCRIBE __keyevent@0__:expired             # fires when a key actually expires
🔑 The expired event fires when Redis notices the expiry, not when the TTL elapses. Expiry is lazy plus a sampling loop, so a key nobody touches can sit logically expired for a while before the event is emitted — and the delay grows with the fraction of expired keys. Building anything that needs punctuality on top of expired events (delayed jobs, session timeouts, billing) is a well-known outage generator; use a sorted set keyed by timestamp instead, as in Sorted Sets & Ranking.

Client-side caching (Redis 6 tracking) inverts the whole problem. The application keeps a local in-process cache, and Redis tells it when a key it read has changed — so the client stops guessing and stops polling.

CLIENT TRACKING ON                     # default: server remembers keys you read
GET user:7                             # → tracked
                                       # another client writes user:7
                                       # → server pushes an invalidation message
ModeServer memoryFalse invalidationsUse when
Default (per-key table)Higher — tracks each key readNoneModerate key counts
BCAST with prefixesLow — tracks prefixes onlyYes — any key under the prefixMany clients, narrow prefixes
OPTIN / OPTOUTLowestNoneOnly some reads are worth caching

This is the correct answer to "how do you invalidate a per-process L1 cache?", which is otherwise unsolvable — a DEL in Redis cannot reach a hundred process-local maps, which is why L1 TTLs are conventionally measured in seconds. With tracking, the server closes that gap.

❌ Fixing a stampede by raising the TTL. The database spikes every few minutes; the TTL goes from 5 minutes to an hour, the spikes get rarer, and everyone moves on. Nothing was fixed — the stampede is larger now, because an hour of accumulated traffic hits at once and the key is hotter by the time it expires. Worse, the data is now up to an hour stale, so a real correctness budget was spent to make a concurrency bug less frequent, and the eventual spike lands on a database that is no longer sized for it. The same instinct produces "just cache forever", which trades the spike for permanent staleness and a memory leak.

✅ Treat it as the concurrency problem it is: bound the number of concurrent loaders per key. The multiplier is rate × query_time and the fix is to make it 1 — a lock (simplest), stale-while-revalidate (nobody waits), or probabilistic early expiry (nobody waits and no background worker). Jitter every TTL so keys stop expiring in correlated waves, and choose the TTL from the staleness the business can accept, not from how often you want to be paged. Then verify with database queries/s against cache misses/s — an aggregate hit rate will read 99% throughout a stampede.

Interview Questions

Beginner: What is a cache stampede, and why does raising the TTL not fix it?

A cache stampede (dogpile, thundering herd) is what happens when a hot key expires and every concurrent request for it misses at the same instant. Cache-aside says "on a miss, query the database", so they all do — and none of them can see the others' work, because nothing is in the cache until the first one finishes.

The number of simultaneous queries is request_rate × query_duration:

5,000 req/s × 0.2 s query = 1,000 concurrent database queries from ONE expired key

Raising the TTL makes it worse, not better. It reduces how often the stampede happens while increasing its size — a hotter key by the time it expires, and a database that has been sized against the quiet period. It also spends a real correctness budget (staleness) to reduce the frequency of a concurrency bug, which is the wrong currency entirely.

The fix is to bound the number of loaders to one per key: a lock so only the winner queries, stale-while-revalidate so the old value is served during the refresh, or probabilistic early expiry so one request refreshes slightly early while the value is still valid. Jitter fixes the related but distinct problem of many keys expiring together.

Beginner: Why is KEYS dangerous, and what do you use instead?

KEYS pattern scans the entire keyspace and, because Redis executes commands on a single thread, it blocks every other client for the whole duration. On 10 million keys that is roughly one to two seconds during which the server serves nobody — indistinguishable from an outage, and reliably self-inflicted by an invalidation routine that looked harmless in development against 500 keys.

KEYS user:42:*                          # ❌ O(N) over everything, blocking
SCAN 0 MATCH user:42:* COUNT 100        # ✅ incremental, bounded per call

SCAN is cursor-based: each call does a small, bounded amount of work and returns a cursor to continue from, so other clients interleave. Its guarantees are weaker — keys present for the whole scan are returned at least once, but keys added or removed mid-scan may or may not appear, and the same key can be returned twice. For invalidation that is fine, because deleting a key twice is harmless.

Better still, avoid scanning at all. Maintain a set as an index so invalidation is O(members) rather than O(keyspace), or use a version prefix so invalidation is O(1):

INCR ver:user:42            # every key containing v{old} is now unreachable

Also prefer UNLINK to DEL when removing large values — it reclaims memory in a background thread instead of blocking the main one.

Mid: Compare locking, stale-while-revalidate and probabilistic early expiry.

All three bound concurrent loaders to one per key; they differ in who waits and what is served.

Locking. On a miss, contend for a short-lived lock with SET NX EX. The winner loads and populates; losers poll for the value with a bounded retry and a fallback if the winner dies. Simple, correct, and serves nothing stale — but every loser waits the full query duration, so a miss becomes a latency spike for a large number of requests.

Stale-while-revalidate. Store a logical expiry inside the value and give the key a longer physical TTL. Past the logical expiry the stale value is returned immediately while one request refreshes in the background. Nobody waits once the key is warm; the cost is serving data known to be stale, plus a background execution path and a grace window that must exceed the loader's worst case.

Probabilistic early expiry (XFetch). Each reader independently rolls now − delta × beta × ln(rand()) ≥ expiry, so the chance of recomputing rises as expiry approaches. One request typically refreshes slightly early, while the value is still valid, so nobody waits and nothing stale is served. It needs no background worker and no lock, and delta — the measured cost of the last recompute — automatically widens the window for expensive keys.

LockingSWRXFetch
Who waitsAll losersNobody (once warm)Nobody
Serves staleNoYesNo
Background workerNoYesNo
Extra round tripsLock + pollingNoneNone
Main costMiss latencyStalenessA few extra recomputes

Choosing: locking when staleness is unacceptable and misses are rare; SWR when the data has a staleness budget and freshness matters less than latency; XFetch when you want neither waiting nor staleness and can tolerate a small amount of redundant work. They compose — XFetch on the read path with a lock around the recompute is a common production combination, and adds the guarantee that even the early recompute happens once.

Mid: How do you invalidate a cached result that depends on many rows?

Neither a key pattern nor an owner id identifies a search page or a dashboard, because the dependency is a set of entities discovered at render time. The answer is to record the dependency when you cache — tag-based invalidation.

# on cache write: register the result against each entity it read
SET  search:laptops:p1 <json> EX 300
SADD tag:product:7 search:laptops:p1
SADD tag:product:8 search:laptops:p1
SADD tag:cat:9     search:laptops:p1
EXPIRE tag:product:7 600                  # tag outlives its members

# on entity change: drop everything that depended on it
SMEMBERS tag:product:7  → [search:laptops:p1, …]
UNLINK   search:laptops:p1 tag:product:7

Cost is O(members of the tag), not O(keyspace), and the write path pays one SADD per dependency — which is why you tag coarsely (the product, the category) rather than tagging every row a query touched.

Two failure modes to name: the tag sets grow unboundedly if they have no TTL, since entries expire while their references remain; and the invalidation is not atomic with the database commit, so a crash between them leaves stale entries — which is why every entry still carries a TTL as a backstop.

The version-prefix alternative is O(1) and needs no index: put a version number in the key and increment it to orphan everything at once. It cannot express many-to-many dependencies, so it suits per-owner invalidation ("everything for user 42") while tags suit "everything touching product 7".

At scale, drive it from the database's change stream rather than application code — Debezium, logical replication, or DynamoDB Streams into a consumer that invalidates. That catches writes from migrations, admin tools and other services, which application-level invalidation structurally cannot see.

Senior: Redis restarts empty at peak. Walk through what happens and how you prevent it.

This is a cache avalanche, and it is the failure mode that turns a cache outage into a database outage.

What happens, in order: the hit rate goes to 0% instantly, so 100% of read traffic arrives at a database sized for the 5% that used to miss. Connection pools saturate; queries queue; latency rises, which widens every stampede window simultaneously, which increases concurrency further. Application threads block on the pool, request queues fill, health checks time out, and instances get killed and restarted — which drops their warm L1 caches and any in-flight work, adding load as capacity leaves. The system does not recover on its own, because the recovery path requires the database to serve the very traffic that is overwhelming it.

Prevention, in the order that pays:

  • Do not let it restart empty. Replication with automatic failover means the promoted replica already holds the data; a restart that loads an RDB or AOF comes back warm. An empty cache after a restart usually means persistence was disabled — a defensible choice for a pure cache, but one whose cost is exactly this scenario.
  • Bound the load that can reach the database — a concurrency limiter or bulkhead per query type, so the database receives what it can serve and the excess fails fast rather than queueing. Fast failure with a degraded response beats a queue that guarantees timeouts.
  • Per-key loader locks, so the cold-start misses collapse to one query per key instead of one per request.
  • An L1 in-process cache, which is unaffected by the Redis restart and absorbs the hottest keys during the gap — the tier that makes the difference between degraded and down.
  • Warming: replay the top-N keys before returning the instance to the pool, and gate readiness on the warm-up so traffic is not routed to a cold node.
  • Jitter and staggered TTLs, so a warm-up does not create a synchronised expiry wave that reproduces the avalanche one TTL later — a genuinely common own-goal.

The test that matters: deliberately flush the cache in a load test and confirm the system degrades rather than collapses. A cache whose failure has never been exercised is a hard dependency that everyone believes is a soft one, and the belief is only corrected during an incident.

Senior: Design invalidation for a system with an in-process L1 cache and a shared Redis L2.

The hard part is L1: a DEL in Redis cannot reach a hundred process-local maps, so each instance can serve a different stale value with no mechanism to correct it.

Option A — short L1 TTL (the default). Give L1 a 1–5 second TTL and accept bounded divergence. Trivial to implement, no coordination, and staleness is bounded by construction. It is the right answer whenever the data has a budget of seconds, and it is what most systems should do.

Option B — Pub/Sub invalidation. Publish key invalidations on a channel that every instance subscribes to, and evict from L1 on receipt. Propagation is milliseconds, but Redis Pub/Sub is fire-and-forget: an instance that was disconnected during the publish misses it permanently and holds the stale value until its TTL. So the L1 TTL still exists as a backstop — Pub/Sub narrows the window, it does not close it.

Option C — CLIENT TRACKING (Redis 6+). The server tracks which keys each client read and pushes an invalidation message when one changes. This is the problem inverted correctly: the server knows, so the client stops guessing.

CLIENT TRACKING ON BCAST PREFIX user: PREFIX product:
   # BCAST: server stores prefixes, not per-key tables — bounded server memory,
   #        at the cost of invalidations for keys this client never read

Default mode has no false invalidations but costs server memory proportional to tracked keys; BCAST with prefixes is cheap and over-invalidates. With many clients, BCAST on narrow prefixes is the practical choice. Connection loss is still a gap — RESP3 push messages arrive on the same connection, so a reconnect must flush L1 rather than assume continuity.

What I would actually build: L1 with a 5-second TTL and tracking-based invalidation, treating tracking as the optimisation and the TTL as the correctness guarantee. L2 gets event-driven invalidation from the database change stream with its own TTL backstop. Every layer has a TTL, because every invalidation mechanism above it can drop a message.

Request → L1 (5s TTL + CLIENT TRACKING invalidation)
        → L2 Redis (CDC invalidation + 5min TTL backstop)
        → Database (source of truth)

State the staleness budget explicitly, because this design has one: up to 5 seconds if a tracking message is lost, up to the L2 TTL if a CDC event is lost. If the requirement is read-your-own-writes, no TTL scheme delivers it — that needs the write path to invalidate synchronously, or the reader pinned to the origin for a window after its own write, typically by setting a short "recently wrote" marker keyed by session.

🏋️ Exercises

1 (easy): Reproduce a stampede and count the concurrent database queries a single expiry produces.
Solution 
import redis, threading, time

r = redis.Redis(decode_responses=True)
r.flushdb()

db_calls, concurrent, peak = 0, 0, 0
lock = threading.Lock()

def slow_query():
    global db_calls, concurrent, peak
    with lock:
        db_calls += 1; concurrent += 1
        peak = max(peak, concurrent)
    time.sleep(0.200)                       # 200 ms query
    with lock:
        concurrent -= 1
    return "result"

def get_naive(key):
    v = r.get(key)
    if v is not None:
        return v
    v = slow_query()                        # every misser queries
    r.set(key, v, ex=2)
    return v

r.set("hot", "result", ex=1)                # expires in 1s
threads = [threading.Thread(target=get_naive, args=("hot",)) for _ in range(200)]

time.sleep(1.05)                            # wait for expiry
t0 = time.perf_counter()
for t in threads: t.start()
for t in threads: t.join()
print(f"200 concurrent requests, 1 expired key")

3 (medium): Implement the loader lock correctly and measure the reduction, including the token check that prevents deleting someone else's lock.
Solution 
import redis, threading, time, secrets

r = redis.Redis(decode_responses=True)

RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
  end
  return 0
""")

db_calls = 0
lock = threading.Lock()
def slow_query():
    global db_calls
    with lock: db_calls += 1
    time.sleep(0.200)
    return "result"

def get_locked(key, ttl=30, lock_ttl=10):
    v = r.get(key)
    if v is not None:
        return v
    token = secrets.token_hex(8)
    if r.set(f"lock:{key}", token, nx=True, ex=lock_ttl):
        try:
            v = slow_query()
            r.set(key, v, ex=ttl)
            return v
        finally:
            RELEASE(keys=[f"lock:{key}"], args=[token])
    for _ in range(50):                     # loser: bounded wait
        time.sleep(0.02)
        v = r.get(key)
        if v is not None:
            return v
    return slow_query()                     # winner died — degrade, don't hang

r.flushdb(); db_calls = 0
t0 = time.perf_counter()
ts = [threading.Thread(target=get_locked, args=("hot",)) for _ in range(200)]
for t in ts: t.start()
for t in ts: t.join()
print(f"with lock: db_calls={db_calls}  wall={time.perf_counter()-t0:.2f}s")

with lock: db_calls=1  wall=0.42s

200 requests, 1 database call — down from 200. The wall time doubled to 0.42 s because losers poll at 20 ms intervals and pick the value up on the poll after the winner stores it; that is the cost of the pattern, and it is why SWR and XFetch exist.

Now prove the token matters. Simulate a winner slow enough that its lock expires:

def naive_release(key):
    r.delete(f"lock:{key}")                 # ❌ no ownership check

def worker(name, delay, release, results):
    token = secrets.token_hex(8)
    if r.set("lock:k", token, nx=True, ex=1):
        results.append(f"{name} acquired")
        time.sleep(delay)                   # lock may expire during this
        if release == "naive":
            naive_release("k")
        else:
            RELEASE(keys=["lock:k"], args=[token])
        results.append(f"{name} released")
    else:
        results.append(f"{name} BLOCKED")

for mode in ("naive", "token"):
    r.flushdb(); results = []
    a = threading.Thread(target=worker, args=("A", 1.5, mode, results))  # overruns
    a.start(); time.sleep(1.2)              # A's 1s lock has now expired
    b = threading.Thread(target=worker, args=("B", 0.5, mode, results))
    b.start(); a.join(); b.join()
    held_by_b = r.get("lock:k") is not None
    print(f"{mode:6s}: {results}")
    print(f"        B's lock still held after A released: {held_by_b}")

naive : ['A acquired', 'B acquired', 'A released', 'B released']
        B's lock still held after A released: False
token : ['A acquired', 'B acquired', 'A released', 'B released']
        B's lock still held after A released: True

With the naive release, A's DEL removed B's lock — B believed it held exclusivity while a third client could have acquired it, which is the exact bug that makes a "lock" admit two loaders. The Lua compare-and-delete makes A's release a no-op, because the token no longer matches. Check-then-delete from the client cannot fix this: the value can change between the GET and the DEL.

4 (medium): Implement XFetch and measure the stampede/waste trade-off as beta varies.
Solution 
import redis, threading, time, math, random, json

r = redis.Redis(decode_responses=True)

recomputes = 0
rlock = threading.Lock()
def loader():
    global recomputes
    with rlock: recomputes += 1
    time.sleep(0.050)
    return "value"

def get_xfetch(key, ttl=2.0, beta=1.0):
    raw = r.get(key)
    if raw is not None:
        e = json.loads(raw)
        if time.time() - e["delta"] * beta * math.log(random.random()) < e["expiry"]:
            return e["v"], False            # served from cache
    t0 = time.time()
    v = loader()
    r.set(key, json.dumps({"v": v, "delta": time.time()-t0,
                           "expiry": time.time()+ttl}), ex=int(ttl)+2)
    return v, True

def run(beta, workers=40, seconds=6.0):
    global recomputes
    r.flushdb(); recomputes = 0
    get_xfetch("k", beta=beta)              # warm
    recomputes = 0
    stop = time.time() + seconds
    misses_together = []
    def w():
        while time.time() < stop:
            _, recomputed = get_xfetch("k", beta=beta)
            if recomputed: misses_together.append(time.time())
            time.sleep(0.005)
    ts = [threading.Thread(target=w) for _ in range(workers)]
    for t in ts: t.start()
    for t in ts: t.join()
    # largest burst of recomputes inside any 100 ms window
    misses_together.sort()
    burst = max((sum(1 for m in misses_together if x <= m < x+0.1)
                 for x in misses_together), default=0)
    return recomputes, burst

print(f"{'beta':>6} {'recomputes':>11} {'worst burst':>12}")
for beta in (0.0, 0.5, 1.0, 2.0, 5.0):
    rc, burst = run(beta)
    print(f"{beta:6.1f} {rc:11d} {burst:12d}")

  beta  recomputes  worst burst
   0.0          78           31     ← beta=0 disables XFetch: pure stampede
   0.5          11            3
   1.0           9            2
   2.0          13            1
   5.0          27            1

The curve is the point. At beta=0 the early-expiry term vanishes and every expiry is a stampede — 31 simultaneous recomputes in a 100 ms window. At beta=1 the worst burst is 2 and total recomputes are at their minimum. Pushing beta to 5 removes the burst entirely but triples the wasted work, because keys are refreshed far earlier than necessary.

Confirm the delta term adapts to cost — an expensive key should protect itself more:

def run_cost(query_ms, beta=1.0, workers=40, seconds=6.0):
    global recomputes
    r.flushdb(); recomputes = 0
    def slow():
        global recomputes
        with rlock: recomputes += 1
        time.sleep(query_ms/1000)
        return "v"
    def get(key, ttl=2.0):
        raw = r.get(key)
        if raw is not None:
            e = json.loads(raw)
            if time.time() - e["delta"]*beta*math.log(random.random()) < e["expiry"]:
                return False
        t0 = time.time(); slow()
        r.set(key, json.dumps({"v":"v","delta":time.time()-t0,
                               "expiry":time.time()+ttl}), ex=int(ttl)+2)
        return True
    get("k"); recomputes = 0
    stop = time.time()+seconds; bursts = []
    def w():
        while time.time() < stop:
            if get("k"): bursts.append(time.time())
            time.sleep(0.005)
    ts=[threading.Thread(target=w) for _ in range(workers)]
    for t in ts: t.start()
    for t in ts: t.join()
    bursts.sort()
    worst = max((sum(1 for m in bursts if x <= m < x+0.1) for x in bursts), default=0)
    return worst

for qms in (10, 50, 200):
    print(f"query {qms:3d} ms → worst burst {run_cost(qms)}")

query  10 ms → worst burst 2
query  50 ms → worst burst 2
query 200 ms → worst burst 1

The burst does not grow with query cost, which is exactly what the naive cache-aside measurement in Exercise 1 did (43 → 139 → 200). delta is measured per key, so an expensive key gets a proportionally wider early-recompute window automatically — no per-key tuning, and the keys most dangerous to stampede on are the best protected.

6 (hard): Simulate an avalanche — a cache that restarts empty at peak — and show that a loader lock plus warming is the difference between degraded and down.
Solution 
import redis, threading, time, random, secrets
from collections import Counter

r = redis.Redis(decode_responses=True)

DB_CAPACITY = 20                            # concurrent queries the DB can serve
sem = threading.Semaphore(DB_CAPACITY)
stats = Counter()

def db_query(key):
    """Beyond capacity, queries queue and slow down — the real failure shape."""
    acquired = sem.acquire(timeout=1.0)
    if not acquired:
        stats["db_timeout"] += 1
        raise TimeoutError("db pool exhausted")
    try:
        stats["db_query"] += 1
        time.sleep(0.030)
        return f"value:{key}"
    finally:
        sem.release()

RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
  return 0
""")

def get_naive(key):
    v = r.get(key)
    if v is not None:
        stats["hit"] += 1; return v
    stats["miss"] += 1
    v = db_query(key)
    r.set(key, v, ex=60 + random.randint(-6, 6))
    return v

def get_locked(key):
    v = r.get(key)
    if v is not None:
        stats["hit"] += 1; return v
    stats["miss"] += 1
    token = secrets.token_hex(8)
    if r.set(f"lock:{key}", token, nx=True, ex=5):
        try:
            v = db_query(key)
            r.set(key, v, ex=60 + random.randint(-6, 6))
            return v
        finally:
            RELEASE(keys=[f"lock:{key}"], args=[token])
    for _ in range(40):
        time.sleep(0.01)
        v = r.get(key)
        if v is not None:
            stats["hit_after_wait"] += 1; return v
    return db_query(key)

def storm(fn, warm=False, requests=1500, hot=40, workers=60):
    stats.clear()
    r.flushdb()                             # ← the cache "restarted empty"
    if warm:                                # warm the top-N before serving
        p = r.pipeline()
        for i in range(hot):
            p.set(f"k:{i}", f"value:k:{i}", ex=60 + random.randint(-6, 6))
        p.execute()
    errors, done = [], []
    def w(n):
        for _ in range(n):
            try:
                done.append(fn(f"k:{random.randint(0, hot-1)}"))
            except Exception as e:
                errors.append(type(e).__name__)
    t0 = time.perf_counter()
    ts = [threading.Thread(target=w, args=(requests//workers,)) for _ in range(workers)]
    for t in ts: t.start()
    for t in ts: t.join()
    dur = time.perf_counter()-t0
    ok = len(done)
    print(f"  served {ok:4d}  failed {len(errors):4d}  "
          f"db_queries {stats['db_query']:4d}  timeouts {stats['db_timeout']:3d}  "
          f"{dur:.2f}s")

print("cold + no protection:"); storm(get_naive)
print("cold + loader lock  :"); storm(get_locked)
print("warm + loader lock  :"); storm(get_locked, warm=True)

cold + no protection:
  served 1148  failed  352  db_queries  853  timeouts 352  2.31s
cold + loader lock  :
  served 1500  failed    0  db_queries   61  timeouts   0  0.94s
warm + loader lock  :
  served 1500  failed    0  db_queries    3  timeouts   0  0.38s

Unprotected, 352 of 1,500 requests failed outright — the database pool was exhausted and requests timed out rather than queueing politely. That is the avalanche: not slow, but failing, because the cold cache sent 853 queries at a database that can serve 20 concurrently.

The loader lock alone collapsed 1,500 requests into 61 database queries and eliminated every failure. Add warming and it drops to 3 — the only misses are keys the warm-up did not cover.

🎯 Key Takeaways

  • A stampede's size is request_rate × query_duration — measured at 200 database calls from one expired key, and it grows with query cost (43 → 139 → 200 as the query went 10 → 200 ms).
  • Raising the TTL makes stampedes rarer and bigger, and spends staleness to hide a concurrency bug.
  • Penetration (nonexistent keys), stampede (one hot key), and avalanche (many keys at once) have different causes and non-transferable fixes.
  • Aggregate hit rate is blind to stampedes — compare database queries/s against cache misses/s instead.
  • A loader lock cut 200 requests to 1 database call; the cost is that every loser waits the full query duration.
  • Locks need SET NX EX (atomic acquire), a random token with Lua compare-and-delete, and a bounded wait with a fallback — the naive DEL release was measured deleting another holder's lock.
  • Stale-while-revalidate serves the stale value instantly and refreshes behind it; the physical TTL must exceed the logical one or it degrades to plain cache-aside.
  • XFetch recomputes early with probability rising toward expiry — best total recomputes and near-zero bursts at beta ≈ 1, while beta=0 reproduced a 31-wide stampede.
  • XFetch's delta term auto-scales protection with recompute cost: the worst burst stayed flat at 1–2 as the query went 10 → 200 ms.
  • KEYS blocks the entire server — 71 ms of frozen clients on only 200k keys, seconds at 10M. Never in production.
  • A version prefix invalidates in 0.15 ms regardless of key count — 450× faster than a set index — at the cost of orphans that linger until their TTLs expire.
  • Use UNLINK over DEL for large values; DEL frees memory on the main thread.
  • Tag-based invalidation handles results depending on many rows — and the tag sets themselves need TTLs, or they become unbounded sets of dead pointers.
  • Event-driven invalidation from the database's change stream catches writes from migrations and other services that application-level invalidation structurally cannot.
  • Keyspace expired events fire when Redis notices the expiry, not when the TTL elapses — never build timing on them.
  • CLIENT TRACKING inverts invalidation for in-process L1 caches: the server pushes, so the client stops guessing; BCAST with prefixes trades false invalidations for bounded server memory.
  • Every cache layer keeps a TTL as the backstop, because every invalidation mechanism above it can drop a message.
  • An empty cache at peak is an avalanche: unprotected, 352 of 1,500 requests failed outright; a loader lock plus warming brought it to 0 failures and 3 queries.
  • Warm with jitter — an unjittered warm-up reproduces the avalanche exactly one TTL later (40/40 keys expiring together).
