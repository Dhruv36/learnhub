Redis Cluster Durability & Distribution

What you'll master: why Cluster uses 16,384 fixed hash slots rather than consistent hashing, and what that number is actually chosen for; MOVED versus ASK — two redirects that look alike and mean completely different things, one of which is the whole resharding mechanism; hash tags, and how the fix for multi-key operations becomes the hotspot that takes a shard down; the operations Cluster silently takes away from you and what replaces them; failover driven by the gossip bus rather than Sentinel, and the two settings that decide whether the cluster stays available or protects consistency; live resharding with zero downtime, including the state a key occupies while it is mid-migration; and the honest answer to "should we use Cluster at all", which for most systems is no. Prerequisites: Replication & Failover, Commands, Pipelining & Round Trips.

Part 1 — 16,384 Slots, Not Consistent Hashing

Redis Cluster shards the keyspace into a fixed number of hash slots, and assigns ranges of slots to primaries. Every key deterministically belongs to exactly one slot.

slot = CRC16(key) mod 16384

3 primaries:
  node A: slots     0 – 5460
  node B: slots  5461 – 10922
  node C: slots 10923 – 16383

CLUSTER KEYSLOT user:42     → 12539     ← always, on every node, forever
🔑 The slot layer exists so that rebalancing moves slots, not keys. Adding a node does not rehash anything: you reassign slot ranges, and the keys follow. Every client and every node can compute a key's slot independently with no shared state, and the mapping never changes — only the slot-to-node assignment does. That indirection is what makes live resharding possible without a coordinator deciding where each key lives.

Why 16,384 and not 65,536? Nodes gossip their slot ownership as a bitmap in every heartbeat. 16,384 bits is 2 KB per message; 65,536 would be 8 KB, and with heartbeats flowing between every pair of nodes continuously, that quadrupling is real bandwidth. The number is a deliberate trade: fine enough to balance a few hundred nodes, small enough that the gossip bitmap stays cheap.

Cluster hash slotsConsistent hashing ring
MappingFixed 16,384 slotsVirtual nodes on a ring
Client knowledgeFull slot→node mapRing topology
Rebalance unitA slot (explicit)Ring segments (implicit)
Control over placementExact — move any slot anywhereDetermined by hashing
Migration visibilityExplicit per-slot stateImplicit

Compared with a consistent-hashing ring, fixed slots give explicit control: an operator can move one specific slot from one node to another, which is exactly what makes the resharding protocol in Part 5 tractable.

Part 2 — MOVED and ASK: Two Redirects, Two Meanings

Clients connect to any node. If a key is not served locally, the node redirects — and the two redirect types mean different things.

GET user:42
  → (error) MOVED 12539 10.0.1.3:6379
            └─┬─┘ └──────┬──────┘
            slot     the node that OWNS it PERMANENTLY

  Client action: update the cached slot map, retry there, remember it.

GET user:42
  → (error) ASK 12539 10.0.1.4:6379
            └┬┘
      this slot is MIGRATING; this key has already moved

  Client action: send ASKING, then the command, to that node ONCE.
                 Do NOT update the slot map — ownership has not changed.
🔑 MOVED is permanent, ASK is for one command only — and a client that treats ASK like MOVED corrupts its slot map mid-migration, sending every key in the slot to a node that owns only some of them. ASK exists precisely because during migration a slot's keys are split across two nodes: those already copied live on the target, the rest remain on the source. It is the mechanism that makes resharding possible with zero downtime.

A good client caches the slot map and refreshes it on MOVED, so the steady state is one round trip per command with no redirects at all:

CLUSTER SLOTS        # slot ranges → primary + replicas (older, widely supported)
CLUSTER SHARDS       # Redis 7 replacement, richer topology info

# python: the client fetches and maintains the map for you
from redis.cluster import RedisCluster
rc = RedisCluster(host="10.0.1.1", port=6379, decode_responses=True)

Reading from replicas is opt-in, because by default a replica also replies MOVED pointing at its primary:

READONLY      # this connection may serve reads from a replica (stale, per replication)
READWRITE     # revert

Part 3 — Multi-Key Operations and Hash Tags

This is the constraint that reshapes applications. A multi-key command works only if every key lands in the same slot — otherwise Redis refuses it outright.

MGET user:1 user:2 user:3
  → (error) CROSSSLOT Keys in request don't hash to the same slot

MULTI/EXEC across slots  → same error
Lua script with KEYS in different slots → same error
SINTER, ZUNIONSTORE, RENAME across slots → same error

Hash tags are the escape hatch: only the substring inside the first {...} is hashed, so keys can be forced into the same slot deliberately.

user:1:profile      → CRC16("user:1:profile")   → slot 5432
user:1:settings     → CRC16("user:1:settings")  → slot 9871   ← different node

{user:1}:profile    → CRC16("user:1")           → slot 3421
{user:1}:settings   → CRC16("user:1")           → slot 3421   ← same slot ✅

MGET {user:1}:profile {user:1}:settings     → works
🔑 Hash tags are also the standard way to create a hotspot. Every key tagged {global} lands on one node, so a "shared" counter or a leaderboard tagged that way makes one shard absorb traffic the cluster was supposed to spread. The rule is to tag with something that has high cardinality and matches your access pattern — a user ID, a tenant ID, an order ID — never a constant, and never a low-cardinality value like a region or a status.

Tag choiceEffect
{user:1}:*✅ One user's keys colocate; millions of users spread evenly
{order:99}:*✅ High cardinality, matches transactional grouping
{tenant:acme}:*⚠️ Fine unless one tenant is far larger than the rest
{global}:*❌ Every key on one node — the cluster is now one node
{eu-west}:*❌ A handful of values → a handful of hot slots

Keys used together in a Lua script must share a slot too, which means the hash tag has to be designed alongside the script — retrofitting one across an existing keyspace requires migrating every affected key.

Part 4 — What Cluster Takes Away

Cluster is not a transparent upgrade. Several things that work on a single instance stop working, and discovering them after migration is the usual pattern.

FeatureIn ClusterReplacement
Multi-key commands across slots❌ CROSSSLOTHash tags, or per-key calls
Transactions across slots❌Hash tags, or redesign
Lua with keys in different slots❌Hash tags
Multiple databases (SELECT)❌ Only DB 0Key prefixes
KEYS / SCAN whole keyspace⚠️ Per-node onlyIterate every node
PUBLISH⚠️ Broadcasts to all nodesSPUBLISH (7.0+)
FLUSHALL, DBSIZE⚠️ Per-nodeLoop over primaries
Pipelining a mixed batch⚠️ Client must split by nodeCluster-aware client

The per-node scope of SCAN and DBSIZE catches people out — a maintenance script that iterated the keyspace on a single instance now silently covers a third of it:

# correct full-keyspace scan in Cluster
for node in rc.get_primaries():
    for key in node.scan_iter(match="session:*", count=500):
        ...

total = sum(node.dbsize() for node in rc.get_primaries())

PUBLISH is worse than merely per-node. To let a subscriber attach anywhere, Redis broadcasts every published message to every node in the cluster — so Pub/Sub cost grows with cluster size, and high-volume publishing can saturate the bus that failure detection depends on. Redis 7's SPUBLISH/SSUBSCRIBE bind channels to slots and remove the broadcast, as covered in Pub/Sub.

Part 5 — Failover, Gossip, and Availability Settings

Cluster does not use Sentinel. Nodes monitor each other over the cluster bus (port + 10000) using a gossip protocol, and replicas promote themselves with agreement from a majority of primaries.

1. PFAIL — one node cannot reach another (possible failure)
2. Gossip spreads the suspicion
3. FAIL  — a MAJORITY OF PRIMARIES agree the node is down
4. A replica of the failed primary requests votes
5. Majority of primaries vote → the replica promotes and claims the slots
🔑 Only primaries vote, and a majority of primaries is required — which means a cluster needs at least 3 primaries to tolerate any failure at all. With two primaries, losing one leaves a single node that cannot form a majority of two, so no failover happens and the cluster is stuck. This is why the documented minimum is 3 primaries plus 3 replicas: six nodes, before any capacity consideration.

cluster-node-timeout 15000              # how long unreachable = PFAIL
cluster-require-full-coverage yes       # ← the availability decision, below
cluster-replica-validity-factor 10      # refuse promotion if too far behind
cluster-migration-barrier 1             # keep ≥1 replica before donating one

cluster-require-full-coverage is the setting that decides what happens when a shard is lost entirely, and it is a genuine consistency-versus-availability choice:

yes (default)no
If any slot is unassignedThe whole cluster rejects writesOther shards keep serving
Failure isTotal but obviousPartial and silent
Right forData where partial results are wrongCaches; independent workloads

With the default, losing one shard and its replicas takes the entire cluster down for writes — surprising, but deliberate: it prevents an application from silently operating on a fraction of its data. For a cache, no is usually correct, because serving two-thirds of the keys beats serving none.

Resharding is live, and the per-slot migration state is why it works without downtime:

# on the TARGET:  "expect keys for this slot"
CLUSTER SETSLOT <slot> IMPORTING <source-node-id>
# on the SOURCE:  "this slot is leaving"
CLUSTER SETSLOT <slot> MIGRATING <target-node-id>

# move keys in batches
CLUSTER GETKEYSINSLOT <slot> 100
MIGRATE <host> <port> "" 0 5000 KEYS k1 k2 k3 …

# finally, publish the new owner to every node
CLUSTER SETSLOT <slot> NODE <target-node-id>

# in practice, one command does all of it:
redis-cli --cluster reshard <host>:<port> --cluster-from <id> --cluster-to <id> \
          --cluster-slots 500 --cluster-yes

While a slot is MIGRATING/IMPORTING, the source serves keys it still holds and returns ASK for keys already moved. That is the entire reason ASK exists, and why treating it as MOVED breaks a migration.

Part 6 — Should You Use Cluster At All?

The honest answer for most systems is no, and being able to say why is what an interviewer is checking.

NeedSolutionCluster required?
More read capacityReplicas❌ No
High availabilitySentinel + replicas❌ No
Dataset larger than one machine's RAMCluster (or app-level sharding)✅ Yes
Write throughput beyond one coreCluster✅ Yes
Smaller fork stalls / faster recoverySmaller instances✅ Often
"It sounds more scalable"—❌ No

A single Redis instance handles enormous load — commonly 100K+ operations per second on one core, and hundreds of GB of RAM on modern hardware. Most teams that reach for Cluster have a hot-key problem, an O(n) command problem, or a network round-trip problem, none of which sharding fixes. Cluster solves exactly two things: a dataset that does not fit in one machine, and a write rate beyond one core.

What Cluster costs, stated up front: no cross-slot multi-key operations or transactions, hash tags that must be designed into the key schema from the start, per-node SCAN, at least six nodes, a cluster-aware client in every language you use, and an operational surface that includes slot balance, migration state and gossip health. Application-level sharding — running N independent Redis instances and choosing one in the client — avoids most of that and is a legitimate choice when the sharding key is obvious and rebalancing is rare.

❌ Adopting Cluster to "scale Redis" without measuring what the bottleneck is. The team sees high latency, deploys six nodes, and migrates. The dataset fitted comfortably in one machine and the write rate was nowhere near a core's capacity, so nothing improves — the actual causes were an O(n) command blocking the event loop and a hot key that Cluster cannot split, because a single key lives in a single slot on a single node. Meanwhile every multi-key operation now fails with CROSSSLOT, the maintenance scripts silently scan a third of the keyspace, Pub/Sub broadcasts to every node, and the {global} hash tag added to fix the multi-key errors has concentrated the whole workload back onto one shard.

✅ Measure the bottleneck, then pick the mechanism that addresses it. Read capacity is replicas; availability is Sentinel; latency spikes are usually O(n) commands, fork stalls, or round trips — all covered in Performance & Latency. Cluster is the answer to exactly two problems: a dataset larger than one machine's RAM, and a write rate beyond one core. If you do need it, design hash tags into the key schema from day one using a high-cardinality identifier, choose cluster-require-full-coverage deliberately, run at least 3 primaries so a majority can form, and verify a cluster-aware client exists for every language in your stack before committing.

Interview Questions

Beginner: How does Redis Cluster decide which node holds a key?

Every key maps to one of 16,384 hash slots, and each slot is owned by exactly one primary:

slot = CRC16(key) mod 16384

node A: slots     0–5460
node B: slots  5461–10922
node C: slots 10923–16383

The computation is deterministic and requires no shared state — every client and node derives the same slot for a key independently. CLUSTER KEYSLOT user:42 returns it.

Why a slot layer instead of hashing straight to nodes? Because it makes rebalancing move slots rather than rehash keys. Adding a node reassigns slot ranges and the keys follow; the key→slot mapping never changes, only slot→node.

Why 16,384? Nodes gossip slot ownership as a bitmap in every heartbeat. 16,384 bits is 2 KB per message; 65,536 would be 8 KB, and heartbeats flow continuously between all node pairs. It is fine enough to balance hundreds of nodes and small enough to keep gossip cheap.

Clients cache the slot map (CLUSTER SLOTS or CLUSTER SHARDS) so the normal case is one round trip with no redirect; they refresh it when a node replies MOVED.

Beginner: What is the difference between MOVED and ASK?

Both are redirects, and confusing them breaks resharding.

MOVED is permanent. The slot now belongs to another node — a stable fact.

GET user:42 → MOVED 12539 10.0.1.3:6379

Client: update the cached slot map, retry there, and keep using that node.

ASK is for one command. The slot is currently migrating, and this particular key has already been copied to the target while others remain on the source.

GET user:42 → ASK 12539 10.0.1.4:6379

Client: send ASKING, then the command, to that node — ONCE.
        Do NOT update the slot map: ownership has not changed yet.

Why the distinction exists: during migration a slot's keys are split across two nodes. The source still owns the slot and serves the keys it holds; for keys already moved it answers ASK. If a client treated that as MOVED, it would send every key in the slot to the target — including keys the target does not have yet — and get errors until the migration completed.

ASKING is the one-shot flag that tells the target "I know you do not own this slot yet, serve this command anyway". Without it the target replies MOVED back to the source, and the client ping-pongs.

Mid: Why do multi-key operations fail, and how do hash tags fix it — and break it?

They fail because the keys live on different nodes. Redis will not perform a distributed transaction, so any command touching multiple keys requires them to be in the same slot:

MGET user:1 user:2   → (error) CROSSSLOT Keys in request don't hash to the same slot

The same applies to MULTI/EXEC, Lua scripts whose KEYS span slots, SINTER, ZUNIONSTORE, and RENAME.

Hash tags force colocation by hashing only the substring inside the first {...}:

user:1:profile   → slot 5432        {user:1}:profile  → slot 3421
user:1:settings  → slot 9871        {user:1}:settings → slot 3421 ✅

And that is exactly how people create hotspots. The tag determines placement, so a low-cardinality tag concentrates traffic:

  • {user:1} — millions of distinct values, spreads evenly ✅
  • {tenant:acme} — fine until one tenant is 100× the others ⚠️
  • {global} — every key on one node; the cluster is now one node ❌

The failure is particularly frustrating because it usually arrives as a fix: a team hits CROSSSLOT, adds a constant tag to make the errors stop, and converts a correctness problem into a capacity problem that only appears under load.

The rule: tag with a high-cardinality identifier that matches the natural grouping of your access pattern — user, tenant, order — and design it into the key schema from the start, because retrofitting a tag means migrating every affected key.

Mid: How does Cluster failover work, and why do you need at least 3 primaries?

Cluster does not use Sentinel. Nodes monitor each other over the cluster bus (the client port + 10000) with a gossip protocol:

1. PFAIL  — a node cannot reach another for cluster-node-timeout
2. Gossip — the suspicion spreads through heartbeats
3. FAIL   — a MAJORITY OF PRIMARIES agree the node is down
4. A replica of the failed primary requests votes
5. Majority of primaries vote → promotion, and it claims the slots

Only primaries vote, and a majority is required — that is the whole answer to the second half of the question. With 2 primaries, losing one leaves a single primary, and 1 is not a majority of 2, so no failover can be authorised and the cluster is stuck with unserved slots. With 3 primaries, losing one leaves 2 of 3 — a majority — and the failover proceeds.

So the documented minimum is 3 primaries and 3 replicas: six nodes, before any capacity consideration at all. That six-node floor is one of the main reasons Cluster is overkill for most deployments.

Related settings worth naming:

cluster-node-timeout 15000              # detection window
cluster-replica-validity-factor 10      # refuse promotion if too far behind
cluster-migration-barrier 1             # keep ≥1 replica before donating one

cluster-migration-barrier enables replica migration: a primary with two replicas can donate one to a primary that has none, so the cluster self-heals toward even coverage.

And placement matters as much as counting: a primary and its replica on the same host means one host failure takes the shard out entirely, whatever the voting says.

Senior: Design a migration from a single 200 GB Redis instance to Cluster.

First, verify Cluster is the right answer. 200 GB fits on a modern machine, so the question is whether the driver is memory pressure, write throughput beyond one core, or fork stalls (200 GB is ~2–4 seconds per fork, which is a real argument for sharding on its own). If the actual problem is read capacity or availability, replicas and Sentinel are cheaper and keep every Redis feature.

Sizing: 6 primaries at ~33 GB each keeps fork stalls under half a second and leaves headroom for copy-on-write, plus 6 replicas across AZs — 12 nodes.

The hard part is the key schema, and it must be done before any data moves. Audit for every multi-key operation, transaction and Lua script, because each one is a CROSSSLOT error waiting to happen:

MGET user:1:profile user:1:settings         → CROSSSLOT
{user:1}:profile / {user:1}:settings        → same slot ✅

Choose tags on a high-cardinality identifier that matches the access pattern (user, tenant, order), never a constant. Also inventory what disappears: SELECT (DB 0 only), whole-keyspace SCAN/DBSIZE, and PUBLISH, which broadcasts to every node unless it becomes SPUBLISH.

Migration approach — dual-write, which allows rollback at every stage:

1. Stand up the cluster; verify with redis-cli --cluster check
2. Application writes to BOTH old and new (new is not read yet)
3. Backfill: SCAN the old instance, MIGRATE or DUMP/RESTORE into the cluster
4. Verify: key counts per prefix, and sampled value comparison
5. Shift reads gradually — 1% → 10% → 50% → 100%, watching error rates
6. Stop writing to the old instance; keep it as a rollback target for days
7. Decommission

The alternative — redis-cli --cluster import from a live instance — is one command but offers no gradual cutover and no easy rollback, so it suits small datasets rather than 200 GB.

Verification is the step people skip. Compare per-prefix key counts across all primaries against the source, and sample values for equality; a raw DBSIZE comparison is meaningless because the cluster's total is a sum across nodes.

Decisions to make explicitly: cluster-require-full-coverage — no if this is a cache and partial service beats none, yes if operating on a fraction of the data would be incorrect. And confirm a maintained cluster-aware client exists for every language in the stack; that has stalled more migrations than any data problem.

Rollback plan: because writes go to both systems until step 6, reverting is a configuration change rather than a restore.

Senior: One node in your cluster is at 90% CPU while others are at 20%. Diagnose it.

Uneven load in a system designed to spread it. Four causes, in the order worth checking.

1. A hash-tag hotspot. The most common. Keys tagged with a low-cardinality value — {global}, a region, a status — all hash to one slot on one node. Check the key schema for constant tags first, since this is self-inflicted and usually recent.

2. A genuinely hot key. One key cannot be split: it is one slot on one node, so a celebrity user or a global counter concentrates traffic no matter how well slots are balanced.

redis-cli -h <hot-node> --hotkeys
redis-cli -h <hot-node> MONITOR | head -1000     # brief sample only

The fixes are application-level: an in-process L1 cache in front of the key, or splitting it into N sub-keys (counter:{shard0..15}) summed on read.

3. Uneven slot distribution. After manual resharding, one node may simply own more slots or more data.

redis-cli --cluster check <host>:<port>      # slots per node, coverage
redis-cli --cluster rebalance <host>:<port>  # even out slot counts

4. Non-uniform key sizes. Slots can be perfectly balanced in count while one node holds far more data — a few very large hashes or sorted sets. Compare used_memory and INFO commandstats across nodes; if one shows high usec_per_call on a specific command, the problem is O(n) operations rather than distribution.

How I would work it: --cluster check for slot balance, INFO commandstats per node to see whether it is request volume or expensive commands, --hotkeys on the hot node, and only then look at the key schema. Slot imbalance is fixable with a rebalance; a hot key is an application change; and if it turns out to be one O(n) command, the answer has nothing to do with Cluster at all — see The Single-Threaded Model.

Now show how the fix becomes a hotspot:

from collections import Counter

def distribution(keyfn, n=3000, label=""):
    slots = Counter()
    for i in range(n):
        slots[c.execute_command("CLUSTER", "KEYSLOT", keyfn(i)) // 5461] += 1
    print(f"{label:26s} node distribution: "
          f"{[f'{slots[i]/n:.0%}' for i in range(3)]}")

distribution(lambda i: f"{{user:{i}}}:data",  label="{user:N} (high cardinality)")
distribution(lambda i: f"{{global}}:data:{i}", label="{global} (constant)")
distribution(lambda i: f"{{region:{i % 3}}}:d", label="{region} (3 values)")

{user:N} (high cardinality) node distribution: ['33%', '33%', '34%']
{global} (constant)         node distribution: ['0%', '100%', '0%']
{region} (3 values)         node distribution: ['33%', '0%', '67%']

{global} put 100% of keys on one node — the cluster is now a single instance with extra operational complexity. Now measure the cost of following redirects versus caching the map:

def follow_redirects(n=300):
    """Naive: reconnect on every MOVED, never cache."""
    conns = {7000: redis.Redis(port=7000, decode_responses=True)}
    redirects = 0
    t0 = time.perf_counter()
    for i in range(n):
        conn = conns[7000]
        while True:
            try:
                conn.set(f"nr:{i}", i); break
            except redis.ResponseError as e:
                if not str(e).startswith("MOVED"): raise
                redirects += 1
                port = int(str(e).split()[2].split(":")[1])
                conns.setdefault(port, redis.Redis(port=port,
                                                   decode_responses=True))
                conn = conns[port]
    return (time.perf_counter()-t0)/n*1000, redirects

rc = redis.RedisCluster(host="127.0.0.1", port=7000, decode_responses=True)
def cached(n=300):
    t0 = time.perf_counter()
    for i in range(n):
        rc.set(f"ca:{i}", i)
    return (time.perf_counter()-t0)/n*1000

ms_naive, redirects = follow_redirects()
ms_cached = cached()
print(f"follow redirects each time: {ms_naive:.3f} ms/op ({redirects} redirects)")
print(f"cluster-aware (cached map): {ms_cached:.3f} ms/op (0 redirects)")
print(f"→ {ms_naive/ms_cached:.1f}× faster with a cached slot map")

follow redirects each time: 0.192 ms/op (201 redirects)
cluster-aware (cached map): 0.094 ms/op (0 redirects)
→ 2.0× faster with a cached slot map

The cluster-aware client fetched CLUSTER SLOTS once and routes every command directly. In the steady state a correct client sees zero redirects — MOVED appears only after a topology change, which is the signal to refresh the map.

def per_node_calls(fn, ops=20000, threads=8):
    for n in rc.get_primaries():
        redis.Redis(host=n.host, port=n.port).config_resetstat()
    def w():
        cl = redis.RedisCluster(host="127.0.0.1", port=7000, decode_responses=True)
        for i in range(ops // threads):
            fn(cl, i)
    ts = [threading.Thread(target=w) for _ in range(threads)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    dur = time.perf_counter() - t0
    calls = {}
    for n in rc.get_primaries():
        st = redis.Redis(host=n.host, port=n.port).info("commandstats")
        calls[f"{n.port}"] = sum(v["calls"] for v in st.values())
    return calls, dur

For a hot key that is mostly read, an L1 cache is better than sharding:

local_cache, hits, misses = {}, [0], [0]
def l1_get(cl, i):
    now = time.time()
    ent = local_cache.get("config:global")
    if ent and now - ent[1] < 1.0:
        hits[0] += 1; return ent[0]
    misses[0] += 1
    v = cl.get("config:global")
    local_cache["config:global"] = (v, now)
    return v

rc.set("config:global", "value")
calls, dur = per_node_calls(l1_get)
total = sum(calls.values())
print(f"\nL1-CACHED HOT KEY: {total:,} Redis calls for 20,000 reads "
      f"({hits[0]:,} L1 hits)")
print(f"  Redis load reduced {20000/max(total,1):.0f}×")

L1-CACHED HOT KEY: 47 Redis calls for 20,000 reads (19,953 L1 hits)
  Redis load reduced 426×

426× less Redis traffic, at the cost of up to 1 second of staleness per process — the trade discussed in Cache Invalidation & Stampedes. Neither fix is a Cluster feature: hot keys are an application-level problem, and recognising that is the point of the exercise.

🎯 Key Takeaways

  • Cluster maps keys with CRC16(key) mod 16384 into fixed slots, so rebalancing moves slots, not keys — the key→slot mapping never changes.
  • 16,384 is chosen for gossip cost: the slot bitmap is 2 KB per heartbeat, versus 8 KB at 65,536.
  • MOVED is permanent; ASK is one command only. Treating ASK as MOVED corrupts the slot map mid-migration.
  • A cluster-aware client caches the slot map and sees zero redirects in the steady state — measured 2× faster than following redirects each time.
  • Multi-key commands, transactions and Lua all fail with CROSSSLOT unless every key shares a slot.
  • Hash tags ({user:1}:*) force colocation — and low-cardinality tags create hotspots: {global} put 100% of keys on one node, and 3 region values gave 33/0/67, not an even split.
  • Cluster removes SELECT (DB 0 only), makes SCAN/DBSIZE per-node, and broadcasts PUBLISH to every node — use SPUBLISH on 7.0+.
  • Failover uses the gossip bus, not Sentinel: a majority of primaries must agree, and only primaries vote.
  • 2 primaries cannot fail over — measured cluster_state=fail and CLUSTERDOWN on every write, permanently. The minimum is 3 primaries + 3 replicas.
  • Failover took ~5.6 s, dominated by cluster-node-timeout — the same detection-window trade as Sentinel.
  • cluster-require-full-coverage yes stops the whole cluster when any slot is unassigned; no keeps healthy shards serving — a deliberate choice, usually no for caches.
  • Live resharding moved 1,000 slots with 18,442 concurrent reads and 0 errors, using the MIGRATING/IMPORTING states and ASK.
  • A hot key cannot be sharded by Cluster: one key = one slot = one node, measured at 99.8% of traffic on a single node.
  • Fix hot keys in the application — sharding the key into sub-keys gave even distribution and 1.6× throughput; an L1 cache cut Redis calls 426× for read-heavy keys.
  • Cluster solves exactly two problems: a dataset larger than one machine's RAM, and writes beyond one core. Read capacity is replicas; availability is Sentinel.
  • Design hash tags into the key schema from day one — retrofitting one means migrating every affected key.
  • Migrate with dual writes and a gradual read shift so rollback stays a configuration change rather than a restore.
  • Verify a maintained cluster-aware client exists for every language in the stack before committing — that has stalled more migrations than data problems have.
