Security & Operations Production

What you'll master: why Redis's defaults assume a trusted network, and exactly what an exposed instance gives an attacker — including the module- and config-based paths from "no password" to remote code execution, which is why unprotected Redis is one of the most reliably exploited services on the internet; protected mode, and the precise conditions under which it silently stops protecting you; ACLs in Redis 6+, with per-command and per-key-pattern rules and the selector syntax that makes least privilege practical; why requirepass alone is weak and how a fast server makes brute force cheap; command renaming and its deprecation in favour of ACLs; TLS, and the throughput it actually costs; and the operational runbook items — upgrades, config changes that do not survive a restart, and the CONFIG SET that has taken down production. Prerequisites: Observability & Debugging, Replication & Failover.

Part 1 — The Threat Model Redis Was Designed For

Redis's defaults were chosen for a trusted network: a fast datastore behind a firewall, spoken to only by application servers. Every security feature since has been added on top of that assumption, and the assumption is still visible in the defaults.

Out of the box:
  no authentication          — anyone who can connect is fully authorised
  no encryption              — everything, including AUTH, is plaintext on the wire
  every command available    — including CONFIG, DEBUG, FLUSHALL, SHUTDOWN
  binds to all interfaces    — unless protected mode or `bind` stops it
🔑 An exposed Redis is not merely a data-disclosure problem — it is usually a full-host compromise. With CONFIG SET available, an attacker can point dir and dbfilename at a filesystem path, write keys whose values are the file content, and SAVE — producing an arbitrary file owned by the Redis user. The classic targets are ~/.ssh/authorized_keys and a cron directory. On versions with module loading available, MODULE LOAD is a direct path to running native code. This is why unauthenticated Redis on a public IP is scanned for continuously and compromised within minutes.

# the shape of the classic attack — why CONFIG must not be reachable
CONFIG SET dir /var/lib/redis/.ssh
CONFIG SET dbfilename authorized_keys
SET payload "\n\nssh-rsa AAAA...attacker-key\n\n"
SAVE                                  # RDB written to the target path

Protected mode (Redis 3.2+) is the guard that stops the most common accident: it refuses connections from non-loopback addresses when both no password is set and no bind directive is configured.

protected-mode yes            # default
bind 127.0.0.1 -::1           # default in shipped configs

# Protected mode STOPS protecting as soon as either is true:
#   - requirepass is set        (any password, even a weak one)
#   - bind is configured        (even `bind 0.0.0.0`)

That second condition is the trap: adding bind 0.0.0.0 to make Redis reachable from another host disables protected mode, so the instance becomes both reachable and unauthenticated in one edit.

Part 2 — ACLs: Users, Commands and Key Patterns

Redis 6 introduced real access control. Before that, requirepass was a single shared password granting full administrative access to everything.

ACL SETUSER app-reader on >s3cr3t-password \
    ~cache:*  ~session:*  \
    +@read +ping
    │        │       │
    │        │       └── command categories / individual commands
    │        └────────── key patterns this user may touch
    └─────────────────── `on` = enabled, `>pw` = add password

ACL SETUSER app-writer on >another-pw ~app:* +@read +@write -@dangerous
ACL SETUSER metrics    on >m-pw       ~*     +info +client|list +slowlog +config|get
ACL SETUSER default    off                              # disable the default user
RuleMeaning
on / offEnable or disable the user
>password / <passwordAdd / remove a password
~patternGrant access to keys matching a glob
%R~p / %W~pRead-only / write-only on a pattern (Redis 7)
&channelPub/Sub channel permission
+command / -commandAllow / deny one command
+@categoryA whole category: @read @write @admin @dangerous @keyspace
+cmd|subcmdOne subcommand only, e.g. +config|get
allkeys / allcommandsShorthand for ~* / +@all
🔑 Build ACLs by starting from nothing and adding, never by starting from +@all and subtracting. A subtractive rule set silently regains privileges every time Redis adds a command in a new version — an upgrade quietly widens the permission. +@read +@write on specific key patterns stays correct across upgrades; +@all -flushall -config does not.

Selectors (Redis 7) express "these commands on these keys" as a unit, which is what makes least privilege practical for a service that needs different rights on different key spaces:

ACL SETUSER worker on >pw \
    (~jobs:*   +@read +@write) \
    (~metrics:* +incr +hincrby)
    └────────── each parenthesised group is an independent permission set

ACL WHOAMI                     # who am I connected as
ACL LIST                       # all rules
ACL GETUSER app-reader         # one user, expanded
ACL CAT                        # available categories
ACL GENPASS                    # generate a 256-bit password
ACL LOG                        # ★ recent permission denials — an audit trail

ACL LOG is the security equivalent of errorstats: it records who was denied what, so a misconfigured service or an intrusion attempt shows up as entries rather than as silence.

Part 3 — Passwords, Renaming and Their Limits

requirepass still exists, and it is weaker than people assume for a specific reason: Redis is fast, so brute force is cheap.

requirepass a-long-random-string      # sets the DEFAULT user's password

An unthrottled Redis serves >100,000 AUTH attempts per second.
  8-char lowercase alphanumeric ≈ 2.8e12 combinations → tractable
  32-char random (ACL GENPASS)  ≈ 1.5e57              → not

There is no built-in login throttling and no account lockout, so password length is the entire defence. Use ACL GENPASS and treat the value as a secret managed by your secret store, not a config-file literal.

Command renaming was the pre-ACL way to disable dangerous commands. It still works and is deprecated in favour of ACLs:

rename-command FLUSHALL ""                      # disable entirely
rename-command CONFIG b840fc02d524045429941cc15f59e41cb7be6c52

# Problems: cluster-wide consistency, client libraries that call CONFIG,
# and the fact that the "secret" name is in a config file on every host.
CommandRiskHandling
CONFIGRCE path — rewrite dir/dbfilenameAdmin ACL only; +config|get for monitoring
MODULELoads native codeDeny everywhere
DEBUGDEBUG SEGFAULT, SLEEPDeny
FLUSHALL/FLUSHDBTotal data loss, replicated instantlyDeny for applications
KEYSBlocks the serverDeny; use SCAN
SHUTDOWNStops the processDeny

Part 4 — TLS and Network Boundaries

Without TLS, every command and every AUTH password crosses the network in plaintext. Redis 6 added native TLS.

port 0                          # ← disable the plaintext port entirely
tls-port 6379
tls-cert-file /path/redis.crt
tls-key-file  /path/redis.key
tls-ca-cert-file /path/ca.crt
tls-auth-clients yes            # require client certificates (mutual TLS)
tls-replication yes             # encrypt replication traffic too
tls-cluster yes                 # and the cluster bus

redis-cli --tls --cert client.crt --key client.key --cacert ca.crt
🔑 port 0 is the line that matters. Enabling tls-port without it leaves the plaintext port listening as well, so anything that connects without TLS still works — and therefore still happens. The configuration looks encrypted, traffic is partially not, and nothing errors to tell you.

TLS costs throughput — commonly 10–30% on small commands, because the per-command overhead is fixed and Redis commands are tiny. That is usually acceptable; the alternative on untrusted networks is not.

Part 5 — Config Changes That Do Not Survive a Restart

CONFIG SET changes the running server and nothing on disk. This is the single most common operational surprise in Redis.

CONFIG SET maxmemory 4gb          # takes effect now
                                  # ...and is GONE after a restart

CONFIG REWRITE                    # persist the running config to redis.conf
CONFIG GET maxmemory              # verify

An instance tuned over months through CONFIG SET reverts entirely on the next restart — typically during an incident, when someone restarts to "clear things up" and the memory limit, eviction policy and timeouts all return to defaults at the worst possible moment.

Some CONFIG SET calls are themselves dangerous:

CONFIG SET maxmemory 100mb        # ← below current usage: MASS EVICTION, immediately
CONFIG SET appendonly no          # ← disables AOF; the file stops being updated
CONFIG SET save ""                # ← disables snapshots silently
CONFIG SET maxmemory-policy noeviction   # ← writes start failing at the limit
🔑 Lowering maxmemory below current usage evicts immediately and synchronously until the instance fits. On a large instance that is a mass-eviction event: the hit rate collapses, the origin database takes the full miss load, and the eviction work itself blocks the single thread. Change maxmemory downward in steps, and never as a reflex during an incident.

Upgrades follow replication topology, and the order matters:

1. Read the release notes for breaking changes (Redis 7 changed the AOF layout)
2. Upgrade REPLICAS first, one at a time; verify master_link_status:up
3. Fail over deliberately to an upgraded replica
4. Upgrade the old primary, which rejoins as a replica
5. Verify: INFO server redis_version, DBSIZE, ACL LIST, CONFIG GET maxmemory

Never upgrade the primary in place and hope — a failed start with no
replica ready is an outage with no rollback.

Part 6 — A Production Hardening Checklist

Everything above, condensed to what should be true of every production instance:

Network
  [ ] Not reachable from the internet; private subnet + security groups
  [ ] `bind` set to specific internal interfaces
  [ ] protected-mode yes

Authentication and authorisation
  [ ] Default user disabled (ACL SETUSER default off)
  [ ] Per-service ACL users, built additively from nothing
  [ ] Passwords from ACL GENPASS, stored in a secret manager
  [ ] CONFIG, MODULE, DEBUG, FLUSHALL, SHUTDOWN, REPLICAOF, KEYS denied to apps
  [ ] Monitoring user limited to +info +client|list +slowlog +config|get

Transport
  [ ] TLS enabled with `port 0` so plaintext is actually off
  [ ] tls-replication yes (and tls-cluster in a cluster)

Data protection
  [ ] Persistence configured deliberately; loss window written down
  [ ] Off-box backups; restores verified by content fingerprint, not key count
  [ ] maxmemory ~60-70% of host RAM, policy chosen deliberately

Operations
  [ ] CONFIG REWRITE after every CONFIG SET that should persist
  [ ] Upgrades: replicas first, then a deliberate failover
  [ ] Alerts on ACL LOG entries and errorstat_* rates
  [ ] Run as a non-root user

❌ Making Redis reachable by adding bind 0.0.0.0, with a short requirepass as "the security". A service on another host needs access, so the bind directive is widened and a password is set. Both changes weaken things more than they appear to: adding any bind line disables protected mode, and if the password is later removed or the config templated wrong, the instance is reachable and unauthenticated with no remaining guard. The password itself is an eight-character string against a server that answers over 100,000 AUTH attempts per second with no throttling and no lockout. And because requirepass authenticates the default user, every client that connects holds full administrative rights — including CONFIG SET, which turns a data breach into remote code execution by rewriting dir and dbfilename and calling SAVE.

✅ Keep Redis off the public network, then layer ACLs on top. Private subnet and security groups first, since network reachability is the control that actually stops the scanners. Disable the default user and create one ACL user per service, built additively — +@read +@write on the key patterns that service owns, never +@all minus a deny list, which silently regains privileges on every upgrade. Generate passwords with ACL GENPASS and store them in a secret manager. Deny CONFIG, MODULE, DEBUG, FLUSHALL, REPLICAOF and KEYS to applications, give monitoring +config|get only, enable TLS with port 0 so the plaintext port is genuinely closed, and alert on ACL LOG so denials are visible instead of silent.

Interview Questions

Beginner: What are Redis's security defaults, and what is protected mode?

The defaults assume a trusted network: no authentication, no encryption, every command available, and a process that will listen on all interfaces unless told otherwise. Redis was designed as a fast datastore behind a firewall, and the defaults still reflect that.

Protected mode (3.2+) guards the most common accident. It refuses connections from non-loopback addresses when both conditions hold:

protected-mode yes    AND    no requirepass    AND    no bind directive
   → non-loopback connections are refused with an explanatory error

The trap is that it stops protecting as soon as either condition is removed. Setting any password disables it, and — more surprisingly — configuring any bind directive disables it too, including bind 0.0.0.0. So the natural edit to make Redis reachable from another host removes the guard in the same change.

Why exposure is so serious: an unauthenticated Redis is not just readable, it is usually a host compromise. With CONFIG SET an attacker points dir and dbfilename at a filesystem path, writes a key whose value is file content, and calls SAVE — producing an arbitrary file owned by the Redis user, classically an SSH authorized_keys or a cron entry.

The correct posture is layered: private network first, then ACL authentication, then TLS, then command restrictions — with network reachability doing most of the work.

Beginner: How do ACLs improve on requirepass?

requirepass is a single shared password that grants full administrative access — every command, every key. Every service shares one secret, and any of them can run FLUSHALL, CONFIG SET, or SHUTDOWN.

ACLs (Redis 6+) give per-user permissions over commands, key patterns and Pub/Sub channels:

ACL SETUSER app-reader on >generated-password ~cache:* ~session:* +@read +ping
ACL SETUSER app-writer on >another-password   ~app:*   +@read +@write -@dangerous
ACL SETUSER metrics    on >metrics-password   ~*       +info +client|list +config|get
ACL SETUSER default off                                  # disable the shared account

That buys three things: least privilege (a cache reader cannot flush the database), credential rotation per service (revoke one without touching the others), and an audit trail via ACL LOG, which records who was denied what.

Build rules additively. +@read +@write on specific patterns stays correct across upgrades; +@all minus a deny list silently regains privileges whenever Redis adds a command in a new version.

requirepass is also weak on its own terms: Redis answers over 100,000 AUTH attempts per second with no throttling and no lockout, so a short password is genuinely brute-forceable. Use ACL GENPASS and a secret manager.

Mid: Design ACLs for a system with a web app, a worker, and a monitoring agent.

Principle: start from nothing and add only what each service demonstrably needs — never +@all with a deny list, which widens silently on upgrade.

# web app: reads and writes its own key space, no admin, no dangerous commands
ACL SETUSER webapp on >$(ACL GENPASS) \
    ~session:* ~cache:* ~user:* \
    +@read +@write +@string +@hash +@list -@dangerous

# worker: job streams plus a metrics counter — expressed with selectors (Redis 7)
ACL SETUSER worker on >$(ACL GENPASS) \
    (~jobs:*    +@read +@write +xadd +xreadgroup +xack +xautoclaim) \
    (~metrics:* +incr +hincrby +expire)

# monitoring: read-only introspection, no key access at all
ACL SETUSER metrics on >$(ACL GENPASS) \
    ~monitor:none \
    +info +ping +client|list +slowlog +latency +memory|stats +config|get

# admin: for humans, via a bastion, with the credential in a vault
ACL SETUSER admin on >$(ACL GENPASS) ~* &* +@all

ACL SETUSER default off        # ← the shared account is gone

Points worth explaining: the monitoring user gets +config|get but not +config, so it can read configuration and not rewrite dir — the subcommand granularity is exactly what prevents a monitoring credential from becoming an RCE path. Selectors let the worker have different rights on jobs:* and metrics:* in one user. And -@dangerous on the web app removes KEYS, FLUSHALL, SHUTDOWN and similar in one rule.

Operationally: generate passwords with ACL GENPASS, store them in a secret manager rather than the config file, persist rules with ACL SAVE to an aclfile (or CONFIG REWRITE), and alert on ACL LOG — denials mean either a misconfigured deploy or someone probing.

Verify by testing the denials, not by reading the rules: connect as each user and confirm the forbidden commands actually fail.

Mid: Why is an exposed Redis an RCE risk rather than just a data leak?

Because CONFIG SET lets a client change where Redis writes files, and SAVE then writes attacker-controlled content there.

CONFIG SET dir /var/lib/redis/.ssh
CONFIG SET dbfilename authorized_keys
SET payload "\n\nssh-rsa AAAA...attacker-key\n\n"
SAVE                            # an RDB file is written to that path

The RDB format has binary headers around the value, but SSH and cron both tolerate junk lines, so a file containing the payload surrounded by noise still works. The result is an arbitrary file write as the Redis user — typically an SSH key or a cron job, and from there a shell.

MODULE LOAD is more direct where it is reachable: it loads a shared library and runs native code inside the Redis process, with no file-format trickery at all.

Other paths worth naming: REPLICAOF can repoint an instance at an attacker-controlled primary, which replaces the entire dataset and — in some versions — enables module loading over replication; and DEBUG exposes process-level operations.

The defences, in order of how much they matter:

  • Network isolation. The control that actually stops mass scanning.
  • Deny CONFIG, MODULE, DEBUG, REPLICAOF to every application user via ACLs. Monitoring gets +config|get only.
  • Run as a dedicated non-root user with no write access to SSH or cron directories — this turns an arbitrary write into a much smaller problem.
  • Authentication and TLS, so reachability alone is not access.

The framing to give: Redis's command set was designed for a trusted operator, so any unauthenticated client is effectively an operator — which is why "it only holds cache data" is not a reason to leave it open.

Senior: Design the security posture for Redis holding session data in a regulated environment.

Session data is authentication material, so a leaked session token is account takeover. That framing sets the requirements rather than "it's only a cache".

Network — the control that does most of the work: private subnet with no route to the internet, security groups allowing 6379 only from the application security group, and no public IP or NAT egress. Redis in a separate subnet from the application tier so lateral movement crosses a boundary.

Transport: TLS with port 0 so the plaintext port is genuinely closed — enabling tls-port alone leaves plaintext listening and therefore in use. Mutual TLS so client certificates identify services, plus tls-replication yes so replication traffic is encrypted too; unencrypted replication would otherwise carry every session token across the network in clear.

Authentication and authorisation: default user disabled; one ACL user per service, built additively:

ACL SETUSER sessions on >$(ACL GENPASS) ~session:* +@read +@write +expire -@dangerous
ACL SETUSER metrics  on >$(ACL GENPASS) ~monitor:none +info +client|list +config|get
ACL SETUSER default off

No application user gets CONFIG, MODULE, DEBUG, REPLICAOF, KEYS or MONITOR — the last because it would stream every session token to whoever ran it.

Data protection: encryption at rest for the volumes holding RDB and AOF files, since a snapshot is a file full of session tokens. TTLs on every session key so data expires by construction rather than by a cleanup job. And a deliberate decision about persistence — for sessions, losing a second of writes means a few users re-login, which is usually acceptable and should be written down rather than assumed.

Audit, which regulated environments require explicitly: ACL LOG shipped to the SIEM and alerted on, since denials indicate either a broken deploy or probing; INFO errorstats for NOAUTH/NOPERM rates; connection logs; and the slow log shipped rather than left in its ring buffer.

Operations: run as a non-root user, credentials rotated on a schedule through the secret manager, upgrades applied to replicas first with a deliberate failover, and CONFIG REWRITE after any change intended to survive a restart.

What I would flag to the team: Redis has no field-level encryption and no native audit of data access — it logs permission denials, not successful reads. If the requirement is "prove who read which session", that belongs in the application layer, because Redis cannot answer it.

Senior: Your settings reverted after a restart. Explain, and design against it.

CONFIG SET changes only the running process. It does not touch redis.conf, so every value tuned that way is lost on restart:

CONFIG SET maxmemory 8gb              # in effect now
# restart
CONFIG GET maxmemory  →  "0"          # back to the file's value (unlimited)

CONFIG REWRITE persists the running configuration back to the file Redis was started with — and it fails if Redis was started without a config file, which is a common container setup.

Why it usually bites during an incident: months of tuning accumulate through CONFIG SET, then someone restarts to clear a problem and maxmemory, the eviction policy and the timeouts all revert to defaults simultaneously — turning a small incident into a larger one. And the reverted eviction policy is noeviction by default, so a cache instance starts refusing writes.

Designing against it:

  • Treat configuration as code. The config file is generated by Ansible, Helm, or a Terraform template and applied by deployment — so the running state and the declared state cannot drift, and a restart is safe by construction.
  • If you must use CONFIG SET, follow it with CONFIG REWRITE and verify with CONFIG GET. Better, make the change in the source of truth and let the pipeline apply it.
  • Alert on drift: a periodic check comparing CONFIG GET for the values you care about against the expected set catches both manual changes and failed deploys.
  • Verify after every restart as part of the runbook — maxmemory, policy, appendonly, ACL users — rather than assuming the process came back as it went down.

One related hazard worth naming: some CONFIG SET calls are dangerous in themselves. Lowering maxmemory below current usage evicts immediately and synchronously until the instance fits, which collapses the hit rate and sends the full miss load to the origin database. Step it down gradually, and never as a reflex during an incident.

6 (hard): Write a security audit script that scores an instance.
Solution 
import redis, subprocess, time, os

def audit(host="localhost", port=6379, **kw):
    r = redis.Redis(host=host, port=port, decode_responses=True, **kw)
    findings = []

    def add(sev, msg): findings.append((sev, msg))

    cfg = lambda k: r.config_get(k).get(k, "")

    # --- network exposure ---
    bind = cfg("bind")
    protected = cfg("protected-mode")
    if not bind or "0.0.0.0" in bind:
        add("CRIT", f"bind='{bind or '(unset)'}' - listening broadly")
    if protected != "yes":
        add("CRIT", "protected-mode is off")
    elif bind:
        add("INFO", "protected-mode yes, but a bind directive disables its guard")

    # --- authentication ---
    try:
        users = r.acl_list()
    except redis.ResponseError:
        users = []
        add("CRIT", "ACLs unavailable (Redis < 6) - requirepass only")
    default = next((u for u in users if u.startswith("user default")), "")
    if "nopass" in default:
        add("CRIT", "default user requires NO PASSWORD")
    if default.startswith("user default on") and "~*" in default and "+@all" in default:
        add("WARN", "default user is enabled with full access")
    if len(users) <= 1:
        add("WARN", "only the default user exists - no per-service ACLs")

    # --- subtractive ACLs ---
    for u in users:
        if "+@all" in u and u.split()[1] != "default":
            add("WARN", f"user '{u.split()[1]}' built from +@all (subtractive)")

    # --- dangerous commands reachable by the CURRENT connection ---
    for cmd, args in [("CONFIG", ("GET", "dir")), ("DEBUG", ("JMAP",)),
                      ("MODULE", ("LIST",)), ("SHUTDOWN", ("ABORT",))]:
        try:
            r.execute_command(cmd, *args)
            add("WARN", f"{cmd} reachable by this user")
        except redis.ResponseError as e:
            if "NOPERM" not in str(e) and "unknown command" not in str(e).lower():
                add("WARN", f"{cmd} reachable by this user")

    # --- transport ---
    if cfg("tls-port") in ("", "0"):
        add("WARN", "TLS not enabled - traffic and AUTH are plaintext")
    elif cfg("port") != "0":
        add("CRIT", "tls-port set but plaintext `port` is still open")

    # --- data protection ---
    if cfg("maxmemory") in ("", "0"):
        add("WARN", "maxmemory unlimited - the OOM killer bounds this instance")
    policy = cfg("maxmemory-policy")
    ks = r.info("keyspace").get("db0")
    if policy.startswith("volatile") and ks:
        cov = ks["expires"] / ks["keys"] if ks["keys"] else 1
        if cov < 0.95:
            add("CRIT", f"policy={policy} with {cov:.0%} TTL coverage - OOM risk")
    if cfg("appendonly") == "no" and not cfg("save"):
        add("INFO", "no persistence configured (fine for a pure cache)")

    # --- process ---
    try:
        if r.info("server").get("executable", "").startswith("/root"):
            add("CRIT", "Redis appears to run as root")
    except Exception: pass

    return findings

🎯 Key Takeaways

  • Redis's defaults assume a trusted network: no auth, no encryption, every command available — every security feature is layered on top of that assumption.
  • An exposed Redis is a host compromise, not a data leak: CONFIG SET dir + dbfilename + SAVE writes an arbitrary file as the Redis user — demonstrated end to end.
  • MODULE LOAD runs native code, and REPLICAOF can repoint an instance at an attacker's primary — deny both everywhere.
  • Protected mode stops protecting as soon as a password or any bind directive is set — so bind 0.0.0.0 removes the guard in the same edit that widens reach.
  • requirepass grants full admin with one shared secret, and Redis answers >100K AUTH attempts/sec with no throttling or lockout — password length is the entire defence.
  • ACLs give per-user control over commands, key patterns and channels; disable the default user and create one user per service.
  • Build ACLs additively. A subtractive rule still allowed DEBUG, REPLICAOF, KEYS and ACL SETUSER — the last letting the "restricted" user create an unrestricted one.
  • Additive rules are upgrade-safe: -@all +@read +@write cannot silently gain a command that a future Redis version adds.
  • Subcommand grants matter: +config|get lets monitoring read configuration without gaining the file-write primitive that +config would.
  • Key permissions and command permissions are independent axes — a user can hold +@write and still be denied a key outside its patterns.
  • ACL LOG records who was denied what and why (command vs key) — alert on it, since denials mean a broken deploy or probing.
  • tls-port without port 0 leaves plaintext listening and therefore in use — verified that both ports answered.
  • TLS cost measured at 23% unpipelined but only 8% pipelined, because the overhead is largely per-record and batching amortises it.
  • CONFIG SET changes only the running process — after a restart both maxmemory and the eviction policy reverted, the latter to noeviction, so a cache starts refusing writes.
  • Follow every intended-to-persist CONFIG SET with CONFIG REWRITE, or better, manage the config file as code so a restart is safe by construction.
  • Lowering maxmemory below current usage evicts immediately: 66% of the keyspace gone in one command, with 118 ms of blocking eviction work. Step it down; never as an incident reflex.
  • Upgrade replicas first, then fail over deliberately — upgrading a primary in place leaves no rollback if it fails to start.
  • Run Redis as a dedicated non-root user, which turns an arbitrary file write from total compromise into a much smaller problem.
  • Audit as an application user, not an admin one — the application credential is the one that leaks, so its reachable command set is the question that matters.
