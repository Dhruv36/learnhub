Persistence: RDB & AOF Durability & Distribution

What you'll master: exactly how much data each persistence configuration loses, stated as a number rather than a feeling — including why the default appendfsync everysec can lose far more than one second; fork() and copy-on-write, which is the mechanism behind every mysterious Redis latency spike and every "why did memory double" incident; why vm.overcommit_memory=1 is the one Linux setting Redis genuinely requires and what happens without it; AOF rewrite, and why the file shrinks by more than you expect; the hybrid RDB+AOF format that is the modern default; and the honest framing an interviewer wants — that persistence is not durability, and replication is not backup. Prerequisites: The Single-Threaded Model, Memory & Eviction.

Part 1 — RDB: A Point-in-Time Fork

RDB writes a compact binary snapshot of the entire dataset. The mechanism is the important part, because everything surprising about RDB follows from it: Redis fork()s, and the child writes the file while the parent keeps serving.

BGSAVE
  │
  ├─ fork()                    ← the ONLY blocking step for the parent
  │                              (page-table copy; ~10-20 ms per GB)
  ├─ parent: keeps serving, copy-on-write for pages it modifies
  └─ child:  walks the dataset, writes dump.rdb, exits

SAVE                           ← synchronous. Blocks EVERYTHING. Never in production.
🔑 The fork itself is the latency spike, not the disk write. The child writes gigabytes without touching the parent's latency, but fork() must copy the parent's page tables, and that cost scales with the size of the dataset — roughly 10–20 ms per GB on bare metal, and substantially worse on virtualised hardware (EC2 without huge pages is commonly 3–5× slower). A 20 GB instance can stall for 200–400 ms on every background save, and because Redis is single-threaded, that stall applies to every client. This is the single most common cause of "Redis had a latency spike and we can't explain it".

save 900 1        # snapshot if ≥1 key changed in 900s
save 300 10       # ...or ≥10 keys in 300s
save 60 10000     # ...or ≥10000 keys in 60s
save ""           # disable RDB entirely

dbfilename dump.rdb
dir /var/lib/redis
rdbcompression yes            # LZF on strings; cheap, usually worth it
rdbchecksum yes               # CRC64; ~10% load-time cost, catches corruption
stop-writes-on-bgsave-error yes   # ← refuse writes if the last save FAILED

That last setting surprises people during incidents. If a background save fails — a full disk is the usual reason — Redis starts rejecting all writes to make the failure impossible to ignore. The error (MISCONF Redis is configured to save RDB snapshots...) reads like a Redis bug and is actually a disk alert being delivered through the only channel Redis has.

PropertyRDB
File size✅ Compact — binary, compressed
Restart load time✅ Fastest available
Effect on write latency✅ None, except the fork stall
Backup / clone friendliness✅ One file to copy
Data loss window❌ Everything since the last snapshot — minutes
Fork cost❌ Scales with dataset size
Memory during save❌ Up to 2× under heavy writes (CoW)

Part 2 — AOF: Every Write, Appended

AOF logs every write command in RESP format, appended to a file. On restart, Redis replays the log to reconstruct the dataset.

appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec          # ← the important one. Options below.

*3\r\n$3\r\nSET\r\n$5\r\nuser1\r\n$4\r\nalice\r\n     ← what the file contains
appendfsyncLoss windowThroughputUse when
always~0 (one command)Drastically reducedGenuinely cannot lose a write
everysec1s, usually — but see belowNear-fullDefault; right for almost everything
noOS-decided — 30s+FullCache only; loss is irrelevant
🔑 everysec does not guarantee one second of loss. A background thread calls fsync every second, but if the previous fsync is still in flight — the disk is slow, or an AOF rewrite is saturating it — the main thread has a choice: block on the write, or proceed and let the buffer grow. Redis waits up to 2 seconds, then proceeds unsynced rather than stalling. Under disk pressure the real loss window is therefore seconds, not one second. Anyone quoting "AOF everysec loses at most 1 second" is quoting the happy path.

appendfsync always is more expensive than people expect, because it is an fsync per write command — not per batch. It also does not make Redis fully durable on its own: the write is on disk, but a machine loss still takes the instance out, so durability still depends on replication or backups.

AOF rewrite is what keeps the file from growing forever. It also forks:

BGREWRITEAOF
  │
  ├─ fork()                  ← same stall as BGSAVE
  ├─ child:  writes a MINIMAL AOF representing the current dataset
  └─ parent: buffers new writes, appends them to the child's file at the end

auto-aof-rewrite-percentage 100      # rewrite when the file doubles
auto-aof-rewrite-min-size 64mb       # ...but not below this

The rewrite shrinks the file more than most people expect, because the log contains history and the rewrite contains only state. A counter incremented a million times is a million INCR commands in the log and one SET after the rewrite. Keys that were written and later deleted vanish entirely. Exercise 3 measures a real case.

Part 3 — Fork, Copy-on-Write, and the Memory Cliff

Both persistence mechanisms fork, so copy-on-write behaviour governs the memory profile of a Redis server under save. Understanding it is what separates a working configuration from a nightly OOM kill.

fork() → parent and child share ALL memory pages, marked read-only

  parent modifies a key → page fault → kernel COPIES that 4 KB page
                                        ↑ now duplicated

Extra memory used = (pages the PARENT modifies during the save) × 4 KB

  Idle instance during save      → ~0 extra memory
  Heavy random writes            → up to 2× the dataset size
🔑 The memory overhead is driven by write dispersion, not write volume. A million writes to a hundred keys touches a handful of pages and costs almost nothing. A hundred thousand writes scattered across a large keyspace touches a hundred thousand distinct pages and copies ~400 MB. This is why the same instance can save cleanly for months and then OOM during a batch job that rewrites the whole keyspace — the workload changed shape, not size.

vm.overcommit_memory=1 is not optional. With the Linux default (0), the kernel heuristically refuses a fork when it estimates the child could need more memory than is available — even though copy-on-write means it almost never will. The result is a save that fails at exactly the moment it matters:

# The log line everyone eventually meets:
#   Can't save in background: fork: Cannot allocate memory

sysctl vm.overcommit_memory=1
echo "vm.overcommit_memory = 1" >> /etc/sysctl.conf

# Also disable transparent huge pages — they make CoW copy 2 MB pages
# instead of 4 KB, inflating both memory use and latency:
echo never > /sys/kernel/mm/transparent_hugepage/enabled

Transparent huge pages deserve emphasis: with THP enabled, a single modified key copies a 2 MB page rather than a 4 KB one — 512× the memory amplification, and a corresponding latency cost on every copy. Redis logs a warning about this at startup, and the warning is worth acting on.

SymptomCauseFix

Part 4 — Hybrid Persistence, and What to Actually Run

Since Redis 4.0, the two formats combine. With aof-use-rdb-preamble yes (the default), an AOF rewrite writes an RDB snapshot as the file's header and appends subsequent commands in AOF format.

appendonly.aof after a rewrite:

  ┌──────────────────────────┐
  │ RDB snapshot (binary)    │  ← fast to load
  ├──────────────────────────┤
  │ SET k v                  │  ← commands since the rewrite
  │ INCR counter             │
  └──────────────────────────┘

Fast load like RDB, small loss window like AOF.

Redis 7 changed the on-disk layout to a multi-part AOF in an appenddirname directory: a base file (RDB or AOF format), incremental files, and a manifest. This removed a long-standing problem where the rewrite had to buffer new writes in memory and write them twice. Backup scripts that assume a single appendonly.aof file break on upgrade to 7 — a small operational detail that causes real incidents.

WorkloadConfigurationLoss window
Pure cachesave "", appendonly noEverything — by design
Cache you prefer warmRDB only, relaxed save rulesMinutes
General purposeAOF everysec + RDB for backups~1s, more under disk pressure
Session storeAOF everysec~1s (users re-login)
Primary datastoreAOF everysec + replicas + off-box backups~1s local; failover may lose more
Financial recordNot Redis — or Redis plus a real database—

The standard production setup keeps persistence off the node serving traffic: AOF everysec everywhere for restart recovery, and RDB snapshots taken on a replica, so the fork stall lands on a machine no client is reading from. That single arrangement removes the most common source of Redis latency spikes without weakening the loss window at all.

Part 5 — Persistence Is Not Durability

The most valuable thing to be clear about — in an interview and in a design review — is what persistence does not give you.

Client: SET order:7 paid     → +OK          ← acknowledged
        │
        ├─ in memory                        ✅
        ├─ in the AOF buffer                ✅
        ├─ fsync'd to disk?                 ❓ up to 1s later (everysec)
        └─ on a replica?                    ❓ asynchronous, no guarantee

The +OK means "accepted", NOT "durable".
🔑 Redis acknowledges writes before they are durable, and replicates asynchronously. A primary can acknowledge a write, fail before the fsync and before the replica receives it, and the promoted replica simply will not have it — the acknowledged write is gone, with no error to anyone. This is not a bug; it is the latency/durability trade Redis chose. It is also why "we use Redis as the source of truth for payments, but we enabled AOF" is not a sufficient answer.

WAIT narrows the window but does not close it:

SET order:7 paid
WAIT 2 100        → returns the number of replicas that acknowledged, within 100ms

# WAIT is NOT consensus:
#   - it can return fewer than requested and the write still stands
#   - replicas ack RECEIPT, not fsync
#   - a failover can still promote a replica that lacked the write

And replication is not backup. A FLUSHALL, a bad migration, or an application bug replicates to every replica in milliseconds. Backups protect against the operator and the code; replicas protect against the hardware. They solve different problems and neither substitutes for the other.

ThreatReplicationAOF/RDB on the boxOff-box backups
Process crash✅✅✅
Machine loss✅❌✅
Accidental FLUSHALL❌ replicates instantly❌ rewritten✅
Bad deploy corrupting data❌ replicates❌✅
Region outageOnly if cross-region❌✅

Part 6 — Restart, Recovery and Verification

On startup Redis loads AOF if appendonly yes, otherwise RDB. If AOF is enabled but the file is missing, Redis starts empty and ignores an existing RDB — a genuinely dangerous behaviour when someone enables AOF on a running instance the wrong way.

# WRONG — restarting now loads an empty (or absent) AOF, discarding the RDB data
CONFIG SET appendonly yes      # ← this DOES trigger a rewrite, so it is safe...
# ...but editing redis.conf and restarting is NOT: no AOF exists yet.

# Correct order when enabling AOF on a live instance:
CONFIG SET appendonly yes      # creates the AOF from current memory
INFO persistence               # confirm aof_rewrite_in_progress:0, aof_enabled:1
# only THEN persist it to redis.conf

Verify persistence health from INFO persistence rather than assuming it:

INFO persistence
  rdb_last_bgsave_status:ok          ← "err" means writes may be blocked
  rdb_last_save_time:1723900000      ← how stale is the snapshot?
  rdb_changes_since_last_save:14829  ← how much would be lost right now
  aof_enabled:1
  aof_last_write_status:ok
  aof_last_bgrewrite_status:ok
  aof_rewrite_in_progress:0
  latest_fork_usec:184000            ← ★ the fork stall, in microseconds
  mem_fragmentation_ratio:1.2

latest_fork_usec is the number to alert on. It is the actual measured duration of the last fork, which is the actual measured duration of the last full-server stall. If it reads 184000, every client saw a 184 ms pause. Watching it over time catches a growing dataset before it produces a user-visible incident.

Repairing damaged files is a routine operation after an unclean shutdown:

redis-check-aof --fix appendonly.aof      # truncates the trailing partial command
redis-check-rdb dump.rdb                  # verifies; cannot repair

aof-load-truncated yes                    # default: tolerate a truncated tail on load

A truncated AOF tail is normal — the process died mid-append — and aof-load-truncated yes handles it by dropping the partial command. Corruption in the middle of the file is a different matter, and it is where backups stop being theoretical.

❌ Treating "AOF is enabled" as proof that data cannot be lost. The team turns on appendfsync everysec, writes "durable" in the design document, and makes Redis the source of truth for something that matters. Three separate gaps remain, and all of them are invisible until an incident: writes are acknowledged before they are fsync'd, so a crash loses up to a second — more when the disk is slow, because Redis proceeds unsynced rather than stalling; replication is asynchronous, so a failover can promote a replica that never received the acknowledged write; and the AOF lives on the same machine as the data, so machine loss takes both. Meanwhile the fork every rewrite performs is stalling every client for hundreds of milliseconds, and nobody has connected the latency graph to the persistence config.

✅ State the loss window as a number, and design for it. AOF everysec means "up to a second, more under disk pressure" — write that down and check whether the business can accept it. Run AOF on the serving node for restart recovery, take RDB snapshots on a replica so the fork stall lands where no client is reading, ship backups off-box because replication does not protect against FLUSHALL or a bad deploy, set vm.overcommit_memory=1 and disable THP so forks succeed and stay cheap, and alert on latest_fork_usec and rdb_last_bgsave_status. If the answer is genuinely "we cannot lose any acknowledged write", the answer is a database with synchronous commit, with Redis in front of it.

Interview Questions

Beginner: What is the difference between RDB and AOF?

RDB is a point-in-time binary snapshot of the whole dataset. Redis forks, and the child writes dump.rdb while the parent keeps serving. AOF is an append-only log of every write command, replayed on startup to rebuild the data.

RDBAOF
ContentsState at a momentEvery write command
Loss windowSince the last snapshot (minutes)~1s with everysec
File sizeCompactLarger; needs rewriting
Restart speedFastestSlower (replays commands)
Ongoing costFork per snapshotAppend per write + fsync
Best forBackups, clones, fast restartMinimising data loss

They are not alternatives — run both. AOF gives a small loss window, RDB gives a compact file for backups and a fast restore. Since Redis 4 the hybrid format combines them: an AOF rewrite writes an RDB snapshot as the file header and appends commands after it, so you get RDB's load speed with AOF's loss window.

appendonly yes
appendfsync everysec
save 900 1                     # RDB as well, for backups
aof-use-rdb-preamble yes       # hybrid format (default)

The exception is a pure cache, where losing everything on restart is acceptable and disabling both (save "", appendonly no) removes the fork stalls entirely.

Beginner: Why does Redis fork to save, and what does that cost?

Because Redis is single-threaded. Writing gigabytes to disk on the main thread would block every client for the whole duration — which is exactly what the synchronous SAVE command does, and why it must never be used in production.

fork() creates a child that shares the parent's memory through copy-on-write. The child sees a frozen, consistent view of the data and writes it out; the parent keeps serving, and the kernel copies a page only when the parent modifies it.

BGSAVE → fork() → child writes dump.rdb, parent serves normally

The costs are two, and both surprise people.

1. The fork stall. fork() copies the parent's page tables, which takes roughly 10–20 ms per GB on bare metal and considerably longer on VMs. A 20 GB instance stalls for 200–400 ms, and every client sees it. latest_fork_usec in INFO persistence reports the last one exactly.

2. Memory amplification. Every page the parent writes to during the save gets copied. The overhead is driven by how scattered the writes are, not how many: a million writes to a hundred keys costs almost nothing, while scattered writes across the keyspace can approach doubling memory. This is why Redis instances should be sized with headroom rather than to their working set.

Two host settings are effectively required: vm.overcommit_memory=1, or the kernel refuses the fork with Cannot allocate memory; and transparent huge pages disabled, or copy-on-write copies 2 MB pages instead of 4 KB.

Mid: How much data can you lose in each configuration?

Stating this as a number is the whole point of the question.

ConfigurationLoss window
No persistenceEverything
RDB, save 900 1Up to 15 minutes
RDB, save 60 10000Up to 60s (if the change rate is met)
AOF everysec~1s — more under disk pressure
AOF always~0 locally; still lost if the machine dies
AOF + replica + failoverWhatever replication lag was at failover

The caveat that matters: everysec is not a guarantee of one second. A background thread fsyncs each second, but if the previous fsync is still in flight, Redis waits up to two seconds and then continues without syncing rather than stalling writes. Under a slow disk or a concurrent AOF rewrite, the real window is several seconds.

And even always is not zero loss in the way people mean it. The write is on that machine's disk; if the machine is gone, so is the write, unless a replica received it — and replication is asynchronous, so a failover can promote a replica that never saw it. WAIT narrows the window but is not consensus: replicas acknowledge receipt rather than fsync, and it can return fewer replicas than requested while the write still stands.

So the honest framing is: Redis acknowledges writes before they are durable. For a cache or a session store that is the right trade. For anything where a lost acknowledged write is unacceptable, the source of truth belongs in a database with synchronous commit, with Redis in front of it.

Mid: Redis has periodic latency spikes. How does persistence cause them, and how do you fix it?

The fork is the prime suspect, and it is measurable rather than a matter of opinion:

INFO persistence
  latest_fork_usec:184000        ← 184 ms — every client stalled for this long
  rdb_bgsave_in_progress:0
  aof_rewrite_in_progress:0

Both BGSAVE and BGREWRITEAOF fork, and the cost scales with dataset size (~10–20 ms/GB bare metal, worse on VMs). If the spike period matches the save rules or the AOF rewrite threshold, that is the answer.

Confirm with the latency tooling, which names the source directly:

CONFIG SET latency-monitor-threshold 100
LATENCY HISTORY fork
LATENCY LATEST                 # event, last, max
redis-cli --latency-history

The other persistence-related causes: transparent huge pages, which make every copy-on-write fault copy 2 MB instead of 4 KB; an AOF rewrite saturating the disk so that everysec fsyncs block the main thread; and appendfsync always, which pays a sync per write.

Fixes, in order of impact:

  • Move snapshots to a replica. Disable save rules on the primary and take RDB snapshots on a replica — the fork stall then lands on a machine no client reads from. This is the standard production arrangement and it removes the spike entirely.
  • Disable THP — a one-line host change with a large effect on both memory and fork cost.
  • Shard. Fork cost scales with instance size, so four 10 GB instances fork four times faster than one 40 GB instance.
  • Tune the rewrite threshold so rewrites are less frequent, accepting a larger AOF.
  • Faster disks, which help the fsync-blocking case rather than the fork itself.

If the spikes turn out not to correlate with forks, the next candidates are O(n) commands and eviction — covered in The Single-Threaded Model and Performance & Latency.

Senior: Design persistence and backup for Redis as a primary datastore holding 50 GB.

First, challenge the premise honestly — an interviewer usually wants to hear it. Redis acknowledges writes before fsync and replicates asynchronously, so a failover can lose acknowledged writes. If the data is financial or legally required, the source of truth belongs in a database and Redis belongs in front of it. If the data is sessions, feature state, real-time aggregates, or a rebuildable projection, Redis as primary is defensible — and the rest of the design follows.

Topology. 50 GB is a large single instance mainly because of fork cost: ~10–20 ms per GB means a 0.5–1 second stall per fork on bare metal, worse on VMs. So shard into ~8 instances of ~6 GB each, which cuts fork stalls to well under 100 ms and lets recovery run in parallel. Each shard gets at least one replica.

Per-node configuration:

# primaries: AOF for the loss window, NO RDB snapshots (no fork stalls)
appendonly yes
appendfsync everysec
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 512mb        # fewer rewrites at this size
save ""                                # snapshots happen on the replica

# replicas: snapshots live here
save 900 1
appendonly yes

Host settings, which are part of the design and not an afterthought: vm.overcommit_memory=1 so forks do not fail, THP disabled so copy-on-write stays at 4 KB pages, and memory sized at roughly 2× the dataset per node to survive CoW amplification during a rewrite.

Backups. RDB snapshots from a replica, shipped off-box to object storage, hourly, with retention that allows point-in-time recovery to before a bad deploy (7 daily + 4 weekly is a typical shape). Replication is explicitly not the backup: FLUSHALL and application-level corruption replicate instantly.

Verification, which is the part that is usually missing. A backup nobody has restored is a hypothesis. Automate a weekly restore into a scratch instance, check DBSIZE and a sample of keys against expectations, and alert if the restore fails or the key count deviates. Also alert on rdb_last_bgsave_status, aof_last_write_status, and latest_fork_usec trending upward as the dataset grows.

State the residual risk in writing: up to ~1 second of writes on a crash (more if the disk is slow), plus whatever replication lag existed at a failover. If that is unacceptable, the requirement is a synchronous-commit database, and no Redis configuration changes that.

Senior: Redis is OOM-killed every night at 2am. Diagnose it.

A precise schedule points at a scheduled job interacting with persistence. The mechanism is almost always copy-on-write amplification during a fork.

The sequence: a nightly batch rewrites a large fraction of the keyspace. If a BGSAVE or AOF rewrite is running concurrently, every page the parent modifies is copied — and a job that touches the whole keyspace copies nearly the whole dataset. Memory approaches 2×, crosses the host limit, and the kernel OOM-killer chooses the largest process, which is Redis.

Confirm it:

grep -i "killed process" /var/log/syslog        # OOM killer, with the RSS at kill time
dmesg -T | grep -i oom

INFO persistence     # rdb_bgsave_in_progress / aof_rewrite_in_progress at 2am?
INFO memory          # used_memory vs used_memory_rss vs maxmemory

The tell is used_memory_rss far above used_memory during the window — that gap is the copied pages.

Other candidates, worth ruling out: transparent huge pages, which turn each 4 KB copy into 2 MB and can alone explain a doubling; a batch job legitimately adding data with no maxmemory configured, so nothing bounds growth; and client output buffers if the job does large reads — CLIENT LIST shows omem per connection.

Fixes, in order:

  • Disable THP. Cheapest change, often sufficient on its own.
  • Do not persist on this node — move snapshots to a replica so no fork happens on the instance the batch job writes to.
  • Deconflict the schedule so the batch job does not overlap the rewrite window.
  • Set maxmemory with an eviction policy, so Redis bounds itself rather than being bounded by the OOM killer. Roughly 60% of host RAM is a reasonable starting point when forking is in play.
  • Shard, so no single process is large enough for CoW amplification to exhaust the host.
  • Have the batch job write in smaller batches with pauses, reducing the number of distinct pages dirtied inside any one save window.

The reasoning to state clearly: Redis memory is not just the dataset. It is the dataset, plus copy-on-write pages during saves, plus client output buffers, plus fragmentation — and sizing a host to the dataset alone is what turns a normal nightly job into a nightly outage.

🏋️ Exercises

1 (easy): Measure the RDB loss window directly — write data, kill Redis without saving, and count what survives.
Solution 
import redis, subprocess, time, os

r = redis.Redis(decode_responses=True)
r.flushall()
r.config_set("appendonly", "no")
r.config_set("save", "")                      # disable automatic snapshots

r.bgsave()                                    # explicit snapshot as our baseline
time.sleep(0.5)
info = r.info("persistence")
print(f"snapshot taken, changes since: {info['rdb_changes_since_last_save']}")

for i in range(1000):                         # writes AFTER the snapshot
    r.set(f"after:{i}", i)

info = r.info("persistence")
print(f"1000 writes later, unsaved changes: {info['rdb_changes_since_last_save']}")
print(f"last save was {int(time.time()) - info['rdb_last_save_time']}s ago")
print(f"→ a crash right now loses {info['rdb_changes_since_last_save']} writes")

snapshot taken, changes since: 0
1000 writes later, unsaved changes: 1000
last save was 1s ago
→ a crash right now loses 1000 writes

rdb_changes_since_last_save is a live readout of the current exposure — it is the number of writes that would vanish if the process died at this instant, and it is the right thing to graph.

Now actually kill it and count the survivors:

pid = r.info("server")["process_id"]
r.bgsave(); time.sleep(0.5)                   # baseline snapshot
before = r.dbsize()

for i in range(500):
    r.set(f"doomed:{i}", i)                   # never snapshotted
print(f"keys in memory before kill: {r.dbsize()}")

os.kill(pid, 9)                               # SIGKILL — no chance to save
time.sleep(3)
subprocess.run(["redis-server", "--daemonize", "yes",
                "--save", "", "--appendonly", "no"], check=False)
time.sleep(2)

r2 = redis.Redis(decode_responses=True)
print(f"keys after restart        : {r2.dbsize()}")
print(f"lost                      : {before + 500 - r2.dbsize()} keys")

keys in memory before kill: 1500
keys after restart        : 1000
lost                      : 500 keys

Exactly the 500 writes made after the snapshot were lost. With the default save 900 1 rules that window is up to 15 minutes of writes — which is the number to compare against what the application can tolerate.

Compare with AOF everysec:

r2.config_set("appendonly", "yes")
time.sleep(1)                                  # let the initial rewrite finish
r2.flushall()
for i in range(500):
    r2.set(f"aof:{i}", i)
time.sleep(1.2)                                # allow one fsync cycle
pid = r2.info("server")["process_id"]
os.kill(pid, 9)
time.sleep(3)
subprocess.run(["redis-server", "--daemonize", "yes", "--appendonly", "yes"],
               check=False)
time.sleep(2)
r3 = redis.Redis(decode_responses=True)
print(f"AOF everysec, after SIGKILL: {r3.dbsize()} of 500 keys survived")

AOF everysec, after SIGKILL: 500 of 500 keys survived

All 500 survived because more than a second elapsed before the kill. Killing immediately after the writes would lose the unsynced tail — which is the ~1 second window, and the reason the exercise sleeps.

2 (easy): Measure the fork stall and show that it scales with dataset size.
Solution 
import redis, time, threading

r = redis.Redis(decode_responses=True)

def fill(mb):
    r.flushall()
    payload = "x" * 1024                        # 1 KB values
    p = r.pipeline()
    for i in range(mb * 1024):
        p.set(f"k:{i}", payload)
        if i % 5000 == 0: p.execute(); p = r.pipeline()
    p.execute()

def measure_fork(label):
    latencies, stop = [], threading.Event()
    def probe():
        c = redis.Redis(decode_responses=True)
        while not stop.is_set():
            t0 = time.perf_counter()
            try: c.ping()
            except Exception: pass
            latencies.append((time.perf_counter() - t0) * 1000)
            time.sleep(0.001)
    t = threading.Thread(target=probe); t.start()
    time.sleep(0.3); latencies.clear()
    r.bgsave()
    while r.info("persistence")["rdb_bgsave_in_progress"]:
        time.sleep(0.01)
    stop.set(); t.join()
    fork_us = r.info("persistence")["latest_fork_usec"]
    used_mb = r.info("memory")["used_memory"] / 1024 / 1024
    print(f"{label:8s} {used_mb:6.0f} MB  latest_fork_usec={fork_us:8,d}  "
          f"max client ping={max(latencies):6.1f} ms")
    return used_mb, fork_us

r.config_set("save", "")
for mb in (100, 500, 1000):
    fill(mb)
    measure_fork(f"{mb}MB")

100MB      142 MB  latest_fork_usec=   1,842  max client ping=   2.3 ms
500MB      672 MB  latest_fork_usec=   8,110  max client ping=   9.4 ms
1000MB    1341 MB  latest_fork_usec=  16,447  max client ping=  17.8 ms

The fork time scales linearly with dataset size — roughly 12 µs per MB here, i.e. ~12 ms per GB — and the maximum client ping tracks it almost exactly. That is the proof that latest_fork_usec is the stall every client experiences, not an internal statistic.

Extrapolating: a 20 GB instance stalls ~240 ms per fork on this hardware, and virtualised hosts are commonly 3–5× slower. That is why large instances move snapshots to a replica.

Confirm with Redis's own latency monitor, which attributes it by name:

4 (medium): Measure copy-on-write memory amplification and show it depends on write dispersion, not volume.
Solution 
import redis, time, threading, random

r = redis.Redis(decode_responses=True)
r.config_set("save", "")
r.config_set("appendonly", "no")

def fill(n=400_000):
    r.flushall()
    p = r.pipeline()
    for i in range(n):
        p.set(f"k:{i}", "x" * 200)
        if i % 5000 == 0: p.execute(); p = r.pipeline()
    p.execute()

def cow_during_save(writer, label):
    fill()
    base_rss = r.info("memory")["used_memory_rss"]
    peak = [base_rss]
    stop = threading.Event()

    def watch():
        c = redis.Redis(decode_responses=True)
        while not stop.is_set():
            peak[0] = max(peak[0], c.info("memory")["used_memory_rss"])
            time.sleep(0.02)

    tw = threading.Thread(target=watch); tw.start()
    r.bgsave()
    writer(stop)                                   # write while the child saves
    while r.info("persistence")["rdb_bgsave_in_progress"]:
        time.sleep(0.02)
    stop.set(); tw.join()
    extra = (peak[0] - base_rss) / 1024 / 1024
    print(f"{label:24s} base={base_rss/1024/1024:6.0f} MB  "
          f"peak extra={extra:6.1f} MB  ({peak[0]/base_rss:.2f}×)")

def no_writes(stop):
    while r.info("persistence")["rdb_bgsave_in_progress"]:
        time.sleep(0.02)

def concentrated(stop):                            # many writes, FEW keys
    c = redis.Redis(decode_responses=True)
    n = 0
    while c.info("persistence")["rdb_bgsave_in_progress"]:
        p = c.pipeline()
        for _ in range(500):
            p.set(f"k:{random.randint(0, 99)}", "y" * 200); n += 1
        p.execute()
    print(f"   ({n:,} writes to 100 keys)")

def dispersed(stop):                               # fewer writes, MANY keys
    c = redis.Redis(decode_responses=True)
    n = 0
    while c.info("persistence")["rdb_bgsave_in_progress"]:
        p = c.pipeline()
        for _ in range(500):
            p.set(f"k:{random.randint(0, 399_999)}", "y" * 200); n += 1
        p.execute()
    print(f"   ({n:,} writes across 400,000 keys)")

cow_during_save(no_writes,    "idle during save")
cow_during_save(concentrated, "concentrated writes")
cow_during_save(dispersed,    "dispersed writes")

idle during save            base=   131 MB  peak extra=   1.2 MB  (1.01×)
   (48,500 writes to 100 keys)
concentrated writes         base=   131 MB  peak extra=   4.8 MB  (1.04×)
   (44,000 writes across 400,000 keys)
dispersed writes            base=   131 MB  peak extra=  67.3 MB  (1.51×)

Nearly the same number of writes, 14× the memory cost. 48,500 writes to 100 keys touched a handful of pages and cost 4.8 MB; 44,000 writes scattered across 400,000 keys dirtied thousands of distinct pages and cost 67 MB. Copy-on-write charges per page touched, not per write.

Scaled up, that is the nightly-OOM story: a batch job that rewrites the whole keyspace during a save approaches 2× the dataset in RSS, and a host sized to the dataset alone gets the OOM killer.

Check the two host settings that govern this:

5 (hard): Prove that an acknowledged write can be lost, and measure how much WAIT actually helps.
Solution 
import redis, time, os, subprocess, threading

r = redis.Redis(decode_responses=True)
r.config_set("appendonly", "yes")
r.config_set("appendfsync", "everysec")
time.sleep(1)
r.flushall()

# --- how many acknowledged writes are not yet fsync'd? ---
acked = 0
t0 = time.time()
while time.time() - t0 < 1.0:                 # one fsync interval
    r.set(f"unsynced:{acked}", acked)         # each returns +OK
    acked += 1
print(f"writes acknowledged in 1s: {acked:,}")
print("every one returned +OK — none is guaranteed to be on disk yet")

pid = r.info("server")["process_id"]
os.kill(pid, 9)                               # SIGKILL immediately after

               check=False)

survived the crash       : 21,760
ACKNOWLEDGED BUT LOST    : 16,652

16,652 writes that returned +OK do not exist after the crash. Nothing malfunctioned — this is what appendfsync everysec means, and it is why "we enabled AOF" is not the same statement as "we cannot lose data".

Compare appendfsync always, and measure what it costs:

def throughput(fsync_mode, n=5000):
    c = redis.Redis(decode_responses=True)
    c.config_set("appendfsync", fsync_mode)
    time.sleep(0.3)
    t0 = time.perf_counter()
    for i in range(n):
        c.set(f"bench:{i}", i)
    dur = time.perf_counter() - t0
    return n / dur

for mode in ("no", "everysec", "always"):
    print(f"appendfsync {mode:9s}: {throughput(mode):9,.0f} writes/s")

appendfsync no       :    41,203 writes/s
appendfsync everysec :    39,847 writes/s
appendfsync always   :     4,118 writes/s

everysec costs almost nothing (3%) while always costs 10× — an fsync per command rather than per second. That ratio is the whole reason everysec is the default and why raising durability here is a real trade, not a free switch.

Now WAIT, and what it does and does not promise:

r3 = redis.Redis(decode_responses=True)
n_replicas = r3.info("replication")["connected_slaves"]
print(f"connected replicas: {n_replicas}")

r3.set("critical", "value")
t0 = time.perf_counter()
acked_by = r3.execute_command("WAIT", 1, 100)      # want 1 replica, 100ms timeout
print(f"WAIT 1 100 → {acked_by} replica(s) acked in "
      f"{(time.perf_counter()-t0)*1000:.1f} ms")

t0 = time.perf_counter()
acked_by = r3.execute_command("WAIT", 5, 100)      # want 5 — more than exist
print(f"WAIT 5 100 → {acked_by} replica(s) after "
      f"{(time.perf_counter()-t0)*1000:.1f} ms  ← returned anyway, write stands")

connected replicas: 1
WAIT 1 100 → 1 replica(s) acked in 1.2 ms
WAIT 5 100 → 1 replica(s) after 100.4 ms  ← returned anyway, write stands

WAIT is not consensus. Asking for 5 replicas when 1 exists returns 1 after the timeout, and the write remains committed on the primary regardless. It also confirms receipt, not fsync — a replica can acknowledge and then crash before writing to disk. It narrows the window; it does not close it, and no Redis configuration does.

6 (hard): Build a backup-and-restore drill that verifies the backup, and show that replication does not protect against FLUSHALL.
Solution 
import redis, subprocess, time, os, shutil, hashlib

r = redis.Redis(decode_responses=True)
r.config_set("appendonly", "no")
r.config_set("save", "")
r.flushall()

# --- seed a known dataset with a verifiable fingerprint ---
for i in range(10_000):
    r.set(f"user:{i}", f"data-{i}")
    if i % 100 == 0:
        r.hset(f"profile:{i}", mapping={"name": f"u{i}", "age": str(20 + i % 50)})

def fingerprint(conn):
    """Order-independent hash of the whole keyspace."""
    h = hashlib.sha256()
    for key in sorted(conn.scan_iter(count=1000)):
        t = conn.type(key)
        if t == "string":  val = conn.get(key)
        elif t == "hash":  val = str(sorted(conn.hgetall(key).items()))
        else:              val = str(conn.dump(key))
        h.update(f"{key}={val}".encode())
    return h.hexdigest()[:16]

original_fp, original_size = fingerprint(r), r.dbsize()
print(f"seeded: {original_size:,} keys, fingerprint {original_fp}")

# --- take the backup ---
rdb_dir = r.config_get("dir")["dir"]
rdb_file = os.path.join(rdb_dir, r.config_get("dbfilename")["dbfilename"])
last = r.info("persistence")["rdb_last_save_time"]
r.bgsave()
while r.info("persistence")["rdb_last_save_time"] == last:
    time.sleep(0.1)

backup = "/tmp/redis-backup-verified.rdb"
shutil.copy2(rdb_file, backup)
print(f"backup: {os.path.getsize(backup):,} bytes → {backup}")

seeded: 10,100 keys, fingerprint 3f8a91c04e7b2d16
backup: 412,883 bytes → /tmp/redis-backup-verified.rdb

# simulate a replica by checking what a FLUSHALL would propagate

r.flushall()                                  # ← replicates to every replica in ms
print(f"after FLUSHALL : {r.dbsize():,} keys")

after FLUSHALL : 0 keys
a replica would now ALSO be empty — replication is not backup

Restore into a scratch instance and verify — the step that is usually skipped:

SCRATCH_PORT = 6399

                "--dir", scratch_dir, "--dbfilename", "dump.rdb",
                "--save", "", "--appendonly", "no"], check=True)

print(f"\nRESTORE VERIFICATION: {'PASS ✅' if ok else 'FAIL ❌'}")

# put the data back on the real instance
for key in rs.scan_iter(count=1000):
    r.restore(key, 0, rs.dump(key), replace=True)
print(f"recovered to primary: {r.dbsize():,} keys, "
      f"fingerprint {fingerprint(r)} → {'matches' if fingerprint(r)==original_fp else 'MISMATCH'}")

rs.shutdown(nosave=True)

restored keys       : 10,100 (expected 10,100)
restored fingerprint: 3f8a91c04e7b2d16 (expected 3f8a91c04e7b2d16)

recovered to primary: 10,100 keys, fingerprint 3f8a91c04e7b2d16 → matches

The fingerprint is what makes this a verification rather than a formality. A key count alone would pass even if every value were corrupted; hashing the actual contents proves the restore is faithful. Run this on a schedule against real backups, alert on FAIL, and the backup stops being a hypothesis.

Finally, confirm the file itself is intact before trusting it:

out = subprocess.run(["redis-check-rdb", backup], capture_output=True, text=True)
print(out.stdout.strip().splitlines()[-1])

redis-check-rdb validates the CRC64 checksum and structure — cheap enough to run on every backup as it is written, and the difference between discovering corruption now and discovering it during a restore.

🎯 Key Takeaways

  • RDB is a forked point-in-time snapshot; AOF is an append-only command log replayed at startup. Run both — the hybrid format gives RDB's load speed with AOF's loss window.
  • appendfsync everysec does not guarantee 1 second of loss: when an fsync lags, Redis proceeds unsynced rather than stalling, so the real window is seconds under disk pressure.
  • Measured: 16,652 acknowledged writes lost to a SIGKILL under everysec — +OK means accepted, not durable.
  • appendfsync always costs ~10× throughput (4,118 vs 39,847 writes/s), while everysec costs about 3%.
  • The fork — not the disk write — is the latency spike: fork time scaled linearly at ~12 ms/GB, and the max client ping tracked it exactly.
  • latest_fork_usec in INFO persistence is the duration every client was stalled; alert on it as the dataset grows.
  • Copy-on-write charges per page touched: 48,500 writes to 100 keys cost 4.8 MB, while 44,000 writes scattered across 400,000 keys cost 67 MB — 14× for the same volume.
  • vm.overcommit_memory=1 is required or forks fail with Cannot allocate memory; transparent huge pages must be disabled or CoW copies 2 MB pages instead of 4 KB.
  • Size hosts for up to 2× the dataset — nightly OOM kills are usually a batch job dirtying the keyspace during a save.
  • An unrewritten AOF stores history, not state: 100,000 INCRs on one key produced 3.9 MB that a rewrite collapsed to 133 bytes, and 20k writes + 20k deletes left 3 MB for a dataset of zero keys.
  • Run AOF on the primary and take RDB snapshots on a replica, so the fork stall lands where no client is reading.
  • Persistence is not durability: Redis acks before fsync and replicates asynchronously, so a failover can lose acknowledged writes.
  • WAIT narrows the window but is not consensus — asking for 5 replicas when 1 exists returned 1 after the timeout, and the write stood; replicas ack receipt, not fsync.
  • Replication is not backup: FLUSHALL and bad deploys replicate in milliseconds. Backups protect against operators and code; replicas protect against hardware.
  • Enabling AOF by editing the config and restarting starts Redis empty — use CONFIG SET appendonly yes first so the file is created from memory.
  • stop-writes-on-bgsave-error yes means a failed save rejects all writes with MISCONF — it is a disk alert delivered through the only channel Redis has.
  • Redis 7 replaced the single AOF file with a multi-part directory plus manifest; backup scripts assuming appendonly.aof break on upgrade.
  • Verify restores with a content fingerprint, not a key count — a count passes even when every value is corrupt, and an unverified backup is only a hypothesis.
