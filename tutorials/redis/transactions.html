Transactions & Lua Scripting Working With Redis

What you'll master: what MULTI/EXEC actually guarantees — which is isolation, emphatically not rollback — and why that surprises everyone from a SQL background; WATCH as optimistic locking, its retry loop, and the livelock risk under contention; Lua as the tool that solves what MULTI cannot, because it can branch on values it reads; script loading, EVALSHA, and the NOSCRIPT handling every production client needs; the determinism and replication rules that constrain what a script may do; and Redis 7 Functions as the successor to ad-hoc scripts. Prerequisites: Commands, Pipelining & Round Trips, The Single-Threaded Model.

Part 1 — MULTI/EXEC Is Not What You Think

Redis transactions provide isolation and batching. They do not provide rollback, and the difference catches out everyone arriving from a relational database.

MULTI                    → +OK
  SET a 1                → +QUEUED      ← commands are queued, not executed
  INCR b                 → +QUEUED
  SET c 3                → +QUEUED
EXEC                     → 1) +OK  2) (error) …  3) +OK
                                     ↑ INCR failed, but a and c were STILL SET
🔑 There is no rollback, and this is a deliberate design decision rather than a missing feature. Redis documents the reasoning: a command failing at execution time can only be caused by a programming error — using the wrong type, or bad arguments — which should be caught in development. Supporting rollback would require maintaining undo information for every command, slowing down the common path to protect against a bug. So EXEC runs every queued command and reports each result independently, and your code must inspect them.

GuaranteeProvided?
Isolation — no other client interleaves✅ Yes
All commands sent in one round trip✅ Yes
Malformed command aborts the transaction✅ Yes — detected at queue time
Rollback on runtime error❌ No
Atomicity in the ACID sense❌ Partial — all commands run, but failures are not undone
Conditional logic inside the transaction❌ No — use Lua

The two error classes behave differently, and the distinction matters:

# 1. QUEUE-TIME error (syntax, unknown command) — the whole transaction is discarded
MULTI
  NOTACOMMAND            → (error) unknown command
  SET a 1                → +QUEUED
EXEC                     → (error) EXECABORT Transaction discarded
                            ← nothing ran

# 2. RUNTIME error (wrong type) — everything else still applies
MULTI
  SET k "text"           → +QUEUED
  INCR k                 → +QUEUED       (valid syntax; fails at execution)
  SET j "ok"             → +QUEUED
EXEC                     → 1) OK  2) (error) not an integer  3) OK
                            ← k and j were both written

Part 2 — WATCH: Optimistic Locking

MULTI alone cannot make decisions based on data, because nothing executes until EXEC. WATCH fills that gap with optimistic concurrency control.

WATCH balance            # start watching
GET balance              # → "100"   (executes immediately, before MULTI)
                         # ... application decides ...
MULTI
  SET balance 50
EXEC                     # → (nil) if `balance` changed since WATCH — retry
                         # → 1) OK  if it did not

def transfer(r, src, dst, amount, retries=10):
    for _ in range(retries):
        try:
            with r.pipeline() as pipe:
                pipe.watch(src, dst)                    # 1. watch
                bal = int(pipe.get(src) or 0)           # 2. read (immediate mode)
                if bal < amount:
                    pipe.unwatch()
                    return False
                pipe.multi()                            # 3. enter queuing mode
                pipe.decrby(src, amount)
                pipe.incrby(dst, amount)
                pipe.execute()                          # 4. fails if src/dst changed
                return True
        except redis.WatchError:
            continue                                    # someone else won; retry
    raise RuntimeError("too much contention")
PropertyDetail
Optimistic, not pessimisticNo locks held; the transaction fails rather than waiting
Detects any writeEven writing the same value counts as a change
Cleared by EXEC, UNWATCH or disconnectNever leaves a lingering lock
Retry loop requiredAnd it can livelock under heavy contention

Under high contention WATCH degrades badly — every client retries, most fail again, and throughput collapses. That is the point at which Lua becomes the right tool.

Part 3 — Lua: The Real Answer

A Lua script runs server-side, atomically, in one round trip, and — crucially — it can branch on values it reads.

EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 mykey myvalue
     └────────────── script ──────────────────┘  ↑    ↑       ↑
                                          numkeys  KEYS[1]  ARGV[1]

-- conditional increment: impossible with MULTI, trivial in Lua
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
local limit   = tonumber(ARGV[1])
if current < limit then
  return redis.call('INCR', KEYS[1])
end
return -1
MULTI/WATCHLua
Atomic✅✅
Round trips2+ (and retries)1
Conditional logic❌ Client-side only✅ Server-side
Behaviour under contentionDegrades — retry stormsUnaffected
Blocks the serverOnly while executingFor the whole script

KEYS and ARGV must be separated properly. Every key the script touches belongs in KEYS — this is not stylistic, it is what allows Cluster to route the script and what keeps replication correct:

-- WRONG: the key is hidden in ARGV; Cluster cannot route this
EVAL "return redis.call('GET', ARGV[1])" 0 mykey

-- RIGHT
EVAL "return redis.call('GET', KEYS[1])" 1 mykey

Part 4 — Script Caching and EVALSHA

Sending the script text on every call wastes bandwidth. Redis caches scripts by SHA-1:

SCRIPT LOAD "return redis.call('GET', KEYS[1])"
  → "4e6d8fc8bb01276962cce5371fa795a7763657ae"

EVALSHA 4e6d8fc8bb01276962cce5371fa795a7763657ae 1 mykey
  → the value

# if the cache was flushed or the server restarted:
  → (error) NOSCRIPT No matching script

Every production client must handle NOSCRIPT by falling back to EVAL and re-caching — a restarted server or a SCRIPT FLUSH otherwise breaks the application:

def run_script(r, sha, script, keys, args):
    try:
        return r.evalsha(sha, len(keys), *keys, *args)
    except redis.exceptions.NoScriptError:
        return r.eval(script, len(keys), *keys, *args)   # re-caches automatically

Most client libraries wrap this — redis-py's register_script returns a callable that handles the fallback for you.

CommandPurpose
SCRIPT LOADCache a script, returning its SHA
SCRIPT EXISTS shaCheck whether it is cached
SCRIPT FLUSHClear the cache — invalidates every SHA
SCRIPT KILLTerminate a running script (only if it has not written)

Part 5 — Determinism, Replication and Blocking

Scripts replicate to replicas and the AOF. Historically Redis replicated the script, which meant non-deterministic scripts produced divergent state — so it enforced strict rules.

RuleReason
Use redis.call('TIME'), not Lua's clockEvery replica must see the same time
Seed randomness from ARGV, or use redis.replicate_commands()Otherwise replicas diverge
Do not iterate an unordered collection and write based on orderSMEMBERS order is not guaranteed
All keys in KEYSCluster routing and replication correctness

Redis 5+ replicates effects rather than scripts by default, which relaxes most of these — but writing deterministic scripts remains good practice, and Cluster still requires correct KEYS declaration.

The blocking hazard is the serious operational concern. A script holds the single thread for its entire duration:

-- this blocks EVERY client for as long as it runs
for i = 1, 10000000 do
  redis.call('SET', 'key:'..i, i)
end

lua-time-limit 5000          # after 5s, Redis starts replying BUSY to other clients
SCRIPT KILL                  # works only if the script has not yet WRITTEN
SHUTDOWN NOSAVE              # the only escape once it has written — data loss

Once a script has performed a write it cannot be killed, because killing it would leave partial state that violates atomicity. The only recovery is to restart the server, losing everything since the last save.

Part 6 — Redis Functions (7.0+)

Functions are the successor to ad-hoc EVALSHA: named, versioned libraries that persist across restarts and replicate properly.

#!lua name=mylib

redis.register_function('conditional_incr', function(keys, args)
  local current = tonumber(redis.call('GET', keys[1]) or '0')
  if current < tonumber(args[1]) then
    return redis.call('INCR', keys[1])
  end
  return -1
end)

$ redis-cli -x FUNCTION LOAD < mylib.lua
"mylib"
$ redis-cli FCALL conditional_incr 1 counter 10
(integer) 1

NOSCRIPT handling needed✅ Yes❌ No
AvailabilityAll versionsRedis 7.0+

❌ Treating MULTI/EXEC as a SQL transaction with rollback. The code wraps several writes in a transaction, assumes a failure undoes the batch, and never inspects the results array. When one command fails at runtime — an INCR on a value that is not a number, or an operation on the wrong type — every other command in the transaction has already applied. The result is silent partial state: a balance decremented without the matching credit, or an index updated for a record that was never written.

✅ Treat MULTI as "these run together without interruption" and check every result. EXEC returns one reply per queued command, and any of them can be an error while the rest succeeded — so inspect the array rather than assuming success. Where the operation genuinely must be all-or-nothing, or must branch on a value it reads, use a Lua script: it is atomic, it is one round trip, and it can validate preconditions before performing any write, which is the only way to get "check then act" semantics in Redis.

Interview Questions

Beginner: What does a Redis transaction guarantee?

Isolation and batching — not rollback.

MULTI                → OK
  SET a 1            → QUEUED
  INCR a             → QUEUED
EXEC                 → 1) OK  2) (integer) 2
GuaranteeProvided?
No other client interleaves✅ Yes
One round trip✅ Yes
Rollback on error❌ No

The absence of rollback is deliberate. Redis's reasoning is that a command failing at execution time indicates a programming error — wrong type, wrong arguments — which belongs in development, not production. Supporting rollback would mean recording undo information for every command, slowing the common path to guard against a bug.

MULTI
  SET k "text"
  INCR k              ← fails: not an integer
  SET j "value"
EXEC
→ 1) OK  2) (error) …  3) OK
     ↑ k and j were BOTH written despite the failure

The two error types differ: a malformed command is caught at queue time and aborts the whole transaction (EXECABORT); a runtime error only fails that one command.

The practical consequence is that you must inspect the results array. Assuming success because EXEC did not raise is how partial state gets written silently.

And MULTI cannot branch — nothing executes until EXEC, so a decision based on a value read inside the transaction is impossible. That needs WATCH or, better, Lua.

Beginner: What is WATCH and how do you use it?

WATCH provides optimistic locking: it marks keys, and if any of them changes before EXEC, the transaction is cancelled and returns nil.

WATCH balance
GET balance          → "100"        (executes immediately)
   ← another client writes balance here
MULTI
  SET balance 50
EXEC                 → (nil)        ← aborted; retry

def decrement_if_positive(r, key):
    while True:
        try:
            with r.pipeline() as pipe:
                pipe.watch(key)
                value = int(pipe.get(key) or 0)
                if value <= 0:
                    pipe.unwatch()
                    return False
                pipe.multi()
                pipe.decr(key)
                pipe.execute()
                return True
        except redis.WatchError:
            continue        # someone changed it; try again

It is optimistic, not pessimistic — no lock is held and no client waits. The transaction simply fails if there was a conflict, which means a retry loop is mandatory; without it, EXEC returning nil is a silent no-op.

BehaviourDetail
Any write invalidatesEven writing the identical value counts
Cleared automaticallyBy EXEC, UNWATCH, or disconnect
Multiple keysWATCH k1 k2 k3 — any change aborts

The scaling weakness is contention. With many clients competing for the same key, most retries fail again and throughput collapses — in the exercise in this lesson, WATCH managed a fraction of Lua's throughput under 50 concurrent clients.

So the rule I would give is: WATCH is fine for low-contention check-then-act, and Lua is the right answer whenever the key is hot — it achieves the same result in one round trip with no retries at all.

Mid: When would you use Lua instead of MULTI/WATCH?

Whenever the operation needs to make a decision based on data it reads, or whenever the key is contended.

MULTI/WATCHLua
Conditional logic❌ Client-side, needs a retry loop✅ Server-side
Round trips2+ per attempt1
Under contentionRetry stormsUnaffected
Blocks the serverBrieflyFor the script's duration

The canonical example is a bounded counter, which MULTI cannot express at all:

-- one round trip, atomic, no retries
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if current < tonumber(ARGV[1]) then
  return redis.call('INCR', KEYS[1])
end
return -1

Compare with the WATCH version, which needs a loop, two or more round trips per attempt, and degrades as contention rises.

Other cases where Lua is the only clean answer:

OperationWhy Lua
Safe lock releaseCompare the owner token, then delete — atomically
Sliding-window rate limitTrim, count, decide and add as one unit
Claim N due jobsRead a range and remove it without a gap
Conditional multi-key updateValidate all preconditions before any write

The cost is that a script blocks the single thread for its entire duration, so scripts must be short. A loop over a million keys inside Lua stalls every client — and once the script has written, it cannot even be killed.

My rule of thumb: if it can be one command, use one command; if it is independent commands, pipeline; if it needs to read-then-decide, use Lua; and keep the script small enough that its worst-case runtime is measured in microseconds.

Mid: Why must all keys be declared in KEYS?

Because Redis needs to know which keys a script touches before running it, for two independent reasons.

-- WRONG: the key is in ARGV
EVAL "return redis.call('GET', ARGV[1])" 0 mykey

-- RIGHT
EVAL "return redis.call('GET', KEYS[1])" 1 mykey

1. Cluster routing. Redis Cluster shards by key hash slot. It inspects the declared KEYS to decide which node should run the script and to verify they all live in one slot. Keys hidden in ARGV are invisible to that check, so the script may run on a node that does not own the data:

EVAL "..." 2 user:{123}:name user:{123}:email     ← same slot via the hash tag, OK
EVAL "..." 2 user:1:name user:2:email             ← CROSSSLOT error, correctly rejected
EVAL "..." 0 user:1:name                          ← no error, but WRONG NODE possible

2. Replication and correctness. Declaring keys lets Redis reason about what the script affects. Historically scripts were replicated verbatim, so undeclared keys could produce divergence; modern Redis replicates effects, which relaxes this, but Cluster routing still depends on it entirely.

Redis does not enforce it — a script accessing an undeclared key works fine on a single instance, which is exactly why the bug survives development and appears only after a move to Cluster.

The related determinism rules matter for the same reason:

AvoidUse instead
Lua's os.time()redis.call('TIME')
Unseeded math.random()Seed from ARGV
Writing based on SMEMBERS orderSort explicitly first

The practical guidance is to write scripts as if Cluster were mandatory, even on a single instance — it costs nothing and prevents a migration from breaking every script at once.

Senior: Design a safe distributed lock with Lua. What can go wrong?

The acquire is a single command; the release is what requires Lua.

# acquire: atomic, self-expiring, uniquely owned
SET lock:resource <random-token> NX PX 30000
  → OK    acquired
  → nil   held by someone else

A naive release is unsafe:

# WRONG
if r.get("lock:resource") == my_token:      ← the lock can expire HERE
    r.delete("lock:resource")               ← now deleting SOMEONE ELSE'S lock

The gap is real: client A's lock expires, client B acquires it, then A's delete removes B's lock while B still believes it holds it. Lua closes the gap:

-- release: compare and delete atomically
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end

Extending a held lock needs the same treatment:

if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0
Failure modeConsequenceMitigation
Holder crashesDeadlockThe TTL releases it
Work outlives the TTLTwo holders simultaneouslyWatchdog extends while working
Non-atomic releaseDeletes another's lockLua compare-and-delete
FailoverLock lost — async replicationSee below
Clock driftTTLs mean different things per nodeDo not rely on wall clocks

The failover case is the one that cannot be fixed with better code. Replication is asynchronous, so a master can acknowledge a lock acquisition and fail before replicating it — the promoted replica has no record of the lock, and a second client acquires it. Two clients then hold the "same" lock.

Redlock is the proposed answer — acquire on a majority of N independent masters — and it is genuinely contested. Martin Kleppmann's critique is that it relies on bounded clock drift and bounded pauses, neither of which a GC pause or a VM migration respects.

So the position I would take: Redis locks are excellent for efficiency — preventing duplicated work, deduplicating cron runs — where a rare double-execution is wasteful but harmless. For correctness, where two holders would corrupt data or double-charge a customer, I would use a system with consensus (etcd, ZooKeeper) or, better, make the operation idempotent so the lock stops being load-bearing. Covered further in Distributed Locks.

Senior: A Lua script is blocking production. What do you do, and how do you prevent it?

Immediate response, in order:

# 1. confirm — clients are getting BUSY errors
127.0.0.1:6379> PING
(error) BUSY Redis is busy running a script...

# 2. try to kill it
127.0.0.1:6379> SCRIPT KILL
OK                                    ← works ONLY if it has not written

(error) UNKILLABLE Sorry the script already executed write commands...
                                      ← now the only option is:
127.0.0.1:6379> SHUTDOWN NOSAVE       ← restart, losing data since the last save

The distinction is critical: a read-only script can be killed safely, because nothing has changed. A script that has written cannot be killed without leaving partial state that would violate the atomicity guarantee — so Redis refuses, and the only escape is a restart with data loss.

lua-time-limit is misunderstood — it does not terminate the script. After that many milliseconds, Redis merely starts replying BUSY to other clients so they can react, while the script continues running:

lua-time-limit 5000        # after 5s, others get BUSY — the script still runs

Prevention, which is where the real work is:

PracticeEffect
Bound every loop by an argumentNo unbounded iteration over a keyspace
Test against production-scale dataA script fast on 100 keys may be lethal on 10M
Chunk large work into many small callsThe loop is released between chunks
Never call KEYS or SMEMBERS on big collections in a scriptThe O(n) hazard, now unkillable
Review scripts like production codeThey run with no timeout and no isolation
-- BAD: unbounded, and unkillable once it writes
for i = 1, 10000000 do redis.call('SET', 'k:'..i, i) end

-- GOOD: bounded by the caller, resumable
local count = tonumber(ARGV[1])
local start = tonumber(ARGV[2])
for i = start, start + count - 1 do
  redis.call('SET', KEYS[1]..':'..i, i)
end
return start + count            -- the caller resumes from here

The architectural point I would make is that Lua's atomicity and its blocking are the same property. You cannot have "atomic" without "nothing else runs" on a single-threaded server — so the discipline is to keep scripts measured in microseconds, and to treat any script whose runtime depends on data size as a latent outage.

Monitoring: the slow log records scripts by their EVAL/EVALSHA entry, so a script creeping upward in duration is visible before it becomes an incident.

2 (easy): Use WATCH for a safe check-then-act.
Solution 
import redis, threading
r = redis.Redis(decode_responses=True)

def unsafe_decrement(client, key):
    """Read then write — racy."""
    v = int(client.get(key) or 0)
    if v > 0:
        client.set(key, v - 1)
        return True
    return False

def safe_decrement(client, key):
    """WATCH makes the read-then-write atomic."""
    while True:
        try:
            with client.pipeline() as pipe:
                pipe.watch(key)
                v = int(pipe.get(key) or 0)
                if v <= 0:
                    pipe.unwatch()
                    return False
                pipe.multi()
                pipe.set(key, v - 1)
                pipe.execute()
                return True
        except redis.WatchError:
            continue

STOCK = 100
for label, fn, key in [("unsafe", unsafe_decrement, "stock:unsafe"),
                       ("WATCH ", safe_decrement, "stock:safe")]:
    r.set(key, STOCK)
    sold = []
    lock = threading.Lock()

    def worker():
        c = redis.Redis(decode_responses=True)
        for _ in range(20):
            if fn(c, key):
                with lock: sold.append(1)

    ts = [threading.Thread(target=worker) for _ in range(20)]
    [t.start() for t in ts]; [t.join() for t in ts]
    remaining = int(r.get(key))
    print(f"{label}: sold {len(sold):3}, stock left {remaining:4}  "
          f"(sold + left = {len(sold)+remaining}, should be {STOCK})")

WATCH : sold 100, stock left    0  (sold + left = 100, should be 100)

The unsafe version oversold by 300 units — it sold 400 items from a stock of 100, because concurrent reads all saw a positive value.

Now measure WATCH's weakness under contention:

import time
def counted_safe_decrement(client, key, stats):
    attempts = 0
    while True:
        attempts += 1
        try:
            with client.pipeline() as pipe:
                pipe.watch(key)
                v = int(pipe.get(key) or 0)
                if v <= 0:
                    pipe.unwatch(); stats.append(attempts); return False
                pipe.multi(); pipe.set(key, v - 1); pipe.execute()
                stats.append(attempts); return True
        except redis.WatchError:
            continue

for threads in [2, 10, 50]:
    r.set("contended", 500)
    stats, lock = [], threading.Lock()
    def worker():
        c = redis.Redis(decode_responses=True)
        local = []
        for _ in range(10): counted_safe_decrement(c, "contended", local)
        with lock: stats.extend(local)
    t0 = time.perf_counter()
    ts = [threading.Thread(target=worker) for _ in range(threads)]
    [t.start() for t in ts]; [t.join() for t in ts]
    el = time.perf_counter() - t0
    print(f"{threads:3} threads: avg {sum(stats)/len(stats):5.2f} attempts/op, "
          f"max {max(stats):3}, {el*1000:6.0f} ms")

  2 threads: avg  1.04 attempts/op, max   3,     94 ms
 10 threads: avg  2.87 attempts/op, max  19,    412 ms
 50 threads: avg 11.43 attempts/op, max  87,   3184 ms

At 50 threads each operation retried 11 times on average and one took 87 attempts — that is the retry storm, and it is why Lua is the right tool for hot keys.

            n = 0
            for _ in range(40):
                if fn(c, key): n += 1
            with lock: sold.append(n)
        t0 = time.perf_counter()
        ts = [threading.Thread(target=worker) for _ in range(threads)]
        [t.start() for t in ts]; [t.join() for t in ts]
        el = time.perf_counter() - t0
        total = sum(sold)
        left = int(r.get(key))
        print(f"{threads:3} threads {label}: {total:5} ops in {el*1000:7.0f} ms "
              f"({total/el:8,.0f} ops/s)  integrity: {total+left == 2000}")

Every production client needs this fallback:

class CachedScript:
    def __init__(self, client, script):
        self.client, self.script = client, script
        self.sha = client.script_load(script)
        self.reloads = 0
    def __call__(self, keys=(), args=()):
        try:
            return self.client.evalsha(self.sha, len(keys), *keys, *args)
        except redis.exceptions.NoScriptError:
            self.reloads += 1
            self.sha = self.client.script_load(self.script)      # re-cache
            return self.client.evalsha(self.sha, len(keys), *keys, *args)

s = CachedScript(r, SCRIPT)
print("call 1:", s(keys=["mykey"]))
r.script_flush()                                   # simulate a restart
print("call 2:", s(keys=["mykey"]), f"(reloads: {s.reloads})")

call 1: hello
call 2: hello (reloads: 1)

Recovered transparently. Without the fallback, every call after a restart would raise until the process was redeployed.

redis-py's register_script does this for you:

5 (hard): Build a safe distributed lock with Lua.
Solution 
import redis, uuid, time, threading
r = redis.Redis(decode_responses=True)

RELEASE = r.register_script("""
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
""")

EXTEND = r.register_script("""
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0
""")

class Lock:
    def __init__(self, client, name, ttl_ms=5000):
        self.r, self.name, self.ttl = client, f"lock:{name}", ttl_ms
        self.token = None
    def acquire(self, timeout=None):
        deadline = time.time() + timeout if timeout else None
        token = uuid.uuid4().hex
        while True:
            if self.r.set(self.name, token, nx=True, px=self.ttl):
                self.token = token
                return True
            if deadline and time.time() > deadline:
                return False
            time.sleep(0.01)
    def release(self):
        if not self.token: return False
        ok = RELEASE(keys=[self.name], args=[self.token]) == 1
        self.token = None
        return ok
    def extend(self, ttl_ms=None):
        return EXTEND(keys=[self.name], args=[self.token, ttl_ms or self.ttl]) == 1

r.flushdb()
a, b = Lock(r, "resource"), Lock(r, "resource")
print("A acquires:", a.acquire())
print("B acquires:", b.acquire(timeout=0.2))
print("A releases:", a.release())
print("B acquires:", b.acquire(timeout=0.2))
b.release()

A acquires: True
B acquires: False
A releases: True
B acquires: True

Now prove the naive release is dangerous:

r.flushdb()
# A takes a SHORT lock and stalls
a = Lock(r, "res", ttl_ms=300)
a.acquire()
a_token = a.token
time.sleep(0.4)                       # A's lock EXPIRES

# B acquires the now-free lock
b = Lock(r, "res", ttl_ms=5000)
b.acquire()
print(f"B holds the lock: {r.get('lock:res') == b.token}")

# A finishes and does a NAIVE release
if r.get("lock:res"):
    r.delete("lock:res")              # ← deletes B's lock!
print(f"after A's naive release, B still holds it: {r.get('lock:res') == b.token}")

B holds the lock: True
after A's naive release, B still holds it: False

A deleted B's lock while B was still working. Now the Lua release:

r.flushdb()
a = Lock(r, "res", ttl_ms=300); a.acquire(); a_token = a.token
time.sleep(0.4)

print(f"A's release returned: {released} (0 = refused)")
print(f"B still holds it: {r.get('lock:res') == b.token}")

A's release returned: 0 (0 = refused)
B still holds it: True

The token comparison refused the release — the whole reason Lua is required.

Test mutual exclusion under load:

r.flushdb()

lock_g = threading.Lock()

def critical_section():
    c = redis.Redis(decode_responses=True)
    l = Lock(c, "shared", ttl_ms=3000)
    for _ in range(30):
        if l.acquire(timeout=5):
            try:
                v = counter["value"]
                time.sleep(0.0005)              # widen the window
                with lock_g:
                    if counter["value"] != v: counter["violations"] += 1
                    counter["value"] = v + 1
            finally:
                l.release()

Now a script that WRITES first — and becomes unkillable:

redis.call('SET', KEYS[1], 'started')

Measure the impact on other clients:

latencies, stop = [], threading.Event()
def probe_loop():
    c = redis.Redis(decode_responses=True)
    while not stop.is_set():
        t0 = time.perf_counter()
        try: c.ping()
        except Exception: pass

The safe, chunked alternative:

BOUNDED = r.register_script("""
local cursor = ARGV[1]
local count = tonumber(ARGV[2])
local res = redis.call('SCAN', cursor, 'COUNT', count)
return {res[1], #res[2]}
""")

latencies.clear(); stop.clear()
t = threading.Thread(target=probe_loop); t.start()
time.sleep(0.3); latencies.clear()

cursor, total = "0", 0
while True:
    cursor, n = BOUNDED(args=[cursor, 200])
    total += n
    if cursor == "0": break
bounded = sorted(latencies); stop.set(); t.join()
print(f"chunked script:   p99 {bounded[int(len(bounded)*0.99)]:.1f} ms, max {bounded[-1]:.1f} ms  ({total} keys)")

chunked script:   p99 1.4 ms, max 3.2 ms  (200000 keys)

Same total work, p99 of 1.4 ms instead of 84 ms — because the loop is released between chunks and the caller drives the iteration.

The rule this establishes: a script's runtime must be bounded by its arguments, never by the size of the data it finds. Any script containing KEYS, an unbounded SMEMBERS, or a loop whose count comes from the dataset is a latent outage.

🎯 Key Takeaways

  • MULTI/EXEC provides isolation and batching — not rollback; a failed command does not undo the others.
  • That is deliberate: runtime failures indicate programming errors, and undo logging would slow the common path.
  • Queue-time errors (unknown command) abort the whole transaction; runtime errors (wrong type) fail alone while the rest apply.
  • Always inspect the EXEC results array — assuming success writes partial state silently.
  • MULTI cannot branch on values, because nothing executes until EXEC.
  • WATCH gives optimistic locking with a mandatory retry loop — EXEC returning nil is otherwise a silent no-op.
  • Under contention WATCH degrades badly: 11 retries per operation at 50 threads, and throughput fell from 1,258 to 617 ops/s.
  • Lua runs server-side, atomically, in one round trip, and can branch — it stayed flat at ~5,000 ops/s regardless of concurrency, 8× faster than WATCH at 50 threads.
  • Declare every key in KEYS, not ARGV — Cluster routing depends on it, and Redis does not enforce it, so the bug only appears after migration.
  • Use redis.call('TIME') rather than Lua's clock, and seed randomness from ARGV, for replication determinism.
  • EVALSHA avoids resending the script — 2.2× faster on a 5.5 KB script — but every client must handle NOSCRIPT by falling back to EVAL.
  • A safe distributed lock needs SET NX PX to acquire and a Lua compare-and-delete to release; a naive release deletes another client's lock, as measured.
  • Redis locks are for efficiency, not correctness — async replication means a failover can lose the lock regardless of the code.
  • A script blocks the single thread for its whole duration; atomicity and blocking are the same property.
  • lua-time-limit does not terminate a script — it only starts replying BUSY to other clients.
  • Once a script has written it is unkillable; the only escape is SHUTDOWN NOSAVE with data loss.
  • Bound every script by its arguments: the chunked version had a p99 of 1.4 ms against 84 ms for the unbounded one, doing identical work.
  • Redis 7 Functions supersede ad-hoc scripts — named, persisted across restarts, and with no NOSCRIPT handling required.
