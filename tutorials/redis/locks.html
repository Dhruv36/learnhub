Distributed Locks Durability & Distribution

What you'll master: the four requirements a correct Redis lock must satisfy, and the specific bug that appears when each one is missing — including the release that deletes someone else's lock, which is the most common distributed-lock bug in production; why a lock TTL is a bet on your own worst-case execution time and what happens when a GC pause makes you lose that bet; fencing tokens, the only mechanism that makes a lock safe against pauses, and why they require cooperation from the resource you are protecting; the Redlock argument between Martillo and Kleppmann, which is a standard senior interview question, and what the defensible position actually is; and the framing that matters most — Redis locks are for efficiency, not correctness, and knowing which one you need decides the whole design. Prerequisites: Transactions & Lua Scripting, Replication & Failover.

Part 1 — The Four Requirements

A working distributed lock needs four things. Every one of them corresponds to a real outage when it is missing.

1. Mutual exclusion    — at most one holder at a time
2. Deadlock freedom    — the lock is released even if the holder dies
3. Ownership           — only the holder may release it
4. Atomicity           — acquire and release cannot be interrupted mid-operation

The naive version fails three of them:

SETNX lock:resource 1          # ❌ no TTL: holder dies → locked forever
EXPIRE lock:resource 10        # ❌ separate command: crash between = no TTL
...
DEL lock:resource              # ❌ no ownership check: deletes ANYONE's lock

The correct primitive is one command:

SET lock:resource <random-token> NX PX 10000
    │              │              │  └── TTL: deadlock freedom
    │              │              └───── only if absent: mutual exclusion
    │              └──────────────────── unique token: ownership
    └─────────────────────────────────── atomic: acquire is one operation
🔑 The release is the half everyone gets wrong. A plain DEL deletes whatever lock is currently there — and if your lock already expired because your work overran, that is someone else's lock. Checking the value from the client first does not fix it: the value can change between the GET and the DEL. Release must be a Lua script, so compare and delete happen as one atomic operation.

RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
  end
  return 0
""")

def acquire(name, ttl_ms=10000):
    token = secrets.token_hex(16)
    return token if r.set(f"lock:{name}", token, nx=True, px=ttl_ms) else None

def release(name, token):
    return RELEASE(keys=[f"lock:{name}"], args=[token]) == 1
Missing pieceFailure it produces
No TTLA crashed holder locks the resource permanently
Separate SETNX + EXPIREA crash between them leaves a lock with no expiry
No unique tokenAny process can release any lock
Plain DEL to releaseA slow holder deletes the next holder's lock
Client-side check-then-deleteSame bug — the value changes in the gap

Part 2 — The TTL Is a Bet You Can Lose

The TTL is what prevents deadlock, and it is also the source of the deepest problem with distributed locks: it is a guess about your own worst-case execution time.

TTL too short → the lock expires while you are still working
                → another process acquires it
                → TWO PROCESSES IN THE CRITICAL SECTION

TTL too long  → a crashed holder blocks everyone for the full TTL
🔑 No TTL value is safe, because the holder can be paused for arbitrarily long between any two instructions. A stop-the-world GC pause, a hypervisor stealing the vCPU, an overloaded host, a page fault on swapped memory — any of these can suspend a process for seconds. The holder does not know it was paused; it wakes and continues, believing it still owns a lock that expired while it was frozen. This is why "make the TTL generous" is a mitigation and never a fix.

Client A: acquires lock, TTL 10s
Client A: ... GC pause, 15 seconds ...
                          (lock expires at t=10)
Client B: acquires the lock at t=10  ✅ legitimately
Client A: wakes at t=15, believes it holds the lock, writes to the resource
          → both A and B are in the critical section. No error anywhere.

The lock extension (watchdog) pattern reduces the exposure by renewing the TTL from a background thread while the work runs:

EXTEND = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ARGV[2])
  end
  return 0
""")

def watchdog(name, token, ttl_ms, stop):
    while not stop.wait(ttl_ms / 3000):          # renew at 1/3 of the TTL
        if not EXTEND(keys=[f"lock:{name}"], args=[token, ttl_ms]):
            break                                # we no longer hold it — stop working

Note what the failed extension means: it is the only signal the holder gets that it lost the lock, and correct code must abort the work at that point rather than continue. A watchdog that renews but never reports failure hides the problem instead of managing it.

It still does not solve the pause problem — a GC pause freezes the watchdog thread too. The renewal only helps when the work is legitimately slow, not when the whole process is suspended.

Part 3 — Fencing Tokens: The Only Real Fix

If the lock cannot guarantee exclusion, the resource must reject stale writers. That is what a fencing token does: a monotonically increasing number issued with each lock grant, which the resource checks and refuses to go backwards on.

Client A: acquires lock, gets token 33
Client A: ... paused ...
Client B: acquires lock, gets token 34
Client B: writes with token 34   → storage records last_token = 34  ✅
Client A: wakes, writes with token 33
          → storage sees 33 < 34  →  REJECTED  ✅

FENCE = r.register_script("""
  if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
    return redis.call('INCR', KEYS[2])          -- monotonic token
  end
  return nil
""")

token_id = FENCE(keys=[f"lock:{name}", f"fence:{name}"], args=[my_token, ttl_ms])
🔑 Fencing tokens move the safety guarantee out of the lock and into the resource, which is the only place it can actually live. The catch is that the protected resource must support a conditional write — a database with a WHERE last_token < :token clause, an object store with compare-and-set, a filesystem with versioned writes. If the resource cannot check the token, fencing is impossible, and no lock implementation can make the operation safe. This is the point Kleppmann's critique turns on, and it is what an interviewer is listening for.

ResourceFencing possible?How
SQL database✅ YesUPDATE … WHERE last_token < :token
DynamoDB / Cosmos✅ YesConditional write on the token attribute
S3 / object store⚠️ PartlyConditional put, or version checks
Sending an email❌ NoNothing to check — make it idempotent instead
Calling a third-party API⚠️ Only if it has an idempotency keyIdempotency key = the token

Where fencing is impossible, the answer is not a better lock — it is making the operation idempotent, so a duplicate execution is harmless rather than prevented.

Part 4 — Redlock, and the Argument About It

A single-instance lock has an obvious weakness: replication is asynchronous, so if the primary fails after granting a lock but before replicating it, the promoted replica has no record and grants the same lock to someone else. Redlock is the algorithm proposed to address this by using N independent Redis primaries.

Redlock, with N = 5 independent primaries (NOT replicas of each other):

1. Record the start time
2. Try to acquire on all 5, with a small per-node timeout
3. Success requires: a MAJORITY (3 of 5) acquired
                     AND elapsed time < TTL
4. Effective validity = TTL − elapsed − clock drift allowance
5. On failure: release on ALL nodes, including ones that may have succeeded

Martin Kleppmann's critique (2016) is the standard reference, and its argument is not about implementation details:

ObjectionThe substance
Timing assumptionsRedlock's safety depends on bounded clock drift, bounded network delay, and bounded pauses — none of which hold in an asynchronous system
GC pausesA pause after acquisition breaks exclusion regardless of how many nodes agreed
Clock jumpsNTP steps or a VM snapshot restore can expire a lock early on some nodes
No fencing tokensRedlock provides no monotonic token, so the resource cannot reject a stale writer
Wrong tool for correctnessIf correctness matters, use a consensus system (ZooKeeper, etcd) that provides fencing

Antirez's response was that Redlock targets a different problem: it is designed for efficiency-style locking where occasional double execution is tolerable, the timing assumptions are reasonable on well-managed infrastructure, and demanding consensus for every mutual-exclusion need is disproportionate.

🔑 The defensible position in an interview is not picking a side — it is the distinction underneath the argument. Ask what the lock is for. If double execution merely wastes work (a duplicate cache rebuild, a report generated twice), a single-instance Redis lock is fine and Redlock is usually unnecessary complexity. If double execution is incorrect (double-charging, corrupting a file), then no Redis lock is sufficient, and the answer is fencing tokens with a resource that enforces them, or a consensus system, or making the operation idempotent so exclusion stops being required.

Redlock's practical costs are worth naming too: five independent Redis deployments to operate, N round trips per acquisition, and a validity window that shrinks with network latency — under slow conditions the effective lock time can approach zero, and the algorithm's own correctness argument depends on clock drift you cannot measure from inside it.

Part 5 — Efficiency Locks vs Correctness Locks

This distinction decides the entire design, and stating it early is what separates a good answer from a recitation of SET NX PX.

Efficiency lockCorrectness lock
PurposeAvoid duplicate workPrevent incorrect state
Cost of double executionWasted CPU, an extra queryCorruption, double charge, data loss
ExamplesCache rebuild, cron dedupe, report generationPayments, inventory decrement, file writes
Redis SET NX PX sufficient?✅ Yes❌ No
What you actually needNothing moreFencing tokens, consensus, or idempotency

Most locks in real systems are efficiency locks, and treating them as correctness locks produces elaborate machinery that protects against something whose cost was one duplicated cache computation. Conversely, using an efficiency lock where correctness is required produces a system that works in testing and double-charges a customer during a GC pause six months later.

Before reaching for a distributed lock at all, check whether the problem dissolves:

Atomic operation instead of a lock:
  INCRBY balance -100                      ← no lock needed at all
  SET key val NX                           ← "only one winner" without locking
  Lua script                               ← read-decide-write, atomically

Database-level:
  SELECT … FOR UPDATE                      ← the DB already provides locking
  UPDATE … WHERE version = :v              ← optimistic concurrency
  UNIQUE constraint                        ← makes duplicates impossible

Design-level:
  Idempotent operations                    ← duplicates become harmless
  Partition work by key                    ← one owner per key, no contention

A single-node Redis operation is already atomic, so anything expressible as one command or one Lua script does not need a lock. The lock is for coordinating work that happens outside Redis.

Part 6 — Production Patterns

Use a maintained library rather than writing this yourself. The failure modes are subtle and the correct implementation is well understood:

# redis-py (built in, single-instance, correct release + optional extension)
lock = r.lock("resource", timeout=10, blocking_timeout=5, thread_local=True)
if lock.acquire():
    try:
        do_work()
    finally:
        try:
            lock.release()
        except redis.exceptions.LockNotOwnedError:
            log.error("lock expired during work — the work may have overlapped")

LockNotOwnedError is not an inconvenience to swallow. It means the lock expired while the work was running, so another process may have entered the critical section — it is the one moment the system tells you your TTL assumption was wrong, and it belongs in an alert.

ConcernPractice
Acquisition failureBounded retries with jittered backoff; never spin forever
Work exceeding the TTLWatchdog extension; abort when extension fails
Lock granularityPer resource ID, never one global lock
ObservabilityMetrics for acquire success/failure, hold time, expiry-during-work
Redis unavailableDecide fail-open or fail-closed deliberately, as with rate limiting
ClusterThe lock key is one key in one slot — no special handling, but Redlock needs independent instances

Lock granularity is the most common performance mistake. A single lock:orders serialises every order in the system; lock:order:{id} serialises only the ones that genuinely conflict. The measurement in Exercise 6 shows the difference is not marginal.

❌ Releasing a lock with DEL, and treating the TTL as a guarantee. The code acquires with SET NX PX, does its work, and calls DEL lock:resource in a finally block. It looks correct and passes every test, because in testing the work always finishes well inside the TTL. In production the work occasionally overruns — a slow query, a GC pause, a noisy neighbour — the lock expires, another process acquires it, and the original holder's DEL then deletes that process's lock. Now a third process can acquire while the second is still working, and the mutual exclusion the whole design rested on is gone. Nothing errors, and the corruption appears as an unreproducible bug weeks later.

✅ Make the lock four-part correct, then decide whether a lock is even the right tool. Acquire with SET key <unique-token> NX PX ttl in one command; release with a Lua compare-and-delete so only the owner can remove it; extend from a watchdog and abort the work when the extension fails, because that is the system telling you the lock was lost. Then ask what the lock is protecting: if double execution merely wastes work, this is sufficient and Redlock is unnecessary; if double execution would be incorrect, add fencing tokens that the resource enforces, use a consensus system, or make the operation idempotent so exclusion is no longer required.

Interview Questions

Beginner: Implement a distributed lock in Redis. What are the requirements?

Four requirements: mutual exclusion, deadlock freedom (release even if the holder dies), ownership (only the holder may release), and atomicity for both operations.

Acquire is a single command that satisfies three of them at once:

SET lock:resource <random-token> NX PX 10000
    NX  → only if absent        (mutual exclusion)
    PX  → expiry in ms          (deadlock freedom)
    token → unique per acquire  (ownership)

Release must be a Lua script, because compare-then-delete is not atomic from the client:

if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0

Why not a plain DEL? If your work overran and the lock already expired, another process holds it — and your DEL deletes their lock, letting a third process in while the second still believes it has exclusivity. Reading the value from the client first does not help: it can change in the gap before the delete.

Why not SETNX then EXPIRE? A crash between the two leaves a lock with no TTL, which never releases — the resource is locked permanently.

Use the implementation in your client library (redis-py's r.lock(), Redisson in Java) rather than writing it by hand; the correct version is well understood and the failure modes are subtle.

Beginner: Why must the lock have a TTL, and what does the TTL break?

The TTL provides deadlock freedom. Without it, a holder that crashes — process killed, host lost, network gone — leaves the lock set forever, and the resource is unusable until somebody deletes the key manually. There is no other mechanism to recover, because Redis does not know the holder died.

What the TTL breaks is mutual exclusion. It is a bet on your own worst-case execution time, and losing the bet puts two processes in the critical section:

A: acquires, TTL 10s
A: pauses (GC / vCPU steal / page fault) for 15s
   lock expires at t=10
B: acquires legitimately at t=10
A: resumes at t=15 believing it still holds the lock
   → A and B both in the critical section, no error anywhere

Tuning does not resolve it — it only chooses which failure you prefer. A short TTL expires under slow work; a long TTL makes a crash block everyone for longer.

Mitigations: a watchdog that extends the TTL while the work runs (and aborts the work when the extension fails, since that means the lock was lost), and keeping critical sections short and bounded.

The actual fix is fencing tokens — a monotonically increasing number the resource checks, so a stale holder's write is rejected even if it believes it holds the lock. That moves the safety guarantee to the resource, which is the only place it can be enforced.

Mid: What are fencing tokens and why does a Redis lock need them?

A fencing token is a monotonically increasing number issued with every lock grant. The holder passes it to the protected resource, and the resource rejects any write carrying a token lower than one it has already accepted.

A: acquires → token 33
A: pauses...
B: acquires → token 34
B: writes with 34   → resource records last_token = 34 ✅
A: wakes, writes with 33 → 33 < 34 → REJECTED ✅

Why it is necessary: no lock can prevent a holder from being paused after acquisition. The lock cannot detect the pause, and the holder does not know it happened. So exclusion cannot be guaranteed by the lock alone — the resource has to be able to tell a stale writer from a current one, and a monotonic token is what makes that possible.

if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
  return redis.call('INCR', KEYS[2])          -- the fencing token
end
return nil

The requirement people miss: the resource must enforce it. A token is useless unless the thing being protected performs a conditional write:

UPDATE resource SET data = :d, last_token = :t WHERE last_token < :t

Databases and conditional-write stores can do this. Sending an email cannot — there is nothing to check — and for those operations the answer is idempotency, making a duplicate harmless rather than preventing it.

Redis does not provide fencing tokens natively, which is the centre of Kleppmann's critique of Redlock: the algorithm establishes agreement about who holds a lock, but issues nothing the resource can use to reject a stale holder.

Mid: Explain Redlock and the criticism of it.

Redlock uses N independent Redis primaries (typically 5) that are not replicas of each other, to avoid the single-instance failure where a primary dies after granting a lock but before replicating it, and the promoted replica grants the same lock again.

1. Note the start time
2. Try SET NX PX on all N nodes, with a short per-node timeout
3. Acquired only if a MAJORITY succeeded AND elapsed < TTL
4. Validity = TTL − elapsed − clock-drift allowance
5. On failure, release on ALL nodes (including partial successes)

Kleppmann's critique (2016) argues Redlock's safety rests on timing assumptions that do not hold in asynchronous systems:

  • A GC pause after acquisition breaks exclusion no matter how many nodes agreed.
  • Clock jumps — NTP steps, VM snapshot restores — can expire a lock early on some nodes, and the algorithm's validity calculation depends on bounded drift.
  • Redlock provides no fencing token, so the resource cannot reject a stale writer.
  • If correctness matters, use a consensus system (ZooKeeper, etcd) that provides both consensus and fencing.

Antirez's response was that Redlock targets efficiency locking, where occasional double execution is acceptable, and that its timing assumptions are reasonable on well-managed infrastructure.

The position worth taking is the distinction rather than a side. Ask what the lock is for. If double execution wastes work — a duplicate cache rebuild, a report generated twice — a single-instance Redis lock is sufficient and Redlock is usually unnecessary operational complexity: five deployments, N round trips per acquire, and a validity window that shrinks with latency. If double execution would be incorrect, no Redis lock is sufficient, and the answer is fencing tokens the resource enforces, a consensus system, or making the operation idempotent so exclusion is not required at all.

Senior: Design coordination for a job scheduler where each job must run on exactly one worker.

First, challenge "exactly once", because it does not exist. A worker can acquire a lock, start the job, and die before finishing. Either it is retried (possible duplicate) or it is not (possible loss). The achievable goal is at-least-once execution with idempotent jobs, or at-most-once with the risk of a skipped run. Which one is right depends on the job, and the design should say so explicitly.

Preferred design — leases, not locks:

CLAIM = """
  if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
    return redis.call('INCR', KEYS[2])       -- fencing token
  end
  return nil
"""
# KEYS[1] = lease:job:{id}   KEYS[2] = fence:job:{id}

Per-job keys, never a global lock, so unrelated jobs never contend. A watchdog renews the lease at a third of its duration while the job runs, and aborts the job if renewal fails — that is the only signal the worker gets that it lost the lease.

Make the jobs idempotent, which is what actually provides safety. Record completion keyed by (job_id, scheduled_time) with a database unique constraint, so a duplicate execution is rejected by the storage layer rather than prevented by the lock. Where the job writes to a resource that supports conditional writes, pass the fencing token:

UPDATE job_state SET status = 'done', token = :t
 WHERE job_id = :id AND token < :t

Handle the two failure modes explicitly. A worker that dies mid-job leaves a lease that expires, and another worker picks the job up — which is why idempotency matters more than the lock does. A worker that is merely slow keeps renewing, so the lease should be short (seconds) with renewal, rather than long and unrenewed.

Recovery and observability: a reaper that finds jobs whose lease expired without a completion record and re-queues them; metrics on lease acquisition failures, renewal failures, and job duration versus lease duration — because renewal failures are the leading indicator that lease durations are mis-set.

When I would not use Redis here: if a duplicate run is genuinely unacceptable and the job cannot be made idempotent — sending money, sending customer emails — then leadership should come from etcd or ZooKeeper, which provide consensus and fencing, or the scheduler should hand the work to a system with transactional semantics. Redis leases are the right tool when duplicates are survivable, which covers most scheduled work.

Senior: A lock-protected section occasionally runs twice. Walk through the causes.

Five causes, in the order I would check them.

1. Release by DEL without an ownership check. The most common, and the easiest to confirm by reading the release code. If the holder's work overran, its DEL removed the next holder's lock, admitting a third process. Fix: Lua compare-and-delete on a unique token.

2. The TTL expiring during the work. The lock lapses, another process acquires legitimately, and both are inside. Confirm by comparing job duration against the TTL, and by looking for LockNotOwnedError (or equivalent) at release — that exception is the system reporting exactly this. Fix: watchdog renewal, and abort the work when renewal fails.

3. A process pause. GC, vCPU steal, page faults on swap, or a suspended container. The holder is frozen past the TTL and wakes believing it still holds the lock. Correlate the incidents with GC logs and host metrics. No TTL fixes this — fencing tokens or idempotency do.

4. Failover. Redis replication is asynchronous, so a primary can grant a lock, die before replicating it, and the promoted replica grants it again. Check whether the incidents coincide with failovers. Redlock addresses this specific case; fencing addresses it more reliably.

5. Clock issues. An NTP step or a VM snapshot restore can expire keys earlier than expected on one node. Rarer, but it produces exactly this symptom.

How I would work it: read the release path first, since cause 1 is both most common and cheapest to verify; then instrument hold time against TTL and count renewal failures; then correlate the events with GC pauses and failovers.

And the framing to give the team: if double execution is merely wasteful, fix the release bug and move on. If it is incorrect, the lock was never the right guarantee — add fencing tokens the resource enforces, or make the operation idempotent so a duplicate is harmless. Locks reduce the probability of concurrent execution; only the resource can make it impossible.

import redis, threading, time, secrets

r = redis.Redis(decode_responses=True)
r.flushdb()

RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
  end
  return 0
""")

def acquire(name, ttl_ms=5000, retries=50):
    for _ in range(retries):
        token = secrets.token_hex(16)
        if r.set(f"lock:{name}", token, nx=True, px=ttl_ms):
            return token
        time.sleep(0.01)
    return None

def release(name, token):
    return RELEASE(keys=[f"lock:{name}"], args=[token]) == 1

ts = [threading.Thread(target=unsafe) for _ in range(10)]

for t in ts: t.join()

# --- protected ---

def safe():

2 (easy): Show the DEL-release bug deleting another holder's lock.
Solution 
import redis, threading, time, secrets

r = redis.Redis(decode_responses=True)
r.flushdb()

RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
  return 0
""")

events = []
def worker(name, work_time, release_mode, ttl_ms=1000):
    token = secrets.token_hex(8)
    t0 = time.time()
    while time.time() - t0 < 5:
        if r.set("lock:res", token, nx=True, px=ttl_ms):
            events.append((round(time.time()-T0, 2), name, "ACQUIRED"))
            time.sleep(work_time)                 # may exceed the TTL
            if release_mode == "del":
                deleted = r.delete("lock:res")    # ❌ no ownership check
            else:
                deleted = RELEASE(keys=["lock:res"], args=[token])
            events.append((round(time.time()-T0, 2), name,
                           f"RELEASED (deleted={deleted})"))
            return
        time.sleep(0.02)

for mode in ("del", "lua"):
    r.flushdb(); events.clear(); T0 = time.time()
    # A overruns its 1s TTL; B acquires after it expires
    a = threading.Thread(target=worker, args=("A", 2.0, mode))
    a.start(); time.sleep(1.3)                    # A's lock has expired
    b = threading.Thread(target=worker, args=("B", 2.0, mode))
    b.start(); a.join(); b.join()

    print(f"--- release with {mode.upper()} ---")
    for t, who, what in sorted(events):
        print(f"  t={t:5.2f}s  {who}: {what}")
    print()

  t= 1.31s  B: ACQUIRED
  t= 2.00s  A: RELEASED (deleted=1)     ← A deleted B's lock!
  t= 3.31s  B: RELEASED (deleted=0)     ← B's lock was already gone

--- release with LUA ---
  t= 0.00s  A: ACQUIRED
  t= 1.31s  B: ACQUIRED
  t= 2.00s  A: RELEASED (deleted=0)     ← refused: token mismatch
  t= 3.31s  B: RELEASED (deleted=1)     ← B released its own lock

With DEL, A deleted B's lock at t=2.00 while B was still working — so from that moment any third process could acquire and enter the critical section alongside B. The Lua release refused, because the stored token no longer matched A's.

3 (medium): Show a TTL expiring during work, and that a watchdog prevents it.
Solution 
import redis, threading, time, secrets

r = redis.Redis(decode_responses=True)

RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
  return 0
""")
EXTEND = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ARGV[2])
  end
  return 0
""")

def run(work_s, ttl_ms, use_watchdog):
    r.flushdb()
    concurrent, peak, results = {"n": 0}, {"v": 0}, []
    lock = threading.Lock()

    def worker(name):
        token = secrets.token_hex(8)
        if not r.set("lock:job", token, nx=True, px=ttl_ms):
            return
        stop = threading.Event()
        if use_watchdog:
            def wd():
                while not stop.wait(ttl_ms / 3000):
                    if not EXTEND(keys=["lock:job"], args=[token, ttl_ms]):
                        results.append((name, "LOST THE LOCK"))
                        return
            threading.Thread(target=wd, daemon=True).start()
        with lock:
            concurrent["n"] += 1
            peak["v"] = max(peak["v"], concurrent["n"])
        time.sleep(work_s)                       # the work
        with lock:
            concurrent["n"] -= 1
        stop.set()
        results.append((name, f"done, released={RELEASE(keys=['lock:job'], args=[token])}"))

    ts = []
    for i, delay in enumerate([0, 0.3, 0.6, 0.9, 1.2, 1.5]):
        def launch(n=f"w{i}", d=delay):
            time.sleep(d); worker(n)
        t = threading.Thread(target=launch); ts.append(t); t.start()
    for t in ts: t.join()
    return peak["v"], results

peak, res = run(work_s=2.0, ttl_ms=1000, use_watchdog=False)
print(f"work 2.0s, TTL 1.0s, NO watchdog → peak concurrent holders: {peak}")
for n, w in res: print(f"   {n}: {w}")

print()
peak, res = run(work_s=2.0, ttl_ms=1000, use_watchdog=True)
print(f"work 2.0s, TTL 1.0s, WITH watchdog → peak concurrent holders: {peak}")
for n, w in res: print(f"   {n}: {w}")

work 2.0s, TTL 1.0s, NO watchdog → peak concurrent holders: 3
   w0: done, released=0
   w3: done, released=0
   w5: done, released=1

work 2.0s, TTL 1.0s, WITH watchdog → peak concurrent holders: 1
   w0: done, released=1

Three workers were in the critical section simultaneously without a watchdog — the lock expired every second while the work took two, so a new worker acquired legitimately each time. The released=0 results show each earlier holder's release being correctly refused, which is the Lua guard doing its job even as exclusion failed.

With the watchdog renewing at a third of the TTL, exactly one worker held the lock for the full duration.

4 (medium): Implement fencing tokens and show the resource rejecting a stale writer.
Solution 
import redis, threading, time, secrets

r = redis.Redis(decode_responses=True)
r.flushdb()

FENCE = r.register_script("""
  if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
    return redis.call('INCR', KEYS[2])
  end
  return nil
""")

class Resource:
    """Storage that enforces fencing — like UPDATE ... WHERE last_token < :t"""
    def __init__(self):
        self.data, self.last_token = None, 0
        self.rejected, self.accepted = [], []
        self.lock = threading.Lock()
    def write(self, value, token):
        with self.lock:
            if token <= self.last_token:
                self.rejected.append((value, token))
                return False
            self.data, self.last_token = value, token
            self.accepted.append((value, token))
            return True

def acquire_fenced(name, ttl_ms=1000):
    tok = secrets.token_hex(8)
    fence = FENCE(keys=[f"lock:{name}", f"fence:{name}"], args=[tok, ttl_ms])
    return (tok, fence) if fence else (None, None)

res = Resource()

# A acquires, then pauses past its TTL
tok_a, fence_a = acquire_fenced("res", ttl_ms=500)
print(f"A acquired with fencing token {fence_a}")
time.sleep(0.7)                                    # A's lock expires

tok_b, fence_b = acquire_fenced("res", ttl_ms=5000)
print(f"B acquired with fencing token {fence_b}")

print(f"B writes with token {fence_b}: {res.write('from-B', fence_b)}")
print(f"A wakes and writes token {fence_a}: {res.write('from-A', fence_a)}  ← STALE")
print(f"\nresource holds: {res.data!r} (last_token={res.last_token})")
print(f"rejected writes: {res.rejected}")

A acquired with fencing token 1
B acquired with fencing token 2
B writes with token 2: True
A wakes and writes token 1: False  ← STALE

resource holds: 'from-B' (last_token=2)
rejected writes: [('from-A', 1)]

A believed it held the lock and its write was rejected anyway — the resource, not the lock, enforced correctness. That is the entire point of fencing.

Compare with the same scenario and no fencing:

class UnfencedResource:
    def __init__(self): self.data = None
    def write(self, value, token=None):
        self.data = value; return True

u = UnfencedResource()
tok_a, _ = acquire_fenced("res2", ttl_ms=500)

tok_b, _ = acquire_fenced("res2", ttl_ms=5000)
u.write("from-B"); u.write("from-A")            # A's stale write lands last
print(f"unfenced resource holds: {u.data!r}  ← the STALE writer won")

Under real concurrency, with many workers:

    tok, fence = acquire_fenced("shared", ttl_ms=300)

Every accepted token is larger than the last, and three stale writers were rejected — despite each of them having legitimately held the lock at some point. No lock configuration produces that guarantee; only the resource can.

5 (hard): Implement Redlock and measure what it costs versus a single-instance lock.
Solution 
import redis, subprocess, time, os, secrets, threading

PORTS = [7100, 7101, 7102, 7103, 7104]
for p in PORTS:
    d = f"/tmp/redlock-{p}"
    os.makedirs(d, exist_ok=True)
    subprocess.run(["redis-server", "--port", str(p), "--daemonize", "yes",
                    "--dir", d, "--save", "", "--appendonly", "no"], check=True)
time.sleep(1.5)

nodes = [redis.Redis(port=p, decode_responses=True) for p in PORTS]
RELEASE_SRC = """
  if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
  return 0
"""
releases = [n.register_script(RELEASE_SRC) for n in nodes]

CLOCK_DRIFT = 0.01          # 1% allowance

def redlock_acquire(name, ttl_ms=1000):
    token = secrets.token_hex(16)
    quorum = len(nodes) // 2 + 1
    start = time.perf_counter()
    acquired = []
    for i, n in enumerate(nodes):
        try:
            if n.set(f"lock:{name}", token, nx=True, px=ttl_ms):
                acquired.append(i)
        except redis.RedisError:
            pass
    elapsed_ms = (time.perf_counter() - start) * 1000
    validity = ttl_ms - elapsed_ms - (ttl_ms * CLOCK_DRIFT)

    if len(acquired) >= quorum and validity > 0:
        return token, validity, len(acquired)
    for i in acquired:                          # release everywhere on failure
        releases[i](keys=[f"lock:{name}"], args=[token])
    return None, 0, len(acquired)

def redlock_release(name, token):
    for i, _ in enumerate(nodes):
        try: releases[i](keys=[f"lock:{name}"], args=[token])
        except redis.RedisError: pass

token, validity, got = redlock_acquire("res", 2000)
print(f"acquired on {got}/{len(nodes)} nodes, validity {validity:.1f} ms of 2000")

t2, v2, got2 = redlock_acquire("res", 2000)
print(f"second attempt while held: acquired={t2 is not None}, nodes={got2}")
redlock_release("res", token)

acquired on 5/5 nodes, validity 1978.4 ms of 2000
second attempt while held: acquired=False, nodes=0

def bench(fn, n=500):
    t0 = time.perf_counter()
    for i in range(n): fn(i)
    return (time.perf_counter() - t0) / n * 1000

def single_cycle(i):
    tok = secrets.token_hex(16)
    if single.set(f"lock:s{i}", tok, nx=True, px=1000):
        single_release(keys=[f"lock:s{i}"], args=[tok])

def redlock_cycle(i):
    tok, val, got = redlock_acquire(f"r{i}", 1000)
    if tok: redlock_release(f"r{i}", tok)

ms_single = bench(single_cycle)
ms_redlock = bench(redlock_cycle)
print(f"single instance: {ms_single:.3f} ms/lock-cycle")
print(f"redlock (5)    : {ms_redlock:.3f} ms/lock-cycle  ({ms_redlock/ms_single:.1f}×)")

redlock (5)    : 0.487 ms/lock-cycle  (4.5×)

4.5× the latency on loopback, where network cost is nearly zero — across real hosts the multiplier is larger, because acquisition is N sequential round trips.

Show the validity window shrinking under latency, which is Redlock's built-in safety check:

def redlock_with_delay(delay_ms, ttl_ms=200):
    token = secrets.token_hex(16)
    start = time.perf_counter()
    acquired = []
    for i, n in enumerate(nodes):
        time.sleep(delay_ms / 1000)              # simulate slow nodes
        try:
            if n.set("lock:slow", token, nx=True, px=ttl_ms): acquired.append(i)
        except redis.RedisError: pass
    elapsed = (time.perf_counter() - start) * 1000
    validity = ttl_ms - elapsed - ttl_ms * CLOCK_DRIFT
    for i in acquired:
        releases[i](keys=["lock:slow"], args=[token])
    return elapsed, validity, len(acquired)

print(f"\n{'per-node delay':>15} {'elapsed':>9} {'validity':>10} {'usable?':>9}")
for d in (0, 10, 30, 45):
    el, val, got = redlock_with_delay(d)
    print(f"{d:13d}ms {el:8.1f}ms {val:9.1f}ms {'yes' if val > 0 else 'NO':>9}")

 per-node delay   elapsed   validity   usable?
            0ms      1.4ms    196.6ms       yes
           10ms     52.3ms    145.7ms       yes
           30ms    152.1ms     45.9ms       yes
           45ms    227.4ms    -49.4ms        NO

At 45 ms per node the lock is unusable before it is even granted — elapsed time exceeded the TTL, so the validity is negative and the algorithm must refuse. That is Redlock working correctly, and it is also why its usable window depends on network conditions you do not control.

What it still does not give you: no fencing token. A holder paused after acquiring on all five nodes is exactly as dangerous as one paused after a single-instance acquire — which is the core of Kleppmann's argument.

6 (hard): Measure lock granularity, and show that the right answer is often no lock at all.
Solution 
import redis, threading, time, secrets

r = redis.Redis(decode_responses=True)
RELEASE = r.register_script("""
  if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
  return 0
""")

def with_lock(key, fn, ttl_ms=5000, retries=200):
    for _ in range(retries):
        tok = secrets.token_hex(8)
        if r.set(key, tok, nx=True, px=ttl_ms):
            try: return fn()
            finally: RELEASE(keys=[key], args=[tok])
        time.sleep(0.002)
    raise TimeoutError("lock unavailable")

ACCOUNTS, OPS, THREADS = 20, 1200, 12

def run(mode):
    r.flushdb()
    for a in range(ACCOUNTS): r.set(f"bal:{a}", 1000)
    errors = []
    def worker(wid):
        for i in range(OPS // THREADS):
            acct = (wid * 7 + i) % ACCOUNTS
            try:
                if mode == "global":
                    with_lock("lock:global",
                              lambda: r.set(f"bal:{acct}",
                                            int(r.get(f"bal:{acct}")) + 1))
                elif mode == "per-key":
                    with_lock(f"lock:acct:{acct}",
                              lambda: r.set(f"bal:{acct}",
                                            int(r.get(f"bal:{acct}")) + 1))
                else:                              # no lock at all
                    r.incr(f"bal:{acct}")          # atomic by itself
            except Exception as e:
                errors.append(type(e).__name__)
    ts = [threading.Thread(target=worker, args=(w,)) for w in range(THREADS)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    dur = time.perf_counter() - t0
    total = sum(int(r.get(f"bal:{a}")) for a in range(ACCOUNTS))
    return dur, total, len(errors)

expected = ACCOUNTS * 1000 + OPS
print(f"{'strategy':>12} {'time':>8} {'ops/s':>9} {'total':>8} {'correct':>8}")
for mode in ("global", "per-key", "atomic"):
    dur, total, errs = run(mode)
    print(f"{mode:>12} {dur:7.2f}s {OPS/dur:9,.0f} {total:8,d} "
          f"{'yes' if total == expected else 'NO':>8}")

    strategy     time     ops/s    total  correct
      global     4.18s       287   21,200      yes
     per-key     0.71s     1,690   21,200      yes
      atomic     0.14s     8,571   21,200      yes

All three are correct; they differ by 30× in throughput. The global lock serialised every operation across 20 unrelated accounts. Per-key locking only serialised genuine conflicts — 5.9× faster. And INCR, which needs no lock at all because a single Redis command is already atomic, was 30× faster than the global lock.

That contrast is the lesson. INCR is exact with no lock because it is one atomic command; the same logic split into GET + SET lost 79% of its updates and does need coordination — from a lock, or better, from a Lua script that makes it one operation again.

Before adding a distributed lock, check whether the operation can be expressed atomically. Most contention in Redis-backed systems is coordinating work that Redis could have done in one command.

🎯 Key Takeaways

  • A correct lock needs four properties: mutual exclusion, deadlock freedom (TTL), ownership (unique token), and atomicity — SET key <token> NX PX ttl delivers three in one command.
  • Release must be a Lua compare-and-delete. A plain DEL was measured deleting another holder's lock mid-work; client-side check-then-delete has the same race.
  • SETNX + EXPIRE as separate commands leaves a permanent lock if the process dies between them.
  • The TTL is a bet on your worst-case execution time — with work at 2 s and a 1 s TTL, 3 workers were in the critical section at once.
  • A watchdog renewing at 1/3 of the TTL restored exclusion to exactly 1 holder — and a failed extension is the only signal you lost the lock, so the work must abort there.
  • No TTL is safe against process pauses: a GC pause freezes the watchdog too, and the holder wakes believing it still owns an expired lock.
  • Fencing tokens are the only real fix — a monotonic token the resource checks. Measured: a stale holder's write rejected while an unfenced resource let the stale writer win.
  • Fencing requires a resource that supports conditional writes (WHERE last_token < :t); where it does not — sending an email — the answer is idempotency, not a better lock.
  • Redlock uses N independent primaries and a majority, costing 4.5× the latency even on loopback, and its validity window went negative at 45 ms per-node latency.
  • Kleppmann's critique: Redlock's safety rests on bounded clocks, delays and pauses, and it provides no fencing token — so it does not make correctness locks safe.
  • The defensible interview position is the distinction, not a side: efficiency locks (duplicate work wasted) are fine on single-instance Redis; correctness locks (duplicate work is wrong) need fencing, consensus, or idempotency.
  • Lock granularity is not a micro-optimisation: a global lock ran at 287 ops/s versus 1,690 for per-key locks — 5.9× — for identical, equally correct results.
  • Often the right answer is no lock: INCR was exact and 30× faster than a global lock, because a single Redis command is already atomic.
  • The same logic as GET + SET lost 79% of its updates — that split is what actually needs coordination, and a Lua script fixes it without a lock.
  • Check for a lock-free alternative first: atomic commands, Lua, SELECT … FOR UPDATE, optimistic version checks, unique constraints, or partitioning work by key.
  • Use a maintained library rather than hand-rolling, and treat LockNotOwnedError as an alert — it means the critical section may have overlapped.
  • Bound acquisition retries with jittered backoff; unbounded spinning piles threads up exactly when the system is already contended.
  • Redis locks reduce the probability of concurrent execution; only the protected resource can make it impossible.
