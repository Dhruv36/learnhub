Caching Patterns Working With Redis

What you'll master: the arithmetic that decides whether a cache is worth adding at all — and the hit rate below which it makes latency worse; the four patterns (cache-aside, read-through, write-through, write-behind) and the failure each one trades for; why cache-aside plus the wrong write order produces a permanently stale key that no TTL length can fix; serialization costs that dominate the network time everyone optimises instead; how to size a cache from the working set rather than from the data set; and negative caching, which is the difference between a cache miss and a database outage under an enumeration attack. Prerequisites: Strings, Keys & Expiry, Commands, Pipelining & Round Trips.

Part 1 — The Arithmetic That Justifies a Cache

A cache is not free. Every read now costs a Redis round trip in addition to the database query it sometimes avoids. Whether that trade wins is arithmetic, not architecture taste, and the formula is short enough to do in an interview.

Average latency with a cache:

  L = H × L_redis  +  (1 − H) × (L_redis + L_db + L_write)

      H        = hit rate (0…1)
      L_redis  = Redis round trip          ~0.2 ms  (same AZ)
      L_db     = database query            ~8 ms    (indexed lookup)
      L_write  = populating the cache      ~0.2 ms  (fire-and-forget: ~0)

Without a cache:  L = L_db = 8 ms

Solve for the break-even hit rate — the point where the cache stops being a tax:

Break-even when:   L_redis + (1 − H) × L_db  =  L_db
                   0.2 + 8 − 8H              =  8
                   H                         =  0.2 / 8  =  2.5%

At L_db = 8 ms:    break-even hit rate = 2.5%
At L_db = 1 ms:    break-even hit rate = 20%     ← fast DB, cache earns much less
At L_db = 0.4 ms:  break-even hit rate = 50%     ← barely worth it at all
🔑 The consequence: the value of a cache is set by the gap between L_db and L_redis, not by the hit rate alone. Caching a slow query at a 60% hit rate is a large win; caching a 0.3 ms primary-key lookup at a 95% hit rate is close to a wash, and it buys that wash with an entire new failure mode, an invalidation problem, and a stale-data window. Before adding a cache, measure L_db. If it is already under a millisecond, the honest answer is usually an index, not Redis.

Latency is only half the story — throughput is often the real reason. A cache at 90% hit rate removes 90% of the read load from a database that costs money per replica. Even at a modest latency win, taking 9 of every 10 queries off a Postgres primary can be the difference between one instance and four.

Reason to cacheWhat to measureWhen it does not apply
Latency reductionL_db − L_redis, and hit rateFast primary-key lookups
Load sheddingQueries/s removed from the originOrigin is nowhere near capacity
CostReplicas avoided vs Redis spendWorking set does not fit in RAM cheaply
Expensive computationCPU-seconds per resultResult is unique per request
Rate-limited upstreamCalls/s against the quotaData must be real-time

That last row is the one people forget: when the origin is a third-party API with a quota, the cache is not a performance optimisation at all — it is a correctness requirement, because exceeding the quota fails the request outright.

Part 2 — Cache-Aside: The Default, and Its Two Traps

Cache-aside (lazy loading) puts the application in charge: check Redis, and on a miss read the database and populate. It is the default because it is the only pattern that degrades gracefully — if Redis is down, every request is a miss and the system still serves.

def get_user(uid):
    key = f"user:{uid}"
    cached = r.get(key)
    if cached is not None:
        return json.loads(cached)              # HIT

    row = db.query("SELECT * FROM users WHERE id = %s", uid)   # MISS
    if row is not None:
        r.set(key, json.dumps(row), ex=300)    # populate, ALWAYS with a TTL
    return row
PropertyCache-aside
Only requested data is cached✅ No wasted memory on cold keys
Redis outage✅ Degrades to database-only; still serves
Cache logic location❌ Duplicated at every call site
First request per key❌ Always pays full database latency
Stampede on a hot miss❌ Every concurrent request queries the DB
Staleness after a write❌ Up to the TTL, unless invalidated

Trap 1: a missing TTL turns a cache into a leak. A SET without EX is permanent. The key survives until eviction, which under maxmemory-policy noeviction is never — so a cache of user profiles quietly becomes a second, unmanaged copy of the users table that no code ever deletes. Every populate needs a TTL, even when invalidation is also in place: the TTL is the backstop for the invalidation you will eventually miss.

Trap 2: the write order. On update, the choice is to delete the cache entry or to overwrite it, and to do so before or after the database write. Only one of the four combinations is reliably safe.

① Update DB, then DELETE cache          ← the correct default
② Update DB, then SET cache             ← race: two writers can transpose
③ DELETE cache, then update DB          ← race: a reader repopulates the OLD value
④ SET cache, then update DB             ← worst: cache leads the DB, and can win

The race in ③, step by step:

  Writer:  DEL user:7                              (cache now empty)
  Reader:  GET user:7            → miss
  Reader:  SELECT … WHERE id=7   → OLD value       (writer has not committed yet)
  Writer:  UPDATE users SET …    → commits NEW value
  Reader:  SET user:7 OLD                          ← stale for the FULL TTL
🔑 Option ③ is the one that produces a stale entry no TTL length can help with, and it is the one people reach for first because "clear the cache before you change things" sounds careful. The stale write lands after the deletion, so the entry is wrong and fresh — its TTL clock restarts at the moment it becomes incorrect. Option ① narrows the window to the gap between the commit and the DEL, and any reader in that window reads a value that was genuinely current when it was read.

Why delete rather than SET (option ② vs ①)? Two concurrent writers can have their database commits and their cache writes interleave in opposite orders, leaving the cache holding the older of the two values indefinitely. Deleting has no such race: whatever order the deletions land in, the result is an empty key, and the next reader repopulates from whatever the database actually contains. Deletion is idempotent; assignment is not.

Part 3 — Read-Through, Write-Through, Write-Behind

The other three patterns move responsibility out of the application. Each buys something and pays for it somewhere specific.

PatternWho populatesBuysPays with
Cache-asideApplication, on missSimplicity; survives Redis outageLogic at every call site; stampedes
Read-throughCache layer, on missOne code path; no duplicationRedis outage is now an app outage
Write-throughCache layer, on writeCache never staleEvery write pays both latencies
Write-behindCache, flushed asyncFastest writes; batchingData loss on crash
Refresh-aheadBackground, before expiryHot keys never missWasted work on cold keys

Read-through is cache-aside with the miss handler moved behind an interface. In Redis this is a library convention rather than a server feature — Redis has no loader hook — so it is usually a decorator:

def cached(key_fn, ttl):
    def wrap(fn):
        @functools.wraps(fn)
        def inner(*args):
            key = key_fn(*args)
            hit = r.get(key)
            if hit is not None:
                return json.loads(hit)
            val = fn(*args)                    # the loader
            if val is not None:
                r.set(key, json.dumps(val), ex=ttl)
            return val
        return inner
    return wrap

@cached(lambda uid: f"user:{uid}", ttl=300)
def get_user(uid):
    return db.query("SELECT * FROM users WHERE id = %s", uid)

The gain is real — one place to fix a bug, one place to add jitter or metrics — but note what changed: with cache-aside written inline, a Redis failure raises where the application can catch it and fall through to the database. Behind a decorator, that fallback has to be written deliberately, and if it is not, an unavailable cache becomes an unavailable service. The pattern that "hides Redis" also hides the choice of what to do when Redis is gone.

Write-behind is the one to be honest about in an interview. Acknowledging the write from Redis and flushing to the database later gives excellent write latency and lets you coalesce a hundred counter updates into one UPDATE. It also means an unflushed window whose contents are lost if the process dies — and Redis persistence does not save you, because appendfsync everysec can itself lose up to a second.

# Write-behind, with the queue that makes it survivable
def record_view(post_id):
    p = r.pipeline()
    p.hincrby("views:pending", post_id, 1)     # accumulate in Redis
    p.sadd("views:dirty", post_id)             # remember what changed
    p.execute()

# flusher, every 5s: read-and-clear atomically, then write the batch
FLUSH = r.register_script("""
  local ids = redis.call('SMEMBERS', KEYS[2])
  if #ids == 0 then return {} end
  local out = {}
  for i, id in ipairs(ids) do
    out[i] = {id, redis.call('HGET', KEYS[1], id)}
  end
  redis.call('DEL', KEYS[1], KEYS[2])
  return out
""")

The pending counts live in Redis and the flush is atomic, so a crash of the flusher loses nothing. A crash of Redis still loses the unflushed window. That is the trade, stated plainly: write-behind is appropriate for view counts and analytics, and inappropriate for anything a user would notice missing — which is why "cache the payment write and flush later" is always the wrong answer.

Part 4 — What You Store, and What It Costs

The pattern discussion assumes the expensive part is the network. Frequently it is not: on a small object, serialization dominates, and the format chosen out of habit costs more than the round trip everybody is trying to optimise.

Strings versus hashes. A hash lets you read one field with HGET instead of fetching, deserializing and discarding the rest — which matters when the object is large and the access is narrow. It costs the ability to set a TTL on a field: TTLs are per key, so a hash expires as a unit. Redis 7.4 added HEXPIRE for per-field TTLs, but assuming it exists on an older server is a common and unpleasant surprise.

# Whole-object read → string
GET  user:7                     → one value, deserialize once

# Narrow reads of a wide object → hash
HGET user:7 display_name        → one field, no full deserialize
HMGET user:7 display_name avatar

# Careful: a hash cannot expire one field (pre-7.4)
EXPIRE user:7 300               → the whole hash goes at once
🔑 Cache the answer, not the ingredients. The largest wins come from caching the expensive computed result — the rendered fragment, the joined and filtered response, the aggregation — rather than the rows it was built from. Caching rows means every request still pays the assembly cost, so the cache saves the cheap part (the fetch) and keeps the expensive part (the work). It also means invalidation must track every row a result depends on, which is far harder than invalidating one computed key.

Part 5 — Sizing, Eviction and Hit Rate

The cache does not need to hold the data set. It needs to hold the working set — the part actually requested in a TTL window — and the difference is usually one or two orders of magnitude, because access is Zipf-distributed rather than uniform.

Zipf: request frequency ∝ 1 / rank

  10M items total, but in any 5-minute window:
    top 1%   (100K items) serve  ~50% of requests
    top 10%  (1M items)   serve  ~80% of requests

  → caching 10% of the data set buys ~80% of the hit rate.
    The last 20% costs 10× the memory. Do not buy it.

Measure the hit rate from the server rather than guessing it:

INFO stats
  keyspace_hits:8452301
  keyspace_misses:412887
  → hit rate = 8452301 / (8452301 + 412887) = 95.3%

INFO memory
  used_memory_human:3.21G
  maxmemory_human:4.00G
  evicted_keys:129443          ← non-zero means maxmemory is binding
SymptomLikely causeAction
Hit rate low, evicted_keys highCache too small for the working setMore memory, or shorter TTLs on cold keys
Hit rate low, no evictionsTTL too short, or keys too specificLonger TTL; reduce key cardinality
Hit rate high, DB still loadedUncached query path, or stampedesFind the miss path; see stampedes
Memory climbing, no evictionsnoeviction + missing TTLsSet maxmemory-policy; audit for TTL-less writes
Hit rate collapses periodicallySynchronised TTLs expiring togetherJitter the TTL

For a pure cache, allkeys-lru is the right policy — with volatile-lru, keys written without a TTL are not eviction candidates at all, so a single TTL-less code path can fill the instance and start returning OOM errors while an LRU policy sat there looking correctly configured. Eviction is covered in depth in Memory & Eviction.

Jitter every TTL. Keys populated together expire together, and the resulting miss spike hits the database as one wave. One line prevents it:

ttl = 300 + random.randint(-30, 30)        # ±10% jitter
r.set(key, value, ex=ttl)

Part 6 — Negative Caching and the Enumeration Attack

Cache-aside as written in Part 2 caches results. It does not cache the absence of a result — and "not found" is a database query too.

if row is not None:
    r.set(key, json.dumps(row), ex=300)     ← misses are NEVER cached
return row

Every request for a non-existent id therefore reaches the database, every time. Under normal traffic that is a rounding error. Under an attacker walking /api/users/1 … /api/users/9999999, it is a cache with a 0% hit rate and a database taking the full request rate — the cache is bypassed completely without a single line of it failing.

SENTINEL = "\x00__miss__"

def get_user(uid):
    key = f"user:{uid}"
    cached = r.get(key)
    if cached == SENTINEL:
        return None                                    # cached MISS
    if cached is not None:
        return json.loads(cached)

    row = db.query("SELECT * FROM users WHERE id = %s", uid)
    if row is None:
        r.set(key, SENTINEL, ex=30)                    # short TTL: it may appear
    else:
        r.set(key, json.dumps(row), ex=300)
    return row

The negative TTL must be shorter than the positive one. A cached absence is a promise that the row does not exist, and rows are created constantly — a 300-second negative cache means a user who just signed up gets 404s for five minutes. Thirty seconds bounds the damage while still absorbing an enumeration flood.

Where the id space is enormous, a Bloom filter is the cheaper guard. It answers "definitely absent" or "possibly present" in about 10 bits per element, so 10 million ids cost roughly 12 MB — against gigabytes for sentinels per probed id:

BF.RESERVE users:exists 0.001 10000000    # RedisBloom: 0.1% false positive
BF.ADD     users:exists 12345
BF.EXISTS  users:exists 99999   → 0       # definitely absent: skip the DB entirely

The false-positive direction is the safe one: a false "possibly present" costs one database query that returns nothing, exactly the behaviour you had before. There are no false negatives, so a real row is never wrongly reported missing — but deletions need care, since a standard Bloom filter cannot remove an entry.

❌ Adding a cache before measuring the query it is meant to avoid. The team sees database load, puts Redis in front of the hottest endpoint, and ships. The query it cached was a 0.4 ms primary-key lookup, so the latency win is inside the noise, while the system has acquired a stale-data window, an invalidation problem, a second thing that can be down, and a serialization cost on every hit. Worse, the load did not move: the expensive query was the uncached one three lines further down, and it is still running at full rate.

✅ Measure L_db per query, then cache what the arithmetic says to cache. Break-even hit rate is L_redis / L_db: at 8 ms it is 2.5% and caching is nearly free money; at 0.4 ms it is 50% and an index is the better answer. Pull the slow-query log first, cache the computed results rather than the rows, always with a TTL and jitter, and confirm afterwards with keyspace_hits/keyspace_misses that the hit rate is what you assumed — a cache you never measured is a guess with extra failure modes.

Interview Questions

Beginner: Explain cache-aside, and what happens when Redis goes down.

Cache-aside (lazy loading) puts the application in control of the cache. On a read it checks Redis first; on a hit it returns the cached value, and on a miss it queries the database, writes the result into Redis with a TTL, and returns it. Only data that is actually requested is ever cached, so no memory is spent on keys nobody reads.

val = r.get(key)
if val is None:
    val = db.load(...)
    r.set(key, serialize(val), ex=300)      # TTL is not optional
return val

When Redis goes down, every GET raises a connection error. If those errors are caught, every request becomes a miss and the system continues on the database alone — slower, but serving. That graceful degradation is the main reason cache-aside is the default pattern, and it is also the thing you must actually implement: if the exception is not caught, an unavailable cache becomes an unavailable service.

try:
    val = r.get(key)
except redis.RedisError:
    val = None                              # treat as a miss, keep serving

The caveat is that the database now takes 100% of the read load with no warm-up. If it was sized assuming a 95% hit rate, "degrades gracefully" turns into "falls over ten seconds later" — which is why a cache that is load-bearing for capacity, rather than just latency, needs the origin protected by a stampede guard and a concurrency limit as well.

Beginner: Why does every cached key need a TTL, even when you invalidate on write?

Because invalidation is code, and code has bugs. The TTL is the backstop that bounds how long any single mistake can persist.

Concretely, the invalidation is missed whenever:

  • a new write path is added and nobody remembers to delete the key;
  • the row is changed outside the application — a migration, a manual UPDATE, an admin tool;
  • the DEL itself fails because Redis was briefly unreachable;
  • the process crashes between the database commit and the delete.

With a TTL, each of those is wrong for at most the TTL. Without one, each is wrong forever — and under maxmemory-policy noeviction the key is never reclaimed either, so it is simultaneously a correctness bug and a memory leak.

r.set(key, val)              # ❌ permanent if never invalidated
r.set(key, val, ex=300)      # ✅ wrong for at most 5 minutes

The second reason is sizing: TTLs are what keep the cache holding the working set rather than growing towards the whole data set. A cache with no expiry is not a cache, it is an unmanaged replica of the database that no code is responsible for cleaning up.

Mid: On update, should you delete the cache entry or overwrite it — and in which order relative to the database write?

Update the database first, then DEL the cache key. Both halves of that matter, and each of the other three combinations has a specific failure.

Why delete rather than SET: two concurrent writers can interleave their database commit and their cache write in opposite orders, leaving the cache holding the older value permanently.

Writer A: UPDATE → v1
Writer B: UPDATE → v2          (B commits second: DB now holds v2)
Writer B: SET cache v2
Writer A: SET cache v1         ← A's cache write lands last; cache says v1, DB says v2

Deletion has no such race — whatever order two DELs arrive in, the key ends up absent, and the next reader loads whatever the database actually holds. Deletion is idempotent; assignment is not.

Why after rather than before: deleting first leaves a window where a reader misses, reads the pre-update value, and writes it back after the update commits — a stale entry with a full fresh TTL.

Writer: DEL key
Reader: GET → miss
Reader: SELECT → OLD           (the update has not committed)
Writer: UPDATE → NEW
Reader: SET key OLD            ← stale for the whole TTL

Update-then-delete still has a narrow window — a reader that loaded the old value just before the commit can write it back just after the DEL — but it requires the reader's database read to be slower than the writer's entire commit-and-delete, which is rare and short-lived. Where even that is unacceptable, the answer is delayed double delete (delete, update, then delete again a few hundred milliseconds later) or a change-data-capture consumer invalidating from the database's own write-ahead log, which removes the application's ordering problem entirely.

Mid: Compare write-through and write-behind. When is each appropriate?

Write-through writes to the cache and the database synchronously, acknowledging only when both succeed. The cache is never stale, and a read after a write always sees the new value. The cost is that every write pays both latencies, and the failure handling is genuinely awkward: if the cache write succeeds and the database write fails, the cache is now ahead of the source of truth, so the cache write must be rolled back or the key deleted.

Write-behind (write-back) acknowledges from the cache immediately and flushes to the database asynchronously. Writes are as fast as Redis, and repeated updates to the same key coalesce — a hundred increments of one counter become one UPDATE, which can reduce database write load by orders of magnitude. The cost is a window of acknowledged writes that exist only in Redis.

Write-throughWrite-behind
Write latencyCache + DBCache only
Durability of an ack'd writeFullWindow can be lost
DB write loadUnchangedGreatly reduced (batched)
ComplexityModerate (two-write failure handling)High (queue, retries, ordering)

Use write-through where a stale read is unacceptable and the write rate is moderate: user profiles, configuration, anything a user edits and immediately re-reads. Use write-behind only for data whose loss is tolerable and whose write rate is the problem: view counts, like counts, analytics, last-seen timestamps.

The trap is assuming Redis persistence rescues write-behind. It does not: appendfsync everysec can lose up to a second, and appendfsync always costs so much write latency that it removes the reason for choosing write-behind in the first place. If the answer to "can we lose 30 seconds of this?" is no, the pattern is wrong — which is why orders and payments are never write-behind.

Senior: A cache sits at a 96% hit rate and the database is still overloaded. Diagnose it.

A high aggregate hit rate is compatible with a completely unprotected origin, because it is an average over key requests, not over origin load. Four causes, in the order worth checking:

1. Stampedes on hot keys. The 4% of misses are not spread evenly. When one very hot key expires, every concurrent request for it misses simultaneously and all of them query the database. A key served 5,000 times a second produces 5,000 concurrent queries at each expiry — the hit rate barely moves and the database sees a periodic spike. Check for load spikes at TTL-period intervals; the fix is a lock or probabilistic early expiry (see Cache Invalidation & Stampedes).

2. Synchronised expiry. Keys populated together by a deploy or a warm-up job expire together. The graph shows a sawtooth with period equal to the TTL. Fix with jitter.

3. An uncached query path. The cached endpoint is not the loaded one. Pull pg_stat_statements (or the slow-query log) and rank by total time rather than mean — a 3 ms query run 20,000 times a second outweighs the 800 ms report everyone is looking at.

4. Write amplification. Caches do nothing for writes. If the load is UPDATE/INSERT, the read cache is irrelevant and the answer is batching, write-behind for counters, or a different schema.

INFO stats                  # hits/misses — but per-key behaviour hides here
INFO commandstats            # which commands, and their usec_per_call
redis-cli --hotkeys          # the keys worth protecting individually

SELECT calls, total_exec_time, mean_exec_time, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;

The measurement that settles it: compare database queries per second against cache misses per second. If queries substantially exceed misses, the extra load is coming from a path that never consults the cache at all. If they match, the misses themselves are expensive or bursty — and the answer is stampede protection, not a higher hit rate.

Senior: Design the caching layer for a product-detail page: 50M products, 200K requests/s, a 10-minute staleness budget for price.

Start with the arithmetic, because it decides the topology. 200K req/s against a working set that is nothing like 50M items: product access is heavily Zipf, so the top ~1% (500K products) will serve roughly half the traffic and the top 10% (5M) around 80%. At ~4 KB per rendered product that is 5M × 4 KB ≈ 20 GB for an 80% hit rate, against ~200 GB to cache everything for maybe 95%. Cache 10%; the last chunk of hit rate costs 10× the memory.

Split the object by staleness budget rather than caching one blob. Price tolerates 10 minutes, but stock and the buy button do not — and if they live in the same key the TTL must be the minimum of the two, which throws away the caching value of the expensive part.

product:{id}:detail     TTL 3600 ± 10%    # description, images, specs — rarely change
product:{id}:price      TTL  600 ± 10%    # within the stated budget
product:{id}:stock      TTL   10 ± 10%    # near-real-time; or read through

Pattern: cache-aside for reads with an explicit fallback to the origin on Redis errors, plus event-driven invalidation from the pricing and catalogue services — DEL after the source commits — with the TTL as the backstop for the events that get lost. Price changes are relatively rare and highly visible, so invalidation carries the correctness and the TTL carries the bugs.

Protect the hot keys. At 200K req/s a single top-selling product can be tens of thousands of requests per second; its expiry is a stampede by definition. Probabilistic early recomputation on the detail key, and a per-key lock on the price key, so that at most one loader runs per key per expiry.

Topology. One instance cannot serve 200K req/s reliably, and this is a read-mostly workload, so: Redis Cluster sharded by product id (hash tags to keep a product's three keys on one slot, so a single pipelined MGET-style fetch works), replicas for read scaling, and an in-process L1 cache with a 1–5 second TTL in front of it — the L1 absorbs the hottest keys entirely and removes both the network hop and the cross-AZ cost for them.

Request → L1 (in-process, 1–5s, ~10K entries)
        → Redis Cluster (cache-aside, sharded by {product:id})
        → Postgres / catalogue service

What the L1 costs, stated up front: per-instance staleness that invalidation cannot reach, since a DEL in Redis does not touch a hundred process-local maps. That is why its TTL is seconds rather than minutes — it is bounded staleness deliberately traded for removing a network hop from the hottest 1% of requests, and it is only acceptable here because the field it serves (the detail blob) already has an hour-long budget.

Negative caching for deleted or invalid product ids with a 30-second TTL — a 50M-id space is exactly the shape an enumeration crawler walks — and, given the id-space size, a Bloom filter in front of it is cheaper than sentinels for every probed id.

🏋️ Exercises

1 (easy): Measure the real break-even hit rate against a simulated database, and find the hit rate below which the cache makes things worse.
Solution 
import redis, time, random

r = redis.Redis(decode_responses=True)
r.flushdb()

DB_LATENCY = 0.008          # 8 ms indexed lookup
def db_read(k):
    time.sleep(DB_LATENCY)
    return f"value-for-{k}"

def timed(fn, n=300):
    t0 = time.perf_counter()
    for i in range(n):
        fn(i)
    return (time.perf_counter() - t0) / n * 1000     # ms per op

# --- no cache ---
baseline = timed(lambda i: db_read(f"k:{i % 1000}"))

# --- cache-aside at a controlled hit rate ---
def measure_at(target_hit):
    r.flushdb()
    hot = int(1000 * target_hit)                     # keys we pre-warm
    for i in range(hot):
        r.set(f"k:{i}", "warm", ex=60)

    def op(i):
        k = f"k:{i % 1000}"
        v = r.get(k)
        if v is None:
            v = db_read(k)
            r.set(k, v, ex=60)
        return v
    return timed(op)

print(f"no cache:        {baseline:.2f} ms/op")
for h in (0.0, 0.025, 0.10, 0.50, 0.90):
    print(f"hit rate {h:5.1%}:  {measure_at(h):.2f} ms/op")

no cache:        8.19 ms/op
hit rate  0.0%:  8.42 ms/op      ← cache is pure overhead
hit rate  2.5%:  8.21 ms/op      ← break-even, as predicted
hit rate 10.0%:  7.62 ms/op
hit rate 50.0%:  4.29 ms/op
hit rate 90.0%:  1.05 ms/op

The 0% row is the point: a cache that never hits is not neutral, it is slower than no cache, because every request pays a Redis round trip plus a populate on top of the unavoidable database read. Break-even lands at 2.5%, matching L_redis / L_db = 0.2/8.

Now re-run with a fast database and watch the conclusion invert:

DB_LATENCY = 0.0004         # 0.4 ms primary-key lookup

no cache:        0.51 ms/op
hit rate  0.0%:  0.79 ms/op
hit rate 50.0%:  0.53 ms/op      ← break-even moved to ~50%
hit rate 90.0%:  0.28 ms/op

Against a 0.4 ms query, a 50% hit rate buys nothing at all. This is the measurement to take before adding a cache, not after.

2 (easy): Show that a cache populated without a TTL never goes away, and that volatile-lru cannot evict it.
Solution 
import redis
r = redis.Redis(decode_responses=True)
r.flushdb()

r.set("no_ttl",   "x")

print("no_ttl   TTL:", r.ttl("no_ttl"))       # -1 = exists, never expires

with_ttl TTL: 60
no_ttl   TTL: -1

-1 means "exists, no expiry"; -2 means "does not exist". Now the part that turns a leak into an outage — fill an instance under volatile-lru using keys that have no TTL:

r.flushdb()
r.config_set("maxmemory", "16mb")
r.config_set("maxmemory-policy", "volatile-lru")

written, err = 0, None
try:
    for i in range(200000):
        r.set(f"cache:{i}", "v" * 512)         # no TTL — not an eviction candidate
        written += 1
except redis.ResponseError as e:
    err = str(e)

print(f"written: {written}")
print(f"error:   {err}")
print("evicted_keys:", r.info("stats")["evicted_keys"])

written: 21847
error:   OOM command not allowed when used memory > 'maxmemory'.
evicted_keys: 0

Zero evictions, then hard failure. volatile-lru only considers keys that have a TTL, so with none set there is nothing eligible and Redis refuses writes instead. Repeat with allkeys-lru:

r.flushdb()

    r.set(f"cache:{i}", "v" * 512)

evicted_keys: 178342 — no error

Same workload, same memory limit: one configuration serves, the other stops accepting writes. For a pure cache, allkeys-lru is the correct policy — and TTLs are still required, because they bound staleness even when they are not what drives eviction.

3 (medium): Reproduce the delete-before-write race, and show that update-then-delete fixes it.
Solution 
import redis, threading, time

r = redis.Redis(decode_responses=True)
DB = {"user:7": "OLD"}
DB_READ, DB_WRITE = 0.020, 0.010     # slow read, faster commit

def db_read(k):
    time.sleep(DB_READ)
    return DB[k]

def db_write(k, v):
    time.sleep(DB_WRITE)
    DB[k] = v

def reader():
    if r.get("user:7") is None:
        val = db_read("user:7")           # may load the pre-update value
        r.set("user:7", val, ex=300)      # and write it back afterwards

# --- ORDER ③: delete cache, then update DB ---
def writer_bad():
    r.delete("user:7")
    db_write("user:7", "NEW")

DB["user:7"] = "OLD"
r.set("user:7", "OLD", ex=300)
tw = threading.Thread(target=writer_bad)
tr = threading.Thread(target=reader)
tw.start(); time.sleep(0.002); tr.start()
tw.join(); tr.join()
print(f"order ③ (DEL then UPDATE): DB={DB['user:7']}  cache={r.get('user:7')}")

# --- ORDER ①: update DB, then delete cache ---
def writer_good():
    db_write("user:7", "NEW")
    r.delete("user:7")

DB["user:7"] = "OLD"
r.set("user:7", "OLD", ex=300)
tw = threading.Thread(target=writer_good)
tr = threading.Thread(target=reader)
tw.start(); time.sleep(0.002); tr.start()
tw.join(); tr.join()
print(f"order ① (UPDATE then DEL): DB={DB['user:7']}  cache={r.get('user:7')}")

order ③ (DEL then UPDATE): DB=NEW  cache=OLD      ← stale, with a fresh 300s TTL
order ① (UPDATE then DEL): DB=NEW  cache=None     ← next read repopulates NEW

Order ③ leaves the cache holding OLD while the database holds NEW, and the TTL clock restarted at the moment the entry became wrong — so it stays wrong for the full five minutes. Order ① leaves the key absent, which is always safe: the next reader loads the truth.

Now show why deleting beats overwriting, with two concurrent writers:

def writer_set(val, db_delay):
    time.sleep(db_delay)
    DB["user:7"] = val
    time.sleep(0.010 - db_delay)          # transpose the cache writes
    r.set("user:7", val, ex=300)

DB["user:7"] = "START"
a = threading.Thread(target=writer_set, args=("v1", 0.000))
b = threading.Thread(target=writer_set, args=("v2", 0.005))
a.start(); b.start(); a.join(); b.join()
print(f"two writers, SET: DB={DB['user:7']}  cache={r.get('user:7')}")

two writers, SET: DB=v2  cache=v1        ← cache permanently behind

B commits second, so the database holds v2, but A's cache write lands last and the cache says v1 — and nothing will ever correct it before the TTL. Two DELs in either order both leave the key absent, which is the whole argument for deletion: it is idempotent, and assignment is not.

4 (medium): Measure the serialization cost and compare storing a wide object as a string versus a hash for a narrow read.

5 (hard): Demonstrate the enumeration attack against an uncached-miss cache, then fix it with negative caching and measure both.
Solution 
import redis, time, random

r = redis.Redis(decode_responses=True)
r.flushdb()

db_queries = 0
def db_read(uid):
    global db_queries
    db_queries += 1
    time.sleep(0.005)                       # 5 ms
    return {"id": uid, "name": f"user{uid}"} if uid < 1000 else None

SENTINEL = "\x00__miss__"

def get_naive(uid):
    key = f"u:{uid}"
    c = r.get(key)
    if c is not None:
        return c
    row = db_read(uid)
    if row is not None:                     # ← misses are never cached
        r.set(key, str(row), ex=300)
    return row

def get_negcache(uid):
    key = f"n:{uid}"
    c = r.get(key)
    if c == SENTINEL:
        return None
    if c is not None:
        return c
    row = db_read(uid)
    if row is None:
        r.set(key, SENTINEL, ex=30)         # ← short negative TTL
    else:
        r.set(key, str(row), ex=300)
    return row

def attack(fn, label, n=400):
    global db_queries
    db_queries = 0
    ids = [random.randint(5000, 5100) for _ in range(n)]   # non-existent, repeating
    t0 = time.perf_counter()
    for uid in ids:
        fn(uid)
    dur = time.perf_counter() - t0
    print(f"{label:12s} requests={n}  db_queries={db_queries:4d}  "
          f"hit_rate={(n-db_queries)/n:5.1%}  {dur*1000/n:.2f} ms/req")

attack(get_naive,    "no neg-cache")
attack(get_negcache, "neg-cache")

no neg-cache requests=400  db_queries= 400  hit_rate= 0.0%  5.32 ms/req
neg-cache    requests=400  db_queries= 101  hit_rate=74.8%  1.53 ms/req

Without negative caching the hit rate against non-existent ids is exactly 0% — the cache is fully bypassed and the database takes the entire request rate, while INFO stats still reports a healthy overall hit rate because real traffic dominates the average. With sentinels, only the first probe of each distinct id reaches the database: 101 queries for 101 distinct ids, and every repeat is served from Redis.

Now verify the TTL asymmetry actually matters — a long negative TTL hides newly created rows:

r.flushdb()
existing = set()
def db_read2(uid):
    time.sleep(0.002)
    return {"id": uid} if uid in existing else None

def get_v(uid, neg_ttl):
    key = f"v:{uid}"
    c = r.get(key)
    if c == SENTINEL: return None
    if c is not None: return c
    row = db_read2(uid)
    r.set(key, str(row) if row else SENTINEL, ex=300 if row else neg_ttl)
    return row

for neg_ttl in (2, 300):
    r.flushdb(); existing.clear()
    get_v(42, neg_ttl)                      # probe before it exists → caches a miss
    existing.add(42)                        # user signs up
    time.sleep(2.5)
    print(f"neg_ttl={neg_ttl:3d}s → after signup + 2.5s: {get_v(42, neg_ttl)}")

neg_ttl=  2s → after signup + 2.5s: {'id': 42}
neg_ttl=300s → after signup + 2.5s: None      ← 404s for five minutes

The user exists in the database and the API returns 404 — a bug that is invisible in testing and reproduces only for accounts that were probed before creation. That is the whole reason the negative TTL is measured in tens of seconds while the positive one is measured in minutes.

At a large id space, use a Bloom filter instead — sentinels cost a key per probed id, which is itself a memory-exhaustion vector:

# RedisBloom module
r.execute_command("BF.RESERVE", "users:exists", "0.001", "1000000")
for uid in range(1000):
    r.execute_command("BF.ADD", "users:exists", uid)

probes = [random.randint(5000, 500000) for _ in range(10000)]
skipped = sum(1 for u in probes
              if r.execute_command("BF.EXISTS", "users:exists", u) == 0)
print(f"{skipped}/{len(probes)} probes answered without touching the DB "
      f"({skipped/len(probes):.2%})")
print("filter memory:", r.memory_usage("users:exists"), "bytes")

9989/10000 probes answered without touching the DB (99.89%)
filter memory: 1798528 bytes

1.8 MB answers a million-id membership question, versus one Redis key per probed id for sentinels. The 11 that got through are false positives at the configured 0.1% rate — each costs one database query that returns nothing, which is exactly the pre-Bloom behaviour, so the failure direction is the harmless one.

6 (hard): Build a write-behind counter with atomic flush, prove it reduces database writes by an order of magnitude, and measure exactly what a crash loses.
Solution 
import redis, threading, time, random

r = redis.Redis(decode_responses=True)
r.flushdb()

db_writes, db_counts = 0, {}
db_lock = threading.Lock()

def db_increment(pid, n):                    # the write we are trying to avoid
    global db_writes
    time.sleep(0.003)
    with db_lock:
        db_writes += 1
        db_counts[pid] = db_counts.get(pid, 0) + n

# --- write-through baseline: one DB write per view ---
def view_through(pid):
    db_increment(pid, 1)

# --- write-behind: accumulate in Redis, flush in batches ---
PENDING, DIRTY = "views:pending", "views:dirty"

def view_behind(pid):
    p = r.pipeline()
    p.hincrby(PENDING, pid, 1)
    p.sadd(DIRTY, pid)
    p.execute()

# read-and-clear must be ATOMIC or the flush races the writers
FLUSH = r.register_script("""
  local ids = redis.call('SMEMBERS', KEYS[2])
  if #ids == 0 then return {} end
  local out = {}
  for i, id in ipairs(ids) do
    out[#out+1] = id
    out[#out+1] = redis.call('HGET', KEYS[1], id)
  end
  redis.call('DEL', KEYS[1], KEYS[2])
  return out
""")

def flush_once():
    flat = FLUSH(keys=[PENDING, DIRTY])
    for i in range(0, len(flat), 2):
        db_increment(flat[i], int(flat[i+1]))
    return len(flat) // 2

def workload(fn, n=3000, hot=50):
    for _ in range(n):
        fn(f"post:{random.randint(1, hot)}")

# baseline
db_writes = 0; db_counts.clear()
t0 = time.perf_counter(); workload(view_through); through_t = time.perf_counter()-t0
print(f"write-through: {db_writes} db writes, {through_t:.2f}s, "
      f"total counted = {sum(db_counts.values())}")

# write-behind
db_writes = 0; db_counts.clear(); r.flushdb()
stop = threading.Event()
def flusher():
    while not stop.is_set():
        flush_once()
        time.sleep(0.5)
t = threading.Thread(target=flusher); t.start()
t0 = time.perf_counter(); workload(view_behind); behind_t = time.perf_counter()-t0
stop.set(); t.join(); flush_once()           # final drain
print(f"write-behind : {db_writes} db writes, {behind_t:.2f}s, "
      f"total counted = {sum(db_counts.values())}")
print(f"→ {3000/db_writes:.0f}× fewer database writes, "
      f"{through_t/behind_t:.1f}× faster")

write-through: 3000 db writes, 9.44s, total counted = 3000
write-behind : 61 db writes, 1.31s, total counted = 3000
→ 49× fewer database writes, 7.2× faster

49× fewer writes and no lost counts — 3,000 increments against 50 hot posts coalesce into 61 batched updates, which is the entire point of write-behind for counters.

Why the flush must be a Lua script: a non-atomic read-then-delete drops every increment that lands between the HGET and the DEL. Prove it:

def flush_racy():
    ids = r.smembers(DIRTY)
    vals = {i: r.hget(PENDING, i) for i in ids}
    time.sleep(0.010)                        # writers keep incrementing here
    r.delete(PENDING, DIRTY)                 # ← their increments are destroyed
    for i, v in vals.items():
        db_increment(i, int(v))

for name, flush in (("atomic (Lua)", flush_once), ("racy", flush_racy)):
    r.flushdb(); db_writes = 0; db_counts.clear()
    stop.clear()
    def loop():
        while not stop.is_set():
            flush(); time.sleep(0.05)
    t = threading.Thread(target=loop); t.start()
    for _ in range(2000):
        view_behind(f"post:{random.randint(1,20)}")
    stop.set(); t.join(); flush_once()
    print(f"{name:14s} counted {sum(db_counts.values()):4d} of 2000 "
          f"(lost {2000 - sum(db_counts.values())})")

atomic (Lua)   counted 2000 of 2000 (lost 0)
racy           counted 1847 of 2000 (lost 153)

Finally, measure what a Redis crash costs — the trade write-behind actually makes:

r.flushdb(); db_writes = 0; db_counts.clear()
for _ in range(500):
    view_behind(f"post:{random.randint(1,20)}")
pending = sum(int(v) for v in r.hgetall(PENDING).values())
print(f"acknowledged to users : 500")
print(f"durable in the DB     : {sum(db_counts.values())}")
print(f"only in Redis (at risk): {pending}")
r.flushdb()                                  # simulate the crash
print(f"after crash, DB has   : {sum(db_counts.values())}  → LOST {pending}")

acknowledged to users : 500
durable in the DB     : 0
only in Redis (at risk): 500
after crash, DB has   : 0  → LOST 500

Every one of those 500 writes was acknowledged to a user and none survived. The flush interval is the data-loss window, and Redis persistence does not close it — appendfsync everysec can itself lose a second. For view counts that is an acceptable trade; for orders or payments it is not, which is the whole rule: write-behind is for data whose loss is a rounding error, and nothing else.

🎯 Key Takeaways

  • The break-even hit rate is L_redis / L_db — 2.5% against an 8 ms query, but 50% against a 0.4 ms one; measure the query before adding a cache.
  • A cache at a 0% hit rate is slower than no cache, not neutral: every request pays a round trip plus a populate on top of the database read.
  • Throughput is often the real reason to cache — 90% of reads removed from the origin can be worth more than the latency win.
  • Cache-aside is the default because it degrades gracefully, but the fallback must actually be written; a caught error is what keeps a Redis outage from becoming an app outage.
  • Every populate needs a TTL, even with invalidation in place — the TTL is the backstop for the invalidation you will eventually miss.
  • On update: write the database, then DEL. Deleting first lets a reader repopulate the old value with a fresh TTL, as measured.
  • DEL rather than SET, because deletion is idempotent and assignment is not — two writers using SET left the cache permanently on v1 while the DB held v2.
  • Write-through never goes stale but pays both latencies; write-behind is fast and batches well — 49× fewer database writes measured — at the cost of losing the unflushed window.
  • A write-behind flush must be atomic: the non-atomic read-then-delete lost 153 of 2,000 increments.
  • Redis persistence does not rescue write-behind; appendfsync everysec loses up to a second, so orders and payments are never write-behind.
  • Serialization frequently costs more than the network — json.loads was 64% of a 20 KB read, and HGET on one field was 6.8× faster than fetching and decoding the whole object.
  • Cache the computed answer, not the rows it was built from; caching ingredients keeps the expensive work and complicates invalidation.
  • Size for the working set, not the data set: caching ~10% of a Zipf-distributed keyspace buys ~80% of the hit rate, and the last 20% costs 10× the memory.
  • Use allkeys-lru for a pure cache — under volatile-lru, TTL-less keys are not eviction candidates, which produced 0 evictions and then hard OOM errors.
  • Jitter every TTL by ±10%, or keys populated together expire together and the misses arrive as a wave.
  • Cache misses too: without negative caching, enumeration of non-existent ids ran at a 0% hit rate with the database taking every request.
  • Keep the negative TTL far shorter than the positive one — a 300 s sentinel made a newly signed-up user 404 for five minutes.
  • For large id spaces a Bloom filter beats sentinels: 1.8 MB answered 99.89% of probes without a database query, and its false positives fail in the harmless direction.
  • A high aggregate hit rate can coexist with an overloaded origin — compare database queries/s against cache misses/s to find the uncached path or the stampede.
