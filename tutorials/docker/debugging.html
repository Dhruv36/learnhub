Debugging Containers Production Concerns

What you'll master: a triage order that narrows the problem in three commands instead of thirty — did it build, was it created, did it start, is it healthy; what exit codes 125, 126 and 127 each tell you about whose fault it is, and the four distinct causes of exec format error; why docker attach is a trap that kills the container you were inspecting, and what to use instead; how to get a shell into an image that has no shell, with an ephemeral sidecar sharing its namespaces; why "connection refused" and "connection timed out" point at completely different layers, and the single most common container networking bug — binding to 127.0.0.1 inside the container; how to extract evidence from a container that is already dead, and how to break a crash-loop long enough to look inside; and how to tell a slow application from a throttled one. Prerequisites: Process Model, PID 1 & Signals, Networking, Logging, Resource Limits.

Part 1 — Triage: Find the Layer Before Touching the Application

Most time lost debugging containers is spent in the wrong layer — reading application code when the image never started, or reading Dockerfiles when the process is up and the network is wrong. Establish the layer first; it takes three commands.

The one-liner worth memorising — everything decisive in a single output:

$ docker inspect app --format '
state={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}
restarts={{.RestartCount}} health={{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}}
cmd={{.Config.Cmd}} entrypoint={{.Config.Entrypoint}} user={{.Config.User}}'

state=exited exit=137 oom=true restarts=4 health=none
cmd=[node server.js] entrypoint=[docker-entrypoint.sh] user=
🔑 That output already contains the diagnosis. oom=true means this is a memory limit question, not an application bug; restarts=4 means a restart policy is masking it; and an empty user= means it is running as root, which is a separate finding for another day. Reading configuration before reading code is the habit that separates fast debugging from slow.

The four causes of exec format error

One message, four completely different problems — and only one of them is about architecture, which is why "just add --platform" so often fails:

① architecture mismatch
$ docker run --rm myapp
exec /server: exec format error
$ docker image inspect myapp --format '{{.Architecture}}'; uname -m
arm64                              ← built on an Apple laptop
x86_64                             ← running on a CI runner
   → build multi-platform, or --platform=linux/amd64. See BuildKit.

② CRLF line endings — the classic Windows-authored entrypoint
$ docker run --rm myapp
exec /entrypoint.sh: no such file or directory      ← the file is RIGHT THERE
$ head -1 entrypoint.sh | xxd | head -1
00000000: 2321 2f62 696e 2f73 680d 0a               #!/bin/sh..
                                    ↑ 0d = \r — the kernel looks for "/bin/sh\r"
   → dos2unix, .gitattributes with "*.sh text eol=lf", or COPY then sed -i 's/\r$//'

③ no shebang at all
$ head -1 entrypoint.sh
echo starting                      ← the kernel has no idea how to execute this
   → add #!/bin/sh

④ a shell script used as a binary in a scratch image
FROM scratch
COPY entrypoint.sh /
ENTRYPOINT ["/entrypoint.sh"]      ← there is no /bin/sh in scratch to interpret it
⚠️ Case ② reports "no such file or directory" about a file you can see. The kernel is reporting the missing interpreter, not the missing script — it is looking for a program literally named /bin/sh\r. The same message appears for a dynamically-linked binary whose loader is absent: a glibc binary on Alpine needs ld-linux-x86-64.so.2, which musl does not provide. ldd on the binary, or building with CGO_ENABLED=0, resolves that one.

   detach without killing:  Ctrl-P Ctrl-Q   (only works if the container has a TTY)

/ # exit                           ← the container is unaffected

When there is no shell

Distroless and scratch images (Security) have no sh, so exec fails. The general answer is an ephemeral sidecar sharing the target's namespaces — it works for every image, needs no changes to the target, and disappears when you exit:

$ docker exec -it api sh
OCI runtime exec failed: exec: "sh": executable file not found in $PATH

$ docker run -it --rm \
    --pid=container:api \          ← see its processes
    --network=container:api \      ← see its network, its localhost, its ports
    --cap-add=SYS_PTRACE \         ← strace/gdb; omit if not needed
    nicolaka/netshoot
netshoot# ps aux
PID   USER     COMMAND
1     1000     /server                      ← the target's PID 1
netshoot# ss -ltnp
State  Local Address:Port
LISTEN 127.0.0.1:8080                       ← its sockets, in its netns
netshoot# ls /proc/1/root/app/              ← its FILESYSTEM, via /proc
config.yaml  server
netshoot# cat /proc/1/environ | tr '\0' '\n' | grep -v SECRET
Namespace sharedWhat it gives you
--pid=container:Xps, /proc/1/root (its whole filesystem), /proc/1/environ, strace
--network=container:Xss, curl localhost, dig, tcpdump — its exact network view
BothEverything short of its mount namespace, which /proc/1/root covers anyway

docker debug (Desktop/Business) does this for you with a shell that works on any image, and from the host, nsenter -t $(docker inspect -f '{{.State.Pid}}' api) -a achieves the same with no extra container at all — useful when the daemon is the thing misbehaving.

Part 4 — Networking: Refused Versus Timeout

Two error messages, two entirely different investigations. Getting this distinction right eliminates most of the guesswork:

ErrorMeansInvestigate
Connection refusedPacket arrived; nothing was listening on that portIs the process up? What address did it bind? Right port?
Connection timed outNo answer at all — dropped or misroutedFirewall, wrong network, wrong host, security group
Name resolution failedDNSSame network? Correct service name? Default bridge has no DNS
Empty reply / resetReached the process; it closed the connectionProtocol mismatch (HTTPS to an HTTP port), TLS, app error

The single most common container networking bug

$ docker run -d -p 8080:3000 --name app myapp
$ curl localhost:8080
curl: (52) Empty reply from server            ← or connection reset

$ docker exec app curl -s localhost:3000
{"status":"ok"}                                ← works INSIDE. So the app is fine?

$ docker run --rm --network=container:app nicolaka/netshoot ss -ltn
State   Local Address:Port
LISTEN  127.0.0.1:3000                         ← THERE IT IS

The application bound to loopback inside its own network namespace. Nothing outside that namespace can reach it — and "outside" includes the host's port-forwarding proxy, which is why publishing the port did not help. The fix is in the application, not in Docker:

  Node    app.listen(3000, '0.0.0.0')        not  app.listen(3000, 'localhost')
  Python  --host 0.0.0.0                     (Flask/uvicorn default to 127.0.0.1)
  Go      http.ListenAndServe(":3000", ...)  the empty host means all interfaces
  Rails   -b 0.0.0.0
  .NET    ASPNETCORE_URLS=http://0.0.0.0:8080

The rest of the network checklist, in the order that resolves fastest:

① is it published at all?
$ docker port app
3000/tcp -> 0.0.0.0:8080                       ← empty output = not published

② same network? (container-to-container)
$ docker inspect app  -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
shop_default
$ docker inspect db   -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
bridge                                          ← different networks: they cannot talk

③ DNS — the DEFAULT bridge has none
$ docker run --rm alpine ping -c1 db
ping: bad address 'db'                          ← default bridge: no embedded DNS
$ docker run --rm --network shop_default alpine getent hosts db
172.19.0.2  db                                  ← user-defined bridge: works

④ connect to the CONTAINER port, not the published one
   with -p 8080:3000, peers use db:3000. 8080 exists only on the host side.

⑤ published ports bypass the host firewall (DNAT precedes INPUT) — see Networking

Part 5 — Evidence From Containers You Cannot Enter

The container is gone, or restarting too fast to catch. Every one of these still works:

① logs survive the process — including across restarts
$ docker logs --tail 100 --timestamps dead-container
   the json-file driver keeps output from previous runs of the SAME container,
   so a crash loop's history is all in one place

② copy files out of a STOPPED container
$ docker cp dead-container:/app/crash.log ./
$ docker cp dead-container:/tmp/heapdump.hprof ./          ← forensics without a restart

③ what did the process change?  (diff against the image)
$ docker diff dead-container
C /app
A /app/cache
A /tmp/upload-4f21.part                          ← A=added C=changed D=deleted
D /etc/nginx/conf.d/default.conf                 ← someone's entrypoint deleted config

④ freeze a broken state for offline analysis
$ docker commit dead-container forensics:incident-4821
$ docker run -it --entrypoint sh forensics:incident-4821    ← poke at it at leisure,
                                                             production stays untouched

⑤ break a crash loop: replace the entrypoint so it cannot crash
$ docker run -it --rm --entrypoint sh myapp                 ← same image, no app
$ docker compose run --rm --entrypoint sh api               ← same config, env, mounts
/ # ls -l /app/config.yaml                                  ← now look around
ls: /app/config.yaml: No such file or directory             ← there is the bug
🔑 docker compose run --entrypoint sh <svc> is the highest-value command in this lesson. It starts the service with its real image, environment, mounts, networks and dependencies — and drops you at a shell instead of running the crashing process. Nearly every "it works on my machine" and "it crashes instantly and logs nothing" case resolves in that shell, because you can run the exact command by hand and read its actual error.

Two more state-related traps worth naming. A restart policy hides crash loops: docker ps shows Up 2 seconds for a container that has died fifty times, so check RestartCount and docker events rather than the status column. And docker diff on a healthy container is a fast way to find writes that should not be there — a service writing logs or uploads into its writable layer is a storage bug waiting to fill a disk.

Part 6 — Slow, Not Broken

When the service responds but badly, the question is which resource is short. Containers add two failure modes that do not exist on a VM, and both are invisible in ordinary application profiling:

① CPU throttling — average utilisation looks fine, p99 does not
$ docker exec app cat /sys/fs/cgroup/cpu.stat
nr_periods 84021
nr_throttled 31447                       ← 37% of periods hit the quota
throttled_usec 402910000
   → see Resource Limits. Average CPU said 62%.

② memory pressure without an OOM kill
$ docker exec app cat /sys/fs/cgroup/memory.stat | grep -E '^(anon|inactive_file) '
anon 402653184
inactive_file 8388608                    ← cache all evicted: every read hits disk
$ docker exec app cat /sys/fs/cgroup/memory.events
high 0
max 4172                                 ← 4172 allocation stalls at the limit
   → the container is alive and thrashing. `max` climbing is the tell.

③ what is it actually doing?
$ docker top app -eo pid,ppid,etime,pcpu,rss,comm
PID   PPID  ELAPSED  %CPU  RSS      COMMAND
20481 20460 02:14:31 61.2  412340   node
20892 20481 00:00:04  0.0    1024   sh                ← host PIDs, useful with nsenter

$ docker run -it --rm --pid=container:app --cap-add=SYS_PTRACE nicolaka/netshoot
netshoot# strace -c -p 1 -f 2>&1 | head -8
% time     seconds  usecs/call     calls    errors syscall
 71.44    4.129201        4129      1000       999 connect          ← 999 failures
 12.03    0.695117           7     99120           futex
                                   ↑ retrying a connection it cannot make
netshoot# ss -tan state syn-sent | head -3
Recv-Q Send-Q  Local Address:Port   Peer Address:Port
0      1       172.19.0.4:51234     10.0.3.9:5432                   ← who it is stuck on
SymptomFirst checkUsual cause

❌ A container exits immediately, so someone adds --privileged, then docker attaches to production to watch, then rebuilds the image five times changing the application code. The exit code was 126, which says the file was found and is not executable — a CRLF shebang from a Windows checkout — but nobody read it, because the error text said "no such file or directory" about a file plainly visible in the image. attach connected to PID 1, so Ctrl-C took down the healthy replica next to the broken one. When the service finally started, it answered curl inside the container and refused connections from outside, which was read as a Docker networking bug and "fixed" by publishing more ports — the application was bound to 127.0.0.1 inside its own namespace all along. Meanwhile the restart policy showed Up 2 seconds in docker ps, so the crash loop looked like a healthy service, and the p99 regression that started the whole investigation was CFS throttling, invisible on a CPU dashboard reading a comfortable 62%.

✅ Establish the layer first, read the exit code before the code, and use the tools that do not change what you are observing. docker ps -a then one docker inspect --format gives state, exit code, OOM flag, restart count and health in a single line — and that line usually contains the diagnosis. Treat 125/126/127 as an address, not an error: 125 is your invocation, 126 and 127 are the image. Use docker exec, never attach, and when the image has no shell, bring your own with --pid=container:X --network=container:X so you inherit its exact view without modifying it. Distinguish refused (arrived, nothing listening — check the bind address with ss -ltn) from timeout (never arrived — check networks and firewall). When it crashes too fast to catch, run docker compose run --rm --entrypoint sh <svc> and reproduce the failure by hand with the real environment, or docker commit the corpse and dissect it offline while production recovers. And for "slow", check cpu.stat and memory.events before profiling the application — the container may be perfectly healthy and merely throttled.

Interview Questions

Beginner: A container exits immediately. How do you find out why?

Read the exit code first — it tells you which layer failed before you read any code.

$ docker ps -a --format '{{.Names}}\t{{.Status}}'
app     Exited (127) 3 seconds ago
$ docker logs app --tail 20
$ docker inspect app --format '{{.State.ExitCode}} {{.Config.Cmd}} {{.Config.Entrypoint}}'
CodeMeaningWhose problem
125The daemon could not start itYour flags — port in use, bad mount
126Found, not executableThe image — chmod +x, CRLF shebang
127Not foundThe image — typo, missing binary, wrong PATH
0Clean exitEither a one-shot job, or the process daemonised itself
137SIGKILLUsually OOM — check .State.OOMKilled

Two findings that are easy to misread: exit 0 for a service usually means it forked into the background and PID 1 returned — run it in the foreground instead. And empty logs are themselves evidence: either it was SIGKILLed before flushing, or stdout is block-buffered (Logging).

When the logs say nothing useful, replace the entrypoint and look: docker run -it --rm --entrypoint sh myapp, or docker compose run --rm --entrypoint sh api to keep the real environment and mounts.

Beginner: What is the difference between docker exec and docker attach?

exec starts a new process in the container; attach connects your terminal to the existing PID 1's streams. That difference is dangerous in one direction:

$ docker attach myapp
   ... logs scroll ...
^C
$ docker ps
   (nothing)                    ← Ctrl-C sent SIGINT to PID 1. The container is gone.

To leave an attach without killing the process, use the detach sequence Ctrl-P Ctrl-Q — and note it only works when the container was started with a TTY.

attachexeclogs -f
Ctrl-CKills the containerKills your shellSafe
New process?NoYesNo
Best forInteractive foreground appsEverythingWatching output

The follow-up: what if the image has no shell? Then exec fails too, and the answer is an ephemeral sidecar sharing its namespaces — docker run -it --rm --pid=container:app --network=container:app nicolaka/netshoot — which gives you its processes, its network view and its filesystem through /proc/1/root, without modifying the image.

Mid: A web app answers curl inside its container but refuses connections from the host, despite -p 8080:3000. Diagnose.

The application is bound to 127.0.0.1 inside its own network namespace. Loopback in a container is that container's loopback — the host's port-forwarding proxy is outside the namespace and cannot reach it.

$ docker run --rm --network=container:app nicolaka/netshoot ss -ltn
State   Local Address:Port
LISTEN  127.0.0.1:3000          ← the whole diagnosis, in one line

The fix is in the application, not in Docker: app.listen(3000,'0.0.0.0'), --host 0.0.0.0 for Flask/uvicorn, ":3000" in Go, ASPNETCORE_URLS=http://0.0.0.0:8080. Frameworks default to loopback for safety on a laptop, which is exactly wrong in a container — where the namespace already provides the isolation that the loopback default was protecting.

Why testing from inside hides it: docker exec app curl localhost:3000 runs in the same namespace, so it succeeds and "proves" the app is fine. Always verify the bind address, not just the response.

The checklist for the rest of the class of bug: docker port app (published at all?), same network for container-to-container, peers must use the container port not the published one, and the default bridge has no DNS. And distinguish the errors — refused means the packet arrived and nothing was listening; timed out means it never arrived, so look at networks and firewalls.

Mid: A container crash-loops every two seconds, logs nothing useful, and you cannot exec into it. How do you debug it?

Stop it from running the failing command, while keeping everything else identical.

$ docker compose run --rm --entrypoint sh api
/ # ls -l /app/config.yaml
ls: /app/config.yaml: No such file or directory     ← the mount did not land
/ # env | grep DATABASE
                                                    ← and the variable is empty
/ # node server.js
Error: Cannot find module './config'                ← the real error, in full

compose run keeps the image, environment, mounts, networks and dependencies but gives you a shell — so you reproduce the failure by hand and read the error the crash loop was truncating. That one command resolves the majority of these cases.

What else still works on a container you cannot enter:

CommandGives you
docker logs --timestampsOutput from previous runs too — the whole loop's history
docker cp c:/path ./Files out of a stopped container
docker diff cWhat it changed vs the image — often reveals a deleted config
docker commit c forensics:xFreeze the broken state, dissect it offline
docker events --since 10mThe loop itself: die/start pairs, exit codes, OOM

The trap to name: docker ps shows Up 2 seconds for a container that has died fifty times, because the restart policy keeps recreating it. Check RestartCount — a status column is not a health signal.

And if the loop is destroying evidence faster than you can collect it, set restart: "no" temporarily so the corpse stays put.

Senior: Latency regressed after a deploy. The application profile looks identical to before. Walk through your investigation.

An unchanged application profile with worse latency points outside the application. In a container, that means the resource envelope or the environment changed, not the code.

① Did the limits change?
$ docker inspect api -f '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}'
1000000000 536870912                    ← 1 CPU / 512 MB. Previously 2.5 / 640 MB.

② Is it being throttled? — invisible in any application profiler
$ docker exec api cat /sys/fs/cgroup/cpu.stat
nr_periods 84021
nr_throttled 31447                      ← 37% of periods
throttled_usec 402910000                ← 403 s frozen
$ docker stats --no-stream api --format '{{.CPUPerc}}'
62.14%                                  ← the dashboard says there is headroom

③ Is it thrashing at the memory limit without OOMing?
$ docker exec api cat /sys/fs/cgroup/memory.events
max 4172                                ← 4172 allocation stalls
$ docker exec api grep '^inactive_file ' /sys/fs/cgroup/memory.stat
inactive_file 8388608                   ← cache evicted; every read hits disk

Why the profiler could not see it: throttling freezes every thread mid-execution. To the profiler the code took longer to run; to the kernel it was not running at all. This is why nr_throttled belongs on the dashboard beside CPU utilisation — Resource Limits shows the same workload going from 41 ms to 488 ms p99 with average CPU unchanged at 62%.

The rest of the container-specific differential, in order of how often it is the answer:

  • Runtime parallelism vs quota — a runtime that sizes pools from host CPUs makes throttling dramatically worse; aligning them nearly halved p99 in that lesson's measurement.
  • A blocking log driver — a slow collector stalls handlers inside console.log(), measured at 14 s (Logging).
  • Health-check cost — a JVM or Python probe every few seconds takes CPU from the app's own quota (Health Checks).
  • Storage driver — writes into the writable layer, or copy-up on first write to a large file (Storage).
  • Neighbours — an unlimited container on the same host; check docker stats across everything, not just the suspect.

The general method: compare the container's configuration before and after (docker inspect both revisions), then read the cgroup counters, and only then profile the application. Deploys change the envelope at least as often as they change the code, and the envelope is the part no application-level tool can see.

Senior: How do you make a distroless production platform debuggable without shipping a shell?

Separate "tools available during an incident" from "tools present in the image". The failure mode to design against is a team that adopts distroless, hits its first 3am incident with no shell, and permanently switches to the :debug tag — which restores the shell and discards the benefit for every future incident.

The mechanism: an ephemeral debug container sharing namespaces. It works on any image, needs no build change, and vanishes on exit:

$ docker run -it --rm --pid=container:api --network=container:api \
    --cap-add=SYS_PTRACE nicolaka/netshoot
netshoot# ps aux                      ← its processes
netshoot# ss -ltnp                    ← its sockets, in its netns
netshoot# ls /proc/1/root/app         ← its filesystem, through /proc
netshoot# strace -p 1 -f              ← with SYS_PTRACE
EnvironmentEquivalent
Docker--pid/--network=container:X, or docker debug
Kuberneteskubectl debug -it pod --image=netshoot --target=app (ephemeral containers)
Hostnsenter -t $(docker inspect -f '{{.State.Pid}}' api) -a

What I would also build in, because the sidecar is a last resort rather than a first response:

  • The application binary exposes its own diagnostics — -healthcheck, -version, -dump-config subcommands, and pprof or equivalent on a localhost-only port. This removes most reasons to need a shell at all.
  • Rich structured logs with trace_id and externally-scraped metrics, so the common questions are answered without entering anything (Logging).
  • Crash artefacts on a volume — heap dumps, core files — so evidence outlives the container that produced it.
  • Rehearse it. A documented, practised debug procedure is what stops the :debug image from becoming permanent. Run it in a game day, not for the first time during an outage.

The trade-off I would state honestly: distroless makes routine debugging slower in exchange for removing an attacker's toolkit (measured at 0 HIGH/CRITICAL CVEs, no shell, no package manager — Security). That is worth it for internet-facing services and probably not worth it for an internal batch job. It is a per-service decision, not a platform mandate — and either way the debug workflow has to exist before it is needed.

4 (medium): Diagnose four networking failures by their error message alone.
Solution 
① "Empty reply" / refused from the host, works inside → bound to loopback
$ docker run -d -p 8080:3000 --name loop node:20-alpine node -e \

② "Connection refused" between containers → nothing listening / wrong port
$ docker network create net1
$ docker run -d --name db --network net1 postgres:16-alpine -c port=5433
$ docker run --rm --network net1 nicolaka/netshoot nc -zv db 5432

④ "bad address" → DNS, and the default bridge has none
$ docker run --rm --network bridge alpine ping -c1 api2

$ docker network connect net1 api2

172.20.0.4  api2                           ← user-defined bridge: DNS works
$ docker run --rm --network net1 alpine cat /etc/resolv.conf | head -1

ErrorPacket arrived?Look at

6 (hard): Build a triage script that diagnoses a container in one command.
Solution 
$ cat > tools/triage.sh <<'SH'
#!/usr/bin/env bash
# Usage: tools/triage.sh <container>   — reads configuration and cgroups, changes nothing.
set -u
c="$1"
i() { docker inspect "$c" --format "$1" 2>/dev/null; }
say() { printf '%-22s %s\n' "$1" "$2"; }

echo "=== state ==="
say state    "$(i '{{.State.Status}}')"
say exit     "$(i '{{.State.ExitCode}}')"
say oom      "$(i '{{.State.OOMKilled}}')"
say restarts "$(i '{{.RestartCount}}')"
say health   "$(i '{{if .State.Health}}{{.State.Health.Status}} streak={{.State.Health.FailingStreak}}{{else}}none{{end}}')"
say started  "$(i '{{.State.StartedAt}}')"

case "$(i '{{.State.ExitCode}}')" in
  125) echo "  >> 125: the DAEMON failed — re-read your flags, not the image" ;;
  126) echo "  >> 126: found but not executable — chmod +x, CRLF shebang, bad interpreter" ;;
  127) echo "  >> 127: not found — path, PATH, missing binary, or no shell for shell-form" ;;
  137) [ "$(i '{{.State.OOMKilled}}')" = true ] \
         && echo "  >> 137 + OOMKilled: raise the memory limit or fix the leak" \
         || echo "  >> 137 without OOM: SIGTERM ignored, stop timeout expired" ;;
  139) echo "  >> 139: SIGSEGV — a real crash" ;;
esac

echo; echo "=== config ==="
say user       "$(i '{{if .Config.User}}{{.Config.User}}{{else}}ROOT (finding){{end}}')"
say entrypoint "$(i '{{.Config.Entrypoint}}')"
say cmd        "$(i '{{.Config.Cmd}}')"
say memlimit   "$(i '{{.HostConfig.Memory}}')"
say cpulimit   "$(i '{{.HostConfig.NanoCpus}}')"
say logconfig  "$(i '{{.HostConfig.LogConfig.Config}}')"
say networks   "$(i '{{range $k,$_ := .NetworkSettings.Networks}}{{$k}} {{end}}')"
say ports      "$(i '{{range $p,$b := .NetworkSettings.Ports}}{{$p}}->{{$b}} {{end}}')"

if [ "$(i '{{.State.Running}}')" = true ]; then
  echo; echo "=== pressure ==="
  cg() { docker exec "$c" cat "/sys/fs/cgroup/$1" 2>/dev/null; }
  per=$(cg cpu.stat | awk '/nr_periods/{print $2}')
  thr=$(cg cpu.stat | awk '/nr_throttled/{print $2}')
  [ -n "${per:-}" ] && [ "${per:-0}" -gt 0 ] && \
    say throttled "$thr/$per periods ($(( 100*thr/per ))%)$([ $((100*thr/per)) -gt 1 ] && echo '  << CPU QUOTA TOO LOW')"
  cur=$(cg memory.current); ina=$(cg memory.stat | awk '/^inactive_file /{print $2}')
  [ -n "${cur:-}" ] && say mem_real "$(( (cur-${ina:-0})/1048576 ))MB (docker stats would say $(( cur/1048576 ))MB)"
  say mem_stalls "$(cg memory.events | awk '/^max/{print $2}')"
  say pids "$(cg pids.current)/$(cg pids.max)"

  echo; echo "=== listeners (inside its netns) ==="
  docker run --rm --network="container:$c" nicolaka/netshoot ss -ltn 2>/dev/null | tail -n +2 |
    while read -r _ _ _ addr _; do
      case "$addr" in 127.0.0.1:*|[::1]:*) echo "  $addr   << LOOPBACK ONLY - unreachable from outside" ;;
                      *) echo "  $addr" ;; esac
    done
fi
SH

🎯 Key Takeaways

  • Establish the layer before reading code: docker ps -a, one inspect --format, then logs. The format line usually contains the diagnosis already.
  • 125 is your invocation, 126 and 127 are the image — 125 means no container was ever created, so stop reading the Dockerfile.
  • Exit 0 for a service usually means the process daemonised itself; empty logs are evidence of a SIGKILL or of stdout buffering.
  • exec format error has four causes: wrong architecture, CRLF shebang, no shebang, and a missing dynamic loader (glibc binary on musl).
  • "No such file or directory" about a file you can see means the missing thing is the interpreter or loader — check head -1 | xxd and ldd.
  • docker attach connects to PID 1: Ctrl-C kills the container (exit 130). Detach with Ctrl-P Ctrl-Q, and prefer exec for everything.
  • For images with no shell, run an ephemeral sidecar with --pid=container:X --network=container:X — its processes, sockets, environment and filesystem via /proc/1/root, with no change to the target.
  • Never ship a :debug image with a shell to production; rehearse the sidecar workflow instead, and expose diagnostics from the application binary.
  • Refused means the packet arrived (check bind address and port); timed out means it never arrived (check networks and firewall); "bad address" is DNS.
  • The most common container networking bug is binding to 127.0.0.1 inside the container — invisible when you test with docker exec curl localhost, obvious in ss -ltn.
  • Container-to-container traffic uses the container port, needs a user-defined network for DNS, and never needs ports: at all.
  • docker logs retains output from previous runs of the same container, so a crash loop's whole history is in one place.
  • docker cp works on stopped containers, docker diff shows what changed versus the image, and docker commit freezes a corpse for offline dissection.
  • docker compose run --rm --entrypoint sh <svc> is the highest-value command here: the real image, env, mounts and networks, with a shell instead of the crashing process.
  • A restart policy hides crash loops — docker ps says Up 2 seconds while RestartCount says 23. Set --restart=no to stop the loop destroying evidence.
  • Collect logs, files, diff and a commit before docker rm; cleanup jobs destroy evidence within minutes.
  • For "slow", read cpu.stat (nr_throttled) and memory.events (max) before profiling — throttling freezes threads and is invisible to application profilers.
  • Deploys change the resource envelope as often as the code; diff docker inspect across revisions early.
  • docker top, strace -c -p 1 in a SYS_PTRACE sidecar, and ss -tan state syn-sent identify what a stuck process is waiting on, by name.
  • A read-only triage script that never restarts or attaches surfaces loopback binds, throttling, real memory and uncapped logging in one command — automate the checks you would otherwise forget at 3am.
