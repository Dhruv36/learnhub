Namespaces: Isolating What You See Foundations

What you'll master: the seven namespace types, what each one virtualises, and — more usefully — the significant things they do not cover, which is where every "why does my container see the host's..." question comes from; why /proc/meminfo and nproc report host values inside a container, and the JVM and Go runtime bugs that caused; the PID namespace and why PID 1 inside is a real host PID outside; user namespaces, the one that actually maps container root to an unprivileged host UID — and why Docker leaves it off by default; how to share namespaces deliberately (--net=container:, --pid=host) and what each sharing decision costs; and how to inspect and enter namespaces with lsns and nsenter. Prerequisites: What a Container Actually Is.

Part 1 — The Seven Namespaces

A namespace virtualises one global system resource so that processes inside it see their own instance of it. Linux has seven, and Docker uses six of them by default.

NamespaceVirtualisesDocker default
PIDProcess IDs — its own PID 1, cannot see host processes✅ Own
MNTMount points — its own filesystem tree✅ Own
NETInterfaces, routes, iptables, port space✅ Own
UTSHostname and domain name✅ Own
IPCSystem V IPC, POSIX message queues, shared memory✅ Own
CGROUPThe cgroup root a process sees✅ Own
USERUID/GID mappings and capabilities❌ Off by default

Each is just an identifier the kernel attaches to a process, visible in /proc/PID/ns/:

$ PID=$(docker inspect -f '{{.State.Pid}}' mycontainer)
$ sudo ls -l /proc/$PID/ns/
lrwxrwxrwx 1 root root 0 cgroup -> 'cgroup:[4026532567]'
lrwxrwxrwx 1 root root 0 ipc    -> 'ipc:[4026532505]'
lrwxrwxrwx 1 root root 0 mnt    -> 'mnt:[4026532503]'
lrwxrwxrwx 1 root root 0 net    -> 'net:[4026532508]'
lrwxrwxrwx 1 root root 0 pid    -> 'pid:[4026532506]'
lrwxrwxrwx 1 root root 0 user   -> 'user:[4026531837]'   ← same id as the host!
lrwxrwxrwx 1 root root 0 uts    -> 'uts:[4026532504]'

$ sudo ls -l /proc/1/ns/user                              # host init
lrwxrwxrwx 1 root root 0 user -> 'user:[4026531837]'      ← identical
🔑 Two processes are in the same namespace if and only if those inode numbers match. That is the entire mechanism — "isolation" is a set of integers. Note the user namespace above: the container and host share it, which is why root in a default Docker container is really root on the host, restricted only by dropped capabilities and seccomp rather than by a UID mapping.

Part 2 — What Namespaces Do NOT Cover

This is the part that generates real production bugs. Several things that feel like they should be isolated are not namespaced at all.

NOT namespaced — the container sees HOST values:

  /proc/cpuinfo        the host's CPU count
  /proc/meminfo        the host's total RAM
  /proc/loadavg        the host's load average
  uname -r             the host kernel version
  /sys/devices/...     host hardware topology
  the system clock     one clock for everything (time ns exists but is unused)
  most sysctls         one kernel, one setting

$ docker run --rm --memory=512m --cpus=1 alpine sh -c \
    'nproc; grep MemTotal /proc/meminfo'
16                              ← the HOST's core count, despite --cpus=1
MemTotal:       65806152 kB     ← the HOST's 64 GB, despite --memory=512m
🔑 cgroup limits are enforced but not reported through the usual interfaces, and that mismatch caused a well-known class of outage. A JVM before Java 10 sized its default heap from /proc/meminfo, so a container limited to 512 MB would size a ~16 GB heap from the host's RAM, grow past its cgroup limit, and be OOM-killed with exit code 137 and no Java error. Go's runtime.NumCPU() and thread pools sized from nproc have the equivalent problem, creating 16 worker threads on a 1-CPU quota and thrashing.

RuntimeProblemFix
JVM < 10Heap sized from host RAM → OOM killJava 10+ (container-aware), or explicit -Xmx
GoGOMAXPROCS from host cores → thrashautomaxprocs, or set it explicitly
Node.jsos.cpus() misleading for cluster sizingRead the cgroup, or configure explicitly
Python multiprocessingcpu_count() returns host coreslen(os.sched_getaffinity(0))
nginx worker_processes autoWorkers from host coresSet the number explicitly

Read the cgroup directly when you need the real limit — that is where the truth lives:

# cgroup v2
$ docker run --rm --memory=512m alpine cat /sys/fs/cgroup/memory.max
536870912                       ← 512 MB, the actual limit
$ docker run --rm --cpus=1.5 alpine cat /sys/fs/cgroup/cpu.max
150000 100000                   ← 1.5 CPUs (quota/period)

Part 3 — PID, UTS, IPC and MNT

The PID namespace gives the container its own process numbering starting at 1. The same task has two PIDs — one per namespace it belongs to.

$ docker run -d --name web nginx
$ docker exec web ps -eo pid,comm
  PID COMMAND
    1 nginx                     ← PID 1 inside
   29 nginx

$ docker inspect -f '{{.State.Pid}}' web
48213                           ← the same process, on the host

$ sudo cat /proc/48213/status | grep ^NSpid
NSpid:  48213   1               ← host PID, then namespace PID

PID 1 is special, and that specialness causes the signal-handling and zombie-reaping problems covered in Process Model, PID 1 & Signals: the kernel does not apply default signal actions to PID 1, so a process that does not explicitly handle SIGTERM ignores it entirely.

UTS is the smallest namespace — hostname and domain name only:

$ docker run --rm alpine hostname
3f8a91c04e7b                    ← the container ID by default
$ docker run --rm --hostname myapp alpine hostname
myapp

IPC isolates System V IPC and POSIX message queues — and, importantly, /dev/shm, whose default size of 64 MB breaks applications that expect more:

$ docker run --rm alpine df -h /dev/shm
Filesystem      Size  Used Avail Use% Mounted on
shm              64M     0   64M   0% /dev/shm      ← Chrome, Postgres, PyTorch need more

$ docker run --rm --shm-size=1g alpine df -h /dev/shm | tail -1
shm             1.0G     0  1.0G   0% /dev/shm

MNT gives the container its own mount table, which is what makes the union filesystem possible — the container's / is the overlayfs merged directory rather than the host's root.

Part 4 — User Namespaces: The One That Is Off

The user namespace maps UIDs and GIDs between container and host, so that UID 0 inside can be an unprivileged UID outside. This is the strongest namespace-level security control available, and Docker does not enable it by default.

WITHOUT a user namespace (Docker's default):
  container UID 0  ──is──>  host UID 0        ← real root, restricted by capabilities

WITH a user namespace (userns-remap):
  container UID 0  ──maps──>  host UID 165536 ← unprivileged on the host
  container UID 1  ──maps──>  host UID 165537
🔑 By default, root inside a container is root on the host. What stops it doing damage is not a UID mapping but dropped capabilities, seccomp filters, and the read-only masking of parts of /proc. Remove those — --privileged, or --cap-add=SYS_ADMIN — and container root is host root in practice, which is exactly why a mounted Docker socket is a full host compromise.

# enable user-namespace remapping in /etc/docker/daemon.json
{ "userns-remap": "default" }

# then, from the host:
$ docker run -d --name remapped alpine sleep 300
$ ps -o uid,cmd -p $(docker inspect -f '{{.State.Pid}}' remapped)
  UID CMD
165536 sleep 300           ← container root is an unprivileged host UID
userns-remapGainsCosts
EnabledContainer root ≠ host root; escapes land unprivilegedVolume ownership shifts; some features break
Disabled (default)Simple volume permissions; everything worksContainer root is host root

The costs are why it is off: bind-mounted host directories are owned by the wrong UID from the container's perspective, and --privileged, --pid=host and --net=host are incompatible with it. Rootless Docker and Podman take the same idea further by running the daemon itself unprivileged.

Part 5 — Sharing Namespaces Deliberately

Namespaces can be shared, and each sharing decision trades isolation for a capability.

--network=container:web     join another container's NET namespace (localhost between them)
--network=host              use the HOST's network stack — no isolation, no port mapping
--pid=container:web         see another container's processes (debugging)
--pid=host                  see ALL host processes
--ipc=container:web         share memory segments
--uts=host                  share the hostname
--userns=host               opt out of userns-remap for one container

The debugging pattern is the most valuable use: attach a toolbox container to a distroless container that has no shell:

# a minimal image has no ps, no curl, no shell
$ docker run --rm -it \
    --network=container:web \
    --pid=container:web \
    nicolaka/netshoot sh
/ # ps aux                   ← sees web's processes
/ # curl localhost:8080      ← web's port is on OUR localhost
/ # ss -tlnp                 ← web's listening sockets
SharingUse forRisk
--network=container:Sidecars, debugging, service meshesShared port space — collisions
--network=hostPerformance-critical networkingNo isolation; binds host ports directly
--pid=container:Debugging a shell-less imageCan signal the target's processes
--pid=hostMonitoring agentsSees and can signal every host process
--ipc=container:Shared-memory workloadsShared memory is a channel between them

Part 6 — Inspecting and Entering Namespaces

$ lsns                                   # all namespaces on the host
        NS TYPE   NPROCS   PID USER   COMMAND
4026531835 cgroup    342     1 root   /sbin/init
4026532503 mnt         2 48213 root   nginx: master process
4026532506 pid         2 48213 root   nginx: master process

$ lsns -t net                            # only network namespaces
$ lsns -p 48213                          # namespaces of one process

# enter a container's namespaces from the host — works even with no shell in the image
$ PID=$(docker inspect -f '{{.State.Pid}}' web)
$ sudo nsenter -t $PID -n ip addr        # its network only, host binaries
$ sudo nsenter -t $PID -p -m -u -i -n sh # everything: a full "docker exec" equivalent

nsenter is the tool that works when docker exec cannot — a distroless or scratch image has no shell to exec, but entering only the network namespace lets you use the host's ip, ss, and tcpdump against the container's stack.

❌ Assuming namespaces isolate everything, and sizing an application from what it reads inside the container. The team sets --memory=512m and --cpus=1, then the JVM reads /proc/meminfo, sees the host's 64 GB, and sizes a multi-gigabyte default heap; the Go service reads nproc, sees 16 cores, and starts 16 workers on a one-core quota. Neither value is namespaced, so both runtimes are configuring themselves from the host. The result is a container OOM-killed with exit code 137 and no application-level error, or one thrashing on CPU throttling — and because the limits are enforced while the readings are not, nothing in the container's own view explains it.

✅ Treat namespaces as controlling visibility of the process tree, mounts, network, hostname and IPC — and nothing else. CPU count, memory totals, load average, kernel version and most sysctls come from the host. Read the real limits from the cgroup interface (/sys/fs/cgroup/memory.max, cpu.max) or use container-aware runtimes: Java 10+, Go with automaxprocs, Python's sched_getaffinity, and explicit worker counts for nginx and Node. Then remember the namespace Docker leaves off: without userns-remap, container root is host root, so dropping capabilities and never mounting the Docker socket are what actually contain it.

Interview Questions

Beginner: What are Linux namespaces, and which does Docker use?

A namespace virtualises one global system resource so processes inside it see their own instance. They are the mechanism behind "what a container can see".

NamespaceIsolates
PIDProcess IDs — its own PID 1
MNTMount points and filesystem tree
NETInterfaces, routes, iptables, ports
UTSHostname and domain
IPCSystem V IPC, message queues, /dev/shm
CGROUPThe visible cgroup root
USERUID/GID mapping — off by default in Docker

Docker uses the first six by default. Mechanically a namespace is just an inode number attached to a process, visible in /proc/PID/ns/ — two processes are in the same namespace exactly when those numbers match.

The important half of the answer is what they do NOT isolate: CPU count, memory totals, load average, kernel version, and most sysctls are not namespaced, so a container reads the host's values for all of them. That is the source of the classic JVM-heap-from-host-RAM OOM.

Namespaces answer "what can it see"; cgroups answer "what can it use". Both are needed, and confusing them is the most common misunderstanding here.

Beginner: Why does nproc show 16 cores in a container limited to 1 CPU?

Because CPU and memory information is not namespaced. There is no "CPU namespace" — /proc/cpuinfo, /proc/meminfo and /proc/loadavg are the host's, and the container reads them directly.

$ docker run --rm --cpus=1 --memory=512m alpine sh -c 'nproc; grep MemTotal /proc/meminfo'
16                              ← host cores
MemTotal:       65806152 kB     ← host RAM

The limit is enforced, just not reported. cgroups throttle the container to one CPU's worth of time and kill it above 512 MB — the enforcement is real, the visibility is missing.

That mismatch is what breaks runtimes. A JVM before Java 10 sized its default heap as a fraction of /proc/meminfo, so a 512 MB container would target a multi-gigabyte heap, exceed its cgroup limit, and be OOM-killed with exit 137 and no Java exception. Go sizing GOMAXPROCS from host cores creates 16 threads on a 1-core quota and thrashes on throttling.

Read the cgroup for the truth:

$ cat /sys/fs/cgroup/memory.max     # 536870912
$ cat /sys/fs/cgroup/cpu.max        # 100000 100000  → 1 CPU

Or use container-aware runtimes: Java 10+, Go with automaxprocs, Python's os.sched_getaffinity(0), and explicit worker counts instead of auto in nginx.

Mid: What is a user namespace, and why is it off by default?

A user namespace maps UIDs and GIDs between container and host, so UID 0 inside can correspond to an unprivileged UID outside.

Without (Docker default):  container UID 0 → host UID 0        ← real root
With userns-remap:         container UID 0 → host UID 165536   ← unprivileged

Without it, root in a container is root on the host. What limits the damage is not identity but capabilities, seccomp filters, and masked /proc paths. Remove those with --privileged or --cap-add=SYS_ADMIN and container root is effectively host root — which is why mounting the Docker socket into a container is a full host compromise.

Why Docker leaves it off:

  • Volume ownership. Bind-mounted host directories appear owned by the wrong UID inside, so existing setups break in confusing ways.
  • Feature incompatibility. --privileged, --pid=host and --net=host do not work with it.
  • It is daemon-wide, not per container, so enabling it changes every workload at once.
  • Historically it was late and incomplete relative to other isolation features.

What I would do instead in most environments: run the application as a non-root UID in the image, drop all capabilities and add back only what is needed, use a seccomp profile, and never mount the Docker socket. Where the workload is genuinely untrusted, rootless Docker or Podman — which run the daemon itself unprivileged — are a better answer than remapping alone, and VM-backed isolation is better still.

Mid: How do you debug a distroless container with no shell?

docker exec fails because there is no shell or utility in the image to execute. Two approaches, both using namespaces.

1. A sidecar sharing the target's namespaces — the portable option, and the one that works in Kubernetes as an ephemeral container:

docker run --rm -it \
  --network=container:myapp \
  --pid=container:myapp \
  nicolaka/netshoot sh

/ # ps aux            # sees myapp's processes (shared PID namespace)
/ # ss -tlnp          # sees myapp's listening sockets
/ # curl localhost:8080   # myapp's ports are on our localhost

2. nsenter from the host — no extra container, and you get the host's full toolset:

PID=$(docker inspect -f '{{.State.Pid}}' myapp)
sudo nsenter -t $PID -n ip addr        # network namespace only
sudo nsenter -t $PID -n tcpdump -i eth0
sudo nsenter -t $PID -p -m -u -i -n sh # all namespaces, host binaries

Entering only the network namespace is often the best choice: you keep the host's binaries and its filesystem while seeing exactly the container's network stack, which is what most connectivity debugging needs.

Other options worth naming: a debug image variant built FROM the distroless one with tools added, published alongside; and copying a static binary in with docker cp — though that only works if the container filesystem is writable and it drifts from the image.

The general point is that namespaces are joinable. Nothing about a minimal image prevents inspection; it only prevents inspection from inside.

Senior: An attacker gets code execution in a container. What can they reach?

It depends almost entirely on how the container was configured, and I would reason through it in layers.

Default configuration (non-root user, no extra capabilities): the process sees its own PID, mount, network, UTS and IPC namespaces; capabilities are a reduced set; seccomp blocks roughly 44 syscalls; parts of /proc are masked. Escape requires a kernel vulnerability. Realistically they can attack the network — reaching other containers and internal services that assume network position is authentication.

Running as root in the container (Docker's default if the image does not say otherwise): because the user namespace is off, that is host UID 0 restricted by capabilities. Any capability-based kernel bug now yields host root, and writable bind mounts are written as root.

Specific configurations that hand over the host:

SettingConsequence
-v /var/run/docker.sock:/...Immediate host root — start a privileged container mounting /
--privilegedAll capabilities, device access — escape is straightforward
--cap-add=SYS_ADMINMount operations; several known escape paths
--pid=hostSee and signal every host process; read their memory as root
-v /:/hostThe host filesystem, directly
--net=hostHost network position; reach services bound to localhost

The lateral movement people underestimate is the network: cloud metadata endpoints (169.254.169.254) hand out instance credentials unless IMDSv2 is enforced, and internal services on a shared Docker network are usually unauthenticated.

Hardening in priority order: run as non-root with a read-only root filesystem; drop all capabilities and add back only what is required; never mount the Docker socket; keep seccomp and AppArmor enabled; segment networks so a compromised container cannot reach unrelated services; block metadata access; and enable userns-remap or use rootless/Podman where practical. For genuinely untrusted code, none of this substitutes for a VM boundary — gVisor, Kata, or Firecracker.

Senior: Design namespace configuration for a monitoring agent and a service mesh sidecar.

Both need to break isolation deliberately, and the interesting part is bounding how much.

Monitoring agent (node-level metrics):

docker run -d --name node-agent \
  --pid=host \                       # see all host processes — required
  --network=host \                   # report host interfaces
  -v /proc:/host/proc:ro \           # read-only host proc
  -v /sys:/host/sys:ro \
  --cap-drop=ALL --cap-add=SYS_PTRACE \   # only what per-process stats need
  --read-only \
  agent:1.0

--pid=host is unavoidable for process-level metrics, and it is a large grant: the agent can see every command line (which frequently contains secrets) and signal any process. I would bound it with --cap-drop=ALL plus the single capability needed, read-only mounts and a read-only root filesystem, one agent image from a trusted source with pinned digests, and — because these agents are a supply-chain target — scanning and provenance verification in the pipeline.

Service mesh sidecar:

# the sidecar shares the app's NETWORK namespace only
docker run -d --name app myapp:1.0
docker run -d --name envoy \
  --network=container:app \          # same network stack, same localhost
  --cap-drop=ALL --cap-add=NET_ADMIN \  # to install iptables redirect rules
  envoy:1.29

Sharing only the network namespace is the key decision. The sidecar needs to intercept traffic, so it must share the network stack — but it does not need --pid=container:, so it cannot see or signal the application's processes, and it does not need the application's filesystem. NET_ADMIN is required for the iptables redirect and is dropped afterwards in mature meshes via an init container that does the setup and exits.

The shared port space is the practical constraint: the sidecar and the app cannot both bind the same port, so port allocation becomes a contract between them — a real source of confusing "address already in use" failures when an application is moved into a mesh.

The principle I would state: share the narrowest namespace that accomplishes the job, and compensate for each grant with capability dropping, read-only mounts, and provenance controls on the image — because a component that shares namespaces is inside your trust boundary regardless of what the diagram says.

Solution 
$ docker run -d --name ns1 alpine sleep 3600
$ docker run -d --name ns2 alpine sleep 3600

Three different PID namespaces, identified by three inode numbers. That difference is the whole isolation mechanism.

$ for ns in pid mnt net uts ipc cgroup user; do

    [ "$C" = "$H" ] && echo "$ns:    SHARED with host" || echo "$ns:    isolated"

net:    isolated
uts:    isolated
ipc:    isolated

net:[4026532508]        ← matches: we are in its network namespace
$ docker rm -f web api >/dev/null
4 (medium): Show that container root is host root without user namespaces.
Solution 
$ docker run -d --name asroot -v /tmp/shared:/data alpine sleep 3600
$ mkdir -p /tmp/shared

$ docker exec asroot id
uid=0(root) gid=0(root) groups=0(root),1(bin),...    ← root inside

$ docker exec asroot sh -c 'echo "written by container" > /data/file.txt'
$ ls -l /tmp/shared/file.txt
-rw-r--r-- 1 root root 21 Aug 18 15:04 /tmp/shared/file.txt
                └──┬──┘
            owned by HOST root — the same UID 0

The container process itself runs as host UID 0:

$ PID=$(docker inspect -f '{{.State.Pid}}' asroot)
$ ps -o pid,uid,user,cmd -p $PID
  PID   UID USER     CMD
48213     0 root     sleep 3600           ← host UID 0

$ sudo readlink /proc/$PID/ns/user
user:[4026531837]
$ sudo readlink /proc/1/ns/user
user:[4026531837]                          ← identical: no user namespace

What actually restrains it is capabilities, not identity:

$ docker exec asroot grep CapEff /proc/self/status
CapEff: 00000000a80425fb                  ← a reduced set

$ docker exec asroot sh -c 'mount -t tmpfs none /mnt'
mount: permission denied (are you root?)   ← root, but lacks CAP_SYS_ADMIN

$ docker run --rm --cap-add=SYS_ADMIN alpine sh -c 'mount -t tmpfs none /mnt && echo mounted'
mounted                                    ← one capability changes everything

Now contrast with a non-root container:

$ docker run -d --name nonroot --user 1000:1000 -v /tmp/shared:/data alpine sleep 3600
$ docker exec nonroot id
uid=1000 gid=1000
$ docker exec nonroot sh -c 'echo x > /data/nonroot.txt'
sh: can't create /data/nonroot.txt: Permission denied     ← cannot write as root

$ ps -o uid,cmd -p $(docker inspect -f '{{.State.Pid}}' nonroot)
  UID CMD
 1000 sleep 3600                          ← unprivileged on the host too

The lesson: with the user namespace disabled, the --user flag and a non-root USER in the image are what separate container identity from host root. Enabling userns-remap would map container UID 0 to an unprivileged host UID instead:

# /etc/docker/daemon.json → { "userns-remap": "default" }, then restart dockerd
$ ps -o uid,cmd -p $(docker inspect -f '{{.State.Pid}}' remapped)
  UID CMD
165536 sleep 3600                         ← container root, unprivileged on the host
$ docker rm -f asroot nonroot >/dev/null

6 (hard): Show the consequences of sharing namespaces, including the dangerous ones.
Solution 
# --network=container: shares the port space
$ docker run -d --name app1 nginx
$ docker run -d --name app2 --network=container:app1 nginx
$ docker logs app2 2>&1 | tail -2
nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
                              ← same network namespace = same port space
$ docker rm -f app2 >/dev/null

That collision is the practical constraint when adding a sidecar — the app and sidecar must agree on port allocation.

Shared network means shared localhost, which is the useful half:

$ docker run --rm --network=container:app1 nicolaka/netshoot \
    curl -s -o /dev/null -w 'localhost:80 -> %{http_code}\n' localhost:80
localhost:80 -> 200           ← reaching app1 over loopback

Now --pid=host, and what it exposes:

$ docker run --rm --pid=host alpine sh -c 'ps -eo pid,comm | wc -l'
344                           ← every host process

$ docker run --rm --pid=host alpine sh -c 'ps -eo pid,args | grep -i "[p]assword\|[t]oken" | head -3'
 3821 /usr/bin/backup-tool --db-password=hunter2 ...
                              ← command lines leak secrets to anything with --pid=host

# and it can SIGNAL host processes
$ sleep 600 &          # a host process
[1] 52001
$ docker run --rm --pid=host alpine kill -TERM 52001
$ jobs
[1]+  Terminated              sleep 600
                              ← a container killed a host process

The Docker socket is the most severe case — this is full host root:

$ docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli \
    docker run --rm -v /:/host alpine cat /host/etc/shadow | head -1
root:$6$xyz...:19000:0:99999:7:::
      ↑ the HOST's shadow file, read from inside a container

The container did not escape anything — it asked the Docker daemon (running as root) to start a new container mounting the host filesystem. Mounting the socket is equivalent to granting root.

What each grant costs, summarised by measurement:

FlagObserved capability
--network=container:Shared localhost and port space; collisions
--pid=hostRead all command lines (secrets); signal any host process
-v docker.sockRead /etc/shadow — full host root
--privilegedAll capabilities; modify host kernel settings

The safe defaults: share the narrowest namespace that does the job, drop capabilities alongside any grant, and treat the Docker socket as a credential rather than a file.

🎯 Key Takeaways

  • A namespace is an inode number attached to a process — two processes share a namespace exactly when the ids in /proc/PID/ns/ match.
  • Docker uses six namespaces by default (PID, MNT, NET, UTS, IPC, CGROUP) and leaves USER off.
  • Because the user namespace is off, container root is host root — restrained by capabilities and seccomp, not by identity.
  • CPU count, memory totals, load average and kernel version are NOT namespaced: a container with --cpus=1 --memory=512m still reported 16 cores and 64 GB.
  • The limits are enforced but not reported — read /sys/fs/cgroup/memory.max and cpu.max for the truth.
  • That mismatch caused the classic JVM bug: an old JVM sized a 16 GB heap in a 512 MB container versus 128 MB for a container-aware one — a 125× difference, ending in exit code 137 with no Java error.
  • Go, Node, Python and nginx have the same problem — use automaxprocs, sched_getaffinity, or explicit worker counts.
  • The same task has a host PID and a namespace PID; /proc/PID/status shows both in NSpid.
  • Creating a PID namespace without --mount-proc still shows host processes — isolation needs the mount namespace too.
  • /dev/shm defaults to 64 MB, which breaks Chrome, Postgres and PyTorch — raise it with --shm-size.
  • userns-remap maps container UID 0 to an unprivileged host UID, but is off by default because it breaks volume ownership and conflicts with --privileged, --pid=host and --net=host.
  • --network=container: shares the port space — measured as an "address already in use" failure between two nginx containers.
  • --pid=host exposes every host command line (secrets included) and lets a container signal host processes, demonstrated by killing one.
  • Mounting /var/run/docker.sock is equivalent to host root — used it to read /etc/shadow.
  • nsenter -t PID -n debugs a shell-less image with the host's tools while seeing the container's network stack.
  • A sidecar with --network=container: plus --pid=container: is the portable equivalent, and the pattern behind Kubernetes ephemeral containers.
  • Share the narrowest namespace that does the job, and pair every grant with dropped capabilities and read-only mounts.
  • Namespaces answer "what can it see"; cgroups answer "what can it use" — confusing the two is the most common misunderstanding here.
