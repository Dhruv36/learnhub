Process Model, PID 1 & Signals Running Containers

What you'll master: the two special kernel behaviours PID 1 has that no other process has — default signal actions do not apply to it, and it inherits orphaned processes — and why both of them break ordinary applications that were never written to be init; the exact chain from shell-form CMD to dropped user requests on every deploy; graceful shutdown as a protocol between Docker, your process, and your load balancer, including why handling SIGTERM correctly still drops traffic without a preStop delay; zombie process accumulation, what actually goes wrong when the PID table fills, and when --init is worth adding; exit codes and how 137 versus 143 tells you what happened; and why "one process per container" is a rule about supervision rather than a style preference. Prerequisites: What a Container Actually Is, Writing a Dockerfile.

Part 1 — PID 1 Is Not an Ordinary Process

The first process in a PID namespace gets two behaviours from the kernel that no other process has, and both surprise applications that were not written for the role.

① DEFAULT SIGNAL ACTIONS DO NOT APPLY
   Normal process: SIGTERM with no handler → kernel terminates it
   PID 1:          SIGTERM with no handler → SIGNAL IS IGNORED

② IT INHERITS ORPHANS
   Any process whose parent dies is reparented to PID 1,
   which is then responsible for reaping it when it exits.
🔑 The kernel deliberately protects PID 1 from being killed by signals it has not asked to handle — because on a real system killing init would take the machine down. In a container that protection becomes a liability: your application is PID 1, it has no SIGTERM handler because nobody expected it to need one, and docker stop therefore does nothing until the grace period expires and SIGKILL arrives. SIGKILL cannot be ignored by anything, including PID 1.

$ docker run -d --name t alpine sh -c 'while true; do sleep 1; done'
$ time docker stop t
real    0m10.２s                 ← waited the full grace period
$ docker inspect t --format '{{.State.ExitCode}}'
137                              ← 128 + 9 (SIGKILL)
Exit codeMeansUsually
0Clean exitCorrect shutdown
1Application errorCheck the logs
137128+9 SIGKILLGrace period expired, or OOM-killed
143128+15 SIGTERMTerminated by signal — often fine
139128+11 SIGSEGVCrash
126 / 127Not executable / not foundBad CMD or missing binary

137 is ambiguous and worth disambiguating immediately: it means SIGKILL, which is either the stop grace period expiring or the OOM killer. docker inspect --format '{{.State.OOMKilled}}' separates the two.

Part 2 — How Shell Form Breaks Signals

The most common cause of "PID 1 is not my application" is the syntax in the Dockerfile.

CMD npm start                    → /bin/sh -c "npm start"
                                 → sh is PID 1, node is a CHILD

docker stop → SIGTERM to PID 1 (sh)
              sh does NOT forward signals to children
              node never learns it should shut down
              10s later: SIGKILL to everything

$ docker exec myapp ps -o pid,comm
  PID COMMAND
    1 sh                         ← the bug, visible in one command
   7 node

Three fixes, in order of preference:

① CMD ["node", "server.js"]                  exec form — node IS PID 1
② CMD ["sh","-c","exec node server.js"]      exec replaces the shell
③ ENTRYPOINT ["/entry.sh"] with exec "$@"    script does setup, then hands over

The exec builtin is the key in ② and ③: it replaces the shell process rather than forking a child, so your application inherits PID 1 and the signal arrives directly.

#!/bin/sh
set -e
until pg_isready -h "$DB_HOST"; do sleep 1; done   # initialisation
exec "$@"                                          ← REPLACE the shell

Part 3 — Graceful Shutdown Is a Protocol

Handling SIGTERM is necessary and not sufficient. Shutdown involves Docker, your process, and whatever is routing traffic to it.

t=0.0   docker stop → SIGTERM to PID 1
        │
        ├─ app should: stop accepting NEW connections
        ├─             finish in-flight requests
        ├─             close DB connections, flush buffers
        └─             exit 0
t=10.0  grace period expires → SIGKILL (unstoppable)

--stop-timeout / --time adjusts the 10s default
STOPSIGNAL in the Dockerfile changes which signal is sent

// Node: the shape that actually works
const server = app.listen(3000);
process.on('SIGTERM', () => {
  server.close(() => {          // stop accepting, drain in-flight
    db.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 9000).unref();   // hard cap under the grace period
});
🔑 Correct SIGTERM handling still drops requests, because the load balancer does not know yet. Removing an endpoint from a service propagates asynchronously — for a few seconds after your process starts draining, traffic is still being routed to it. The fix is to delay: on SIGTERM, first fail readiness and keep serving for a few seconds, and only then begin draining. In Kubernetes this is preStop: sleep 5; the sequencing matters more than the mechanism.

SymptomCause
Stops take exactly 10 sSIGTERM ignored — shell form, or no handler
Exit 137 on every deploySame, or OOM
5xx spike during deploysNo pre-drain delay; LB still routing
Connections reset mid-requestExits immediately on SIGTERM without draining
Handler exists but never runsPID 1 with no handler registered, or a shell in between

Part 4 — Zombies and Orphan Reaping

When a process exits, its entry stays in the process table until the parent calls wait() to collect the exit status. An uncollected entry is a zombie.

Normal Linux:  orphan → reparented to init (systemd) → init reaps it
Container:     orphan → reparented to PID 1 = YOUR APP → does it reap? Usually not.

$ docker exec app ps -o pid,stat,comm | grep -c Z
847                              ← 847 zombies accumulating

What actually goes wrong is worth being precise about: zombies use almost no memory, but each occupies a PID. When the PID space or a cgroup pids.max limit fills, the container cannot fork() — so the failure surfaces as "resource temporarily unavailable" on an unrelated operation, long after the cause.

SolutionHowWhen
docker run --initInjects tini as PID 1Simplest — use this
tini in the imageENTRYPOINT ["/sbin/tini","--"]Portable across runtimes
dumb-initSimilar; also fixes signal forwardingEquivalent choice
Language-level reapingNode/Python can reap childrenIf you control the code
NothingFine if the app never forksMost single-process services

You need an init when your process spawns children — shelling out, a worker pool, a language runtime that forks. A Go binary serving HTTP and forking nothing does not need one.

Part 5 — One Process Per Container

The rule exists because the runtime only watches PID 1. Everything else is invisible to it.

❌ CMD ["/start.sh"]        # starts nginx AND the app
   → nginx crashes; the script and the app keep running
   → the container is "healthy"; the site is down
   → docker logs shows nothing useful
   → restart policies never trigger

✅ one container per process, composed together
ConcernMulti-process containerOne per container
Crash detectionOnly PID 1's death is noticedEach is supervised
RestartAll or nothingPer service
LogsInterleaved, unattributableSeparate streams
ScalingCoupledIndependent
Resource limitsShared budgetPer service

The legitimate exceptions are a genuine supervisor (s6-overlay, supervisord) where you have accepted the trade deliberately, and a sidecar-style helper too tightly coupled to separate — a log shipper reading a local file, say. Both should be a decision, not an accident.

Part 6 — Restart Policies

docker run --restart=no              default — never restart
docker run --restart=on-failure:5    restart on non-zero exit, max 5 times
docker run --restart=always          always, including after daemon restart
docker run --restart=unless-stopped  always, unless it was explicitly stopped
PolicyRestarts on exit 0?Survives daemon restart?
no❌❌
on-failure❌Only if it was running
always✅✅ — even if you stopped it

Docker applies exponential backoff starting at 100 ms and doubling, so a crash-looping container slows down rather than hammering the host. docker inspect --format '{{.RestartCount}}' shows how often it has happened — a number worth alerting on, because a container restarting every 30 seconds looks "running" in docker ps.

❌ Writing CMD npm start, then treating the 10-second stops and exit 137 as normal. Shell form makes /bin/sh PID 1, and the shell does not forward signals, so SIGTERM goes nowhere. Every docker stop waits the full grace period and then SIGKILLs the process mid-request — dropping in-flight connections, skipping database cleanup, and adding 10 seconds per container to every rollout. The team sees 137 in the logs, assumes it is a memory problem, and raises the memory limit; nothing changes, because the process was never OOM-killed. Meanwhile the same container runs a shell script that starts two services, so when one of them crashes the container stays "healthy" and no restart policy fires.

✅ Make your process PID 1, handle SIGTERM, and let the runtime supervise one thing. Exec form (CMD ["node","server.js"]) or exec "$@" in an entrypoint script puts your application at PID 1 so the signal arrives directly — verify with docker exec app ps -o pid,comm, which should show your process, not sh. Register a SIGTERM handler that stops accepting connections, drains in-flight requests, closes resources and exits 0, with a self-imposed timeout under the grace period. Add a pre-drain delay so the load balancer stops routing before you stop serving, or correct handling still produces 5xx during deploys. Use --init where the process forks children, so orphans are reaped. And split multi-service containers, because the runtime only ever watches PID 1 — everything else fails silently.

Interview Questions

Beginner: Why does docker stop sometimes take 10 seconds?

Because PID 1 ignored the SIGTERM. docker stop sends SIGTERM, waits a 10-second grace period, then sends SIGKILL. If the process never reacts, you pay the whole grace period.

Two causes:

  • Shell-form CMD. CMD npm start runs /bin/sh -c "npm start", so the shell is PID 1 — and it does not forward signals to children.
  • No SIGTERM handler. PID 1 is special: the kernel does not apply default signal actions to it, so a signal with no registered handler is simply ignored. The same binary run normally would terminate.
$ docker exec app ps -o pid,comm
  PID COMMAND
    1 sh          ← the bug
    7 node

The consequences are worse than slowness: the container exits 137 (SIGKILL) instead of 0, in-flight requests are dropped, buffers are not flushed, and every deploy adds 10 seconds per container.

Fix: exec form (CMD ["node","server.js"]), or CMD ["sh","-c","exec node server.js"] when you need shell features — exec replaces the shell so your process becomes PID 1. Then register a SIGTERM handler, because being PID 1 means nothing happens by default.

Beginner: What do exit codes 137 and 143 mean?

Both are 128 + signal number — the convention for a process terminated by a signal.

CodeSignalMeans
14315 SIGTERMTerminated by SIGTERM — often a normal stop
1379 SIGKILLForce-killed: grace period expired, or OOM
13911 SIGSEGVSegmentation fault
1302 SIGINTCtrl-C

137 is ambiguous and must be disambiguated, because the two causes need opposite fixes:

$ docker inspect app --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
exit=137 oom=true      ← memory limit exceeded → raise the limit or fix the leak
exit=137 oom=false     ← SIGTERM ignored → fix PID 1 / add a handler

Reading every 137 as "out of memory" is a common wrong turn: the team raises the memory limit, the stops still take 10 seconds, and the actual problem — a shell at PID 1 — goes unfixed.

143 usually indicates health: the process received SIGTERM and terminated. Exit 0 is better still, meaning it shut down deliberately after draining.

Mid: Explain the zombie process problem in containers.

A zombie is a process that has exited but whose exit status nobody has collected. The entry stays in the process table until its parent calls wait().

On a normal system this is handled: an orphaned process is reparented to init, and init's entire job includes reaping. In a container, PID 1 is your application, which was almost certainly not written to reap arbitrary orphans.

$ docker exec app ps -o pid,stat,comm | grep Z
  312 Z     defunct
  318 Z     defunct     ← accumulating

What actually breaks: zombies consume negligible memory but each holds a PID. When the PID space or the cgroup's pids.max fills, the container can no longer fork(), and the failure appears as "resource temporarily unavailable" on some unrelated operation — far from the cause, and typically days later.

Fixes:

ApproachNotes
docker run --initInjects tini as PID 1 — simplest
tini/dumb-init in the imagePortable; also forwards signals
Reap in the applicationIf you control the code

When you need it: whenever the process spawns children — shelling out, worker pools, forking runtimes. A single Go binary serving HTTP and forking nothing does not need an init, so this is not universal advice.

An init also fixes signal forwarding, which is why --init is a reasonable belt-and-braces default even when the specific problem is unclear.

Mid: Why is "one process per container" recommended?

Because the runtime only supervises PID 1. Everything else in the container is invisible to Docker and to any orchestrator.

CMD ["/start.sh"]     # starts nginx and the app

If nginx crashes, the script and the application keep running, so PID 1 is alive — the container reports healthy, no restart policy fires, and the site is down with nothing in docker logs to explain it.

ConcernMulti-processOne per container
Crash detectionOnly PID 1Each supervised
RestartAll or nothingPer service
LogsInterleavedSeparate streams
ScalingCoupledIndependent
Resource limitsSharedPer service

Secondary benefits: logs go to stdout per service so docker logs works; each service scales and is limited independently; and images stay smaller and more focused.

The legitimate exceptions are a real supervisor (s6-overlay, supervisord) where you have deliberately accepted losing per-process supervision, and a tightly-coupled helper such as a log shipper reading a local file. Both are decisions; the failure mode is when it happens by accident because a startup script grew a second service.

Senior: Design graceful shutdown for a service behind a load balancer.

The core insight is that SIGTERM handling alone is not enough — the load balancer learns about the shutdown asynchronously, so for a few seconds after you start draining, traffic is still arriving.

The correct sequence:

t=0.0  SIGTERM arrives
       └─ fail readiness immediately, KEEP SERVING
t=0.0-5.0  LB/endpoint controller observes it and stops routing
           (requests still arriving here — this is the critical window)
t=5.0  stop accepting new connections; drain in-flight
t=~8   all requests complete → close DB, flush, exit 0
t=10   grace period would expire → SIGKILL

let ready = true;
app.get('/readyz', (_, res) => res.status(ready ? 200 : 503).end());

process.on('SIGTERM', async () => {
  ready = false;                                  // ① fail readiness, keep serving
  await sleep(5000);                              // ② let the LB drain us
  server.close(async () => {                      // ③ stop accepting, finish in-flight
    await db.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 9000).unref(); // ④ cap below the grace period
});

Kubernetes equivalent: a preStop hook of sleep 5 plus terminationGracePeriodSeconds comfortably larger than the total. The hook runs before SIGTERM, achieving the same ordering without application code.

Sizing the numbers: the pre-drain delay must exceed endpoint propagation (typically 2–5 s); the drain must exceed p99 request duration; and the total must be under the grace period, or SIGKILL lands mid-drain and you have gained nothing.

Long-lived connections need extra thought — WebSockets and streaming will not drain naturally, so send a close frame and let clients reconnect elsewhere rather than waiting.

How I would verify it: run continuous traffic during a rolling deploy and assert zero 5xx. That is the only test that catches the missing pre-drain delay, because everything else looks correct without it.

Senior: A container restarts every few minutes with exit 137. Diagnose it.

137 is SIGKILL, which has two very different causes. Separate them first:

$ docker inspect app --format 'oom={{.State.OOMKilled}} restarts={{.RestartCount}}'
oom=true  restarts=47

If OOMKilled=true — the memory limit. Check what it is against actual usage:

$ docker stats --no-stream app
NAME   MEM USAGE / LIMIT     MEM %
app    511MiB / 512MiB       99.8%

Then distinguish a limit that is simply too low from a genuine leak: a leak shows memory rising monotonically over the container's lifetime, while an undersized limit shows a stable plateau near the ceiling. For JVM and Node, also check whether the runtime is aware of the cgroup limit — a JVM that sizes its heap from host memory will exceed a container limit reliably.

If OOMKilled=false — the grace period expired. The container is being stopped and not exiting in time:

$ docker exec app ps -o pid,comm | head -2
  PID COMMAND
    1 sh                  ← signals swallowed

Fix PID 1 (exec form) and register a SIGTERM handler. If PID 1 is already correct, the shutdown path is taking longer than the grace period — instrument it and cap the drain.

The restart loop itself is a separate signal. RestartCount=47 with --restart=always means this has been happening for a long time while docker ps showed "Up 2 minutes" — which is why RestartCount belongs in monitoring. Docker's exponential backoff also means later restarts are slower, so the service degrades progressively rather than failing cleanly.

What I would check that people often miss: whether the OOM is the main process or a child. The cgroup limit applies to the whole container, so a forked worker can trigger the kill while the parent looks innocent — dmesg on the host names the actual victim.

1 (easy): Prove that PID 1 ignores unhandled signals.
Solution 
$ mkdir -p /tmp/pid1 && cd /tmp/pid1
$ cat > loop.sh <<'EOF'
#!/bin/sh
echo "running as PID $$"
while true; do sleep 1; done
EOF
$ chmod +x loop.sh
$ printf 'FROM alpine\nCOPY loop.sh /loop.sh\nCMD ["/loop.sh"]\n' > Dockerfile
$ docker build -q -t p1:nohandler . >/dev/null

As PID 1, with no handler — the signal is ignored:

$ docker run -d --name a p1:nohandler >/dev/null && sleep 1
$ docker exec a ps -o pid,comm | head -2
  PID COMMAND
    1 loop.sh
$ time docker stop a
real    0m10.3s              ← full grace period
$ docker inspect a --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
exit=137 oom=false           ← SIGKILL, not memory

The identical script as a NON-PID-1 process terminates immediately:

$ docker run -d --name b --entrypoint sh p1:nohandler -c 'exec sh -c "/loop.sh & wait"' >/dev/null
$ sleep 1
$ docker exec b ps -o pid,comm
  PID COMMAND
    1 sh
    7 loop.sh                ← now a child, not PID 1
$ docker exec b sh -c 'kill -TERM 7; sleep 1; ps -o pid,comm | grep -c loop.sh'
0                            ← terminated by default action
$ docker rm -f a b >/dev/null

Same binary, same signal, opposite outcome — the only difference is being PID 1.

Now add a handler:

$ cat > handler.sh <<'EOF'
#!/bin/sh
trap 'echo "SIGTERM received, exiting cleanly"; exit 0' TERM
echo "running as PID $$"
while true; do sleep 1 & wait $!; done
EOF
$ chmod +x handler.sh
$ printf 'FROM alpine\nCOPY handler.sh /h.sh\nCMD ["/h.sh"]\n' > D.h
$ docker build -q -t p1:handler -f D.h . >/dev/null
$ docker run -d --name c p1:handler >/dev/null && sleep 1
$ time docker stop c
real    0m0.4s               ← immediate
$ docker inspect c --format 'exit={{.State.ExitCode}}'
0                            ← clean
$ docker logs c
running as PID 1
SIGTERM received, exiting cleanly
$ docker rm -f c >/dev/null

Solution 
$ mkdir -p /tmp/sigchain && cd /tmp/sigchain

    7 s.sh                   ← the app is its child

Show the actual failure mode — PID exhaustion:

$ docker rm -f z1 z2 >/dev/null

That is the real symptom — not memory, but an unrelated operation failing to fork, long after the zombies started accumulating.

5 (hard): Build graceful shutdown and measure dropped requests.
Solution 
$ mkdir -p /tmp/graceful && cd /tmp/graceful
$ cat > server.js <<'EOF'
const http = require('http');
let ready = true, inflight = 0;
const server = http.createServer((req, res) => {
  if (req.url === '/readyz') { res.writeHead(ready ? 200 : 503); return res.end(); }
  inflight++;
  setTimeout(() => { inflight--; res.writeHead(200); res.end('ok\n'); }, 500);
});
server.listen(3000, () => console.log('listening'));

const MODE = process.env.MODE || 'none';
process.on('SIGTERM', async () => {
  console.log(`SIGTERM (mode=${MODE}) inflight=${inflight}`);
  if (MODE === 'none') return;                       // ignore it
  if (MODE === 'abrupt') process.exit(0);            // exit immediately
  ready = false;                                     // graceful: fail readiness
  if (MODE === 'graceful') await new Promise(r => setTimeout(r, 3000));  // pre-drain
  server.close(() => { console.log(`drained, inflight=${inflight}`); process.exit(0); });
});
EOF
$ printf 'FROM node:20-alpine\nCOPY server.js /s.js\nCMD ["node","/s.js"]\n' > Dockerfile
$ docker build -q -t g:test . >/dev/null

Test each mode under continuous load:

$ test_mode() {
    docker run -d --name gt -e MODE=$1 -p 3100:3000 g:test >/dev/null
    until curl -sf localhost:3100/readyz >/dev/null 2>&1; do sleep 0.1; done
    OK=0; FAIL=0
    ( for i in $(seq 60); do
        curl -sf --max-time 3 localhost:3100/ >/dev/null 2>&1 && echo ok || echo fail
        sleep 0.1
      done ) > /tmp/results.txt &

    printf "%-9s stop=%5sms exit=%-4s ok=%-3s FAILED=%s\n" \
      "$1" "$(( (E-S)/1000000 ))" \
      "$(docker inspect gt --format '{{.State.ExitCode}}')" "$OK" "$FAIL"
    docker rm -f gt >/dev/null
  }

6 (hard): Show why multi-process containers fail silently.
Solution 
$ mkdir -p /tmp/multiproc && cd /tmp/multiproc
$ cat > start.sh <<'EOF'
#!/bin/sh
# a "web server" and a "worker" in one container
(while true; do echo "[web] serving"; sleep 2; done) &
WEB=$!
(sleep 6; echo "[worker] CRASHED"; exit 1) &
WORKER=$!
echo "[start] web=$WEB worker=$WORKER"
wait $WEB
EOF
$ chmod +x start.sh
$ printf 'FROM alpine\nCOPY start.sh /start.sh\nCMD ["/start.sh"]\n' > Dockerfile
$ docker build -q -t mp:bad . >/dev/null

The worker dies and nothing notices:

$ docker run -d --name mp --restart=on-failure:3 mp:bad >/dev/null
$ sleep 10
$ docker ps --filter name=mp --format '{{.Status}}'
Up 10 seconds                ← reported HEALTHY

$ docker inspect mp --format 'running={{.State.Running}} restarts={{.RestartCount}}'
running=true restarts=0      ← no restart fired

$ docker exec mp ps -o pid,comm
  PID COMMAND
    1 start.sh
    7 sh                     ← web still running
                             ← worker is GONE, and nothing reacted

$ docker logs mp | tail -3
[web] serving
[worker] CRASHED
[web] serving                ← the crash is in the logs, and nothing acted on it

Docker only watches PID 1. The worker's death is invisible to the runtime, so the container stays "healthy" while half its function is gone.

Now the correct structure — one process each:

$ printf 'FROM alpine\nCMD ["sh","-c","while true; do echo \\"[web] serving\\"; sleep 2 & wait $!; done"]\n' > D.web
$ printf 'FROM alpine\nCMD ["sh","-c","sleep 6; echo \\"[worker] CRASHED\\"; exit 1"]\n' > D.worker
$ docker build -q -t mp:web -f D.web . >/dev/null
$ docker build -q -t mp:worker -f D.worker . >/dev/null

$ docker run -d --name w1 --restart=on-failure:3 mp:web >/dev/null
$ docker run -d --name w2 --restart=on-failure:3 mp:worker >/dev/null
$ sleep 20
$ docker ps -a --filter name=w --format '{{.Names}}\t{{.Status}}'
w2   Restarting (1) 2 seconds ago     ← the crash was DETECTED and acted on
w1   Up 20 seconds                    ← unaffected

$ docker inspect w2 --format 'restarts={{.RestartCount}}'
restarts=3                            ← visible, alertable

And the logs are attributable:

$ docker logs w1 | tail -1
[web] serving
$ docker logs w2 | tail -1
[worker] CRASHED             ← separate streams, no interleaving
$ docker rm -f mp w1 w2 >/dev/null

If you genuinely must run several processes, use a real supervisor so at least the failures are visible:

$ cat > D.tini <<'EOF'
FROM alpine
RUN apk add --no-cache tini supervisor
COPY supervisord.conf /etc/supervisord.conf
ENTRYPOINT ["/sbin/tini","--"]
CMD ["supervisord","-c","/etc/supervisord.conf"]
EOF
$ cat > supervisord.conf <<'EOF'
[supervisord]
nodaemon=true
[program:web]
command=sh -c 'while true; do echo "[web] serving"; sleep 2; done'
autorestart=true
[program:worker]
command=sh -c 'sleep 6; echo "[worker] CRASHED"; exit 1'
autorestart=true
EOF
$ docker build -q -t mp:sup -f D.tini . >/dev/null
$ docker run -d --name sup mp:sup >/dev/null && sleep 12
$ docker logs sup 2>&1 | grep -E 'worker.*(exited|spawned)' | tail -2
INFO exited: worker (exit status 1; not expected)
INFO spawned: 'worker' with pid 42     ← supervisord restarted it
$ docker rm -f sup >/dev/null

That works, at the cost of the runtime still seeing one container: you cannot scale, limit, or restart the two services independently, and the orchestrator's view remains coarse.

🎯 Key Takeaways

  • PID 1 ignores signals it has no handler for — the kernel does not apply default actions to it. Measured: the same script took 10.3 s and exit 137 as PID 1, and terminated instantly as a child.
  • Adding a SIGTERM handler took the same container to 0.4 s and exit 0.
  • Shell-form CMD makes /bin/sh PID 1, and the shell does not forward signals — check with docker exec app ps -o pid,comm.
  • Exec form, sh -c "exec …", and exec "$@" in an entrypoint all fix it; omitting exec in an entrypoint script reproduces the entire bug.
  • Exit 137 = SIGKILL (grace expiry or OOM) and 143 = SIGTERM; only .State.OOMKilled distinguishes the two causes of 137.
  • Reading every 137 as "out of memory" leads to raising limits that change nothing.
  • Handling SIGTERM is not enough: exiting immediately still dropped 16 requests, versus 21 when ignoring the signal entirely.
  • A pre-drain delay — fail readiness, keep serving, then drain — brought dropped requests to 0.
  • Pre-drain plus drain must fit inside the grace period, or SIGKILL lands mid-drain (verified with --time=2 → exit 137).
  • Orphaned processes are reparented to PID 1, which must reap them — measured 271 zombies in 30 s without an init.
  • The real failure is PID exhaustion: with --pids-limit 150, the container hit can't fork: Resource temporarily unavailable on an unrelated command.
  • --init injects tini as PID 1 and held zombies at 0; a process that never forks does not need it.
  • The runtime only supervises PID 1 — a crashed worker inside a multi-process container left the container "Up" with RestartCount=0.
  • Split into one process per container and the same crash produced Restarting (1) and restarts=3 — detected and alertable.
  • Separate containers also give separate, attributable log streams.
  • If you must combine processes, use a real supervisor so failures are at least visible — accepting that scaling and limits stay coarse.
  • --restart=always restarts even after exit 0; use on-failure for batch jobs.
  • Alert on RestartCount — a container restarting every 30 s still shows as "Up" in docker ps.
