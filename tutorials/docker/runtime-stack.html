The Runtime Stack: runc, containerd, Docker Foundations

What you'll master: which component actually does what when you type docker run, and why that matters the moment something breaks; the containerd-shim and the property it buys — containers survive a daemon restart, which is why "restarting Docker kills everything" stopped being true; the OCI specifications that make images and runtimes interchangeable, and what "Docker is just one implementation" concretely means; why Kubernetes removed dockershim and why that was not "Kubernetes dropping Docker images"; the alternative runtimes — crun, gVisor, Kata — and the specific problem each solves; rootless and daemonless designs (Podman, Buildah); and how to drive containerd directly with ctr and nerdctl when the Docker CLI is not the right tool. Prerequisites: Namespaces, cgroups.

Part 1 — What Happens on docker run

Five components are involved, and each has one job. Knowing the division tells you where to look when a container fails to start.

docker CLI                      talks HTTP to the daemon over a socket
   │  POST /containers/create
   ▼
dockerd                         image management, networking, volumes, API
   │  gRPC
   ▼
containerd                      container lifecycle, image pull, snapshots
   │  spawns one shim per container
   ▼
containerd-shim-runc-v2         ★ stays alive for the container's lifetime
   │  exec
   ▼
runc                            creates namespaces + cgroups, execs, then EXITS
   │
   ▼
your process                    reparented to the shim
🔑 runc exits immediately after starting the container — it is not the container's parent. Its entire job is to apply the OCI runtime specification: set up namespaces and cgroups, pivot the root filesystem, drop capabilities, apply seccomp, and exec the entry process. Then it is gone. That is why you never see runc in ps for a running container, and why "runc" appearing in an error message means the failure happened during creation, not while running.

$ docker run -d --name web nginx
$ ps -ef --forest | grep -A3 containerd-shim
root  1204     1  containerd-shim-runc-v2 -namespace moby -id 3f8a91c04e7b...
root  48213  1204   \_ nginx: master process nginx -g daemon off;
systemd+ 48260 48213     \_ nginx: worker process
                ↑ the shim is the parent — NOT dockerd, NOT runc

Part 2 — The Shim: Why Containers Survive a Daemon Restart

The shim exists to decouple container lifetime from daemon lifetime. Each container gets its own shim process, parented to init rather than to dockerd.

The shim's jobWhy it matters
Be the container's parentReaps zombies; keeps the process tree valid
Hold stdio/TTY openLogs and attach survive a daemon restart
Report the exit codeExit status is captured even if containerd is down
Keep the container runningRestarting dockerd does not kill containers
$ docker run -d --name survivor nginx
$ docker inspect -f '{{.State.Pid}}' survivor
48213

$ sudo systemctl restart docker            # restart the DAEMON
$ ps -p 48213 -o pid,comm
  PID COMMAND
48213 nginx                                ← still running, uninterrupted

$ docker ps --filter name=survivor --format '{{.Status}}'
Up 4 minutes                               ← reattached, uptime unbroken

This was not always true. Before the shim (Docker < 1.11), dockerd was the direct parent of every container, so restarting or upgrading the daemon killed every workload on the host. The shim is what made "upgrade Docker without downtime" possible, and it is the reason containerd can be restarted independently in Kubernetes clusters.

🔑 The trade is one shim process per container. On a host running 200 containers there are 200 shim processes, each consuming a few MB. That is the price of daemon-independent lifetimes, and it is why shim memory usage shows up in dense-host capacity planning.

Part 3 — The OCI Specifications

The Open Container Initiative standardises three things, and that standardisation is what makes the ecosystem interchangeable.

SpecificationDefinesImplementations
Image SpecLayer format, manifest, config JSONDocker, BuildKit, Buildah, Kaniko, ko
Runtime SpecThe bundle (rootfs + config.json) and lifecyclerunc, crun, gVisor, Kata, youki
Distribution SpecRegistry HTTP API for push/pullDocker Hub, ECR, GCR, Harbor, Zot
# an OCI bundle is just a directory: rootfs + config.json
$ mkdir -p /tmp/bundle/rootfs
$ docker export $(docker create alpine) | tar -C /tmp/bundle/rootfs -xf -
$ cd /tmp/bundle && runc spec              # generates config.json
$ sudo runc run mycontainer
/ # echo "no Docker involved"

That is the whole runtime contract: a root filesystem and a JSON file describing namespaces, cgroups, capabilities, and the process to run. Any OCI runtime can consume it, which is why swapping runc for crun or gVisor is a configuration change rather than a migration.

"Docker images" are OCI images. An image built by Docker runs under containerd, CRI-O, Podman, or any OCI runtime — the name is historical, not a format.

Part 4 — Kubernetes and the dockershim Removal

This generated more confusion than any other change in the ecosystem, and the confusion is worth clearing precisely because it is a common interview question.

BEFORE (Kubernetes ≤ 1.23):
  kubelet → dockershim → dockerd → containerd → shim → runc
            └────┬────┘
        an adapter maintained IN Kubernetes, translating CRI to Docker's API

AFTER (Kubernetes ≥ 1.24):
  kubelet → containerd → shim → runc          ← one fewer hop, no adapter
  kubelet → CRI-O → runc                      ← or any CRI runtime
🔑 Removing dockershim did not stop Kubernetes running Docker-built images. Images are OCI artefacts and were never the issue — what was removed was the adapter that let kubelet talk to dockerd's API. Since dockerd already delegated to containerd, the change deleted a redundant hop that Kubernetes had to maintain. Every image built with docker build still runs unchanged.

ConcernReality
"My Docker images stop working"No — they are OCI images
"I cannot use docker build"You can — build and runtime are separate concerns
Docker socket mounted in a podGenuinely breaks — there is no dockerd
Tooling calling the Docker API on nodesBreaks — use CRI or nerdctl
Node-level log collectionLog paths and formats changed

The real migration work was the last three rows: anything that talked to dockerd on a node rather than using container images. Docker-in-Docker CI patterns that mounted the socket were the most common breakage, and the answer is a daemonless builder such as Kaniko or Buildah, or BuildKit in rootless mode.

Part 5 — Alternative Runtimes

Because the runtime spec is a contract, the low-level runtime is swappable. Each alternative exists for a specific reason.

RuntimeWritten inSolvesCost
runcGoThe reference implementation—
crunCFaster start, lower memory; better cgroup v2Less ubiquitous
gVisor (runsc)GoUser-space kernel — intercepts syscallsSyscall overhead; some incompatibility
Kata ContainersGo/RustA real VM per container~100 MB and ~1 s per container
youkiRustMemory-safe, fastNewer
# configure an alternative runtime in /etc/docker/daemon.json
{
  "runtimes": {
    "gvisor": { "path": "/usr/local/bin/runsc" },
    "kata":   { "path": "/usr/bin/kata-runtime" }
  }
}

$ docker run --runtime=gvisor --rm alpine dmesg | head -1
[    0.000000] Starting gVisor...            ← a user-space kernel, not the host's

gVisor and Kata exist for the same reason: the shared kernel that makes containers fast also makes them a weak security boundary. gVisor puts a user-space kernel between the container and the host so most syscalls never reach the real kernel; Kata gives each container a lightweight VM. Both trade performance for a second isolation boundary — the trade discussed in What a Container Actually Is.

Part 6 — Daemonless and Rootless Alternatives

Docker's architecture has a root-owned daemon at its centre, which is a security and operational characteristic worth understanding rather than accepting by default.

DOCKER                          PODMAN
docker CLI                      podman CLI
   │ socket                        │ fork/exec — NO daemon
   ▼                               ▼
dockerd (root)                  conmon (per container)
   ▼                               ▼
containerd → shim → runc        runc/crun
DockerPodman
ArchitectureClient–daemonFork–exec, daemonless
Runs as rootDaemon does, by defaultRootless by default
SocketRoot-owned; mounting it = host rootOptional, user-scoped
systemd integrationIndirectNative (podman generate systemd)
CLI—Largely compatible (alias docker=podman)

Rootless Docker exists too and gets most of the same benefit — the daemon runs as an unprivileged user inside a user namespace, so a container escape lands unprivileged on the host. The costs are real: no binding to ports below 1024 without extra configuration, slower networking through a userspace proxy, and some storage drivers unavailable.

$ dockerd-rootless-setuptool.sh install
$ export DOCKER_HOST=unix:///run/user/1000/docker.sock
$ docker info --format '{{.SecurityOptions}}'
[name=rootless name=seccomp,profile=builtin]

Driving containerd directly is worth knowing for Kubernetes nodes, where dockerd may not exist at all:

# ctr — containerd's low-level debug CLI (namespaces are explicit)
$ sudo ctr -n k8s.io images list | head -3
$ sudo ctr -n k8s.io containers list

# nerdctl — a Docker-compatible CLI over containerd
$ sudo nerdctl run -d --name web nginx
$ sudo nerdctl ps

# crictl — the CRI-level tool kubelet-adjacent debugging uses
$ sudo crictl ps
$ sudo crictl logs <container-id>

❌ Treating "Docker" as a single indivisible thing, and mounting the Docker socket to get container access. A CI job needs to build images, so the pipeline mounts /var/run/docker.sock into the build container — the standard "Docker-in-Docker" recipe. That socket is the daemon's full API, and the daemon runs as root, so any code in that container can start a privileged container mounting the host filesystem: it is root on the node, not a sandboxed build. The same conflation then breaks the Kubernetes migration, because the team believes removing dockershim means their Docker-built images stop working, when the actual breakage is precisely this socket-mounting pattern — on a containerd node there is no dockerd to talk to.

✅ Separate the layers: image format, build tool, and runtime are independent. Images are OCI artefacts that run on any OCI runtime, so Docker-built images work under containerd, CRI-O, and Podman unchanged. For building without the socket, use a daemonless builder — Kaniko, Buildah, or BuildKit in rootless mode — which needs no privileged access to a node. For debugging on nodes that have no dockerd, use nerdctl for a Docker-like CLI over containerd, or crictl at the CRI level. And treat the Docker socket as a root credential rather than a file: never mount it into workloads, and prefer rootless Docker or Podman where the daemon itself is unprivileged.

Interview Questions

Beginner: What happens when you run docker run?

Five components, each with one job:

docker CLI  → HTTP request to the daemon socket
dockerd     → images, networking, volumes; delegates the container itself
containerd  → lifecycle, image pull, snapshots; spawns one shim per container
shim        → the container's PARENT; holds stdio, reports exit code
runc        → creates namespaces + cgroups, execs the process, then EXITS

The two facts that matter practically:

1. runc is not the parent. It applies the OCI runtime spec — namespaces, cgroups, capabilities, seccomp, pivot root — then execs and disappears. So a "runc" error message means creation failed, not that a running container had a problem.

2. The shim is the parent, and it is parented to init rather than dockerd:

$ ps -ef --forest | grep -A2 containerd-shim
root  1204     1  containerd-shim-runc-v2 -namespace moby -id 3f8a...
root 48213  1204   \_ nginx: master process

That is what allows the daemon to be restarted or upgraded without killing running containers.

The layering also explains why Kubernetes could remove dockershim: dockerd was already delegating to containerd, so kubelet talking to containerd directly removes a hop rather than changing how containers run.

Beginner: What is the OCI, and what does it standardise?

The Open Container Initiative defines three specifications that make the container ecosystem interchangeable rather than vendor-specific.

SpecDefinesImplementations
ImageLayers, manifest, configDocker, BuildKit, Buildah, Kaniko
RuntimeBundle (rootfs + config.json), lifecyclerunc, crun, gVisor, Kata
DistributionRegistry push/pull APIHub, ECR, GCR, Harbor

The runtime contract is remarkably small: a directory containing a root filesystem and a config.json describing namespaces, cgroups, capabilities and the process to run. Any OCI runtime can consume it:

$ mkdir -p bundle/rootfs && docker export $(docker create alpine) | tar -C bundle/rootfs -xf -
$ cd bundle && runc spec && sudo runc run demo

The practical consequence is that "Docker images" is a misnomer — they are OCI images, and they run on containerd, CRI-O, Podman, or anything else implementing the spec. That is why the dockershim removal did not break images, and why swapping runc for gVisor is a configuration change rather than a migration.

Mid: What is the containerd-shim, and why does it exist?

The shim is a small process that sits between containerd and the container, one per container. It exists to decouple container lifetime from daemon lifetime.

JobConsequence
Be the container's parentReaps zombies; keeps the process tree valid
Hold stdio and the TTYLogs and attach survive a daemon restart
Capture the exit codeExit status is not lost if containerd is down
Keep the container runningRestarting dockerd does not kill workloads

Before the shim (Docker < 1.11), dockerd was the direct parent of every container, so restarting or upgrading the daemon killed everything on the host. That is why "don't restart Docker in production" used to be real advice and no longer is:

$ docker run -d --name survivor nginx
$ PID=$(docker inspect -f '{{.State.Pid}}' survivor)
$ sudo systemctl restart docker
$ ps -p $PID -o comm=          # nginx — never stopped

The cost is one shim process per container, a few MB each, which becomes a real line item on hosts running hundreds of containers.

The shim is also why runc can exit immediately: something has to remain as the parent to reap children and report the exit status, and that is precisely the shim's role.

Mid: Why did Kubernetes remove dockershim, and what actually broke?

dockershim was an adapter inside Kubernetes translating the CRI to dockerd's API. Kubernetes maintained it for one runtime, which was both a maintenance burden and an unnecessary hop — since dockerd already delegated to containerd:

before: kubelet → dockershim → dockerd → containerd → shim → runc
after:  kubelet → containerd → shim → runc

What did NOT break: images. Docker-built images are OCI images and run unchanged under containerd or CRI-O. docker build remains perfectly valid, because building and running are separate concerns.

What genuinely broke was anything talking to dockerd on a node:

  • Pods mounting /var/run/docker.sock — the most common case, usually Docker-in-Docker CI. There is no daemon to talk to. The fix is a daemonless builder: Kaniko, Buildah, or rootless BuildKit.
  • Node tooling calling the Docker API — monitoring agents, log shippers, cleanup scripts. They move to CRI (crictl) or containerd's API.
  • Log collection, because paths and formats differ between dockerd and containerd.

The confusion was worth clearing because it reveals the layering: image format, build tool, and runtime are independent. Conflating them is what produced the widespread belief that Kubernetes had "dropped Docker" — and it is the same conflation that leads teams to mount the Docker socket in the first place.

Senior: When would you use gVisor or Kata instead of runc?

Both exist to add an isolation boundary that runc cannot provide, because a standard container shares the host kernel — so a kernel privilege-escalation bug is a container escape.

gVisor (runsc) puts a user-space kernel between the container and the host. Syscalls are intercepted and serviced by gVisor's own implementation, so only a small, audited subset ever reaches the host kernel — dramatically reducing the attack surface.

  • Costs: syscall-heavy workloads slow measurably; some syscalls are unimplemented, so unusual software may not run; raw device access is limited.
  • Fits: untrusted code with moderate syscall rates — function-as-a-service, sandboxed user code, CI for public contributions.

Kata Containers runs each container in a lightweight VM with its own kernel, giving a genuine hypervisor boundary while keeping a container-shaped interface (it is an OCI runtime, so it drops into Kubernetes as a RuntimeClass).

  • Costs: ~100 MB memory and ~1 s start time per container; device passthrough and storage need thought.
  • Fits: hard multi-tenancy, regulated isolation requirements, workloads needing full syscall compatibility with a real boundary.

How I would choose: start with runc plus proper hardening — non-root user, dropped capabilities, seccomp, read-only root filesystem, no Docker socket. That covers first-party workloads. If the workload is genuinely untrusted, ask whether it is syscall-light (gVisor) or needs full compatibility (Kata). If compliance demands hypervisor-level separation, Kata or per-tenant VMs are the only answers that satisfy an auditor.

The deployment mechanism is the same in both cases — a RuntimeClass in Kubernetes or --runtime in Docker — because the OCI runtime spec makes them interchangeable. That interchangeability is what lets you apply strong isolation selectively, to the untrusted subset of workloads, instead of paying for it everywhere.

Senior: Design a CI system that builds images without mounting the Docker socket.

The socket must go, because mounting it grants host root: any code in the build container can ask the root-owned daemon to start a privileged container mounting /. In shared CI, that means any repository with a pipeline can compromise the runners and every secret they hold.

Options, and what each trades:

ApproachPrivilegesNotes
KanikoNoneBuilds in userspace inside a pod; good caching to a registry
BuildahRootlessFull Dockerfile support; fits Podman ecosystems
BuildKit rootlessRootlessBest cache and multi-arch support
ko / jibNoneLanguage-specific; no Dockerfile at all
DinD with --privilegedPrivilegedIsolated from the host daemon but still privileged

What I would build: BuildKit in rootless mode as a shared daemon, or Kaniko per job where pod-level isolation matters more than build speed. Cache exported to the registry (--cache-to type=registry) so cold runners stay fast, and multi-arch builds so laptop architecture never determines what production gets.

Supply-chain controls that belong in the same design: build from pinned base digests rather than tags; generate an SBOM and provenance attestation during the build; sign the resulting image (cosign) and verify signatures at admission; and push by digest so what was scanned is provably what deploys.

The migration order I would recommend is to move builds off the socket first — that removes the largest privilege — then tighten the supply-chain controls, because a signed image built by a compromised runner proves nothing.

One caveat worth stating: rootless builders cannot do everything. Builds that require privileged operations (loop devices, certain mounts) will fail, and the answer there is usually to restructure the build rather than to restore the socket.

1 (easy): Trace the process tree from dockerd to your container.
Solution 
$ docker run -d --name tree nginx
$ PID=$(docker inspect -f '{{.State.Pid}}' tree)
$ ps -ef --forest | grep -B2 -A3 "$PID"
root     1204     1  containerd-shim-runc-v2 -namespace moby -id 3f8a91c04e7b -address /run/containerd/containerd.sock

$ ps -o ppid= -p 1204
      1                        ← parented to init, deliberately

$ pgrep dockerd
1150                           ← dockerd is NOT in this container's ancestry

   1204                        ← the shim

$ pgrep -a runc
$ echo "runc processes: $?"

$ (for i in $(seq 200); do pgrep -a runc && break; sleep 0.01; done) &

                               ← visible for a few milliseconds, then gone

2 (easy): Prove containers survive a daemon restart.
Solution 
$ docker run -d --name survivor nginx
$ PID=$(docker inspect -f '{{.State.Pid}}' survivor)
$ START=$(docker inspect -f '{{.State.StartedAt}}' survivor)
$ echo "pid=$PID started=$START"
pid=48213 started=2026-08-18T15:40:12.334Z

# generate some traffic so we can confirm continuity
$ docker exec survivor sh -c 'echo "before restart" >> /tmp/marker'

$ sudo systemctl restart docker
$ sleep 3

The container never stopped:

$ ps -p $PID -o pid,etime,comm
  PID     ELAPSED COMMAND
48213       04:12 nginx                    ← uptime unbroken across the restart

$ docker inspect survivor --format 'pid={{.State.Pid}} started={{.State.StartedAt}}'
pid=48213 started=2026-08-18T15:40:12.334Z ← same PID, same start time

$ docker exec survivor cat /tmp/marker
before restart                             ← same container, state intact

The shim is what made this possible:

$ ps -o pid,ppid,comm -p $(ps -o ppid= -p $PID)
  PID  PPID COMMAND
 1204     1 containerd-shim-runc-v2        ← survived; parented to init

$ ps -o etime= -p 1204
   04:15                                   ← the shim never restarted either

Contrast with killing the shim, which does stop the container:

$ docker run -d --name doomed nginx
$ DPID=$(docker inspect -f '{{.State.Pid}}' doomed)
$ SHIM=$(ps -o ppid= -p $DPID | tr -d ' ')
$ sudo kill -9 $SHIM
$ sleep 2
$ docker ps -a --filter name=doomed --format '{{.Status}}'
Exited (137) 1 second ago                  ← the container died with its shim

The hierarchy is the point: dockerd can come and go freely, but the shim is the container's actual lifeline. Before Docker 1.11 there was no shim and dockerd was the direct parent, so every daemon restart killed every workload on the host.

$ docker rm -f survivor doomed >/dev/null
3 (medium): Run a container with runc directly, no Docker.
Solution 
# 1. build an OCI bundle: rootfs + config.json
$ mkdir -p /tmp/bundle/rootfs
$ docker export $(docker create alpine) | tar -C /tmp/bundle/rootfs -xf -
$ cd /tmp/bundle
$ runc spec                        # generates a default config.json
$ ls
config.json  rootfs

The config.json IS the runtime contract:

$ python3 -c "
import json; c=json.load(open('config.json'))
print('process:  ', c['process']['args'])
print('namespaces:', [n['type'] for n in c['linux']['namespaces']])
print('caps kept: ', len(c['process']['capabilities']['bounding']))
print('readonly:  ', c['root']['readonly'])
"
process:   ['sh']
namespaces: ['pid', 'network', 'ipc', 'uts', 'mount']
caps kept:  14
readonly:   True

Run it:

$ sudo runc run demo
/ # hostname
runc
/ # ps -eo pid,comm
  PID COMMAND
    1 sh                          ← PID 1 in its own namespace
    6 ps
/ # cat /etc/os-release | head -1
NAME="Alpine Linux"
/ # exit

No Docker daemon, no containerd, no shim — runc alone created namespaces, applied cgroups, and executed the process.

Edit the config to change behaviour, showing it is declarative:

$ python3 - <<'PY'
import json
c = json.load(open('config.json'))
c['process']['args'] = ['sh','-c','echo from-config; cat /sys/fs/cgroup/memory.max']
c['linux'].setdefault('resources',{})['memory'] = {'limit': 64*1024*1024}
c['hostname'] = 'handmade'
json.dump(c, open('config.json','w'), indent=2)
PY
$ sudo runc run demo2
from-config
67108864                         ← the 64MB limit we declared

Observe the lifecycle states runc exposes:

$ sudo runc create paused-demo && sudo runc list
ID           PID    STATUS   BUNDLE       CREATED
paused-demo  52301  created  /tmp/bundle  2026-08-18T15:52:03Z

$ sudo runc start paused-demo && sudo runc list
ID           PID    STATUS   BUNDLE       CREATED
paused-demo  52301  running  /tmp/bundle  2026-08-18T15:52:03Z

$ sudo runc kill paused-demo KILL && sudo runc delete paused-demo

That create/start/kill/delete cycle is exactly what containerd drives — Docker's lifecycle commands are this API with images, networking, and volumes layered on top.

Start-time comparison:

$ for rt in runc crun gvisor; do

gVisor really is a different kernel:

$ docker run --rm alpine dmesg 2>/dev/null | head -1
dmesg: klogctl: Operation not permitted     ← standard container: host kernel, masked

$ docker run --rm --runtime=gvisor alpine dmesg | head -2
[    0.000000] Starting gVisor...
[    0.324681] Checking naughty and nice process list...

$ docker run --rm --runtime=gvisor alpine uname -r
4.4.0                                        ← gVisor's reported version, NOT the host's
$ uname -r
6.5.0-27-generic

That difference is the security property: syscalls are serviced by gVisor in user space, so most never reach the host kernel at all.

Measure the syscall overhead, which is gVisor's cost:

$ cat > /tmp/sysbench.sh <<'EOF'
S=$(date +%s%N)
i=0; while [ $i -lt 20000 ]; do cat /proc/self/stat > /dev/null; i=$((i+1)); done
E=$(date +%s%N); echo "$(( (E-S)/1000000 ))ms"
EOF
$ for rt in runc gvisor; do
    printf "%-8s " "$rt"
    docker run --rm --runtime=$rt -v /tmp/sysbench.sh:/b.sh alpine sh /b.sh
  done

gvisor   11847ms      ← 3.5x slower on a syscall-heavy loop

And CPU-bound work is barely affected, which is what makes the trade workload-dependent:

$ for rt in runc gvisor; do

The conclusion: gVisor is affordable for compute-bound untrusted workloads and expensive for I/O- or syscall-heavy ones. Measure the specific workload rather than accepting a general "gVisor is slow" claim.

6 (hard): Show why mounting the Docker socket is host root, and build without it.
Solution 
# a "sandboxed" build container with the socket mounted
$ docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli sh -c '
    docker run --rm -v /:/host alpine cat /host/etc/shadow | head -2'
root:$6$abcxyz...:19000:0:99999:7:::
daemon:*:19000:0:99999:7:::
      ↑ the HOST's shadow file

Nothing was exploited. The container asked the root-owned daemon to start another container mounting /. The socket is the privilege.

🎯 Key Takeaways

  • The stack is docker CLI → dockerd → containerd → shim → runc → your process, and each layer has one job.
  • runc exits immediately after creating the container — it applies namespaces, cgroups, capabilities and seccomp, then execs. A "runc" error means creation failed, not a runtime problem.
  • The containerd-shim is the container's parent, parented to init — verified with ps --forest; dockerd is nowhere in the ancestry.
  • That is why systemctl restart docker leaves containers running with the same PID and unbroken uptime — while killing the shim exits the container with 137.
  • Before Docker 1.11 there was no shim and dockerd was the direct parent, so daemon restarts killed every workload.
  • The cost is one shim per container — measured ~10 MB each, a real line item on dense hosts.
  • The OCI defines three specs: Image, Runtime, Distribution — which is why "Docker images" are really OCI images that run anywhere.
  • An OCI bundle is just rootfs/ plus config.json; runc spec and runc run start a container with no Docker at all.
  • Removing dockershim did not break Docker-built images — it removed the kubelet↔dockerd adapter, since dockerd already delegated to containerd.
  • What genuinely broke was socket-mounting pods and node tooling calling the Docker API.
  • Runtimes are swappable: crun measured ~20% faster to start, gVisor 2.3× slower.
  • gVisor runs a user-space kernel — it reports its own uname -r and its own dmesg — costing 3.5× on syscall-heavy work but only 1.08× on CPU-bound work.
  • Kata gives each container a real VM (~100 MB, ~1 s) for hypervisor-grade isolation with full syscall compatibility.
  • Choose isolation per workload via RuntimeClass or --runtime, so strong isolation is paid for only where it is needed.
  • Mounting /var/run/docker.sock is host root — demonstrated by reading /etc/shadow, extracting another container's secrets, and writing to the host as root.
  • Build without it: Kaniko and rootless BuildKit produce OCI images with no daemon access and no privileged flag.
  • Podman is daemonless and rootless by default; rootless Docker gets most of the benefit at the cost of low ports and slower networking.
  • On containerd-only nodes use nerdctl (Docker-like), crictl (CRI level), or ctr (raw containerd) — and note ctr -n means a containerd namespace, not a Linux one.
