Environment, Config & Secrets Running Containers

What you'll master: the difference between configuration and secrets, and why the same mechanism is right for one and wrong for the other; the four places an environment variable can leak that people do not check — docker inspect, the process environment readable by any process in the container, child processes that inherit it, and crash dumps; the precedence order when ENV, --env-file, -e and Compose all set the same variable, which decides which value actually wins; why file-based secrets are strictly better than environment variables and what _FILE conventions exist to support them; runtime secret injection from a real secret manager; and the rotation question — what to do about a secret that has already been in an image or a log. Prerequisites: Writing a Dockerfile, Storage.

Part 1 — Configuration Is Not Secrets

Both are "things that vary per environment", and treating them identically is how credentials end up in version control.

ConfigurationSecrets
ExamplesLog level, feature flags, URLs, timeoutsPasswords, API keys, certificates, tokens
In version control✅ Fine❌ Never
In image layersAcceptable❌ Never
In environment variables✅ Fine⚠️ Works, leaks easily
Visible in docker inspectFine❌ Problem
Needs rotationNo✅ Yes
Best mechanismEnv vars or a config fileMounted files
🔑 The test is whether disclosure requires action. If a value appearing in a log, a support ticket, or a screenshot would require you to change it, it is a secret and belongs in a mounted file rather than an environment variable. Log level does not; a database password does.

Part 2 — Where Environment Variables Leak

Environment variables are the default choice because twelve-factor recommends them, and they leak in four places people rarely check.

① docker inspect — plain text, to anyone with daemon access
$ docker inspect app --format '{{json .Config.Env}}'
["PATH=...","DB_PASSWORD=hunter2"]

② /proc — readable by ANY process in the container, not just yours
$ docker exec app cat /proc/1/environ | tr '\0' '\n' | grep PASSWORD
DB_PASSWORD=hunter2

③ child processes inherit the whole environment
   a shelled-out command, a crash reporter, a debug endpoint

④ crash dumps, error trackers and framework debug pages
   many frameworks print the environment on an unhandled exception
Leak pathEnv varMounted file
docker inspect❌ Visible✅ Only the path
/proc/PID/environ❌ Visible✅ Not present
Inherited by children❌ Yes✅ No
Crash dumps / debug pages❌ Often✅ No
Can be rotated without restart❌ No✅ Yes
Filesystem permissions apply❌ No✅ Yes

The rotation point is underrated. An environment variable is fixed for the life of the process, so rotating a credential means restarting every container. A mounted file can be replaced and re-read, which is what makes short-lived credentials practical.

Part 3 — Precedence

When the same variable is set in several places, the order decides which value the process sees — and getting this wrong produces "the config change had no effect".

LOWEST  → HIGHEST

1. ENV in the Dockerfile          baked into the image
2. env_file: in Compose
3. environment: in Compose
4. -e / --env on the command line
5. the shell environment, for ${VAR} substitution in Compose

# Dockerfile:            ENV LOG_LEVEL=info
# .env file:             LOG_LEVEL=debug
# docker run -e LOG_LEVEL=warn

$ docker run --env-file .env -e LOG_LEVEL=warn myapp env | grep LOG_LEVEL
LOG_LEVEL=warn           ← the command line wins

-e VAR with no value passes it through from your shell, which is convenient and easy to do accidentally:

$ export API_KEY=secret
$ docker run -e API_KEY myapp        # takes the value from the host shell

Part 4 — File-Based Secrets

The better pattern is to mount the secret as a file and have the application read it. Many official images support a _FILE suffix convention for exactly this.

# instead of POSTGRES_PASSWORD=hunter2
$ docker run -d \
    -e POSTGRES_PASSWORD_FILE=/run/secrets/pgpass \
    -v $(pwd)/pgpass:/run/secrets/pgpass:ro \
    postgres:16

$ docker inspect pg --format '{{json .Config.Env}}'
["POSTGRES_PASSWORD_FILE=/run/secrets/pgpass", ...]
                        ↑ a PATH, not the secret
ImageSupports
postgresPOSTGRES_PASSWORD_FILE
mysqlMYSQL_ROOT_PASSWORD_FILE
redisVia config file
Many others*_FILE is a widespread convention

Supporting it in your own application is a few lines, and worth doing:

function readSecret(name) {
  const filePath = process.env[`${name}_FILE`];
  if (filePath) return fs.readFileSync(filePath, 'utf8').trim();
  return process.env[name];              // fall back for development
}
const dbPassword = readSecret('DB_PASSWORD');
🔑 Mount secrets read-only, and prefer tmpfs so they never touch disk. A secret bind-mounted from the host persists on that host's filesystem; a tmpfs mount lives in memory and disappears with the container. Combining --read-only with a tmpfs secrets path is the strongest simple arrangement available without a secret manager.

Part 5 — Compose and Swarm Secrets

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt      # Compose: a local file
    # external: true                      # Swarm: managed by the cluster

Compose mounts each secret at /run/secrets/<name>. In plain Compose the source is a local file, which is better than an environment variable but still a file on disk; in Swarm the secret is stored encrypted in the raft log and delivered to the node in memory.

Part 6 — Runtime Injection and Rotation

The strongest pattern fetches credentials at start-up from a secret manager, using an identity the workload already has — so no long-lived secret exists on disk anywhere.

#!/bin/sh
# entrypoint: fetch, export into THIS process only, then exec
DB_PASSWORD=$(vault kv get -field=password secret/app/db)
export DB_PASSWORD
exec "$@"

Even this leaves the value in /proc/1/environ, which is why writing to a tmpfs file is better where the application supports it. The real gain is that the credential is short-lived and never stored — rotation becomes a restart rather than a redeploy.

If a secret has ever been committed, built into an image, or logged, rotate it. Removing it does not retract what has been pulled, cloned, or shipped to a log aggregator:

$ docker history --no-trunc myimage | grep -i 'token\|password\|key'
$ git log -p --all -S 'AKIA' | head          # search history for AWS keys
$ trivy image --scanners secret myimage      # scan an image for credentials

❌ Putting the database password in an environment variable and a committed .env. The value is set with -e DB_PASSWORD=..., which puts it in docker inspect output for anyone with daemon access, in /proc/1/environ where any process in the container can read it, and in the environment of every child process the application shells out to. The framework's debug page prints the environment on an unhandled exception, so it reaches the error tracker too. Meanwhile .env is in the repository "because it is only staging", so the credential is in every clone and every fork of the history — and when it is eventually noticed, someone deletes the file in a new commit and considers it handled.

✅ Mount secrets as files, keep configuration in environment variables, and rotate anything that has ever been exposed. Use the _FILE convention that official images already support — POSTGRES_PASSWORD_FILE=/run/secrets/pgpass puts a path in docker inspect rather than the credential, keeps it out of /proc and out of child environments, and lets filesystem permissions apply. Mount it read-only and prefer tmpfs so it never reaches disk. Keep .env in .gitignore with a committed .env.example holding keys and no values. In production, fetch short-lived credentials at start-up from a secret manager using the workload's own identity. And treat any secret that reached a commit, an image layer, or a log as compromised — deleting the file does not retract the clones.

Interview Questions

Beginner: How do you pass configuration into a container?

Environment variables are the standard mechanism, with several ways to set them:

-e LOG_LEVEL=debug                    one variable
-e LOG_LEVEL                          pass through from the host shell
--env-file .env                       many at once
ENV LOG_LEVEL=info                    a default baked into the image

Precedence, lowest to highest: Dockerfile ENV → Compose env_file → Compose environment → -e on the command line. Not knowing this produces the classic "I changed the config and nothing happened", where a lower-precedence value was edited.

The other options are a mounted config file (better for large or structured configuration, and re-readable without a restart) and command-line arguments via CMD.

The important caveat is that this applies to configuration, not secrets. Environment variables are visible in docker inspect, readable from /proc/1/environ by any process in the container, inherited by child processes, and often printed by framework error pages. A log level in an environment variable is fine; a database password belongs in a mounted file.

Beginner: Why are environment variables a poor place for secrets?

Four leak paths, and most people only think about the first.

① docker inspect app --format '{{json .Config.Env}}'
   ["DB_PASSWORD=hunter2", ...]        ← anyone with daemon access

② docker exec app cat /proc/1/environ | tr '\0' '\n'
   DB_PASSWORD=hunter2                 ← any process IN the container

③ child processes inherit the entire environment
   a shelled-out command, a crash reporter, a subprocess

④ crash dumps and framework debug pages print the environment
   → the secret reaches your error tracker

A fifth problem is rotation: an environment variable is fixed for the process's lifetime, so changing a credential requires restarting every container. A mounted file can be replaced and re-read, which is what makes short-lived credentials workable.

The alternative is a mounted file, ideally with the _FILE convention that official images support:

-e POSTGRES_PASSWORD_FILE=/run/secrets/pgpass
-v ./pgpass:/run/secrets/pgpass:ro

Now docker inspect shows a path rather than the credential, /proc does not contain it, children do not inherit it, and filesystem permissions apply.

Better still, mount it on tmpfs so it exists only in memory, and in production fetch it at start-up from a secret manager so no long-lived credential is stored anywhere.

Mid: Explain the _FILE convention and why it helps.

Instead of the secret's value, you pass the path to a file containing it. Official images from postgres, mysql and others support this by convention:

docker run -d \
  -e POSTGRES_PASSWORD_FILE=/run/secrets/pgpass \
  -v ./pgpass:/run/secrets/pgpass:ro \
  postgres:16
Leak pathPASSWORD=xPASSWORD_FILE=/path
docker inspect❌ the secret✅ a path
/proc/1/environ❌ the secret✅ a path
Child processes❌ inherited✅ path only
File permissions❌ N/A✅ apply
Rotate without restart❌✅ re-read

Implementing it in your own application is trivial and worth doing, with a fallback so local development stays convenient:

function readSecret(name) {
  const p = process.env[`${name}_FILE`];
  return p ? fs.readFileSync(p, 'utf8').trim() : process.env[name];
}

Pair it with tmpfs so the file never touches disk, and set restrictive permissions — a world-readable secret file inside the container is only marginally better than an environment variable if other processes run there.

This is also exactly how Docker Swarm and Kubernetes deliver secrets: as files under /run/secrets, which is why applications written to the convention work unchanged under an orchestrator.

Mid: A secret was committed to Git. What do you do?

Rotate it first. Everything else is secondary.

The credential must be assumed compromised: the repository has been cloned, forked, mirrored to CI, and possibly indexed by automated scanners that watch public pushes. Deleting the file in a new commit changes nothing, because the value remains in history and in every existing clone.

The order I would work in:

  1. Rotate the credential — new password, new key, revoke the old one. Until this is done nothing else matters.
  2. Check for use — audit logs for access with the old credential, to know whether this is an incident or a near miss.
  3. Remove it from history with git filter-repo or BFG, and force-push. Coordinate this, since it rewrites every commit hash — and note it does not reach existing clones or forks.
  4. Prevent recurrence: pre-commit secret scanning (gitleaks, trufflehog), CI scanning, and .env in .gitignore with a committed .env.example.
git log -p --all -S 'AKIA' | head           # find AWS keys in history
trivy image --scanners secret myimage       # and check images too
docker history --no-trunc myimage | grep -i 'password\|token'

The same reasoning applies to images. A secret in an image layer or a build argument is recoverable by anyone who pulled it, so rebuilding without it is not remediation — rotation is.

What I would push for afterwards is removing the class of problem: secrets injected at runtime from a manager, so there is no long-lived value that can be committed.

Senior: Design secret management for a production containerised platform.

Goal: no long-lived credential exists at rest, and every access is attributable.

1. A secret manager as the source of truth — Vault, AWS Secrets Manager, or the cloud equivalent. Secrets are never in Git, never in images, never in Compose files.

2. Workload identity rather than a bootstrap secret. This is the part that distinguishes a real design from a shell game: if the container needs a credential to fetch its credentials, you have moved the problem rather than solved it. Use the platform's identity — IRSA on EKS, workload identity on GKE, Vault's Kubernetes auth — so the pod authenticates with something the platform vouches for.

pod identity → secret manager → short-lived credential → mounted at /run/secrets

3. Delivery as files, not environment variables, at /run/secrets/* on tmpfs, mode 400, owned by the application user. Applications read them via the _FILE convention, which also keeps them portable across Compose, Swarm and Kubernetes.

4. Short lifetimes with automatic renewal. Dynamic database credentials with a 1-hour TTL mean a leaked value has bounded value and rotation is routine rather than an incident response. A sidecar or agent renews and rewrites the file; the application re-reads on change.

5. Defence in depth around the leak paths: redact secrets in logging middleware, disable framework debug pages in production, and scan images for embedded credentials in CI.

ControlPrevents
Files not env varsinspect / /proc / child inheritance leaks
tmpfsPersistence on disk
Short TTLUnbounded value of a leak
Workload identityThe bootstrap-secret problem
CI secret scanningCommitted and baked-in credentials
Audit loggingUndetected misuse

What I would flag as the residual risk: an attacker with code execution in the container can read the mounted file, exactly as they could read an environment variable. Secret management limits blast radius and lifetime; it does not stop a compromised application from using its own credentials — which is why short TTLs and audit logging matter as much as the storage mechanism.

Senior: How do you handle configuration across dev, staging and production?

Principle: one image, promoted unchanged; configuration supplied by the environment. An image built per environment cannot be tested meaningfully, because what you tested is not what you ship.

build once → registry@sha256:... → dev → staging → production
                    ↑ the SAME digest, different config injected

Layering, lowest to highest precedence:

LayerContainsWhere
Image defaultsSafe defaults for everythingENV in the Dockerfile
Environment configURLs, limits, feature flagsConfigMap, env file, Parameter Store
SecretsCredentialsSecret manager → mounted files
Per-instance overridesRare, targetedDeployment manifest

Validate configuration at start-up and fail fast. A service that starts with a missing or malformed setting and fails later under load is far worse than one that refuses to start:

const required = ['DATABASE_URL','REDIS_URL','JWT_SECRET_FILE'];
const missing = required.filter(k => !process.env[k]);
if (missing.length) { console.error('missing config:', missing); process.exit(1); }

Keep a committed .env.example listing every key with no values, so the required surface is discoverable and reviewable, and .env itself is git-ignored.

The trade-off I would name is that environment-specific configuration means production behaviour differs from what was tested. Mitigations: keep the number of environment-varying settings small and documented, prefer feature flags evaluated at runtime over environment-specific builds, and run staging with production-shaped configuration so the difference is data rather than structure.

5 (hard): Build runtime secret injection with rotation.
Solution 
$ mkdir -p /tmp/rotate && cd /tmp/rotate

# a stand-in "secret manager"
$ mkdir -p vault && echo -n 'password-v1' > vault/db_password

$ cat > app.js <<'EOF'
const fs = require('fs');
const SECRET_PATH = process.env.DB_PASSWORD_FILE;
let current = null;
function load() {
  const v = fs.readFileSync(SECRET_PATH, 'utf8').trim();
  if (v !== current) { current = v; console.log(`[app] credential loaded: ${v.slice(0,8)}...`); }
  return current;
}
load();
fs.watchFile(SECRET_PATH, { interval: 500 }, load);     // re-read on change
setInterval(() => console.log(`[app] using: ${current.slice(0,8)}...`), 2000);
EOF
$ printf 'FROM node:20-alpine\nCOPY app.js /a.js\nCMD ["node","/a.js"]\n' > Dockerfile
$ docker build -q -t rot:app . >/dev/null

Start with the secret mounted as a file:

$ docker run -d --name rot \

6 (hard): Build a config system that validates and fails fast.
Solution 
$ mkdir -p /tmp/configsys && cd /tmp/configsys
$ cat > config.js <<'EOF'
const fs = require('fs');

function readSecret(name) {
  const p = process.env[`${name}_FILE`];
  if (p) {
    if (!fs.existsSync(p)) throw new Error(`${name}_FILE points to a missing file: ${p}`);
    return fs.readFileSync(p, 'utf8').trim();
  }
  return process.env[name];
}

const schema = {
  PORT:         { required: true,  type: 'number', default: 3000 },
  LOG_LEVEL:    { required: false, type: 'enum', values: ['debug','info','warn','error'],
                  default: 'info' },
  DATABASE_URL: { required: true,  type: 'string' },
  DB_PASSWORD:  { required: true,  type: 'secret' },
};

const cfg = {}, errors = [];
for (const [key, s] of Object.entries(schema)) {
  const raw = s.type === 'secret' ? readSecret(key) : process.env[key];
  if (raw === undefined || raw === '') {
    if (s.required && s.default === undefined) { errors.push(`missing required: ${key}`); continue; }
    cfg[key] = s.default; continue;
  }
  if (s.type === 'number') {
    const n = Number(raw);
    if (Number.isNaN(n)) { errors.push(`${key} must be a number, got "${raw}"`); continue; }
    cfg[key] = n;
  } else if (s.type === 'enum') {
    if (!s.values.includes(raw)) {
      errors.push(`${key} must be one of ${s.values.join('|')}, got "${raw}"`); continue;
    }
    cfg[key] = raw;
  } else cfg[key] = raw;
}

if (errors.length) {
  console.error('CONFIGURATION ERRORS:');
  errors.forEach(e => console.error('  -', e));
  process.exit(1);
}

// redacted dump — never log secret VALUES
const redacted = Object.fromEntries(Object.entries(cfg).map(([k,v]) =>
  [k, schema[k].type === 'secret' ? '***REDACTED***' : v]));
console.log('config OK:', JSON.stringify(redacted));
EOF
$ printf 'FROM node:20-alpine\nCOPY config.js /c.js\nCMD ["node","/c.js"]\n' > Dockerfile
$ docker build -q -t cfg:test . >/dev/null

Missing required config fails immediately:

$ docker run --rm cfg:test; echo "exit=$?"

🎯 Key Takeaways

  • Configuration and secrets are not the same: the test is whether disclosure requires action.
  • Environment variables leak in four places — verified: docker inspect, /proc/1/environ, inherited child environments, and framework error reports.
  • Any process in the container can read another's environment, so a non-root app does not protect a secret in -e.
  • Precedence, lowest to highest: Dockerfile ENV → Compose env_file → Compose environment → docker run -e.
  • -e VAR with the variable unset in your shell sets it to empty, overriding the image default rather than falling back.
  • The _FILE convention puts a path in docker inspect instead of the credential — confirmed absent from /proc while the app still reads it.
  • Official images (postgres, mysql) support it already, and implementing it yourself is a few lines with a dev fallback.
  • Mount secrets read-only and prefer tmpfs so they never touch disk; pair with --read-only.
  • File-based secrets can be rotated without restarting — demonstrated with fs.watchFile picking up a new value on a live container.
  • An entrypoint that exports the fetched value puts it back in /proc — write to a tmpfs file instead.
  • Secrets in ENV or ARG are recoverable from the published image via docker history; a deleted file is still extractable from its layer.
  • Rebuilding without the secret is not remediation — the old image is already pulled. Rotate.
  • The same applies to Git: deleting the file leaves the value in history and in every clone and fork.
  • Scan for both in CI — trivy image --scanners secret found the embedded key, and gitleaks/trufflehog cover commits.
  • Production pattern: workload identity → secret manager → short-lived credential → tmpfs file, so no long-lived secret exists at rest.
  • Solve the bootstrap problem with platform identity (IRSA, workload identity), or you have only moved the secret.
  • Validate configuration at start-up and exit non-zero — a service that starts misconfigured and fails under load is worse than one that refuses to start.
  • Redact secret values in any config dump or log line; commit .env.example with keys and no values, and git-ignore .env.
  • One image promoted unchanged across environments, with configuration injected — building per environment means you did not test what you ship.
