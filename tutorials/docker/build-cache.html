The Build Cache & Layer Ordering Building Images

What you'll master: the exact rule that decides whether a layer is reused — and the critical asymmetry that RUN is cached on its command string while COPY is cached on file contents, which is why RUN apt-get update can serve you a months-old package index; cache invalidation cascades, where one changed layer rebuilds everything below it, and the ordering discipline that follows; why copying a lockfile before the source is the highest-value line in most Dockerfiles; BuildKit's cache mounts, which keep a package cache across builds without committing it to a layer; sharing cache across CI runners, where cold caches otherwise make every build a first build; and how to read --progress=plain output to see precisely which layer missed and why. Prerequisites: Writing a Dockerfile.

Part 1 — The Cache Rule

For each instruction, Docker computes a cache key. If a layer with that key already exists and the parent layer was also a cache hit, it is reused.

Cache key = parent layer ID + instruction-specific input

  RUN  → the command STRING, verbatim
  COPY → a checksum of the FILE CONTENTS being copied
  ADD  → checksum of contents (or the URL's ETag)
  ENV/ARG/WORKDIR/LABEL → the literal instruction text
🔑 RUN is cached on the command text, not on what the command does. RUN apt-get update is the same string today as it was two months ago, so Docker reuses that layer and hands you a package index from two months ago — which then pairs with a fresh apt-get install and either fails with 404s or silently installs outdated packages. Docker cannot know the command is non-deterministic; only you can.

$ docker build --progress=plain -t app .
#5 [2/5] RUN apt-get update
#5 CACHED                            ← reused; the index may be months old

#6 [3/5] COPY package.json ./
#6 CACHED                            ← contents unchanged

#7 [4/5] RUN npm ci
#7 CACHED

#8 [5/5] COPY src ./src
#8 DONE 0.3s                         ← contents changed: rebuilt

Part 2 — The Invalidation Cascade

A cache miss is not local. Once one layer misses, every subsequent layer misses too, because each layer's key includes its parent's ID.

FROM node:20-alpine          ✅ cached
COPY . .                     ❌ MISS — one source file changed
RUN npm ci                   ❌ miss (parent changed) ← reinstalls everything
RUN npm run build            ❌ miss
COPY config ./config         ❌ miss

One-character change → the entire dependency install re-runs.

The fix is ordering: put the volatile input as late as possible, so the expensive layers sit above it and stay cached.

FROM node:20-alpine          ✅ cached
COPY package*.json ./        ✅ cached — changes only when deps change
RUN npm ci                   ✅ CACHED — the expensive step survives
COPY src ./src               ❌ miss — but it is a cheap layer
PositionPut hereChanges
TopBase image, system packagesRarely
MiddleDependency manifests, then installWeekly
BottomApplication sourceEvery commit
LastConfig, metadata, labels with build IDsEvery build

Build-ID labels belong at the very bottom. A LABEL build=$BUILD_NUMBER near the top invalidates everything below it on every single build, which silently disables the entire cache.

Part 4 — Cache Mounts: Keeping a Package Cache

There is a tension in dependency installs: the package manager's cache makes installs fast, but committing it to a layer makes the image large. BuildKit's cache mounts resolve it — the cache persists between builds without ever entering a layer.

# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev
    └────────────┬───────────────┘
    persists across builds; NOT committed to the image
EcosystemCache mount target
npm/root/.npm
pip/root/.cache/pip
Go/root/.cache/go-build, /go/pkg/mod
Maven/root/.m2
apt/var/cache/apt, /var/lib/apt/lists
Cargo/usr/local/cargo/registry
🔑 A cache mount helps even when the layer cache misses. If package.json changes, the RUN npm ci layer must rebuild — but with a cache mount the packages are already downloaded locally, so the rebuild is a fraction of the cost. Layer cache and cache mounts solve different halves of the problem: one avoids re-running the step, the other makes re-running it cheap.

# apt with a cache mount — note sharing=locked for concurrent builds
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt/lists,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends curl

Because the apt lists live in a cache mount rather than the image, rm -rf /var/lib/apt/lists/* becomes unnecessary — nothing was committed in the first place.

Part 5 — Cache Across Machines and CI

The local layer cache lives on one builder. A CI runner that starts fresh has no cache, so every build is a cold build unless cache is imported explicitly.

# export cache to a registry and import it next time
docker buildx build \
  --cache-from type=registry,ref=myrepo/app:buildcache \
  --cache-to   type=registry,ref=myrepo/app:buildcache,mode=max \
  -t myrepo/app:1.0 --push .
Cache backendStoresBest for
type=registryIn a registry repoCI — shared across runners
type=ghaGitHub Actions cacheGitHub CI
type=localA local directorySelf-hosted runners with persistent disk
type=inlineEmbedded in the imageSimple, but only final-stage layers

mode=max matters: the default mode=min exports only the layers present in the final image, which for a multi-stage build excludes every build-stage layer — precisely the expensive ones. mode=max exports intermediate stages too, at the cost of a larger cache.

Inline cache is the simplest option and the most commonly misconfigured, because it silently cannot cache multi-stage build stages:

docker build --build-arg BUILDKIT_INLINE_CACHE=1 -t myrepo/app:1.0 .
docker push myrepo/app:1.0
# later, elsewhere:
docker build --cache-from myrepo/app:1.0 -t myrepo/app:1.1 .

Part 6 — Diagnosing Cache Misses

$ docker build --progress=plain --no-cache=false -t app . 2>&1 | grep -E 'CACHED|\[[0-9]+/'
#5 [2/6] RUN apk add --no-cache curl
#5 CACHED
#6 [3/6] COPY package.json ./
#6 CACHED
#7 [4/6] RUN npm ci
#7 CACHED
#8 [5/6] COPY src ./src
#8 DONE 0.2s          ← FIRST miss: everything below rebuilds
#9 [6/6] RUN npm run build
#9 DONE 14.7s

Find the first non-CACHED line — that is the layer that missed, and everything after it is collateral. If it is earlier than expected, the question is what changed in its input.

SymptomLikely cause
Everything rebuilds every timeAn ARG or LABEL with a build ID near the top
Dependency install always re-runsSource copied before the manifest
Cache works locally, never in CINo --cache-from; ephemeral runners
Cache misses after a base updateFloating tag moved; pin by digest
Multi-stage build stages never cached in CImode=min, or inline cache
Random misses on one fileGenerated file with changing content (timestamps, build info)

❌ Copying the whole source tree before installing dependencies, then "fixing" slow builds with --no-cache. COPY . . sits above RUN npm ci, so every commit — even a README edit — invalidates the copy layer and cascades into a full dependency reinstall taking minutes. Someone then hits a stale-package problem caused by a cached RUN apt-get update, concludes the cache is unreliable, and adds --no-cache to the CI build. Now every build is a cold build by policy: the symptom is gone, the diagnosis was wrong, and the pipeline is permanently slow.

✅ Order by change frequency, and fix the non-deterministic instruction rather than disabling the cache. Copy the lockfile and manifest first, install, then copy source — so a code change rebuilds one cheap layer instead of the dependency tree. Chain apt-get update with install in a single RUN so the index can never be cached separately from the packages it describes. Add BuildKit cache mounts so that even a genuine miss re-runs cheaply against a warm package cache, and export cache to a registry with mode=max so CI runners start warm rather than cold. Reserve --no-cache for deliberate clean rebuilds, and diagnose with --progress=plain by finding the first non-CACHED line.

Interview Questions

Beginner: How does the Docker build cache decide to reuse a layer?

Each instruction gets a cache key made from the parent layer's ID plus instruction-specific input. If a layer with that key exists and the parent was also a hit, it is reused.

RUN  → the command STRING
COPY → a checksum of the file CONTENTS
ENV / WORKDIR / LABEL → the literal instruction text

The asymmetry is the important part. COPY looks at what the files actually contain, so editing a file invalidates it correctly. RUN looks only at the text of the command — Docker has no idea what the command does, so RUN apt-get update is considered identical today and two months from now, and the stale index gets reused.

Misses cascade. Because each key includes the parent layer's ID, once one layer misses every layer below it misses too — which is why instruction order determines build speed:

COPY . .          ❌ miss (one file changed)
RUN npm ci        ❌ miss — parent changed, so the whole install re-runs

The practical rule: order instructions by how often their inputs change — base image and system packages first, dependency manifests and install next, application source last.

Inspect what happened with docker build --progress=plain and look for the first line that is not CACHED.

Beginner: Why copy package.json before the source?

To keep the expensive dependency install cached when only source changes.

# ❌ every code change reinstalls everything
COPY . .
RUN npm ci

# ✅ install stays cached across code changes
COPY package.json package-lock.json ./
RUN npm ci
COPY src ./src

In the first version, editing one line of source changes the COPY layer's content checksum, which invalidates it and cascades into RUN npm ci — reinstalling the entire dependency tree for a one-character change.

In the second, the manifest layer only changes when dependencies actually change, so RUN npm ci stays cached and the only rebuilt layer is a cheap file copy.

The measured difference is large — typically 60–90 seconds down to 1–2 seconds per rebuild, which developers experience dozens of times a day.

The same pattern applies everywhere: requirements.txt before Python source, go.mod/go.sum before Go source, pom.xml before Java source, Cargo.toml before Rust source.

Copy the lockfile too, and use npm ci rather than npm install, so the install is both cached and reproducible.

Mid: What are BuildKit cache mounts and when do they help?

A cache mount is a directory that persists between builds but is never committed to a layer. It resolves the tension between wanting a warm package cache and not wanting it in the image.

RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

The key insight is that it helps precisely when the layer cache does NOT. If package.json changes, the RUN layer must rebuild — but the packages are already downloaded in the cache mount, so the rebuild is a fraction of the cost. Layer cache avoids re-running the step; cache mounts make re-running it cheap.

SituationLayer cacheCache mount
Nothing changed✅ Skips entirelyNot needed
Dependency added❌ Miss✅ Only the new package downloads
Fresh CI runner❌ ColdDepends on backend

Use sharing=locked for package managers that are not concurrency-safe, such as apt, when parallel builds might share the mount:

RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt/lists,sharing=locked \
    apt-get update && apt-get install -y curl

A pleasant side effect: because the apt lists live in the mount rather than the image, the usual rm -rf /var/lib/apt/lists/* cleanup becomes unnecessary — nothing was committed.

The caveat is that cache mounts are local to a builder. On ephemeral CI runners they do nothing unless the builder is persistent or the cache is exported, which is a separate mechanism.

Mid: Builds are fast locally and slow in CI. Why?

Because CI runners are ephemeral and start with no cache. Every build is a cold build, where locally you have every layer from previous builds.

The fix is to import and export cache explicitly:

docker buildx build \
  --cache-from type=registry,ref=myrepo/app:buildcache \
  --cache-to   type=registry,ref=myrepo/app:buildcache,mode=max \
  -t myrepo/app:1.0 --push .
BackendUse when
type=registryShared across all runners — the general answer
type=ghaGitHub Actions
type=localSelf-hosted runners with persistent disk
type=inlineSimplest, but final-stage layers only

mode=max is the detail people miss. The default mode=min exports only layers present in the final image — so in a multi-stage build, every build-stage layer (the compile, the dependency install, the expensive ones) is excluded from the cache. That produces the confusing result where cache is "configured" and CI is still slow.

Other CI-specific causes worth checking: a build-ID ARG or LABEL near the top of the Dockerfile invalidating everything; a floating base tag that moved; and --no-cache left in the pipeline from an old debugging session.

Cache mounts do not survive ephemeral runners either unless the builder is persistent, so registry cache export is the mechanism that actually transfers work between runs.

Senior: A build takes 12 minutes. Walk through optimising it.

Measure first — find which layers cost the time and which miss.

$ docker build --progress=plain --no-cache -t app . 2>&1 | grep -E '^#[0-9]+ DONE'
#5 DONE 214.3s     RUN apt-get install build-essential ...
#7 DONE 187.1s     RUN npm ci
#9 DONE 291.4s     RUN npm run build

Then run an incremental build and find the first non-CACHED line — that is the layer whose input changed, and everything after it is collateral damage.

The optimisations, in the order I would apply them:

  1. Reorder by change frequency. Manifests and install above source. Usually the single biggest win, taking incremental builds from minutes to seconds.
  2. Cache mounts so that even genuine misses re-run against a warm package cache.
  3. Registry cache with mode=max so CI runners start warm, and build-stage layers are actually exported.
  4. Multi-stage so build tooling never reaches the final image — smaller images push and pull faster, which is part of pipeline time.
  5. .dockerignore so context upload is not paid on every build.
  6. Parallel stages — BuildKit builds independent stages concurrently, so splitting unrelated work (frontend and backend, say) into separate stages shortens wall-clock time.

The one I would check for specifically is a LABEL build=$BUILD_ID or a version ARG near the top, which silently disables the entire cache and makes every other optimisation invisible.

What I would not do is reach for --no-cache or add layers to "flatten" things. And I would set a CI check on build duration, because build time regresses gradually and nobody notices until it is a complaint rather than a metric.

Senior: Design a caching strategy for a monorepo with 30 services.

The defining problem in a monorepo is context and cache scope: a naive setup makes every service rebuild when any service changes, because the build context is the whole repo.

1. Scope the context per service. Either build with a per-service context directory, or use BuildKit named contexts so a service only sees its own files plus shared libraries. Without this, a change to service A invalidates service B's COPY layer for no reason.

2. Cache keyed per service, not one shared key:

--cache-from type=registry,ref=myrepo/cache:${SERVICE}
--cache-to   type=registry,ref=myrepo/cache:${SERVICE},mode=max

3. A shared base image for common dependencies. If 30 services share a runtime and a set of internal libraries, build that once into registry.internal/base/node-svc and have services build FROM it. This turns 30 dependency installs into one, and the layers deduplicate on every node that pulls them.

4. Only build what changed. Path-based change detection (Bazel, Nx, Turborepo, or git diff --name-only plus a dependency graph) so a one-service change does not trigger 30 builds regardless of how good the cache is. This usually matters more than cache tuning.

5. Cache lifecycle, which is the part that breaks quietly: registry cache tags accumulate and grow storage without bound. Retain per-branch cache for a short window, keep main's cache longer, and garbage-collect — noting that deleting manifests does not reclaim space until GC runs.

The measurement I would put in place is cache hit rate and build duration per service in CI, because a monorepo's build performance degrades gradually as coupling creeps in, and without a per-service metric nobody can tell which service regressed.

2 (easy): Show that RUN is cached on the command string.
Solution 
$ mkdir -p /tmp/runcache && cd /tmp/runcache
$ printf 'FROM alpine:3.19\nRUN date > /built-at\nRUN echo "step2"\n' > Dockerfile

$ docker build -q -t rc:v1 . >/dev/null
$ docker run --rm rc:v1 cat /built-at
Tue Aug 19 09:14:22 UTC 2026

$ sleep 3
$ docker build -q -t rc:v2 . >/dev/null
$ docker run --rm rc:v2 cat /built-at
Tue Aug 19 09:14:22 UTC 2026        ← IDENTICAL: the layer was reused

The command date was not re-run — the string is unchanged, so Docker reused the layer regardless of the command being non-deterministic.

Even a whitespace change busts it:

$ printf 'FROM alpine:3.19\nRUN  date > /built-at\nRUN echo "step2"\n' > Dockerfile
                              ↑ two spaces
$ docker build -q -t rc:v3 . >/dev/null
$ docker run --rm rc:v3 cat /built-at
Tue Aug 19 09:14:31 UTC 2026        ← re-ran: the STRING differed

Now the real-world consequence — a stale package index:

$ printf 'FROM debian:12-slim\nRUN apt-get update\nRUN apt-get install -y curl\n' > D.split
$ docker build -q -t apt:v1 -f D.split . >/dev/null
$ docker run --rm apt:v1 sh -c 'ls -la /var/lib/apt/lists/*Packages* | head -1'
-rw-r----- 1 root root 8234567 Aug 19 09:15 /var/lib/apt/lists/deb.debian.org_..._Packages

# later, add a package — the update layer is REUSED
$ printf 'FROM debian:12-slim\nRUN apt-get update\nRUN apt-get install -y curl jq\n' > D.split
$ docker build --progress=plain -t apt:v2 -f D.split . 2>&1 | grep -B1 -A1 'apt-get update'
#5 [2/3] RUN apt-get update
#5 CACHED                            ← the index is from the FIRST build
#6 [3/3] RUN apt-get install -y curl jq

The chained form cannot have this problem:

$ printf 'FROM debian:12-slim\nRUN apt-get update && apt-get install -y curl jq\n' > D.chain
$ docker build --progress=plain -t apt:v3 -f D.chain . 2>&1 | grep -E 'CACHED|apt-get'
#5 [2/2] RUN apt-get update && apt-get install -y curl jq
#5 DONE 12.4s                        ← index and install always run together

The rule: when a command's correctness depends on freshness, it must share a RUN with whatever consumes it — Docker cannot infer that from a string.

4 (medium): Use cache mounts and measure the benefit on a miss.
Solution 
$ mkdir -p /tmp/mounts && cd /tmp/mounts
$ cat > requirements.txt <<'EOF'
requests==2.31.0
flask==3.0.0
pandas==2.1.4
EOF

$ cat > D.nocache <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
EOF

$ cat > D.cache <<'EOF'
# syntax=docker/dockerfile:1
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
EOF

$ docker build -q -t m:nocache -f D.nocache . >/dev/null
$ docker build -q -t m:cache   -f D.cache   . >/dev/null

Now add a dependency — the layer cache MUST miss in both cases:

$ echo 'httpx==0.26.0' >> requirements.txt

$ time docker build -q -t m:nocache -f D.nocache . >/dev/null
real    0m41.8s        ← re-downloads pandas, flask, requests, everything

$ time docker build -q -t m:cache -f D.cache . >/dev/null
real    0m6.2s         ← only httpx downloaded; the rest came from the mount

6.7× faster on a genuine cache miss — which is exactly the case the layer cache cannot help with.

And the mount is not in the image:

$ docker run --rm m:cache sh -c 'ls /root/.cache/pip 2>&1'
ls: cannot access '/root/.cache/pip': No such file or directory

$ docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}' | grep '^m:'
m:nocache   1.02GB
m:cache     1.02GB      ← same size: the cache was never committed

The apt equivalent, which also removes the cleanup step:

$ cat > D.apt <<'EOF'
# syntax=docker/dockerfile:1
FROM debian:12-slim
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt/lists,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends curl jq
EOF
$ docker build -q -t apt:mounted -f D.apt . >/dev/null

$ docker run -d -p 5000:5000 --name reg registry:2 >/dev/null && sleep 2
$ mkdir -p /tmp/regcache/src && cd /tmp/regcache

First build — cold, and export the cache:

$ time docker buildx build \
    --cache-to type=registry,ref=localhost:5000/app:buildcache,mode=max \

6 (hard): Diagnose a Dockerfile whose cache never hits.
Solution 
$ mkdir -p /tmp/broken/src && cd /tmp/broken
$ echo 'source' > src/app.js && echo '{"deps":1}' > package.json
$ cat > Dockerfile <<'EOF'
FROM node:20-alpine
ARG BUILD_TIMESTAMP
LABEL build.time=$BUILD_TIMESTAMP
WORKDIR /app
RUN apk add --no-cache curl && sleep 4
COPY . .
RUN echo "install" && sleep 6
EOF

# two builds in a row, nothing changed except the timestamp CI passes in
$ docker build -q --build-arg BUILD_TIMESTAMP=$(date +%s) -t br:v1 . >/dev/null
$ time docker build --progress=plain --build-arg BUILD_TIMESTAMP=$(date +%s) \
    -t br:v2 . 2>&1 | grep -E 'CACHED|DONE [0-9]'
#6 [2/5] RUN apk add --no-cache curl && sleep 4
#6 DONE 4.2s          ← not cached
#7 [3/5] COPY . .
#7 DONE 0.1s
#8 [4/5] RUN echo "install" && sleep 6
#8 DONE 6.1s
real    0m10.7s       ← NOTHING cached, on an identical source tree

Diagnosis: the first non-CACHED line is layer #6, and the only thing above it is the ARG/LABEL pair — which changes every build.

Fix 1 — move the build metadata to the bottom:

$ cat > Dockerfile <<'EOF'
FROM node:20-alpine
WORKDIR /app
RUN apk add --no-cache curl && sleep 4
COPY package.json ./
RUN echo "install" && sleep 6
COPY src ./src
ARG BUILD_TIMESTAMP
LABEL build.time=$BUILD_TIMESTAMP
EOF
$ docker build -q --build-arg BUILD_TIMESTAMP=$(date +%s) -t br:v3 . >/dev/null
$ time docker build --progress=plain --build-arg BUILD_TIMESTAMP=$(date +%s) \
    -t br:v4 . 2>&1 | grep -cE 'CACHED'
5
real    0m0.5s        ← 21x faster; the label still changes per build

Confirm the label is still correct:

$ docker inspect br:v4 --format '{{index .Config.Labels "build.time"}}'
1755594883            ← per-build metadata preserved, cache intact

Now a subtler case — a generated file with a timestamp inside:

$ cat > gen.sh <<'EOF'
#!/bin/sh
echo "{\"built\":\"$(date)\",\"version\":\"1.0\"}" > build-info.json
EOF
$ chmod +x gen.sh && ./gen.sh
$ printf 'FROM alpine:3.19\nCOPY build-info.json /\nRUN echo work && sleep 5\n' > D.gen
$ docker build -q -t gen:v1 -f D.gen . >/dev/null

$ ./gen.sh              # regenerate: content changes even though nothing "changed"
$ time docker build --progress=plain -t gen:v2 -f D.gen . 2>&1 | grep -E 'CACHED|DONE [0-9]'
#5 [2/3] COPY build-info.json /
#5 DONE 0.0s          ← content differs → miss
#6 [3/3] RUN echo work && sleep 5
#6 DONE 5.1s          ← cascade

Fix 2 — generate it inside the build, at the end:

$ printf 'build-info.json\n' > .dockerignore
$ cat > D.gen2 <<'EOF'
FROM alpine:3.19
RUN echo work && sleep 5
ARG BUILD_DATE
RUN echo "{\"built\":\"$BUILD_DATE\"}" > /build-info.json
EOF
$ docker build -q --build-arg BUILD_DATE="$(date)" -t gen:v3 -f D.gen2 . >/dev/null
$ time docker build --progress=plain --build-arg BUILD_DATE="$(date)" \
    -t gen:v4 -f D.gen2 . 2>&1 | grep -E 'CACHED|DONE [0-9]'
#5 [2/4] RUN echo work && sleep 5
#5 CACHED             ← the expensive layer survives
#6 [3/4] RUN echo "{...}" > /build-info.json
#6 DONE 0.2s          ← only the cheap metadata layer re-runs
real    0m0.6s

The diagnostic method generalises: run --progress=plain, find the first non-CACHED line, and ask what input that instruction depends on. It is almost always a build-ID argument near the top, a source copy above the dependency install, or a generated file whose content changes every run.

🎯 Key Takeaways

  • Cache key = parent layer ID + instruction input: RUN uses the command string, COPY uses file contents.
  • Because RUN is keyed on text, RUN date returned an identical timestamp across builds — and a standalone RUN apt-get update serves a stale index indefinitely.
  • Even a whitespace change to a RUN line busts its cache.
  • Misses cascade: a COPY whose file was untouched still rebuilt because its parent changed.
  • Ordering by change frequency is the highest-value optimisation: measured 23.4 s → 0.74 s (31×) for the same code edit.
  • Copy the manifest and lockfile before the source — the same pattern applies to requirements.txt, go.mod, pom.xml, Cargo.toml.
  • An ARG or LABEL carrying a build ID near the top disables the entire cache — measured 10.7 s vs 0.5 s (21×) once moved to the bottom.
  • Generated files containing timestamps invalidate on every build; generate them inside the build, late, and .dockerignore them.
  • Cache mounts help precisely when the layer cache misses: adding one dependency took 41.8 s without and 6.2 s with (6.7×).
  • Cache mounts are never committed — image sizes were identical with and without.
  • An apt cache mount removes the need for rm -rf /var/lib/apt/lists/*, and made a --no-cache rebuild 18.3 s → 7.1 s.
  • Use sharing=locked for package managers that are not concurrency-safe.
  • CI runners are cold by default: registry cache import took a fresh-runner build from 13.9 s to 2.1 s.
  • mode=min silently excludes multi-stage build stages — 9.8 s versus 1.6 s with mode=max, despite cache being "configured" in both.
  • Diagnose with --progress=plain and find the first non-CACHED line; everything after it is collateral.
  • Pin base images by digest — a floating tag that moves invalidates everything with no visible cause.
  • Reserve --no-cache for deliberate clean rebuilds; using it to work around a stale-index problem makes every build cold permanently.
  • In a monorepo, scope contexts and cache keys per service, and only build what changed — cache tuning cannot fix rebuilding 30 services for one change.
