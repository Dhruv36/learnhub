Docker Compose Composing Systems

What you'll master: what Compose actually is — a client that issues the same API calls you would issue by hand, plus a project namespace that decides what up and down are allowed to touch; why the project name is the single most consequential setting in the tool and how renaming a directory silently orphans your data; the difference between the .env file (which interpolates into the Compose file) and env_file (which goes into the container) — a distinction that produces the most common "my variable is empty" bug; why depends_on does not do what its name suggests, measured; the YAML base-60 trap that turns ports: - 22:22 into port 1342; how multiple -f files merge, which keys concatenate and which replace; which deploy: keys Compose honours and which it silently ignores; and where Compose stops being the right tool. Prerequisites: Networking & Port Publishing, Storage, Environment, Config & Secrets.

Part 1 — Compose Is a Client, Not a Runtime

There is no "Compose engine". docker compose up reads YAML, resolves it into a set of container/network/volume definitions, and calls the same daemon API that docker run calls. Everything you learned about namespaces, cgroups and networking applies unchanged — Compose only decides which calls to make.

docker-compose.yml
        │
        │  parse + interpolate ${VARS} + merge override files
        ▼
   resolved model  ──►  docker compose config   (this is what actually runs)
        │
        ├─► POST /networks/create      myapp_default
        ├─► POST /volumes/create       myapp_pgdata
        ├─► POST /containers/create    myapp-db-1     labels: com.docker.compose.project=myapp
        ├─► POST /containers/create    myapp-api-1    labels: com.docker.compose.project=myapp
        └─► POST /containers/{id}/start ...

Two consequences follow immediately, and both explain behaviour that otherwise looks like magic:

ConsequenceWhat it means in practice
Compose is stateless between runsIt re-derives everything from the file plus the labels on existing objects. Delete the file and down can no longer find your containers.
Ownership is expressed with labelscom.docker.compose.project, .service, .container-number, .config-hash. down deletes exactly what carries the project label — no more, no less.
$ docker compose up -d
$ docker inspect myapp-api-1 --format '{{json .Config.Labels}}' | tr ',' '\n'
{"com.docker.compose.config-hash":"9f21c0e4b1..."
 "com.docker.compose.container-number":"1"
 "com.docker.compose.depends_on":"db:service_started:false"
 "com.docker.compose.project":"myapp"
 "com.docker.compose.project.working_dir":"/home/dev/myapp"
 "com.docker.compose.service":"api"}
🔑 The config-hash is why up is idempotent. Compose hashes each service's resolved definition and stores it on the container. Re-running up compares the new hash to the stored one: equal means leave the container alone, different means recreate it. This is also why docker compose restart does not pick up a file change — restart is a stop/start of the existing container and never consults the hash. Use up -d to apply changes.

Part 2 — The Project Name Is the Whole Namespace

Every object Compose creates is prefixed with the project name, and the project name defaults to the basename of the directory containing the file. That default is convenient and it is the source of two nasty failure modes.

ObjectNameNotes
Container<project>-<service>-<n>myapp-api-1. Older v1 used underscores.
Default network<project>_defaultA user-defined bridge, so it has DNS.
Named volume<project>_<volume>This is where your data lives.
Named network<project>_<network>Unless external: true.
① Rename the directory → new project → new empty volume, old data stranded
$ mv ~/work/shop ~/work/shop-v2
$ cd ~/work/shop-v2 && docker compose up -d
$ docker volume ls
DRIVER    VOLUME NAME
local     shop_pgdata          ← 2.1 GB of production-like data, now unreferenced
local     shop-v2_pgdata       ← brand new, empty; the app "lost its database"

② Two checkouts with the same basename → same project → they fight
$ ~/clients/acme/api      → project "api"
$ ~/clients/globex/api    → project "api"     ← docker compose up in the second
                                                RECREATES the first one's containers

Pin the project name explicitly and neither happens:

name: shop                      # top-level key in the Compose file (recommended)
# or  COMPOSE_PROJECT_NAME=shop in .env
# or  docker compose -p shop up -d

The same namespace decides deletion scope, and the asymmetry between the down variants is worth memorising exactly, because one of them is irreversible:

CommandContainersNetworksNamed volumesImages
compose stopStoppedKeptKeptKept
compose downRemovedRemovedKeptKept
compose down -vRemovedRemovedDESTROYEDKept
compose down --rmi localRemovedRemovedKeptBuilt ones removed
⚠️ down -v deletes named volumes; anonymous volumes are deleted by plain down too. If a service declares volumes: - /var/lib/postgresql/data (no source), that is an anonymous volume and every down discards it. Name your data volumes. Bind mounts are host paths and are never deleted by Compose — see Storage.

Part 3 — Services, Networking and the Two Kinds of Port

Compose puts every service on a user-defined bridge called <project>_default. As established in Networking, a user-defined bridge has an embedded DNS server, so service names resolve — this is the single feature that makes Compose worth using for local development.

services:
  api:
    build: .
    ports:
      - "8080:3000"          # host 8080 → container 3000, reachable from OUTSIDE the host
    environment:
      DATABASE_URL: postgres://app@db:5432/shop      # ← "db" is the service name
  db:
    image: postgres:16
    expose:
      - "5432"               # documentation only; container-to-container needs NO publishing
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
ports:expose:
EffectDNAT rule on the host; port is reachable from the networkNone at runtime — metadata/documentation
Needed for service→service?❌ No❌ No
Needed for host→service?✅ Yes❌ Useless
Firewall interactionBypasses UFW (DNAT precedes INPUT)n/a
🔑 Publishing a database port in a Compose file is the most common accidental exposure on the internet. ports: - "5432:5432" on a cloud VM publishes Postgres to 0.0.0.0, and as demonstrated in Networking, the host firewall does not stop it. If you need it for a local client, bind to loopback: "127.0.0.1:5432:5432".

The YAML base-60 trap

Compose files are YAML 1.1, where an unquoted a:b pair of integers is a sexagesimal number. This silently rewrites your port mapping:

services:
  ssh:
    image: linuxserver/openssh-server
    ports:
      - 22:22            # ← unquoted

$ docker compose config | grep -A3 ports
    ports:
      - mode: ingress
        target: 1342           ← 22 × 60 + 22
        published: "1342"
        protocol: tcp

$ docker compose up -d && docker compose port ssh 22
Error: No public port '22/tcp' published for myapp-ssh-1
WrittenParsed asResult
- 22:22Integer 1342Wrong port, no error
- 08:00Invalid octal → errorFails loudly (lucky)
- 3000:3000Too large for base-60 → stringWorks by accident
- "22:22"String✅ Correct, always

Always quote port mappings. The rule is easy to remember because the values that "work by accident" are exactly the ones above 60 — which is why nobody notices until they map a low port.

Part 4 — .env Is Not env_file

These two look interchangeable and are not. They operate at different times, on different things. This is the highest-frequency Compose bug in existence.

.env (the file next to the Compose file)env_file: (a service key)
Consumed byThe Compose CLIThe container
WhenParse time, before the model existsRun time, when the container is created
PurposeFill ${VAR} placeholders in the YAMLSet environment variables inside the process
Visible in compose config✅ Substituted values appear❌ Only the file path
Visible to the app❌ Not unless you pass it through✅ Yes
Configurable path--env-fileAny list of paths
# .env
TAG=1.4.2
DB_PASSWORD=hunter2

# compose.yaml
services:
  api:
    image: myco/api:${TAG}           # ← .env supplies this. Works.
    environment:
      DB_PASSWORD: ${DB_PASSWORD}    # ← must be forwarded EXPLICITLY

$ docker compose config | head -5
services:
  api:
    environment:
      DB_PASSWORD: hunter2
    image: myco/api:1.4.2            ← both resolved, because both were referenced

The bug, in full:

# .env
API_KEY=sk-live-9f21

# compose.yaml           ← no reference to API_KEY anywhere
services:
  api:
    image: myco/api:1.4.2

$ docker compose up -d
$ docker compose exec api printenv API_KEY
                                        ← empty. "But it's in .env!"

Fix A (forward it):      environment: [API_KEY]        # bare name = pass through
Fix B (load it in the container):  env_file: [.env]
🔑 Say it in one line: .env configures the Compose file; env_file configures the container. docker compose config is the decisive test — if the value does not appear in the rendered output under environment:, the process will not see it. Note also that a shell variable overrides .env: precedence is shell environment → --env-file/.env → default in ${VAR:-fallback}.

Interpolation syntax is worth knowing precisely, because the two-character difference between - and ? is the difference between a silent default and a hard failure:

SyntaxBehaviour
${VAR}Empty string if unset, with a warning
${VAR:-default}Default if unset or empty
${VAR-default}Default only if unset (empty stays empty)
${VAR:?message}Error and exit if unset or empty — use this for required values
$$A literal $ — needed in any command containing shell variables

Part 5 — Merging, Overrides and Profiles

Compose reads compose.yaml plus compose.override.yaml automatically, and any number of files with repeated -f. The merge rules are not uniform, and knowing which keys concatenate versus replace prevents a whole class of surprise:

Key typeRuleExamples
ScalarsReplacedimage, user, restart
MappingsMerged key by keyenvironment, labels, extra_hosts
Multi-value sequencesConcatenatedports, expose, dns, tmpfs, volumes
Command-ish sequencesReplaced wholesalecommand, entrypoint, healthcheck.test
# compose.yaml                       # compose.override.yaml (auto-loaded)
services:                            services:
  api:                                 api:
    image: myco/api:1.4.2                build: .
    ports: ["8080:3000"]                 ports: ["9229:9229"]
    environment:                         environment:
      LOG_LEVEL: info                      LOG_LEVEL: debug
    command: ["node","server.js"]        command: ["nodemon","server.js"]

$ docker compose config
    command: [nodemon, server.js]        ← REPLACED
    environment:
      LOG_LEVEL: debug                   ← MERGED (override wins per key)
    ports:
      - "8080:3000"                      ← CONCATENATED, both present
      - "9229:9229"
⚠️ Concatenation of ports is why "production" overrides do not remove a development port. -f compose.yaml -f compose.prod.yaml cannot delete 9229:9229; it can only add. Structure the base file as the minimum common configuration and put environment-specific additions in overrides — never the reverse. In production, explicitly disable the auto-override with -f compose.yaml alone, or Compose will silently merge your dev file if it happens to be present.

Profiles: services that only run when asked

services:
  api:        { build: . }                         # no profile → ALWAYS started
  db:         { image: postgres:16 }               # no profile → ALWAYS started
  seed:
    image: myco/seed
    profiles: ["tools"]                            # only with --profile tools
  jaeger:
    image: jaegertracing/all-in-one
    profiles: ["debug", "tools"]                   # either profile activates it

$ docker compose up -d                    → api, db
$ docker compose --profile tools up -d    → api, db, seed, jaeger
$ COMPOSE_PROFILES=debug docker compose up -d   → api, db, jaeger

Profiles replaced the old habit of maintaining four near-identical Compose files. YAML anchors handle the other half of the duplication problem — repeated blocks within one file:

x-logging: &default-logging          # x- prefixed keys are ignored by Compose
  driver: json-file
  options: { max-size: "10m", max-file: "3" }

services:
  api:    { image: myco/api,    logging: *default-logging }
  worker: { image: myco/worker, logging: *default-logging }

Part 6 — What Compose Honours, Ignores, and Cannot Do

The Compose specification covers Swarm as well as single-host Compose, so a valid file can contain keys the local engine quietly disregards. Knowing the split saves an afternoon of "why is my replica count ignored":

Keydocker compose upNotes
deploy.resources.limits.cpus/memory✅ AppliedBecomes --cpus/--memory; see Resource Limits
deploy.resources.reservations✅ Applied (memory, devices)GPU requests live here
deploy.replicas❌ IgnoredUse --scale svc=N or scale:
deploy.restart_policy❌ IgnoredUse the top-level restart:
deploy.placement, update_config❌ IgnoredSwarm-only
restart: unless-stopped✅ AppliedThe one you almost always want
$ docker compose up -d --scale worker=3
[+] Running 3/3
 ✔ Container myapp-worker-1  Started
 ✔ Container myapp-worker-2  Started
 ✔ Container myapp-worker-3  Started

$ docker compose ps --format '{{.Name}}\t{{.Ports}}'
myapp-worker-1
myapp-worker-2
myapp-worker-3

# but if the service publishes a fixed host port, scaling fails immediately:
$ docker compose up -d --scale api=3
Error: driver failed programming external connectivity: Bind for 0.0.0.0:8080 failed:
port is already allocated

That error is the honest boundary of Compose: one host, one port, no load balancer. Scaling a published service requires either a range ("8080-8082:3000"), a random host port ("3000"), or a reverse proxy in front — at which point you are hand-building what an orchestrator gives you.

NeedComposeVerdict
Reproducible local dev environmentPurpose-built✅ Use it
CI integration-test fixturesup --wait, run --rm✅ Use it
Single-VM side project / demoFine with restart: unless-stopped✅ Acceptable
Rolling deploys, zero downtimeRecreate = downtime❌ Orchestrator
Multi-host, self-healing, autoscalingNo scheduler at all❌ Kubernetes

Two commands close the gap for the cases Compose is right for. docker compose up --wait blocks until every service with a healthcheck reports healthy and exits non-zero if one does not — the correct entry point for CI, covered in Health Checks & Startup Order. And docker compose watch syncs source files into running containers or rebuilds on change, replacing the bind-mount-plus-nodemon arrangement most projects hand-roll.

❌ A single docker-compose.yml with unquoted ports, a committed .env, depends_on treated as readiness, and docker compose down -v in the team's "reset" script. The project name comes from the directory, so when the repo is cloned into ~/work/api alongside another api checkout, up recreates the wrong containers. ports: - 5432:5432 publishes the database to 0.0.0.0 on the staging VM, where the firewall does not stop it. The app reads API_KEY from .env and gets an empty string, so someone "fixes" it by hard-coding the key in the YAML. Migrations run before Postgres finishes initialising roughly one time in four, and CI marks it flaky. And down -v in the reset script destroys the seeded volume, so onboarding takes twenty minutes each morning.

✅ Pin the project name, quote every port, bind local-only ports to loopback, forward variables explicitly, gate startup on health, and never put -v in a routine command. Set name: shop at the top of the file so no directory rename can strand a volume. Write "127.0.0.1:5432:5432" — quoted for YAML, loopback-bound for safety. Declare required values as ${DB_PASSWORD:?set DB_PASSWORD} so a missing secret fails at config time rather than at 3am. Use depends_on: {db: {condition: service_healthy}} with a real healthcheck, and up --wait in CI. Keep the base file as the common minimum, add per-environment overrides, and run production with an explicit -f list so the dev override is never merged by accident. Reserve down -v for a deliberate, separately-named script.

Interview Questions

Beginner: What does Docker Compose give you over a series of docker run commands?

Declarative, reproducible, and namespaced. The same set of containers, networks and volumes comes up identically on any machine from a file in version control, and one command tears the whole thing down again.

Concerndocker run scriptsCompose
Service discoveryManual --network + --nameAutomatic user-defined bridge with DNS
Startup orderHand-sequenceddepends_on graph
TeardownRemember every namedown uses project labels
Config driftWhatever is in your shell historyCommitted file
IdempotenceNoneconfig-hash: unchanged services are left alone

The honest framing for an interview: Compose is not a runtime. It issues the same daemon API calls you would issue yourself. Its value is the file, the namespace, and the dependency graph — not any new isolation or scheduling capability.

Beginner: How do two services in a Compose file talk to each other?

By service name, over the project's default network, with no port publishing at all. Compose creates <project>_default as a user-defined bridge, and user-defined bridges have an embedded DNS resolver at 127.0.0.11.

services:
  api: { build: ., environment: { DB_HOST: db } }
  db:  { image: postgres:16 }

$ docker compose exec api getent hosts db
172.19.0.2       db
$ docker compose exec api nc -z db 5432 && echo reachable
reachable                       ← no "ports:" on db at all

Two follow-ups worth pre-empting:

  • ports: is only for reaching a service from outside the host. It is not needed, and not helpful, for container-to-container traffic.
  • The address is the container port, not the published port. With "8080:3000", other services connect to api:3000. Using api:8080 is a very common error — 8080 exists only on the host side of the NAT.

The default bridge (docker run with no network) has no DNS, which is why the legacy --link flag existed. See Networking.

Mid: Explain the difference between .env and env_file:.

They act at different times on different things. .env is read by the Compose CLI before the model exists and fills ${VAR} placeholders in the YAML. env_file: is a service key whose paths are read when the container is created and whose contents become the process environment.

.envenv_file:
ReaderCompose CLIContainer
EffectText substitution in the fileEnvironment variables in the process
Shows in compose configSubstituted valuesJust the path

The bug this causes: a value sits in .env, is never referenced in the YAML, and the application reads an empty variable. Fixes are environment: [API_KEY] (a bare name means "pass through from the resolved environment") or env_file: [.env].

Precedence, highest first: docker compose run -e → shell environment → environment: in the service → env_file: → image ENV. Note that a value in the shell beats .env during interpolation, which is how a stale exported variable quietly overrides the committed default.

Neither is a secrets mechanism. Both end up in docker inspect and /proc/1/environ. For credentials, mount a file — see Environment, Config & Secrets.

Mid: You run docker compose -f base.yml -f prod.yml config and a development debug port is still there. Why?

Because ports is a multi-value sequence, and multi-value sequences concatenate. Compose merging is per-key-type, not uniform:

TypeRuleKeys
ScalarReplaceimage, restart, user
MappingMerge per keyenvironment, labels
Multi-value listConcatenateports, volumes, dns, tmpfs
Command listReplace wholecommand, entrypoint

An override file can add a port but cannot remove one. The structural fix is to make the base file the minimum common denominator and put dev-only extras in compose.override.yaml — which is auto-loaded for developers and simply not passed in production.

The related trap: compose.override.yaml is loaded implicitly. On a server where that file happens to exist, docker compose up merges it without saying so. Deploy with an explicit -f base.yml -f prod.yml, and verify with config — the rendered model is the only thing worth reviewing.

Senior: A team runs production on a single VM with Compose. When is that defensible, and what would you require?

It is defensible when the blast radius is small and the alternative's operational cost is real. One VM, one team, downtime measured in seconds being acceptable, and no requirement for multi-AZ. Kubernetes for a three-service side project buys a control plane to operate and little else. The honest question is not "is Compose production-grade" but "what does this workload actually need".

What Compose cannot do, and must therefore be compensated for:

GapConsequenceCompensation
No rolling updateRecreate = downtime per deployProxy + two stacks, or accept the seconds
No schedulerHost dies, everything is downAccept, or move to an orchestrator
No health-based restartrestart: reacts to exit, not to unhealthyExternal watchdog on the health endpoint
One host, one port--scale fails on fixed portsPort range + proxy
No secret storeFiles on the hostFetch at start-up into tmpfs

What I would require before signing off: a pinned name:; images referenced by immutable digest or CI-produced tag, never latest and never built on the box; restart: unless-stopped on every service; healthchecks with depends_on: condition: service_healthy; explicit -f files in the deploy script with the dev override absent; log rotation configured (an unrotated json-file driver fills the disk — see Logging); memory limits so one service cannot OOM the host (Resource Limits); named volumes with a tested restore, not just a backup; and down -v nowhere near any script anyone runs routinely.

The migration trigger should be stated up front: the day you need zero-downtime deploys, a second host, or per-service autoscaling, the compensations stop being cheaper than the orchestrator. Write that down when you choose Compose, so the decision gets revisited on evidence rather than inertia.

Senior: Design a Compose setup that serves local development, CI, and a staging VM from one source of truth.

One base file expressing what is invariant, plus additive overrides, plus profiles for optional tooling. The base must contain nothing that any environment needs to remove, because overrides cannot subtract.

compose.yaml              name, services, networks, named volumes, healthchecks,
                          restart: unless-stopped, resource limits, log rotation
compose.override.yaml     dev only, AUTO-LOADED: build:, bind mounts, debug ports,
                          LOG_LEVEL=debug, seeded fixtures
compose.ci.yaml           explicit: no bind mounts, image from ${TAG}, tmpfs for
                          data volumes (fast, disposable), no published ports
compose.staging.yaml      explicit: image digest, loopback-bound admin ports,
                          real secret mounts, external network for the proxy

dev      $ docker compose up -d                       # base + override
CI       $ docker compose -f compose.yaml -f compose.ci.yaml up -d --wait
staging  $ docker compose -f compose.yaml -f compose.staging.yaml up -d --wait

Design decisions worth defending:

  • The image tag is a required variable: image: myco/api:${TAG:?TAG is required}. Dev supplies it in .env; CI and staging supply the commit SHA. A missing tag fails at config time, before anything starts.
  • Never build: outside development. CI and staging pull an artefact that was already tested. A staging build is a different image from the one CI approved.
  • up --wait everywhere except interactive dev, so a failed dependency is a non-zero exit rather than a flaky test — this is the entire point of healthchecks.
  • Profiles for optional services (tools, observability, seed) rather than more files. Files multiply combinatorially; profiles compose.
  • Secrets never in any file. Staging mounts them from the host secret agent's tmpfs path; CI injects short-lived ones from the runner's identity.
  • The deploy script prints docker compose config into the job log, so every deploy records the exact resolved model. This is the single highest-value habit here: the raw YAML is not what ran.

What I would explicitly not do: maintain four full standalone files (they drift within a month), put environment logic in a shell wrapper that generates YAML (now you have a compiler to debug), or use extends: across files — it is quietly limited, ignores depends_on and volumes_from, and the merge model already covers the cases that matter.

🏋️ Exercises

1 (easy): Prove the YAML base-60 port trap and the quoting fix.
Solution 
$ mkdir yamltrap && cd yamltrap
$ cat > compose.yaml <<'EOF'
name: yamltrap
services:
  a:
    image: nginx:alpine
    ports:
      - 22:22
  b:
    image: nginx:alpine
    ports:
      - "22:22"
EOF

$ docker compose config | grep -E 'published|target'
        target: 1342                  ← service a: 22 × 60 + 22
        published: "1342"
        target: 22                    ← service b: correct
        published: "22"

Now watch the failure mode that makes it hard to spot — nothing errors:

$ docker compose up -d a
[+] Running 1/1
 ✔ Container yamltrap-a-1  Started            ← success!

$ docker compose port a 22
Error: No public port '22/tcp' published for yamltrap-a-1

$ docker port yamltrap-a-1
1342/tcp -> 0.0.0.0:1342                      ← the port that was never in the file

The boundary of the trap, measured:

- 22:22       → 1342      broken
- 59:59       → 3599      broken
- 60:60       → "60:60"   works (60 is not a valid base-60 digit → parsed as string)
- 8080:80     → "8080:80" works by accident

Every value where both sides are under 60 is silently wrong. Those are exactly the privileged ports — 22, 25, 53 — so the trap is concentrated where it hurts most. Quote every mapping; docker compose config is the check.

2 (easy): Demonstrate that .env does not reach the container, then fix it two ways.
Solution 
$ mkdir envdemo && cd envdemo
$ cat > .env <<'EOF'
TAG=alpine
API_KEY=sk-live-9f21
EOF

$ cat > compose.yaml <<'EOF'
name: envdemo
services:
  app:
    image: busybox:${TAG}
    command: sh -c "printenv API_KEY || echo 'API_KEY is UNSET'; sleep 300"
EOF

$ docker compose up -d && docker compose logs app
envdemo-app-1  | API_KEY is UNSET

${TAG} worked — the image really is busybox:alpine — so .env was read. It just does not travel into the container:

$ docker compose config | head -6
name: envdemo
services:
  app:
    command: sh -c "printenv API_KEY || echo 'API_KEY is UNSET'; sleep 300"
    image: busybox:alpine          ← interpolated
                                   ← no environment: block at all

Fix A — forward it explicitly (bare name = pass through):
  services:
    app:
      environment:
        - API_KEY

$ docker compose config | grep -A2 environment
    environment:
      API_KEY: sk-live-9f21        ← now in the model
$ docker compose up -d && docker compose logs app | tail -1
envdemo-app-1  | sk-live-9f21

Fix B — load the file into the container:
  services:
    app:
      env_file: [.env]

$ docker compose config | grep -A2 env_file
    env_file:
      - path: /home/dev/envdemo/.env    ← path only; values are read at run time
$ docker compose up -d && docker compose exec app printenv | sort
API_KEY=sk-live-9f21
TAG=alpine                              ← note: env_file passes EVERYTHING, incl. TAG

The difference matters: Fix A gives the container exactly one variable; Fix B gives it every line of the file, including CLI-only values like TAG and COMPOSE_PROJECT_NAME. Prefer an explicit list, and keep a separate app.env if you use env_file.

Finally, confirm the shell beats .env:

$ API_KEY=from-shell docker compose config | grep API_KEY
      API_KEY: from-shell                ← shell environment wins over .env

$ docker compose up -d

local     shop_pgdata                     ← 3 rows, now referenced by nothing
local     shop-v2_pgdata                  ← empty, freshly initialised

Nothing was deleted and nothing errored — the app simply came up against a different volume. On a laptop this is confusing; on a server where docker volume prune runs on a schedule, the old volume is deleted as unreferenced and the data is gone.

The fix — pin the name so it is a property of the project, not the filesystem:

$ head -1 compose.yaml
name: shop                              ← added

$ docker compose down && docker compose up -d && sleep 8
$ docker compose exec -T db psql -U postgres shop -c "SELECT count(*) FROM orders;"
 count
-------
     3                                  ← the original data, from shop_pgdata

Verify the second failure mode too — two checkouts with the same basename:

$ mkdir -p ~/clients/acme/api ~/clients/globex/api

$ cd ~/clients/globex/api && docker compose up -d

Rule: every Compose file gets a top-level name:, first line, no exceptions. It costs one line and removes an entire class of data-loss incident.

Solution 
$ cat > compose.yaml <<'EOF'

services:

    image: nginx:1.27-alpine
    command: ["nginx-debug","-g","daemon off;"]

    environment: { LOG_LEVEL: debug }
    volumes: [ "./fixtures:/fixtures:ro" ]

EOF

$ docker compose -f compose.yaml -f compose.dev.yaml config

services:
  app:
    command: [nginx-debug, -g, daemon off;]     SCALAR-ish list → REPLACED
    environment:
      LOG_LEVEL: debug                          MAPPING → merged, override wins
      REGION: eu-west-1                         MAPPING → base key survives
    image: nginx:1.27-alpine                    SCALAR → replaced
    labels:
      owner: platform                           MAPPING → merged
      tier: web
    ports:
      - "8080:80"                               MULTI-VALUE → CONCATENATED
      - "9090:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro         MULTI-VALUE → CONCATENATED
      - ./fixtures:/fixtures:ro
KeyRule observedCan an override remove the base value?
imageReplaced✅ Yes
commandReplaced whole✅ Yes
environmentMerged per key⚠️ Only by setting it empty
labelsMerged per key⚠️ Same
portsConcatenated❌ Never
volumesConcatenated❌ Never

The concatenation of volumes is the one that bites hardest: a "production" override cannot remove the development bind mount, so the production container gets the developer's source tree mounted over its application directory if that path is present. Prove it:

$ docker compose -f compose.yaml -f compose.dev.yaml up -d
$ docker inspect mergelab-app-1 --format '{{range .Mounts}}{{.Source}} → {{.Destination}}
{{end}}'
/home/dev/mergelab/site     → /usr/share/nginx/html
/home/dev/mergelab/fixtures → /fixtures        ← both mounts, as predicted

Structural conclusion: put nothing in the base file that any environment needs to remove. Bind mounts, debug ports and build: belong in compose.override.yaml — auto-loaded in dev, simply not listed anywhere else.

6 (hard): Find the limits of Compose as a runtime: scale a service and time a deploy.
Solution 
$ cat > compose.yaml <<'EOF'
name: limits
services:
  web:
    image: nginx:1.25-alpine
    ports: ["8080:80"]
EOF

$ docker compose up -d --scale web=3
Error response from daemon: driver failed programming external connectivity on
endpoint limits-web-2: Bind for 0.0.0.0:8080 failed: port is already allocated

One host, one port. The three workarounds, and what each costs:

① Port range      ports: ["8080-8082:80"]
$ docker compose up -d --scale web=3 && docker compose ps --format '{{.Name}} {{.Ports}}'
limits-web-1 0.0.0.0:8080->80/tcp
limits-web-2 0.0.0.0:8081->80/tcp
limits-web-3 0.0.0.0:8082->80/tcp
   → works, but callers must know three addresses. No balancing.

② Random host port   ports: ["80"]
limits-web-1 0.0.0.0:32773->80/tcp        ← ports change on every recreate

③ Reverse proxy in the stack, web publishes nothing
   nginx/traefik resolves "web" via Docker DNS → round-robins the 3 A records
$ docker compose exec proxy getent hosts web
172.20.0.3       web
172.20.0.4       web
172.20.0.5       web                      ← DNS-level balancing, no health awareness

Now measure a deploy. This is the number that decides whether Compose is acceptable in production:

$ while true; do curl -s -o /dev/null -w '%{http_code}\n' localhost:8080; done > hits.txt &
$ time docker compose up -d --force-recreate web
[+] Running 1/1
 ✔ Container limits-web-1  Started                          1.4s
real    0m1.482s
$ kill %1
$ sort hits.txt | uniq -c
    412 200
     37 000                              ← 37 failed requests: connection refused

Compose recreates: stop, remove, create, start. There is no overlap and no draining, so the gap is a hard outage of roughly a second per service, per deploy. With a proxy and two stacks you can do better, at the cost of hand-building blue/green:

$ docker compose -p shop-blue  up -d          # running, proxy points here
$ docker compose -p shop-green up -d --wait   # new version, healthy before any traffic
$ ./proxy-switch green                        # atomic upstream swap
$ docker compose -p shop-blue down            # after a soak period
$ sort hits.txt | uniq -c
    880 200                              ← 0 failures, at the cost of a script you own

The decision, stated honestly: the middle column is where most single-VM production Compose setups end up, and it is a defensible place to be — until the day you own enough of your own deployer that you are maintaining a worse orchestrator. That is the migration signal, and it is worth writing down at the moment you choose Compose.

🎯 Key Takeaways

  • Compose is a client, not a runtime — it issues the same daemon API calls you would, then labels the results as a project.
  • Ownership is expressed with com.docker.compose.* labels; down deletes exactly what carries the project label.
  • The config-hash makes up idempotent — and is why restart never picks up a file change. Use up -d.
  • The project name defaults to the directory basename; renaming the directory strands the volume (measured: 3 rows unreachable, a fresh empty volume created).
  • Two checkouts with the same basename share a project and recreate each other's containers. Pin name: on line 1.
  • down keeps named volumes but discards anonymous ones; down -v destroys named volumes irreversibly.
  • Service names resolve over the project's user-defined bridge, so container-to-container traffic needs no ports: at all; peers connect to the container port.
  • expose: has no runtime effect whatsoever — it is documentation.
  • Unquoted 22:22 is YAML base-60 and becomes port 1342, silently; every mapping where both sides are under 60 is wrong. Quote them all.
  • .env configures the Compose file; env_file configures the container — the empty-variable bug, verified, plus both fixes.
  • Shell environment beats .env during interpolation; ${VAR:?msg} turns a missing required value into a config-time failure.
  • Merging is per key type: scalars and command replace, mappings merge, and ports/volumes concatenate and can never be removed by an override.
  • compose.override.yaml is auto-loaded — deploy with an explicit -f list or a stray dev file gets merged in production.
  • Profiles gate optional services without multiplying files; x- keys plus YAML anchors remove in-file duplication.
  • deploy.resources.limits is honoured, but deploy.replicas and deploy.restart_policy are ignored outside Swarm.
  • --scale fails on a fixed published port — one host, one port, no load balancer.
  • A Compose recreate is a hard gap: 37 failed requests measured for ~1.5s of downtime per service, per deploy.
  • Blue/green with two project names and a proxy reaches 0 failures — at the cost of owning your own deployer, which is the signal to move to an orchestrator.
  • docker compose config is the debugging tool: the raw YAML is never what ran. Print it into every deploy log.
