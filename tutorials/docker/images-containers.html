Images, Layers & the Union Filesystem Foundations

What you'll master: why an image is a stack rather than a filesystem, and the two consequences that follow — layers are shared between images (so 10 images can cost barely more than one) and layers are immutable (so deleting a file in a later layer does not reclaim its space, which is how secrets leak into published images); how overlayfs assembles those layers into one root directory, and what a whiteout file is; copy-up, the mechanism that makes the first write to a large file slow and surprises people benchmarking containers; content-addressable digests, and why deploying by tag is deploying something mutable; the difference between what docker images reports and what the disk actually holds; and how to read image history to find what made an image large. Prerequisites: What a Container Actually Is.

Part 1 — An Image Is a Stack of Layers

Each instruction in a Dockerfile that changes the filesystem produces a layer. An image is those layers, ordered, plus metadata describing how to run it.

FROM node:20-alpine        →  layer 1: the base image filesystem
WORKDIR /app               →  (metadata only, no filesystem layer)
COPY package.json .        →  layer 2: adds /app/package.json
RUN npm ci                 →  layer 3: adds /app/node_modules
COPY . .                   →  layer 4: adds the application source
CMD ["node","server.js"]   →  (metadata only)

           ┌──────────────────────────────┐  ← thin WRITABLE layer (per container)
           ├──────────────────────────────┤
           │ layer 4: app source          │  ┐
           │ layer 3: node_modules        │  │ read-only,
           │ layer 2: package.json        │  │ shared by every container
           │ layer 1: node:20-alpine      │  ┘ from this image
           └──────────────────────────────┘
🔑 Layers are immutable and content-addressed, which is what makes them shareable. A layer is identified by the SHA-256 digest of its contents, so two images built from the same base literally reference the same layer on disk — pulled once, stored once. That is why the second image based on node:20-alpine downloads almost nothing, and why docker images reporting "1.1 GB" for ten images does not mean 1.1 GB of disk is in use.

$ docker images
REPOSITORY   TAG       IMAGE ID       SIZE
myapp        v1        a1b2c3d4e5f6   412MB
myapp        v2        f6e5d4c3b2a1   412MB
myapp        v3        1a2b3c4d5e6f   413MB
                                      ────── "1.2GB" if you add them up

$ docker system df
TYPE      TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images    3       1        418.2MB   6.1MB (1%)
                           ↑ the ACTUAL disk usage — layers counted once

docker images reports each image's full size including shared layers, so the column cannot be summed. docker system df is the honest number.

Part 2 — Overlayfs: How the Stack Becomes One Directory

The union filesystem — overlay2 on modern Docker — merges the layers so the process sees a single root.

overlayfs terminology:

  lowerdir   the read-only image layers (multiple, stacked)
  upperdir   the container's writable layer
  workdir    scratch space overlayfs needs internally
  merged     the unified view the process actually sees

Reads:   search upperdir first, then each lowerdir top-down; first match wins
Writes:  always go to upperdir

$ docker run -d --name demo alpine sleep 3600
$ docker inspect demo --format '{{json .GraphDriver.Data}}' | python -m json.tool
{
    "LowerDir": "/var/lib/docker/overlay2/9f8e.../diff",
    "MergedDir": "/var/lib/docker/overlay2/a1b2.../merged",
    "UpperDir": "/var/lib/docker/overlay2/a1b2.../diff",
    "WorkDir": "/var/lib/docker/overlay2/a1b2.../work"
}

$ sudo ls /var/lib/docker/overlay2/a1b2.../diff      # empty until something is written
$ docker exec demo sh -c 'echo hello > /newfile'
$ sudo ls /var/lib/docker/overlay2/a1b2.../diff
newfile                                              ← the write landed in upperdir

Deleting a file from a lower layer cannot actually remove it, because lower layers are read-only. Overlayfs records a whiteout — a character device with major/minor 0/0 — in the upper layer, which hides the file from the merged view while it remains on disk underneath.

$ docker exec demo rm /etc/hostname
$ sudo ls -l /var/lib/docker/overlay2/a1b2.../diff/etc/
c--------- 2 root root 0, 0 Aug 18 14:22 hostname
└┬┘                    └─┬─┘
character device       0/0  = a WHITEOUT marker, not the file

# the file is still present in the lower layer
$ sudo ls /var/lib/docker/overlay2/9f8e.../diff/etc/hostname
/var/lib/docker/overlay2/9f8e.../diff/etc/hostname
🔑 This is why RUN rm secret.txt in a Dockerfile does not remove the secret from the image. The delete creates a whiteout in a new layer; the file itself is still sitting in the earlier layer, and anyone who pulls the image can extract it. The image also does not get smaller — it gets slightly larger, because you added a layer. Secrets removed this way are still published.

Part 3 — Copy-Up: Why the First Write Is Slow

Writes go to the upper layer, but overlayfs cannot modify a file in place if it lives in a lower layer. It must first copy the entire file upward — regardless of how much of it you are changing.

Modifying one byte of a 500 MB file that lives in a lower layer:

  1. overlayfs copies all 500 MB into upperdir      ← copy-up, the expensive part
  2. the one-byte change is applied to the copy
  3. subsequent writes to that file are normal speed

Cost is proportional to FILE SIZE, not to how much you wrote.
OperationCost
Reading a file from a lower layerNormal — no copy involved
First write to a lower-layer fileCopy the whole file up
Subsequent writes to that fileNormal — it now lives in upperdir
Creating a brand-new fileNormal — created directly in upperdir
Any write inside a volumeNormal — volumes bypass the union filesystem entirely

The practical consequences are the reason databases and other write-heavy workloads must use volumes rather than the container filesystem: a database file baked into an image pays a full copy-up on the first write, and every container from that image pays it separately. Exercise 3 measures it.

Many small files are also expensive — overlayfs performs a copy-up per file, so a build step touching thousands of files in a lower layer is slow in a way that is invisible from the Dockerfile.

Part 4 — Digests, Tags and What You Actually Deploy

Images are content-addressable. The digest is derived from the content, so it cannot change; a tag is a mutable pointer that can be moved to different content at any time.

myapp:1.2.3                                   ← a TAG: mutable, can be repointed
myapp@sha256:a1b2c3d4e5f6...                  ← a DIGEST: immutable, content-addressed

$ docker images --digests
REPOSITORY  TAG    DIGEST                    IMAGE ID      SIZE
myapp       1.2.3  sha256:a1b2c3...          f6e5d4c3b2a1  412MB
🔑 Deploying by tag means deploying whatever that tag points at right now, which may not be what you tested. Anyone with push access can move 1.2.3, and :latest is simply a tag with a misleading name — it carries no ordering and no guarantee of recency. Production should deploy by digest, or use an immutable-tag policy in the registry, so that what was tested is provably what runs.

# what a deploy should reference
image: myrepo/myapp@sha256:a1b2c3d4e5f6...

# resolve a tag to a digest before promoting
$ docker buildx imagetools inspect myrepo/myapp:1.2.3 --format '{{.Manifest.Digest}}'
sha256:a1b2c3d4e5f6...

Two IDs get confused constantly. The image ID is a local content hash of the image config; the digest is the hash of the manifest as stored in a registry. They differ, and only the digest is meaningful across machines.

IdentifierScopeUse for
Tag (myapp:1.2.3)Registry, mutableHuman convenience
Digest (sha256:…)Global, immutableDeployments, provenance
Image IDLocal daemon onlyLocal scripting
Layer digestGlobalDeduplication, caching

Part 5 — Reading an Image's History

When an image is unexpectedly large, the layer history tells you which instruction caused it.

$ docker history myapp:v1
IMAGE          CREATED BY                                      SIZE
a1b2c3d4e5f6   CMD ["node" "server.js"]                        0B
<missing>      COPY . . # buildkit                             2.4MB
<missing>      RUN npm ci # buildkit                           268MB      ← the bulk
<missing>      COPY package.json . # buildkit                  1.2kB
<missing>      WORKDIR /app                                    0B
<missing>      /bin/sh -c #(nop) CMD ["node"]                  0B
<missing>      /bin/sh -c #(nop) ADD file:abc… in /            141MB      ← the base

$ docker history myapp:v1 --no-trunc --format '{{.Size}}\t{{.CreatedBy}}' | sort -rh | head -3
# largest layers first — where to focus optimisation

$ docker image inspect myapp:v1 --format '{{len .RootFS.Layers}}'
9                                          # layer count

<missing> is not an error. Intermediate image IDs are only retained for layers built locally; for pulled images the history is present but the intermediate IDs are not, so Docker prints <missing>. The sizes and commands are still accurate.

To find large files rather than large layers, export the filesystem and inspect it directly — this is how you discover the 300 MB of build cache someone left in /root/.npm:

$ docker create --name tmp myapp:v1
$ docker export tmp | tar -tv | sort -k3 -rn | head -10
$ docker rm tmp

Part 6 — Layer Count, Sharing and Housekeeping

Two questions get conflated: how many layers an image has, and how much disk it costs.

ConcernReality
"Fewer layers is faster"Largely a myth now — overlayfs handles many layers fine; there is a 127-layer limit
"Combining RUNs saves space"Only if it prevents intermediate files from being committed in a layer
Shared base layersReal and significant — standardise base images across your fleet
Layer orderMatters enormously for cache hits, not for size
Deleting files in a later layerDoes not shrink the image; adds a whiteout layer

The rule that actually saves space is to avoid creating the file in a committed layer at all — clean up within the same RUN, or use a multi-stage build so build artefacts never reach the final image:

# ❌ 3 layers; the .deb files are permanently in layer 1
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# ✅ 1 layer; the lists are never committed
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

Housekeeping matters because dangling layers and build cache accumulate quietly:

docker system df -v            # per-image, per-container, per-volume detail
docker image prune             # dangling images only
docker image prune -a          # ★ everything not used by a container — aggressive
docker builder prune           # BuildKit cache, often the largest consumer
docker system prune -a --volumes    # everything; volumes included — be careful

❌ Trying to shrink an image, or remove a secret, by deleting files in a later instruction. The Dockerfile copies a private key or a credentials file, uses it, then runs RUN rm -f /root/.ssh/id_rsa — and the team believes the secret is gone because the file is not visible in a running container. It is still in the earlier layer, extractable by anyone who pulls the image with docker save and a tar command. The same mistake applied to build artefacts makes images larger rather than smaller, because the delete adds a whiteout layer while the original data remains underneath — so a team optimising size by adding cleanup steps watches the image grow.

✅ Never let the file be committed to a layer in the first place. Do the work and the cleanup inside a single RUN, so the intermediate state never becomes a layer; use a multi-stage build so build-time material stays in a stage that is discarded; and mount secrets at build time with RUN --mount=type=secret, which makes them available to the command without ever entering the filesystem history. To verify rather than assume, run docker history for size attribution and extract the image with docker save to confirm the file is genuinely absent — if a secret was ever committed, the fix is rotating the credential, because rebuilding does not un-publish it.

Interview Questions

Beginner: What is an image layer, and why are layers shared?

A layer is the set of filesystem changes produced by one build instruction — the files added, modified, or deleted. An image is those layers stacked in order, plus metadata (entrypoint, env, exposed ports).

FROM node:20-alpine     → layer 1 (the base filesystem)
COPY package.json .     → layer 2 (adds one file)
RUN npm ci              → layer 3 (adds node_modules)
COPY . .                → layer 4 (adds source)

Layers are shared because they are content-addressed. Each layer's identity is the SHA-256 of its contents, so two images built on the same base reference the identical layer on disk. It is pulled once and stored once, no matter how many images use it.

That is why the second image from a familiar base pulls almost nothing, and why standardising base images across a fleet is a real efficiency win rather than a style preference.

A common misreading: docker images shows each image's total size including shared layers, so the column cannot be summed. Three 412 MB images may occupy 418 MB on disk in total — docker system df reports the truth.

Layers are also immutable, which has a consequence people meet the hard way: deleting a file in a later layer cannot remove it from an earlier one.

Beginner: Why doesn't RUN rm secret.txt remove the secret from the image?

Because layers are immutable and a delete only records a whiteout in a new layer.

COPY secret.txt /app/     → layer 3: the file's contents are HERE, permanently
RUN rm /app/secret.txt    → layer 4: a whiteout entry hiding it from the merged view

The merged filesystem a running container sees does not show the file, which is why the mistake feels safe. But layer 3 still contains the bytes, and anyone who pulls the image can extract them:

$ docker save myimage -o img.tar
$ tar -xf img.tar && for l in */layer.tar; do tar -tf "$l" | grep secret && \
    tar -xOf "$l" app/secret.txt; done
<the secret contents>

The image also gets bigger, not smaller — you added a layer without removing any data, which is why "cleanup" steps sometimes increase image size.

The correct approaches:

  • Same-RUN cleanup, so the file never becomes a committed layer.
  • Multi-stage builds — do the work in a stage that is discarded and copy only the artefact.
  • RUN --mount=type=secret (BuildKit) — the secret is available to the command but never enters the filesystem history.

And if a secret was already published: rotate it. Rebuilding the image does not un-publish the layer that anyone may already have pulled.

Mid: Explain copy-up and its performance implications.

Copy-up is what overlayfs does on the first write to a file that lives in a read-only lower layer. Since lower layers cannot be modified, the entire file is copied into the writable upper layer before the write is applied.

Write one byte to a 500 MB file from a lower layer:
  1. copy all 500 MB into upperdir     ← the cost
  2. apply the 1-byte change
  3. later writes are normal speed

The cost is proportional to file size, not write size, which is what makes it counterintuitive — appending a line to a large log file baked into an image is slow exactly once, then fast.

OperationCost
Read from a lower layerNormal
First write to a lower-layer fileFull file copy
New file in upperdirNormal
Anything inside a volumeNormal — bypasses overlayfs

Practical implications: databases and other write-heavy workloads must use volumes, not the container filesystem — a database file baked into an image pays copy-up on first write, in every container, separately. Workloads touching many small files pay a copy-up per file, which can make a build or startup step mysteriously slow. And benchmarks run against the container filesystem measure overlayfs rather than the application.

The general rule: the container filesystem is for the application's own files; anything written at runtime belongs in a volume, both for persistence and for I/O performance.

Mid: Why deploy by digest rather than by tag?

Because a tag is a mutable pointer and a digest is content-addressed.

myapp:1.2.3                        ← can be repointed to different content at any time
myapp@sha256:a1b2c3d4...           ← immutable: the content IS the identity

What goes wrong with tags: anyone with push access can move 1.2.3, so the image you tested is not provably the image that runs. A rebuild-and-repush under the same tag produces different content with an identical reference, and nodes that pulled earlier keep the old layers while new nodes get the new ones — a fleet running two different builds under one version number, which is extremely difficult to diagnose from logs.

:latest is the same problem with a misleading name. It is an ordinary tag with no notion of recency or ordering; it means "whatever was last pushed with that tag", which may be older than a numbered release.

How to do it properly:

# resolve at build/promotion time
DIGEST=$(docker buildx imagetools inspect myrepo/app:1.2.3 --format '{{.Manifest.Digest}}')
# deploy the digest
image: myrepo/app@${DIGEST}

Also enable immutable tags in the registry where supported (ECR, GCR, Harbor), so a tag cannot be overwritten at all — belt and braces.

The related benefit is supply-chain integrity: a digest is what signatures and attestations are bound to, so verifying provenance is only meaningful when you deploy the digest that was signed. That is covered in Registry & Supply Chain.

Senior: An image is 2 GB and should be 200 MB. How do you find and fix it?

Attribute the size to layers first, because that points directly at the instruction responsible:

$ docker history myapp:v1 --no-trunc --format '{{.Size}}\t{{.CreatedBy}}' | sort -rh | head
1.2GB   RUN /bin/sh -c apt-get update && apt-get install -y build-essential …
412MB   RUN /bin/sh -c npm ci
141MB   ADD file:… in /

Then find the actual files, since a large layer does not say which files inside it matter:

$ docker create --name tmp myapp:v1
$ docker export tmp | tar -tv | sort -k3 -rn | head -20
$ docker rm tmp
# or: dive myapp:v1   — shows per-layer file trees and wasted space

The usual culprits, in the order I find them:

  • Build toolchains in the final image — compilers, headers, build-essential. Fix with a multi-stage build so only the artefact is copied forward.
  • Package manager caches — /var/lib/apt/lists, ~/.npm, ~/.cache/pip. These must be removed in the same RUN, or they are already committed.
  • Dev dependencies — npm ci without --omit=dev.
  • The build context — COPY . . pulling in .git, node_modules, test fixtures. Fix with .dockerignore.
  • An oversized base — ubuntu or a full node where -slim or -alpine would do.

The trap to name explicitly: adding RUN rm -rf in a later instruction does not shrink anything — the data stays in the earlier layer and you have added a whiteout layer on top. The only fixes are cleaning up within the same instruction or not producing the file in the final stage at all.

How I would prioritise: multi-stage first, since it usually removes the single largest contributor in one change; then .dockerignore; then base image; then cache cleanup. And I would add a CI check that fails the build if the image exceeds a size budget, because image size regresses silently otherwise.

Senior: Your registry storage is growing without bound. Diagnose and design a fix.

Registry growth is usually not the images people think about — it is the ones nobody deletes.

The main sources:

  • Per-commit CI tags. Every build pushes app:sha-abc123, and nothing ever removes them. At 50 builds a day this dominates everything else within months.
  • Untagged manifests. Repushing a tag orphans the previous manifest — it still occupies storage but is invisible in the tag list, so it is missed by any cleanup keyed on tags.
  • Multi-arch indexes holding several per-platform images per tag, multiplying everything.
  • Layers with no remaining references, which are only reclaimed by garbage collection — deleting a manifest does not free disk on its own.

Measuring it:

# ECR
aws ecr describe-images --repository-name app \
  --query 'sort_by(imageDetails,&imageSizeInBytes)[-10:].[imageTags,imageSizeInBytes]'
# self-hosted registry
GET /v2/_catalog ; GET /v2/<name>/tags/list
registry garbage-collect /etc/docker/registry/config.yml

The retention design I would put in place:

ClassPolicy
Release tags (semver)Keep indefinitely — they may need to be redeployed
CI/commit tagsKeep 30 days, or the last N per branch
PR/preview tagsDelete when the PR closes
Untagged manifestsDelete after a short grace period (they may be part of an index)

Two details that cause incidents. First, never delete an untagged manifest that is referenced by a multi-arch index — the index survives while a platform image disappears, and pulls fail on that architecture only, which looks like a network problem. Lifecycle rules need to be index-aware. Second, deletion is only half the job: without running garbage collection, the layers stay on disk, so teams delete thousands of tags and see no space reclaimed.

Prevention is reducing what gets pushed: build multi-stage so images are small, share base images so layers deduplicate across repositories, and avoid pushing an image per commit when a tag per merged PR would do.

🏋️ Exercises

1 (easy): Prove that layers are shared and that docker images overstates disk usage.
Solution 
$ printf 'FROM alpine:3.19\nRUN echo one > /f1\n'   > /tmp/D1
$ printf 'FROM alpine:3.19\nRUN echo two > /f2\n'   > /tmp/D2
$ printf 'FROM alpine:3.19\nRUN echo three > /f3\n' > /tmp/D3
$ for i in 1 2 3; do docker build -q -t shared:v$i -f /tmp/D$i /tmp; done

$ docker images shared
REPOSITORY   TAG   IMAGE ID       SIZE
shared       v3    9c1f2e3d4a5b   7.38MB
shared       v2    8b2e1d4c3f6a   7.38MB
shared       v1    7a3d2c1b4e5f   7.38MB
                                  ────── looks like 22.1MB

Now the real disk usage:

$ docker system df
TYPE      TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images    4       0        7.42MB    7.42MB (100%)
                           ↑ 7.42MB, not 22.1MB

Three "7.38 MB images" occupy 7.42 MB total, because they share the alpine base layer. Only the tiny per-image layer is distinct.

Confirm they reference identical layer digests:

$ for i in 1 2 3; do
    echo "v$i: $(docker image inspect shared:v$i --format '{{index .RootFS.Layers 0}}')"
  done
v1: sha256:f4f8a1e4d1c1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7
v2: sha256:f4f8a1e4d1c1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7
v3: sha256:f4f8a1e4d1c1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7
     ↑ byte-identical: ONE layer on disk, referenced three times

And see sharing during a pull:

$ docker rmi -f $(docker images -q 'node:20-*') 2>/dev/null
$ docker pull node:20-alpine  | tail -2
$ docker pull node:20-alpine3.19 | grep -c "Already exists"
5                        ← 5 of the layers were already present

This is why standardising base images across a fleet is a genuine efficiency measure: shared layers are pulled once per host and stored once, no matter how many images use them.

2 (easy): Extract a "deleted" secret from a published image.
Solution 
$ mkdir -p /tmp/leak && cd /tmp/leak
$ echo "AWS_SECRET_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCY" > secret.txt
$ cat > Dockerfile <<'EOF'
FROM alpine:3.19
COPY secret.txt /app/secret.txt
RUN cat /app/secret.txt > /dev/null   # "use" it
RUN rm -f /app/secret.txt             # "remove" it
EOF
$ docker build -q -t leaky:v1 .

# the running container shows nothing — which is why this feels safe
$ docker run --rm leaky:v1 ls /app
$ docker run --rm leaky:v1 cat /app/secret.txt
cat: can't open '/app/secret.txt': No such file or directory

Now extract it from the image anyway:

$ docker save leaky:v1 -o img.tar
$ mkdir x && tar -xf img.tar -C x
$ for l in x/blobs/sha256/*; do
    tar -tf "$l" 2>/dev/null | grep -q 'secret.txt' && \
      echo "FOUND in $l:" && tar -xOf "$l" app/secret.txt
  done
FOUND in x/blobs/sha256/3f8a91c04e7b...:
AWS_SECRET_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCY

The secret is fully recoverable by anyone who can pull the image.

And the "cleanup" made the image larger:

$ printf 'FROM alpine:3.19\nCOPY secret.txt /app/secret.txt\n' > Dockerfile.nodel
$ docker build -q -t nodel:v1 -f Dockerfile.nodel .
$ docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}' | grep -E 'leaky|nodel'
leaky:v1    7.39MB      ← WITH the rm
nodel:v1    7.38MB      ← without it

The correct fix — a build secret that never enters the filesystem:

$ cat > Dockerfile.safe <<'EOF'
FROM alpine:3.19
RUN --mount=type=secret,id=mysecret \
    cat /run/secrets/mysecret > /dev/null   # used, never committed
EOF
$ docker build -q --secret id=mysecret,src=secret.txt -t safe:v1 -f Dockerfile.safe .

$ docker save safe:v1 -o safe.tar && mkdir s && tar -xf safe.tar -C s
$ for l in s/blobs/sha256/*; do tar -tf "$l" 2>/dev/null | grep 'secret.txt'; done
$ echo "exit=$?  → not present in any layer"
exit=1  → not present in any layer

The operational rule: if a secret was ever committed to a published layer, rotate the credential. Rebuilding does not retract what has already been pulled.

3 (medium): Measure copy-up cost and show volumes bypass it.
Solution 
# an image containing a large file in a lower layer
$ cat > /tmp/Dockerfile.big <<'EOF'
FROM alpine:3.19
RUN dd if=/dev/zero of=/bigfile bs=1M count=500 2>/dev/null
EOF
$ docker build -q -t bigfile:v1 -f /tmp/Dockerfile.big /tmp

# FIRST write to that lower-layer file
$ docker run --rm bigfile:v1 sh -c \
    'time dd if=/dev/zero of=/bigfile bs=1 count=1 conv=notrunc 2>/dev/null'
real    0m2.847s      ← writing ONE BYTE

2.8 seconds to write a single byte — overlayfs copied all 500 MB into the writable layer first.

The second write is normal:

$ docker run --rm bigfile:v1 sh -c \
    'dd if=/dev/zero of=/bigfile bs=1 count=1 conv=notrunc 2>/dev/null
     time dd if=/dev/zero of=/bigfile bs=1 count=1 conv=notrunc 2>/dev/null'
real    0m0.004s      ← 700x faster; the file now lives in upperdir

Cost scales with file size, not write size:

$ for sz in 50 200 500; do
    printf 'FROM alpine:3.19\nRUN dd if=/dev/zero of=/f bs=1M count=%s 2>/dev/null\n' $sz \
      > /tmp/Df
    docker build -q -t cu:$sz -f /tmp/Df /tmp >/dev/null
    printf "%4sMB file: " $sz
    docker run --rm cu:$sz sh -c \
      'S=$(date +%s%N); dd if=/dev/zero of=/f bs=1 count=1 conv=notrunc 2>/dev/null;
       E=$(date +%s%N); echo $(( (E-S)/1000000 ))ms'
  done
  50MB file: 291ms
 200MB file: 1142ms
 500MB file: 2831ms

Linear in file size, for an identical one-byte write.

A volume bypasses overlayfs entirely:

$ docker volume create vdata
$ docker run --rm -v vdata:/data alpine sh -c \
    'dd if=/dev/zero of=/data/bigfile bs=1M count=500 2>/dev/null'
$ docker run --rm -v vdata:/data alpine sh -c \
    'time dd if=/dev/zero of=/data/bigfile bs=1 count=1 conv=notrunc 2>/dev/null'
real    0m0.005s      ← no copy-up: volumes are not part of the union filesystem
LocationFirst 1-byte write to a 500MB file
Container filesystem (lower layer)2,831 ms
Container filesystem (already copied up)4 ms
Volume5 ms

This is the concrete reason databases must use volumes — not only for persistence, but because every container would otherwise pay a full copy-up on its first write to each data file.

5 (hard): Find what made an image large and cut it down.
Solution 
$ mkdir -p /tmp/fat && cd /tmp/fat
$ echo 'console.log("hi")' > app.js
$ printf '{"name":"a","version":"1.0.0","dependencies":{"express":"^4"},"devDependencies":{"jest":"^29"}}' > package.json

$ docker export t | tar -tv | sort -k3 -rn | head -6

Apply the four standard fixes:

$ printf 'node_modules\n.git\nDockerfile*\n' > .dockerignore

Verify the naive "cleanup" approach does the opposite:

$ cat > Dockerfile.cleanup <<'EOF'
FROM node:20
WORKDIR /app
RUN apt-get update && apt-get install -y build-essential
RUN apt-get remove -y build-essential && rm -rf /var/lib/apt/lists/*
COPY package.json .
RUN npm install
EOF
$ docker build -q -t cleanup:v1 -f Dockerfile.cleanup . && \
  docker images cleanup:v1 --format '{{.Size}}'
1.44GB          ← LARGER than fat:v1 (1.42GB)

Removing the packages in a later layer made the image bigger, because the original data stays in the earlier layer and the removal added another one. Only same-RUN cleanup or multi-stage actually removes bytes.

6 (hard): Show that a tag is mutable and build a digest-based deploy.
Solution 
# a local registry to demonstrate against
$ docker run -d -p 5000:5000 --name reg registry:2 >/dev/null && sleep 2

$ printf 'FROM alpine:3.19\nRUN echo "VERSION-A" > /version\n' > /tmp/Da
$ docker build -q -t localhost:5000/app:1.0 -f /tmp/Da /tmp
$ docker push -q localhost:5000/app:1.0
$ DIGEST_A=$(docker image inspect localhost:5000/app:1.0 \
             --format '{{index .RepoDigests 0}}' | cut -d@ -f2)
$ echo "digest A: $DIGEST_A"
digest A: sha256:7c9d1f2e3a4b5c6d...

$ docker run --rm localhost:5000/app:1.0 cat /version
VERSION-A

Now repoint the SAME tag at different content:

$ printf 'FROM alpine:3.19\nRUN echo "VERSION-B" > /version\n' > /tmp/Db
$ docker build -q -t localhost:5000/app:1.0 -f /tmp/Db /tmp
$ docker push -q localhost:5000/app:1.0
$ DIGEST_B=$(docker image inspect localhost:5000/app:1.0 \
             --format '{{index .RepoDigests 0}}' | cut -d@ -f2)

$ echo "digest A: $DIGEST_A"
$ echo "digest B: $DIGEST_B"
digest A: sha256:7c9d1f2e3a4b5c6d...
digest B: sha256:2f4e8a1b9c3d7e5f...     ← same tag, different content

$ docker rmi -f localhost:5000/app:1.0 >/dev/null
$ docker run --rm localhost:5000/app:1.0 cat /version
VERSION-B                                 ← "1.0" now means something else

The tag did not change; what it points at did. A node that pulled earlier still runs VERSION-A while a node pulling now gets VERSION-B — one version number, two behaviours in the fleet.

A digest cannot do this:

$ docker run --rm localhost:5000/app@$DIGEST_A cat /version
VERSION-A                                 ← still exactly what was tested
$ docker run --rm localhost:5000/app@$DIGEST_B cat /version
VERSION-B

A promotion script that pins the digest:

$ cat > promote.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
IMAGE="$1"; TAG="$2"
DIGEST=$(docker buildx imagetools inspect "${IMAGE}:${TAG}" \
         --format '{{.Manifest.Digest}}')
echo "resolved ${IMAGE}:${TAG} -> ${DIGEST}"
cat > deploy.yaml <<YAML
spec:
  containers:
    - name: app
      image: ${IMAGE}@${DIGEST}
YAML
echo "deploy.yaml pins the digest, not the tag"
EOF
$ chmod +x promote.sh && ./promote.sh localhost:5000/app 1.0
resolved localhost:5000/app:1.0 -> sha256:2f4e8a1b9c3d7e5f...
deploy.yaml pins the digest, not the tag

Also verify what a running container is actually from, which is the check that catches drift:

$ docker run -d --name running localhost:5000/app@$DIGEST_A sleep 300 >/dev/null
$ docker inspect running --format '{{.Image}}'
sha256:9a1b2c3d...                        # local image ID
$ docker inspect running --format '{{.Config.Image}}'
localhost:5000/app@sha256:7c9d1f2e3a4b5c6d...   ← provable provenance
$ docker rm -f running reg >/dev/null

🎯 Key Takeaways

  • An image is an ordered stack of immutable, content-addressed layers plus metadata; a container adds one thin writable layer.
  • Layers are shared by digest: three "7.38 MB images" occupied 7.42 MB total because they referenced the identical base layer.
  • docker images counts shared layers in every row, so the SIZE column cannot be summed — docker system df is the honest number.
  • Overlayfs merges lowerdir (read-only layers) and upperdir (writable) into the merged view the process sees.
  • Deleting a lower-layer file writes a whiteout (a 0/0 character device) that hides it — the bytes remain on disk underneath.
  • RUN rm secret.txt does not remove the secret: it was extracted from a published image with docker save and tar. Rotate any credential that was ever committed.
  • Deleting files in a later layer makes the image larger — measured 1.44 GB with cleanup versus 1.42 GB without.
  • Copy-up: the first write to a lower-layer file copies the whole file up — 2,831 ms to write one byte to a 500 MB file, and linear in file size.
  • The second write to the same file was 4 ms (700× faster), and a volume write was 5 ms because volumes bypass overlayfs entirely.
  • That is the concrete reason databases and write-heavy workloads must use volumes, not the container filesystem.
  • Tags are mutable pointers; digests are content-addressed. Demonstrated: the same tag served VERSION-A then VERSION-B while nodes ran both.
  • Deploy by digest, and enable immutable tags in the registry — signatures and attestations bind to digests, not tags.
  • :latest is an ordinary tag with no recency or ordering guarantee.
  • Image ID is local-only; the digest is what is portable across machines.
  • docker history attributes size to instructions; docker export | tar -tv finds the actual large files.
  • Real size fixes: multi-stage builds, a slimmer base, production-only dependencies, and .dockerignore — measured 1.42 GB → 213 MB (6.7×).
  • Layer count barely matters for performance (the limit is 127); layer order matters enormously for cache hits.
  • Clean up inside the same RUN, or the intermediate files are already committed to a layer.
  • Registry growth is usually per-commit CI tags and untagged manifests — and deleting manifests reclaims nothing until garbage collection runs.
