Multi-stage Builds Building Images

What you'll master: the one technique that reliably cuts image size by an order of magnitude — and the reason it works, which is that a discarded stage leaves nothing behind at all, unlike deleting files in a later layer; why this is also the correct way to handle build-time secrets, since a stage that is never copied from is never published; targeting a specific stage with --target for test and debug images from one Dockerfile; parallel stage execution in BuildKit, which makes several stages cheaper than one long chain; copying from external images and named contexts; scratch and distroless final stages, including the static-linking requirement that trips people up; and the cache implications, particularly why multi-stage builds need mode=max in CI. Prerequisites: The Build Cache & Layer Ordering.

Part 1 — Why a Discarded Stage Leaves Nothing

A Dockerfile can contain several FROM instructions. Each starts a new stage with its own filesystem, and only the last stage becomes the image — unless you copy from an earlier one explicitly.

FROM golang:1.22 AS build           ← stage 0: ~900 MB with the toolchain
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

FROM alpine:3.19                    ← stage 1: a fresh, empty filesystem
COPY --from=build /app /app         ← copy ONLY the binary
ENTRYPOINT ["/app"]

Final image: ~15 MB. The 900 MB build stage is not in it — not in a layer,
not as a whiteout, not recoverable.
🔑 This is fundamentally different from deleting files. As shown in Images, Layers & the Union Filesystem, RUN rm secret adds a whiteout while the bytes stay in the earlier layer — the image gets larger and the file is still extractable. A discarded stage is never part of the final image's layer chain at all, so there is nothing to extract. That property is what makes multi-stage the correct answer to both image size and build-time secrets.

ApproachRemoves bytes?Secret recoverable?
RUN rm file in a later layer❌ No — image grows✅ Yes
Cleanup in the same RUN✅ Yes❌ No
Separate stage, not copied from✅ Yes❌ No

Part 2 — Stage Syntax and Targets

FROM node:20 AS deps                 name a stage with AS
FROM node:20 AS builder
COPY --from=deps /app/node_modules ./node_modules     copy by NAME
COPY --from=0 /app/x /x                                or by INDEX (fragile)
COPY --from=nginx:alpine /etc/nginx/nginx.conf /conf   or from an EXTERNAL image

--target builds only up to a named stage, which lets one Dockerfile produce production, test, and debug images:

FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json ./

FROM base AS deps-prod
RUN npm ci --omit=dev

FROM base AS deps-dev
RUN npm ci                      ← includes devDependencies

FROM deps-dev AS test
COPY . .
RUN npm test                    ← fails the build if tests fail

FROM base AS production
COPY --from=deps-prod /app/node_modules ./node_modules
COPY src ./src
USER node
CMD ["node", "src/server.js"]

$ docker build --target test -t app:test .          # run tests in the build
$ docker build --target production -t app:prod .    # ship this one
$ docker build -t app:prod .                        # last stage = production
🔑 BuildKit only builds the stages the target actually depends on. Building --target production never executes the test stage, and never even builds deps-dev, because nothing in the dependency graph reaches them. Stages you do not need cost nothing — which is what makes a Dockerfile with eight stages perfectly reasonable.

Part 3 — Parallelism

BuildKit builds the stage graph, not a linear script, so independent stages run concurrently.

FROM node:20 AS frontend
RUN npm run build            ─┐
                              ├── these two run AT THE SAME TIME
FROM golang:1.22 AS backend   │
RUN go build -o /api         ─┘

FROM alpine:3.19
COPY --from=frontend /dist /www
COPY --from=backend  /api  /api

The consequence is counterintuitive: splitting work into more stages can make a build faster, because a single long RUN chain is serial by definition while separate stages are scheduled in parallel. Exercise 4 measures it.

StructureExecution
One stage, chained RUNsStrictly serial
Independent stagesParallel
Stages with COPY --from dependenciesOrdered by the graph
Unreferenced stages with a --targetNot built at all

# Go: static build → scratch
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /app ./cmd/server
            └──────┬──────┘
      REQUIRED: scratch has no libc to link against

FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /app /app
USER 65534:65534
ENTRYPOINT ["/app"]
🔑 The two things a scratch image is always missing are CA certificates and a non-root user. Without the certificate bundle, every outbound HTTPS call fails with x509: certificate signed by unknown authority — a failure that only appears at run time, against real endpoints. And scratch has no /etc/passwd, so USER must be given numerically. Distroless static solves both and costs 2 MB.

Forgetting CGO_ENABLED=0 produces a dynamically linked binary that builds fine and then fails at startup with no such file or directory — because the loader it needs does not exist, not because the binary is missing.

Part 5 — Secrets and Private Dependencies

A build stage that needs a credential can use it and be discarded, so the credential never reaches the published image.

FROM node:20 AS build
ARG NPM_TOKEN                        ← visible in THIS stage's history…
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc \
 && npm ci && rm .npmrc
COPY . .
RUN npm run build

FROM node:20-alpine                  ← …but this stage is what ships
COPY --from=build /app/dist ./dist

This works, and there is still a better option. The build stage's layers are not published, so the token is not in the final image — but if that stage is ever exported as a cache with mode=max, or built with --target build and pushed, the token travels with it. BuildKit secrets avoid the question entirely:

# syntax=docker/dockerfile:1
FROM node:20 AS build
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci                          ← never written to any filesystem layer

$ docker build --secret id=npmrc,src=$HOME/.npmrc -t app .

SSH forwarding handles private Git dependencies without copying a key:

RUN --mount=type=ssh git clone git@github.com:org/private-lib.git
$ docker build --ssh default -t app .

Part 6 — Cache Behaviour

Multi-stage interacts with caching in one way that regularly catches teams out in CI.

# ❌ mode=min exports ONLY final-image layers.
#    The expensive build stage is NOT cached.
--cache-to type=registry,ref=repo/app:cache,mode=min

# ✅ mode=max exports intermediate stages too
--cache-to type=registry,ref=repo/app:cache,mode=max
🔑 With mode=min, a multi-stage build's cache contains everything except the parts that are slow. The compile, the dependency install, the asset bundle — all of them live in stages that never appear in the final image, so none of them is exported. Cache looks configured, CI is still slow, and the cause is one word in a flag.

Order stages by stability too, not just instructions within a stage: a stage that changes rarely (dependency install) should not depend on one that changes constantly (source copy).

❌ Shipping the build toolchain, and removing it afterwards to "slim down". The Dockerfile installs a compiler, headers, and dev dependencies in the final image, then adds RUN apt-get remove build-essential && rm -rf /var/lib/apt/lists/* to shrink it — and the image gets bigger, because the removal adds a whiteout layer while the original bytes stay in the earlier layer. The same pattern is used for a private registry token: written to .npmrc, used, then deleted — and still fully extractable from the published image with docker save. Every deploy then ships a 1.5 GB image containing a compiler and a live credential.

✅ Put build-time material in a stage you do not copy from. Compile or install in a builder stage, then start a fresh FROM and copy only the artefact — the discarded stage is not in the final image's layer chain at all, so there is nothing to extract and nothing to remove. Choose the final base by what the binary actually needs: scratch or distroless-static for a statically linked binary (remembering CA certificates and a numeric USER), distroless-base or slim for glibc. For credentials, prefer RUN --mount=type=secret and --mount=type=ssh so they never touch a filesystem layer even in the discarded stage. And in CI, export cache with mode=max, or the expensive build stages are exactly what the cache omits.

Interview Questions

Beginner: What is a multi-stage build and why does it reduce image size?

Multiple FROM instructions in one Dockerfile. Each starts a stage with its own filesystem, and only the last stage becomes the image unless you copy from an earlier one explicitly.

FROM golang:1.22 AS build      # ~900MB with the toolchain
RUN go build -o /app ./cmd

FROM alpine:3.19               # fresh filesystem
COPY --from=build /app /app    # copy ONLY the binary
# → ~15MB final image

Why it works is the important part. The build stage's layers are never part of the final image's layer chain — not present, not hidden, not recoverable. That is different from deleting files, where a RUN rm adds a whiteout in a new layer while the original bytes remain in the earlier one, so the image actually grows and the file is still extractable.

ApproachBytes removed?
RUN rm later❌ No — image grows
Cleanup in the same RUN✅ Yes
Discarded stage✅ Yes

The same property makes it the right tool for build secrets — a credential used in a stage nobody copies from is not in the published image.

Typical reductions are 5–15× for compiled languages and 3–5× for interpreted ones, because the compiler, headers, and dev dependencies all stay behind.

Beginner: What does --target do?

It builds only up to a named stage, so one Dockerfile can produce several images.

FROM node:20-alpine AS base
FROM base AS deps-dev
RUN npm ci
FROM deps-dev AS test
RUN npm test
FROM base AS production
COPY --from=deps-prod /app/node_modules ./node_modules

$ docker build --target test -t app:test .
$ docker build --target production -t app:prod .

BuildKit builds only what the target depends on. Building --target production never runs the test stage and never builds deps-dev, because nothing in the dependency graph reaches them — so unused stages cost nothing.

Common uses: a test stage that fails the build when tests fail; a debug variant with a shell and tooling on top of a distroless production image; a dev image with hot-reload dependencies; and a lint stage in CI.

Without an explicit --target, the last stage is built — so put production last, and a developer running plain docker build gets the right thing by default.

Mid: How do multi-stage builds handle build-time secrets?

A stage that is never copied from is never published, so a credential used there does not reach the final image:

FROM node:20 AS build
ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc && npm ci

FROM node:20-alpine
COPY --from=build /app/dist ./dist    # only the artefact ships

This is genuinely better than the RUN rm pattern, where the secret stays extractable in an earlier layer of the published image.

But it is not airtight, and the caveats are what a senior answer should include: the build stage's layers exist in the local build cache; if cache is exported with mode=max to a shared registry, the token goes with it; and anyone building --target build gets an image containing it.

BuildKit secrets remove the question entirely:

# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
$ docker build --secret id=npmrc,src=$HOME/.npmrc -t app .

The value is mounted for that command only and never written to any layer — verifiable by extracting the image and finding nothing.

For private Git dependencies, --mount=type=ssh forwards the agent so no key is ever copied. And if a token was ever committed to a published layer, rotate it — rebuilding does not retract what has been pulled.

Mid: When would you use scratch versus distroless versus alpine?
BaseSizeTrade
scratch0 BAbsolutely nothing — you supply everything
distroless/static~2 MBCA certs, tzdata, nonroot user included
distroless/base~20 MBglibc for dynamically linked binaries
alpine~7 MBmusl + a shell; apk available
debian-slim~75 MBglibc, apt, familiar

My default for a static binary is distroless/static, not scratch. It costs 2 MB and supplies the two things scratch always lacks: CA certificates (without which every HTTPS call fails at run time with x509: certificate signed by unknown authority) and a nonroot user, since scratch has no /etc/passwd for a named USER to resolve.

Alpine when you need a shell — for debugging, an entrypoint script, or software that shells out. The caveat is musl rather than glibc: some binaries fail subtly, and Python workloads historically suffered because manylinux wheels do not apply, forcing slow source builds.

Debian-slim when glibc is required or the software's packaging assumes apt. It is bigger and often the pragmatic answer.

The failure that catches people is forgetting CGO_ENABLED=0 for a Go binary destined for scratch: it builds fine and then fails at startup with no such file or directory, which refers to the missing dynamic loader rather than the binary.

Senior: Design a Dockerfile producing production, test and debug images.

One file, several targets, sharing every expensive layer.

# syntax=docker/dockerfile:1
FROM golang:1.22 AS base
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download

FROM base AS build
COPY . .
RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -ldflags="-w -s" -o /app ./cmd/server

FROM base AS test
COPY . .
RUN --mount=type=cache,target=/root/.cache/go-build \
    go test ./... -race -coverprofile=/cover.out

FROM base AS lint
COPY . .
RUN golangci-lint run ./...

FROM gcr.io/distroless/static-debian12:nonroot AS production
COPY --from=build /app /app
ENTRYPOINT ["/app"]

FROM alpine:3.19 AS debug          ← same binary, plus tools
RUN apk add --no-cache curl bind-tools strace
COPY --from=build /app /app
ENTRYPOINT ["/app"]

Why this shape: base holds the dependency download so build, test and lint all reuse it; those three are independent, so BuildKit runs them in parallel; and production is last, so a plain docker build yields the right image.

The debug image matters operationally. A distroless production image cannot be docker execed into, so having a byte-identical binary in an image with a shell — built from the same build stage, so it is provably the same artefact — is what makes incident debugging possible without shipping tools to production.

In CI: run --target lint and --target test in parallel jobs, then build --target production and push by digest, with --cache-to mode=max so the shared base and build stages are actually exported.

The trade to acknowledge: one Dockerfile with six stages is more complex than one with two, and a developer reading it must understand the graph. I would accept that for the guarantee that test, debug, and production all derive from identical dependency and build stages.

Senior: A Go service image is 1.2 GB. Take it to under 20 MB.

1.2 GB means the Go toolchain is in the final image, which is a single-stage build. Confirm with layer attribution:

$ docker history --format '{{.Size}}\t{{.CreatedBy}}' app:v1 | sort -rh | head -3
812MB   /bin/sh -c #(nop) ADD file:... in /     ← the golang base
267MB   RUN go build ...                        ← build cache in the layer
 14MB   COPY . .

The rewrite:

# syntax=docker/dockerfile:1
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /app ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /app /app
ENTRYPOINT ["/app"]

What each change contributes:

ChangeEffect
Multi-stageRemoves the 812 MB toolchain — the dominant win
CGO_ENABLED=0Static binary; enables a distroless/scratch final stage
-ldflags="-w -s"Strips debug info and symbol table, ~25% off the binary
distroless/static2 MB base, with CA certs and a nonroot user
Cache mountsBuild speed; module and build caches never enter a layer

Expect roughly 12–18 MB, essentially the binary plus 2 MB of base.

What I would verify rather than assume: that HTTPS calls work (the CA-certificate trap), that the binary is genuinely static (file reports "statically linked"), and that the process runs as nonroot. And I would add a size budget check in CI, because image size regresses quietly — the next person adding a debugging tool to the final stage will not notice they undid this.

If the service needs cgo — a C dependency, or certain DNS behaviour — then CGO_ENABLED=0 is not available, and the answer is distroless/base at ~20 MB rather than scratch.

3 (medium): Prove a discarded stage leaves no trace, unlike RUN rm.
Solution 
$ mkdir -p /tmp/stagesecret && cd /tmp/stagesecret
$ echo "NPM_TOKEN=npm_live_SECRET123" > .npmrc

# ❌ single stage with rm
$ cat > D.rm <<'EOF'
FROM alpine:3.19
COPY .npmrc /root/.npmrc
RUN cat /root/.npmrc > /dev/null
RUN rm -f /root/.npmrc
EOF
$ docker build -q -t s:rm -f D.rm . >/dev/null

# ✅ multi-stage, credential confined to the discarded stage
$ cat > D.stage <<'EOF'
FROM alpine:3.19 AS build
COPY .npmrc /root/.npmrc
RUN cat /root/.npmrc > /dev/null && echo "artifact" > /out.txt

FROM alpine:3.19
COPY --from=build /out.txt /out.txt
EOF
$ docker build -q -t s:stage -f D.stage . >/dev/null

Neither shows the file in a running container:

$ docker run --rm s:rm    ls /root/.npmrc 2>&1 | tail -1
ls: /root/.npmrc: No such file or directory
$ docker run --rm s:stage ls /root/.npmrc 2>&1 | tail -1
ls: /root/.npmrc: No such file or directory

Now extract both images and search the layers:

$ for img in s:rm s:stage; do
    rm -rf x && mkdir x
    docker save $img -o i.tar && tar -xf i.tar -C x
    HITS=$(grep -rl 'npm_live_SECRET123' x/ 2>/dev/null | wc -l)
    echo "$img: $HITS layer(s) contain the secret"
  done
s:rm:    1 layer(s) contain the secret       ← RECOVERABLE
s:stage: 0 layer(s) contain the secret       ← genuinely gone

Recover it from the single-stage image to make the point concrete:

$ rm -rf x && mkdir x && docker save s:rm -o i.tar && tar -xf i.tar -C x
$ for l in x/blobs/sha256/*; do
    tar -tf "$l" 2>/dev/null | grep -q 'root/.npmrc' && tar -xOf "$l" root/.npmrc
  done
NPM_TOKEN=npm_live_SECRET123

And the sizes:

$ docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}' | grep '^s:'
s:rm      7.39MB           ← the rm added a layer
s:stage   7.38MB

The best option removes the question entirely — a build secret never touches any filesystem:

$ cat > D.secret <<'EOF'
# syntax=docker/dockerfile:1
FROM alpine:3.19 AS build
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    cat /root/.npmrc > /dev/null && echo "artifact" > /out.txt
FROM alpine:3.19
COPY --from=build /out.txt /out.txt
EOF
$ docker build -q --secret id=npmrc,src=.npmrc -t s:secret -f D.secret . >/dev/null
$ rm -rf x && mkdir x && docker save s:secret -o i.tar && tar -xf i.tar -C x
$ grep -rl 'npm_live_SECRET123' x/ 2>/dev/null | wc -l
0

Note the remaining caveat for the multi-stage approach: the build stage still exists in the local build cache, so docker build --target build would produce an image containing the token. Only the secret mount avoids that.

4 (medium): Show that independent stages build in parallel.
Solution 
$ mkdir -p /tmp/parallel && cd /tmp/parallel

# SERIAL: one stage, chained work
$ cat > D.serial <<'EOF'
FROM alpine:3.19
RUN echo "task A" && sleep 8
RUN echo "task B" && sleep 8
RUN echo "task C" && sleep 8
EOF

# PARALLEL: three independent stages, joined at the end
$ cat > D.parallel <<'EOF'
FROM alpine:3.19 AS a
RUN echo "task A" && sleep 8 && echo A > /out

FROM alpine:3.19 AS b
RUN echo "task B" && sleep 8 && echo B > /out

FROM alpine:3.19 AS c
RUN echo "task C" && sleep 8 && echo C > /out

FROM alpine:3.19
COPY --from=a /out /a
COPY --from=b /out /b
COPY --from=c /out /c
EOF

$ docker builder prune -af >/dev/null 2>&1
$ time docker build -q -t p:serial -f D.serial . >/dev/null
real    0m24.6s          ← 3 x 8s, strictly serial

$ docker builder prune -af >/dev/null 2>&1
$ time docker build -q -t p:parallel -f D.parallel . >/dev/null
real    0m8.9s           ← 2.8x faster: the three stages ran concurrently

Watch them interleave in the progress output:

$ docker builder prune -af >/dev/null 2>&1
$ docker build --progress=plain -t p:parallel -f D.parallel . 2>&1 | \
    grep -E '^#[0-9]+ [0-9]+\.[0-9]+ task'
#7 0.201 task A
#8 0.198 task B          ← all three started within milliseconds
#9 0.205 task C

A dependency forces ordering:

$ cat > D.chained <<'EOF'
FROM alpine:3.19 AS a
RUN echo "task A" && sleep 8 && echo A > /out

FROM alpine:3.19 AS b
COPY --from=a /out /prev        ← b now DEPENDS on a
RUN echo "task B" && sleep 8 && echo B > /out

FROM alpine:3.19
COPY --from=b /out /b
EOF

$ time docker build -q -t p:chained -f D.chained . >/dev/null

The practical application is a polyglot build — frontend assets and a backend binary are independent, so putting them in separate stages roughly halves the wall-clock time compared with doing both in one stage.

🎯 Key Takeaways

  • Only the last stage becomes the image — earlier stages are not in the layer chain at all, so their contents are unrecoverable rather than merely hidden.
  • Measured: a Go service went 1.19 GB single-stage → 14.2 MB multi-stage (84×).
  • Deleting the toolchain instead made the image larger (1.19 GB → 1.21 GB) — whiteouts add layers without removing bytes.
  • A discarded stage is the correct answer to build secrets: layer extraction found the credential in 1 layer of the RUN rm image and 0 in the multi-stage one.
  • The remaining caveat: build-stage layers exist in the local cache and travel with mode=max cache export or --target build — RUN --mount=type=secret avoids that entirely.
  • --target builds one named stage, and BuildKit does not build stages the target does not depend on — verified with zero output from unused stages.
  • A failing test in a test stage fails the build with exit 1, but production still builds — so the gate must be an explicit CI step.
  • Independent stages run in parallel: three 8-second tasks took 24.6 s chained in one stage versus 8.9 s as separate stages (2.8×).
  • A COPY --from dependency reimposes ordering — the graph decides, not the file order.
  • Name stages with AS; --from=0 by index breaks when stages are reordered.
  • scratch needs CA certificates or every HTTPS call fails with x509: certificate signed by unknown authority.
  • It also has no /etc/passwd, so USER must be numeric — distroless-static supplies both for ~2 MB.
  • Forgetting CGO_ENABLED=0 produces exec /app: no such file or directory — the missing dynamic loader, not a missing binary.
  • -ldflags="-w -s" strips debug info and symbols for roughly 25% off a Go binary.
  • Multi-stage requires mode=max in CI — mode=min exports only final-image layers, omitting exactly the expensive build stages.
  • Keep a debug image built from the same build stage, so a distroless production image can be investigated with a provably identical binary.
  • Full polyglot conversion measured: 1.68 GB → 12.4 MB (135×), clean build 3.5× faster, and a frontend-only rebuild 31× faster.
  • Copy specific artefacts (/app, /dist) rather than whole directories, or build output leaks back into the final image.
