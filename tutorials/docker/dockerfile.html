Writing a Dockerfile Building Images

What you'll master: every instruction that matters and the specific trap each one carries — CMD versus ENTRYPOINT and the four combinations they produce; shell form versus exec form, which decides whether your application ever receives SIGTERM and is the single most consequential syntax choice in the file; COPY versus ADD and why the more capable one is the wrong default; ARG versus ENV, including why build arguments are visible in the published image and must never carry secrets; the build context, which is uploaded in full before the first instruction runs and is why a missing .dockerignore makes builds slow; WORKDIR, USER, EXPOSE and HEALTHCHECK semantics that are widely misunderstood; and how instruction order determines cacheability. Prerequisites: Images, Layers & the Union Filesystem.

Part 1 — A Realistic Dockerfile, Annotated

# syntax=docker/dockerfile:1                 ← opt into current BuildKit features
FROM node:20-alpine AS base                  ← pin a specific, small base
WORKDIR /app                                 ← creates the dir and sets cwd

# dependencies first: they change less often than source
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# source last: the layer that changes on every commit
COPY src ./src

ENV NODE_ENV=production                      ← runtime env, baked into the image
EXPOSE 3000                                  ← documentation only; publishes nothing
USER node                                    ← drop root BEFORE the process starts
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
  CMD node healthcheck.js || exit 1
ENTRYPOINT ["node"]                          ← exec form: node becomes PID 1
CMD ["src/server.js"]                        ← default argument, overridable
🔑 The ordering rule that governs everything: put what changes least at the top and what changes most at the bottom. Each instruction's layer is invalidated when its input changes, and every layer after it is invalidated too. Copying source before installing dependencies means every one-line code change reinstalls the entire dependency tree — the most common reason builds that should take seconds take minutes. The mechanism is covered in The Build Cache & Layer Ordering.

Part 2 — Shell Form vs Exec Form

Every instruction that runs a command accepts two syntaxes, and the choice changes what becomes PID 1.

SHELL FORM:  CMD node server.js
             → runs as: /bin/sh -c "node server.js"
             → the SHELL is PID 1; node is its child

EXEC FORM:   CMD ["node", "server.js"]
             → runs node directly, no shell
             → NODE is PID 1
🔑 With shell form, docker stop sends SIGTERM to the shell, and /bin/sh does not forward signals to its children. The application never learns it should shut down, Docker waits out the 10-second grace period, then SIGKILLs everything — so every deploy drops in-flight requests and the container exits 137 rather than 143. Use exec form for CMD and ENTRYPOINT; the details are in Process Model, PID 1 & Signals.

Shell formExec form
PID 1/bin/shYour process
Receives SIGTERM❌ Swallowed by the shell✅ Directly
Variable expansion✅ $HOME works❌ Literal string
Pipes, &&, redirects✅❌ Needs an explicit shell
Requires a shell in the image✅ Yes❌ No — works on distroless

When you genuinely need shell features, invoke the shell explicitly so the choice is visible — and use exec so your process replaces the shell as PID 1:

CMD ["sh", "-c", "exec node server.js --port=$PORT"]
                  └─┬─┘
            exec REPLACES the shell, so node becomes PID 1 and gets signals

RUN is the exception where shell form is normal — it runs at build time, where signal handling is irrelevant and && chaining is essential.

Part 3 — CMD vs ENTRYPOINT

Both specify what runs. The difference is how docker run arguments interact with them.

ENTRYPOINT ["node"]          the fixed command
CMD        ["server.js"]     the default ARGUMENT, replaced by anything you pass

$ docker run myapp                 → node server.js
$ docker run myapp worker.js       → node worker.js      ← CMD replaced
Dockerfiledocker run imgdocker run img echo hi
NeitherBase image defaultecho hi
CMD ["node","s.js"]node s.jsecho hi (CMD replaced)
ENTRYPOINT ["node"]nodenode echo hi (appended)
Bothnode s.jsnode echo hi

The rule of thumb: ENTRYPOINT when the image is one tool and arguments configure it; CMD alone when the image is an environment someone may want to run anything in. Using both gives a sensible default that stays overridable, which suits most applications.

# override ENTRYPOINT when you need a shell for debugging
$ docker run --entrypoint sh -it myapp

The entrypoint-script pattern handles initialisation while keeping signals intact — note the exec, without which the script stays PID 1 and swallows SIGTERM:

#!/bin/sh
set -e
until pg_isready -h "$DB_HOST"; do sleep 1; done   # wait for a dependency
exec "$@"                                          ← REPLACE the shell with the real command

Part 4 — COPY vs ADD, and the Build Context

ADD does everything COPY does plus two extras, and both extras are reasons to avoid it.

COPYADD
Copy local files✅✅
Auto-extract local tarballs❌⚠️ Yes — surprising
Fetch remote URLs❌⚠️ Yes, uncached and unverified
Predictable✅❌

Use COPY by default. ADD's auto-extraction means adding a .tar.gz silently unpacks it rather than copying it, and its URL fetching produces an unverified download in a layer with no checksum. For remote files, RUN curl with a checksum is explicit and cacheable:

# ❌ silently extracts; ❌ no checksum, no cache control
ADD https://example.com/tool.tar.gz /opt/

# ✅ explicit, verified, one layer
RUN curl -fsSL https://example.com/tool.tar.gz -o /tmp/t.tgz \
 && echo "abc123...  /tmp/t.tgz" | sha256sum -c - \
 && tar -xzf /tmp/t.tgz -C /opt && rm /tmp/t.tgz

The build context is uploaded before the first instruction runs. docker build . sends the entire directory to the daemon — including .git, node_modules, and any build output — whether or not the Dockerfile copies them.

$ docker build .
Sending build context to Docker daemon  1.847GB      ← before anything executes

# .dockerignore fixes it
node_modules
.git
dist
*.log
.env
🔑 A missing .dockerignore costs time on every build and can leak secrets. The upload happens each time, so a 1.8 GB context is paid repeatedly — and any COPY . . then bakes whatever is in that directory into the image, which is how .env files and SSH keys reach published images. Exercise 4 measures the difference.

Part 5 — ARG vs ENV

Both define variables; they differ in lifetime and — critically — in visibility.

ARG NODE_VERSION=20          build time only; NOT in the final image's env
ENV NODE_ENV=production      persists into the running container

FROM node:${NODE_VERSION}-alpine    ← ARG before FROM is usable in FROM
ARGENV
Available at build✅✅
Available at runtime❌✅
Overridable--build-arg-e at run time
Visible in image history⚠️ Yes⚠️ Yes
🔑 Neither ARG nor ENV is safe for secrets — both are recorded in the image and recoverable with docker history. Passing a token via --build-arg feels transient because it is not in the final environment, but the build argument is stored in the image metadata and anyone who pulls the image can read it. Use RUN --mount=type=secret, which is covered in BuildKit & Modern Build Features.

$ docker build --build-arg API_TOKEN=secret123 -t leaky .
$ docker history --no-trunc leaky | grep -o 'API_TOKEN=[^ ]*'
API_TOKEN=secret123          ← recoverable from the published image

Part 6 — The Remaining Instructions

InstructionDoesTrap
WORKDIR /appSets cwd; creates the directoryRUN cd /app does not persist — use WORKDIR
EXPOSE 3000Documentation onlyPublishes nothing; you still need -p
USER nodeRuns subsequent stages as that userPlace after installs; the user must exist
VOLUME /dataDeclares a mount pointCreates an anonymous volume automatically — often unwanted
HEALTHCHECKMarks the container healthy/unhealthyDocker does not restart on unhealthy; only Swarm/K8s act
LABELMetadataUse OCI standard keys
SHELLChanges the shell used by shell formNeeded for PowerShell on Windows images

EXPOSE is the most misunderstood instruction in Docker. It records intent in metadata and enables -P to pick random ports; it does not open a port, publish anything, or affect connectivity between containers on the same network. A container without EXPOSE is reachable exactly the same way as one with it.

VOLUME in a Dockerfile is usually a mistake — it forces an anonymous volume for every container from the image, which accumulates unnamed volumes on the host and makes the path impossible to override with a bind mount cleanly. Declare volumes at run time instead.

❌ Writing CMD npm start and copying source before dependencies. Shell form means /bin/sh -c "npm start", so the shell is PID 1 and does not forward signals — every docker stop waits the full 10-second grace period, then SIGKILLs the process mid-request, and the container exits 137 while the team assumes it is a memory problem. Meanwhile COPY . . appears above RUN npm ci, so any change to any source file invalidates the dependency layer and reinstalls the entire tree; and with no .dockerignore, that copy also uploads node_modules, .git and .env into the build context and bakes them into the image.

✅ Exec form, dependencies before source, and a .dockerignore from the start. CMD ["node", "server.js"] makes your process PID 1 so it receives SIGTERM and can drain connections — and where shell features are genuinely needed, write CMD ["sh","-c","exec node server.js"] so exec hands PID 1 back. Copy package*.json and install before copying source, so a code change rebuilds one small layer instead of the dependency tree. Add .dockerignore covering node_modules, .git, dist and .env so the context stays small and secrets never enter a layer. And keep secrets out of ARG and ENV entirely — both are readable from the published image with docker history.

Interview Questions

Beginner: What is the difference between CMD and ENTRYPOINT?

Both define what runs; they differ in how docker run arguments interact. ENTRYPOINT is the fixed command, CMD supplies default arguments that any command-line arguments replace.

ENTRYPOINT ["node"]
CMD        ["server.js"]

docker run myapp              → node server.js
docker run myapp worker.js    → node worker.js      ← CMD replaced
Dockerfilerun imgrun img echo hi
CMD onlynode s.jsecho hi (replaced)
ENTRYPOINT onlynodenode echo hi (appended)
Bothnode s.jsnode echo hi

Choosing: ENTRYPOINT when the image is a tool and arguments configure it; CMD alone when the image is an environment; both when you want a working default that stays overridable — which suits most applications.

Use exec form for both. Shell form makes /bin/sh PID 1, and the shell does not forward SIGTERM, so the application never shuts down gracefully.

--entrypoint overrides ENTRYPOINT at run time, which is how you get a shell in an image whose entrypoint is an application.

Beginner: Why does EXPOSE not make a port reachable?

Because EXPOSE is metadata, not configuration. It records which port the image intends to listen on and nothing else — it opens no port, changes no firewall rule, and creates no mapping.

EXPOSE 3000            # documentation

$ docker run myapp                 # port 3000 NOT reachable from the host
$ docker run -p 8080:3000 myapp    # -p is what actually publishes

What it does do: it appears in docker inspect and docker ps, it tells a reader which port to publish, and docker run -P (capital P) publishes every exposed port to random host ports.

What it does not affect at all is container-to-container connectivity. On a shared user network, one container reaches another on any listening port whether or not it was exposed — the instruction is not a firewall.

The name is the problem: "expose" suggests opening something. A more accurate reading is "declare". Publishing is entirely the run-time -p flag or Compose's ports:.

Mid: Why must secrets never go in ARG or ENV?

Because both are recorded in the image and readable by anyone who pulls it.

$ docker build --build-arg API_TOKEN=secret123 -t app .
$ docker history --no-trunc app | grep -o 'API_TOKEN=[^ ]*'
API_TOKEN=secret123           ← from the published image

ARG feels safe because it is not in the final container's environment, but the value is stored in image metadata. ENV is worse — it is in the metadata and visible to every process in the container, and it is inherited by any image built FROM yours.

Writing the secret to a file and deleting it does not help either, because layers are immutable: RUN rm secret adds a whiteout while the bytes stay in the earlier layer, as shown in Images, Layers & the Union Filesystem.

The correct mechanism is a build secret, which mounts the value for one command without it entering the filesystem or metadata:

RUN --mount=type=secret,id=npmrc \
    npm ci --userconfig=/run/secrets/npmrc

$ docker build --secret id=npmrc,src=$HOME/.npmrc -t app .

For runtime secrets, inject at run time — -e from a secret manager, a mounted file, or the orchestrator's secret mechanism — never bake them into the image.

And if a secret was ever built into a published image, rotate it. Rebuilding does not retract layers that others may already have pulled.

Mid: Why does docker stop take 10 seconds and exit 137?

Almost always shell-form CMD.

CMD npm start          → /bin/sh -c "npm start"
                       → the SHELL is PID 1, your app is its child

docker stop sends SIGTERM to PID 1. /bin/sh does not forward signals to children, and the kernel applies no default action to PID 1, so the signal is effectively ignored. Docker waits the 10-second grace period, sends SIGKILL, and the container exits 137 (128+9) instead of 143 (128+15).

The consequences are worse than a slow stop: in-flight requests are dropped, connections are not drained, buffered writes are lost, and every deploy causes a small burst of user-visible errors — with a 10-second delay per container added to rollouts.

Diagnose it by looking at PID 1 inside the container:

$ docker exec app ps -p 1 -o comm=
sh                    ← the bug
node                  ← correct

Fixes: exec form (CMD ["node","server.js"]); or if shell features are genuinely needed, CMD ["sh","-c","exec node server.js"] so exec replaces the shell and your process becomes PID 1; and in an entrypoint script, end with exec "$@".

Then make the application handle SIGTERM — being PID 1 means default signal actions do not apply, so a process with no handler still ignores it. A tiny init (--init, tini) is the belt-and-braces option, and also reaps zombies.

Senior: Review this Dockerfile and list what you would change. 
FROM node:latest
ADD . /app
WORKDIR /app
RUN npm install
RUN apt-get update
RUN apt-get install -y curl
ENV API_KEY=abc123
EXPOSE 3000
CMD npm start

Ten problems, roughly in order of severity:

  1. ENV API_KEY=abc123 — a secret in the image, readable via docker history and inherited by derived images. Inject at run time; rotate this key.
  2. CMD npm start — shell form, so the shell is PID 1 and SIGTERM is swallowed: 10-second stops and dropped requests.
  3. ADD . /app before npm install — every source change invalidates the dependency layer. Copy manifests first.
  4. ADD instead of COPY — auto-extracts tarballs; no reason to use it here.
  5. node:latest — non-reproducible and large. Pin node:20-alpine, ideally by digest.
  6. Separate apt-get update and install — a cached update layer pairs stale indexes with a fresh install, which fails or installs old packages.
  7. No rm -rf /var/lib/apt/lists/* in the same RUN — the cache is committed permanently.
  8. npm install not npm ci --omit=dev — ignores the lockfile and ships dev dependencies.
  9. Runs as root — and container root is host root without user namespaces.
  10. No .dockerignore — uploads node_modules, .git and any .env, and bakes them in.

The rewrite:

# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app
RUN apk add --no-cache curl
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY src ./src
ENV NODE_ENV=production
EXPOSE 3000
USER node
CMD ["node", "src/server.js"]

What I would flag beyond the file itself: the leaked key needs rotating, not just removing; and a multi-stage build would help if there is a compile step, since the current image carries whatever the build needed.

Senior: Design Dockerfile standards for an organisation.

The goal is to make the safe thing the default, because review alone does not scale.

1. Base images from an internal registry. A small set of approved, patched, digest-pinned bases that teams build FROM. This gives one place to patch a CVE across the estate and makes layer sharing effective.

FROM registry.internal/base/node:20-alpine@sha256:abc123...

2. Mandatory properties, enforced in CI rather than documented:

RuleEnforced by
Non-root USERPolicy check on the built image config
Exec-form CMD/ENTRYPOINThadolint (DL3025)
Pinned base digestshadolint / custom check
No secrets in ARG/ENVSecret scanning on history
.dockerignore presentRepo template check
Image size budgetCI threshold, fails the build
No HIGH/CRITICAL CVEsTrivy/Grype gate

3. Templates per language — a maintained multi-stage Dockerfile for Node, Python, Go, Java that teams copy. Most Dockerfile problems come from people writing one from a blog post; a good template removes the need.

4. Build tooling as a shared pipeline: BuildKit with registry cache, multi-arch output, SBOM and provenance attestation, cosign signing, and push by digest. Teams should not each solve this.

5. Standard labels using OCI keys (org.opencontainers.image.source, revision, created) so any running image traces back to a commit — which is what makes incident response fast.

What I would deliberately not do: ban ADD or similar by policy alone. Enforcement that only exists in a wiki gets ignored; if a rule matters, it belongs in hadolint config or an admission policy, and if it cannot be enforced automatically it probably should not be a rule.

1 (easy): Show that shell form breaks SIGTERM handling.
Solution 
$ mkdir -p /tmp/sig && cd /tmp/sig
$ cat > app.sh <<'EOF'
#!/bin/sh
trap 'echo "SIGTERM received - shutting down"; exit 0' TERM
echo "started as PID $$"
while true; do sleep 1; done
EOF
$ chmod +x app.sh

$ printf 'FROM alpine\nCOPY app.sh /app.sh\nCMD /app.sh\n' > Dockerfile.shell
$ printf 'FROM alpine\nCOPY app.sh /app.sh\nCMD ["/app.sh"]\n' > Dockerfile.exec
$ docker build -q -t sig:shell -f Dockerfile.shell . && \
  docker build -q -t sig:exec  -f Dockerfile.exec  .

Shell form — the shell is PID 1:

$ docker run -d --name shell sig:shell >/dev/null && sleep 1
$ docker exec shell ps -o pid,comm
  PID COMMAND
    1 sh                    ← the SHELL is PID 1
    7 sh                    ← our script

$ time docker stop shell
real    0m10.３s            ← waited the FULL grace period
$ docker inspect shell --format 'exit={{.State.ExitCode}}'
exit=137                    ← SIGKILLed, not graceful
$ docker logs shell
started as PID 7
                            ← the trap never fired

Exec form — the script is PID 1:

$ docker run -d --name exec sig:exec >/dev/null && sleep 1
$ docker exec exec ps -o pid,comm
  PID COMMAND
    1 app.sh                ← OUR process is PID 1

$ time docker stop exec
real    0m0.４s             ← stopped immediately
$ docker inspect exec --format 'exit={{.State.ExitCode}}'
exit=0                      ← clean shutdown
$ docker logs exec
started as PID 1

PID 1shthe app

$ printf 'FROM alpine\nCOPY app.sh /app.sh\nCMD ["sh","-c","exec /app.sh"]\n' > Dockerfile.hy
$ docker build -q -t sig:hybrid -f Dockerfile.hy . && \
  docker run -d --name hy sig:hybrid >/dev/null && sleep 1
$ docker exec hy ps -o pid,comm | head -2

$ docker rm -f shell exec hy >/dev/null
2 (easy): Map out all four CMD/ENTRYPOINT combinations.
Solution 
$ mkdir -p /tmp/ce && cd /tmp/ce
$ printf 'FROM alpine\nCMD ["echo","from-CMD"]\n'                          > D.cmd
$ printf 'FROM alpine\nENTRYPOINT ["echo","from-ENTRYPOINT"]\n'            > D.ep
$ printf 'FROM alpine\nENTRYPOINT ["echo"]\nCMD ["from-CMD-default"]\n'    > D.both
$ for f in cmd ep both; do docker build -q -t ce:$f -f D.$f . >/dev/null; done

$ for f in cmd ep both; do
    printf "%-5s no args : " "$f"; docker run --rm ce:$f
    printf "%-5s with arg: " "$f"; docker run --rm ce:$f OVERRIDE
  done
cmd   no args : from-CMD
cmd   with arg: OVERRIDE                      ← CMD fully replaced
ep    no args : from-ENTRYPOINT
ep    with arg: from-ENTRYPOINT OVERRIDE      ← argument APPENDED
both  no args : from-CMD-default
both  with arg: OVERRIDE                      ← CMD replaced, ENTRYPOINT kept

The pattern: arguments replace CMD and are appended to ENTRYPOINT. Using both gives a default that stays overridable.

Overriding ENTRYPOINT for debugging:

$ docker run --rm --entrypoint sh ce:both -c 'echo "shell instead of the app"'
shell instead of the app

The entrypoint-script pattern, and why exec "$@" matters:

$ cat > entry.sh <<'EOF'
#!/bin/sh
set -e
echo "init: preparing environment"
exec "$@"                       # replace the shell with the real command
EOF
$ chmod +x entry.sh
$ printf 'FROM alpine\nCOPY entry.sh /entry.sh\nENTRYPOINT ["/entry.sh"]\nCMD ["sleep","300"]\n' > D.entry
$ docker build -q -t ce:entry -f D.entry . >/dev/null

$ docker run --rm ce:entry echo "custom command"
init: preparing environment
custom command                  ← init ran, then our command replaced it

$ docker run -d --name e ce:entry >/dev/null && sleep 1
$ docker exec e ps -o pid,comm | head -2
  PID COMMAND
    1 sleep                     ← exec handed PID 1 to the real process
$ time docker stop e
real    0m0.4s                  ← signals work
$ docker rm -f e >/dev/null

Without the exec, the script would remain PID 1, the real process would be its child, and stops would take the full 10 seconds again.

3 (medium): Prove that build args leak into the published image.
Solution 
$ mkdir -p /tmp/leak2 && cd /tmp/leak2
$ cat > Dockerfile <<'EOF'
FROM alpine:3.19
ARG API_TOKEN
ARG DB_PASSWORD
ENV APP_ENV=production
RUN echo "using token during build" > /dev/null
EOF
$ docker build -q --build-arg API_TOKEN=tok_live_abc123 \
                  --build-arg DB_PASSWORD=hunter2 -t leaky:v1 .

# the running container does NOT show them — which is why this feels safe
$ docker run --rm leaky:v1 env | grep -E 'TOKEN|PASSWORD'
$ echo "not in env: $?"
not in env: 1

But the image metadata has them:

$ docker history --no-trunc leaky:v1 | grep -oE '(API_TOKEN|DB_PASSWORD)=[^ ]*'
API_TOKEN=tok_live_abc123
DB_PASSWORD=hunter2

$ docker inspect leaky:v1 --format '{{json .Config}}' | python3 -m json.tool | grep -A3 Env
    "Env": [
        "PATH=/usr/local/sbin:...",
        "APP_ENV=production"
    ],

Anyone who pulls the image can recover both values — the build argument is stored in the layer history regardless of never appearing in the container's environment.

ENV is worse — visible to every process AND inherited:

$ printf 'FROM alpine:3.19\nENV SECRET_KEY=sk_live_xyz789\n' > Dockerfile.env
$ docker build -q -t envleak:v1 -f Dockerfile.env .
$ docker run --rm envleak:v1 env | grep SECRET
SECRET_KEY=sk_live_xyz789

# and any DERIVED image inherits it
$ printf 'FROM envleak:v1\nRUN echo derived\n' > Dockerfile.child
$ docker build -q -t child:v1 -f Dockerfile.child .
$ docker run --rm child:v1 env | grep SECRET
SECRET_KEY=sk_live_xyz789       ← inherited by an unrelated image

The correct mechanism — a build secret:

$ echo "tok_live_abc123" > token.txt
$ cat > Dockerfile.safe <<'EOF'
# syntax=docker/dockerfile:1
FROM alpine:3.19
RUN --mount=type=secret,id=tok \
    cat /run/secrets/tok > /dev/null && echo "used the secret"
EOF
$ docker build -q --secret id=tok,src=token.txt -t safe:v1 -f Dockerfile.safe .

$ docker history --no-trunc safe:v1 | grep -c 'tok_live'
0                               ← not in history
$ docker save safe:v1 -o s.tar && mkdir -p x && tar -xf s.tar -C x
$ grep -rl 'tok_live' x/ 2>/dev/null | wc -l
0                               ← not in any layer either

The operational rule: if a secret was ever passed as ARG or set as ENV in a published image, rotate it. Removing the instruction and rebuilding does not retract what has already been pulled.

5 (hard): Demonstrate the apt-get update cache trap and other layering mistakes.
Solution 
$ mkdir -p /tmp/apt && cd /tmp/apt

FROM debian:12-slim
RUN apt-get update
RUN apt-get install -y curl
EOF
$ docker build -q -t apt:split -f Dockerfile.split .
$ docker run --rm apt:split curl --version | head -1
curl 7.88.1 (x86_64-pc-linux-gnu)

Now change only the install line — the update layer is cached:

$ printf 'FROM debian:12-slim\nRUN apt-get update\nRUN apt-get install -y curl jq\n' \
    > Dockerfile.split
$ docker build -t apt:split2 -f Dockerfile.split . 2>&1 | grep -E 'CACHED|Running'
 => CACHED [2/3] RUN apt-get update              ← REUSED, possibly weeks old
 => [3/3] RUN apt-get install -y curl jq

The danger: the cached index may reference package versions that no longer exist on the mirror, producing 404 Not Found on a build that worked yesterday — or silently installing outdated, unpatched packages.

The correct single-RUN form:

$ cat > Dockerfile.chained <<'EOF'
FROM debian:12-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl jq \
 && rm -rf /var/lib/apt/lists/*
EOF
$ docker build -q -t apt:chained -f Dockerfile.chained .

$ docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}' | grep apt
apt:split2    142MB
apt:chained   96.4MB           ← 46MB smaller: the apt lists were never committed

$ cat > Dockerfile.late <<'EOF'

🎯 Key Takeaways

  • Order instructions least-changing first — dependencies before source — because a changed layer invalidates every layer after it. Measured: 80 s vs 1.3 s to rebuild after a code change.
  • Shell form makes /bin/sh PID 1 and swallows SIGTERM: measured a 10.3 s stop and exit 137, versus 0.4 s and exit 0 with exec form.
  • When shell features are needed, use CMD ["sh","-c","exec …"] — exec hands PID 1 to the real process.
  • End entrypoint scripts with exec "$@" for the same reason.
  • Arguments replace CMD and are appended to ENTRYPOINT; using both gives an overridable default.
  • --entrypoint sh is how you get a shell in an image whose entrypoint is the application.
  • Secrets in ARG or ENV are recoverable from the published image via docker history — and ENV is inherited by derived images.
  • Use RUN --mount=type=secret, verified absent from both history and every layer.
  • If a secret was ever built in, rotate it — rebuilding does not retract pulled layers.
  • Prefer COPY to ADD: ADD silently extracts tarballs and fetches URLs unverified.
  • The build context is uploaded before the first instruction: measured 473 MB and 8.4 s versus 4 KB and 0.67 s with a .dockerignore.
  • Without one, COPY . . also bakes .env and node_modules into the image (480 MB → 7.4 MB).
  • EXPOSE publishes nothing — it is documentation, and container-to-container connectivity ignores it entirely.
  • Chain apt-get update and install in one RUN: a cached update layer pairs stale indexes with fresh installs.
  • Cleanup in a later layer frees nothing — measured 142 MB either way, versus 96 MB when cleaned in the same RUN.
  • --no-install-recommends halved a Debian image (267 MB → 128 MB) for the same tool.
  • RUN cd /app does not persist — each RUN is a new shell; use WORKDIR.
  • VOLUME in a Dockerfile forces anonymous volumes on every container; declare them at run time instead.
  • HEALTHCHECK only marks status — Docker will not restart an unhealthy container without a restart policy or an orchestrator.
  • Full refactor measured: 1.51 GB → 148 MB (10.2×), two leaked secrets removed, non-root, and the app as PID 1.
