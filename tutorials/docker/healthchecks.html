Health Checks & Startup Order Composing Systems

What you'll master: why depends_on orders starts and not readiness, measured as a real flake rate; the health state machine — starting → healthy | unhealthy — and exactly what interval, timeout, retries and start_period each control, including the one people always get backwards; the Postgres double-start trap, where a naive TCP check passes against a server that is about to be shut down; why Docker does nothing at all when a container becomes unhealthy and what actually acts on the signal; why the check runs inside the container and what that costs on a distroless image or a JVM; the difference between liveness, readiness and startup probes, and the cascading outage that follows from conflating them; and the ordering primitives — service_healthy, service_completed_successfully, up --wait — plus the reason application-level retry is still mandatory. Prerequisites: Docker Compose, Process Model, PID 1 & Signals.

Part 1 — depends_on Orders Starts, Not Readiness

The name promises more than it delivers. Plain depends_on means: create and start this container before that one. "Started" means the daemon has executed the entrypoint. It says nothing about whether the process inside has bound a socket, loaded a schema, or is willing to answer.

services:
  api:
    build: .
    depends_on: [db]           ← "start db first". That is ALL it means.
  db:
    image: postgres:16-alpine

timeline of what actually happens
  t=0.00  docker creates db, starts it            ← depends_on is satisfied HERE
  t=0.02  docker creates api, starts it
  t=0.15  api's entrypoint connects to db:5432    ← connection refused
  t=0.9   postgres entrypoint begins initdb
  t=3.4   postgres finishes init, binds 5432      ← 3.25 s after "started"

The gap is not theoretical. Run the same stack a hundred times and count:

$ for i in $(seq 1 100); do
    docker compose down -v >/dev/null 2>&1
    docker compose up -d >/dev/null 2>&1
    sleep 12
    docker compose ps api --format '{{.State}}'
  done | sort | uniq -c
     73 running
     27 exited                  ← 27% failure rate, entirely timing
ConditionWaits forRequires a healthcheck?Use for
service_started (default)Container created and startedNoAlmost nothing
service_healthyHealth state = healthyYesDatabases, queues, any dependency
service_completed_successfullyContainer exited with code 0NoMigrations, seeders, one-shot jobs
🔑 The flake is a distributed-systems bug wearing a Compose costume. A 27% failure rate that "goes away when I re-run it" is the same class of problem as a service that assumes its dependency is up. Ordering makes the common case work; it never makes the dependency reliable. Both fixes below are needed, and only one of them is a Compose feature.

Part 2 — The Health State Machine

A container with a healthcheck has a State.Health.Status field, and it moves through exactly three values:

                 start_period elapsed OR first success
   ┌──────────┐  ─────────────────────────────────────►  ┌─────────┐
   │ starting │                                          │ healthy │
   └──────────┘  ◄─────────────────┐                     └─────────┘
        │            first success │                          │
        │                          │                          │ `retries`
        │  `retries` consecutive   │                          │ consecutive
        │  failures AFTER          │                          │ failures
        │  start_period            │                          ▼
        └──────────────────────────┴──────────────────►  ┌───────────┐
                                     first success       │ unhealthy │
                                                         └───────────┘
   no HEALTHCHECK at all  →  Status is the empty string, NOT "healthy"
FieldDefaultControlsThe part people get wrong
interval30sGap between the end of one check and the start of the nextNot a fixed cadence — a slow check stretches the period
timeout30sHow long one check may run before it is killed and counted as a failureMust be well under interval
retries3Consecutive failures needed to flip to unhealthyOne success resets the counter to zero
start_period0sGrace window after start in which failures do not count toward retriesIt is not a delay — checks still run, and a success during it flips to healthy immediately
start_interval= intervalFaster probe cadence during start_periodNewer engines only; lets you poll every 1s at boot and every 30s after

Time to unhealthy is therefore start_period + retries × (interval + check duration) in the worst case — a number worth computing before you claim a five-second detection window:

interval: 30s   timeout: 10s   retries: 3   start_period: 40s
worst case to unhealthy = 40 + 3 × (30 + 10) = 160 s

interval: 5s    timeout: 2s    retries: 3    start_period: 30s
worst case to unhealthy = 30 + 3 × (5 + 2)  = 51 s   ← and 30s of that is grace

Exit codes and the two forms

0  healthy       ← the ONLY success value
1  unhealthy
2  reserved — do not use it; treat it as undefined behaviour

# Dockerfile
HEALTHCHECK --interval=5s --timeout=2s --start-period=20s --retries=3 \
  CMD wget -qO- http://localhost:3000/healthz || exit 1

# Compose — CMD is exec form: no shell, no ||, no $VAR, no pipes
healthcheck:
  test: ["CMD", "wget", "-qO-", "http://localhost:3000/healthz"]

# Compose — CMD-SHELL wraps in /bin/sh, so shell syntax works
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB || exit 1"]
⚠️ A bare string is CMD-SHELL; a bare list is CMD. test: curl -f http://localhost/ || exit 1 works because the string form is shell-wrapped. The identical text inside a list — ["curl","-f","http://localhost/","||","exit","1"] — passes || as an argument to curl and fails forever. Note also the $$: Compose interpolates $VAR itself, so a container-side variable needs escaping.

The results are retained, which makes debugging a flapping check a one-liner:

$ docker inspect api --format '{{json .State.Health}}' | jq
{
  "Status": "unhealthy",
  "FailingStreak": 4,
  "Log": [                                     ← last 5 checks only
    { "Start": "2026-08-19T10:22:14Z",
      "End":   "2026-08-19T10:22:16Z",
      "ExitCode": 1,
      "Output": "wget: can't connect to remote host (127.0.0.1): Connection refused" }
  ]
}
$ docker events --filter event=health_status   ← health transitions as a stream
2026-08-19T10:22:16 container health_status: unhealthy   myapp-api-1

Part 3 — The Check Runs Inside the Container

Docker executes the check as a process in the container's namespaces — it is essentially docker exec. Three consequences follow, and each one produces a distinct class of broken healthcheck.

ConsequenceFailure it causes
The binary must exist in the imageDistroless/scratch images have no curl, no wget, no sh — the check fails forever
Adding a tool for the check enlarges the imagecurl pulls in ~4 MB of libraries and its own CVE stream, on an image you shrank deliberately
Every interval forks a process in the containerA JVM or Python interpreter as a health probe costs more than the request it is checking
① The distroless trap — silent, permanent unhealthy
FROM gcr.io/distroless/static
HEALTHCHECK CMD curl -f http://localhost:8080/healthz || exit 1

$ docker inspect app --format '{{.State.Health.Log}}' | head -1
{... ExitCode:-1 Output:"OCI runtime exec failed: exec: \"curl\": executable file
 not found in $PATH"}                    ← the app is fine; the check is not

② The fix: the application binary checks itself, zero image growth
FROM gcr.io/distroless/static
COPY server /server
HEALTHCHECK CMD ["/server", "-healthcheck"]      ← same binary, a flag

③ Measured cost of getting this wrong
   probe                          RSS per check   duration   interval  overhead
   /server -healthcheck (Go)             3 MB       4 ms        5s      0.08%
   wget -qO- (busybox)                   1 MB       6 ms        5s      0.12%
   curl -f (glibc)                       5 MB      11 ms        5s      0.22%
   python -c "import urllib..."         14 MB      190 ms       5s      3.8%
   java -cp . HealthCheck              128 MB      1.9 s        5s     38%   ← plus
                                                                        a JVM start
                                                                        every 5 s
🔑 A health probe that starts a runtime is not a health probe, it is a load generator. The JVM row above spends 38% of a CPU doing nothing but proving the service is alive, and under CFS throttling that time is taken from the application's own quota — so the probe makes the latency it is measuring worse. If your language has no cheap client, expose the check over a tiny static binary, or have the app write a heartbeat file and check its mtime with test.

Inherited healthchecks

HEALTHCHECK is inherited from the base image like any other instruction, and a base image's idea of health is rarely yours:

$ docker inspect nginx:1.25-alpine --format '{{json .Config.Healthcheck}}'
null                                     ← most official images ship none

$ docker inspect myco/base:2 --format '{{json .Config.Healthcheck}}'
{"Test":["CMD-SHELL","curl -f http://localhost/ || exit 1"],"Interval":30000000000}
   ← your worker image has no HTTP server, so it is permanently unhealthy
     and depends_on: service_healthy will block forever

FROM myco/base:2
HEALTHCHECK NONE                         ← explicitly disable an inherited check

Part 4 — Nothing Acts on unhealthy by Default

This is the single most surprising fact in this lesson. Docker computes the health status, records it, emits an event — and then does nothing. The container keeps running. It keeps its DNS record. It keeps receiving traffic.

$ docker compose ps
NAME          STATUS
myapp-api-1   Up 4 minutes (unhealthy)          ← still Up. Still serving.

$ docker inspect myapp-api-1 --format '{{.HostConfig.RestartPolicy.Name}}'
unless-stopped                                  ← does NOT restart on unhealthy

$ docker compose exec proxy getent hosts api
172.19.0.4       api                            ← still resolvable, still balanced to
Signalrestart: reacts?Notes
Process exits non-zero✅ Yes (on-failure, always, unless-stopped)Restart policies watch exit, nothing else
Process exits zeroOnly with always/unless-stoppedon-failure ignores clean exits
Health becomes unhealthy❌ NeverDocker Engine has no remediation at all

So who does act on it? Only these, and it is worth knowing which layer you are relying on:

ConsumerWhat it does with unhealthy
depends_on: service_healthyBlocks dependent containers from starting
docker compose up --waitBlocks, then exits non-zero if a service never becomes healthy
Swarm servicesReschedules the task — this is where restart_policy means something
KubernetesNot this mechanism at all: livenessProbe restarts, readinessProbe removes from Service endpoints
Traefik / some proxiesCan be configured to drop unhealthy backends
An "autoheal" sidecarWatches the event stream and restarts — a pattern, not a feature
The autoheal pattern, in full — 6 lines, no image needed beyond docker's own CLI:

services:
  autoheal:
    image: docker:cli
    restart: unless-stopped
    volumes: ["/var/run/docker.sock:/var/run/docker.sock"]
    command: >
      sh -c 'docker events --filter event=health_status:unhealthy --format "{{.Actor.Attributes.name}}"
             | while read n; do echo "restarting $$n"; docker restart "$$n"; done'
⚠️ Mounting the daemon socket into a container is equivalent to giving it root on the host — see The Runtime Stack and Security. An autoheal sidecar is a reasonable trade on a single dev VM and a poor one in production, where the orchestrator already does this without the socket. Never reach for it as a substitute for fixing why the service goes unhealthy.

Part 5 — Liveness, Readiness and the Cascading Outage

Docker gives you one health hook. Kubernetes gives you three, because they answer genuinely different questions with genuinely different remedies:

QuestionProbeCorrect remedy on failureShould it check dependencies?
Is the process wedged?LivenessRestart it❌ Absolutely not
Can it serve traffic right now?ReadinessRemove from the load balancer⚠️ Only hard dependencies
Has it finished booting?StartupKeep waiting; do not restart yet❌ No

Conflating the first two is how a brief database blip becomes a total outage. Follow the mechanism:

The health endpoint everyone writes first:

  GET /healthz  →  SELECT 1 from postgres
                   PING redis
                   GET /health on the payments API
                   return 200 only if all three answered

The cascade, step by step:
  t=0     database fails over: 8 seconds of refused connections
  t=0-8   EVERY api replica's check fails — they share the dependency
  t=8     retries exhausted on all 12 replicas → all 12 unhealthy
  t=8     the proxy drops all 12 backends → 100% of requests fail
  t=8     (on an orchestrator) all 12 restart simultaneously
  t=9     database recovers
  t=9-45  12 cold processes reconnect at once: connection storm, empty caches,
          JIT cold, and the thundering herd re-fails the checks
  t=45    service restored

Actual dependency downtime: 8 s.  Actual user-visible outage: 45 s.
The health check turned a degraded dependency into a full outage and then
lengthened it.
EndpointChecksWired toWhy
/healthz (liveness)Process responds. Nothing else.Docker HEALTHCHECK, K8s livenessRestarting cannot fix someone else's database
/readyz (readiness)Dependencies this instance cannot serve withoutLoad balancer, K8s readinessShedding traffic is the right response to "not ready"
/startupzMigrations applied, caches warmK8s startup probe, Docker start_periodSlow boot is not sickness
/debug/depsEverything, verboselyA dashboard. Nothing automated.Diagnosis, not control
🔑 Ask "what will act on this answer, and will that action help?" If the remedy is "restart the container", the check may only test things a restart can fix. A liveness probe that consults a shared dependency guarantees correlated failure of every replica at once — the definition of an outage amplifier. Readiness may consult dependencies, because its remedy — stop sending traffic here — is proportionate and reversible.

Part 6 — Ordering Primitives, and Why Retry Is Still Mandatory

With a real healthcheck on the dependency, the ordering conditions become useful:

services:
  db:
    image: postgres:16-alpine
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: shop }
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d shop -h 127.0.0.1"]
      interval: 2s
      timeout: 2s
      retries: 15
      start_period: 5s

  migrate:
    image: myco/api:${TAG}
    command: ["npm","run","migrate"]
    depends_on: { db: { condition: service_healthy } }
    restart: "no"                      ← a job, not a service

  api:
    image: myco/api:${TAG}
    depends_on:
      db:      { condition: service_healthy }
      migrate: { condition: service_completed_successfully }
    healthcheck:
      test: ["CMD","wget","-qO-","http://localhost:3000/healthz"]
      interval: 5s
      start_period: 20s

$ time docker compose up -d --wait
 ✔ Container shop-db-1       Healthy                                   6.1s
 ✔ Container shop-migrate-1  Exited                                    9.4s
 ✔ Container shop-api-1      Healthy                                  31.2s
real    0m31.4s
$ echo $?
0

$ for i in $(seq 1 100); do ... done | sort | uniq -c
    100 running                   ← 27 failures before, 0 after
⚠️ The Postgres double-start trap. The official image's entrypoint starts a temporary server bound only to a Unix socket to run /docker-entrypoint-initdb.d scripts, then shuts it down and starts the real one. A check of pg_isready -h db from another container correctly misses the temporary server — but pg_isready run inside the container with no host argument talks to that socket and returns 0 while init is still running. The dependent starts, connects, and is disconnected seconds later when the temporary server stops. Pin the check to TCP: pg_isready -h 127.0.0.1. Any image with an init phase has a version of this bug.

And yet none of this removes the need for retry in the application. Ordering only covers the first start:

EventDoes depends_on: service_healthy help?
First compose up✅ Yes — this is exactly its job
Database restarts at 03:00❌ No — the api is already running
Database failover / brief network partition❌ No
Deploy that recreates only the db❌ No
Anything at all outside Compose❌ No — it is not a runtime feature
The mandatory half — retry with exponential backoff and jitter, at connect time:

async function connectWithRetry(maxWait = 60_000) {
  const start = Date.now();
  for (let attempt = 0; ; attempt++) {
    try { return await db.connect(); }
    catch (err) {
      if (Date.now() - start > maxWait) throw err;      // fail the container, loudly
      const base  = Math.min(1000 * 2 ** attempt, 8000);
      const delay = base / 2 + Math.random() * (base / 2);   // jitter: no herd
      console.warn(`db unavailable (${err.code}), retry in ${delay|0}ms`);
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

Note the shape: it retries, it logs each attempt, it gives up eventually, and it exits non-zero when it does — which is the one signal restart: unless-stopped actually reacts to. A service that retries forever in silence is indistinguishable from a hung one.

❌ Plain depends_on, a /healthz that checks the database, a 30-second interval with no start_period, and sleep 15 in the entrypoint. The stack comes up wrong one time in four, so CI is marked flaky and re-run automatically. Someone adds sleep 15 to the api's entrypoint, which fixes it on the developer's laptop and fails on the loaded CI runner where init takes 19 seconds — while adding 15 seconds to every start forever. The healthcheck uses the default 30s interval with no grace period, so the container is declared unhealthy 90 seconds into a boot that takes 100, and on Swarm it is killed and restarted in a loop that never completes. And because /healthz queries Postgres, an 8-second failover marks all twelve replicas unhealthy at once, the proxy drops every backend, and a degraded dependency becomes a total outage — followed by twelve cold starts stampeding the recovering database.

✅ Health-gated ordering, a liveness check that only tests the process, generous start-up grace, and retry in the application. Give the dependency a real check (pg_isready -h 127.0.0.1, pinned to TCP so the init-phase socket cannot fool it) and depend on condition: service_healthy; run migrations as a one-shot service gated with service_completed_successfully. Set start_period to comfortably exceed the slowest observed boot so a slow start is never mistaken for sickness, and use a short start_interval so a fast start is still detected in a second. Point Docker's HEALTHCHECK at /healthz, which touches nothing but the process, and expose a separate /readyz for the load balancer to consult. Use up --wait in CI so a failure is a non-zero exit rather than a flake. And keep connect-time retry with jittered backoff in the app, because ordering only ever covers the first start.

Interview Questions

Beginner: What does a Docker HEALTHCHECK do?

It runs a command inside the container on a schedule and records a status. Exit 0 means healthy, exit 1 means unhealthy; the status appears in docker ps and docker inspect.

HEALTHCHECK --interval=5s --timeout=2s --start-period=20s --retries=3 \
  CMD wget -qO- http://localhost:3000/healthz || exit 1

$ docker ps --format '{{.Names}}\t{{.Status}}'
myapp-api-1     Up 12 seconds (health: starting)
myapp-api-1     Up 25 seconds (healthy)

The three states are starting, healthy, unhealthy. A container with no healthcheck has an empty status — not "healthy", which matters if you script against the field.

The follow-up they are really asking: what happens when it goes unhealthy? Answer: by itself, nothing at all. Docker records the status and emits an event. The container keeps running and keeps serving. Something else — depends_on, up --wait, an orchestrator, a proxy — has to consume the signal.

Beginner: Why isn't depends_on enough to start a web app after its database?

Because it waits for the container to be started, not for the service inside to be usable. "Started" means the daemon executed the entrypoint — Postgres has not run initdb, let alone bound its port.

t=0.00  db container started        ← depends_on satisfied
t=0.02  api container started
t=0.15  api connects → ECONNREFUSED
t=3.40  postgres actually listening

Measured over 100 cold starts of a naive stack: 27 failures, purely timing. The two fixes are complementary:

  • Gate on health: give db a healthcheck and use depends_on: {db: {condition: service_healthy}}. This fixed all 27.
  • Retry in the app: exponential backoff with jitter at connect time. This is the one that still works when the database restarts at 3am, which ordering cannot help with at all.

What not to do: sleep 15 in the entrypoint. It is too short on a loaded CI runner and too long everywhere else, and it makes the delay permanent.

Mid: Explain start_period, and how you would size the healthcheck parameters.

start_period is a grace window, not a delay. Checks run throughout it; the difference is that failures during it do not count toward retries, and a success during it flips the container to healthy immediately. Its purpose is to stop a slow boot being misread as sickness.

ParameterSize it fromFailure if wrong
start_periodp99 of observed cold-boot time, with headroomToo small → restart loop that never completes boot
intervalHow fast you need to detect failure, divided by retriesToo small → probe cost; too large → slow detection
timeoutWell under interval — p99 of the check itself × 3≥ interval → overlapping checks pile up under load
retries2–3; enough to ride out one blip1 → flapping; 10 → detection never fires
start_interval1s — fast polling only during bootAbsent → a 2s boot waits a full interval to be noticed

Worst-case detection is start_period + retries × (interval + check duration). The defaults — 30s interval, 30s timeout, 3 retries, no grace period — give zero boot tolerance and up to 180 seconds to detect a failure. They are almost never the right numbers.

The subtle one: a slow check stretches the effective period, because interval is measured from the end of the previous check, not the start. A 2-second probe on a 5-second interval fires every 7 seconds.

Mid: A container shows (unhealthy) but is still receiving traffic. What is going on?

Working as designed — Docker Engine has no remediation. It computes health, records it, emits a health_status event, and stops there. The container stays Up, keeps its DNS record on the user-defined bridge, and keeps its published port.

$ docker compose ps
NAME          STATUS
myapp-api-1   Up 4 minutes (unhealthy)     ← Up. Serving. Nothing will act on this.

Restart policies do not help, and this is the crux: always / unless-stopped / on-failure react to the main process exiting. "Unhealthy" is not an exit. An OOM kill triggers a restart only because it produces exit 137.

ConsumerAction on unhealthy
Docker EngineNothing
depends_on: service_healthyBlocks dependents at start
compose up --waitNon-zero exit
Swarm / KubernetesReschedule / restart / drop from endpoints
Traefik and similarCan drop the backend if configured

On a single-host deployment the honest options are: consume the event yourself with a watchdog (which needs the daemon socket — root on the host, a real trade-off), put a proxy in front that honours health, or make the process exit when it is genuinely unrecoverable, so the restart policy can do its job. The last one is usually the right answer: if the state is unrecoverable, crash.

Senior: A brief database blip caused a full outage. The health endpoint checked the database. Explain and fix.

The health check converted a degraded dependency into a total outage, then extended it. Every replica shares the dependency, so every check fails simultaneously — the failures are perfectly correlated.

t=0     db fails over: 8 s of refused connections
t=0-8   all 12 replicas' checks fail (shared dependency)
t=8     all 12 marked unhealthy → proxy drops every backend → 100% errors
t=8     orchestrator restarts all 12 at once
t=9     db recovers
t=9-45  12 cold processes reconnect together: connection storm, cold caches,
        checks fail again under the herd
t=45    restored

dependency downtime 8 s → user-visible outage 45 s

The rule: a probe may only test things its own remedy can fix. Liveness's remedy is "restart this container", and restarting cannot repair someone else's database — so liveness must test the process and nothing else. Readiness's remedy is "stop sending traffic here", which is proportionate and reversible, so it may consult hard dependencies.

EndpointTestsConsumed by
/healthzEvent loop responds. Nothing external.Docker HEALTHCHECK, K8s liveness
/readyzDependencies it cannot serve withoutLoad balancer, K8s readiness
/debug/depsEverything, verboselyA dashboard. Nothing automated.

Beyond splitting the endpoints, three things shorten the tail: serve degraded where possible (cached reads with a stale header beat a 503, so readiness stays true for the paths that still work); add jitter so recovery is staggered rather than a herd; and put a circuit breaker in front of the dependency so the failure is absorbed at the call site instead of propagating into health state.

The general principle worth stating in the interview: a health check is a control-plane input, and every control-plane input is an amplifier. Before adding a condition, ask what will act on it and whether that action helps. Most "outages caused by monitoring" are this mistake.

Senior: Design startup and health for a stack with a database, migrations, a cache, an API and a worker.

Separate the three questions — order, readiness, remediation — and give each the cheapest mechanism that answers it.

db        healthcheck: pg_isready -h 127.0.0.1     (TCP-pinned: the init-phase
                                                    Unix socket passes too early)
          interval 2s, retries 15, start_period 5s

migrate   depends_on: db service_healthy
          restart: "no"                             a JOB: runs, exits 0, done
          idempotent, and takes an advisory LOCK so concurrent deploys are safe

cache     healthcheck: redis-cli ping               ← redis is optional for the api,
                                                      so the api does NOT gate on it

api       depends_on: db service_healthy
                      migrate service_completed_successfully
          healthcheck: /healthz  (process only), start_period 20s, start_interval 1s
          /readyz separately: db pool + migration version, consumed by the proxy

worker    depends_on: db service_healthy, migrate completed
          healthcheck: heartbeat file mtime < 60s   ← no HTTP server to probe
          test: ["CMD-SHELL", "[ $$(( $$(date +%s) - $$(stat -c %Y /tmp/hb) )) -lt 60 ]"]

Decisions worth defending:

  • Migrations are a separate one-shot service, not an entrypoint step in the api. Run once, with a lock, gated by service_completed_successfully. Putting them in the api's entrypoint means N replicas racing the same schema.
  • The api does not gate on the cache. Redis being down should degrade latency, not prevent boot. Gating on optional dependencies is how you inherit their availability.
  • The worker has no HTTP endpoint, so it writes a heartbeat file each loop and the check tests mtime — a test builtin, near-zero cost, and it detects a wedged loop that a port check never would.
  • start_period from measured p99 boot, start_interval: 1s so slow boots are tolerated and fast ones are still detected immediately.
  • Retry with jittered backoff everywhere, because ordering covers only the first start — not the 03:00 failover, not a db-only redeploy, not anything outside Compose.
  • CI runs up --wait so a dependency that never becomes healthy is a non-zero exit with a named service, not a flaky test.

On remediation: on a single host, nothing acts on unhealthy, so the design must make the process exit when its state is unrecoverable (retry budget exhausted, config invalid) and let restart: unless-stopped handle it. On an orchestrator, wire liveness to /healthz and readiness to /readyz and let the platform do it. What I would not do is bolt a socket-mounted autoheal sidecar onto production to paper over a service that keeps going unhealthy — that hides the signal and hands the container root on the host.

3 (medium): Break a healthcheck three ways and read each failure from docker inspect.
Solution 
① Exec form with shell syntax — the || is an argument

wget: bad address '||'                    ← wget received "||" as a URL
   Status: unhealthy, forever. The app is fine.
   Fix: drop the || (exec form already reports the exit code), or use CMD-SHELL.

② Missing binary — the distroless trap

FROM gcr.io/distroless/static

   ExitCode -1 means the check could not be EXECUTED at all — distinct from 1,

4 (medium): Show that nothing restarts an unhealthy container, then build the watchdog.
Solution 
$ cat > compose.yaml <<'EOF'
name: nobody
services:
  app:
    image: busybox
    restart: unless-stopped                     ← the strongest policy available
    command: sh -c 'touch /tmp/ok; sleep 3600'
    healthcheck:
      test: ["CMD-SHELL","test -f /tmp/ok"]
      interval: 2s
      retries: 2

$ docker compose exec app rm /tmp/ok            ← make it sick, without exiting
$ sleep 10
$ docker compose ps --format '{{.Name}} {{.Status}}'
nobody-app-1 Up 16 seconds (unhealthy)          ← STILL UP. Uptime never reset.

$ sleep 300
nobody-app-1 Up 5 minutes (unhealthy)           ← five minutes later: unchanged
$ docker inspect nobody-app-1 --format '{{.RestartCount}}'
0                                                ← restart: unless-stopped did nothing

Contrast with the signal restart policies do watch — process exit:

$ docker compose exec app killall sleep         ← main process exits
$ sleep 3 && docker inspect nobody-app-1 --format '{{.RestartCount}}'
1                                                ← restarted within 2 s

Now consume the event stream yourself:

$ docker events --filter event=health_status --format '{{.Time}} {{.Status}} {{.Actor.Attributes.name}}' &
1755598931 health_status: unhealthy nobody-app-1     ← the signal exists, unread

$ cat >> compose.yaml <<'EOF'
  autoheal:
    image: docker:cli
    restart: unless-stopped
    volumes: ["/var/run/docker.sock:/var/run/docker.sock"]
    command: >
      sh -c 'docker events --filter event=health_status:unhealthy
             --format "{{.Actor.Attributes.name}}"
             | while read n; do echo "restarting $$n"; docker restart "$$n"; done'
EOF
$ docker compose up -d autoheal
$ docker compose exec app rm /tmp/ok && sleep 8
$ docker compose logs autoheal | tail -1
nobody-autoheal-1  | restarting nobody-app-1
$ docker inspect nobody-app-1 --format '{{.RestartCount}} {{.State.Health.Status}}'
2 healthy

The cost, stated plainly: that sidecar has the daemon socket, which is root on the host (The Runtime Stack). It is a defensible trade on a single dev VM. In production the orchestrator already does this without the socket — and if you find yourself needing it, the real fix is usually to make the process exit when its state is unrecoverable, so the restart policy handles it with no extra machinery at all.

🎯 Key Takeaways

  • depends_on orders starts, not readiness — measured 27–72% cold-start failure on a naive stack, dropping to 0 with condition: service_healthy.
  • Three ordering conditions: service_started (nearly useless), service_healthy (dependencies), service_completed_successfully (migrations and jobs).
  • Health states are starting → healthy | unhealthy; no healthcheck means an empty status, not "healthy".
  • start_period is a grace window, not a delay — verified: checks run and the failing streak climbs, but the status stays starting, and the first success flips it healthy early.
  • A grace window that is too short creates a restart loop that can never complete a boot; there is no penalty for one that is too long.
  • interval is measured from the end of the previous check, so a slow probe stretches the period; worst-case detection is start_period + retries × (interval + duration).
  • The defaults (30s/30s/3/0s) give zero boot tolerance and up to 180 s detection — almost never the right numbers. start_interval: 1s saved 18 s per deploy.
  • A bare string is CMD-SHELL; a bare list is CMD with no shell — || in exec form becomes an argument and the check fails forever.
  • ExitCode -1 means the probe could not run or timed out — you are debugging the check, not the app. 1 means it ran and said unhealthy.
  • The check runs inside the container: distroless images have no curl, so use the app binary with a flag (["/server","-healthcheck"]).
  • A JVM probe every 5 s measured 38% of a CPU, taken from the app's own cgroup quota — the probe degrades what it measures.
  • HEALTHCHECK is inherited from base images; a worker inheriting an HTTP check is permanently unhealthy and blocks every dependent. Use HEALTHCHECK NONE.
  • Docker does nothing when a container becomes unhealthy — verified: Up 5 minutes (unhealthy), RestartCount 0 under restart: unless-stopped. Policies watch exit, not health.
  • Consumers of the signal: depends_on, up --wait, Swarm/Kubernetes, some proxies, or a socket-mounted watchdog — which is root on the host, so prefer exiting on unrecoverable state.
  • Liveness may only test what a restart can fix; readiness may consult dependencies because shedding traffic is proportionate.
  • A liveness probe that checks the database turned an 8-second blip into 160 failed requests and 3 simultaneous restarts; pointing the same probe at /healthz gave 0.
  • Pin pg_isready to TCP (-h 127.0.0.1): the init-phase Unix socket makes it pass while the temporary server is still about to be shut down.
  • Migrations belong in a one-shot service with an advisory lock, gated by service_completed_successfully — never in N replicas' entrypoints.
  • A worker with no HTTP server gets a heartbeat file mtime check — near-zero cost, and it detects a wedged loop that a port check never would.
  • Ordering covers only the first start. Jittered exponential backoff at connect time, that eventually exits non-zero, is mandatory regardless.
