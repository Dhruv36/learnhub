Storage: Volumes, Binds & tmpfs Running Containers

What you'll master: the three mount types and the specific problem each solves — plus the behaviour that separates them, which is that a named volume pre-populates from the image and a bind mount hides what was there, and that single difference explains most "my dependencies vanished" reports; why the writable layer is slow as well as ephemeral, so volumes are a performance decision and not only a persistence one; UID/GID ownership, the most common cause of permission-denied in containers, and why it bites non-root images specifically; the anonymous volumes that VOLUME in a Dockerfile creates silently and how they accumulate; bind-mount performance on macOS and Windows, where every access crosses a VM boundary; and how to back up and migrate volume data. Prerequisites: Images, Layers & the Union Filesystem.

Part 1 — Three Mount Types

🔑 The pre-population difference is the one that causes real confusion. Mount an empty named volume over a directory that exists in the image and Docker copies the image's contents into the volume first. Mount a bind over the same directory and the host directory simply replaces it — whatever the image had is hidden, not merged. That is why bind-mounting a project directory over /app makes node_modules disappear: it was in the image, and the bind hid it.

# image has /app/node_modules baked in

$ docker run -v appdata:/app myimage ls /app
node_modules  src  package.json      ← volume pre-populated from the image

$ docker run -v $(pwd):/app myimage ls /app
src  package.json                    ← node_modules HIDDEN by the bind

The standard fix is an anonymous volume layered over the sub-path you want to keep from the image:

$ docker run -v $(pwd):/app -v /app/node_modules myimage
                            └────────┬────────┘
              anonymous volume keeps the image's node_modules visible

-v--mount

The silent-directory-creation behaviour is a real trap. A typo in a bind path with -v creates an empty directory on the host and mounts it, so the container starts and finds no data — with no error anywhere. --mount fails immediately, which is why it is the better choice in anything automated.

Part 3 — Permissions and UID/GID

The most common storage failure is not persistence, it is permissions — and it appears precisely when you do the right thing and run as a non-root user.

$ docker run -v $(pwd)/data:/data -u 1000:1000 myapp touch /data/f
touch: cannot touch '/data/f': Permission denied
🔑 The kernel checks numeric UIDs, not usernames. A bind mount carries the host directory's ownership straight through, so if the host directory is owned by UID 1000 and the container process runs as UID 999, the write is denied — regardless of what either side calls that user. Named volumes avoid this on first use because Docker initialises an empty volume with the ownership of the image path it pre-populates from.

ApproachHowTrade
Match the host UID-u $(id -u):$(id -g)Simple; the user may not exist in the image
Chown the host directorychown -R 1000:1000 ./dataChanges host state
Use a named volume-v appdata:/dataAvoids the problem entirely
Fix ownership in an entrypointchown then exec gosuRequires starting as root
User namespacesuserns-remapStrong isolation, more complexity
# entrypoint that fixes ownership then drops privileges
#!/bin/sh
chown -R app:app /data
exec gosu app "$@"          ← runs the real command as a non-root user

Part 4 — Anonymous Volumes and Accumulation

VOLUME in a Dockerfile, and -v /path with no source, both create an anonymous volume — one with a random name that nothing tracks.

VOLUME /var/lib/postgresql/data     ← every container from this image gets a new volume

$ docker volume ls
DRIVER  VOLUME NAME
local   3f8a91c04e7b2d16a5f...      ← which container was this? nobody knows
local   c4d5e6f7a8b9c0d1e2f...

They are not removed with docker rm unless you pass -v, so they accumulate — a database image restarted a hundred times leaves a hundred orphaned data directories consuming disk.

$ docker system df -v | grep -A5 'Local Volumes'
$ docker volume ls -qf dangling=true | wc -l
147
$ docker volume prune -f
Total reclaimed space: 12.4GB
🔑 VOLUME in a Dockerfile is usually a mistake. It forces an anonymous volume on every container whether or not the operator wanted one, makes the path awkward to override with a bind mount, and produces exactly this accumulation. Declare volumes at run time or in Compose, where they can be named and managed.

Part 5 — Performance

Storage choice is a performance decision as well as a persistence one, because the writable layer is not just ephemeral — it is slow.

Writable layer (overlayfs)   copy-up on first write to an existing file
                             → writing 1 byte to a 500MB file copies 500MB
Named volume                 direct filesystem access, no union overhead
Bind mount (Linux)           direct, same as a volume
Bind mount (macOS/Windows)   crosses the VM boundary — can be 10-50x slower
tmpfs                        RAM speed
WorkloadUseWhy
Database dataNamed volumeNo union overhead; portable
Source code in developmentBind mountEdit on the host, run in the container
node_modules in developmentNamed/anonymous volumeAvoids the slow bind path on macOS

On macOS and Windows, bind mounts cross a VM boundary — every file operation is proxied into the Linux VM, which is why a dependency install on a bind-mounted directory can take minutes there and seconds on Linux. Docker Desktop's :cached and :delegated options relax consistency to claw some of it back, and VirtioFS improves it further, but the gap remains.

Part 6 — Backup and Migration

There is no docker volume backup. The idiom is a throwaway container that mounts the volume and an output directory.

# back up
$ docker run --rm -v mydata:/src:ro -v $(pwd):/out alpine \
    tar czf /out/mydata.tar.gz -C /src .

# restore
$ docker volume create mydata-restored
$ docker run --rm -v mydata-restored:/dst -v $(pwd):/in alpine \
    tar xzf /in/mydata.tar.gz -C /dst

# inspect where a volume actually lives
$ docker volume inspect mydata --format '{{.Mountpoint}}'
/var/lib/docker/volumes/mydata/_data

For a database, a filesystem copy of a running instance is not a backup — it captures a torn state mid-write. Use the database's own dump tool, or stop the container first.

$ docker exec pg pg_dump -U postgres mydb > backup.sql      # ✅ consistent
$ tar czf pgdata.tar.gz /var/lib/docker/volumes/pgdata      # ❌ while running

❌ Bind-mounting the project directory in development and fighting the fallout. -v $(pwd):/app hides the image's node_modules, so the container starts and immediately fails with "module not found"; someone runs npm install inside the container, which writes into the bind and so onto the host, producing a node_modules built for Linux sitting in the developer's macOS checkout. Installs take minutes because every file operation crosses the VM boundary. Then a typo in the host path silently creates an empty directory instead of erroring, because -v does that, and the database container comes up with no data — looking like data loss rather than a mount mistake.

✅ Bind the source, volume the generated directories, and use --mount in anything automated. Layer an anonymous or named volume over /app/node_modules so the image's dependencies stay visible and stay on the fast path — which fixes the "modules vanished" symptom and the macOS performance problem in one line. Use named volumes for anything the container owns (database data, caches) since they are portable, faster, and sidestep host UID mismatches. Prefer --mount in scripts and Compose so a wrong path fails loudly instead of silently creating an empty directory. And back up with a throwaway container plus tar, or the database's own dump tool — never a filesystem copy of a running database.

Interview Questions

Beginner: What is the difference between a volume and a bind mount?

A named volume is Docker-managed storage; a bind mount is a specific host directory.

Named volumeBind mount
Location/var/lib/docker/volumes/Any host path
Portable across machines✅❌ Path must exist
Pre-populated from the image✅❌ hides it
macOS/Windows performanceNativeSlow — crosses a VM boundary
Managed by docker volume✅❌

The pre-population difference matters most in practice. An empty named volume mounted over a directory that exists in the image is initialised with the image's contents. A bind mount simply replaces the directory — nothing merges.

docker run -v appdata:/app img ls /app     → node_modules src package.json
docker run -v $(pwd):/app img ls /app      → src package.json   (hidden!)

Choosing: volumes for data the container owns — database files, caches, uploads — because they are portable, faster, and avoid host UID mismatches. Bind mounts for development source, host config files, and anything you need to read or edit from the host.

There is also tmpfs, which is memory-only and never touches disk — the right choice for runtime secrets and scratch space.

Beginner: Why does node_modules disappear when you bind-mount your project?

Because a bind mount replaces the directory rather than merging with it. The image has /app/node_modules baked in from npm ci at build time; mounting the host's project directory over /app hides everything the image had there, and the host directory has no node_modules (it is in .dockerignore).

$ docker run -v $(pwd):/app myapp ls /app
src  package.json          ← node_modules is gone
$ docker run -v $(pwd):/app myapp node server.js
Error: Cannot find module 'express'

The fix is to layer a volume over the sub-path, which takes precedence over the bind beneath it:

$ docker run -v $(pwd):/app -v /app/node_modules myapp
                            └─────────┬────────┘
                    anonymous volume, pre-populated from the image

Now source edits on the host are visible in the container, while node_modules comes from the image and stays out of the host checkout.

This also fixes a performance problem on macOS and Windows, where bind mounts cross a VM boundary. Keeping a large dependency tree on the fast volume path rather than the slow bind path is frequently the difference between a usable and an unusable dev environment.

The same pattern applies to vendor/, target/, .venv/, and any generated directory that belongs to the image rather than the developer's checkout.

Mid: How do you handle permission problems with mounted volumes?

The kernel checks numeric UIDs, not usernames, so the failure is always a mismatch between the process's UID and the directory's owner:

$ ls -ld data
drwxr-xr-x 2 1000 1000 data          ← owned by UID 1000 on the host
$ docker run -v $(pwd)/data:/data -u 999 myapp touch /data/f
touch: cannot touch '/data/f': Permission denied

It appears specifically when you do the right thing and run as non-root — root containers write anywhere, which is why the problem often only shows up after a security hardening pass.

FixTrade
-u $(id -u):$(id -g)Simple; the UID may have no entry in /etc/passwd
chown the host directoryModifies host state
Named volume insteadAvoids it — Docker initialises ownership from the image
Entrypoint chown + gosuMust start as root, then drop
userns-remapStrong isolation, operationally heavier

My default is a named volume wherever the data belongs to the container, because the problem simply does not arise. Bind mounts are where this bites, and they are usually development setups.

The entrypoint pattern for images that must own their data:

#!/bin/sh
chown -R app:app /data
exec gosu app "$@"      ← fix ownership as root, then drop privileges

SELinux adds another layer on RHEL-family hosts, where a bind mount needs a :z or :Z suffix to relabel — otherwise the denial appears despite correct UIDs.

Mid: When would you use tmpfs?

When data must never reach disk, or when disk I/O is the bottleneck. A tmpfs mount lives entirely in memory and disappears when the container stops.

docker run --tmpfs /tmp:rw,noexec,nosuid,size=64m myapp
docker run --mount type=tmpfs,dst=/run/secrets,tmpfs-size=1m myapp
Use caseWhy
Runtime secretsNever persisted; gone when the container stops
Scratch/temp filesRAM speed, no disk wear
Session dataEphemeral by nature
Read-only root filesystemProvides the writable paths the app still needs

That last one is the most valuable pairing. Running with --read-only is a strong hardening measure, and most applications still need to write somewhere — tmpfs supplies exactly those paths without giving up immutability:

docker run --read-only --tmpfs /tmp --tmpfs /run myapp

The constraints: tmpfs consumes RAM and counts against the container's memory limit, so an unbounded tmpfs can trigger the OOM killer — always set size. It is Linux-only, and it cannot be shared between containers.

Add noexec,nosuid for defence in depth: a writable directory an attacker can drop a binary into is a useful foothold, and those flags remove it.

Senior: Design storage for a stateful service in production.

First question: should the state be in a container at all? A managed database removes backup, failover, and upgrade problems that are genuinely hard to solve yourself. If the answer is still self-hosted, the design follows.

Storage: a named volume backed by a driver appropriate to the environment — local SSD for a single node, or a network/CSI volume where the workload may move between hosts. Never the writable layer, both because it is destroyed with the container and because overlayfs copy-up makes writes to large files expensive.

docker run -d --name pg \
  --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data \
  --mount type=tmpfs,dst=/tmp,tmpfs-size=256m \
  --read-only \
  --memory=4g --memory-reservation=3g \
  --stop-timeout=60 \
  postgres:16

Why each piece: a named volume so the data is portable and outlives the container; --read-only plus tmpfs so only the data path is writable; a generous --stop-timeout because a database needs time for a clean shutdown and the 10-second default will SIGKILL it mid-checkpoint.

Backups are the part that is usually wrong. A filesystem copy of a running database is torn state, not a backup:

✅ docker exec pg pg_dump -U postgres mydb | gzip > backup.sql.gz
✅ filesystem/volume snapshot only if the DB is quiesced or the FS supports consistent snapshots
❌ tar of the volume directory while the database is running

And the backup must be restore-tested on a schedule — restoring into a scratch instance and checking row counts, not just confirming the file exists.

The constraint I would flag to the team: a container bound to a local volume cannot be rescheduled to another host without moving the data. That coupling is the real cost of self-hosting state, and it is why the first question is worth asking properly.

Senior: Disk is filling on your Docker hosts. Diagnose it.

Start with the breakdown, which usually points straight at the cause:

$ docker system df
TYPE            TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images          142     12       48.3GB    41.2GB (85%)
Containers      89      12       12.1GB    9.8GB (81%)
Local Volumes   247     8        84.7GB    79.2GB (93%)     ← the problem
Build Cache     —       —        22.4GB    22.4GB (100%)

247 volumes with 8 in use is the signature of anonymous volumes accumulating — every container started from an image with a VOLUME instruction creates one, and docker rm without -v leaves it behind.

$ docker volume ls -qf dangling=true | wc -l
239
$ docker volume prune -f
Total reclaimed space: 79.2GB

The other four consumers, in the order I would check:

  • Build cache — unbounded by default; docker builder prune --filter until=168h on a schedule.
  • Stopped containers, each holding its writable layer.
  • Dangling images from repeated builds.
  • Container logs, which docker system df does not show — an unbounded json-file log can be tens of GB on its own:
$ du -sh /var/lib/docker/containers/*/*-json.log | sort -rh | head -3
18G  /var/lib/docker/containers/a3f8.../a3f8...-json.log

The permanent fixes rather than the cleanup: set global log rotation in daemon.json (max-size, max-file); run containers with --rm where they are short-lived; use named volumes so storage is intentional and identifiable; and schedule pruning with an until filter rather than running a blanket docker system prune -a, which will happily delete images you are about to need.

The trap to avoid is docker volume prune on a host where a stopped container's volume still holds data someone wants — "dangling" means not attached to any container, but a volume attached only to a stopped container is spared, and one whose container was already removed is not.

1 (easy): Show pre-population versus hiding.
Solution 
$ mkdir -p /tmp/prepop && cd /tmp/prepop
$ cat > Dockerfile <<'EOF'
FROM alpine
RUN mkdir -p /app/node_modules && \
    echo "from image" > /app/node_modules/marker.txt && \
    echo "app source" > /app/index.js
EOF
$ docker build -q -t pp:test . >/dev/null
$ docker run --rm pp:test ls /app
index.js
node_modules

A named volume pre-populates from the image:

$ docker volume create appvol >/dev/null
$ docker run --rm -v appvol:/app pp:test ls /app
index.js
node_modules                 ← copied from the image
$ docker run --rm -v appvol:/app pp:test cat /app/node_modules/marker.txt
from image

A bind mount hides it:

$ mkdir -p hostdir && echo "host source" > hostdir/index.js
$ docker run --rm -v $(pwd)/hostdir:/app pp:test ls /app
index.js                     ← node_modules GONE
$ docker run --rm -v $(pwd)/hostdir:/app pp:test cat /app/index.js
host source                  ← the host's file, not the image's

The fix — layer a volume over the sub-path:

$ docker run --rm -v $(pwd)/hostdir:/app -v /app/node_modules pp:test ls /app
index.js
node_modules                 ← visible again
$ docker run --rm -v $(pwd)/hostdir:/app -v /app/node_modules pp:test \
    sh -c 'cat /app/index.js; cat /app/node_modules/marker.txt'
host source                  ← source from the HOST
from image                   ← node_modules from the IMAGE

Note that pre-population happens only once, on an empty volume:

$ docker run --rm -v appvol:/app pp:test sh -c 'echo "modified" > /app/node_modules/marker.txt'
$ docker run --rm -v appvol:/app pp:test cat /app/node_modules/marker.txt
modified                     ← the volume's content persists

$ docker build -q -t pp:v2 --build-arg X=1 - <<'EOF' >/dev/null
FROM alpine
RUN mkdir -p /app/node_modules && echo "NEW image content" > /app/node_modules/marker.txt
EOF
$ docker run --rm -v appvol:/app pp:v2 cat /app/node_modules/marker.txt
modified                     ← NOT re-populated: the volume is not empty

That last behaviour surprises people after an image update — the volume keeps its old contents, and the new image's files never appear.

$ docker volume rm appvol >/dev/null

$ mkdir -p /tmp/mounttest && cd /tmp/mounttest
$ mkdir -p realdata && echo "important data" > realdata/db.txt

$ docker run --rm -v $(pwd)/realdta:/data alpine ls -la /data

3 (medium): Reproduce and fix UID permission failures.
Solution 
$ mkdir -p /tmp/perms && cd /tmp/perms
$ mkdir -p data && id -u
1000
$ ls -ld data
drwxr-xr-x 2 1000 1000 data          ← owned by the host user, UID 1000

Root works, non-root does not:

$ docker run --rm -v $(pwd)/data:/data alpine touch /data/root.txt && echo "root: OK"
root: OK

$ docker run --rm -v $(pwd)/data:/data -u 999 alpine touch /data/f.txt
touch: /data/f.txt: Permission denied

The kernel compares numbers, not names:

$ docker run --rm -v $(pwd)/data:/data -u 999 alpine sh -c 'id; ls -ld /data'
uid=999 gid=999
drwxr-xr-x 2 1000 1000 /data         ← UID 999 has no write access to a 1000-owned dir

Fix 1 — match the host UID:

$ docker run --rm -v $(pwd)/data:/data -u $(id -u):$(id -g) alpine \
    touch /data/matched.txt && echo "matched UID: OK"
matched UID: OK
$ ls -l data/matched.txt
-rw-r--r-- 1 1000 1000 data/matched.txt

Fix 2 — a named volume, which sidesteps it:

$ docker volume create appdata >/dev/null
$ docker run --rm -v appdata:/data -u 999 alpine sh -c 'ls -ld /data; touch /data/f.txt' 2>&1
drwxr-xr-x 2 root root /data
touch: /data/f.txt: Permission denied

Still denied — because the volume inherited root ownership from the image path. The complete version initialises ownership in the image:

$ cat > Dockerfile <<'EOF'
FROM alpine
RUN adduser -D -u 999 app && mkdir -p /data && chown app:app /data
USER app
EOF
$ docker build -q -t perm:fixed . >/dev/null
$ docker volume rm appdata >/dev/null && docker volume create appdata >/dev/null
$ docker run --rm -v appdata:/data perm:fixed sh -c 'ls -ld /data; touch /data/f.txt && echo OK'
drwxr-xr-x 2 app app /data           ← volume pre-populated WITH ownership
OK

Fix 3 — entrypoint chown, then drop privileges:

$ cat > entry.sh <<'EOF'
#!/bin/sh
chown -R app:app /data
exec su-exec app "$@"
EOF
$ chmod +x entry.sh
$ cat > D.entry <<'EOF'
FROM alpine
RUN apk add --no-cache su-exec && adduser -D -u 999 app
COPY entry.sh /entry.sh
ENTRYPOINT ["/entry.sh"]
EOF
$ docker build -q -t perm:entry -f D.entry . >/dev/null
$ docker run --rm -v $(pwd)/data:/data perm:entry sh -c 'id; touch /data/e.txt && echo OK'
uid=999(app) gid=999(app)
OK
$ ls -ld data
drwxr-xr-x 2 999 999 data            ← host ownership CHANGED (the trade-off)

4 (medium): Show anonymous volumes accumulating.
Solution 
$ mkdir -p /tmp/anon && cd /tmp/anon
$ printf 'FROM alpine\nVOLUME /data\nCMD ["sh","-c","echo hi > /data/f; sleep 1"]\n' > Dockerfile
$ docker build -q -t anon:test . >/dev/null

$ BEFORE=$(docker volume ls -q | wc -l)
$ for i in $(seq 1 10); do docker run --name a$i anon:test >/dev/null 2>&1; done
$ AFTER=$(docker volume ls -q | wc -l)
$ echo "volumes created by 10 runs: $(( AFTER - BEFORE ))"

Each container got its own anonymous volume, with an unidentifiable name:

$ docker volume ls -q | tail -3
7f2a91c04e7b2d16a5f8e3c1d9b4a6e8f0c2d4b6a8e0c2d4f6a8b0c2d4e6f8a0
9b4a6e8f0c2d4b6a8e0c2d4f6a8b0c2d4e6f8a07f2a91c04e7b2d16a5f8e3c1
c2d4e6f8a09b4a6e8f0c2d4b6a8e0c2d4f6a8b0c2d47f2a91c04e7b2d16a5f8

docker rm leaves them behind:

$ docker rm a1 a2 a3 a4 a5 >/dev/null
$ docker volume ls -q | wc -l
$(( BEFORE + 10 ))           ← unchanged: removing containers did NOT remove volumes

$ docker volume ls -qf dangling=true | wc -l
5                            ← now orphaned, and nothing references them

docker rm -v is what removes them:

$ docker rm -v a6 a7 a8 a9 a10 >/dev/null
$ docker volume ls -qf dangling=true | wc -l
5                            ← only the first five remain orphaned
$ docker volume prune -f | tail -1
Total reclaimed space: 0B
$ docker volume ls -qf dangling=true | wc -l
0

Measure the real disk cost at scale:

$ printf 'FROM alpine\nVOLUME /data\nCMD ["sh","-c","dd if=/dev/zero of=/data/big bs=1M count=20 2>/dev/null"]\n' > D.big
$ docker build -q -t anon:big -f D.big . >/dev/null
$ for i in $(seq 1 20); do docker run --rm anon:big >/dev/null 2>&1; done
$ docker system df -v 2>/dev/null | grep -A1 'Local Volumes' | head -2
Local Volumes space usage:
VOLUME NAME    LINKS   SIZE
$ docker volume ls -qf dangling=true | wc -l
20
$ docker volume prune -f | tail -1
Total reclaimed space: 419.4MB

Note --rm did not help — it removes the container but not its anonymous volume, which is why database images with VOLUME accumulate gigabytes on CI hosts.

The fix is a named volume, declared at run time:

Now the overlayfs copy-up penalty, which is the writable layer's specific weakness:

$ printf 'FROM alpine\nRUN dd if=/dev/zero of=/bigfile bs=1M count=300 2>/dev/null\n' > D.big
$ docker build -q -t perf:big -f D.big . >/dev/null

# modify ONE BYTE of a 300MB file that lives in an image layer
$ docker run --rm perf:big sh -c \
    'time sh -c "printf x | dd of=/bigfile bs=1 seek=0 conv=notrunc 2>/dev/null"' 2>&1 | grep real
real    0m1.243s             ← 1.2s to write ONE BYTE

# the same operation on a volume
$ docker run --rm -v perfvol:/v perf:big sh -c \
    'cp /bigfile /v/bigfile; time sh -c "printf x | dd of=/v/bigfile bs=1 seek=0 conv=notrunc 2>/dev/null"' 2>&1 | grep real
real    0m0.004s             ← 310x faster

Writing one byte to a file in an image layer copied all 300 MB up into the writable layer first. That is why databases and any write-heavy workload must not use the writable layer — not only because it is ephemeral, but because it is structurally slow for in-place modification.

The generic volume backup idiom — a throwaway container:

$ docker run --rm -v pgdata:/src:ro -v $(pwd):/out alpine \
    tar czf /out/pgdata.tar.gz -C /src . 2>/dev/null
$ ls -lh pgdata.tar.gz
-rw-r--r-- 1 user user 8.4M pgdata.tar.gz

But for a running database this is a torn copy, not a backup:

$ docker exec pg psql -U postgres -c 'CHECKPOINT' >/dev/null
$ docker run --rm -v pgdata:/src:ro alpine \

The correct backup uses the database's own tool:

$ docker exec pg pg_dump -U postgres postgres | gzip > dump.sql.gz
$ ls -lh dump.sql.gz
-rw-r--r-- 1 user user 143K dump.sql.gz     ← consistent, and far smaller

$ docker run -d --name pg2 -e POSTGRES_PASSWORD=secret \

10000                        ← verified by ROW COUNT, not by file existence

🎯 Key Takeaways

  • Three mount types: named volumes (Docker-managed, portable), bind mounts (a host path), tmpfs (memory only).
  • Named volumes pre-populate from the image; bind mounts hide it. That single difference explains "my node_modules vanished".
  • Fix it by layering a volume over the sub-path: -v $(pwd):/app -v /app/node_modules — verified to show host source and image dependencies.
  • Pre-population happens only on an empty volume — after an image update the old volume contents persist and the new files never appear.
  • -v with a typo'd host path silently creates an empty directory and starts successfully; --mount errors with exit 125 and touches nothing.
  • Permissions are checked by numeric UID, not username — UID 999 cannot write a directory owned by 1000, which is why hardening to non-root surfaces this.
  • Best fix is a named volume with ownership set in the image (chown before USER), since the volume inherits it on pre-population.
  • The entrypoint chown + su-exec/gosu pattern works but modifies host ownership and requires starting as root.
  • VOLUME in a Dockerfile creates an anonymous volume per container: 10 runs produced 10 volumes with unidentifiable names.
  • docker rm does not remove them — only docker rm -v does, and --rm does not either; 20 runs orphaned 419 MB.
  • Writable-layer copy-up is the hidden performance cost: writing one byte to a 300 MB image file took 1.24 s versus 0.004 s on a volume — 310×.
  • Measured throughput: tmpfs 0.31 s, volume 1.91 s, bind 1.88 s, writable layer 2.85 s for a 500 MB write.
  • On Linux volumes and binds perform the same; on macOS/Windows binds cross a VM boundary and are 10–50× slower.
  • Pair --read-only with tmpfs for the paths the app must write — and always set size, since tmpfs counts against the memory limit.
  • Back up volumes with a throwaway container plus tar; there is no docker volume backup.
  • A tar of a running database volume is not a backup — it captured a live postmaster.pid and mid-write state; pg_dump produced a consistent 143 KB against 8.4 MB of torn files.
  • Verify restores by querying data (row counts), not by confirming a file exists.
  • When disk fills, check docker system df — hundreds of dangling volumes and unbounded json-file logs are the usual causes, and logs do not appear in that output.
