BuildKit & Modern Build Features Building Images

What you'll master: what changed when BuildKit replaced the legacy builder — a dependency graph instead of a linear script, which is what makes parallel stages, skipped stages, and content-addressed caching possible; the # syntax= directive, which lets a Dockerfile opt into newer features than your Docker version ships; the four mount types (cache, secret, ssh, bind) and exactly which problem each removes; multi-platform builds and why an emulated build can be 15× slower than a native one; buildx drivers, including why the default driver silently lacks features people then report as bugs; SBOM and provenance attestations generated at build time; and the failure modes that appear only with BuildKit, such as heredoc support depending on the syntax version rather than the Docker version. Prerequisites: Multi-stage Builds.

Part 1 — Graph, Not Script

The legacy builder executed instructions top to bottom, committing a container after each one. BuildKit parses the Dockerfile into a directed acyclic graph of operations and solves it.

LEGACY BUILDER                      BUILDKIT
run instruction 1                   build the DAG
  commit container                  ├─ solve only nodes the target needs
run instruction 2                   ├─ run independent nodes in PARALLEL
  commit container                  ├─ content-addressed cache per node
...strictly serial                  └─ skip nodes whose output is cached
CapabilityLegacyBuildKit
Parallel stage execution❌✅
Skip stages not needed by the target❌ Builds everything✅
Cache mounts❌✅
Build secrets❌✅
SSH forwarding❌✅
Multi-platform in one build❌✅
Cache import/exportLimited✅ Registry, GHA, local
Only sends needed context files❌ Sends everything✅ On demand
🔑 BuildKit is the default in modern Docker, but the legacy builder is still reachable — DOCKER_BUILDKIT=0, some CI images, and older Docker versions. That matters because a Dockerfile using cache mounts or secrets fails with a confusing syntax error rather than a feature error under the legacy builder, which sends people looking for a typo.

$ docker build --progress=plain -t app . 2>&1 | head -2
#1 [internal] load build definition from Dockerfile      ← BuildKit
Sending build context to Docker daemon  1.2MB            ← legacy

Part 2 — The Syntax Directive

The first line of a Dockerfile can select a frontend — the parser BuildKit uses — which is downloaded at build time.

# syntax=docker/dockerfile:1
FROM alpine
...
🔑 This decouples Dockerfile features from your Docker version. A machine running an older Docker can use heredocs, COPY --link, and newer mount options simply because the frontend image is fetched during the build. Omitting the directive pins you to whatever the built-in parser supports, which is the usual explanation for "this syntax works on my colleague's machine".

DirectiveMeaning
docker/dockerfile:1Latest stable v1 — the recommended default
docker/dockerfile:1.7Pinned minor, for reproducibility
docker/dockerfile:1-labsExperimental features (COPY --parents, RUN --network)

Heredocs are the most immediately useful thing it unlocks — they collapse the backslash-and-&& chains that make Dockerfiles unreadable:

# syntax=docker/dockerfile:1
RUN <<EOF
set -eux
apt-get update
apt-get install -y --no-install-recommends curl jq
rm -rf /var/lib/apt/lists/*
EOF

Still one layer, but with real error handling (set -e) instead of relying on && to short-circuit.

# syntax=docker/dockerfile:1

Bind mounts avoid a layer entirely when you only need to read something during a command:

# instead of COPY package.json ./  (which creates a layer)
RUN --mount=type=bind,source=package.json,target=/tmp/package.json \
    npm ci --prefix /tmp

Part 4 — Multi-Platform Builds

One command can produce images for several architectures and publish them under a single tag as a manifest list.

$ docker buildx build --platform linux/amd64,linux/arm64 \
    -t myrepo/app:1.0 --push .

$ docker buildx imagetools inspect myrepo/app:1.0
MediaType: application/vnd.oci.image.index.v1+json
Manifests:
  Platform:  linux/amd64
  Platform:  linux/arm64          ← one tag, per-architecture images
🔑 There are two ways to build for another architecture, and they differ by more than an order of magnitude. QEMU emulation runs the foreign binaries on your CPU — universally available and very slow. Native builders (a real arm64 machine, or a remote builder node) run at full speed. For compiled languages, cross-compilation avoids the question entirely by building the foreign binary natively and only packaging it for the target platform.

# ✅ cross-compile: the Go toolchain runs NATIVELY, targets the foreign platform
FROM --platform=$BUILDPLATFORM golang:1.22 AS build
ARG TARGETOS TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /app .

FROM alpine:3.19
COPY --from=build /app /app
VariableIs
BUILDPLATFORMWhere the build runs (your machine)
TARGETPLATFORMWhat is being built for
TARGETOS, TARGETARCHSplit components of the target

Part 5 — buildx Drivers

buildx can drive several builder backends, and the default one lacks features that people then report as broken.

DriverMulti-platformCache exportUse for
docker (default)❌ One at a time❌ Inline onlySimple local builds
docker-container✅✅ All backendsThe usual answer
kubernetes✅✅Shared CI builders in a cluster
remote✅✅A dedicated build server
$ docker buildx create --name mybuilder --driver docker-container --use
$ docker buildx inspect --bootstrap
Name:   mybuilder
Driver: docker-container
Platforms: linux/amd64, linux/arm64, linux/arm/v7, ...

The default docker driver cannot do multi-platform or registry cache export, so --platform linux/amd64,linux/arm64 fails and --cache-to type=registry errors — both with messages that suggest a flag problem rather than a driver one.

--load versus --push is the other frequent confusion: a container-driver build produces an image in the builder, not in your local daemon.

--load    import the result into the local Docker daemon (single platform only)
--push    push directly to a registry (required for multi-platform)
(neither) the image stays in the build cache and is discarded

Part 6 — Attestations: SBOM and Provenance

BuildKit can attach supply-chain metadata to an image at build time, which is what makes later verification meaningful.

$ docker buildx build --sbom=true --provenance=mode=max \
    -t myrepo/app:1.0 --push .

$ docker buildx imagetools inspect myrepo/app:1.0 --format '{{json .SBOM}}' | head -5
$ docker buildx imagetools inspect myrepo/app:1.0 --format '{{json .Provenance}}'
AttestationRecordsAnswers
SBOMEvery package and version in the image"Are we affected by CVE-2024-X?"
ProvenanceSource repo, commit, builder, materials"Where did this image come from?"

The SBOM turns vulnerability response from a scan into a query. When a CVE lands, scanning every image takes hours; querying stored SBOMs for the affected package takes seconds and covers images that are no longer being built.

❌ Using buildx flags on the default driver and concluding the features are broken. The team adds --platform linux/amd64,linux/arm64 and gets ERROR: docker exporter does not currently support exporting manifest lists; they add --cache-to type=registry and get another export error. The messages point at the flags, so the conclusion is that buildx multi-platform "does not work", and the workaround becomes building on two machines and pushing two tags. Meanwhile a Dockerfile with cache mounts fails on one CI runner with a syntax error, because that runner has DOCKER_BUILDKIT=0 — and someone removes the mounts to make the error go away.

✅ Create a docker-container builder, and pin the syntax directive. One docker buildx create --driver docker-container --use enables multi-platform output, every cache backend, and attestations — the default docker driver supports none of them. Start every Dockerfile with # syntax=docker/dockerfile:1 so features come from the frontend rather than the host's Docker version, which makes builds behave identically across machines and CI images. Remember that a container-driver build needs --push or --load to produce anything outside the builder, and that multi-platform requires --push. Where the target is a compiled language, cross-compile with $BUILDPLATFORM and $TARGETARCH rather than emulating — the difference is measured in Exercise 4.

Interview Questions

Beginner: What is BuildKit and how does it differ from the legacy builder?

BuildKit is Docker's modern build engine, default since Docker 23. The architectural difference is that it builds a dependency graph rather than executing instructions top-to-bottom.

LegacyBuildKit
Serial execution, commit per instructionSolves a DAG
Builds every stageSkips stages the target does not need
No parallelismIndependent stages run concurrently
Uploads the whole context firstFetches context files on demand
No mountscache / secret / ssh / bind mounts
No multi-platformManifest lists in one build

The practical wins are parallel stages, cache mounts that survive between builds without entering layers, and build secrets that never touch a filesystem layer — none of which the legacy builder can express.

Check which one is running from the output: BuildKit prints numbered steps like #1 [internal] load build definition, while the legacy builder starts with Sending build context to Docker daemon.

The legacy builder is still reachable via DOCKER_BUILDKIT=0 and in some older CI images, which matters because a Dockerfile using mounts fails there with a syntax error rather than an unsupported-feature error.

Beginner: What does # syntax=docker/dockerfile:1 do?

It selects the Dockerfile frontend — the parser BuildKit uses — and downloads it at build time. That decouples Dockerfile features from the installed Docker version.

# syntax=docker/dockerfile:1
FROM alpine
RUN --mount=type=cache,target=/var/cache/apk apk add curl

Without the directive, you get whatever the built-in parser supports. With it, an older Docker can still use heredocs, COPY --link, and newer mount options, because the frontend image is fetched during the build.

TagUse
dockerfile:1Latest stable — the usual choice
dockerfile:1.7Pinned, for reproducible builds
dockerfile:1-labsExperimental (COPY --parents, RUN --network)

It explains a common confusion: "this Dockerfile works on my colleague's machine but not mine" is usually a missing syntax directive plus different Docker versions. Adding the line makes both machines use the same parser.

The trade-off is a network fetch of the frontend image on first use, and in regulated environments a floating :1 tag means the parser can change — which is why pinning a minor version is reasonable there.

Mid: Explain the BuildKit mount types and when to use each.
MountPurpose
cachePersist a package cache between builds, never committed
secretExpose a credential to one command, never in a layer
sshForward the SSH agent for private dependencies
bindRead files from another stage or image without a COPY layer

Cache mounts solve the tension between wanting a warm package cache and not wanting it in the image — and crucially they help when the layer cache misses, because the packages are already downloaded:

RUN --mount=type=cache,target=/root/.npm npm ci
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked apt-get update && ...

Secret mounts replace the ARG-plus-rm pattern, which leaves the value in image history or an earlier layer:

RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
$ docker build --secret id=npmrc,src=$HOME/.npmrc .

SSH mounts avoid copying a deploy key into the build at all:

RUN --mount=type=ssh git clone git@github.com:org/private.git
$ docker build --ssh default .

Bind mounts are the least known and useful when you only need to read something during a command — no layer is created, which matters for large inputs used once.

All four require BuildKit and a # syntax= directive for the newer options; under DOCKER_BUILDKIT=0 they are parse errors rather than graceful failures.

Mid: How do you build multi-platform images, and what are the approaches?

One buildx command produces a manifest list covering several architectures:

docker buildx create --name mb --driver docker-container --use
docker buildx build --platform linux/amd64,linux/arm64 -t repo/app:1.0 --push .

--push is required — the local daemon cannot hold a manifest list, so --load fails for multi-platform.

Two mechanisms, with very different costs:

Emulation (QEMU)Cross-compilation
HowRuns foreign binaries via binfmtToolchain runs natively, targets the platform
SpeedVery slow (often 10–20×)Native speed
Works forAnythingGo, Rust, .NET, Java

Cross-compilation is the right default for compiled languages:

FROM --platform=$BUILDPLATFORM golang:1.22 AS build
ARG TARGETOS TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /app .
FROM alpine:3.19
COPY --from=build /app /app

--platform=$BUILDPLATFORM pins the build stage to the native architecture so the compiler never runs under emulation, while $TARGETARCH tells it what to produce.

The third option is native builders — a remote arm64 machine added to the builder — which is what large projects use for interpreted languages where cross-compilation does not apply.

Why it matters at all: a laptop building arm64 by default produces images that fail on amd64 hosts with exec format error, which is silent until deploy.

Senior: Design a CI build pipeline using BuildKit.

The pipeline has to solve four things: cold caches, multi-arch, secrets, and provenance.

docker buildx create --name ci --driver docker-container --use

docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --cache-from type=registry,ref=repo/app:buildcache \
  --cache-to   type=registry,ref=repo/app:buildcache,mode=max \
  --secret id=npmrc,src=$NPMRC_PATH \
  --sbom=true --provenance=mode=max \
  --build-arg VERSION=$GIT_SHA \
  -t repo/app:$GIT_SHA --push .

Why each piece:

  • docker-container driver — the default driver supports neither multi-platform output nor registry cache.
  • mode=max — with multi-stage builds, mode=min exports only final-image layers, omitting exactly the expensive stages.
  • Secrets via --secret — never --build-arg, which is recoverable from image history.
  • SBOM and provenance — so CVE response is a query against stored SBOMs rather than a rescan of every image, and every artefact traces to a commit.
  • Tag by commit SHA, deploy by digest — tags are mutable, so the promotion step should resolve and pin the digest.

Pipeline shape: run --target lint and --target test as parallel jobs sharing the same cache, then build production once and push. Sign with cosign after push, and verify signatures at admission so an unsigned image cannot deploy.

What I would watch: cache hit rate and build duration as CI metrics, because both regress silently; and cache-tag storage growth, since registry cache accumulates and needs retention plus garbage collection.

The failure I would design against explicitly is a runner with DOCKER_BUILDKIT=0 or an old Docker — pin # syntax=docker/dockerfile:1 and assert the builder driver in the pipeline, so a misconfigured runner fails loudly rather than producing a subtly different image.

Senior: Your arm64 builds take 40 minutes and amd64 takes 3. Diagnose and fix.

QEMU emulation. The builder is running arm64 binaries on amd64 hardware through binfmt, which typically costs 10–20× on CPU-bound work — compilation being the worst case.

Confirm it:

$ docker buildx inspect --bootstrap | grep -i platforms
Platforms: linux/amd64, linux/arm64*, linux/arm/v7*
                                   ↑ asterisk = emulated, not native

Fix 1 — cross-compile, if the language allows. This is the biggest win and usually removes the problem entirely:

FROM --platform=$BUILDPLATFORM golang:1.22 AS build
ARG TARGETOS TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /app .

The compiler now runs natively on amd64 and emits an arm64 binary; only the tiny final stage is arm64-specific, and it contains no executed instructions.

Fix 2 — native builders. Add a real arm64 node to the builder so each platform builds on matching hardware:

docker buildx create --name multi --node amd64 --platform linux/amd64
docker buildx create --name multi --append --node arm64 \
  --platform linux/arm64 ssh://builder-arm64

This is the right answer for interpreted languages and anything with native extensions, where cross-compilation is not available. Cloud CI increasingly offers arm64 runners, which makes it cheap.

Fix 3 — reduce emulated work if neither is possible: move as much as possible into a $BUILDPLATFORM stage and copy artefacts forward, so only the unavoidable steps run emulated.

What I would not do is drop arm64 support to make CI fast, or build the two architectures in separate pipelines pushing separate tags — that reintroduces the exec format error class of failure and loses the single-tag manifest list that makes multi-arch transparent to deployers.

Solution 
$ mkdir -p /tmp/heredoc && cd /tmp/heredoc

# the traditional chained form
$ cat > D.chained <<'OUTER'
FROM debian:12-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl jq \
 && rm -rf /var/lib/apt/lists/* \
 && echo "done"
OUTER

# heredoc form — needs the syntax directive
$ cat > D.heredoc <<'OUTER'
# syntax=docker/dockerfile:1
FROM debian:12-slim
RUN <<EOF
set -eux
apt-get update
apt-get install -y --no-install-recommends curl jq
rm -rf /var/lib/apt/lists/*
echo "done"

OUTER

$ docker build -q -t hd:chained -f D.chained . >/dev/null
$ docker build -q -t hd:heredoc -f D.heredoc . >/dev/null
$ docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}' | grep '^hd:'
hd:chained   96.4MB
hd:heredoc   96.4MB      ← identical: still ONE layer

Confirm both are a single layer:

$ for t in chained heredoc; do
    printf "%-8s layers: %s\n" "$t" "$(docker image inspect hd:$t --format '{{len .RootFS.Layers}}')"
  done
chained  layers: 2
heredoc  layers: 2

The difference is error handling. With set -eux the script stops on the first failure and echoes each command; the chained form relies on && and is easy to break with a stray ;:

$ cat > D.bug <<'OUTER'
FROM debian:12-slim
RUN apt-get update \
 ; apt-get install -y nonexistent-package-xyz \
 ; echo "this still runs"
OUTER
$ docker build -q -t hd:bug -f D.bug . >/dev/null 2>&1 && echo "build SUCCEEDED despite failure"
build SUCCEEDED despite failure     ← the ; swallowed the error

$ cat > D.safe <<'OUTER'
# syntax=docker/dockerfile:1
FROM debian:12-slim
RUN <<EOF
set -eux
apt-get update
apt-get install -y nonexistent-package-xyz
echo "this should NOT run"
EOF
OUTER
$ docker build -q -t hd:safe -f D.safe . 2>&1 | tail -1
ERROR: process "/bin/sh -c ..." did not complete successfully: exit code: 100
$ echo "exit: $?"
exit: 1                             ← failed correctly

$ docker run --rm hd:file cat /etc/myapp.conf

SSH forwarding for a private dependency:

$ cat > D.ssh <<'EOF'
# syntax=docker/dockerfile:1
FROM alpine:3.19

$ docker build -q --ssh default -t sec:ssh -f D.ssh . >/dev/null

total 12
-rw-------    1 root  root   142 known_hosts     ← no private key present

The agent was forwarded for that one command; no key was ever copied into the build context or a layer.

🎯 Key Takeaways

  • BuildKit solves a dependency graph rather than running a script — measured 18.9 s legacy vs 6.4 s for the same Dockerfile.
  • Two separate effects: independent stages ran in parallel, and a stage nothing depended on was never built at all.
  • Identify the builder from output: #1 [internal] load build definition is BuildKit; Sending build context to Docker daemon is legacy.
  • Mounts fail under DOCKER_BUILDKIT=0 with Unknown flag: mount — a parse error that reads like a typo.
  • # syntax=docker/dockerfile:1 decouples features from your Docker version, because the frontend is fetched at build time.
  • Heredocs are still one layer but add real error handling — a ;-chained RUN succeeded despite a failed install, while set -eux failed correctly.
  • Four mount types: cache (persist between builds), secret (never in a layer), ssh (no key copied), bind (read without creating a layer).
  • Verified: a --build-arg token appeared in docker history; the same value via --mount=type=secret appeared in neither history nor any layer.
  • Multi-platform requires --push — the local daemon cannot hold a manifest list, so --load fails.
  • Cross-compilation beat QEMU emulation 15.4× (14.8 s vs 227 s) for an arm64 Go build.
  • The key line is FROM --platform=$BUILDPLATFORM on the build stage — without it the toolchain runs emulated whatever GOARCH says.
  • An asterisk in buildx inspect's platform list marks emulated platforms.
  • The default docker driver supports neither multi-platform nor registry cache, failing with messages that blame the exporter rather than the driver.
  • docker-container is the practical default; without --load or --push a build produces nothing usable.
  • --sbom=true records every package and version, turning CVE response into a query rather than a rescan of every image.
  • --provenance=mode=max records builder, source and materials — including the exact base image, so a compromised base is traceable.
  • In CI: docker-container driver, registry cache with mode=max, secrets via --secret, attestations on, tag by SHA and deploy by digest.
  • Pin the frontend version (dockerfile:1.7) where builds must be reproducible, since :1 can change.
