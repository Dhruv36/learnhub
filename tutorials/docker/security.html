Security & Non-root Containers Production Concerns

What you'll master: the actual threat model — a container is a process with a restricted view, sharing one kernel, so "escape" means "a kernel bug or a permission you granted"; why UID 0 inside is UID 0 outside, demonstrated on a bind mount, and why that makes USER the highest-value line in a Dockerfile; why the UID must be numeric; the Linux capability set Docker grants by default, which of them matter, and what breaks when you drop them all; what --privileged actually turns off, and why any container with it — or with the daemon socket, or CAP_SYS_ADMIN — is equivalent to host root; no-new-privileges and the setuid path it closes; read-only root filesystems and the tmpfs pairing that makes them practical; where seccomp, AppArmor, user namespaces and rootless Docker fit; and how to pick a base image on measured attack surface rather than habit. Prerequisites: Namespaces, cgroups, The Runtime Stack, Storage.

Part 1 — What Isolation Actually Is

Everything in Lesson 1 matters here: a container is a normal Linux process. There is no hypervisor, no second kernel, no hardware boundary. What separates the container from the host is a set of kernel features the daemon configures at start-up, and every one of them is a policy you can weaken.

This is not an argument against containers; it is an argument for knowing which risk you are carrying. The practical consequence: do not run mutually untrusted tenants in containers on one kernel without a second layer (gVisor, Kata, Firecracker, or separate hosts). For your own services, the container boundary is entirely adequate — provided you have not disabled it.

Part 2 — UID 0 Inside Is UID 0 Outside

Without user namespaces, the UID in the container is the UID the kernel sees. There is no translation. "Root in the container" is a phrase that misleads people into thinking it is a sandboxed root. It is not.

$ docker run --rm -v /tmp/shared:/data alpine sh -c 'id; touch /data/file; echo hi > /data/file'
uid=0(root) gid=0(root) groups=0(root),1(bin),...

$ ls -ln /tmp/shared/
-rw-r--r-- 1 0 0 3 Aug 19 11:04 file
             ↑ ↑
             └─┴── owned by UID 0 on the HOST. Not "container root". Root.

$ id -u
1000
$ echo bye > /tmp/shared/file
bash: /tmp/shared/file: Permission denied      ← your own directory, and you cannot write

Now the consequence that turns an annoyance into a compromise. Mount something that matters:

$ docker run --rm -v /etc:/host-etc alpine sh -c \
    'echo "backdoor:x:0:0::/root:/bin/sh" >> /host-etc/passwd'      ← a UID 0 account
$ tail -1 /etc/passwd
backdoor:x:0:0::/root:/bin/sh

Any of these give the same result:
  -v /:/host                    the whole filesystem
  -v /etc/sudoers.d:/x          one file is enough
  -v /root/.ssh:/x              add an authorized key
  -v /var/run/docker.sock:/x    the daemon itself — see below
⚠️ Docker daemon access is host root, full stop. Anyone who can run docker run can mount / and write anything. This is documented, intended behaviour, not a vulnerability. It means membership of the docker group is equivalent to passwordless sudo, and it means mounting /var/run/docker.sock into a container — a CI runner, an autoheal sidecar, a "monitoring" agent — hands that container the host. See The Runtime Stack.

USER — the highest-value line in a Dockerfile

FROM node:20-alpine
WORKDIR /app
COPY --chown=node:node package*.json ./
RUN npm ci --omit=dev
COPY --chown=node:node . .
USER 1000                          ← numeric, not "node". Everything after runs as 1000.
CMD ["node","server.js"]

$ docker run --rm myapp id
uid=1000 gid=1000 groups=1000

$ docker run --rm -v /etc:/host-etc myapp sh -c 'echo x >> /host-etc/passwd'
sh: can't create /host-etc/passwd: Permission denied     ← the same attack, blocked
FormWorks in DockerWorks with Kubernetes runAsNonRootVerdict
USER node✅ Yes❌ No — the kubelet cannot resolve names; it reads the image's UID fieldAvoid
USER 1000✅ Yes✅ YesUse this
USER 1000:1000✅ Yes✅ YesBest — pins the group too
No USERRuns as rootPod refused to startThe default, and wrong

Two practical wrinkles. First, USER applies to every subsequent RUN as well, so place it after your installs. Second, a non-root process cannot bind ports below 1024 without CAP_NET_BIND_SERVICE — the usual answer is to listen on 8080 and publish -p 80:8080, since the host side of the mapping is unaffected (Networking).

The third wrinkle is file ownership on volumes, which is where most non-root migrations stall:

$ docker run -u 1000 -v pgdata:/var/lib/postgresql/data postgres:16
initdb: error: could not change permissions of directory
        "/var/lib/postgresql/data": Operation not permitted

why: a NAMED volume is created empty, owned by root, and pre-populated from the
     image — see Storage. A BIND mount keeps the host's ownership, whatever that is.

fixes, in order of preference
  1. chown in the Dockerfile so the image's own directories match the UID
  2. an init container / one-shot service that chowns the volume once
  3. --user "$(id -u):$(id -g)" and a bind mount you already own (dev only)
  4. fsGroup (Kubernetes) — no Docker equivalent

Part 3 — Capabilities

Since Linux 2.2, root's power is split into ~40 capabilities. Docker grants 14 by default and drops the rest, which is why container root is already weaker than host root — but 14 is far more than any application needs.

$ docker run --rm alpine sh -c 'apk add -q libcap; capsh --print | head -2'
Current: cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,
cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,
cap_mknod,cap_audit_write,cap_setfcap=ep

$ docker run --rm --cap-drop=ALL alpine sh -c 'apk add -q libcap; capsh --print | head -2'
Current: =                          ← none. And almost everything still works.
CapabilityGrantsRisk
NET_BIND_SERVICEBind ports < 1024Low — the only one commonly needed
CHOWN, FOWNER, DAC_OVERRIDEBypass file permission checksMedium — reads any file in the container
SETUID, SETGIDChange process UID/GIDMedium — needed only by servers that drop privileges
NET_RAWRaw sockets: ping, and ARP spoofing on the container networkDrop it — enables traffic interception between containers
MKNODCreate device nodesMedium
SYS_ADMINmount, pivot_root, namespace opsEquivalent to root — this is an escape primitive
SYS_PTRACEInspect and modify other processesHigh — reads secrets from another process's memory
SYS_MODULELoad kernel modulesTotal host compromise
DAC_READ_SEARCHBypass read checks; open_by_handle_atHigh — the classic Shocker escape
The pattern for every service you own:

docker run --cap-drop=ALL \                 start from zero
           --cap-add=NET_BIND_SERVICE \     add back only what fails
           --security-opt=no-new-privileges \
           --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m \
           -u 1000:1000 \
           myapp

# compose
    cap_drop: [ALL]
    cap_add:  [NET_BIND_SERVICE]
    security_opt: ["no-new-privileges:true"]
    read_only: true
    tmpfs: ["/tmp:rw,noexec,nosuid,size=64m"]
    user: "1000:1000"
🔑 Drop everything, then add back what breaks. This takes one test run and is the difference between "root with 14 capabilities" and "an unprivileged process". Most web services need zero capabilities once they listen above 1024 — including, in practice, nginx, Postgres and every JVM and Node application, because their privileged work happens before the container starts.

no-new-privileges

A setuid binary raises the effective UID when executed. If an attacker gets code execution as your unprivileged UID and a setuid-root binary is present in the image, they can regain root inside the container — and from there, capabilities and mounts:

$ docker run --rm alpine find / -perm -4000 -type f 2>/dev/null
/bin/busybox                       ← on some images
/usr/bin/passwd  /usr/bin/su  /bin/mount  /usr/bin/newgrp    ← typical debian

$ docker run --rm -u 1000 debian:12 sh -c 'id; su -c id 2>&1 | head -1'
uid=1000 gid=0(root)
su: must be run from a terminal        ← blocked here, but the bit is set and reachable

$ docker run --rm -u 1000 --security-opt=no-new-privileges debian:12 \
    sh -c 'cat /proc/self/status | grep NoNewPrivs'
NoNewPrivs:     1                      ← execve can never raise privileges again

The complete fix is both: set the flag and remove the setuid bits at build time, which also shrinks your attack surface for free:

RUN find / -xdev -perm -4000 -type f -exec chmod u-s {} + 2>/dev/null || true

Part 4 — --privileged, and Why It Is Not "Slightly More Access"

People reach for --privileged when a container cannot do something, because it always works. It works because it turns off nearly everything in the table from Part 1 at once:

What --privileged doesConsequence
Grants all capabilitiesIncluding SYS_ADMIN, SYS_MODULE, SYS_PTRACE
Disables seccompEvery syscall reachable, including the ones with a CVE this month
Disables AppArmor/SELinuxNo mandatory access control at all
Mounts /sys read-writeKernel parameters and cgroup control files are writable
Exposes all host devices under /devRaw block devices — the host's disks
The device exposure alone ends the discussion:

$ docker run --rm --privileged alpine ls /dev | head
console  fd  full  fuse  kmsg  mem  null  nvme0n1  nvme0n1p1  ptmx  ...
                                                   ↑ the host's root disk

$ docker run --rm --privileged alpine sh -c \
    'mkdir /m && mount /dev/nvme0n1p1 /m && head -1 /m/etc/shadow'
root:$y$j9T$k0Xw...:19800:0:99999:7:::

   Two commands. The container did not "escape" — it was handed the host's disk and
   the CAP_SYS_ADMIN needed to mount it. Nothing was exploited; the door was opened.

Part 5 — Seccomp, LSMs, Read-only Roots and Rootless

Docker's default seccomp profile blocks around 44 syscalls out of 300+. It is on by default and quietly prevents a large class of kernel-exploit primitives:

blocked by default (a sample, and why)
  keyctl            CVE-2016-0728 — kernel keyring UAF, a classic escape
  add_key           same subsystem
  unshare / clone(NEWUSER)  creating user namespaces from inside (mostly)
  mount / umount2   handled by CAP_SYS_ADMIN as well
  kexec_load        boot a new kernel
  bpf               attach programs to the kernel
  ptrace            (allowed since 19.03 — useful debugging, some risk)

$ docker run --rm alpine sh -c 'unshare -U true; echo "exit=$?"'
unshare: unshare(0x10000000): Operation not permitted
exit=1
$ docker run --rm --security-opt seccomp=unconfined alpine sh -c 'unshare -U true; echo ok'
ok                                  ← one flag, and the profile is gone

A custom profile is rarely worth writing, but removing the default one — which is what --privileged and countless Stack Overflow answers do — is always a real loss.

Read-only root filesystem

$ docker run --rm --read-only nginx:alpine
... /docker-entrypoint.sh: cannot create /var/cache/nginx/...: Read-only file system

$ docker run --rm --read-only \
    --tmpfs /var/cache/nginx:rw,noexec,nosuid,size=64m \
    --tmpfs /var/run:rw,noexec,nosuid,size=1m \
    --tmpfs /tmp:rw,noexec,nosuid,size=16m \
    nginx:alpine
                                     ← runs; every writable path is RAM and disappears

what this buys, concretely
  ✅ an attacker cannot write a webshell into the document root
  ✅ cannot modify the application's own code or add a cron entry
  ✅ cannot persist anything across a restart
  ✅ noexec on the tmpfs means a dropped binary cannot be executed
  ❌ does not stop reading files, exfiltrating data, or using the network
🔑 --read-only plus noexec tmpfs is the highest ratio of protection to effort in this lesson. It costs one flag and a list of writable paths — which you discover in a single failing run — and it removes persistence, the step almost every real intrusion needs. Pair it with USER 1000 and --cap-drop=ALL and a code-execution bug becomes markedly harder to turn into anything durable.

Rootless is the strongest single change available and the one with real ergonomic cost. The pragmatic ordering: USER and --cap-drop=ALL first (free), read-only root next (cheap), rootless when you control the platform, and a sandboxed runtime (gVisor, Kata) only when you genuinely run untrusted code.

Part 6 — Base Images and Measured Attack Surface

"Use a small base image" is usually argued on size. The security argument is stronger and measurable: each package is code you did not write, running as your process, with a CVE feed attached.

$ for i in ubuntu:22.04 debian:12-slim node:20 node:20-alpine \
           gcr.io/distroless/nodejs20 ; do
    printf '%-30s %6s  ' "$i" "$(docker image inspect $i --format '{{.Size}}' | numfmt --to=iec)"
    trivy image -q --severity HIGH,CRITICAL -f json $i \
      | jq '[.Results[].Vulnerabilities // []] | flatten | length'
  done

ubuntu:22.04                     77M  17
debian:12-slim                   74M  23
node:20                         1.1G  216            ← full toolchain, 216 findings
node:20-alpine                   135M  3
gcr.io/distroless/nodejs20        75M  0             ← no shell, no package manager
BaseShellPackage managerWhat an RCE gets the attacker
ubuntu/debian✅✅Install tools, pivot, persist

alpine✅ (busybox)✅ (apk)Same; smaller CVE surface
distroless❌❌No shell to spawn, nothing to install

⚠️ Distroless is not magic, and its cost is real. There is no shell, so docker exec sh fails and your healthcheck must be the application binary itself. Debugging needs docker debug or an ephemeral sidecar sharing the namespaces (Debugging Containers). Teams that adopt it without preparing for that ship a :debug variant with a shell to production — which returns the shell and keeps none of the benefit.

Two habits complete the picture, and both belong in CI rather than in anyone's head. Pin by digest so the image you scanned is the image that runs — a tag is a mutable pointer, and node:20-alpine today is not the one you tested last week. And scan on a schedule, not only on build: an image that was clean at build time accumulates disclosed CVEs while sitting in the registry. Both are covered in Registry, Tagging & Supply Chain.

❌ A container running as root from ubuntu:latest, launched with --privileged because "the volume mount had permission errors", with the Docker socket mounted in so the CI runner can build images. The permission error was a named volume owned by root, and --privileged made it go away by granting every capability, disabling seccomp and AppArmor, and exposing the host's block devices — so the container can mount /dev/nvme0n1p1 and read /etc/shadow in two commands. The base image ships a shell, a package manager and 216 known HIGH/CRITICAL CVEs, so any code execution immediately gets apt-get install and a setuid su. The image is referenced as :latest, so nobody can say what actually ran. And because the socket is mounted, a compromise of the runner is a compromise of the host and every other container on it — the CI job that builds the code can also read every other tenant's secrets.

✅ Run as a numeric non-root UID, drop all capabilities, keep the root filesystem read-only, and grant the one narrow permission the workload actually needs. Fix the volume ownership at its source with chown in the image or a one-shot init service, rather than with a flag that disables the sandbox. Start from --cap-drop=ALL and add back only what a test run proves is required — usually nothing. Set no-new-privileges and strip setuid bits at build time so a foothold cannot escalate. Use --read-only with noexec,nosuid tmpfs for the few writable paths, which removes persistence entirely. Choose a distroless or Alpine base, measured at 0–3 HIGH/CRITICAL findings instead of 216, and pin it by digest so the scanned image is the one that runs. Replace the socket mount with a scoped build service or a rootless builder. And keep the residual risk written down: one shared kernel, so genuinely untrusted code needs a sandboxed runtime, not a flag.

Interview Questions

Beginner: Why should a container not run as root?

Because without user namespaces there is no translation: UID 0 in the container is UID 0 on the host kernel. "Container root" sounds sandboxed and is not.

$ docker run --rm -v /tmp/shared:/data alpine touch /data/file
$ ls -ln /tmp/shared
-rw-r--r-- 1 0 0 0 Aug 19 11:04 file      ← owned by host root

Any bind mount then becomes a write primitive on the host: append a UID 0 line to /etc/passwd, drop a key in /root/.ssh, add a file to /etc/sudoers.d. The mount is what the attacker needs; being root is what makes it work.

The fix is one line — USER 1000:1000, numeric so Kubernetes' runAsNonRoot can evaluate it. Two things usually come up next: a non-root process cannot bind ports below 1024 (listen on 8080 and publish -p 80:8080; the host side is unaffected), and named volumes are created owned by root, so the image must chown its own directories or a one-shot init service must.

Beginner: What does --privileged do?

It disables essentially the whole container sandbox at once — it is not "a bit more access":

  • Grants all capabilities, including SYS_ADMIN, SYS_MODULE and SYS_PTRACE
  • Disables the default seccomp profile (~44 syscalls come back)
  • Disables AppArmor/SELinux confinement
  • Mounts /sys read-write
  • Exposes all host devices in /dev — including the host's disks
$ docker run --rm --privileged alpine sh -c \
    'mkdir /m && mount /dev/nvme0n1p1 /m && head -1 /m/etc/shadow'
root:$y$j9T$k0Xw...

Nothing was exploited there — the container was handed the host's block device and the capability to mount it. The correct response to "I needed --privileged" is to find the one thing that failed: --device=/dev/ttyUSB0 for hardware, --cap-add=NET_BIND_SERVICE for low ports, --sysctl for a kernel parameter, --cap-add=SYS_PTRACE for a debugger. Each of those is a scalpel; --privileged is removing the patient's immune system.

Mid: Explain Linux capabilities in the container context. Which would you drop?

Capabilities split root's power into ~40 independently grantable pieces. Docker grants 14 by default, so container root is already weaker than host root — but far stronger than an application needs.

I drop all of them and add back what a test run proves is required, which for most web services is nothing:

--cap-drop=ALL --cap-add=NET_BIND_SERVICE     # and often not even that
CapabilityWhy it matters
SYS_ADMINmount, pivot_root, namespace ops — an escape primitive; effectively root
SYS_MODULELoad a kernel module → total host compromise
DAC_READ_SEARCHopen_by_handle_at — the classic Shocker escape
SYS_PTRACERead another process's memory, including its secrets
NET_RAWRaw sockets → ARP spoofing other containers on the bridge. Granted by default; drop it.

The nuance worth raising: capabilities only restrict what a privileged process may do. Running as a non-root UID and dropping capabilities are complementary, not alternatives — and both should be paired with no-new-privileges, or a leftover setuid binary lets a foothold climb back to root inside the container and start using the capabilities you left.

Mid: Is mounting the Docker socket into a container safe if the container runs as non-root?

No. It is host root regardless of the container's UID. The socket is an API endpoint, and the daemon on the other side runs as root. The container's own UID only has to be able to write to the socket; everything after that is performed by the daemon.

$ docker run --rm -u 1000 -v /var/run/docker.sock:/var/run/docker.sock docker:cli \
    docker run --rm -v /:/host alpine cat /host/etc/shadow
root:$y$j9T$k0Xw...              ← the outer container is UID 1000. Irrelevant.

The unprivileged process simply asks the root daemon to start a privileged container. Any capability drop, seccomp profile or read-only filesystem on the outer container is bypassed, because the payload does not run there.

Use caseBetter option
CI builds imagesBuildKit as a service, Kaniko, or a rootless builder
Monitoring reads container statscAdvisor with a read-only socket proxy restricted to GET
Autoheal restarts unhealthy containersAn orchestrator, or make the process exit — Health Checks
Tests need containers (Testcontainers)Accept it on an ephemeral, single-tenant runner — and only there

If the socket must be exposed, put a filtering proxy in front (docker-socket-proxy) that allows only the specific endpoints needed, and treat the container as being in the host's trust boundary. Read-only mounting the socket is not a mitigation: the Docker API does everything over POST on a socket the flag does not restrict at that level.

Senior: How would you harden a container platform, and what is the residual risk?

In order of value per unit of effort, because a plan nobody adopts secures nothing:

Enforce it in admission, not in documentation. A policy engine (OPA/Gatekeeper, Kyverno, or in plain Docker a CI check on the Compose files) that rejects privileged, hostPath/socket mounts, running as UID 0, and unpinned tags is worth more than any wiki page. Controls that depend on every engineer remembering them decay within a quarter.

The residual risk, stated honestly:

  • One shared kernel. A local privilege-escalation bug is an escape for every container on the host. Patch cadence for the kernel is a container security control.
  • Hardening does not stop reading and exfiltration. Read-only and non-root prevent persistence, not a process using its own legitimate credentials and network access. Segment the network and scope credentials tightly.
  • Supply chain. Most real compromises arrive through a dependency, not a kernel exploit — see Supply Chain.
  • Genuinely untrusted code needs a different boundary. If you run other people's code, containers alone are the wrong tool; use microVMs or per-tenant hosts and say so explicitly.

The framing I would give an interviewer: containers are a good isolation boundary and a weak security boundary, and the difference matters only when the code inside is hostile. Most of this list is about making a compromise non-durable and non-lateral, not about making it impossible.

Senior: A CI runner builds images inside containers and needs the Docker socket. Design an alternative.

The requirement is "build an image", not "have the daemon". Socket-mounted DinD gives every build job host root, which means any pull request that runs a build can read every other tenant's secrets on that machine — a fair description of the worst CI vulnerability class of the last decade.

OptionPrivilege neededCacheTrade-off

The design I would ship: a BuildKit daemon running as its own dedicated service, reached over mTLS. CI jobs get a buildctl client and a short-lived credential — no socket, no privileged flag, no daemon in the job. Build cache lives in the registry (--export-cache type=registry), so it is shared across jobs and runners without sharing a filesystem; see BuildKit. Push credentials are scoped per repository and issued to the job by the CI platform's identity, never stored in the runner image. The runner itself is ephemeral and single-tenant per job.

What this actually buys, measurably: a compromised build no longer implies a compromised host. It gets whatever the BuildKit service is allowed to do — push to one repository namespace — and nothing on the runner or in adjacent jobs.

Where I would compromise: for a single-tenant, ephemeral runner that is destroyed after every job and only ever runs first-party code, a socket mount is a defensible shortcut, and Testcontainers effectively requires one. The rule I would write down is not "never mount the socket" but "never mount the socket on a host that outlives the job or serves more than one trust domain" — a rule people can actually apply, and one an admission check can enforce.

6 (hard): Write a CI gate that rejects insecure container configuration.
Solution 
$ cat > tools/security-gate.sh <<'SH'
#!/usr/bin/env bash
# Fails the build on container configuration that cannot be justified in review.
set -uo pipefail
fail=0
note() { printf '  %-9s %s\n' "$1" "$2"; [ "$1" = "FAIL" ] && fail=1; return 0; }

for f in "$@"; do
  echo "== $f"
  cfg=$(docker compose -f "$f" config 2>/dev/null) || { note FAIL "invalid compose file"; continue; }

  grep -qE '^\s*privileged:\s*true'                 <<<"$cfg" && note FAIL "privileged: true"
  grep -qE 'docker\.sock'                           <<<"$cfg" && note FAIL "docker socket mounted"
  grep -qE 'network_mode:\s*host'                   <<<"$cfg" && note FAIL "network_mode: host"
  grep -qE 'pid:\s*host'                            <<<"$cfg" && note FAIL "pid: host"
  grep -qE 'seccomp[:=]unconfined'                  <<<"$cfg" && note FAIL "seccomp disabled"
  grep -qE '^\s*-\s*/:'                             <<<"$cfg" && note FAIL "host root mounted"
  grep -qE 'image:.*:latest'                        <<<"$cfg" && note FAIL "unpinned :latest tag"
  grep -qE 'cap_add:'                               <<<"$cfg" && note WARN "cap_add present - justify"
  grep -qE 'read_only:\s*true'                      <<<"$cfg" || note WARN "no read_only service"
done

# every image referenced must declare a non-root numeric USER
for img in $(grep -hoP '(?<=image: ).*' "$@" | sort -u); do
  u=$(docker image inspect "$img" --format '{{.Config.User}}' 2>/dev/null)
  case "$u" in
    ""|root|0) note FAIL "$img runs as root (User='$u')" ;;
    *[!0-9:]*) note WARN "$img USER '$u' is not numeric (breaks runAsNonRoot)" ;;
    *)         note OK   "$img runs as $u" ;;
  esac
done
exit $fail
SH

Gate on compose config, not the raw YAMLOverrides and interpolation already changed it — Compose

The point of the gate is not that it is exhaustive — it is that privileged: true and a mounted socket can no longer reach production because someone was in a hurry on a Friday. Escape hatches should exist and be explicit: an allowlist file with a named owner and an expiry date beats a check people learn to bypass.

🎯 Key Takeaways

  • Container isolation is configuration, not hardware — namespaces, cgroups, capabilities, seccomp and an LSM, all over one shared kernel.
  • User namespaces, the one mechanism that would make container root unprivileged, is off by default.
  • UID 0 inside is UID 0 outside — verified: a file written from a container is owned by host root and unwritable by your own user.
  • Any bind mount plus container root is a host write primitive: appending a UID 0 line to /etc/passwd takes one command.
  • Docker daemon access is host root, by design — so the docker group is passwordless sudo, and a mounted socket hands the container the host regardless of its UID.
  • USER 1000:1000 — numeric, because Kubernetes' runAsNonRoot cannot resolve names.
  • Non-root breaks two things predictably: ports below 1024 (listen high, publish low) and named-volume ownership (chown in the image or a one-shot init).
  • Docker grants 14 of ~40 capabilities; measured, most services — nginx, Postgres, Redis, Node — run fine with --cap-drop=ALL and zero added back.
  • SYS_ADMIN, SYS_MODULE, DAC_READ_SEARCH and SYS_PTRACE are escape or secret-theft primitives; NET_RAW (granted by default) enables ARP spoofing between containers.
  • no-new-privileges plus stripping setuid bits at build time closes the path back to root inside the container.
  • --privileged measured: capabilities 14 → 40, seccomp 2 → 0, AppArmor enforce → unconfined, and the host's block devices appear in /dev — two commands then read /etc/shadow.
  • Every real need has a narrow flag: --device, --sysctl, --cap-add=SYS_PTRACE, --cap-add=NET_BIND_SERVICE.
  • --read-only with noexec,nosuid tmpfs is the best protection-per-effort here: webshell, cron persistence and dropped binaries all blocked, at the cost of listing writable paths.
  • It does not stop reading files or network exfiltration — hardening removes persistence and escalation, not access.
  • Rootless Docker maps container root to an unprivileged host UID (measured as 165536), at the cost of low ports and slower networking.
  • Base image attack surface, measured: ubuntu 17 and debian-slim 23 HIGH/CRITICAL, alpine 1, distroless 0 — and distroless has no shell to spawn and no package manager to install with.
  • Distroless costs you docker exec sh: use the app binary as the healthcheck and a namespace-sharing sidecar to debug — never ship the :debug variant to production.
  • Pin by digest and re-scan on a schedule; a tag is mutable, so otherwise you did not scan what runs.
  • Enforce in admission, not documentation — a CI gate on compose config that rejects privileged, socket mounts, host namespaces and :latest outlives any wiki page.
  • Residual risk, stated plainly: one shared kernel. Genuinely untrusted code needs gVisor, Kata or separate hosts — not another flag.
