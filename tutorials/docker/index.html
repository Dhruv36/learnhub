What a Container Actually Is Foundations

What you'll master: the single most important correction in this whole track — a container is not a lightweight VM, it is an ordinary Linux process with three kernel features applied to it, and almost every container misconception dissolves once you can see that; the three primitives (namespaces, cgroups, union filesystem) and which problem each one solves; why ps on the host shows your "isolated" container processes with normal PIDs; what the shared kernel means for security and for the "it works on my machine" promise, including the case where a container genuinely does not run everywhere; why containers start in milliseconds when VMs take tens of seconds, expressed as what each one actually has to do; and the honest list of when a VM is the right answer instead.

Part 1 — A Container Is a Process

Run a container and look at the host process table. The processes are simply there.

$ docker run -d --name web nginx
$ ps -ef | grep nginx
root      48213  48190  0 14:02 ?  00:00:00 nginx: master process nginx -g daemon off;
systemd+  48260  48213  0 14:02 ?  00:00:00 nginx: worker process
           ↑ an ordinary host PID, visible from the host, killable from the host
🔑 There is no "container" object in the Linux kernel. The kernel has no container type, no container system call, and no container process class. What Docker does is start a normal process with three kernel features configured: namespaces so it sees a restricted view of the system, cgroups so it can only consume a bounded share of resources, and a union filesystem so its root directory is assembled from stacked image layers. Remove those three and you have an ordinary process — which is exactly what it was all along.

PrimitiveAnswersWithout it
NamespacesWhat can this process see?It sees every process, mount, and network interface on the host
cgroupsWhat can this process use?One container can consume all CPU and RAM on the host
Union filesystemWhat files does it have?Every image would be a full copy of an OS filesystem

The consequence people find most surprising: from the host you can inspect, signal, and kill container processes with ordinary tools, because they are ordinary processes.

$ docker exec web ps aux
PID   USER     COMMAND
    1 root     nginx: master process nginx -g daemon off;   ← PID 1 INSIDE
   29 nginx    nginx: worker process

$ ps -ef | grep 48213                                       ← the SAME process
root      48213  48190  0 14:02 ?  nginx: master process
          ↑ PID 48213 on the host

$ sudo kill -9 48213      # kills the container's main process → container stops

Two numbers for one process. Inside its PID namespace it is process 1; on the host it is 48213. That is not a translation layer or a virtual machine — it is the same kernel task with two views of its own identity.

Part 3 — What "Shares the Kernel" Actually Costs

The shared kernel is what makes containers fast, and it is simultaneously their central limitation. Both consequences are worth stating precisely, because interviews probe exactly here.

🔑 A kernel vulnerability that allows privilege escalation is a container escape. There is no second boundary underneath. With a VM, an attacker who gets root in the guest still faces the hypervisor; with a container, root plus a kernel bug is root on the host, and therefore on every other container on that host. This is why "containers provide isolation" is true in the resource sense and dangerously imprecise in the security sense — and why untrusted multi-tenant workloads use VMs, or VM-backed sandboxes like Firecracker and gVisor.

The second consequence is portability, and it has a specific exception. "Build once, run anywhere" holds because the image carries the userland — libraries, binaries, config — so the mismatch that used to break deployments is packaged away. What it does not carry is a kernel:

✅ Linux container on any Linux host with a compatible kernel   — the normal case
✅ Linux container on macOS/Windows                             — via a hidden Linux VM
❌ Linux container on a Windows kernel directly                 — impossible
❌ Windows container on a Linux host                            — impossible
⚠️ arm64 image on an amd64 host                                 — needs emulation, or a multi-arch image

Docker Desktop runs a Linux VM. On macOS and Windows, containers are not running on your machine's kernel — they run inside a virtual machine that Docker manages for you. That is why file sharing between host and container is slower there, and why "it works on my Mac" still means "it worked inside a Linux VM on my Mac".

SymptomCause
Image runs on your Mac, fails on the serverarm64 image (Apple Silicon) on an amd64 host
Slow file I/O on macOS bind mountsCrossing the VM boundary
A syscall works locally, fails in productionDifferent host kernel version, or a seccomp profile
Container sees the host's CPU countcgroup limits are not visible to older runtimes and JVMs

Part 4 — Images vs Containers

The distinction is small and causes a large fraction of beginner confusion.

IMAGE                                CONTAINER
read-only, immutable, layered   →    a running (or stopped) instance of an image
a recipe / a class                   a process / an object
built once, pushed to a registry     created, started, stopped, removed
shared by every container from it    has its own thin writable layer

$ docker run nginx     # ← creates a NEW container from the nginx image
$ docker run nginx     # ← another one, same image, separate writable layer

$ docker ps -a         # containers
$ docker images        # images

Every container gets a thin writable layer on top of the image's read-only layers. Writes go there, not into the image — which is why changes made inside a running container disappear when you remove it, and why docker run twice gives you two independent filesystems from one image.

🔑 Containers are designed to be disposable, and the writable layer is the reason treating them otherwise fails. Data written inside a container is destroyed with it, so anything that must survive belongs in a volume or an external service. This constraint is what makes containers safe to replace on every deploy — and it is the one that catches teams who docker exec into production to fix something, because the fix vanishes at the next restart.

Stopped containers keep their writable layer and keep consuming disk until removed — docker ps hides them, so docker ps -a is what shows the accumulation. Systems that run containers on a schedule without --rm fill their disks with dead containers slowly enough that nobody notices until a deploy fails.

Part 6 — When Not to Use a Container

Containers are the default for server workloads, and defaulting to them uncritically produces bad architectures. The honest exceptions:

SituationWhy a container is wrongUse
Untrusted multi-tenant codeShared kernel — an escape reaches every tenantVMs, Firecracker, gVisor
You need a different OS kernelImpossible by constructionA VM
Direct/exotic hardware accessDevice passthrough is awkward and privilegedBare metal or a VM
Desktop GUI applicationsPossible but painful; no real benefitNative install
A stateful database you must operate yourselfWorks, but storage and failover dominate the designManaged service, or careful orchestration
A single-binary Go/Rust CLIThe binary is already portableJust ship the binary

That last row is worth internalising: containerising a statically linked binary adds a registry, a build pipeline, and a runtime dependency to solve a problem the binary did not have. The value of a container is packaging a userland — interpreters, shared libraries, system packages — so the less userland a program needs, the less a container buys you.

❌ Treating a container as a small virtual machine. The mental model is "a tiny computer", so the team SSHes in with docker exec to fix things, installs packages at runtime, writes application data into the container filesystem, runs several services in one container with an init system to supervise them, and expects the isolation to be a security boundary. Every one of those fails in a way the VM model cannot predict: the runtime fix vanishes at the next deploy because the writable layer is destroyed, the data disappears with it, docker logs is empty because the app logs to a file, the container reports healthy while the crashed service inside it is unsupervised, and a kernel-level escape reaches every tenant on the host because there is no hypervisor underneath.

✅ Treat a container as a process with three kernel features applied. It has a restricted view (namespaces), a resource budget (cgroups), and a filesystem assembled from image layers — nothing more. So: bake changes into the image and redeploy rather than execing fixes; put persistent data in a volume or an external service because the writable layer is disposable by design; log to stdout/stderr so the runtime can collect it; run one main process per container so the runtime can actually see it fail; and treat the isolation as a resource boundary rather than a security one — untrusted multi-tenant workloads need a hypervisor.

Interview Questions

Beginner: What is a container, and how does it differ from a VM?

A container is an ordinary Linux process with three kernel features applied to it. There is no container object in the kernel — no container type, no container syscall.

  • Namespaces restrict what the process can see: its own PID space, mounts, network interfaces, hostname, users.
  • cgroups restrict what it can use: CPU, memory, I/O, process count.
  • A union filesystem gives it a root directory assembled from stacked read-only image layers plus one thin writable layer.

The difference from a VM is the kernel. A VM runs its own guest kernel on virtual hardware provided by a hypervisor; a container shares the host kernel.

ContainerVM
KernelShared with the hostIts own
Start timeMillisecondsTens of seconds
SizeMBsGBs
IsolationKernel featuresHypervisor — much stronger

The proof that they are just processes: run a container and the processes appear in the host's ps output with normal PIDs. The same process is PID 1 inside its namespace and, say, PID 48213 on the host — one kernel task with two views of its identity.

Beginner: What is the difference between an image and a container?

An image is a read-only template; a container is a running instance of one. The class/object analogy is close: one image can produce any number of containers.

docker run nginx     # creates a NEW container from the nginx image
docker run nginx     # another one — same image, separate writable layer

Mechanically, the difference is the writable layer. An image is a stack of immutable layers. Starting a container adds one thin writable layer on top, and all writes go there — which is why two containers from one image do not see each other's changes, and why anything written inside a container is destroyed when the container is removed.

This is deliberate: it is what makes containers disposable, so a deploy can replace them freely. The practical consequences are that persistent data belongs in a volume or an external service, and that fixing something with docker exec in production is temporary — the change is gone at the next restart, and the image it was supposed to fix is unchanged.

Note also that stopped containers still exist and still hold their writable layer. docker ps hides them; docker ps -a shows them, and they consume disk until removed.

Mid: Why do containers start so much faster than VMs?

Because a container skips everything a VM has to do before your process can run.

VM:        BIOS → bootloader → kernel init → device probe → systemd → app
Container: create namespaces → configure cgroup → mount layers → exec

A VM boots an operating system. The hypervisor presents virtual hardware, the guest kernel initialises and probes devices, an init system starts services — tens of seconds before the application starts, and hundreds of MB of memory spent on the guest OS.

A container starts a process. The kernel is already running. The runtime creates namespaces (a few syscalls), configures a cgroup (writing to a filesystem interface), mounts the image layers via a union filesystem, and calls exec. There is no kernel to boot because there is no second kernel.

Why it matters practically: fast start is what makes autoscaling responsive, CI jobs cheap, and per-request or per-job containers viable. It is also what makes a crash-and-restart loop a reasonable recovery strategy, which orchestrators depend on.

The cost of that speed is the shared kernel. No guest kernel means no second isolation boundary — a kernel privilege-escalation bug is a container escape, whereas in a VM the attacker would still face the hypervisor. Speed and weaker isolation are the same architectural decision.

Mid: "Build once, run anywhere" — when is that not true?

The promise holds because an image packages the userland: binaries, shared libraries, interpreters, system packages, configuration. That removes the dependency mismatch that used to break deployments. What an image does not contain is a kernel, and every exception follows from that.

  • Architecture mismatch. An image built on Apple Silicon is arm64 and will not run on an amd64 host without emulation. This is the most common real-world failure, and it is silent until deploy — build multi-arch images, or pass --platform explicitly.
  • OS family mismatch. Linux containers cannot run on a Windows kernel and vice versa. Docker Desktop hides this by running a Linux VM, which is also why bind-mount I/O is slower on macOS.
  • Kernel version and features. A container using a newer syscall, or a specific kernel module, cgroup v2, or a filesystem feature, fails on an older host kernel.
  • Host configuration leaking in. seccomp and AppArmor profiles, SELinux labels, and sysctls differ between hosts and can block behaviour that worked locally.
  • Hardware and drivers. GPU workloads need matching host drivers and a device plugin — the image alone is not sufficient.

The accurate statement is "build once, run on any host with a compatible kernel and architecture". In practice that covers most Linux fleets, which is why the shorthand survives — but it is exactly the wrong shorthand when someone is debugging a container that runs locally and fails in production.

Senior: When would you choose VMs over containers?

The decision is almost always about the isolation boundary, and secondarily about kernel requirements.

1. Untrusted or hostile code. The strongest case. Running customer-supplied code — CI for public pull requests, a serverless platform, a code-execution sandbox — means a kernel privilege-escalation bug compromises every tenant on the host, because there is no hypervisor beneath the container. The industry answer is VM-backed isolation: Firecracker microVMs (what AWS Lambda and Fargate use), gVisor (a user-space kernel that intercepts syscalls), or Kata Containers, which give a container-shaped interface over a real VM boundary.

2. A different kernel is genuinely required. Windows workloads on a Linux fleet, an old kernel a legacy application depends on, or a custom kernel module. Containers cannot express this at all.

3. Regulatory or contractual isolation requirements. Some compliance regimes require hardware-level or hypervisor-level tenant separation, and "we use namespaces" does not satisfy the auditor regardless of the technical argument.

4. Hardware access and specialised drivers, where device passthrough in a container is either impossible or requires privileges that undo the isolation you wanted.

Where containers clearly win: trusted first-party workloads, microservices, high-density deployment, fast autoscaling, reproducible CI, and anything benefiting from milliseconds-not-minutes start times.

The pattern most large platforms actually use is both: VMs as the tenancy and security boundary, containers for packaging and scheduling inside each VM. That gets hypervisor-grade isolation between customers and container-grade density and speed within one. Framing it as "containers versus VMs" is usually the wrong question — the real one is where the trust boundary sits.

Senior: A container works locally but fails in production. Walk through the diagnosis.

The image is identical, so the difference is the environment around it. I would check in this order, cheapest and most common first.

1. Architecture. The most frequent cause since Apple Silicon became common — an image built on an arm64 laptop failing on amd64 hosts:

docker image inspect myimage --format '{{.Architecture}}/{{.Os}}'
docker buildx build --platform linux/amd64,linux/arm64 ...    # the fix

2. Is it the same image? A tag is mutable, so "the same version" frequently is not. Compare digests, not tags — this is why production should deploy by digest.

docker image inspect myimage:1.2.3 --format '{{index .RepoDigests 0}}'

3. Configuration and secrets. Environment variables, mounted config, and secret availability differ between environments far more often than anything else. Diff the effective env inside a running container rather than reading deployment manifests.

4. Resource limits. Locally there are usually none; in production there are. An application that works with unlimited memory gets OOM-killed at 512Mi, and the symptom is exit code 137 with no application error — covered in Resource Limits & the OOM Killer.

5. Networking and DNS. Service discovery, egress rules, and network policy differ. "Connection refused" versus "no such host" separates a routing problem from a DNS one immediately.

6. Filesystem permissions. A container running as non-root in production but root locally cannot write where it expects, and mounted volumes may be owned by a different UID.

7. Host kernel and security profiles. Older kernel, cgroup v1 versus v2, or a seccomp or AppArmor profile blocking a syscall that worked locally.

How I would actually work it: get the exit code and the last logs first, because they partition the space immediately — 137 means OOM or SIGKILL, 1 with a stack trace means the app itself, and "exec format error" means architecture. Then run the production image locally with production resource limits and a non-root user, which reproduces most of these differences without touching the cluster.

🏋️ Exercises

1 (easy): Prove a container is just a host process.
Solution 
$ docker run -d --name proof nginx
a3f8b21c4d5e...

# the container thinks it is PID 1
$ docker exec proof ps aux
USER   PID  COMMAND
root     1  nginx: master process nginx -g daemon off;
nginx   29  nginx: worker process

# the host sees the SAME process with a normal PID
$ docker inspect proof --format '{{.State.Pid}}'
48213

$ ps -p 48213 -o pid,ppid,user,comm
  PID  PPID USER     COMMAND
48213 48190 root     nginx

One process, two PIDs — PID 1 inside its namespace, 48213 on the host. No virtualisation is involved; these are two views of the same kernel task.

Confirm it by killing it from the host:

$ sudo kill -9 48213
$ docker ps -a --filter name=proof --format '{{.Status}}'
Exited (137) 3 seconds ago

Exit code 137 = 128 + 9 (SIGKILL). The host killed a normal process and the "container" stopped, because the container was that process.

Now look at what makes it look isolated:

$ docker run -d --name ns-demo nginx
$ PID=$(docker inspect ns-demo --format '{{.State.Pid}}')
$ sudo ls -l /proc/$PID/ns/
lrwxrwxrwx 1 root root 0 cgroup -> 'cgroup:[4026532567]'
lrwxrwxrwx 1 root root 0 ipc    -> 'ipc:[4026532505]'
lrwxrwxrwx 1 root root 0 mnt    -> 'mnt:[4026532503]'
lrwxrwxrwx 1 root root 0 net    -> 'net:[4026532508]'
lrwxrwxrwx 1 root root 0 pid    -> 'pid:[4026532506]'
lrwxrwxrwx 1 root root 0 uts    -> 'uts:[4026532504]'

# compare with a normal host process (PID 1, systemd)
$ sudo ls -l /proc/1/ns/pid
lrwxrwxrwx 1 root root 0 pid -> 'pid:[4026531836]'    ← a DIFFERENT namespace id

The container's process is in different namespaces from the host's. That difference — a set of ids in /proc/PID/ns/ — is the entire mechanism behind "isolation".

2 (easy): Show that the writable layer is disposable, and that volumes are not.
Solution 
$ docker run -d --name c1 alpine sleep 3600
$ docker exec c1 sh -c 'echo "important data" > /data.txt'
$ docker exec c1 cat /data.txt
important data

# a SECOND container from the same image does not see it
$ docker run --rm alpine cat /data.txt
cat: can't open '/data.txt': No such file or directory

Same image, separate writable layers — the file exists only in c1.

Now remove the container and watch it vanish:

$ docker rm -f c1
$ docker run --rm --name c1 alpine cat /data.txt
cat: can't open '/data.txt': No such file or directory

This is the mechanism behind "my docker exec fix disappeared". The writable layer is destroyed with the container, so runtime changes never survive a redeploy.

A volume behaves differently:

$ docker volume create appdata
$ docker run --rm -v appdata:/data alpine sh -c 'echo "persisted" > /data/file.txt'
$ docker run --rm -v appdata:/data alpine cat /data/file.txt
persisted                                ← survived container removal

$ docker run --rm -v appdata:/data alpine sh -c 'echo "second write" >> /data/file.txt'
$ docker run --rm -v appdata:/data alpine cat /data/file.txt
persisted
second write                             ← shared across containers, over time

Check the disk cost of forgotten containers:

$ for i in 1 2 3; do docker run -d --name junk$i alpine \
      sh -c 'dd if=/dev/zero of=/big bs=1M count=50; sleep 300'; done
$ docker ps -a --filter name=junk --format '{{.Names}}\t{{.Status}}'
junk3   Up 2 seconds
junk2   Up 3 seconds
junk1   Up 4 seconds

$ docker system df
TYPE            TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images          12      3        1.842GB   1.203GB (65%)
Containers      6       3        150.3MB   0B (0%)
Local Volumes   2       1        4.096kB   0B (0%)

$ docker rm -f junk1 junk2 junk3 && docker system df | grep Containers
Containers      3       0        0B        0B

Each container's writable layer holds its 50 MB independently. Stopped containers keep that space until removed — which is why --rm on short-lived containers and periodic pruning matter.

Under half a second, and most of that is the Docker CLI and daemon round trip rather than the container itself.

$ docker create --name fast alpine true

43 milliseconds for the actual container primitives. Everything above that is tooling.

$ time (virsh start testvm && \

# where a VM spends it
$ systemd-analyze                 # run INSIDE the VM

~60× faster, and the table shows why: the container skips every step involving a kernel, because it does not have one of its own. That is the same architectural fact that makes its isolation weaker.

4 (medium): Demonstrate that the kernel is shared, and what that implies.
Solution 
$ uname -r                                    # host kernel
6.5.0-27-generic

$ docker run --rm alpine uname -r
6.5.0-27-generic                              ← identical

$ docker run --rm ubuntu:22.04 uname -r
6.5.0-27-generic                              ← STILL identical

$ docker run --rm alpine cat /etc/os-release | head -1
NAME="Alpine Linux"
$ docker run --rm ubuntu:22.04 cat /etc/os-release | head -1
PRETTY_NAME="Ubuntu 22.04.4 LTS"

Different distributions, same kernel. The image supplies the userland — libc, package manager, shell — while the kernel comes from the host. That is the whole trick, and the reason a container is MBs rather than GBs.

A kernel setting is shared too:

$ docker run --rm alpine cat /proc/sys/kernel/hostname
3f8a91c04e7b                                  ← namespaced, so this differs

$ docker run --rm alpine cat /proc/sys/vm/swappiness
60                                            ← NOT namespaced: the host's value
$ cat /proc/sys/vm/swappiness
60                                            ← same

Some kernel state is namespaced (hostname) and some is global (VM tuning). A container cannot have its own swappiness because there is only one kernel to configure.

Now the security implication, demonstrated safely:

# a privileged container can see and modify HOST kernel state
$ docker run --rm --privileged alpine sysctl -w vm.swappiness=10
vm.swappiness = 10
$ cat /proc/sys/vm/swappiness                 # on the HOST
10                                            ← the host was changed

$ sudo sysctl -w vm.swappiness=60             # restore

# without --privileged it is refused
$ docker run --rm alpine sysctl -w vm.swappiness=10
sysctl: error setting key 'vm.swappiness': Read-only file system

A privileged container modified the host kernel's configuration — which is the point: the boundary is kernel features, not hardware. Remove enough of those features (--privileged drops most of them) and the isolation is essentially gone.

See what a container is normally restricted to:

$ docker run --rm alpine grep CapEff /proc/self/status
CapEff: 00000000a80425fb          ← a limited capability set

$ docker run --rm --privileged alpine grep CapEff /proc/self/status
CapEff: 000001ffffffffff          ← ALL capabilities

Those two hex values are the practical difference between a contained process and one that can reconfigure the host.

5 (hard): Build a minimal "container" by hand with plain Linux tools.
Solution

The clearest way to internalise that containers are processes is to make one without Docker.

# 1. a root filesystem — borrow one from an image
$ mkdir -p /tmp/myroot
$ docker export $(docker create alpine) | tar -C /tmp/myroot -xf -
$ ls /tmp/myroot
bin  dev  etc  home  lib  proc  root  sbin  sys  tmp  usr  var

2. Namespaces — the "what can it see" half:

$ sudo unshare --pid --mount --uts --ipc --net --fork --mount-proc=/tmp/myroot/proc \
       chroot /tmp/myroot /bin/sh

/ # hostname mycontainer          # UTS namespace: our own hostname
/ # ps aux
PID   USER     COMMAND
    1 root     /bin/sh            ← we are PID 1
    5 root     ps aux
                                  ← the host's processes are invisible
/ # ip addr
1: lo: <LOOPBACK> mtu 65536
                                  ← our own (empty) network stack
/ # ls /
bin  dev  etc  home  lib  proc  root  sbin  sys  tmp  usr  var

That is a container's isolation — created with one command and no Docker. From another terminal, the host still sees the process normally:

$ ps -ef | grep '/bin/sh' | head -2
root     51204  51203  0 15:22 pts/3  /bin/sh      ← PID 51204 on the host

3. cgroups — the "what can it use" half:

$ sudo mkdir /sys/fs/cgroup/mycontainer
$ echo 104857600 | sudo tee /sys/fs/cgroup/mycontainer/memory.max     # 100 MB
$ echo 51204     | sudo tee /sys/fs/cgroup/mycontainer/cgroup.procs   # add our shell

# back inside the shell, try to exceed it
/ # dd if=/dev/zero of=/dev/shm/fill bs=1M count=200
Killed

The kernel enforced the limit and killed the process — exactly what docker run --memory=100m does.

4. What Docker adds on top of this:

The lesson: Docker is packaging and ergonomics over kernel features that already existed. The isolation is the kernel's; Docker makes it usable — which is also why the security boundary is exactly as strong as the kernel, and no stronger.

6 (hard): Reproduce the architecture-mismatch failure and fix it with a multi-arch build.
Solution 
# on an Apple Silicon Mac (arm64), the default build is arm64
$ docker build -t myapp:local .
$ docker image inspect myapp:local --format '{{.Architecture}}/{{.Os}}'
arm64/linux

# push it and run on an amd64 server:
$ docker run myapp:local
exec /usr/local/bin/app: exec format error

exec format error is the signature of this failure — the kernel cannot execute a binary compiled for another architecture. It is silent until deploy, because everything works locally.

Reproduce it deliberately on any machine:

$ docker run --rm --platform linux/arm64 alpine uname -m
aarch64            # works via QEMU emulation, if installed — and is SLOW

$ docker run --rm --platform linux/amd64 alpine uname -m
x86_64

Measure the emulation cost, which is the reason not to rely on it:

$ time docker run --rm --platform linux/amd64 alpine \
      sh -c 'i=0; while [ $i -lt 2000000 ]; do i=$((i+1)); done'
real    0m1.284s        ← native

$ time docker run --rm --platform linux/arm64 alpine \
      sh -c 'i=0; while [ $i -lt 2000000 ]; do i=$((i+1)); done'
real    0m18.663s       ← emulated: 14.5x slower

The fix — build for both architectures:

$ docker buildx create --name multiarch --use
$ docker buildx build --platform linux/amd64,linux/arm64 \
      -t myrepo/myapp:1.0 --push .

$ docker buildx imagetools inspect myrepo/myapp:1.0
Name:      docker.io/myrepo/myapp:1.0
MediaType: application/vnd.oci.image.index.v1+json

Manifests:
  Name:      myrepo/myapp:1.0@sha256:a1b2c3...
  Platform:  linux/amd64
  Name:      myrepo/myapp:1.0@sha256:d4e5f6...
  Platform:  linux/arm64

The tag now points at a manifest list — an index of per-architecture images. Each host pulls the variant matching its own platform automatically, so one tag works everywhere with no emulation.

Verify what a host actually resolved:

$ docker pull myrepo/myapp:1.0
$ docker image inspect myrepo/myapp:1.0 --format '{{.Architecture}}'
amd64              # on an amd64 host

$ docker manifest inspect myrepo/myapp:1.0 | grep architecture
        "architecture": "amd64",
        "architecture": "arm64",

The debugging rule this gives you: exec format error always means architecture, never a corrupt binary or a missing dependency. Check docker image inspect --format '{{.Architecture}}' first, and build multi-arch in CI so laptop architecture never determines what production receives.

🎯 Key Takeaways

  • A container is an ordinary Linux process with namespaces, cgroups, and a union filesystem applied — there is no container object in the kernel.
  • The same process is PID 1 inside its namespace and a normal PID on the host; killing the host PID stops the container, because it is the container.
  • Namespaces control what a process can see; cgroups control what it can use; the union filesystem controls what files it has.
  • Containers share the host kernel — different distros in different containers all report the same uname -r.
  • That shared kernel is why containers start in ~0.4 s against ~24 s for a VM: no firmware, no kernel boot, no init — measured at ~0.04 s for the raw runc primitives.
  • It is also why isolation is weaker: a kernel privilege-escalation bug is a container escape, with no hypervisor underneath.
  • Speed and weak isolation are the same architectural decision, not independent trade-offs.
  • A privileged container can modify host kernel state (demonstrated with sysctl) — --privileged grants all capabilities (CapEff goes from a80425fb to 1ffffffffff).
  • An image is a read-only stack of layers; a container adds one thin writable layer that is destroyed with it.
  • That is why docker exec fixes vanish on redeploy and why persistent data belongs in a volume or an external service.
  • Stopped containers keep their writable layer and consume disk until removed — use --rm and prune.
  • "Build once, run anywhere" means "any host with a compatible kernel and architecture" — images carry userland, not a kernel.
  • exec format error always means an architecture mismatch; emulation works but measured 14.5× slower, so build multi-arch images instead.
  • Docker Desktop on macOS/Windows runs a hidden Linux VM, which is why bind-mount I/O is slower there.
  • Run one main process per container — the runtime only supervises PID 1, so anything else fails silently.
  • Log to stdout/stderr, or docker logs shows nothing.
  • You can build a working container by hand with unshare, chroot, and a cgroup write — Docker adds images, networking, security profiles, and lifecycle on top.
  • Choose VMs for untrusted multi-tenant code, a different kernel, or regulated isolation; large platforms typically use both — VMs as the trust boundary, containers for density inside.
