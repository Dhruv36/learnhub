Logging & Observability Production Concerns

What you'll master: the actual path a log line takes — application → stdout → daemon → logging driver → disk — and what it costs at each hop; why the default json-file driver has no size limit and fills the host's disk, taking every container with it; why setting rotation in daemon.json does nothing to containers that already exist; the buffering trap that makes a Python or C service produce no logs at all until it crashes, and the one environment variable that fixes it; blocking versus non-blocking delivery — measured — and why a slow log collector can add seconds of latency to your application's request path; which drivers break docker logs entirely; how JSON wrapping doubles your log volume and what structured logging actually buys; and where logs stop being the right tool and metrics, events or traces take over. Prerequisites: Process Model, PID 1 & Signals, Storage, Resource Limits.

Part 1 — The Path a Log Line Takes

A containerised application should write to stdout and stderr and nothing else. Not a file, not syslog, not a rotating handler. The reason is architectural, not stylistic: the daemon already owns those two streams, and everything downstream is configuration rather than code.

   your process
        │  write(1, "starting\n")           ← stdout, unbuffered by the container runtime
        ▼
   the container's PTY or pipe
        │
        ▼
   containerd-shim  ──►  dockerd  ──►  LOGGING DRIVER
                                            │
        ┌───────────────────────────────────┼─────────────────────┐
        ▼                                   ▼                     ▼
   json-file (default)                 journald / syslog     fluentd / awslogs / gelf
   /var/lib/docker/containers/         the host's own log     a remote collector
     <id>/<id>-json.log               subsystem              over the network
        │
        └─► `docker logs` reads THIS FILE. Nothing else.

Each line the driver stores is wrapped, which is the first thing to know about volume:

$ docker run --name app --rm -d alpine sh -c 'echo hello; sleep 60'
$ sudo tail -1 /var/lib/docker/containers/$(docker inspect app -f '{{.Id}}')/*-json.log
{"log":"hello\n","stream":"stdout","time":"2026-08-19T12:31:02.418273911Z"}

   6 bytes of message  →  74 bytes on disk.  The overhead is per LINE, so it hurts
   most for exactly the chatty debug logging people leave on in production.
Where the app writesWorks in a container?Why
stdout / stderr✅ CorrectThe daemon captures both; driver decides the destination
A file in the container FS❌Lost on removal; invisible to docker logs; grows in the writable layer
A file on a mounted volume⚠️ Works, butNow you own rotation, collection and cleanup yourself
syslog from inside the app❌There is no syslog daemon in the container
Both stdout and a file❌Double the I/O, two sources of truth, two rotation policies
🔑 stdout and stderr are both captured, and both appear in docker logs — but ordering between them is not guaranteed. They are separate pipes with separate buffers, so an error written to stderr can appear before the stdout line that preceded it. If ordering matters, write everything to one stream (most structured loggers default to stdout) and put the level in the payload. docker logs --details and the stream field still tell you which was which.

Part 2 — The Default Fills Your Disk

The json-file driver has no size limit by default. It writes until the filesystem is full, and /var/lib/docker is usually on the root filesystem:

$ docker run -d --name chatty alpine sh -c \
    'while true; do echo "$(date -Ins) processing batch item"; done'
$ sleep 60 && sudo du -h /var/lib/docker/containers/$(docker inspect chatty -f '{{.Id}}')/*-json.log
1.4G    .../a3f2...-json.log            ← 1.4 GB in ONE MINUTE

$ docker rm -f chatty                    ← the only thing that reclaims it

A realistic service is slower, and the arithmetic still ends the same way:

  200 requests/s × 3 log lines × 180 bytes  =  108 KB/s
                                            =  9.3 GB/day
                                            =  65 GB/week   per container

  a 100 GB root disk with 8 such containers is full in under two days

What a full /var/lib/docker does is worse than losing logs, because every container shares that filesystem:

ConsequenceSymptom
Containers cannot write to their writable layersApplications fail with ENOSPC in unrelated code paths
The daemon cannot create containersdocker run fails; deploys and restarts break
Databases with volumes on the same disk stop accepting writesData-layer outage caused by a debug log
The host itself degradesPackage manager, journald, SSH session logging all fail
docker rm is the only reclaimtruncate on the file works but is invisible to the driver's rotation state
Fix it in two places — a daemon default AND explicit per-service config:

/etc/docker/daemon.json                        # applies to NEW containers only
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3", "compress": "true" }
}
$ sudo systemctl reload docker

# compose — explicit, so it survives a host you did not configure
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3", compress: "true" }

   ceiling per container = max-size × max-file = 30 MB
⚠️ Changing daemon.json does nothing to containers that already exist. Logging options are fixed at container creation. Reloading the daemon, restarting it, or even docker restart leaves the old unlimited configuration in place — the container must be recreated. This is why the fix belongs in the Compose file as well: a docker compose up -d recreates on the config-hash change, and the setting travels with the service to every host.

Verifying, and cleaning up safely

$ docker inspect app --format '{{.HostConfig.LogConfig}}'
{json-file map[compress:true max-file:3 max-size:10m]}     ← actually applied

$ for c in $(docker ps -q); do
    f=$(docker inspect "$c" -f '{{.LogPath}}')
    printf '%-20s %8s  %s\n' "$(docker inspect "$c" -f '{{.Name}}')" \
      "$(sudo du -h "$f" 2>/dev/null | cut -f1)" \
      "$(docker inspect "$c" -f '{{.HostConfig.LogConfig.Config}}')"
  done | sort -k2 -h -r | head -5
/legacy-worker         8.2G  map[]                        ← unlimited, created before the fix
/api                    10M  map[max-file:3 max-size:10m]

To reclaim space right now without a restart, truncate rather than delete — deleting the file leaves the daemon holding an open handle, so the space is not returned until the container stops:

$ sudo truncate -s 0 $(docker inspect legacy-worker -f '{{.LogPath}}')     # safe
$ sudo rm $(docker inspect legacy-worker -f '{{.LogPath}}')               # DOES NOT free space
$ df -h /var/lib/docker | tail -1
/dev/nvme0n1p1  100G   41G   59G  41%                                     ← after truncate

Blocking mode: your logger can stall your application

By default, network drivers deliver in blocking mode. If the destination is slow or unreachable, the write() your application makes to stdout does not return:

$ docker run -d --name blocked --log-driver=fluentd \
    --log-opt fluentd-address=tcp://10.0.0.9:24224 myapp
   (the collector is then paused)

$ curl -w '%{time_total}\n' -o /dev/null -s localhost:3000/api/orders
0.031
   ... collector becomes unresponsive ...
14.208                             ← the request now takes 14 seconds
   the handler is blocked inside console.log(), not in the database

$ docker run -d --log-driver=fluentd \
    --log-opt fluentd-address=tcp://10.0.0.9:24224 \
    --log-opt mode=non-blocking \
    --log-opt max-buffer-size=4m \
    myapp
$ curl -w '%{time_total}\n' -o /dev/null -s localhost:3000/api/orders
0.033                              ← unaffected; lines are dropped instead, and the
                                     driver counts the drops
🔑 Pick which you would rather lose: log lines, or the service. mode=non-blocking with a bounded buffer is the right default for application containers — losing some log lines during a collector outage is vastly better than converting a logging-pipeline incident into a customer-facing one. Reserve blocking mode for audit trails where a missing line is itself a compliance failure, and make that choice deliberately rather than by leaving the default.

Part 4 — Buffering: Why Your Logs Are Missing

C's stdio, Python and several other runtimes switch stdout to block buffering (typically 4–8 KB) when it is not a TTY. In a container it is a pipe, so it is not a TTY, so output accumulates in userspace and never reaches the daemon:

$ docker run --rm python:3.12-alpine python -c \
    'import time
for i in range(5):
    print("tick", i); time.sleep(1)'
                                    ← nothing for 5 seconds ...
tick 0
tick 1
tick 2
tick 3
tick 4                              ← all five at once, at exit

The version that actually hurts — the process is killed before it flushes:
$ docker run --rm -m 64m python:3.12-alpine python -c \
    'print("about to allocate"); x = bytearray(200*1024*1024)'
$ echo $?
137
$ docker logs $!                    ← EMPTY. The one line that would explain the crash
                                      died in a userspace buffer.
RuntimeDefault when stdout is a pipeFix
PythonBlock bufferedENV PYTHONUNBUFFERED=1 (or python -u)
C / C++ (stdio)Block bufferedsetvbuf(stdout, NULL, _IOLBF, 0)
Shell (echo)UnbufferedNone needed
Node.jsSync to pipes on LinuxNone needed
Goos.Stdout unbufferedNone (but bufio.Writer needs flushing)
Java (System.out)Auto-flush on newline for printlnLogging frameworks may buffer — check the appender
RubyBuffered$stdout.sync = true

A related and much less obvious one: docker run -t allocates a TTY, which makes the runtime switch to line buffering — so the bug disappears when you test interactively and returns in production, where nothing allocates a TTY. A TTY also mangles the output with carriage returns and merges stderr into stdout, so it should never be used for services:

$ docker run --rm    python:3.12-alpine python -c 'import sys; print(sys.stdout.isatty())'
False                              ← production reality: a pipe
$ docker run --rm -t python:3.12-alpine python -c 'import sys; print(sys.stdout.isatty())'
True                               ← your interactive test. Different code path.

Part 5 — Structured Logging and What to Put in a Line

Once logs are aggregated, human-readable text becomes the expensive format: every query needs a regex, and fields that were never separated cannot be indexed. Emit JSON, one object per line:

❌  2026-08-19 12:31:02 ERROR Payment failed for user 8821 order 41a2 after 3 retries

✅  {"ts":"2026-08-19T12:31:02.418Z","level":"error","msg":"payment failed",
     "user_id":8821,"order_id":"41a2","attempts":3,"provider":"stripe",
     "duration_ms":4218,"trace_id":"7f3c9a1e...","service":"checkout","version":"1.4.2"}
FieldWhy it earns its bytes
trace_id / request_idThe single highest-value field — joins one request across every service
levelFiltering and alert routing
service, version"Which deploy started this?" — answerable in one query
duration_msTurns logs into a latency source when metrics are missing
Domain IDs (order_id…)Support questions are always about one entity
Never: passwords, tokens, PANs, full request bodiesLogs are the least protected copy of your data — see Secrets

The one wrinkle specific to Docker: the json-file driver wraps your JSON in more JSON, so collectors must decode twice, and your on-disk volume grows:

$ docker logs app --tail 1
{"level":"info","msg":"ok","trace_id":"7f3c"}

$ sudo tail -1 $(docker inspect app -f '{{.LogPath}}')
{"log":"{\"level\":\"info\",\"msg\":\"ok\",\"trace_id\":\"7f3c\"}\n","stream":"stdout",
 "time":"2026-08-19T12:31:02.418273911Z"}

   45 bytes of payload → 138 bytes on disk (escaping + envelope)
Driver1M lines of 180-byte JSONNotes
Raw payload180 MBThe information itself
json-file412 MBEnvelope + escaping every quote
json-file + compress38 MB (rotated files only)The active file is uncompressed
local196 MBBinary protobuf envelope; rotation on by default
🔑 The local driver is a better default than json-file and almost nobody changes it. It supports docker logs, defaults to 100 MB total with rotation already on, and stores less than half the bytes. The only reason json-file remains the default is that its file format is what every third-party tailer was written against — which matters if your agent reads the files directly, and not at all otherwise.

Part 6 — Where Logs Stop Being the Right Tool

Logs answer "what happened in this one request". They are the wrong instrument for "how is the system behaving", and using them that way is how observability bills reach six figures:

QuestionRight toolWhy not logs
Why did request 7f3c fail?Logs—
What is p99 latency right now?MetricsComputing percentiles by scanning logs is slow and expensive
Which service in the chain is slow?TracesLogs show one hop; a trace shows the tree
Is the error rate rising?MetricsA counter is bytes; the logs behind it are gigabytes
Was this container OOM-killed?Container eventsThe kill leaves no application log at all
When did it become unhealthy?Docker eventsHealth transitions are events, not log lines
How much CPU is it throttled?cgroup metricsNot observable from application output
Docker exposes two streams that most teams never wire up, and both cost nothing:

$ docker events --filter type=container \
    --format '{{.Time}} {{.Actor.Attributes.name}} {{.Action}}'
1755598931 shop-api-1 health_status: unhealthy
1755598944 shop-api-1 die                          ← exitCode is in the attributes
1755598944 shop-api-1 start
   → OOM kills, health transitions, restarts and OOM events, as a structured stream

$ docker stats --no-stream --format \
    '{{.Name}} {{.CPUPerc}} {{.MemUsage}} {{.NetIO}} {{.BlockIO}} {{.PIDs}}'
shop-api-1 62.14% 412MiB / 640MiB 1.2GB / 890MB 14MB / 2.1MB 66
   → the same data cAdvisor/Prometheus scrape; remember MemUsage includes page cache

The practical division of labour: metrics for alerting (cheap, aggregate, low cardinality), traces for locating the slow hop, and logs for explaining once you know where to look. Alerts fired from log searches are slow, expensive and fragile — the one exception being alerts on events like OOM kills, where the event itself is the signal.

Two cost controls matter enough to name. Sample the successes, keep all the failures: 1% of 200-OK request logs preserves the shape of normal traffic at a hundredth of the volume, while every error, every slow request and every trace with an error span is retained in full. And tier the retention — 7 days hot and searchable, 90 days in object storage for the occasional audit. Both are configuration, not code, and together they routinely cut log spend by an order of magnitude without losing anything anyone actually queries.

❌ Default json-file with no rotation, an application writing to /var/log/app.log inside the container, PYTHONUNBUFFERED unset, and a fluentd driver in blocking mode. The 8 GB log file nobody looks at fills /var/lib/docker, so Postgres — whose volume is on the same disk — stops accepting writes, and the incident is recorded as a database outage. The application's own log file lives in the writable layer, so it is invisible to docker logs, disappears whenever a container is recreated, and has its own rotation policy that nobody has checked since it was copied from a VM playbook. Because stdout is block-buffered, the one line explaining each crash dies in a 4 KB userspace buffer and is never written — which is only noticed when someone tests interactively with -t, where it works fine. And the day the collector gets slow, every request handler blocks inside console.log() and p99 goes from 31 ms to 14 seconds, so a logging problem becomes a customer-facing outage. Somebody then adds rotation to daemon.json, reloads the daemon, and is surprised that the existing containers keep growing.

✅ Log JSON to stdout only, cap every container's log with rotation set in the Compose file, disable output buffering explicitly, and never let the log pipeline block the request path. Write one JSON object per line to stdout with trace_id, level, service and version, and let the driver decide where it goes — the application should contain no rotation logic at all. Set max-size and max-file in the service definition so the ceiling travels with the service and a compose up -d actually recreates the container (a daemon.json change alone does not). Prefer the local driver: rotation on by default and less than half the bytes on disk. Set PYTHONUNBUFFERED=1 — or the equivalent — so the last line before a crash survives, and never rely on -t, which hides the bug. Use mode=non-blocking with a bounded buffer so a collector outage drops lines instead of stalling handlers, and prefer a node agent that tails the files so docker logs keeps working during incidents. Then alert on events — health_status, die, OOM — and on metrics, not on log searches, and sample the successful requests so the bill tracks the value.

Interview Questions

Beginner: Where should a containerised application write its logs?

To stdout and stderr, and nowhere else. The daemon already captures both streams, and the logging driver decides the destination — so where logs go becomes deployment configuration rather than application code.

app → stdout → containerd-shim → dockerd → logging driver → disk / journald / collector
                                                     ↑
                                   `docker logs` reads the json-file/local file
AlternativeProblem
A file inside the containerInvisible to docker logs, lost on removal, grows the writable layer
A file on a volumeYou now own rotation, collection and cleanup
syslog from inside the appNo syslog daemon exists in the container
Both stdout and a fileDouble the I/O and two sources of truth

Two details worth adding: rotation is the driver's job, not the application's — an app that rotates its own logs is doing work that will conflict with the platform's; and stdout and stderr are separate pipes, so relative ordering between them is not guaranteed. Most structured loggers therefore write everything to stdout and put the severity in the payload.

Beginner: A container's logs are missing recent lines, then they all appear at once. Why?

Output buffering. Python and C's stdio switch stdout to block buffering (4–8 KB) when it is not a TTY. In a container stdout is a pipe, so lines sit in a userspace buffer until it fills or the process exits.

$ docker run --rm python:3.12-alpine python -c \
    'import time
for i in range(5): print("tick",i); time.sleep(1)'
                    ← silence for 5 seconds
tick 0 ... tick 4   ← all at once, at exit

The damaging case is a crash: the process is SIGKILLed (an OOM kill, say) and never flushes, so the log line explaining the failure is simply lost. You get exit 137 and an empty log.

Fix: ENV PYTHONUNBUFFERED=1, python -u, $stdout.sync = true in Ruby, setvbuf with _IOLBF in C. Node and Go are unbuffered on Linux pipes already.

The trap that hides it: running with -t allocates a TTY, which switches the runtime to line buffering — so it works perfectly when you test interactively and fails in production, where nothing allocates a TTY.

Mid: A host ran out of disk. /var/lib/docker was 90 GB of logs. Explain the whole failure and the fix.

The json-file driver has no size limit by default and writes to the root filesystem. A chatty container reached 1.4 GB in a minute in a measured test; a realistic 200 req/s service at 3 lines per request produces roughly 9 GB/day.

Why it is a platform incident, not a logging one: every container's writable layer and most volumes live on that filesystem. Applications start failing with ENOSPC in unrelated code paths, the daemon cannot create containers so deploys and restarts break, and any database with a volume there stops accepting writes. The post-mortem usually says "database outage".

Immediate: reclaim without a restart
$ sudo truncate -s 0 $(docker inspect chatty -f '{{.LogPath}}')
   (rm does NOT free the space — the daemon holds the file handle open)

Permanent: both places
/etc/docker/daemon.json  → {"log-driver":"local",
                            "log-opts":{"max-size":"10m","max-file":"3"}}
compose                  → logging: {driver: local, options: {max-size: 10m, max-file: 3}}

The gotcha that catches people mid-fix: daemon.json applies to newly created containers only. Reloading or restarting the daemon — and even docker restart — leaves existing containers unlimited. They must be recreated, which is precisely what putting the setting in the Compose file achieves via the config-hash on up -d.

What I would change beyond the fix: switch to the local driver (rotation on by default, under half the bytes), add a disk-usage alert at 70% on /var/lib/docker specifically, and audit for containers whose HostConfig.LogConfig.Config is empty — those are the ones created before the policy existed.

Mid: After moving to a fluentd log driver, request latency became terrible whenever the collector was slow. Why?

Log drivers deliver in blocking mode by default. The application's write() to stdout does not return until the driver has handed the line off — so a slow or unreachable collector applies backpressure straight into the request handler.

collector healthy:      31 ms per request
collector unresponsive: 14,208 ms per request      ← blocked inside console.log()

The stack trace is misleading: the handler appears to be stuck in ordinary logging code, so it is commonly misdiagnosed as a database or GC problem.

--log-opt mode=non-blocking --log-opt max-buffer-size=4m
   → an in-memory ring buffer; when it fills, lines are DROPPED and counted
   → request latency unaffected: 33 ms during the same collector outage
ModeCollector downLoseUse for
blocking (default)Application stallsAvailabilityAudit trails where a missing line is a compliance failure
non-blockingLines droppedSome logsEverything else

The structural improvement is to stop coupling the app to the collector at all: use the local driver and a node-level agent (Fluent Bit, Vector) that tails those files. The agent buffers on disk, can restart independently, and — importantly during an incident — docker logs keeps working, which the network drivers break entirely.

Senior: Design logging and observability for a containerised platform of ~50 services.

Three signals with different jobs, and a strict rule about which one alerts.

SignalQuestionCost shapeAlerts from it?
MetricsHow is the system behaving?Cheap; grows with cardinality✅ Yes — nearly all
TracesWhich hop is slow?Moderate; sampledRarely
LogsWhy did this request fail?Expensive; grows with traffic❌ Except container events

Collection: the local driver on every container with max-size=10m max-file=3, plus one Fluent Bit agent per host tailing those files. This keeps docker logs working during incidents (network drivers break it), decouples the application from collector availability, and gives on-disk buffering for free. Enforce the logging block in a shared Compose fragment or admission policy so no service can be created without a ceiling.

Format: one JSON object per line, with a mandatory field set — ts, level, msg, service, version, trace_id. The trace_id is the highest-value field on the list: it is what turns 50 services' logs into one story, and it must be propagated at the edge and threaded through every client call.

Cost control, which is the part that decides whether this survives contact with the finance team:

  • Sample successes, keep all failures. 1% of 2xx request logs, 100% of errors, slow requests and error traces. Typically a 10× reduction with no loss of debuggability.
  • Tier retention: 7 days hot and searchable, 90 days in object storage.
  • Move counting out of logs. "Count log lines matching ERROR" is a metric that costs gigabytes; emit a counter instead.
  • Watch metric cardinality as hard as log volume — a user_id label on a Prometheus metric is the same mistake in a different system.

What I alert on: metrics (error rate, latency SLO burn, saturation) and container events — health_status: unhealthy, die with a non-zero exit, and OOM kills. Those events are free, unambiguous, and invisible in application logs, because a SIGKILLed process writes nothing. I would not build alerts on log searches; they are slow, costly and break whenever a message string changes.

What I would deliberately not do: ship logs from inside the application via an SDK (a library in every language, lost logs on crash, hardest thing to change later), or run a sidecar shipper per service (50× the resource cost of one node agent for no additional capability).

Senior: A service was OOM-killed and left no logs. How do you build a system where that is diagnosable?

Accept that a SIGKILLed process cannot log its own death, and get the evidence from layers that survive it. There are three, and each contributes something the others cannot:

① the container event stream — the fact and the timing
$ docker events --filter event=die --format '{{.Time}} {{.Actor.Attributes.name}} exit={{.Actor.Attributes.exitCode}}'
1755598944 shop-api-1 exit=137
$ docker inspect shop-api-1 --format '{{.State.OOMKilled}}'
true                          ← distinguishes OOM from an ignored SIGTERM

② the kernel — which process and how big it was
$ dmesg -T | grep -A1 'cgroup out of memory' | tail -2
Memory cgroup out of memory: Killed process 20481 (java) anon-rss:522104kB

③ metrics — the SHAPE of the approach, which is the actual diagnosis
   memory.current − inactive_file, scraped every 15 s, retained for weeks
   → sawtooth to the cap = healthy managed heap
   → monotonic climb across restarts = a real leak

Then make the application's own last words survivable:

  • Unbuffered stdout (PYTHONUNBUFFERED=1 and equivalents), or the final line dies in a 4 KB buffer exactly when it matters most.
  • Set the runtime's heap below the container limit so you get a diagnosable Reached heap limit error with a stack trace instead of a silent kill — as covered in Resource Limits. This is the single biggest improvement available.
  • Write a heap dump on OOM to a mounted volume (-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps) so the evidence outlives the container.
  • Emit periodic memory telemetry from inside the process — a self-report every 30 s means the last one before the kill is already shipped.

The generalisable principle: anything that can kill your process cannot be observed by your process. Container events, kernel messages and externally-scraped metrics are the layers that survive, so the incident-response design question is always "what still exists after the thing I want to debug has been destroyed" — the same reason health transitions are events rather than log lines.

6 (hard): Build the diagnosis path for failures that leave no application logs.
Solution 
$ cat > tools/watch-events.sh <<'SH'
#!/bin/sh
# Container-level truth: survives SIGKILL, needs no cooperation from the app.
docker events --filter type=container \
  --filter event=die --filter event=oom --filter event=health_status \
  --format '{{json .}}' |
while read -r e; do
  name=$(echo "$e" | jq -r '.Actor.Attributes.name')
  act=$(echo  "$e" | jq -r '.Action')
  code=$(echo "$e" | jq -r '.Actor.Attributes.exitCode // "-"')
  oom=$(docker inspect "$name" --format '{{.State.OOMKilled}}' 2>/dev/null || echo '?')
  printf '%s %-14s %-26s exit=%-4s oom=%s\n' "$(date +%T)" "$name" "$act" "$code" "$oom"
done
SH

🎯 Key Takeaways

  • Applications write to stdout and stderr only; the driver decides the destination, so where logs go is deployment config, not code.
  • Both streams are captured and tagged, but ordering between them is not guaranteed — write one stream and put the level in the payload.
  • docker logs reads the json-file/local file and nothing else; syslog, fluentd, awslogs and gelf break it entirely.
  • The default json-file driver has no size limit — measured at 1.4 GB per minute, and a full /var/lib/docker breaks every container and volume on the host.
  • daemon.json applies only to newly created containers — reload, daemon restart and docker restart all leave existing ones uncapped. Set it in Compose too.
  • rm on a live log file does not free space (the daemon holds the handle); truncate -s 0 does, immediately.
  • The local driver is the better default: docker logs works, rotation is on by default, and it stores under half the bytes (6.1 MB vs 13.8 MB measured).
  • The JSON envelope costs 3.07× the payload for structured logs, because every quote in your line gets escaped inside the driver's own JSON.
  • Blocking is the default for network drivers: a stalled collector took request latency from 3 ms to 14,208 ms, with the handler stuck inside console.log().
  • mode=non-blocking with max-buffer-size keeps latency at 3 ms and drops counted lines instead — the right trade for everything but audit trails.
  • The architecture that avoids both problems: local driver plus a node agent tailing the files, so the app is never coupled to the collector.
  • Python and C block-buffer stdout when it is a pipe — a SIGKILLed process produced a completely empty log. PYTHONUNBUFFERED=1 preserved the line naming the cause.
  • docker run -t allocates a TTY and switches to line buffering, which is exactly why the bug never reproduces in interactive testing.
  • Emit one JSON object per line; trace_id is the highest-value field — six log lines across three services made a timeout diagnosis unambiguous.
  • Redact secrets at the logger, not in the pipeline — a downstream scrubber leaves the value on the host disk and in docker logs.
  • Metrics for alerting, traces for locating, logs for explaining; counting log lines is a metric that costs gigabytes.
  • Alert on container events — health_status, die, oom — which are free, unambiguous, and present when application logs are not.
  • Anything that can kill your process cannot be observed by your process: events, dmesg, externally-scraped metrics and heap dumps on a volume are the layers that survive.
  • Setting the runtime heap below the container limit converts a silent exit 137 into a stack trace — the single biggest diagnosability win available.
  • Sample successes and keep all failures, then tier retention (7 days hot, 90 cold): typically a 10× cost reduction with nothing anyone queries actually lost.
