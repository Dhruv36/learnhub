Image Size & Base Image Choice Building Images

What you'll master: why image size matters and — more usefully — the cases where it does not, since shared layers mean a 400 MB image can cost 12 MB to deploy; how to choose a base image on the axis that actually matters, which is glibc versus musl rather than megabytes, and why Alpine can make a Python service build 40× slower while looking like the smaller choice; the four techniques that produce real reductions, ranked by what they actually deliver; measuring attack surface rather than guessing at it, since fewer packages is the security argument people make without checking; tooling — dive, docker history, and size budgets in CI; and the point at which further optimisation costs more in engineering time than it saves. Prerequisites: Multi-stage Builds.

Part 1 — What Image Size Actually Costs

Before optimising, be precise about what a large image costs — because the answer determines how much effort is justified.

CostReal impactMitigated by
Registry storageSmall — layers deduplicateShared bases
Cold pull timeLarge — a new node pulls everythingSmaller images, prewarming
Warm pull timeNear zero — only changed layers moveLayer ordering
Autoscaling latencyDirectly proportional to cold pullSmaller images
Attack surfaceEvery package is a potential CVEFewer packages
CI bandwidthModerate, and recurringCaching, smaller images
🔑 Warm pulls only transfer changed layers, so a 400 MB image can cost 12 MB to deploy. If your nodes already have the base and dependency layers, redeploying a new build pulls only the application layer. That means image size matters most for cold starts — new nodes, autoscaling events, a fresh cluster — and barely at all for routine deploys onto warm nodes. Optimising size to speed up a deploy that already only moves 12 MB is wasted effort.

The two cases where size genuinely dominates are autoscaling (a node that must pull 1.5 GB before serving traffic is minutes behind demand) and security (each installed package is a CVE that someone must triage, whether or not your application uses it).

Part 2 — Choosing a Base: glibc vs musl

The size column is the least interesting property of a base image. The C library it uses determines whether your software works, and how fast it builds.

BaseSizelibcPackage managerShell
scratch0 Bnonenone❌
distroless/static~2 MBnonenone❌
alpine~7 MBmuslapk✅ busybox
distroless/base~20 MBglibcnone❌
debian:12-slim~75 MBglibcapt✅ bash
ubuntu:24.04~78 MBglibcapt✅ bash
🔑 Alpine uses musl, and Python wheels are built for glibc. PyPI's precompiled manylinux wheels do not apply on musl, so pip install falls back to compiling from source — which means installing pandas or numpy on Alpine can take minutes instead of seconds, needs a full build toolchain, and often produces a larger final image than debian-slim would have. Choosing Alpine for a Python service to save 68 MB is one of the most common self-inflicted build problems in Docker.

LanguageAlpine suitable?Notes
Go (static)✅ Prefer scratch/distrolessNo libc needed at all
Rust (static)✅musl target works well
Node.js⚠️ Usually fineNative modules may need rebuilding
Python❌ Usually notNo manylinux wheels — slow builds
Java✅JRE-specific images are better still
.NET⚠️Use Microsoft's Alpine variants

Other musl differences that bite in production: a smaller default thread stack size, which can crash software expecting glibc's 8 MB; different DNS resolution behaviour, historically breaking search-domain handling; and subtly different getaddrinfo semantics. These are rare but very hard to diagnose.

Part 3 — The Four Techniques That Matter

TechniqueTypical reductionEffort
Multi-stage build5–100×Low
Smaller base image2–10×Low
Production-only dependencies1.5–3×Trivial
.dockerignoreVaries; also fixes secret leaksTrivial
Same-RUN cache cleanup1.1–1.5×Trivial
Squashing layersMarginalBreaks sharing — avoid

Multi-stage dominates everything else, because it removes whole categories — compilers, headers, build caches — rather than trimming within them. Apply it first; the rest are refinements.

# the standard four applied together
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                        ← dev deps available for the build
COPY . .
RUN npm run build

FROM node:20-alpine               ← ① multi-stage
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev \           ← ③ production dependencies only
 && npm cache clean --force       ← ⑤ cleanup in the SAME RUN
COPY --from=build /app/dist ./dist
USER node
CMD ["node","dist/server.js"]

Layer squashing is the one to avoid. It merges layers into one, which looks like a saving and destroys layer sharing: every image becomes a single unique blob, so nodes re-pull everything on every deploy and the registry stores full copies. The measured deploy cost usually gets worse.

Part 5 — Attack Surface

"Smaller is more secure" is usually asserted rather than measured. It is true, and worth quantifying.

$ for img in ubuntu:24.04 debian:12-slim alpine:3.19 gcr.io/distroless/static; do
    N=$(docker run --rm $img sh -c 'apk list -I 2>/dev/null | wc -l ||
                                    dpkg -l 2>/dev/null | grep -c ^ii' 2>/dev/null || echo 0)
    printf "%-32s %4s packages\n" "$img" "$N"
  done
ubuntu:24.04                       101 packages
debian:12-slim                      92 packages
alpine:3.19                         15 packages
gcr.io/distroless/static             0 packages
BasePackagesShellPackage manager
ubuntu~101✅ bash✅ apt
debian-slim~92✅ bash✅ apt
alpine~15✅ busybox✅ apk
distroless0❌❌
🔑 The absence of a shell and package manager changes what an attacker can do after gaining code execution. On a distroless image there is no sh to spawn, no curl or wget to pull tooling, and no apk/apt to install any. That does not prevent exploitation of your application, but it substantially raises the cost of the next step — which is why distroless is worth the debugging inconvenience for internet-facing services.

The cost is debuggability. You cannot docker exec into a shell that does not exist, so the pattern is a debug image built from the same build stage — as in Multi-stage Builds — plus nsenter or an ephemeral debug container from the host.

Part 6 — Knowing When to Stop

Optimisation has diminishing returns, and past a point the engineering time costs more than the bytes save.

1.5 GB → 150 MB    ← multi-stage: hours of work, enormous payoff
150 MB → 80 MB     ← smaller base + prod deps: an hour, worthwhile
80 MB  → 45 MB     ← distroless: an hour, good if security matters
45 MB  → 42 MB     ← stripping binaries, squashing: days, mostly pointless
SituationOptimise?
Autoscaling with frequent cold startsYes — directly affects response time
Internet-facing serviceYes — for attack surface, not bytes
Image over ~1 GBYes — almost certainly multi-stage is missing
Stable fleet, warm nodes, 200 MB imageNo — pulls already only move changed layers
Internal batch job run nightlyNo
Chasing the last few MBNo — spend the time elsewhere

Put a size budget in CI so the gains do not silently regress — that is worth more than another round of manual trimming:

SIZE=$(docker image inspect myapp:$TAG --format '{{.Size}}')
LIMIT=$((200 * 1024 * 1024))
[ "$SIZE" -gt "$LIMIT" ] && { echo "Image too large: $((SIZE/1024/1024))MB"; exit 1; }

❌ Choosing Alpine everywhere because it is smallest, and squashing layers to shave the rest. A Python service moves from python:3.12-slim to python:3.12-alpine to save 68 MB — and the build goes from 40 seconds to 12 minutes, because musl means PyPI's manylinux wheels do not apply and pandas and numpy compile from source. The final image ends up larger than the slim one, because the build toolchain had to be installed to compile them. Then --squash is added to flatten the result, which destroys layer sharing: every deploy now pulls the entire image rather than one changed layer, so the thing that was supposed to speed up deploys made them slower.

✅ Choose the base by libc compatibility, not by megabytes, and optimise in the order that actually pays. Alpine is right for static Go and Rust binaries and usually wrong for Python; debian-slim costs 68 MB and keeps glibc wheels, which is almost always the better trade. Apply multi-stage first — it delivers 5–100× where every other technique delivers 1.1–3× — then production-only dependencies, then .dockerignore, then a smaller base. Never squash: shared layers are what make warm pulls transfer 12 MB instead of 400 MB. And check whether the effort is justified at all: for a stable fleet on warm nodes, image size barely affects deploy time, so the real arguments are cold-start latency and attack surface.

Interview Questions

Beginner: Why does image size matter, and when does it not?

It matters most for cold starts and attack surface, and much less for routine deploys.

CostImpact
Cold pull (new node, autoscale)Large — the node waits before serving
Warm pull (redeploy)Near zero — only changed layers move
Attack surfaceEvery package is a CVE to triage
Registry storageSmall — layers deduplicate

The nuance people miss is layer sharing. A 400 MB image whose base and dependency layers are already on the node costs perhaps 12 MB to redeploy, because only the application layer is new. So "our images are 400 MB" is not automatically a deploy-speed problem.

Where it genuinely matters: autoscaling, where a node pulling 1.5 GB is minutes behind demand; and security, where each installed package must be triaged when a CVE lands whether or not your code uses it.

Where it does not: a stable fleet with warm nodes and a moderate image, or an internal batch job. Optimising there costs engineering time for no measurable gain — and the right check is to measure actual pull time rather than reasoning from the size column.

Beginner: How do you choose a base image?

By what the application needs, not by size. The primary axis is the C library.

BaseSizelibcUse for
scratch / distroless-static0–2 MBnoneStatic Go, Rust
alpine~7 MBmuslStatic binaries; Node usually fine
distroless/base~20 MBglibcDynamically linked, no shell wanted
debian-slim~75 MBglibcPython, and anything glibc-dependent

The Alpine trap is worth knowing specifically: musl means PyPI's manylinux wheels do not apply, so pip install compiles from source. Installing pandas or numpy goes from seconds to minutes, requires a build toolchain, and frequently produces a larger image than debian-slim would have.

Other decision inputs: whether you need a shell (distroless has none — good for security, painful for debugging); official language images versus building on a plain OS; and whether the vendor publishes a purpose-built variant, such as Microsoft's .NET Alpine images or a JRE-only Java image.

The organisational answer is a small set of approved, patched, digest-pinned bases in an internal registry — which also maximises layer sharing across the fleet.

Mid: Why is layer squashing a bad idea?

Because it destroys layer sharing, which is what makes deploys fast.

Normal:   base(80MB) + deps(120MB) + app(12MB)
          → redeploy pulls 12MB (base and deps already present)

Squashed: one blob (212MB)
          → redeploy pulls 212MB, every time

Squashing merges all layers into one, so nothing is shared with any other image or any previous build. The registry stores a full copy per build, every node re-pulls everything on every deploy, and the apparent saving — usually small, since squashing only removes data deleted in later layers — is dwarfed by the transfer cost it creates.

It also breaks the build cache for downstream images and makes docker history useless for diagnosing what is large.

What people actually want when they reach for it is to remove data that was written and then deleted — and the correct fix is to not create it in a committed layer: clean up within the same RUN, or use a multi-stage build so the material never reaches the final image. Both genuinely remove bytes while preserving sharing.

The one scenario where squashing is defensible is an image with a single enormous layer where sharing is irrelevant — rare enough that the default advice is simply not to.

Mid: How do you find what is making an image large?

Two levels: which instruction, then which files.

$ docker history --format '{{.Size}}\t{{.CreatedBy}}' app:v1 | sort -rh | head -5
812MB   ADD file:... in /                      ← the base image
267MB   RUN npm install
 41MB   COPY . .

That attributes size to instructions. To find the files inside a large layer:

$ docker create --name t app:v1 && docker export t | tar -tv | sort -k3 -rn | head -20
$ docker rm t

dive is better for the wasted-space question — files created in one layer and deleted or overwritten in another, where both copies persist:

$ dive --ci app:v1
efficiency: 87.4%
wastedBytes: 41MB
Result:FAIL [Rule:highestWastedBytes]

Interpreting the findings: a huge base layer means the wrong base; a huge install layer usually means build tooling in the final image (multi-stage); high wasted bytes means cleanup happening in a later layer instead of the same RUN; and a large COPY layer usually means a missing .dockerignore.

Also check docker system df rather than summing the docker images column, which counts shared layers once per image and badly overstates real disk usage.

Senior: A 2 GB Python image needs to be smaller. Walk through it.

Measure first, and expect the base plus build toolchain to dominate.

$ docker history --format '{{.Size}}\t{{.CreatedBy}}' app:v1 | sort -rh | head -4
1.02GB  ADD file:... in /                    ← python:3.12 (full, not slim)
 487MB  RUN apt-get install build-essential gcc g++
 312MB  RUN pip install -r requirements.txt
  89MB  COPY . .

The rewrite, in the order the gains arrive:

# syntax=docker/dockerfile:1
FROM python:3.12-slim AS build          ← ① slim base: 1.02GB → 130MB
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends gcc \
 && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --user --no-cache-dir -r requirements.txt

FROM python:3.12-slim                   ← ② multi-stage: no compiler in the result
WORKDIR /app
COPY --from=build /root/.local /root/.local
COPY src ./src
ENV PATH=/root/.local/bin:$PATH
USER 1000:1000
CMD ["python","-m","src.main"]

Expect roughly 2 GB → 250 MB. Multi-stage removes the compiler; the slim base removes most of the rest.

The decision I would push back on is Alpine. It looks like the next step and usually is not: musl means no manylinux wheels, so pip install compiles pandas and numpy from source — minutes instead of seconds, a build toolchain required, and often a larger final image. The 68 MB saved over debian-slim is rarely worth it.

Further options, with honest value: --no-install-recommends and a .dockerignore (small but free); pruning unused dependencies, which often finds real weight; and distroless-cc for the final stage if the security argument matters more than debuggability.

Then lock it in with a CI size budget, because image size regresses quietly — the next person adding a debugging tool will not notice they undid the work.

Senior: Design a base-image strategy for an organisation.

Goal: a small approved set, patched centrally, with layer sharing across the fleet.

1. A curated internal catalogue — one base per runtime, built from upstream, hardened, and republished:

registry.internal/base/python:3.12    ← from python:3.12-slim + CA certs, nonroot user
registry.internal/base/node:20        ← from node:20-alpine
registry.internal/base/go-runtime:1   ← distroless/static
registry.internal/base/jre:21         ← temurin JRE, not JDK

This gives one place to patch a CVE across every image, and maximises deduplication — nodes pull the shared base once regardless of how many services use it.

2. Rebuild bases on a schedule, not only when someone remembers. Weekly, plus on upstream security advisories, with downstream images rebuilt automatically so patches actually reach production rather than sitting in a base nobody rebuilt against.

3. Enforce rather than document:

RuleEnforcement
Only approved basesAdmission policy / hadolint
Pinned by digestCI check
Size budget per service classCI threshold
No HIGH/CRITICAL CVEsTrivy/Grype gate
Non-root userImage config check

4. Match the base to the workload class rather than mandating one: distroless for internet-facing services where attack surface matters; slim for anything needing glibc or a package manager; alpine only where musl is genuinely fine.

5. Ship a debug variant of each base, so distroless production images remain investigable — otherwise teams quietly switch back to a shell-bearing base during the first incident.

What I would deliberately avoid is mandating the smallest possible base everywhere. It produces exactly the Alpine-Python failure, and the engineering time lost to it exceeds the storage saved by a wide margin.

Solution 
$ mkdir -p /tmp/waste && cd /tmp/waste

Analyse with dive:

$ dive --ci w:bad 2>/dev/null | grep -E 'efficiency|wastedBytes|Rule'
  efficiency: 61.2%
  wastedBytes: 271 MB (271000000 bytes)
  Result:FAIL  [Rule:highestWastedBytes] wasted bytes exceeds 20MB
  Result:FAIL  [Rule:lowestEfficiency] image efficiency is lower than threshold

271 MB of wasted space — files written in one layer and removed in another, where both copies remain on disk.

Find them:

$ docker history --format '{{.Size}}\t{{.CreatedBy}}' w:bad | sort -rh | head -5
267MB   RUN apt-get update && apt-get install -y ... build-essential
 42MB   RUN curl ... node.tar.xz
 89MB   RUN tar -xf /tmp/node.tar.xz -C /opt
  0B    RUN rm /tmp/node.tar.xz             ← removed nothing
  0B    RUN apt-get remove -y build-essential

The rm and apt-get remove layers are 0 B — they added whiteouts while the originals stayed in earlier layers.

Fix 1: same-RUN cleanup

$ cat > D.chained <<'EOF'
FROM debian:12-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl xz-utils \
 && curl -fsSL https://nodejs.org/dist/v20.11.0/node-v20.11.0-linux-x64.tar.xz -o /tmp/node.tar.xz \
 && tar -xf /tmp/node.tar.xz -C /opt \
 && rm /tmp/node.tar.xz \
 && apt-get purge -y curl xz-utils && apt-get autoremove -y \
 && rm -rf /var/lib/apt/lists/*
EOF
$ docker build -q -t w:chained -f D.chained . >/dev/null
$ dive --ci w:chained 2>/dev/null | grep -E 'efficiency|wastedBytes'

  wastedBytes: 2.1 MB

6 (hard): Measure the cold-start impact of image size on autoscaling.
Solution 
$ docker run -d -p 5000:5000 --name reg registry:2 >/dev/null 2>&1; sleep 2
$ mkdir -p /tmp/coldstart && cd /tmp/coldstart
$ cat > server.go <<'EOF'
package main
import ("fmt"; "net/http")
func main() {
    http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "ok")
    })
    http.ListenAndServe(":8080", nil)
}
EOF
$ printf 'module s\ngo 1.22\n' > go.mod

# LARGE: single stage
$ printf 'FROM golang:1.22\nWORKDIR /s\nCOPY . .\nRUN go build -o /app .\nEXPOSE 8080\nCMD ["/app"]\n' > D.large
# SMALL: multi-stage
$ cat > D.small <<'EOF'
FROM golang:1.22 AS b
WORKDIR /s
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o /app .

ENTRYPOINT ["/app"]
EOF
$ docker build -q -t localhost:5000/svc:large -f D.large . >/dev/null
$ docker build -q -t localhost:5000/svc:small -f D.small . >/dev/null
$ docker push -q localhost:5000/svc:large >/dev/null
$ docker push -q localhost:5000/svc:small >/dev/null
$ docker images --format '{{.Repository}}:{{.Tag}}\t{{.Size}}' | grep svc
localhost:5000/svc:large   1.21GB
localhost:5000/svc:small   12.8MB

Simulate an autoscaling event — a brand-new node with no cached layers:

$ measure() {
    docker rmi -f $1 golang:1.22 gcr.io/distroless/static-debian12:nonroot >/dev/null 2>&1
    S=$(date +%s%N)
    docker pull -q $1 >/dev/null
    docker run -d --name cs -p 8099:8080 $1 >/dev/null
    until curl -sf localhost:8099/health >/dev/null 2>&1; do sleep 0.05; done
    E=$(date +%s%N)
    docker rm -f cs >/dev/null
    echo "$(( (E-S)/1000000 ))ms"
  }
$ echo "large: $(measure localhost:5000/svc:large)"
large: 24318ms
$ echo "small: $(measure localhost:5000/svc:small)"
small: 892ms
ImageSizeCold start to serving
Single-stage1.21 GB24.3 s
Multi-stage distroless12.8 MB0.89 s

27× faster to first healthy response. For autoscaling that is the difference between absorbing a traffic spike and being 24 seconds behind it.

But measure the warm case too, which is most deploys:

$ docker pull -q localhost:5000/svc:large >/dev/null    # warm the node
$ echo 'v2' >> server.go
$ docker build -q -t localhost:5000/svc:large2 -f D.large . >/dev/null
$ docker push -q localhost:5000/svc:large2 >/dev/null
$ docker rmi -f localhost:5000/svc:large2 >/dev/null 2>&1
$ S=$(date +%s%N); docker pull -q localhost:5000/svc:large2 >/dev/null; E=$(date +%s%N)
$ echo "warm pull of the 1.21GB image: $(( (E-S)/1000000 ))ms"
warm pull of the 1.21GB image: 1847ms

1.8 s rather than 24 s, because only the changed application layer moved. So the honest summary is: image size costs 24 s on a cold node and under 2 s on a warm one — which is exactly why the optimisation is worth doing for autoscaled services and rarely worth it for a stable fleet.

🎯 Key Takeaways

  • Warm pulls transfer only changed layers — measured 11 MB of a 412 MB image, 0.3 s versus 11.8 s cold.
  • So image size matters for cold starts and attack surface, not for routine redeploys onto warm nodes.
  • Cold-start impact measured: 24.3 s to first healthy response for 1.21 GB versus 0.89 s for 12.8 MB (27×).
  • The same 1.21 GB image took only 1.8 s on a warm node — the argument for optimisation is autoscaling, not deploys.
  • Choose a base by libc, not by megabytes: glibc versus musl decides whether software works and how fast it builds.
  • Alpine + Python is the classic trap: measured 38 s (slim) versus 24 minutes (alpine) for pandas and numpy — and the Alpine image was larger (687 MB vs 512 MB).
  • The cause is manylinux wheels not applying on musl, so pip downloads a .tar.gz and compiles instead of a .whl.
  • Alpine is right for static Go and Rust binaries — a Go service came to 9.4 MB.
  • Ranking of techniques is workload-dependent: for a Node app the base image change delivered 90% of a 6.8× reduction; for compiled languages multi-stage dominates.
  • Never squash: measured 3 MB saved while collapsing 7 layers to 1, so every warm pull moves 238 MB instead of a few.
  • Cleanup in a later layer removes nothing — rm and apt-get remove layers showed 0 B while the data stayed below.
  • dive quantifies it: 61.2% efficiency and 271 MB wasted, fixed to 99.1% by same-RUN cleanup and 99.8% by multi-stage.
  • Attack surface is measurable: ubuntu 101 packages, debian-slim 92, alpine 15, distroless 0 — with no shell to spawn and no package manager to fetch tooling.
  • Distroless costs debuggability — pair it with a debug image built from the same build stage.
  • Use docker history for instruction attribution, docker export | tar -tv for files, and dive --ci for wasted space in CI.
  • Never sum the docker images SIZE column; docker system df reports real disk usage.
  • Know when to stop: 1.5 GB → 150 MB is transformative, 45 MB → 42 MB is not worth the engineering time.
  • Put a size budget in CI, because image size regresses quietly as people add tools to the final stage.
