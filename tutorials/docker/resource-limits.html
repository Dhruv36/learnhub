Resource Limits & the OOM Killer Production Concerns

What you'll master: why an unlimited container is a host outage waiting for a bad deploy; what --memory actually enforces and why exit 137 is not a bug in your application; the page-cache accounting trap that makes docker stats report 94% memory use on an idle container and how to read the real number; the difference between --cpus (a hard quota that throttles) and --cpu-shares (a weight that only matters under contention), and the latency cliff quota produces even at low average utilisation; the single most expensive default in containerised runtimes — the process inside sees the host's CPUs and RAM, not yours — and the fix for the JVM, Node, Go and Python; PID limits and the fork bomb they stop; how to size limits from measurement rather than superstition; and how to tell an OOM kill from a crash, from a liveness restart, in one command. Prerequisites: cgroups, Process Model, PID 1 & Signals, Namespaces.

Part 1 — The Default Is Unlimited

A container with no limits is a normal process with a normal appetite. Nothing about being containerised restrains it: it can allocate until the host's memory is gone, spin every core, and open every file descriptor the kernel allows.

$ docker run -d --name greedy alpine sh -c 'while true; do :; done'
$ docker inspect greedy --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}} {{.HostConfig.PidsLimit}}'
0 0 0                              ← zero means UNLIMITED, in all three cases

$ docker stats --no-stream
CONTAINER  CPU %    MEM USAGE / LIMIT     MEM %
greedy     100.04%  1.1MiB / 15.61GiB     0.01%
                              ↑ "LIMIT" is the HOST's total RAM, not a limit

The failure this produces is not subtle, and it is not the leaking container that suffers most:

t=0     api container has a leak; RSS climbs past its normal 400 MB
t=6m    host free memory approaches zero; the kernel starts reclaiming page cache
t=7m    every container's disk reads slow down (cache evicted) — unrelated services degrade
t=8m    global OOM killer fires and picks by oom_score, which favours BIG processes
t=8m    it kills postgres (2.1 GB RSS), not the 3.4 GB api that caused it
t=8m    sshd is also a candidate; the host may become unreachable
🔑 Limits are not only about capping the offender — they are about localising the damage. With --memory set, the kernel fires a cgroup OOM kill that can only select processes inside that cgroup. The leaking container dies, the restart policy restarts it, and every other service on the host is untouched. Without limits, a memory bug in your least important service is a host-wide incident whose victim is chosen by a heuristic you do not control.

Part 2 — Memory, and Exit 137

--memory sets memory.max on the container's cgroup. When the cgroup cannot reclaim enough to satisfy an allocation, the kernel OOM killer fires inside that cgroup:

$ docker run --rm -m 128m --name hog alpine sh -c \
    'dd if=/dev/zero of=/dev/shm/x bs=1M count=200'
$ echo $?
137
Exit codeSignalMeaningTypical cause
137128 + 9 (SIGKILL)Killed, no chance to clean upOOM, or docker kill, or a stop timeout expiring
143128 + 15 (SIGTERM)Asked to stop and didNormal docker stop
139128 + 11 (SIGSEGV)SegfaultA real crash
1—Application error exitYour code
125 / 126 / 127—Daemon error / not executable / not foundBad command or image

137 alone is ambiguous — it also appears when a container ignores SIGTERM and the stop timeout expires (Process Model). One field disambiguates it:

$ docker inspect hog --format '{{.State.OOMKilled}} {{.State.ExitCode}} {{.State.Error}}'
true 137

$ dmesg -T | tail -4
[Tue Aug 19 12:31:02] Memory cgroup out of memory: Killed process 20481 (dd)
  total-vm:206184kB, anon-rss:130024kB, file-rss:1436kB
[Tue Aug 19 12:31:02] Memory cgroup stats for /docker/8f21c0e4: anon 129.9M file 0
                       ↑ "Memory cgroup out of memory" = the container's own limit,
                         NOT a host-wide OOM. Exactly what you want to see.
⚠️ The OOM killer chooses a process, not the container. If your container runs several processes, the kernel may kill a worker and leave PID 1 alive — so the container stays Up, with a silently missing worker and no restart. This is one more argument for one process per container, and for --oom-kill-disable being a trap: it does not prevent the OOM, it freezes the cgroup until memory is freed, which usually means a hung container instead of a dead one.

The page-cache accounting trap

A cgroup's memory usage includes the page cache for files that container read or wrote. Page cache is reclaimable — it is not a leak — but docker stats reports it as usage:

$ docker run -d --name reader -m 512m alpine sh -c 'sleep 3600'
$ docker stats --no-stream reader
CONTAINER  MEM USAGE / LIMIT   MEM %
reader     1.2MiB / 512MiB     0.23%

$ docker exec reader sh -c 'dd if=/dev/zero of=/tmp/big bs=1M count=400 && sync'
$ docker stats --no-stream reader
CONTAINER  MEM USAGE / LIMIT   MEM %
reader     402.1MiB / 512MiB   78.54%     ← "78% memory used" — by a sleeping shell

$ docker exec reader cat /sys/fs/cgroup/memory.stat | head -3
anon 1298432                              ← 1.2 MB actually anonymous (the real usage)
file 419430400                            ← 400 MB page cache (reclaimable)
kernel 1105920

The alert this generates ("container at 94% of its memory limit!") is almost always this. Compute the number that matters:

  real usage  =  memory.current  −  inactive_file
  (cgroup v2: /sys/fs/cgroup/memory.current and memory.stat)

$ docker exec reader sh -c \
   'echo $(( ($(cat /sys/fs/cgroup/memory.current) - \
              $(awk "/^inactive_file/{print \$2}" /sys/fs/cgroup/memory.stat)) / 1048576 ))MB'
2MB                                       ← the honest figure

$ docker exec reader sh -c 'dd if=/dev/zero of=/dev/null bs=1M count=600'
   (memory pressure) → cache is reclaimed automatically, no OOM
$ docker stats --no-stream reader
reader     3.4MiB / 512MiB     0.66%      ← the "78%" evaporated on demand

Swap deserves one clarification because the flag is counter-intuitive: --memory-swap is the combined limit, not the swap portion.

FlagsRAMSwap available
-m 512m (default)512 MB512 MB (total 1 GB)
-m 512m --memory-swap=512m512 MBNone — swap disabled
-m 512m --memory-swap=2g512 MB1.5 GB
-m 512m --memory-swap=-1512 MBUnlimited

Disabling swap (--memory-swap equal to --memory) is usually right for services: a container that swaps is not working, it is dying slowly while producing terrible latency. Fail fast and let the restart policy act.

Part 3 — CPU: Quota Versus Weight

Two mechanisms, constantly confused, with completely different behaviour under load:

--cpus=1.5 (quota)--cpu-shares=512 (weight)
cgroup filecpu.max = 150000 100000cpu.weight
Effect on an idle hostStill capped at 1.5 coresNone — can use everything
Effect under contentionCapped at 1.5Gets its proportional share
Predictable?✅ Absolutely❌ Depends on the neighbours
Wastes idle capacity?✅ Yes, by design❌ No
Causes throttling?✅ Yes — the whole point❌ Never
$ docker run --rm --cpus=1.5 alpine cat /sys/fs/cgroup/cpu.max
150000 100000                     ← 150 ms of CPU time per 100 ms period

$ docker run --rm --cpu-shares=512 alpine cat /sys/fs/cgroup/cpu.weight
20                                ← a weight; means nothing until someone competes

The throttling cliff

Quota is enforced per 100 ms period. A container that exhausts its quota is stopped until the next period begins — which is invisible in average CPU graphs and extremely visible in p99 latency, as measured in cgroups:

a request needing 200 ms of CPU across 4 threads, with --cpus=1:
  period 1 (0–100ms):   100 ms of quota consumed by the 4 threads in 25 ms wall time
  period 1 (25–100ms):  THROTTLED. All four threads frozen for 75 ms.
  period 2 (100–200ms): another 100 ms of quota, consumed in 25 ms
  period 2 (125–200ms): THROTTLED again
  total wall time: 200 ms of work took 225 ms, with two 75 ms freezes

$ docker exec app cat /sys/fs/cgroup/cpu.stat
nr_periods 84021
nr_throttled 31447            ← 37% of periods hit the cap
throttled_usec 402910000      ← 403 seconds of frozen time
ConfigurationAverage CPUp50 latencyp99 latencyThrottled periods
No limit62%18 ms41 ms0%
--cpus=462%18 ms44 ms0.2%
--cpus=262%21 ms96 ms11%
--cpus=162%34 ms488 ms37%
🔑 Average CPU is identical in every row — 62% — while p99 grows 12×. This is why "the container is only using 62% of its CPU, so the limit is fine" is wrong and why cpu.stat's nr_throttled belongs on your dashboard next to utilisation. A latency-sensitive service should be sized so throttling is rare (target under ~1% of periods), or given a weight instead of a quota so it can burst.

--cpuset-cpus is the third option and a specialist one: it pins the container to specific cores. It genuinely helps for NUMA locality and cache-sensitive workloads, and it hurts everywhere else by preventing the scheduler from balancing. Use it when you have measured a benefit, not by default.

Part 4 — The Process Inside Cannot See Your Limit

This is the most expensive default in containerised runtimes. /proc/cpuinfo and /proc/meminfo are not namespaced — as established in Namespaces, the container sees the host's values. Every runtime that sizes its thread pools or heap from those files sizes them wrong:

$ nproc                                   # on the host
16
$ free -g | awk '/^Mem/{print $2"GB"}'
62GB

$ docker run --rm --cpus=2 -m 512m alpine sh -c 'nproc; free -m | awk "/^Mem/{print \$2}"'
16                                        ← sees 16 CPUs; it has 2
64243                                     ← sees 62 GB; it has 0.5

JVM 8 (old builds)Reads the hostHeap = 15 GB → OOM kill at 512 MBUpgrade, or set -Xmx explicitly
GoGOMAXPROCS = host CPUs16 OS threads on a 2-core quota → heavy throttlingautomaxprocs, or set GOMAXPROCS=2
Node.jsHeap default from host RAM; libuv pool = 4Old-space can exceed the limit → OOM kill--max-old-space-size=384
Pythonos.cpu_count() = host CPUs16 gunicorn workers × 80 MB = 1.3 GB → OOMCompute workers from the limit
nginxworker_processes auto = host CPUs16 workers on 2 coresSet it explicitly
.NET ≥ 3.0Container-aware✅ Correct—
$ docker run --rm -m 512m eclipse-temurin:21 java -XX:+PrintFlagsFinal -version \
    | grep -E 'MaxHeapSize|ActiveProcessorCount'
   size_t MaxHeapSize = 134217728    {product} {ergonomic}      ← 128 MB = ¼ of 512
      int ActiveProcessorCount = -1  {product} {default}

$ docker run --rm -m 512m eclipse-temurin:21 java \
    -XX:MaxRAMPercentage=75 -XX:+PrintFlagsFinal -version | grep MaxHeapSize
   size_t MaxHeapSize = 402653184                              ← 384 MB, deliberate
⚠️ A JVM heap set to 75% of the memory limit is not 25% of headroom — it is barely enough. The container must also hold metaspace, thread stacks (1 MB each), code cache, direct byte buffers, GC structures and the JVM itself, none of which count toward the heap. A heap at 100% of the limit is a guaranteed exit 137 that looks like a memory leak and is not. The same arithmetic applies to Node's --max-old-space-size: leave 25–30% for everything outside the managed heap.

Part 5 — PIDs, File Descriptors and I/O

Memory and CPU get the attention; the process table is what actually takes hosts down, because exhausting it stops everything from forking, including your shell:

$ docker run --rm alpine sh -c ':(){ :|:& };:'        # a fork bomb — DO NOT run unlimited
   → host process table exhausted; ssh cannot fork; reboot required

$ docker run --rm --pids-limit=100 alpine sh -c ':(){ :|:& };:'
sh: can't fork: Resource temporarily unavailable
   → the container is stuck; the host is completely unaffected
$ docker exec other-container echo ok
ok

A PID limit costs nothing and bounds an entire class of failure. It also catches thread leaks, which are far more common than deliberate fork bombs — a thread is a task and counts against the limit:

$ docker run -d --pids-limit=200 --name app myapp
$ docker exec app cat /sys/fs/cgroup/pids.current /sys/fs/cgroup/pids.max
47
200
$ watch -n60 'docker exec app cat /sys/fs/cgroup/pids.current'
47 ... 89 ... 143 ... 197        ← a thread leak, visible before it becomes an incident
LimitReasonable valueDetects / prevents
--pids-limit2–4× steady-state threadsFork bombs, thread leaks

The /dev/shm default catches people constantly:

$ docker run --rm python:3.12 df -h /dev/shm | tail -1
shm              64M     0   64M   0% /dev/shm      ← 64 MB regardless of -m

$ docker run --rm --shm-size=1g python:3.12 df -h /dev/shm | tail -1
shm             1.0G     0  1.0G   0% /dev/shm

Part 6 — Sizing Limits From Measurement

Limits chosen by guesswork fail in both directions: too low and you get OOM kills or throttling under normal load; too high and the limit never binds, which is the same as having none. The method is mechanical:

① Run without a limit under REALISTIC load (production traffic replay, or a soak test)
② Record the real numbers, not docker stats' inflated ones:
     memory  = max over the window of (memory.current − inactive_file)
     cpu     = p99 of utilisation, plus nr_throttled if any limit is already set
③ Memory limit  = peak_anon × 1.5     (GC languages need headroom to avoid thrash)
④ CPU limit     = p99 × 1.5, or omit the quota and use a weight for latency-critical
   services that are allowed to burst
⑤ PIDs limit    = steady_state_threads × 3
⑥ Deploy, then WATCH: OOMKilled events, nr_throttled, and how close usage runs to
   the cap. Re-derive quarterly — workloads change.
SymptomDiagnosisAction
Exit 137, OOMKilled=trueLimit genuinely exceededRaise the limit or fix the leak — check the trend first
Exit 137, OOMKilled=falseIgnored SIGTERM, stop timeout expiredSignal handling, not memory
Memory climbs to the cap then flattensNormal for a JVM/Go/Node heapNothing. Managed heaps grow to fill their budget.
Memory climbs across restarts, never flattensA real leakHeap dump; raising the limit only delays it
p99 latency spikes, average CPU lowCFS throttlingCheck nr_throttled; raise the quota or use a weight
"94% of memory" alert on an idle servicePage cache counted as usageAlert on anon, not memory.current
Container Up but a worker vanishedOOM killed a child, PID 1 survivedOne process per container; check dmesg

Two operational habits complete this. Alert on OOM kill events rather than on memory percentage — the percentage is noisy and the kill is unambiguous. And set restart: unless-stopped so that an OOM kill becomes a brief restart rather than a missing service, while the alert makes sure it is still investigated rather than silently absorbed.

❌ No limits anywhere, because "the host has 64 GB and Kubernetes will handle it later". A memory leak in a low-traffic reporting service climbs past 30 GB over a weekend. The host's page cache is evicted first, so every other container's disk reads slow down and the database's p99 doubles for reasons nobody can explain. When the global OOM killer finally fires it picks by oom_score, which favours the largest resident process — so it kills Postgres, not the reporting service, and takes the platform down. Elsewhere, someone did set --cpus=1 on a four-thread API because "it only uses 60% of a core on average", and its p99 is 488 ms with 37% of periods throttled, which the CPU dashboard shows as a comfortable 62%. A Java 8 service reads the host's 62 GB and sizes a 15 GB heap inside a 512 MB limit, dying at exit 137 on every deploy, and is written off as "a bad image". And an alert fires nightly saying a sleeping container is at 94% memory, which is page cache, so the team mutes it — along with the real alerts that later share the same rule.

✅ Set memory, CPU and PID limits on every container, derive them from measurement, and read the right counters. Give every container a memory limit so an OOM is a cgroup kill that removes the offender and leaves the host intact, and confirm it with State.OOMKilled plus the "Memory cgroup out of memory" line in dmesg. Size it at 1.5× measured peak anonymous memory — memory.current − inactive_file, not docker stats — and alert on OOM kill events rather than a percentage that page cache inflates. Tell the runtime what it actually has: -XX:MaxRAMPercentage=75, --max-old-space-size, automaxprocs, workers computed from the quota — because /proc reports the host. Put nr_throttled on the dashboard next to utilisation, and for latency-sensitive services prefer a weight over a quota so they may burst. Add --pids-limit at 3× steady-state threads, which costs nothing and turns a fork bomb or a thread leak into one dead container instead of an unreachable host.

Interview Questions

Beginner: What does exit code 137 mean?

128 + 9 — the process was killed with SIGKILL. By far the most common cause is the kernel OOM killer firing because the container hit its memory limit.

$ docker inspect app --format '{{.State.ExitCode}} {{.State.OOMKilled}}'
137 true
$ dmesg -T | grep -i 'cgroup out of memory' | tail -1
Memory cgroup out of memory: Killed process 20481 (java) anon-rss:522104kB

The important nuance: 137 does not always mean OOM. It also appears when a container ignores SIGTERM and Docker escalates to SIGKILL after the stop timeout (Process Model). State.OOMKilled is what tells the two apart, and answering that distinction is what separates a memorised answer from an understood one.

CodeSignalMeaning
137SIGKILLOOM, docker kill, or stop timeout expired
143SIGTERMClean docker stop
139SIGSEGVSegfault — a real crash
Beginner: What happens if you never set resource limits?

Nothing constrains the container — 0 means unlimited for memory, CPU and PIDs. It can allocate until the host is out of memory and use every core.

The failure mode is worse than "the greedy container dies", because the global OOM killer chooses by oom_score, which is weighted by resident size:

leaking service reaches 3.4 GB → host memory exhausted
global OOM killer selects the LARGEST process → postgres (2.1 GB)
the database dies; the leaking service keeps running

With --memory set, the kill happens in the container's own cgroup and can only select processes inside it. That is the real argument for limits: they localise damage, so a bug in your least important service cannot choose your most important one as its victim.

The same applies to CPU (an unlimited container starves its neighbours) and to PIDs (a fork bomb exhausts the host's process table, so nothing — including SSH — can fork).

Mid: docker stats shows a container at 94% of its memory limit but it never OOMs. Explain.

Page cache. A cgroup's memory accounting includes the page cache for files that container read or wrote, and docker stats reports the total. Cache is reclaimable, so it is not usage in any meaningful sense.

$ docker exec app cat /sys/fs/cgroup/memory.stat | head -2
anon 1298432          ← 1.2 MB actually anonymous — the real usage
file 419430400        ← 400 MB of page cache

The number that matters is memory.current − inactive_file. Under pressure the kernel reclaims cache before it OOMs, which is exactly why the container sits at 94% indefinitely without dying.

Why it matters operationally: alerting on memory percentage generates nightly pages for containers that write logs or read large files, and the team mutes the rule — taking the real alerts with it. Alert on OOM kill events instead: unambiguous, and it fires exactly when something is wrong.

The related trap in the other direction: a JVM or Go service whose memory climbs to the cap and flattens is usually healthy — a managed heap expands to fill its budget. A leak looks different: it climbs across restarts and never flattens. Confusing "grew to the limit" with "leaking" leads to raising limits forever.

Mid: A service shows 60% average CPU but terrible p99 latency. What do you check?

CFS throttling. --cpus is a quota per 100 ms period; a container that exhausts it is frozen until the next period. Averages hide this completely.

$ docker exec app cat /sys/fs/cgroup/cpu.stat
nr_periods 84021
nr_throttled 31447            ← 37% of periods hit the cap
throttled_usec 402910000      ← 403 s of frozen time
LimitAverage CPUp99Throttled
none62%41 ms0%
--cpus=262%96 ms11%
--cpus=162%488 ms37%

Average utilisation is identical in all three rows. A multithreaded process burns its quota in a fraction of the period — four threads consume 100 ms of quota in 25 ms of wall time — and then all four freeze for the remaining 75 ms.

Fixes, in order: raise the quota until nr_throttled is under ~1% of periods; align the runtime's parallelism with the quota (GOMAXPROCS, ActiveProcessorCount, worker counts) so it stops trying to use cores it does not have; or for latency-critical services drop the quota entirely and use --cpu-shares, accepting less predictability in exchange for the ability to burst.

The dashboard lesson: nr_throttled belongs next to CPU utilisation. Without it, this class of problem is invisible and gets misdiagnosed as a database or network issue.

Senior: How do you decide limits for a fleet of services, and what goes wrong at each extreme?

Measure, apply a headroom factor, then watch the counters that prove the choice was right. Both extremes fail, in different and equally expensive ways:

Limits too lowLimits too high (or absent)
MemoryOOM kills under normal peaks; restart loops during traffic spikesThe limit never binds — a leak becomes a host incident with an unrelated victim
CPUThrottling; p99 collapses while averages look fineNoisy neighbours; no capacity planning signal at all
DensityPoor — you reserved capacity nobody usesOvercommitted; one bad deploy takes the node

The method: run unlimited under realistic load, take peak anonymous memory (memory.current − inactive_file) and p99 CPU, then set memory at 1.5× peak anon and CPU at 1.5× p99. Set PIDs at 3× steady-state threads. Re-derive quarterly, because workloads drift and a limit set from last year's traffic is a guess wearing a number.

Where I deviate deliberately:

  • Latency-critical services get a memory limit but no CPU quota — a weight instead, so they can burst. Predictability of scheduling matters less than p99 for these, and quota buys predictability by destroying tail latency.
  • Batch and background jobs get hard quotas and low weights. They are the ones that should absorb throttling.
  • Memory is never overcommitted on a node — sum of limits ≤ node capacity minus a system reserve. CPU may be, because throttling degrades and OOM kills.

Monitoring that makes the whole thing self-correcting: OOM kill events (not memory percentage), nr_throttled as a ratio of nr_periods, pids.current against its limit, and a "limit utilisation" panel that catches both a service running at 95% of its cap and one at 4% — the second is wasted reservation and the more common problem at scale.

The organisational half: defaults in a shared template, so a new service inherits reasonable limits without anyone thinking about it, and an admission check that rejects containers with no memory limit at all. Per-service tuning is worthwhile for the top ten services by cost and a waste of time for the other two hundred.

Senior: A Java service is OOM-killed at 512 MB with -Xmx512m. Explain and fix.

The heap is not the process. -Xmx bounds one region; the JVM's total RSS includes several others, none of which count toward it:

heap            -Xmx512m                        512 MB
metaspace       class metadata, unbounded by default   ~80 MB
code cache      JIT-compiled code               ~50 MB
thread stacks   1 MB × 200 threads              ~200 MB   ← the usual surprise
GC structures   card tables, remembered sets    ~40 MB
direct buffers  NIO, Netty — OFF-heap entirely  ~100 MB
JVM itself      ~30 MB
                                                ─────────
                                          total ~1 GB in a 512 MB container

The fix is to size from the container limit, not the heap, and to bound the parts that are unbounded by default:

docker run -m 1g \
  -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=60 \
                        -XX:MaxMetaspaceSize=128m \
                        -XX:MaxDirectMemorySize=128m \
                        -Xss512k" \
  myapp

MaxRAMPercentage is preferable to a fixed -Xmx because it tracks the container limit — change the limit and the heap follows, so the two can never drift apart in a config file.

Diagnosis, so this is not guesswork: -XX:NativeMemoryTracking=summary plus jcmd VM.native_memory summary attributes RSS to each region and usually points straight at thread stacks or direct buffers. If the count of threads is the problem, the answer is a bounded pool, not more memory.

The general lesson worth stating: every managed runtime has this shape. Node's --max-old-space-size excludes buffers and the C++ heap; Python's allocator holds arenas the OS never gets back; Go's GOGC trades RSS for CPU. Budget roughly 25–30% of the container limit for everything outside the managed heap, and verify it with a soak test rather than arithmetic alone.

5 (hard): Contain a fork bomb and detect a thread leak before it becomes an incident.
Solution

Run this on a throwaway VM only. The unlimited case requires a reboot.

① no limit — the host, not the container, is the casualty
$ docker run --rm -d alpine sh -c ':(){ :|:& };:'
$ ssh host
-bash: fork: retry: Resource temporarily unavailable
-bash: fork: Resource temporarily unavailable        ← cannot even run ps
   → the container's cgroup has no pids.max, so it consumes the host's process table
   → recovery: hard reboot

② with a PID limit
$ docker run --rm --pids-limit=100 --name bomb -d alpine sh -c ':(){ :|:& };:'
$ docker exec other echo ok
ok                                                   ← the rest of the host is fine
$ docker logs bomb | tail -2
sh: can't fork: Resource temporarily unavailable
$ docker exec bomb cat /sys/fs/cgroup/pids.current /sys/fs/cgroup/pids.max
100
100                                                  ← pinned at the ceiling, contained
$ docker rm -f bomb

Now the realistic version — a thread leak, which is the same mechanism at a slower pace:

$ cat > leak.js <<'EOF'
const { Worker } = require('worker_threads');
const held = [];
setInterval(() => {                                  // leaks one worker every 2 s
  held.push(new Worker('setInterval(()=>{},1e9)', { eval: true }));
}, 2000);
EOF
$ docker run -d --name leaky --pids-limit=60 -v $PWD/leak.js:/leak.js \
    node:20-alpine node /leak.js

$ while sleep 20; do
    printf '%s pids=%s/%s status=%s\n' "$(date +%T)" \
      "$(docker exec leaky cat /sys/fs/cgroup/pids.current 2>/dev/null)" \
      "$(docker exec leaky cat /sys/fs/cgroup/pids.max 2>/dev/null)" \
      "$(docker inspect leaky --format '{{.State.Status}}')"
  done
12:40:03 pids=18/60 status=running
12:40:23 pids=28/60 status=running
12:40:43 pids=38/60 status=running      ← a clean linear ramp: unambiguous leak signal
12:41:03 pids=49/60 status=running
12:41:23 pids=59/60 status=running
12:41:43 pids=60/60 status=running      ← pinned at the ceiling
$ docker logs leaky | tail -2
Error: Resource temporarily unavailable
    at new Worker (node:internal/worker:...)

Contrast the two diagnostics, which is the real point of the limit:

No --pids-limit--pids-limit=60
SymptomHost cannot fork; SSH failsOne container errors
Blast radiusEvery service on the hostThe leaking service

$ docker exec leaky sh -c \

🎯 Key Takeaways

  • Memory, CPU and PID limits all default to unlimited (0), and docker stats' "LIMIT" column shows host RAM when none is set.
  • Limits localise damage: a cgroup OOM kills inside the container, while a host OOM picks by oom_score and often kills the database instead of the leaker.
  • Exit 137 = 128 + SIGKILL, usually OOM — but also a stop timeout on an ignored SIGTERM. .State.OOMKilled is what distinguishes them.
  • dmesg saying "Memory cgroup out of memory" confirms the container's own limit fired, not a host-wide event.
  • The OOM killer picks a process: in a multi-process container it can kill a worker and leave PID 1 Up with a silently missing child.
  • --oom-kill-disable freezes the cgroup rather than preventing the OOM — a hung container instead of a dead one.
  • Page cache counts toward cgroup memory — measured: a sleeping container reported 78.54% after writing a 400 MB file, with 1.2 MB actually anonymous.
  • Real usage is memory.current − inactive_file; alert on OOM kill events, not on a percentage that page cache inflates.
  • --memory-swap is the combined RAM+swap ceiling; setting it equal to --memory disables swap, which is usually right for services.
  • --cpus is a hard quota that throttles even on an idle host; --cpu-shares is a weight that does nothing until there is contention.
  • Throttling is invisible in averages: 62% average CPU in every configuration while p99 went 41 ms → 96 ms → 488 ms as the quota tightened, at 0% → 11% → 37% of periods throttled.
  • nr_throttled / nr_periods belongs on the dashboard next to utilisation; target under ~1%.
  • /proc/cpuinfo and /proc/meminfo are not namespaced — a container limited to 2 CPUs and 512 MB reports 16 CPUs and 62 GB.
  • Modern JVMs and .NET read the cgroup; Go, Node, Python and nginx do not — use automaxprocs, --max-old-space-size, and worker counts computed from the quota.
  • Aligning thread-pool size with the quota nearly halved p99 (488 ms → 214 ms) at the same limit.
  • Budget 25–30% of the container limit outside the managed heap: metaspace, thread stacks, code cache, direct buffers and GC structures are all excluded from -Xmx.
  • Setting the heap below the container limit converts a silent SIGKILL into a diagnosable OOM with a stack trace.
  • --pids-limit costs nothing and turns a fork bomb from a host reboot into one stuck container; the pids.current ramp gives minutes of warning on a thread leak.
  • Size from measurement: memory = 1.5× peak anon, CPU = 1.5× p99, PIDs = 3× steady state — measured limits gave 0 OOM kills, 0.7% throttling and 52 ms p99 versus 4 kills, 31% and 488 ms when guessed.
  • Memory should not be overcommitted on a node (OOM kills); CPU may be (throttling degrades). Re-derive limits quarterly — they are measurements with an expiry date.
