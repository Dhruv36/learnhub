cgroups: Limiting What You Use Foundations

What you'll master: the asymmetry at the heart of container resource limits — exceeding a memory limit kills your process, while exceeding a CPU limit merely slows it down, and confusing the two produces most container capacity mistakes; CPU quota versus shares, and why --cpus=1 is a hard ceiling while --cpu-shares only matters under contention; CFS throttling, and the pathological case where a multi-threaded app burns its entire 100 ms quota in 10 ms and then stalls for 90 ms — the single most common cause of mystifying p99 latency in containers; what exit code 137 actually tells you and how to distinguish an OOM kill from a plain SIGKILL; cgroup v1 versus v2 and why the paths changed; and the memory accounting details (page cache, swap) that make "memory usage" ambiguous. Prerequisites: Namespaces.

Part 1 — What cgroups Control

Where namespaces decide what a process can see, cgroups decide what it can use. A cgroup is a directory in a virtual filesystem; limits are set by writing to files in it.

$ docker run -d --name limited --memory=512m --cpus=1.5 nginx
$ docker exec limited sh -c 'cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max'
536870912                       ← memory.max: 512 MB
150000 100000                   ← cpu.max: 150ms quota per 100ms period = 1.5 CPUs
ControllerLimitsDocker flagExceeding it
memoryRAM, swap, page cache--memoryProcess is killed
cpuCPU time per period--cpus, --cpu-sharesThrottled — slowed, not killed
ioBlock device bandwidth/IOPS--device-read-bps etc.Throttled
pidsNumber of processes--pids-limitfork fails
cpusetWhich cores/NUMA nodes--cpuset-cpusConfined to those cores
🔑 Memory and CPU limits fail in fundamentally different ways, and this asymmetry drives every sizing decision. Memory is incompressible: a process cannot be given "less memory" on demand, so the kernel's only recourse when the limit is hit is to kill something. CPU is compressible: a process can always be given fewer cycles, so exceeding the limit means waiting. Set memory limits with headroom because being wrong is fatal; set CPU limits knowing that being wrong is a latency problem, not an availability one.

Part 2 — CPU: Quota, Shares and Sets

Three different mechanisms are commonly confused. They answer different questions.

--cpus=1.5            HARD CEILING. 150ms of CPU per 100ms period.
                      Enforced always, even on a completely idle host.

--cpu-shares=512      RELATIVE WEIGHT. Only matters under contention.
                      Default is 1024; 512 means "half as much as a default
                      container" when both want CPU. Unlimited when idle.

--cpuset-cpus=0,1     PINNING. Runs only on cores 0 and 1.
                      Useful for NUMA locality and cache affinity.

$ docker run --rm --cpus=0.5 alpine cat /sys/fs/cgroup/cpu.max
50000 100000                    ← 50ms quota per 100ms period

$ docker run --rm --cpu-shares=512 alpine cat /sys/fs/cgroup/cpu.weight
20                              ← a weight, not a limit

$ docker run --rm --cpuset-cpus=0,1 alpine cat /sys/fs/cgroup/cpuset.cpus
0-1

The distinction that matters in production: a container with --cpus=1 on a 32-core idle host still gets exactly one CPU's worth. A container with --cpu-shares=512 on the same idle host can use all 32 cores — the weight only applies when someone else wants CPU too.

Part 3 — CFS Throttling: The p99 Killer

The CPU quota is enforced per 100 ms period, and that granularity produces a failure mode that surprises almost everyone.

--cpus=1 means: 100ms of CPU time per 100ms period.

A single-threaded app uses 100ms over the full period.        ✅ smooth

A 10-THREADED app can consume 100ms of CPU in 10ms of wall clock
(10 threads x 10ms each), then:

  ├──10ms running──┤├────────── 90ms THROTTLED ──────────┤
                      every thread frozen until the next period
🔑 Throttling is a latency cliff, not a gradual slowdown. Once the quota is exhausted the container gets zero CPU until the period rolls over — up to 90 ms of complete stall. Average CPU utilisation looks low (the container "only used 100 ms of its 100 ms"), so dashboards show nothing wrong while p99 latency is catastrophic. This is the number-one cause of "our containerised service is inexplicably slow at the tail".

# the metric that reveals it
$ docker exec app cat /sys/fs/cgroup/cpu.stat
usage_usec 45231000
nr_periods 12043            ← periods elapsed
nr_throttled 8912           ← periods where we hit the quota  ★
throttled_usec 623410000    ← total time frozen               ★

throttle ratio = 8912 / 12043 = 74%   ← throttled in 3 of every 4 periods
SymptomCauseFix
High p99, low average CPUCFS throttlingRaise the limit, or reduce thread count
nr_throttled climbingQuota exhausted repeatedlyCheck throttled_usec against wall time
More threads made it slowerThreads exhaust the quota fasterMatch thread count to the CPU limit
Fine locally, slow in productionNo limits locally, quota in productionTest with production limits

The fix is usually thread count, not a bigger limit. A JVM or Go service sizing its thread pool from the host's core count (see Namespaces) creates far more threads than the quota can feed, which is what turns a modest limit into a throttling storm.

Part 4 — Memory: The OOM Kill

Memory limits are enforced by killing. Understanding exactly what gets killed, and by whom, is what makes exit code 137 diagnosable.

Exceeding memory.max:
  1. the kernel tries to reclaim (drop page cache, swap if allowed)
  2. if it cannot reclaim enough → the cgroup OOM killer runs
  3. it selects a process in that cgroup and sends SIGKILL
  4. if that was PID 1, the container dies with exit code 137

137 = 128 + 9  (SIGKILL)

$ docker run --rm --memory=100m alpine sh -c \
    'dd if=/dev/zero of=/dev/shm/f bs=1M count=200'
Killed
$ echo $?
137

$ docker inspect mycontainer --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
true 137                        ← OOMKilled distinguishes it from a plain SIGKILL
🔑 Exit code 137 alone does not mean OOM. It means the process received SIGKILL, which could equally be docker kill, an orchestrator terminating a pod that ignored SIGTERM, or a host-level OOM killer. The distinguishing signal is .State.OOMKilled in docker inspect, or the kernel log — without checking one of those, "137 means out of memory" is a guess that sends people optimising memory when the real cause was a missed SIGTERM handler.

$ dmesg | tail -3
[12345.678] Memory cgroup out of memory: Killed process 48213 (java)
            total-vm:4194304kB, anon-rss:512000kB, file-rss:12000kB
[12345.679] oom_reaper: reaped process 48213 (java)

Memory accounting includes page cache, which makes "memory usage" ambiguous: a container reading large files shows high usage that is mostly reclaimable cache, not a leak.

$ docker exec app cat /sys/fs/cgroup/memory.stat | head -5
anon 268435456              ← actual application memory  ★
file 178257920              ← page cache (reclaimable)
kernel_stack 1048576
slab 8388608
sock 262144

$ docker stats --no-stream app
CONTAINER   MEM USAGE / LIMIT     MEM %
app         426MiB / 512MiB       83.2%     ← includes page cache; alarming but fine

Judge memory pressure by anon, not by total usage — and by whether memory.events shows the kernel actually struggling:

$ docker exec app cat /sys/fs/cgroup/memory.events
low 0
high 0
max 1247                    ← times the limit was hit and reclaim was forced  ★
oom 0
oom_kill 0

Part 5 — cgroup v1 vs v2

The paths and file names changed, which is why older documentation and scripts break on modern systems.

HierarchyOne per controllerSingle unified tree
Memory limitmemory/memory.limit_in_bytesmemory.max
Memory usagememory.usage_in_bytesmemory.current
CPU quotacpu.cfs_quota_us + cpu.cfs_period_uscpu.max (both in one file)
CPU weightcpu.shares (2–262144)cpu.weight (1–10000)
Pressure stall info❌✅ *.pressure
# detect which version is in use
$ stat -fc %T /sys/fs/cgroup
cgroup2fs                   ← v2
tmpfs                       ← v1

$ docker info | grep -i cgroup
 Cgroup Driver: systemd
 Cgroup Version: 2

cgroup v2 added Pressure Stall Information, which is a better signal than utilisation because it measures time lost to resource shortage rather than resource consumed:

$ docker exec app cat /sys/fs/cgroup/cpu.pressure
some avg10=42.31 avg60=38.72 avg300=25.14 total=891234567
     ↑ 42% of the last 10s, some task was stalled waiting for CPU

$ docker exec app cat /sys/fs/cgroup/memory.pressure
some avg10=0.00 avg60=0.00 avg300=0.00 total=0

Part 6 — Setting Limits That Work

SettingGuidance
Memory limitPeak RSS + 25–50% headroom. Being wrong kills the process.
Memory reservation--memory-reservation = soft target for scheduling
CPU limitGenerous, or absent for latency-sensitive services
CPU request/sharesThe number that actually drives scheduling fairness
Thread poolsMust match the CPU limit, not host cores
PIDs limitSet it — a fork bomb otherwise takes the host down
SwapUsually disable (--memory-swap = --memory)
docker run -d \
  --memory=512m --memory-swap=512m \     # no swap: fail fast rather than thrash
  --memory-reservation=384m \            # soft target
  --cpus=2 \
  --pids-limit=200 \                     # fork-bomb protection
  myapp:1.0

Disabling swap for containers is usually right. Swapping makes a memory-starved container slow rather than dead, which sounds better but is worse in practice: the process thrashes, latency collapses, and no alert fires because nothing crashed. Failing fast on a clear OOM is more debuggable than a service that is technically alive and unusably slow.

❌ Setting a tight CPU limit and treating throttling as harmless. The team sets --cpus=1 because the service "only uses about 40% of a core on average", and the dashboards agree — average CPU utilisation sits comfortably under the limit. Meanwhile p99 latency is 900 ms and nobody can explain it. The service runs 16 worker threads sized from the host's core count, so it burns its entire 100 ms quota within the first 10 ms of each period and is then frozen for the remaining 90 ms. Utilisation looks low precisely because the container is throttled — it cannot use more, so the graph that would reveal the problem is the one being used to rule it out.

✅ Measure throttling directly and size thread pools to the limit. Read cpu.stat: nr_throttled / nr_periods is the fraction of periods that hit the cliff, and throttled_usec is the wall-clock time spent frozen — neither appears in a CPU utilisation graph. Then fix the cause rather than the symptom: match worker counts to the CPU quota (automaxprocs for Go, explicit pool sizes for JVM and Node, never auto for nginx), and prefer CPU requests/shares over hard limits for latency-sensitive services so a container can burst into idle capacity instead of stalling. Memory is the opposite case — there, a hard limit with headroom is correct, because exceeding it kills rather than slows.

Interview Questions

Beginner: What are cgroups, and how do they differ from namespaces?

Namespaces control what a process can see; cgroups control what it can use. Both are kernel features, and a container is a process with both applied.

Namespacescgroups
Visibility: PIDs, mounts, network, hostname, IPCConsumption: CPU, memory, I/O, process count
"I cannot see host processes""I cannot use more than 512 MB"

Mechanically a cgroup is a directory in a virtual filesystem, and limits are set by writing to files:

$ docker run -d --memory=512m --cpus=1.5 --name c1 nginx
$ docker exec c1 cat /sys/fs/cgroup/memory.max     # 536870912
$ docker exec c1 cat /sys/fs/cgroup/cpu.max        # 150000 100000

The critical difference between the two resources is what happens when you exceed them: memory is incompressible, so the kernel kills a process; CPU is compressible, so the process is throttled and simply waits. Memory limits are an availability risk if set too low; CPU limits are a latency risk.

Note that cgroup limits are enforced but not reported through /proc — a container with --cpus=1 still sees the host's core count in nproc, which is the interaction with namespaces covered in Namespaces.

Beginner: What does exit code 137 mean?

137 = 128 + 9, meaning the process was killed by signal 9 (SIGKILL). It does not by itself say who sent it.

The possible causes:

  • cgroup OOM kill — the container exceeded its memory limit.
  • Host OOM kill — the host ran out of memory and the kernel chose this process.
  • docker kill, or an orchestrator escalating after SIGTERM was ignored.
  • A liveness probe failure leading to a forced termination.

Distinguish them with OOMKilled:

$ docker inspect mycontainer --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
true 137        ← memory limit exceeded
false 137       ← SIGKILL from somewhere else

$ dmesg | grep -i "killed process"
Memory cgroup out of memory: Killed process 48213 (java) anon-rss:512000kB

Why this matters: assuming 137 always means OOM sends people to optimise memory when the real cause was often a process that ignored SIGTERM during shutdown and was force-killed after the grace period. That is a signal-handling bug — usually shell-form CMD making the shell PID 1, as in Process Model, PID 1 & Signals — and no amount of memory tuning fixes it.

The related code is 143 = 128 + 15 (SIGTERM), which means the process did shut down on request — usually a clean stop.

Mid: Explain CFS throttling and why it causes latency spikes.

The CPU quota is enforced per period, not continuously. With --cpus=1, the container gets 100 ms of CPU time per 100 ms period. Once that budget is spent, every thread is frozen until the next period begins.

A 10-threaded app with --cpus=1:
  10 threads x 10ms each = 100ms of CPU consumed in 10ms of WALL CLOCK
  ├─10ms running─┤├──────── 90ms completely stalled ────────┤

The result is a latency cliff rather than a gradual slowdown. A request unlucky enough to arrive during the frozen window waits up to 90 ms doing nothing — which is exactly the shape of a p99 problem with a healthy-looking p50.

Why dashboards hide it: average CPU utilisation looks low, because the container is prevented from using more. The graph people check to rule out a CPU problem is the one the problem suppresses.

Measure it directly:

$ cat /sys/fs/cgroup/cpu.stat
nr_periods 12043
nr_throttled 8912         ← 74% of periods hit the quota
throttled_usec 623410000  ← 623 seconds spent frozen

Fixes, in order of preference: reduce thread count to match the quota (the usual root cause, since runtimes size pools from host cores); raise the limit; remove the hard limit and use shares/requests so the container can burst into idle capacity; or, in Kubernetes, use a CPU request without a limit for latency-sensitive services. Increasing the CFS period is possible but rarely the right lever.

Mid: How do you size memory limits, and what does docker stats actually show?

Sizing: peak RSS plus 25–50% headroom, because being wrong is fatal rather than slow. Measure the peak under realistic load, including startup spikes and garbage-collection peaks, not steady state.

The complication is that "memory usage" is ambiguous, because the cgroup counts page cache as usage:

$ docker stats --no-stream app
MEM USAGE / LIMIT     MEM %
426MiB / 512MiB       83.2%        ← looks alarming

$ docker exec app cat /sys/fs/cgroup/memory.stat | head -3
anon 268435456                     ← 256 MB: the actual application memory
file 178257920                     ← 170 MB: page cache, reclaimable

The container is using 256 MB, not 426 MB. The page cache is files the kernel is caching and will drop under pressure rather than OOM-killing over. A container reading large files always looks near its limit, and that is normal.

The signal that matters is whether reclaim is failing:

$ cat /sys/fs/cgroup/memory.events
max 1247        ← times the limit was hit and reclaim was forced
oom_kill 0      ← but nothing was killed

A high max with zero oom_kill means the limit is tight enough to cause constant reclaim — wasteful, worth raising, but not yet failing.

I would also disable swap (--memory-swap equal to --memory). Swapping turns a clear OOM into a service that is alive and unusably slow, which is harder to detect and harder to debug than a crash.

Finally, make the application aware of its limit: a JVM before Java 10, or any runtime sizing itself from /proc/meminfo, will size a heap from host RAM and be killed regardless of how carefully the limit was chosen.

Senior: A service has good average latency but terrible p99 in containers, not on VMs. Diagnose it.

The container-only aspect points at cgroup limits, and CFS throttling is the leading hypothesis because it produces exactly this signature: fine p50, catastrophic p99, low average CPU.

1. Confirm throttling first — it is one file:

$ cat /sys/fs/cgroup/cpu.stat
nr_periods 12043
nr_throttled 8912           → 74% of periods throttled
throttled_usec 623410000    → 623s frozen

# per-container, over time
$ docker stats --no-stream --format '{{.Name}}\t{{.CPUPerc}}'

A throttle ratio above a few percent on a latency-sensitive service is already a problem; 74% explains any p99 number.

2. Find why the quota is exhausted so fast. Usually thread count: the runtime sized its pool from host cores because that is not namespaced, so 16 threads share a 1-CPU quota and burn it in milliseconds. Check GOMAXPROCS, JVM availableProcessors(), nginx worker_processes, and any explicit pool configuration against the cgroup limit.

3. Rule out the other container-specific causes if throttling is clean:

  • Memory pressure — memory.events max climbing means constant reclaim, which stalls allocation.
  • Page cache eviction — a tight memory limit evicts cache the app depends on, turning reads into disk I/O.
  • PSI — cpu.pressure and io.pressure measure time lost to contention directly, which is a better signal than utilisation.
  • Overlayfs copy-up if the app writes to the container filesystem rather than a volume.
  • Noisy neighbours — with shares rather than quota, another container's load changes this one's latency.

The fix I would push for is matching concurrency to the quota, then removing the hard CPU limit in favour of a request/share so the service can burst into idle capacity. Hard CPU limits buy predictability for the cluster at the cost of tail latency for the service, and for a latency-sensitive workload that is usually the wrong trade — while memory limits should stay hard, because the failure mode there is being killed rather than being slow.

Senior: Design resource limits for a mixed workload cluster.

Start by classifying workloads, because the right limit policy differs per class and a single policy guarantees some of them are wrong.

ClassCPUMemoryRationale
Latency-sensitive APIRequest, no hard limitHard limit + 50% headroomThrottling destroys p99; OOM destroys availability
Batch / async workersHard limitHard limitPredictability matters more than tail latency
Databases / statefulRequest + generous limitHard limit, large headroomAn OOM-killed database is an incident
Build / CI jobsHard limitHard limitUntrusted and bursty — contain them

The core trade to state explicitly: hard CPU limits give the cluster predictable capacity and prevent noisy neighbours, at the cost of tail latency for the limited workload. Requests without limits give better latency and let idle capacity be used, at the cost of less predictable scheduling. Memory has no such trade — always set a hard limit, because unbounded memory takes the node down.

Concrete defaults I would set:

--memory=<peak RSS x 1.5>
--memory-swap=<same as --memory>      # no swap: fail fast, do not thrash
--memory-reservation=<peak RSS>       # soft target for the scheduler
--pids-limit=200                       # fork-bomb containment
--cpus=<only for batch/CI>
--cpu-shares=<proportional to importance>

Then make applications limit-aware, which is the step most often skipped: Java 10+ or explicit -Xmx, automaxprocs for Go, explicit worker counts for Node and nginx. Without this, careful limits are undermined by runtimes configuring themselves from host values.

Monitoring that closes the loop: alert on nr_throttled/nr_periods above a threshold per workload class, on memory.events.max rising (reclaim pressure before OOM), on oom_kill at all, and on PSI (cpu.pressure, memory.pressure) which measures time lost rather than resource used.

Capacity policy: allow requests to be overcommitted but keep memory limits within node capacity, since CPU contention degrades and memory contention kills. And run a load test with production limits applied — most limit-related incidents are discovered in production precisely because the test environment had no limits at all.

🏋️ Exercises

1 (easy): Show that memory limits kill and CPU limits only slow.
Solution 
# MEMORY: exceeding the limit is fatal
$ docker run --rm --memory=100m --name memtest alpine sh -c \
    'dd if=/dev/zero of=/dev/shm/fill bs=1M count=200'
Killed
$ echo "exit code: $?"
exit code: 137

# CPU: exceeding the limit just takes longer
$ time docker run --rm --cpus=1 alpine sh -c \
    'i=0; while [ $i -lt 3000000 ]; do i=$((i+1)); done'
real    0m6.412s

$ time docker run --rm --cpus=0.25 alpine sh -c \
    'i=0; while [ $i -lt 3000000 ]; do i=$((i+1)); done'
real    0m24.107s        ← 4x slower, but it COMPLETED

That asymmetry is the whole point: a quarter of the CPU took four times as long and finished; 200 MB in a 100 MB limit was killed outright. Memory is incompressible, CPU is compressible.

Confirm the OOM kill was the cgroup's, not something else:

$ docker run -d --name oomtest --memory=100m alpine sh -c \
    'dd if=/dev/zero of=/dev/shm/fill bs=1M count=500; sleep 60'
$ sleep 3
$ docker inspect oomtest --format 'OOMKilled={{.State.OOMKilled}} Exit={{.State.ExitCode}}'
OOMKilled=true Exit=137

$ dmesg | grep -i "memory cgroup out of memory" | tail -1
[12345.678] Memory cgroup out of memory: Killed process 48213 (dd) anon-rss:102400kB
$ docker rm -f oomtest >/dev/null

And show that 137 does NOT always mean OOM:

$ docker run -d --name killtest alpine sleep 300
$ docker kill killtest >/dev/null
$ docker inspect killtest --format 'OOMKilled={{.State.OOMKilled}} Exit={{.State.ExitCode}}'
OOMKilled=false Exit=137        ← same exit code, completely different cause
$ docker rm killtest >/dev/null

Both exited 137; only OOMKilled separates "ran out of memory" from "someone sent SIGKILL". Diagnosing on the exit code alone sends you to the wrong problem half the time.

3 (medium): Reproduce CFS throttling and show it in cpu.stat.
Solution 
# a container with 1 CPU running MANY threads
$ docker run -d --name throttled --cpus=1 progrium/stress --cpu 8
$ sleep 10
$ docker exec throttled cat /sys/fs/cgroup/cpu.stat
usage_usec 9982341
nr_periods 103
nr_throttled 101          ← throttled in 98% of periods
throttled_usec 8734129    ← 8.7 seconds frozen out of ~10

98% of periods hit the quota, and the container spent 8.7 of 10 seconds completely frozen.

Yet CPU utilisation looks unremarkable:

$ docker stats --no-stream throttled --format '{{.CPUPerc}}'
99.9%                     ← "using its full 1 CPU" — nothing looks wrong
$ docker rm -f throttled >/dev/null

Now measure the latency impact, which is what users feel:

$ cat > /tmp/lat.sh <<'EOF'
# a worker loop that records how long each 1ms unit of work actually takes
for i in $(seq 200); do
  S=$(date +%s%N)
  j=0; while [ $j -lt 20000 ]; do j=$((j+1)); done
  E=$(date +%s%N)
  echo $(( (E-S)/1000000 ))
done | sort -n | awk '{a[NR]=$1} END {print "p50="a[int(NR*0.5)]"ms  p99="a[int(NR*0.99)]"ms  max="a[NR]"ms"}'
EOF

# with plenty of CPU
$ docker run --rm --cpus=4 -v /tmp/lat.sh:/lat.sh alpine sh /lat.sh
p50=4ms  p99=6ms  max=8ms

# with a tight quota AND competing threads
$ docker run -d --name noise --cpus=1 progrium/stress --cpu 8 >/dev/null
$ docker run --rm --cpus=1 -v /tmp/lat.sh:/lat.sh alpine sh /lat.sh
p50=5ms  p99=94ms  max=112ms
                          ↑ p99 is 15x worse; max ≈ a full 100ms period
$ docker rm -f noise >/dev/null

p50 barely moved while p99 went from 6 ms to 94 ms — and 94 ms is almost exactly one CFS period, which is the fingerprint of throttling rather than general slowness.

The fix is fewer threads, not a bigger limit:

$ for w in 8 4 1; do
    docker run -d --name t --cpus=1 progrium/stress --cpu $w >/dev/null
    sleep 8
    S=$(docker exec t cat /sys/fs/cgroup/cpu.stat)
    P=$(echo "$S" | awk '/nr_periods/{print $2}')
    T=$(echo "$S" | awk '/nr_throttled/{print $2}')
    echo "$w workers: throttled $T/$P periods ($(( T*100/P ))%)"
    docker rm -f t >/dev/null
  done
8 workers: throttled 79/81 periods (97%)
4 workers: throttled 74/80 periods (92%)
1 workers: throttled  2/80 periods (2%)

Same CPU limit, same total work available — matching the worker count to the quota took throttling from 97% to 2%.

4 (medium): Show that memory usage includes page cache.
Solution 
$ docker run -d --name cache --memory=512m alpine sleep 3600
$ docker stats --no-stream cache --format '{{.MemUsage}}'
1.234MiB / 512MiB        ← baseline

# read a large file: page cache fills
$ docker exec cache sh -c 'dd if=/dev/zero of=/tmp/big bs=1M count=300 2>/dev/null; \

312.4MiB / 512MiB 61.02%     ← alarming... but it is nearly all cache

Break it down properly:

$ docker exec cache sh -c 'grep -E "^(anon|file) " /sys/fs/cgroup/memory.stat'
anon 1441792             ← 1.4 MB of ACTUAL application memory
file 325058560           ← 310 MB of page cache (reclaimable)

The app is using 1.4 MB, not 312 MB. A dashboard alerting at 60% "memory usage" would be paging someone about a container that is essentially idle.

Prove the cache is reclaimable rather than a leak:

$ docker exec cache sh -c 'rm /tmp/big'
$ docker stats --no-stream cache --format '{{.MemUsage}}'
2.1MiB / 512MiB          ← released immediately

# or force reclaim by pressure
$ docker exec cache sh -c 'dd if=/dev/zero of=/tmp/b2 bs=1M count=400 2>/dev/null; \
                           cat /tmp/b2 > /dev/null'
$ docker exec cache sh -c 'dd if=/dev/zero of=/dev/shm/anon bs=1M count=200 2>/dev/null'
$ docker exec cache sh -c 'grep -E "^(anon|file) " /sys/fs/cgroup/memory.stat'
anon 209715200           ← 200 MB anonymous now
file  87031808           ← cache SHRANK to make room, no OOM kill

The kernel evicted cache instead of killing the container — which is exactly why page cache should not be counted as pressure.

The signal that does indicate pressure:

$ docker exec cache cat /sys/fs/cgroup/memory.events
low 0
high 0
max 1247                 ← times the limit forced reclaim
oom 0
oom_kill 0               ← nothing killed

Compare with a container that is genuinely near its limit:

$ docker run -d --name real --memory=256m alpine sh -c \
    'dd if=/dev/zero of=/dev/shm/x bs=1M count=200 2>/dev/null; sleep 300'
$ sleep 2
$ docker exec real sh -c 'grep -E "^(anon|file) " /sys/fs/cgroup/memory.stat'
anon 209715200           ← 200 MB of 256 MB is REAL memory
file    262144
$ docker rm -f cache real >/dev/null

The rule: alert on anon approaching the limit, and on memory.events max or oom_kill — never on total usage, which includes cache the kernel will happily drop.

6 (hard): Size limits for a real workload using throttling and OOM signals.
Solution 
# a workload with a startup spike and steady state
$ cat > /tmp/app.py <<'PY'
import time, os
startup = [bytearray(1024*1024) for _ in range(120)]   # 120MB startup spike
time.sleep(2)
del startup[60:]                                        # settles to ~60MB
print("steady", flush=True)
end = time.time() + 20
while time.time() < end:
    sum(i*i for i in range(50000))                      # CPU work
PY

# STEP 1: measure with NO limits to find the real peak
$ docker run -d --name probe -v /tmp/app.py:/app.py python:3.12-alpine python /app.py
$ PEAK=0; for i in $(seq 25); do
    M=$(docker exec probe cat /sys/fs/cgroup/memory.current 2>/dev/null || echo 0)
    [ "$M" -gt "$PEAK" ] && PEAK=$M
    sleep 1
  done
$ echo "peak: $((PEAK/1024/1024)) MB"
peak: 138 MB
$ docker rm -f probe >/dev/null

STEP 2: size memory from the peak, not the steady state:

$ for lim in 64m 128m 200m; do
    docker run -d --name t --memory=$lim -v /tmp/app.py:/app.py \
      python:3.12-alpine python /app.py >/dev/null
    sleep 8
    OOM=$(docker inspect t --format '{{.State.OOMKilled}}')
    ST=$(docker inspect t --format '{{.State.Status}}')
    printf "%-5s OOMKilled=%-5s status=%s\n" "$lim" "$OOM" "$ST"
    docker rm -f t >/dev/null
  done
64m   OOMKilled=true  status=exited        ← killed during the startup spike
128m  OOMKilled=true  status=exited        ← killed: peak was 138MB
200m  OOMKilled=false status=running       ← survives (138MB x 1.45)

Sizing from steady-state usage (60 MB) would have chosen 128 MB and died on every start — the startup spike is what the limit must accommodate.

STEP 3: size CPU by throttle ratio rather than by utilisation:

$ for c in 0.25 0.5 1 2; do
    docker run -d --name t --memory=200m --cpus=$c -v /tmp/app.py:/app.py \
      python:3.12-alpine python /app.py >/dev/null
    sleep 12
    S=$(docker exec t cat /sys/fs/cgroup/cpu.stat 2>/dev/null)
    P=$(echo "$S" | awk '/nr_periods/{print $2}')
    T=$(echo "$S" | awk '/nr_throttled/{print $2}')
    U=$(docker stats --no-stream t --format '{{.CPUPerc}}')
    printf "cpus=%-5s throttled=%3d%%  reported CPU=%s\n" \
      "$c" "$(( P>0 ? T*100/P : 0 ))" "$U"
    docker rm -f t >/dev/null
  done
cpus=0.25  throttled= 96%  reported CPU=24.9%
cpus=0.5   throttled= 91%  reported CPU=49.8%
cpus=1     throttled= 12%  reported CPU=92.4%
cpus=2     throttled=  0%  reported CPU=98.1%

Note the trap in the "reported CPU" column: at --cpus=0.25 utilisation reads 24.9%, which looks like a container comfortably under its limit. It is throttled 96% of the time. Judging by utilisation would conclude the limit is generous; judging by nr_throttled shows it is strangling the workload.

Final configuration, with the reasoning recorded:

docker run -d \
  --memory=200m --memory-swap=200m \   # peak 138MB x 1.45; no swap → fail fast
  --memory-reservation=150m \          # soft target for the scheduler
  --cpus=2 \                           # 0% throttling; drop to a share if bursty
  --pids-limit=100 \                   # fork-bomb containment
  myapp:1.0

The method generalises: measure the peak with no limits, add 40–50% for memory because being wrong kills, and choose CPU by driving nr_throttled to near zero rather than by watching a utilisation graph that throttling suppresses.

🎯 Key Takeaways

  • Namespaces control what a process can see; cgroups control what it can use.
  • Memory is incompressible and CPU is compressible — exceeding memory kills the process, exceeding CPU only slows it. Measured: 200 MB in a 100 MB limit was killed; 0.25 CPU merely took 4× longer and finished.
  • --cpus is a hard ceiling enforced even on an idle host; --cpu-shares is a weight that does nothing until there is contention (measured: 1587% CPU with 512 shares on an idle host).
  • Under contention, shares divide CPU in proportion — 1024 vs 512 measured at 133% vs 66%.
  • CFS throttling is a latency cliff: once the quota is spent the container gets zero CPU until the next 100 ms period.
  • Measured: 8 workers on --cpus=1 were throttled in 98% of periods and frozen 8.7 of 10 seconds, while docker stats showed a healthy-looking 99.9%.
  • p50 barely moved (5 ms) while p99 went from 6 ms to 94 ms — and ~94 ms is one CFS period, the fingerprint of throttling.
  • The fix is usually fewer threads, not a bigger limit: 8 → 1 worker took throttling from 97% to 2% at the same quota.
  • Utilisation graphs hide throttling: at --cpus=0.25 a container read 24.9% CPU while throttled 96% of periods.
  • Alert on nr_throttled / nr_periods and throttled_usec from cpu.stat.
  • Exit code 137 = SIGKILL, not necessarily OOM — docker kill produced the same code. Only .State.OOMKilled or dmesg distinguishes them.
  • 143 = SIGTERM, meaning a clean requested shutdown.
  • docker stats memory includes reclaimable page cache: a container reading files showed 312 MB of 512 MB while anon was 1.4 MB.
  • Judge memory by anon in memory.stat, and by memory.events (max = reclaim forced, oom_kill = actually killed).
  • Size memory from the peak including startup spikes plus 40–50% — a workload peaking at 138 MB was OOM-killed at 128 MB despite a 60 MB steady state.
  • Disable swap (--memory-swap = --memory) so a starved container fails clearly instead of thrashing while technically alive.
  • Set --pids-limit, or a fork bomb exhausts host PIDs.
  • cgroup v2 renamed everything (memory.max, cpu.max) and added PSI, which measures time lost to contention rather than resource consumed.
  • Prefer CPU requests/shares over hard limits for latency-sensitive services, and hard limits for batch and untrusted work — memory should always be a hard limit.
