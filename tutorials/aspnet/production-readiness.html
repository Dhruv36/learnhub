Production Readiness & Observability Production

What you'll master: health checks that mean something to an orchestrator, structured logging and the cardinality traps that take down a metrics backend, OpenTelemetry across traces, metrics and logs, graceful shutdown and zero-downtime deploys, resilience that fails fast instead of cascading, and the small set of signals worth alerting on. This is the capstone: it assembles the pipeline, DI, configuration, EF, caching, security and background-work lessons into one production service. Prerequisites: the whole track, particularly Configuration, Background Services and Error Handling.

Part 1 — Health Checks That Mean Something

// Three DIFFERENT questions, and conflating them causes outages:
//   LIVENESS   is the process broken beyond recovery? → restart it
//   READINESS  can it serve traffic right now?        → route to it or not
//   STARTUP    has it finished initialising?          → do not kill it yet

builder.Services.AddHealthChecks()
    // Liveness: NOTHING external. A dependency being down must NOT restart us.
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])

    // Readiness: the dependencies required to serve a request.
    .AddNpgSql(connectionString, name: "database", tags: ["ready"])
    .AddRedis(redisConnection, name: "cache", tags: ["ready"])
    .AddUrlGroup(new Uri("https://payments.example.com/health"),
        name: "payments", tags: ["ready"],
        failureStatus: HealthStatus.Degraded);   // degraded, not unhealthy

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready"),
    ResponseWriter = WriteDetailedResponse
});

// ── THE MISTAKE THAT CAUSES CASCADING FAILURE ────────────────────────────
// Putting a database check in LIVENESS. When the database has a brief blip,
// every replica reports unhealthy, Kubernetes restarts all of them
// simultaneously, they all reconnect at once, and the reconnection storm
// keeps the database down. A transient dependency failure has become a
// full outage caused by the health check itself.
//
// LIVENESS answers "is this process wedged?" — a deadlock, an exhausted
// thread pool, a corrupted state that only a restart fixes. Nothing external
// belongs in it.

// ── DEGRADED IS A REAL AND USEFUL STATE ──────────────────────────────────
// A non-essential dependency being down should not remove the instance from
// the load balancer. Map Degraded to 200 so traffic keeps flowing:
options.ResultStatusCodes = new Dictionary<HealthStatus, int>
{
    [HealthStatus.Healthy]   = StatusCodes.Status200OK,
    [HealthStatus.Degraded]  = StatusCodes.Status200OK,      // still serving
    [HealthStatus.Unhealthy] = StatusCodes.Status503ServiceUnavailable
};

// ── CUSTOM CHECKS: check the thing you actually depend on ────────────────
public sealed class DatabaseHealthCheck(AppDbContext db) : IHealthCheck
{
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken ct)
    {
        try
        {
            // A real query, not just CanConnect — a pooled connection can
            // report "connected" while the database refuses queries.
            using var timeout = CancellationTokenSource
                .CreateLinkedTokenSource(ct);
            timeout.CancelAfter(TimeSpan.FromSeconds(2));   // BOUND IT

            _ = await db.Database
                .SqlQuery<int>($"SELECT 1")
                .FirstAsync(timeout.Token);

            return HealthCheckResult.Healthy();
        }
        catch (Exception ex)
        {
            return HealthCheckResult.Unhealthy("Database unreachable.", ex);
        }
    }
}
// The timeout matters: an unbounded health check on a hung database blocks
// until the probe's own timeout, and probe timeouts are usually generous
// enough that the instance sits half-dead for a long time.

// Health endpoints must be ANONYMOUS but need not be public — expose them on
// a separate port or restrict by network so they are not part of the API's
// attack surface, since they enumerate your dependencies.

Part 2 — Structured Logging

// Log MESSAGE TEMPLATES, never interpolated strings. The template is the
// unit of aggregation.
// ✗ log.LogInformation($"Order {orderId} shipped to {country}");
//   → every log line is a unique string; you cannot group or filter by them
// ✓ log.LogInformation("Order {OrderId} shipped to {Country}", orderId, country);
//   → OrderId and Country become queryable FIELDS

// SOURCE-GENERATED LOGGING — allocation-free and checked at compile time:
public static partial class Log
{
    [LoggerMessage(Level = LogLevel.Information,
        Message = "Order {OrderId} shipped to {Country}")]
    public static partial void OrderShipped(
        ILogger logger, Guid orderId, string country);
}
Log.OrderShipped(logger, order.Id, order.Country);
// No boxing, no string formatting when the level is disabled, and a typo in
// the argument count is a build error rather than a broken log line.

// SCOPES attach context to everything logged inside them:
using (logger.BeginScope(new Dictionary<string, object>
{
    ["OrderId"] = order.Id,
    ["CustomerId"] = order.CustomerId,
    ["CorrelationId"] = correlationId
}))
{
    await ProcessAsync(order, ct);      // every log inside carries all three
}

// ── LOG LEVELS, USED CONSISTENTLY ────────────────────────────────────────
//   Trace        never in production — often contains sensitive values
//   Debug        diagnostics, off by default
//   Information  significant business events: order placed, payment captured
//   Warning      recoverable problems and client mistakes: 404, 409, retries
//   Error        unhandled failures needing investigation
//   Critical     the application cannot continue
//
// THE MOST COMMON MISTAKE is logging client errors at Error. A 404 or a
// validation failure is the system working correctly; logging thousands of
// them at Error makes the error rate meaningless and trains everyone to
// ignore the alert that eventually matters.

// ── WHAT NEVER GOES IN A LOG ─────────────────────────────────────────────
//   ✗ passwords, tokens, API keys, full request bodies
//   ✗ card numbers, national identifiers, health data
//   ✗ the entire configuration object
//   ✓ user IDs, correlation IDs, and the SHAPE of what failed

// Redaction as a safety net, since discipline alone leaks eventually:
builder.Logging.EnableRedaction();
builder.Services.AddRedaction(redaction =>
    redaction.SetRedactor<ErasingRedactor>(new DataClassificationSet(
        DataTaxonomy.SensitiveData)));

// ── SAMPLING AT VOLUME ───────────────────────────────────────────────────
// At high throughput, logging every request costs real money and hides the
// interesting entries. Sample the successful ones and keep all failures:
builder.Logging.AddFilter("Microsoft.AspNetCore.Hosting", LogLevel.Warning);
// plus HTTP logging restricted to what you actually query:
builder.Services.AddHttpLogging(o =>
    o.LoggingFields = HttpLoggingFields.RequestPath
                    | HttpLoggingFields.ResponseStatusCode
                    | HttpLoggingFields.Duration);
Key insight: the single most expensive observability mistake is unbounded label cardinality. A metric tagged with the raw request path, a user id, or an order id creates one time series per distinct value — millions of them — and that will exhaust a Prometheus instance or produce an enormous bill. Metrics take bounded labels only: the route pattern rather than the path, the status code, the method. High-cardinality identifiers belong in logs and traces, where they are indexed for lookup rather than aggregated into series. Getting this wrong is how an observability change causes the outage it was meant to detect.

Part 3 — OpenTelemetry

// One vendor-neutral pipeline for traces, metrics and logs.
builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource
        .AddService(serviceName: "orders-api",
                    serviceVersion: Assembly.GetExecutingAssembly()
                        .GetName().Version?.ToString() ?? "unknown")
        .AddAttributes([new("deployment.environment", builder.Environment.EnvironmentName)]))

    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation(o =>
        {
            o.RecordException = true;
            // Do not trace the health endpoints — they are the highest-volume,
            // least interesting requests in the system.
            o.Filter = context =>
                !context.Request.Path.StartsWithSegments("/health");
        })
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation(o => o.SetDbStatementForText = false)
        .AddSource("Orders.Application")
        .AddOtlpExporter())

    .WithMetrics(metrics => metrics
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()          // GC, thread pool, exceptions
        .AddMeter("Orders.Application")
        .AddOtlpExporter());

builder.Logging.AddOpenTelemetry(logging =>
{
    logging.IncludeScopes = true;             // scopes become log attributes
    logging.AddOtlpExporter();
});

// SetDbStatementForText = false by default: SQL text can contain parameter
// values, and traces are usually retained and broadly readable.

// ── CUSTOM SPANS for business operations ─────────────────────────────────
private static readonly ActivitySource Source = new("Orders.Application");

public async Task<Result<OrderId>> CreateAsync(CreateOrder command, CancellationToken ct)
{
    using var activity = Source.StartActivity("order.create");
    activity?.SetTag("order.line_count", command.Lines.Count);
    activity?.SetTag("customer.id", command.CustomerId.ToString());

    try
    {
        var result = await _handler.Handle(command, ct);
        activity?.SetTag("order.id", result.Value.ToString());
        return result;
    }
    catch (Exception ex)
    {
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        throw;
    }
}
// Traces carry high-cardinality identifiers happily — that is exactly what
// they are for, and it is the complement of the metrics rule.

// ── CUSTOM METRICS, with BOUNDED labels only ─────────────────────────────
public sealed class OrderMetrics
{
    private readonly Counter<long> _created;
    private readonly Histogram<double> _value;

    public OrderMetrics(IMeterFactory factory)
    {
        var meter = factory.Create("Orders.Application");
        _created = meter.CreateCounter<long>("orders.created");
        _value = meter.CreateHistogram<double>("orders.value", unit: "USD");
    }

    public void OrderCreated(string channel, string country)
    {
        // channel and country are bounded sets — a handful of values each.
        _created.Add(1, new("channel", channel), new("country", country));
    }
    // ✗ NEVER: _created.Add(1, new("order.id", id)) — unbounded series
}
builder.Services.AddSingleton<OrderMetrics>();

// ── SAMPLING: keep the cost proportionate ────────────────────────────────
.SetSampler(new ParentBasedSampler(new TraceIdRatioBasedSampler(0.1)))
// ParentBased means a sampling decision made upstream is honoured, so a trace
// is not half-recorded across services. Ideally combine with tail sampling in
// the collector so all ERRORS are kept regardless of the ratio — head
// sampling alone discards the traces you most want.

Part 4 — Graceful Shutdown and Zero-Downtime Deploys

// THE SEQUENCE, and where deployments lose requests:
//   1. the orchestrator sends SIGTERM
//   2. ApplicationStopping fires
//   3. the server stops accepting NEW connections
//   4. in-flight requests get ShutdownTimeout to finish
//   5. hosted services stop, in reverse registration order
//   6. the container is killed after the grace period

builder.Services.Configure<HostOptions>(options =>
{
    // Above the longest expected request, BELOW the orchestrator's grace
    // period (Kubernetes defaults to 30s, then SIGKILL).
    options.ShutdownTimeout = TimeSpan.FromSeconds(25);
});

// ── THE RACE THAT DROPS REQUESTS ─────────────────────────────────────────
// The load balancer learns an instance is going away only after its next
// readiness probe fails — typically several seconds later. Until then it
// keeps sending traffic to a process that has already stopped accepting
// connections, and those requests fail.
//
// ✓ FAIL READINESS FIRST, then wait, then actually shut down:
public sealed class GracefulShutdown(
    IHostApplicationLifetime lifetime,
    ReadinessState readiness,
    ILogger<GracefulShutdown> log) : IHostedService
{
    public Task StartAsync(CancellationToken ct)
    {
        lifetime.ApplicationStopping.Register(() =>
        {
            log.LogInformation("Draining: readiness now failing.");
            readiness.SetNotReady();          // /health/ready → 503

            // Give the load balancer time to observe it and stop routing.
            // Must exceed (probe period × failure threshold).
            Thread.Sleep(TimeSpan.FromSeconds(10));

            log.LogInformation("Drain complete; shutting down.");
        });
        return Task.CompletedTask;
    }
    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}
// In Kubernetes the equivalent is a preStop hook sleeping for the same
// reason — the pod stays alive and serving while the endpoints controller
// propagates its removal.

// ── KESTREL, so long requests are not cut off mid-response ───────────────
builder.WebHost.ConfigureKestrel(o =>
{
    o.Limits.MinResponseDataRate = null;      // no rate floor for slow clients
    o.Limits.KeepAliveTimeout = TimeSpan.FromSeconds(130);
});

// ── DATABASE MIGRATIONS AND ROLLING DEPLOYS ──────────────────────────────
// During a rolling deploy, OLD AND NEW CODE RUN SIMULTANEOUSLY against ONE
// database. Migrations must therefore be BACKWARD COMPATIBLE:
//   ✓ add a nullable column                 old code ignores it
//   ✓ add a table                           old code ignores it
//   ✗ drop or rename a column               old code breaks immediately
//   ✗ add a NOT NULL column with no default old INSERTs fail
//
// Renaming a column is a THREE-DEPLOY sequence:
//   1. add the new column; write to BOTH, read from the old
//   2. backfill; switch reads to the new column
//   3. once no running code references the old column, drop it
//
// ✗ DO NOT auto-migrate on startup in production:
//     await db.Database.MigrateAsync();
//   With N replicas, N instances race to migrate; it needs elevated
//   permissions at runtime; and a failed migration crash-loops the app.
//   Run migrations as a separate, ordered pipeline step or an init job.

Part 5 — Resilience

// Failures cascade when a slow dependency consumes all your capacity. The
// goal is to FAIL FAST rather than to retry harder.
builder.Services.AddHttpClient<IPaymentGateway, StripeGateway>()
    .AddStandardResilienceHandler(options =>
    {
        options.Retry.MaxRetryAttempts = 3;
        options.Retry.Delay = TimeSpan.FromMilliseconds(200);
        options.Retry.BackoffType = DelayBackoffType.Exponential;
        options.Retry.UseJitter = true;        // ← prevents synchronised
                                               //   retry storms across replicas
        options.CircuitBreaker.FailureRatio = 0.5;
        options.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
        options.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(15);

        options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(5);
        options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(20);
    });

// ── WHAT EACH POLICY IS FOR ──────────────────────────────────────────────
//   TIMEOUT          bounds one attempt, so a hung call cannot hold a thread
//   RETRY            handles TRANSIENT failures — network blips, brief 503s
//   CIRCUIT BREAKER  stops calling a dependency that is clearly down, so you
//                    fail fast instead of queueing behind it
//   BULKHEAD         caps concurrent calls, so one slow dependency cannot
//                    consume every thread
//
// THE CIRCUIT BREAKER IS THE ONE THAT PREVENTS CASCADING FAILURE. Retries
// alone make an overloaded dependency worse: three retries times N replicas
// is a self-inflicted denial of service on a service already struggling.

// ── RETRY ONLY WHAT IS SAFE TO RETRY ─────────────────────────────────────
// Retrying a non-idempotent POST after a timeout can double-charge. Either
// restrict retries to idempotent methods, or require an idempotency key:
options.Retry.ShouldHandle = args => ValueTask.FromResult(
    args.Outcome.Result?.StatusCode is HttpStatusCode.ServiceUnavailable
                                     or HttpStatusCode.GatewayTimeout
    && args.Context.GetRequestMessage()?.Method == HttpMethod.Get);

// ── TIMEOUTS EVERYWHERE, because the default is often infinite ───────────
db.Database.SetCommandTimeout(TimeSpan.FromSeconds(10));
httpClient.Timeout = TimeSpan.FromSeconds(15);
redisOptions.SyncTimeout = 1000;
// An operation with no timeout will eventually hang forever, and one hung
// operation holding a request thread multiplies into thread-pool starvation
// that presents as the WHOLE application being slow.

// ── HONOUR CLIENT CANCELLATION ───────────────────────────────────────────
// Thread RequestAborted through every call so abandoned work stops:
public async Task<IResult> Get(int id, CancellationToken ct) => ...;
// Under load, requests whose clients have given up still consuming database
// capacity is a meaningful multiplier on an existing problem.

// ── LOAD SHEDDING ────────────────────────────────────────────────────────
// When saturated, rejecting quickly is kinder than accepting and timing out:
options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(_ =>
    RateLimitPartition.GetConcurrencyLimiter("global",
        _ => new ConcurrencyLimiterOptions { PermitLimit = 200, QueueLimit = 0 }));
// A fast 429 lets a client retry elsewhere or back off; a request that waits
// 30 seconds and then times out has consumed resources and helped nobody.

Part 6 — What to Measure and Alert On

// ── THE FOUR GOLDEN SIGNALS ──────────────────────────────────────────────
//   LATENCY     p50, p95, p99 — and ALWAYS separate successful from failed
//               requests, because fast failures flatter the average
//   TRAFFIC     requests per second, by route pattern
//   ERRORS      5xx rate; track 4xx separately, since those are client errors
//   SATURATION  thread pool queue length, connection pool usage, memory,
//               CPU — the leading indicators that predict the other three
//
// Built-in ASP.NET Core metrics give most of this already:
//   http.server.request.duration        histogram, tagged by route + status
//   http.server.active_requests
//   kestrel.active_connections
//   dotnet.thread_pool.queue.length     ← the best early saturation signal

// ── ALERT ON SYMPTOMS, NOT CAUSES ────────────────────────────────────────
//   ✓ "checkout p99 latency above 2s for 5 minutes"     users are affected
//   ✓ "5xx rate above 1% for 5 minutes"
//   ✓ "billing job has not succeeded in 26 hours"       ← absence
//   ✗ "CPU above 80%"                                   often harmless
//   ✗ "a pod restarted"                                 that is the design
//
// Cause-based alerts fire constantly without user impact and train everyone
// to ignore the page. Symptom-based alerts fire when something is actually
// wrong.

// ── THE ALERT MOST SYSTEMS ARE MISSING ───────────────────────────────────
// Background work fails SILENTLY: no traffic, no errors, no signal at all.
// Only an ABSENCE alert catches it:
//   expr: time() - job_last_success_timestamp_seconds > 93600
// Every scheduled job needs a last-success gauge and this alert. It is the
// only thing that detects a worker that died three weeks ago.

// ── SLOs, WHICH TURN ARGUMENTS INTO ARITHMETIC ───────────────────────────
//   SLI    what you measure: the fraction of requests under 500ms
//   SLO    the target: 99.5% over 30 days
//   BUDGET the allowance: 0.5% ≈ 3.6 hours of failure per month
//
// The value is in the error budget: while it holds, ship features; when it is
// exhausted, work on reliability. It converts "is this reliable enough?" from
// an opinion into a number both engineering and product can act on.

// ── A PRODUCTION-READY Program.cs, assembling the whole track ────────────

Interview Questions

Beginner: What is the difference between liveness and readiness probes?

Liveness answers "is this process broken in a way only a restart fixes?" and a failure causes the orchestrator to kill and restart the container. Readiness answers "can this instance serve traffic right now?" and a failure removes it from the load balancer without restarting it. The practical consequence is that external dependencies belong in readiness and never in liveness: if a database blip made liveness fail, every replica would restart simultaneously, and the resulting reconnection storm would keep the database down — the health check itself causes an outage. Readiness failing during the same blip simply stops routing traffic until the dependency recovers, which is the correct behaviour.

Beginner: Why use message templates rather than string interpolation in logs?

Because the template is what makes logs queryable. With LogInformation("Order {OrderId} shipped", id) the logging pipeline records the template and OrderId as a structured field, so you can filter by that field, group every occurrence of the same event, and count them regardless of the values. With an interpolated string the message is already flattened before the logger sees it, so every line is unique text, aggregation is impossible, and finding all shipment events means substring matching. Source-generated logging with [LoggerMessage] goes further by avoiding allocation entirely when the level is disabled.

Mid: Why is high cardinality dangerous in metrics but fine in traces?

Because they store data differently. A metric is a time series per unique label combination, retained at a fixed resolution for a long period, so adding a label with a million possible values creates a million series — memory, storage and query cost all scale with that, and it will exhaust a Prometheus instance or generate an enormous bill. Traces are individual records indexed for lookup rather than aggregated into series, so attaching an order id or user id to a span is exactly what they are for and costs nothing structurally. The rule that follows is that metrics take bounded labels only — route pattern, status code, method — while high-cardinality identifiers go into traces and structured logs, with the trace id linking the two.

Mid: Why must database migrations be backward compatible during a rolling deploy?

Because a rolling deploy runs old and new code simultaneously against a single database, often for minutes. If the migration drops or renames a column, instances still running the old code immediately start failing on every query touching it; if it adds a NOT NULL column without a default, old inserts fail. Both produce errors for real users during what was supposed to be a zero-downtime deployment. Backward-compatible changes — adding nullable columns, adding tables — are ignored by old code and are safe. A rename becomes a three-deploy sequence: add the new column and write to both while reading the old, then backfill and switch reads, then drop the old column once no running code references it.

Senior: A dependency slowed down and the entire API became unavailable. Explain the cascade and how to prevent it.

The mechanism is thread and connection exhaustion. When a dependency slows from milliseconds to seconds, each request holds its thread and its connection far longer, so concurrency in flight rises until the thread pool queue grows and the connection pool is exhausted. At that point every endpoint becomes slow, including ones that never touch the slow dependency, because they cannot acquire a thread — which is why the symptom is total unavailability rather than a single degraded feature. Retries make it worse: three retries multiplied across every replica turns a struggling dependency into an overwhelmed one, and the queue grows faster. The prevention is layered. Timeouts on every outbound call bound how long a single operation can hold resources, and the default in several clients is effectively infinite. A circuit breaker is the piece that actually stops the cascade, because once the failure ratio is exceeded it fails fast instead of queueing behind a dependency that is clearly unwell. A bulkhead caps concurrent calls to that dependency so it cannot consume the whole thread pool. Retries need jittered exponential backoff and should be restricted to idempotent operations. Load shedding at the edge converts saturation into fast 429s rather than slow timeouts, which is kinder to clients and cheaper for us. And for detection, thread-pool queue length is the leading indicator that predicts this minutes before latency alerts fire, which makes it worth a dashboard even though it is a cause rather than a symptom.

Senior: Design the observability and deployment strategy for a payment service.

I would start from what must never be ambiguous during an incident, which for payments is whether a given charge happened. That drives a correlation identifier propagated through W3C traceparent across every service and included in every log line and error response, so a customer's reference resolves the entire call graph in one query. Traces would use tail-based sampling in the collector — a low head ratio would discard exactly the failed traces I need — with all errors and all slow requests retained. Metrics stay strictly bounded: request duration by route pattern and status, payment outcomes by result category and provider, but never by customer or order id, since that cardinality would take the metrics backend down. Business metrics matter as much as technical ones here: charge success rate, decline rate by reason, and provider latency, because a rise in declines is a revenue incident that no 5xx alert will ever surface. For health checks, liveness stays purely internal while readiness covers the database and the provider — the provider mapped to Degraded rather than Unhealthy, so we keep serving reads and queue writes rather than removing every instance from the load balancer when a third party has a bad minute. Deployment would be rolling with a readiness drain before shutdown, migrations run as a separate ordered step with strictly backward-compatible changes, and canary analysis on the payment success rate rather than only on error rate. Resilience means per-attempt and total timeouts, a circuit breaker, and retries confined to idempotent operations — with an idempotency key required on every charge, because a retried timeout is otherwise a double charge, which is the failure mode that matters most in this domain. On alerting I would page on symptoms with user impact — success rate dropping, p99 latency, provider circuit open — and specifically include an absence alert on settlement and reconciliation jobs, since those fail silently and a gap is discovered days later in finance rather than in monitoring. Everything sensitive is redacted at the logging pipeline rather than by convention, because card data reaching logs is a compliance incident regardless of intent.

4 (medium): Deployments drop requests. Implement a proper drain.
Solution 
// THE RACE: on SIGTERM the app stops accepting connections immediately, but
// the load balancer only notices when its next readiness probe fails —
// several seconds later. Requests routed in that window are dropped.

public sealed class ReadinessState
{
    private volatile bool _ready = true;
    public bool IsReady => _ready;
    public void SetNotReady() => _ready = false;
}

builder.Services.AddSingleton<ReadinessState>();
builder.Services.AddHealthChecks()
    .AddCheck<ReadinessCheck>("readiness", tags: ["ready"]);

public sealed class ReadinessCheck(ReadinessState state) : IHealthCheck
{
    public Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken ct)
        => Task.FromResult(state.IsReady
            ? HealthCheckResult.Healthy()
            : HealthCheckResult.Unhealthy("Draining."));
}

public sealed class GracefulShutdown(
    IHostApplicationLifetime lifetime,
    ReadinessState readiness,
    ILogger<GracefulShutdown> log) : IHostedService
{
    public Task StartAsync(CancellationToken ct)
    {
        lifetime.ApplicationStopping.Register(() =>
        {
            readiness.SetNotReady();          // 1. /health/ready → 503
            log.LogInformation("Draining; waiting for the load balancer.");

            // 2. Wait longer than (probe period × failure threshold) so the
            //    LB definitely observes it. Blocking is CORRECT here: it
            //    holds the shutdown sequence while we keep serving.
            Thread.Sleep(TimeSpan.FromSeconds(10));

            log.LogInformation("Drain complete.");
        });                                    // 3. normal shutdown proceeds
        return Task.CompletedTask;
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(25));

5 (hard): A slow payment provider takes down the whole API. Add resilience and explain each policy.
Solution 
// THE CASCADE: the provider slows from 200ms to 30s. Each request holds its
// thread and connection 150x longer, the thread pool queue grows, and
// eventually EVERY endpoint is slow — including ones that never call
// payments — because none can acquire a thread.

builder.Services.AddHttpClient<IPaymentGateway, StripeGateway>(client =>
{
    client.BaseAddress = new Uri(config["Payments:BaseUrl"]!);
})
.AddResilienceHandler("payments", pipeline =>
{
    // 1. TOTAL TIMEOUT — the absolute bound across all attempts. Without
    //    this, retries multiply the worst case.
    pipeline.AddTimeout(TimeSpan.FromSeconds(20));

    // 2. RETRY — only TRANSIENT failures, jittered so replicas do not
    //    synchronise into a thundering herd against a struggling service.
    pipeline.AddRetry(new HttpRetryStrategyOptions
    {
        MaxRetryAttempts = 2,
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        ShouldHandle = args => ValueTask.FromResult(
            args.Outcome.Result?.StatusCode is HttpStatusCode.ServiceUnavailable
                                             or HttpStatusCode.GatewayTimeout
            || args.Outcome.Exception is HttpRequestException)
    });

    // 3. CIRCUIT BREAKER — THE POLICY THAT ACTUALLY STOPS THE CASCADE.
    //    Once half the calls in the window fail, stop calling and fail fast.
    //    Without it, retries make an overloaded dependency worse.
    pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
    {
        FailureRatio = 0.5,
        SamplingDuration = TimeSpan.FromSeconds(30),
        MinimumThroughput = 10,
        BreakDuration = TimeSpan.FromSeconds(15)
    });

    // 4. PER-ATTEMPT TIMEOUT — bounds how long ONE call holds a thread.
    pipeline.AddTimeout(TimeSpan.FromSeconds(5));
});

// 5. BULKHEAD — cap concurrent payment calls so this dependency can never
//    consume the whole thread pool, regardless of the above.
builder.Services.AddResiliencePipeline("payment-bulkhead", pipeline =>
    pipeline.AddConcurrencyLimiter(permitLimit: 20, queueLimit: 10));

{
    return await gateway.ChargeAsync(request, ct);
}
catch (BrokenCircuitException)
{

// retry, which wraps the circuit breaker, which wraps the per-attempt
// timeout. A per-attempt timeout INSIDE retry means each attempt is bounded;
// outside it, one slow attempt would consume the whole budget.
//
// IDEMPOTENCY IS MANDATORY HERE: retrying a charge after a timeout can
// double-charge unless the request carries an idempotency key.
6 (hard): Define the alerts for an order service, and say which failures each catches.
Solution 
# ── SYMPTOM ALERTS: page a human, users are affected ────────────────────

- alert: HighErrorRate
  expr: |
    sum(rate(http_server_request_duration_seconds_count{status=~"5.."}[5m]))
    / sum(rate(http_server_request_duration_seconds_count[5m])) > 0.01
  for: 5m
  labels: { severity: page }
  # CATCHES: a bad deploy, a dependency failing, an unhandled exception path.
  # 4xx is deliberately EXCLUDED — client errors are not our outage.

- alert: HighLatency
  expr: |
    histogram_quantile(0.99,
      sum(rate(http_server_request_duration_seconds_bucket{status!~"5.."}[5m]))
      by (le, http_route)) > 2
  for: 5m
  labels: { severity: page }
  # status!~"5.." matters: fast failures otherwise flatter the percentile and
  # hide a genuine slowdown behind a rising error rate.

- alert: CheckoutSuccessRateDropped
  expr: |
    sum(rate(orders_created_total{outcome="success"}[10m]))
    / sum(rate(orders_created_total[10m])) < 0.95
  for: 10m
  labels: { severity: page }
  # CATCHES the incident no technical alert sees: every request returns 200
  # while payments are being declined. A BUSINESS metric is the only signal.

# ── ABSENCE ALERT: the one most systems are missing ─────────────────────

- alert: NightlyReconciliationNotCompleting
  expr: time() - job_last_success_timestamp_seconds{job="reconciliation"} > 93600
  labels: { severity: page }
  # CATCHES a background worker that died silently. It produces NO errors and
  # NO traffic, so every rate-based alert above is blind to it. Without this,
  # a worker that stopped three weeks ago is discovered by finance.

# ── SATURATION: warn, do not page — leading indicators ──────────────────

- alert: ThreadPoolStarvation
  expr: dotnet_thread_pool_queue_length > 100
  for: 5m
  labels: { severity: warn }
  # The BEST early warning of a cascading failure — it rises minutes before
  # latency does, usually because a dependency slowed and threads are blocked.

- alert: OutboxBacklogGrowing
  expr: outbox_unprocessed_messages > 1000
  for: 15m
  labels: { severity: warn }
  # The publisher is stalled: data is committing but events are not reaching
  # downstream systems. Invisible in API metrics entirely.

# ── WHAT I DELIBERATELY DO NOT ALERT ON ─────────────────────────────────
#   ✗ CPU > 80%           often perfectly healthy under load
#   ✗ memory > 80%        the GC is supposed to use available memory
#   ✗ a pod restarted     that is the orchestrator working as designed
#   ✗ any single 5xx      noise; the RATE is what matters
#
# Cause-based alerts fire without user impact and train the team to ignore
# the page — which is how the one real incident gets missed.

# ── THE SLO THAT TIES IT TOGETHER ───────────────────────────────────────
#   SLI:    fraction of checkout requests succeeding under 2s
#   SLO:    99.5% over 30 days
#   BUDGET: 0.5% ≈ 3.6 hours per month
# While budget remains, ship features. When it is exhausted, reliability work
# takes priority — turning "is this reliable enough?" into arithmetic rather
# than an argument.

🎯 Key Takeaways

  • Liveness must check nothing external — a dependency in the liveness probe turns a blip into a restart storm.
  • Degraded is a useful state: keep serving when a non-essential dependency is down.
  • Log message templates, not interpolated strings, and log client mistakes at Information rather than Error.
  • Metrics take bounded labels only — route patterns, not paths; identifiers belong in traces and logs.
  • OpenTelemetry unifies traces, metrics and logs; use tail sampling so errors survive a low head-sampling ratio.
  • Fail readiness and wait before shutting down, or the load balancer keeps routing to a draining instance.
  • Rolling deploys run old and new code together, so migrations must be backward compatible and renames take three deploys.
  • Retries without a circuit breaker amplify an outage; timeouts on every outbound call prevent thread-pool starvation.
  • Alert on symptoms and on business outcomes, not on CPU or restarts.
  • Every scheduled job needs a last-success gauge and an absence alert — silent failure is the defining property of background work.
