Filters & Cross-Cutting Concerns The Pipeline

What you'll master: the MVC filter pipeline and its five filter types, endpoint filters for minimal APIs and how the two models differ, the execution order that decides which filter wins, filters that need dependencies, and the judgement call of what belongs in a filter versus middleware versus the domain. Prerequisites: Middleware Pipeline and Dependency Injection.

Part 1 — Why Filters Exist When Middleware Already Does

// Middleware runs for every request that reaches it and sees only the raw
// HttpContext. Filters run INSIDE the endpoint's execution, after routing has
// selected it and after model binding has produced typed arguments.
//
// The difference that decides which to use:
//
//   MIDDLEWARE                         FILTERS
//   runs before routing completes      runs after the endpoint is selected
//   sees HttpContext only              sees bound arguments and the result
//   applies to every request           applies per endpoint/controller/group
//   cannot read [Authorize] metadata   can read endpoint metadata
//   cannot short-circuit with a        can return an IActionResult directly
//     typed result
//
// Concretely: correlation IDs, HTTPS redirection, forwarded headers and
// exception handling are middleware, because they must apply to everything
// including requests that match no endpoint. Validating a bound DTO, checking
// that the caller owns the resource being requested, or caching an action's
// result are filters, because they need the model or the endpoint identity.

// THE FIVE MVC FILTER TYPES, in execution order:
//
//   1. AUTHORIZATION  — runs first, short-circuits everything. Never do I/O
//                       here; use policies (see the Authorization lesson).
//   2. RESOURCE       — around model binding. The only place to intercept
//                       BEFORE binding — output caching lives here.
//   3. ACTION         — around the action method. Sees bound arguments and
//                       the returned result. The most commonly used type.
//   4. EXCEPTION      — handles unhandled exceptions from the action.
//   5. RESULT         — around result EXECUTION (serialization, writing).
//
// The ordering is not arbitrary: each stage has strictly more information
// available than the one before it, and correspondingly less ability to avoid
// work that has already happened.

Part 2 — Action Filters, the Workhorse

// The interface form — two methods, before and after:
public sealed class TimingFilter : IActionFilter
{
    private const string Key = "__timing";

    public void OnActionExecuting(ActionExecutingContext context)
    {
        context.HttpContext.Items[Key] = Stopwatch.StartNew();
        // Short-circuit by setting Result — the action never runs:
        // context.Result = new BadRequestObjectResult("nope");
    }

    public void OnActionExecuted(ActionExecutedContext context)
    {
        var sw = (Stopwatch)context.HttpContext.Items[Key]!;
        sw.Stop();
        // context.Exception is populated if the action threw.
        // Setting context.ExceptionHandled = true swallows it.
    }
}

// The ASYNC form — preferred, because one method makes the wrapping explicit
// and there is nowhere to accidentally block:
public sealed class AuditFilter(IAuditService audit) : IAsyncActionFilter
{
    public async Task OnActionExecutionAsync(
        ActionExecutingContext context, ActionExecutionDelegate next)
    {
        // BEFORE — arguments are bound and available by name:
        var id = context.ActionArguments.TryGetValue("id", out var v) ? v : null;

        await audit.RecordAsync(context.HttpContext.User, id);

        var executed = await next();     // runs the action (and later filters)

        // AFTER — the result and any exception are available:
        if (executed.Exception is null)
            await audit.RecordSuccessAsync(context.HttpContext.User);
    }
}
// Implement EITHER the sync or async interface, never both — if a filter
// implements both, only the async one runs and the sync methods are silently
// ignored, which produces "my filter does nothing" confusion.

// ATTRIBUTE FILTERS WITH DEPENDENCIES — attributes cannot take constructor
// injection, so use one of these:

// [ServiceFilter] — the filter is resolved from DI, registered separately:
builder.Services.AddScoped<AuditFilter>();
[ServiceFilter(typeof(AuditFilter))]
public IActionResult Get(int id) => Ok();

// [TypeFilter] — the filter is constructed by the container without needing
// registration, and can take extra literal arguments:
[TypeFilter(typeof(RoleFilter), Arguments = ["admin"])]
public IActionResult Delete(int id) => NoContent();

// IFilterFactory — a self-activating attribute, the cleanest for reuse:
public sealed class AuditAttribute : Attribute, IFilterFactory
{
    public bool IsReusable => false;
    public IFilterMetadata CreateInstance(IServiceProvider sp)
        => ActivatorUtilities.CreateInstance<AuditFilter>(sp);
}
[Audit]                                   // ← plain attribute, DI works
public IActionResult Post(Order order) => Ok();

Part 3 — Scope and Execution Order

// Filters can be registered at three scopes, and order is decided in two
// stages: first by Order property, then by scope.

// GLOBAL — every action in the application:
builder.Services.AddControllers(options =>
{
    options.Filters.Add<TimingFilter>();
    options.Filters.Add(new RequireHttpsAttribute());
});

// CONTROLLER — every action on the controller:
[Audit]
public class OrdersController : ControllerBase { }

// ACTION — one action:
public class OrdersController : ControllerBase
{
    [Audit]
    public IActionResult Get(int id) => Ok();
}

// DEFAULT ORDER (all Order = 0), on the way IN:
//   global → controller → action
// and on the way OUT, exactly reversed:
//   action → controller → global
//
// This nests like middleware: global filters are outermost, so they see the
// request first and the result last.

// EXPLICIT ORDER OVERRIDES SCOPE ENTIRELY — this is the part that surprises:
[Audit(Order = 10)]                       // controller-level, order 10
public class OrdersController : ControllerBase
{
    [Timing(Order = 1)]                   // action-level, order 1
    public IActionResult Get(int id) => Ok();
}
// Timing runs FIRST despite being action-scoped, because a lower Order wins
// regardless of scope. Scope only breaks ties among equal Order values.
//
// Practical advice: leave Order alone unless you have a genuine dependency
// between two filters. An explicit Order is a number a future reader must
// hunt down to understand, and it silently outranks the scope intuition
// everyone else is relying on.

// FILTERS ON THE SAME ACTION FROM DIFFERENT SOURCES all apply — there is no
// "override". A [Authorize] on the controller and another on the action means
// BOTH are enforced, not the more specific one. Removing controller-level
// protection requires [AllowAnonymous], which is an explicit opt-out rather
// than a replacement.
Key insight: filters make cross-cutting behaviour declarative, and that is both the appeal and the risk. An attribute on a controller reads as documentation, but it also means the behaviour is invisible at the call site and can be forgotten when someone adds a new controller. This is why security concerns belong in a global filter or a fallback policy that applies by default and is opted out of explicitly, never in a per-controller attribute that must be remembered — the failure mode of a forgotten attribute is an unprotected endpoint, and it looks exactly like correct code.

Part 4 — Endpoint Filters for Minimal APIs

// Minimal APIs have ONE filter type instead of five, and it wraps the whole
// handler invocation.
public sealed class ValidationFilter<T>(IValidator<T> validator)
    : IEndpointFilter where T : class
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context, EndpointFilterDelegate next)
    {
        if (context.Arguments.OfType<T>().FirstOrDefault() is not { } model)
            return await next(context);

        var result = await validator.ValidateAsync(
            model, context.HttpContext.RequestAborted);

        if (!result.IsValid)
            return TypedResults.ValidationProblem(result.ToDictionary());

        return await next(context);      // not calling next() short-circuits
    }
}

// Applied per endpoint or per group:
app.MapPost("/orders", Create).AddEndpointFilter<ValidationFilter<CreateOrder>>();

var group = app.MapGroup("/api/orders")
    .AddEndpointFilter<ValidationFilter<CreateOrder>>()   // whole group
    .AddEndpointFilter<AuditFilter>();

// Inline, for something small:
app.MapGet("/items/{id:int}", GetItem)
   .AddEndpointFilter(async (context, next) =>
   {
       var id = context.GetArgument<int>(0);
       if (id > 1_000_000) return TypedResults.NotFound();
       return await next(context);
   });

// DIFFERENCES FROM MVC FILTERS THAT MATTER:
//   • one type, not five — no separate authorization/resource/result stages
//   • arguments come from context.Arguments POSITIONALLY (or GetArgument<T>),
//     not by name from a dictionary. Reordering handler parameters silently
//     changes which argument index a filter reads — a real refactoring hazard.
//   • the return value is the RESULT: return an IResult to short-circuit,
//     or the value from next() to continue
//   • DI works through the constructor normally, with no ServiceFilter dance
//   • they compose in registration order inbound, reverse outbound — the same
//     nesting model as everything else in this framework
//
// GROUP FILTERS RUN BEFORE ENDPOINT FILTERS, which mirrors the global →
// controller → action nesting of MVC.

Part 5 — Exception and Result Filters

// EXCEPTION FILTERS catch unhandled exceptions from the action and its
// filters — but NOT from middleware, model binding, or result execution.
public sealed class DomainExceptionFilter(ILogger<DomainExceptionFilter> log)
    : IAsyncExceptionFilter
{
    public Task OnExceptionAsync(ExceptionContext context)
    {
        if (context.Exception is not DomainException ex)
            return Task.CompletedTask;      // let it bubble to middleware

        log.LogWarning(ex, "Domain rule violated");

        context.Result = new ObjectResult(new ProblemDetails
        {
            Status = StatusCodes.Status409Conflict,
            Title = ex.Message,
            Instance = context.HttpContext.Request.Path
        })
        { StatusCode = StatusCodes.Status409Conflict };

        context.ExceptionHandled = true;    // ← without this it still bubbles
        return Task.CompletedTask;
    }
}

// WHEN TO PREFER EXCEPTION MIDDLEWARE INSTEAD: an exception filter only covers
// MVC actions, so exceptions from middleware or from a minimal API endpoint
// escape it entirely. For a uniform error contract across the whole
// application, UseExceptionHandler is the better home, and an exception filter
// is for genuinely MVC-specific handling. Using both is fine — the filter
// handles what it knows and lets everything else bubble to the middleware.

// RESULT FILTERS wrap result EXECUTION — serialization and writing:
public sealed class ETagFilter : IAsyncResultFilter
{
    public async Task OnResultExecutionAsync(
        ResultExecutingContext context, ResultExecutionDelegate next)
    {
        if (context.Result is ObjectResult { Value: not null } result
            && context.HttpContext.Request.Method == HttpMethods.Get)
        {
            var etag = ComputeETag(result.Value);
            context.HttpContext.Response.Headers.ETag = etag;

            // Conditional GET: skip serialization entirely if unchanged.
            var inm = context.HttpContext.Request.Headers.IfNoneMatch;
            if (inm == etag)
            {
                context.Result = new StatusCodeResult(
                    StatusCodes.Status304NotModified);
                return;                    // do NOT call next()
            }
        }

        await next();
    }
}
// This is a good example of why result filters exist: the header must be set
// BEFORE the body is written, and the decision needs the typed result object —
// middleware has neither.

// RESOURCE FILTERS run around model binding, so they are the only place to
// short-circuit before the body is read — which is what makes them the right
// home for output caching:
public sealed class CacheResourceFilter : IAsyncResourceFilter
{
    public async Task OnResourceExecutionAsync(
        ResourceExecutingContext context, ResourceExecutionDelegate next)
    {
        var key = context.HttpContext.Request.Path.ToString();
        if (_cache.TryGetValue(key, out IActionResult? cached))
        {
            context.Result = cached;       // binding never runs
            return;
        }
        var executed = await next();
        _cache.Set(key, executed.Result, TimeSpan.FromMinutes(5));
    }
}

Part 6 — What Belongs Where

// The judgement call that separates a maintainable codebase from a pile of
// attributes nobody can reason about.

// ── MIDDLEWARE ────────────────────────────────────────────────────────────
//   correlation IDs, HTTPS redirection, forwarded headers, CORS,
//   global exception handling, request logging, rate limiting
//   → must apply to EVERY request, including ones matching no endpoint
//   → needs no typed model

// ── FILTERS ───────────────────────────────────────────────────────────────
//   model validation, resource-ownership checks, response caching, ETags,
//   action-level auditing, per-endpoint feature flags
//   → needs the bound model, the endpoint identity, or the typed result
//   → applies to a SUBSET of endpoints

// ── THE DOMAIN ────────────────────────────────────────────────────────────
//   business rules, invariants, workflow state transitions
//   → NOT a filter, even when the rule rejects a request
//
// The last one is the mistake worth naming. "An order cannot be cancelled
// after dispatch" feels like a cross-cutting check and it is not: it depends
// on entity state, belongs in the aggregate, and needs to hold when the same
// operation is invoked from a background job or a message handler that never
// touches the filter pipeline. A rule enforced only in a filter is a rule
// with a hole in it the moment a second entry point exists.
//
// The test I apply: if this rule must still hold when the operation is called
// from a queue consumer with no HTTP request, it is domain logic, not a
// filter.

// FILTERS AND PERFORMANCE — they are not free:
//   • every filter is an allocation and an async state machine per request
//   • IFilterFactory with IsReusable = false constructs a new instance per
//     request; true caches it, but then the filter MUST be stateless and
//     thread-safe, and must not depend on scoped services
//   • an action filter that awaits I/O adds that latency to every decorated
//     request — an audit filter writing synchronously to a database doubles
//     the latency of every write endpoint
//
// A filter doing I/O on every request is usually a queue-it-and-return
// candidate, not a filter to optimise.

Interview Questions

Beginner: What is the difference between middleware and a filter?

Middleware sits in the application pipeline and runs for every request that reaches it, before routing has necessarily chosen an endpoint, and it sees only the raw HttpContext. A filter runs inside the execution of a specific endpoint, after routing and model binding, so it has access to the bound arguments, the endpoint's metadata, and the result the action produced. That drives the choice: concerns that must apply to everything including unmatched requests — correlation IDs, HTTPS redirection, global exception handling — belong in middleware, while concerns needing the typed model or applying only to a subset of endpoints — validation, resource-ownership checks, ETags — belong in filters.

Beginner: What are the five MVC filter types and what order do they run in?

Authorization filters run first and short-circuit everything if the caller is not permitted. Resource filters run next, wrapping model binding, which makes them the only place to intercept before the body is read — output caching lives there. Action filters wrap the action method itself and can see the bound arguments and the returned result; they are the most commonly used type. Exception filters handle unhandled exceptions escaping the action. Result filters wrap result execution, meaning serialization and writing the response. The ordering reflects increasing information: each stage knows more than the last, and correspondingly can avoid less of the work already done.

Mid: How do you inject dependencies into a filter applied as an attribute?

Attributes can only take compile-time constant arguments, so constructor injection is impossible directly. There are three routes. [ServiceFilter(typeof(T))] resolves the filter from the container, which requires registering it in DI. [TypeFilter(typeof(T))] has the container construct it without a registration and allows passing additional literal arguments alongside the injected ones. The cleanest for something reused widely is implementing IFilterFactory on the attribute itself, so the attribute stays a plain [Audit] at the usage site while CreateInstance uses ActivatorUtilities to build the real filter with its dependencies. In minimal APIs none of this applies — endpoint filters are classes resolved from DI normally, so constructor injection just works.

Mid: Two filters are applied, one on the controller with Order = 10 and one on the action with Order = 1. Which runs first, and why is that worth knowing?

The action-level filter with Order = 1 runs first, because Order is evaluated before scope: a lower Order wins regardless of whether the filter is global, controller-level or action-level, and scope only breaks ties between filters with equal Order. It is worth knowing because it inverts the intuition that scope determines nesting — most developers reasonably expect controller filters to always wrap action filters, and an explicit Order silently overrides that expectation. That is precisely why I would avoid setting Order unless two filters have a genuine dependency: it encodes execution sequence as a number a future reader has to hunt for, in a place they are not looking.

Senior: An audit filter on every write endpoint has doubled p99 latency. Diagnose and redesign.

The filter is almost certainly doing synchronous or blocking I/O in the request path — writing an audit row to a database, or worse calling a remote audit service — so its full latency is added to every decorated request, and any variance in that dependency shows up directly in the p99 rather than the median. The first check is whether it blocks: a .Result or .Wait() inside a filter consumes a thread-pool thread while waiting, which under load causes starvation and inflates latency across every endpoint, not just audited ones — that would explain a p99 impact out of proportion to the audit call's own duration. The redesign depends on what the audit is for. If it is compliance-critical and must be durable before the response is returned, then it genuinely belongs in the request path, but it should share the transaction with the business write so it cannot silently diverge, and it should be one round trip rather than a separate service call. If it is observational — the common case — it should not be in the request path at all: write to an in-memory channel and have a hosted service drain it in batches, which turns per-request latency into near-zero and amortises the writes. The trade-off to state explicitly is durability: a queued audit entry is lost if the process dies before the drain, so this is only acceptable when the audit is observational rather than a legal record. I would also question the scope — auditing every write uniformly is often over-collection, and restricting it to genuinely sensitive operations reduces both the latency cost and the storage bill.

Senior: How do you decide between a filter, middleware, and domain logic for a rule like "users may only access their own orders"?

This particular rule is a resource-ownership check, and my answer is that it belongs primarily in the domain or data layer, with a filter as an optional early rejection — never in a filter alone. The reasoning is about entry points: the rule depends on both the authenticated identity and the state of the entity being accessed, and it must hold for every path that can reach an order, including a background job reconciling records, a message handler processing an event, or a GraphQL resolver added later. A filter only runs on HTTP requests through the MVC pipeline, so enforcing it there leaves the rule with a hole the moment a second entry point exists, and that hole is invisible because the HTTP path is still correctly protected. Middleware is worse still, because it cannot know which order is being requested without duplicating routing and binding. So the durable enforcement is a query scoped by the current user — a global query filter or a repository that takes the principal — so an order the caller does not own is simply not returned, and a missing check produces a 404 rather than a leak. A filter can still be worthwhile on top of that as a fast-fail: it rejects obviously invalid access before the action does work, and it makes the intent visible at the endpoint. The test I apply generally is whether the rule must still hold when invoked with no HTTP context; if yes it is domain logic, and a filter is at most an optimisation or a documentation aid. The related judgement is that authorization requiring only claims — roles, scopes, tenancy from a token — is properly an authorization policy rather than a hand-written filter, because policies are declarative, testable in isolation, and integrate with the fallback-policy mechanism that makes endpoints protected by default.

{

        // Set BEFORE the action runs — afterwards the response may have

Solution 
// Attributes cannot take injected constructor arguments, so the attribute
// becomes a FACTORY for the real filter.

public sealed class AuditFilter(IAuditService audit) : IAsyncActionFilter
{
    public async Task OnActionExecutionAsync(
        ActionExecutingContext context, ActionExecutionDelegate next)
    {
        await audit.RecordAsync(context.HttpContext.User,
                                context.ActionDescriptor.DisplayName);
        await next();
    }
}

{

    // true would cache the instance, requiring it to be stateless AND
    // forbidding scoped dependencies entirely.

    public IFilterMetadata CreateInstance(IServiceProvider sp)
        => ActivatorUtilities.CreateInstance<AuditFilter>(sp);

Solution 
public sealed class ValidationFilter<T>(IValidator<T> validator)
    : IEndpointFilter where T : class
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context, EndpointFilterDelegate next)
    {
        // Match by TYPE rather than by position: parameter order changes
        // during refactors, and a positional read would silently start

        return await next(context);
    }

4 (medium): Add ETag support so unchanged GET responses return 304 without serializing the body.
Solution 
public sealed class ETagFilter : IAsyncResultFilter
{
    public async Task OnResultExecutionAsync(
        ResultExecutingContext context, ResultExecutionDelegate next)
    {
        var request = context.HttpContext.Request;

        if (request.Method != HttpMethods.Get
            || context.Result is not ObjectResult { Value: not null } result)
        {
            await next();
            return;
        }

        var etag = $"\"{Convert.ToHexString(
            SHA256.HashData(JsonSerializer.SerializeToUtf8Bytes(result.Value)))[..16]}\"";

        context.HttpContext.Response.Headers.ETag = etag;

        if (request.Headers.IfNoneMatch.Contains(etag))
        {
            context.Result = new StatusCodeResult(StatusCodes.Status304NotModified);
            return;            // do NOT call next() — skips serialization
        }

        await next();
    }
}

// WHY A RESULT FILTER: the ETag must be set before the body is written, and
// computing it needs the typed result object. Middleware has the timing but
// not the object; an action filter has the object but runs before result
// execution, where the header could still be set — but it cannot cleanly
// substitute a 304 for the result without duplicating result-execution logic.
//
// HONEST LIMITATION: this still serializes once to compute the hash, so it
// saves bandwidth, not CPU. A genuine optimisation stores the ETag alongside
// the entity (a rowversion or updated-at timestamp) and compares before
// loading the object at all.
5 (hard): Security is enforced by [Authorize] on each controller, and a new controller shipped unprotected. Redesign so this cannot recur.
Solution 
// THE PROBLEM: per-controller attributes are an ALLOWLIST maintained by
// memory. Forgetting one produces an unprotected endpoint that looks exactly
// like correct code — nothing fails, no test breaks, and review has to notice
// an ABSENCE.

// FIX — invert the default: everything is protected unless explicitly opted
// out. A fallback policy applies to any endpoint with NO authorization
// metadata of its own.
builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build());

// Now a new controller with no attribute is protected by default, and public
// endpoints must say so out loud:
[AllowAnonymous]
public class HealthController : ControllerBase { }

// EQUIVALENT FOR MINIMAL APIs — on the group, so new endpoints inherit it:
var api = app.MapGroup("/api").RequireAuthorization();
api.MapGet("/public", () => ...).AllowAnonymous();   // explicit opt-out

// DEFENCE IN DEPTH — a test that enumerates every endpoint and asserts each
// one either requires authorization or is deliberately listed as public:
[Fact]
public void Every_endpoint_is_protected_or_explicitly_public()
{
    var known = new HashSet<string> { "/health", "/api/public" };

    var endpoints = _factory.Services
        .GetRequiredService<EndpointDataSource>().Endpoints;

    foreach (var e in endpoints.OfType<RouteEndpoint>())
    {
        var anonymous = e.Metadata.GetMetadata<IAllowAnonymous>() is not null;
        var pattern = e.RoutePattern.RawText!;

        if (anonymous)
            Assert.Contains(pattern, known);   // new public endpoint = failing
    }                                          // test, reviewed deliberately
}

// WHY BOTH: the fallback policy fixes the default, and the test makes any
// future opt-out a deliberate, reviewed decision rather than a silent one.
// The failure mode moves from "unprotected endpoint in production" to "a
// failing test in CI", which is the entire point.
6 (hard): Design cross-cutting concerns for an API with validation, auditing, caching, tenant isolation and error handling. Say where each lives and why.
Solution 
// ── MIDDLEWARE (applies to everything, needs no typed model) ─────────────
app.UseExceptionHandler(...);   // 1. outermost: uniform problem-details errors
                                //    for MVC, minimal APIs and middleware alike
app.UseCorrelationId();         // 2. every log line and error response needs it
app.UseForwardedHeaders();      // 3. before anything reads IP or scheme
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();         // 4. with a FALLBACK POLICY: protected by
                                //    default, opted out explicitly
app.UseRateLimiter();           // 5. after auth so limits key on user identity

// ── FILTERS (needs the bound model or endpoint identity) ─────────────────
//   VALIDATION → endpoint filter / action filter.
//     Needs the deserialized model, applies per endpoint. Returns
//     ValidationProblem so the error contract matches the middleware's.
//
//   CACHING → resource filter or output-caching middleware.
//     A resource filter can short-circuit BEFORE model binding, which is the
//     whole point: a cache hit should not pay deserialization cost.
//
//   ETAGS → result filter, because the header must be written before the body
//     and the decision needs the typed result.

// ── DOMAIN / DATA LAYER (must hold with no HTTP request) ─────────────────
//   TENANT ISOLATION → a global query filter, NOT a request filter:
modelBuilder.Entity<Order>().HasQueryFilter(o => o.TenantId == _tenant.Current);
//     A filter-only check is bypassed by background jobs, message handlers and
//     any future entry point. The query filter holds everywhere, so a missing
//     WHERE cannot leak rows. A request filter on top is a fast-fail and a
//     documentation aid, not the enforcement.
//
//   BUSINESS RULES → the aggregate. "Cannot cancel after dispatch" depends on
//     entity state and must hold for the queue consumer too.

// ── AUDITING — the one that needs a decision, not a location ─────────────
//   Observational auditing → an action/endpoint filter writing to an in-memory
//   Channel, drained by a hosted service in batches. Keeps per-request latency
//   near zero.
//     TRADE-OFF: entries queued but not drained are LOST if the process dies.
//     Acceptable for observability, NOT for a legal record.
//
//   Compliance auditing → inside the same transaction as the business write,
//   in the application service. It must be atomic with the change it records,
//   which a filter fundamentally cannot guarantee: a filter runs outside the
//   handler's transaction, so a crash between them leaves the audit and the
//   data disagreeing.

// ── THE ORGANISING PRINCIPLE ─────────────────────────────────────────────
// Ask what happens when the operation is invoked with NO HTTP request. If the
// concern must still apply, it is not a filter — it is domain or data-layer
// responsibility. Filters are for concerns that are genuinely about the HTTP
// endpoint: shaping requests and responses, not enforcing truth about data.

🎯 Key Takeaways

  • Middleware sees raw HttpContext and runs for everything; filters see bound arguments and the endpoint, and apply to a subset.
  • MVC has five filter types running authorization → resource → action → exception → result, each with more information than the last.
  • Minimal APIs have one IEndpointFilter that wraps the handler and supports normal constructor injection.
  • Implement either the sync or async filter interface, never both — implementing both silently runs only the async one.
  • Order is evaluated before scope, so an action filter can outrank a global one; leave it at 0 unless filters genuinely depend on each other.
  • Controller and action filters both apply — there is no override. Opt out of authorization explicitly with [AllowAnonymous].
  • Attributes cannot take injected dependencies: use [ServiceFilter], [TypeFilter] or IFilterFactory.
  • Never enforce security with per-controller attributes — use a fallback policy so endpoints are protected by default and opt-outs are visible.
  • Exception filters only catch action-scope exceptions; use UseExceptionHandler for a contract covering middleware and minimal APIs too.
  • If a rule must hold when invoked without an HTTP request, it is domain logic — a filter enforcing it alone leaves a hole for every other entry point.
