Error Handling & Problem Details The Pipeline

What you'll master: a single error contract that covers MVC, minimal APIs and middleware alike, IExceptionHandler and the handler chain, mapping domain failures to honest status codes, what must never appear in an error response, and how to make failures diagnosable in production without leaking internals. Prerequisites: Middleware Pipeline and Model Binding & Validation.

Part 1 — One Contract, Every Failure

// The goal: a client parses ONE error shape regardless of which layer failed.
// RFC 9457 (which obsoleted RFC 7807) defines it, and ASP.NET Core has it
// built in.

builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = ctx =>
    {
        ctx.ProblemDetails.Instance = ctx.HttpContext.Request.Path;
        ctx.ProblemDetails.Extensions["traceId"] =
            Activity.Current?.Id ?? ctx.HttpContext.TraceIdentifier;
    };
});

// The shape every failure produces:
// {
//   "type":     "https://tools.ietf.org/html/rfc9110#section-15.5.1",
//   "title":    "One or more validation errors occurred.",
//   "status":   400,
//   "instance": "/api/orders",
//   "traceId":  "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
//   "errors":   { "Quantity": ["Must be between 1 and 999."] }
// }
//
// FIELD BY FIELD, and why each earns its place:
//   type     a URI identifying the error CLASS — stable, documentable
//   title    a short human summary, the same for every instance of this type
//   status   duplicates the HTTP status, so a logged body is self-contained
//   detail   instance-specific explanation (optional, and see Part 5 on leaks)
//   instance which request this was
//   traceId  ← the single most valuable field in production. It turns a user's
//            screenshot into a log query. Without it, "the site broke at about
//            three" is the entire bug report.

// AddProblemDetails also converts bare status-code responses into the same
// shape, so a 404 from routing looks like a 404 from your handler:
app.UseStatusCodePages();

// WHAT THIS BUYS: a client writes one error parser. Without it, a validation
// failure returns one shape, an unhandled exception returns an HTML page, a
// 404 from routing returns an empty body, and every consumer writes
// defensive code for all three.

Part 2 — IExceptionHandler, the Modern Approach

// .NET 8 introduced IExceptionHandler — a chain of typed handlers, each of
// which can claim an exception or pass it along. This replaces the older
// pattern of one large UseExceptionHandler lambda with a switch.

public sealed class DomainExceptionHandler(ILogger<DomainExceptionHandler> log)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context, Exception exception, CancellationToken ct)
    {
        if (exception is not DomainException ex)
            return false;             // ← not mine; try the next handler

        log.LogWarning(ex, "Domain rule violated at {Path}", context.Request.Path);

        context.Response.StatusCode = StatusCodes.Status409Conflict;
        await context.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = StatusCodes.Status409Conflict,
            Title = "The operation conflicts with the current state.",
            Detail = ex.Message,          // safe: domain messages are authored
            Instance = context.Request.Path,
            Extensions = { ["traceId"] = Activity.Current?.Id }
        }, ct);

        return true;                  // handled — stop the chain
    }
}

// A catch-all registered LAST, for everything unclaimed:
public sealed class UnhandledExceptionHandler(ILogger<UnhandledExceptionHandler> log)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context, Exception exception, CancellationToken ct)
    {
        log.LogError(exception, "Unhandled exception at {Path}", context.Request.Path);

        context.Response.StatusCode = StatusCodes.Status500InternalServerError;
        await context.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 500,
            // NO Detail. A 500 means we did not anticipate this, so the
            // message may contain a connection string, a file path, or a
            // stack frame. See Part 5.
            Title = "An unexpected error occurred.",
            Instance = context.Request.Path,
            Extensions = { ["traceId"] = Activity.Current?.Id }
        }, ct);

        return true;
    }
}

// REGISTRATION ORDER IS EXECUTION ORDER — specific first, catch-all last:
builder.Services.AddExceptionHandler<DomainExceptionHandler>();
builder.Services.AddExceptionHandler<ValidationExceptionHandler>();
builder.Services.AddExceptionHandler<UnhandledExceptionHandler>();
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler();     // ← still required to install the middleware

// Registering the catch-all first would make it claim everything and the
// specific handlers would never run — a silent behaviour change from a
// registration reorder.
Key insight: the exception handler middleware must be registered first in the pipeline, and that is not a stylistic preference. It works by catching exceptions that propagate up from everything registered below it, so anything above it is outside its protection — an exception in a middleware registered earlier escapes to the web server and produces a raw HTML error page, which is exactly the inconsistency the problem-details contract exists to eliminate. The pipeline nests, and the error handler must be the outermost frame.

Part 3 — Mapping Failures to Honest Status Codes

// The status code is the first thing a client branches on, so getting it right
// matters more than the body. The distinctions that are routinely got wrong:

// 400 vs 422 — MALFORMED vs SEMANTICALLY INVALID
//   400  the request could not be parsed or bound: invalid JSON, a string
//        where an int belongs, a missing required field
//   422  it parsed fine and the content is unacceptable: a date in the past
//        where a future date is required
//   ASP.NET Core defaults to 400 for both. That is defensible; what is NOT
//   defensible is mixing them arbitrarily across endpoints, because then a
//   client cannot write one handler.

// 401 vs 403 — the one that produces support tickets
//   401 Unauthorized  authentication is MISSING or INVALID. Retrying with
//                     credentials could succeed. The name is a spec misnomer;
//                     it means "unauthenticated".
//   403 Forbidden     identity is established and still not permitted.
//                     Retrying changes nothing.
//   Returning 401 for a permissions failure sends clients into a re-login
//   loop against a wall — they authenticate successfully, retry, get 401
//   again, and conclude the login is broken.

// 404 vs 403 — a DELIBERATE security decision
//   Returning 403 for a resource the caller may not see CONFIRMS IT EXISTS.
//   That is an information leak: an attacker enumerating /orders/{id} learns
//   which ids are real. Returning 404 for both "does not exist" and "not
//   yours" leaks nothing.
//   The trade-off is diagnosability — a legitimate user with a permissions
//   problem sees "not found" and files a confusing ticket. Resolve it by
//   logging the real reason server-side with the traceId, so support can
//   distinguish them without the response doing so.

// 409 vs 400 — STATE conflicts are not input errors
//   "Cannot cancel an order after dispatch" is a 409: the request was
//   perfectly well-formed and simply arrived against the wrong state.
//   Returning 400 tells the client its input was malformed, which is a lie
//   that sends developers to debug their serialization.

// 500 vs 502/503/504 — WHOSE fault
//   500  our code failed unexpectedly
//   502  an upstream dependency returned garbage
//   503  we are deliberately refusing load (shedding, maintenance)
//   504  an upstream dependency timed out
//   The distinction drives client retry behaviour: 503 and 504 are worth
//   retrying with backoff, a 500 usually is not, and blanket-500 makes
//   every failure look permanent.

// Implemented as one map, so the policy lives in one reviewable place:
context.Response.StatusCode = exception switch
{
    ValidationException        => StatusCodes.Status400BadRequest,
    UnauthorizedAccessException => StatusCodes.Status403Forbidden,
    NotFoundException          => StatusCodes.Status404NotFound,
    ConflictException          => StatusCodes.Status409Conflict,
    TimeoutException           => StatusCodes.Status504GatewayTimeout,
    _                          => StatusCodes.Status500InternalServerError
};

Part 4 — Development vs Production

// The developer exception page is genuinely useful and genuinely dangerous.
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();   // stack trace, headers, query, cookies
}
else
{
    app.UseExceptionHandler();         // problem details, no internals
    app.UseHsts();
}

// WHAT THE DEVELOPER PAGE EXPOSES: the full stack trace including file paths
// and line numbers, the request headers (so, the Authorization header and
// session cookies), the query string, and the routing table. Enabling it in
// production hands an attacker a map of the application — framework versions,
// internal namespaces, file layout, and often connection strings from an
// inner exception message.
//
// The failure mode is not usually "someone enabled it deliberately". It is
// ASPNETCORE_ENVIRONMENT being unset or misspelled in one environment, so
// IsDevelopment() returns true in production. That is why the environment
// variable is worth asserting at startup:
if (app.Environment.IsProduction() && app.Environment.IsDevelopment())
    throw new InvalidOperationException("Contradictory environment.");

// A more useful guard — fail fast if the environment is not one of the three
// canonical values, rather than silently defaulting to Production behaviour:
var env = app.Environment.EnvironmentName;
if (env is not ("Development" or "Staging" or "Production"))
    throw new InvalidOperationException($"Unexpected environment '{env}'.");

// STAGING SHOULD BEHAVE LIKE PRODUCTION. A staging environment running the
// developer page is a staging environment that cannot validate the production
// error contract — the thing you most want staging to prove.

Part 5 — What Must Never Reach the Client

// Error responses are an information-disclosure surface. The rules:

// ✗ NEVER return ex.Message from an UNANTICIPATED exception.
//   Real examples of what ends up in there:
//     SqlException     → "Login failed for user 'app_prod'." + server name
//     IOException      → "Could not find file 'C:\app\secrets\key.pem'."
//     HttpRequestException → the full internal URL of a service
//     NullReferenceException → nothing useful, but confirms a code path
context.Response.StatusCode = 500;
await context.Response.WriteAsJsonAsync(new ProblemDetails
{
    Status = 500,
    Title = "An unexpected error occurred.",   // ✓ constant, safe
    Instance = context.Request.Path,
    Extensions = { ["traceId"] = Activity.Current?.Id }
});

// ✓ DO return ex.Message from exceptions YOU AUTHORED for this purpose.
//   A DomainException's message was written by a developer to be read by a
//   caller. That is the distinction: authored-for-display versus incidental.
public sealed class DomainException(string message) : Exception(message);

// ✗ NEVER include a stack trace in a production response, even truncated.
// ✗ NEVER echo back the full request body in an error — it may contain the
//   password the user just submitted, and it will be logged by the client too.
// ✗ NEVER let a 500 differ by input in a way that reveals structure. If
//   /users/1 returns 500 and /users/abc returns 400, an attacker learns the
//   id is numeric and that id 1 hits a code path with a bug.

// THE RECONCILIATION — diagnosable without leaking:
//   put EVERYTHING in the LOG, keyed by traceId
//   put NOTHING in the RESPONSE except the traceId
log.LogError(exception,
    "Unhandled {ExceptionType} at {Path} for user {UserId}",
    exception.GetType().Name,
    context.Request.Path,
    context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value);
// Support asks for the traceId from the user's screenshot; one log query
// returns the stack trace, the user, the path, and the correlated upstream
// calls. The client learned nothing; the engineer learned everything.

// LOGGING LEVELS MATTER TOO — a client sending bad input is not an error:
//   400/404 from client mistakes  → LogInformation or LogDebug
//   409 conflicts                 → LogWarning
//   500 unhandled                 → LogError
//   Logging every 404 at Error makes the error rate meaningless and trains
//   everyone to ignore the alert.

Part 6 — Errors Across Service Boundaries

// When your service calls another, its failures become yours to translate.

public sealed class UpstreamClient(HttpClient http, ILogger<UpstreamClient> log)
{
    public async Task<Product> GetAsync(int id, CancellationToken ct)
    {
        HttpResponseMessage response;
        try
        {
            response = await http.GetAsync($"/products/{id}", ct);
        }
        catch (TaskCanceledException ex) when (!ct.IsCancellationRequested)
        {
            // A TIMEOUT, not a client cancellation — the distinguishing check
            // is whether OUR token was signalled. Without the `when` clause
            // these are indistinguishable and every client disconnect looks
            // like an upstream timeout.
            throw new UpstreamTimeoutException("Product service timed out.", ex);
        }
        catch (HttpRequestException ex)
        {
            throw new UpstreamUnavailableException("Product service unreachable.", ex);
        }

        // Translate THEIR status into OURS deliberately:
        return response.StatusCode switch
        {
            HttpStatusCode.OK       => (await response.Content
                                          .ReadFromJsonAsync<Product>(ct))!,
            HttpStatusCode.NotFound => throw new NotFoundException($"Product {id}."),
            // THEIR 401 is not OUR 401. If our service credential is rejected,
            // that is OUR configuration problem — a 500 or 502, never a 401
            // passed through, which would tell our caller to re-authenticate
            // for a failure that has nothing to do with them.
            HttpStatusCode.Unauthorized or HttpStatusCode.Forbidden
                => throw new UpstreamAuthException("Upstream rejected our credentials."),
            _ => throw new UpstreamException($"Upstream returned {(int)response.StatusCode}.")
        };
    }
}

// Then map those to client-facing codes in the handler:
//   UpstreamTimeoutException     → 504 Gateway Timeout
//   UpstreamUnavailableException → 503 Service Unavailable
//   UpstreamAuthException        → 500 (our misconfiguration, not theirs)
//   NotFoundException            → 404
//
// WHY NOT JUST PASS UPSTREAM STATUS THROUGH: because the codes mean different
// things at different hops. An upstream 429 means WE are rate limited, not our
// caller — passing it through tells the caller to slow down when the fix is
// entirely on our side. Every boundary crossing needs a deliberate
// translation, and "pass it through" is a decision, not a default.

// PROPAGATE THE TRACE, so one traceId spans services:
//   W3C traceparent headers flow automatically with HttpClient when
//   OpenTelemetry or Activity is configured — that is what makes a single
//   traceId in your error response resolvable across the whole call graph.

Interview Questions

Beginner: What is RFC 9457 problem details and why use it?

It is a standard JSON shape for HTTP error responses, served as application/problem+json, with well-known fields: type identifying the error class, title as a short summary, status mirroring the HTTP status, detail for instance-specific information, and instance for the request path. The value is that a client writes one error parser instead of handling a different shape per failure mode — without it a validation failure, an unhandled exception and a routing 404 typically return three completely different bodies. In ASP.NET Core, AddProblemDetails plus UseStatusCodePages makes even bare status-code responses conform to it.

Beginner: Why must the exception handler middleware be registered first?

Because the pipeline nests: each middleware wraps everything registered after it, so exceptions propagate outward to earlier-registered components. The exception handler can therefore only catch failures from middleware and endpoints registered below it. Anything above it is outside its protection, and an exception there escapes to the web server, which produces its own HTML error page — breaking the JSON contract precisely when a client is least able to cope with it. Registering it first makes it the outermost frame, which is the same reasoning as an outer try/catch covering more than an inner one.

Mid: When would you return 404 instead of 403, and what do you give up?

When returning 403 would confirm that a resource exists to someone not entitled to know. If an endpoint returns 403 for orders belonging to other users and 404 for ids that do not exist, an attacker can enumerate valid ids by observing which code comes back — the response leaks the existence of records even though it withholds their content. Returning 404 for both cases leaks nothing. What you give up is diagnosability for legitimate users: someone with a genuine permissions problem sees "not found" and files a confusing support ticket. The resolution is to log the real distinction server-side against the traceId, so support can tell the two apart from the logs while the response stays uninformative. The same reasoning drives generic "invalid username or password" on login rather than saying which was wrong.

Mid: How does IExceptionHandler differ from a UseExceptionHandler lambda?

IExceptionHandler is a chain of registered classes, each with a TryHandleAsync returning a boolean that says whether it claimed the exception; returning false passes it to the next handler, and the middleware falls back to a default response if none claim it. That gives three practical advantages over one large lambda with a switch statement: each handler is a class with constructor injection so dependencies are explicit, each is independently unit-testable without spinning up a pipeline, and handlers can be added per feature without editing a central file. The important operational detail is that registration order is execution order, so a catch-all handler registered before the specific ones will claim everything and silently disable them.

Senior: A production API returns HTML for some errors, JSON for others, and one response leaked a connection string. Diagnose and fix.

Three distinct defects, and it is worth separating them because they have different fixes. The HTML responses mean exceptions are escaping the exception handler entirely — either it is not registered first, so middleware above it fails unprotected, or the failure occurs during result execution after the response has already started, at which point the handler cannot rewrite what is on the wire. I would confirm by checking pipeline order and by looking for whether the affected responses have a partial body. The inconsistent JSON suggests several error paths constructing their own bodies — a mix of manually written responses, framework defaults, and problem details — which is fixed by routing every failure through one handler chain plus AddProblemDetails and UseStatusCodePages, so even bare status codes conform. The leaked connection string is the serious one: something is returning ex.Message for an unanticipated exception, and a SqlException message routinely contains the server name and user. The rule I would enforce is that only exceptions authored by us for display — a DomainException whose message a developer wrote for a caller to read — may have their message returned; everything else gets a constant title and a traceId, with the full detail in the log. I would also check whether the developer exception page is reachable, since a misspelled ASPNETCORE_ENVIRONMENT is a common cause of exactly this symptom, and add a startup assertion that the environment name is one of the three canonical values. Finally I would add contract tests asserting the shape and the absence of a stack trace for a forced failure in each layer — middleware, binding, action, result execution — because this class of regression is invisible until someone reads a production response.

Senior: Design an error-handling strategy for a service with upstream dependencies, consumed by web, mobile and partner clients.

I would treat the error contract as public API with the same stability guarantees as the success shapes, standardise on problem details for every failure, and make the translation at each boundary explicit. Internally the service raises typed domain exceptions — not-found, conflict, validation, upstream-timeout — and a chain of IExceptionHandler implementations maps each to a status code in one reviewable place, with a catch-all registered last. The upstream translation is where most of the judgement lives: another service's status codes do not mean the same thing at my boundary, so passing them through is a bug rather than a shortcut. Their 404 may legitimately become my 404, but their 401 means my credentials were rejected, which is my misconfiguration and therefore a 500 or 502 — never a 401 telling my caller to re-authenticate. Their 429 means I am being throttled, not my caller, so it becomes a 503 with a Retry-After if I can estimate one. Timeouts become 504 and connection failures 503, both of which signal retryability, which matters because mobile clients on poor networks need to distinguish "try again" from "this will never work". For the three consumer types I would add a stable machine-readable error code alongside the human-readable title, because partners will otherwise branch on English prose and then the message can never be reworded or localised. The traceId goes on every response and propagates via W3C traceparent to upstream calls, so one identifier from a partner's email resolves the entire call graph. On disclosure, nothing unanticipated reaches the client: only messages authored for display are returned, everything else is a constant title with the detail in logs. I would enforce all of it with contract tests per failure class rather than documentation, and I would set logging levels so client mistakes log at information and only genuine faults log at error — otherwise the error rate is dominated by 404s and the alert becomes noise nobody reads.

3 (medium): Write an IExceptionHandler that maps NotFoundException to 404 and lets everything else pass through.
Solution 
public sealed class NotFoundExceptionHandler(ILogger<NotFoundExceptionHandler> log)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context, Exception exception, CancellationToken ct)
    {
        if (exception is not NotFoundException ex)
            return false;          // ← the pass-through: try the next handler

        // Information, not Error: a missing resource is a client mistake, and
        // logging it at Error makes the error rate meaningless.
        log.LogInformation("Not found: {Path}", context.Request.Path);

        context.Response.StatusCode = StatusCodes.Status404NotFound;
        await context.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 404,
            Title = "Resource not found.",
            Detail = ex.Message,      // safe — we authored this exception type
            Instance = context.Request.Path,
            Extensions = { ["traceId"] = Activity.Current?.Id }
        }, ct);

        return true;
    }
}

4 (medium): An error response leaked "Login failed for user 'app_prod'". Fix it while keeping the failure diagnosable.
Solution 
// CAUSE: ex.Message was returned for an unanticipated exception. A
// SqlException message contains the login name and often the server.

public sealed class UnhandledExceptionHandler(ILogger<UnhandledExceptionHandler> log)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context, Exception exception, CancellationToken ct)
    {
        var traceId = Activity.Current?.Id ?? context.TraceIdentifier;

        // EVERYTHING goes to the log, keyed by traceId.
        log.LogError(exception,
            "Unhandled {Type} at {Path} for user {UserId} trace {TraceId}",
            exception.GetType().Name,
            context.Request.Path,
            context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value,
            traceId);

        context.Response.StatusCode = 500;
        await context.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 500,
            Title = "An unexpected error occurred.",   // CONSTANT — no ex data
            // No Detail at all: for an exception we did not anticipate, we
            // cannot know what its message contains.
            Instance = context.Request.Path,
            Extensions = { ["traceId"] = traceId }     // the ONLY link out
        }, ct);

        return true;
    }
}

5 (hard): Your service calls a payment API. Design the exception translation, including the case where the upstream rejects your credentials.
Solution 
public sealed class PaymentClient(HttpClient http, ILogger<PaymentClient> log)
{
    public async Task<PaymentResult> ChargeAsync(ChargeRequest req, CancellationToken ct)
    {
        HttpResponseMessage response;
        try
        {
            response = await http.PostAsJsonAsync("/v1/charges", req, ct);
        }
        catch (TaskCanceledException ex) when (!ct.IsCancellationRequested)
        {
            // OUR token was not signalled → this is a TIMEOUT, not the client
            // hanging up. Without the `when`, the two are indistinguishable.
            throw new UpstreamTimeoutException("Payment provider timed out.", ex);
        }
        catch (HttpRequestException ex)
        {
            throw new UpstreamUnavailableException("Payment provider unreachable.", ex);
        }

        return response.StatusCode switch
        {
            HttpStatusCode.OK =>
                (await response.Content.ReadFromJsonAsync<PaymentResult>(ct))!,

            // Their 402 is a real, caller-actionable outcome — pass its meaning
            // through as a domain result, not as an exception.
            HttpStatusCode.PaymentRequired =>
                throw new PaymentDeclinedException("The card was declined."),

            // THE INTERESTING CASE: their 401/403 means OUR api key is bad.
            // That is OUR misconfiguration and has nothing to do with our
            // caller. Passing 401 through would tell them to re-authenticate
            // for a problem they cannot fix and did not cause.
            HttpStatusCode.Unauthorized or HttpStatusCode.Forbidden =>
                throw new UpstreamAuthException("Payment credentials rejected."),

            // Their 429 means WE are throttled, not our caller.
            HttpStatusCode.TooManyRequests =>
                throw new UpstreamThrottledException("Payment provider throttled us."),

            _ => throw new UpstreamException($"Payment provider returned {(int)response.StatusCode}.")
        };
    }
}

// MAPPING TO CLIENT-FACING CODES:
//   PaymentDeclinedException    → 402 (or 409) — the caller CAN act on this
//   UpstreamTimeoutException    → 504 — retryable
//   UpstreamUnavailableException→ 503 — retryable, with Retry-After
//   UpstreamThrottledException  → 503 — retryable; do NOT surface 429
//   UpstreamAuthException       → 500 — our fault, alert on it immediately
//
// The auth case deserves a HIGH-SEVERITY alert rather than a quiet 500: an
// expired API key breaks every payment, and it is invisible in the client
// error rate because it looks like a generic server error.
//
// IDEMPOTENCY NOTE: if the client retries after a 504, the charge may have
// SUCCEEDED upstream before the timeout. Every charge must carry an
// idempotency key so the retry is recognised rather than double-charging —
// timeout translation without idempotency turns a slow response into
// duplicate payments.
6 (hard): Write contract tests proving every failure class returns problem details with no internal disclosure.
Solution 
public class ErrorContractTests(WebApplicationFactory<Program> factory)
    : IClassFixture<WebApplicationFactory<Program>>
{
    // Force a failure in EACH layer — they take different paths through the
    // pipeline and a handler can cover one while missing another.
    [Theory]
    [InlineData("/test/throw-unhandled",  500)]  // action-scope exception
    [InlineData("/test/throw-domain",     409)]  // typed domain exception
    [InlineData("/test/not-found",        404)]  // handler-returned
    [InlineData("/does-not-exist",        404)]  // routing, no endpoint
    [InlineData("/test/bad-model",        400)]  // model binding failure
    public async Task Every_failure_returns_problem_details(string path, int expected)
    {
        var client = factory.CreateClient();
        var response = await client.GetAsync(path);

        Assert.Equal(expected, (int)response.StatusCode);
        Assert.Equal("application/problem+json",
            response.Content.Headers.ContentType?.MediaType);

        var problem = await response.Content.ReadFromJsonAsync<JsonElement>();
        Assert.True(problem.TryGetProperty("title", out _));
        Assert.True(problem.TryGetProperty("status", out _));
        Assert.True(problem.TryGetProperty("traceId", out var trace));
        Assert.False(string.IsNullOrWhiteSpace(trace.GetString()));
    }

    [Fact]
    public async Task Unhandled_errors_disclose_nothing_internal()
    {
        var client = factory.CreateClient();
        var response = await client.GetAsync("/test/throw-unhandled");
        var body = await response.Content.ReadAsStringAsync();

        // The forced exception's message is a known sentinel the test endpoint
        // throws; asserting its ABSENCE proves ex.Message is not returned.
        Assert.DoesNotContain("SENTINEL_SECRET", body);
        Assert.DoesNotContain("at System.", body);        // no stack frames
        Assert.DoesNotContain("Exception", body);         // no type names
        Assert.DoesNotContain("\\", body);                // no file paths
    }

    [Fact]
    public async Task Developer_exception_page_is_not_reachable()
    {
        // The factory defaults to the Development environment, so pin it —
        // otherwise this test passes for the wrong reason.
        var prod = factory.WithWebHostBuilder(b => b.UseEnvironment("Production"));
        var response = await prod.CreateClient().GetAsync("/test/throw-unhandled");
        var body = await response.Content.ReadAsStringAsync();

        Assert.DoesNotContain("<html", body, StringComparison.OrdinalIgnoreCase);
    }
}

// WHY THESE TESTS EARN THEIR PLACE: this class of regression is invisible in
// normal development. Nobody reads production error bodies until an incident,
// and by then the disclosure has been live for months. Asserting the ABSENCE
// of internals is the only way to keep it from drifting back — and the
// per-layer theory matters because a handler that covers action exceptions
// can silently miss model-binding or routing failures.

🎯 Key Takeaways

  • One error contract for every failure: RFC 9457 problem details, applied to MVC, minimal APIs, middleware and bare status codes alike.
  • The exception handler must be registered first — anything above it escapes as a raw HTML page.
  • IExceptionHandler forms a chain where registration order is execution order; the catch-all goes last or it claims everything.
  • 401 means unauthenticated, 403 means authenticated and not permitted — confusing them sends clients into re-login loops.
  • Prefer 404 over 403 when a 403 would confirm a resource exists, and log the real reason server-side.
  • State conflicts are 409, not 400: the request was well-formed and simply arrived against the wrong state.
  • Distinguish 500 from 502/503/504 — it is what tells a client whether retrying is worth anything.
  • Only return messages from exception types you authored for display; an unanticipated ex.Message leaks credentials and paths.
  • Put everything in the log keyed by traceId and nothing but the traceId in the response — diagnosable without disclosure.
  • Translate upstream failures deliberately at each boundary: their 401 is your 500, and their 429 throttles you, not your caller.
