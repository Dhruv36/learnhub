Dependency Injection The Pipeline

What you'll master: the three lifetimes and the bugs each wrong choice produces, captive dependencies and why the container can catch them for you, scope management in background work where there is no request, disposal rules that decide whether your app leaks, and the registration patterns that keep a large Program.cs readable. Prerequisites: How ASP.NET Core Runs — the configure/run split and the frozen container.

Part 1 — The Three Lifetimes

builder.Services.AddSingleton<IClock, SystemClock>();     // one, forever
builder.Services.AddScoped<IOrderService, OrderService>(); // one per request
builder.Services.AddTransient<IEmailBuilder, EmailBuilder>(); // one per resolve

// SINGLETON — created once, on first resolution, and reused for the process
// lifetime. Shared across every concurrent request, so it MUST be thread-safe.
//   Right for: caches, clocks, HttpClientFactory, configuration snapshots,
//   anything expensive to build with no per-request state.
//   Wrong for: anything holding a DbContext, a user identity, or mutable
//   per-request data.

// SCOPED — one instance per scope. In a web app the framework creates a scope
// per HTTP request and disposes it when the response completes.
//   Right for: DbContext, unit-of-work, per-request caches, anything carrying
//   the current user or tenant.
//   This is the correct DEFAULT for application services. Reach for it unless
//   you have a reason not to.

// TRANSIENT — a new instance every single time it is resolved, including
// multiple times within one request if several classes depend on it.
//   Right for: cheap, stateless helpers.
//   Wrong for: anything expensive, and anything you expect to be shared —
//   two classes depending on the same transient get DIFFERENT objects, which
//   surprises people using it to share state.

// THE ONE THAT CATCHES EVERYONE — a transient resolved five times in a request
// is five allocations. If it holds a connection or a large buffer, that is a
// real cost hiding behind a one-word registration.

// Registration overloads worth knowing:
services.AddSingleton<IClock>(new SystemClock());            // pre-built instance
services.AddSingleton<IClock>(sp => new SystemClock());      // factory, lazy
services.AddScoped<IRepo, SqlRepo>();                        // by type
services.TryAddScoped<IRepo, SqlRepo>();                     // skip if present
services.TryAddEnumerable(
    ServiceDescriptor.Scoped<IValidator, EmailValidator>());  // dedupe by impl

// Multiple implementations of one interface are legal and resolve as a set:
services.AddScoped<INotifier, EmailNotifier>();
services.AddScoped<INotifier, SmsNotifier>();
public class Sender(IEnumerable<INotifier> notifiers) { }   // gets BOTH
// Resolving INotifier alone returns the LAST registered — which is a silent
// behaviour change when someone adds a registration. Prefer IEnumerable when
// several are expected, or keyed services when you need to pick one.

// Keyed services — pick a specific implementation by key:
services.AddKeyedScoped<INotifier, EmailNotifier>("email");
services.AddKeyedScoped<INotifier, SmsNotifier>("sms");
public class Sender([FromKeyedServices("email")] INotifier notifier) { }

Part 2 — Captive Dependencies

// A captive dependency is a LONGER-lived service holding a SHORTER-lived one.
// The shorter one is then kept alive past its intended lifetime — captured.

public sealed class CacheWarmer            // registered as SINGLETON
{
    private readonly AppDbContext _db;     // ← SCOPED. This is the bug.

    public CacheWarmer(AppDbContext db) => _db = db;
}
builder.Services.AddSingleton<CacheWarmer>();

// WHAT ACTUALLY HAPPENS: the singleton is built once, during the first request
// that resolves it, and captures THAT request's DbContext. When the request
// ends, the scope disposes the context — but the singleton still holds the
// reference. From then on:
//   • ObjectDisposedException on the next use, OR
//   • worse, if it is not disposed, ONE non-thread-safe DbContext is now
//     shared across every concurrent request. EF Core will throw
//     "A second operation was started on this context" intermittently, under
//     load, in production, and not in your tests.

// THE LIFETIME RULE, in one line: a service may depend on its OWN lifetime or
// a LONGER one, never a shorter one.
//   singleton → singleton ✓        singleton → scoped ✗
//   scoped    → singleton ✓        scoped    → transient ✓ (but see below)
//   transient → anything ✓

// THE FIX — create a scope per unit of work:
public sealed class CacheWarmer(IServiceScopeFactory scopeFactory)
{
    public async Task WarmAsync(CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope();       // ← own scope
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Products.LoadAsync(ct);
    }   // scope disposes here, and the context with it
}

// OR, for DbContext specifically, the purpose-built factory:
builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseNpgsql(conn));

public sealed class CacheWarmer(IDbContextFactory<AppDbContext> factory)
{
    public async Task WarmAsync(CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        await db.Products.LoadAsync(ct);
    }
}

// MAKE THE CONTAINER CATCH IT FOR YOU — this is the important part:
builder.Host.UseDefaultServiceProvider((context, options) =>
{
    options.ValidateScopes = true;     // throw on captive dependencies
    options.ValidateOnBuild = true;    // check the WHOLE graph at startup
});
// Both default to true in Development ONLY. Enabling them in every
// environment turns a subtle production race into a failed deploy — and the
// production-only default is exactly why these bugs reach production.
Key insight: ValidateScopes and ValidateOnBuild being Development-only by default is a trap worth understanding rather than just working around. The reasoning is performance: validating the full graph costs startup time. But a captive dependency is precisely the kind of bug that behaves fine in single-user development and fails under concurrency, so the default disables the check in the only environment where the bug manifests. Turn both on everywhere. The startup cost is milliseconds; the alternative is an intermittent ObjectDisposedException that reproduces only under load.

Part 3 — Scopes Where There Is No Request

// A scope is created per HTTP request automatically. Background work has no
// request, so nothing creates one for you — and a BackgroundService is a
// SINGLETON, so it cannot inject scoped services at all.

// ✗ WRONG — will not even start with scope validation on:
public sealed class OrderProcessor(AppDbContext db) : BackgroundService { }

// ✓ RIGHT — a scope per unit of work, INSIDE the loop:
public sealed class OrderProcessor(
    IServiceScopeFactory scopeFactory,
    ILogger<OrderProcessor> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // The scope is created and disposed PER ITERATION. Hoisting it
            // outside the loop rebuilds the captive-dependency bug: one
            // DbContext accumulating tracked entities for the process
            // lifetime, growing until the app is restarted.
            using (var scope = scopeFactory.CreateScope())
            {
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                try
                {
                    await ProcessBatchAsync(db, ct);
                }
                catch (Exception ex) when (ex is not OperationCanceledException)
                {
                    // An unhandled exception in ExecuteAsync silently STOPS the
                    // service — the host keeps running and the work just stops
                    // happening. Catch inside the loop so one bad batch does not
                    // kill the worker permanently.
                    logger.LogError(ex, "Batch failed; continuing.");
                }
            }

            await Task.Delay(TimeSpan.FromSeconds(30), ct);
        }
    }
}

// The same applies anywhere outside a request: startup tasks, IHostedService,
// message-queue consumers, timer callbacks. If there is no HTTP request, there
// is no ambient scope, and you must create one.

// A SUBTLE VARIANT — capturing IServiceProvider itself:
public sealed class Bad(IServiceProvider sp)
{
    // sp here is the ROOT provider when Bad is a singleton. Resolving a scoped
    // service from the root provider succeeds and creates an instance that
    // lives until the APPLICATION shuts down — a permanent leak, one per call,
    // with no error to tell you.
    public void Work() => sp.GetRequiredService<AppDbContext>();   // ✗
}
// Injecting IServiceProvider is service-location, not injection. It hides
// dependencies from the constructor signature and defeats ValidateOnBuild,
// which can only check what it can see. Use IServiceScopeFactory when you
// genuinely need dynamic resolution — it makes the scoping explicit.

Part 4 — Disposal: Who Cleans Up What

// The container disposes what it CREATED, when the owning scope ends.
//
//   transient/scoped registered by TYPE   → disposed with the scope
//   singleton registered by TYPE          → disposed at app shutdown
//   registered with a FACTORY (sp => ...)  → disposed by the container
//   registered as a pre-built INSTANCE    → NOT disposed. You own it.

services.AddSingleton<IExpensive>(new Expensive());        // ✗ never disposed
services.AddSingleton<IExpensive>(sp => new Expensive());  // ✓ container disposes

// THE TRANSIENT-DISPOSABLE TRAP, the leak that surprises people most:
services.AddTransient<IDisposableThing, DisposableThing>();
// Every resolution creates an instance the container must track so it can
// dispose it — and it tracks them ON THE SCOPE. In a long-lived scope, or
// worse from the ROOT provider (a singleton's dependency), those instances
// accumulate for the lifetime of that scope. A transient IDisposable resolved
// from the root provider is a memory leak that grows until restart.
//
// Symptoms: memory climbing steadily with no obvious retention, and a heap
// dump full of objects you thought were short-lived.
//
// Fixes, in order of preference:
//   1. do not make transients disposable — usually a design smell
//   2. register it scoped, so the request scope bounds the accumulation
//   3. resolve it from an explicit scope you control and dispose

// IAsyncDisposable is honoured, but ONLY if the scope is disposed
// asynchronously. Disposing an async-disposable scope synchronously throws:
await using var scope = scopeFactory.CreateAsyncScope();   // ✓ async scope
// using var scope = scopeFactory.CreateScope();           // ✗ throws if the
//                                                         //   service is
//                                                         //   IAsyncDisposable

// Ownership of things you did NOT create is yours:
services.AddSingleton<IConnection>(sp =>
{
    var factory = new ConnectionFactory { Uri = new Uri(conn) };
    return factory.CreateConnection();     // container disposes this ✓
});

Part 5 — HttpClient, the Special Case

// HttpClient breaks the normal lifetime intuition in both directions, which is
// why it has a dedicated factory.

// ✗ SOCKET EXHAUSTION — a new client per request:
using var client = new HttpClient();       // disposed connections sit in
await client.GetAsync(url);                // TIME_WAIT for ~240 seconds

// ✗ STALE DNS — one client forever:
static readonly HttpClient Shared = new();  // never observes a DNS change,
                                            // so a failover is not picked up

// ✓ IHttpClientFactory solves BOTH: it pools handlers and rotates them on a
// timer (default 2 minutes), so sockets are reused AND DNS is re-resolved.
builder.Services.AddHttpClient<ApiClient>((sp, http) =>
{
    var o = sp.GetRequiredService<IOptions<ApiOptions>>().Value;
    http.BaseAddress = new Uri(o.BaseUrl);
    http.Timeout = TimeSpan.FromSeconds(o.TimeoutSeconds);
})
.AddStandardResilienceHandler();     // retries, circuit breaker, timeout

// The TYPED CLIENT is registered as TRANSIENT, and that is deliberate: the
// client itself is cheap, while the expensive HANDLER underneath is pooled and
// shared by the factory. So the usual "transient is wasteful" instinct does
// not apply here.
public sealed class ApiClient(HttpClient http)
{
    public async Task<Product?> GetAsync(int id, CancellationToken ct)
        => await http.GetFromJsonAsync<Product>($"/products/{id}", ct);
}

// A TYPED CLIENT MUST NOT BE INJECTED INTO A SINGLETON. Doing so captures one
// HttpClient — and therefore one handler — forever, defeating the rotation
// that solves the DNS problem. Inject IHttpClientFactory into the singleton
// instead and create the client per call.

Part 6 — Registration That Scales

// A 400-line Program.cs of AddScoped calls is unreviewable. Group by feature,
// one extension method each, in a file near the code it registers.

public static class PersistenceExtensions
{
    public static IServiceCollection AddPersistence(
        this IServiceCollection services, IConfiguration config)
    {
        services.AddDbContext<AppDbContext>(o =>
            o.UseNpgsql(config.GetConnectionString("Default")));

        services.AddScoped<IOrderRepository, OrderRepository>();
        services.AddScoped<IUnitOfWork, UnitOfWork>();

        return services;      // fluent, so calls chain
    }
}

// Program.cs stays a table of contents:
builder.Services
    .AddPersistence(builder.Configuration)
    .AddApplicationServices()
    .AddObservability()
    .AddAuthN(builder.Configuration);

// DECORATORS — cross-cutting behaviour without touching the implementation:
services.AddScoped<IOrderService, OrderService>();
services.Decorate<IOrderService, CachedOrderService>();   // Scrutor package
// Hand-rolled, if you would rather not take the dependency:
services.AddScoped<OrderService>();
services.AddScoped<IOrderService>(sp => new CachedOrderService(
    sp.GetRequiredService<OrderService>(),
    sp.GetRequiredService<IMemoryCache>()));

// WHAT NOT TO DO — the service locator anti-pattern:
public sealed class Bad(IServiceProvider sp)
{
    public void Work()
    {
        var repo = sp.GetRequiredService<IOrderRepository>();   // ✗
    }
}
// Three concrete costs, not stylistic objections:
//   1. the constructor no longer declares what the class needs, so a reader
//      must scan the whole body to learn its dependencies
//   2. ValidateOnBuild cannot verify a dependency it cannot see, so a missing
//      registration becomes a runtime failure instead of a startup one
//   3. tests must build a container rather than pass fakes to a constructor
//
// The legitimate exceptions are narrow: IServiceScopeFactory in background
// work, and genuinely dynamic resolution driven by runtime data (a handler
// chosen by message type). Both should be explicit and rare.

// ASSEMBLY SCANNING — convenient, and worth a caution:
services.Scan(scan => scan.FromAssemblyOf<IOrderService>()
    .AddClasses(c => c.AssignableTo(typeof(IHandler<>)))
    .AsImplementedInterfaces()
    .WithScopedLifetime());
// It removes boilerplate but makes registration implicit: a class is now
// registered because of where it lives and what it implements. Renaming or
// moving it can silently unregister it. Use it for genuinely uniform families
// (handlers, validators), not for the whole application.

Interview Questions

Beginner: What are the three service lifetimes and when do you use each?

Singleton is created once and shared for the application's lifetime, so it must be thread-safe — right for caches, clocks and anything expensive to construct with no per-request state. Scoped creates one instance per scope, which in a web application means per HTTP request, and it is the correct default for application services and essential for DbContext, which is not thread-safe. Transient creates a new instance on every resolution, suiting cheap stateless helpers; the thing to watch is that two classes depending on the same transient receive different objects, so it cannot be used to share state within a request.

Beginner: Why is new HttpClient() per request a problem?

Because disposing an HttpClient does not immediately release its underlying TCP connection — the socket sits in TIME_WAIT for a couple of minutes. Under load the application exhausts available ports and new connections start failing with what looks like a network fault. The naive fix, a single static client reused forever, trades that for a different bug: the handler caches DNS resolution indefinitely, so a failover or IP change is never observed. IHttpClientFactory solves both by pooling handlers and rotating them on a timer, which reuses sockets while still re-resolving DNS periodically.

Mid: What is a captive dependency and how do you prevent it systematically?

A captive dependency is a longer-lived service holding a reference to a shorter-lived one — classically a singleton injecting a scoped DbContext. The singleton captures the first request's instance and keeps it after that request's scope disposes, producing either an ObjectDisposedException or, more dangerously, one non-thread-safe context shared across concurrent requests, which fails intermittently under load. The rule is that a service may depend on its own lifetime or a longer one, never a shorter one. Systematically, the prevention is to enable ValidateScopes and ValidateOnBuild in every environment rather than accepting the Development-only default, because that turns the whole class of bug into a startup failure caught by the deployment pipeline. Where a singleton genuinely needs scoped work, it should take IServiceScopeFactory and create a scope per unit of work.

Mid: Why is injecting IServiceProvider generally a bad idea?

It is service location rather than dependency injection, and it costs three concrete things. The constructor stops declaring what the class actually needs, so a reader has to scan the entire implementation to find out. ValidateOnBuild can only verify dependencies it can see in constructor signatures, so a missing registration that would have failed at startup becomes a runtime exception on some particular code path instead. And tests have to construct a container and populate it rather than simply passing fakes to a constructor. There is an additional hazard specific to singletons: the provider they receive is the root provider, so resolving a scoped service from it succeeds and produces an instance that lives until application shutdown — a silent leak. The legitimate uses are narrow, essentially IServiceScopeFactory for background work and genuinely dynamic resolution driven by runtime data.

Senior: A background service throws ObjectDisposedException on its DbContext after running fine for a while. Diagnose.

The service is a singleton that either injected the context directly or created a single scope outside its processing loop, so one DbContext is being reused across iterations. The delay before failure is the diagnostic signal: the context works until something disposes it or until its connection is invalidated, so the failure looks time-dependent rather than structural. There are usually two overlapping problems. The first is lifetime — the fix is a scope created and disposed inside the loop, per unit of work, so each iteration gets a fresh context; if the service is a singleton by nature, that means IServiceScopeFactory rather than constructor injection. The second, which the first fix also addresses, is that a long-lived context accumulates tracked entities indefinitely, so memory grows and change tracking gets progressively slower even before anything throws. I would also check whether the service swallows exceptions, because an unhandled exception inside ExecuteAsync stops the background service silently while the host keeps running — so the symptom becomes "the worker stopped doing anything" with no crash and no obvious log. The durable configuration change is enabling ValidateScopes in all environments, which would have made this a startup failure rather than a runtime one.

Senior: How would you structure DI registration for a large application, and where do you draw the line on abstraction?

I would group registrations into feature-oriented extension methods — AddPersistence, AddApplicationServices, AddObservability — each living in a file beside the code it registers, so Program.cs stays a readable table of contents and adding a feature touches one place. Scoped is the default lifetime for application services, with singleton reserved for genuinely shared, thread-safe, expensive things, and transient for cheap stateless helpers. I would enable ValidateScopes and ValidateOnBuild in every environment, because the cost is milliseconds of startup and the benefit is that an entire class of concurrency bug becomes a failed deploy. On abstraction, my line is whether the interface earns its keep by having a real second implementation, a genuine test seam, or an external dependency worth isolating: a repository interface over a third-party client is usually worth it, whereas an IOrderService with exactly one implementation that exists only because "we always add an interface" is indirection with no payoff — it makes navigation worse and tests no better, since the concrete class was already injectable. I would also be cautious with assembly scanning: it removes boilerplate for uniform families like handlers and validators, but it makes registration implicit, so moving or renaming a class can silently unregister it and produce a runtime failure with no obvious cause. Explicit registration for anything structurally important, scanning only for genuinely repetitive families. Finally I would treat the container as composition only — no business logic in factories, no resolution inside domain code — so the application remains testable by constructing objects directly, which is what keeps a large codebase's tests fast.

1 (easy): Register a thread-safe IClock, a per-request IOrderService, and a cheap stateless IEmailBuilder with the correct lifetimes.
Solution 
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddTransient<IEmailBuilder, EmailBuilder>();

// IClock is singleton: no state, thread-safe, and creating one per request
// would be pure waste.
// IOrderService is scoped: it almost certainly depends on a DbContext, and
// scoped is the right default for application services regardless.
// IEmailBuilder is transient: cheap and stateless, so a fresh instance per
// resolution costs nothing and avoids any accidental state sharing.
2 (easy): Explain why this throws, and fix it: a singleton ReportGenerator whose constructor takes AppDbContext.
Solution 
// WHY: AppDbContext is registered SCOPED. A singleton is constructed once and
// captures that first instance permanently — a captive dependency. With scope
// validation on, the container refuses at startup:
//   "Cannot consume scoped service 'AppDbContext' from singleton
//    'ReportGenerator'."
// Without validation it starts fine and fails later, which is worse.

public sealed class ReportGenerator(IServiceScopeFactory scopeFactory)
{
    public async Task<Report> GenerateAsync(CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        return await BuildAsync(db, ct);
    }   // the scope — and the context — dispose here
}

// Alternative, and cleaner when the dependency is specifically a DbContext:
builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseNpgsql(conn));

public sealed class ReportGenerator(IDbContextFactory<AppDbContext> factory)
{
    public async Task<Report> GenerateAsync(CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        return await BuildAsync(db, ct);
    }
}
3 (medium): Write a BackgroundService that processes a queue every 30 seconds using a scoped repository, surviving individual failures.
Solution 
public sealed class QueueProcessor(
    IServiceScopeFactory scopeFactory,
    ILogger<QueueProcessor> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // SCOPE INSIDE THE LOOP — one per unit of work. Outside the loop
            // it becomes a process-lifetime context accumulating tracked
            // entities until restart.
            using (var scope = scopeFactory.CreateScope())
            {
                try
                {
                    var repo = scope.ServiceProvider
                        .GetRequiredService<IQueueRepository>();
                    await repo.ProcessPendingAsync(ct);
                }
                catch (Exception ex) when (ex is not OperationCanceledException)
                {
                    // WITHOUT THIS the service dies permanently on the first
                    // failure: an unhandled exception in ExecuteAsync stops the
                    // BackgroundService while the host keeps running, so the
                    // work silently stops with no crash to alert on.
                    logger.LogError(ex, "Queue batch failed; continuing.");
                }
            }

            try
            {
                await Task.Delay(TimeSpan.FromSeconds(30), ct);
            }
            catch (OperationCanceledException)
            {
                break;   // shutdown requested — exit cleanly, do not log
            }
        }
    }
}

// Note OperationCanceledException is deliberately excluded from the catch:
// it signals shutdown, not failure, and logging it as an error makes every
// deploy look like an incident.
4 (medium): Register two INotifier implementations so one class receives both and another selects only SMS.
Solution 
// BOTH — register normally and inject the collection:
builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<INotifier, SmsNotifier>();

public sealed class Broadcaster(IEnumerable<INotifier> notifiers)
{
    public async Task NotifyAllAsync(string message, CancellationToken ct)
    {
        foreach (var n in notifiers)
            await n.SendAsync(message, ct);
    }
}

// ONE SPECIFIC — keyed services:
builder.Services.AddKeyedScoped<INotifier, EmailNotifier>("email");
builder.Services.AddKeyedScoped<INotifier, SmsNotifier>("sms");

public sealed class UrgentAlerter([FromKeyedServices("sms")] INotifier sms)
{
    public Task AlertAsync(string message, CancellationToken ct)
        => sms.SendAsync(message, ct);
}

// WHY NOT just resolve INotifier and rely on ordering: a plain resolution
// returns the LAST registered implementation. That is invisible in the
// consuming code and changes silently the day someone adds a third notifier
// or reorders registrations — a behaviour change with no code change at the
// call site. Keys make the intent explicit and stable.
5 (hard): Memory grows steadily in production with no obvious retention. The heap holds thousands of DisposableThing instances. Diagnose and fix.
Solution 
// THE CAUSE — a transient IDisposable resolved from a long-lived provider:
services.AddTransient<IDisposableThing, DisposableThing>();

public sealed class Cache(IServiceProvider sp)      // SINGLETON
{
    public void Refresh() => sp.GetRequiredService<IDisposableThing>();
}

// The container must dispose what it creates, so it TRACKS every disposable
// instance on the owning scope. Here the owner is the ROOT provider, whose
// scope ends at application shutdown — so every instance ever created is
// retained until the process restarts. Nothing throws; memory just climbs.
//
// The tell in a heap dump is the retention path: instances held by
// ServiceProviderEngineScope rather than by application code.

// FIX 1 (best) — do not make transients disposable. A disposable type usually
// owns a resource, which is a signal it should be scoped or singleton.

// FIX 2 — register it scoped, so the request scope bounds accumulation:
services.AddScoped<IDisposableThing, DisposableThing>();

// FIX 3 — if it must be transient, own the scope explicitly:
public sealed class Cache(IServiceScopeFactory scopeFactory)
{
    public void Refresh()
    {
        using var scope = scopeFactory.CreateScope();
        var thing = scope.ServiceProvider.GetRequiredService<IDisposableThing>();
        thing.Use();
    }   // scope disposal releases the instance
}

// PREVENTION: injecting IServiceProvider into the singleton is what allowed
// this. Constructor injection would have made the dependency visible, and
// ValidateOnBuild would have had something to check. Service location hides
// exactly the relationships this bug lives in.
6 (hard): A service calls a third-party API. Design its registration for correct connection reuse, resilience, testability, and use from a singleton.
Solution 
// 1. TYPED CLIENT — connection pooling and DNS rotation handled by the factory.
builder.Services.AddHttpClient<IPaymentGateway, StripeGateway>((sp, http) =>
{
    var o = sp.GetRequiredService<IOptions<PaymentOptions>>().Value;
    http.BaseAddress = new Uri(o.BaseUrl);
    http.Timeout = TimeSpan.FromSeconds(o.TimeoutSeconds);
})
// 2. RESILIENCE — retry, circuit breaker and per-attempt timeout.
.AddStandardResilienceHandler(o =>
{
    o.Retry.MaxRetryAttempts = 3;
    o.Retry.UseJitter = true;          // avoid synchronised retry storms
    o.CircuitBreaker.FailureRatio = 0.5;
});

// 3. THE INTERFACE IS THE TEST SEAM — tests substitute a fake gateway with no
//    HTTP involved. This interface earns its keep: a real second
//    implementation (a sandbox gateway) and an external dependency worth
//    isolating.
public sealed class StripeGateway(HttpClient http, ILogger<StripeGateway> log)
    : IPaymentGateway
{
    public async Task<PaymentResult> ChargeAsync(
        ChargeRequest request, CancellationToken ct)
    {
        var response = await http.PostAsJsonAsync("/v1/charges", request, ct);
        // ...
    }
}

// 4. USE FROM A SINGLETON — the part that is easy to get wrong.
//    Injecting IPaymentGateway (transient, holding an HttpClient) into a
//    singleton captures one handler forever and defeats the rotation that
//    solves stale DNS. Take the factory instead:
public sealed class ReconciliationWorker(
    IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopeFactory.CreateScope();
            var gateway = scope.ServiceProvider
                .GetRequiredService<IPaymentGateway>();
            await gateway.ReconcileAsync(ct);

            await Task.Delay(TimeSpan.FromMinutes(5), ct);
        }
    }
}

// WHY A SCOPE RATHER THAN IHttpClientFactory DIRECTLY: the worker wants the
// GATEWAY abstraction, not an HttpClient. Resolving it from a per-iteration
// scope gets a correctly-constructed gateway with a pooled handler, and keeps
// the worker testable against the interface.
//
// TRADE-OFF TO STATE: the standard resilience handler retries, so the API call
// must be idempotent or retries will double-charge. A payment gateway is
// exactly where that matters — the request needs an idempotency key so a retry
// after a timeout is recognised as the same charge, not a second one.

🎯 Key Takeaways

  • Singleton is process-wide and must be thread-safe; scoped is per request and the right default; transient is per resolution and cannot be used to share state.
  • A service may depend on its own lifetime or a longer one, never a shorter one — violating that is a captive dependency.
  • Enable ValidateScopes and ValidateOnBuild in every environment; the Development-only default disables the check precisely where the bug cannot reproduce.
  • Background work has no ambient scope: create one with IServiceScopeFactory, inside the loop, per unit of work.
  • An unhandled exception in ExecuteAsync stops a BackgroundService silently while the host keeps running — catch inside the loop.
  • The container disposes what it created; a pre-built instance passed to AddSingleton is never disposed.
  • Transient IDisposable resolved from the root provider accumulates until shutdown — a leak with no error.
  • Use IHttpClientFactory: raw clients cause socket exhaustion, and a static client caches DNS forever.
  • Never inject a typed HttpClient into a singleton — it pins one handler and defeats rotation.
  • Injecting IServiceProvider hides dependencies, blinds ValidateOnBuild, and complicates tests; reserve it for genuinely dynamic resolution.
