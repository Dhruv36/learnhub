Minimal APIs Foundations

What you'll master: the endpoint model that replaced controllers as the default for new ASP.NET Core services — how a lambda becomes an HTTP handler, how parameters are resolved without attributes, what Results and TypedResults actually return, how to organise hundreds of endpoints without a 2000-line Program.cs, and the honest list of what minimal APIs still cannot do. Prerequisites: How ASP.NET Core Runs — the host, two-phase startup, and the pipeline.

Part 1 — A Lambda Is an Endpoint

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// The whole model in one line: an HTTP method, a route template, and a delegate.
app.MapGet("/products/{id:int}", (int id) => $"product {id}");

app.Run();

// What MapGet actually does: it registers an ENDPOINT — a route pattern plus a
// RequestDelegate plus metadata — into the endpoint data source. UseRouting
// matches the incoming request against those patterns; UseEndpoints (added
// implicitly) executes the match. Minimal APIs are not a separate framework
// bolted on; they produce the same endpoint objects controllers produce, which
// is why filters, authorization, CORS and OpenAPI all work identically on both.

// The delegate can be anything invocable, which matters for testability:
app.MapGet("/a", () => "inline lambda");
app.MapGet("/b", Handlers.GetB);                    // static method group
app.MapGet("/c", (ProductService s) => s.All());    // injected dependency

// Every HTTP verb has a Map method, plus two escape hatches:
app.MapPost("/products", (Product p) => Results.Created($"/products/{p.Id}", p));
app.MapPut("/products/{id:int}", (int id, Product p) => Results.NoContent());
app.MapDelete("/products/{id:int}", (int id) => Results.NoContent());
app.MapMethods("/products/{id:int}", ["PATCH"], (int id) => Results.NoContent());
app.Map("/any", () => "responds to every verb");    // rarely what you want

// MapGet also matches HEAD automatically — the framework runs the handler and
// discards the body, so a HEAD request costs the same as the GET. If a handler
// is expensive, that is worth knowing before someone health-checks it with HEAD.

Part 2 — Parameter Binding Without Attributes

// Controllers need [FromRoute], [FromQuery], [FromBody]. Minimal APIs infer
// the source from the parameter's TYPE and NAME, using fixed rules. Learn the
// rules once and most endpoints need no attributes at all.
//
// The resolution order, first match wins:
//   1. name matches a route template parameter  → route value
//   2. type is a registered DI service          → dependency injection
//   3. type is a "special" type                 → HttpContext, ClaimsPrincipal,
//                                                 CancellationToken, Stream...
//   4. type has TryParse / is a simple type     → query string
//   5. anything else (a complex type)           → JSON request body
//
// Rule 4 vs 5 is the one that surprises people: SIMPLE types come from the
// query string, COMPLEX types come from the body. There is no attribute
// involved and no ambiguity — but it means adding a property to a DTO can
// never accidentally change where it binds, while changing a parameter from
// `string` to a record CAN move it from query to body.

app.MapGet("/search/{category}", (
    string category,             // 1. route — the name matches the template
    ProductService service,      // 2. DI  — registered in the container
    CancellationToken ct,        // 3. special — request abort token
    string? q,                   // 4. query — simple type, ?q=...
    int page = 1) =>             // 4. query with a default → optional
        service.Search(category, q, page, ct));

app.MapPost("/products", (Product product) => ...);   // 5. complex → JSON body

// Override the inference explicitly when the rules do not fit:
app.MapPost("/import", (
    [FromBody] List<Product> items,
    [FromHeader(Name = "X-Request-Id")] string requestId,
    [FromQuery(Name = "dry-run")] bool dryRun = false) => ...);

// A type can OPT IN to query binding by implementing TryParse — this keeps
// primitive obsession out of handlers while staying on rule 4:
public readonly record struct Coordinate(double Lat, double Lon)
{
    public static bool TryParse(string? value, out Coordinate result)
    {
        result = default;
        var parts = value?.Split(',');
        if (parts is not [var a, var b]) return false;
        if (!double.TryParse(a, out var lat) || !double.TryParse(b, out var lon))
            return false;
        result = new Coordinate(lat, lon);
        return true;
    }
}
app.MapGet("/near", (Coordinate at) => ...);          // GET /near?at=51.5,-0.1

// BindAsync takes full control for cases TryParse cannot express — it receives
// the whole HttpContext, so it can read headers, cookies, or several values:
public record PagingOptions(int Page, int Size)
{
    public static ValueTask<PagingOptions?> BindAsync(HttpContext ctx)
    {
        int.TryParse(ctx.Request.Query["page"], out var page);
        int.TryParse(ctx.Request.Query["size"], out var size);
        return ValueTask.FromResult<PagingOptions?>(
            new PagingOptions(Math.Max(page, 1), Math.Clamp(size, 1, 100)));
    }
}
// When both exist, BindAsync wins over TryParse. Clamping in the binder like
// this is a real pattern: it makes an unbounded page size unrepresentable
// rather than relying on every handler to remember to validate it.

Part 3 — AsParameters and the Argument-Count Problem

// Endpoints accumulate parameters until the signature is unreadable:
app.MapGet("/reports", (DateOnly? from, DateOnly? to, string? region,
    int page, int size, string? sort, bool descending,
    ReportService service, CancellationToken ct) => ...);

// [AsParameters] flattens a struct/record into individual bindings, each still
// following the normal inference rules:
public readonly record struct ReportQuery(
    DateOnly? From,
    DateOnly? To,
    string? Region,
    int Page = 1,
    int Size = 20);

app.MapGet("/reports", ([AsParameters] ReportQuery query,
                        ReportService service,
                        CancellationToken ct) =>
    service.Run(query, ct));

// This is not merely cosmetic. The record is now a real type, so it can carry
// validation, be reused across endpoints, and be constructed directly in unit
// tests without going through HTTP at all.

// AsParameters also works with route values, headers and services together —
// each property binds by the same rules the parameters would have used:
public record struct GetProduct(
    int Id,                                      // route
    [FromHeader(Name = "If-None-Match")] string? ETag,
    ProductService Service);                     // DI

app.MapGet("/products/{id:int}", ([AsParameters] GetProduct r) => ...);
Key insight: minimal API binding is a compile-time source-generated concern, not reflection at request time. The framework generates a strongly-typed invoker per endpoint during build, which is why minimal APIs are faster than controllers and why they work under NativeAOT with CreateSlimBuilder. It is also why binding errors surface as build warnings or startup exceptions rather than as mysterious nulls: an unbindable parameter is a failure the framework can see before a request arrives.

Part 4 — Results, TypedResults, and Status Codes

// A handler's return value is converted to a response by these rules:
//   string              → text/plain, 200
//   any other object    → JSON, 200
//   IResult             → whatever that IResult says
//   Task<T>/ValueTask<T> → awaited, then the above applied to T
//   null (as IResult)   → throws; return Results.NoContent() instead

app.MapGet("/plain", () => "hello");              // 200 text/plain
app.MapGet("/json", () => new { ok = true });     // 200 application/json

// Results is the factory for explicit responses:
app.MapGet("/products/{id:int}", async (int id, ProductService svc) =>
{
    var product = await svc.FindAsync(id);
    return product is null
        ? Results.NotFound()
        : Results.Ok(product);
});

// TypedResults is the same set, but STRONGLY TYPED. Prefer it — two reasons:
//   1. the return type documents the contract and feeds OpenAPI automatically
//   2. tests can assert on the type without inspecting an HTTP response
app.MapGet("/products/{id:int}", async Task<Results<Ok<Product>, NotFound>> (
    int id, ProductService svc) =>
{
    var product = await svc.FindAsync(id);
    return product is null
        ? TypedResults.NotFound()
        : TypedResults.Ok(product);
});
// Results<T1, T2> is a discriminated union: the compiler enforces that every
// path returns one of the declared results, so adding a 409 branch without
// declaring it is a build error rather than an undocumented response.

// The results worth knowing by name:
TypedResults.Ok(value);                       // 200 with body
TypedResults.NoContent();                     // 204 — the right answer for PUT/DELETE
TypedResults.Created($"/products/{id}", p);   // 201 + Location header
TypedResults.NotFound();                      // 404
TypedResults.ValidationProblem(errors);       // 400 + RFC 9457 problem details
TypedResults.Problem("Upstream failed", statusCode: 502);
TypedResults.Conflict();                      // 409 — optimistic concurrency
TypedResults.Unauthorized();                  // 401 — who are you?
TypedResults.Forbid();                        // 403 — I know, and no
TypedResults.File(stream, "application/pdf", "invoice.pdf");
TypedResults.Redirect("/new-location", permanent: true);

// 401 vs 403 is asked in interviews and got wrong in code constantly:
// 401 means authentication is missing or invalid — retrying WITH credentials
// could succeed. 403 means the identity is established and still not allowed —
// retrying changes nothing. Returning 401 for a permissions failure sends
// clients into a pointless re-login loop.

Part 5 — Route Groups: Structure at Scale

// Everything above collapses under its own weight if Program.cs holds 200
// endpoints. MapGroup extracts a common prefix AND shared metadata:
var products = app.MapGroup("/api/products")
    .RequireAuthorization()
    .WithTags("Products")
    .AddEndpointFilter<LoggingFilter>();

products.MapGet("/", GetAll);                  // GET  /api/products
products.MapGet("/{id:int}", GetById);         // GET  /api/products/42
products.MapPost("/", Create).RequireAuthorization("admin");

// Conventions applied to a group flow to every endpoint in it, and groups
// nest — so cross-cutting policy is declared once, at the level it applies to,
// instead of being repeated per endpoint where one omission is a security hole.

// The organising pattern that scales: one extension method per feature,
// each in its own file, Program.cs just lists them.
public static class ProductEndpoints
{
    public static RouteGroupBuilder MapProductEndpoints(this IEndpointRouteBuilder routes)
    {
        var group = routes.MapGroup("/api/products").WithTags("Products");

        group.MapGet("/", async (ProductService svc, CancellationToken ct)
            => TypedResults.Ok(await svc.AllAsync(ct)));

        group.MapGet("/{id:int}", async Task<Results<Ok<Product>, NotFound>> (
            int id, ProductService svc, CancellationToken ct)
            => await svc.FindAsync(id, ct) is { } p
                ? TypedResults.Ok(p)
                : TypedResults.NotFound());

        return group;
    }
}

// Program.cs stays a table of contents — the shape of the API at a glance:
app.MapProductEndpoints();
app.MapOrderEndpoints();
app.MapCustomerEndpoints();

Part 6 — Endpoint Filters and the Honest Limitations

// Endpoint filters are the minimal-API answer to action filters: they wrap the
// handler, see the bound arguments, and can short-circuit.
public sealed class ValidationFilter<T> : IEndpointFilter where T : class
{
    private readonly IValidator<T> _validator;
    public ValidationFilter(IValidator<T> validator) => _validator = validator;

    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context, EndpointFilterDelegate next)
    {
        var model = context.Arguments.OfType<T>().FirstOrDefault();
        if (model is not null)
        {
            var result = await _validator.ValidateAsync(model);
            if (!result.IsValid)
                return TypedResults.ValidationProblem(result.ToDictionary());
        }
        return await next(context);      // not calling next() short-circuits
    }
}
products.MapPost("/", Create).AddEndpointFilter<ValidationFilter<Product>>();

// Filters run in registration order on the way in and REVERSE order on the way
// out — the same nesting model as middleware, but scoped to one endpoint and
// with access to typed arguments rather than raw HttpContext.

// WHAT MINIMAL APIS STILL DO NOT DO — the honest list, because choosing them
// for a project that needs these means rewriting later:
//   • no model binding to complex types from FORM POSTS with the full
//     controller semantics (basic form binding exists; the nested-object,
//     collection-index conventions do not)
//   • no built-in [ApiController] automatic 400 on invalid ModelState —
//     validation is yours to wire (a filter, as above, or FluentValidation)
//   • no view rendering — minimal APIs are for APIs; use Razor Pages or MVC
//     for server-rendered HTML
//   • no OnActionExecuting-style inheritance hierarchy — composition via
//     filters and groups replaces base-controller inheritance, which is
//     usually an improvement but IS a migration cost
//
// When to still choose controllers: heavy server-rendered views, an existing
// large MVC codebase, or a team relying on convention-based inheritance.
// For a new JSON API in 2026, minimal APIs are the default.

Interview Questions

Beginner: How does a minimal API decide where a parameter comes from without attributes?

By a fixed resolution order based on the parameter's name and type: a name matching a route template parameter binds from the route; a type registered in DI is injected; special types like HttpContext, ClaimsPrincipal and CancellationToken are supplied by the framework; simple types and types implementing TryParse bind from the query string; and anything else — a complex type — is deserialized from the JSON body. First match wins. Attributes such as [FromQuery] or [FromBody] exist to override the inference when those rules do not fit, but most endpoints need none.

Beginner: What is the difference between Results and TypedResults?

They produce the same HTTP responses, but TypedResults returns concrete types like Ok<Product> or NotFound instead of the general IResult interface. That gives you two things: OpenAPI can infer the documented response shapes and status codes directly from the method signature, and unit tests can assert on the returned type and its value without spinning up an HTTP pipeline or parsing a response body. Combined with a Results<Ok<T>, NotFound> return type, the compiler also enforces that every code path returns a declared result.

Mid: When would you reach for BindAsync over TryParse?

TryParse maps a single string value to a type, so it fits when one query parameter or route segment becomes one object — a coordinate, an ISO date, a strongly-typed ID. BindAsync receives the entire HttpContext, so it is the choice when binding needs more than one input or a source TryParse cannot see: combining several query parameters into a paging object, reading a header alongside a body, or consulting a cookie. It is also the place to normalise and clamp — bounding a page size in the binder makes an unbounded request unrepresentable rather than trusting every handler to re-validate. When a type defines both, BindAsync takes precedence.

Mid: How do endpoint filters differ from middleware, and when does each belong?

Middleware sits in the application pipeline and runs for every request that reaches it, before routing has necessarily selected an endpoint, and it only sees the raw HttpContext. Endpoint filters run after model binding for one specific endpoint or group, and receive the bound, typed arguments through EndpointFilterInvocationContext. So genuinely global concerns that must apply even to unmatched requests — HTTPS redirection, forwarded headers, exception handling, correlation IDs — belong in middleware. Concerns that need the deserialized model or apply to a subset of routes — validating a DTO, checking resource ownership, per-endpoint auditing — belong in filters. Both compose in registration order inbound and reverse order outbound, and both short-circuit by not calling the next delegate.

Senior: A GET endpoint takes a filter object and always receives null. What is wrong and what are the fixes?

The filter object is a complex type, so binding rule five applies: the framework attempts to deserialize it from the request body. A GET has no body, so the parameter binds null — and because nothing threw, it looks like a silent framework failure rather than a binding decision. There are three legitimate fixes and the choice matters. Implementing TryParse on the type moves it to rule four, which suits a single compact value like ?at=51.5,-0.1. Implementing BindAsync suits assembling the object from several query parameters and lets you normalise and clamp centrally. [AsParameters] is usually the best answer for a filter or paging object: each property binds individually by the normal rules, so the query string stays conventional and discoverable, OpenAPI documents each parameter separately, and the type remains directly constructible in tests. What I would avoid is [FromBody] on a GET — it technically binds but sends a body on a GET, which proxies, caches and some HTTP clients are entitled to strip.

Senior: You are choosing between minimal APIs and controllers for a new service. How do you decide, and how do you keep the decision from becoming expensive?

For a new JSON API I default to minimal APIs: lower per-request overhead because binding is source-generated rather than reflective, NativeAOT compatibility with CreateSlimBuilder, and route groups that let authorization and filters be declared once at the level they apply to rather than repeated per action. I would choose controllers when the application renders server-side views, when there is a large existing MVC codebase whose conventions the team relies on, or when the automatic [ApiController] behaviours — implicit 400 on invalid ModelState, inferred binding sources — carry real weight for a large team. The honest gaps to price in are that minimal APIs have no automatic model validation, no view rendering, and no base-controller inheritance hierarchy, so those become explicit wiring. The way to keep the decision cheap either way is to keep handlers thin: if a handler binds, delegates to an application service, and maps the outcome to a result, then the hosting style is a surface concern and switching it later is mechanical. The expensive version is business logic living inside handlers or controllers, because then the choice has been baked into the domain and migration means a rewrite. Note too that both produce the same endpoint objects, so they coexist in one application — an incremental migration is genuinely viable rather than all-or-nothing.

🏋️ Graded Exercises

1 (easy): Map a GET /ping returning {"pong": true} as JSON, and a GET /echo/{text} returning the route value as plain text.
Solution 
app.MapGet("/ping", () => new { pong = true });   // object → JSON, 200
app.MapGet("/echo/{text}", (string text) => text); // string → text/plain, 200

// The parameter name matching the route template is what selects route
// binding; renaming either one silently moves it to the query string.
2 (easy): Write GET /products/{id:int} that returns 200 with the product or 404, using TypedResults and a declared union return type.
Solution 
app.MapGet("/products/{id:int}",
    async Task<Results<Ok<Product>, NotFound>> (
        int id, ProductService svc, CancellationToken ct) =>
{
    var product = await svc.FindAsync(id, ct);
    return product is null
        ? TypedResults.NotFound()
        : TypedResults.Ok(product);
});

// The union return type means adding a 409 branch without declaring it is a
// COMPILE error, and OpenAPI documents both 200 and 404 with no attributes.
3 (medium): A GET /reports endpoint has grown to nine parameters. Refactor it with [AsParameters], giving page and size sensible defaults.
Solution 
public readonly record struct ReportQuery(
    DateOnly? From,
    DateOnly? To,
    string? Region,
    string? Sort,
    bool Descending = false,
    int Page = 1,
    int Size = 20);

app.MapGet("/reports", async (
    [AsParameters] ReportQuery query,
    ReportService service,
    CancellationToken ct) => TypedResults.Ok(await service.RunAsync(query, ct)));

// Each property still binds from the query string by the normal rules, so the
// public URL contract is unchanged — this is purely a signature refactor.
// The win is that ReportQuery is now a testable type: service.RunAsync can be
// unit tested with `new ReportQuery(Region: "eu")` and no HTTP involved.
4 (medium): Group all /api/orders endpoints so every one requires authorization and is tagged "Orders", but DELETE additionally requires an "admin" policy.
Solution 
public static class OrderEndpoints
{
    public static RouteGroupBuilder MapOrderEndpoints(this IEndpointRouteBuilder routes)
    {
        var group = routes.MapGroup("/api/orders")
            .RequireAuthorization()      // applies to EVERY endpoint below
            .WithTags("Orders");

        group.MapGet("/", GetAll);
        group.MapGet("/{id:int}", GetById);
        group.MapPost("/", Create);

        group.MapDelete("/{id:int}", Delete)
             .RequireAuthorization("admin");   // ADDS to the group requirement

        return group;
    }
}

// Declaring auth on the group is the security-relevant part: a new endpoint
// added to this group is protected by default. The per-endpoint alternative
// fails open — one forgotten call is a publicly deletable resource.
5 (hard): Write a reusable endpoint filter that rejects requests whose body fails IValidator<T> with a 400 problem-details response, and explain why it must run after binding.
Solution 
public sealed class ValidationFilter<T>(IValidator<T> validator) : IEndpointFilter
    where T : class
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context, EndpointFilterDelegate next)
    {
        var model = context.Arguments.OfType<T>().FirstOrDefault();
        if (model is null) return await next(context);   // nothing to validate

        var result = await validator.ValidateAsync(model);
        if (!result.IsValid)
            return TypedResults.ValidationProblem(result.ToDictionary());

        return await next(context);
    }
}

public static RouteHandlerBuilder Validate<T>(this RouteHandlerBuilder b)
    where T : class => b.AddEndpointFilter<ValidationFilter<T>>();

group.MapPost("/", Create).Validate<CreateOrder>();

// WHY AFTER BINDING: the filter reads the DEserialized model out of
// context.Arguments. Middleware runs before routing has bound anything, so the
// equivalent middleware would have to read and buffer the raw body, deserialize
// it a second time, and guess the target type — duplicating work the framework
// already did and desynchronising if binding rules differ. Returning a result
// without calling next() short-circuits: the handler never runs.
6 (hard): An endpoint accepts POST /orders and must be safe to retry after a network timeout without creating duplicate orders. Design the endpoint.
Solution 
// The requirement is IDEMPOTENCY, and it cannot be solved by the handler
// signature alone — a retried POST is indistinguishable from a second genuine
// order unless the CLIENT supplies a key identifying the attempt.

app.MapPost("/orders", async Task<Results<Created<Order>, Ok<Order>, ValidationProblem>> (
    [FromHeader(Name = "Idempotency-Key")] string? key,
    CreateOrder request,
    OrderService orders,
    IIdempotencyStore store,
    CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(key))
        return TypedResults.ValidationProblem(new Dictionary<string, string[]>
            { ["Idempotency-Key"] = ["Header is required for this endpoint."] });

    // Atomic reserve-or-fetch: the store must do this in ONE operation
    // (INSERT ... ON CONFLICT, or SETNX) or two concurrent retries both pass.
    if (await store.TryGetAsync(key, ct) is { } existing)
        return TypedResults.Ok(existing);        // 200, not 201 — nothing new

    var order = await orders.CreateAsync(request, ct);
    await store.SaveAsync(key, order, TimeSpan.FromHours(24), ct);
    return TypedResults.Created($"/orders/{order.Id}", order);
});

// The design decisions worth defending:
//  • the key comes from the CLIENT, because only the client knows that attempt
//    two is a retry of attempt one rather than a new order
//  • the replay returns 200, not 201 — 201 asserts a resource was created now
//  • the reserve must be atomic; a get-then-set race under concurrent retries
//    is exactly the duplicate this endpoint exists to prevent
//  • the record expires: keys are a retry window, not permanent history
//  • CancellationToken is threaded through, so an abandoned retry stops work
//
// Note what is NOT solved: if the process dies between CreateAsync and
// SaveAsync, the order exists with no idempotency record and a retry duplicates
// it. Closing that needs the order and the key written in ONE transaction.

Writing the order and the idempotency record in a single transaction is covered in EF Core: Change Tracking & Transactions.

🎯 Key Takeaways

  • A minimal API endpoint is an HTTP method, a route template and a delegate — producing the same endpoint objects controllers produce, so filters, auth, CORS and OpenAPI work identically on both.
  • Binding is inferred by name and type in a fixed order: route → DI → special types → query (simple/TryParse) → JSON body (complex). Simple types come from the query, complex types from the body.
  • TryParse maps one string to a type; BindAsync sees the whole HttpContext and wins when both exist. Both are the right place to normalise and clamp.
  • [AsParameters] flattens a record into individual bindings — the fix for unreadable signatures, and it makes the query object independently testable.
  • Prefer TypedResults with a Results<T1,T2> return type: OpenAPI infers the contract and the compiler enforces that every path returns a declared result.
  • 401 means "authenticate and retry"; 403 means "authenticated and still not allowed". Confusing them sends clients into re-login loops.
  • MapGroup declares prefix, authorization and filters once for a whole feature area — security by default rather than per-endpoint repetition that fails open when forgotten.
  • Endpoint filters see bound, typed arguments; middleware sees raw HttpContext before routing. Validation belongs in a filter, correlation IDs in middleware.
  • Minimal APIs still have no automatic model validation, no view rendering and no controller inheritance — know the gaps before choosing them, and keep handlers thin so the choice stays cheap to reverse.
