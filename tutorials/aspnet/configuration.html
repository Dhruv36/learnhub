Configuration & Options Foundations

What you'll master: the layered configuration system and its precedence rules, the three options interfaces and which one you actually want, validating configuration so a typo fails the deploy instead of the third request, and where secrets belong in each environment. Prerequisites: How ASP.NET Core Runs — the configure phase and the host.

Part 1 — Providers and Precedence

// Configuration is a LIST of key-value providers, read in order, LAST WINS.
// CreateBuilder registers these by default, lowest precedence first:
//
//   1. appsettings.json
//   2. appsettings.{Environment}.json        ← Development / Staging / Production
//   3. user secrets                          ← Development only, off-disk
//   4. environment variables
//   5. command-line arguments                ← highest
//
// So a value in appsettings.json is a DEFAULT, and anything later overrides it.
// This ordering is the whole design: commit safe defaults, override per
// environment without editing files, and override again at the command line
// for a one-off run.

var builder = WebApplication.CreateBuilder(args);

// Reading is by key path, with ':' as the section separator:
var conn    = builder.Configuration.GetConnectionString("Default");
var timeout = builder.Configuration.GetValue<int>("Api:TimeoutSeconds", 30);
var section = builder.Configuration.GetSection("Api");

// ENVIRONMENT VARIABLES AND THE COLON PROBLEM: ':' is not legal in an env var
// name on most platforms, so use DOUBLE UNDERSCORE instead. Both of these set
// the same key:
//   appsettings.json   { "Api": { "TimeoutSeconds": 30 } }
//   environment        Api__TimeoutSeconds=30
// A single underscore does NOT work — Api_TimeoutSeconds is a different,
// unrelated key that nothing reads. This silently-does-nothing failure is the
// most common configuration bug in containerised deployments.

// Adding providers — order of registration IS precedence:
builder.Configuration
    .AddJsonFile("shared.json", optional: true, reloadOnChange: true)
    .AddIniFile("legacy.ini", optional: true)
    .AddEnvironmentVariables(prefix: "MYAPP_");   // strips the prefix off keys

// ARRAYS flatten to indexed keys, which is how you override one element:
//   { "Hosts": [ "a.example.com", "b.example.com" ] }
// becomes  Hosts:0=a.example.com  and  Hosts:1=b.example.com
//   env:   Hosts__0=override.example.com
// The trap: providers MERGE, they do not replace. Setting Hosts__0 overrides
// only element zero — the original element one survives. There is no way to
// shorten an array by overriding it, so an environment-specific list that must
// be smaller has to be defined in a file, not patched.

Part 2 — Binding to Typed Options

// Reading string keys all over the codebase is how typos reach production.
// Bind a section to a class ONCE, inject the class everywhere.

public sealed class ApiOptions
{
    public const string SectionName = "Api";      // one place, not a literal

    public required string BaseUrl { get; init; }
    public int TimeoutSeconds { get; init; } = 30;
    public int RetryCount { get; init; } = 3;
    public string[] AllowedHosts { get; init; } = [];
}

// appsettings.json
// {
//   "Api": {
//     "BaseUrl": "https://api.example.com",
//     "TimeoutSeconds": 10,
//     "AllowedHosts": [ "a.example.com" ]
//   }
// }

builder.Services
    .AddOptions<ApiOptions>()
    .Bind(builder.Configuration.GetSection(ApiOptions.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();          // ← see Part 4, this line matters

// Binding rules worth knowing:
//  • property names match case-insensitively
//  • missing keys leave the property at its initialiser default — they do NOT
//    throw, which is why validation is a separate, necessary step
//  • `required` gives you compile-time discipline but does NOT make binding
//    fail at runtime; only validation does
//  • private setters are not bound; use init or set
//  • complex nested objects and arrays bind recursively

// Consuming it — inject the OPTIONS INTERFACE, not IConfiguration:
public sealed class ApiClient(IOptions<ApiOptions> options, HttpClient http)
{
    private readonly ApiOptions _options = options.Value;

    public async Task<T?> GetAsync<T>(string path, CancellationToken ct) => ...
}
// Injecting IConfiguration into a service is a design smell: it hides which
// keys the service depends on, defeats validation, cannot be strongly typed,
// and makes tests construct a configuration builder instead of an object.

Part 3 — The Three Options Interfaces

// This is the part interviews probe, because choosing wrong produces bugs that
// only appear after a config change in production.

// IOptions<T> — SINGLETON. Resolved once, cached forever.
//   Reload does nothing. The value is fixed at first resolution.
//   Use for: settings that cannot change without a restart anyway —
//   connection strings, a service's base URL, feature wiring.
public class Fixed(IOptions<ApiOptions> o) { private readonly ApiOptions _o = o.Value; }

// IOptionsSnapshot<T> — SCOPED. Recomputed once per request.
//   Picks up reloadOnChange edits on the next request.
//   Use for: per-request settings that should track a live file edit.
//   CANNOT be injected into a singleton — it is scoped, so that is a captive
//   dependency and the container throws when scope validation is on.
public class PerRequest(IOptionsSnapshot<ApiOptions> o) { }

// IOptionsMonitor<T> — SINGLETON, but always current.
//   Exposes CurrentValue and an OnChange callback.
//   Use for: singletons and background services that must see updates.
public sealed class Worker : BackgroundService
{
    private readonly IOptionsMonitor<ApiOptions> _monitor;
    private readonly IDisposable? _subscription;

    public Worker(IOptionsMonitor<ApiOptions> monitor)
    {
        _monitor = monitor;
        _subscription = monitor.OnChange(o =>
            logger.LogInformation("Api timeout now {T}s", o.TimeoutSeconds));
    }

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // Read CurrentValue INSIDE the loop, never cache it in a field —
            // caching it defeats the entire point of using Monitor.
            var timeout = _monitor.CurrentValue.TimeoutSeconds;
            await DoWorkAsync(timeout, ct);
        }
    }

    public override void Dispose()
    {
        _subscription?.Dispose();     // OnChange leaks without this
        base.Dispose();
    }
}

// THE DECISION IN ONE LINE: singleton that must see changes → Monitor;
// per-request that should see changes → Snapshot; everything else → Options.
// Defaulting to IOptions is correct far more often than teams assume, because
// most settings genuinely cannot be applied without a restart.

// Named options — several configurations of the same shape:
builder.Services.Configure<ApiOptions>("primary", config.GetSection("Api:Primary"));
builder.Services.Configure<ApiOptions>("backup",  config.GetSection("Api:Backup"));

public class Dual(IOptionsMonitor<ApiOptions> monitor)
{
    private readonly ApiOptions _primary = monitor.Get("primary");
    private readonly ApiOptions _backup  = monitor.Get("backup");
}
Key insight: ValidateOnStart() converts a class of production incidents into failed deploys. Without it, options validation runs lazily on first resolution — so a missing connection string surfaces as an exception on the first request that touches the database, after the deployment reported success and traffic has shifted. With it, the host refuses to start, the health check never passes, and the orchestrator rolls back automatically. The cost is one line; the benefit is that configuration errors are caught by the deployment pipeline rather than by users.

Part 4 — Validating Configuration Properly

// THREE LEVELS, use all of them.

// LEVEL 1 — data annotations for shape:
public sealed class ApiOptions
{
    [Required, Url]
    public required string BaseUrl { get; init; }

    [Range(1, 300)]
    public int TimeoutSeconds { get; init; } = 30;

    [Range(0, 10)]
    public int RetryCount { get; init; } = 3;
}

// LEVEL 2 — a delegate for cross-property rules:
builder.Services.AddOptions<ApiOptions>()
    .Bind(builder.Configuration.GetSection(ApiOptions.SectionName))
    .ValidateDataAnnotations()
    .Validate(o => o.TimeoutSeconds > o.RetryCount * 2,
        "TimeoutSeconds must exceed RetryCount * 2, or retries cannot complete.")
    .ValidateOnStart();

// LEVEL 3 — IValidateOptions<T> when validation needs a dependency:
public sealed class ApiOptionsValidator(IHostEnvironment env)
    : IValidateOptions<ApiOptions>
{
    public ValidateOptionsResult Validate(string? name, ApiOptions options)
    {
        var failures = new List<string>();

        if (env.IsProduction() && options.BaseUrl.StartsWith("http://"))
            failures.Add("BaseUrl must use https in Production.");

        if (env.IsProduction() && options.AllowedHosts.Length == 0)
            failures.Add("AllowedHosts must not be empty in Production.");

        return failures.Count > 0
            ? ValidateOptionsResult.Fail(failures)
            : ValidateOptionsResult.Success;
    }
}
builder.Services.AddSingleton<IValidateOptions<ApiOptions>, ApiOptionsValidator>();

// Environment-conditional validation like this is worth the effort: it encodes
// "we know http is fine locally and unacceptable in production" as a rule the
// deploy enforces, rather than as tribal knowledge someone violates at 2am.

// WHAT VALIDATION CANNOT CATCH: a value that is well-formed and WRONG. A valid
// https URL pointing at the staging API passes every rule above. Guard that
// with a startup health check that actually calls the dependency, not with
// more validation.

Part 5 — Secrets, Per Environment

// The rule: secrets never live in appsettings.json, because that file is
// committed. Where they DO live depends on the environment.

// DEVELOPMENT — user secrets. Stored outside the repo, per developer, keyed by
// the project's UserSecretsId. Automatically loaded in Development only.
//   dotnet user-secrets init
//   dotnet user-secrets set "ConnectionStrings:Default" "Server=..."
//   dotnet user-secrets list
// Plaintext JSON in the user profile — protection against COMMITTING a secret,
// not against a compromised machine. Do not mistake it for encryption.

// PRODUCTION — a real secret store, loaded as a provider:
if (builder.Environment.IsProduction())
{
    var uri = new Uri($"https://{builder.Configuration["KeyVaultName"]}.vault.azure.net/");
    builder.Configuration.AddAzureKeyVault(uri, new DefaultAzureCredential());
}
// Registered LAST, so vault values override file values. Equivalents: AWS
// Secrets Manager, HashiCorp Vault, Kubernetes secrets mounted as env vars.

// KEY NAMING ACROSS STORES: vault key names usually cannot contain ':', so
// providers translate '--' into the section separator:
//   vault key   ConnectionStrings--Default
//   config key  ConnectionStrings:Default
// Same class of trap as '__' in environment variables — get it wrong and the
// key simply never appears, with no error anywhere.

// NEVER LOG THE WHOLE CONFIGURATION. This one line has leaked more credentials
// than any exploit:
//   logger.LogInformation("{Config}", configuration.AsEnumerable());   // ← NO

// A safe startup summary logs KEYS and PROVENANCE, never values:
foreach (var provider in ((IConfigurationRoot)builder.Configuration).Providers)
    logger.LogInformation("Config provider: {Provider}", provider);

// Debug-time provenance — which provider supplied a key. Invaluable for
// "why is this value not what the file says", and safe because it shows the
// provider chain rather than the secret itself:
var debugView = ((IConfigurationRoot)app.Configuration).GetDebugView();
// Still: never expose this on an endpoint. It contains values.

Part 6 — A Realistic Setup

var builder = WebApplication.CreateBuilder(args);

// 1. Environment-specific providers, in deliberate precedence order.
if (builder.Environment.IsProduction())
{
    builder.Configuration.AddAzureKeyVault(
        new Uri($"https://{builder.Configuration["KeyVaultName"]}.vault.azure.net/"),
        new DefaultAzureCredential());
}

// 2. One options class per feature area, each validated on start.
builder.Services.AddOptions<ApiOptions>()
    .Bind(builder.Configuration.GetSection(ApiOptions.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();

builder.Services.AddOptions<DatabaseOptions>()
    .Bind(builder.Configuration.GetSection(DatabaseOptions.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();

// 3. Options consumed where they are needed, typed:
builder.Services.AddHttpClient<ApiClient>((sp, http) =>
{
    var o = sp.GetRequiredService<IOptions<ApiOptions>>().Value;
    http.BaseAddress = new Uri(o.BaseUrl);
    http.Timeout = TimeSpan.FromSeconds(o.TimeoutSeconds);
});

var app = builder.Build();

// 4. Fail loudly at startup, not quietly at request time. ValidateOnStart
//    already does this for options; a health check covers reachability, which
//    validation cannot express.
app.MapHealthChecks("/health/ready");

app.Run();

// appsettings.json — committed, safe defaults, NO secrets:
// {
//   "Api": { "BaseUrl": "https://api.example.com", "TimeoutSeconds": 10 },
//   "Database": { "CommandTimeoutSeconds": 30 }
// }
//
// appsettings.Development.json — committed, local overrides, still no secrets:
// {
//   "Api": { "BaseUrl": "https://localhost:5001", "TimeoutSeconds": 60 },
//   "Logging": { "LogLevel": { "Microsoft.AspNetCore": "Debug" } }
// }
//
// Secrets: user-secrets locally, key vault in production. Never in either file.

Interview Questions

Beginner: What is the precedence order of the default configuration providers?

Lowest to highest: appsettings.json, then appsettings.{Environment}.json, then user secrets in Development, then environment variables, then command-line arguments. Later providers override earlier ones for the same key. The design intent is that the committed JSON file holds safe defaults, environment-specific files adjust them per deployment target, and environment variables or command-line arguments override anything without editing a file — which is what makes the same build artifact deployable to every environment.

Beginner: Why do environment variables use a double underscore?

Because configuration keys use a colon as the section separator — Api:TimeoutSeconds — and a colon is not a legal character in environment variable names on most platforms. The double underscore is the portable substitute, so Api__TimeoutSeconds sets the same key. The reason this matters practically is that a single underscore does not fail: Api_TimeoutSeconds is simply a different key that nothing reads, so the application starts normally using the default value. It is a silent misconfiguration, and it is one of the most common deployment bugs in containerised apps.

Mid: Explain IOptions, IOptionsSnapshot and IOptionsMonitor.

IOptions<T> is registered as a singleton and computes its value once, so it never reflects later configuration changes — appropriate for settings that could not be applied without a restart anyway, like a connection string. IOptionsSnapshot<T> is scoped and recomputed per request, so each request sees the current values; because it is scoped it cannot be injected into a singleton, which would be a captive dependency. IOptionsMonitor<T> is a singleton that always exposes the current value through CurrentValue and supports change notifications via OnChange, making it the right choice for singletons and background services. The rule of thumb: singleton needing live values takes Monitor, per-request needing live values takes Snapshot, and everything else takes Options — which is more often than people expect.

Mid: What does ValidateOnStart() change, and why is it worth a line of code?

Without it, options validation is lazy: it runs the first time the options object is resolved, which for a rarely-used service might be minutes or hours after startup. That means a typo'd or missing setting produces a runtime exception on some unlucky request, after the deployment has already been reported successful and traffic has shifted to the new version. ValidateOnStart() forces validation during host startup, so the process fails to start, readiness checks never pass, and the orchestrator rolls back automatically. It converts a production incident into a failed deploy, which is the single cheapest reliability improvement available in the configuration system.

Senior: A setting is correct in appsettings.Production.json but the application uses a different value. Diagnose.

The most likely cause is a higher-precedence provider overriding it — environment variables and command-line arguments both outrank JSON files, so a stale Api__TimeoutSeconds left in a container definition, Helm chart or App Service setting wins silently. I would confirm with GetDebugView() on the configuration root, which reports each key alongside the provider that supplied it, and that immediately distinguishes "overridden" from "never loaded". The second candidate is that the environment-specific file is not being loaded at all, which almost always means ASPNETCORE_ENVIRONMENT is unset or misspelled — if it says "production" in lowercase, or "Prod", the file name no longer matches and the app silently runs on base defaults. The third is a key-name mismatch that looks right at a glance: a single underscore instead of a double one, or a vault key using -- incorrectly, both of which create an unread key rather than an error. A fourth, easy to miss, is that the file exists in the repository but was not copied into the published output, so it is absent on the server entirely. What makes this whole class of bug expensive is that every one of these fails silently by design — configuration treats a missing key as "use the default", so the application starts and behaves plausibly. That is the argument for [Required] plus ValidateOnStart: it turns an unnoticed default into a refused startup.

Senior: Design configuration and secret management for a service deployed to dev, staging and production across multiple regions.

The organising principle is that one build artifact deploys everywhere and configuration is entirely external, because any scheme requiring a rebuild per environment guarantees that what was tested is not what ships. Concretely: appsettings.json holds only safe, non-secret defaults and is committed; environment-specific files carry structural differences that are genuinely static; and everything that varies per deployment arrives through environment variables or a secret store, layered last so it wins. Secrets never sit in files at any tier — user secrets locally, and a managed store such as Key Vault or Secrets Manager in deployed environments, accessed with a workload identity rather than a bootstrap credential, since a secret used to fetch secrets has just moved the problem. For multi-region I would separate configuration into three tiers: global settings identical everywhere, regional settings such as the local database endpoint or region code, and instance settings like the pod name. That hierarchy keeps a regional change from requiring edits in every region's blob, and it makes it obvious which tier a new setting belongs to. Every options class gets data-annotation validation plus environment-conditional rules — https required in production, allowed hosts non-empty — and ValidateOnStart everywhere, so a bad regional rollout fails its health check and the orchestrator halts the rollout at the first region rather than propagating. I would deliberately not use live reload for anything security-relevant: a setting that changes authentication behaviour underneath in-flight requests is far harder to reason about than a rolling restart, and restarts are cheap when startup is fast. Feature flags are the exception, and they belong in a purpose-built flag service with audit and targeting rather than in the configuration system, because the operational requirements — who changed what, when, for whom — are entirely different. Finally, I would treat provenance as a first-class operational need: log the provider chain at startup and never the values, and keep GetDebugView available to operators through a secured channel rather than an endpoint, since the fastest way to resolve a configuration incident is knowing which layer supplied the value.

4 (medium): A BackgroundService must pick up a changed poll interval without a restart. Wire it correctly, including cleanup.
Solution 
public sealed class PollingWorker : BackgroundService
{
    private readonly IOptionsMonitor<PollOptions> _options;
    private readonly ILogger<PollingWorker> _logger;
    private readonly IDisposable? _subscription;

    public PollingWorker(IOptionsMonitor<PollOptions> options,
                         ILogger<PollingWorker> logger)
    {
        _options = options;
        _logger = logger;
        _subscription = options.OnChange(o =>
            _logger.LogInformation("Poll interval now {Seconds}s", o.IntervalSeconds));
    }

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await PollAsync(ct);

            // Read CurrentValue INSIDE the loop. Hoisting it above the loop or
            // into a field caches the startup value and silently defeats the
            // entire reason for using IOptionsMonitor.
            var interval = TimeSpan.FromSeconds(_options.CurrentValue.IntervalSeconds);
            await Task.Delay(interval, ct);
        }
    }

    public override void Dispose()
    {
        _subscription?.Dispose();     // OnChange returns IDisposable; dropping
        base.Dispose();               // it leaks the callback registration
    }
}

// scope validation is enabled.
//
// Also requires reloadOnChange:true on the JSON provider (the default for

5 (hard): Enforce that production uses https and a non-empty allowed-hosts list, while development may use http. Fail the deploy otherwise.
Solution 
public sealed class ApiOptionsValidator(IHostEnvironment env)
    : IValidateOptions<ApiOptions>
{
    public ValidateOptionsResult Validate(string? name, ApiOptions options)
    {
        var failures = new List<string>();

        if (!Uri.TryCreate(options.BaseUrl, UriKind.Absolute, out var uri))
        {
            failures.Add($"BaseUrl '{options.BaseUrl}' is not an absolute URI.");
        }
        else if (env.IsProduction() && uri.Scheme != Uri.UriSchemeHttps)
        {
            failures.Add("BaseUrl must use https in Production.");
        }

        if (env.IsProduction() && options.AllowedHosts.Length == 0)
            failures.Add("AllowedHosts must not be empty in Production.");

        return failures.Count > 0
            ? ValidateOptionsResult.Fail(failures)
            : ValidateOptionsResult.Success;
    }
}

6 (hard): Design configuration for one artifact deployed to dev, staging and three production regions, including secrets. State what you deliberately would not make reloadable.
Solution 
// PRINCIPLE: one build artifact, configuration entirely external. Anything
// requiring a rebuild per environment means the tested binary is not the
// shipped binary.

// THREE TIERS, layered lowest to highest:
//
//   1. GLOBAL     appsettings.json — committed, identical everywhere.
//                 Safe defaults only, never a secret.
//                 { "Api": { "TimeoutSeconds": 10 }, "Features": {...} }
//
//   2. REGIONAL   environment variables from the deployment manifest.
//                 Region code, regional database endpoint, regional cache.
//                 Region__Code=eu-west-1
//                 ConnectionStrings__Default=[regional endpoint]
//
//   3. SECRETS    a managed store, registered LAST so it always wins.
if (builder.Environment.IsProduction())
{
    builder.Configuration.AddAzureKeyVault(
        new Uri($"https://{builder.Configuration["KeyVault:Name"]}.vault.azure.net/"),
        new DefaultAzureCredential());     // workload identity, NOT a stored key
}

// WHY THE TIERS: without them, a change to a global default requires editing
// five regional blobs and someone forgets one. The tier a setting belongs to
// is decided by what it varies with — nothing, region, or instance.

// SECRET ACCESS: a workload/managed identity, never a bootstrap credential in
// an env var. A secret used to fetch secrets has relocated the problem, not
// solved it. Rotation then happens in the store with no redeploy.

// VALIDATION AT EVERY TIER, so a bad rollout stops at region one:
builder.Services.AddOptions<ApiOptions>()
    .Bind(builder.Configuration.GetSection(ApiOptions.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();
// Combined with a readiness probe, a misconfigured region fails its health
// check and the orchestrator halts the rollout rather than propagating it.

// WHAT I WOULD DELIBERATELY NOT MAKE RELOADABLE — and why:
//  • authentication and authorization settings: changing the token audience or
//    a policy underneath in-flight requests produces a window where some
//    requests are evaluated under the old rules and some under the new, which
//    is unreviewable and unauditable. A rolling restart is cheap and atomic
//    per instance.
//  • connection strings: existing pooled connections do not migrate, so the
//    app ends up split across two databases with no clear cutover point.
//  • anything that changes the shape of the DI graph — services are already
//    constructed; only the values they read can change, so a "reloadable"
//    setting that should have swapped an implementation is a lie.
//
// Reload IS appropriate for log levels and timeouts — genuinely per-operation
// values with no cross-request invariant.
//
// FEATURE FLAGS belong in a purpose-built flag service, not here: they need
// audit trails, per-user targeting and gradual rollout, which the
// configuration system does not model. Reusing config for flags means every
// flag flip is an untracked deployment change.

🎯 Key Takeaways

  • Configuration is layered providers where the last one wins: JSON → environment JSON → user secrets → environment variables → command line.
  • Environment variables use __ for the section separator. A single underscore creates a different key and fails silently.
  • Bind sections to typed options classes and inject those — injecting IConfiguration into services hides dependencies and defeats validation.
  • IOptions is a fixed singleton, IOptionsSnapshot is per-request, IOptionsMonitor is a singleton that tracks changes. Snapshot in a singleton is a captive dependency.
  • Read Monitor.CurrentValue at the point of use and dispose the OnChange subscription, or the mechanism silently does nothing and leaks.
  • ValidateOnStart() turns configuration errors into failed deploys instead of failed requests — the cheapest reliability win in the system.
  • required is a compile-time initialiser rule and does not affect binding; use [Required] with ValidateDataAnnotations for runtime enforcement.
  • Use IValidateOptions<T> when a rule needs a dependency, and collect all failures so one startup log shows every problem.
  • Secrets belong in user secrets locally and a managed store in production, accessed by workload identity — never in appsettings.json, never in logs.
  • Validation proves a value is well-formed, not that it is correct: a valid URL pointing at the wrong environment passes everything. Reachability is a health check's job.
