Authorization Policies & Requirements Security

What you'll master: why role checks stop scaling and what replaces them, policies built from requirements and handlers, resource-based authorization for "may this user edit this record", making endpoints protected by default so a forgotten attribute cannot ship, and testing authorization so a fail-open bug is caught in CI. Prerequisites: Authentication and Middleware Pipeline.

Part 1 — From Roles to Policies

// The simplest form, and where every codebase starts:
[Authorize]                            // any authenticated user
[Authorize(Roles = "admin")]           // must hold the admin role
[Authorize(Roles = "admin,manager")]   // admin OR manager

// WHY ROLE CHECKS STOP SCALING — the failure is gradual, not sudden:
//   • the role string is duplicated across dozens of endpoints, so adding a
//     "supervisor" role that should behave like "manager" means finding and
//     editing every one of them
//   • the rule is invisible: [Authorize(Roles = "admin")] says WHO, never WHY.
//     Six months later nobody knows whether it means "can delete orders" or
//     "is internal staff", so nobody dares change it
//   • roles cannot express anything conditional — "manager, but only for their
//     own department" has no expression in an attribute
//   • testing requires an HTTP request; the rule cannot be unit-tested alone

// POLICIES name the RULE rather than the holder:
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("CanDeleteOrders", policy => policy.RequireRole("admin"))
    .AddPolicy("CanViewReports", policy => policy
        .RequireAuthenticatedUser()
        .RequireClaim("department", "finance", "executive"))
    .AddPolicy("IsVerified", policy => policy
        .RequireClaim("email_verified", "true"));

[Authorize(Policy = "CanDeleteOrders")]
public async Task<IActionResult> Delete(int id) => ...;

// The indirection is the entire point. The endpoint declares the CAPABILITY
// it needs; the policy decides who has it. Changing "admin can delete" to
// "admin or a manager with the orders.delete claim" is one edit in one place,
// and every endpoint follows automatically.

// THE BUILT-IN BUILDER METHODS:
policy.RequireAuthenticatedUser();
policy.RequireRole("admin", "manager");                 // any of these
policy.RequireClaim("scope");                           // claim must exist
policy.RequireClaim("scope", "orders.write");           // with this value
policy.RequireUserName("service-account");
policy.RequireAssertion(ctx =>                          // arbitrary predicate
    ctx.User.HasClaim("tenant_id", currentTenant));

// COMBINING is AND — every requirement must pass:
.AddPolicy("SeniorFinance", policy => policy
    .RequireRole("manager")                  // must be a manager
    .RequireClaim("department", "finance")); // AND in finance

// FOR "OR", use a single assertion or a custom requirement — there is no
// RequireAny, and chaining does not give you one:
.AddPolicy("StaffOrOwner", policy => policy.RequireAssertion(context =>
    context.User.IsInRole("staff") ||
    context.User.HasClaim("account_owner", "true")));

Part 2 — Requirements and Handlers

// When a rule needs data, a service, or real logic, it becomes a REQUIREMENT
// (the question) plus a HANDLER (the answer).

public sealed class MinimumAgeRequirement(int age) : IAuthorizationRequirement
{
    public int MinimumAge { get; } = age;
}

public sealed class MinimumAgeHandler(TimeProvider clock)
    : AuthorizationHandler<MinimumAgeRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, MinimumAgeRequirement requirement)
    {
        var claim = context.User.FindFirst("date_of_birth");
        if (claim is null || !DateOnly.TryParse(claim.Value, out var dob))
            return Task.CompletedTask;      // ← NOT Fail(). See below.

        var today = DateOnly.FromDateTime(clock.GetUtcNow().DateTime);
        var age = today.Year - dob.Year;
        if (dob > today.AddYears(-age)) age--;

        if (age >= requirement.MinimumAge)
            context.Succeed(requirement);   // this requirement is satisfied

        return Task.CompletedTask;
    }
}

builder.Services.AddSingleton<IAuthorizationHandler, MinimumAgeHandler>();
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("AtLeast18", policy =>
        policy.Requirements.Add(new MinimumAgeRequirement(18)));

// ── THE THREE OUTCOMES, AND WHY THE DIFFERENCE MATTERS ───────────────────
//   context.Succeed(requirement)  this requirement is met
//   context.Fail()                VETO — the whole policy fails, and no other
//                                 handler can undo it
//   returning without either      this handler has no opinion
//
// Doing nothing is NOT the same as failing. A requirement with several
// handlers passes if ANY of them succeeds — so a handler that cannot judge
// should stay silent, letting another handler decide. Calling Fail() instead
// makes the policy fail permanently even when a later handler would have
// approved. This is the single most common bug in custom handlers.

// MULTIPLE HANDLERS FOR ONE REQUIREMENT — an OR across handlers:
public sealed class OwnerHandler : AuthorizationHandler<EditRequirement> { }
public sealed class AdminHandler : AuthorizationHandler<EditRequirement> { }
// Registered together: the owner OR an admin may edit. Each handler answers
// only the case it knows about and stays silent otherwise.

// A HANDLER CAN SATISFY SEVERAL REQUIREMENTS at once — useful for a
// superuser bypass:
public sealed class SuperAdminHandler : IAuthorizationHandler
{
    public Task HandleAsync(AuthorizationHandlerContext context)
    {
        if (context.User.IsInRole("superadmin"))
            foreach (var requirement in context.PendingRequirements.ToList())
                context.Succeed(requirement);

        return Task.CompletedTask;
    }
}
// Deliberate and dangerous in equal measure — it is a global bypass, so it
// deserves auditing and a very small population of holders.
Key insight: the difference between "this handler declines" and "this handler vetoes" decides whether your authorization composes. Handlers are additive by default: a requirement is satisfied when any handler succeeds, so silence means "not my case, ask someone else". context.Fail() is a hard veto that no later handler can override, which is occasionally what you want — a compliance block, a suspended account — and is otherwise a bug that surfaces as "authorization works until I add a second rule". Reach for silence by default and Fail() only when the denial must be absolute.

Part 3 — Resource-Based Authorization

// Attribute policies answer "may this user delete orders?" They cannot answer
// "may this user delete THIS order?" — because the resource is not known
// until it has been loaded, which happens inside the handler.

public sealed class OrderOwnerHandler
    : AuthorizationHandler<OperationAuthorizationRequirement, Order>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        OperationAuthorizationRequirement requirement,
        Order resource)                       // ← the loaded entity
    {
        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

        if (requirement.Name == "Read" && resource.CustomerId.ToString() == userId)
            context.Succeed(requirement);

        if (requirement.Name == "Delete"
            && resource.CustomerId.ToString() == userId
            && resource.Status == OrderStatus.Draft)     // business rule
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}

public static class OrderOperations
{
    public static readonly OperationAuthorizationRequirement Read = new() { Name = "Read" };
    public static readonly OperationAuthorizationRequirement Delete = new() { Name = "Delete" };
}

// Invoked IMPERATIVELY, after loading the resource:
[HttpDelete("{id:int}")]
public async Task<IActionResult> Delete(
    int id, IAuthorizationService authorization, CancellationToken ct)
{
    var order = await db.Orders.FindAsync([id], ct);
    if (order is null) return NotFound();

    var result = await authorization.AuthorizeAsync(
        User, order, OrderOperations.Delete);

    if (!result.Succeeded)
        return User.Identity?.IsAuthenticated == true
            ? Forbid()          // authenticated but not permitted
            : Challenge();      // not authenticated at all

    db.Orders.Remove(order);
    await db.SaveChangesAsync(ct);
    return NoContent();
}

// ── 403 vs 404, A DELIBERATE SECURITY DECISION ───────────────────────────
// Returning 403 for an order the caller may not see CONFIRMS IT EXISTS. An
// attacker iterating /orders/{id} learns which ids are real. Returning 404 for
// both "missing" and "not yours" leaks nothing:
if (!result.Succeeded) return NotFound();
// The cost is diagnosability — a legitimate user with a permissions problem
// sees "not found". Resolve it by logging the real reason with the traceId, so
// support can distinguish them while the response does not.

// ── AND THE LIMIT OF ALL OF THIS ─────────────────────────────────────────
// Resource authorization runs only where it is CALLED. A background job or a
// message handler that loads the same order never invokes it. For data
// isolation, the durable enforcement is at the QUERY layer:
modelBuilder.Entity<Order>()
    .HasQueryFilter(o => o.CustomerId == _currentUser.Id);
// Then an order the caller does not own is not returned at all, on every code
// path, and the resource handler becomes defence in depth rather than the only
// line.

Part 4 — Secure by Default

// The most consequential authorization bug is not a wrong rule. It is a
// MISSING attribute on a new endpoint — which looks exactly like correct code
// and fails silently.

// ✗ THE OPT-IN MODEL: every endpoint must remember to protect itself.
[Authorize] public class OrdersController : ControllerBase { }
public class ReportsController : ControllerBase { }   // ← forgot. Public.

// ✓ INVERT IT — a FALLBACK POLICY applies to any endpoint with NO
//   authorization metadata of its own:
builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build());

// Now the new controller is protected automatically, and being public
// requires saying so OUT LOUD:
[AllowAnonymous]
public class HealthController : ControllerBase { }

// FALLBACK vs DEFAULT — a distinction people conflate:
//   DefaultPolicy   used by a bare [Authorize] with no policy named
//   FallbackPolicy  used when an endpoint has NO authorization metadata at all
// The fallback is the one that closes the forgotten-attribute hole.

// MINIMAL APIs — declare it on the group so new endpoints inherit:
var api = app.MapGroup("/api").RequireAuthorization();
api.MapGet("/orders", GetOrders);                    // protected
api.MapGet("/status", GetStatus).AllowAnonymous();   // explicit opt-out

// ── THE TEST THAT KEEPS IT HONEST ────────────────────────────────────────
[Fact]
public void Every_endpoint_is_protected_or_explicitly_listed_public()
{
    var endpoints = _factory.Services
        .GetRequiredService<EndpointDataSource>().Endpoints;

    var known = new HashSet<string> { "/health", "/api/v1/auth/token" };

    var unprotected = endpoints.OfType<RouteEndpoint>()
        .Where(e => e.Metadata.GetMetadata<IAllowAnonymous>() is not null)
        .Select(e => e.RoutePattern.RawText!)
        .Where(pattern => !known.Contains(pattern))
        .ToList();

    Assert.Empty(unprotected);
}
// A new public endpoint now FAILS THE BUILD and must be added to the list
// deliberately — turning "we forgot" into a reviewed decision.

// ── AND THE ORDERING RULE THAT UNDOES ALL OF IT ──────────────────────────
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();      // MUST come after UseRouting
// Before UseRouting, no endpoint is selected, so no [Authorize] metadata
// exists, so authorization finds nothing to enforce and PERMITS the request.
// It fails OPEN with no exception and no log entry — see the Middleware
// lesson. Every mechanism in this section is defeated by that one mistake.

Part 5 — Scopes, Tenancy, and Real Policies

// ── OAUTH SCOPES: what the CLIENT may do, not what the USER may do ───────
// A common conflation. The scope says the calling application was granted
// permission to attempt something; the user's own permissions are separate
// and BOTH must hold.
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("orders.read", policy => policy
        .RequireAuthenticatedUser()
        .RequireAssertion(context =>
        {
            // The `scope` claim is a SPACE-DELIMITED string, not a list —
            // RequireClaim("scope", "orders.read") fails when the token
            // carries "orders.read orders.write". This is a very common bug.
            var scopes = context.User.FindFirst("scope")?.Value?.Split(' ') ?? [];
            return scopes.Contains("orders.read");
        }));

// ── MULTI-TENANCY: the route value is CLIENT-SUPPLIED ────────────────────
public sealed class SameTenantRequirement : IAuthorizationRequirement;

public sealed class SameTenantHandler(IHttpContextAccessor accessor)
    : AuthorizationHandler<SameTenantRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, SameTenantRequirement requirement)
    {
        var routeTenant = accessor.HttpContext?
            .Request.RouteValues["tenantId"]?.ToString();
        var claimTenant = context.User.FindFirst("tenant_id")?.Value;

        if (routeTenant is not null && claimTenant is not null
            && string.Equals(routeTenant, claimTenant, StringComparison.OrdinalIgnoreCase))
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}
// Binding a tenant id from the route proves nothing about entitlement.
// Without this comparison, changing a GUID in the URL reads another
// customer's data — an IDOR, and one that looks like ordinary routing code.

// ── PERMISSIONS IN CLAIMS, AND THE LIMIT ─────────────────────────────────
// Putting permissions in the token avoids a database lookup per request:
//   "permissions": ["orders.read", "orders.write", "reports.view"]
// The cost is STALENESS: a revoked permission stays effective until the token
// expires. With 15-minute tokens that window is usually acceptable; with
// 8-hour tokens it is not, and "we removed their access this morning" becomes
// false during an incident.
//
// The alternative — loading permissions per request — is always fresh and
// costs a lookup. Cache it briefly (30-60s) and you get most of the
// performance with a bounded staleness window you can state precisely.

// ── DYNAMIC POLICIES, when names are not known at startup ────────────────
public sealed class PermissionPolicyProvider(IOptions<AuthorizationOptions> options)
    : DefaultAuthorizationPolicyProvider(options)
{
    public override async Task<AuthorizationPolicy?> GetPolicyAsync(string name)
    {
        if (await base.GetPolicyAsync(name) is { } existing) return existing;

        if (name.StartsWith("permission:"))
            return new AuthorizationPolicyBuilder()
                .AddRequirements(new PermissionRequirement(name["permission:".Length..]))
                .Build();

        return null;
    }
}
builder.Services.AddSingleton<IAuthorizationPolicyProvider, PermissionPolicyProvider>();
// Now [Authorize(Policy = "permission:orders.delete")] works without
// registering every permission by hand — which matters when permissions live
// in a database rather than in code.

Part 6 — Testing and Auditing Authorization

// ── UNIT-TEST HANDLERS DIRECTLY — no HTTP, no container ──────────────────
[Fact]
public async Task Owner_may_delete_their_draft_order()
{
    var user = new ClaimsPrincipal(new ClaimsIdentity(
        [new Claim(ClaimTypes.NameIdentifier, "42")], "test"));

    var order = new Order { CustomerId = 42, Status = OrderStatus.Draft };

    var context = new AuthorizationHandlerContext(
        [OrderOperations.Delete], user, order);

    await new OrderOwnerHandler().HandleAsync(context);

    Assert.True(context.HasSucceeded);
}

[Fact]
public async Task Owner_may_not_delete_a_dispatched_order()
{
    var user = new ClaimsPrincipal(new ClaimsIdentity(
        [new Claim(ClaimTypes.NameIdentifier, "42")], "test"));

    var order = new Order { CustomerId = 42, Status = OrderStatus.Dispatched };

    var context = new AuthorizationHandlerContext(
        [OrderOperations.Delete], user, order);

    await new OrderOwnerHandler().HandleAsync(context);

    Assert.False(context.HasSucceeded);
}
// This is the payoff of policies over inline role checks: the RULE is a unit
// under test, in milliseconds, with no pipeline. An inline
// `if (User.IsInRole(...))` inside an action can only be tested through HTTP.

// ── INTEGRATION-TEST THE WIRING ──────────────────────────────────────────
// Unit tests prove the rule; only an integration test proves it is ATTACHED.
[Theory]
[InlineData(null,      HttpStatusCode.Unauthorized)]   // anonymous
[InlineData("user",    HttpStatusCode.Forbidden)]      // authenticated, wrong role
[InlineData("admin",   HttpStatusCode.NoContent)]      // permitted
public async Task Delete_enforces_authorization(string? role, HttpStatusCode expected)
{
    var client = _factory.CreateClient();
    if (role is not null)
    {
        client.DefaultRequestHeaders.Add("X-Test-User", "1");
        client.DefaultRequestHeaders.Add("X-Test-Role", role);
    }

    var response = await client.DeleteAsync("/api/orders/1");
    Assert.Equal(expected, response.StatusCode);
}
// The FIRST row is the one that catches a deleted [Authorize] or a
// misordered pipeline. The SECOND catches an endpoint that checks
// "authenticated" where it meant "is an admin" — a distinction no
// happy-path test exercises.

// ── AUDIT DENIALS, NOT JUST FAILURES ─────────────────────────────────────
public sealed class AuditingAuthorizationMiddlewareResultHandler(
    ILogger<AuditingAuthorizationMiddlewareResultHandler> log)
    : IAuthorizationMiddlewareResultHandler
{
    private readonly AuthorizationMiddlewareResultHandler _default = new();

    public async Task HandleAsync(RequestDelegate next, HttpContext context,
        AuthorizationPolicy policy, PolicyAuthorizationResult result)
    {
        if (result.Forbidden)
            log.LogWarning(
                "Authorization denied. User {User} endpoint {Endpoint}",
                context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value,
                context.GetEndpoint()?.DisplayName);

        await _default.HandleAsync(next, context, policy, result);
    }
}
builder.Services.AddSingleton<IAuthorizationMiddlewareResultHandler,
    AuditingAuthorizationMiddlewareResultHandler>();
// A spike in denials for one user is a strong signal — either an attacker
// probing, or a legitimate permissions bug affecting real work. Both are
// worth knowing about, and neither appears in the error rate because a 403 is
// a successful, correct response.

Interview Questions

Beginner: What is the difference between role-based and policy-based authorization?

Role-based checks assert that the user holds a named role, written directly at the endpoint as [Authorize(Roles = "admin")]. Policy-based authorization names the rule instead — [Authorize(Policy = "CanDeleteOrders")] — and the policy definition decides what satisfies it, whether that is a role, a claim, or arbitrary logic in a handler. The practical benefit is indirection: the endpoint declares the capability it needs, so changing who has that capability is one edit in one place rather than a search across every endpoint. Policies also express things roles cannot, such as combining claims, consulting a service, or evaluating the specific resource being accessed.

Beginner: What does a fallback policy do?

It applies to any endpoint that has no authorization metadata of its own — no [Authorize] and no [AllowAnonymous]. Setting it to require an authenticated user inverts the default so endpoints are protected unless they explicitly opt out, which closes the most common authorization hole: a new controller or endpoint where someone simply forgot the attribute. That failure mode is dangerous precisely because it looks like correct code and no test fails. It differs from the default policy, which is what a bare [Authorize] with no named policy resolves to.

Mid: In a custom handler, when should you call context.Fail()?

Rarely — only when the denial must be absolute. Handlers are additive: a requirement is satisfied if any registered handler calls Succeed, so a handler that cannot evaluate a particular case should simply return without doing anything, leaving the decision to another handler. Fail() is a hard veto that no later handler can override, so calling it when you merely lack an opinion breaks composition — the symptom is authorization that works until a second handler is added for the same requirement, at which point the OR silently becomes impossible. Legitimate uses are things like a suspended account or a compliance block, where no other rule should be able to grant access.

Mid: Why can't an attribute policy express "the user may edit this specific order"?

Because attribute-based authorization runs before the action executes, at which point the resource has not been loaded — the framework knows the route values but not the entity they identify, nor its owner or state. Resource-based authorization solves this by being invoked imperatively inside the action after loading the entity, passing it to IAuthorizationService.AuthorizeAsync along with an operation requirement, so the handler can compare the resource's owner against the current user and consider its state. The trade-off is that it only runs where it is called, so it protects the HTTP path and nothing else — durable data isolation belongs at the query layer, with the resource handler as defence in depth.

Senior: A protected endpoint serves anonymous users in production but is correctly protected locally. Diagnose.

The leading candidate is middleware ordering — UseAuthorization registered before UseRouting. Authorization decides by reading the matched endpoint's metadata, so if it runs before routing has selected an endpoint there is no metadata, nothing to enforce, and the request is permitted. What makes it dangerous is that it fails open with no exception and no log entry, so every authenticated test still passes and only an unauthenticated request reveals it. The environment split usually comes from a conditional pipeline — an if (env.IsDevelopment()) branch registering middleware in a different order, or a development-only authentication stub that supplies an identity so the missing check is invisible locally. I would confirm by issuing an unauthenticated request against each environment and by checking context.GetEndpoint() inside the authorization middleware to prove whether a match exists at that point. The durable fixes are one unconditional pipeline order with environment differences expressed as configuration rather than as different Use sequences, a fallback policy so endpoints are protected by default, and an integration test asserting 401 for an anonymous call — the test that would have caught it. I would also add denial logging, since the absence of any 403s in production telemetry for a supposedly protected endpoint is itself the signal that nothing is being enforced.

Senior: Design authorization for a multi-tenant SaaS with per-tenant roles and resource ownership.

I would layer it, because each layer fails differently and no single one is sufficient. The outermost layer is a fallback policy requiring an authenticated user, so a new endpoint is protected by default and being public is an explicit, reviewable opt-out. Next, tenant isolation: the tenant identifier is structural in the route, and a requirement compares that route value against the tenant claim in the token, because a route value is client-supplied and binding it proves nothing — without that comparison, changing a GUID in the URL reads another customer's data. Then per-tenant roles, which I would model as claims scoped to the tenant rather than global roles, since "admin" means administrator of a tenant and a global role claim silently grants it everywhere. Resource ownership goes in resource-based handlers invoked after loading the entity, so rules can depend on both the caller and the record's state — an owner may delete a draft order but not a dispatched one. Underneath all of it, the durable enforcement is a global query filter scoping every query by tenant, because the layers above only run on the HTTP path and a background job, message handler or future GraphQL resolver bypasses them entirely; with the filter, a missing check returns no rows rather than another tenant's rows. On the staleness question I would keep permissions in short-lived tokens and accept a bounded revocation window, documenting it, rather than paying a database lookup per request — or cache a per-request permission load for thirty seconds, which gets most of the performance with a window I can state precisely. For verification, handlers get unit tests since they are pure functions of principal and resource, and integration tests assert the anonymous 401 and the under-privileged 403, because those are the cases that catch a detached attribute or a misordered pipeline. Finally I would log every denial with the user and endpoint, since a spike is either probing or a real permissions regression, and neither shows up in the error rate — a 403 is a correct response.

3 (medium): Write a requirement and handler for "subscription is active", allowing an admin override.
Solution 
public sealed class ActiveSubscriptionRequirement : IAuthorizationRequirement;

// HANDLER 1 — the normal case.
public sealed class ActiveSubscriptionHandler(
    ISubscriptionService subscriptions, TimeProvider clock)
    : AuthorizationHandler<ActiveSubscriptionRequirement>
{
    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context, ActiveSubscriptionRequirement requirement)
    {
        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
        if (userId is null) return;          // no opinion — NOT Fail()

        var subscription = await subscriptions.GetAsync(userId);
        if (subscription?.ExpiresAt > clock.GetUtcNow())
            context.Succeed(requirement);
        // otherwise stay silent: the admin handler may still approve
    }
}

// HANDLER 2 — the override, registered for the SAME requirement.
public sealed class AdminSubscriptionOverrideHandler
    : AuthorizationHandler<ActiveSubscriptionRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, ActiveSubscriptionRequirement requirement)
    {
        if (context.User.IsInRole("admin"))
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}

builder.Services.AddScoped<IAuthorizationHandler, ActiveSubscriptionHandler>();
builder.Services.AddScoped<IAuthorizationHandler, AdminSubscriptionOverrideHandler>();

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("ActiveSubscription", policy =>
        policy.Requirements.Add(new ActiveSubscriptionRequirement()));

// THE KEY DESIGN POINT: neither handler calls Fail(). Because a requirement
// is satisfied when ANY handler succeeds, two silent handlers compose into an
// OR. If ActiveSubscriptionHandler called Fail() on an expired subscription,
// the admin override could never take effect — Fail() cannot be undone.
//
// Note the handlers are SCOPED, not singleton, because one depends on a
// scoped ISubscriptionService.
4 (medium): Implement resource-based authorization so a user edits only their own draft orders.
Solution 
public static class OrderOperations
{
    public static readonly OperationAuthorizationRequirement Edit = new() { Name = "Edit" };
}

public sealed class OrderEditHandler
    : AuthorizationHandler<OperationAuthorizationRequirement, Order>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        OperationAuthorizationRequirement requirement,
        Order order)
    {
        if (requirement.Name != OrderOperations.Edit.Name)
            return Task.CompletedTask;

        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

        // BOTH conditions: ownership AND a state rule.
        if (order.CustomerId.ToString() == userId
            && order.Status == OrderStatus.Draft)
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}
builder.Services.AddSingleton<IAuthorizationHandler, OrderEditHandler>();

[HttpPut("{id:int}")]
public async Task<IActionResult> Update(
    int id, UpdateOrder request,
    IAuthorizationService authorization, CancellationToken ct)
{
    var order = await db.Orders.FindAsync([id], ct);
    if (order is null) return NotFound();

    var result = await authorization.AuthorizeAsync(User, order, OrderOperations.Edit);

    // 404 rather than 403: a 403 would confirm the order EXISTS, letting an
    // attacker enumerate valid ids. Log the real reason server-side.
    if (!result.Succeeded)
    {
        logger.LogWarning("Edit denied for order {OrderId} user {UserId}",
            id, User.FindFirst(ClaimTypes.NameIdentifier)?.Value);
        return NotFound();
    }

    order.Apply(request);
    await db.SaveChangesAsync(ct);
    return NoContent();
}

// WHY IMPERATIVE: the rule depends on the LOADED order's owner and status,
// neither of which exists when attribute authorization runs.
5 (hard): A tenant id comes from the route. Prevent cross-tenant access at every layer.
Solution 
// ── LAYER 1: STRUCTURAL — the tenant is in the template, on a group ──────
var tenant = app.MapGroup("/tenants/{tenantId:guid}")
    .RequireAuthorization("SameTenant");
// Every endpoint under the group binds tenantId and inherits the check, so a
// new endpoint cannot forget it.

// ── LAYER 2: AUTHORIZED, not merely bound ────────────────────────────────
// A route value is CLIENT-SUPPLIED. Binding it proves nothing.
public sealed class SameTenantRequirement : IAuthorizationRequirement;

public sealed class SameTenantHandler(IHttpContextAccessor accessor)
    : AuthorizationHandler<SameTenantRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, SameTenantRequirement requirement)
    {
        var routeTenant = accessor.HttpContext?
            .Request.RouteValues["tenantId"]?.ToString();
        var claimTenant = context.User.FindFirst("tenant_id")?.Value;

        if (routeTenant is not null && claimTenant is not null
            && string.Equals(routeTenant, claimTenant, StringComparison.OrdinalIgnoreCase))
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("SameTenant", p => p.Requirements.Add(new SameTenantRequirement()));

// ── LAYER 3: THE DATA LAYER — the only one that holds everywhere ─────────
public sealed class AppDbContext(DbContextOptions options, ITenantContext tenant)
    : DbContext(options)
{
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(o => o.TenantId == tenant.CurrentTenantId);
        modelBuilder.Entity<Customer>()
            .HasQueryFilter(c => c.TenantId == tenant.CurrentTenantId);
    }
}
// Now a query for another tenant's order returns NOTHING, on EVERY code path
// — including the background job and the message handler that never touch
// layers 1 and 2.

// ── WHY ALL THREE ────────────────────────────────────────────────────────
// Each fails differently, which is the point:
//   • the group is bypassed by a new endpoint declared outside it
//   • the policy is bypassed by anything with no HttpContext (jobs, consumers)
//   • the query filter catches both — but is itself bypassable with
//     IgnoreQueryFilters(), and does not stop a WRITE to another tenant's row
//
// One mistake should never be sufficient to leak data across tenants.

6 (hard): Design permission-based authorization where permissions are stored in a database and change at runtime.
Solution 
// ── THE PROBLEM: policies are registered at STARTUP, but permissions live in
//    a database and change while the app runs. Registering every permission
//    by hand does not scale and cannot handle new ones.

// ── 1. A DYNAMIC POLICY PROVIDER — invents policies on demand ────────────
public sealed class PermissionPolicyProvider(IOptions<AuthorizationOptions> options)
    : DefaultAuthorizationPolicyProvider(options)
{
    public override async Task<AuthorizationPolicy?> GetPolicyAsync(string name)
    {
        if (await base.GetPolicyAsync(name) is { } registered)
            return registered;                        // explicit policies win

        if (name.StartsWith("permission:", StringComparison.Ordinal))
            return new AuthorizationPolicyBuilder()
                .RequireAuthenticatedUser()
                .AddRequirements(new PermissionRequirement(name["permission:".Length..]))
                .Build();

        return null;
    }
}
builder.Services.AddSingleton<IAuthorizationPolicyProvider, PermissionPolicyProvider>();

// Usage needs no registration per permission:
[Authorize(Policy = "permission:orders.delete")]

// ── 2. THE REQUIREMENT AND HANDLER ───────────────────────────────────────
public sealed class PermissionRequirement(string permission) : IAuthorizationRequirement
{
    public string Permission { get; } = permission;
}

public sealed class PermissionHandler(
    IPermissionService permissions, HybridCache cache)
    : AuthorizationHandler<PermissionRequirement>
{
    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context, PermissionRequirement requirement)
    {
        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
        if (userId is null) return;

        // CACHED BRIEFLY — the staleness window is a deliberate, stated
        // trade-off, not an accident.
        var granted = await cache.GetOrCreateAsync(
            $"permissions:{userId}",
            async ct => await permissions.GetForUserAsync(userId, ct),
            new HybridCacheEntryOptions { Expiration = TimeSpan.FromSeconds(30) });

        if (granted.Contains(requirement.Permission))
            context.Succeed(requirement);
    }
}

// ── 3. THE STALENESS DECISION, STATED EXPLICITLY ─────────────────────────
//   permissions IN THE TOKEN   → zero lookups, but revocation waits for token
//                                expiry. With 8-hour tokens, unacceptable.
//   per-request DB lookup      → always fresh, one query per request
//   30-SECOND CACHE (chosen)   → ~1 query per user per 30s, and revocation
//                                takes effect within 30 seconds
//
// I would state that window in the security documentation. "Access is revoked
// within 30 seconds" is a defensible answer during an incident; "within 8
// hours" is not.

// ── 4. IMMEDIATE REVOCATION for the cases that need it ───────────────────
public async Task RevokeAsync(string userId, string permission, CancellationToken ct)
{
    await permissions.RevokeAsync(userId, permission, ct);
    await cache.RemoveAsync($"permissions:{userId}", ct);   // ← evict now
}
// Combined with an eviction message to other instances (see the Caching
// lesson), revocation becomes effectively immediate while the cache still
// absorbs normal traffic.

// ── 5. AUDIT ─────────────────────────────────────────────────────────────
// Log every denial with user, permission and endpoint. A denial spike is
// either probing or a permissions regression breaking real work — and neither
// appears in the error rate, because 403 is a correct response.

🎯 Key Takeaways

  • Policies name the capability an endpoint needs; roles name who holds it. The indirection is what makes rules changeable in one place.
  • A requirement is the question and a handler is the answer — handlers compose additively, so several can satisfy one requirement as an OR.
  • Returning without succeeding means "no opinion"; context.Fail() is an unrecoverable veto and is usually a bug.
  • Attribute policies cannot see the resource — resource-based authorization is invoked imperatively after loading the entity.
  • Set a fallback policy so endpoints are protected by default and being public is an explicit, reviewable opt-out.
  • UseAuthorization before UseRouting defeats every mechanism here by failing open with no error.
  • The scope claim is a space-delimited string, so RequireClaim with a single value fails on multi-scope tokens.
  • A tenant id from the route is client-supplied — compare it against the token claim, and scope queries at the data layer too.
  • Prefer 404 over 403 where a 403 would confirm a resource exists, and log the real reason server-side.
  • Unit-test handlers directly and integration-test the anonymous 401 and under-privileged 403 — the two cases that catch fail-open bugs.
