Controllers & MVC Building APIs

What you'll master: what [ApiController] actually turns on, the ControllerBase surface worth knowing, action results and their typed equivalents, keeping controllers thin enough to test, and an honest comparison with minimal APIs including when each is the right call. Prerequisites: Routing, Model Binding & Validation and Dependency Injection.

Part 1 — What [ApiController] Actually Does

[ApiController]
[Route("api/[controller]")]              // → /api/products
public sealed class ProductsController(IProductService products) : ControllerBase
{
    [HttpGet("{id:int}")]
    public async Task<ActionResult<Product>> Get(int id, CancellationToken ct)
    {
        var product = await products.FindAsync(id, ct);
        return product is null ? NotFound() : Ok(product);
    }
}

// The attribute is not decoration — it enables FIVE distinct behaviours, and
// knowing which is which explains most "why does this work differently in
// minimal APIs" questions:
//
// 1. AUTOMATIC 400 ON INVALID MODELSTATE
//    Data annotations run and a failing model short-circuits with a
//    ValidationProblemDetails BEFORE the action body executes. This is why
//    `if (!ModelState.IsValid) return BadRequest(ModelState);` is redundant
//    in an [ApiController] — and why removing the attribute silently disables
//    validation everywhere.
//
// 2. BINDING SOURCE INFERENCE
//    Complex types → body, simple types → route/query, IFormFile → form.
//    Without it, every parameter needs an explicit [FromBody]/[FromQuery].
//
// 3. ATTRIBUTE ROUTING REQUIRED
//    Conventional routes (MapControllerRoute) no longer apply to this
//    controller. Every action needs an [HttpGet]/[HttpPost] template.
//
// 4. PROBLEM DETAILS FOR ERROR STATUS CODES
//    NotFound(), BadRequest() etc. produce RFC 9457 bodies instead of empty
//    responses.
//
// 5. MULTIPART/FORM-DATA INFERENCE for IFormFile parameters.

// Turning off just the automatic 400, when you want to shape the response:
builder.Services.Configure<ApiBehaviorOptions>(o =>
{
    o.SuppressModelStateInvalidFilter = true;       // you now handle it
    // or customise the response while keeping the behaviour:
    o.InvalidModelStateResponseFactory = context =>
        new BadRequestObjectResult(new ValidationProblemDetails(context.ModelState)
        {
            Instance = context.HttpContext.Request.Path,
            Extensions = { ["traceId"] = Activity.Current?.Id }
        });
});

// ControllerBase vs Controller — pick the right base class:
//   ControllerBase   API controllers. No view support. Use this for JSON APIs.
//   Controller       adds View(), ViewBag, ViewData, PartialView — MVC with
//                    server-rendered Razor views.
// Inheriting Controller for a JSON API drags in view-engine machinery you
// never use and invites someone to return View() by accident.

Part 2 — Action Results and Their Typed Forms

// THREE return styles, in increasing order of what the compiler and OpenAPI
// can see:

// 1. IActionResult — flexible, opaque. OpenAPI infers nothing.
[HttpGet("{id:int}")]
public async Task<IActionResult> Get(int id)
{
    var p = await products.FindAsync(id);
    return p is null ? NotFound() : Ok(p);
}

// 2. ActionResult<T> — the sweet spot for controllers. Carries the success
//    type AND allows any result. Implicit conversion means you can return the
//    value directly.
[HttpGet("{id:int}")]
[ProducesResponseType<Product>(StatusCodes.Status200OK)]
[ProducesResponseType(StatusCodes.Status404NotFound)]
public async Task<ActionResult<Product>> Get(int id, CancellationToken ct)
{
    var p = await products.FindAsync(id, ct);
    if (p is null) return NotFound();
    return p;                     // implicit conversion to Ok(p)
}

// 3. Results<T1, T2> — the minimal-API union, also usable in controllers.
//    The compiler ENFORCES that every path returns a declared result, and
//    OpenAPI needs no attributes at all.
[HttpGet("{id:int}")]
public async Task<Results<Ok<Product>, NotFound>> Get(int id, CancellationToken ct)
    => await products.FindAsync(id, ct) is { } p
        ? TypedResults.Ok(p)
        : TypedResults.NotFound();

// THE HELPERS WORTH KNOWING, and the ones people get wrong:
Ok(value);                             // 200
Created($"/api/products/{id}", p);     // 201 + Location
CreatedAtAction(nameof(Get), new { id }, p);   // 201, URL from the ROUTE
NoContent();                           // 204 — correct for PUT/DELETE
NotFound();                            // 404
BadRequest(ModelState);                // 400 + validation errors
ValidationProblem(ModelState);         // 400 + problem details (preferred)
Conflict();                            // 409
Unauthorized();                        // 401 — unauthenticated
Forbid();                              // 403 — authenticated, not allowed
Problem(detail, statusCode: 502);      // arbitrary problem details
File(stream, "application/pdf", "invoice.pdf");

// CreatedAtAction over a hand-built string: it generates the URL from the
// route table, so renaming the route updates the Location header. The
// interpolated version compiles fine and rots silently.
//
// Forbid() vs Unauthorized() is the same 401/403 distinction as everywhere:
// Forbid() also invokes the authentication scheme's forbid handler, which may
// redirect for cookie auth — that is usually what you want and occasionally
// surprising in an API, where you may prefer StatusCode(403).
Key insight: ActionResult<T> exists to solve a specific typing problem: a method returning Task<Product> cannot also return NotFound(), and one returning Task<IActionResult> loses the success type that OpenAPI and tests want. ActionResult<T> is a union of the two, with an implicit conversion so return product; just works. Reach for it as the controller default; reach for Results<T1,T2> when you want the compiler to enforce the full set of outcomes rather than trusting [ProducesResponseType] attributes to stay accurate.

Part 3 — Keeping Controllers Thin

// ✗ THE CONTROLLER THAT BECAME THE APPLICATION:
[HttpPost]
public async Task<IActionResult> Create(CreateOrderRequest request)
{
    if (request.Items.Count == 0) return BadRequest("Empty order.");

    var customer = await _db.Customers.FindAsync(request.CustomerId);
    if (customer is null) return NotFound();
    if (customer.IsSuspended) return Forbid();

    decimal total = 0;
    foreach (var item in request.Items)
    {
        var product = await _db.Products.FindAsync(item.ProductId);
        if (product is null) return BadRequest($"Unknown product {item.ProductId}.");
        if (product.Stock < item.Quantity) return Conflict("Insufficient stock.");
        product.Stock -= item.Quantity;
        total += product.Price * item.Quantity;
    }

    if (total > customer.CreditLimit) return Conflict("Credit limit exceeded.");
    // ...30 more lines, a transaction, an email, an audit entry
}
// THE PROBLEMS, concretely:
//   • the stock and credit rules exist ONLY here, so a background importer or
//     a message handler creating an order bypasses every one of them
//   • testing "credit limit exceeded" requires an HTTP request, a DbContext
//     and a full pipeline — so it does not get tested
//   • the transaction boundary is implicit and easy to get wrong

// ✓ THIN CONTROLLER — bind, delegate, map the outcome:
[HttpPost]
[ProducesResponseType<OrderResponse>(StatusCodes.Status201Created)]
[ProducesResponseType(StatusCodes.Status409Conflict)]
public async Task<ActionResult<OrderResponse>> Create(
    CreateOrderRequest request, CancellationToken ct)
{
    var result = await _orders.CreateAsync(request.ToCommand(), ct);

    return result switch
    {
        { IsSuccess: true } => CreatedAtAction(
            nameof(Get), new { id = result.Value.Id }, result.Value.ToResponse()),
        { Error: OrderError.CustomerNotFound } => NotFound(),
        { Error: OrderError.InsufficientStock } => Conflict(result.Message),
        { Error: OrderError.CreditExceeded }    => Conflict(result.Message),
        _ => Problem()
    };
}
// The domain rules now live in OrderService, where a queue consumer reaches
// them too, and where they are unit-testable with no HTTP involved.

// THE RESULT-VS-EXCEPTION DECISION, since both appear in real codebases:
//   RESULT OBJECTS      expected outcomes the caller must handle —
//                       insufficient stock, credit exceeded. Explicit in the
//                       signature, no stack-unwinding cost, and the compiler
//                       reminds you to handle the cases.
//   EXCEPTIONS          genuinely exceptional — a database is unreachable,
//                       an invariant was violated. Handled centrally by the
//                       exception handler chain.
// Using exceptions for ordinary business outcomes makes control flow invisible
// and is measurably slower on hot paths; using results for infrastructure
// failures forces every layer to propagate them manually. Mixing them is fine
// as long as the RULE is written down and followed.

Part 4 — Conventions, Areas, and Model Binding Details

// TOKEN REPLACEMENT in route templates keeps routes in sync with names:
[Route("api/[controller]")]      // ProductsController → api/products
[Route("api/v{version:apiVersion}/[controller]/[action]")]
// [controller] strips the "Controller" suffix. Renaming the class renames the
// route — which is either convenient or a silent breaking change, so prefer
// literal routes on public APIs where the URL is a contract.

// ACTION SELECTION when several actions could match. Constraints disambiguate:
[HttpGet("{id:int}")]     public IActionResult GetById(int id) => ...;
[HttpGet("{slug}")]       public IActionResult GetBySlug(string slug) => ...;
// The int constraint makes these unambiguous. Without it → AmbiguousMatch at
// request time, not startup.

// [NonAction] excludes a public method from action discovery:
[NonAction]
public string BuildKey(int id) => $"product:{id}";
// Without it, every public method on a controller is a candidate action —
// a helper method becomes an accidentally routable endpoint.

// [ActionName] decouples the method name from the route:
[HttpGet("latest")]
[ActionName("GetLatest")]
public IActionResult Latest() => ...;
// Matters because CreatedAtAction(nameof(...)) resolves by ACTION name, so a
// mismatch produces a null Location header — silently, not as an error.

// APPLICATION MODEL CONVENTIONS — apply a rule across every controller
// without touching each one:
public sealed class ApiPrefixConvention : IApplicationModelConvention
{
    public void Apply(ApplicationModel application)
    {
        foreach (var controller in application.Controllers)
            foreach (var selector in controller.Selectors)
                selector.AttributeRouteModel = AttributeRouteModel.CombineAttributeRouteModel(
                    new AttributeRouteModel(new RouteAttribute("api")),
                    selector.AttributeRouteModel);
    }
}
builder.Services.AddControllers(o => o.Conventions.Add(new ApiPrefixConvention()));
// Powerful and easy to overuse: a convention changes routing for controllers
// whose source shows no sign of it. Worth it for genuinely global rules,
// harmful as a substitute for being explicit.

// AREAS — a folder-level grouping for large MVC apps:
[Area("Admin")]
[Route("[area]/[controller]")]
public class UsersController : ControllerBase { }   // → /Admin/Users
// Largely a Razor-era feature. For APIs, route groups or a versioned prefix
// express the same intent with less machinery.

Part 5 — Testing Controllers

// A thin controller is a UNIT-TESTABLE controller: construct it directly, pass
// a fake service, assert on the returned ActionResult. No HTTP, no container.
[Fact]
public async Task Get_returns_404_when_missing()
{
    var products = Substitute.For<IProductService>();
    products.FindAsync(42, Arg.Any<CancellationToken>()).Returns((Product?)null);

    var controller = new ProductsController(products);

    var result = await controller.Get(42, default);

    Assert.IsType<NotFoundResult>(result.Result);
}

[Fact]
public async Task Get_returns_the_product()
{
    var expected = new Product { Id = 42, Name = "Widget" };
    var products = Substitute.For<IProductService>();
    products.FindAsync(42, Arg.Any<CancellationToken>()).Returns(expected);

    var result = await new ProductsController(products).Get(42, default);

    // ActionResult<T> puts the value in .Value when returned directly, and in
    // .Result when returned via Ok(). Checking both is what trips people up:
    var ok = Assert.IsType<OkObjectResult>(result.Result);
    Assert.Same(expected, ok.Value);
}

// WHEN A CONTROLLER NEEDS HttpContext — supply a fake one rather than a
// full pipeline:
var controller = new ProductsController(products)
{
    ControllerContext = new ControllerContext
    {
        HttpContext = new DefaultHttpContext
        {
            User = new ClaimsPrincipal(new ClaimsIdentity(
                [new Claim(ClaimTypes.NameIdentifier, "user-1")], "test"))
        }
    }
};

// WHAT UNIT TESTS CANNOT COVER — and therefore what integration tests must:
//   • routing: does the URL actually reach this action
//   • model binding: does the request shape bind to these parameters
//   • filters: does [Authorize] actually reject an anonymous caller
//   • the [ApiController] automatic 400
// All of those are pipeline behaviour, and a unit test calling the method
// directly bypasses every one of them. A controller unit test that passes
// proves the LOGIC is right, never that the endpoint is reachable or
// protected — which is exactly the gap that lets an unprotected endpoint
// ship with green tests.

Part 6 — Controllers or Minimal APIs?

// They produce the SAME endpoint objects, so filters, authorization, CORS and
// OpenAPI work identically. The choice is about ergonomics, not capability.

// ── CHOOSE CONTROLLERS WHEN ──────────────────────────────────────────────
//   • the app renders server-side views (Razor) — minimal APIs have no View()
//   • [ApiController]'s automatic validation and binding inference carry real
//     weight for a large team, and you do not want to wire it per endpoint
//   • an existing large MVC codebase whose conventions the team relies on
//   • you want related actions grouped by class with shared constructor
//     dependencies injected once
//   • model binding needs full form-post semantics (nested objects,
//     collection indexing) — minimal APIs' form support is basic

// ── CHOOSE MINIMAL APIS WHEN ─────────────────────────────────────────────
//   • a new JSON API — this is the 2026 default
//   • startup time and per-request overhead matter (binding is
//     source-generated, not reflective)
//   • NativeAOT is a target — controllers are not AOT-friendly
//   • you want route groups declaring auth and filters once per feature area
//     rather than attributes repeated per action

// ── THEY COEXIST ─────────────────────────────────────────────────────────
app.MapControllers();          // existing controllers keep working
app.MapProductEndpoints();     // new features as minimal APIs
// This is what makes migration incremental rather than a rewrite: both
// register into the same endpoint data source, share the same pipeline, and
// appear in the same OpenAPI document.

// THE DECISION THAT ACTUALLY MATTERS is neither of these. If handlers are
// thin — bind, delegate to an application service, map the outcome — then the
// hosting style is a surface concern and switching costs an afternoon. If
// business logic lives inside controllers, the choice is baked into the
// domain and migration means a rewrite. Optimise for thin handlers and the
// controllers-versus-minimal question stops being expensive.

Interview Questions

Beginner: What does the [ApiController] attribute do?

It enables a set of API-specific behaviours: automatic 400 responses when ModelState is invalid, so validation runs before the action body; binding source inference, so complex types come from the body and simple types from the route or query without explicit attributes; a requirement that routing be attribute-based rather than conventional; problem-details bodies for error status codes; and form-data inference for file uploads. The practical consequence worth remembering is that removing the attribute silently disables model validation across the whole controller — the code still compiles and the actions still run, they just stop rejecting invalid input.

Beginner: What is the difference between ControllerBase and Controller?

ControllerBase provides everything an API needs: the action-result helpers like Ok, NotFound and CreatedAtAction, plus access to HttpContext, User and ModelState. Controller derives from it and adds view support — View(), ViewBag, ViewData, PartialView — for server-rendered Razor pages. For a JSON API you want ControllerBase, because inheriting Controller pulls in view-engine machinery that is never used and makes it possible to return a view from an API by accident.

Mid: When would you use ActionResult<T> over IActionResult?

Almost always, for API actions. IActionResult is opaque: the signature says nothing about what a success returns, so OpenAPI cannot document the response shape without [ProducesResponseType] attributes that must be maintained by hand and silently drift. ActionResult<T> is a union of the success type and any action result, so the success shape is visible to tooling and to readers, and an implicit conversion lets you return product; directly while still being able to return NotFound();. The step beyond it is Results<Ok<T>, NotFound>, which additionally makes the compiler enforce that every path returns one of the declared outcomes — so adding an unhandled branch is a build error rather than an undocumented response.

Mid: Why is a passing controller unit test not evidence that an endpoint is secure?

Because a unit test constructs the controller and calls the method directly, which bypasses the entire request pipeline. Routing never runs, so the test does not prove the action is reachable at the expected URL. Model binding never runs, so it does not prove the request shape binds to those parameters. And crucially filters never run, so [Authorize], the automatic [ApiController] 400, and any custom action filters are all absent — an action decorated with [Authorize] and one with the attribute deleted behave identically under unit test. Security and binding are pipeline behaviours, so they need integration tests through WebApplicationFactory that issue real requests, including an anonymous one asserting 401.

Senior: A controller has grown to 800 lines with business rules inline. Walk through refactoring it.

I would start by separating the three responsibilities tangled together: HTTP concerns, application orchestration, and domain rules. The first move is to extract the orchestration into an application service per use case, taking a command object and returning a result — at this stage a mechanical extraction, no behaviour change, so it is safe to do incrementally under existing tests. That immediately makes the rules reachable from other entry points, which matters because the reason inline rules are dangerous is not aesthetics: a background importer or message handler creating an order bypasses every check that lives only in the controller. Next I would push genuine invariants down into the domain — stock cannot go negative, an order cannot be cancelled after dispatch — so they hold wherever the entity is used rather than only on the path that happens to run this code. The controller then becomes bind, delegate, map: a switch over the result mapping each outcome to a status code. On results versus exceptions I would use result objects for expected business outcomes so they are explicit in the signature and the compiler prompts handling, and exceptions only for genuinely exceptional infrastructure failures handled centrally. Sequencing matters for safety: I would add integration tests characterising current behaviour at the HTTP boundary first, because those keep passing through every subsequent step and are the only thing proving the refactor is behaviour-preserving; unit tests come after extraction, when there are units worth testing. I would also watch for hidden transaction boundaries, since inline code often relies on one implicit SaveChanges at the end, and splitting it across services can accidentally turn one atomic operation into several.

Senior: Your team is starting a new service and debating controllers versus minimal APIs. How do you frame the decision?

I would first establish that this is a lower-stakes decision than it feels, because both produce the same endpoint objects and share the same pipeline — filters, authorization, CORS and OpenAPI behave identically, and the two coexist in one application, so an incremental migration either direction is genuinely viable rather than all-or-nothing. For a new JSON API I would default to minimal APIs: source-generated binding rather than reflection gives lower per-request overhead and faster startup, NativeAOT is available, and route groups let authorization and filters be declared once per feature area instead of repeated as attributes where one omission is an unprotected endpoint. I would choose controllers if the service renders Razor views, if the team is large enough that [ApiController]'s automatic validation and binding inference meaningfully reduce per-endpoint mistakes, or if there is an existing MVC codebase whose conventions people already know — consistency with a large existing surface usually beats a marginal technical edge. The gaps to price in for minimal APIs are that validation is not automatic, there is no view rendering, and there is no base-controller inheritance, so shared behaviour comes from filters and groups rather than a base class. But I would steer the discussion to what actually determines cost, which is neither option: if handlers stay thin — bind, delegate to an application service, map the outcome — the hosting style is a surface concern and reversing the decision is an afternoon's work. If business logic accumulates inside handlers or controllers, the choice becomes structural and switching means a rewrite. So I would spend the team's attention on the layering rule and treat the controllers-versus-minimal question as a default to be set once and not relitigated per feature.

3 (medium): Refactor an action containing stock and credit-limit checks so those rules are reachable from a background importer.
Solution 
// 1. The rules move into an application service returning a RESULT.
public sealed class OrderService(AppDbContext db, IStockPolicy stock)
{
    public async Task<Result<Order, OrderError>> CreateAsync(
        CreateOrderCommand command, CancellationToken ct)
    {
        var customer = await db.Customers.FindAsync([command.CustomerId], ct);
        if (customer is null) return OrderError.CustomerNotFound;
        if (customer.IsSuspended) return OrderError.CustomerSuspended;

        var order = new Order(customer.Id);
        foreach (var line in command.Items)
        {
            var product = await db.Products.FindAsync([line.ProductId], ct);
            if (product is null) return OrderError.UnknownProduct;

            // Invariant enforced on the ENTITY, so it holds for every caller.
            if (!product.TryReserve(line.Quantity))
                return OrderError.InsufficientStock;

            order.AddLine(product, line.Quantity);
        }

        if (order.Total > customer.CreditLimit) return OrderError.CreditExceeded;

        db.Orders.Add(order);
        await db.SaveChangesAsync(ct);   // ONE transaction for the whole unit
        return order;
    }
}

// 2. The controller becomes bind → delegate → map.
[HttpPost]
public async Task<ActionResult<OrderResponse>> Create(
    CreateOrderRequest request, CancellationToken ct)
{
    var result = await orders.CreateAsync(request.ToCommand(), ct);

    return result.Error switch
    {
        null                          => CreatedAtAction(nameof(Get),
                                            new { id = result.Value!.Id },
                                            result.Value.ToResponse()),
        OrderError.CustomerNotFound   => NotFound(),
        OrderError.CustomerSuspended  => Forbid(),
        OrderError.UnknownProduct     => BadRequest("Unknown product."),
        OrderError.InsufficientStock  => Conflict("Insufficient stock."),
        OrderError.CreditExceeded     => Conflict("Credit limit exceeded."),
        _                             => Problem()
    };
}

// 3. The importer calls the SAME service, so every rule applies:
await orderService.CreateAsync(command, ct);

4 (medium): Two actions both match GET /api/products/latest. Diagnose and fix.
Solution 
// THE COLLISION:
[HttpGet("{id}")]        public IActionResult Get(string id) => ...;
[HttpGet("latest")]      public IActionResult Latest() => ...;

// GET /api/products/latest matches BOTH — "latest" is a valid string id.
// Routing precedence says a literal segment beats a parameter, so "latest"
// actually wins here. The genuine ambiguity appears when the parameter is
// unconstrained AND another action is equally specific:
[HttpGet("{id}")]        public IActionResult Get(string id) => ...;
[HttpGet("{slug}")]      public IActionResult BySlug(string slug) => ...;
// → AmbiguousMatchException, at REQUEST time, not startup.

// FIX — constrain so the templates are genuinely distinguishable:
[HttpGet("{id:int}")]           public IActionResult Get(int id) => ...;
[HttpGet("{slug:regex(^[a-z0-9-]+$)}")]
                                public IActionResult BySlug(string slug) => ...;
[HttpGet("latest")]             public IActionResult Latest() => ...;

// Now:
//   /api/products/42       → Get       (int constraint)
//   /api/products/blue-hat → BySlug    (slug pattern)
//   /api/products/latest   → Latest    (literal beats parameter)

// WHY NOT [ActionName] or Order: those hide the resolution in metadata a
// reader has to hunt for. Distinct constraints are self-documenting — the
// route itself states what it accepts.
//
// DEFENCE: an integration test hitting every registered route catches
// ambiguity at build time instead of on a production request.

    {
        var response = await factory.CreateClient().GetAsync("/api/products/42");
        Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
    }

    [Fact]
    public async Task Route_reaches_the_action_and_binds()
    {
        var client = factory.WithAuthenticatedUser().CreateClient();
        var response = await client.GetAsync("/api/products/42");
        Assert.Equal(HttpStatusCode.OK, response.StatusCode);
    }
}

// The anonymous test is the important one: it is the ONLY thing that catches
// a deleted [Authorize] or an authorization middleware ordered before
// UseRouting, both of which fail open with every unit test still green.
6 (hard): Design the layering for a service where the same operation is invoked by HTTP, a message queue, and a scheduled job.
Solution 
// THE CONSTRAINT: three entry points, one set of rules. Anything enforced in
// only one entry point is a rule with a hole in it.

// ── LAYER 1: ENTRY POINTS — translation only, no rules ───────────────────
[HttpPost("orders")]
public async Task<ActionResult<OrderResponse>> Create(
    CreateOrderRequest request, CancellationToken ct)
{
    var result = await orders.CreateAsync(request.ToCommand(), ct);
    return result.Error switch
    {
        null                         => CreatedAtAction(...),
        OrderError.InsufficientStock => Conflict(result.Message),
        _                            => Problem()
    };
}

public sealed class OrderMessageHandler(OrderService orders)
{
    public async Task HandleAsync(OrderPlaced message, CancellationToken ct)
    {
        var result = await orders.CreateAsync(message.ToCommand(), ct);
        // SAME service. Different failure translation: a queue handler retries
        // or dead-letters rather than returning a status code.
        if (result.Error is OrderError.InsufficientStock)
            throw new RetryableException();      // let the broker redeliver
    }
}

public sealed class NightlyOrderJob(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();   // no ambient scope here
            var orders = scope.ServiceProvider.GetRequiredService<OrderService>();
            await orders.CreateAsync(command, ct);
            await Task.Delay(TimeSpan.FromHours(1), ct);
        }
    }
}

// ── LAYER 2: APPLICATION SERVICE — orchestration, transactions ───────────
//   Takes a COMMAND, not an HTTP request. Returns a RESULT, not an
//   IActionResult. Knows nothing about HTTP, and therefore works identically
//   for all three callers.

// ── LAYER 3: DOMAIN — invariants that hold everywhere ────────────────────
public sealed class Product
{
    public int Stock { get; private set; }        // private setter is the point
    public bool TryReserve(int quantity)
    {
        if (quantity <= 0 || quantity > Stock) return false;
        Stock -= quantity;
        return true;
    }
}

// ── WHAT LIVES WHERE, AND WHY ────────────────────────────────────────────
//   HTTP status codes        → controller ONLY. A queue handler has no use
//                              for a 409, and returning IActionResult from a
//                              service is what couples the domain to HTTP.
//   Authorization from claims→ controller/filter. The job has no principal;
//                              it is trusted by virtue of running in-process.
//   Authorization from DATA  → the service or query layer, because the queue
//                              handler needs it too (tenant scoping).
//   Retry semantics          → entry point. HTTP returns a code and lets the
//                              client decide; the queue throws to redeliver.
//   Business rules           → domain. Non-negotiable, all three paths.

// ── THE TEST THAT KEEPS IT HONEST ────────────────────────────────────────
// Unit-test the application service directly with a command object. If that
// test needs an HttpContext, a ClaimsPrincipal or an IActionResult, HTTP has
// leaked into a layer two of the three callers cannot satisfy — and the queue
// handler will fail at runtime in a way no controller test reveals.

🎯 Key Takeaways

  • [ApiController] enables automatic 400s, binding inference, required attribute routing and problem-details errors — removing it silently disables validation.
  • Use ControllerBase for APIs; Controller only when rendering Razor views.
  • ActionResult<T> is the controller default — it carries the success type for OpenAPI and tests while still allowing any result.
  • CreatedAtAction derives the Location header from the route table; interpolated URLs rot silently on rename.
  • Keep controllers thin: bind, delegate to an application service, map the outcome to a status code.
  • Rules living only in a controller are bypassed by queue handlers and jobs — invariants belong on the entity.
  • Result objects for expected business outcomes, exceptions for genuine infrastructure failures.
  • Every public method on a controller is a candidate action — mark helpers [NonAction] or make them private.
  • Controller unit tests bypass routing, binding and filters, so they can never prove an endpoint is reachable or protected.
  • Controllers and minimal APIs produce the same endpoints and coexist; thin handlers make the choice cheap to reverse.
