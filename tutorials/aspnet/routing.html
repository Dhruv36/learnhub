Routing Foundations

What you'll master: how ASP.NET Core turns a URL into an endpoint — route templates and constraints, the precedence rules that decide which of several matching routes wins, why routing is split into two middleware stages, link generation, and the diagnostic habits that turn "why is my 404 a 404" into a five-second answer. Prerequisites: How ASP.NET Core Runs and Minimal APIs.

Part 1 — Two Middleware, One Job

// Routing is deliberately SPLIT across two points in the pipeline:
app.UseRouting();        // 1. MATCH: pick the endpoint, attach it to HttpContext
app.UseAuthentication(); //    ...middleware in between can now SEE the match
app.UseAuthorization();
app.UseEndpoints();      // 2. EXECUTE: run the endpoint's delegate
                         //    (added implicitly in modern minimal hosting)

// Why split? Because everything between the two stages can inspect the chosen
// endpoint and its metadata BEFORE the handler runs. That is the entire reason
// UseAuthorization works: it reads the [Authorize] metadata off the matched
// endpoint. Placed before UseRouting, no endpoint has been selected yet, so it
// finds no metadata, permits the request, and FAILS OPEN. This is the single
// most consequential ordering rule in ASP.NET Core.

// Read the match yourself from any middleware after UseRouting:
app.Use(async (context, next) =>
{
    var endpoint = context.GetEndpoint();
    if (endpoint is not null)
    {
        // The route pattern that matched — invaluable for metrics, because
        // it is LOW CARDINALITY: "/products/{id}" not "/products/12345".
        var pattern = (endpoint as RouteEndpoint)?.RoutePattern.RawText;
        var name    = endpoint.DisplayName;
        var values  = context.Request.RouteValues;   // { ["id"] = "42" }
    }
    await next();
});

// In modern minimal hosting you rarely call UseRouting explicitly — the
// framework inserts it at the start of the pipeline. You MUST call it
// explicitly when you need middleware to run BEFORE matching, or when you need
// to control exactly where matching happens relative to your own middleware.

Part 2 — Templates, Constraints, and What They Are Not

// A route template is literal segments plus {parameters}:
"/products/{id}"                    // /products/42
"/products/{id:int}"                // constrained to integers
"/products/{id:int?}"               // optional
"/files/{*path}"                    // catch-all: matches the rest, slashes too
"/files/{**path}"                   // catch-all, round-trippable (unescaped)
"/orders/{year:int}/{month:int:range(1,12)}"   // multiple constraints, chained

// The built-in constraints worth memorising:
{id:int}          {id:long}        {id:guid}      {id:bool}
{d:datetime}      {p:decimal}      {s:alpha}
{s:minlength(3)}  {s:maxlength(50)}  {s:length(6)}
{n:min(1)}        {n:max(100)}      {n:range(1,100)}
{s:regex(^[a-z0-9-]+$)}                          // escape } as }} in regex

// CONSTRAINTS ARE FOR DISAMBIGUATION, NOT VALIDATION. This distinction is
// asked in interviews and got wrong in production:
//
//   /products/{id:int}   +  request GET /products/abc   →  404, not 400
//
// A failed constraint means "this route did not match", so routing keeps
// looking and eventually returns 404. It does NOT produce a helpful validation
// error, because from routing's perspective the client asked for a URL that
// does not exist. If a caller passing a non-integer id deserves a 400 with an
// explanatory message, that is model validation's job.
//
// The practical consequence: use constraints to tell two similar routes apart,
// not to enforce business rules. {id:min(1)} looks like validation but a
// request for id=0 silently becomes 404 rather than "id must be positive".

// Custom constraints exist for genuinely reusable disambiguation:
public sealed class SkuConstraint : IRouteConstraint
{
    public bool Match(HttpContext? ctx, IRouter? route, string key,
        RouteValueDictionary values, RouteDirection direction)
        => values.TryGetValue(key, out var v)
           && v is string s
           && s.Length == 8
           && s.StartsWith("SKU");
}
builder.Services.Configure<RouteOptions>(o =>
    o.ConstraintMap["sku"] = typeof(SkuConstraint));
// now usable as {code:sku}

Producing a helpful 400 for malformed input — rather than the 404 a failed constraint gives you — is the job of Model Binding & Validation.

Part 3 — Precedence: Which Route Wins

// Several templates can match one URL. The winner is decided by a defined
// order, NOT by registration order — which surprises people arriving from
// frameworks where the first registered route wins.
//
// Precedence, most specific first:
//   1. more literal segments beat fewer
//   2. literal segment beats parameter segment (at the same position)
//   3. constrained parameter beats unconstrained parameter
//   4. parameter beats catch-all
//   5. catch-all is always last

// Given these four registrations IN THIS ORDER:
app.MapGet("/products/{*rest}",   () => "catch-all");
app.MapGet("/products/{id}",      () => "any id");
app.MapGet("/products/{id:int}",  () => "int id");
app.MapGet("/products/featured",  () => "featured");

// GET /products/featured  → "featured"   (rule 2: literal wins)
// GET /products/42        → "int id"     (rule 3: constrained wins)
// GET /products/abc       → "any id"     (int constraint failed, falls through)
// GET /products/a/b/c     → "catch-all"  (rule 5: only the catch-all matches)
//
// Registration order changed NOTHING here. That is a feature: routes can be
// registered across many files without their order mattering.

// AMBIGUITY IS A STARTUP-TIME... no — a REQUEST-TIME exception:
app.MapGet("/reports/{a}/{b}", () => "one");
app.MapGet("/reports/{x}/{y}", () => "two");
// GET /reports/1/2 → AmbiguousMatchException (500), because the two templates
// are equally specific and routing has no basis to choose. It throws on the
// REQUEST, not at startup, so an ambiguous pair can ship and only break the
// routes that actually collide. Integration tests that hit every route are the
// cheap defence.

// Break a tie explicitly when you genuinely want one to win:
app.MapGet("/reports/{a}/{b}", () => "one").WithOrder(-1);   // lower runs first
Key insight: route matching is compiled into a DFA-style decision tree at startup, not evaluated as a linear list per request. Adding the thousandth route does not make matching meaningfully slower than the tenth, because the matcher walks segments once rather than testing every template. This is why registration order is irrelevant to precedence — by request time there is no list left to be ordered, only a tree with tie-break rules baked in.

Part 4 — Link Generation: Routing in Reverse

// Hardcoding URLs in responses is how a route rename becomes a broken client.
// LinkGenerator turns route data back into a URL, using the same templates.

app.MapGet("/products/{id:int}", (int id) => ...).WithName("GetProduct");

app.MapPost("/products", (Product p, LinkGenerator links, HttpContext ctx) =>
{
    var url = links.GetPathByName(ctx, "GetProduct", new { id = p.Id });
    // "/products/42" — derived from the template, so renaming the route
    // updates every generated link automatically.
    return TypedResults.Created(url, p);
});

// GetPathByName  → "/products/42"                        (relative)
// GetUriByName   → "https://api.example.com/products/42" (absolute)
//
// Absolute URIs depend on Request.Scheme and Host being correct — behind a
// reverse proxy that means forwarded headers must be configured, or every
// generated link comes out as http on an https site. See Part 3 of
// How ASP.NET Core Runs.

// Named routes are the contract worth maintaining: unnamed link generation by
// values is possible but couples the caller to the template's parameter names.

// In a Created response, prefer generating the Location header this way over
// string interpolation — $"/products/{p.Id}" compiles fine and silently rots
// the day the route becomes /catalog/products/{id}.

Part 5 — Route Groups, Ordering, and Real Structure

// MapGroup composes templates, so nesting builds the prefix:
var api = app.MapGroup("/api");
var v1  = api.MapGroup("/v1");
var products = v1.MapGroup("/products").WithTags("Products");

products.MapGet("/{id:int}", ...);   // → /api/v1/products/{id:int}

// Group prefixes participate in precedence exactly like inline templates —
// the composed template is what the matcher sees. There is no separate
// "group matching" phase.

// Route parameters declared in a group prefix are available to every endpoint:
var tenant = app.MapGroup("/tenants/{tenantId:guid}");
tenant.MapGet("/users", (Guid tenantId, UserService svc) =>
    svc.ForTenant(tenantId));        // binds from the GROUP's template

// This is a genuinely good pattern for multi-tenancy: the tenant is structural
// in the URL, every endpoint under the group receives it, and no endpoint can
// forget to scope its query because the parameter is required to bind.

// Endpoint metadata that affects matching rather than execution:
app.MapGet("/legacy", () => ...).WithOrder(100);         // tie-break late
app.MapGet("/internal", () => ...).ExcludeFromDescription(); // hide from OpenAPI

// Host and method constraints:
app.MapGet("/", () => "admin site").RequireHost("admin.example.com");
app.MapMethods("/resource", ["PATCH", "PUT"], () => ...);

Part 6 — Diagnosing a 404 Systematically

// A 404 in ASP.NET Core has exactly four causes. Check them in this order and
// the answer arrives in seconds instead of a debugging session.
//
// 1. NO ROUTE MATCHED — the template genuinely does not cover this URL,
//    or a constraint rejected it (remember: failed constraint → 404, not 400).
// 2. A ROUTE MATCHED BUT THE HANDLER RETURNED 404 — TypedResults.NotFound()
//    because the record was missing. Completely different problem.
// 3. MIDDLEWARE SHORT-CIRCUITED BEFORE ROUTING — UseStaticFiles, a rewrite
//    rule, or custom middleware ended the request before matching ran.
// 4. THE ENDPOINT IS NOT REGISTERED AT ALL — the Map*Endpoints extension was
//    never called from Program.cs. Common after a merge.

// Distinguishing 1 from 2 takes one line of middleware:
app.Use(async (ctx, next) =>
{
    await next();
    if (ctx.Response.StatusCode == 404)
    {
        var matched = ctx.GetEndpoint() is not null;
        // matched == true  → cause 2: your handler chose to 404
        // matched == false → cause 1 or 4: routing found nothing
        logger.LogWarning("404 {Path} matched={Matched}", ctx.Request.Path, matched);
    }
});

// List every registered endpoint at startup — the fastest cure for cause 4:
var sources = app.Services.GetRequiredService<EndpointDataSource>();
foreach (var e in sources.Endpoints.OfType<RouteEndpoint>())
    logger.LogInformation("{Order} {Pattern}",
        e.Order, e.RoutePattern.RawText);

// Enable routing's own diagnostics when precedence is the mystery:
// appsettings.Development.json
// "Logging": { "LogLevel": {
//     "Microsoft.AspNetCore.Routing": "Debug"
// }}
// It logs the candidate set and the selected endpoint per request, which shows
// you exactly which templates competed and which one won.

// METRICS NOTE: always label metrics with the route PATTERN, never the raw
// path. Using ctx.Request.Path produces one time series per product id and
// will take down a Prometheus instance; the pattern from RouteEndpoint is the
// low-cardinality version that stays bounded.

Interview Questions

Beginner: What is the difference between UseRouting and UseEndpoints?

UseRouting performs the match: it compares the request against every registered route template, selects the winning endpoint, and attaches it to the HttpContext along with the extracted route values. UseEndpoints executes that endpoint's delegate. They are separate so that middleware registered between them can inspect the selected endpoint and its metadata before the handler runs — which is exactly how authorization, CORS and endpoint-aware logging work. In modern minimal hosting both are inserted automatically, and you only call them explicitly when you need middleware to sit before matching or between the two stages.

Beginner: Why does GET /products/abc return 404 rather than 400 when the route is /products/{id:int}?

Because a route constraint is part of matching, not validation. When the int constraint rejects "abc", the meaning is "this template does not match this URL", so routing continues looking at other templates and, finding none, returns 404. Nothing in the pipeline has formed an opinion about whether "abc" is a bad id — from routing's point of view the client requested a URL that does not exist. If a caller sending a non-integer id should receive an explanatory 400, that has to come from model binding and validation on a route that actually matches.

Mid: Given /products/featured, /products/{id:int} and /products/{id}, which matches GET /products/featured and why?

/products/featured wins, because a literal segment beats a parameter segment at the same position. Precedence is determined by specificity, not registration order: more literal segments beat fewer, literals beat parameters, constrained parameters beat unconstrained ones, and catch-alls always come last. So GET /products/42 would select {id:int} over {id}, and GET /products/abc would fall through to {id} once the int constraint fails. The practical benefit is that routes can be registered across many files in any order without their relative position changing behaviour.

Mid: Why prefer LinkGenerator over string interpolation for a Location header?

Because interpolation duplicates the route template as a string literal, and the compiler cannot tell you when the two drift apart. $"/products/{id}" keeps compiling perfectly after someone moves the route to /catalog/products/{id}, and the break surfaces as clients following a dead Location — at runtime, in production, possibly only for the create path that nobody integration-tests. LinkGenerator with a named route derives the URL from the same template the matcher uses, so a rename propagates automatically. The one thing to watch is absolute URI generation, which depends on Request.Scheme and Host: behind a reverse proxy those are the proxy's values unless forwarded headers are configured, so links come out as http on an https site.

Senior: A protected endpoint is serving anonymous users in production but is correctly protected in local testing. Diagnose.

The prime suspect is middleware ordering — UseAuthorization registered before UseRouting. Authorization decides by reading [Authorize] metadata from the matched endpoint, so if it runs before matching there is no endpoint on the context, no metadata is found, and the request is permitted. The failure mode is what makes it dangerous: it fails open, with no exception and nothing in the logs, so every authenticated happy-path test still passes and only an unauthenticated request reveals it. The environment split usually comes from a conditional pipeline — a if (env.IsDevelopment()) branch that registers middleware in a different order, or a dev-only authentication handler that stubs an identity so the missing check is invisible locally. I would confirm by requesting the endpoint with no credentials against each environment, then check GetEndpoint() inside the authorization middleware to prove whether a match exists at that point. The durable fixes are to keep one unconditional pipeline order with environment differences expressed as configuration rather than as different Use sequences, add a fallback authorization policy so endpoints are protected by default and opt out explicitly via AllowAnonymous, and add an integration test that asserts 401 for an anonymous call — the test that would have caught it.

Senior: How would you design routing for a multi-tenant API where every request is scoped to a tenant?

I would make the tenant structural in the URL — /tenants/{tenantId:guid}/... — declared once on a route group that every tenant-scoped endpoint hangs off. The reason is that it makes the scoping impossible to forget: the parameter is part of the composed template, so every endpoint in the group binds it, and an endpoint that fails to use it is visible in review rather than silently querying across tenants. The alternatives each give something up. A subdomain per tenant (acme.api.example.com) keeps URLs clean and supports per-tenant TLS and routing at the edge, but needs wildcard certificates and DNS automation, and RequireHost plus a host-parsing middleware to extract the tenant. A header or JWT claim keeps URLs uniform and is the right answer when tenancy is an identity property rather than a resource hierarchy, but it makes the tenant invisible in logs, metrics and cache keys unless deliberately propagated, and it makes URLs non-shareable between tenants in a way that is either a feature or a support burden. Whichever carries the tenant, the critical decision is that the identifier must be authorized, not merely bound: a route parameter is client-supplied, so an endpoint must verify the authenticated principal is entitled to that tenant. Skipping that turns a tidy URL scheme into an IDOR vulnerability where changing a GUID reads another customer's data. I would enforce it centrally — an endpoint filter or authorization requirement on the group that compares the route's tenant against the token's claim — so it cannot be omitted per endpoint, and I would ensure the query layer scopes by tenant too, via a global query filter, so a missing WHERE is defence-in-depth rather than a breach.

🏋️ Graded Exercises

1 (easy): Write templates for: an integer id, an optional page number, a GUID, and a catch-all file path.
Solution 
app.MapGet("/products/{id:int}",        (int id) => ...);
app.MapGet("/list/{page:int?}",         (int? page) => ...);   // optional
app.MapGet("/orders/{id:guid}",         (Guid id) => ...);
app.MapGet("/files/{*path}",            (string path) => ...); // slashes included

// {page:int?} with a nullable parameter and {page:int} with a default value
// (int page = 1) both work; the default-value form is usually clearer because
// the fallback lives next to the parameter rather than inside the handler.
2 (easy): Given /orders/latest and /orders/{id:int}, which handles GET /orders/latest, and does registering them in the opposite order change anything?
Solution 
// /orders/latest wins — a literal segment beats a parameter segment at the
// same position. Registration order changes NOTHING.
//
// Precedence is computed from template specificity when the matcher's decision
// tree is built at startup, so by request time there is no list to be ordered.
// This is why routes spread across many feature files behave predictably.
//
// Contrast with frameworks like Express, where the first registered matching
// route wins and moving a route up or down the file genuinely changes
// behaviour. Carrying that assumption into ASP.NET Core produces "I moved the
// route and nothing changed" confusion.
3 (medium): An endpoint /reports/{a}/{b} and another /reports/{x}/{y} both exist. What happens, when, and how do you fix it properly?
Solution 
// WHAT: AmbiguousMatchException → HTTP 500, on the REQUEST, not at startup.
// The two templates are equally specific, so precedence rules cannot break the
// tie and routing refuses to guess.
//
// WHEN: only when a URL actually matches both. The app starts cleanly and
// every other route works, so this can pass a smoke test and ship.

// THE PROPER FIX is to make the templates genuinely distinguishable, because
// that reflects a real difference in what they accept:
app.MapGet("/reports/{year:int}/{month:int:range(1,12)}", ...);
app.MapGet("/reports/{category:alpha}/{slug}",            ...);
// Now /reports/2026/03 and /reports/sales/q1 select different endpoints on
// specificity, with no ordering hint required.

// THE TIE-BREAK, when both really must accept the same shape:
app.MapGet("/reports/{a}/{b}", ...).WithOrder(-1);   // lower order wins
// Use this sparingly — it encodes precedence as a number a future reader has
// to hunt for, whereas distinct constraints are self-documenting.

// THE DEFENCE: an integration test that requests every registered route.
// Enumerate EndpointDataSource and assert none of them throws — that turns a
// request-time exception into a build-time failure.
4 (medium): Return a 201 from POST /products whose Location header survives a later rename of the GET route.
Solution 
app.MapGet("/products/{id:int}", async (int id, ProductService svc) => ...)
   .WithName("GetProduct");          // the stable contract

app.MapPost("/products", async (
    CreateProduct request,
    ProductService svc,
    LinkGenerator links,
    HttpContext ctx,
    CancellationToken ct) =>
{
    var product = await svc.CreateAsync(request, ct);
    var url = links.GetPathByName(ctx, "GetProduct", new { id = product.Id });
    return TypedResults.Created(url, product);
});

// Renaming the GET route to "/catalog/products/{id:int}" now updates the
// Location header automatically, because the URL is derived from the same
// template the matcher uses. The route NAME is the contract, not the path.
//
// GetPathByName gives a relative path, which is usually right. GetUriByName
// gives an absolute URI and depends on Request.Scheme/Host being accurate —
// behind a proxy that requires forwarded headers, or the link says http.
5 (hard): Requests to /api/v1/orders/42 return 404 in production. Write the diagnostic procedure.
Solution 
// There are exactly four causes. Separate them before theorising.

// STEP 1 — did routing match anything at all? One middleware answers it:
app.Use(async (ctx, next) =>
{
    await next();
    if (ctx.Response.StatusCode == 404)
        logger.LogWarning("404 {Path} matched={Matched} endpoint={Endpoint}",
            ctx.Request.Path,
            ctx.GetEndpoint() is not null,
            ctx.GetEndpoint()?.DisplayName);
});
//   matched=true  → the route is fine; the HANDLER returned NotFound because
//                   order 42 does not exist (or is filtered by a tenant/soft
//                   delete predicate). This is a DATA question, not routing.
//   matched=false → continue to step 2.

// STEP 2 — is the endpoint registered in this environment?
var ds = app.Services.GetRequiredService<EndpointDataSource>();
foreach (var e in ds.Endpoints.OfType<RouteEndpoint>())
    logger.LogInformation("{Pattern}", e.RoutePattern.RawText);
//   Absent → MapOrderEndpoints() is not being called. Classic causes: it sits
//   behind an environment conditional, or a merge dropped the line. This is
//   the most common production-only 404.

// STEP 3 — is something short-circuiting before routing?
//   UseStaticFiles, a URL rewrite, or custom middleware that ends the request.
//   Production-only rewrite rules at the proxy are a frequent culprit: the app
//   may be receiving /orders/42 with the /api/v1 prefix already stripped, or
//   NOT stripped when the app expects it to be. Log ctx.Request.Path at the
//   very TOP of the pipeline to see what actually arrived.

// STEP 4 — enable routing diagnostics to see the candidate set:
// "Microsoft.AspNetCore.Routing": "Debug"
//   Shows which templates competed and which won.

// The prod/local asymmetry in step 3 is what makes this class of bug annoying:
// locally you call the app directly, in production a proxy rewrites the path
// first, so the app sees a different URL than you think it does.
6 (hard): Design tenant-scoped routing where no endpoint can accidentally serve another tenant's data.
Solution 
// 1. STRUCTURAL: the tenant lives in the template, declared once on a group.
var tenant = app.MapGroup("/tenants/{tenantId:guid}")
    .RequireAuthorization()
    .AddEndpointFilter<TenantAuthorizationFilter>();

tenant.MapGet("/orders", async (Guid tenantId, OrderService svc, CancellationToken ct)
    => TypedResults.Ok(await svc.ForTenantAsync(tenantId, ct)));

// Every endpoint under the group binds tenantId because it is part of the
// composed template — it cannot be forgotten at the signature level.

// 2. AUTHORIZED, not merely bound. A route value is CLIENT-SUPPLIED. Binding
//    it proves nothing about entitlement, and stopping here is an IDOR: change
//    the GUID, read another customer's orders.
public sealed class TenantAuthorizationFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        var routeTenant = ctx.HttpContext.Request.RouteValues["tenantId"]?.ToString();
        var claimTenant = ctx.HttpContext.User.FindFirst("tenant_id")?.Value;

        if (routeTenant is null || claimTenant is null ||
            !string.Equals(routeTenant, claimTenant, StringComparison.OrdinalIgnoreCase))
            return TypedResults.Forbid();     // 403: identity known, not entitled

        return await next(ctx);
    }
}
// On the GROUP, so a new endpoint inherits the check by default. Per-endpoint
// registration fails open the first time someone forgets it.

// 3. DEFENCE IN DEPTH at the data layer — a global query filter so a missing
//    WHERE clause cannot leak rows even if layers 1 and 2 were bypassed:
modelBuilder.Entity<Order>().HasQueryFilter(o => o.TenantId == _tenant.Current);

// WHY THREE LAYERS: each fails differently. The template can be bypassed by a
// new endpoint outside the group; the filter can be bypassed by a background
// job with no HttpContext; the query filter catches both but is itself
// bypassable with IgnoreQueryFilters(). Independent failure modes are the
// point — one mistake should not be sufficient to leak data.

// TRADE-OFF worth stating: putting the tenant in the URL makes it visible in
// logs, metrics and cache keys for free, which is operationally valuable. The
// alternative — tenant from the JWT claim only — gives uniform URLs but needs
// deliberate propagation into every log scope and cache key, and a cache key
// that forgets the tenant is a cross-tenant data leak of a much worse kind.

🎯 Key Takeaways

  • Routing is split into matching (UseRouting) and execution (UseEndpoints) so middleware in between can read the selected endpoint's metadata — that split is why authorization must come after routing.
  • UseAuthorization before UseRouting fails open: no metadata, no exception, no log entry. It is the highest-consequence ordering mistake in the framework.
  • Constraints disambiguate routes, they do not validate input. A failed constraint yields 404, never a helpful 400.
  • Precedence comes from specificity — literals beat parameters, constrained beats unconstrained, catch-all is last — and never from registration order.
  • Two equally specific templates throw AmbiguousMatchException at request time, not startup, so ambiguous pairs can ship undetected.
  • Matching compiles to a decision tree at startup, so route count barely affects per-request cost.
  • Generate URLs with LinkGenerator and named routes; interpolated paths rot silently when a route is renamed.
  • Every 404 is one of four things: no match, handler-returned, short-circuited before routing, or never registered. GetEndpoint() is not null separates the first two instantly.
  • Label metrics with the route pattern, never the raw path — /products/{id} is bounded, /products/12345 is a cardinality explosion.
  • A tenant in the route is client-supplied data: bind it structurally, authorize it centrally, and filter at the data layer too.
