Authentication (Identity, JWT, OIDC) Security

What you'll master: the scheme/handler model underneath every authentication method, cookies versus tokens and when each is genuinely right, JWT validation parameters and which ones being wrong makes the whole thing decorative, OIDC and the flows worth using in 2026, and refresh-token handling that survives a stolen token. Prerequisites: Middleware Pipeline and Dependency Injection.

Part 1 — Schemes, Handlers, and the Three Verbs

// Authentication answers WHO the caller is. Authorization answers WHETHER
// they may proceed — a separate lesson, and a separate middleware.

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options => { /* ... */ });

var app = builder.Build();
app.UseAuthentication();     // builds HttpContext.User from the request
app.UseAuthorization();      // reads it and enforces policy — AFTER routing

// A SCHEME is a named handler. Every scheme implements three operations, and
// knowing which is which explains most confusing redirect behaviour:
//
//   AUTHENTICATE  read the request, produce a ClaimsPrincipal (or fail)
//   CHALLENGE     the caller is unauthenticated — how do we ask them to
//                 authenticate? Cookies REDIRECT to a login page; JWT returns
//                 401 with a WWW-Authenticate header.
//   FORBID        the caller IS authenticated but not allowed. Cookies
//                 redirect to an access-denied page; JWT returns 403.
//
// This is why an API using cookie authentication returns a 302 to /login
// instead of a 401 when a token expires — the challenge operation is doing
// exactly what cookies are designed to do, which is wrong for an API client.

// MULTIPLE SCHEMES — common when a service has both a UI and an API:
builder.Services.AddAuthentication(options =>
{
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = CookieAuthenticationDefaults.AuthenticationScheme;
})
.AddCookie()
.AddJwtBearer("Bearer", options => { /* ... */ });

// Then select per endpoint:
[Authorize(AuthenticationSchemes = "Bearer")]
public sealed class ApiController : ControllerBase { }

// Or accept EITHER, which is the usual intent for a shared endpoint:
builder.Services.AddAuthorization(options =>
{
    options.DefaultPolicy = new AuthorizationPolicyBuilder(
            CookieAuthenticationDefaults.AuthenticationScheme, "Bearer")
        .RequireAuthenticatedUser()
        .Build();
});

// CLAIMS are the output. A ClaimsPrincipal holds one or more identities, each
// holding claims — name/value pairs asserted by whoever issued the token:
var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
var email  = User.FindFirst(ClaimTypes.Email)?.Value;
var tenant = User.FindFirst("tenant_id")?.Value;
var isAdmin = User.IsInRole("admin");     // roles are just claims by another name

// CLAIM TYPE MAPPING — a real source of confusion. By default the JWT handler
// rewrites short JWT claim names to long WS-Federation URIs, so `sub` becomes
// ClaimTypes.NameIdentifier. Turn it off to work with the raw names:
JwtSecurityTokenHandler.DefaultInboundClaimTypeMap.Clear();
// Then User.FindFirst("sub") works and the claims match the token you can see
// in a debugger — which makes everything easier to reason about.

Part 2 — Cookies vs Tokens

// The decision is not "cookies are old". They solve different problems, and
// the wrong choice creates security work you did not need.

// ── COOKIE AUTHENTICATION ────────────────────────────────────────────────
builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.Cookie.Name = "__Host-auth";     // __Host- prefix: strongest
        options.Cookie.HttpOnly = true;          // JavaScript CANNOT read it
        options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
        options.Cookie.SameSite = SameSiteMode.Lax;   // CSRF mitigation
        options.ExpireTimeSpan = TimeSpan.FromHours(8);
        options.SlidingExpiration = true;
        options.LoginPath = "/login";
        options.AccessDeniedPath = "/forbidden";
    });
//   + HttpOnly means XSS cannot steal the session — a genuinely large
//     security advantage that token-in-localStorage does not have
//   + revocation is easy: the server owns the session
//   + the browser handles storage and transmission automatically
//   − CSRF becomes a concern (the browser sends it automatically, so a
//     malicious site can trigger authenticated requests) → antiforgery tokens
//   − awkward across origins and for non-browser clients
//   → RIGHT FOR: server-rendered apps, and SPAs served from the SAME origin
//     as the API (the BFF pattern)

// ── JWT BEARER ───────────────────────────────────────────────────────────
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options => { /* validation — see Part 3 */ });
//   + stateless: any instance validates without shared session storage
//   + works for mobile, service-to-service, and cross-origin clients
//   + carries claims, so no lookup is needed per request
//   − CANNOT BE REVOKED before expiry without reintroducing state
//   − if stored in localStorage, XSS steals it outright
//   − every claim is stale from the moment it is issued
//   → RIGHT FOR: APIs with non-browser clients, service-to-service, mobile

// THE CRITICAL TRADE-OFF, stated plainly: a JWT is a bearer token that is
// valid until it expires. There is no logout. "Log out" clears the client's
// copy; a stolen token keeps working. That is why access-token lifetimes are
// SHORT — 5 to 15 minutes — with refresh tokens doing the long-lived work,
// because the exposure window is the token lifetime.

// THE MODERN DEFAULT FOR SPAs — Backend-for-Frontend:
//   the SPA authenticates against ITS OWN backend using a cookie;
//   the backend holds the tokens and calls downstream APIs.
//   → HttpOnly cookie protects against XSS, tokens never reach the browser,
//     and revocation works. This is what most guidance now recommends over
//     storing a JWT in localStorage.
Key insight: the most consequential JWT misconfiguration is not a subtle cryptographic one — it is setting ValidateIssuer, ValidateAudience or ValidateLifetime to false to make something work during development, and shipping it. Each disables a check with no visible symptom: the API keeps accepting valid tokens normally, while also accepting expired tokens, or tokens issued by a completely different system for a completely different audience. The application behaves identically in every test. Treat any Validate* = false as a production incident waiting to happen, and assert the correct values in a startup check.

Part 3 — Validating JWTs Properly

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        // For an OIDC provider, this fetches signing keys from the discovery
        // document and ROTATES them automatically. Prefer it to hardcoding.
        options.Authority = "https://id.example.com";
        options.Audience = "orders-api";

        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,               // WHO issued it
            ValidIssuer = "https://id.example.com",

            ValidateAudience = true,             // was it meant for US
            ValidAudience = "orders-api",

            ValidateLifetime = true,             // is it expired
            ClockSkew = TimeSpan.FromSeconds(30),// default is FIVE MINUTES

            ValidateIssuerSigningKey = true,     // is the signature ours
            // omit IssuerSigningKey when Authority is set — keys come from
            // the discovery endpoint and rotate without a redeploy

            RequireExpirationTime = true,
            RequireSignedTokens = true,
            ValidAlgorithms = ["RS256"]          // ← pin the algorithm
        };

        options.MapInboundClaims = false;        // keep raw JWT claim names

        options.Events = new JwtBearerEvents
        {
            OnAuthenticationFailed = context =>
            {
                // Log the REASON server-side; never return it to the caller.
                logger.LogWarning(context.Exception, "JWT validation failed");
                return Task.CompletedTask;
            }
        };
    });

// WHY EACH CHECK EXISTS — the attack each one stops:
//   ValidateIssuer     without it, a token from ANY issuer with a valid
//                      signature is accepted. Attacker sets up their own IdP.
//   ValidateAudience   without it, a token issued for a DIFFERENT service is
//                      accepted here. A low-value app's tokens open your API.
//   ValidateLifetime   without it, expired tokens work forever. Revocation by
//                      expiry — your only revocation — stops existing.
//   ValidAlgorithms    without pinning, an attacker may attempt algorithm
//                      confusion (presenting an HMAC token signed with the
//                      public RSA key). Modern libraries resist this, but
//                      pinning removes the class of attack entirely.
//
//   ClockSkew          defaults to FIVE MINUTES, so a "15-minute" token is
//                      really valid for 20. Tighten it once your servers run
//                      NTP, and know the real number when reasoning about
//                      exposure windows.

// SYMMETRIC KEYS, when there is no external IdP:
options.TokenValidationParameters.IssuerSigningKey =
    new SymmetricSecurityKey(Encoding.UTF8.GetBytes(
        builder.Configuration["Jwt:Key"]!));          // ≥32 bytes for HS256
// The key is a SECRET shared by every validator — anyone who can validate can
// also FORGE. Asymmetric (RS256) is better whenever the issuer and the
// validator are different services.

// ISSUING A TOKEN:
var claims = new List<Claim>
{
    new(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
    new(JwtRegisteredClaimNames.Email, user.Email),
    new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),  // unique id
    new("tenant_id", user.TenantId.ToString())
};
claims.AddRange(user.Roles.Select(r => new Claim(ClaimTypes.Role, r)));

var token = new JwtSecurityToken(
    issuer: "https://id.example.com",
    audience: "orders-api",
    claims: claims,
    expires: DateTime.UtcNow.AddMinutes(15),      // SHORT
    signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256));

// NEVER PUT SECRETS IN A JWT. The payload is base64, not encrypted — anyone
// holding the token can read every claim. It is signed, not confidential.

Part 4 — OIDC and Delegating Authentication

// OpenID Connect is an identity layer over OAuth 2.0. OAuth alone is about
// AUTHORIZATION (delegated access); OIDC adds AUTHENTICATION (who the user
// is) via the id_token. Confusing the two is why people implement OAuth and
// wonder where the user's identity went.

builder.Services.AddAuthentication(options =>
{
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
})
.AddCookie()                                  // holds the session AFTER login
.AddOpenIdConnect(options =>
{
    options.Authority = "https://id.example.com";
    options.ClientId = "orders-web";
    options.ClientSecret = builder.Configuration["Oidc:ClientSecret"];

    options.ResponseType = "code";            // AUTHORIZATION CODE flow
    options.UsePkce = true;                   // ← mandatory in 2026

    options.SaveTokens = true;                // keep tokens for downstream calls
    options.GetClaimsFromUserInfoEndpoint = true;

    options.Scope.Clear();
    options.Scope.Add("openid");              // required for OIDC
    options.Scope.Add("profile");
    options.Scope.Add("email");
    options.Scope.Add("offline_access");      // asks for a refresh token

    options.TokenValidationParameters.NameClaimType = "name";
    options.TokenValidationParameters.RoleClaimType = "role";
});

// THE FLOWS, and which to use:
//   AUTHORIZATION CODE + PKCE   the answer for essentially everything today —
//                               web apps, SPAs, and mobile. PKCE removes the
//                               need for a client secret in public clients and
//                               defeats code interception.
//   CLIENT CREDENTIALS          service-to-service, no user involved.
//   DEVICE CODE                 input-constrained devices (TVs, CLIs).
//   ✗ IMPLICIT                  DEPRECATED. Returned tokens in the URL
//                               fragment, where they land in browser history
//                               and referrer headers.
//   ✗ RESOURCE OWNER PASSWORD   DEPRECATED. The app handles the user's
//                               password directly, defeating the entire point
//                               of delegated authentication, and it cannot
//                               support MFA or federation.

// THE TOKENS AND WHAT EACH IS FOR — routinely mixed up:
//   id_token       proves WHO the user is. For YOUR app to consume. NEVER
//                  send it to an API as a credential.
//   access_token   grants access to an API. Send this in the Authorization
//                  header. Opaque to your app — do not parse it unless you
//                  are the resource server.
//   refresh_token  obtains new access tokens. HIGHEST-VALUE secret; never
//                  goes to a browser.

// SERVICE-TO-SERVICE, no user in sight:
builder.Services.AddHttpClient<InventoryClient>()
    .AddHttpMessageHandler(sp => new ClientCredentialsHandler(
        sp.GetRequiredService<ITokenService>()));
// The handler caches the token until shortly before expiry and refreshes it.
// Requesting a new token per outbound call is a common and expensive mistake
// — it adds a full round trip to the IdP on every single request.

Part 5 — Refresh Tokens and Revocation

// Short access tokens limit exposure. Refresh tokens keep users logged in
// without holding a long-lived credential in play.

public sealed class RefreshToken
{
    public required string TokenHash { get; set; }   // HASHED, like a password
    public required Guid UserId { get; set; }
    public required DateTimeOffset ExpiresAt { get; set; }
    public DateTimeOffset? RevokedAt { get; set; }
    public string? ReplacedByHash { get; set; }      // the rotation chain
    public string? CreatedByIp { get; set; }
}

// ROTATION — every use issues a NEW refresh token and invalidates the old one:
public async Task<Result<TokenPair>> RefreshAsync(string presented, CancellationToken ct)
{
    var hash = Sha256(presented);
    var stored = await db.RefreshTokens
        .FirstOrDefaultAsync(t => t.TokenHash == hash, ct);

    if (stored is null) return Result.Fail("Invalid refresh token.");

    // ── REUSE DETECTION — the important part ─────────────────────────────
    // An ALREADY-ROTATED token being presented means either an attacker stole
    // it, or the legitimate client is replaying. Both are indistinguishable,
    // and both warrant revoking the whole family: the attacker and the victim
    // are now using the same chain, so the only safe action is to end it.
    if (stored.RevokedAt is not null)
    {
        await RevokeDescendantsAsync(stored, ct);
        log.LogWarning("Refresh token reuse detected for user {UserId}", stored.UserId);
        return Result.Fail("Session invalidated. Please sign in again.");
    }

    if (stored.ExpiresAt < clock.GetUtcNow())
        return Result.Fail("Refresh token expired.");

    var replacement = GenerateRefreshToken();
    stored.RevokedAt = clock.GetUtcNow();
    stored.ReplacedByHash = Sha256(replacement);

    db.RefreshTokens.Add(new RefreshToken
    {
        TokenHash = Sha256(replacement),
        UserId = stored.UserId,
        ExpiresAt = clock.GetUtcNow().AddDays(14)
    });

    await db.SaveChangesAsync(ct);           // one transaction: both changes

    return new TokenPair(IssueAccessToken(stored.UserId), replacement);
}

// STORE THEM HASHED. A refresh token is a credential; a database leak of
// plaintext refresh tokens is a full account compromise for every user.

// REVOKING ACCESS TOKENS — the honest options, none of them free:
//
// 1. SHORT LIFETIMES (5-15 min) and accept the window. Simplest, stateless,
//    and correct for most systems. "Revocation takes up to 15 minutes."
//
// 2. A DENYLIST of jti values in Redis until natural expiry. Reintroduces
//    state and a cache lookup per request, but bounded — entries expire with
//    the token.
if (await cache.KeyExistsAsync($"revoked:{jti}")) return Unauthorized();
//
// 3. A SECURITY STAMP compared per request — how ASP.NET Core Identity does
//    it. Changing a user's stamp invalidates every existing token, at the
//    cost of a lookup per request.
//
// 4. INTROSPECTION on every call. Fully accurate, and it discards the entire
//    performance argument for JWTs.
//
// PICK DELIBERATELY. Most systems should choose (1) and state the window in
// their security documentation, rather than building (4) and calling the
// result stateless.

Part 6 — Testing and Operating Authentication

// INTEGRATION TESTS need a real authenticated request, not a mocked
// ClaimsPrincipal — mocking it bypasses the middleware you most want tested.
public sealed class TestAuthHandler(
    IOptionsMonitor<AuthenticationSchemeOptions> options,
    ILoggerFactory logger, UrlEncoder encoder)
    : AuthenticationHandler<AuthenticationSchemeOptions>(options, logger, encoder)
{
    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        if (!Request.Headers.TryGetValue("X-Test-User", out var userId))
            return Task.FromResult(AuthenticateResult.NoResult());   // anonymous

        var claims = new[]
        {
            new Claim(ClaimTypes.NameIdentifier, userId!),
            new Claim(ClaimTypes.Role, Request.Headers["X-Test-Role"].ToString())
        };
        var principal = new ClaimsPrincipal(new ClaimsIdentity(claims, "Test"));
        return Task.FromResult(AuthenticateResult.Success(
            new AuthenticationTicket(principal, "Test")));
    }
}

Interview Questions

Beginner: What is the difference between authentication and authorization?

Authentication establishes who the caller is — validating a cookie, token or credential and producing a ClaimsPrincipal on HttpContext.User. Authorization decides whether that established identity may perform the requested operation, by evaluating roles, claims or policies against the endpoint's requirements. They are separate middleware for a reason and the order matters: UseAuthentication must run first because authorization has nothing to evaluate until the user is populated. The corresponding status codes reflect the same split — 401 means authentication is missing or invalid, 403 means the identity is known and not permitted.

Beginner: Why are JWT access tokens short-lived?

Because a JWT is a bearer token validated purely by its signature and claims, with no server-side lookup — which is what makes it stateless and fast, and also what makes it impossible to revoke before it expires. Anyone holding the token can use it until the expiry time, so "logging out" only clears the client's copy while a stolen token keeps working. The lifetime is therefore the exposure window for a compromised token, and keeping it to five or fifteen minutes bounds the damage. Refresh tokens then provide continuity without a long-lived credential in play, because they are stored server-side, can be rotated on every use, and can be revoked.

Mid: When would you choose cookies over JWTs?

When the client is a browser and the API shares an origin with the app serving it. The decisive advantage is that an HttpOnly cookie is unreadable by JavaScript, so a cross-site scripting flaw cannot exfiltrate the session — whereas a JWT in localStorage is trivially stolen by any XSS. Cookies also give real revocation, because the server owns the session, and the browser handles storage and transmission automatically. The costs are CSRF exposure, since the browser attaches the cookie to cross-site requests, which needs antiforgery tokens and SameSite, and awkwardness across origins and for non-browser clients. So: cookies for server-rendered apps and same-origin SPAs, JWTs for mobile, service-to-service and genuinely cross-origin APIs. For SPAs specifically, the backend-for-frontend pattern is now the common recommendation — a cookie between browser and backend, with tokens held server-side.

Mid: What does refresh-token rotation with reuse detection protect against?

It protects against a stolen refresh token granting indefinite access. With rotation, each refresh issues a new token and marks the presented one revoked, so a given refresh token is single-use. Reuse detection then handles the theft case: if an already-rotated token is presented, either an attacker is using a stolen copy or the legitimate client is replaying an old one, and those two situations are indistinguishable from the server's perspective. Since both mean the token chain is compromised, the correct response is to revoke the entire family of descendant tokens, forcing everyone — attacker and legitimate user alike — to reauthenticate. Without rotation, a stolen refresh token works silently until its expiry, potentially for weeks, with nothing in the logs to distinguish it from normal use.

Senior: An API accepts tokens it should reject, but only in production. Diagnose.

The most likely cause is a validation parameter disabled by configuration rather than by code — a ValidateIssuer, ValidateAudience or ValidateLifetime set to false in a production settings file or environment variable, possibly added during a migration to work around an issuer-URL mismatch and never reverted. The reason it manifests only in production is that configuration layering differs per environment, so the same code validates correctly locally. This class of bug is silent by design: the API keeps accepting legitimate tokens exactly as before, and the only symptom is that it also accepts tokens it should not — expired ones, or ones issued for a different audience by a different system. I would confirm by resolving JwtBearerOptions at startup and logging the actual TokenValidationParameters, since that shows the effective values after all configuration layers rather than what the source suggests. Related candidates worth checking are an over-broad ValidAudiences or ValidIssuers list accumulated during a migration, and a default ClockSkew of five minutes making expiry look broken when it is merely lenient. The durable fix is a startup assertion that throws in production when any of the four validations is disabled, turning a silent vulnerability into a failed deploy, plus an integration test presenting a deliberately expired and a wrong-audience token and asserting 401 — both cheap, and both would have caught this at the commit that introduced it.

Senior: Design authentication for a system with a web SPA, a mobile app, and internal service-to-service calls.

I would use one identity provider issuing OIDC tokens for all three, but deliberately different client patterns, because the threat models genuinely differ. For the web SPA I would use the backend-for-frontend pattern: the SPA authenticates against its own backend, which performs the authorization-code-with-PKCE flow, holds the access and refresh tokens server-side, and issues the browser only an HttpOnly, Secure, SameSite cookie. That keeps tokens entirely out of reach of JavaScript, so an XSS flaw cannot exfiltrate a credential, and it gives real revocation — the two things storing a JWT in localStorage gets wrong. The cost is CSRF protection and server-side session state, both well-understood. For mobile I would use authorization-code with PKCE and no client secret, since a secret shipped in an app binary is not a secret, storing the refresh token in the platform keychain and rotating it on every use with reuse detection. Access tokens stay short — around fifteen minutes — for both. For service-to-service I would use client credentials with per-service identities rather than one shared credential, so an individual service can be revoked and its access audited independently, and I would cache tokens until shortly before expiry rather than requesting one per call, which is a common and expensive mistake. Workload identity, where the platform provides it, is better still because it removes the stored secret entirely. On the resource-server side every API validates issuer, audience, lifetime and signature against the IdP's discovery document so key rotation needs no redeploy, with audiences scoped per API so a token for one service is not accepted by another. For revocation I would default to accepting the short-lifetime window and documenting it, adding a jti denylist only for the specific high-impact case of an admin forcing immediate logout — introspection on every call would discard the performance rationale for tokens altogether. Finally I would put the anonymous-request test and the startup validation assertion in CI, because the failure modes here are silent and neither code review nor happy-path testing catches them.

2 (easy): Explain why ValidateAudience = false is dangerous, with a concrete attack.
Solution 
// The `aud` claim states WHICH service a token was issued for. Disabling the
// check means any token signed by a trusted issuer is accepted.

// THE ATTACK, concretely:
//   Your company runs one identity provider for everything.
//   • orders-api        (this service — handles payments)
//   • marketing-signup  (a low-value app, minimal review, one intern)
//
//   Both trust tokens from https://id.example.com.
//   With ValidateAudience = false, orders-api accepts a token issued for
//   marketing-signup.
//
//   So anyone who can obtain a marketing-signup token — by signing up, or by

//   payments API. The weakest application in the estate becomes the security
//   boundary for the strongest.

// every request 401s, someone sets ValidateAudience = false, everything works,
// and it ships. There is NO visible symptom afterwards — legitimate tokens

// ✓ THE FIX — validate, and scope audiences per API:
ValidateAudience = true,

// ✓ AND ASSERT IT, so it cannot regress:
if (app.Environment.IsProduction() && !p.ValidateAudience)

Solution 
public async Task<Result<TokenPair>> RefreshAsync(string presented, string ip, CancellationToken ct)
{
    var hash = Convert.ToBase64String(
        SHA256.HashData(Encoding.UTF8.GetBytes(presented)));

    var stored = await db.RefreshTokens
        .FirstOrDefaultAsync(t => t.TokenHash == hash, ct);

    if (stored is null)
        return Result.Fail("Invalid refresh token.");

    // ── REUSE DETECTION ──────────────────────────────────────────────────
    // An already-rotated token was presented. Either an attacker stole it, or
    // the real client replayed an old one — INDISTINGUISHABLE. Both mean the
    // chain is compromised, so end the whole family.
    if (stored.RevokedAt is not null)
    {
        await RevokeFamilyAsync(stored.FamilyId, ct);
        log.LogWarning(
            "Refresh reuse detected. User {UserId} family {Family} from {Ip}",
            stored.UserId, stored.FamilyId, ip);
        return Result.Fail("Session invalidated. Please sign in again.");
    }

    if (stored.ExpiresAt < clock.GetUtcNow())
        return Result.Fail("Refresh token expired.");

    // ── ROTATE ───────────────────────────────────────────────────────────
    var replacement = Convert.ToBase64String(RandomNumberGenerator.GetBytes(64));
    var replacementHash = Convert.ToBase64String(
        SHA256.HashData(Encoding.UTF8.GetBytes(replacement)));

    stored.RevokedAt = clock.GetUtcNow();
    stored.ReplacedByHash = replacementHash;

    db.RefreshTokens.Add(new RefreshToken
    {
        TokenHash = replacementHash,
        UserId = stored.UserId,
        FamilyId = stored.FamilyId,          // same chain
        ExpiresAt = clock.GetUtcNow().AddDays(14),
        CreatedByIp = ip
    });

    await db.SaveChangesAsync(ct);   // ONE transaction: revoke + issue

    return new TokenPair(
        AccessToken: IssueAccessToken(stored.UserId, TimeSpan.FromMinutes(15)),
        RefreshToken: replacement);
}

// THREE DETAILS THAT MATTER:
//   • tokens are stored HASHED — a database leak must not yield usable
//     credentials, exactly as with passwords
//   • FamilyId lets one reuse event revoke the entire chain rather than
//     walking ReplacedByHash links one at a time
//   • revoke and issue happen in ONE SaveChanges, so a crash cannot leave the
//     old token revoked with no replacement issued — which would log the user
//     out for no reason

public sealed class TestAuthHandler(
    IOptionsMonitor<AuthenticationSchemeOptions> options,
    ILoggerFactory logger, UrlEncoder encoder)
    : AuthenticationHandler<AuthenticationSchemeOptions>(options, logger, encoder)
{
    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        // NoResult, NOT Fail — this is what lets the same handler serve
        // anonymous requests so the 401 path is genuinely exercised.
        if (!Request.Headers.TryGetValue("X-Test-User", out var userId))
            return Task.FromResult(AuthenticateResult.NoResult());

        var claims = new List<Claim> { new(ClaimTypes.NameIdentifier, userId!) };

        if (Request.Headers.TryGetValue("X-Test-Role", out var role))
            claims.Add(new Claim(ClaimTypes.Role, role!));

        var principal = new ClaimsPrincipal(new ClaimsIdentity(claims, "Test"));
        return Task.FromResult(AuthenticateResult.Success(
            new AuthenticationTicket(principal, "Test")));
    }
}

6 (hard): Design token handling for a SPA, justifying storage and revocation.
Solution 
// ── THE STORAGE QUESTION, AND WHY THE OBVIOUS ANSWERS LOSE ──────────────
//   localStorage    readable by ANY JavaScript on the page. One XSS — in your
//                   code or in any of your ~800 transitive npm dependencies —
//                   exfiltrates the token. No mitigation once it happens.
//   sessionStorage  same exposure, shorter window. Not a fix.
//   in-memory only  survives XSS-at-rest but is lost on refresh, forcing a
//                   silent re-auth on every page load.
//   HttpOnly cookie unreadable by JavaScript. XSS can still ISSUE requests,
//                   but it cannot STEAL the credential — the attacker is
//                   confined to the session rather than owning it portably.

// ── THE DESIGN: BACKEND-FOR-FRONTEND ─────────────────────────────────────
//   Browser  ──cookie──▶  BFF  ──access token──▶  APIs
//
// The SPA never sees a token at all.
builder.Services.AddAuthentication(options =>
{
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
})
.AddCookie(options =>
{
    options.Cookie.Name = "__Host-spa";       // __Host-: no domain, path=/, secure
    options.Cookie.HttpOnly = true;           // JS cannot read it
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    options.Cookie.SameSite = SameSiteMode.Lax;   // CSRF mitigation
    options.ExpireTimeSpan = TimeSpan.FromHours(8);
    options.SlidingExpiration = true;
})
.AddOpenIdConnect(options =>
{
    options.Authority = "https://id.example.com";
    options.ClientId = "spa-bff";
    options.ClientSecret = config["Oidc:ClientSecret"];   // safe: server-side
    options.ResponseType = "code";
    options.UsePkce = true;
    options.SaveTokens = true;                // tokens stay on the SERVER
    options.Scope.Add("offline_access");
});

// The BFF proxies API calls, attaching the access token server-side:
app.MapForwarder("/api/{**catch-all}", "https://orders-api", transform =>
{
    transform.AddRequestTransform(async ctx =>
    {
        var token = await ctx.HttpContext.GetTokenAsync("access_token");
        ctx.ProxyRequest.Headers.Authorization = new("Bearer", token);
    });
}).RequireAuthorization();

// ── WHY THIS WINS ────────────────────────────────────────────────────────
//   1. no token in the browser → XSS cannot steal a portable credential
//   2. REAL revocation → the BFF owns the session; deleting it logs the user
//      out immediately, which no stateless JWT design can offer
//   3. refresh tokens never leave the server — the highest-value secret is
//      never exposed to the most hostile environment
//   4. the client secret is genuinely secret, so the BFF is a confidential
//      client with stronger flows available

// ── THE COSTS, STATED HONESTLY ───────────────────────────────────────────
//   • server-side session state, so the BFF is no longer stateless and needs
//     a distributed session store to scale horizontally
//   • CSRF protection is now required — SameSite=Lax plus antiforgery tokens
//     on state-changing requests
//   • an extra network hop for every API call
//   • the BFF must be same-site with the SPA for __Host- cookies to work

// ── REVOCATION ACROSS THE LAYERS ─────────────────────────────────────────
//   BFF session      delete server-side → immediate, complete
//   access tokens    short-lived (15 min); accept the window
//   refresh tokens   rotated on use with reuse detection; revoking the family
//                    ends the chain
//
// ── WHEN I WOULD NOT DO THIS ─────────────────────────────────────────────
// A purely static SPA with no backend of its own, or a mobile client where
// there is no shared browser origin. There, authorization-code with PKCE and
// keychain storage is correct — the platform provides the secure storage that
// a browser does not.

🎯 Key Takeaways

  • A scheme implements authenticate, challenge and forbid — cookie challenges redirect, JWT challenges return 401, which is why cookie auth on an API returns HTML login pages.
  • Authentication populates HttpContext.User; authorization evaluates it. Order matters, and authorization must also come after routing.
  • Validate*= false disables a check with no visible symptom — assert all four are enabled at startup in production.
  • Default ClockSkew is five minutes, so a 15-minute token really lives 20.
  • A JWT cannot be revoked before expiry; its lifetime is the exposure window for theft.
  • JWT payloads are base64-encoded, not encrypted — never put secrets in claims.
  • Store refresh tokens hashed, rotate them on every use, and revoke the whole family on reuse detection.
  • Use authorization code with PKCE; implicit and password grants are deprecated for good reasons.
  • The id_token identifies the user to your app; the access_token is what APIs accept.
  • For SPAs prefer the BFF pattern — an HttpOnly cookie to the browser, tokens held server-side, which gives XSS resistance and real revocation.
