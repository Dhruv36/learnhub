OpenAPI & Client Generation Building APIs

What you'll master: how ASP.NET Core builds an OpenAPI document and why it is often wrong, making response types accurate without attribute sprawl, documenting authentication so the generated client actually works, generating typed clients that stay in sync, and using the document as a contract test rather than as decoration. Prerequisites: Controllers & MVC, Minimal APIs and API Versioning.

Part 1 — Where the Document Comes From

// .NET 9+ ships built-in OpenAPI generation — no Swashbuckle required:
builder.Services.AddOpenApi();

var app = builder.Build();
app.MapOpenApi();                    // serves /openapi/v1.json

// The document is built by the API EXPLORER walking the endpoint data source
// and inferring, per endpoint:
//   • path and HTTP method            ← from routing, always accurate
//   • parameters and binding sources  ← from the signature, usually accurate
//   • request body schema             ← from the parameter type
//   • RESPONSE types and status codes ← INFERRED, and this is where it lies
//   • security requirements           ← from authorization metadata
//
// Everything except responses is derived from facts the framework already
// knows. Responses are guessed, which is why an unreviewed document is
// usually wrong in exactly the way that matters to a client.

// ✗ THE INFERENCE PROBLEM — what does this return?
[HttpGet("{id:int}")]
public async Task<IActionResult> Get(int id)
{
    var p = await products.FindAsync(id);
    return p is null ? NotFound() : Ok(p);
}
// The document says: 200, schema unknown. It cannot see Product, and it does
// not know 404 is possible. A generated client gets `Task<object>` and no
// 404 handling — so the most important information is the least reliable.

// ✓ TypedResults with a union — the framework can see everything:
app.MapGet("/products/{id:int}",
    async Task<Results<Ok<Product>, NotFound>> (int id, ProductService svc) =>
        await svc.FindAsync(id) is { } p
            ? TypedResults.Ok(p)
            : TypedResults.NotFound());
// Document: 200 with Product schema, 404 with no body. Zero attributes, and
// the compiler enforces that the declared set stays accurate — adding a 409
// branch without declaring it is a BUILD error, not a stale document.

// ✓ Controllers — ActionResult<T> plus explicit attributes:
[HttpGet("{id:int}")]
[ProducesResponseType<Product>(StatusCodes.Status200OK)]
[ProducesResponseType(StatusCodes.Status404NotFound)]
public async Task<ActionResult<Product>> Get(int id) => ...;

// THE ASYMMETRY WORTH INTERNALISING: in minimal APIs the type system carries
// the documentation, so it cannot drift. In controllers the attributes are a
// PARALLEL declaration that nothing verifies — delete the 404 branch and the
// attribute happily keeps advertising it.

Part 2 — Making the Document Accurate

// Set global conventions once instead of attributing every action:
builder.Services.AddControllers(options =>
{
    // Every action can return these — declaring them per action is noise.
    options.Filters.Add(new ProducesResponseTypeAttribute(
        typeof(ProblemDetails), StatusCodes.Status500InternalServerError));
    options.Filters.Add(new ProducesResponseTypeAttribute(
        typeof(ProblemDetails), StatusCodes.Status401Unauthorized));
});

// Or per controller, for a whole family of endpoints:
[ApiController]
[Produces("application/json")]
[ProducesResponseType<ValidationProblemDetails>(StatusCodes.Status400BadRequest)]
public sealed class OrdersController : ControllerBase { }

// DESCRIBE THE SCHEMA, not just the shape. XML comments become descriptions:
// <PropertyGroup>
//   <GenerateDocumentationFile>true</GenerateDocumentationFile>
//   <NoWarn>$(NoWarn);1591</NoWarn>
// </PropertyGroup>

/// <summary>Creates an order and reserves stock.</summary>
/// <param name="request">The order to create.</param>
/// <response code="201">The order was created.</response>
/// <response code="409">Insufficient stock for one or more lines.</response>
[HttpPost]
public async Task<ActionResult<OrderResponse>> Create(CreateOrder request) => ...;

// MINIMAL APIS — fluent metadata, checked at the call site:
app.MapPost("/orders", CreateOrder)
   .WithName("CreateOrder")            // becomes the generated METHOD NAME
   .WithSummary("Creates an order and reserves stock.")
   .WithTags("Orders")                 // groups endpoints in the UI
   .Produces<OrderResponse>(StatusCodes.Status201Created)
   .ProducesProblem(StatusCodes.Status409Conflict);

// TRANSFORMERS — programmatic edits to the finished document. Use them for
// facts the framework genuinely cannot know:
builder.Services.AddOpenApi(options =>
{
    options.AddDocumentTransformer((document, context, ct) =>
    {
        document.Info = new OpenApiInfo
        {
            Title = "Orders API",
            Version = "v1",
            Contact = new OpenApiContact { Email = "api@example.com" }
        };
        return Task.CompletedTask;
    });

    // Add an example to every response of a given type:
    options.AddSchemaTransformer((schema, context, ct) =>
    {
        if (context.JsonTypeInfo.Type == typeof(DateTimeOffset))
            schema.Example = new OpenApiString("2026-08-03T14:30:00+00:00");
        return Task.CompletedTask;
    });
});

// NULLABILITY reaches the schema automatically from C# nullable annotations —
// `string Name` is required, `string? Notes` is not. This is a real reason to
// keep nullable reference types enabled: it makes the contract self-describing
// with no annotation effort.
Key insight: the value of an OpenAPI document is entirely determined by whether it is generated from executable truth or maintained alongside it. A Results<Ok<T>, NotFound> return type cannot lie — the compiler rejects any path that returns something undeclared. A [ProducesResponseType] attribute is a comment the compiler never checks, so it drifts the first time someone adds a branch in a hurry. Prefer mechanisms the compiler enforces, and treat attributes as a fallback for what the type system cannot express.

Part 3 — Documenting Authentication

// A document without security definitions produces a client that cannot
// authenticate — the single most common reason a generated SDK "does not
// work" on first use.

builder.Services.AddOpenApi(options =>
{
    options.AddDocumentTransformer((document, context, ct) =>
    {
        document.Components ??= new OpenApiComponents();
        document.Components.SecuritySchemes["bearer"] = new OpenApiSecurityScheme
        {
            Type = SecuritySchemeType.Http,
            Scheme = "bearer",
            BearerFormat = "JWT",
            Description = "Paste the access token, without the 'Bearer ' prefix."
        };
        return Task.CompletedTask;
    });

    // Apply the requirement ONLY to endpoints that actually need it, by
    // reading the authorization metadata the framework already computed:
    options.AddOperationTransformer((operation, context, ct) =>
    {
        var requiresAuth = context.Description.ActionDescriptor
            .EndpointMetadata.OfType<IAuthorizeData>().Any();

        if (requiresAuth)
        {
            operation.Security =
            [
                new OpenApiSecurityRequirement
                {
                    [new OpenApiSecurityScheme
                    {
                        Reference = new OpenApiReference
                        {
                            Type = ReferenceType.SecurityScheme,
                            Id = "bearer"
                        }
                    }] = Array.Empty<string>()
                }
            ];

            operation.Responses.TryAdd("401", new OpenApiResponse
            {
                Description = "Authentication required."
            });
        }
        return Task.CompletedTask;
    });
});

// DERIVING the requirement from metadata rather than hardcoding it is the
// point: a new endpoint with [Authorize] is documented as protected
// automatically, and one where the attribute was forgotten shows up as public
// in the document — which makes the document a REVIEW ARTEFACT for security,
// not just for shape.

// OAUTH2 / OIDC, when the API is behind an identity provider:
document.Components.SecuritySchemes["oauth2"] = new OpenApiSecurityScheme
{
    Type = SecuritySchemeType.OAuth2,
    Flows = new OpenApiOAuthFlows
    {
        AuthorizationCode = new OpenApiOAuthFlow
        {
            AuthorizationUrl = new Uri("https://id.example.com/connect/authorize"),
            TokenUrl = new Uri("https://id.example.com/connect/token"),
            Scopes = new Dictionary<string, string>
            {
                ["orders.read"]  = "Read orders",
                ["orders.write"] = "Create and modify orders"
            }
        }
    }
};
// Scopes documented here appear in the UI's authorise dialog, which is how a
// consumer discovers which scopes to request — otherwise that lives only in
// a wiki page nobody finds.

Part 4 — Generating Clients

// Three mainstream generators, with genuinely different trade-offs:
//
//   NSwag           C#/TypeScript. Best .NET integration, MSBuild task,
//                   readable output. Weaker on exotic OpenAPI features.
//   Kiota           Microsoft's current direction. Many languages, fluent
//                   request builders, good auth story. Verbose output.
//   openapi-generator  JVM-based, supports ~50 languages. Widest coverage,
//                   most configuration, output quality varies by language.

// NSwag as a build step — the client is regenerated on every build, so it
// CANNOT drift from the contract:
// <Target Name="GenerateClient" BeforeTargets="Build">
//   <Exec Command="nswag openapi2csclient /input:openapi.json
//                  /namespace:Orders.Client /output:OrdersClient.cs" />
// </Target>

// Kiota:
//   kiota generate -l csharp -d openapi.json -o ./Client -n Orders.Client

// WHAT MAKES A GENERATED CLIENT GOOD OR USELESS:
//
//   OPERATION IDS become method names. Unset, they are generated from the
//   route and produce names like `Api_V1_Orders_GetById_2`. Set them:
app.MapGet("/orders/{id:int}", GetOrder).WithName("GetOrderById");
//   → client.GetOrderByIdAsync(42)   ✓ readable, stable
//
//   DUPLICATE operation ids silently produce broken or renamed methods, and
//   the generator often does not warn. Enforce uniqueness in CI.
//
//   SCHEMA NAMES become type names. Two DTOs with the same class name in
//   different namespaces collide into `Product` and `Product2`.
//
//   MISSING response types produce `Task<object>` or `Task<string>`, which
//   pushes deserialization back onto the caller — defeating the purpose.

// CONSUMING a generated client with correct DI and resilience:
builder.Services.AddHttpClient<IOrdersClient, OrdersClient>(http =>
{
    http.BaseAddress = new Uri(config["Orders:BaseUrl"]!);
})
.AddStandardResilienceHandler();
// The generated client takes an HttpClient, so it participates in
// IHttpClientFactory pooling, DNS rotation and resilience policies — do not
// let it construct its own.

// SERVER-SIDE CONTRACT-FIRST is the inverse approach: write the OpenAPI
// document by hand, generate server stubs AND clients from it. Better when
// multiple teams negotiate a contract before implementation; heavier
// ceremony when one team owns both sides. Code-first (everything above) suits
// most services; contract-first suits organisational boundaries.

Part 5 — The Document as a Contract Test

// This is where OpenAPI stops being documentation and becomes a safety net.

// 1. SNAPSHOT THE DOCUMENT IN CI — any unintended change fails the build:
[Fact]
public async Task OpenApi_document_has_not_changed_unexpectedly()
{
    var client = _factory.CreateClient();
    var actual = await client.GetStringAsync("/openapi/v1.json");

    var expected = await File.ReadAllTextAsync("Snapshots/openapi-v1.json");

    // A diff here is not necessarily a failure — it is a PROMPT. Either the
    // change was intended (update the snapshot, note it in the changelog) or
    // it was accidental (a DTO field renamed without anyone realising it was
    // on the wire).
    Assert.Equal(Normalize(expected), Normalize(actual));
}

// 2. ASSERT SPECIFIC INVARIANTS that matter more than the whole document:
[Fact]
public async Task Every_endpoint_declares_its_error_responses()
{
    var doc = await GetOpenApiDocumentAsync();

    foreach (var (path, item) in doc.Paths)
        foreach (var (method, operation) in item.Operations)
        {
            Assert.True(operation.Responses.ContainsKey("400")
                     || operation.Responses.ContainsKey("404")
                     || method == OperationType.Get,
                $"{method} {path} declares no error responses.");
        }
}

[Fact]
public async Task No_endpoint_returns_an_untyped_response()
{
    var doc = await GetOpenApiDocumentAsync();

    foreach (var (path, item) in doc.Paths)
        foreach (var (method, op) in item.Operations)
            foreach (var (code, response) in op.Responses)
            {
                if (code.StartsWith('2') && response.Content.Count > 0)
                    Assert.All(response.Content.Values, c =>
                        Assert.NotNull(c.Schema?.Reference ?? c.Schema?.Type as object));
            }
}
// This catches the IActionResult problem from Part 1 automatically, across
// every endpoint, instead of relying on review to notice.

// 3. DETECT BREAKING CHANGES between versions, mechanically:
//      npx @useoptic/openapi-diff  or  oasdiff breaking old.json new.json
//   Run it in CI against the previous release's document. A removed field or
//   a narrowed type fails the pipeline, which is far more reliable than
//   expecting a reviewer to spot it in a DTO diff.

// 4. THE SECURITY REVIEW ANGLE — the document lists every endpoint and
//    whether it requires authorization. Diffing that list per release is one
//    of the cheapest ways to catch an accidentally public endpoint:
[Fact]
public async Task No_endpoint_became_unexpectedly_public()
{
    var doc = await GetOpenApiDocumentAsync();
    var publicEndpoints = doc.Paths
        .SelectMany(p => p.Value.Operations.Select(o => $"{o.Key} {p.Key}"))
        .Where(_ => /* operation.Security is empty */ true)
        .ToHashSet();

    var expected = new HashSet<string> { "Get /health", "Post /api/v1/auth/token" };
    Assert.Equal(expected, publicEndpoints);
}

Part 6 — Exposure, Versioning, and Practical Hygiene

// SHOULD THE DOCUMENT BE PUBLIC? It depends on the API's audience, and the
// reasoning is not "security through obscurity is worthless".
//
//   PUBLIC API      publish it. It IS the documentation, and consumers need
//                   it to generate clients.
//   PARTNER API     publish behind authentication. Partners need it; the
//                   world does not.
//   INTERNAL API    do NOT expose in production. It enumerates every endpoint,
//                   parameter and schema — a complete map for an attacker,
//                   including endpoints they would never have found.
//
// Obscurity is not a control, but reducing an attacker's information is still
// worth doing when the document has no legitimate production audience:
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
    app.MapScalarApiReference();      // or Swagger UI
}
// For internal APIs, generate the document at BUILD time and publish it to an
// internal portal, rather than serving it from production at runtime.

// VERSIONED DOCUMENTS — one per API version:
foreach (var description in app.DescribeApiVersions())
    app.MapOpenApi($"/openapi/{description.GroupName}.json");

// UI OPTIONS in 2026:
//   Scalar          modern, fast, good defaults      app.MapScalarApiReference()
//   Swagger UI      familiar, heavier                app.UseSwaggerUI()
//   Redoc           read-optimised, no "try it"      documentation sites
// Swashbuckle is no longer the default in the .NET templates; the built-in
// AddOpenApi plus a UI package is the current path.

// PRACTICAL HYGIENE, in rough order of payoff:
//   • set an explicit operation id on every endpoint (WithName) — generated
//     method names depend on it and default names are unusable
//   • give DTOs distinct names across namespaces to avoid `Product2`
//   • enable nullable reference types so required/optional is accurate for free
//   • serialize enums as strings, or the schema documents meaningless integers
//   • declare error responses globally rather than per action
//   • exclude internal endpoints: .ExcludeFromDescription() or [ApiExplorerSettings(IgnoreApi = true)]
//   • commit the generated document to source control so its diff appears in
//     every pull request — a contract change becomes visible in review rather
//     than being discovered by a consumer

Interview Questions

Beginner: What is OpenAPI and where does the document come from in ASP.NET Core?

OpenAPI is a machine-readable specification describing an HTTP API's endpoints, parameters, request and response schemas, and security requirements. In ASP.NET Core the document is generated at runtime by the API Explorer, which walks the registered endpoints and reads what the framework already knows: the route templates and HTTP methods from routing, parameter binding sources from the signatures, and authorization requirements from endpoint metadata. Response types are the exception — those are inferred from return types and attributes, which is why they are the part most likely to be wrong. Modern .NET exposes this through AddOpenApi and MapOpenApi, without needing Swashbuckle.

Beginner: Why does returning IActionResult weaken the generated document?

Because IActionResult erases the success type. The generator can see that the action returns some action result but has no way to know it produces a Product on success or that a 404 is possible, so it documents a 200 with an unknown schema and omits the 404 entirely. A client generated from that gets a method returning object or string, pushing deserialization back onto the caller and providing no typed error handling. Using ActionResult<Product> restores the success type, and adding [ProducesResponseType] declares the other status codes.

Mid: Why are typed results preferable to [ProducesResponseType] attributes?

Because the compiler enforces them. A Results<Ok<Product>, NotFound> return type means every code path must return one of those declared results — adding a conflict branch without updating the signature is a build error, so the document cannot drift from the implementation. [ProducesResponseType] is a parallel declaration that nothing verifies: deleting the 404 branch leaves the attribute happily advertising a response the endpoint can no longer produce, and nothing fails until a consumer notices. Attributes remain necessary in controllers for status codes the type system cannot express, but the general principle is to prefer mechanisms where the compiler is the one keeping the documentation honest.

Mid: Should an OpenAPI document be exposed in production?

It depends on the audience. For a public API the document is the product documentation and should absolutely be served, since consumers need it to generate clients. For a partner API, serving it behind authentication gives partners access without publishing it broadly. For an internal API I would not expose it in production, because it enumerates every endpoint, parameter and schema — a complete map including administrative endpoints an attacker would otherwise have to discover. That is not a claim that obscurity is a security control; the controls are authentication and authorization regardless. It is that when a document has no legitimate production audience, publishing it only lowers the cost of reconnaissance. The practical approach is to generate it at build time and publish it to an internal portal, keeping the runtime endpoint to Development only.

Senior: A generated client is unusable — object return types and names like Api_Orders_Get_2. Diagnose.

Both symptoms come from an under-specified document rather than a generator problem. The object returns mean endpoints declare no response schema, almost certainly because actions return bare IActionResult or Task<IActionResult> with no [ProducesResponseType], so the API Explorer has nothing to describe. The mangled method names mean operation ids are unset, so the generator synthesises them from route segments and disambiguates collisions with numeric suffixes — the trailing _2 specifically indicates a duplicate, meaning two endpoints produced the same synthesised id. The fixes are to give every endpoint an explicit stable id via WithName or [EndpointName], and to make responses typed, preferring Results<Ok<T>, NotFound> in minimal APIs or ActionResult<T> plus attributes in controllers. I would also check for duplicate DTO class names across namespaces, since those generate colliding schema names and produce Product and Product2 in the client. Then I would prevent recurrence rather than just fixing the instance: a CI test asserting that every operation has a unique id and every 2xx response with content has a schema reference turns this from a recurring complaint into a build failure, because the underlying cause is that nothing was checking the document at all.

Senior: How would you use OpenAPI to prevent breaking changes reaching consumers?

I would treat the document as a build artefact under version control rather than as generated decoration, because that single change makes contract drift visible in code review — a renamed DTO property shows up as a diff in the committed document in the same pull request that caused it, instead of being discovered by a consumer weeks later. On top of that I would run an automated breaking-change diff in CI, using a tool like oasdiff or Optic, comparing the current document against the last released one and failing the build on removals, type narrowings, newly-required request fields or removed status codes. That is far more reliable than expecting a reviewer to notice that a nullable field became non-nullable. I would add targeted invariant tests beyond the diff: every operation has a unique operation id, every success response with content has a schema, and every endpoint declares its error responses — these catch the under-specification that makes generated clients useless before it ships. I would also diff the set of endpoints lacking security requirements between releases, which is one of the cheapest available detectors for an accidentally public endpoint, since the document reflects the authorization metadata the framework actually computed rather than what someone believes is configured. For consumers I would publish the document per version and generate clients from it in their build, so a contract change surfaces as a compilation error on their side rather than a runtime deserialization failure. The overall philosophy is that the document is executable truth derived from the code, so every check I can run against it is a check against reality — which is exactly why the code must be written so the document is accurate in the first place, with typed results rather than attributes that drift.

Solution 
app.MapGet("/products/{id:int}",
    async Task<Results<Ok<Product>, NotFound>> (
        int id, ProductService products, CancellationToken ct) =>
    {
        var product = await products.FindAsync(id, ct);
        return product is null
            ? TypedResults.NotFound()
            : TypedResults.Ok(product);
    })
    .WithName("GetProductById");       // → client.GetProductByIdAsync(42)

// with the Product schema and 404 with no body — with zero attributes.
//
// The compiler enforces it: adding a `return TypedResults.Conflict();` branch
// without declaring Conflict in the union is a BUILD ERROR. That is the whole
// advantage over [ProducesResponseType], which would silently keep claiming
// the old set.
3 (medium): Add JWT bearer authentication to the document so only protected endpoints show a security requirement.
Solution 
builder.Services.AddOpenApi(options =>
{
    // 1. Declare the scheme once.
    options.AddDocumentTransformer((document, context, ct) =>
    {
        document.Components ??= new OpenApiComponents();
        document.Components.SecuritySchemes["bearer"] = new OpenApiSecurityScheme
        {
            Type = SecuritySchemeType.Http,
            Scheme = "bearer",
            BearerFormat = "JWT",
            Description = "Access token without the 'Bearer ' prefix."
        };
        return Task.CompletedTask;
    });

    // 2. Apply it per operation, DERIVED from real authorization metadata.
    options.AddOperationTransformer((operation, context, ct) =>
    {
        var requiresAuth = context.Description.ActionDescriptor
            .EndpointMetadata.OfType<IAuthorizeData>().Any();

        if (!requiresAuth) return Task.CompletedTask;

        operation.Security =
        [
            new OpenApiSecurityRequirement
            {
                [new OpenApiSecurityScheme
                {
                    Reference = new OpenApiReference
                    {
                        Type = ReferenceType.SecurityScheme, Id = "bearer"
                    }
                }] = Array.Empty<string>()
            }
        ];

        operation.Responses.TryAdd("401",
            new OpenApiResponse { Description = "Authentication required." });

        return Task.CompletedTask;
    });
});

// DERIVING from IAuthorizeData rather than hardcoding a list is what makes
// this maintainable AND useful as a security review artefact: a new endpoint
// with [Authorize] is documented as protected automatically, and an endpoint
// where someone forgot the attribute appears as PUBLIC in the document —
// visible in the committed diff.

    http.Timeout = TimeSpan.FromSeconds(30);

// WHY THIS REGISTRATION AND NOT `new OrdersClient(new HttpClient())`:
//   • IHttpClientFactory pools handlers → no socket exhaustion
//   • handlers rotate → DNS changes are observed
//   • resilience policies apply to every call
//   • the interface is a test seam — substitute a fake, no HTTP involved
//
// generateClientInterfaces:true is what produces IOrdersClient. Without it,
// consumers depend on the concrete generated class and cannot fake it.
//
// CAUTION: the resilience handler RETRIES, so any non-idempotent call needs
// an idempotency key or retries will duplicate the operation.
5 (hard): Write CI checks that catch under-specified endpoints before they reach client generation.
Solution 
public class OpenApiContractTests(WebApplicationFactory<Program> factory)
    : IClassFixture<WebApplicationFactory<Program>>
{
    private async Task<OpenApiDocument> GetDocumentAsync()
    {
        var json = await factory.CreateClient().GetStringAsync("/openapi/v1.json");
        return new OpenApiStringReader().Read(json, out _);
    }

    [Fact]
    public async Task Every_operation_has_a_unique_explicit_id()
    {
        var doc = await GetDocumentAsync();
        var ids = new List<string>();

        foreach (var (path, item) in doc.Paths)
            foreach (var (method, op) in item.Operations)
            {
                Assert.False(string.IsNullOrWhiteSpace(op.OperationId),
                    $"{method} {path} has no operationId — generated client "
                  + "methods will be named from the route.");
                ids.Add(op.OperationId);
            }

        // Duplicates silently produce renamed or broken client methods.
        Assert.Equal(ids.Count, ids.Distinct().Count());
    }

    [Fact]
    public async Task Every_success_response_with_content_has_a_schema()
    {
        var doc = await GetDocumentAsync();

        foreach (var (path, item) in doc.Paths)
            foreach (var (method, op) in item.Operations)
                foreach (var (code, response) in op.Responses)
                {
                    if (!code.StartsWith('2')) continue;

                    foreach (var (mediaType, content) in response.Content)
                        Assert.True(
                            content.Schema?.Reference is not null
                            || content.Schema?.Type is not null,
                            $"{method} {path} → {code} has no schema. This "
                          + "generates a client returning `object`.");
                }
    }

    [Fact]
    public async Task Public_endpoints_are_exactly_the_expected_set()
    {
        var doc = await GetDocumentAsync();

        var actual = doc.Paths
            .SelectMany(p => p.Value.Operations
                .Where(o => o.Value.Security is null or { Count: 0 })
                .Select(o => $"{o.Key} {p.Key}"))
            .ToHashSet();

        // A new unprotected endpoint FAILS THE BUILD and must be added here
        // deliberately — turning "we forgot [Authorize]" into a review moment.
        var expected = new HashSet<string>
        {
            "Get /health",
            "Post /api/v1/auth/token"
        };

        Assert.Equal(expected, actual);
    }
}

// These three catch, respectively: unusable generated method names, clients
// returning `object`, and accidentally public endpoints. All three are
// currently found by consumers or by security review — moving them into CI
// is close to free and catches them at the commit that causes them.
6 (hard): Design the workflow so a breaking change cannot reach consumers unnoticed.
Solution 
// ── 1. COMMIT THE DOCUMENT ───────────────────────────────────────────────
// Generate at build time and check it in. This single step makes contract
// drift visible in code review: renaming a DTO property produces a diff in
// api/openapi-v1.json in the SAME pull request.
<Target Name="ExportOpenApi" AfterTargets="Build"
        Condition="'$(Configuration)'=='Debug'">
  <Exec Command="dotnet run --no-build -- --export-openapi api/openapi-v1.json" />
</Target>

// ── 2. FAIL CI ON BREAKING CHANGES ───────────────────────────────────────
// oasdiff compares against the last RELEASED document, not the previous
// commit — what matters is what consumers currently have.
//
// .github/workflows/api-contract.yml
//   - name: Detect breaking changes
//     run: |
//       curl -sL "$RELEASED_SPEC_URL" -o released.json
//       oasdiff breaking released.json api/openapi-v1.json --fail-on ERR
//
// Catches: removed fields, narrowed types, newly-required request fields,
// removed status codes, removed endpoints — all of which a human reviewer
// reliably misses in a large DTO diff.

// ── 3. REQUIRE AN EXPLICIT DECISION TO BREAK ─────────────────────────────
// The CI failure is overridable only by a labelled PR:
//   - if: contains(github.event.pull_request.labels.*.name, 'breaking-change')
//     run: echo "Breaking change acknowledged; version bump required."
// The label forces the conversation: is this genuinely necessary, and does it
// need a new API version? A silent break becomes impossible; a deliberate one
// stays possible.

// ── 4. CONSUMER-SIDE GENERATION ──────────────────────────────────────────
// Consumers regenerate their client from the published document in their own
// build, so a contract change surfaces as a COMPILE error on their side
// rather than a runtime deserialization failure in production.

// ── 5. CONTRACT TESTS FROM REAL TRAFFIC ──────────────────────────────────
// The gap the document cannot close: it describes what the API CLAIMS, not
// what consumers actually depend on. Record real request/response pairs from
// a sample of production traffic and replay them against each build. This
// catches dependencies on undocumented behaviour — a field consumers rely on
// that was never in the spec, or an error shape they parse.

// ── 6. VERSION WHEN THE DIFF SAYS SO ─────────────────────────────────────
// If step 2 reports a genuine break that cannot be made additive, that is the
// signal to cut a new API version rather than to override the check.

// ── WHY THIS ORDERING ────────────────────────────────────────────────────
// Each layer catches what the previous one misses:
//   committed document  → visible in review (catches the obvious)
//   oasdiff             → mechanical (catches what reviewers miss)
//   label gate          → forces a decision (catches "I'll just fix it")
//   consumer generation → compile-time on their side (catches integration)
//   traffic replay      → catches dependencies on UNDOCUMENTED behaviour
// The last one matters most in mature APIs, because the real contract is
// always slightly larger than the written one.

🎯 Key Takeaways

  • The document is generated by the API Explorer from routing, signatures and metadata — everything except response types is derived from fact.
  • Response types are inferred, so IActionResult produces an untyped schema and a generated client returning object.
  • Prefer Results<T1,T2> and ActionResult<T>: the compiler enforces them, so they cannot drift as attributes do.
  • Declare error responses globally via convention rather than repeating attributes on every action.
  • Without a security scheme, generated clients cannot authenticate — derive requirements from real authorization metadata so the document doubles as a security review artefact.
  • Operation ids become client method names; unset ids produce unusable names and duplicates silently break generation.
  • Register generated clients through AddHttpClient so they get pooling, DNS rotation and resilience.
  • Do not serve the document from an internal production API — generate it at build time for an internal portal instead.
  • Commit the document so contract changes appear in pull-request diffs, and run a breaking-change diff in CI.
  • The written contract is always smaller than the real one; replaying recorded traffic catches dependencies the document never described.
