How ASP.NET Core Runs Foundations

What you'll master: the model underneath every ASP.NET Core app — the host, the WebApplicationBuilder, the two-phase startup that trips people up, Kestrel and reverse proxies, and how a request actually becomes a response. Everything later in this track is a specialization of what happens here. Prerequisites: C# fundamentals — see the .NET track.

Part 1 — The Six Lines, and What Each One Is

var builder = WebApplication.CreateBuilder(args);   // 1. CONFIGURE phase
builder.Services.AddSingleton<IClock, SystemClock>();

var app = builder.Build();                          // 2. the point of no return
app.MapGet("/health", () => Results.Ok(new { ok = true }));   // 3. RUN phase
app.Run();

// Four objects do all the work:
//
// WebApplicationBuilder — the CONFIGURE phase. Two properties matter:
//   builder.Services       the DI container registrations
//   builder.Configuration  appsettings, env vars, secrets, CLI args
//
// WebApplication — the RUN phase. Also two roles:
//   app.Use*/app.Map*      the middleware pipeline and endpoints
//   app.Services           the BUILT container (resolve, don't register)
//
// THE RULE THAT CATCHES EVERYONE: after builder.Build(), the service
// collection is frozen. Registering a service on app.Services throws, because
// the container has already been constructed from the collection. Configure
// before Build; use after. If you find yourself wanting to register something
// late, what you actually want is a factory or an options callback.

// CreateBuilder is not magic — it applies defaults you would otherwise write:
//   • configuration sources, in precedence order (lowest → highest):
//       appsettings.json → appsettings.{Environment}.json → user secrets
//       (Development only) → environment variables → command line args
//   • logging providers (console, debug, event source)
//   • Kestrel as the web server, with IIS integration on Windows
//   • DI container, hosted-service support, and the environment abstraction
// CreateSlimBuilder() drops some of these for smaller, faster startup —
// useful for containers and AOT, and worth knowing exists.

Part 2 — The Host and the Lifecycle

// Underneath WebApplication is the GENERIC HOST — the thing that owns
// startup, shutdown, DI, configuration, and logging for any .NET app
// (web, worker service, or console). A web app is a host that happens to
// listen on a port.

// The host manages IHostedService, which is how anything long-running
// participates in the lifecycle:
public class WarmupService(IServiceProvider sp, ILogger<WarmupService> log)
    : IHostedService
{
    public async Task StartAsync(CancellationToken ct)
    {
        // Runs BEFORE the server starts accepting requests. Blocking here
        // delays startup — which is deliberate for warmup, and a problem if
        // you accidentally do slow work.
        using var scope = sp.CreateScope();          // ← see Part 5
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Database.CanConnectAsync(ct);
        log.LogInformation("warmup complete");
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}
builder.Services.AddHostedService<WarmupService>();

// Shutdown ordering, which matters for not dropping requests:
//   1. SIGTERM arrives (or Ctrl+C)
//   2. IHostApplicationLifetime.ApplicationStopping fires
//   3. the server stops accepting NEW connections
//   4. in-flight requests get ShutdownTimeout to finish (default 30s)
//   5. IHostedService.StopAsync runs, in REVERSE registration order
//   6. the DI container is disposed
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(45));

// Reverse order on shutdown is intentional and useful: services registered
// later can depend on earlier ones, so tearing down in reverse means a
// dependency is still alive while its dependents stop.

Part 3 — Kestrel, Reverse Proxies, and Forwarded Headers

// Kestrel is the cross-platform HTTP server built into ASP.NET Core. It is
// fast and production-capable, and it is usually deployed BEHIND a reverse
// proxy (nginx, IIS, YARP, or a cloud load balancer) for TLS termination,
// request buffering, and static-file serving.

builder.WebHost.ConfigureKestrel(o =>
{
    o.Limits.MaxRequestBodySize = 10 * 1024 * 1024;             // 10MB
    o.Limits.RequestHeadersTimeout = TimeSpan.FromSeconds(10);  // slowloris
    o.Limits.MaxConcurrentConnections = 1000;
    o.Limits.KeepAliveTimeout = TimeSpan.FromSeconds(130);
});

// BEHIND A PROXY, THE PROXY'S ADDRESS IS THE CLIENT ADDRESS — unless you
// tell ASP.NET Core otherwise. Consequences if you forget: rate limiting
// buckets every user together, logs record one IP forever, and
// HttpContext.Request.Scheme says "http" so generated links and redirects
// come out as http on an https site.
app.UseForwardedHeaders(new ForwardedHeadersOptions
{
    ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto,
    // Trust ONLY your known proxies. The default trusts loopback only, which
    // is why this silently does nothing in Kubernetes until configured.
    KnownNetworks = { new IPNetwork(IPAddress.Parse("10.0.0.0"), 8) },
});
// Trusting arbitrary proxies lets a client spoof X-Forwarded-For and defeat
// any IP-based logic. Configure trust to match your real topology — the
// same reasoning as `trust proxy` in Node.

// UseForwardedHeaders must run EARLY, before anything reads the scheme or
// the remote IP. Middleware order is covered in the pipeline lesson, but
// this is the first place order changes behaviour rather than performance.
ASPNETCORE_ENVIRONMENT drives more than you think. It selects appsettings.{Environment}.json, enables user secrets and the developer exception page in Development, and is what app.Environment.IsDevelopment() reads. The values Development, Staging, and Production are conventions, not an enum — a typo like "Prod" silently means "not Production", so the developer exception page stays off but Production-only branches never run either.

Part 4 — The Request Journey

// A request from socket to response:
//
//  1. Kestrel accepts the connection, parses the HTTP request
//  2. an HttpContext is created — Request, Response, User, Items, and the
//     REQUEST SERVICES scope (a fresh DI scope per request)
//  3. the middleware pipeline runs, in registration order
//  4. UseRouting matches the request to an endpoint (but does not run it)
//  5. middleware between UseRouting and the endpoint can now SEE the chosen
//     endpoint — this is exactly why authorization sits there: it needs to
//     know which endpoint was matched to read its [Authorize] metadata
//  6. the endpoint executes (a minimal API delegate or a controller action)
//  7. the result is written to the response
//  8. the pipeline unwinds in reverse; the request scope is disposed

app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(context);                       // ← everything downstream
    // Runs AFTER the response is produced, on the way back out.
    logger.LogInformation("{Method} {Path} {Status} {Ms}ms",
        context.Request.Method, context.Request.Path,
        context.Response.StatusCode, sw.ElapsedMilliseconds);
});

// The pipeline is nested, not sequential: each middleware WRAPS the rest.
// So the code before `await next()` runs on the way in, and the code after
// runs on the way out — which is why exception handling and timing
// middleware go first: outermost sees everything.
//
// HttpContext.Items is a per-request dictionary for passing data between
// middleware — request-scoped state without touching DI.
// HttpContext.RequestAborted is a CancellationToken that fires when the
// client disconnects; pass it to every async call and abandoned requests
// stop doing work.

Part 5 — Service Lifetimes (the Preview That Prevents Bugs)

builder.Services.AddSingleton<IClock, SystemClock>();      // one, forever
builder.Services.AddScoped<IOrderService, OrderService>(); // one per REQUEST
builder.Services.AddTransient<IEmailSender, EmailSender>();// one per injection

// Scoped is the default choice for anything touching a request, and
// DbContext is registered scoped by AddDbContext for a reason: it is not
// thread-safe and holds per-request change-tracking state.

// THE CAPTIVE DEPENDENCY BUG — the most common DI error in ASP.NET Core:
public class Cache(AppDbContext db) { }          // ❌ singleton holding scoped
builder.Services.AddSingleton<Cache>();
// The singleton captures the FIRST request's DbContext and keeps it alive
// forever: you get a disposed-object exception, or worse, concurrent use of
// one non-thread-safe context across requests. In Development the container
// validates scopes and throws at startup, which is why it often surfaces
// only after deploying to Production — where validation is off by default.
builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;        // ← turn on in ALL environments
    o.ValidateOnBuild = true;       // catch missing registrations at startup
});

// The correct pattern when a singleton needs scoped work: create a scope.
public class Cache(IServiceScopeFactory scopeFactory)
{
    public async Task<Order?> LoadAsync(int id)
    {
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        return await db.Orders.FindAsync(id);
    }
}
// Full treatment in the DI lesson; it appears here because getting lifetimes
// wrong produces confusing failures long before you reach that page.

Part 6 — A Realistic Program.cs

var builder = WebApplication.CreateBuilder(args);

// ---- CONFIGURE ----
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseNpgsql(builder.Configuration.GetConnectionString("Default")));
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddProblemDetails();          // RFC 9457 error responses
builder.Services.AddHealthChecks().AddDbContextCheck<AppDbContext>();
builder.Services.AddAuthentication().AddJwtBearer();
builder.Services.AddAuthorization();

var app = builder.Build();

// ---- PIPELINE (order is behaviour, not preference) ----
app.UseForwardedHeaders();                     // before anything reads IP/scheme
app.UseExceptionHandler();                     // outermost: catches everything below
if (!app.Environment.IsDevelopment()) app.UseHsts();
app.UseHttpsRedirection();
app.UseRouting();                              // decide WHICH endpoint
app.UseAuthentication();                       // who are you
app.UseAuthorization();                        // may you — needs the endpoint
app.MapControllers();
app.MapHealthChecks("/health/ready");
app.MapGet("/health/live", () => Results.Ok());

app.Run();

// Two invariants worth memorizing now, because both fail silently:
//   • UseAuthorization must come AFTER UseRouting, or there is no endpoint
//     to read [Authorize] from — and it fails OPEN, serving protected
//     endpoints to anonymous callers with no error anywhere.
//   • UseExceptionHandler goes near the top, because it only catches
//     exceptions thrown by middleware registered after it.

Interview Questions

Beginner: What is the difference between builder.Services and app.Services?

builder.Services is the service collection — a mutable list of registrations during the configure phase. app.Services is the built service provider, the container constructed from that list when builder.Build() is called. You register on the first and resolve from the second; attempting to register after Build() throws because the container already exists. That split is what makes the two-phase startup model explicit.

Beginner: What does WebApplication.CreateBuilder set up for you?

It applies the standard defaults: configuration sources in precedence order — appsettings.json, the environment-specific appsettings file, user secrets in Development, environment variables, then command line arguments — plus logging providers, the DI container, Kestrel as the server, IIS integration on Windows, and the hosting environment abstraction. None of it is magic; it is the boilerplate you would otherwise write, and CreateSlimBuilder exists for when you want less of it.

Mid: Why must UseAuthorization come after UseRouting?

Because authorization decisions depend on endpoint metadata — the [Authorize] attributes and policies attached to the matched endpoint — and UseRouting is what performs the match and places the endpoint on the context. Registered before routing, the authorization middleware runs when no endpoint has been selected, so it finds no metadata and permits the request. The critical property is that it fails open: protected endpoints serve anonymous callers with no exception and nothing in the logs, so it is a security bug that testing an authenticated happy path will never reveal.

Mid: What is a captive dependency and how do you avoid it?

A longer-lived service capturing a shorter-lived one — typically a singleton injecting a scoped DbContext. The singleton holds the first request's instance forever, so you get ObjectDisposedException, or silently worse, one non-thread-safe context shared across concurrent requests. The fix is to inject IServiceScopeFactory and create a scope per unit of work, or use IDbContextFactory. Enable ValidateScopes and ValidateOnBuild in every environment, not just Development, so the container throws at startup rather than letting the bug reach production where validation is off by default.

Senior: A service works locally but behind a load balancer produces http redirect URLs and rate-limits all users as one. Diagnose.

Both symptoms come from one cause: forwarded headers are not being honoured, so ASP.NET Core sees the proxy rather than the client. Request.Scheme is http because TLS terminated at the proxy and the hop to Kestrel is plaintext, so any generated absolute URL or redirect comes out as http — which browsers may block as mixed content or which breaks OAuth redirect URIs. Meanwhile Connection.RemoteIpAddress is the proxy's address, so per-IP rate limiting places every user in one bucket. The fix is UseForwardedHeaders processing X-Forwarded-For and X-Forwarded-Proto, registered early enough that nothing reads the scheme or IP before it. The subtlety that makes this a recurring production issue is trust configuration: the middleware defaults to trusting only loopback, so in Kubernetes or behind a cloud load balancer it appears to do nothing until KnownNetworks or KnownProxies is configured. Trusting everything is the wrong correction, since a client could then send its own X-Forwarded-For and defeat any IP-based control. Trust must mirror the actual topology.

Senior: How would you structure Program.cs for a large application, and what belongs in the host lifecycle?

I would keep Program.cs as a readable table of contents rather than an implementation dump: grouped registration extension methods per feature area — AddPersistence, AddAuthN, AddObservability — each in its own file near the code it configures, so adding a feature touches one place and the startup file still shows the shape of the application at a glance. The pipeline stays explicit and in one block, because order is behaviour and hiding it behind helpers makes a security-relevant sequence unreviewable. For the lifecycle, IHostedService start work should be limited to things that must complete before traffic arrives — verifying connectivity, warming a critical cache — since anything slow there delays readiness during every rollout; genuinely long-running work belongs in BackgroundService so it starts and then yields. On shutdown I would set ShutdownTimeout above the longest expected in-flight request and below the orchestrator's grace period, and make sure background workers observe the stopping token so they finish rather than being killed mid-operation. I would also enable ValidateOnBuild and ValidateScopes in all environments so misconfiguration fails at startup during the deploy rather than on the first request that hits a bad path.

🏋️ Graded Exercises

1 (easy): Write a minimal app with a /health endpoint and a singleton clock service.
Solution 
public interface IClock { DateTimeOffset UtcNow { get; } }
public sealed class SystemClock : IClock
{
    public DateTimeOffset UtcNow => DateTimeOffset.UtcNow;
}

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<IClock, SystemClock>();

var app = builder.Build();
app.MapGet("/health", (IClock clock) =>
    Results.Ok(new { ok = true, at = clock.UtcNow }));
app.Run();

// The clock is an interface rather than DateTimeOffset.UtcNow inline so
// tests can substitute a fixed time — the same determinism argument as
// injecting the clock in any language. .NET 8 also ships TimeProvider,
// which is the framework's built-in version of exactly this abstraction.
2 (easy): Why does this throw? var app = builder.Build(); app.Services.AddSingleton<IFoo, Foo>();
Solution 
// app.Services is an IServiceProvider — the BUILT container — not an
// IServiceCollection. Build() reads the collection and constructs the
// provider, after which registrations cannot change: existing singletons
// and resolution caches are already fixed.
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<IFoo, Foo>();     // ✅ configure phase
var app = builder.Build();                       // ✅ then build
// If registration genuinely must be deferred, register a FACTORY that
// decides at resolve time, rather than trying to mutate the container.
3 (medium): Write timing middleware that logs method, path, status, and duration.
Solution 
app.Use(async (context, next) =>
{
    var start = Stopwatch.GetTimestamp();
    try
    {
        await next(context);
    }
    finally
    {
        // finally: still logs when a downstream middleware throws, which is
        // exactly when you most want the record.
        var elapsed = Stopwatch.GetElapsedTime(start);
        context.RequestServices
            .GetRequiredService<ILogger<Program>>()
            .LogInformation("{Method} {Path} {Status} {Ms}ms",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds);
    }
});
// Stopwatch.GetTimestamp/GetElapsedTime avoids allocating a Stopwatch per
// request and uses a monotonic clock, so an NTP correction cannot produce a
// negative duration.
// Register EARLY so it measures the whole pipeline, not a fragment of it.
4 (medium): Add a hosted service that verifies database connectivity before traffic is accepted.
Solution 
public sealed class StartupChecks(
    IServiceProvider services,
    ILogger<StartupChecks> logger) : IHostedService
{
    public async Task StartAsync(CancellationToken ct)
    {
        // A singleton hosted service cannot inject the scoped DbContext
        // directly — that is the captive dependency bug. Create a scope.
        using var scope = services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        if (!await db.Database.CanConnectAsync(ct))
            throw new InvalidOperationException("Database unreachable at startup");

        logger.LogInformation("startup checks passed");
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

builder.Services.AddHostedService<StartupChecks>();

// Throwing here aborts startup, so a misconfigured connection string fails
// the deploy instead of surfacing as errors on the first real request.
// Keep this fast: StartAsync runs before the server accepts traffic, so
// slow work here delays every rollout.
5 (hard): Configure forwarded headers correctly for a service behind a Kubernetes ingress. Explain the trust model.
Solution 
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders =
        ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;

    // Defaults trust loopback ONLY, so in a cluster the middleware appears
    // to do nothing until the pod network is trusted explicitly.
    options.KnownNetworks.Clear();
    options.KnownProxies.Clear();
    options.KnownNetworks.Add(new IPNetwork(IPAddress.Parse("10.0.0.0"), 8));

    // How many proxy hops to walk back through. Must match reality: too few
    // and you get the ingress IP; too many and you walk into
    // client-controlled entries.
    options.ForwardLimit = 2;      // e.g. cloud LB → ingress
});

var app = builder.Build();
app.UseForwardedHeaders();         // FIRST — before anything reads IP/scheme

// The trust model: X-Forwarded-For is an append-only list, and any client
// can send one. Entries are only meaningful if a proxy you control appended
// them, so ASP.NET Core walks the list from the RIGHT (nearest hop) and
// accepts entries only while they come from a trusted address. Clearing the
// defaults and adding your real network is what makes that walk work.
//
// Trusting everything (or an unbounded ForwardLimit) means an attacker sends
// "X-Forwarded-For: 1.2.3.4" and becomes whatever IP they choose, defeating
// per-IP rate limiting, IP allowlists, and audit logging. Trust must equal
// the topology — the identical reasoning as `trust proxy` in Node, and
// getting it wrong has the same two failure shapes: everyone shares one
// bucket, or everyone can forge their own.
6 (hard): A singleton injecting AppDbContext works in tests but throws ObjectDisposedException in production. Explain fully and fix.
Solution 
// ❌ The bug
public class OrderCache(AppDbContext db)          // scoped captured by...
{
    public async Task<Order?> GetAsync(int id) => await db.Orders.FindAsync(id);
}
builder.Services.AddSingleton<OrderCache>();      // ...a singleton

// WHY IT THROWS: AddDbContext registers AppDbContext as SCOPED, so the
// instance belongs to one request's scope and is disposed when that request
// ends. The singleton captured that instance and holds it forever, so every
// later call touches a disposed context.
//
// WHY TESTS PASS: a test typically resolves the singleton within a single
// scope that stays alive for the test's duration, so disposal never happens
// mid-use. Concurrency also never occurs, which hides the second, worse
// problem: DbContext is not thread-safe, so before disposal you can get
// concurrent access from multiple requests, producing corrupted change
// tracking and "A second operation was started on this context" errors —
// data-integrity failures rather than clean exceptions.

// ✅ Fix: own the scope
public class OrderCache(IServiceScopeFactory scopeFactory)
{
    public async Task<Order?> GetAsync(int id)
    {
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        return await db.Orders.FindAsync(id);
    }
}

// ✅ Or IDbContextFactory, designed for exactly this:
builder.Services.AddDbContextFactory<AppDbContext>(...);
public class OrderCache(IDbContextFactory<AppDbContext> factory)
{
    public async Task<Order?> GetAsync(int id)
    {
        await using var db = await factory.CreateDbContextAsync();
        return await db.Orders.FindAsync(id);
    }
}

// ✅ And make the whole CLASS of bug impossible to ship:
builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;      // throws at RESOLUTION on lifetime violations
    o.ValidateOnBuild = true;     // throws at STARTUP on missing registrations
});
// These default to on in Development and OFF in Production — which is
// precisely backwards for catching this before users do. Enabling them
// everywhere turns a runtime data-corruption bug into a startup crash
// during the deploy.

🎯 Key Takeaways

  • Startup has two phases: configure the service collection, then Build() freezes it and you resolve from the provider.
  • CreateBuilder is just conventional defaults — configuration precedence, logging, Kestrel, DI — not magic.
  • The generic host owns lifecycle, DI, configuration, and logging; a web app is a host that listens.
  • Middleware wraps rather than sequences: code before next() runs inbound, after it runs outbound.
  • UseRouting selects the endpoint; middleware after it can read endpoint metadata, which is why authorization must follow it.
  • Authorization registered before routing fails open — a silent security bug with no error to notice.
  • Behind a proxy, configure UseForwardedHeaders with trust matching your real topology, or IP and scheme are wrong.
  • Captive dependencies (singleton holding scoped) cause disposal errors and unsafe concurrent DbContext use.
  • Enable ValidateScopes and ValidateOnBuild in every environment, not just Development.
  • HttpContext.RequestAborted lets abandoned requests stop working — thread it through async calls.
