Model Binding & Validation Foundations

What you'll master: how raw HTTP text becomes typed .NET objects, where binding silently succeeds when you wanted it to fail, the three validation approaches and when each is right, RFC 9457 problem details as an error contract, and the over-posting vulnerability that binding makes easy to write and easy to miss. Prerequisites: Minimal APIs and Routing — constraints reject at match time, validation rejects after.

Part 1 — The Binding Sources, and Their Precedence

// Binding answers one question per parameter: which part of the request
// supplies this value? The candidate sources, and what they read:
//
//   route values   /products/{id}          from the matched template
//   query string   ?page=2&sort=name       always strings, always optional
//   request body   JSON (or form)          deserialized, once
//   headers        [FromHeader]            explicit only
//   form fields    multipart/form-data     files and fields
//   services       [FromServices] or type  the DI container
//   special types  HttpContext, ClaimsPrincipal, CancellationToken
//
// MINIMAL APIS infer the source (route → DI → special → query → body).
// CONTROLLERS with [ApiController] infer too, but by different rules:
//   complex types → body, simple types → route/query, IFormFile → form.
// Both let you override with attributes. The attributes mean the same thing in
// both; only the defaults differ.

// EXPLICIT ALWAYS BEATS INFERRED — use it when the inference is wrong or when
// being explicit documents intent for the next reader:
app.MapPost("/import/{jobId:guid}", (
    Guid jobId,                                          // route
    [FromQuery(Name = "dry-run")] bool dryRun,           // query, renamed
    [FromHeader(Name = "X-Correlation-Id")] string? cid, // header
    [FromBody] ImportRequest body,                       // body
    ImportService service) => ...);                      // DI

// ONE BODY PER REQUEST. Two [FromBody] parameters throw at startup, because
// the body is a forward-only stream that gets read once. If you need two
// logical objects, they are one object with two properties.

// Case-insensitivity is the rule everywhere: ?Page=2 and ?page=2 both bind to
// `int page`. Route values, query keys, form fields and JSON properties all
// match case-insensitively by default. Do not rely on casing to distinguish
// two parameters — you cannot.

Part 2 — Where Binding Silently Succeeds

// The dangerous cases are not the ones that throw. They are the ones that
// produce a valid-looking object from missing or malformed input.

// CASE 1 — a missing query parameter binds to default, not an error:
app.MapGet("/search", (int page) => ...);
// GET /search          → page = 0.   Not an error. Your query does
//                        OFFSET (0-1)*20 = -20 and throws in the database.
app.MapGet("/search", (int page = 1) => ...);   // ← state the default

// CASE 2 — a malformed value binds to default in CONTROLLERS:
// GET /search?page=abc → page = 0, and ModelState is invalid. If you do not
// check ModelState (or lack [ApiController]'s automatic 400), the handler runs
// with page=0 as though the client sent it.
// In MINIMAL APIS the same request returns 400 automatically, because binding
// failure has nowhere to record itself and the framework rejects instead.
// THIS IS A REAL BEHAVIOURAL DIFFERENCE between the two models.

// CASE 3 — a JSON body with unknown fields is accepted and ignored:
// POST {"name":"x","isAdmin":true} into a DTO with no IsAdmin property
// binds fine, and the extra field vanishes. That is usually what you want —
// but see Part 5 on over-posting for when it is not.

// CASE 4 — a null body binds to null, not 400, for a nullable parameter:
app.MapPost("/products", (Product? p) => ...);   // POST with no body → p is null
app.MapPost("/products", (Product p) => ...);    // POST with no body → 400
// Making the parameter non-nullable is the cheapest correctness win available.

// CASE 5 — empty string vs missing, for reference types:
// ?q=      → q is ""      (present, empty)
// (absent) → q is null    (missing)
// Treating these the same is usually right and occasionally very wrong —
// "filter by empty name" and "do not filter by name" are different queries.
Key insight: binding's job is shape, validation's job is meaning. Binding answers "can this text become an int"; validation answers "is -5 an acceptable quantity". Conflating them produces the two classic failures: business rules pushed into route constraints, where violations become confusing 404s, and shape errors left to validation, where a malformed request produces a null-reference exception instead of a 400. Keep the boundary sharp and both layers stay simple.

Part 3 — Three Ways to Validate

// APPROACH 1 — DATA ANNOTATIONS. Declarative, on the DTO.
public record CreateProduct(
    [Required, StringLength(100, MinimumLength = 3)] string Name,
    [Range(0.01, 1_000_000)] decimal Price,
    [EmailAddress] string ContactEmail,
    [RegularExpression(@"^[A-Z]{3}$")] string CurrencyCode);

// In CONTROLLERS with [ApiController], these run automatically and an invalid
// model returns 400 + ValidationProblemDetails before the action executes.
// In MINIMAL APIS they do NOT run automatically. This surprises everyone
// migrating. .NET 10 adds AddValidation() to close the gap:
builder.Services.AddValidation();          // opt in, then annotations apply
// On earlier versions, wire an endpoint filter yourself (Part 4).

// Annotations are right for shape-level rules that live with the type and
// need no collaborators: required, length, range, format.

// APPROACH 2 — IVALIDATABLEOBJECT. For rules spanning several properties.
public record DateRange(DateOnly From, DateOnly To) : IValidatableObject
{
    public IEnumerable<ValidationResult> Validate(ValidationContext ctx)
    {
        if (To < From)
            yield return new ValidationResult(
                "To must not be earlier than From.", [nameof(To)]);

        if ((To.DayNumber - From.DayNumber) > 366)
            yield return new ValidationResult(
                "Range must not exceed one year.", [nameof(To)]);
    }
}
// Runs AFTER property-level annotations, and only if those passed — so it can
// assume individual properties are individually valid.

// APPROACH 3 — FLUENTVALIDATION. Separate validator classes, DI-friendly.
public sealed class CreateProductValidator : AbstractValidator<CreateProduct>
{
    public CreateProductValidator(ICurrencyCatalog currencies)
    {
        RuleFor(x => x.Name).NotEmpty().Length(3, 100);
        RuleFor(x => x.Price).GreaterThan(0);

        // The reason to reach for this: the rule needs a DEPENDENCY.
        RuleFor(x => x.CurrencyCode)
            .MustAsync(async (code, ct) => await currencies.ExistsAsync(code, ct))
            .WithMessage("Unknown currency code.");

        // ...and conditional rules read far better than attributes allow:
        When(x => x.Price > 10_000, () =>
            RuleFor(x => x.ContactEmail).NotEmpty()
                .WithMessage("High-value products require a contact."));
    }
}

// CHOOSING: annotations for shape rules on the DTO; IValidatableObject for
// cross-property rules with no dependencies; FluentValidation when rules need
// injected services, async lookups, or conditional composition. Mixing them is
// fine and common — but pick ONE as the default so a reader knows where to
// look for a given rule.

Part 4 — Problem Details: One Error Contract

// RFC 9457 (which obsoleted RFC 7807) defines a standard error body. Using it
// means clients parse ONE shape regardless of which endpoint failed.
builder.Services.AddProblemDetails(options =>
{
    options.CustomizeProblemDetails = ctx =>
    {
        ctx.ProblemDetails.Instance = ctx.HttpContext.Request.Path;
        ctx.ProblemDetails.Extensions["traceId"] =
            Activity.Current?.Id ?? ctx.HttpContext.TraceIdentifier;
    };
});

// A validation failure produces this shape:
// HTTP 400
// Content-Type: application/problem+json
// {
//   "type":   "https://tools.ietf.org/html/rfc9110#section-15.5.1",
//   "title":  "One or more validation errors occurred.",
//   "status": 400,
//   "instance": "/api/products",
//   "traceId": "00-8f2c...-01",
//   "errors": {
//     "Name":  ["The Name field is required."],
//     "Price": ["The field Price must be between 0.01 and 1000000."]
//   }
// }
//
// The `errors` dictionary is keyed by property path, which is what lets a
// client highlight the offending form field rather than showing one blob.
// traceId is the field that turns a user's screenshot into a log query — it
// is worth more in production than any other part of this response.

// A reusable validation filter for minimal APIs:
public sealed class ValidationFilter<T>(IValidator<T> validator)
    : IEndpointFilter where T : class
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        if (ctx.Arguments.OfType<T>().FirstOrDefault() is not { } model)
            return await next(ctx);

        var result = await validator.ValidateAsync(model, ctx.HttpContext.RequestAborted);
        if (!result.IsValid)
            return TypedResults.ValidationProblem(result.ToDictionary());

        return await next(ctx);
    }
}

// 400 vs 422 — the question that starts arguments:
//   400 Bad Request        the request is MALFORMED: invalid JSON, wrong type,
//                          a string where a number belongs. Parsing failed.
//   422 Unprocessable      the request PARSED but the content is semantically
//                          wrong: a valid date that is in the past, a quantity
//                          exceeding stock.
// ASP.NET Core defaults to 400 for both, which is defensible and what most
// clients expect. If you adopt 422 for semantic failures, apply it
// consistently across every endpoint — a mixed convention is worse than
// either convention chosen wholesale.

Part 5 — Over-Posting: the Vulnerability Binding Hands You

// Binding a request straight onto an entity is convenient and is a privilege
// escalation vulnerability.

public class User                       // the ENTITY
{
    public int Id { get; set; }
    public string Email { get; set; } = "";
    public string DisplayName { get; set; } = "";
    public bool IsAdmin { get; set; }          // ← the problem
    public decimal AccountBalance { get; set; }
}

// VULNERABLE — binds every public settable property, including IsAdmin:
app.MapPut("/users/{id:int}", async (int id, User user, AppDbContext db) =>
{
    db.Update(user);                    // attacker sends {"isAdmin":true}
    await db.SaveChangesAsync();        // and is now an admin
    return TypedResults.NoContent();
});
// The endpoint LOOKS correct. There is no missing null check, no injection,
// nothing a linter flags. The bug is that the binding surface is the entity's
// full shape rather than what the caller is permitted to change.

// FIXED — a DTO that CANNOT express the privileged fields:
public record UpdateUserProfile(string Email, string DisplayName);

app.MapPut("/users/{id:int}", async (
    int id, UpdateUserProfile request, AppDbContext db, CancellationToken ct) =>
{
    var user = await db.Users.FindAsync([id], ct);
    if (user is null) return Results.NotFound();

    user.Email = request.Email;         // exactly two fields are assignable
    user.DisplayName = request.DisplayName;

    await db.SaveChangesAsync(ct);
    return Results.NoContent();
});

// WHY THE DTO IS THE FIX AND NOT A DEFENCE-IN-DEPTH NICETY: the vulnerability
// class is "the attacker can set a field you did not intend to expose". A DTO
// makes that unrepresentable — there is no IsAdmin property to bind, so no
// payload can reach it. Every alternative is a blocklist you must maintain
// forever, and blocklists fail the day someone adds a property to the entity:
//   • [JsonIgnore] on IsAdmin — works until a second privileged field appears
//   • [Bind(nameof(...))] in MVC — an allowlist, but far from the entity it
//     guards, so it silently goes stale
//   • checking IsAdmin manually in the handler — one forgotten endpoint away
//     from the same bug
// The DTO puts the allowlist in the type system, where drift is a compile
// error rather than a security incident.

// The same reasoning applies OUTBOUND: returning entities leaks fields as they
// are added. A response DTO keeps the contract deliberate in both directions.

Part 6 — Custom Binding and Sanitising at the Edge

// When the built-in sources do not fit, bind explicitly rather than parsing
// inside the handler. A handler that starts with parsing code is a handler
// whose contract is a lie.

// TryParse — one string, one type. Ideal for strongly-typed IDs:
public readonly record struct ProductId(int Value)
{
    public static bool TryParse(string? s, out ProductId result)
    {
        result = default;
        if (!int.TryParse(s, out var v) || v <= 0) return false;
        result = new ProductId(v);
        return true;
    }
    public override string ToString() => Value.ToString();
}
app.MapGet("/products/{id}", (ProductId id) => ...);
// Now a negative id cannot reach the handler, and ProductId cannot be passed
// where an OrderId is expected — a whole class of argument-swap bug removed by
// the type system rather than by remembering to check.

// BindAsync — the whole HttpContext. Use it to normalise and CLAMP centrally:
public record PageRequest(int Page, int Size)
{
    public const int MaxSize = 100;

    public static ValueTask<PageRequest?> BindAsync(HttpContext ctx)
    {
        _ = int.TryParse(ctx.Request.Query["page"], out var page);
        _ = int.TryParse(ctx.Request.Query["size"], out var size);

        return ValueTask.FromResult<PageRequest?>(new PageRequest(
            Page: Math.Max(page, 1),
            Size: size is <= 0 ? 20 : Math.Min(size, MaxSize)));
    }
}
// Clamping HERE rather than in each handler means an unbounded page size is
// unrepresentable. The alternative — validating in every handler — is one
// forgotten check away from ?size=1000000 becoming a denial of service.

// Model-level input hygiene worth doing at the boundary:
//   • trim strings that will be compared or stored
//   • normalise Unicode (FormC) before uniqueness checks, or "café" and
//     "café" compare unequal despite looking identical
//   • bound every collection — a List<T> body with no length limit is an
//     unbounded allocation driven by the caller
builder.Services.Configure<JsonOptions>(o =>
    o.SerializerOptions.MaxDepth = 32);      // reject deeply nested payloads

Interview Questions

Beginner: What is the difference between model binding and validation?

Binding converts the raw HTTP request — route segments, query string, headers, body bytes — into typed .NET objects, so it is concerned with shape: can this text become an int, does this JSON deserialize into this record. Validation runs afterwards on the bound object and is concerned with meaning: is this integer within the allowed range, is this date in the future, does this currency code exist. They fail differently too — a binding failure means the request is malformed and cannot be interpreted, whereas a validation failure means it was understood perfectly and is not acceptable.

Beginner: What is over-posting and why does a DTO fix it?

Over-posting is when a client sends fields the developer never intended to be settable and binding assigns them anyway — the canonical example being {"isAdmin": true} against an endpoint that binds directly onto a User entity, granting the attacker admin rights. A DTO fixes it by making those fields unrepresentable: if the bound type has no IsAdmin property, no payload can set one. That is stronger than the alternatives — [JsonIgnore], [Bind] allowlists, or manual checks — because those are blocklists maintained by hand, and they go stale the moment someone adds a new privileged property to the entity.

Mid: When would you choose FluentValidation over data annotations?

When the rule needs something the attribute cannot reach. Attributes are compile-time constants attached to a property, so they cannot inject a service, perform an async lookup, or express a rule conditional on another property's value without awkward workarounds. FluentValidation puts rules in a class that participates in DI, so "the currency code must exist in the catalogue" becomes a MustAsync with the catalogue injected, and "a contact email is required when the price exceeds ten thousand" becomes a readable When block. It also keeps validation out of the DTO entirely, which matters when the same DTO is shared with a client library. I would still use annotations for plain shape rules — required, length, range — because having them on the type is the most discoverable place for a reader, and reserve FluentValidation for rules with dependencies or real conditional logic.

Mid: A minimal API endpoint has [Required] on its DTO but invalid data still reaches the handler. Why?

Because data annotations are not evaluated automatically in minimal APIs. In controllers the [ApiController] attribute installs a filter that runs annotations, populates ModelState, and short-circuits with a 400 before the action executes. Minimal APIs have no equivalent by default — the attributes are simply metadata nobody read. The fix is to opt in: call AddValidation() on .NET 10 or later, or add an endpoint filter that resolves a validator, checks the bound argument, and returns TypedResults.ValidationProblem on failure. This is one of the most common surprises when migrating a controller-based API to minimal APIs, because the code compiles unchanged and simply stops enforcing anything.

Senior: A paging endpoint occasionally times out and shows negative offsets in the logs. Diagnose and fix it properly.

Two symptoms, one root cause: the endpoint trusts caller-supplied paging values. The negative offset comes from a missing default — int page with no default binds to 0 when the parameter is absent, so (page - 1) * size is negative and the database either errors or behaves unexpectedly. The timeout comes from the absence of an upper bound: nothing stops ?size=1000000, so a single request materialises an enormous result set, and that is effectively a denial-of-service vector any anonymous caller can trigger. The shallow fix is to clamp inside the handler, but that fails the next time someone adds a paging endpoint and forgets. The proper fix is to make invalid paging unrepresentable at the boundary: a PageRequest type with BindAsync that clamps page to at least one and size to a maximum, used by every paging endpoint. Now the handler cannot receive bad values regardless of what the caller sends, the limit is stated in one place, and the type is directly constructible in tests. I would additionally cap the underlying query with a hard Take as defence in depth, add the parameters to the endpoint's OpenAPI description so the limit is discoverable, and consider keyset pagination if deep offsets are a real access pattern, because OFFSET degrades linearly no matter how well the input is validated.

Senior: Design the validation and error-contract strategy for an API consumed by a web client, a mobile app, and partner integrations.

The organising principle is that the error contract is part of the public API and deserves the same stability guarantees as the success shapes, so I would standardise on RFC 9457 problem details for every failure across every endpoint, with no endpoint inventing its own error body. The errors dictionary keyed by property path is what lets the web and mobile clients attach messages to specific form fields instead of showing one opaque banner, so validators must produce property paths that match the request DTO's shape rather than internal domain names. I would include a traceId extension on every response, because that single field is what converts a partner's support email or a user's screenshot into a log query, and I would add a stable machine-readable code per error alongside the human-readable message — partners write conditional logic, and they will otherwise parse English prose, which then cannot be changed or localised. Layering matters: shape rules as annotations on the DTO so they are visible with the type and feed OpenAPI, cross-property rules in IValidatableObject or a validator, and genuine business rules in the domain rather than the request layer — a rule like "this order cannot be cancelled after dispatch" is not a property constraint and does not belong in a request validator, because it needs state the request does not carry. That distinction also drives status codes: request-shape failures are 400, and domain-state conflicts are 409 with a problem-details body explaining the state, not a 400 pretending the input was malformed. On the 400-versus-422 question I would default everything semantic to 400 unless the organisation already has a 422 convention, because consistency across a surface consumed by three very different clients is worth more than the finer distinction. Finally I would enforce it with a shared filter and contract tests rather than documentation, since an error contract maintained by convention drifts the first time someone is in a hurry.

🏋️ Graded Exercises

1 (easy): An endpoint GET /search takes q, page and size. Write the signature so absent parameters produce sensible values rather than zeroes.
Solution 
app.MapGet("/search", (
    string? q,                    // absent → null, which is a valid "no filter"
    SearchService svc,
    CancellationToken ct,
    int page = 1,                 // absent → 1, NOT 0
    int size = 20) =>             // absent → 20, NOT 0
        svc.SearchAsync(q, page, size, ct));

// Without the defaults, `int page` binds to 0 on an absent parameter and
// (page - 1) * size is -20 — a negative OFFSET the database rejects, from a
// request that looks completely reasonable in the access log.
//
// Note this fixes ABSENT values only. It does nothing about ?size=1000000 —
// see exercise 5.
2 (easy): Add data annotations to a CreateCustomer record: name required and 2–100 characters, a valid email, and an age between 18 and 120.
Solution 
public record CreateCustomer(
    [property: Required]
    [property: StringLength(100, MinimumLength = 2)]
    string Name,

    [property: Required]
    [property: EmailAddress]
    string Email,

    [property: Range(18, 120)]
    int Age);

// The [property:] prefix is REQUIRED on positional records. Without it the
// attribute targets the constructor PARAMETER, where the validation system
// never looks — so the annotations compile, appear correct in review, and
// enforce nothing. This is the single most common records-plus-validation bug.

// And remember: in minimal APIs these need AddValidation() or a filter to run
// at all.
3 (medium): A PUT /users/{id} binds directly to the User entity. Show the vulnerability concretely and fix it.
Solution 
// THE ATTACK — a request that looks ordinary:
// PUT /users/42
// {"id":42,"email":"me@example.com","displayName":"Me","isAdmin":true}
//
// Binding sets IsAdmin because the entity has a public settable IsAdmin.
// Nothing in the endpoint is obviously wrong; the bug is the binding SURFACE.

// THE FIX — a DTO with no privileged fields:
public record UpdateUserProfile(
    [property: Required, EmailAddress] string Email,
    [property: Required, StringLength(50)] string DisplayName);

app.MapPut("/users/{id:int}", async Task<Results<NoContent, NotFound, ForbidHttpResult>> (
    int id,
    UpdateUserProfile request,
    ClaimsPrincipal principal,
    AppDbContext db,
    CancellationToken ct) =>
{
    // Authorization is a SEPARATE concern from over-posting — both are needed.
    if (principal.GetUserId() != id && !principal.IsInRole("admin"))
        return TypedResults.Forbid();

    var user = await db.Users.FindAsync([id], ct);
    if (user is null) return TypedResults.NotFound();

    user.Email = request.Email;
    user.DisplayName = request.DisplayName;
    await db.SaveChangesAsync(ct);

    return TypedResults.NoContent();
});

// Note the id comes from the ROUTE, never the body. Trusting a body id lets a
// caller update a different user than the URL names — a second, independent
// bug that the DTO alone would not have closed.
4 (medium): Write a DateRange validated so To is not before From and the span is at most 90 days, with errors attributed to the right field.
Solution 
public record DateRange(DateOnly From, DateOnly To) : IValidatableObject
{
    public IEnumerable<ValidationResult> Validate(ValidationContext ctx)
    {
        if (To < From)
        {
            yield return new ValidationResult(
                "To must not be earlier than From.",
                [nameof(To)]);
            yield break;          // the span check below is meaningless now
        }

        if (To.DayNumber - From.DayNumber > 90)
            yield return new ValidationResult(
                "The range must not exceed 90 days.",
                [nameof(To)]);
    }
}

// Two details that matter:
//  • the member name array is what puts the message under "To" in the errors
//    dictionary, so a form client can highlight the right input. Omit it and
//    the error lands in a general bucket the UI cannot place.
//  • yield break after the ordering failure avoids emitting a confusing
//    "exceeds 90 days" alongside it when the range is inverted — a negative
//    span cannot exceed 90 and the second message would just be noise.
//
// IValidatableObject runs only after property-level annotations pass, so this
// can assume From and To individually bound successfully.
5 (hard): Make unbounded page sizes structurally impossible across every paging endpoint, and explain why handler-level clamping is insufficient.
Solution 
public record PageRequest(int Page, int Size)
{
    public const int MaxSize = 100;
    public const int DefaultSize = 20;

    public int Offset => (Page - 1) * Size;   // provably non-negative

    public static ValueTask<PageRequest?> BindAsync(HttpContext ctx)
    {
        _ = int.TryParse(ctx.Request.Query["page"], out var page);
        _ = int.TryParse(ctx.Request.Query["size"], out var size);

        return ValueTask.FromResult<PageRequest?>(new PageRequest(
            Page: page < 1 ? 1 : page,
            Size: size switch
            {
                <= 0      => DefaultSize,
                > MaxSize => MaxSize,
                _         => size
            }));
    }
}

app.MapGet("/products", (PageRequest paging, ProductService svc, CancellationToken ct)
    => svc.ListAsync(paging, ct));

// WHY HANDLER CLAMPING IS INSUFFICIENT: it is a rule enforced by everyone who
// writes a paging endpoint remembering to enforce it. The failure mode is not
// the endpoint you are looking at — it is the ninth paging endpoint added in
// six months by someone who copied a handler written before the rule existed.
// Binding-level clamping removes the choice: there is no code path that
// produces a PageRequest with Size > 100, so no handler can receive one.
//
// It also makes the constraint TESTABLE without HTTP, DISCOVERABLE as one
// constant rather than scattered magic numbers, and CHANGEABLE in one place.
//
// Defence in depth, because BindAsync only guards this binding path:
//   • a hard .Take(PageRequest.MaxSize) in the query layer, so a directly
//     constructed PageRequest cannot bypass the cap either
//   • rate limiting, since even 100-row pages fetched in a tight loop are load
//   • keyset pagination if deep offsets are a genuine access pattern —
//     OFFSET 500000 is slow no matter how well-validated the input is
6 (hard): Design a consistent error contract for an API with web, mobile and partner consumers. Specify the response shape and where each rule type lives.
Solution 
// THE SHAPE — RFC 9457 problem details, every failure, every endpoint:
// {
//   "type":     "https://api.example.com/errors/validation",
//   "title":    "One or more validation errors occurred.",
//   "status":   400,
//   "instance": "/api/v1/orders",
//   "traceId":  "00-4bf92f...-01",
//   "errors": {
//     "Items[0].Quantity": [
//       { "code": "quantity_out_of_range",
//         "message": "Quantity must be between 1 and 999." }
//     ]
//   }
// }

builder.Services.AddProblemDetails(o =>
{
    o.CustomizeProblemDetails = ctx =>
    {
        ctx.ProblemDetails.Instance = ctx.HttpContext.Request.Path;
        ctx.ProblemDetails.Extensions["traceId"] =
            Activity.Current?.Id ?? ctx.HttpContext.TraceIdentifier;
    };
});

// WHY EACH PIECE EARNS ITS PLACE:
//  • errors keyed by PROPERTY PATH — the web and mobile clients highlight the
//    offending field. Paths must mirror the REQUEST DTO ("Items[0].Quantity"),
//    not internal domain names, or the client cannot map them to inputs.
//  • a stable machine-readable CODE beside each message — partners branch on
//    failures. Without a code they parse English, and then the message can
//    never be reworded or localised without breaking an integration.
//  • traceId on every response — turns a screenshot or a partner email into a
//    log query. In production this field is worth more than the rest combined.
//  • type as a documentation URL — self-describing for new integrators.

// WHERE EACH RULE LIVES, and the status code it produces:
//   shape (required, length, format)      → annotations on the DTO      → 400
//   cross-property (To after From)        → IValidatableObject/validator → 400
//   needs a lookup (currency exists)      → FluentValidation + DI        → 400
//   domain state (cancel after dispatch)  → the DOMAIN, not the request  → 409
//
// That last row is the one teams get wrong. "This order cannot be cancelled
// after dispatch" is not a property constraint — it depends on state the
// request does not carry, so a request validator cannot express it honestly.
// Returning 400 for it tells the client the input was malformed when it was
// perfectly well-formed and merely arrived too late; 409 Conflict with a
// problem-details body describing the current state is the truthful answer.

// ENFORCEMENT — conventions decay, so make it structural:
//  • one shared endpoint filter produces every validation response
//  • UseExceptionHandler maps unhandled exceptions into the same shape, so an
//    unexpected 500 is still parseable rather than an HTML error page
//  • contract tests assert the shape for a known-bad request per endpoint
//  • 400 vs 422: pick ONE and apply it wholesale. Across three consumer types
//    a mixed convention costs more than the semantic precision gains.

🎯 Key Takeaways

  • Binding handles shape, validation handles meaning. Route constraints belong to matching and produce 404s, so business rules never belong there.
  • Minimal APIs infer binding sources by name and type; controllers with [ApiController] infer by different rules. Explicit attributes mean the same thing in both.
  • Data annotations run automatically in controllers but not in minimal APIs — opt in with AddValidation() or an endpoint filter, or they silently enforce nothing.
  • On positional records, validation attributes need the [property:] target or they attach to the constructor parameter and are never read.
  • Missing query parameters bind to default, so int page becomes 0 and produces a negative offset. State defaults in the signature.
  • Over-posting is fixed by DTOs that cannot express privileged fields — a type-system allowlist, not a hand-maintained blocklist that goes stale.
  • Take the resource id from the route, never the body, or a caller can modify a different record than the URL names.
  • Clamp paging and collection sizes in BindAsync, not in handlers: binding-level limits cannot be forgotten by the next endpoint author.
  • Standardise on RFC 9457 problem details with property-path keys, a stable error code and a traceId — the error body is public API.
  • Domain-state failures are 409, not 400: the request was well-formed and simply arrived against the wrong state.
