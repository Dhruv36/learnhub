Testing ASP.NET Core Production

What you'll master: what unit tests genuinely prove about a web application and what they structurally cannot, WebApplicationFactory for real in-process HTTP tests, database strategies and why the in-memory provider misleads, faking authentication and time, testing background services and external dependencies, and the small set of tests that catch the failures nothing else does. Prerequisites: Controllers & MVC and Dependency Injection.

Part 1 — What Each Level Actually Proves

// UNIT TESTS — a class in isolation, no framework:
[Fact]
public async Task Create_rejects_an_order_exceeding_the_credit_limit()
{
    var customers = Substitute.For<ICustomerRepository>();
    customers.FindAsync(1, Arg.Any<CancellationToken>())
        .Returns(new Customer { Id = 1, CreditLimit = 100m });

    var service = new OrderService(customers, Substitute.For<IStockPolicy>());

    var result = await service.CreateAsync(
        new CreateOrderCommand(CustomerId: 1, Total: 250m), default);

    Assert.Equal(OrderError.CreditExceeded, result.Error);
}
// PROVES: the business rule. Fast, precise, and the failure message points
// directly at the logic.

// ── WHAT UNIT TESTS STRUCTURALLY CANNOT PROVE ────────────────────────────
// Calling a controller method directly bypasses the entire pipeline:
//   • ROUTING — is the action reachable at the expected URL?
//   • MODEL BINDING — does the request shape bind to these parameters?
//   • FILTERS — [Authorize] NEVER RUNS. An action with the attribute and one
//     without it behave IDENTICALLY under unit test.
//   • the [ApiController] automatic 400 for invalid ModelState
//   • SERIALIZATION — does the response round-trip as the client expects?
//   • middleware: exception handling, CORS, rate limiting
//
// That list is why "100% unit coverage" and "an unprotected endpoint in
// production" are entirely compatible states.

// INTEGRATION TESTS — the real pipeline, in-process:
public class OrdersEndpointTests(WebApplicationFactory<Program> factory)
    : IClassFixture<WebApplicationFactory<Program>>
{
    [Fact]
    public async Task Get_returns_the_order()
    {
        var client = factory.CreateClient();
        var response = await client.GetAsync("/api/orders/1");

        response.EnsureSuccessStatusCode();
        var order = await response.Content.ReadFromJsonAsync<OrderResponse>();
        Assert.Equal(1, order!.Id);
    }
}
// PROVES: routing, binding, filters, serialization and middleware all agree.
// WebApplicationFactory runs the app IN-PROCESS with a TestServer — no
// sockets, no ports, no localhost — so these are fast enough to run in the
// hundreds.

// THE PRACTICAL SPLIT for a web API, which differs from the classic pyramid:
//   • business logic and domain rules      → unit tests, many
//   • every endpoint's contract and auth   → integration tests, one or two each
//   • critical user journeys               → a handful of end-to-end tests
// Web applications are mostly wiring, and wiring is exactly what unit tests
// cannot check — so the integration layer is proportionally larger here than
// in a library.

Part 2 — WebApplicationFactory

// Your Program.cs must be reachable from the test project. With top-level
// statements, add this at the end:
public partial class Program { }
// ...and reference the web project from the test project.

// A CUSTOM FACTORY is where environment overrides belong:
public sealed class ApiFactory : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _db = new PostgreSqlBuilder()
        .WithImage("postgres:16-alpine")
        .Build();

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment("Testing");

        builder.ConfigureTestServices(services =>
        {
            // ConfigureTestServices runs AFTER the app's own registrations,
            // so Remove/Add here reliably wins. ConfigureServices runs BEFORE
            // and gets overwritten — a common and confusing mistake.
            services.RemoveAll<DbContextOptions<AppDbContext>>();
            services.AddDbContext<AppDbContext>(o =>
                o.UseNpgsql(_db.GetConnectionString()));

            // Replace only what crosses a boundary you do not control.
            services.RemoveAll<IPaymentGateway>();
            services.AddSingleton<IPaymentGateway, FakePaymentGateway>();

            services.AddAuthentication("Test")
                .AddScheme<AuthenticationSchemeOptions, TestAuthHandler>("Test", _ => { });
        });
    }

    public async Task InitializeAsync()
    {
        await _db.StartAsync();
        using var scope = Services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Database.MigrateAsync();      // real migrations, real schema
    }

    public new async Task DisposeAsync() => await _db.DisposeAsync();
}

// CONFIGURATION for tests — appsettings.Testing.json plus in-memory overrides:
builder.ConfigureAppConfiguration((context, config) =>
{
    config.AddInMemoryCollection(new Dictionary<string, string?>
    {
        ["Features:SendEmails"] = "false",
        ["Jwt:Authority"] = "https://test.local"
    });
});

// CLIENT OPTIONS worth knowing:
var client = factory.CreateClient(new WebApplicationFactoryClientOptions
{
    AllowAutoRedirect = false,       // assert on the 302 itself
    BaseAddress = new Uri("https://localhost")   // makes RequireHttps work
});

// SHARING THE FACTORY: IClassFixture shares one instance per test class;
// ICollectionFixture shares across classes. Starting a container per test
// class is slow, so a collection fixture is usually the right unit — with the
// caveat that tests then share a database and must not depend on each other's
// state.
Key insight: the single most valuable test in a web application is the one asserting that an anonymous request to a protected endpoint returns 401. It is the only check that fails when someone deletes an [Authorize] attribute, when UseAuthorization is registered before UseRouting, or when a fallback policy is misconfigured — all of which fail open, producing no exception, no log entry, and no failing test anywhere else. Every authenticated happy-path test continues to pass while the endpoint serves the world. One line per protected endpoint group closes an entire class of silent vulnerability.

Part 3 — Databases in Tests

// ✗ THE EF IN-MEMORY PROVIDER — convenient and actively misleading:
services.AddDbContext<AppDbContext>(o => o.UseInMemoryDatabase("test"));
//
// It is a LINQ-to-Objects fake, not a database. It does not enforce:
//   • unique constraints, foreign keys, or check constraints
//   • column length limits or NOT NULL
//   • transactions (BeginTransaction is a no-op)
//   • concurrency tokens
//   • raw SQL, computed columns, or database-generated values
// And it SUCCEEDS on queries a real provider cannot translate, so a test
// passes and production throws. It is a source of false confidence, and
// Microsoft's own guidance now discourages it for anything but the simplest
// cases.

// ✓ TESTCONTAINERS — the real engine, disposable, per test run:
private readonly PostgreSqlContainer _db = new PostgreSqlBuilder()
    .WithImage("postgres:16-alpine")
    .Build();
// Same engine, same SQL dialect, same constraints, same migrations as
// production. Startup is a few seconds, amortised across the whole run with a
// collection fixture.

// ✓ SQLITE IN-MEMORY — a middle ground when Docker is unavailable:
var connection = new SqliteConnection("DataSource=:memory:");
connection.Open();            // MUST stay open — closing drops the database
services.AddDbContext<AppDbContext>(o => o.UseSqlite(connection));
// A REAL relational engine, so constraints and transactions work. But the
// dialect differs from PostgreSQL or SQL Server, so provider-specific SQL,
// certain column types and some functions behave differently.

// ── ISOLATION BETWEEN TESTS ──────────────────────────────────────────────
// Tests sharing a database must not see each other's data.

// OPTION A — a transaction per test, rolled back:
public async Task InitializeAsync()
{
    _transaction = await _db.Database.BeginTransactionAsync();
}
public async Task DisposeAsync() => await _transaction.RollbackAsync();
// Fast and thorough, but the code under test cannot manage its own
// transactions, which rules it out for anything calling SaveChanges inside an
// explicit transaction.

// OPTION B — respawn between tests (usually the best default):
private static readonly Respawner Respawner = await Respawner.CreateAsync(conn,
    new RespawnerOptions { TablesToIgnore = ["__EFMigrationsHistory"] });

public async Task DisposeAsync() => await Respawner.ResetAsync(_connection);
// Deletes all data while preserving schema. Works with any transaction usage
// in the code under test.

// OPTION C — unique data per test. No cleanup needed, but tests that query
// broadly ("all pending orders") see each other's rows, so it only works
// where every query is scoped by a test-specific key.

// ── SEEDING ──────────────────────────────────────────────────────────────
// Seed inside the test, not in a global fixture, so each test states its own
// preconditions and a reader does not have to hunt for them:
private async Task<Order> GivenAnOrder(OrderStatus status = OrderStatus.Draft)
{
    using var scope = _factory.Services.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    var order = new Order { Status = status, CustomerId = 1 };
    db.Orders.Add(order);
    await db.SaveChangesAsync();
    return order;
}

Part 4 — Faking Authentication, Time, and HTTP

// ── AUTHENTICATION ───────────────────────────────────────────────────────
public sealed class TestAuthHandler(
    IOptionsMonitor<AuthenticationSchemeOptions> options,
    ILoggerFactory logger, UrlEncoder encoder)
    : AuthenticationHandler<AuthenticationSchemeOptions>(options, logger, encoder)
{
    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        // NoResult, NOT Fail — this is what allows the SAME handler to serve
        // anonymous requests, so the 401 path is genuinely exercised.
        if (!Request.Headers.TryGetValue("X-Test-User", out var userId))
            return Task.FromResult(AuthenticateResult.NoResult());

        var claims = new List<Claim> { new(ClaimTypes.NameIdentifier, userId!) };

        foreach (var role in Request.Headers["X-Test-Role"].ToString()
                     .Split(',', StringSplitOptions.RemoveEmptyEntries))
            claims.Add(new Claim(ClaimTypes.Role, role));

        if (Request.Headers.TryGetValue("X-Test-Tenant", out var tenant))
            claims.Add(new Claim("tenant_id", tenant!));

        var principal = new ClaimsPrincipal(new ClaimsIdentity(claims, "Test"));
        return Task.FromResult(AuthenticateResult.Success(
            new AuthenticationTicket(principal, "Test")));
    }
}

// Readable helpers keep the intent visible at the call site:
public static HttpClient AsUser(this WebApplicationFactory<Program> factory,
    string userId, params string[] roles)
{
    var client = factory.CreateClient();
    client.DefaultRequestHeaders.Add("X-Test-User", userId);
    if (roles.Length > 0)
        client.DefaultRequestHeaders.Add("X-Test-Role", string.Join(',', roles));
    return client;
}

var client = factory.AsUser("user-1", "admin");
var anonymous = factory.CreateClient();          // no headers → anonymous

// ── TIME ─────────────────────────────────────────────────────────────────
// Never call DateTime.UtcNow in code you want to test — inject TimeProvider:
public sealed class SubscriptionService(TimeProvider clock)
{
    public bool IsExpired(Subscription s) => s.ExpiresAt < clock.GetUtcNow();
}

var clock = new FakeTimeProvider(new DateTimeOffset(2026, 8, 3, 12, 0, 0, TimeSpan.Zero));
services.AddSingleton<TimeProvider>(clock);

clock.Advance(TimeSpan.FromDays(31));       // deterministic time travel
// FakeTimeProvider also drives PeriodicTimer and Task.Delay, so a background
// service's schedule becomes testable without a single real sleep — turning
// a 30-second test into a 3-millisecond one.

// ── OUTBOUND HTTP ────────────────────────────────────────────────────────
public sealed class StubHttpHandler(
    Func<HttpRequestMessage, HttpResponseMessage> responder) : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
        => Task.FromResult(responder(request));
}

services.AddHttpClient<IPaymentGateway, StripeGateway>()
    .ConfigurePrimaryHttpMessageHandler(() => new StubHttpHandler(request =>
        new HttpResponseMessage(HttpStatusCode.OK)
        {
            Content = JsonContent.Create(new { id = "ch_123", status = "succeeded" })
        }));
// Replacing the HANDLER rather than the client keeps the real serialization,
// headers, retry policies and resilience pipeline in the test — so a bug in
// the request construction is still caught.
//
// For richer scenarios, WireMock.Net gives a real stub server with request
// matching and verification, which is worth it once you need to assert on
// what was SENT rather than just control what comes back.

Part 5 — Testing Background Services and Contracts

// ── BACKGROUND SERVICES: test the WORK, not the loop ─────────────────────
// The loop is framework plumbing. Extract the unit of work and test it:
public sealed class OrderProcessor(IOrderRepository repo, TimeProvider clock)
{
    public async Task<int> ProcessBatchAsync(CancellationToken ct)
    {
        var pending = await repo.GetPendingAsync(ct);
        foreach (var order in pending) order.Process(clock.GetUtcNow());
        await repo.SaveAsync(ct);
        return pending.Count;
    }
}

public sealed class OrderWorker(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));
        while (await timer.WaitForNextTickAsync(ct))
        {
            using var scope = scopes.CreateScope();
            await scope.ServiceProvider
                .GetRequiredService<OrderProcessor>()
                .ProcessBatchAsync(ct);
        }
    }
}
// Now ProcessBatchAsync is an ordinary unit test with no timers and no host.

// When the LOOP itself needs testing, drive it with FakeTimeProvider:
[Fact]
public async Task Worker_processes_on_each_tick()
{
    var clock = new FakeTimeProvider();
    var processor = Substitute.For<IOrderProcessor>();

    var worker = new OrderWorker(scopes, clock);
    await worker.StartAsync(default);

    clock.Advance(TimeSpan.FromSeconds(30));    // no real waiting
    await Task.Yield();

    await processor.Received(1).ProcessBatchAsync(Arg.Any<CancellationToken>());

    await worker.StopAsync(default);
}

Part 6 — Making the Suite Fast and Trustworthy

// ── PARALLELISM ──────────────────────────────────────────────────────────
// xUnit runs test COLLECTIONS in parallel and tests within a collection
// sequentially. Tests sharing a database must share a collection, or they
// will interfere:
[CollectionDefinition("Database")]
public class DatabaseCollection : ICollectionFixture<ApiFactory> { }

[Collection("Database")]
public class OrdersEndpointTests(ApiFactory factory) { }
// One container, shared across every class in the collection, with tests
// inside it running sequentially. This is usually the right trade: container
// startup dominates, so sharing it matters more than intra-collection
// parallelism.

// ── FLAKINESS: the three causes, and the fixes ───────────────────────────
// 1. TIME — anything using DateTime.UtcNow or real delays.
//    → TimeProvider everywhere; FakeTimeProvider in tests.
// 2. SHARED STATE — leftover rows, a static cache, a singleton holding data.
//    → Respawn between tests; avoid statics; reset caches in the fixture.
// 3. ASYNC RACES — asserting before background work completes.
//    → do NOT sleep. Poll for the condition with a timeout:
public static async Task WaitUntilAsync(Func<Task<bool>> condition,
    TimeSpan timeout)
{
    using var cts = new CancellationTokenSource(timeout);
    while (!cts.IsCancellationRequested)
    {
        if (await condition()) return;
        await Task.Delay(50, cts.Token);
    }
    throw new TimeoutException("Condition was not met within the timeout.");
}
// Thread.Sleep(2000) is both slow and unreliable: too short on a loaded CI
// machine, too long everywhere else. A polled condition is faster AND more
// stable.
//
// A flaky test that gets retried is worse than no test — it trains everyone
// to ignore red. Fix it or delete it.

// ── WHAT NOT TO TEST ─────────────────────────────────────────────────────
//   ✗ the framework itself (does [Required] work? — yes, it does)
//   ✗ trivial getters and mapping with no logic
//   ✗ implementation details: asserting a repository method was called with
//     exact arguments couples the test to the code's shape, so every refactor
//     breaks tests without any behaviour changing
//   ✓ behaviour observable at a boundary: the response, the database state,
//     the message published

// ── ASSERT ON OUTCOMES, NOT INTERACTIONS ─────────────────────────────────
// ✗ await repo.Received(1).SaveAsync(Arg.Is<Order>(o => o.Status == "paid"));
// ✓ var stored = await db.Orders.FindAsync(id);
//   Assert.Equal(OrderStatus.Paid, stored.Status);
// The second survives a refactor that changes how saving happens; the first
// does not, and it is testing your mock rather than your application.

// ── CI CONSIDERATIONS ────────────────────────────────────────────────────
//   • Testcontainers needs a Docker daemon — available on GitHub Actions
//     runners by default
//   • run unit and integration suites as separate jobs so a slow container
//     start does not delay fast feedback
//   • collect coverage, but treat it as a MAP of what is untested rather than
//     a target. A codebase at 95% can still be missing the anonymous-request
//     test, because coverage measures lines executed, never assertions made.

Interview Questions

Beginner: What is WebApplicationFactory for?

It bootstraps your real application in-process for testing, using a TestServer instead of Kestrel, and hands you an HttpClient wired directly to it. That means requests go through the genuine pipeline — routing, model binding, filters, authorization, serialization and middleware — without opening a socket or binding a port, so the tests are fast enough to run in the hundreds while still exercising everything a unit test skips. It also provides hooks to override services, configuration and the environment, so external dependencies can be replaced with fakes while the rest of the application stays real.

Beginner: Why avoid the EF Core in-memory provider?

Because it is not a database — it is a LINQ-to-Objects implementation of the EF provider interface. It does not enforce unique constraints, foreign keys, check constraints, column lengths or nullability, and transactions are no-ops. That means a test can happily insert data the real database would reject, and a concurrency or constraint bug passes cleanly and fails in production. It also has the opposite problem: it executes queries that a real provider cannot translate to SQL, so a query that works in tests throws at runtime. Testcontainers running the real engine is the reliable option, with SQLite in-memory as a middle ground when Docker is unavailable — SQLite is at least a real relational engine, though its dialect differs.

Mid: Why is ConfigureTestServices different from ConfigureServices?

Ordering. ConfigureServices on the host builder runs before the application's own registrations in Program.cs, so anything you register there is subsequently overwritten by the real registration — your test double silently does not take effect. ConfigureTestServices runs after everything the application registered, so removing a descriptor and adding a replacement reliably wins. This is a frequent source of confusion because the test compiles, runs, and quietly uses the real dependency, which typically surfaces as an unexpected network call or a test that only fails in CI.

Mid: How do you make time-dependent code testable?

By injecting TimeProvider rather than calling DateTime.UtcNow directly, then substituting FakeTimeProvider in tests. That turns time into an input you control: subscription expiry, token lifetimes, retention windows and scheduling all become deterministic, and tests that would otherwise fail at midnight, at month end or during a daylight-saving transition become stable. It also has a substantial speed benefit, because FakeTimeProvider drives PeriodicTimer and Task.Delay, so a background service's thirty-second interval can be advanced instantly rather than waited out — turning a slow, timing-sensitive test into a millisecond one.

Senior: A team has 95% coverage and still shipped an unprotected endpoint. Explain how, and what to add.

Coverage measures which lines executed, never which properties were asserted, and unit tests of controllers execute the action body while bypassing the entire pipeline. Calling a controller method directly means routing never runs, model binding never runs, and — critically — filters never run, so an action decorated with [Authorize] and one with the attribute deleted are literally indistinguishable under unit test. The same applies to a misordered pipeline: registering UseAuthorization before UseRouting means no endpoint metadata is available, so authorization finds nothing to enforce and permits the request, with no exception and nothing in the logs. Both failure modes fail open, which is why every existing test stayed green. What I would add is an integration test per protected endpoint group asserting that an anonymous request returns 401 and that an authenticated-but-under-privileged request returns 403 — those two assertions cover the whole class. On top of that, a contract test that enumerates EndpointDataSource and asserts the set of endpoints carrying IAllowAnonymous exactly matches a known list, so a newly public endpoint fails the build and has to be added deliberately. I would also set a fallback authorization policy so endpoints are protected by default rather than by remembering an attribute. And I would stop treating coverage as a target, because the incentive it creates is to execute lines rather than to assert behaviour at boundaries — the metric was satisfied precisely while the property that mattered was never checked.

Senior: Design a testing strategy for a service with a database, an external payment API, and background workers.

I would organise it by what each layer can actually prove and keep the boundaries deliberate. Domain and application logic gets fast unit tests with no framework — credit limits, state transitions, pricing — because those are where the rules live and where precise failure messages are most valuable; the key enabler is that the application service takes a command and returns a result rather than touching HTTP, so it is directly constructible. Endpoints get integration tests through WebApplicationFactory against a real database in Testcontainers, since routing, binding, filters and serialization are exactly what unit tests cannot see, and the in-memory provider would silently accept data the real schema rejects. For the payment API I would replace the primary HttpMessageHandler rather than mocking the client, so serialization, headers and the resilience pipeline remain under test, and I would explicitly cover the failure paths that matter — timeouts, 402 declines, 429 throttling and a rejected credential — because those are the branches that only execute during an incident and are therefore the least exercised in practice. Idempotency deserves a dedicated test: submit the same idempotency key twice concurrently and assert exactly one charge, since that is the property protecting against duplicate payments and it is easy to break in a refactor. For background workers I would extract the unit of work from the loop so the work is an ordinary unit test, and drive any remaining timer logic with FakeTimeProvider instead of real delays. Beyond the per-feature tests I would add a small set of contract tests that nothing else covers: anonymous requests receive 401, the public-endpoint set matches an explicit list, error responses are problem details containing no stack traces, and every registered service resolves. For isolation, Respawn between tests with a shared container per collection, since container startup dominates the runtime. And I would keep a handful of true end-to-end tests for the critical journey only, because they are slow and brittle in proportion to their coverage — their value is confirming the pieces are deployed together, not finding logic bugs.

2 (easy): Add a fake authentication scheme supporting authenticated, anonymous and role-based requests.
Solution 
public sealed class TestAuthHandler(
    IOptionsMonitor<AuthenticationSchemeOptions> options,
    ILoggerFactory logger, UrlEncoder encoder)
    : AuthenticationHandler<AuthenticationSchemeOptions>(options, logger, encoder)
{
    protected override Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        // NoResult() — NOT Fail(). This is the whole trick: it means "no
        // credentials presented", so the request proceeds as ANONYMOUS and
        // the 401 path is genuinely exercised. Fail() would short-circuit
        // with an authentication error instead, which tests a different thing.
        if (!Request.Headers.TryGetValue("X-Test-User", out var userId))
            return Task.FromResult(AuthenticateResult.NoResult());

        var claims = new List<Claim> { new(ClaimTypes.NameIdentifier, userId!) };

        foreach (var role in Request.Headers["X-Test-Role"].ToString()
                     .Split(',', StringSplitOptions.RemoveEmptyEntries))
            claims.Add(new Claim(ClaimTypes.Role, role));

        var identity = new ClaimsIdentity(claims, "Test");
        return Task.FromResult(AuthenticateResult.Success(
            new AuthenticationTicket(new ClaimsPrincipal(identity), "Test")));
    }
}

// Registered in the factory:
services.AddAuthentication("Test")
    .AddScheme<AuthenticationSchemeOptions, TestAuthHandler>("Test", _ => { });
services.Configure<AuthenticationOptions>(o =>
{
    o.DefaultAuthenticateScheme = "Test";
    o.DefaultChallengeScheme = "Test";
});

// Usage:
var anonymous = factory.CreateClient();                    // → 401
var user      = factory.AsUser("user-1");                  // → 200 / 403

3 (medium): Set up a factory using Testcontainers with clean isolation between tests.
Solution 
public sealed class ApiFactory : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _container = new PostgreSqlBuilder()
        .WithImage("postgres:16-alpine")
        .WithDatabase("testdb")
        .Build();

    private DbConnection _connection = null!;
    private Respawner _respawner = null!;

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment("Testing");

        // ConfigureTestServices runs AFTER Program.cs registrations, so these
        // replacements reliably win.
        builder.ConfigureTestServices(services =>
        {
            services.RemoveAll<DbContextOptions<AppDbContext>>();
            services.AddDbContext<AppDbContext>(o =>
                o.UseNpgsql(_container.GetConnectionString()));

            services.AddAuthentication("Test")
                .AddScheme<AuthenticationSchemeOptions, TestAuthHandler>("Test", _ => { });
        });
    }

    public async Task InitializeAsync()
    {
        await _container.StartAsync();

        using var scope = Services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Database.MigrateAsync();     // REAL migrations, real schema

        _connection = new NpgsqlConnection(_container.GetConnectionString());
        await _connection.OpenAsync();
        _respawner = await Respawner.CreateAsync(_connection,
            new RespawnerOptions
            {
                DbAdapter = DbAdapter.Postgres,
                TablesToIgnore = [new Table("__EFMigrationsHistory")]
            });
    }

    // Called by each test to return to a clean slate.
    public Task ResetAsync() => _respawner.ResetAsync(_connection);

    public new async Task DisposeAsync()
    {
        await _connection.DisposeAsync();
        await _container.DisposeAsync();
    }
}

// Respawn rather than a rolled-back transaction, because the code under test

4 (medium): Test that a subscription expires after 30 days without waiting 30 days.
Solution 
// The service takes TimeProvider rather than calling DateTime.UtcNow:
public sealed class SubscriptionService(
    ISubscriptionRepository repo, TimeProvider clock)
{
    public async Task<bool> IsActiveAsync(int id, CancellationToken ct)
    {
        var subscription = await repo.FindAsync(id, ct);
        return subscription is not null && subscription.ExpiresAt > clock.GetUtcNow();
    }
}

[Fact]
public async Task Subscription_expires_after_thirty_days()
{
    var start = new DateTimeOffset(2026, 8, 3, 12, 0, 0, TimeSpan.Zero);
    var clock = new FakeTimeProvider(start);

    var repo = Substitute.For<ISubscriptionRepository>();
    repo.FindAsync(1, Arg.Any<CancellationToken>())
        .Returns(new Subscription { Id = 1, ExpiresAt = start.AddDays(30) });

    var service = new SubscriptionService(repo, clock);

    Assert.True(await service.IsActiveAsync(1, default));       // day 0

    clock.Advance(TimeSpan.FromDays(29));
    Assert.True(await service.IsActiveAsync(1, default));       // day 29

    clock.Advance(TimeSpan.FromDays(2));
    Assert.False(await service.IsActiveAsync(1, default));      // day 31
}

// Runs in microseconds and is completely deterministic. The equivalent using
// DateTime.UtcNow could only be tested by manipulating the stored expiry —
// which tests the arithmetic backwards and would still fail unpredictably
// across a daylight-saving boundary.
//
// FakeTimeProvider also drives PeriodicTimer and Task.Delay, so the same
// technique tests a background service's schedule with no real waiting.
5 (hard): Test an endpoint calling an external payment API, covering success, decline and timeout.
Solution 
public sealed class StubHttpHandler(
    Func<HttpRequestMessage, CancellationToken, Task<HttpResponseMessage>> responder)
    : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct) => responder(request, ct);
}

private HttpClient ClientWithGateway(
    Func<HttpRequestMessage, CancellationToken, Task<HttpResponseMessage>> responder)
    => _factory.WithWebHostBuilder(b => b.ConfigureTestServices(services =>
    {
        services.AddHttpClient<IPaymentGateway, StripeGateway>()
            .ConfigurePrimaryHttpMessageHandler(() => new StubHttpHandler(responder));
    })).AsUser("user-1");

[Fact]
public async Task Successful_charge_returns_201()
{
    var client = ClientWithGateway((_, _) => Task.FromResult(
        new HttpResponseMessage(HttpStatusCode.OK)
        {
            Content = JsonContent.Create(new { id = "ch_1", status = "succeeded" })
        }));

    var response = await client.PostAsJsonAsync("/api/payments",
        new PaymentRequest(100m, "USD"));

    Assert.Equal(HttpStatusCode.Created, response.StatusCode);
}

[Fact]
public async Task Declined_card_returns_402_not_500()
{
    var client = ClientWithGateway((_, _) => Task.FromResult(
        new HttpResponseMessage(HttpStatusCode.PaymentRequired)));

    var response = await client.PostAsJsonAsync("/api/payments",
        new PaymentRequest(100m, "USD"));

    // A decline is a CALLER-ACTIONABLE outcome, not a server fault.
    Assert.Equal(HttpStatusCode.PaymentRequired, response.StatusCode);

    var problem = await response.Content.ReadFromJsonAsync<ProblemDetails>();
    Assert.Contains("declined", problem!.Title, StringComparison.OrdinalIgnoreCase);
}

[Fact]
public async Task Upstream_timeout_returns_504()
{
    var client = ClientWithGateway(async (_, ct) =>
    {
        await Task.Delay(Timeout.Infinite, ct);      // never completes
        return new HttpResponseMessage();
    });

    var response = await client.PostAsJsonAsync("/api/payments",
        new PaymentRequest(100m, "USD"));

    // 504 tells the client this is transient and retryable; 500 would imply
    // a permanent fault in us.
    Assert.Equal(HttpStatusCode.GatewayTimeout, response.StatusCode);
}

[Fact]
public async Task Retried_request_with_the_same_idempotency_key_charges_once()
{
    var charges = 0;
    var client = ClientWithGateway((_, _) =>
    {
        Interlocked.Increment(ref charges);
        return Task.FromResult(new HttpResponseMessage(HttpStatusCode.OK)
        {
            Content = JsonContent.Create(new { id = "ch_1", status = "succeeded" })
        });
    });

    client.DefaultRequestHeaders.Add("Idempotency-Key", "key-123");
    await client.PostAsJsonAsync("/api/payments", new PaymentRequest(100m, "USD"));
    await client.PostAsJsonAsync("/api/payments", new PaymentRequest(100m, "USD"));

    Assert.Equal(1, charges);       // the property that prevents double charges
}

// REPLACING THE HANDLER, not the client, keeps request construction,
// serialization, headers and the resilience pipeline under test — so a bug in
// how the request is built is still caught. Mocking IPaymentGateway would
// skip all of that.
//
// The failure paths matter most here: they only execute during incidents, so
// they are the least exercised in practice and the most likely to be wrong.
6 (hard): Write the contract tests that catch what feature tests never do.
Solution 
[Collection("Database")]
public class ContractTests(ApiFactory factory)
{
    // ── 1. NOTHING BECAME ACCIDENTALLY PUBLIC ────────────────────────────
    [Fact]
    public void Public_endpoints_match_the_approved_list()
    {
        var endpoints = factory.Services
            .GetRequiredService<EndpointDataSource>().Endpoints;

        var actual = endpoints.OfType<RouteEndpoint>()
            .Where(e => e.Metadata.GetMetadata<IAllowAnonymous>() is not null)
            .Select(e => e.RoutePattern.RawText!)
            .ToHashSet();

        // A new public endpoint FAILS THE BUILD and must be added here
        // deliberately — turning an omission into a reviewed decision.
        Assert.Equal(new HashSet<string>
        {
            "/health", "/health/ready", "/api/v1/auth/token"
        }, actual);
    }

    // ── 2. AUTHORIZATION IS ACTUALLY WIRED ───────────────────────────────
    [Theory]
    [InlineData("/api/orders")]
    [InlineData("/api/customers")]
    [InlineData("/api/reports")]
    public async Task Protected_endpoints_reject_anonymous_callers(string path)
    {
        var response = await factory.CreateClient().GetAsync(path);
        Assert.Equal(HttpStatusCode.Unauthorized, response.StatusCode);
    }
    // The ONLY test that fails if [Authorize] is deleted or if
    // UseAuthorization is registered before UseRouting. Both fail OPEN.

    // ── 3. ERRORS LEAK NOTHING ───────────────────────────────────────────
    [Fact]
    public async Task Unhandled_errors_return_problem_details_without_internals()
    {
        var prod = factory.WithWebHostBuilder(b => b.UseEnvironment("Production"));
        var response = await prod.CreateClient().GetAsync("/test/throw");
        var body = await response.Content.ReadAsStringAsync();

        Assert.Equal("application/problem+json",
            response.Content.Headers.ContentType?.MediaType);
        Assert.DoesNotContain("at System.", body);          // no stack frames
        Assert.DoesNotContain("Server=", body);             // no connection strings
        Assert.DoesNotContain("<html", body, StringComparison.OrdinalIgnoreCase);
    }

    // ── 4. THE DI GRAPH IS COMPLETE ──────────────────────────────────────
    [Fact]
    public void Every_service_resolves()
    {
        using var scope = factory.Services.CreateScope();

        foreach (var type in typeof(Program).Assembly.GetTypes()
                     .Where(t => t.IsInterface && t.Name.EndsWith("Service")))
        {
            Assert.NotNull(scope.ServiceProvider.GetService(type));
        }
    }
    // Catches a missing registration on a rarely-hit path at build time
    // instead of on the first request that needs it.

    // ── 5. SECURITY HEADERS ARE NOT WEAKENED ─────────────────────────────
    [Fact]
    public async Task Csp_is_present_and_not_neutered()
    {
        var response = await factory.CreateClient().GetAsync("/health");
        var csp = response.Headers.GetValues("Content-Security-Policy").Single();

        Assert.Contains("frame-ancestors 'none'", csp);
        // Asserting the ABSENCE is the valuable part — this is the directive
        // that gets re-added under delivery pressure.
        Assert.DoesNotContain("unsafe-inline", csp);
    }
}

// WHY THESE FIVE: every one covers a regression that is invisible to feature
// tests and to code review, and that fails silently in production — an
// accidentally public endpoint, detached authorization, a leaking error
// handler, a missing registration, and a weakened CSP. Each is a handful of
// lines and each has shipped to production in real systems.

🎯 Key Takeaways

  • Unit tests bypass routing, binding, filters and serialization — they can never prove an endpoint is reachable or protected.
  • The anonymous-request 401 test is the highest-value test in a web application, because every fail-open bug leaves other tests green.
  • WebApplicationFactory runs the real pipeline in-process, fast enough for hundreds of tests.
  • ConfigureTestServices runs after the app's registrations; ConfigureServices gets overwritten.
  • The EF in-memory provider enforces no constraints and no transactions — use Testcontainers, or SQLite as a middle ground.
  • Isolate tests with Respawn, share one container per collection, and let each test seed its own data.
  • Inject TimeProvider so time is an input — FakeTimeProvider also drives timers, removing real waits.
  • Replace the primary HttpMessageHandler rather than mocking the client, so serialization and resilience stay under test.
  • Extract a background service's unit of work from its loop; test the work, not the framework's plumbing.
  • Assert on observable outcomes rather than mock interactions, and treat coverage as a map of what is untested rather than a target.
