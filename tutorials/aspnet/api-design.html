REST API Design in ASP.NET Building APIs

What you'll master: resource modelling that survives contact with real requirements, the safety and idempotency properties that decide what clients may retry, pagination that does not degrade at page 5000, concurrency control that prevents lost updates, and the design decisions that are expensive to reverse once clients depend on them. Prerequisites: Controllers & MVC and Error Handling & Problem Details.

Part 1 — Resources, Not Remote Procedures

// The single most common design failure is exposing verbs as endpoints:
//   POST /api/createOrder
//   POST /api/getOrderById
//   POST /api/cancelOrderAndRefund
// This is RPC over HTTP. Everything is a POST, so nothing is cacheable,
// nothing is safely retryable, and the HTTP method carries no information.

// RESOURCE-ORIENTED — nouns as URLs, verbs as HTTP methods:
GET    /api/orders              // list
POST   /api/orders              // create
GET    /api/orders/42           // read one
PUT    /api/orders/42           // full replace
PATCH  /api/orders/42           // partial update
DELETE /api/orders/42           // remove

// SUB-RESOURCES express containment:
GET    /api/orders/42/lines           // the lines of order 42
POST   /api/orders/42/lines           // add a line
DELETE /api/orders/42/lines/7         // remove one line

// NESTING DEPTH: stop at two levels. /api/customers/1/orders/42/lines/7 is
// worse than /api/orders/42/lines/7 — the order id already identifies the
// order, so the customer segment is redundant and makes every URL longer and
// every route more brittle. Nest only when the child cannot be addressed
// without the parent.

// THE HARD CASE — operations that are genuinely not CRUD. Cancelling an
// order, sending an email, running a report. Three legitimate options:
//
// 1. MODEL THE STATE CHANGE AS A FIELD (preferred where it fits):
PATCH /api/orders/42     { "status": "cancelled" }
//    Honest when cancellation really is just a status transition.
//
// 2. MODEL THE ACTION AS A SUB-RESOURCE (preferred where it has substance):
POST /api/orders/42/cancellation    { "reason": "customer request" }
//    Right when the action has its own data, its own audit trail, or can be
//    queried later — a cancellation is a THING, with a time and a reason.
//
// 3. AN EXPLICIT ACTION ENDPOINT, when neither fits:
POST /api/orders/42/cancel
//    Pragmatic, and not a sin. Purity that produces a confusing API is worse
//    than a clear verb. Use it deliberately, not as the default.

// COLLECTION vs SINGLETON responses — be consistent:
GET /api/orders      → { "items": [...], "total": 240, "next": "..." }
GET /api/orders/42   → { "id": 42, ... }
// Returning a BARE ARRAY from a list endpoint is a decision you cannot
// reverse: adding pagination metadata later is a breaking change, because
// clients wrote `response.map(...)` against the top-level array. Always wrap.

Part 2 — Safety, Idempotency, and What Clients May Retry

// Two properties, frequently confused, that determine client behaviour:
//
//   SAFE        does not modify state. Caches and crawlers may call it freely.
//   IDEMPOTENT  calling N times has the same effect as calling once.
//
//   METHOD   SAFE   IDEMPOTENT   NOTES
//   GET      yes    yes          never modify state in a GET
//   HEAD     yes    yes          GET without a body
//   PUT      no     YES          full replace — same payload, same result
//   DELETE   no     YES          deleting twice leaves it deleted
//   POST     no     NO           each call creates something new
//   PATCH    no     depends      on the patch semantics (see below)

// WHY THIS IS NOT TRIVIA: a client, proxy or retry policy that sees a timeout
// must decide whether to retry. For PUT and DELETE it is always safe. For
// POST it is NOT, and retrying a timed-out POST is exactly how duplicate
// orders and double charges happen.

// MAKING POST SAFELY RETRYABLE — an idempotency key:
[HttpPost]
public async Task<ActionResult<Order>> Create(
    [FromHeader(Name = "Idempotency-Key")] string? key,
    CreateOrderRequest request,
    CancellationToken ct)
{
    if (string.IsNullOrWhiteSpace(key))
        return ValidationProblem("Idempotency-Key header is required.");

    // Must be an ATOMIC reserve-or-fetch (INSERT ... ON CONFLICT, or SETNX).
    // A get-then-set race under concurrent retries creates the duplicate this
    // exists to prevent.
    if (await idempotency.TryGetAsync<Order>(key, ct) is { } existing)
        return Ok(existing);          // 200, not 201 — nothing was created NOW

    var order = await orders.CreateAsync(request.ToCommand(), ct);
    await idempotency.SaveAsync(key, order, TimeSpan.FromHours(24), ct);

    return CreatedAtAction(nameof(Get), new { id = order.Id }, order);
}

// PATCH IDEMPOTENCY DEPENDS ON THE PATCH:
//   { "status": "cancelled" }        idempotent — same result every time
//   { "op": "increment", "n": 1 }    NOT idempotent — each call adds one
// JSON Merge Patch (RFC 7396) is idempotent by construction; JSON Patch
// (RFC 6902) is not, because it supports operations like "add to array".

// PUT vs PATCH, the practical difference:
PUT   /api/orders/42   { "customerId": 1, "status": "paid", "notes": null }
//   FULL replacement. Omitting a field means "set it to its default", so a
//   client that GETs, modifies one field and PUTs back will WIPE any field it
//   did not know about — a real hazard when the API adds fields over time.
PATCH /api/orders/42   { "status": "paid" }
//   Partial. Absent fields are untouched. Safer for evolving APIs, and the
//   right default for update endpoints.
Key insight: the difference between "unspecified" and "explicitly null" is where PATCH implementations quietly break. In JSON, {"notes": null} means "clear the notes" while {} means "leave notes alone" — but a naive DTO with a nullable string? Notes binds both to null and cannot tell them apart. The fixes are a wrapper type carrying an explicit "was this present" flag, JSON Merge Patch semantics via JsonElement inspection, or JsonPatchDocument. Ignoring the distinction produces an API where clearing a field is impossible, or where every partial update silently nulls everything omitted.

Part 3 — Pagination That Scales

// OFFSET PAGINATION — simple, universally understood, degrades badly:
GET /api/orders?page=3&size=20        // SQL: OFFSET 40 LIMIT 20

[HttpGet]
public async Task<ActionResult<PagedResult<OrderSummary>>> List(
    [FromQuery] PageRequest paging, CancellationToken ct)
{
    var query = db.Orders.AsNoTracking().OrderByDescending(o => o.CreatedAt);

    var total = await query.CountAsync(ct);          // ← a second full scan
    var items = await query
        .Skip((paging.Page - 1) * paging.Size)
        .Take(paging.Size)
        .Select(o => new OrderSummary(o.Id, o.Total, o.CreatedAt))
        .ToListAsync(ct);

    return Ok(new PagedResult<OrderSummary>(items, total, paging.Page, paging.Size));
}

// TWO PROBLEMS AT SCALE, both invisible in development:
//   1. OFFSET 500000 makes the database read and DISCARD 500,000 rows. Page
//      one is instant; page 25,000 times out. The cost is linear in the offset.
//   2. INSTABILITY — if a row is inserted between requests, page 2 repeats an
//      item from page 1, or skips one. Users see duplicates while scrolling.

// KEYSET (CURSOR) PAGINATION — constant time, stable:
GET /api/orders?after=2026-08-01T10:30:00Z_4821&size=20

var query = db.Orders.AsNoTracking();
if (cursor is not null)
{
    // Compare the SORT TUPLE, not just the timestamp — ties on CreatedAt
    // would otherwise skip or repeat rows.
    query = query.Where(o =>
        o.CreatedAt < cursor.CreatedAt ||
        (o.CreatedAt == cursor.CreatedAt && o.Id < cursor.Id));
}
var items = await query
    .OrderByDescending(o => o.CreatedAt).ThenByDescending(o => o.Id)
    .Take(size + 1)                    // fetch one extra to detect "has more"
    .ToListAsync(ct);

var hasMore = items.Count > size;
if (hasMore) items.RemoveAt(items.Count - 1);

// The index (CreatedAt DESC, Id DESC) makes this a SEEK: the database jumps
// straight to the position. Page 25,000 costs the same as page 1.

// WHAT KEYSET GIVES UP, honestly:
//   • no "jump to page 47" — only next/previous. Fine for infinite scroll,
//     wrong for a table with numbered page links.
//   • no total count without a separate (expensive) query. Often the right
//     answer is not to show one, or to show "1000+".
//   • the cursor must encode the full sort tuple, so changing the sort order
//     invalidates outstanding cursors.
//
// CHOOSING: offset for admin tables with modest data and page numbers;
// keyset for feeds, large datasets, and anything a client scrolls. Offering
// both is legitimate — offset for the UI, keyset for bulk export.

// ALWAYS CAP THE PAGE SIZE, in the binder rather than the handler, so no
// endpoint can forget — see Model Binding & Validation.

Part 4 — Concurrency: Preventing Lost Updates

// THE PROBLEM: two clients GET order 42, both edit, both PUT. The second
// write silently overwrites the first. Nobody sees an error, and the first
// user's change is simply gone.

// OPTIMISTIC CONCURRENCY WITH ETAGS — the HTTP-native solution:

[HttpGet("{id:int}")]
public async Task<ActionResult<Order>> Get(int id, CancellationToken ct)
{
    var order = await db.Orders.AsNoTracking()
        .FirstOrDefaultAsync(o => o.Id == id, ct);
    if (order is null) return NotFound();

    // RowVersion is a SQL Server rowversion / PostgreSQL xmin — changed by
    // the database on every update.
    Response.Headers.ETag = $"\"{Convert.ToBase64String(order.RowVersion)}\"";
    return Ok(order);
}

[HttpPut("{id:int}")]
public async Task<IActionResult> Update(
    int id,
    [FromHeader(Name = "If-Match")] string? ifMatch,
    UpdateOrderRequest request,
    CancellationToken ct)
{
    if (string.IsNullOrEmpty(ifMatch))
        return StatusCode(StatusCodes.Status428PreconditionRequired,
            new ProblemDetails { Title = "If-Match header is required." });

    var order = await db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct);
    if (order is null) return NotFound();

    // Tell EF what version we THINK we are updating; it adds the version to
    // the WHERE clause, so a concurrent change makes the UPDATE affect 0 rows.
    db.Entry(order).Property(o => o.RowVersion).OriginalValue =
        Convert.FromBase64String(ifMatch.Trim('"'));

    order.Apply(request);

    try
    {
        await db.SaveChangesAsync(ct);
    }
    catch (DbUpdateConcurrencyException)
    {
        return StatusCode(StatusCodes.Status412PreconditionFailed,
            new ProblemDetails
            {
                Title = "The resource was modified by someone else.",
                Detail = "Re-fetch and retry."
            });
    }

    return NoContent();
}

// STATUS CODES THAT MATTER HERE:
//   428 Precondition Required  the client did not send If-Match. Demanding it
//                              is what makes lost updates IMPOSSIBLE rather
//                              than merely detectable.
//   412 Precondition Failed    the version did not match — someone else won.
//
// A 428 on a missing header is the difference between an API that PREVENTS
// lost updates and one that only prevents them for well-behaved clients.

// PESSIMISTIC LOCKING is the alternative and is usually wrong over HTTP: it
// requires holding a lock across a stateless request boundary, so an
// abandoned browser tab holds a row lock until a timeout. Optimistic
// concurrency fits HTTP's statelessness; pessimistic fits long transactions
// inside one process.

Part 5 — Response Shape and Contract Stability

// A response body is a contract. These decisions are cheap now and expensive
// after clients depend on them.

// 1. NEVER RETURN ENTITIES. Return DTOs.
//    An entity gains a field → that field appears in every response, possibly
//    leaking internal state. An entity is renamed → the API breaks. A lazy
//    navigation property → an N+1 query or a serialization cycle.
public sealed record OrderResponse(
    int Id,
    string Status,
    decimal Total,
    DateTimeOffset CreatedAt,
    IReadOnlyList<OrderLineResponse> Lines);

// 2. WRAP COLLECTIONS from day one:
public sealed record PagedResult<T>(
    IReadOnlyList<T> Items,
    int? Total,
    string? NextCursor);
// A bare array cannot gain metadata without breaking every client.

// 3. BE CONSISTENT ABOUT NULL vs ABSENT:
builder.Services.ConfigureHttpJsonOptions(o =>
{
    o.SerializerOptions.DefaultIgnoreCondition =
        JsonIgnoreCondition.WhenWritingNull;      // omit nulls
    o.SerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase;
});
// Pick one and never mix: a client checking `if ('notes' in response)` breaks
// when the field starts being omitted, and one checking `response.notes !==
// null` breaks when it starts being present-but-null.

// 4. DATES AS ISO 8601 WITH OFFSET — DateTimeOffset, not DateTime:
//    "2026-08-03T14:30:00+00:00"   ✓ unambiguous
//    "2026-08-03T14:30:00"         ✗ whose timezone?
//    1754231400                    ✗ seconds or milliseconds? Which epoch?

// 5. MONEY IS NEVER A DOUBLE:
public sealed record Money(decimal Amount, string Currency);
// A bare `decimal Total` with an implicit currency is a bug waiting for the
// first international customer. Serialize as a string if clients are
// JavaScript, since JSON numbers are IEEE doubles and will corrupt large
// decimals.

// 6. ENUMS AS STRINGS, never as integers:
o.SerializerOptions.Converters.Add(new JsonStringEnumConverter());
// Integer enums couple clients to declaration ORDER. Inserting a value in the
// middle silently reassigns every subsequent one — a breaking change with no
// visible diff in the response shape.

// WHAT COUNTS AS BREAKING, for the record:
//   BREAKING: removing a field, renaming a field, changing a type, changing
//             a status code, making an optional request field required,
//             tightening validation, changing enum integer values
//   SAFE:     adding an optional response field, adding a new endpoint,
//             adding an optional request field, relaxing validation
// Clients that deserialize strictly will break even on "safe" additions,
// which is why documenting a tolerant-reader expectation matters.

Part 6 — Filtering, Sorting, and Bulk Operations

// FILTERING — explicit parameters beat a generic query language:
GET /api/orders?status=paid&from=2026-01-01&minTotal=100

public sealed record OrderFilter(
    string? Status, DateOnly? From, DateOnly? To, decimal? MinTotal);

var query = db.Orders.AsNoTracking();
if (filter.Status is { } s) query = query.Where(o => o.Status == s);
if (filter.From is { } f)   query = query.Where(o => o.CreatedAt >= f.ToDateTime(default));
if (filter.MinTotal is { } m) query = query.Where(o => o.Total >= m);

// WHY NOT OData or a generic filter DSL: it exposes your schema as the public
// contract, makes every column indexable-or-slow, and lets a client write a
// query that scans a billion rows. Explicit parameters are more code and a far
// better boundary — each one is a deliberate, indexable access path.

// SORTING — an ALLOWLIST, never raw column names:
private static readonly Dictionary<string, Expression<Func<Order, object>>> Sorts =
    new(StringComparer.OrdinalIgnoreCase)
    {
        ["createdAt"] = o => o.CreatedAt,
        ["total"]     = o => o.Total,
        ["status"]    = o => o.Status
    };

if (!Sorts.TryGetValue(sort ?? "createdAt", out var keySelector))
    return ValidationProblem($"Cannot sort by '{sort}'.");
// Passing a client string into dynamic LINQ or raw SQL is injection. An
// allowlist also guarantees every sortable column is one you have INDEXED —
// unsortable-because-unindexed is a design decision, not an oversight.

// BULK OPERATIONS — one request, many outcomes. The status code question:
POST /api/orders/bulk
{ "orders": [ {...}, {...}, {...} ] }

// 207 MULTI-STATUS when partial success is meaningful:
{
  "results": [
    { "index": 0, "status": 201, "id": 101 },
    { "index": 1, "status": 409, "error": "Insufficient stock." },
    { "index": 2, "status": 201, "id": 102 }
  ]
}
// The alternative — all-or-nothing in one transaction, returning 201 or 409 —
// is simpler and often better. Choose by asking whether the client can
// usefully act on partial success. If it would just retry everything anyway,
// all-or-nothing is the honest contract.
//
// ALWAYS CAP THE BATCH SIZE. An uncapped bulk endpoint is a caller-controlled
// transaction of unbounded size — it will eventually be sent 100,000 items
// and hold locks long enough to take the database down.

// LONG-RUNNING WORK — 202 Accepted with a status resource:
POST /api/reports          → 202 Accepted
                             Location: /api/reports/jobs/abc123
GET  /api/reports/jobs/abc123 → { "status": "running", "progress": 0.4 }
                             → { "status": "done", "result": "/api/reports/99" }
// Holding an HTTP connection open for a two-minute report is how you discover
// every proxy timeout in your infrastructure at once.

Interview Questions

Beginner: What does idempotent mean, and which HTTP methods are?

An idempotent operation produces the same resulting state whether it is performed once or many times. GET, HEAD, PUT and DELETE are idempotent: fetching twice changes nothing, replacing a resource with the same payload twice leaves the same resource, and deleting an already-deleted resource leaves it deleted. POST is not, because each call is meant to create something new. PATCH depends on the patch itself — setting a field to a value is idempotent, incrementing a counter is not. This matters practically because it tells a client, proxy or retry policy whether a timed-out request can safely be repeated; retrying a POST is exactly how duplicate orders occur.

Beginner: Why should a list endpoint return an object rather than a bare array?

Because the response shape is a contract, and a bare array leaves nowhere to add metadata later. Once clients have written response.map(...) against a top-level array, introducing pagination, a total count, or a next-page cursor requires changing the top-level type, which breaks every consumer. Wrapping from the start — { "items": [...] } — costs nothing and makes all of those additive, non-breaking changes. There is also a minor security argument: top-level JSON arrays were historically vulnerable to JSON hijacking in older browsers.

Mid: Explain the difference between offset and keyset pagination and when to use each.

Offset pagination uses page and size translated to SQL OFFSET/LIMIT. It is simple and supports jumping to an arbitrary page, but the database must read and discard every skipped row, so cost grows linearly with depth and page 25,000 times out. It is also unstable: rows inserted between requests cause items to repeat or be skipped as the user scrolls. Keyset pagination instead carries a cursor encoding the last row's sort values and filters with a WHERE on that tuple, letting the database seek directly via an index, so every page costs the same and results are stable under concurrent inserts. What keyset gives up is random page access and a cheap total count. So offset suits admin tables with numbered pages and modest data, keyset suits feeds, infinite scroll and large datasets, and offering both is a reasonable answer when the UI needs page numbers but exports need to scale.

Mid: How do you prevent lost updates in a REST API?

With optimistic concurrency over HTTP's conditional-request mechanism. The GET response carries an ETag derived from a version marker on the row — a SQL Server rowversion, PostgreSQL's xmin, or a hash. The client echoes it back in an If-Match header on the update. The server includes that version in the WHERE clause, so if another writer changed the row in between, the update affects zero rows and EF raises DbUpdateConcurrencyException, which becomes a 412 Precondition Failed telling the client to re-fetch and retry. The detail that turns this from detection into prevention is rejecting updates that omit If-Match with 428 Precondition Required — otherwise a careless client simply skips the check and overwrites silently. Pessimistic locking is the alternative but fits HTTP poorly, since it would hold a database lock across a stateless request boundary and an abandoned client would block the row until timeout.

Senior: A mobile client reports occasional duplicate orders. Diagnose and design the fix.

The signature of this is a POST that timed out at the client while succeeding at the server: the order was created, the response never arrived, and the client's retry logic sent it again. Mobile networks make this common rather than rare, so I would expect it to correlate with poor connectivity rather than with load. I would confirm by looking for orders with near-identical payloads and timestamps seconds apart from one user, and by checking whether the client retries POSTs at all. The fix is an idempotency key generated by the client — it has to be the client, because only it knows that attempt two is a retry of attempt one rather than a genuine second order — sent as a header and stored server-side with the resulting order. The critical implementation detail is that the reserve must be atomic: a get-then-set sequence has a race where two concurrent retries both find nothing and both create, which is precisely the duplicate the mechanism exists to prevent, so it needs an INSERT ... ON CONFLICT, a unique constraint, or a Redis SETNX. The replay should return 200 with the original order rather than 201, since nothing was created on that call, and keys should expire after a retry window rather than being retained forever. There is one residual gap worth naming: if the process dies between creating the order and saving the key, a retry duplicates anyway — closing that requires writing the order and the key in the same transaction. I would also add a unique constraint on a natural business key where one exists, as defence in depth, because it makes duplicates impossible at the storage layer regardless of application logic.

Senior: How do you evolve a public API without breaking clients?

I start from the distinction between additive and breaking changes and try to keep almost everything additive. Adding an optional response field, a new endpoint, or an optional request parameter is safe for tolerant readers; removing or renaming a field, changing a type, changing a status code, tightening validation, or making an optional field required are all breaking. Some are subtly breaking in ways teams miss — changing integer enum values by inserting a member, or switching a field from always-present-null to omitted, both break clients while looking cosmetic in a diff. So the first practice is documenting a tolerant-reader expectation: clients must ignore unknown fields, and that expectation has to be stated early because it cannot be introduced retroactively. Second, I version only when genuinely forced, because every version is a maintenance burden and parallel code paths diverge; most changes can be additive with a deprecation period instead. When a version is unavoidable I prefer URL-path versioning for its visibility in logs and cache keys, run both versions concurrently for a stated window, and instrument usage so I can see who is still on the old one rather than guessing. Third, I use Sunset and Deprecation headers plus direct outreach to the top consumers, since a changelog nobody reads is not a migration plan. Fourth, contract tests run against recorded real client payloads, because unit tests assert what I believe the contract is while recorded traffic reveals what clients actually depend on — including fields I thought were unused. Finally I treat error responses as part of the contract too: changing a status code or an error body shape breaks client branching exactly as surely as changing a success shape, and it is the part teams most often forget to version.

//   the original all-POST design made every one of these unretryable

2 (easy): Choose status codes: (a) created a resource, (b) successful delete, (c) version conflict on update, (d) accepted a long-running job.
Solution 
// (a) resource created        → 201 Created + Location header
return CreatedAtAction(nameof(Get), new { id = order.Id }, response);

// (b) successful delete        → 204 No Content
//     Not 200 with an empty body, and not 404 on a second delete — DELETE is
//     idempotent, so deleting an already-deleted resource is a SUCCESS.
return NoContent();

// (c) version conflict         → 412 Precondition Failed
//     (428 Precondition Required if the client omitted If-Match entirely)
return StatusCode(StatusCodes.Status412PreconditionFailed, problem);

// (d) long-running job accepted → 202 Accepted + Location of a status resource
Response.Headers.Location = $"/api/reports/jobs/{jobId}";
return Accepted();

// 202 means "I have not done this yet but I have taken responsibility for it".
// The Location points at a resource the client polls, which is what keeps the
// HTTP connection short and avoids every proxy timeout in the path.
3 (medium): Implement keyset pagination over orders sorted by CreatedAt descending, handling ties correctly.
Solution 
public sealed record Cursor(DateTimeOffset CreatedAt, int Id)
{
    public string Encode() => Convert.ToBase64String(
        Encoding.UTF8.GetBytes($"{CreatedAt:O}|{Id}"));

    public static Cursor? Decode(string? value)
    {
        if (string.IsNullOrEmpty(value)) return null;
        var parts = Encoding.UTF8.GetString(Convert.FromBase64String(value)).Split('|');
        return new Cursor(DateTimeOffset.Parse(parts[0]), int.Parse(parts[1]));
    }
}

[HttpGet]
public async Task<ActionResult<CursorPage<OrderSummary>>> List(
    string? after, int size = 20, CancellationToken ct = default)
{
    size = Math.Clamp(size, 1, 100);
    var cursor = Cursor.Decode(after);

    var query = db.Orders.AsNoTracking();

    if (cursor is not null)
    {
        // THE TIE HANDLING: comparing CreatedAt alone would skip or repeat
        // rows sharing a timestamp. Compare the full sort TUPLE.
        query = query.Where(o =>
            o.CreatedAt < cursor.CreatedAt ||
            (o.CreatedAt == cursor.CreatedAt && o.Id < cursor.Id));
    }

    var items = await query
        .OrderByDescending(o => o.CreatedAt)
        .ThenByDescending(o => o.Id)          // MUST match the WHERE tuple
        .Take(size + 1)                       // one extra detects "has more"
        .Select(o => new OrderSummary(o.Id, o.Total, o.CreatedAt))
        .ToListAsync(ct);

    var hasMore = items.Count > size;
    if (hasMore) items.RemoveAt(items.Count - 1);

    return Ok(new CursorPage<OrderSummary>(
        items,
        hasMore ? new Cursor(items[^1].CreatedAt, items[^1].Id).Encode() : null));
}

Solution 
[HttpGet("{id:int}")]
public async Task<ActionResult<OrderResponse>> Get(int id, CancellationToken ct)
{
    var order = await db.Orders.AsNoTracking()
        .FirstOrDefaultAsync(o => o.Id == id, ct);
    if (order is null) return NotFound();

    Response.Headers.ETag = $"\"{Convert.ToBase64String(order.RowVersion)}\"";
    return Ok(order.ToResponse());
}

[HttpPut("{id:int}")]
public async Task<IActionResult> Update(
    int id,
    [FromHeader(Name = "If-Match")] string? ifMatch,
    UpdateOrderRequest request,
    CancellationToken ct)
{
    // 428 — the step that turns DETECTION into PREVENTION. Without it a
    // client that simply omits the header overwrites silently, and the whole
    // mechanism protects only well-behaved callers.
    if (string.IsNullOrWhiteSpace(ifMatch))
        return StatusCode(StatusCodes.Status428PreconditionRequired,
            new ProblemDetails
            {
                Title = "If-Match header is required for updates.",
                Detail = "GET the resource to obtain its current ETag."
            });

    var order = await db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct);
    if (order is null) return NotFound();

    db.Entry(order).Property(o => o.RowVersion).OriginalValue =
        Convert.FromBase64String(ifMatch.Trim('"'));

    order.Apply(request);

    try
    {
        await db.SaveChangesAsync(ct);
    }
    catch (DbUpdateConcurrencyException)
    {
        // EF adds RowVersion to the WHERE clause; a concurrent change makes
        // the UPDATE affect 0 rows, which EF surfaces as this exception.
        return StatusCode(StatusCodes.Status412PreconditionFailed,
            new ProblemDetails
            {
                Title = "The resource was modified by another user.",
                Detail = "Re-fetch the resource and reapply your changes."
            });
    }

    Response.Headers.ETag = $"\"{Convert.ToBase64String(order.RowVersion)}\"";
    return NoContent();
}

5 (hard): Design a PATCH endpoint that can distinguish "set to null" from "leave unchanged".
Solution 
// THE PROBLEM: a naive DTO cannot tell these apart —
//   PATCH { "notes": null }   → clear the notes
//   PATCH { }                 → leave notes alone
// Both bind `string? Notes` to null. Result: either clearing is impossible,
// or every omitted field gets wiped.

// OPTION A — an explicit optional wrapper (type-safe, self-documenting):
public readonly struct Optional<T>
{
    public bool HasValue { get; }
    public T? Value { get; }
    private Optional(T? value, bool hasValue) { Value = value; HasValue = hasValue; }
    public static Optional<T> Of(T? value) => new(value, true);
    public static Optional<T> None => default;      // HasValue == false
}

public sealed class OptionalConverter<T> : JsonConverter<Optional<T>>
{
    // Only invoked when the PROPERTY IS PRESENT, which is exactly the signal
    // we need — an absent property leaves the field at default (None).
    public override Optional<T> Read(ref Utf8JsonReader reader,
        Type type, JsonSerializerOptions options)
        => Optional<T>.Of(JsonSerializer.Deserialize<T>(ref reader, options));

    public override void Write(Utf8JsonWriter writer,
        Optional<T> value, JsonSerializerOptions options)
        => JsonSerializer.Serialize(writer, value.Value, options);
}

public sealed record PatchOrderRequest
{
    public Optional<string?> Notes { get; init; }
    public Optional<string> Status { get; init; }
}

[HttpPatch("{id:int}")]
public async Task<IActionResult> Patch(
    int id, PatchOrderRequest request, CancellationToken ct)
{
    var order = await db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct);
    if (order is null) return NotFound();

    if (request.Notes.HasValue)  order.Notes = request.Notes.Value;   // may be null
    if (request.Status.HasValue) order.Status = request.Status.Value!;

    await db.SaveChangesAsync(ct);
    return NoContent();
}

// OPTION B — JSON Merge Patch (RFC 7396) semantics via raw JsonElement:
//   null means DELETE the member, absent means leave it. Idempotent by
//   construction, and a widely understood standard, but you lose static typing
//   and must validate by hand.

// OPTION C — JsonPatchDocument (RFC 6902): op/path/value arrays.
//   Most expressive (supports array operations), least ergonomic, and NOT
//   idempotent for ops like "add" to a collection — which undermines safe
//   retries.

// I default to OPTION A: it keeps the DTO typed and validatable, makes the
// three-state nature explicit in the signature, and stays idempotent.
6 (hard): Design the read endpoints for an order history feed serving web (page numbers) and mobile (infinite scroll), at 50 million rows.
Solution 
// TWO CLIENTS WITH GENUINELY DIFFERENT ACCESS PATTERNS. Serving both from one
// pagination style means serving one of them badly.

// ── MOBILE: keyset, the scalable default ────────────────────────────────
GET /api/orders?after={cursor}&size=20
//   • constant-time regardless of depth — page 25,000 costs what page 1 does
//   • stable under concurrent inserts, so scrolling never repeats an item
//   • no total count, which infinite scroll does not need anyway
//   Requires: INDEX (customer_id, created_at DESC, id DESC)

// ── WEB: offset, BOUNDED ────────────────────────────────────────────────
GET /api/orders?page=3&size=20
//   Page numbers genuinely need random access, which keyset cannot give.
//   The mitigation is to CAP the reachable depth:
if (page * size > 10_000)
    return ValidationProblem(
        "Cannot page beyond 10,000 results. Narrow the filter or use a cursor.");
//   This is a real product decision, not a cop-out: nobody browses to page
//   500 of their order history. They filter. Capping depth converts an
//   unbounded scan into a bounded one and pushes users toward the filter,
//   which is the access path that actually has an index.

// ── THE COUNT PROBLEM ───────────────────────────────────────────────────
//   COUNT(*) over 50M rows per request is unacceptable. Options:
//     • omit the total entirely for cursor clients
//     • "1,000+" — cap the count query with .Take(1001) and report
//       approximately, which is what most UIs actually need
//     • a periodically-refreshed materialised count per customer
var total = await query.Take(1001).CountAsync(ct);
var display = total > 1000 ? "1000+" : total.ToString();

// ── ONE ENDPOINT, BOTH MODES ────────────────────────────────────────────
// `after` present → keyset; `page` present → offset. Rejecting BOTH at once
// prevents an incoherent request:
if (after is not null && page is not null)
    return ValidationProblem("Specify either 'after' or 'page', not both.");

// ── SUPPORTING DECISIONS AT THIS SCALE ──────────────────────────────────
//   • ALWAYS scope by customer first — the index leads with customer_id, so
//     the working set per request is one customer's orders, not 50M rows
//   • project to a summary DTO in the query (.Select before .ToListAsync) so
//     the database returns three columns rather than whole entities
//   • AsNoTracking on every read path — change tracking on a list query is
//     pure overhead
//   • consider a read replica; order history is tolerant of replication lag
//   • cache the FIRST page per customer, since it is requested far more often
//     than any other and is cheap to invalidate on a new order
//
// ── THE TRADE-OFF STATED PLAINLY ────────────────────────────────────────
// Web clients lose the ability to jump arbitrarily deep. That is a deliberate
// exchange: unbounded deep paging is a latent outage that one bored user or
// one scraper triggers. Bounding it makes worst-case cost predictable, and
// the filter path — which is indexed — is the one users genuinely want.

🎯 Key Takeaways

  • Model resources as nouns with HTTP methods as verbs; verbs in URLs turn REST into RPC and forfeit caching and safe retries.
  • Safe means no state change; idempotent means repeatable. GET/HEAD are both, PUT/DELETE are idempotent, POST is neither.
  • Make POST retryable with a client-supplied idempotency key reserved atomically — a get-then-set race recreates the duplicate.
  • Wrap list responses in an object from day one; a bare array cannot gain pagination metadata without breaking clients.
  • Offset pagination degrades linearly and repeats rows under inserts; keyset is constant-time and stable but gives up page numbers and cheap totals.
  • Prevent lost updates with ETag plus If-Match, returning 412 on mismatch and 428 when the header is missing.
  • Return DTOs, never entities — entities leak new fields, cause cycles, and couple the wire format to the schema.
  • Serialize enums as strings and dates as DateTimeOffset; integer enums break silently when a member is inserted.
  • Filter and sort through explicit allowlists mapped to indexed columns — never client-supplied column names.
  • PATCH needs a three-state model to distinguish "set null" from "omitted", or clearing a field becomes impossible.
