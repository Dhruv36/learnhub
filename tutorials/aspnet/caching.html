Caching & Output Caching Data

What you'll master: the caching layers available and which problem each one actually solves, invalidation strategies and why time-based expiry is usually the honest choice, the stampede and its fixes, the cache-key mistakes that leak one user's data to another, and the HTTP caching headers that let you avoid the work entirely. Prerequisites: EF Core: Change Tracking & Transactions and Middleware Pipeline.

Part 1 — The Layers, and What Each Is For

// Five distinct caching layers, ordered from closest to the user. Each solves
// a different problem, and using the wrong one is why caches disappoint.
//
//   1. CLIENT / CDN      Cache-Control headers. Zero server cost per hit —
//                        the request never arrives. Best possible outcome.
//   2. OUTPUT CACHE      the whole HTTP response, server-side, keyed by URL
//                        and chosen varying headers.
//   3. RESPONSE CACHE    HTTP-compliant caching middleware honouring
//                        Cache-Control. Largely superseded by output caching.
//   4. IN-MEMORY         IMemoryCache. Objects in this process's heap.
//                        Fastest, but per-instance and lost on restart.
//   5. DISTRIBUTED       IDistributedCache / Redis. Shared across instances,
//                        survives restarts, costs a network hop and
//                        serialization.

// THE DECISION, in one pass:
//   • can the CLIENT cache it? → Cache-Control. Nothing beats a request that
//     is never made.
//   • is the whole RESPONSE cacheable for all users? → output caching
//   • is it an expensive OBJECT used by one instance? → IMemoryCache
//   • must every instance see the same value, or must it survive restart?
//     → distributed cache
//   • is it a computed value with a stampede risk? → HybridCache (Part 4)

// IN-MEMORY — the basics plus the part people miss:
builder.Services.AddMemoryCache(o => o.SizeLimit = 1024);   // ← bound it

var product = await cache.GetOrCreateAsync($"product:{id}", async entry =>
{
    entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
    entry.Size = 1;                          // REQUIRED when SizeLimit is set
    return await db.Products.FindAsync(id, ct);
});

// SizeLimit without Size on entries throws at runtime. And WITHOUT a
// SizeLimit at all, IMemoryCache grows until the process is OOM-killed —
// which is the most common in-memory caching incident, because it works
// perfectly until traffic shifts.

// SLIDING vs ABSOLUTE, and why you usually want both:
entry.SlidingExpiration = TimeSpan.FromMinutes(5);       // extends on each hit
entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1);   // hard ceiling
// Sliding alone means a continuously-requested key NEVER expires, so stale
// data can live forever. The absolute expiry is the guarantee that it does not.

// DISTRIBUTED — the interface is byte-oriented, so serialization is yours:
var cached = await distributedCache.GetStringAsync($"product:{id}", ct);
if (cached is not null) return JsonSerializer.Deserialize<Product>(cached);

var product = await db.Products.FindAsync([id], ct);
await distributedCache.SetStringAsync($"product:{id}",
    JsonSerializer.Serialize(product),
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
    }, ct);

// THE COST TO WEIGH: a Redis round trip is roughly 0.5-2ms plus
// serialization. If the underlying query takes 1ms, the cache makes it
// SLOWER. Measure before assuming a cache helps — caching a fast query behind
// a network hop is a real and common regression.

Part 2 — Output Caching

// Output caching stores the entire response and serves it without running
// the endpoint at all.
builder.Services.AddOutputCache(options =>
{
    options.DefaultExpirationTimeSpan = TimeSpan.FromSeconds(30);

    options.AddBasePolicy(builder => builder.Cache());

    options.AddPolicy("products", builder => builder
        .Expire(TimeSpan.FromMinutes(5))
        .SetVaryByQuery("category", "page")     // ← key includes these
        .Tag("products"));                      // ← for targeted eviction
});

var app = builder.Build();
app.UseOutputCache();                           // AFTER UseRouting

app.MapGet("/api/products", GetProducts).CacheOutput("products");
app.MapGet("/api/stats", GetStats).CacheOutput(b => b.Expire(TimeSpan.FromMinutes(1)));

// TAG-BASED EVICTION — the feature that makes output caching practical,
// because it lets a write invalidate exactly the affected responses:
app.MapPost("/api/products", async (
    CreateProduct request,
    ProductService products,
    IOutputCacheStore cache,
    CancellationToken ct) =>
{
    var product = await products.CreateAsync(request, ct);
    await cache.EvictByTagAsync("products", ct);   // every tagged response
    return TypedResults.Created($"/api/products/{product.Id}", product);
});

// WHAT IS CACHED AND WHAT IS NOT — the rules that cause surprises:
//   • only GET and HEAD are cached by default
//   • responses with a Set-Cookie header are NOT cached
//   • authenticated requests are NOT cached by default, which is correct:
//     caching a personalised response under a shared key serves one user's
//     data to another
//   • only 200 responses are cached
//   • VaryByQuery must be EXPLICIT — by default the query string is ignored,
//     so /products?category=a and /products?category=b share a cache entry
//     and return the same content. This is the single most common output
//     caching bug.

// PER-USER CACHING, when you genuinely need it — vary by the identity:
options.AddPolicy("user-dashboard", builder => builder
    .Expire(TimeSpan.FromMinutes(1))
    .SetVaryByValue((context, ct) => new ValueTask<KeyValuePair<string, string>>(
        new("user", context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value ?? "anon"))));
// Getting this wrong is a data leak, not a performance bug. If the vary key
// omits any input that affects the response — user, tenant, role, locale —
// some user receives another's content.

// OUTPUT CACHE vs RESPONSE CACHE:
//   Output caching   server-side store you control, with tag eviction.
//                    Ignores client Cache-Control by default, so a client
//                    cannot force a bypass. This is the modern choice.
//   Response caching HTTP-spec middleware honouring request Cache-Control,
//                    which means any client can send no-cache and bypass it.
//                    Rarely what you want on a server.
Key insight: a cache key must include every input that changes the response. This sounds obvious and is violated constantly, because the inputs are not all in the URL — the authenticated user, the tenant, the locale, the role, and any feature flag can all vary the output while leaving the path identical. When a key omits one of these, the failure mode is not a stale value, it is one user receiving another user's data, which is a security incident rather than a performance defect. Before adding any cache, enumerate the inputs deliberately and confirm each one is either in the key or genuinely cannot vary.

Part 3 — Invalidation

// Four strategies, in increasing order of complexity and correctness.

// 1. TIME-BASED EXPIRY — the default, and usually the right answer.
entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
// Correct within a bounded staleness window, requires no coordination, and
// cannot leak. Ask "how stale can this be?" — the answer is often minutes,
// and then nothing more elaborate is warranted.

// 2. WRITE-THROUGH / EXPLICIT EVICTION — evict on the write path.
public async Task<Product> UpdateAsync(int id, UpdateProduct request, CancellationToken ct)
{
    var product = await db.Products.FindAsync([id], ct);
    product!.Apply(request);
    await db.SaveChangesAsync(ct);

    await cache.RemoveAsync($"product:{id}", ct);      // evict, do not update
    await outputCache.EvictByTagAsync("products", ct);

    return product;
}
// EVICT RATHER THAN UPDATE: writing the new value into the cache introduces a
// race where two concurrent writers store values in the opposite order to
// their commits, leaving the cache permanently disagreeing with the database.
// Deleting is idempotent and always converges to a correct re-read.
//
// THE HARD PART: this only works if every write path evicts. A background
// job, a database migration, an admin tool or a second service writing the
// same table all bypass it — and then the cache is silently wrong until the
// TTL saves you. Which is the argument for always having a TTL as well.

// 3. VERSIONED KEYS — invalidate a whole family without enumerating it:
var version = await cache.GetStringAsync($"catalog:version", ct) ?? "1";
var key = $"catalog:v{version}:page:{page}";
// Bumping catalog:version orphans every old key at once. They expire on their
// own TTL, so there is no scan and no eviction storm.

// 4. DEPENDENCY / CHANGE TOKENS — evict a group when a source changes:
var cts = new CancellationTokenSource();
cache.Set("product:1", product, new MemoryCacheEntryOptions()
    .AddExpirationToken(new CancellationChangeToken(cts.Token)));
cts.Cancel();      // evicts every entry holding this token

// THE CACHE-ASIDE PATTERN, written correctly:
public async Task<Product?> GetAsync(int id, CancellationToken ct)
{
    var key = $"product:{id}";

    if (await cache.GetStringAsync(key, ct) is { } json)
        return JsonSerializer.Deserialize<Product>(json);

    var product = await db.Products.AsNoTracking()
        .FirstOrDefaultAsync(p => p.Id == id, ct);

    if (product is not null)
    {
        await cache.SetStringAsync(key, JsonSerializer.Serialize(product),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            }, ct);
    }
    // NOTE: a null result is deliberately NOT cached here — see the cache
    // penetration problem in Part 4.

    return product;
}

Part 4 — Stampedes, Penetration, and HybridCache

// THE STAMPEDE (dogpile): a popular key expires, and every concurrent request
// misses simultaneously. All of them run the expensive query at once.
//
//   normal:   1 query per 5 minutes
//   stampede: 500 identical queries in the same millisecond
//
// Under sustained load this is self-reinforcing: the queries slow the
// database, so more requests pile up before the first one repopulates. A
// cache that works fine at moderate traffic can take a system down at peak.

// ✗ The naive cache-aside above has NO stampede protection.

// ✓ HybridCache (.NET 9+) — the modern answer, and it solves this by design:
builder.Services.AddHybridCache(options =>
{
    options.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration = TimeSpan.FromMinutes(5),        // distributed (L2)
        LocalCacheExpiration = TimeSpan.FromMinutes(1)   // in-process (L1)
    };
});

public async Task<Product?> GetAsync(int id, CancellationToken ct)
    => await hybrid.GetOrCreateAsync(
        $"product:{id}",
        async token => await db.Products.AsNoTracking()
            .FirstOrDefaultAsync(p => p.Id == id, token),
        cancellationToken: ct);

// WHAT HYBRIDCACHE GIVES YOU over hand-rolled cache-aside:
//   • TWO TIERS: L1 in-memory (no network hop) backed by L2 distributed
//     (shared, survives restart) — you get both without writing the
//     coordination
//   • STAMPEDE PROTECTION built in: concurrent misses for the same key are
//     coalesced, so exactly ONE factory call runs and the rest await it
//   • TAG-BASED INVALIDATION: RemoveByTagAsync across both tiers
//   • pluggable serialization, and it is the direction Microsoft is investing
//
// The two-tier design also fixes the "Redis round trip is slower than the
// query" problem from Part 1 — hot keys are served from L1 at memory speed.

await hybrid.RemoveAsync($"product:{id}", ct);
await hybrid.RemoveByTagAsync("products", ct);

// HAND-ROLLED STAMPEDE PROTECTION, if you cannot use HybridCache:
private static readonly SemaphoreSlim Gate = new(1, 1);

if (cache.TryGetValue(key, out Product? cached)) return cached;

await Gate.WaitAsync(ct);
try
{
    if (cache.TryGetValue(key, out cached)) return cached;   // double-check
    cached = await LoadAsync(ct);
    cache.Set(key, cached, TimeSpan.FromMinutes(5));
    return cached;
}
finally { Gate.Release(); }
// ponytail: one global semaphore serialises ALL misses, not just misses for
// the same key. Per-key locks (a ConcurrentDictionary of semaphores) fix that
// if contention across different keys becomes measurable.

// CACHE PENETRATION — the other failure mode: repeated requests for a key
// that does NOT exist miss the cache every time and hit the database every
// time. An attacker enumerating random ids bypasses the cache entirely.
//   ✓ cache the negative result, briefly:
if (product is null)
{
    await cache.SetStringAsync(key, "null",
        new() { AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(30) }, ct);
}
// A SHORT TTL is deliberate: a newly-created record should become visible
// quickly, so 30 seconds bounds the wrongness while still absorbing an
// enumeration attack.

Part 5 — HTTP Caching: Avoiding the Request Entirely

// The cheapest response is the one never sent. Cache-Control tells clients
// and CDNs they may reuse what they already have.

app.MapGet("/api/products/{id:int}", async (int id, ProductService products,
    HttpContext context, CancellationToken ct) =>
{
    var product = await products.FindAsync(id, ct);
    if (product is null) return Results.NotFound();

    context.Response.GetTypedHeaders().CacheControl = new CacheControlHeaderValue
    {
        Public = true,                                // CDNs may cache
        MaxAge = TimeSpan.FromMinutes(5),             // browser TTL
        SharedMaxAge = TimeSpan.FromMinutes(30)       // CDN TTL (s-maxage)
    };

    return Results.Ok(product);
});

// THE DIRECTIVES THAT MATTER:
//   public          any cache may store it (CDN, proxy, browser)
//   private         only the end client — REQUIRED for personalised responses
//   no-cache        may store, but must revalidate before reuse
//   no-store        never store anywhere. For anything sensitive.
//   max-age         freshness for private caches
//   s-maxage        freshness for shared caches, overrides max-age
//   must-revalidate once stale, do NOT serve without revalidating
//
// `public` on a personalised response is a data leak: a shared CDN will serve
// one user's response to the next requester. Personalised responses are
// `private`, and secrets are `no-store`.

// CONDITIONAL REQUESTS — a 304 sends headers only, no body:
var etag = $"\"{product.RowVersion}\"";

if (context.Request.Headers.IfNoneMatch == etag)
    return Results.StatusCode(StatusCodes.Status304NotModified);

context.Response.Headers.ETag = etag;
return Results.Ok(product);

// This still runs the query, so it saves BANDWIDTH not database load. To save
// both, derive the ETag from something you can check cheaply — a version
// column, an updated-at timestamp, or a cached version number — and return
// 304 before loading the entity at all.

// VARY tells caches which request headers change the response:
context.Response.Headers.Vary = "Accept-Encoding, Accept-Language";
// Omitting Vary when the response depends on a header means a cache serves
// the wrong variant — the compressed body to a client that cannot decompress
// it, or the wrong language. Vary: Authorization is generally wrong; use
// Cache-Control: private instead, since varying by credential produces an
// unbounded number of cache entries.

Part 6 — Operating a Cache

// MEASURE BEFORE AND AFTER. A cache with a low hit ratio is pure overhead —
// extra latency, extra memory, extra failure modes, no benefit.
private static readonly Counter<long> Hits =
    Meter.CreateCounter<long>("cache.hits");
private static readonly Counter<long> Misses =
    Meter.CreateCounter<long>("cache.misses");

// Track per cache NAME, not per key — per-key metrics are a cardinality
// explosion that will take down your metrics backend:
Hits.Add(1, new KeyValuePair<string, object?>("cache", "products"));

// A hit ratio below ~70% usually means one of:
//   • the TTL is shorter than the request interval for that key
//   • the key includes something too variable (a timestamp, a request id)
//   • the data genuinely is not reused, and should not be cached

// RESILIENCE: THE CACHE MUST NOT BE A HARD DEPENDENCY. If Redis is down, the
// application should be slower, not broken:
try
{
    if (await cache.GetStringAsync(key, ct) is { } json)
        return JsonSerializer.Deserialize<Product>(json);
}
catch (RedisConnectionException ex)
{
    log.LogWarning(ex, "Cache unavailable; falling through to the database.");
    // swallow deliberately — continue to the source of truth
}

return await db.Products.FindAsync([id], ct);
// Without this, a cache outage becomes an application outage, which is the
// opposite of what the cache was added to achieve. Combine with a short cache
// timeout so a hung Redis does not stall every request:
//   options.ConnectTimeout = 1000; options.SyncTimeout = 1000;

// CACHE WARMING at startup, for keys whose first miss is expensive:
public sealed class CacheWarmer(IServiceScopeFactory scopes, HybridCache cache)
    : IHostedService
{
    public async Task StartAsync(CancellationToken ct)
    {
        using var scope = scopes.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        foreach (var category in await db.Categories.AsNoTracking().ToListAsync(ct))
            await cache.GetOrCreateAsync($"category:{category.Id}",
                _ => ValueTask.FromResult(category), cancellationToken: ct);
    }
    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}
// Keep this fast. Slow work in StartAsync delays readiness on every rollout,
// and a warmer that queries everything turns a deploy into an outage.

// WHAT NOT TO CACHE, stated plainly:
//   • anything a user may not see, under a key that omits their identity
//   • data whose staleness has legal or financial consequences — account
//     balances, stock levels used for reservation, permissions
//   • results of fast queries: a 1ms query behind a 2ms Redis hop is slower
//   • data written far more often than read: every write evicts, so the hit
//     ratio approaches zero and only the overhead remains
//
// PERMISSIONS are the one worth stating twice. Caching an authorization
// decision means a revoked permission stays effective until the TTL — and
// "we revoked their access an hour ago" is not an acceptable answer during an
// incident.

Interview Questions

Beginner: What is the difference between in-memory and distributed caching?

IMemoryCache stores objects on the current process's heap, so access is extremely fast with no serialization or network hop — but each instance has its own copy, entries are lost on restart, and the cache competes with the application for memory. A distributed cache such as Redis stores data in an external service, so every instance sees the same values and the cache survives restarts and deployments, at the cost of serialization and a network round trip of roughly half a millisecond to a few milliseconds. The practical consequence is that in-memory suits per-instance derived data where inconsistency between instances is tolerable, while distributed is required when instances must agree — session state, rate-limit counters, or anything where a user hitting a different server must see the same result.

Beginner: Why must a cache key include the user for personalised responses?

Because the cache key is the entire basis on which a stored response is considered reusable. If the key is just the URL and the response depends on who is asking, then the first user's response is stored and served to everyone else who requests that URL. That is not a stale-data bug, it is one user receiving another user's private data — a security incident. The same reasoning applies to tenant, role and locale: every input that changes the response must appear in the key, and the safest habit is to enumerate those inputs explicitly before adding a cache rather than assuming the URL captures them.

Mid: What is a cache stampede and how do you prevent it?

A stampede — or dogpile — happens when a popular cache entry expires and every concurrent request misses at the same moment, so instead of one expensive query you get hundreds executing simultaneously. It is particularly dangerous because it is self-reinforcing under load: the flood of identical queries slows the database, which means more requests arrive and miss before the first one repopulates the entry. The standard fix is request coalescing, where concurrent misses for the same key wait on a single in-flight factory call rather than all executing it. HybridCache provides this by default, which is a strong reason to prefer it over hand-rolled cache-aside. Hand-rolling it requires a per-key lock with a double-check after acquiring, and the detail people get wrong is using one global lock, which serialises misses across unrelated keys. Probabilistic early expiration — refreshing slightly before the TTL with a randomised jitter — is a complementary technique that avoids synchronised expiry across many keys.

Mid: When would you evict a cache entry rather than update it in place?

Almost always. Updating in place looks more efficient because it avoids the next request's cache miss, but it introduces a race: two concurrent writers can commit to the database in one order and write to the cache in the opposite order, leaving the cache holding a value that matches neither the final database state nor any consistent point in time — and it stays wrong until the TTL expires. Eviction is idempotent and always converges, because the next read repopulates from the source of truth. The cost is one extra miss, which is negligible compared to serving indefinitely wrong data. The related discipline is that eviction must happen on every write path, and since background jobs, migrations and other services often bypass the application's write path entirely, a TTL should always remain as the backstop.

Senior: After adding Redis caching, p99 latency got worse and an outage took the whole API down. Diagnose.

Two separate problems that commonly arrive together. The latency regression suggests the cached operations were not expensive enough to justify the round trip — a query taking around a millisecond placed behind a Redis call costing one to two milliseconds plus serialization is strictly slower, and the effect is most visible at p99 where Redis latency has its own tail. I would check the hit ratio first: a low ratio means most requests now pay the cache cost and then the database cost, which is the worst of both. The outage is the more serious finding and indicates the cache became a hard dependency — the code path almost certainly lets a RedisConnectionException propagate, so when Redis became unavailable every request failed rather than falling through to the database. That inverts the cache's purpose: it was added for resilience and performance and instead introduced a new single point of failure. The fixes are to wrap cache reads in a try/catch that logs and falls through to the source of truth, and to set aggressive connect and sync timeouts so a hung Redis does not stall request threads — a slow cache can be worse than an absent one, because threads pile up waiting. I would then remove caching from the operations that were already fast, keeping it only where the underlying work genuinely costs more than the round trip, and consider HybridCache so hot keys are served from an in-process L1 without touching Redis at all. Finally I would add hit-ratio and cache-latency metrics per cache name, because the original decision was evidently made without measurement and the same mistake will otherwise recur.

Senior: Design caching for a product catalogue: high read volume, occasional writes, per-tenant pricing.

The per-tenant pricing requirement is the constraint that shapes everything, because it means the response is not globally cacheable and a naive URL-keyed cache would leak one tenant's pricing to another. I would split the data by its variability rather than caching whole responses: the product catalogue itself — names, descriptions, images, categories — is identical for everyone and changes rarely, so it can be cached aggressively with a long TTL, shared across tenants, and served from a CDN with Cache-Control: public. Pricing is per-tenant and cached separately under a key including the tenant id, with a shorter TTL, and never marked public. The endpoint composes the two at request time, which keeps the large, expensive, shared part cacheable while the small tenant-specific part carries the tighter constraints. For the layering I would use HybridCache so hot catalogue entries are served from in-process L1 without a Redis hop while L2 keeps instances consistent and survives deploys, and I would take the built-in stampede protection as a requirement rather than a bonus given the read volume. Invalidation would be tag-based on write — a product update evicts that product's tag and the affected list tags — with TTLs retained as a backstop because a background import or another service will eventually write without going through the API. For pricing I would keep the TTL genuinely short, since pricing errors have financial consequences and I would rather pay for more recomputation than serve a wrong price. Operationally: hit ratio and latency metrics per cache name, cache failures logged and swallowed so Redis being down degrades rather than breaks the service, and negative caching with a short TTL so enumeration of nonexistent product ids does not bypass the cache. The thing I would deliberately not cache is anything used to make an authorization or reservation decision — availability checked at add-to-cart can be cached, but the reservation itself must read through to the database, because a stale stock count that permits an oversell is a business problem no cache hit ratio justifies.

1 (easy): Cache a product lookup in memory for five minutes, bounded so it cannot exhaust memory.
Solution 
builder.Services.AddMemoryCache(options =>
{
    options.SizeLimit = 10_000;          // in units YOU define via entry.Size
});

public async Task<Product?> GetAsync(int id, CancellationToken ct)
    => await cache.GetOrCreateAsync($"product:{id}", async entry =>
    {
        entry.Size = 1;                  // REQUIRED once SizeLimit is set

    });

// SizeLimit is the important part. Without it IMemoryCache grows without

// Setting SizeLimit but forgetting entry.Size throws at runtime, so the two

3 (medium): A cached dashboard is showing one user's data to another. Diagnose and fix.
Solution 
// ✗ THE BUG — the key is the URL, but the response depends on the user:
app.MapGet("/api/dashboard", GetDashboard).CacheOutput(p => p.Expire(TimeSpan.FromMinutes(5)));
// The first user's dashboard is stored under "/api/dashboard" and served to
// everyone. This is a DATA BREACH, not a caching bug.

// ✓ FIX 1 — vary by the authenticated identity:
options.AddPolicy("dashboard", policy => policy
    .Expire(TimeSpan.FromMinutes(1))
    .SetVaryByValue((context, ct) =>
    {
        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
        return ValueTask.FromResult(
            new KeyValuePair<string, string>("user", userId ?? "anonymous"));
    }));

// ✓ FIX 2 — and set the HTTP header correctly, so no CDN or proxy caches it
//   under a shared key either:
context.Response.GetTypedHeaders().CacheControl = new CacheControlHeaderValue
{
    Private = true,                       // NEVER public for personalised data
    MaxAge = TimeSpan.FromMinutes(1)
};

// ✓ FIX 3 — the safest option when the data is genuinely sensitive: do not
//   cache the response at all. Cache the expensive COMPONENTS behind
//   per-user keys instead, and compose per request.

// THE GENERAL RULE: enumerate every input that varies the response — user,
// tenant, role, locale, feature flags — and confirm each is either in the key
// or genuinely invariant. Note that output caching skips authenticated
// requests BY DEFAULT precisely to avoid this; the bug appears when someone
// overrides that default without adding a vary key.
4 (medium): Add stampede protection to an expensive report query.
Solution 
// ✓ PREFERRED — HybridCache coalesces concurrent misses automatically:
builder.Services.AddHybridCache(o =>
{
    o.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration = TimeSpan.FromMinutes(10),
        LocalCacheExpiration = TimeSpan.FromMinutes(2)
    };
});

public async Task<Report> GetAsync(DateOnly date, CancellationToken ct)
    => await hybrid.GetOrCreateAsync(
        $"report:{date:yyyy-MM-dd}",
        async token => await BuildExpensiveReportAsync(date, token),
        cancellationToken: ct);
// 500 concurrent misses → exactly ONE call to BuildExpensiveReportAsync;
// the other 499 await its result.

// ✓ HAND-ROLLED, if HybridCache is unavailable — note PER-KEY locking:
private static readonly ConcurrentDictionary<string, SemaphoreSlim> Locks = new();

public async Task<Report> GetAsync(DateOnly date, CancellationToken ct)
{
    var key = $"report:{date:yyyy-MM-dd}";

    if (cache.TryGetValue(key, out Report? cached)) return cached!;

    var gate = Locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);
    try
    {
        // DOUBLE-CHECK: another waiter may have populated it while we queued.
        if (cache.TryGetValue(key, out cached)) return cached!;

        cached = await BuildExpensiveReportAsync(date, ct);
        cache.Set(key, cached, TimeSpan.FromMinutes(10));
        return cached;
    }
    finally
    {
        gate.Release();
        Locks.TryRemove(key, out _);      // or the dictionary leaks a
    }                                     // semaphore per distinct key
}

// WHY PER-KEY AND NOT ONE GLOBAL LOCK: a single semaphore serialises misses
// for UNRELATED keys, so a slow report for one date blocks every other date.
// The dictionary cleanup matters too — without it, an endpoint with unbounded
// key variety accumulates semaphores indefinitely.
5 (hard): Design invalidation for a product cache written by the API, a background importer, and an admin tool.
Solution 
// THE CORE PROBLEM: three writers, and only one of them goes through the
// application's write path. Eviction-on-write alone is therefore INSUFFICIENT
// by construction — the importer and admin tool will silently leave the cache
// wrong.

// ── LAYER 1: TTL AS THE BACKSTOP (non-negotiable) ────────────────────────
// Bounds the wrongness for ANY writer, including ones added next year by
// someone who never reads this code.
new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(5) }

// ── LAYER 2: EVICTION ON THE PATHS YOU CONTROL ───────────────────────────
public async Task<Product> UpdateAsync(int id, UpdateProduct request, CancellationToken ct)
{
    var product = await db.Products.FindAsync([id], ct);
    product!.Apply(request);
    await db.SaveChangesAsync(ct);

    // AFTER the commit, never before — evicting first opens a window where a
    // concurrent read repopulates the cache with the OLD value.
    await hybrid.RemoveAsync($"product:{id}", ct);
    await hybrid.RemoveByTagAsync("product-lists", ct);
    return product;
}

// ── LAYER 3: A SHARED INVALIDATION CHANNEL FOR EVERY WRITER ──────────────
// The importer and admin tool publish to the same channel; every instance
// subscribes and evicts locally. This is what makes non-API writers correct
// rather than merely TTL-bounded.
public interface ICacheInvalidator
{
    Task InvalidateProductAsync(int id, CancellationToken ct);
}

public sealed class RedisCacheInvalidator(
    IConnectionMultiplexer redis, HybridCache cache) : ICacheInvalidator
{
    public async Task InvalidateProductAsync(int id, CancellationToken ct)
    {
        await cache.RemoveAsync($"product:{id}", ct);
        // Tell OTHER instances to drop their L1 copies — this is the part
        // teams miss with two-tier caches. Evicting L2 does not clear the
        // in-process L1 on five other servers.
        await redis.GetSubscriber().PublishAsync(
            RedisChannel.Literal("cache-invalidate"), $"product:{id}");
    }
}

// ── LAYER 4: CDC AS THE SAFETY NET (optional, for high-value data) ───────
// Tail the database change log and invalidate from there. Catches EVERY
// writer including manual SQL, at the cost of another moving part.

// ── LAYER 5: VERSIONED KEYS FOR BULK CHANGES ─────────────────────────────
// The importer rewrites 50,000 products. Evicting 50,000 keys individually is
// an eviction storm; bump one version instead and orphan them all at once:
var version = await cache.GetOrCreateAsync("catalog:version", ...);
var key = $"catalog:v{version}:product:{id}";
// Orphaned keys expire on their own TTL — no scan, no storm.

// ── THE PRINCIPLE ────────────────────────────────────────────────────────
// Eviction is an OPTIMISATION that makes the cache fresh quickly; the TTL is
// the CORRECTNESS guarantee that bounds staleness when eviction is missed.
// A design relying on eviction alone is one forgotten write path away from
// serving wrong data indefinitely — and there is always another write path.
6 (hard): A cache was added and made things worse. Write the analysis that decides what to keep.
Solution 
// ── STEP 1: MEASURE, PER CACHE NAME ──────────────────────────────────────
// Without these numbers every subsequent decision is a guess.
Hits.Add(1, new("cache", name));
Misses.Add(1, new("cache", name));
CacheLatency.Record(elapsed.TotalMilliseconds, new("cache", name));
SourceLatency.Record(sourceElapsed.TotalMilliseconds, new("cache", name));
// Per NAME, never per key — per-key labels are a cardinality explosion.

// ── STEP 2: THE DECISION RULE ────────────────────────────────────────────
// A cache is worth keeping only if:
//     hitRatio × sourceLatency  >  cacheLatency
//
// Worked example, cache A:
//   hit ratio 20%, source 1.2ms, cache round trip 1.8ms
//   benefit: 0.20 × 1.2ms = 0.24ms saved per request
//   cost:    1.8ms paid on EVERY request (hit or miss)
//   → strictly worse. DELETE IT.
//
// Cache B:
//   hit ratio 92%, source 240ms, cache 1.8ms
//   benefit: 0.92 × 240ms = 220ms
//   → obviously keep.

// ── STEP 3: DIAGNOSE LOW HIT RATIOS BEFORE DELETING ──────────────────────
// A low ratio may be a fixable key problem rather than an unsuitable workload:
//   • TTL shorter than the request interval → nothing is ever reused
//   • the key contains something too variable (a timestamp, a request id,
//     an unrounded float) → every request is a distinct key
//   • the key includes a parameter that does NOT affect the response →
//     unnecessary fragmentation
//   • writes evict more often than reads occur → the ratio can never be good

// ── STEP 4: FIX THE TAIL, NOT JUST THE MEAN ──────────────────────────────
// p99 regressions after adding a cache usually mean cache latency has its own
// tail. Bound it so a slow cache cannot become the bottleneck:
options.ConnectTimeout = 1000;
options.SyncTimeout = 1000;
// and serve from L1 where possible so hot keys never touch the network:
o.DefaultEntryOptions = new() { LocalCacheExpiration = TimeSpan.FromMinutes(1) };

// ── STEP 5: REMOVE THE HARD DEPENDENCY ───────────────────────────────────
// If a cache outage can take the API down, the cache is a liability
// regardless of its hit ratio:
try { /* read cache */ }
catch (RedisConnectionException ex)
{
    log.LogWarning(ex, "Cache unavailable; using source.");
}
return await LoadFromSourceAsync(ct);

// ── THE CONCLUSION ───────────────────────────────────────────────────────
// Keep caches where the source is genuinely expensive AND reuse is high.
// Delete caches over fast queries — they add latency, memory pressure, a
// failure mode and an invalidation-correctness burden in exchange for
// nothing. "We cache it" is not an achievement; a measured hit ratio against
// a measured source cost is.

🎯 Key Takeaways

  • Pick the layer by the problem: client/CDN headers avoid the request entirely, output caching skips the endpoint, in-memory is fastest per instance, distributed is shared and durable.
  • A cache key must include every input that varies the response — user, tenant, locale, role. Omitting one leaks data rather than serving stale data.
  • Output caching ignores the query string unless you declare SetVaryByQuery.
  • Bound IMemoryCache with SizeLimit, and pair sliding expiration with an absolute ceiling or hot keys never expire.
  • Evict rather than update in place: eviction is idempotent and converges, while racing writers can leave an updated cache permanently wrong.
  • Always keep a TTL as the correctness backstop — some writer will always bypass your eviction path.
  • Stampedes turn one expensive query into hundreds at expiry; HybridCache coalesces concurrent misses by default.
  • Cache negative results briefly, or enumeration of missing keys bypasses the cache entirely.
  • A cache must never be a hard dependency — catch its failures and fall through, with aggressive timeouts so a hung cache does not stall requests.
  • Caching a fast query behind a network hop makes it slower; a cache is justified by measured hit ratio against measured source cost.
