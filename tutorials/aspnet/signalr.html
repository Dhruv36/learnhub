SignalR (Realtime) Security & Realtime

What you'll master: the transport negotiation underneath SignalR and why it matters, hubs and the targeting model, why scaling out breaks a naive hub and how a backplane fixes it, authentication over WebSockets where headers do not exist, and the reconnection and backpressure realities that decide whether a realtime feature survives contact with mobile networks. Prerequisites: Dependency Injection and Authentication.

Part 1 — Transports and What SignalR Actually Gives You

// SignalR is an abstraction over three transports, negotiated automatically,
// best first:
//   1. WEBSOCKETS         full duplex, one persistent TCP connection, lowest
//                         overhead. What you want.
//   2. SERVER-SENT EVENTS server→client only; client→server uses separate
//                         HTTP POSTs. Falls back here when WebSockets are
//                         blocked by a proxy.
//   3. LONG POLLING       a request held open until data arrives, then
//                         immediately reissued. Works everywhere, costs the
//                         most.

builder.Services.AddSignalR();
var app = builder.Build();
app.MapHub<ChatHub>("/hubs/chat");

// NEGOTIATION: the client first POSTs to /hubs/chat/negotiate, which returns
// a connection id and the transports the server supports. The client then
// connects with the best one both sides allow.
//
// This handshake is why STICKY SESSIONS are required when scaling out with
// any transport other than pure WebSockets — the negotiate request and the
// subsequent connection must reach the SAME server. Skip negotiation entirely
// if you can guarantee WebSockets:
connection = new HubConnectionBuilder()
    .WithUrl("/hubs/chat", options =>
    {
        options.SkipNegotiation = true;
        options.Transports = HttpTransportType.WebSockets;
    })
    .Build();
// Skipping negotiation removes the sticky-session requirement and one round
// trip, at the cost of failing outright where WebSockets are blocked.

// WHAT SIGNALR ADDS OVER RAW WEBSOCKETS — this is the real value:
//   • transport fallback and reconnection with backoff
//   • an RPC model: call a named method with typed arguments, in both
//     directions, instead of hand-rolling a message envelope and a dispatcher
//   • groups, and user-based targeting across connections
//   • a backplane abstraction for multi-server fan-out
//   • connection lifetime events tied to DI scopes
//
// WHEN NOT TO USE IT: if the client is not .NET or JavaScript, or you need a
// specific wire protocol, raw WebSockets or gRPC streaming may fit better.
// And if updates are infrequent, ordinary polling is simpler and cheaper than
// holding thousands of connections open.

Part 2 — Hubs and Targeting

public sealed class ChatHub(IMessageService messages, ILogger<ChatHub> log) : Hub
{
    // Called BY clients. Public methods on a Hub are remotely invocable —
    // treat every one as an untrusted entry point, exactly like an endpoint.
    public async Task SendMessage(string roomId, string text)
    {
        if (text.Length > 2000)
            throw new HubException("Message too long.");   // ← see below

        var userId = Context.UserIdentifier!;
        var message = await messages.SaveAsync(roomId, userId, text);

        // Call a method ON THE CLIENTS in that group.
        await Clients.Group(roomId).SendAsync("ReceiveMessage", message);
    }

    public override async Task OnConnectedAsync()
    {
        log.LogInformation("Connected {ConnectionId}", Context.ConnectionId);
        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? exception)
    {
        // Group membership is cleaned up automatically; YOUR OWN state is not.
        await base.OnDisconnectedAsync(exception);
    }
}

// HubException is the ONLY exception type whose message reaches the client.
// Every other exception is replaced by a generic error — which is correct,
// because hub methods otherwise leak internals exactly as an unhandled
// endpoint exception would. Use HubException deliberately for messages the
// caller is meant to read.

// ── TARGETING ────────────────────────────────────────────────────────────
await Clients.All.SendAsync("Event", payload);                  // everyone
await Clients.Caller.SendAsync("Ack", id);                      // just them
await Clients.Others.SendAsync("Event", payload);               // all but caller
await Clients.Client(connectionId).SendAsync("Event", payload); // one connection
await Clients.Group("room-42").SendAsync("Event", payload);     // a group
await Clients.GroupExcept("room-42", Context.ConnectionId)
             .SendAsync("Event", payload);
await Clients.User(userId).SendAsync("Event", payload);         // EVERY device

// Clients.User targets by IUserIdProvider, defaulting to the
// NameIdentifier claim — so it reaches the user's phone AND laptop, which is
// usually what "notify the user" means. Clients.Client targets one connection.
// Choosing wrongly is why a notification appears on only one device.

// ── GROUPS ───────────────────────────────────────────────────────────────
await Groups.AddToGroupAsync(Context.ConnectionId, roomId);
await Groups.RemoveFromGroupAsync(Context.ConnectionId, roomId);
// Groups are CONNECTION-scoped and ephemeral: membership is lost on
// disconnect and must be re-established on reconnect. There is no API to
// enumerate a group's members or ask which groups a connection is in — if you
// need that, you must track it yourself.

// ── STRONGLY-TYPED HUBS — worth doing always ─────────────────────────────
public interface IChatClient
{
    Task ReceiveMessage(ChatMessage message);
    Task UserJoined(string userId);
}

public sealed class ChatHub : Hub<IChatClient>
{
    public async Task SendMessage(string roomId, string text)
        => await Clients.Group(roomId).ReceiveMessage(message);   // compiled
}
// The magic-string version fails silently: SendAsync("RecieveMessage", ...)
// compiles, runs, and simply never reaches a handler. The typed version turns
// that typo into a build error.

// ── SENDING FROM OUTSIDE A HUB ───────────────────────────────────────────
public sealed class OrderService(IHubContext<OrderHub, IOrderClient> hub)
{
    public async Task ShipAsync(Order order, CancellationToken ct)
    {
        await repository.MarkShippedAsync(order, ct);
        await hub.Clients.User(order.CustomerId.ToString()).OrderShipped(order.Id);
    }
}
// IHubContext is how a controller, background service or message handler
// pushes to clients. Note it exposes Clients and Groups but NOT Context —
// there is no caller outside a hub invocation.
Key insight: a Hub instance is created per method invocation and disposed immediately afterwards, exactly like a controller. Storing state in a hub field does nothing useful — it is gone before the next message. This surprises people because a SignalR connection is long-lived, so the hub feels like it should be too. Per-connection state belongs in Context.Items, which lives for the connection's duration, and anything that must survive a reconnect or be visible to other servers belongs in a distributed store, because a reconnecting client may land on a different instance entirely.

Part 3 — Scaling Out

// THE PROBLEM: a hub's Clients.All only reaches connections held by THIS
// server. Two instances behind a load balancer means a message sent on
// instance A never reaches the clients connected to instance B — and it works
// perfectly on one machine, so the bug appears only after scaling.

// ✓ A BACKPLANE relays messages between instances:
builder.Services.AddSignalR()
    .AddStackExchangeRedis("redis:6379", options =>
    {
        options.Configuration.ChannelPrefix = RedisChannel.Literal("chat");
    });

// Now Clients.All publishes to Redis, every instance subscribes, and each
// forwards to its own local connections. Groups and user targeting work the
// same way.

// WHAT THE BACKPLANE COSTS — and why it is not free scaling:
//   • EVERY message crosses Redis, so Redis becomes a throughput ceiling and
//     a single point of failure
//   • latency gains a hop
//   • fan-out is O(instances) publishes regardless of where subscribers are
//   • ordering is per-publisher, not global
//
// A backplane makes a chat application correct across instances. It does NOT
// make a high-throughput broadcast system scale — at that point you want
// Azure SignalR Service or a purpose-built pub/sub layer, where the
// connection management itself is offloaded.

// ✓ AZURE SIGNALR SERVICE — connections terminate at the service, not your
//   app, so your instances hold no WebSockets at all:
builder.Services.AddSignalR().AddAzureSignalR(connectionString);
// This removes the connection-count ceiling from your app entirely, which is
// usually the real constraint: each WebSocket costs a socket, a buffer and
// some memory, and a few thousand per instance is a practical limit before
// tuning.

// ── STICKY SESSIONS ──────────────────────────────────────────────────────
// Required when using long polling or SSE, because the negotiate request and
// the transport connection must reach the same server. NOT required if you
// skip negotiation and use WebSockets only.
//
// In Kubernetes:
//   sessionAffinity: ClientIP
// Behind nginx:
//   ip_hash;  or  sticky cookie srv_id expires=1h;
//
// A missing sticky-session config presents as intermittent connection
// failures during negotiation that vanish when you scale to one replica —
// which is a useful diagnostic signal in itself.

// ── CONNECTION LIMITS AND TIMEOUTS ───────────────────────────────────────
builder.Services.AddSignalR(options =>
{
    options.KeepAliveInterval = TimeSpan.FromSeconds(15);   // server ping
    options.ClientTimeoutInterval = TimeSpan.FromSeconds(30); // ≥ 2x keepalive
    options.HandshakeTimeout = TimeSpan.FromSeconds(15);
    options.MaximumReceiveMessageSize = 32 * 1024;          // caller-controlled
    options.StreamBufferCapacity = 10;
    options.EnableDetailedErrors = false;                    // production
});
// ClientTimeoutInterval must be at least twice KeepAliveInterval, or clients
// are disconnected while a keepalive is still in flight — producing
// mysterious drops under normal conditions.
//
// EnableDetailedErrors sends exception messages to clients. Useful in
// development, an information leak in production.

Part 4 — Authentication and Authorization

// Hubs use the same authorization primitives as endpoints:
[Authorize]
public sealed class ChatHub : Hub<IChatClient>
{
    [Authorize(Policy = "CanModerate")]
    public async Task DeleteMessage(int messageId) => ...;
}

// ── THE WEBSOCKET TOKEN PROBLEM ──────────────────────────────────────────
// The browser WebSocket API cannot set custom headers, so an Authorization
// header is impossible. SignalR's JS client therefore sends the token as a
// QUERY STRING parameter on the negotiate and connect requests.
builder.Services.AddAuthentication()
    .AddJwtBearer(options =>
    {
        options.Events = new JwtBearerEvents
        {
            OnMessageReceived = context =>
            {
                var token = context.Request.Query["access_token"];
                var path = context.HttpContext.Request.Path;

                // SCOPE THIS TO HUB PATHS ONLY. Accepting tokens from the
                // query string on ordinary endpoints is a real weakening:
                // URLs land in access logs, browser history, proxy logs and
                // Referer headers.
                if (!string.IsNullOrEmpty(token) &&
                    path.StartsWithSegments("/hubs"))
                {
                    context.Token = token;
                }
                return Task.CompletedTask;
            }
        };
    });

// Client side:
new HubConnectionBuilder()
    .WithUrl("/hubs/chat", options =>
    {
        // A FACTORY, not a value — it is re-invoked on every reconnect, so a
        // refreshed token is picked up. Passing a captured string means
        // reconnection fails once the original token expires.
        options.AccessTokenProvider = async () => await GetFreshTokenAsync();
    })
    .Build();

// ── TOKEN EXPIRY ON A LONG-LIVED CONNECTION ──────────────────────────────
// A connection authenticated at 09:00 with a 15-minute token stays open past
// expiry — the token is validated at CONNECT time, not per message. That is
// a deliberate design decision with a real consequence: revoking access does
// not drop existing connections.
//
// If that matters, close connections whose token has expired:
options.Events = new JwtBearerEvents
{
    OnTokenValidated = context =>
    {
        var expiry = context.SecurityToken.ValidTo;
        context.HttpContext.Items["token_expiry"] = expiry;
        return Task.CompletedTask;
    }
};
// then a periodic sweep, or a check in each hub method, disconnects
// connections past expiry and forces a reconnect with a fresh token.

// ── AUTHORIZING GROUP MEMBERSHIP ─────────────────────────────────────────
public async Task JoinRoom(string roomId)
{
    // The room id is CLIENT-SUPPLIED. Without this check any authenticated
    // user joins any room and receives every message sent to it — the
    // realtime equivalent of an IDOR.
    if (!await rooms.CanAccessAsync(Context.UserIdentifier!, roomId))
        throw new HubException("Access denied.");

    await Groups.AddToGroupAsync(Context.ConnectionId, roomId);
}
// [Authorize] on the hub proves the caller is authenticated. It says nothing
// about WHICH rooms they may join — that check has to be explicit and is
// routinely forgotten.

Part 5 — Reconnection, Ordering, and Backpressure

// ── AUTOMATIC RECONNECT ──────────────────────────────────────────────────
const connection = new signalR.HubConnectionBuilder()
    .withUrl("/hubs/chat")
    .withAutomaticReconnect([0, 2000, 10000, 30000])   // explicit backoff
    .configureLogging(signalR.LogLevel.Warning)
    .build();

connection.onreconnecting(error => showBanner("Reconnecting..."));
connection.onreconnected(async connectionId => {
    hideBanner();
    // THE CONNECTION ID IS NEW and group membership is GONE. Re-join, and
    // fetch anything missed while disconnected.
    await connection.invoke("JoinRoom", currentRoomId);
    await fetchMessagesSince(lastMessageId);
});
connection.onclose(error => showBanner("Disconnected."));

// The two facts that break naive implementations:
//   1. RECONNECTION PRODUCES A NEW CONNECTION ID, so anything keyed on it
//      server-side must be rebuilt
//   2. MESSAGES SENT WHILE DISCONNECTED ARE LOST — SignalR has no replay
//      buffer, so a client that was offline for ten seconds simply never
//      sees those messages
//
// Therefore: SignalR delivers to CURRENTLY CONNECTED clients. If a message
// must not be missed, it has to be durable somewhere and the client must
// reconcile on reconnect, typically by requesting everything since its last
// known id. Treating SignalR as a message queue is the most common
// architectural mistake with it.

// ── ORDERING ─────────────────────────────────────────────────────────────
// Messages from ONE server to ONE connection preserve order. Nothing else is
// guaranteed: with a backplane, two servers publishing concurrently can
// arrive in either order. If order matters, carry a sequence number and let
// the client sort or request gaps.

// ── BACKPRESSURE ─────────────────────────────────────────────────────────
// A slow client cannot absorb messages as fast as you send them. SignalR
// buffers per connection, and when that buffer fills, sends BLOCK — so a
// single slow mobile client can stall a broadcast loop for everyone.
builder.Services.AddSignalR(options =>
{
    options.MaximumParallelInvocationsPerClient = 1;   // default; keeps order
});

// Do NOT await a broadcast loop client by client:
// ✗ foreach (var id in connectionIds)
//       await Clients.Client(id).SendAsync("Tick", data);   // slowest wins
// ✓ send to a group and let SignalR fan out, or fire concurrently with a
//   bounded degree of parallelism and a timeout per send.

// STREAMING for large or long-running results, which applies backpressure
// naturally because the client pulls:
public async IAsyncEnumerable<Update> StreamUpdates(
    string topic, [EnumeratorCancellation] CancellationToken ct)
{
    await foreach (var update in source.WatchAsync(topic, ct))
        yield return update;      // the client's consumption rate governs
}

// ── SCOPED SERVICES IN HUBS ──────────────────────────────────────────────
// A hub method invocation gets its own DI scope, so injecting a DbContext
// into a hub CONSTRUCTOR is fine — unlike middleware. But a background loop
// started inside a hub method outlives the scope, so it must create its own:
public sealed class ChatHub(IServiceScopeFactory scopes) : Hub
{
    public async Task StartWatching()
    {
        _ = Task.Run(async () =>
        {
            using var scope = scopes.CreateScope();   // own scope, own context
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            // ...
        });
    }
}

// ── WHAT TO MONITOR ──────────────────────────────────────────────────────
//   • CURRENT CONNECTION COUNT per instance — the ceiling that matters most,
//     since each connection holds a socket and buffers
//   • connection duration distribution — a collapse to seconds means clients
//     are reconnect-looping, usually a keepalive/timeout misconfiguration
//   • message rate and backplane latency
//   • handshake failures — often a sticky-session or CORS problem
//
// SignalR emits these via EventCounters:
//   dotnet-counters monitor --counters Microsoft.AspNetCore.Http.Connections

// ── OPERATIONAL REALITIES WORTH PLANNING FOR ─────────────────────────────
//   • DEPLOYMENTS DISCONNECT EVERY CLIENT on that instance. With automatic
//     reconnect this is a blip, but a thundering herd of reconnects hits the
//     remaining instances at once — stagger rollouts and ensure backoff has
//     jitter.
//   • IDLE TIMEOUTS in load balancers and proxies kill connections that look
//     idle; the keepalive interval must be shorter than the shortest idle
//     timeout in the path (Azure App Service defaults to about 4 minutes).
//   • MOBILE CLIENTS disconnect constantly — backgrounding, network
//     switching, tunnels. Reconnection is the normal case, not the exception,
//     so the reconcile-on-reconnect path deserves as much care as the happy
//     path.

Interview Questions

Beginner: What transports does SignalR use and how is one chosen?

WebSockets, Server-Sent Events and long polling, in that order of preference. The client first sends a negotiate request, the server responds with a connection id and the transports it supports, and the client connects using the best one available to both. WebSockets is full duplex over a single persistent connection and is what you want; SSE handles server-to-client only with separate POSTs for the reverse direction; long polling works essentially everywhere but costs the most in requests and latency. Negotiation can be skipped entirely if you require WebSockets, which removes a round trip and the sticky-session requirement, at the cost of failing where WebSockets are blocked.

Beginner: Why does a hub stop working correctly when you scale to two servers?

Because each server only knows about the connections it is holding. Clients.All or Clients.Group on instance A reaches only clients connected to instance A, so a message sent by a user on one server never arrives for users on the other. It works perfectly on a single machine, which is why the bug appears at deployment rather than in development. The fix is a backplane — Redis or Azure SignalR Service — which relays messages between instances so each can forward to its own local connections.

Mid: Why can't SignalR be treated as a message queue?

Because it delivers only to currently connected clients and keeps no replay buffer. If a client is disconnected — a tunnel, a backgrounded mobile app, a deployment restarting its server — messages sent during that window are simply gone, and nothing informs either side that delivery was missed. A queue guarantees durability and redelivery; SignalR guarantees neither. So any message that must not be lost has to be persisted independently, with the client reconciling on reconnect by requesting everything since its last known id. SignalR is then the low-latency notification path, and the database or queue is the source of truth — which is also what makes reconnection correct rather than merely fast.

Mid: How does authentication work over WebSockets, and what is the risk?

The browser's WebSocket API cannot set custom headers, so an Authorization header is impossible. SignalR's JavaScript client instead appends the token as an access_token query string parameter, and the server picks it up in the OnMessageReceived event and assigns it to context.Token. The risk is that URLs are logged far more widely than headers — they appear in web server access logs, proxy logs, browser history and potentially Referer headers — so a token there is exposed in places a header would not be. The mitigation is to accept query-string tokens only for hub paths, checked explicitly in the handler, and to keep those tokens short-lived. A related detail is that the client must supply a token factory rather than a captured string, because the factory is re-invoked on each reconnect and a stale captured token makes reconnection fail after expiry.

Senior: Users report missing realtime updates, intermittently, more on mobile. Diagnose.

The pattern — intermittent and worse on mobile — points at disconnection windows rather than a messaging bug, and there are several overlapping causes worth separating. First, messages sent while a client is disconnected are lost permanently, since SignalR has no replay, and mobile clients disconnect constantly through backgrounding and network switching; if the client does not reconcile from a last known id on reconnect, those updates never arrive. Second, group membership is tied to the connection id, which changes on reconnect, so a client that reconnects without re-joining its groups appears connected and healthy while silently receiving nothing — this is the failure I would check first because it looks so much like a server problem. Third, if the deployment scaled out without a backplane, delivery depends on which instance each user happens to hold, producing exactly this intermittency. Fourth, an idle timeout in a proxy or load balancer shorter than the keepalive interval drops connections periodically, and a ClientTimeoutInterval below twice the keepalive causes spurious disconnects under normal latency. I would confirm by monitoring connection duration and reconnect rate — a collapse in duration or a high reconnect rate distinguishes a connection-stability problem from a delivery problem — and by checking whether the backplane is present. The durable fix is architectural rather than a setting: treat SignalR as a latency optimisation over a durable source, persist anything that matters, and make reconnect re-join groups and fetch everything since the last received id. That makes correctness independent of connection stability, which on mobile can never be assumed.

Senior: Design a realtime notification system for 100,000 concurrent users.

At that scale the first decision is where connections terminate, because each WebSocket costs a socket, buffers and memory, and a few thousand per instance is a practical ceiling before serious tuning. Holding 100,000 in my own application means roughly 20–50 instances existing purely for connection management, so I would use Azure SignalR Service or an equivalent, where connections terminate at the service and my application instances hold none — that decouples connection count from application capacity entirely and is the single highest-leverage choice. If self-hosting were required, a Redis backplane is necessary for correctness across instances, but I would size it carefully since every message crosses it, making it both a throughput ceiling and a single point of failure. On the messaging model, I would not broadcast to all users; almost all notifications are per-user or per-subscription, so Clients.User and groups keep fan-out proportional to the audience rather than the population. Crucially I would treat SignalR as a delivery accelerator over a durable store rather than the system of record: notifications are written to the database first, pushed opportunistically, and clients reconcile from a last-seen cursor on connect — which makes the design correct for the large fraction of users who are offline or reconnecting at any moment, and removes any need for delivery guarantees from the transport. For backpressure I would avoid per-client loops entirely, cap message size, and use streaming where a client consumes a long-running result, since a slow client must never be able to stall others. Operationally I would monitor connection count per instance, connection duration and reconnect rate, stagger deployments because every restart disconnects its clients and produces a reconnect herd, and ensure reconnect backoff has jitter so that herd is spread. I would also set keepalive shorter than the shortest idle timeout anywhere in the network path, since that misconfiguration produces exactly the intermittent drops that are hardest to attribute.

2 (easy): Push a notification from a background service to one user across all their devices.
Solution 
public interface INotificationClient
{
    Task OrderShipped(int orderId, string trackingNumber);
}

public sealed class ShipmentWorker(
    IServiceScopeFactory scopes,
    IHubContext<NotificationHub, INotificationClient> hub) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();       // scope per iteration
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            foreach (var shipment in await db.PendingShipments(ct))
            {
                await db.MarkNotifiedAsync(shipment, ct);   // PERSIST first

                await hub.Clients
                    .User(shipment.CustomerId.ToString())   // every device
                    .OrderShipped(shipment.OrderId, shipment.Tracking);
            }

            await Task.Delay(TimeSpan.FromSeconds(30), ct);
        }
    }
}

Solution 
// SYMPTOM: users only see messages from others who happen to be connected to
// the SAME instance. With three replicas roughly two thirds of messages go
// missing, seemingly at random.
//
// CAUSE: a hub only knows its own connections. Clients.Group on instance A
// reaches nobody on B or C. Nothing errors — the send succeeds locally.

// ✓ FIX 1 — a Redis backplane relays between instances:
builder.Services.AddSignalR()
    .AddStackExchangeRedis(config.GetConnectionString("Redis")!, options =>
    {
        options.Configuration.ChannelPrefix = RedisChannel.Literal("chat");
    });

// ✓ FIX 2 — sticky sessions, IF any client may fall back to SSE or long
//   polling, because negotiate and the connection must hit the same server:
//     Kubernetes:  service.spec.sessionAffinity: ClientIP
//     nginx:       ip_hash;
//
//   Or remove the requirement by mandating WebSockets:
options.SkipNegotiation = true;
options.Transports = HttpTransportType.WebSockets;

// ✓ FIX 3 — data protection keys must be shared, or the negotiate handshake
//   fails across instances:
builder.Services.AddDataProtection()
    .PersistKeysToStackExchangeRedis(redis, "DataProtection-Keys")
    .SetApplicationName("chat-app");

// WHAT THE BACKPLANE DOES NOT FIX: it makes delivery CORRECT, not scalable.
// Every message now crosses Redis, so Redis is a throughput ceiling and a
// single point of failure. Beyond a few thousand concurrent connections,
// Azure SignalR Service — where connections terminate off your instances — is
// the better answer.
4 (medium): Authenticate a hub with JWTs from a browser, handling reconnection and token expiry.
Solution 
// SERVER — accept the token from the query string, but ONLY for hub paths:
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = config["Jwt:Authority"];
        options.Audience = config["Jwt:Audience"];

        options.Events = new JwtBearerEvents
        {
            OnMessageReceived = context =>
            {
                var token = context.Request.Query["access_token"];
                var path = context.HttpContext.Request.Path;

                // The path check is the security-relevant part. Without it,
                // ordinary API endpoints would also accept query-string
                // tokens — and URLs appear in access logs, browser history,
                // proxy logs and Referer headers, where headers do not.
                if (!string.IsNullOrEmpty(token) &&
                    path.StartsWithSegments("/hubs"))
                {
                    context.Token = token;
                }

                return Task.CompletedTask;
            }
        };
    });

public sealed class ChatHub : Hub<IChatClient> { }

// CLIENT — a FACTORY, not a captured value:
const connection = new signalR.HubConnectionBuilder()

5 (hard): Make a realtime feed correct despite disconnections.
Solution 
// THE PREMISE: SignalR delivers only to CURRENTLY CONNECTED clients and keeps
// no replay buffer. Any design that relies on every message arriving is wrong
// on mobile, where disconnection is the normal case.

// ── SERVER: persist first, push second ───────────────────────────────────
public async Task<Message> PostAsync(string roomId, string text, CancellationToken ct)
{
    var message = new Message
    {
        RoomId = roomId,
        Text = text,
        // A monotonic per-room sequence is what makes gap detection possible.
        Sequence = await sequences.NextAsync(roomId, ct),
        CreatedAt = clock.GetUtcNow()
    };

    await db.Messages.AddAsync(message, ct);
    await db.SaveChangesAsync(ct);            // DURABLE first

    await hub.Clients.Group(roomId).ReceiveMessage(message);   // then push
    return message;
}

// ── SERVER: a catch-up endpoint ──────────────────────────────────────────
app.MapGet("/api/rooms/{roomId}/messages", async (
    string roomId, long since, AppDbContext db, CancellationToken ct) =>
    await db.Messages.AsNoTracking()
        .Where(m => m.RoomId == roomId && m.Sequence > since)
        .OrderBy(m => m.Sequence)
        .Take(500)                            // bounded — see note below
        .ToListAsync(ct));

// ── CLIENT: reconcile on every (re)connect ───────────────────────────────
let lastSequence = 0;

connection.on("ReceiveMessage", (message) => {
    if (message.sequence <= lastSequence) return;        // duplicate, ignore

    if (message.sequence > lastSequence + 1) {
        // A GAP: messages were missed. Fetch them rather than rendering out
        // of order — this is the case a naive client never notices.
        catchUp();
        return;
    }

    lastSequence = message.sequence;
    render(message);
});

connection.onreconnected(async () => {
    await connection.invoke("JoinRoom", roomId);   // membership was LOST
    await catchUp();                              // and messages were missed
});

async function catchUp() {
    const missed = await fetch(`/api/rooms/${roomId}/messages?since=${lastSequence}`)
        .then(r => r.json());
    for (const m of missed) { render(m); lastSequence = m.sequence; }
}

// ── WHY THIS IS CORRECT ──────────────────────────────────────────────────
//   • the DATABASE is the source of truth; SignalR is a latency optimisation
//   • sequence numbers make gaps DETECTABLE rather than silent
//   • duplicates are idempotent at the client, so at-least-once push is fine
//   • an offline client converges on reconnect, however long it was away
//
// The initial page load uses the SAME catch-up path with since=0, so there is
// one code path rather than a separate "load" and "live" implementation that
// can disagree.
//
// LIMIT WORTH NAMING: the catch-up query is capped at 500. A client offline
// long enough to exceed that needs a full reload rather than an incremental
// one — worth detecting explicitly instead of silently truncating history.
6 (hard): A broadcast to 10,000 clients causes latency spikes and timeouts. Diagnose and redesign.
Solution 
// ✗ THE LIKELY CODE:
foreach (var connectionId in _connections)
    await hub.Clients.Client(connectionId).SendAsync("Tick", payload);

// THREE PROBLEMS, compounding:
//   1. SEQUENTIAL AWAIT — total time is the SUM of 10,000 sends. One slow
//      mobile client on a bad connection blocks all of the ones after it.
//   2. NO BACKPRESSURE HANDLING — SignalR buffers per connection, and when
//      that buffer fills the send BLOCKS. A single stalled client can hold
//      the loop indefinitely.
//   3. PER-CLIENT ADDRESSING defeats the backplane's fan-out: with a Redis
//      backplane this publishes 10,000 separate messages instead of one.

// ✓ FIX 1 — send to a GROUP and let SignalR (and the backplane) fan out:
await hub.Clients.Group("ticker").SendAsync("Tick", payload);
// One publish, fan-out handled at the right layer. This alone usually
// resolves the incident.

// ✓ FIX 2 — if per-client targeting is genuinely required, bound the
//   parallelism and time-box each send so one client cannot stall the batch:
await Parallel.ForEachAsync(
    connectionIds,
    new ParallelOptions { MaxDegreeOfParallelism = 50, CancellationToken = ct },
    async (connectionId, token) =>
    {
        using var timeout = CancellationTokenSource
            .CreateLinkedTokenSource(token);
        timeout.CancelAfter(TimeSpan.FromSeconds(2));

        try
        {
            await hub.Clients.Client(connectionId)
                .SendAsync("Tick", payload, timeout.Token);
        }
        catch (OperationCanceledException)
        {
            // A slow client is dropped from THIS broadcast, not allowed to
            // degrade everyone else's.
            log.LogDebug("Send timed out for {ConnectionId}", connectionId);
        }
    });

// ✓ FIX 3 — reduce message VOLUME, which is often the real problem:
//   • coalesce: send one batched update per interval rather than per change
//   • send deltas, not full state
//   • let clients subscribe to only what they display, so fan-out is
//     proportional to interest rather than to population

// ✓ FIX 4 — at this scale, move connections off the app entirely:
builder.Services.AddSignalR().AddAzureSignalR(connectionString);
// 10,000 WebSockets on one instance is already near the practical ceiling
// before tuning; the service removes connection count as an app constraint.

// ── VERIFY WITH THE RIGHT METRIC ─────────────────────────────────────────
// Track TIME TO COMPLETE A BROADCAST, not average send latency. The average
// hides exactly the tail behaviour causing the incident, and the tail is the
// whole problem here.

🎯 Key Takeaways

  • SignalR negotiates WebSockets, then SSE, then long polling — skipping negotiation removes a round trip and the sticky-session requirement.
  • A hub instance lives for one method invocation; per-connection state belongs in Context.Items, durable state in a store.
  • Use Hub<TClient> with a typed interface — magic strings turn a typo into a silent no-op.
  • Clients.User reaches every device for a user; Clients.Client reaches one connection.
  • Scaling out requires a backplane, which makes delivery correct but adds a throughput ceiling and a single point of failure.
  • Browsers cannot set WebSocket headers, so tokens travel in the query string — accept them for hub paths only.
  • Supply a token factory, not a captured token, or reconnection fails after the first expiry.
  • Reconnection produces a new connection id and loses group membership — re-join and reconcile explicitly.
  • SignalR is not a queue: persist anything that matters and have clients catch up from a sequence number.
  • Never await a per-client broadcast loop; send to groups, bound parallelism, and time-box sends so one slow client cannot stall the rest.
