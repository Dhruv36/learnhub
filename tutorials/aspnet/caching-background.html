Background Services & Hosted Workers Production

What you'll master: IHostedService versus BackgroundService and the lifecycle each participates in, the silent-death failure mode that makes background work stop without a crash, scope and cancellation discipline, graceful shutdown that does not lose in-flight work, in-process queues with Channel, and the coordination problem that appears the moment you run more than one replica. Prerequisites: Dependency Injection and Configuration & Options.

Part 1 — The Two Abstractions

// IHostedService is the raw interface. The host calls StartAsync before the
// server accepts traffic, and StopAsync during shutdown.
public sealed class WarmupService(IServiceScopeFactory scopes) : IHostedService
{
    public async Task StartAsync(CancellationToken ct)
    {
        // Runs BEFORE the server starts listening. Blocking here delays
        // readiness — deliberate for warmup, a problem if done accidentally.
        using var scope = scopes.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Database.CanConnectAsync(ct);
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

// THE TRAP: StartAsync is AWAITED by the host. Long-running work here blocks
// startup forever, so the application never begins serving:
public Task StartAsync(CancellationToken ct)
{
    while (true) { /* ... */ }      // ✗ the host never finishes starting
}

// BackgroundService exists precisely for that case — it starts your work and
// returns immediately:
public sealed class PollingWorker(
    IServiceScopeFactory scopes,
    ILogger<PollingWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await DoWorkAsync(stoppingToken);
            await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
        }
    }
}
builder.Services.AddHostedService<PollingWorker>();

// HOW BackgroundService WORKS UNDERNEATH — worth knowing because it explains
// the next section: StartAsync calls ExecuteAsync and stores the returned
// Task WITHOUT awaiting it. The host continues starting. StopAsync signals
// the token and then awaits that stored Task.
//
// The consequence: ExecuteAsync returning — for any reason — simply ends the
// worker. Nothing restarts it.

// ORDERING: hosted services start in REGISTRATION order and stop in REVERSE,
// so a service registered later can depend on an earlier one still being
// alive during its own shutdown.

// ── AND THE FIRST-AWAIT SUBTLETY ─────────────────────────────────────────
// Code in ExecuteAsync BEFORE the first await runs synchronously inside
// StartAsync, and therefore still blocks startup:
protected override async Task ExecuteAsync(CancellationToken ct)
{
    Thread.Sleep(30_000);            // ✗ blocks host startup for 30 seconds
    await Task.Yield();              // ← yield first if you must do setup
    // ...
}

Part 2 — Silent Death

// THE MOST IMPORTANT FAILURE MODE IN THIS LESSON. An unhandled exception in
// ExecuteAsync stops that worker permanently. The host keeps running, the
// health check keeps passing, the API keeps serving — and the background work
// simply never happens again.

// ✗ VULNERABLE — one transient database blip ends the worker forever:
protected override async Task ExecuteAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        await ProcessBatchAsync(ct);      // throws once → worker is dead
        await Task.Delay(_interval, ct);
    }
}

// ✓ RESILIENT — catch INSIDE the loop so one failure costs one iteration:
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        try
        {
            await ProcessBatchAsync(stoppingToken);
        }
        catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
        {
            break;                        // shutdown — exit cleanly, no log
        }
        catch (Exception ex)
        {
            // Log and CONTINUE. The next iteration may well succeed.
            log.LogError(ex, "Batch failed; continuing.");
        }

        try
        {
            await Task.Delay(_interval, stoppingToken);
        }
        catch (OperationCanceledException)
        {
            break;                        // Task.Delay throws on shutdown
        }
    }
}

// NOTE THE TWO SEPARATE try BLOCKS. Wrapping the Delay in the same catch-all
// would swallow the shutdown cancellation and spin the loop, which is worse
// than the original bug.

// ── DETECTING A DEAD WORKER ──────────────────────────────────────────────
// Since .NET 6, an unhandled exception in a BackgroundService stops the HOST
// by default — which is usually what you want, because a crash is visible
// whereas silence is not:
builder.Services.Configure<HostOptions>(options =>
{
    options.BackgroundServiceExceptionBehavior =
        BackgroundServiceExceptionBehavior.StopHost;      // the default
    // Ignore keeps the host alive and the worker dead — the silent mode.
});

// Belt and braces: a heartbeat the health check can observe, so a stalled
// (rather than crashed) worker is also detectable:
public sealed class WorkerHeartbeat
{
    private long _ticks;
    public void Beat() => Interlocked.Exchange(ref _ticks,
        DateTimeOffset.UtcNow.Ticks);
    public DateTimeOffset Last => new(Interlocked.Read(ref _ticks), TimeSpan.Zero);
}

builder.Services.AddHealthChecks()
    .AddCheck<WorkerLivenessCheck>("worker", tags: ["live"]);
// The check fails if the last beat is older than a few intervals — catching
// both a dead worker and one wedged on a hung call, which StopHost cannot.
Key insight: a background worker fails differently from a request handler, and that is what makes it dangerous. A broken endpoint produces errors that appear in dashboards within seconds. A broken worker produces nothing — no errors, no traffic, no alerts — and the first symptom is usually downstream: a queue growing, emails not sent, a report missing. Every background service therefore needs an explicit liveness signal, because the absence of failure is indistinguishable from the absence of work.

Part 3 — Scopes, Cancellation, and Timers

// A BackgroundService is a SINGLETON, so it cannot inject scoped services.
// ✗ public sealed class Worker(AppDbContext db) : BackgroundService
//   → fails at startup with scope validation enabled

// ✓ A scope per unit of work, created INSIDE the loop:
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        using (var scope = _scopes.CreateScope())
        {
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            await ProcessAsync(db, stoppingToken);
        }   // scope and DbContext disposed here

        await Task.Delay(_interval, stoppingToken);
    }
}
// Hoisting the scope outside the loop rebuilds the captive-dependency bug:
// one DbContext for the process lifetime, accumulating tracked entities until
// memory and change detection both degrade. That failure is gradual — the
// worker gets slower over days rather than breaking — which makes it hard to
// attribute after the fact.

// ── CANCELLATION ─────────────────────────────────────────────────────────
// The stoppingToken must reach every await, or shutdown waits for work that
// is not listening:
await db.SaveChangesAsync(stoppingToken);
await http.GetAsync(url, stoppingToken);
await Task.Delay(interval, stoppingToken);

// Task.Delay(interval) WITHOUT the token means shutdown blocks for up to the
// full interval — a 5-minute poll interval turns every deploy into a 5-minute
// wait, or a SIGKILL if the orchestrator's grace period is shorter.

// A per-iteration timeout, linked to shutdown, so one hung call cannot wedge
// the worker forever:
using var timeout = CancellationTokenSource.CreateLinkedTokenSource(stoppingToken);
timeout.CancelAfter(TimeSpan.FromMinutes(2));
await ProcessAsync(timeout.Token);
// Linked means it cancels on EITHER the timeout or shutdown.

// ── PERIODICTIMER: better than Task.Delay for scheduled work ─────────────
using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

while (await timer.WaitForNextTickAsync(stoppingToken))
{
    await DoWorkAsync(stoppingToken);
}
// WHY IT IS BETTER: PeriodicTimer ticks on a FIXED SCHEDULE, whereas
// `work + Task.Delay(1min)` drifts by however long the work took — 40 seconds
// of work makes the real interval 100 seconds, and the drift accumulates.
//
// It also does not overlap: if work takes longer than the period, the next
// tick is skipped rather than starting a concurrent run. With a Timer
// callback, overlapping executions are the default and are a classic source
// of double-processing.

// ── DO NOT USE System.Threading.Timer FOR ASYNC WORK ─────────────────────
// ✗ new Timer(async _ => await DoWorkAsync(), null, 0, 60_000);
//   async void semantics: exceptions cannot be caught and crash the process,
//   and executions overlap freely.

Part 4 — Graceful Shutdown

// THE SEQUENCE when SIGTERM arrives:
//   1. IHostApplicationLifetime.ApplicationStopping fires
//   2. the server stops accepting NEW connections
//   3. in-flight requests get ShutdownTimeout to finish (default 30s)
//   4. hosted services' StopAsync runs, in REVERSE registration order
//   5. the DI container is disposed

builder.Services.Configure<HostOptions>(options =>
{
    // Must exceed the longest expected unit of work, and stay BELOW the
    // orchestrator's grace period — Kubernetes defaults to 30s, after which
    // it sends SIGKILL and any remaining work is lost mid-operation.
    options.ShutdownTimeout = TimeSpan.FromSeconds(25);
});

// ── FINISHING THE CURRENT ITEM RATHER THAN ABANDONING IT ─────────────────
public sealed class OrderProcessor(
    IServiceScopeFactory scopes,
    ILogger<OrderProcessor> log) : BackgroundService
{
    private readonly SemaphoreSlim _inFlight = new(1, 1);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await _inFlight.WaitAsync(stoppingToken);
            try
            {
                // Deliberately NOT passing stoppingToken here: once an order
                // is claimed we want it FINISHED, not torn down mid-write.
                await ProcessOneAsync(CancellationToken.None);
            }
            finally { _inFlight.Release(); }

            await Task.Delay(_interval, stoppingToken);
        }
    }

    public override async Task StopAsync(CancellationToken ct)
    {
        log.LogInformation("Shutdown requested; finishing current item.");
        await base.StopAsync(ct);          // signals the stopping token

        // Wait for the in-flight item, bounded by the host's timeout.
        await _inFlight.WaitAsync(ct);
        _inFlight.Release();

        log.LogInformation("Worker stopped cleanly.");
    }
}

// THE JUDGEMENT CALL: pass the token into work that is SAFE TO ABANDON (a
// read, a poll, an idempotent step), and withhold it from work that must
// complete atomically once started. Passing it everywhere risks a half-written
// operation; passing it nowhere risks a SIGKILL.
//
// The genuinely robust answer is to make the work RESUMABLE — claim an item
// with a lease, and let a crash or kill simply expire the lease so another
// instance retries. Then abandonment is safe at any point.

// ── REACTING TO LIFECYCLE EVENTS ─────────────────────────────────────────
public sealed class ShutdownAware(IHostApplicationLifetime lifetime)
{
    public ShutdownAware()
    {
        lifetime.ApplicationStarted.Register(() => { /* now serving */ });
        lifetime.ApplicationStopping.Register(() => { /* drain */ });
        lifetime.ApplicationStopped.Register(() => { /* final flush */ });
    }
}
// In Kubernetes, ApplicationStopping is the moment to start failing the
// READINESS probe while keeping liveness healthy, so traffic drains before
// the process actually stops.

Part 5 — In-Process Queues with Channel

// The common need: return from a request immediately and do slow work after.
// ✗ THE WRONG WAY — fire and forget:
_ = Task.Run(async () => await SendEmailAsync(order));   // ✗
// Three failures: the request's DI scope disposes underneath it, so a scoped
// DbContext throws ObjectDisposedException intermittently; exceptions are
// unobserved; and shutdown does not wait, so queued work vanishes on deploy.

// ✓ A BOUNDED CHANNEL plus a consumer:
public interface IBackgroundQueue
{
    ValueTask EnqueueAsync(Func<IServiceProvider, CancellationToken, ValueTask> work,
                           CancellationToken ct = default);
    ValueTask<Func<IServiceProvider, CancellationToken, ValueTask>> DequeueAsync(
        CancellationToken ct);
}

public sealed class BackgroundQueue : IBackgroundQueue
{
    private readonly Channel<Func<IServiceProvider, CancellationToken, ValueTask>> _channel =
        Channel.CreateBounded<Func<IServiceProvider, CancellationToken, ValueTask>>(
            new BoundedChannelOptions(1000)
            {
                // BOUNDED with Wait: when full, producers await rather than
                // allocating without limit. An UNBOUNDED channel under load
                // is an out-of-memory kill waiting to happen.
                FullMode = BoundedChannelFullMode.Wait
            });

    public ValueTask EnqueueAsync(
        Func<IServiceProvider, CancellationToken, ValueTask> work,
        CancellationToken ct = default) => _channel.Writer.WriteAsync(work, ct);

    public ValueTask<Func<IServiceProvider, CancellationToken, ValueTask>> DequeueAsync(
        CancellationToken ct) => _channel.Reader.ReadAsync(ct);
}

public sealed class QueuedHostedService(
    IBackgroundQueue queue,
    IServiceScopeFactory scopes,
    ILogger<QueuedHostedService> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            Func<IServiceProvider, CancellationToken, ValueTask> work;
            try
            {
                work = await queue.DequeueAsync(stoppingToken);
            }
            catch (OperationCanceledException) { break; }

            try
            {
                // A FRESH SCOPE — the request's scope is long gone.
                using var scope = scopes.CreateScope();
                await work(scope.ServiceProvider, stoppingToken);
            }
            catch (Exception ex)
            {
                log.LogError(ex, "Queued work item failed.");
            }
        }
    }
}

// Usage from an endpoint:
app.MapPost("/orders", async (CreateOrder request, OrderService orders,
    IBackgroundQueue queue, CancellationToken ct) =>
{
    var order = await orders.CreateAsync(request, ct);

    await queue.EnqueueAsync(async (services, token) =>
    {
        var email = services.GetRequiredService<IEmailSender>();
        await email.SendConfirmationAsync(order.Id, token);
    }, ct);

    return TypedResults.Created($"/orders/{order.Id}", order);
});

// ── THE DURABILITY LIMIT, STATED PLAINLY ─────────────────────────────────
// An in-process channel is IN MEMORY. Anything queued but not yet processed
// is LOST if the process stops — every deploy, every crash, every scale-down.
// That is acceptable for best-effort work like a nice-to-have email, and
// unacceptable for anything a user paid for or a system depends on.
//
// For durable work use a real queue (Azure Service Bus, RabbitMQ, SQS) or the
// transactional outbox pattern, where the work item is committed in the same
// transaction as the data change and survives restarts.

Part 6 — Running More Than One Instance

// THE PROBLEM: three replicas means three copies of every background service.
// A nightly billing job runs three times. A poller processes each row three
// times. Nothing warns you — it works correctly on one instance.

// ── OPTION 1: MAKE THE WORK IDEMPOTENT OR CLAIMED ────────────────────────
// Claim rows atomically so concurrent workers cannot take the same item.
// PostgreSQL — the cleanest expression:
var claimed = await db.Database.SqlQuery<Order>($@"
    UPDATE orders SET status = 'processing', claimed_by = {_instanceId},
                      claimed_at = now()
    WHERE id IN (
        SELECT id FROM orders
        WHERE status = 'pending'
        ORDER BY created_at
        LIMIT 10
        FOR UPDATE SKIP LOCKED      -- ← concurrent workers take DIFFERENT rows
    )
    RETURNING *").ToListAsync(ct);
// SKIP LOCKED is what makes this scale: each worker takes rows nobody else
// holds, with no coordination service and no lock contention.
//
// Pair it with a LEASE so a crashed worker's rows return to the pool:
//   WHERE status = 'pending'
//      OR (status = 'processing' AND claimed_at < now() - interval '5 minutes')

// ── OPTION 2: DISTRIBUTED LEADER ELECTION ────────────────────────────────
// For genuinely singleton work — a nightly report, a schema maintenance job.
public sealed class LeaderElectedWorker(
    IDistributedLock locks, ILogger<LeaderElectedWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // A Redis lock with a TTL, renewed while held. Only one instance
            // acquires it; the others wait and take over if the holder dies.
            await using var handle = await locks.TryAcquireAsync(
                "nightly-billing", TimeSpan.FromMinutes(10), stoppingToken);

            if (handle is not null)
            {
                try { await RunBillingAsync(stoppingToken); }
                catch (Exception ex) { log.LogError(ex, "Billing failed."); }
            }

            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
// CAVEAT WORTH KNOWING: a lock with a TTL does not guarantee mutual exclusion
// under arbitrary pauses — a GC pause or a network partition can let the lease
// expire while the holder still believes it is leading, so two instances run
// briefly. If correctness depends on exactly-once, the WORK must also be
// idempotent; the lock reduces duplication rather than eliminating it.

// ── OPTION 3: SEPARATE THE DEPLOYMENT ────────────────────────────────────
// Often the simplest and most robust answer: run workers as their own
// deployment with replicas=1, and the API scaled independently.
if (builder.Configuration.GetValue<bool>("Workers:Enabled"))
{
    builder.Services.AddHostedService<BillingWorker>();
}
// Same image, different configuration. The API scales for traffic without
// multiplying background work, and worker failures do not affect request
// serving. This also makes resource limits meaningful — a memory-hungry batch
// job no longer competes with request handling.

// ── AND THE MONITORING THAT MAKES ANY OF IT OPERABLE ─────────────────────
//   • last successful run timestamp per job — alert when it is too old
//   • items processed and failed, as counters
//   • queue depth and oldest-item age for anything queue-driven
//   • duration, so a job creeping toward its interval is visible before it
//     starts overlapping
//
// The alert that matters most is on ABSENCE: "billing has not completed in 26
// hours" catches the silent-death case that no error-rate alert ever will.

Interview Questions

Beginner: What is the difference between IHostedService and BackgroundService?

IHostedService is the interface the host calls, with StartAsync before the server begins accepting traffic and StopAsync during shutdown. Because the host awaits StartAsync, any long-running loop placed there prevents the application from ever finishing startup. BackgroundService is an abstract base class implementing that interface for exactly this case: its StartAsync invokes ExecuteAsync and stores the task without awaiting it, so the host continues starting while your loop runs. Use IHostedService directly for short startup or shutdown tasks, and BackgroundService for anything continuous.

Beginner: Why can't a BackgroundService inject a DbContext?

Because hosted services are registered as singletons and DbContext is scoped. Injecting it into the constructor captures a single instance for the entire process lifetime, which is a captive dependency — with scope validation enabled the container refuses at startup, and without it you get a context that is either disposed or shared unsafely, and which accumulates tracked entities indefinitely. The correct approach is to inject IServiceScopeFactory and create a scope inside the processing loop, so each unit of work gets a fresh context that is disposed when the iteration completes.

Mid: Why is PeriodicTimer preferable to await Task.Delay in a loop?

Two reasons. First, drift: a loop that does work and then delays a fixed period has an effective interval of the work duration plus the delay, so a job intended to run every minute that takes forty seconds actually runs every hundred seconds, and the offset accumulates over the day. PeriodicTimer ticks on a fixed schedule regardless of how long the work took. Second, overlap behaviour: if work exceeds the period, PeriodicTimer simply returns the next tick immediately without starting a concurrent execution, whereas a Timer with a callback fires overlapping executions by default, which is a common source of double-processing. It also composes properly with cancellation through WaitForNextTickAsync.

Mid: What happens to fire-and-forget Task.Run work started from a request?

Several things go wrong at once. The request's DI scope is disposed when the response completes, so any scoped service captured by the closure — typically a DbContext — throws ObjectDisposedException, intermittently, depending on timing. Exceptions inside the task are unobserved, so failures are silent. And the host does not know the work exists, so shutdown does not wait for it and anything in flight is lost on every deployment. The correct pattern is to enqueue the work onto a bounded Channel consumed by a hosted service, which creates its own scope per item, logs failures, and participates in graceful shutdown.

Senior: A nightly job silently stopped running weeks ago. Diagnose and prevent recurrence.

The overwhelmingly likely cause is an unhandled exception in ExecuteAsync, which ends the task and therefore the worker, while the host and the API continue running normally — so no health check fails, no error rate rises, and nothing distinguishes "not working" from "nothing to do". The reason it went unnoticed for weeks is structural rather than accidental: background work generates no signal when it does not happen, so monitoring built around errors and latency cannot see it. I would confirm by looking for a single exception around the time output stopped, and by checking whether BackgroundServiceExceptionBehavior is set to Ignore, which keeps the host alive with a dead worker. The immediate fix is a try/catch inside the loop so one failure costs one iteration rather than the worker, with the shutdown cancellation deliberately excluded from that catch so stopping still works. The preventive fixes matter more: leave the exception behaviour at StopHost so a crash is visible, emit a heartbeat the health check observes so a wedged worker is caught as well as a dead one, and — most importantly — alert on absence, meaning a last-successful-run timestamp with an alert when it exceeds the expected interval. That last alert is the only one that would have fired here. I would also record duration and item counts, since a job creeping toward its interval is a warning that it will eventually overlap or time out.

Senior: Design background processing for a service running on multiple replicas with a mix of scheduled and queued work.

My first move is to separate the two kinds of work, because they have different correctness requirements. Queue-driven work is naturally parallel and should run on every replica, claiming items atomically — FOR UPDATE SKIP LOCKED against the database, or the visibility-timeout semantics of a real broker — so concurrent workers take different items with no coordination service and no contention. I would pair claiming with a lease so that a worker crashing mid-item returns it to the pool automatically rather than stranding it, and I would require consumers to be idempotent, since any lease-based scheme delivers at least once. Scheduled singleton work — nightly billing, report generation — is the case that breaks on multiple replicas, and I would strongly prefer running it as a separate deployment with a single replica, or as a platform-level scheduled job, over leader election inside the application. That is a deployment change rather than code, it makes the singleton property obvious to anyone reading the manifests, and it lets the API scale for traffic without multiplying background load or competing for memory with a batch job. Where leader election is genuinely necessary I would use a distributed lock with a renewed TTL, while being clear that a TTL lock does not guarantee mutual exclusion under GC pauses or partitions — the lease can expire while the holder still believes it leads — so the work must remain idempotent regardless. For queued work originating in requests I would use a bounded channel for best-effort items only, and a durable queue or the transactional outbox for anything that must not be lost, since an in-memory channel discards its contents on every deploy. On shutdown I would set the host timeout below the orchestrator's grace period, pass the stopping token into abandonable work while withholding it from operations that must complete atomically, and prefer making work resumable so abandonment is always safe. Finally, monitoring built on absence rather than errors: last-success timestamps per job, queue depth and oldest-item age, and a liveness heartbeat per worker — because the defining property of background work is that failure is silent.

🏋️ Graded Exercises

1 (easy): Write a worker polling every 30 seconds using a scoped repository, that survives individual failures.
Solution 
public sealed class PollingWorker(
    IServiceScopeFactory scopes,
    ILogger<PollingWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try
            {
                // A SCOPE PER ITERATION — outside the loop it would become a
                // process-lifetime DbContext accumulating tracked entities.
                using var scope = scopes.CreateScope();
                var repo = scope.ServiceProvider.GetRequiredService<IOrderRepository>();

                await repo.ProcessPendingAsync(stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;      // shutdown, not a failure — do not log as an error
            }
            catch (Exception ex)
            {
                // Without this, ONE transient failure ends the worker forever
                // while the host keeps running and looks perfectly healthy.
                log.LogError(ex, "Poll iteration failed; continuing.");
            }
        }
    }
}

// ✗ THE BUG:
public sealed class Worker : IHostedService
{
    public async Task StartAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)      // never returns
        {
            await DoWorkAsync(ct);
            await Task.Delay(TimeSpan.FromMinutes(1), ct);

public sealed class Worker(ILogger<Worker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));
        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try { await DoWorkAsync(stoppingToken); }
            catch (Exception ex) { log.LogError(ex, "Iteration failed."); }
        }
    }
}

Solution 
public sealed class BackgroundQueue
{
    private readonly Channel<Func<IServiceProvider, CancellationToken, ValueTask>> _channel =
        Channel.CreateBounded<Func<IServiceProvider, CancellationToken, ValueTask>>(
            new BoundedChannelOptions(1_000)
            {
                // BOUNDED: producers wait when full rather than allocating
                // without limit. An unbounded channel under sustained load is
                // an out-of-memory kill.

            });

    public ValueTask EnqueueAsync(
        Func<IServiceProvider, CancellationToken, ValueTask> work,
        CancellationToken ct = default) => _channel.Writer.WriteAsync(work, ct);

    public IAsyncEnumerable<Func<IServiceProvider, CancellationToken, ValueTask>>
        ReadAllAsync(CancellationToken ct) => _channel.Reader.ReadAllAsync(ct);
}

public sealed class QueueConsumer(
    BackgroundQueue queue,
    IServiceScopeFactory scopes,
    ILogger<QueueConsumer> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var work in queue.ReadAllAsync(stoppingToken))
        {
            try
            {
                // A FRESH SCOPE — the originating request's scope is long
                // disposed by the time this runs.
                using var scope = scopes.CreateScope();
                await work(scope.ServiceProvider, stoppingToken);
            }
            catch (Exception ex)
            {
                log.LogError(ex, "Queued work item failed.");
            }
        }
    }
}

builder.Services.AddSingleton<BackgroundQueue>();
builder.Services.AddHostedService<QueueConsumer>();

// DURABILITY LIMIT: this is in memory. Items queued but unprocessed are LOST
// on every deploy and crash. Fine for a confirmation email; not for anything
// the business depends on — use a durable queue or the outbox pattern there.
4 (medium): A worker's shutdown takes five minutes and gets killed. Fix it.
Solution 
// ✗ THE CAUSE — Task.Delay without the token:
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        await ProcessAsync(stoppingToken);
        await Task.Delay(TimeSpan.FromMinutes(5));   // ✗ ignores shutdown
    }
}
// On SIGTERM the token is signalled, but the worker is asleep inside a delay
// that is not listening. The host waits for its ShutdownTimeout (30s), gives
// up, and the orchestrator SIGKILLs — so any in-flight work dies mid-write.

// ✓ FIX 1 — thread the token through every await:
using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
while (await timer.WaitForNextTickAsync(stoppingToken))   // cancels instantly
{
    await ProcessAsync(stoppingToken);
}

// ✓ FIX 2 — set the host timeout to fit inside the orchestrator's grace
//   period, above the longest expected unit of work:
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(25));   // K8s default grace: 30s

// ✓ FIX 3 — let the CURRENT item finish while refusing new ones:
private readonly SemaphoreSlim _inFlight = new(1, 1);

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    using var timer = new PeriodicTimer(_interval);
    while (await timer.WaitForNextTickAsync(stoppingToken))
    {
        await _inFlight.WaitAsync(stoppingToken);
        try
        {
            // Deliberately NOT the stopping token: once claimed, finish it.
            await ProcessAsync(CancellationToken.None);
        }
        finally { _inFlight.Release(); }
    }
}

public override async Task StopAsync(CancellationToken ct)
{
    await base.StopAsync(ct);           // signal the stopping token
    await _inFlight.WaitAsync(ct);      // wait for the in-flight item
    _inFlight.Release();
}

// THE JUDGEMENT: pass the token into abandonable work, withhold it from work
// that must complete atomically. The robust alternative is to make the work
// RESUMABLE with a lease, so being killed at any point is safe and another
// instance simply picks it up.
5 (hard): Three replicas each run the same nightly job, so it executes three times. Give two solutions with trade-offs.
Solution 
// ── SOLUTION A: SEPARATE DEPLOYMENT (preferred) ──────────────────────────
if (builder.Configuration.GetValue<bool>("Workers:Enabled"))
    builder.Services.AddHostedService<NightlyBillingWorker>();

//   + genuinely one instance; no distributed coordination to get wrong
//   + the API scales for traffic without multiplying background load
//   + resource limits become meaningful — a heavy batch job stops competing
//     with request handling for memory
//   + the singleton property is visible in the manifests, not buried in code
//   − a second deployment to operate
//   − replicas: 1 means a window with NO worker during a rolling update

// ── SOLUTION B: DISTRIBUTED LOCK ─────────────────────────────────────────
public sealed class NightlyBillingWorker(
    IDistributedLockProvider locks,
    IServiceScopeFactory scopes,
    ILogger<NightlyBillingWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            if (!IsScheduledWindow(DateTimeOffset.UtcNow)) continue;

            await using var handle = await locks.TryAcquireLockAsync(
                "nightly-billing", TimeSpan.FromMinutes(30), stoppingToken);

            if (handle is null) continue;      // another replica holds it

            try
            {
                using var scope = scopes.CreateScope();
                await scope.ServiceProvider
                    .GetRequiredService<IBillingService>()
                    .RunAsync(stoppingToken);
            }
            catch (Exception ex) { log.LogError(ex, "Billing failed."); }
        }
    }
}

//   + one deployment; automatic failover if the holder dies
//   − a TTL lock does NOT guarantee mutual exclusion: a GC pause or network
//     partition can let the lease expire while the holder still believes it
//     leads, so two replicas run briefly. The work MUST be idempotent anyway.
//   − adds Redis (or equivalent) as a dependency of correctness
//   − harder to reason about and to test than a replica count

// ── WHICH ──────────────────────────────────────────────────────────────
// A for scheduled singleton work: the guarantee comes from the platform
// rather than from a lock whose failure modes are subtle. B when a separate
// deployment is not available, or when automatic failover matters more than
// simplicity. Either way, make the job idempotent — a run-log row with a
// unique constraint on the business date makes a duplicate run a no-op, which
// is the only defence that holds under both designs.
6 (hard): Make a silently-failing background service observable.
Solution 
// ── 1. HEARTBEAT + LAST SUCCESS ──────────────────────────────────────────
public sealed class WorkerState
{
    private long _lastBeat;
    private long _lastSuccess;

    public void Beat() => Interlocked.Exchange(ref _lastBeat, DateTimeOffset.UtcNow.Ticks);
    public void Success() => Interlocked.Exchange(ref _lastSuccess, DateTimeOffset.UtcNow.Ticks);

    public DateTimeOffset LastBeat => new(Interlocked.Read(ref _lastBeat), TimeSpan.Zero);
    public DateTimeOffset LastSuccess => new(Interlocked.Read(ref _lastSuccess), TimeSpan.Zero);
}

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    using var timer = new PeriodicTimer(_interval);
    while (await timer.WaitForNextTickAsync(stoppingToken))
    {
        _state.Beat();                       // "I am alive" — even on failure
        using var activity = ActivitySource.StartActivity("billing.run");
        var sw = Stopwatch.StartNew();

        try
        {
            var processed = await ProcessAsync(stoppingToken);

            _state.Success();                // "I actually did the work"
            ItemsProcessed.Add(processed);
            Duration.Record(sw.Elapsed.TotalSeconds);
        }
        catch (Exception ex)
        {
            Failures.Add(1);
            activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
            log.LogError(ex, "Iteration failed; continuing.");
        }
    }
}
// BEAT and SUCCESS are separate on purpose: a worker looping but failing
// every time beats without succeeding, which is a distinct and important
// state from being dead.

// ── 2. HEALTH CHECK ──────────────────────────────────────────────────────
public sealed class WorkerHealthCheck(WorkerState state, TimeProvider clock)
    : IHealthCheck
{
    public Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken ct)
    {
        var sinceBeat = clock.GetUtcNow() - state.LastBeat;
        var sinceSuccess = clock.GetUtcNow() - state.LastSuccess;

        if (sinceBeat > TimeSpan.FromMinutes(5))
            return Task.FromResult(HealthCheckResult.Unhealthy(
                $"Worker has not run for {sinceBeat}. It may have died."));

        if (sinceSuccess > TimeSpan.FromMinutes(30))
            return Task.FromResult(HealthCheckResult.Degraded(
                $"Worker running but not succeeding for {sinceSuccess}."));

        return Task.FromResult(HealthCheckResult.Healthy());
    }
}
builder.Services.AddHealthChecks().AddCheck<WorkerHealthCheck>("worker");

// ── 3. THE ALERT THAT ACTUALLY CATCHES IT ────────────────────────────────
// Error-rate alerts NEVER fire for a dead worker, because a dead worker
// produces no errors. Alert on ABSENCE:
//
//   # Prometheus
//   - alert: BillingJobNotCompleting
//     expr: time() - billing_last_success_timestamp_seconds > 93600   # 26h
//     annotations:
//       summary: "Billing has not completed successfully in 26 hours"
//
// Export the timestamp as a gauge so the query is possible:
LastSuccessGauge.Record(state.LastSuccess.ToUnixTimeSeconds());

// ── 4. FAIL LOUDLY BY DEFAULT ────────────────────────────────────────────
builder.Services.Configure<HostOptions>(o =>
    o.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.StopHost);
// A crash is visible; a silent dead worker is not. Stopping the host converts
// an invisible failure into a restart the orchestrator reports.

// ── WHY ALL FOUR ─────────────────────────────────────────────────────────
// StopHost catches crashes. The heartbeat catches a worker WEDGED on a hung
// call, which StopHost cannot see. The success timestamp catches a worker
// looping but never succeeding. And the absence alert is the only one that
// fires when nothing at all is happening — which is precisely the state that
// every error-based alert is blind to.

🎯 Key Takeaways

  • IHostedService.StartAsync is awaited by the host, so continuous work belongs in BackgroundService.ExecuteAsync.
  • An unhandled exception in ExecuteAsync ends the worker permanently while the host stays healthy — catch inside the loop.
  • Background failure is silent by nature: alert on absence of success, because error-rate alerts never fire for work that is not happening.
  • Workers are singletons — inject IServiceScopeFactory and create a scope per iteration, never outside the loop.
  • Pass the stopping token into every await, or shutdown waits a full interval and then gets SIGKILLed.
  • PeriodicTimer avoids the cumulative drift of work-plus-delay and will not start overlapping runs.
  • Never use Timer with an async callback — async void exceptions cannot be caught.
  • Fire-and-forget Task.Run from a request loses its DI scope, swallows exceptions, and vanishes on shutdown.
  • Bound every in-process queue, and remember an in-memory channel is not durable — deploys discard it.
  • Every replica runs every hosted service: claim work with SKIP LOCKED, elect a leader, or give workers their own single-replica deployment.
