EF Core: Modelling & Querying Data

What you'll master: registering DbContext with the right lifetime and resilience, modelling with fluent configuration rather than attributes, the client-versus-server evaluation boundary that decides whether a query is fast or catastrophic, loading strategies and the N+1 problem, projection as the default read path, and migrations that survive a rolling deploy. Prerequisites: Dependency Injection and Configuration & Options.

Part 1 — Registering DbContext

builder.Services.AddDbContext<AppDbContext>(options => options
    .UseNpgsql(builder.Configuration.GetConnectionString("Default"), npgsql =>
    {
        npgsql.EnableRetryOnFailure(
            maxRetryCount: 3,
            maxRetryDelay: TimeSpan.FromSeconds(5),
            errorCodesToAdd: null);
        npgsql.CommandTimeout(30);          // the default is often unbounded
        npgsql.MigrationsAssembly("Infrastructure");
    }));

// AddDbContext registers it SCOPED — one instance per HTTP request, which is
// correct because DbContext is NOT thread-safe and is designed as a
// short-lived unit of work. Two concurrent operations on one context throw
// "A second operation was started on this context".

// ── THE FOUR REGISTRATION METHODS, and when each applies ─────────────────
AddDbContext<T>()          // scoped. The default; right for web requests.
AddDbContextPool<T>()      // scoped, but instances are POOLED and reset
                           // between requests. Measurably faster under high
                           // throughput — at the cost that the context cannot
                           // hold per-request state in fields, because the
                           // instance is reused.
AddDbContextFactory<T>()   // for singletons and background work, where there
                           // is no ambient scope. See Background Services.
AddPooledDbContextFactory<T>()   // both

// AddDbContextPool has a real trap: a context with a constructor-injected
// tenant or user (for a global query filter) breaks, because the pooled
// instance is reused across requests with the FIRST request's tenant still
// captured. That is a cross-tenant data leak, not a performance nuance.

// ── CONNECTION RESILIENCE ────────────────────────────────────────────────
// EnableRetryOnFailure handles transient faults — a failover, a brief network
// partition, a throttled cloud database. Without it, a two-second failover
// surfaces as a wave of 500s.
//
// THE CONSEQUENCE TO KNOW: with retries enabled you cannot call
// BeginTransaction directly — the execution strategy cannot retry a block it
// does not own. Wrap the unit in CreateExecutionStrategy().ExecuteAsync,
// covered in Change Tracking & Transactions.

// ── DEVELOPMENT-ONLY DIAGNOSTICS ─────────────────────────────────────────
if (builder.Environment.IsDevelopment())
{
    options.EnableSensitiveDataLogging();   // logs PARAMETER VALUES
    options.EnableDetailedErrors();
}
// EnableSensitiveDataLogging writes parameter values into logs — passwords,
// tokens, personal data. It is genuinely useful locally and a compliance
// incident in production, so guard it on the environment rather than a
// comment saying "remember to turn this off".

// ── LOGGING QUERIES USEFULLY ─────────────────────────────────────────────
// "Microsoft.EntityFrameworkCore.Database.Command": "Information"
// shows the SQL EF actually generated — which is the fastest way to discover
// that a LINQ query you believed was one round trip is thirty.

Part 2 — Modelling

// Prefer FLUENT CONFIGURATION over attributes. Attributes put persistence
// concerns on the entity, which breaks the dependency rule and cannot express
// most of what EF supports anyway.
public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> builder)
    {
        builder.ToTable("orders");
        builder.HasKey(o => o.Id);

        // STRONGLY-TYPED IDs — a value conversion keeps the domain expressive
        // while storing a plain guid.
        builder.Property(o => o.Id)
            .HasConversion(id => id.Value, value => new OrderId(value));

        builder.Property(o => o.Status)
            .HasConversion<string>()        // store the NAME, not the ordinal
            .HasMaxLength(32);

        builder.Property(o => o.CreatedAt).HasColumnType("timestamptz");

        // OWNED TYPES — a value object stored inline, with no separate table
        // and no identity of its own:
        builder.OwnsOne(o => o.ShippingAddress, address =>
        {
            address.Property(a => a.Line1).HasColumnName("shipping_line1");
            address.Property(a => a.PostCode).HasColumnName("shipping_postcode");
        });

        // BACKING FIELD — the collection is exposed read-only on the entity,
        // so EF must be told to use the field rather than the property.
        builder.Metadata
            .FindNavigation(nameof(Order.Lines))!
            .SetPropertyAccessMode(PropertyAccessMode.Field);

        builder.HasMany(o => o.Lines)
            .WithOne()
            .HasForeignKey(l => l.OrderId)
            .OnDelete(DeleteBehavior.Cascade);

        // INDEXES belong in the model, next to the queries that need them.
        builder.HasIndex(o => new { o.CustomerId, o.CreatedAt })
            .HasDatabaseName("ix_orders_customer_created");
    }
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
    => modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);

// ── ENUMS AS STRINGS, essentially always ─────────────────────────────────
// Storing the ordinal means inserting a new enum member in the middle
// silently reassigns every existing row's meaning. It is also unreadable in
// the database, so every ad-hoc query needs the C# source to interpret.

// ── GLOBAL QUERY FILTERS ─────────────────────────────────────────────────
builder.HasQueryFilter(o => !o.IsDeleted && o.TenantId == _tenant.Current);
// Applied to EVERY query for this entity automatically — the durable place
// for soft deletes and tenant isolation, because it holds for background jobs
// and message handlers that never touch the HTTP pipeline.
//
// TWO CAVEATS: IgnoreQueryFilters() bypasses it deliberately, and a filter
// referencing an injected field with AddDbContextPool captures a stale value.

// ── NULLABILITY drives the schema ────────────────────────────────────────
public string Name { get; set; } = "";      // → NOT NULL
public string? Notes { get; set; }          // → NULL
// With nullable reference types enabled, the C# declaration IS the schema
// decision — worth knowing before wondering why a column became required.
Key insight: the single most consequential thing to understand about EF Core is where server evaluation stops and client evaluation begins. Everything before the query is materialised must translate to SQL; anything EF cannot translate throws at runtime rather than silently fetching the table — a deliberate change from EF6, which would happily pull a million rows into memory to run a predicate. But the boundary moves the instant you call ToList, AsEnumerable or foreach: after that, every operation runs in your process on whatever was fetched. Most catastrophic EF performance problems are one ToList() in the wrong place.

Part 3 — The Translation Boundary

// ✓ SERVER-EVALUATED — one SQL statement, filtered in the database:
var orders = await db.Orders
    .Where(o => o.Status == OrderStatus.Paid && o.Total > 100m)
    .OrderByDescending(o => o.CreatedAt)
    .Take(20)
    .ToListAsync(ct);
// SELECT ... FROM orders WHERE status = 'Paid' AND total > 100
// ORDER BY created_at DESC LIMIT 20

// ✗ THE CATASTROPHE — ToList() before the filter:
var orders = (await db.Orders.ToListAsync(ct))       // ← fetches EVERY row
    .Where(o => o.Status == OrderStatus.Paid)        // ← filters in memory
    .Take(20)
    .ToList();
// Correct results, and it will work perfectly on a development database with
// 200 rows. In production with 8 million orders it transfers all of them,
// allocates all of them, and times out. The bug is invisible in review
// because the LINQ reads identically.

// ── WHAT DOES NOT TRANSLATE ──────────────────────────────────────────────
// A method EF cannot express in SQL throws InvalidOperationException:
.Where(o => IsEligible(o))                    // ✗ your own C# method
.Where(o => o.Total.ToString().Contains("9")) // ✗ no SQL equivalent
.Where(o => o.CreatedAt.ToLocalTime() > from) // ✗ time-zone conversion
// Throwing is the RIGHT behaviour — the alternative is a silent full scan.
// The fix is to express the rule in translatable terms, not to call ToList.

// ── CASE SENSITIVITY, a genuine cross-provider trap ──────────────────────
.Where(o => o.Reference.ToLower() == reference.ToLower())
// Translates, but usually defeats the index on Reference — the database
// cannot use a b-tree index on a computed expression. On PostgreSQL prefer a
// case-insensitive collation or a functional index; on SQL Server the default
// collation is already case-insensitive, so the ToLower is pure cost.

// ── EF.Functions FOR PROVIDER-SPECIFIC SQL ───────────────────────────────
.Where(o => EF.Functions.Like(o.Reference, "ORD-2026-%"))
.Where(o => EF.Functions.ILike(o.Email, pattern))         // PostgreSQL
// Prefer these over string methods when you need a specific SQL construct.

// ── SPLIT QUERIES for multiple collection includes ───────────────────────
var order = await db.Orders
    .Include(o => o.Lines)
    .Include(o => o.Payments)
    .AsSplitQuery()                          // ← two statements, not a join
    .FirstOrDefaultAsync(o => o.Id == id, ct);
// A single query joining two collections produces a CARTESIAN EXPLOSION:
// 20 lines × 5 payments = 100 rows, with the order's columns duplicated in
// every one. Split queries issue one statement per collection instead.
// The trade-off is that they are not atomic — a concurrent write between the
// two statements gives an inconsistent result, so wrap in a transaction if
// that matters.

Part 4 — Loading Strategies and N+1

// ── EAGER: Include, loaded in the same round trip ────────────────────────
var order = await db.Orders
    .Include(o => o.Lines)
        .ThenInclude(l => l.Product)
    .FirstOrDefaultAsync(o => o.Id == id, ct);

// ── EXPLICIT: load on demand, deliberately ───────────────────────────────
await db.Entry(order).Collection(o => o.Lines).LoadAsync(ct);

// ── LAZY: proxies load on property access — AVOID IN WEB APPLICATIONS ─────
options.UseLazyLoadingProxies();      // requires virtual navigations
// It makes N+1 the DEFAULT and invisible: a loop touching a navigation issues
// one query per iteration with nothing in the source suggesting a database
// call. It also throws if the context is disposed, which turns a
// serialization pass into a runtime error.

// ── THE N+1 PROBLEM ──────────────────────────────────────────────────────
// ✗ 1 query for orders, then ONE PER ORDER for the customer:
var orders = await db.Orders.Take(100).ToListAsync(ct);
foreach (var order in orders)
{
    var customer = await db.Customers.FindAsync(order.CustomerId);  // ← ×100
    Console.WriteLine(customer!.Name);
}
// 101 round trips. At 2ms each that is 200ms of pure latency, and it scales
// linearly with the page size — so it looks fine on page one and collapses on
// an export.

// ✓ ONE query with a join:
var summaries = await db.Orders
    .Take(100)
    .Select(o => new { o.Id, CustomerName = o.Customer.Name })
    .ToListAsync(ct);

// ── HOW TO ACTUALLY FIND N+1 ─────────────────────────────────────────────
// Not by reading code — by counting queries. Log them in development:
// "Microsoft.EntityFrameworkCore.Database.Command": "Information"
//
// Or fail a test when a request exceeds a query budget:
[Fact]
public async Task Order_list_uses_a_bounded_number_of_queries()
{
    var counter = new QueryCountingInterceptor();
    // ...configure the factory with the interceptor...

    await client.GetAsync("/api/orders?page=1&size=50");

    Assert.True(counter.Count <= 3,
        $"Expected at most 3 queries, saw {counter.Count} — likely N+1.");
}
// This is one of the highest-value tests available for a data-heavy API,
// because N+1 is invisible in code review and only appears under real data
// volumes.

// ── FILTERED INCLUDES ────────────────────────────────────────────────────
.Include(o => o.Lines.Where(l => !l.IsCancelled).OrderBy(l => l.Sequence))
// Loads only the lines you need rather than the whole collection.

Part 5 — Projection as the Default Read Path

// ✗ Loading entities to display a list:
var orders = await db.Orders
    .Include(o => o.Lines)
    .Include(o => o.Customer)
    .Where(o => o.CustomerId == customerId)
    .ToListAsync(ct);
return orders.Select(o => new OrderSummary(o.Id, o.Customer.Name, o.Total));
// Materialises every column of every order, every line and every customer —
// then discards nearly all of it. It also tracks all of them, doubling
// memory for change detection that will never be used.

// ✓ PROJECT IN THE DATABASE — fetch exactly what is rendered:
var summaries = await db.Orders
    .AsNoTracking()
    .Where(o => o.CustomerId == customerId)
    .OrderByDescending(o => o.CreatedAt)
    .Select(o => new OrderSummary(
        o.Id.Value,
        o.Customer.Name,                       // a JOIN, not a second query
        o.Total.Amount,
        o.Lines.Count(),                       // COUNT in SQL
        o.CreatedAt))
    .Take(50)
    .ToListAsync(ct);
// SELECT o.id, c.name, o.total, (SELECT COUNT(*) ...), o.created_at
// FROM orders o JOIN customers c ... LIMIT 50

// FOUR SEPARATE WINS, each worth having on its own:
//   • fewer columns transferred — often 10x less data
//   • no large text or blob columns loaded incidentally
//   • aggregates computed by the database rather than in memory
//   • projections are automatically untracked, so no snapshots
//
// A projection with Select is already untracked for the projected type, but
// AsNoTracking still matters when projecting from a tracked source.

// ── PAGINATION, always bounded ───────────────────────────────────────────
var page = await db.Orders
    .AsNoTracking()
    .Where(o => o.CustomerId == customerId)
    .OrderByDescending(o => o.CreatedAt).ThenByDescending(o => o.Id)
    .Skip((pageNumber - 1) * pageSize)
    .Take(pageSize)
    .Select(o => new OrderSummary(...))
    .ToListAsync(ct);
// ORDER BY IS MANDATORY for correct paging — without it the database may
// return rows in any order, so pages overlap or skip records
// nondeterministically. Include a tiebreaker so ties are stable.
// For deep pages, keyset pagination beats OFFSET; see REST API Design.

// ── COMPILED QUERIES for genuinely hot paths ─────────────────────────────
private static readonly Func<AppDbContext, Guid, CancellationToken, Task<Order?>>
    GetById = EF.CompileAsyncQuery((AppDbContext db, Guid id, CancellationToken ct) =>
        db.Orders.FirstOrDefault(o => o.Id == new OrderId(id)));
// Skips expression-tree translation per call. A measurable win on a query
// executed thousands of times per second, and pointless anywhere else —
// measure before reaching for it.

// ── RAW SQL when LINQ is the wrong tool ──────────────────────────────────
var report = await db.Database
    .SqlQuery<MonthlyTotal>($@"
        SELECT date_trunc('month', created_at) AS month, SUM(total) AS total
        FROM orders WHERE customer_id = {customerId}
        GROUP BY 1 ORDER BY 1")
    .ToListAsync(ct);
// Interpolated SqlQuery parameterises automatically. Complex analytical SQL
// is clearer written directly than contorted through LINQ.

Part 6 — Migrations

// dotnet ef migrations add AddOrderStatus --project Infrastructure --startup-project Api
// dotnet ef migrations script FromMigration ToMigration --idempotent --output migrate.sql
// dotnet ef database update

// ── DO NOT MIGRATE ON STARTUP IN PRODUCTION ──────────────────────────────
// ✗ await db.Database.MigrateAsync();
//   With N replicas, N instances race to apply the same migration. It also
//   requires the application's runtime credentials to hold DDL permissions —
//   a meaningful privilege escalation — and a failed migration crash-loops
//   the deployment.
//
// ✓ Generate an idempotent script and apply it as an ordered pipeline step,
//   or run a dedicated migration job before the rollout.

// ── BACKWARD-COMPATIBLE MIGRATIONS ARE MANDATORY ─────────────────────────
// During a rolling deploy, OLD AND NEW CODE RUN SIMULTANEOUSLY against ONE
// database, often for minutes.
//   ✓ add a NULLABLE column                 old code ignores it
//   ✓ add a table or an index               old code ignores it
//   ✓ widen a column                        old code still fits
//   ✗ drop or rename a column               old code breaks instantly
//   ✗ add NOT NULL with no default          old INSERTs fail
//   ✗ narrow a column or add a constraint   existing rows may violate it
//
// RENAMING IS A THREE-DEPLOY SEQUENCE:
//   1. add the new column; write BOTH, read the old
//   2. backfill; switch reads to the new column
//   3. once no running code references it, drop the old column
// Tedious, and the alternative is downtime.

// ── DATA MIGRATIONS ──────────────────────────────────────────────────────
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>("status_v2", "orders", nullable: true);
    migrationBuilder.Sql(
        "UPDATE orders SET status_v2 = CASE status WHEN 0 THEN 'Draft' " +
        "WHEN 1 THEN 'Paid' ELSE 'Unknown' END");
}
// Backfill in SQL, not by loading entities — a C# loop over ten million rows
// is hours of round trips. For very large tables, batch the UPDATE so it does
// not hold locks or bloat the transaction log.

// ── ALWAYS REVIEW THE GENERATED MIGRATION ────────────────────────────────
// EF infers intent from a model diff and cannot distinguish a RENAME from a
// DROP plus ADD — and it generates the latter, which silently destroys the
// column's data. Reading the migration before committing it is not optional.

// ── AND WRITE Down() OR ACCEPT THAT ROLLBACK MEANS RESTORE ───────────────
// An empty Down() is a decision, not an oversight — many teams roll forward
// only. But make it explicit, because discovering it during an incident is
// the wrong time.

Interview Questions

Beginner: Why is DbContext registered as scoped?

Because a DbContext is designed as a short-lived unit of work, and one HTTP request is the natural unit. AddDbContext registers it scoped: every request gets its own context, and the request scope disposes it when the response completes, releasing its connection and everything its change tracker holds.

It is also not thread-safe. A context supports one operation at a time; starting a second before the first completes throws "A second operation was started on this context". That rules out singleton: concurrent requests would share one context and fail intermittently under load, while its change tracker grew for the life of the process and served stale entities from memory.

Transient fails differently. Every class that asks for a context gets its own, so the repository that loads an order and the service that calls SaveChanges hold different change trackers — the save writes nothing, and the two can never share a transaction. Scoped is exactly the granularity at which every collaborator in a request sees the same unit of work.

  // web requests: one context per request, shared by every service in it
  builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(conn));

  // or, where there is no request scope or you need parallel queries:
  builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseNpgsql(conn));
  await using var db = await factory.CreateDbContextAsync(ct);

The follow-ups show depth. Where there is no request scope — a BackgroundService, a singleton — use IDbContextFactory<T> and create a context per unit of work. The same factory answers parallelism inside one request: Task.WhenAll over one context throws, so each concurrent query needs its own. And AddDbContextPool keeps scoped semantics while reusing instances — faster, but anything injected into the context's constructor, such as a tenant, is captured by the pooled instance.

Beginner: What is the N+1 problem?

The N+1 problem is one query to fetch a list, then one more query per item to fetch related data — 100 orders and their customers cost 101 round trips instead of one. Each query may be fast on its own; the damage is round-trip latency multiplied by N, plus pressure on the connection pool. At 2 ms a trip, a page of 100 spends 200 ms waiting on the network, and an export of 10,000 simply times out.

  // N+1: one query for the page, one per order for its customer
  var orders = await db.Orders.OrderBy(o => o.Id).Take(100).ToListAsync(ct);
  foreach (var o in orders)
      names.Add((await db.Customers.FindAsync(o.CustomerId))!.Name);   // x100

  // one query: the join happens in the database
  var rows = await db.Orders.OrderBy(o => o.Id).Take(100)
      .Select(o => new { o.Id, CustomerName = o.Customer.Name })
      .ToListAsync(ct);

What makes it dangerous is that it is invisible. The code reads naturally, passes review, and is fast against a development database with ten rows. The usual sources are a loop that touches a navigation or calls FindAsync, lazy loading — which turns every navigation access into a hidden query — and serializers or mappers walking an object graph after the query has already run.

The fixes, in order of preference: a projection that selects exactly what the response needs, so the database joins and aggregates; an Include when you genuinely need entities; or, when the related keys come from elsewhere, one batched query — collect the ids, load them with a single Contains that becomes WHERE id IN (...), and join in memory.

What the interviewer really wants is how you find it: count queries rather than read code. Log Microsoft.EntityFrameworkCore.Database.Command in development, watch per-request query counts in tracing, and keep a test with a query budget per endpoint, so a regression fails in CI instead of in production.

Mid: What is the difference between client and server evaluation?

An EF Core query is an IQueryable: an expression tree describing the query, not code that has run. When you materialise it, the provider translates the tree to SQL and the database executes it — server evaluation. Anything applied after materialisation runs in your process over the rows that came back — client evaluation. The cost difference is an indexed seek returning 20 rows versus transferring the whole table.

Since EF Core 3, EF throws when it cannot translate part of a query, instead of silently fetching everything and filtering in memory as EF6 did. A custom C# method in a Where, or ToString() on a column, raises InvalidOperationException. That is the right behaviour: a loud failure in development rather than a silent full scan in production. The fix is to express the rule in translatable terms — a direct comparison, an EF.Functions call, a computed column — not to add ToList() until the error goes away.

  db.Orders.Where(o => o.Total > 100m).Take(20)              // server: WHERE ... LIMIT 20

  db.Orders.AsEnumerable().Where(o => o.Total > 100m)        // client: every row fetched

  db.Orders.Where(o => o.Total > 100m)
      .Select(o => new OrderDto(o.Id, FormatMoney(o.Total)))  // allowed: final projection

There is one sanctioned exception: client code in the final Select is allowed, because EF can fetch the columns and call your method per row without changing which rows come back. Everywhere else the boundary moves at ToList, AsEnumerable and foreach — and, less obviously, whenever a query is passed or returned as IEnumerable<T>. A repository method returning IEnumerable<Order> turns every caller's Where into an in-memory filter over a full fetch.

That is what the interviewer is probing: whether you can read a LINQ chain and say which operators reach the database. Deliberate client evaluation is fine — after a server-side filter has already narrowed the rows.

Mid: When would you use AsSplitQuery?

When a query includes more than one collection navigation and the collections are large enough that a single join multiplies rows. By default EF Core loads an Include graph in one SQL statement with JOINs. For one collection that is fine; for two sibling collections the join produces a cartesian product — 20 lines times 5 payments returns 100 rows, each repeating every column of the order — and a third collection multiplies again.

  var order = await db.Orders
      .Include(o => o.Lines)
      .Include(o => o.Payments)
      .AsSplitQuery()                 // three statements: orders, lines, payments
      .FirstOrDefaultAsync(o => o.Id == id, ct);

  // or split by default, opting back in per query with AsSingleQuery():
  o.UseNpgsql(conn, npg => npg.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));

AsSplitQuery issues one statement per collection, so row counts add instead of multiply: 1 + 20 + 5 rows instead of 100, with no duplicated order columns. EF logs a warning when it sees multiple collection includes with no splitting behaviour configured, which is a useful prompt to decide.

The trade-offs are what the interviewer is checking. More round trips: for small collections or on a high-latency link, the single query is faster. No consistency between statements: a write landing between them can pair a parent with children that do not match; if that matters, run them in a transaction at snapshot or repeatable-read isolation. And with Skip/Take, a split query needs a unique, deterministic ordering, because each statement re-applies the paging — with ties, the collection queries can load children for a different page of parents.

The rule of thumb: one collection, single query; several sizable collections, split. And for read paths, often neither — a projection that selects only what the page shows avoids loading the collections at all.

Senior: An endpoint is fast in staging and times out in production with the same code. Diagnose.

The pattern points at something whose cost scales with data volume rather than with code, so I would look first for operations that are correct at any size but only expensive at production scale. The leading candidate is client evaluation — a ToList or AsEnumerable before the filtering, which transfers the whole table and then filters in memory; on a staging database of a few thousand rows that is imperceptible, and on eight million it is fatal. The second is N+1: a loop touching a navigation issues one query per row, so a page of fifty is tolerable and an export of five thousand is not. The third is a missing index — staging often has different data distribution, and a query that scans a small table happily will not scan a large one. The fourth is a cartesian explosion from multiple collection includes, which multiplies rather than adds. I would confirm rather than guess by enabling command logging to count queries and see the generated SQL, then taking the actual SQL to the database and reading its execution plan, which distinguishes a missing index from an unindexable predicate such as a ToLower that defeats a b-tree. The durable preventions are a projection as the default read path so only needed columns are transferred, bounded page sizes at the binding layer so no caller can request everything, and a test asserting a query-count budget per endpoint — that last one is the only mechanism I know that catches N+1 before production, because it is invisible in code review.

Senior: How do you evolve a schema with zero downtime on a rolling deploy?

The governing constraint is that during a rolling deploy the old and new versions run simultaneously against one database, so every migration must be compatible with both. That makes additive changes safe — a nullable column, a new table, a new index, a widened column — and makes drops, renames, narrowing and new constraints unsafe, because instances still running the previous version will fail immediately or the existing data will violate the constraint. A rename therefore becomes an expand-and-contract sequence across three deploys: add the new column and have the application write both while reading the old, then backfill and switch reads to the new column, then drop the old one once no running code references it. It is tedious and it is the price of not taking downtime. Operationally I would not run migrations at application startup, because with several replicas they race, it requires the runtime credentials to hold DDL permissions, and a failure crash-loops the deployment; instead I generate an idempotent script and apply it as an ordered pipeline step or a dedicated job before the rollout. Backfills belong in batched SQL rather than a C# loop, since ten million rows through the change tracker is hours of round trips and a single unbatched UPDATE holds locks and bloats the transaction log. I would also insist on reading every generated migration, because EF infers intent from a model diff and cannot tell a rename from a drop plus add — it generates the latter, which silently discards the column's data. And I would decide explicitly whether Down methods are maintained or whether the team rolls forward only, because discovering that during an incident is the wrong moment.

        npgsql =>

    {
        options.EnableSensitiveDataLogging();   // logs PARAMETER VALUES
        options.EnableDetailedErrors();

});

// cloud database — that would otherwise surface as a wave of 500s.
//
// The environment guard on EnableSensitiveDataLogging is the important part:
// it writes parameter values into logs, which in production means passwords

// KNOCK-ON EFFECT: with retries enabled, BeginTransaction throws. Any

2 (easy): Rewrite this to run entirely in the database: db.Orders.ToList().Where(o => o.Total > 100).Take(10).
Solution 
// ✗ BEFORE — ToList() materialises EVERY order, then filters in memory:
var orders = db.Orders.ToList()
    .Where(o => o.Total > 100)
    .Take(10)
    .ToList();

// ✓ AFTER — the filter and limit reach the database:
var orders = await db.Orders
    .AsNoTracking()
    .Where(o => o.Total > 100m)
    .OrderByDescending(o => o.CreatedAt)     // required for a stable Take
    .Take(10)
    .Select(o => new OrderSummary(o.Id.Value, o.Total.Amount, o.CreatedAt))
    .ToListAsync(ct);

// SELECT o.id, o.total, o.created_at FROM orders
// WHERE o.total > 100 ORDER BY o.created_at DESC LIMIT 10

// FOUR CHANGES, each independent:
//   • filtering before materialisation — the actual bug
//   • OrderBy, because Take without an order returns arbitrary rows
//   • a projection, so three columns transfer instead of all of them
//   • AsNoTracking and ToListAsync, since this is a read and should not block
//
// The original returns CORRECT results, which is what makes it dangerous: it
// passes every test on a small database and times out on a large one.
3 (medium): Configure an Order entity with a strongly-typed id, a string enum, an owned address and a backing-field collection.
Solution 
public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> builder)
    {
        builder.ToTable("orders");
        builder.HasKey(o => o.Id);

        // Strongly-typed ID stored as a plain guid.
        builder.Property(o => o.Id)
            .HasConversion(id => id.Value, value => new OrderId(value))
            .ValueGeneratedNever();

        builder.Property(o => o.CustomerId)
            .HasConversion(id => id.Value, value => new CustomerId(value));

        // Enum as a STRING — an ordinal silently reassigns meaning when a
        // member is inserted, and is unreadable in ad-hoc queries.
        builder.Property(o => o.Status)
            .HasConversion<string>()
            .HasMaxLength(32)
            .IsRequired();

        // Owned value object — inline columns, no separate table, no identity.
        builder.OwnsOne(o => o.ShippingAddress, address =>
        {
            address.Property(a => a.Line1).HasColumnName("shipping_line1")
                   .HasMaxLength(200).IsRequired();
            address.Property(a => a.City).HasColumnName("shipping_city")
                   .HasMaxLength(100).IsRequired();
            address.Property(a => a.PostCode).HasColumnName("shipping_postcode")
                   .HasMaxLength(20).IsRequired();
        });

        // The entity exposes Lines as IReadOnlyList over a private _lines
        // field, so EF must be told to write through the FIELD — otherwise it
        // cannot materialise the collection at all.
        builder.Metadata
            .FindNavigation(nameof(Order.Lines))!
            .SetPropertyAccessMode(PropertyAccessMode.Field);

        builder.HasMany(o => o.Lines)
            .WithOne()
            .HasForeignKey(l => l.OrderId)
            .OnDelete(DeleteBehavior.Cascade);

        builder.HasIndex(o => new { o.CustomerId, o.CreatedAt })
            .HasDatabaseName("ix_orders_customer_created");
    }
}

4 (medium): An endpoint issues 200 queries per request. Find the cause and fix it.
Solution 
// ✗ THE CAUSE — a navigation touched inside a loop:
var orders = await db.Orders.Where(o => o.CustomerId == id).ToListAsync(ct);

var result = new List<OrderDto>();
foreach (var order in orders)                          // 100 orders
{
    var customer = await db.Customers.FindAsync(order.CustomerId);   // +100
    await db.Entry(order).Collection(o => o.Lines).LoadAsync(ct);    // +100
    result.Add(new OrderDto(order.Id, customer!.Name, order.Lines.Count));
}
// 1 + 100 + 100 = 201 round trips.

// ✓ ONE projected query:
var result = await db.Orders
    .AsNoTracking()
    .Where(o => o.CustomerId == id)
    .OrderByDescending(o => o.CreatedAt)
    .Select(o => new OrderDto(
        o.Id.Value,
        o.Customer.Name,        // JOIN — not a second query
        o.Lines.Count()))       // COUNT in SQL — the lines are never fetched
    .Take(50)                   // and BOUND it
    .ToListAsync(ct);

// SELECT o.id, c.name, (SELECT COUNT(*) FROM order_lines l WHERE l.order_id = o.id)
// FROM orders o INNER JOIN customers c ON c.id = o.customer_id
// WHERE o.customer_id = @id ORDER BY o.created_at DESC LIMIT 50

// Note the line COUNT never loads the lines — the database computes it.
// Include(o => o.Lines) would transfer every line row just to count them.

// ── HOW TO CATCH THIS AUTOMATICALLY ──────────────────────────────────────
public sealed class QueryCountingInterceptor : DbCommandInterceptor
{
    private int _count;
    public int Count => _count;

    public override ValueTask<InterceptionResult<DbDataReader>> ReaderExecutingAsync(
        DbCommand command, CommandEventData eventData,
        InterceptionResult<DbDataReader> result, CancellationToken ct = default)
    {
        Interlocked.Increment(ref _count);
        return base.ReaderExecutingAsync(command, eventData, result, ct);
    }
}

[Fact]
public async Task Order_list_stays_within_its_query_budget()
{
    var counter = new QueryCountingInterceptor();
    var client = CreateClientWithInterceptor(counter);

    await client.GetAsync("/api/orders?size=50");

    Assert.True(counter.Count <= 3,
        $"Expected ≤3 queries, saw {counter.Count} — likely an N+1 regression.");
}

// query-count budget is one of the highest-value tests for a data-heavy API.
5 (hard): Design a paged, filtered, sorted order-list query that stays fast at 50 million rows.
Solution 
public async Task<PagedResult<OrderSummary>> ListAsync(
    OrderFilter filter, PageRequest paging, CancellationToken ct)
{
    // 1. START SCOPED. The index leads with customer_id, so the working set
    //    is one customer's orders — never 50M rows.
    var query = db.Orders.AsNoTracking()
        .Where(o => o.CustomerId == filter.CustomerId);

    // 2. COMPOSE FILTERS conditionally — each is a deliberate, indexed path.
    if (filter.Status is { } status)
        query = query.Where(o => o.Status == status);

    if (filter.From is { } from)
        query = query.Where(o => o.CreatedAt >= from);

    if (filter.MinTotal is { } min)
        query = query.Where(o => o.Total >= min);

    // 3. SORT FROM AN ALLOWLIST — never a client-supplied column name, which
    //    is both an injection vector and a guaranteed unindexed scan.
    query = filter.Sort switch
    {
        "total"  => query.OrderByDescending(o => o.Total).ThenByDescending(o => o.Id),
        "status" => query.OrderBy(o => o.Status).ThenByDescending(o => o.Id),
        _        => query.OrderByDescending(o => o.CreatedAt)
                         .ThenByDescending(o => o.Id)   // stable tiebreaker
    };

    // 4. COUNT IS EXPENSIVE AT THIS SCALE. Cap it rather than counting 50M.
    var total = await query.Take(1001).CountAsync(ct);
    var displayTotal = total > 1000 ? "1000+" : total.ToString();

    // 5. PROJECT — three columns, not entities, and the line count computed
    //    by the database.
    var items = await query
        .Skip((paging.Page - 1) * paging.Size)
        .Take(paging.Size)                       // clamped at binding, max 100
        .Select(o => new OrderSummary(
            o.Id.Value, o.Status.ToString(), o.Total.Amount,
            o.Lines.Count(), o.CreatedAt))
        .ToListAsync(ct);

    return new PagedResult<OrderSummary>(items, displayTotal);
}

// REQUIRED INDEX — without it none of the above helps:
//   CREATE INDEX ix_orders_customer_created
//     ON orders (customer_id, created_at DESC, id DESC);

// ── THE REMAINING LIMIT, STATED HONESTLY ─────────────────────────────────
// OFFSET still degrades linearly: page 25,000 makes the database read and
// discard 500,000 rows. Two mitigations, and the choice is a product decision:
//
//   a) CAP THE DEPTH — reject page × size > 10,000 and push users to filter.
//      Nobody browses to page 500; capping converts an unbounded scan into a
//      bounded one.
//
//   b) KEYSET PAGINATION for clients that scroll — constant time at any
//      depth, at the cost of losing random page access. See REST API Design.
//
// Also: AsNoTracking on every read path, and every sortable column indexed —
// the allowlist doubles as the guarantee that this is true.
6 (hard): Rename a column with zero downtime across a rolling deploy.
Solution 
// THE CONSTRAINT: during a rolling deploy, old and new code run
// SIMULTANEOUSLY against ONE database. A rename in a single migration breaks
// every instance still running the old version, instantly.
//
// ✗ WHAT EF GENERATES IF YOU JUST RENAME THE PROPERTY:
//     migrationBuilder.DropColumn("customer_ref", "orders");
//     migrationBuilder.AddColumn<string>("customer_reference", "orders");
//   A DROP plus ADD — which DESTROYS THE DATA. EF diffs the model and cannot
//   tell a rename from a delete-and-create. This is why every generated
//   migration must be read before committing.

// ── DEPLOY 1: ADD, and write to BOTH ─────────────────────────────────────
migrationBuilder.AddColumn<string>(
    name: "customer_reference", table: "orders",
    type: "varchar(50)", nullable: true);        // NULLABLE — old INSERTs
                                                 // do not set it

public sealed class Order
{
    private string _customerRef = "";

    public string CustomerRef                    // still the read path
    {
        get => _customerRef;
        set { _customerRef = value; CustomerReference = value; }  // dual write
    }

    public string? CustomerReference { get; private set; }   // new, write-only
}
// Old instances write only customer_ref; new instances write both. Both
// versions work against this schema, which is the whole requirement.

// ── BETWEEN DEPLOYS: BACKFILL, in batches ────────────────────────────────
// Batched so it does not hold locks or bloat the transaction log:
//   UPDATE orders SET customer_reference = customer_ref
//   WHERE customer_reference IS NULL AND id IN (
//       SELECT id FROM orders WHERE customer_reference IS NULL LIMIT 10000);
// Repeat until zero rows affected. NOT a C# loop over ten million entities —
// that is hours of round trips through the change tracker.

// ── DEPLOY 2: READ FROM THE NEW COLUMN, still writing both ───────────────
public string CustomerReference { get; set; } = "";   // now the read path
public string CustomerRef { get => CustomerReference;  // kept in sync for
                            set => CustomerReference = value; }   // old rows

// ── DEPLOY 3: DROP the old column ────────────────────────────────────────
// ONLY once no running instance references customer_ref. Verify before
// dropping — a query-log check or an application metric, not an assumption.
migrationBuilder.DropColumn("customer_ref", "orders");
// Add the NOT NULL constraint here too, now that every row is populated:
migrationBuilder.AlterColumn<string>(
    "customer_reference", "orders", nullable: false, defaultValue: "");

// ── WHY THREE DEPLOYS ────────────────────────────────────────────────────
// Each step is individually compatible with the version running before it.
// There is no instant at which any deployed code sees a schema it cannot
// handle. The alternative is a maintenance window — which is a legitimate
// choice, but it should be a decision rather than a surprise.
//
// APPLY MIGRATIONS AS A PIPELINE STEP, not on startup: replicas race,
// runtime credentials would need DDL rights, and a failure crash-loops the
// deployment.
//   dotnet ef migrations script Prev Next --idempotent --output migrate.sql

🎯 Key Takeaways

  • DbContext is scoped because it is a short-lived, non-thread-safe unit of work; use a factory wherever there is no ambient scope.
  • AddDbContextPool is faster but reuses instances — constructor-injected tenant or user state becomes a cross-request leak.
  • Configure the model fluently in infrastructure so entities stay free of EF attributes.
  • Store enums as strings; ordinals silently reassign meaning when a member is inserted.
  • Everything before materialisation must translate to SQL — one misplaced ToList() turns an indexed query into a full table transfer.
  • N+1 comes from touching navigations in loops or from lazy loading; catch it with a query-count budget test, not code review.
  • Use AsSplitQuery for multiple collection includes to avoid a cartesian explosion.
  • Project to DTOs as the default read path — fewer columns, database-side aggregates, and no tracking.
  • Skip/Take without a stable OrderBy produces overlapping or missing rows.
  • Never migrate on startup, keep migrations backward compatible for rolling deploys, and always read the generated migration — EF turns a rename into a data-destroying drop and add.
  • A transient DbContext splits one request across several contexts, so they cannot share change tracking or a transaction.
  • A context runs one operation at a time; parallel queries need separate contexts from IDbContextFactory.
  • Client code is still allowed in the final Select; everywhere else an untranslatable expression throws.
  • Returning IEnumerable<T> from a data method moves every later operator into memory.
  • Split queries with Skip/Take need a unique, deterministic order, or children are loaded for the wrong parents.
  • Fix N+1 by fetching related data in one query: a projection, an Include, or a single Contains over collected keys.
