Middleware Pipeline The Pipeline

What you'll master: the nested-delegate model that makes ASP.NET Core's pipeline work, why order is behaviour rather than style, the correct order and what breaks at each wrong position, writing middleware that does not leak or deadlock, and the response-already-started rule that turns a small mistake into an unfixable 500. Prerequisites: How ASP.NET Core Runs and Routing.

Part 1 — The Pipeline Is Nested Function Calls

// Every piece of middleware is a function that receives the context and the
// NEXT function. That is the entire model.
app.Use(async (context, next) =>
{
    // ── inbound: runs on the way IN, before everything below ──
    var sw = Stopwatch.StartNew();

    await next();          // hand off to the rest of the pipeline

    // ── outbound: runs on the way OUT, after everything below returned ──
    sw.Stop();
    logger.LogInformation("{Path} took {Ms}ms",
        context.Request.Path, sw.ElapsedMilliseconds);
});

// Registration order builds a RUSSIAN DOLL, not a queue:
app.Use(A);
app.Use(B);
app.Use(C);
//
//   request  →  A-in  →  B-in  →  C-in  →  endpoint
//   response ←  A-out ←  B-out ←  C-out ←──┘
//
// Inbound in registration order, outbound in REVERSE. This is why exception
// handling belongs at the TOP: it must be the outermost frame to catch what
// anything below throws — the same reason an outer try/catch catches more.

// Not calling next() SHORT-CIRCUITS — nothing below ever runs:
app.Use(async (context, next) =>
{
    if (!context.Request.Headers.ContainsKey("X-Api-Key"))
    {
        context.Response.StatusCode = 401;
        return;                       // pipeline stops here
    }
    await next();
});

// app.Run() is TERMINAL — it takes no next and always ends the pipeline:
app.Run(async context => await context.Response.WriteAsync("fallback"));

// app.Map branches on a path prefix; the branch has its own pipeline:
app.Map("/admin", admin =>
{
    admin.UseMiddleware<AdminAuditMiddleware>();
    admin.Run(async ctx => await ctx.Response.WriteAsync("admin"));
});

// app.UseWhen branches on ANY predicate and REJOINS the main pipeline —
// usually what you actually want:
app.UseWhen(
    ctx => ctx.Request.Path.StartsWithSegments("/api"),
    api => api.UseMiddleware<ApiKeyMiddleware>());
// MapWhen also branches on a predicate but does NOT rejoin — the branch must
// terminate. Choosing Map/MapWhen when you meant UseWhen produces a request
// that mysteriously never reaches your endpoints.

Part 2 — The Correct Order, and What Each Mistake Costs

// The canonical order. Every line's position is load-bearing.
var app = builder.Build();

app.UseExceptionHandler("/error");   // 1. OUTERMOST — catches everything below
app.UseHsts();                       // 2. production only, sets the HSTS header

app.UseHttpsRedirection();           // 3. before anything reads the body
app.UseForwardedHeaders();           // 4. before anything reads IP or scheme
app.UseStaticFiles();                // 5. short-circuits — no auth cost for CSS

app.UseRouting();                    // 6. MATCH: endpoint now on the context

app.UseCors();                       // 7. after routing, before auth
app.UseAuthentication();             // 8. WHO are you (sets User)
app.UseAuthorization();              // 9. ARE you allowed (reads endpoint metadata)
app.UseRateLimiter();                // 10. after auth, so limits can be per-user

app.MapControllers();                // 11. EXECUTE the endpoint

// ── WHAT BREAKS AT EACH WRONG POSITION ───────────────────────────────────
//
// UseExceptionHandler NOT first
//   → exceptions thrown ABOVE it escape to the server: no custom error page,
//     a raw 500, and in Development a stack trace to the client.
//
// UseAuthorization BEFORE UseRouting
//   → no endpoint is selected yet, so no [Authorize] metadata is found, so the
//     request is ALLOWED. Fails OPEN, silently. The single most dangerous
//     ordering bug in the framework: no exception, no log, protected endpoints
//     served anonymously, and every authenticated test still passes.
//
// UseAuthentication AFTER UseAuthorization
//   → HttpContext.User is not populated when authorization evaluates it, so
//     every authenticated user looks anonymous and everything 401s. Loud and
//     obvious — the opposite failure mode, and much safer for it.
//
// UseCors AFTER UseAuthorization
//   → the browser's preflight OPTIONS request is rejected by authorization
//     before CORS can answer it, so the browser reports a CORS error while the
//     server logs a 401 — two teams debugging two different problems.
//
// UseForwardedHeaders AFTER anything reading IP/scheme
//   → rate limiting buckets every user under the proxy's IP, generated links
//     come out as http, and audit logs record one address forever.
//
// UseStaticFiles AFTER UseAuthorization
//   → every CSS and image request runs the full auth stack. Works, wastes
//     real CPU, and can make static assets require a login by accident.
//
// UseRateLimiter BEFORE UseAuthentication
//   → limits can only key on IP, never on user identity, so one NAT'd office
//     shares a bucket and per-tenant quotas are impossible.
Key insight: the two authentication/authorization mistakes fail in opposite directions, and that asymmetry is what makes one of them dangerous. Putting authentication too late means everyone is anonymous — every request 401s, and you find out in the first minute of testing. Putting authorization before routing means the metadata is missing and the request is permitted — nothing breaks, nothing logs, and the bug ships. Whenever a security control can fail open, the ordering that produces it deserves an integration test asserting an anonymous request gets 401, because no happy-path test will ever catch it.

Part 3 — Writing Middleware Three Ways

// 1. INLINE — fine for one-offs and small apps:
app.Use(async (context, next) =>
{
    context.Response.Headers["X-Request-Id"] = Guid.NewGuid().ToString();
    await next();
});

// 2. CONVENTIONAL CLASS — the classic form. Note the constructor rule:
public sealed class RequestIdMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestIdMiddleware> _logger;

    // Constructor runs ONCE at startup — this class is effectively a SINGLETON.
    // Injecting a scoped service here is a captive dependency: you capture the
    // first request's DbContext forever.
    public RequestIdMiddleware(RequestDelegate next, ILogger<RequestIdMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    // Scoped services are injected HERE instead — InvokeAsync is called per
    // request, so the container resolves them from the request's scope.
    public async Task InvokeAsync(HttpContext context, IRequestAudit audit)
    {
        var id = context.Request.Headers["X-Request-Id"].FirstOrDefault()
                 ?? Guid.NewGuid().ToString();

        context.Response.Headers["X-Request-Id"] = id;

        using (_logger.BeginScope(new Dictionary<string, object> { ["RequestId"] = id }))
        {
            await audit.RecordAsync(id, context.Request.Path);
            await _next(context);
        }
    }
}
app.UseMiddleware<RequestIdMiddleware>();

// 3. IMiddleware — factory-activated, resolved PER REQUEST from DI:
public sealed class AuditMiddleware(IAuditService audit) : IMiddleware
{
    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        await audit.RecordAsync(context.Request.Path);   // scoped is FINE here
        await next(context);
    }
}
builder.Services.AddScoped<AuditMiddleware>();   // MUST be registered
app.UseMiddleware<AuditMiddleware>();

// CHOOSING: IMiddleware when the class needs scoped dependencies in its
// constructor and you want that checked by the container; conventional when
// it does not, since it avoids a per-request allocation. The conventional
// form's constructor/InvokeAsync split is the thing to remember — it is not
// stylistic, it is the difference between a singleton and a per-request
// resolution.

// The extension-method convention, so Program.cs reads cleanly:
public static class RequestIdMiddlewareExtensions
{
    public static IApplicationBuilder UseRequestId(this IApplicationBuilder app)
        => app.UseMiddleware<RequestIdMiddleware>();
}

Part 4 — The Response-Already-Started Rule

// Once the first byte of the response leaves, headers and status code are
// FROZEN. Writing them afterwards throws InvalidOperationException.

app.Use(async (context, next) =>
{
    await next();

    // ✗ WRONG — the endpoint below has very likely already written.
    context.Response.Headers["X-Total-Time"] = sw.ElapsedMilliseconds.ToString();
    // InvalidOperationException: Headers are read-only, response has started.
});

// ✓ RIGHT — register a callback that fires just BEFORE the first write:
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();

    context.Response.OnStarting(() =>
    {
        sw.Stop();
        context.Response.Headers["X-Response-Time-Ms"] = sw.ElapsedMilliseconds.ToString();
        return Task.CompletedTask;
    });

    await next();
});

// OnCompleted runs after the response is fully sent — for cleanup and metrics
// that do not touch headers:
context.Response.OnCompleted(() =>
{
    metrics.RecordDuration(sw.Elapsed);
    return Task.CompletedTask;
});

// THIS IS ALSO WHY EXCEPTION HANDLERS CAN FAIL. If an endpoint writes 200 and
// half a JSON body, then throws, the exception handler cannot turn it into a
// 500 — the status is already on the wire. The client receives a truncated
// body with a success status, which is worse than an error. Check before
// attempting to rewrite:
app.UseExceptionHandler(errorApp => errorApp.Run(async context =>
{
    if (context.Response.HasStarted)
    {
        logger.LogError("Exception after response started; connection aborted.");
        context.Abort();          // kill the connection — a truncated response
        return;                   // is at least detectable by the client
    }

    context.Response.StatusCode = 500;
    context.Response.ContentType = "application/problem+json";
    await context.Response.WriteAsJsonAsync(new ProblemDetails
    {
        Status = 500,
        Title = "An unexpected error occurred.",
        Instance = context.Request.Path,
        Extensions = { ["traceId"] = Activity.Current?.Id }
    });
}));

// The design lesson: buffer or compute anything that affects headers BEFORE
// the endpoint runs, or defer it to OnStarting. Do not plan to fix up headers
// on the way out.

Part 5 — Reading the Body Without Breaking Everything

// The request body is a FORWARD-ONLY, READ-ONCE stream. Middleware that reads
// it for logging or signature verification leaves nothing for model binding —
// the endpoint then sees an empty body and binds null.

// ✓ Enable buffering so the stream can be rewound:
app.Use(async (context, next) =>
{
    context.Request.EnableBuffering();          // switches to a seekable stream

    using var reader = new StreamReader(
        context.Request.Body,
        Encoding.UTF8,
        detectEncodingFromByteOrderMarks: false,
        leaveOpen: true);                       // ← without this you close it

    var body = await reader.ReadToEndAsync();
    logger.LogDebug("Body: {Body}", body);

    context.Request.Body.Position = 0;          // ← REWIND for model binding
    await next();
});

// THE COSTS, which is why this must never be on by default:
//   • EnableBuffering spools to memory up to a threshold (30KB), then to a
//     TEMP FILE on disk. A large upload therefore becomes disk I/O.
//   • the whole body is retained for the request's lifetime — under load that
//     is a real memory multiplier
//   • logging bodies logs PASSWORDS, TOKENS AND CARD NUMBERS. This is how
//     credentials end up permanently in a log aggregator.
//
// If body logging is genuinely needed: sample it, cap the size, redact known
// sensitive fields, and scope it to specific paths — never the whole app.
app.UseWhen(ctx => ctx.Request.Path.StartsWithSegments("/api/webhooks"),
    branch => branch.UseMiddleware<WebhookSignatureMiddleware>());

// RESPONSE body capture needs a swapped stream, and the memory risk is worse
// because you buffer the ENTIRE response before sending a byte — which also
// destroys streaming and server-sent events:
app.Use(async (context, next) =>
{
    var original = context.Response.Body;
    using var buffer = new MemoryStream();
    context.Response.Body = buffer;

    try
    {
        await next();
        buffer.Position = 0;
        // ...inspect buffer here...
        buffer.Position = 0;
        await buffer.CopyToAsync(original);     // MUST copy back
    }
    finally
    {
        context.Response.Body = original;       // MUST restore, even on throw
    }
});
// Forgetting the finally leaves a disposed MemoryStream on the context for
// anything downstream — an error that surfaces far from its cause.

Part 6 — Cancellation, Async Discipline, and Shared State

// RequestAborted fires when the client disconnects. Honouring it is what stops
// abandoned work from consuming the server during a traffic spike.
app.Use(async (context, next) =>
{
    var ct = context.RequestAborted;
    try
    {
        await next();
    }
    catch (OperationCanceledException) when (ct.IsCancellationRequested)
    {
        // EXPECTED — the client went away. Not an error; do not log it as one
        // or a mobile app backgrounding will look like an outage.
        logger.LogDebug("Request aborted by client: {Path}", context.Request.Path);
    }
});

// ASYNC DISCIPLINE — the rules that prevent deadlocks and thread starvation:
//   • ALWAYS await next(); never .Result or .Wait(). Blocking a request thread
//     on async work exhausts the thread pool under load, and the symptom is
//     rising latency across every endpoint, not an obvious error.
//   • never use async void in middleware — exceptions cannot be caught and
//     will terminate the process
//   • do not fire-and-forget work in middleware. The request scope disposes
//     when the response completes, so a background continuation using a scoped
//     service hits ObjectDisposedException intermittently. Queue it to a
//     hosted service instead.

// STATE: middleware instances are shared. HttpContext.Items is the per-request
// bag; instance fields are NOT.
app.Use(async (context, next) =>
{
    context.Items["CorrelationId"] = Guid.NewGuid();   // ✓ per request
    await next();
});
// A mutable field on a conventional middleware class is shared across every
// concurrent request — a data race that appears only under load, and one that
// a single-user test can never reproduce.

// DIAGNOSTICS: "the request returned 401 and I do not know which middleware
// did it" is a common afternoon. Built-in HTTP logging answers it:
builder.Services.AddHttpLogging(o =>
    o.LoggingFields = HttpLoggingFields.RequestPath
                    | HttpLoggingFields.ResponseStatusCode);
app.UseHttpLogging();

Interview Questions

Beginner: Explain the order middleware runs in.

Middleware nests rather than queues. Each component runs its inbound code in registration order, calls next() to invoke everything registered after it, and then runs its outbound code as the call stack unwinds — so outbound execution happens in reverse registration order. The practical consequence is that the first registered middleware is the outermost frame: it sees the request first and the response last. That is exactly why exception handling is registered first, since only an outer frame can catch what inner frames throw, and why a component that does not call next() short-circuits everything below it.

Beginner: What is the difference between app.Use and app.Run?

app.Use registers middleware that receives a next delegate and can choose to continue the pipeline or short-circuit. app.Run registers terminal middleware: it takes no next, so nothing after it can ever execute. Run is for the end of a pipeline or a branch — a catch-all handler or the terminus of a Map branch. Registering anything after an app.Run is dead code, and the framework will not warn you about it.

Mid: Why can't you set a response header after await next(), and what do you do instead?

Because once any middleware or the endpoint writes the first byte of the response body, the status code and headers have already been sent to the client and are immutable — attempting to modify them throws InvalidOperationException. Since await next() runs the entire rest of the pipeline including the endpoint, the response has usually started by the time control returns. The correct approach is Response.OnStarting, which registers a callback invoked immediately before the first write, when headers are still mutable — that is where a timing header or correlation ID belongs. Response.OnCompleted covers the other case, work that must happen after the response is fully sent and does not touch headers, such as recording metrics.

Mid: Why must a conventional middleware class inject scoped services into InvokeAsync rather than its constructor?

Because conventional middleware is instantiated once, at application startup, and reused for every request — it is effectively a singleton. A scoped service injected into the constructor is therefore resolved once and captured forever, which is a captive dependency: with a DbContext you get an ObjectDisposedException after the first request completes, or worse, one non-thread-safe instance shared across concurrent requests. InvokeAsync is called per request with the request's own scope, so parameters declared there resolve correctly each time. The alternative is implementing IMiddleware, which is factory-activated per request and therefore allows scoped constructor injection — at the cost of an allocation per request and a required DI registration.

Senior: Logging middleware was added and now POST endpoints receive null models. Explain and fix.

The middleware read the request body, and the body is a forward-only, read-once stream. By the time model binding runs the stream is positioned at the end, so the binder reads zero bytes, deserializes nothing, and the parameter binds null — with no exception anywhere, which is what makes it puzzling. The fix is to call Request.EnableBuffering() before reading, which swaps in a seekable stream, then reset Request.Body.Position = 0 after reading so binding starts from the beginning; the StreamReader must also be constructed with leaveOpen: true or disposing it closes the underlying stream and reintroduces the same symptom. Beyond the mechanical fix I would question the requirement, because this middleware carries three real costs: buffering spools bodies over roughly 30KB to temporary files on disk, the buffer is retained for the request's lifetime which multiplies memory under load, and logging raw bodies writes passwords, tokens and card numbers into log storage where they are retained and broadly readable. If body capture is genuinely required — webhook signature verification is the legitimate case — I would scope it to those specific paths with UseWhen, cap the size read, redact known sensitive fields, and sample rather than capture every request.

Senior: Design middleware for correlation IDs, timing and error handling across a service that also streams responses.

I would order it exception handler outermost, then correlation, then timing, and treat the streaming requirement as the constraint that shapes all three. Correlation comes first among my own components because everything downstream — logs, metrics, the error response — needs the ID: it reads an inbound header if present so a trace spans services, generates one otherwise, writes it into HttpContext.Items and a logging scope so every log line inherits it automatically, and sets it on the response immediately, before any handler can start writing. Timing cannot work the naive way of measuring around await next() and then setting a header, because by then the response has started; it must register the header write in Response.OnStarting and record the metric in OnCompleted. Streaming is where most designs break: any middleware that buffers the response to inspect it destroys streaming and server-sent events by holding the entire body before sending a byte, turning an incremental response into a single delayed one and breaking long-lived connections outright. So I would not buffer responses at all, and if some diagnostic genuinely required it I would gate it behind UseWhen on non-streaming paths only. The error handler has to account for streaming too: once bytes are on the wire the status cannot be changed, so it must check Response.HasStarted and, when true, log with the correlation ID and call context.Abort() rather than attempt a rewrite — an aborted connection is detectable by the client, whereas a truncated body under a 200 status is silently interpreted as success. I would also distinguish client disconnects from failures by catching OperationCanceledException only when RequestAborted is signalled and logging it at debug, since streaming endpoints see disconnects constantly and treating them as errors makes an alerting dashboard useless.

🏋️ Graded Exercises

1 (easy): Write middleware that adds an X-App-Version header to every response.
Solution 
var version = typeof(Program).Assembly
    .GetCustomAttribute<AssemblyInformationalVersionAttribute>()?.InformationalVersion
    ?? "unknown";

app.Use(async (context, next) =>
{
    // Set BEFORE next() — after it the response has started and this throws.
    context.Response.Headers["X-App-Version"] = version;
    await next();
});

// The version is read once outside the delegate: reflection per request is
// pure waste when the value cannot change while the process is running.
2 (easy): Order these correctly and say what breaks if authorization comes before routing: UseAuthorization, UseRouting, UseExceptionHandler, UseAuthentication.
Solution 
app.UseExceptionHandler("/error");   // outermost — catches everything below
app.UseRouting();                    // match the endpoint first
app.UseAuthentication();             // establish WHO the caller is
app.UseAuthorization();              // decide whether they are ALLOWED

// IF AUTHORIZATION COMES BEFORE ROUTING: no endpoint has been selected, so the
// [Authorize] metadata attached to that endpoint does not exist yet. The
// authorization middleware finds nothing to enforce and PERMITS the request.
//
// It fails OPEN: no exception, no log entry, protected endpoints served to
// anonymous callers. Every authenticated happy-path test still passes, which
// is precisely why this reaches production. The regression test that catches
// it is an anonymous request asserting 401.
3 (medium): Add an X-Response-Time-Ms header measuring the full pipeline duration.
Solution 
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();

    // Registered BEFORE next() but INVOKED just before the first byte is
    // written — the only window where the duration is known AND headers are
    // still mutable.
    context.Response.OnStarting(() =>
    {
        sw.Stop();
        context.Response.Headers["X-Response-Time-Ms"] =
            sw.ElapsedMilliseconds.ToString();
        return Task.CompletedTask;
    });

    await next();
});

// The obvious version — measure around next(), then set the header — throws
// InvalidOperationException, because next() runs the endpoint and the endpoint
// has already started the response.
//
// Caveat worth knowing: OnStarting fires at the FIRST WRITE, so for a
// streaming response this measures time-to-first-byte, not total duration.
// For total duration record a metric in OnCompleted instead — it cannot be a
// header, because headers are long gone by then.
4 (medium): Write API-key middleware that applies only to /api paths and rejects with problem details.
Solution 
app.UseWhen(
    context => context.Request.Path.StartsWithSegments("/api"),
    branch => branch.Use(async (context, next) =>
    {
        var provided = context.Request.Headers["X-Api-Key"].FirstOrDefault();
        var expected = context.RequestServices
            .GetRequiredService<IOptions<ApiOptions>>().Value.ApiKey;

        // Fixed-time comparison: a plain == leaks key material through timing.
        var ok = provided is not null && CryptographicOperations.FixedTimeEquals(
            Encoding.UTF8.GetBytes(provided),
            Encoding.UTF8.GetBytes(expected));

        if (!ok)
        {
            context.Response.StatusCode = 401;
            context.Response.ContentType = "application/problem+json";
            await context.Response.WriteAsJsonAsync(new ProblemDetails
            {
                Status = 401,
                Title = "Missing or invalid API key.",
                Instance = context.Request.Path
            });
            return;                    // short-circuit: next() is NOT called
        }

        await next();
    }));

// UseWhen, not MapWhen: UseWhen REJOINS the main pipeline so matching requests
// continue to routing and the endpoint. MapWhen creates a branch that never
// rejoins, so every /api request would terminate in the branch and no endpoint
// would ever run — a confusing 404 for every API call.
5 (hard): Body-logging middleware broke model binding. Fix it and list the costs that justify limiting its scope.
Solution 
app.UseWhen(
    ctx => ctx.Request.Path.StartsWithSegments("/api/webhooks"),   // SCOPED
    branch => branch.Use(async (context, next) =>
{
    context.Request.EnableBuffering();       // 1. seekable stream

    using (var reader = new StreamReader(
        context.Request.Body, Encoding.UTF8,
        detectEncodingFromByteOrderMarks: false,
        bufferSize: 4096,
        leaveOpen: true))                    // 2. do NOT close the body
    {
        var buffer = new char[4096];         // 3. CAP the read
        var read = await reader.ReadBlockAsync(buffer, context.RequestAborted);
        logger.LogDebug("Body (truncated): {Body}", Redact(new string(buffer, 0, read)));
    }

    context.Request.Body.Position = 0;       // 4. REWIND for model binding
    await next();
}));

// WHY IT BROKE: the body is a forward-only, read-once stream. After reading,
// the position is at the end, so model binding reads zero bytes and binds
// null — with no exception, which is what makes it hard to diagnose.
//
// THE FOUR FIXES, each necessary:
//   1. EnableBuffering  — without it the stream cannot be rewound at all
//   2. leaveOpen: true  — disposing the reader otherwise closes the body
//   3. a size cap       — an unbounded read is caller-controlled memory
//   4. Position = 0     — the actual rewind binding depends on
//
// THE COSTS THAT JUSTIFY SCOPING IT:
//   • buffering spools bodies over ~30KB to a TEMP FILE — an upload endpoint
//     becomes disk I/O on every request
//   • the buffer is held for the request lifetime: a memory multiplier under
//     concurrency, and a large-upload endpoint is now a memory risk
//   • logging raw bodies writes PASSWORDS, TOKENS AND CARD NUMBERS into log
//     storage, retained per your retention policy and readable by anyone with
//     log access — this is a compliance incident, not a performance note
//
// Hence: specific paths only, capped, redacted, and ideally sampled rather
// than every request.
6 (hard): An exception handler returns HTML instead of JSON for some failures, and some responses are truncated. Diagnose and build a correct handler.
Solution 
// TWO DISTINCT CAUSES, commonly present together.
//
// CAUSE 1 — HTML instead of JSON: the exception was thrown ABOVE
// UseExceptionHandler in the pipeline, so it escaped to the web server, which
// produced its own error page. Anything registered before the handler is
// outside its protection.
//
// CAUSE 2 — truncation: the endpoint had already written part of the response
// before throwing. Status and headers were on the wire, so the handler could
// not rewrite them; the client got a partial body under a 200 status, which it
// reads as SUCCESS with malformed content — the worst possible outcome.

var app = builder.Build();

app.UseExceptionHandler(errorApp => errorApp.Run(async context =>
{
    var feature = context.Features.Get<IExceptionHandlerFeature>();
    var ex = feature?.Error;

    var correlationId = context.Items["CorrelationId"]?.ToString()
                        ?? Activity.Current?.Id
                        ?? context.TraceIdentifier;

    logger.LogError(ex, "Unhandled exception {CorrelationId} at {Path}",
        correlationId, feature?.Path ?? context.Request.Path);

    // THE CRITICAL CHECK — cannot rewrite what is already sent.
    if (context.Response.HasStarted)
    {
        // Abort deliberately. A truncated body under a success status is
        // silently misread by clients; a killed connection is at least a
        // detectable transport error they will retry or surface.
        context.Abort();
        return;
    }

    context.Response.Clear();
    context.Response.StatusCode = ex switch
    {
        // Map known domain failures; everything else is a genuine 500.
        ValidationException => StatusCodes.Status400BadRequest,
        UnauthorizedAccessException => StatusCodes.Status403Forbidden,
        TimeoutException => StatusCodes.Status504GatewayTimeout,
        _ => StatusCodes.Status500InternalServerError
    };
    context.Response.ContentType = "application/problem+json";

    await context.Response.WriteAsJsonAsync(new ProblemDetails
    {
        Status = context.Response.StatusCode,
        // Never leak ex.Message on a 500 — it carries connection strings,
        // file paths and internal structure.
        Title = context.Response.StatusCode == 500
            ? "An unexpected error occurred."
            : ex?.Message ?? "Request failed.",
        Instance = context.Request.Path,
        Extensions = { ["traceId"] = correlationId }
    });
}));

🎯 Key Takeaways

  • The pipeline is nested delegates: inbound in registration order, outbound in reverse. The first registered component is the outermost frame.
  • Order is behaviour, not style. UseExceptionHandler first, UseRouting before authorization, UseCors before authentication.
  • UseAuthorization before UseRouting fails open — no metadata, no error, protected endpoints served anonymously. Test with an anonymous request.
  • Not calling next() short-circuits everything below; app.Run is terminal by design.
  • UseWhen branches and rejoins; Map/MapWhen branch without rejoining and must terminate.
  • Headers freeze once the response starts — use OnStarting for headers and OnCompleted for metrics.
  • Conventional middleware is a singleton: scoped services go in InvokeAsync, not the constructor, or use IMiddleware.
  • Reading the body requires EnableBuffering, leaveOpen: true and a rewind — and costs disk spooling, memory, and credential leakage into logs.
  • Never buffer responses in middleware if the service streams: it destroys server-sent events and turns incremental responses into delayed ones.
  • An exception handler must check Response.HasStarted and abort rather than attempt a rewrite, and must never leak ex.Message on a 500.
