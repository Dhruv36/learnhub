Clean Architecture & CQRS Production

What you'll master: the dependency rule and what it actually buys you, layering that earns its cost versus ceremony that does not, CQRS at each of its three very different scales, the repository debate resolved honestly, and how to decide when a simpler structure is the correct engineering answer. Prerequisites: Dependency Injection, EF Core: Change Tracking and Testing ASP.NET Core.

Part 1 — The Dependency Rule

// Clean Architecture reduces to ONE rule: source code dependencies point
// INWARD. Inner layers know nothing about outer ones.
//
//   ┌─────────────────────────────────────────┐
//   │  API / Infrastructure  (outermost)      │  EF Core, HTTP, Stripe, SMTP
//   │  ┌───────────────────────────────────┐  │
//   │  │  Application                      │  │  use cases, orchestration
//   │  │  ┌─────────────────────────────┐  │  │
//   │  │  │  Domain      (innermost)    │  │  │  entities, invariants
//   │  │  └─────────────────────────────┘  │  │
//   │  └───────────────────────────────────┘  │
//   └─────────────────────────────────────────┘

// Enforced by PROJECT REFERENCES, which is what makes it real rather than a
// convention people forget:
//   Domain.csproj          → references NOTHING
//   Application.csproj     → references Domain
//   Infrastructure.csproj  → references Application, Domain
//   Api.csproj             → references Application, Infrastructure
//
// A compiler error is a better guardrail than a diagram.

// ── DOMAIN: rules that hold regardless of how they are invoked ───────────
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyList<OrderLine> Lines => _lines;      // no external mutation
    public OrderStatus Status { get; private set; }        // private setters
    public Money Total => new(_lines.Sum(l => l.Amount.Value), "USD");

    public Result AddLine(Product product, int quantity)
    {
        if (Status != OrderStatus.Draft)
            return Result.Fail("Lines cannot be added after submission.");
        if (quantity <= 0)
            return Result.Fail("Quantity must be positive.");

        _lines.Add(new OrderLine(product.Id, quantity, product.Price));
        return Result.Ok();
    }

    public Result Cancel(DateTimeOffset now)
    {
        // THE INVARIANT. It holds for the HTTP path, the queue consumer, the
        // admin tool, and anything written next year — because it lives on
        // the entity rather than in a caller.
        if (Status == OrderStatus.Dispatched)
            return Result.Fail("A dispatched order cannot be cancelled.");

        Status = OrderStatus.Cancelled;
        CancelledAt = now;
        return Result.Ok();
    }
}
// No EF attributes, no JSON attributes, no framework types. Configure
// persistence with IEntityTypeConfiguration in Infrastructure instead, so
// changing ORM never touches the domain.

// ── THE DEPENDENCY INVERSION THAT MAKES IT WORK ──────────────────────────
// Application defines the interface; Infrastructure implements it:
namespace Application.Abstractions;
public interface IOrderRepository
{
    Task<Order?> FindAsync(OrderId id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}

namespace Infrastructure.Persistence;
public sealed class OrderRepository(AppDbContext db) : IOrderRepository { }
// The arrow points inward at COMPILE time even though control flows outward
// at RUNTIME. That inversion is the entire mechanism.

// ── WHAT THIS ACTUALLY BUYS ──────────────────────────────────────────────
//   ✓ business rules testable with no database, no HTTP, no container
//   ✓ rules hold across every entry point, not just the one you thought of
//   ✓ infrastructure swaps without touching logic
//   ✓ the domain reads as domain language rather than framework plumbing
//
// ── AND WHAT IT COSTS ────────────────────────────────────────────────────
//   ✗ more projects, more files, more mapping between layers
//   ✗ a trivial CRUD change touches four layers
//   ✗ indirection that slows a newcomer down
//
// It pays for itself when the domain has real rules. It is pure overhead for
// a service that reads and writes rows.

Part 2 — CQRS at Three Scales

// CQRS means separating reads from writes. It is THREE different things at
// three scales, and conflating them is why the pattern gets a bad reputation.

// ── LEVEL 1: SEPARATE MODELS, ONE DATABASE (usually enough) ──────────────
// Writes go through the domain; reads project straight to a DTO.
public async Task<Result<OrderId>> Handle(CreateOrder command, CancellationToken ct)
{
    var order = new Order(command.CustomerId);
    foreach (var line in command.Lines)
    {
        var product = await products.FindAsync(line.ProductId, ct);
        var result = order.AddLine(product!, line.Quantity);   // invariants
        if (result.IsFailure) return Result.Fail<OrderId>(result.Error);
    }
    await orders.AddAsync(order, ct);
    await unitOfWork.SaveChangesAsync(ct);
    return order.Id;
}

// The read side skips the domain model ENTIRELY — no aggregate loading, no
// change tracking, exactly the columns needed:
public async Task<IReadOnlyList<OrderSummary>> Handle(
    GetOrderSummaries query, CancellationToken ct)
    => await db.Orders
        .AsNoTracking()
        .Where(o => o.CustomerId == query.CustomerId)
        .Select(o => new OrderSummary(o.Id, o.Status, o.Total, o.CreatedAt))
        .ToListAsync(ct);

// THIS IS THE VALUABLE 90%. Loading a full aggregate to display a list is
// wasteful, and forcing reads through a write-shaped model is what makes
// repositories feel obstructive. Separating them costs nothing structurally.

// ── LEVEL 2: SEPARATE DATABASES (read replica) ───────────────────────────
// Writes to the primary, reads from a replica. Buys read scaling; costs
// REPLICATION LAG, which is a user-visible correctness change:
//   a user creates an order, is redirected to the list, and it is not there.
// Mitigations: read-your-own-writes routing for a short window after a write,
// or reading from the primary immediately after a mutation.

// ── LEVEL 3: SEPARATE STORES + EVENT SOURCING (rarely justified) ─────────
// Writes append events; a projection builds a denormalised read model.
//   + full audit history, temporal queries, independent read scaling
//   − EVENTUAL CONSISTENCY everywhere, projection rebuilds, schema evolution
//     of events, and a much larger operational surface
//
// Adopt level 3 for a genuine need — regulatory audit, or read load that
// cannot be met otherwise — never because the architecture diagram looks
// impressive. Most teams that adopt it needed level 1.

// ── COMMANDS AND QUERIES AS TYPES ────────────────────────────────────────
public sealed record CreateOrder(Guid CustomerId, IReadOnlyList<OrderLineDto> Lines)
    : ICommand<Result<OrderId>>;

public sealed record GetOrderById(OrderId Id) : IQuery<OrderDetail?>;

// COMMANDS change state and return minimal data — an id, or a result.
// QUERIES never change state and return exactly what the caller displays.
// A "command" that returns a full DTO is usually a query in disguise, and a
// query that writes an audit row has broken the rule that makes queries safe
// to retry and cache.
Key insight: the layer that most often fails to earn its keep is the repository over EF Core. DbContext is already a unit of work and DbSet<T> is already a repository, so wrapping them adds a layer that mostly forwards calls — and the usual justification, swapping the ORM, essentially never happens. The legitimate reasons are narrower and worth being honest about: constraining aggregate access so callers cannot bypass invariants, and giving the domain an interface it owns so the dependency rule holds. If neither applies, injecting DbContext into an application service is a defensible engineering choice, not a shortcut.

Part 3 — Handlers, Pipelines, and Cross-Cutting Concerns

// One handler per use case keeps each file small and independently testable:
public sealed class CreateOrderHandler(
    IOrderRepository orders,
    IProductRepository products,
    IUnitOfWork unitOfWork) : ICommandHandler<CreateOrder, Result<OrderId>>
{
    public async Task<Result<OrderId>> Handle(CreateOrder command, CancellationToken ct)
    {
        var order = new Order(command.CustomerId);

        foreach (var line in command.Lines)
        {
            var product = await products.FindAsync(line.ProductId, ct);
            if (product is null) return Result.Fail<OrderId>("Unknown product.");

            var added = order.AddLine(product, line.Quantity);
            if (added.IsFailure) return Result.Fail<OrderId>(added.Error);
        }

        await orders.AddAsync(order, ct);
        await unitOfWork.SaveChangesAsync(ct);       // ONE transaction
        return order.Id;
    }
}

// ── PIPELINE BEHAVIOURS: cross-cutting concerns, declared once ───────────
public sealed class ValidationBehaviour<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehaviour<TRequest, TResponse> where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var failures = (await Task.WhenAll(validators
                .Select(v => v.ValidateAsync(request, ct))))
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        if (failures.Count > 0) throw new ValidationException(failures);
        return await next();
    }
}

public sealed class TransactionBehaviour<TRequest, TResponse>(AppDbContext db)
    : IPipelineBehaviour<TRequest, TResponse> where TRequest : ICommand<TResponse>
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        // Constrained to ICommand, so QUERIES do not pay for a transaction.
        var strategy = db.Database.CreateExecutionStrategy();
        return await strategy.ExecuteAsync(async () =>
        {
            await using var tx = await db.Database.BeginTransactionAsync(ct);
            var response = await next();
            await tx.CommitAsync(ct);
            return response;
        });
    }
}
// Behaviours run in registration order, nesting like middleware. Logging
// outermost, then validation, then transaction closest to the handler — so a
// validation failure never opens a transaction.

// ── THE ENDPOINT BECOMES TRANSLATION ONLY ────────────────────────────────
app.MapPost("/api/orders", async (
    CreateOrderRequest request, ISender sender, CancellationToken ct) =>
{
    var result = await sender.Send(request.ToCommand(), ct);

    return result.IsSuccess
        ? Results.Created($"/api/orders/{result.Value}", new { id = result.Value })
        : Results.Conflict(new ProblemDetails { Title = result.Error });
});
// HTTP concerns stay in the endpoint; the handler knows nothing about status
// codes, which is what lets a queue consumer call the same handler.

// ── THE HONEST COST OF A MEDIATOR ────────────────────────────────────────
// Send(command) is resolved at runtime by type, so "find all callers" no
// longer works and navigation depends on tooling. For a small application
// that indirection buys little: injecting CreateOrderHandler directly gives
// the same testability with a traceable call graph. The mediator earns its
// place when pipeline behaviours are doing real work across many handlers.

Part 4 — Domain Events and Aggregate Boundaries

// Domain events let an aggregate announce something happened without knowing
// who cares — keeping the domain free of infrastructure.
public abstract class Entity
{
    private readonly List<IDomainEvent> _events = [];
    public IReadOnlyList<IDomainEvent> DomainEvents => _events;
    protected void Raise(IDomainEvent e) => _events.Add(e);
    public void ClearDomainEvents() => _events.Clear();
}

public sealed class Order : Entity
{
    public Result Dispatch(DateTimeOffset now)
    {
        if (Status != OrderStatus.Paid)
            return Result.Fail("Only paid orders can be dispatched.");

        Status = OrderStatus.Dispatched;
        Raise(new OrderDispatched(Id, CustomerId, now));   // just a record
        return Result.Ok();
    }
}

// Dispatched when the transaction commits, via an interceptor:
public sealed class DomainEventInterceptor(IPublisher publisher)
    : SaveChangesInterceptor
{
    public override async ValueTask<int> SavedChangesAsync(
        SaveChangesCompletedEventData eventData, int result,
        CancellationToken ct = default)
    {
        // AFTER the commit — publishing before it risks handlers reacting to
        // a change that then rolls back.
        var entities = eventData.Context!.ChangeTracker
            .Entries<Entity>()
            .Where(e => e.Entity.DomainEvents.Count > 0)
            .Select(e => e.Entity)
            .ToList();

        var events = entities.SelectMany(e => e.DomainEvents).ToList();
        entities.ForEach(e => e.ClearDomainEvents());

        foreach (var domainEvent in events)
            await publisher.Publish(domainEvent, ct);

        return result;
    }
}

// ── THE ATOMICITY PROBLEM, HONESTLY ──────────────────────────────────────
// Publishing AFTER commit means a crash between the two loses the event.
// Publishing BEFORE means handlers may react to a rollback. Neither is
// atomic, and for anything that must not be lost the answer is the
// TRANSACTIONAL OUTBOX: write the event as a row in the same transaction, and
// let a background publisher deliver it. Delivery is then at-least-once, so
// handlers must be idempotent.

// ── AGGREGATE BOUNDARIES: the design decision that matters most ──────────
// An aggregate is a consistency boundary — everything inside it is updated in
// ONE transaction, and it is the unit that enforces its own invariants.
//
// THE RULES THAT KEEP THEM SMALL:
//   • reference other aggregates BY ID, never by object reference
//   • ONE aggregate per transaction — needing two usually means the boundary
//     is wrong, or the consistency requirement is actually eventual
//   • an invariant spanning two aggregates cannot be enforced transactionally
//     without merging them, so ask whether it truly must be immediate
public sealed class Order : Entity
{
    public CustomerId CustomerId { get; }        // ✓ an ID
    // public Customer Customer { get; }         // ✗ drags a second aggregate
                                                 //   into this transaction
}

// LARGE AGGREGATES ARE THE COMMON FAILURE: an Order holding every line, every
// payment, every shipment and the customer must load it all to change a
// status, and two users editing unrelated parts collide on the same
// concurrency token. Smaller aggregates with eventual consistency between
// them nearly always scale better — and "must be immediately consistent" is
// a claim worth challenging every time it is made.

Part 5 — Structure and Testing

// ── VERTICAL SLICES: an alternative worth taking seriously ───────────────
// Layered structure groups by TECHNICAL role:
//   Application/Commands/CreateOrderHandler.cs
//   Application/Queries/GetOrderHandler.cs
//   Domain/Order.cs
//   Infrastructure/OrderRepository.cs
// A change to "create order" touches four directories.

// Vertical slices group by FEATURE:
//   Features/Orders/Create/    Command.cs, Handler.cs, Validator.cs, Endpoint.cs
//   Features/Orders/GetById/   Query.cs, Handler.cs, Response.cs
//   Domain/Order.cs
// A change touches ONE directory, and deleting a feature deletes a folder.
//
// The trade-off is real: slices accept some duplication in exchange for
// locality, which usually turns out to be the better trade because coupling
// between features is what makes large codebases hard to change. Slices and
// a clean domain are compatible — keep the domain shared and let each slice

Part 6 — Choosing the Right Amount of Architecture

// The most valuable skill here is knowing when NOT to apply this.

// ── WHEN CLEAN ARCHITECTURE + CQRS EARNS ITS COST ────────────────────────
//   • genuine business rules — pricing, eligibility, workflow state machines
//   • several entry points: HTTP, queue consumers, scheduled jobs, admin
//   • a long-lived system with a team that rotates
//   • rules that must be verifiable in isolation for audit or compliance
//   • read and write shapes that genuinely differ

// ── WHEN IT IS PURE OVERHEAD ─────────────────────────────────────────────
//   • CRUD over a database with no rules beyond validation
//   • a small service with one entry point
//   • a prototype, or anything whose lifespan is measured in weeks
//   • a team of one or two who share full context
//
// For those, a two-project solution — an API and a small services layer —
// with EF Core injected directly is not a compromise. It is the correct
// engineering decision, and dressing it in four layers makes every change
// slower with no compensating benefit.

// ── THE MIDDLE PATH, which suits most services ───────────────────────────
//   Api/                endpoints, DTOs, HTTP concerns
//   Application/        services with real rules; EF injected directly
//   Domain/             entities with invariants (only if there ARE invariants)
//
// No repository, no mediator, no separate infrastructure project. Add each
// only when a specific pain appears:
//   • add a REPOSITORY when you need to constrain aggregate access, not
//     because a diagram says to
//   • add a MEDIATOR when pipeline behaviours are doing real cross-cutting
//     work across many handlers
//   • split INFRASTRUCTURE when the dependency rule is genuinely being
//     violated and a compiler error would help

// ── EVOLVING WITHOUT A REWRITE ───────────────────────────────────────────
// The one investment that always pays, at any size: keep HTTP concerns out of
// business logic. An application service taking a command and returning a
// result — not an IActionResult, not an HttpContext — can be called by a
// queue consumer tomorrow and wrapped in whatever structure the code grows
// into. That single boundary is what makes later refactoring mechanical
// rather than a rewrite.
//
// A useful test: can this logic be invoked with NO HttpContext? If yes, the
// layering can evolve freely. If no, every architectural change is expensive
// regardless of how many projects the solution has.

Interview Questions

Beginner: What is the dependency rule in Clean Architecture?

Source code dependencies point inward only: outer layers may reference inner ones, never the reverse. The domain sits innermost and references nothing — no EF Core, no ASP.NET Core — the application layer references the domain, and infrastructure and the API reference both. When an inner layer needs something an outer one provides, such as persistence, the inner layer defines the interface and the outer one implements it, which is why it is called dependency inversion: the compile-time arrow points inward even though control flows outward at runtime. In practice the rule is enforced by project references, so a violation is a compiler error rather than a code-review comment.

Beginner: What does CQRS actually mean?

Separating the model used to change state from the model used to read it. At its simplest and most useful, that means commands go through domain entities that enforce invariants, while queries project directly to DTOs with no tracking and no aggregate loading — one database, two models. People often assume CQRS requires separate read and write databases or event sourcing, but those are larger, optional scales of the same idea that bring eventual consistency and substantial operational cost. The first level costs essentially nothing structurally and solves the common problem of a write-shaped model making reads awkward and slow.

Mid: Do you need a repository over EF Core?

Often not. DbContext already implements the unit of work pattern and DbSet<T> is already a repository, so a wrapper that forwards calls adds a layer with no behaviour while making queries harder to express. The usual justification — swapping the ORM — is almost never exercised, and a repository built for that goal ends up leaking IQueryable anyway, which defeats it. The genuinely good reasons are narrower: constraining access so callers can only load whole aggregates and cannot bypass invariants, and giving the domain or application layer an interface it owns so the dependency rule holds without referencing EF. If neither applies, injecting DbContext into an application service is a legitimate choice rather than a shortcut, and it keeps queries expressive.

Mid: What is an aggregate boundary and why keep aggregates small?

An aggregate is a consistency boundary: a cluster of objects updated together within a single transaction, with a root that enforces the invariants across them. Keeping it small matters for two reasons. Operationally, a large aggregate must be loaded in full to change anything, so updating an order's status might materialise every line, payment and shipment. And for concurrency, the aggregate is the unit of contention — two users editing unrelated parts of a large aggregate collide on the same version token even though their changes do not conflict. The rules that keep them small are to reference other aggregates by identifier rather than object reference, and to modify only one aggregate per transaction. When an invariant appears to span two aggregates, the useful question is whether it must truly be immediately consistent, because that claim is frequently made and rarely required.

Senior: A team applied Clean Architecture and CQRS to a CRUD service and velocity collapsed. Diagnose.

The architecture was chosen for a problem the service does not have. Clean Architecture pays for itself when there are genuine business rules to isolate and multiple entry points that must all enforce them; a service whose logic is validate-and-save gets all of the indirection and none of the benefit. The symptom is characteristic: adding a field means touching a domain entity, a command, a handler, a DTO, a mapping profile, a validator and a database configuration — seven files for something that was one column, with each mapping layer offering a fresh opportunity to make a mistake. I would not propose a rewrite, since that trades one large cost for another. I would collapse the layers that are not earning their place, most likely starting with the repository, since over EF Core it is usually pure forwarding, and then the mediator if pipeline behaviours are not doing real cross-cutting work — direct handler injection gives the same testability with a traceable call graph. I would keep the one boundary that always pays: application logic that takes a command and returns a result rather than touching HttpContext, because that is what allows a queue consumer or job to reuse it and what makes any future restructuring mechanical. I would also suggest reorganising by feature rather than by technical layer, so a change lives in one folder. The broader point I would make to the team is that architecture is a trade of present cost against future flexibility, and buying flexibility you have no evidence of needing is as much a mistake as having none — the discipline is matching the structure to the actual complexity, and being willing to remove structure when the evidence says it is not paying.

Senior: How do you decide aggregate boundaries and handle an invariant spanning two of them?

I start from transactional consistency: what must be true at the instant a transaction commits, and what may be true a moment later. Everything that must hold immediately belongs inside one aggregate; anything that may lag belongs in separate aggregates coordinated by events. That framing usually shrinks aggregates considerably, because most claimed invariants turn out to be business processes rather than instantaneous truths. For an invariant genuinely spanning two aggregates there are three options and the choice depends on how the business tolerates violation. Merging them into one aggregate gives immediate consistency at the cost of a larger contention unit and more loading, and it is right when a violation is genuinely unacceptable — a financial ledger balance, for instance. Eventual consistency via a domain event lets each aggregate commit independently, with a handler reconciling afterwards, and it needs a defined compensating action when reconciliation fails; this is right for most cases, such as decrementing inventory after an order is placed. The third option is to move the invariant into a process manager or saga that owns the multi-step workflow explicitly, which is right when the coordination itself has states worth modelling. What I would push back on is the reflexive assumption that consistency must be immediate — a business that is happy to oversell occasionally and reconcile is describing eventual consistency, and forcing a transactional boundary there buys contention nobody asked for. I would also note that whichever option is chosen, the event-driven variants require idempotent handlers and an outbox for reliable delivery, because at-least-once is the realistic guarantee and designs that assume exactly-once break in production.

🏋️ Graded Exercises

1 (easy): Given an Order entity with EF attributes and public setters, refactor it to a clean domain entity.
Solution 
// ✗ BEFORE — the domain depends on the ORM, and any caller can corrupt state:
public class Order
{
    [Key] public int Id { get; set; }
    [Required, MaxLength(50)] public string Status { get; set; }
    public List<OrderLine> Lines { get; set; } = new();
    [ForeignKey("Customer")] public int CustomerId { get; set; }
}

// ✓ AFTER — invariants enforced, no framework types:
public sealed class Order : Entity
{
    private readonly List<OrderLine> _lines = [];

    private Order() { }                      // EF needs a parameterless ctor

    public Order(CustomerId customerId)
    {
        Id = new OrderId(Guid.CreateVersion7());
        CustomerId = customerId;
        Status = OrderStatus.Draft;
    }

    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }     // ID, not a reference
    public OrderStatus Status { get; private set; }        // an enum, not a string
    public IReadOnlyList<OrderLine> Lines => _lines;       // no external Add

    public Result AddLine(Product product, int quantity)
    {
        if (Status != OrderStatus.Draft)
            return Result.Fail("Cannot modify a submitted order.");
        if (quantity <= 0)
            return Result.Fail("Quantity must be positive.");

        _lines.Add(new OrderLine(product.Id, quantity, product.Price));
        return Result.Ok();
    }
}

// Persistence configuration moves to Infrastructure:
public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> builder)
    {
        builder.HasKey(o => o.Id);
        builder.Property(o => o.Id)
            .HasConversion(id => id.Value, value => new OrderId(value));
        builder.Property(o => o.Status).HasMaxLength(50).HasConversion<string>();
        builder.Metadata.FindNavigation(nameof(Order.Lines))!
            .SetPropertyAccessMode(PropertyAccessMode.Field);   // uses _lines
    }
}

2 (easy): Write a command and a query handler for orders, showing the read/write asymmetry.
Solution 
// ── WRITE: through the domain, so invariants are enforced ────────────────
public sealed record CreateOrder(CustomerId CustomerId, IReadOnlyList<LineDto> Lines)
    : ICommand<Result<OrderId>>;

public sealed class CreateOrderHandler(
    IOrderRepository orders, IProductRepository products, IUnitOfWork uow)
    : ICommandHandler<CreateOrder, Result<OrderId>>
{
    public async Task<Result<OrderId>> Handle(CreateOrder command, CancellationToken ct)
    {
        var order = new Order(command.CustomerId);

        foreach (var line in command.Lines)
        {
            var product = await products.FindAsync(line.ProductId, ct);
            if (product is null) return Result.Fail<OrderId>("Unknown product.");

            var added = order.AddLine(product, line.Quantity);   // ← invariant
            if (added.IsFailure) return Result.Fail<OrderId>(added.Error);
        }

        await orders.AddAsync(order, ct);
        await uow.SaveChangesAsync(ct);
        return order.Id;              // an ID, not a DTO — commands stay thin
    }
}

// ── READ: skips the domain entirely ──────────────────────────────────────
public sealed record GetOrderSummaries(CustomerId CustomerId)
    : IQuery<IReadOnlyList<OrderSummary>>;

public sealed class GetOrderSummariesHandler(AppDbContext db)
    : IQueryHandler<GetOrderSummaries, IReadOnlyList<OrderSummary>>
{
    public async Task<IReadOnlyList<OrderSummary>> Handle(
        GetOrderSummaries query, CancellationToken ct)
        => await db.Orders
            .AsNoTracking()                      // no snapshots
            .Where(o => o.CustomerId == query.CustomerId)
            .OrderByDescending(o => o.CreatedAt)
            .Select(o => new OrderSummary(       // exactly four columns
                o.Id.Value, o.Status.ToString(), o.Total.Amount, o.CreatedAt))
            .Take(100)
            .ToListAsync(ct);
}

// THE ASYMMETRY IS THE POINT: the write path loads aggregates because it must
// enforce rules; the read path projects columns because it only needs to
// display them. Forcing reads through repositories and aggregates is what
// makes people dislike the pattern — and is exactly what CQRS avoids.
//
// Note the query handler takes DbContext directly. There is no invariant to
// protect on a read, so a repository would add nothing here.
3 (medium): Write a pipeline behaviour wrapping commands in a transaction but leaving queries alone.
Solution 
public sealed class TransactionBehaviour<TRequest, TResponse>(
    AppDbContext db, ILogger<TransactionBehaviour<TRequest, TResponse>> log)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : ICommand<TResponse>      // ← the generic constraint that
{                                              //   excludes queries entirely
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        // Already in a transaction (a nested handler) — do not open another.
        if (db.Database.CurrentTransaction is not null) return await next();

        // The execution strategy must own the transaction when
        // EnableRetryOnFailure is configured, or BeginTransaction throws.
        var strategy = db.Database.CreateExecutionStrategy();

        return await strategy.ExecuteAsync(async () =>
        {
            await using var tx = await db.Database.BeginTransactionAsync(ct);
            try
            {
                var response = await next();
                await tx.CommitAsync(ct);
                return response;
            }
            catch
            {
                await tx.RollbackAsync(ct);
                throw;
            }
        });
    }
}

builder.Services.AddScoped(typeof(IPipelineBehavior<,>), typeof(LoggingBehaviour<,>));
builder.Services.AddScoped(typeof(IPipelineBehavior<,>), typeof(ValidationBehaviour<,>));
builder.Services.AddScoped(typeof(IPipelineBehavior<,>), typeof(TransactionBehaviour<,>));

// ORDER MATTERS and mirrors middleware nesting: logging outermost so it
// records everything, validation next so a failure never opens a transaction,
// and the transaction closest to the handler so it is held for the shortest
// possible time.
//
// TWO CAVEATS WORTH KNOWING:
//   • the strategy delegate may run MORE THAN ONCE on retry, so nothing with
//     side effects — emails, message publishing — belongs inside it
//   • the generic constraint on ICommand is what keeps queries from paying
//     for a transaction they do not need
4 (medium): Raise a domain event on dispatch and dispatch it reliably.
Solution 
// 1. The entity raises it — a plain record, no infrastructure:
public sealed class Order : Entity
{
    public Result Dispatch(DateTimeOffset now)
    {
        if (Status != OrderStatus.Paid)
            return Result.Fail("Only paid orders can be dispatched.");

        Status = OrderStatus.Dispatched;
        DispatchedAt = now;
        Raise(new OrderDispatched(Id, CustomerId, now));
        return Result.Ok();
    }
}

public sealed record OrderDispatched(OrderId OrderId, CustomerId CustomerId,
    DateTimeOffset DispatchedAt) : IDomainEvent;

// 2. RELIABLE dispatch — write events to the OUTBOX in the SAME transaction:
public sealed class OutboxInterceptor(TimeProvider clock) : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result,
        CancellationToken ct = default)
    {
        var context = eventData.Context!;

        var entities = context.ChangeTracker.Entries<Entity>()
            .Where(e => e.Entity.DomainEvents.Count > 0)
            .Select(e => e.Entity)
            .ToList();

        foreach (var domainEvent in entities.SelectMany(e => e.DomainEvents))
        {
            context.Set<OutboxMessage>().Add(new OutboxMessage
            {
                Id = Guid.CreateVersion7(),
                Type = domainEvent.GetType().FullName!,
                Payload = JsonSerializer.Serialize(domainEvent, domainEvent.GetType()),
                OccurredAt = clock.GetUtcNow()
            });
        }

        entities.ForEach(e => e.ClearDomainEvents());
        return base.SavingChangesAsync(eventData, result, ct);
    }
}

// 3. A background publisher drains the outbox and marks rows processed.

// WHY THE OUTBOX RATHER THAN PUBLISHING DIRECTLY:
//   publish BEFORE commit → handlers react to a change that may roll back
//   publish AFTER commit  → a crash in between loses the event silently
//   OUTBOX                → the event row commits WITH the state change, so
//                           there is no window where one exists without the
//                           other
//
// THE COST, which must be stated: delivery becomes AT-LEAST-ONCE, since a
// crash after publishing but before marking processed causes a republish.
// Every handler must therefore be idempotent — a requirement to agree up
// front, not discover later.
5 (hard): An Order aggregate has grown to hold lines, payments, shipments and the customer. Redesign it.
Solution 
// ✗ THE PROBLEM AGGREGATE:
public class Order
{
    public List<OrderLine> Lines { get; set; }
    public List<Payment> Payments { get; set; }
    public List<Shipment> Shipments { get; set; }
    public Customer Customer { get; set; }        // an entire second aggregate
}
// CONSEQUENCES:
//   • changing a status loads lines, payments, shipments AND the customer
//   • a warehouse updating a shipment collides with finance recording a
//     payment — same aggregate, same concurrency token, unrelated changes
//   • the transaction spans four consistency boundaries
//   • the customer is mutable from the order, so invariants can be bypassed

// ✓ REDESIGNED — split by CONSISTENCY REQUIREMENT, not by data relationship:

public sealed class Order : Entity                 // aggregate 1
{
    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }   // ID, not a reference
    public OrderStatus Status { get; private set; }
    private readonly List<OrderLine> _lines = [];        // TRUE invariant:
    public IReadOnlyList<OrderLine> Lines => _lines;     // the total must match
                                                          // the lines exactly
    public Money Total => new(_lines.Sum(l => l.Amount.Value), "USD");
}

public sealed class Payment : Entity               // aggregate 2
{
    public OrderId OrderId { get; private set; }   // reference by ID
}

public sealed class Shipment : Entity              // aggregate 3
{
    public OrderId OrderId { get; private set; }
}

// WHY LINES STAY INSIDE: the order total is derived from the lines, so they
// must change together or the total is wrong at commit. That is a genuine
// transactional invariant.
//
// WHY PAYMENTS AND SHIPMENTS LEAVE: "the order is paid when payments cover
// the total" does NOT need to be true at the instant a payment row is
// written. It can be reconciled a moment later, so it is a process rather
// than an invariant.

// COORDINATION BY EVENT:
public sealed class PaymentReceivedHandler(IOrderRepository orders)
    : INotificationHandler<PaymentReceived>
{
    public async Task Handle(PaymentReceived e, CancellationToken ct)
    {
        var order = await orders.FindAsync(e.OrderId, ct);
        order!.RecordPayment(e.Amount);        // may transition to Paid
        await orders.SaveAsync(ct);
    }
}

// THE RESULT:
//   • updating a shipment loads ONE small aggregate
//   • warehouse and finance no longer contend on the same version token
//   • each transaction touches exactly one consistency boundary
//
// THE TRADE-OFF, STATED: there is now a window where a payment exists and the
// order still reads Unpaid. That is eventual consistency, and it must be
// acceptable to the business — which it almost always is, because the
// alternative is contention that limits throughput and a workflow the model
// was pretending was instantaneous.
6 (hard): Decide the architecture for three different services and justify each.
Solution 
// ── SERVICE A: an internal admin CRUD tool ───────────────────────────────
//   ~15 tables, forms over data, one entry point, two developers, no rules
//   beyond field validation.
//
// DECISION: two projects. Api + a thin services layer, EF Core injected
// directly. No repository, no mediator, no domain project.
//
//   Api/            endpoints, DTOs
//   Services/       ProductService, UserService — EF injected
//
// JUSTIFICATION: there are no invariants to protect and one caller, so every
// layer would be pure mapping. Clean Architecture here means seven files to
// add a column. This is the CORRECT engineering choice, not a shortcut.

// ── SERVICE B: order management ──────────────────────────────────────────
//   real rules (credit limits, stock reservation, cancellation windows),
//   entry points: HTTP + queue consumer + nightly job, team of six, long-lived.
//
// DECISION: full Clean Architecture with level-1 CQRS.
//
//   Domain/          Order, Payment aggregates with invariants
//   Application/     command and query handlers, interfaces
//   Infrastructure/  EF, repositories, external gateways
//   Api/             endpoints
//
// JUSTIFICATION: THREE ENTRY POINTS is the deciding factor. A rule enforced
// in the controller is bypassed by the queue consumer, so invariants must
// live on entities. Rules are complex enough to deserve isolated tests, and a
// six-person rotating team benefits from enforced boundaries. Reads and
// writes genuinely differ — a list page needs four columns, not aggregates.
// I would use vertical slices inside Application so a feature lives in one
// folder.

// ── SERVICE C: an analytics read API ─────────────────────────────────────
//   heavy read traffic, no writes, complex aggregation queries.
//
// DECISION: queries only — no domain model, no repositories, hand-written SQL
// or Dapper behind query handlers.
//
//   Api/         endpoints
//   Queries/     one handler per query, returning DTOs
//
// JUSTIFICATION: there is nothing to protect, so a domain model would be
// ceremony around a SELECT. EF's abstraction actively hurts here — complex
// analytical SQL is clearer written directly, and the ORM's translation is a
// liability at this shape of query. This is CQRS with the command side simply
// absent.

// ── THE DECIDING QUESTIONS, in order ─────────────────────────────────────
//   1. Are there invariants that must hold regardless of caller?
//        no  → no domain model
//   2. Is there more than one entry point?
//        no  → layering buys much less
//   3. Do read and write shapes genuinely differ?
//        yes → CQRS level 1, which is nearly free
//   4. Is the team large or rotating?
//        yes → enforced boundaries pay for themselves
//
// The one investment that pays at EVERY size: keep business logic callable
// with no HttpContext. That single boundary makes any later restructuring
// mechanical rather than a rewrite — and it costs nothing to maintain.

🎯 Key Takeaways

  • The dependency rule is the whole idea: dependencies point inward, and project references make violations compiler errors.
  • Keep the domain free of framework types — configure persistence in infrastructure so the ORM never reaches the entities.
  • CQRS has three very different scales; level one, separate models over one database, delivers most of the value for almost no cost.
  • A repository over EF Core earns its place only for aggregate access control or dependency inversion — not for a hypothetical ORM swap.
  • Reads should project to DTOs with AsNoTracking, never load aggregates built for enforcing writes.
  • Reference other aggregates by id and modify one aggregate per transaction; large aggregates cause loading cost and false concurrency conflicts.
  • Domain events published after commit can be lost and published before commit can be wrong — the outbox is the reliable option, at the cost of at-least-once delivery.
  • Pipeline behaviours handle cross-cutting concerns once, but a mediator's runtime dispatch costs traceability — adopt it when behaviours earn it.
  • Enforce architecture mechanically with NetArchTest, or it erodes one pragmatic exception at a time.
  • Match structure to actual complexity: for CRUD with one entry point, fewer layers is the correct answer — but always keep business logic callable without HttpContext.
