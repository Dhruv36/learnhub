API Versioning Building APIs

What you'll master: which changes actually break clients and which only look like they do, the four versioning strategies and their real trade-offs, wiring Asp.Versioning in ASP.NET Core, running versions side by side without duplicating a codebase, and retiring a version without breaking the consumers who never read your changelog. Prerequisites: REST API Design and Routing.

Part 1 — What Actually Breaks a Client

// Versioning decisions start here, because most teams version too eagerly and
// then maintain parallel code paths they never needed.

// ── BREAKING ──────────────────────────────────────────────────────────────
//   removing a response field                a client reads it
//   renaming a field                         removal + addition
//   changing a field's TYPE                  "42" vs 42 breaks deserializers
//   changing a status code                   clients branch on it
//   making an optional request field required
//   tightening validation                    previously-accepted input now 400s
//   changing INTEGER enum values             inserting a member shifts the rest
//   changing an error body shape             error handling is contract too
//   changing default sort order or pagination size
//                                            silently changes what page 1 IS

// ── ADDITIVE (safe for tolerant readers) ─────────────────────────────────
//   adding an OPTIONAL response field
//   adding a new endpoint
//   adding an OPTIONAL request parameter
//   relaxing validation
//   adding a new enum member                 ← but see below

// THE TOLERANT READER CONTRACT is what makes the second list safe, and it must
// be stated up front because it cannot be introduced retroactively:
//   "Clients MUST ignore unknown fields and MUST tolerate new enum members."
// Without it, a client using strict deserialization breaks on an added field,
// and you have no additive changes at all — every change becomes a version.
builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.UnmappedMemberHandling = JsonUnmappedMemberHandling.Skip);

// ADDING AN ENUM MEMBER is the honest edge case. It is additive on the wire,
// but a client with an exhaustive switch may throw on the new value. Document
// it as expected, and prefer returning strings so at least the value is
// legible when it does arrive.

// THE ORDER OF PREFERENCE, and this is the actual lesson:
//   1. make the change ADDITIVE and avoid a version entirely
//   2. if unavoidable, version, run both, and deprecate on a schedule
//   3. never break in place — silence is not consent, it is absence of
//      awareness, and you will discover the dependency during an incident

Part 2 — Four Strategies, Honestly Compared

// 1. URL PATH — /api/v1/orders
//    + immediately visible in logs, metrics, cache keys and bug reports
//    + trivially routable at a proxy or gateway
//    + a developer can paste a URL and it means one thing forever
//    − arguably "unRESTful": the same resource has two URIs
//    − version leaks into every hyperlink you generate
//    → THE PRAGMATIC DEFAULT. The operational visibility is worth more in
//      practice than the URI purity argument costs.

// 2. QUERY STRING — /api/orders?api-version=2.0
//    + the resource keeps one path
//    + easy to default (absent = v1)
//    − easy to lose: proxies strip query strings, caches key on them
//      inconsistently, and it is invisible in most access-log formats
//    → acceptable, rarely the best choice

// 3. HEADER — X-Api-Version: 2.0
//    + URLs stay clean; the version is metadata, which is arguably correct
//    − INVISIBLE. Cannot be pasted into a browser, easily lost by proxies,
//      and requires Vary: X-Api-Version or caches serve the wrong version
//    − makes debugging materially harder — "which version did this call use"
//      needs header capture, which most log pipelines do not do by default
//    → correct in theory, costly in operations

// 4. MEDIA TYPE — Accept: application/vnd.company.v2+json
//    + the most theoretically correct: version the REPRESENTATION, not the
//      resource, which is exactly what content negotiation is for
//    − highest friction. Every client must set Accept precisely; a typo
//      yields 406 rather than a helpful error, and browsers cannot do it
//    → right for hypermedia-heavy APIs and standards-driven organisations;
//      overkill for most services

// MY RECOMMENDATION, stated plainly: URL path versioning for public APIs. The
// deciding argument is not aesthetics — it is that during an incident at 3am
// you can tell which version a failing request used by reading one log line,
// and you can route or block a version at the edge without touching the app.

// WHAT TO VERSION — the unit matters as much as the mechanism:
//   WHOLE API      one version for everything. Simple to reason about,
//                  forces unrelated consumers to migrate together.
//   PER RESOURCE   /api/orders/v2 while /api/customers stays v1. Flexible,
//                  and quickly becomes a compatibility matrix nobody can hold
//                  in their head.
// Start with whole-API. Per-resource is a decision to make when you have
// concrete evidence that the coupling is hurting, not in advance.

Part 3 — Wiring Asp.Versioning

// dotnet add package Asp.Versioning.Mvc.ApiExplorer

builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;   // see the caution
    options.ReportApiVersions = true;                     // response headers

    options.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),
        new HeaderApiVersionReader("X-Api-Version"),
        new QueryStringApiVersionReader("api-version"));
})
.AddApiExplorer(options =>
{
    options.GroupNameFormat = "'v'VVV";          // v1, v1.1, v2
    options.SubstituteApiVersionInUrl = true;     // for OpenAPI docs
});

// ReportApiVersions adds headers that make the API self-describing:
//   api-supported-versions: 1.0, 2.0
//   api-deprecated-versions: 1.0
// A client can discover it is on a deprecated version WITHOUT reading docs —
// which matters because most consumers never read docs after integration.

// AssumeDefaultVersionWhenUnspecified — CONSIDER TURNING THIS OFF:
//   ON:  an unversioned request silently gets v1. Convenient for existing
//        clients, but it means clients never state intent, so when v1 is
//        finally retired every one of them breaks at once with no warning.
//   OFF: an unversioned request is rejected, forcing explicitness from day
//        one. Painful at launch, far safer at retirement.
// If launching a NEW API, turn it off. If retrofitting versioning onto an
// existing one, leave it on and migrate clients deliberately.

// CONTROLLERS:
[ApiController]
[ApiVersion("1.0")]
[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/[controller]")]
public sealed class OrdersController : ControllerBase
{
    [HttpGet("{id:int}")]
    [MapToApiVersion("1.0")]
    public async Task<ActionResult<OrderV1>> GetV1(int id) => ...;

    [HttpGet("{id:int}")]
    [MapToApiVersion("2.0")]
    public async Task<ActionResult<OrderV2>> GetV2(int id) => ...;
}

// DEPRECATION as metadata, not just documentation:
[ApiVersion("1.0", Deprecated = true)]
[ApiVersion("2.0")]
public sealed class OrdersController : ControllerBase { }

// MINIMAL APIS — version sets on groups:
var versionSet = app.NewApiVersionSet()
    .HasApiVersion(new ApiVersion(1, 0))
    .HasApiVersion(new ApiVersion(2, 0))
    .ReportApiVersions()
    .Build();

var orders = app.MapGroup("/api/v{version:apiVersion}/orders")
    .WithApiVersionSet(versionSet);

orders.MapGet("/{id:int}", GetOrderV1).MapToApiVersion(1.0);
orders.MapGet("/{id:int}", GetOrderV2).MapToApiVersion(2.0);
Key insight: versioning the URL is cheap; versioning the code is where the cost lives. Duplicating a controller per version works for two versions and collapses at four — the copies drift, a bug fixed in v2 stays broken in v1, and nobody can tell which differences are intentional. The durable pattern is one implementation with versioned edges: shared domain and application services, with per-version DTOs and mapping. Then a new version is a new mapping layer, not a new copy of the business logic, and a bug fix lands once.

Part 4 — Structuring Code for Multiple Versions

// ✗ THE DUPLICATION TRAP — works for v1/v2, unmanageable by v4:
//   Controllers/V1/OrdersController.cs      500 lines
//   Controllers/V2/OrdersController.cs      510 lines, 90% identical
//   Controllers/V3/OrdersController.cs      505 lines, drifting
// Every bug fix must be applied three times, and reviewers cannot tell which
// differences are deliberate.

// ✓ SHARED CORE, VERSIONED EDGES:
//
//   Domain/            Order.cs                    ← one, unversioned
//   Application/       OrderService.cs             ← one, unversioned
//   Api/V1/            OrderV1Response.cs, mapping
//   Api/V2/            OrderV2Response.cs, mapping
//   Api/               OrdersController.cs         ← thin, both versions

[ApiVersion("1.0")]
[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/orders")]
public sealed class OrdersController(OrderService orders) : ControllerBase
{
    [HttpGet("{id:int}"), MapToApiVersion("1.0")]
    public async Task<ActionResult<OrderV1Response>> GetV1(int id, CancellationToken ct)
        => await orders.FindAsync(id, ct) is { } o
            ? OrderV1Response.From(o) : NotFound();

    [HttpGet("{id:int}"), MapToApiVersion("2.0")]
    public async Task<ActionResult<OrderV2Response>> GetV2(int id, CancellationToken ct)
        => await orders.FindAsync(id, ct) is { } o
            ? OrderV2Response.From(o) : NotFound();
}

// The version difference lives ENTIRELY in the response mapping:
public sealed record OrderV1Response(int Id, string Customer, decimal Total)
{
    // v1 flattened the customer to a name string.
    public static OrderV1Response From(Order o) =>
        new(o.Id, o.Customer.Name, o.Total.Amount);
}

public sealed record OrderV2Response(
    int Id, CustomerRef Customer, Money Total, DateTimeOffset CreatedAt)
{
    // v2 exposes a customer object, structured money, and a new field.
    public static OrderV2Response From(Order o) =>
        new(o.Id,
            new CustomerRef(o.Customer.Id, o.Customer.Name),
            new Money(o.Total.Amount, o.Total.Currency),
            o.CreatedAt);
}

// WHEN THE DOMAIN ITSELF CHANGES — the genuinely hard case. If v2 adds a
// required concept v1 cannot express (multi-currency where v1 assumed one),
// the mapping needs a decision, not a projection:
public static OrderV1Response From(Order o)
{
    // v1 clients cannot express currency. Options, in order of honesty:
    //   a) convert to the v1 assumed currency and document it
    //   b) return 409 for orders v1 cannot faithfully represent
    //   c) silently return the raw amount        ← WRONG: v1 clients would
    //      treat ¥1000 as $1000, which is a financial bug, not a formatting one
    if (o.Total.Currency != "USD")
        throw new UnrepresentableInVersionException(
            "This order uses a currency the v1 API cannot represent.");

    return new OrderV1Response(o.Id, o.Customer.Name, o.Total.Amount);
}
// Choosing (c) by default is how versioning causes data corruption downstream.
// If old clients cannot represent new data, say so loudly rather than lying
// quietly.

Part 5 — OpenAPI, Discovery, and Communicating Deprecation

// One OpenAPI document PER VERSION, so a consumer sees exactly their surface:
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();
builder.Services.ConfigureOptions<ConfigureSwaggerOptions>();

public sealed class ConfigureSwaggerOptions(IApiVersionDescriptionProvider provider)
    : IConfigureOptions<SwaggerGenOptions>
{
    public void Configure(SwaggerGenOptions options)
    {
        foreach (var description in provider.ApiVersionDescriptions)
        {
            options.SwaggerDoc(description.GroupName, new OpenApiInfo
            {
                Title = "Orders API",
                Version = description.ApiVersion.ToString(),
                Description = description.IsDeprecated
                    ? "⚠ This version is deprecated and will be removed on 2027-01-31."
                    : null
            });
        }
    }
}

app.UseSwaggerUI(options =>
{
    var provider = app.Services.GetRequiredService<IApiVersionDescriptionProvider>();
    foreach (var description in provider.ApiVersionDescriptions)
        options.SwaggerEndpoint(
            $"/swagger/{description.GroupName}/swagger.json",
            description.GroupName.ToUpperInvariant());
});

// STANDARD DEPRECATION HEADERS — machine-readable, so tooling can warn:
app.Use(async (context, next) =>
{
    await next();

    var version = context.GetRequestedApiVersion();
    if (version?.ToString() == "1.0")
    {
        // RFC 8594 Sunset: when the resource stops working.
        context.Response.Headers["Sunset"] = "Sat, 31 Jan 2027 23:59:59 GMT";
        context.Response.Headers["Deprecation"] = "true";
        context.Response.Headers["Link"] =
            "<https://docs.example.com/migration/v2>; rel=\"deprecation\"";
    }
});

// MEASURE BEFORE YOU RETIRE — this is the step teams skip and regret:
app.Use(async (context, next) =>
{
    var version = context.GetRequestedApiVersion()?.ToString() ?? "unspecified";
    var clientId = context.User.FindFirst("client_id")?.Value ?? "anonymous";

    // Low-cardinality labels only — never the raw path.
    metrics.Add(1, new("version", version), new("client", clientId));

    await next();
});
// Now "who is still on v1" is a query, not a guess. Retiring a version
// without this data means finding out who depended on it from the incident
// channel.

Part 6 — Retiring a Version

// A version's lifecycle has four stages, and skipping any of them is how
// retirement becomes an outage.

// STAGE 1 — ANNOUNCE (T minus 6-12 months for a public API)
//   • mark it Deprecated in code, so headers and OpenAPI say so automatically
//   • Sunset and Deprecation headers on every response
//   • direct outreach to the top consumers BY NAME, using your usage metrics.
//     A changelog entry is not outreach; nobody reads changelogs after
//     integration.

// STAGE 2 — MEASURE AND CHASE
//   • track usage per client, weekly
//   • the distribution is always long-tailed: a handful of clients are 95% of
//     traffic and migrate quickly, then a long tail of forgotten integrations
//   • the tail is the risk. Those are often the ones with no maintainer, and
//     they are exactly who will escalate loudest when the version disappears.

// STAGE 3 — BROWNOUTS (the step that actually works)
//   Deliberately disable v1 for short, announced windows before retirement:
//     30 minutes, then 2 hours, then a day.
if (version == "1.0" && brownout.IsActive)
    return StatusCode(StatusCodes.Status410Gone, new ProblemDetails
    {
        Title = "API v1 is retiring on 2027-01-31.",
        Detail = "This is a scheduled brownout. Migrate to v2.",
        Extensions = { ["migrationGuide"] = "https://docs.example.com/v2" }
    });
//   WHY BROWNOUTS WORK: they convert a future problem into a present one,
//   during business hours, when you are watching. A client that breaks during
//   an announced 30-minute brownout discovers its dependency safely. The same
//   client discovering it at retirement discovers it during an outage.

// STAGE 4 — RETIRE
//   • return 410 Gone, NOT 404. 410 means "this existed and is deliberately
//     gone", which tells a developer they have a migration problem rather
//     than a typo. 404 sends them debugging their URL.
//   • keep the 410 with a migration link for at least a year — the response
//     is the last piece of documentation a stranded client will ever read.

// WHAT NOT TO DO:
//   ✗ silently route v1 to v2 — a "compatible" mapping is never quite
//     compatible, and clients get subtly wrong data instead of a clear error
//   ✗ retire on a Friday, or before a holiday
//   ✗ retire without brownouts, then discover the long tail during an incident
//   ✗ keep a version alive forever "just in case" — an unretired version is
//     permanent tax on every future change, and it is why some APIs cannot
//     evolve at all

Interview Questions

Beginner: What kinds of API change are breaking?

Removing or renaming a response field, changing a field's type, changing a status code, making an optional request field required, tightening validation so previously-accepted input is rejected, and changing integer enum values. Changing an error response's shape counts too, since clients branch on it. Safe additive changes are adding an optional response field, adding a new endpoint, adding an optional request parameter, and relaxing validation — but those are only safe if clients ignore unknown fields, which is why the tolerant-reader expectation has to be documented from the start rather than assumed.

Beginner: What are the main ways to version an API?

URL path (/api/v2/orders), query string (?api-version=2.0), a custom header (X-Api-Version: 2.0), and media type negotiation (Accept: application/vnd.company.v2+json). URL path is the most visible — it appears in logs, metrics and cache keys, and can be routed at a gateway — which makes it the common pragmatic choice despite the argument that the same resource then has two URIs. Media-type versioning is the most theoretically correct since it versions the representation rather than the resource, but it has the highest client friction. Header versioning keeps URLs clean at the cost of being invisible when debugging.

Mid: How do you avoid duplicating an entire codebase per version?

By versioning only the edges. The domain model and application services stay unversioned and shared, and each version gets its own request and response DTOs plus mapping code. A controller can host both versions with [MapToApiVersion] on individual actions, each calling the same service and projecting to a different DTO. That way a bug fix in the business logic lands once for every version, and the diff between versions is a small, readable mapping file rather than two 500-line controllers whose intentional differences are indistinguishable from drift. The case that still needs judgement is when the domain itself changes in a way an old version cannot represent — then the mapping has to make an explicit decision, such as converting to the old assumption or refusing with an error, rather than silently returning data the old client will misinterpret.

Mid: Why return 410 Gone rather than 404 for a retired version?

Because the two say different things to the developer debugging the failure. 404 means "no such resource", which sends someone to check their URL for typos, verify their routing, and generally assume they made a mistake. 410 Gone means "this existed and has been deliberately removed", which immediately tells them they have a migration problem rather than a spelling problem. Combined with a problem-details body containing a link to the migration guide, the response itself becomes the last and most effective piece of documentation a stranded client will read — which matters because the clients still calling a retired version are by definition the ones who did not read anything else.

Senior: You need to change a field's type from string to object. Walk through doing it without breaking anyone.

Changing a type in place is breaking, so the goal is to avoid the break rather than manage it. My first move is the expand-and-contract pattern: add the new field alongside the old one rather than replacing it. If customer is currently a name string and needs to become an object, I add customerRef as the object, populate both from the same source, and mark the old field deprecated in documentation and OpenAPI. Both are additive, so no version is required and no client breaks. Then I measure — usage metrics on which clients still read the old field, which requires either response-field instrumentation or, more practically, tracking client versions and asking. Once usage is near zero I remove the old field, and only that removal needs a new API version. This sequencing means the disruptive step happens once, late, with data supporting it, rather than immediately on faith. If the change genuinely cannot be expressed additively — say the semantics of an existing field change rather than its shape — then I version, keeping the domain shared and the difference confined to the response mapping, and I would be careful that the old version's mapping fails loudly when it encounters data it cannot faithfully represent rather than emitting a plausible-looking wrong value. Throughout, I would treat the transition period as the normal state rather than an exception: both fields coexisting for six months is not technical debt, it is the mechanism, and trying to shorten it is what causes breakage.

Senior: Design the versioning and deprecation policy for a public API with hundreds of external consumers.

I would use URL-path versioning at whole-API granularity, because at that consumer count the operational properties dominate the design purity: the version is visible in every log line and metric, routable at the gateway, and unambiguous in a support ticket. Per-resource versioning would give more flexibility but produces a compatibility matrix that neither my team nor the consumers can reason about, so I would start whole-API and only split if there is concrete evidence of harm. Structurally the domain stays shared with versioned DTOs and mapping, so a bug fix lands once. The policy I would publish commits to specifics rather than intentions: at least two versions supported concurrently, a minimum twelve-month deprecation window for a public API, and a stated tolerant-reader requirement so additive changes stay non-breaking. Instrumentation is the part I would build first, before it is needed — requests per version per client identity — because every retirement decision depends on it and retrofitting it during a migration is too late. Communication has three layers: machine-readable Sunset and Deprecation headers so tooling can surface it automatically, deprecation notices in the OpenAPI description so it appears in generated clients and documentation portals, and direct outreach by name to the top consumers using the usage data. The step I would insist on is scheduled brownouts before retirement — thirty minutes, then two hours, then a full day, all announced — because they convert a future outage into a controlled event during business hours, and they are the only mechanism I have found that reliably reaches the long tail of unmaintained integrations. At retirement the endpoint returns 410 Gone with a migration link, kept in place for at least a year. The failure mode I am designing against is not the large well-staffed consumer who migrates on announcement; it is the forgotten integration with no maintainer, and everything above is calibrated to surface that dependency safely rather than during an incident.

5 (hard): v1 assumed a single currency; v2 supports many. Design the v1 mapping and justify it.
Solution 
// THE PROBLEM: v1's contract is `decimal total` with an IMPLICIT currency —
// every v1 client hardcodes the assumption that it is USD. v2 orders may be
// in any currency. Whatever v1 returns will be interpreted as USD.

public sealed record OrderV1Response(int Id, string Customer, decimal Total)
{
    private const string V1AssumedCurrency = "USD";

    public static Result<OrderV1Response> From(Order order)
    {
        if (order.Total.Currency == V1AssumedCurrency)
            return new OrderV1Response(order.Id, order.Customer.Name,
                                       order.Total.Amount);

        // The order CANNOT be represented in v1's contract. Refuse.
        return Result.Fail(OrderError.UnrepresentableInVersion);
    }
}

[HttpGet("{id:int}"), MapToApiVersion("1.0")]
public async Task<ActionResult<OrderV1Response>> GetV1(int id, CancellationToken ct)
{
    var order = await orders.FindAsync(id, ct);
    if (order is null) return NotFound();

    var mapped = OrderV1Response.From(order);
    if (mapped.IsFailed)
        return StatusCode(StatusCodes.Status409Conflict, new ProblemDetails
        {
            Title = "This order cannot be represented in API v1.",
            Detail = "The order uses a currency v1 does not support. "
                   + "Upgrade to v2 to read multi-currency orders.",
            Extensions = { ["migrationGuide"] = "https://docs.example.com/v2" }
        });

    return mapped.Value;
}

// WHY REFUSING BEATS THE ALTERNATIVES:
//
//   ✗ Return the raw amount. A ¥150,000 order becomes "150000" and the v1
//     client displays $150,000 — or worse, CHARGES it. This is a financial
//     bug caused by a formatting decision, and it is silent.
//
//   ✗ Convert to USD at the current rate. Now the API returns a number that
//     does not match the order, changes between calls as rates move, and
//     reconciliation against the real total fails. Plausible-looking wrong
//     data is worse than an error because nobody investigates it.
//
//   ✓ Refuse with 409 and an explanatory body. The v1 client gets a clear,
//     actionable failure. It surfaces during integration testing rather than
//     in a finance reconciliation three months later.
//
// THE PRINCIPLE: when an old version cannot faithfully represent new data,
// fail loudly. Silence is only acceptable when the mapping is genuinely
// lossless — and "close enough" is not lossless where money is concerned.
//
// Practically I would also cap the blast radius: most v1 clients only ever
// see USD orders, so this 409 is rare and concentrated exactly on the
// consumers who need to migrate.
6 (hard): Write the retirement plan for v1, twelve months out, with hundreds of unknown consumers.
Solution 
// ── MONTH 0: INSTRUMENT FIRST ────────────────────────────────────────────
// Everything below depends on knowing WHO is calling. Build this before
// announcing anything — retrofitting it mid-migration is too late.
app.Use(async (context, next) =>
{
    var version = context.GetRequestedApiVersion()?.ToString() ?? "unspecified";
    var client  = context.User.FindFirst("client_id")?.Value ?? "anonymous";
    metrics.Add(1, new("api.version", version), new("client.id", client));
    await next();
});
// "unspecified" is its own bucket and usually the scariest one: those clients
// never stated a version, so they will break on ANY default change.

// ── MONTH 1: ANNOUNCE ────────────────────────────────────────────────────
[ApiVersion("1.0", Deprecated = true)]
//   • Sunset + Deprecation + Link headers on every v1 response
//   • deprecation banner in the OpenAPI description and the docs portal
//   • email the top 20 consumers BY NAME using the metrics — they are
//     typically 95% of traffic and will migrate quickly
//   • a changelog entry is NOT outreach; assume nobody reads it

// ── MONTHS 2-8: CHASE THE TAIL ───────────────────────────────────────────
//   Weekly usage review. The distribution is always long-tailed: the big
//   consumers go early, then progress stalls with a residue of small,
//   often unmaintained integrations. That tail is the entire risk.
//   • quarterly re-contact
//   • offer migration help directly — for a handful of clients it is cheaper
//     to write their patch than to manage the escalation

// ── MONTHS 9-11: BROWNOUTS ───────────────────────────────────────────────
//   Announced, escalating, ALWAYS during business hours mid-week:
//     month  9: 30 minutes
//     month 10: 2 hours
//     month 11: 24 hours
if (version == "1.0" && brownoutWindow.IsActive)
    return StatusCode(StatusCodes.Status410Gone, new ProblemDetails
    {
        Title  = "Scheduled brownout — API v1 retires 2027-01-31.",
        Detail = "This is a planned rehearsal. Migrate to v2.",
        Extensions = { ["migrationGuide"] = "https://docs.example.com/v2" }
    });
// This is the highest-value step in the plan. It converts a future outage
// into a controlled event while you are watching, and it reaches the clients
// that ignored every email — because a broken integration generates a ticket
// where an email generates nothing.

// ── MONTH 12: RETIRE ─────────────────────────────────────────────────────
//   • NOT on a Friday, not near a holiday, not during a customer peak
//   • 410 Gone with the migration link, retained for 12+ months — the
//     response body is the last documentation a stranded client will read
//   • keep the v1 CODE for two weeks behind a feature flag so rollback is a
//     config change rather than a deploy
//   • staff the support channel for the first 48 hours

// ── WHAT MAKES THIS WORK ─────────────────────────────────────────────────
// The plan is designed around the forgotten integration with no maintainer,
// not the well-staffed consumer who migrates on announcement. Every mechanism
// — headers, metrics, targeted outreach, brownouts — exists to surface that
// dependency safely and early. A plan calibrated for attentive consumers
// works fine until the day it doesn't, and then it fails as an incident.

🎯 Key Takeaways

  • Version only for genuine breaks — removals, renames, type and status-code changes — and prefer additive changes that need no version at all.
  • The tolerant-reader contract must be documented at launch; without it even additive changes break strict clients.
  • URL-path versioning wins on operations: visible in logs, metrics and cache keys, and routable at the gateway.
  • Version the edges, not the codebase — shared domain and services with per-version DTOs means a bug fix lands once.
  • AssumeDefaultVersionWhenUnspecified lets clients avoid stating intent, so they all break together at retirement.
  • ReportApiVersions plus Sunset/Deprecation headers make the API self-describing to tooling.
  • Instrument usage per version per client before announcing anything — retirement decisions depend on that data.
  • When an old version cannot faithfully represent new data, fail loudly; plausible-looking wrong data is worse than an error.
  • Scheduled brownouts are the only mechanism that reliably reaches unmaintained integrations before retirement day.
  • Retire with 410 Gone and a migration link, not 404 — one says "migrate", the other says "check your typo".
